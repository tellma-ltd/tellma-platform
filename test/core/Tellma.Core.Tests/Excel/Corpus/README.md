# Import corpus

The workbooks the import tests read as each spreadsheet application saves them.

## Why the corpus is generated

A corpus of files saved by the applications themselves would pin exactly what each one writes,
but none of them can be driven from a test run on Windows and Linux alike, and checked-in binary
files cannot be reviewed. The corpus is therefore generated by `SyntheticWorkbook`, which writes
each producer's package the way that application lays out its parts:

| Producer       | What its package carries                                                                                   |
| -------------- | ---------------------------------------------------------------------------------------------------------- |
| `Excel`        | A shared-string table, a dimension, sheet views, a markup-compatibility namespace and an extension list.   |
| `LibreOffice`  | A shared-string table, a dimension, a file version, sheet properties and column widths.                    |
| `GoogleSheets` | A shared-string table, sheet properties, and no dimension, so the reader counts rows itself.               |
| `Strict`       | Every namespace and relationship type of the strict dialect.                                               |

Each test may also replace or add a part (`Parts`) or leave one out (`Omitted`), which is how the
hostile packages of `WorkbookReaderTests` are made.

## Keeping it honest

The builder writes nothing a real producer would not, except where a test asks. When a file saved
by one of the applications is found that the import reads differently from its synthetic twin,
the difference belongs in `SyntheticWorkbook` first, as the producer's habit, and then in a test
of `CorpusTests`.
