# Tellma.Testing.Support

Test doubles shared across the email, webhook and host suites, and the SQL Server fixture every
integration suite shares. Not a test project — it carries no test SDK,
so `dotnet test` never tries to run it — and not a shipped package either: it is referenced only by
projects under `test/`.

The line between this project and the published `Tellma.Core.Testing` is what a **consumer** needs
versus what **our own suites** need. `Tellma.Core.Testing` ships the contract-level doubles any
consumer of `Tellma.Core.Abstractions` benefits from — the capturing email sender, the delivery-event
builders, and the sender conformance suite every transport must pass. This project holds the wire
plumbing those suites happen to need to drive a specific transport, which no consumer would want.

| Folder | Contents |
|---|---|
| `Http/` | [ScriptedHttpMessageHandler](Http/ScriptedHttpMessageHandler.cs) — answers from a script, synchronously or asynchronously, and records every request: bodies and request headers, plus content headers and a per-exchange snapshot on `Exchanges`. An asynchronous responder is what lets a suite hold a response open while it arranges something else — a second caller reaching a single-flight gate, a clock advanced past a timeout — rather than racing a real one. One handler drives both HTTP-based transports: the SendGrid client takes an `HttpClient` directly, and the Azure pipeline accepts one through its transport. [SingleClientHttpClientFactory](Http/SingleClientHttpClientFactory.cs) — hands that one client to an adapter that resolves `IHttpClientFactory`, whatever name it asks for. |
| `Logging/` | [StateCapturingLoggerProvider](Logging/StateCapturingLoggerProvider.cs) — a logger provider enabled at every level that keeps, for each event and scope, every text its structured state carries alongside the rendered message: the key and value of each pair and dictionary entry, each element of a nested sequence (such as a header's values), and each readable public property of any other object, as a destructuring sink writes it; each object once, to a bounded depth. So a suite can assert a secret reaches no log in any form a structured sink would serialise. Its walk is pinned by `Tellma.Core.Testing.Tests`. |
| `Observability/` | [AlertQueries](Observability/AlertQueries.cs) — reads the checked-in `.kql` alert queries under `infra/monitoring/` (comment lines dropped) and resolves every metric name, dimension key and compared value against what a suite says its code emits, and lists the instruments no query covers. The email and host suites each link their folder's queries into their output and run the same check. |
| `Options/` | [StaticOptionsMonitor](Options/StaticOptionsMonitor.cs) — an `IOptionsMonitor<T>` over a fixed instance, so a sender that reads options per batch can be driven without a configuration stack. |
| `Sql/` | [SqlServerFixture](Sql/SqlServerFixture.cs) — one SQL Server for a suite, registered as an assembly or collection fixture: a Testcontainers container by default (`TELLMA_TEST_SQL_IMAGE` overrides the image), or the server `TELLMA_TEST_SQL` names. It hands out uniquely named databases (`NewDatabaseName`, `ReserveDatabase` for a host that creates its own, `CreateDatabaseAsync` in a stated collation), drops them at the end on an existing server, and runs batches and scalar queries. `OwnsContainer` tells a suite whether the server is its own container, for a test that must never run on a server other suites share. Referencing it brings Testcontainers and xunit's extensibility core along. [SqlDatabaseCreation](Sql/SqlDatabaseCreation.cs) — the one way a fixture or test runs `CREATE DATABASE`: in a stated collation, under a five-minute command bound (the server alone may wait about 25 seconds for the `model` lock), and retried by [CreateDatabaseRetry](Sql/CreateDatabaseRetry.cs) while it fails with SQL error 1807, "Could not obtain exclusive lock on database 'model'", which parallel creations queue on. Only 1807 (with the 1802 that follows it) is retried, at most six runs with jittered doubling waits of about 1 to 10 seconds; every other error, a command timeout included, surfaces at once. Each retry is written to the running test's output, or as a diagnostic message outside a test. Its `PrepareAsync` runs a fresh database's preparation statements (`ALTER DATABASE` options, a role) under the same bound, never retried. Its policy and its behaviour under a real held `model` lock are pinned by `Tellma.Core.Testing.Tests`. [SqlDatabaseDrop](Sql/SqlDatabaseDrop.cs) — the drops at the end of a suite on an existing server, used by `SqlServerFixture` and the identity E2E fixture: one `master` connection opened (a failed open names every database as not tried), the process's pooled connections closed next (on LocalDB, rolling back the sessions left in a database cost its drop about 3 s, so a suite's cleanup ran for minutes), then each database set to single-user with its sessions rolled back and dropped, under the same five-minute bound, and rerun on `CreateDatabaseRetry`'s waits while the database is held for a moment (SQL errors 3702, 5061, 5064, 924, 952 or a 1205 deadlock), each rerun closing the pooled connections again. A database that cannot be dropped does not stop the rest; once the connection is lost the rest are left untried; and every database left behind is named in one exception at the end, each failure an inner exception, so a cleanup that leaves databases behind fails the run. |
| `Tenancy/` | [StubSandboxContext](Tenancy/StubSandboxContext.cs) — a settable sandbox flag, for driving the routing matrix. |
