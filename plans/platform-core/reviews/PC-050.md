# PC-050: Connect prologue, caches, guarded runner and the Order-100 initializer

## Implementer notes

### What was built

The user connection of spec 0014 §6.2-§6.3, §7.1-§7.6, §7.8 and §13, with the runner cases of spec 0013 §2.10, §5.7 and §9.3.

- **Contracts** (`Tellma.Core.Abstractions/Access`):
  - `ConnectPremises`, a closed set: `ForSubject`, `ForUser` and `ForSystem`, plus the `Cold` and `For` factories.
  - The records `ConnectExpectations`, `ConnectResult`, `ConnectedUser` and `UserProfile`.
  - The interfaces `IUserConnector` and `IGuardedBatchRunner`.
  - New entries in `ReservedSqlNames` and `AccessTelemetryNames`.
  - `RequestContextInputs.SuppressActivityStamp`. The ASP.NET Core `RequestInputs.Of` sets it from `NoActivityStampMetadata` or a background request.
- **`ConnectPrologue`** (Core/Access) holds the three §7.3 texts:
  - Each text is built once, so every batch of a variant carries the same text and binds the same parameters with the same SQL types.
  - The settings cold load (§5.7) is absorbed under `IF @tm_SettingsStale = 1 OR @tm_LoadSettings = 1`.
  - The reader reads set 0, set 1 (the prelude), and then sets 2 and 3 and the settings sets only when the connect row announces them.
  - It reports the guard verdict, the tenant tags, and the caller's user tags.
- **Caches**:
  - `ConnectCache`: keyed by tenant and subject, compared byte for byte. It has its own bounded MemoryCache and single-flights cold connects. If a starter's connect is cancelled, a joiner runs a connect of its own.
  - `PermissionsCache` and `ProfileCache`: versioned-cache kinds keyed by `TenantUserCacheKey`.
- **`UserConnector`** (scoped):
  - Implements `IUserConnector` and the internal `IScopeConnection` the runner drives.
  - Supports connect by subject, by id (`ConnectAsUserAsync`) and as the system. Builds the premises for the next batch, applies prologue results, runs the cold re-connect, and drops a deactivated caller's entries.
  - Activity-stamp throttling uses an in-process memo against `ActivityStampInterval`. Frozen tenants and background requests never stamp; Frozen tenants never flip.
  - Metering and `ConnectRejected` logging happen in `Apply`.
- **`GuardedBatchRunner`** (scoped):
  - Each call composes, executes and applies.
  - It recomposes once after any one of: a failed guard, a `50412` (after a cold re-connect), or an executor `StaleContextException`.
  - A second failure is a `StaleContextException`: the result is counted as `guard_thrash`, exhaustion is metered, and `GuardThrash` (3102) is logged.
  - A `50401` drops the caller and throws `TenantNotFoundException`.
  - When a round trip brings newer settings, the initializers after Order 100 run again.
- **`ConnectInitializer`** (Order 100):
  - A system scope connects as the system and binds `UserId = 1`.
  - A user or service-account scope connects by id when the context carries one (background), else by subject.
  - An anonymous caller gets `TenantNotFoundException`.
  - `ConnectedUserPreferences` implements `IUserLocalePreferences` for the Order-200 negotiation.
- **DataBatch and DataExecutor**:
  - Statements begun with `BeginConnectPrologue` record their writes in `_connectWrites`. Those writes are excluded from `WrittenTables` and included in the new `AuditedWrites`, which the executor's audit now uses.
  - A batch in `Explicit` mode that carries such writes is refused.
  - `AttemptStarted` (set by the executor per attempt) times the prologue round trip.
- **Composition**: `AccessRuntimeComposition` registers the caches, `ConnectorServices`, the connector (one instance behind both interfaces), the runner, the initializer and the preferences.
- **Test hosts**:
  - `CatalogHost`, `TellmaTestHost` and `TenantContextHarness` remove the real `ConnectInitializer`, because they bind users through their own stand-ins.
  - `RequestContextHolderTests` admits the runner as the third context writer.
- **Tests**:
  - Unit, in `Tellma.Core.Tests/Access`:
    - `ConnectPrologueTests`: all 16 presence combinations of the reader, plus the texts and bindings.
    - `GuardedBatchRunnerTests`: fakes over `BatchScript`.
    - `ConnectCacheTests` and `ConnectInitializerTests`.
  - Integration, in `Tellma.Core.IntegrationTests/Access`:
    - `UserConnectionTests` over the new `ConnectDatabase`: two tenant databases in one composition, with no stand-in.
- READMEs are updated (Core, Core.Tests, Core.IntegrationTests). ARCHITECTURE.md needed no change: its tenant-state paragraph already says `ReadOnly` keeps the bookkeeping writes and `Frozen` writes nothing.

### Deviations

1. **`ConnectPremises.For` takes two more parameters.** `expectedSettingsTag` and `reloadPermissions` are needed because the premises carry the settings tag the batch composes under.
2. **`@tm_callerIds` is declared by the user variants.** The caller's id is inserted in the active branch, because `PersistChecks`' user-level bumps and the caller re-check source from it.
3. **The `ForUser` text resolves by id.** It omits the stamp and flip statements entirely rather than binding them to 0, and nulls `@tm_UserId` when no row matches, so that "no user" reads the same as an unknown subject.
4. **New input `RequestContextInputs.SuppressActivityStamp`.** It carries the "background request stamps nothing" rule from the ASP.NET Core front door to the connector.
5. **Connect writes are excluded from `WrittenTables`.** They are included in `AuditedWrites`, and an `Explicit` batch carrying them is refused: the stamp must stay autocommit, outside any caller transaction. The existing frame test was updated to match.
6. **User tags are reported only for the caller.** That means `ForSubject`, or `ForUser` of the scope's own user, so an `EvaluateFor` load of another user never overlays the caller's snapshot.
7. **An unbindable subject is refused without a round trip.** An unbindable subject is empty, longer than 255 characters, or not printable ASCII.
8. **`ConnectAsSystemAsync` makes a round trip only when the settings are missing.** It returns the synthetic system user when the expected settings tag is known. `ConnectAsUserAsync` always makes a round trip. The system profile is synthetic: `AccessSeeds.SystemUserName` and `SeededAt`.
9. **`Apply` never writes the request context.** The initializer returns the context with `UserId`, and only the runner's refresh writes through the holder. That makes `GuardedBatchRunner` a third holder writer, admitted in `RequestContextHolderTests`.
10. **The runner's settings refresh re-runs every initializer with `Order > 100`,** not just the locale negotiation, and only when the context's settings tag differs from the round trip's.
11. **A cached subject that now resolves to a different user than the one the scope is bound to is refused as `unknown_subject`.** The result is `TenantNotFoundException`.
12. **The permission-set witness is deferred to PC-052,** as its analysis assigns.
13. **Review 1: one rule has no test that fails deterministically.** The connector re-connects cold once when an entry the prologue confirmed is evicted between the premises' peek and the apply. No seam can evict in that window without a fault hook in production code.

**R1-1 (major): `ConnectAsUserAsync` rebinds the scope to whichever user it is given, so later guarded batches run under that user's permissions.**
- Where: `src/core/Tellma.Core/Access/UserConnector.cs:119-140`, and the cache-hit path at `:102-105`.
- The bug: `Apply` (`:497`) is careful to connect a `ForUser` result only when `context.UserId` is null or equal. `ConnectAsUserAsync` then calls `Connected(ConnectionMode.User, user)` unconditionally at `:138`, which overrides that check. `EnsureCaller` only checks the principal kind, so a request scope can make this call.
- Scenario: a request scope (caller A, `context.UserId = A`) calls `IUserConnector.ConnectAsUserAsync(B)`. This is the natural way to load another user's set for `EvaluateFor` ("can I, and why for another user", §5.1, §7.5), which PC-052 builds next.
  - `_mode` becomes `User` and `Current` becomes B.
  - From then on, `GuardedBatchRunner.RunAsync` gets B from `CurrentAsync`. `PremisesFor` builds `ForUser(B, B's tags)`, so the guard passes and `compose(user, …)` authorises A's request with B's `UserAccess`.
  - The persist re-check then validates B (`@tm_UserId` and `@tm_callerIds` are B), while the audit columns carry A.
- The same hole in the cache-hit path: `ConnectAsync` connects the cached entry without comparing its `UserId` with a bound `context.UserId`. After the subject's entry was replaced by another scope's `Apply` (deviation 11's re-mapped subject), a second `ConnectAsync` in the scope connects as B. The guard then passes (it expects B and resolves B), the body runs, and only then does `Apply` refuse. A persist has already committed by that point.
- Fix:
  - `Connected` refuses any user whose id differs from a bound `context.UserId`: `InvalidOperationException` for `ConnectAsUserAsync`, the `unknown_subject` refusal for the subject path.
  - `ConnectAsUserAsync` connects the scope only when `context.UserId` is null or equal. Otherwise it returns the loaded user without touching `Current`/`_mode`, or it refuses outside a background scope and leaves the other-user load to `Contribute` + `Apply`.
  - Add a unit test: a request scope's `ConnectAsUserAsync(other)` leaves the runner's next premises on the caller.

**R1-2 (major): `Apply` throws `InvalidOperationException` (a 500) when the guard confirmed the cached set but the tags it reads back differ.**
- Where: `src/core/Tellma.Core/Access/UserConnector.cs:438-458` (and the profile twin at `:474-479`); `src/core/Tellma.Core/Access/ConnectPrologue.cs:260-265`.
- The bug: the no-rows branch looks the confirmed set up under `tenantTag`, which comes from `result.TenantTags`, i.e. set 1. Set 1 is a separate statement from `SELECT @tm_PermissionsTag`, which is the value the guard and `PermissionsStale` compared. Each statement reads its own committed state, so the two can differ.
- Scenario 1 (race):
  1. A role save commits between the prologue's tag read and set 1.
  2. The prologue reports `PermissionsStale = 0` (old tag = expected), and on a Read/Validate the guard passes and the body runs.
  3. Set 1 carries the new tag, so `held.Tag == tenantTag` is false and the `Peek` for the new tag misses: "The connect prologue confirmed a permission set this instance no longer holds."
  4. The served result becomes a 500. A Persist is saved by the 50412 re-check, but reads and validations are not.
- Scenario 2 (persistent):
  1. The subject now resolves to user B, while the cache holds A. This is deviation 11's case, from the request initializer where `context.UserId` is still null.
  2. B's user tags equal A's. This is common: one `@tm_tag` per batch bumps every user of a bulk membership edit, and the companion insert stamps every user created in one batch.
  3. The prologue reports nothing stale, because the stale flags ignore the user-id mismatch. The guard fails on the id, no rows or profile come back, `own` is null, and B's set is not cached.
  4. The result is an `InvalidOperationException` before `Connections.Set`. The stale entry stays, so every request of that subject on this instance fails with a 500 until eviction.
- Fix:
  - When `!result.PermissionsStale`, look up the set (and the profile when `!ProfileStale`) by the tags the premises expected, which the prologue confirmed (`origin.Premises`'s `Expected`), not by set 1's.
  - Make a user mismatch read as stale in the text: `… OR @tm_ExpectedUserId IS NULL OR @tm_UserId <> @tm_ExpectedUserId` in both `PermissionsStale` and `ProfileStale`, and keep the reader in step. Rows and profile then always come back for a user the basis does not describe.
  - On a remaining miss (eviction between `ConnectAsUserAsync`'s `Peek` at `:129-130` and `Apply`, where the basis is null), re-connect cold instead of throwing.

### Responses

**R1-1: fixed.**
- `Connected` refuses any user other than a bound `context.UserId` with `InvalidOperationException`; only the system scope may run as a user it names.
- `ConnectAsUserAsync` connects the scope only when the context is bound to that user, or to none. For any other user it returns the loaded user and caches its set and profile, but leaves `Current` and the mode alone.
- This is the seam for "can I, and why, for another user": a later `EvaluateFor` calls `ConnectAsUserAsync(other)` in the caller's scope and gets the other user's set without rebinding the scope. `Contribute` reports user tags only for the bound user, so the other user's stamps never enter the batch's outcome. The `IUserConnector` docs state the seam.
- `ConnectAsync` takes a cache hit only when its user is the bound one. Otherwise it makes the cold round trip, whose `Apply` refuses a re-mapped subject as `unknown_subject`. A flight that another scope started and that resolves to another user is refused the same way.
- Tests, in `UserConnectionTests`:
  - `Loading_another_users_set_in_a_callers_scope_returns_it_and_leaves_the_scope_on_the_caller`.
  - `A_cached_connection_naming_another_user_than_the_scopes_is_never_connected`.

**R1-2: fixed.**
- `Apply` looks up a set it was told is current by the tags the premises expected, which are the tags the prologue compared. It no longer uses set 1's. The profile does the same.
- Both user texts now read a user mismatch as stale: `PermissionsStale` and `ProfileStale` start with `@tm_ExpectedUserId IS NULL OR @tm_UserId <> @tm_ExpectedUserId`. The reader needs no change, because it already follows the flags.
- On a remaining miss (a confirmed entry evicted between the premises and the apply), the connector's own round trip re-connects cold once. The public `Apply` still throws, because the runner's basis always holds the confirmed entry.
- Tests:
  - `ConnectPrologueTests.A_set_the_prologue_confirmed_is_found_by_the_tags_it_compared_although_the_tag_set_read_after_them_moved` (scripted sets, the real connector) covers scenario 1.
  - `UserConnectionTests.A_subject_moved_to_another_user_with_the_same_tags_is_refused_to_the_scope_bound_to_the_first_and_connects_the_next_request_as_the_second` covers scenario 2. The two users share their tags, so without the text change the result is the old `InvalidOperationException`.
  - `ConnectPrologueTests.A_user_the_premises_did_not_expect_reads_stale_in_every_part_of_both_user_variants` pins the text.
- Not covered: the cold re-connect after an eviction. No seam evicts between the premises' peek and the apply without a fault hook in production code (deviation 13).

**R1-3: fixed.** A new `GuardedPersistTests` runs over `ConnectDatabase`. A transaction-head statement on the chosen attempts plays the commit that lands between the guard and the re-checks; `XACT_ABORT` rolls it back.
- **50412, subject and user variants:** two attempts and three prologue round trips (the failed attempt, the cold re-connect, the recompose). The results are `cold` then `warm`, and the job commits once.
- **50412 on every attempt:** `StaleContextException` and `guard_thrash`; nothing commits.
- **50401, subject and user variants:** `TenantNotFoundException` and a `deactivated` count. The connect, permissions and profile entries are dropped, and nothing commits.
- **System persist:** the permissions tag is moved and the system row deactivated inside the window. It commits on the first attempt in one round trip and the tag stays moved, so the batch has no permissions expectation and no caller re-check. The body re-activates the row.
- **0013 runner cases:** an `entity:fixture.Lookup` dependency that moved re-runs once under `Rerun` (2 round trips) and is served under `Refresh` (1). If it moves again after the re-run, it is refused as stale with `guard_thrash`.
- **Budgets (§7.5):** a create on a warm id buffer costs 1 round trip; a save of an existing row costs 2 (validate, persist).
- The review's other names come in through these tests on real SQL: `@tm_UserId` in all three variants, `@tm_ExpectedUserPermissionsTag` and `@tm_callerIds`.

**R1-4: fixed.**
