# PC-084: Blob references: validator, effect, attach/release, resolve, reconcile and the FK exemption

## Implementer notes

### What was built

Spec 0017 §4.1–§4.4 (attach rule, validator, effect, persist translation), §5.1–§5.2
(`ResolveAsync`), the §7.2 reconcile statement and the §10.1 attach instrument. PC-212 still owns
the sweep and reconcile handlers, their schedules and metrics; PC-089 owns the endpoints, the Azure
adapter and the downloads metric.

- **Attach rule** (`Blobs/BlobAttachments.cs`). It walks an aggregate's blob columns (the root,
  then children depth first, cached per root metadata). It computes what a payload row newly
  attaches: a non-null value on an inserted row (a child absent by key from the stored collection
  counts as inserted), or a changed non-null value on an updated one. It also counts a persist
  refusal once per attached value.
- **Validator** (`Blobs/BlobReferenceValidator.cs`).
  - It loads `Id,State,Kind,CreatedById,ExpiresAt` through `context.Loader.ByIds<Blob,int>`.
  - It refuses with `Blob.DuplicateReference` (every occurrence after the first), or with
    `Blob.NotAttachable` and a `reason` (`missing`, `not-staged`, `kind`, `uploader`, `expired`,
    first failure in that order).
  - It counts every refusal on `tellma.blobs.attach.rejected{kind, reason}` (`BlobAttachMetrics`).
- **Effect** (`Blobs/BlobReferenceEffect.cs`).
  - It finds each column's capture by `(Table, Column)` in `PersistContext.Captures`, and never
    forms a name.
  - A save gets one statement per column: release the changed or cleared old values, confirm the
    new ones under the validator's conditions with `OUTPUT inserted.[Id]` into a declared id table,
    then `THROW 50422, N'Blob.NotAttachable'` if any new value went unconfirmed.
  - A delete gets the release alone. An action has no captures, so nothing is appended.
  - The existing `PersistFailures` translation turns the THROW into a root
    `Blob.NotAttachable(reason=persist)`, and a `UX_<Table>_<Column>` violation into the same error
    at the property path. `SaveRun.Persist`'s catch counts it once per attached value of the save.
- **Registration, "the realizer"** (`Blobs/BlobReferenceComponents.cs`, called from
  `StackComposition.Build`).
  - It walks each stack's leaf and child-collection leaves by type, as the metadata does, and finds
    every stack with a `[BlobReference]` at any depth.
  - It inserts the validator/effect pair at index 0 of the stack's components, attached by `core`.
- **Resolve** (`Blobs/BlobResolver.cs`, `BlobStatements.Resolve`, `BlobDownload`,
  `IBlobService.ResolveAsync`).
  - The kind and variant checks come first. Then `EvaluateAsync(OwnerResource, Read)` runs up front
    (it records, counts and connects).
  - Inside the runner's compose, the read is decided again from the connected user's set, as
    `DetailsPlanner` does. A denied read skips statement 1. A filtered one is conjoined, through
    `Via(OwnerPath)` when the owner path is non-empty.
  - The blob row is read by raw SQL in the same read batch. `Combine` applies §5.1 step 4. A miss is
    logged as `BlobDownloadNotFound` at debug level.
  - `BlobService` is now a facade over `BlobStager` (the staging code, renamed unchanged from the
    old `BlobService`) and `BlobResolver`.
- **Reconcile** (`BlobStatements.Reconcile`). §7.2's release of a kind's day-old unreferenced
  committed blobs. It returns the count.
- **The FK exemption** (spec 0015 §7.4).
  - `RowRules.References` already excluded blob columns. Two tests pin it now: a caller with no
    `core.Blob` grant attaches a blob, and a missing id is `Blob.NotAttachable missing`, never
    `Fk.NotFound`.
  - I found that `RowRules.Unique` also swept in blob columns: their `UX_` index makes them
    `IsUnique`. That gave `Unique` errors plus a key-set load per blob value. They are now
    excluded too (see Deviations).
- **Fixture.**
  - `fixture.BlobOwners` (Name, FileId `fixture-file`, PhotoId `fixture-photo`), and its child
    `fixture.BlobOwnerFiles` (FileId `fixture-child-file`, with `[ApiResource(Queryable = false)]`
    so the child kind is owned through the parent's grant, OwnerPath `BlobOwner`).
  - `fixture.BlobFolders` (a tree with IconId `fixture-folder-icon`), for delete with descendants.
  - The migration was regenerated with dotnet-ef and BOMs were stripped. The goldens
    `fixture-stacks.txt` and `fixture-routes.txt` were re-recorded, and the change-tracked table
    list in `DataBatchTests` gained the three new tables.

### Deviations

1. **Effect text.** §4.4's `DECLARE @tb{b}_expected` and `@@ROWCOUNT` comparison cannot be written
   through `IDataBatch.Sql`, which forbids reserved names. The effect declares an id table
   (`batch.DeclareIdTable()`), confirms with `OUTPUT inserted.[Id] INTO` it, and throws when a
   new value is missing from it. The semantics are the same and it is still one statement per
   column.
2. **Deletes and actions.** A delete appends the release alone, since its capture has no new
   values. An action appends nothing, since it has no captures.
3. **Validator candidates before round 1.** The before images are not known when the validator
   starts, so it loads every non-null value of update rows as a candidate. It applies the exact
   rule after `LoadAsync`. When the before images are already known (a deferred validator start),
   it loads exactly.
4. **`RowRules.Unique` excludes blob columns.** Spec 0015 §6.6 names `[Unique]`/`[NaturalKey]`
   only, and spec 0017 §4.2 gives payload duplicates to `Blob.DuplicateReference`.
5. **The owner read orders by `Id`.** Queryex refuses `Take` without an ordering (QX4006).
6. **The fixture adds `BlobFolders`.** Delete with descendants needs a tree, and `BlobOwners` is
   not one.
7. **`BlobOwnerFiles` is `[ApiResource(Queryable = false)]`.** This makes the child kind's
   authorisation go through the parent's grant via `OwnerPath`, as §11 asks.
8. **`BlobService` is split into `BlobStager` plus a facade.** This gives the resolver its own
   dependencies.

9. **A warm-buffer, insert-only save that attaches takes one extra round trip** (D-123). Spec 0017
   §4.2 mandates the blob load before the persist, and such a save has no other round for it to
   ride. This conflicts with §10.1's "a save adds none" and the checkpoint's done-when; that is
   left for the spec to reconcile. Every other save shape pays no round, a cold buffer included.

### Open risks / rulings for the orchestrator

- **Round trips ("adds zero round trips"), as corrected in review 1.**
  - A replace or a clear on a warm buffer rides the update's before-image round.
  - On a cold buffer the validators start after round 1, so the save prefetches every blob row of
    the payload on round 1 (`BlobAttachments.Prefetch`), and the validator's exact request is then
    answered from the loader's cache. An insert or an update that adds a child with a file
    therefore costs the same as one without.
  - The one shape that pays a round is an insert-only save on a warm buffer that runs no first
    round otherwise (deviation 9).
  - A null release needs no load.
  - All of these counts are asserted in `BlobReferenceTests`.
- **Persist-refusal metric.** One count per newly attached value of the save. The THROW cannot
  name its column, and the whole save rolled back.
- **Write implies read** (spec 0014). Any Save or Delete grant on the owner serves its committed
  blobs. This is intended, and the test uses an unrelated grant for "no read".

**R1-1 (major): the "adds zero round trips" done-criterion is not met, and the stated account of
when a round is added is wrong.** Open point 1.

- **The deferred path.** When the id buffer does not cover the payload's new rows,
  `SaveRun.cs:177-185` sets `_deferred`. The validators then start only after round 1
  (`SaveRun.Rounds.cs:52-55`: "Round trip 1 then carries no validator's load"). So the
  validator's `ByIds` + `LoadAsync` (`BlobReferenceValidator.cs:55-56`) always gets a validation
  round of its own on that path. It happens even when round 1 runs anyway: for the reservation,
  for FK references, or for the update roots' before images.
- **Saves this adds a round to:**
  - a cold-buffer insert that attaches (3 round trips against 2 without a blob);
  - every update that adds a child row while the buffer is cold, for example an existing
    `BlobOwner` gaining a `BlobOwnerFile` line with a file. A replace or clear on such a save also
    pays +1.
- **Claims this contradicts:**
  - The implementer note "A save that already runs a round for any reason gains nothing".
  - The validator remarks at `BlobReferenceValidator.cs:22-26` ("The load rides a round the save
    runs anyway for its update rows").
  - `src/core/Tellma.Core/README.md:617-619`.
- **The warm-buffer insert-only case.** Its +1 is pinned by `BlobReferenceTests.cs:339-340`, and
  it is the case §4.2 can't avoid: the validator needs the rows before the persist, and nothing
  else needs a round. Spec 0017 §10.1 ("a save adds none") and the checkpoint's done-when conflict
  with §4.2 ("rides the validation round's batch") when there is no such round. That is a spec
  misalignment for the orchestrator to rule on, not something the code can close.
- **The deferred case can be folded.** Two ways:
  - Load the blob candidates as a pipeline load of round 1, beside `CollectReferences`/`_targets`
    (`SaveRun.cs:389-407`, `ComposeFirstRound` at `SaveRun.Rounds.cs:62-99`). Take every non-null
    value as the candidate set and apply the exact rule after round 1. The validator then answers
    from the loader's cache: `Keyed` loads are served by `Covers`, so the subset needs no round.
  - Let the blob validator start before round 1 even when the ids are deferred. It reads no ids;
    its paths are payload indexes.
- **Fix.**
  - Fold the deferred case with one of the two ways above.
  - Correct the remarks, the README and the note.
  - Add a round-trip test with a cold buffer (a fresh stack's first insert, or a buffer reset)
    for an insert that attaches and for an update that adds a child with a file.
  - Escalate the insert-only +1 against §10.1 and the done-criterion.

**R1-3 (minor): `ResolveAsync`'s `AnyMember` path has no test.**

**R1-4 (minor): a blob row deleted between validation and persist surfaces as `Fk.NotFound`, not
`Blob.NotAttachable`.**

- **The failure path.**
  - The emitter's `INSERT`/`UPDATE` runs before the effect.
  - The blob row can be gone by then: a staged blob expires after the validation round, and the
    sweep claims it and deletes its row.
  - The write then fails on `FK_<Table>_<Column> → core.Blobs`.
  - `PersistFailures.MissingTarget` (`PersistFailures.cs:230-247`) answers it as `Fk.NotFound`
    with `entity = core.Blob` at the property path.
- **What the spec says.** Spec 0017 §4.4 and §8.2 name this case ("it expired between validation
  and persist") as `Blob.NotAttachable` with `reason = persist`. The point of the FK exemption is
  that a blob column never reports `Fk.NotFound`.
- **The metric.** `BlobAttachments.CountPersistRefusal` does not count it.
- **How likely.** The window is narrow: the claim and the row delete must both fall inside it.
  But the outcome is a code the client cannot act on ("re-upload").
- **Fix.** In `MissingTarget`, when the reference's foreign key is a `[BlobReference]` property,
  return `Blob.NotAttachable` with `reason = persist`, as `Unique` already does at
  `PersistFailures.cs:173-178`. Add a unit test over a synthetic 547 on a blob column.

**R1-5 (minor): the race test does not establish that it runs under RCSI.**

- **The gap.** `BlobLifecycleStatementTests.cs:76-109` proves "blocks, then skips". It would pass
  just the same under locking read committed, where an `UPDATE` also blocks on the X lock and then
  re-reads. Spec 0017 §11 asks for the property "under RCSI", the setting where a stale snapshot
  could let the claim through.
- **Fix.** Assert `SELECT is_read_committed_snapshot_on FROM sys.databases WHERE name = DB_NAME()`
  is 1 on the sweeper's connection before the claim. Otherwise a fixture change that drops RCSI
  silently voids the test.
- **The rest of the choreography holds:**
  - OnPersist sits after the effects (`SaveRun.Persist.cs:149-160`), so the gate is taken after
    the confirm.
  - Both waits are on lock-wait DMVs, not sleeps.
  - The outcome is asserted on both sides: no row claimed, and the blob `Committed`.

**R1-6 (minor): after the PC-077 merge, a blob refusal raised by an enlisted group's statements is
not counted.** Open point 3.

- **The merge.** The textual merge is clean, and the host save loses nothing. In the merged
  `SaveRun.Persist.cs`, `Enlistments?.Translate(failure)` returns before `PersistFailures.Translate`
  and this checkpoint's `CountPersistRefusal`.
- **The gap.** A `THROW 50422` or `UX_` violation from an enlisted group's blob effect therefore
  never reaches `tellma.blobs.attach.rejected{persist}`. Spec 0017 §4.6's job-frame `Exports`
  insert is the canonical enlisted blob path.
- **Fix (a carry for whichever of PC-077/PC-084 integrates second).** Count in the group
  translation path too: call `CountPersistRefusal` with the group's roots wherever a group failure
  is translated to `Blob.NotAttachable(persist)`. Pin it with one enlisted-save test once PC-077
  lands.

**Judgements on the implementer's open points and deviations**

- **Open point 1.** See R1-1. The deferred case is foldable. The warm insert-only +1 needs a
  spec ruling.
- **Open point 2: no finding; the `RowRules.Unique` exemption is narrow and correct.**
  - Metadata marks a property unique only through a single-column unique index, or a
    parent-scoped pair (`EntityMetadataBuilder.Parts.cs:390-400`). For a blob column that is its
    own `UX_` index.
  - A repeat inside the payload is `Blob.DuplicateReference`.
  - A value held by a stored row is a blob that is no longer `Staged` (`not-staged`).
  - A concurrent holder is the `UX_` translation to `Blob.NotAttachable(persist)`, at
    `PersistFailures.cs:173`.
  - So no real uniqueness check is lost. It also removes a key-set load per blob value from
    round 1.
- **Open point 3.** See R1-6. The hunk merges cleanly with both branches. The only semantic gap
  is the enlisted-group path.
- **Deviations 1-8: all accepted.**
  - Deviation 1 (the effect text) has the same semantics as §4.4. The confirm counts every capture
    row whose new value differs from the old one, and the `NOT EXISTS` over the confirmed ids
    matches the spec's `@@ROWCOUNT <> expected`. A duplicate id across rows is stopped by the
    `UX_` index first.
  - Deviation 3 (candidates before round 1) is correct on re-entry too. `RevalidateAsync` asks for
    the exact subset, and the keyed cache covers it.
  - Deviations 5-8 are justified as written.
