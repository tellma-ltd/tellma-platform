# PC-174: Excel row source

## Implementer notes

### What was built

The Excel row source of spec 0015 §15 (`IExcelRowSource`), served by a stack's `ExcelRowSource`
and by `IChildQueryService.ExcelRowSource` for an exportable child surface, under the
`excel_rows` operation (§12). Spec coverage: §15, §12 (row source), §16.2 Excel export row,
§18.2 row-source pins.

- **`src/core/Tellma.Core/Crud/ExcelRows/`** (new).
  - `ExcelRowsOperation` (scoped): creates the row source, runs each page or lookup read as one
    `excel_rows` operation through `CrudOperations` (its lane, its translation of arithmetic and
    retry failures as the query's), runs one round trip through the `GuardedBatchRunner` and
    re-checks a refusal raised in the composition once through `AccessEvaluator.RecheckAsync`.
  - `RowsNode`: the admitted `ExcelQuery` tree. The root is the stack's own entity, a child
    collection (`Dependent`) or a lookup target (`Lookup`). The ordering is
    `query.OrderBy ?? source.OrderBy ?? "Id"` on the own root, `query.OrderBy ?? "Id"` elsewhere.
    A node with dependents gets its key column appended (and stripped from the rows returned), so
    its dependents can be restricted by its keys.
  - `RowsComposition`: one round trip's composition. The own root is decided under `Read` (Denied
    refuses as `ForbiddenException` NoGrant); a lookup root under `TargetReads.Of` (Denied reads
    no rows; sensitive asks for the step-up); a dependent carries no filter of its own. Then the
    restrictions (the by-ids TVP, the query's restriction bound per column type, and either the
    owner's captured keys or an owner-id TVP on the parent key), `QueryShape.AdmitRows`,
    `QueryPlanner.Plan`, the traversal rule and the select-type rule, and `IDataBatch.Rows` with
    `CaptureKeys` when the node has dependents.
  - `ExcelRowSource`: `Pages` streams `MaxTake` root rows per page (one batch each), `Take` capping
    the total and `CountCap` on the first page only; every dependent at every depth rides its
    owner's batch, and a dependent chunk that reaches `MaxTake` is completed by follow-up reads
    over the owner ids, each carrying its own dependents. `ReadAsync` reads flat queries in waves:
    every first chunk in one round trip, then one round trip per wave of follow-ups.
- **`Crud/TargetReads.cs`** (new): the reads of entities an operation reaches without reading them
  directly, extracted from `WriteRun` and `SaveOperation` (decide, own securable or the owner's
  filter rebased through the child's navigation, step-up). The save now calls it; behaviour is
  unchanged.
- **`Crud/Query/`**: `QueryShape.AdmitRows` (the clauses without the take ceiling, skip window or
  count ceiling, the search length kept); `QuerySurfaces.Root`/`Entity` (a plain surface for a
  lookup target that is no stack and no child surface); `QueryOperation.TranslatedAsync` made
  internal for reuse; `ChildQueryService.ExcelRowSource` built.
- **`Crud/EntityPipeline.cs`**, `EntityPipelineFactory.cs`, `CrudComposition.cs`: the pipeline's
  `CreateExcelRowSource` built (`Require(Export, excel_rows)`), registrations for
  `ExcelRowsOperation` and `TargetReads`.
- **`Tellma.Core.Abstractions/Excel/ExportSource.cs`**: `ByQuery.OrderBy`'s doc says null orders
  by id (it said the stack's default).
- **Conformance (D-131)**, `src/core/Tellma.Core.Testing/Crud/`: an `excel_rows` row in the
  operations table (answers none for a missing id), a `Read` refusal through the row source in the
  guarded table, `excel_rows` in the instruments case, and three §16.2 rows in the read budget: an
  Excel page with every collection at every depth = 1, an Excel lookup = 1, and each exportable
  child surface's page by query = 1.
- **Fixture**: `Widget` gets `[Stack(MaxTake = 50)]`, so the suites cross a page boundary and a
  collection beyond the ceiling with few rows (the goldens moved with it).
- **Tests**: `test/core/Tellma.Core.Tests/Crud/ExcelRows/ExcelRowSourceTests.cs` (composition over
  the query rig) and `test/core/Tellma.Core.IntegrationTests/Crud/ExcelRowSourceTests.cs` with
  `ExcelRowSourceDatabase` (120 widgets; a part per third widget; the first widget's 60 parts).
- **Docs**: the Tellma.Core README gains "The Excel row source" and the `Crud/ExcelRows/` row.
  ARCHITECTURE.md does not describe the row source's mechanics; nothing in it disagreed.

### Deviations

1. `ExcelRowSource` is one non-generic class over the `QuerySurface`, not
   `ExcelRowSource<TEntity, TKey>`: the row source reads rows by path and never touches an entity
   instance, and one class serves both the stack and the child surface.
2. `ExportSource.ByQuery.OrderBy`'s doc said "null for the stack's default"; §15 and §18.2 say
   `Id`. The code follows the spec and the doc was corrected.
3. The traversal rule, `MaxSearchLength` and `MaxIds` (by-ids source, `LimitExceededException`)
   apply to the row source, as they do to a query; §15 does not list them.
4. A child surface's row source refuses `All` and named filters with `ArgumentException` at
   creation (§15's child surface names by-ids and by-query without named filters).
5. The stack's `MaxTake` is also the chunk size of every dependent and lookup read.
6. A dependent `ExcelQuery` carrying `Take`, `Restriction` or `CountCap` is refused with
   `ArgumentException` (the record's remarks say they are null on a dependent).
7. A nested overflow (a grandchild beyond the ceiling under a chunk) is completed by more
   follow-ups, each counted as "+1 per follow-up" of §16.2.
8. `ReadAsync`'s follow-ups for several queries ride one round trip per wave, not one per query.
9. `TargetReads` was extracted from `WriteRun` and `SaveOperation` so lookups share the save's
   reference-read semantics.
10. The fixture's `Widget` takes `[Stack(MaxTake = 50)]`, so the integration and conformance suites
    cross a page boundary and a collection beyond the ceiling with few rows; the descriptor golden
    moved with it (the client entity fixtures did not change).

### Open risks

- Revocation mid-stream relies on the runner recomposing on a stale tag and the composition
  re-deciding `Read`; the integration pin covers the stack root only.
- The dependent's rows are ordered by its own ordering across the page (default `Id`), not grouped
  by owner; the codec groups by parent key.
- A lookup restriction on a string column binds a `StringList` of at most 450 characters per value;
  longer values throw `ArgumentException`.

### What reviewers should examine hardest

- `RowsComposition.Compose`: which restriction and which access filter applies to each root kind,
  and that a dependent carries no filter of its own (its owner's keys already passed the owner's).
- `ExcelRowSource.CompleteAsync`: the skip arithmetic of follow-ups and the grouping of nested
  dependents across chunks.
- `QueryShape.AdmitRows`: what it keeps and what it drops from the query admission.
- The `TargetReads` extraction: that the save's reference reads are unchanged.
