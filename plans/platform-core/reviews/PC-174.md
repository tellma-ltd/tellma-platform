# PC-174: Excel row source

## Implementer notes

### What was built

The Excel row source of spec 0015 §15 (`IExcelRowSource`), served by a stack's `ExcelRowSource`
and by `IChildQueryService.ExcelRowSource` for an exportable child surface, under the
`excel_rows` operation (§12). Spec coverage: §15, §12 (row source), §16.2 Excel export row,
§18.2 row-source pins.

- **`src/core/Tellma.Core/Crud/ExcelRows/`** (new).
  - `ExcelRowsOperation` (scoped): creates the row source, runs each page or lookup read as one
    `excel_rows` operation through `CrudOperations` (its lane, its translation of arithmetic and
    retry failures as the query's), runs one round trip through the `GuardedBatchRunner` and
    re-checks a refusal raised in the composition once through `AccessEvaluator.RecheckAsync`.
  - `RowsNode`: the admitted `ExcelQuery` tree. The root is the stack's own entity, a child
    collection (`Dependent`) or a lookup target (`Lookup`). The ordering is
    `query.OrderBy ?? source.OrderBy ?? "Id"` on the own root, `query.OrderBy ?? "Id"` elsewhere.
    A node with dependents gets its key column appended (and stripped from the rows returned), so
    its dependents can be restricted by its keys.
  - `RowsComposition`: one round trip's composition. The own root is decided under `Read` (Denied
    refuses as `ForbiddenException` NoGrant); a lookup root under `TargetReads.Of` (Denied reads
    no rows; sensitive asks for the step-up); a dependent carries no filter of its own. Then the
    restrictions (the by-ids TVP, the query's restriction bound per column type, and either the
    owner's captured keys or an owner-id TVP on the parent key), `QueryShape.AdmitRows`,
    `QueryPlanner.Plan`, the traversal rule and the select-type rule, and `IDataBatch.Rows` with
    `CaptureKeys` when the node has dependents.
  - `ExcelRowSource`: `Pages` streams `MaxTake` root rows per page (one batch each), `Take` capping
    the total and `CountCap` on the first page only; every dependent at every depth rides its
    owner's batch, and a dependent chunk that reaches `MaxTake` is completed by follow-up reads
    over the owner ids, each carrying its own dependents. `ReadAsync` reads flat queries in waves:
    every first chunk in one round trip, then one round trip per wave of follow-ups.
- **`Crud/TargetReads.cs`** (new): the reads of entities an operation reaches without reading them
  directly, extracted from `WriteRun` and `SaveOperation` (decide, own securable or the owner's
  filter rebased through the child's navigation, step-up). The save now calls it; behaviour is
  unchanged.
- **`Crud/Query/`**: `QueryShape.AdmitRows` (the clauses without the take ceiling, skip window or
  count ceiling, the search length kept); `QuerySurfaces.Root`/`Entity` (a plain surface for a
  lookup target that is no stack and no child surface); `QueryOperation.TranslatedAsync` made
  internal for reuse; `ChildQueryService.ExcelRowSource` built.
- **`Crud/EntityPipeline.cs`**, `EntityPipelineFactory.cs`, `CrudComposition.cs`: the pipeline's
  `CreateExcelRowSource` built (`Require(Export, excel_rows)`), registrations for
  `ExcelRowsOperation` and `TargetReads`.
- **`Tellma.Core.Abstractions/Excel/ExportSource.cs`**: `ByQuery.OrderBy`'s doc says null orders
  by id (it said the stack's default).
- **Conformance (D-131)**, `src/core/Tellma.Core.Testing/Crud/`: an `excel_rows` row in the
  operations table (answers none for a missing id), a `Read` refusal through the row source in the
  guarded table, `excel_rows` in the instruments case, and three §16.2 rows in the read budget: an
  Excel page with every collection at every depth = 1, an Excel lookup = 1, and each exportable
  child surface's page by query = 1.
- **Fixture**: `Widget` gets `[Stack(MaxTake = 50)]`, so the suites cross a page boundary and a
  collection beyond the ceiling with few rows (the goldens moved with it).
- **Tests**: `test/core/Tellma.Core.Tests/Crud/ExcelRows/ExcelRowSourceTests.cs` (composition over
  the query rig) and `test/core/Tellma.Core.IntegrationTests/Crud/ExcelRowSourceTests.cs` with
  `ExcelRowSourceDatabase` (120 widgets; a part per third widget; the first widget's 60 parts).
- **Docs**: the Tellma.Core README gains "The Excel row source" and the `Crud/ExcelRows/` row.
  ARCHITECTURE.md does not describe the row source's mechanics; nothing in it disagreed.

### Deviations

1. `ExcelRowSource` is one non-generic class over the `QuerySurface`, not
   `ExcelRowSource<TEntity, TKey>`: the row source reads rows by path and never touches an entity
   instance, and one class serves both the stack and the child surface.
2. `ExportSource.ByQuery.OrderBy`'s doc said "null for the stack's default"; §15 and §18.2 say
   `Id`. The code follows §15 and the doc was corrected. This conflicts with spec 0019 §4.1 (a
   display export runs exactly the query `query` would run, whose ordering defaults to
   `DefaultOrderBy ?? "Id desc"` per 0015 §5.2 and §2.2) and with §15's own "its defaults the
   surface's" for a child surface (`Id desc`): an unsorted grid exports in `Id` order. The specs
   need bringing in line.
3. The traversal rule, `MaxSearchLength` and `MaxIds` (by-ids source, `LimitExceededException`)
   apply to the row source, as they do to a query; §15 does not list them.
4. A child surface's row source refuses `All` and named filters with `ArgumentException` at
   creation (§15's child surface names by-ids and by-query without named filters).
5. The stack's `MaxTake` is also the chunk size of every dependent and lookup read.
6. A dependent `ExcelQuery` carrying `Take`, `Restriction` or `CountCap` is refused with
   `ArgumentException` (the record's remarks say they are null on a dependent).
7. A nested overflow (a grandchild beyond the ceiling under a chunk) is completed by more
   follow-ups, each counted as "+1 per follow-up" of §16.2.
8. `ReadAsync`'s follow-ups for several queries ride one round trip per wave, not one per query.
9. `TargetReads` was extracted from `WriteRun` and `SaveOperation` so lookups share the save's
   reference-read semantics. That includes its last branch: a lookup target that no securable
   guards and no owner holds is read unrestricted, as a save's reference to it is resolved, where
   §15 says "under the caller's `Read` decision for its resource" (a direct decision on an
   unregistered resource is a denial). Kept so an import resolves exactly what a JSON save of the
   same rows resolves; it needs a ruling.
10. The fixture's `Widget` takes `[Stack(MaxTake = 50)]`, so the integration and conformance suites
    cross a page boundary and a collection beyond the ceiling with few rows; the descriptor golden
    moved with it (the client entity fixtures did not change).
11. Every ordering a node reads by (root, dependent, lookup) is ended by the key unless its last
    term already is the key (`RowsNode.TieBroken`), so pages and follow-ups cut by skip neither
    repeat nor drop rows that tie; §15 states only `query.OrderBy ?? source.OrderBy ?? "Id"`.
    (Added in review 1.)

### Open risks

- Revocation mid-stream relies on the runner recomposing on a stale tag and the composition
  re-deciding `Read`; the integration pin covers the stack root only.
- The dependent's rows are ordered by its own ordering across the page (default `Id`), not grouped
  by owner; the codec groups by parent key.
- A lookup restriction on a string column binds a `StringList` of at most 450 characters per value;
  longer values throw `ArgumentException`.

### What reviewers should examine hardest

- `RowsComposition.Compose`: which restriction and which access filter applies to each root kind,
  and that a dependent carries no filter of its own (its owner's keys already passed the owner's).
- `ExcelRowSource.CompleteAsync`: the skip arithmetic of follow-ups and the grouping of nested
  dependents across chunks.
- `QueryShape.AdmitRows`: what it keeps and what it drops from the query admission.
- The `TargetReads` extraction: that the save's reference reads are unchanged.

## Review 1

### Findings

**R1-1 (major): the pages are cut by `OFFSET`/`FETCH` over an ordering that need not be unique, so an
export beyond one page can repeat or drop rows.**
`src/core/Tellma.Core/Crud/ExcelRows/RowsNode.cs:140` takes the ordering as sent (the query's, else
the source's, else `Id`), and `ExcelRowSource.StreamAsync` (`ExcelRowSource.cs:80-105`) reads each
page as its own statement with `Skip` advancing. `StatementEmitter.WriteOrdering` (`src/core/Tellma.Core.Queryex/Emit/StatementEmitter.cs:202-234`) appends no
tie-breaker, and SQL Server gives no stable order among rows that tie on the `ORDER BY` columns, so
two `OFFSET` reads can each place a tied row on either side of the boundary.
Failure: a display export of more than `MaxTake` rows sorted by the grid's `Name`, `State` or a
date (spec 0019 §4.1 passes `request.OrderBy` through), or an export-for-import with a non-key
`OrderBy`. Rows that tie across a page boundary can come back on both pages or on neither. The
workbook then silently holds duplicate or missing rows, and a later import of it deletes or
re-inserts children. The same applies to a dependent's follow-ups (`CompleteAsync`, skip =
gathered count) when its `OrderBy` is not unique. The codec sends `"<ParentKey>, Id"`, but the
contract accepts any ordering.
Fix: in `RowsNode.Shaped`, append the root's key (`, Id`) to every node's ordering unless the
ordering already ends with the key (or contains it). Pin it with a unit test that asserts
`"Name, Id"` on a by-query page and on a dependent, and record the tie-breaker under Deviations
(§15 states only `query.OrderBy ?? source.OrderBy ?? "Id"`).

**R1-2 (major): two of the new completion paths have no test that would fail if they broke.**
- `ReadAsync`'s follow-ups (`ExcelRowSource.ReadAllAsync`, `ExcelRowSource.cs:195-228`): §15 says
  "completing any result that reaches `MaxTake` the same way", and deviation 8 adds one round trip
  per wave. No unit or integration test returns a full lookup chunk. If `pending` were never
  refilled, or the skip passed was `0`, every test would still pass. Spec 0019 §10.1 lookups hold
  up to `MaxIds` values each, so on a non-unique key path (or with the fixture's take ceiling of 50)
  this is a live path for the import.
- The nested overflow of deviation 7 (a grandchild chunk reaching the ceiling under a dependent
  chunk, `CompleteAsync`, `ExcelRowSource.cs:165-185`, under the recursive call at line 171). The
  integration case `A_collection_beyond_the_take_ceiling_is_completed_by_one_more_round_trip_its_rows_in_order`
  overflows the parts only. No case has a full grandchild chunk, so the skip arithmetic and the
  grouping that the implementer asked reviewers to examine hardest are not exercised at depth two.
- The `MaxIds` refusal of a by-ids source (`ExcelRowSource.cs:254-257`, deviation 3) is untested.
Fix: add unit cases to `test/core/Tellma.Core.Tests/Crud/ExcelRows/ExcelRowSourceTests.cs` on the
scripted rig. (a) Two lookups, one with a full first chunk: two batches, the second holding only
the full query at `Skip = MaxTake`, with the rows concatenated in order. (b) A root with a dependent
whose own dependent's first chunk is full: a follow-up over the dependent chunk's ids at
`Skip = MaxTake`, and the grandchild rows complete under the dependent. (c) `ByIds` with
`MaxIds + 1` ids refused as `LimitExceededException` before any batch.

**R1-3 (minor): a lookup target that no securable guards, and that no owner holds, is read
unrestricted, where §15 says it is read "under the caller's `Read` decision for its resource".**
`RowsComposition.Compose` (`RowsComposition.cs:103-115`) takes `TargetReads.Of`, whose last branch
(`src/core/Tellma.Core/Crud/TargetReads.cs:89-90`) answers `Unrestricted` for such an entity. A
direct decision on an unregistered resource is a denial (`AccessEvaluator.Unknown`). That is also
what the same composition's traversal rule uses through `Decide` (`RowsComposition.cs:198-207`), so
a path through such an entity is refused while a lookup rooted on it reads every row.
Failure: any `ExcelQuery` whose `RootEntity` is a mapped entity outside every stack and child
surface (a platform-internal table) returns its `[KeyPath, Id]` pairs, matched against caller-chosen
values, to any caller holding `Read` on the row source's stack. Sharing the save's reference
semantics may well be intended (an import should resolve what a JSON save resolves). But it departs
from §15's wording and is not listed. The commit describes the extraction only as "behaviour
unchanged".
Fix: either list it under Deviations (and in the README's row-source section) as "a lookup target
no grant can reach is read as a save's reference is, unrestricted", and raise it for a ruling.
Or, for `RowsRoot.Lookup`, treat `Securable is null` with no owner as denied (a lookup reads
nothing), and add a unit case either way.

**R1-4 (minor): `ByQuery.OrderBy = null` → `Id` follows §15/§18.2, but conflicts with spec 0019
§4.1 and 0015 §2.2, and the conflict is not flagged.**
The doc fix in `src/core/Tellma.Core.Abstractions/Excel/ExportSource.cs:52` matches §15
(`query.OrderBy ?? source.OrderBy ?? "Id"`) and the §18.2 pin ("an empty `ByQuery` in `Id` order").
But spec 0019 §4.1 says a display export "runs exactly the query `query` would run for the same
request", and `query` defaults to `DefaultOrderBy ?? "Id desc"` (0015 §5.2 step "Order"; §2.2 calls
`DefaultOrderBy` "the ordering an operation uses when the request names none"). §15 also says a
child surface's row source takes "its defaults the surface's", and the fixture's child surfaces
default to `Id desc`.
Failure: on any stack with a `DefaultOrderBy`, and on every child surface, a display export of an
unsorted grid lists its rows in a different order from the grid. The child-surface integration pin
passes only because its query names `OrderBy = "Id"` explicitly.
Fix: no code change is needed if §15 stands. Add the 0019 §4.1 / 0015 §2.2 tension to the deviation
text and to `decisions_for_orchestrator`, so the specs can be brought in line.

**R1-5 (minor): the README sentence now says the Excel row source is an authoring bug.**
`src/core/Tellma.Core/README.md:1343-1345` reads: an operation the stack does not serve "is an
authoring bug (`InvalidOperationException`), and so are the Excel row source and the import's
lookups". The intent is that they are built.
Fix: "… are built, and so are the Excel row source and the import's lookups (see …): an operation
the stack does not serve is an authoring bug (`InvalidOperationException`)."

**Checked, no finding:**

### Responses

- R1-1: fixed in the "PC-174: review 1 fixes" commit (child of dc83114f), per ruling D-176.
  `RowsNode.Shaped` ends every node's ordering with the entity's key unless its last top-level
  term (outside parentheses and quotes, its `asc`/`desc` dropped) already is the key
  (`RowsNode.TieBroken`). It applies to the root, every dependent and every lookup, so pages, chunk
  follow-ups and lookup waves all read under a total order. Pinned by
  `Every_ordering_of_a_page_and_its_dependents_is_ended_by_the_key` and the
  `An_ordering_that_does_not_end_with_the_key_is_ended_by_it` theory (unit), and by the integration
  case `Rows_that_tie_on_the_ordering_across_the_cuts_are_read_once_each`: 120 widgets of one kind
  ordered by `Kind` over three pages, and the first page's 76 parts ordered by `WidgetId` across
  the chunk and its follow-ups, each row read once and none missing. Recorded as deviation 11.
- R1-2: fixed in the same commit. `ExcelRowSourceCompletionTests` runs on the scripted rig over a
  new `ExcelRowsModel` (a sheet with lines that hold notes, two collections deep, `MaxTake = 3`,
  `MaxIds = 4`), because the query model has no grandchild collection. (a) Two lookups, one with a
  full first chunk: two batches, the second holding only the full query at `Skip = MaxTake` with
  its values rebound, and the rows concatenated in order. (b) A grandchild chunk that reaches the
  ceiling under a line chunk: one follow-up over the line chunk's ids (`IdList [11, 12]`) at
  `Skip = MaxTake`, and the notes complete under the lines. (c) A by-ids source with `MaxIds + 1`
  ids is refused as `LimitExceededException` (`MaxIds`) before any batch.
- R1-3: kept, per ruling D-176. A lookup is read as a save's reference is (`TargetReads`),
  including unrestricted for a target that no securable guards and no owner holds, so an import
  resolves exactly what a JSON save of the same rows resolves. Deviation 9 now explains this for
  a ruling, and the README's row-source section states it.
- R1-4: kept, per ruling D-176. A by-query source without an ordering reads in `Id` order, as §15
  and the §18.2 pin say. Deviation 2 now names the conflict with spec 0019 §4.1 and 0015 §5.2 and
  §2.2 (`DefaultOrderBy ?? "Id desc"`), and with the child surface's `Id desc` default.
- R1-5: fixed in the same commit. The README now says the reads, the save, the deletes and the
  actions are built, and so are the Excel row source and the import's lookups; an operation the
  stack does not serve is an authoring bug.
