- **Statements** (`src/core/Tellma.Core/Jobs/JobStatements.cs`), each on the internal channel with `core.Jobs` as its one declared write:
  - `Claim`: collects the rows the token already leases, computes `@room`, leases `TOP (@room)` due rows of one key with `READPAST, UPDLOCK, ROWLOCK` in `DueAt, Id` order (counting an attempt, stamping `StartedAt` once), and returns every row under the token. Idempotent, so an ambiguous failure re-runs it and the rows come back once.
  - `Renew`: extends every lease of the tenant by token through `JobLeaseList`, writes the buffered `JobProgressList` (null columns keep their stored values), returns the rows still leased with `CancelRequestedAt`.
  - `AppendProgress`: a fenced checkpoint inside the handler's own transaction.
  - `Complete`: records `JobOutcomeList` under the token; the TVP is bound when the batch is sent, so the worker fills the outcomes after the handler appended its statements.
  - The append and the completion throw `50422` / `Job.LeaseLost` when a row is no longer leased under the token.
- **Runtime** (`src/core/Tellma.Core/Jobs/`):

### Deviations

- **D-1. An `OperationCanceledException` is the worker's stop only when a token the worker handed out was cancelled.** Any other (a handler's own `HttpClient` timeout, say) is "threw anything else": `Retry` with `Jobs.Internal`. The §3.4 table maps every OCE to `Released`/`Retry(0)`, which would release a timing-out job forever without counting an attempt.
- **D-2. Once the host is stopping, any exception ends the invocation as its stop** (`Released` when unobserved, else `Retry(0)`), as D-056 carries.
- **D-3. `Retry → Failed` at `MaxAttempts` also applies to the `Retry(0)` of a guard failure and of a stop after progress.** The §3.4 rule is stated for every `Retry`. The consequence, kept for now and deferred to Ahmad (D-129): on a job's last allowed attempt, a guard failure (the tenant's `permissions` tag moved, which any role save does) or a host stop after the handler observed an item fails the job as `Failed/Jobs.AttemptsExhausted` with a `core.job.failed` notice, and its handler's work and enlisted writes are discarded, although nothing it did was refused. Spec §5.6 says the guard path exists so that the work re-runs under the new permissions; under the literal reading a third-attempt `core.import` (`MaxAttempts = 3`) fails on a role save or a deploy. An inline comment at `JobOutcomeRules.AfterGuardFailure` records the reading.
- **D-4. After a failed completion, the handler's marks are discarded** with the work they describe; every item follows the failure, except that a requested cancel still ends `Cancelled` (rule 3).
- **D-5. A `ValidationException` whose first code is longer than the 64-character `ErrorCode` column records `Jobs.Internal`;** arguments longer than their column are dropped. The spec is silent; a truncated code would name nothing.
- **D-6. Partitions that never started** (the host stopped or the lease was lost before their turn) complete `Released`, or record nothing when the lease was lost.
- **D-7. Partitioning is by run-as user and normalised confirmed keys,** not run-as user alone. Each job scope's `IConfirmations` is seeded from its jobs' `ConfirmedKeys`, so jobs that carry different consents cannot share a scope.
- **D-8. A user job scope's snapshot carries no `Subject`.** The connect initializer binds the user by id; the jobs table stores no subject.
- **D-9. `IJobProgress.Report` makes the checkpoint current at once** (spec line on `JobItem.State`), and a non-null value overwrites the buffered one; the Abstractions docs said the opposite and were corrected. `Append`'s checkpoint becomes current on commit only if no later `Report`/`Append` replaced it.
- **D-10. The completion batch is created before the scope token becomes the scope's,** so the completion executes uncancelled; the scope token is reset after the handler.
- **D-11. Rows completed without the handler run under a `settle <key>` span** (a child of the poll's activity, so `ErrorTraceId` is the poll's trace id).
- **D-12. `job.changed` after a renewal that wrote progress is published here** (`JobRenewal`), since `FlushAsync` is in scope; the `job.changed` after a claim stays with the worker.
- **D-13. The test driver lives in `Tellma.Testing.Entities`** beside `FixtureTenant`, which gained a one-tenant registry and a `compose` hook.
- **D-14. The administrators are looked up only when a notice has no requester;** a lookup failure is logged (`JobNoticeRecipientsFailed`) and the outcomes still complete.
- **D-15. Job frame seam fixes** (D-121/D-122): the Limits restore, the deferred count/release through `EndCompletion`, and `CompletionBroken`.
- **D-16. Two log events beyond the spec's list:** `JobScopeUnavailable` (`Warning`: the job scope could not be opened for a reason other than an unknown tenant or a stop; the lease lapses) and `JobNoticeRecipientsFailed` (`Warning`: D-14). A post-commit failure of the enlisted groups is logged as `JobCompletionFailed`; the commit stands.
- **D-17. `IJobProgress.Append` refuses `JobBatch.Batch`** with `ArgumentException` (review 1, R1-1). The completion statement runs first in that batch and releases the lease, so a fenced append behind it could only fail and loop the job as a lost lease; the completion records the reported checkpoint itself. The spec is silent; the refusal is documented on `IJobProgress.Append` and `JobBatch.Batch`.

### Rulings worth knowing

- **"Observed"** (for `Released` vs `Retry(0)`) means the handler called `Report`, `FlushAsync` or `Append` for the item, or marked it. Reading `State` does not count.
- **Amharic resources** are partial in this repo (217 of 424 keys); the new job codes are in English and Arabic only.
- **`JobEnqueueCodes`** (from the enqueue checkpoint) still have no resources; untouched here.
- **The constraint test** uses an enlisted insert: a save's update never writes a server-owned member, so a `JobId` set on an update would not reach the database.
- **The plan test** reads the actual plan (`SET STATISTICS XML ON`) of the parameterised claim: `SHOWPLAN_XML` returns nothing for an RPC call.

### Open risks

- **The completion-batch ordering.** The completion statement precedes the handler's statements, with its outcomes bound at send time. A handler statement that fails after the completion statement ran rolls the whole transaction back, which is the intent, but the translation of that failure depends on the executor attributing it to the right statement.
- **The renewal's verdicts** (`JobRenewal.Judge`) are unit-tested over real leases (a row absent or under another token losing the whole lease and no other, a returned cancel stopping its item alone, `Completing` rows not judged), and a flush's renewal is integration-tested for a row claimed elsewhere and for a requested cancel. The renewal loop and its timing belong to the worker checkpoint.
- **Two §5.6 branches have no integration test:** the in-transaction `50401` (`CallerInvalid`) and the `50412` (`StaleVersionTag`) re-checks. Each needs a write that lands between the connect prologue and the transaction's first statement of one round trip, which no test can place deterministically; the `50401` branch shares `InactiveAsync` with the tested connect-time inactive path, and the `50412` branch shares `GuardFailedAsync` with the tested guard failure.
- **The plan test** depends on the optimizer choosing the filtered seek on 40,000 rows; it does today on LocalDB (SQL Server 2022).

### What reviewers should examine hardest

1. `JobRunner.SendAsync` and `FreshAsync`: every §5.6 branch, especially the guard-failure fresh batch and what happens to the frame's reservations (`EndCompletion`) on each path.
2. `JobOutcomeRules.Decide` and `JobEnding.Of`: the OCE classification (D-1, D-2) and the remap after a failed completion (D-4).
3. `JobItemProgress.Append` and the state version check: a promotion that races a later `Report`.
4. `JobStatements.Claim`: the token re-collection, `@room`, and the locking hints under RCSI off.
5. `OpenWriteFrame.AppendAsync` / `RunAsync`: the deferred count and release, and the Limits restore.

#### Major

**R1-1 (major). `IJobProgress.Append` onto `JobBatch.Batch` always trips the lease fence and loops
the job as a "lost lease".**
`src/core/Tellma.Core/Jobs/JobRunner.cs:413` appends the completion statement to the completion
batch before the handler runs, and `src/core/Tellma.Core/Jobs/JobItemProgress.cs:105-158` accepts
any `DataBatch` in `Auto` mode, `JobBatch<TItem>.Batch` included.
- *Failure scenario.* A handler checkpoints its final step with
  `item.Progress.Append(batch.Batch, 100, msg, state)`. That is a natural call, since spec §3.6
  says "or `Append` inside its own transaction". In the completion round trip, the completion
  statement runs first and sets `LeaseToken = NULL` and `Status <> 'Running'`. The append's
  `WHERE [LeaseToken] = @token AND [Status] = 'Running'` then matches 0 rows and throws `50422
  Job.LeaseLost`. The whole transaction rolls back. `SendAsync` maps the error to
  `JobSettlement.LostLease` (line 557) and logs `JobLeaseLost`. The rows stay `Running` under a
  lease nobody tracks, lapse, and are re-claimed. Every attempt repeats this until the claim fails
  the row with `Jobs.AttemptsExhausted`. The handler's work never commits, and the log blames
  another instance.
- *Fix.* Hand `JobItemProgress` the item's completion batch, and have `Append` throw
  `ArgumentException` when `ReferenceEquals(batch, completion)`. The message should say that the
  completion records the item's `State` itself, and the `RecordingBatch` replay target needs the
  same check. Then add one sentence to the TSDoc of `IJobProgress.Append` and `JobBatch.Batch`, and
  a unit test or integration test for the refusal.

**R1-2 (major). The worker side of the renewal (spec §5.2) is untested, and the implementer notes
say it is unit-tested.**
`src/core/Tellma.Core/Jobs/JobRenewal.cs:68-130` holds the verdicts that make leases safe:
- a judged row that is missing, or returned under another token, calls `lease.Lose()`;
- a returned `CancelRequestedAt` calls `RequestCancel`;
- `Completing` slots are skipped;
- carried rows are cleared by version, and `job.changed` is published for each carried row that has
  a requester.

No test calls `JobRenewal`. The only grep hits are the integration flush happy path
(`JobRunTests.cs:99`) and fakes. `JobLeasesTests` covers `Lose` and `RequestCancel` directly, not
the renewal's decision to call them. The implementer's open-risk line ("exercised only in unit
tests here") is therefore wrong.
- *Failure scenario.* A regression of any kind would pass every gate. Examples: judging by
  `Id` without the token, judging `Completing` slots, or clearing the buffer without the version.
  Such a regression either runs a job twice concurrently (a lost lease goes unnoticed) or fails a
  completing batch spuriously.
- *Fix.* Add integration tests through the driver, under RCSI on and off:
  - (a) The handler moves its row to another token and calls `FlushAsync`. Assert that the item's
    `CancellationReason` is `LeaseLost`, that `ScopeToken` is cancelled, and that the poll reports
    `LostLease` with nothing recorded.
  - (b) The handler stamps `CancelRequestedAt` and calls `FlushAsync`. Assert that the item token is
    cancelled with `CancelRequested`, that the scope token is not cancelled, and that the job ends
    `Cancelled` with `Jobs.Cancelled`.
  - (c) Add a unit test or integration test showing that a slot marked `Completing` whose row is
    gone does not lose the lease.

  Correct the open-risk note.

#### Minor

**R1-3 (minor). Completions without a handler of tracked partitions never mark their slots
`Completing`, so a concurrent renewal can lose the whole claim.**
The affected paths are in `src/core/Tellma.Core/Jobs/JobRunner.cs`:
- lines 315-319: the host is stopping, so a partition that never started is released;
- lines 361-371: an inactive run-as user at connect, or the scope token cancelled while
  connecting;
- `InactiveAsync` at line 668 on those paths.

Each of these completes rows that are still in the lease's `_slots` and not `Completing`, and
`Leave` runs only in the `finally` at line 333.
- *Failure scenario.* A claim has partitions P1 (user A, now inactive) and P2 (user B). P1 completes
  `Failed/Jobs.UserInactive`. Before its `Leave`, a renewal runs: another handler of the tenant
  calls `FlushAsync`, and PC-100's loop will do the same. The renewal does not find P1's rows, so
  `JobRenewal` calls `lease.Lose()`. P2 then returns `LostLease` at line 310. Its rows stay leased
  until they lapse and are re-run with an attempt counted, and a spurious `JobLeaseLost` is logged.
  On the stop path, later partitions lose their uncounted release the same way.
- *Fix.* Call `BeginCompleting()` on the partition's slots before each of these completions, as the
  main path does at line 483. Add a unit test for the renewal verdict (with R1-2 (c)).

**R1-4 (minor, for Ahmad). D-3 makes a guard failure on a last attempt a permanent failure.**
`JobOutcomeRules.AfterGuardFailure` (`src/core/Tellma.Core/Jobs/JobOutcomeRules.cs:122-127`) runs
`Exhausted` over the guard's `Retry(0)`. The guard fails whenever the tenant-wide `permissions` tag
moves, which any role save causes (see the test at `JobRunTests.cs:297`).
- *Failure scenario.* An administrator saves a role while a `core.import`
  (`MaxAttempts = 3`, spec 0019 §12.4) is on its third attempt. The import's enlisted `Import`-row
  write is discarded, and the job ends `Failed/Jobs.AttemptsExhausted` with a `core.job.failed`
  notice, although nothing it did was refused. Spec §5.6 says the guard path exists so that "the
  work re-runs under the new permissions".

  D-3 follows §3.4's last sentence literally, so this is not a code defect.
- *Suggested fix.* Exempt the guard-failure retry from exhaustion, or give its attempt back while
  keeping the checkpoint, which the outcome table has no row for today. Otherwise, record the
  literal reading as a spec question for Ahmad. Apply the same treatment to the `Retry(0)` of a stop
  after progress, where a deploy fails a third-attempt import.

**R1-5 (minor). Several §5.6 completion paths that the checkpoint lists have no test.**
