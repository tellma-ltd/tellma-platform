# PC-078: Write side: guards, validators, companion insert, preference bag, bootstrap, drift scanner

## Implementer notes

### What was built, and where

All under `src/core/Tellma.Core/Access/` unless noted.

- **Guards** (`AccessGuards.cs`, replaces `NullAccessGuards`). `ContributeLock` appends, at
  `BatchSection.TransactionHead`, `sp_getapplock 'tellma.access'` (exclusive, transaction-owned,
  `@LockTimeout` = `SecurityLockTimeout` rounded up to whole ms and capped at `int.MaxValue`);
  `-3` → `THROW 50503 Access.LockDeadlock`, any other negative → `THROW 50503 Access.LockTimeout`
  (transient, so the executor retries). `ContributeInvariants` appends L1-L3 as `THROW 50422`
  (`Access.LastAdministrator`, `Access.PublicRoleHasMembers`, `Access.AdministratorRoleDamaged`).
  Each is added once per batch (a `ConditionalWeakTable` of marks), so the pipeline and the
  enlistment engine can both call them. Metering goes through a new internal seam:
  `DataBatch.OnServerErrors(observer)`, which `DataExecutor.RunAsync` calls with each failed
  attempt's `SqlErrorInfo` list after classification. Observer failures are logged
  (`FailureObservationFailed`) and contained. The guards count `tellma.access.guards.triggered` by
  `guard` and log `GuardTriggered` (3103).
- **Validators.** `UserAccessRules<TUser>` and `RoleAccessRules<TRole>` (internal sealed). They
  cover every Appendix A code the two stacks own, and implement `ValidateDeleteAsync` and
  `ValidateActionAsync` for activate and deactivate.
  - `AccessDelegation.cs` holds the escalation test: (R,*) and (*,A) are covered only by the same
    wildcard or */*; for Read, also any action on R, or (*,A') where R registers A' (D-073). It
    exempts the system set and */* holders.
  - `AccessRefusals.cs` holds the shared path and metering helpers: self-protection refusals count
    as `self_deactivation`, `self_deletion` and `own_administrator_membership`; an escalation counts
    as `escalation` and logs `EscalationRejected` (3104).
  - The codes are in `Tellma.Core.Abstractions/Access/AccessCodes.cs`.
  - §3.7 rule 1 refuses (*, A) when no resource registers A (PC-043 D5).
- **Companion insert** (`UserStampsCompanion.cs`). An `IPersistEffect<TUser>` over `save.NewIds`
  writes both tags as `@tm_tag`, `InboxVersion` 0, and nulls elsewhere. It is idempotent
  (`NOT EXISTS`, `idempotent: true`).
- **Preference bag** (`UserPreferenceStatements.cs`). `Set`, `Delete` and `Replace` statement
  shapes, each for the caller (`@tm_UserId`, `SqlOptions.ForCaller`) or for another user (id bound,
  plus a one-row `IdList` as `userIds`, so the epilogue bumps that user's `PreferencesTag`). The
  `TooManyPreferenceKeys` assertion follows the insert. `Check` and `CheckKeys` do the C# item
  checks: grammar, duplicate and `PreferenceValueTooLarge`. No service calls these yet; 0018's
  `me/preferences` actions will.
- **Bootstrap.**
  - `TenantBootstrapper<TUser>` (behind `ITenantBootstrapper`): System scope only, idempotent on
    the normalised email, saves through `EntityService<TUser>` with `SaveSource.System`.
  - `BootstrapSubject` plus `BootstrapSubjectEffect<TUser>`: a scoped holder and a users-stack
    persist effect that writes `Subject`, `InvitedAt` and `InviteStatus = 'Invited'` on the created
    row in the same save. This is the Development-only path.
  - `BootstrapAdministratorStep`: `core.bootstrap-administrator`, order 10, named by the email's
    local part, `languages.Offered[0]`.
- **Drift scanner** (`PermissionDriftScanner.cs`). One read of every permission joined to its role,
  classified by the same `PermissionClassifier` the sets use. The one scoped instance is both
  `IPermissionDriftScanner` and the migrator's existing `ITenantDriftReport`, which prints
  `Permission {id} of role {role} ({code}) grants nothing: {Problem}; {diag} k=v ….`
- **Shells and the feature.**
  - `src/core/Tellma.Core/Users/UserService.cs` (declares `IEnlists<TUser>` for the self-service
    pair) and `RoleService.cs`.
  - `CoreFeature` registers `Entity<User, UserService<User>>`, `Entity<Role, RoleService<Role>>`,
    both validators, both persist effects and the step.
  - `AccessRuntimeComposition` registers the guards, the bootstrapper closed over the user leaf,
    the held subject and the scanner.
- **Telemetry names and constants.** `AccessTelemetryNames` gains the `Guard*` values;
  `ReservedSqlNames.SecurityLock` (`@tm_Lock`) is new.
- **Docs.**
  - `Tellma.Core` README gains a new section, "The access write side".
  - The `Tellma.Core.Abstractions` README lists the new types.
  - Both test READMEs are updated.
  - ARCHITECTURE.md needed no change: nothing it says disagrees.

### Where this meets PC-077 (slot pc-3)

- PC-077's `PersistAsync` calls the guards "over the union of writes". `AccessGuards` is idempotent
  per batch, so a group-wise or repeated call adds the lock and the invariants once. The pipeline's
  current decision looks only at the stack's own tables; the union decision belongs to PC-077.
- `UserService<TUser>` declares `IEnlists<TUser>` (the `users/me/save` self-pair). PC-077's
  enlistment engine and `core.enlistments` read it.
- `BootstrapSubjectEffect` writes `core.Users` from inside the users' own stack, never raw. Once
  PC-077's append-authority check lands, a raw write to a stack-owned table from outside its stack
  is refused.

### Open risks

- **Delete by query bypasses `ValidateDeleteAsync`.** This is the pipeline's existing behaviour.
  The user and role delete rules (self-deletion, system user, `OnlyNewUsersDeletable`,
  `HasMembers`, the administrator role) are then held only by L1-L3 and the FKs. L3 holds the
  administrator role, and the audit FKs refuse a referenced user. Self-deletion by query of a `New`
  caller is impossible, since a `New` user has no subject to connect with. Worth a ruling on
  whether delete-by-query of users and roles should be refused or validated.
- **A deployed bootstrap leaves the administrator `New`** (no subject or invitation), so L1 is
  unsatisfied until the invitation. Any non-System security write on such a tenant is refused by
  L1 until then. This is by design (L1 counts invited or joined only); 0011's run invites right
  after step 10.
- **An existing but inactive user is not reactivated** by the bootstrap. It gains the membership
  but L1 stays unmet. The spec is silent on this.
- **Load flake.** `TenantScopeTests.A_tenant_whose_database_is_missing_fails_its_open_at_once…`
  failed once under a parallel load (expected 4060). It passes alone, and its code is untouched
  here.

### Blocked commands

- **One command was blocked by the permission system and was not retried:**
  `powershell.exe -NoProfile -Command "Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -like '*pc-1*' -and $_.CommandLine -like '*test*' } | …"`.
  - Its purpose was to check for a leftover testhost after a stopped `--no-build` unit run.
  - Later full builds succeeded, so no DLL was left locked.

### What reviewers should examine hardest

- The L1 text in `AccessGuards.InvariantsText`: started and permanent only, the individual kind,
  active, `Invited` or `Joined`. Also the lock's position relative to the version-tag guard and the
  caller re-check (`TransactionHead`).
- `RoleAccessRules`'s stamping matrix and escalation scope: new or changed rows, all rows on
  becoming public, and unchanged rows exempt.
- `UserAccessRules.CheckOwnAdministratorMembership` and `Removal`. Ended memberships are free; a
  cleared `EndsAt` passes; a moved start past now, a new or moved end, or a role change are refused.
- The `DataExecutor` observer call site: once per failed attempt, retried attempts included, before
  a retry or the surface.
- `TenantBootstrapper.Grant`: the replacement row's `StartsAt` is the last ended row's end, so the
  windows never overlap.

R1-1 (major): **Delete-by-query skips every user and role delete rule.**
- **Where.** `src/core/Tellma.Core/Crud/Delete/DeleteRun.cs:234` sets
  `_hooked = _shape != DeleteShape.ByQuery && …`. So `UserAccessRules.ValidateDeleteAsync`
  (`UserAccessRules.cs:86-113`) and `RoleAccessRules.ValidateDeleteAsync` never run for
  `delete-by-query`. Both stacks project that operation (`StackOperations.All`).
- **Roles are backstopped.** `FK_RoleMemberships_RoleId` refuses a role with members, and L3
  refuses role 1.
- **Users are not.** `Users.CannotDeleteSelf` and `Users.OnlyNewUsersDeletable` have no backstop
  when no audit FK references the row.
- **Failure scenario.**
  - Take a `Joined` user who signed in but never authored or modified a row. The join flip leaves
    `ModifiedById` alone, and `UserStamps` and `UserPreferences` cascade.
  - That user can be deleted by query.
  - This includes the caller deleting themselves, given `Delete` on `core.User` and another
    administrator remaining.
- **Spec.** Spec 0015 §16.2's budget row ("Delete by ids / by query / with descendants | 1 |
  `ValidateDeleteAsync` overridden (→ 2)") reads as by-query validating too. Spec 0014 §3.9
  exempts no delete shape.
- **Ruling on open point 1: validate.**
  - On a stack whose service or a component overrides `ValidateDeleteAsync`, run by-query on the
    general path.
  - RT1 collects the matching keys `TOP (cap + 1)` under `And(filter, Delete grant)` and loads the
    targets.
  - `ValidateDeleteAsync` runs over them.
  - RT2 deletes `ByIds` with those ids, and the count is checked against `ExpectedCount`.
- **Interim fix** if that is too large for the fix round: the users and roles stacks refuse
  `delete-by-query` with a closed-set code.
- **Either way, add an integration test.**
  - Deleting a joined, never-referenced user by query is refused with
    `Users.OnlyNewUsersDeletable`.
  - The caller deleting themselves by query is refused with `Users.CannotDeleteSelf`.

R1-2 (minor): **The guard decision reads the stack's tables, not the batch's writes.**
- **Where.** `SaveRun.Persist.cs:133`, `ActionRun.Persist.cs:201` and `DeleteRun.Persist.cs:203`
  decide `guarded` from `StackTables`. Spec 0014 §8.3 calls the guards on every Persist batch
  "whose `WrittenTables` meets" a security table.
- **Failure scenario.**
  - A participant of a non-security stack writes `core.RoleMemberships` or `core.Users` raw,
    through an `IPersistEffect`, `OnPersist` or an action method's statements.
  - That write runs without the security lock and without L1-L3.
  - Append authority does not stop it today, because the table owners are still
    `NoStackTableOwners` (D-114).
- **Severity.** No current path does this, so this is minor. But this checkpoint is the one that
  makes the guards real.
- **Fix.**
  - The lock goes to `BatchSection.TransactionHead` wherever it is appended.
  - So at the invariants step, compute
    `guarded = !IsSystem && WritesSecurityTable(StackTables.Concat(batch.WrittenTables))`, and call
    both `ContributeLock` and `ContributeInvariants` then.
- **Open point 4.** This rule also answers PC-077's union over enlisted groups. Land it here, or
  carry it explicitly to PC-077 as the rule to adopt.

R1-3 (minor): **The bag's key cap is not race-free for another user's bag.**
- **Where.**
  - The remark at `UserPreferenceStatements.cs:34` says the version-tag guard serialises
    concurrent writes "on the user's stamp row".
  - But `PersistChecks.cs:174` takes `UPDLOCK` only on the caller's own stamp row
    (`@tm_UserId`).
- **Failure scenario.**
  - An administrator's `ForUser` write (`UserPreferenceStatements.cs:216`) races the owner's own
    write, or a second administrator's. The two writes lock different stamp rows.
  - Under RCSI, each statement's `COUNT(*)` misses the other's uncommitted inserts.
  - So both can pass on a bag one key short of `MaxPreferenceKeys`.
- **Test gap.**
  `Two_concurrent_writes_of_one_bag_serialise_on_its_owner_s_stamp_row_so_the_key_cap_holds`
  covers only two writes by the caller.
- **Fix.**
  - Lead the three `ForUser` shapes with
    `SELECT @x = 1 FROM [core].[UserStamps] WITH (UPDLOCK, ROWLOCK) WHERE [UserId] = {id};`.
    This serialises with the owner's persist, which holds that row under `UPDLOCK` from its head.
  - Add the administrator-versus-owner race to the test.
  - Otherwise, narrow the remark to the caller's own writes and list the overshoot as a deviation.

R1-6 (minor): **Bootstrapping an existing, deactivated user silently leaves the tenant locked**
