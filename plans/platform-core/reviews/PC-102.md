# PC-102: queryex/discover server endpoint

## Implementer notes

### What was built

Spec 0029 §9: `POST /{tenantId}/api/web/queryex/discover`, a member-only, idempotent read with no
securable, hidden from MCP, projected through the route model and the access witness like every
other routed action.

- **Wire records** (`Tellma.Core.Abstractions/Api/`). `QueryexDiscoverRequest`,
  `QueryexParameterInput`, `QueryexProfile` (`query`, `permission`), `QueryexDiscoverResult`,
  `QueryexParameterInfo`, `QueryexPathInfo`, `QueryexSite` and `QueryexConjunct` (its literal a
  `JsonElement` in the wire's own encoding). Both top-level records are in `TellmaApiJsonContext`.
- **`QueryexTypeJsonConverter`**, first in `TellmaJson`'s converter list. A `QueryexType` is written
  as its name without the `Qx` prefix (`Date`, `Numeric`) and read case-insensitively; the prefixed
  name, a number, an undefined value and null are refused. `QueryRowSetJsonConverter`'s column
  types and `ContractDescriber`'s enum description use the same names, so the row set, the
  discovery answer and the route fingerprints cannot disagree.
- **The service** (`Tellma.Core/Api/QueryexService.cs`, `[ApiRoute("queryex")]`, registered in
  `CoreFeature`). The steps run in the spec's order:
  1. Admission (`Api/DiscoverShape.cs`), with no I/O: the root (blank is 400, unknown in the widest
     schema or the tenant's schema is 404), the profile, the measures, a having without an
     aggregate, the confirmed parameter types, and the permission profile's single filter.
  2. The caller's connection (`IScopeConnection.CurrentAsync`): no round trip when it is cached.
  3. Query profile: `DiscoverQuery` and `CompileQuery` under the pipeline's ceilings, over the
     caller's clauses only, with the confirmed types declared (else the inferred ones, when they do
     not conflict). The compile's diagnostics are located exactly as the query locates them
     (`QueryDiagnostics.Locate` over a `CompositionMap` of user filters), carried to the wire
     through the new `QueryWireDiagnostics`, and an undeclared parameter (QX3007) is left out.
  4. Query profile: the traversal rule's new `Refusals` (the walk without the step-up) decides each
     path from the connected user's set. A refused path is `reachable: false` and adds a
     `Query.PathNotReachable` diagnostic at the path's own site, with `entity` and `path`.
  5. Permission profile: `PermissionFilterRules.Check`, extracted from `RoleAccessRules.CheckFilter`
     so the role save and the editor judge a filter with the same code. Too long is a
     `FilterTooLong` diagnostic over the excess; the engine's diagnostics are carried verbatim
     (QX3007 included, since a stored filter takes no parameters); invalid with no diagnostic is a
     bare `FilterInvalid`.
  6. The answer: each parameter with its sites, type, conflicts, the paths it is compared with, and
     the entity a key or foreign key it meets identifies; each path with its entity; and, when
     asked, each filter's top-level comparisons with their literals.
- **`QueryDiagnostics.LocateSite`** places a discovery site (a location in the composed filter) in
  the caller's clauses, the same way `Locate` places a diagnostic. `CallerFilterClause` is public.
- **`QueryWireDiagnostics`** maps a located location to the wire's clause and item: `filters[i]`
  and `namedFilters[i]` with the path below the root, `select`/`orderBy`/`measures` with the
  engine's item, `having` with the path below it, and a location in no clause placed where the
  query places it.

### Deviations

1. The guarded runner runs only when a prologue is due. A runner with no statement still executes
   its prologue batch, so discovery reads the caller through `IScopeConnection.CurrentAsync` and
   runs the runner's prologue-only batch only when `IScopeConnection.IsPrologueDue` holds (no
   prologue confirmed the set within the fast-deny window, the set is past its maximum age, or an
   activity stamp is due). No round trip when warm and confirmed; one otherwise (review 1, R1-1).
2. The service is `internal sealed`: its constructor takes internal types (`SettingsService` is the
   precedent).
3. Measures are deferred: non-blank `measures` is 400 (with an aggregate, "not supported yet";
   without, "an aggregate query only").
4. A filter leaf's wire `location` is null, by `QueryDiagnostic`'s own rule, where the spec's
   example shows the engine's `Filter.And[0]`. The select and the ordering are each one text, so
   the engine locates their diagnostics at the clause and the wire location is null too.
5. With no select, the compile selects the root's key by its own name, not a literal `Id`.
6. Discovery's own diagnostics are not added to the answer, so it equals what the query refuses.
7. A having without an aggregate, a confirmed parameter that is unnamed, named twice, or typed as a
   hierarchy position or geography, and any clause but one filter in the permission profile are
   each 400.
8. The permission profile keeps QX3007, reports `FilterTooLong` over the excess span, and marks
   every path reachable (a stored filter is not held to the editor's own access).
9. A sensitive path is reachable and asks for no step-up; a filtered grant's refusal is the only
   unreachability.
10. A root the caller cannot read is not special-cased: the root's own columns are not decided, only
    the navigations past it, as the traversal rule decides them for a query.
11. `QueryexType` is written without the `Qx` prefix everywhere through one converter. This changes
    the enum's description in contract fingerprints.
12. `PermissionFilterRules` is extracted from `RoleAccessRules`, so the two cannot disagree.
13. The compile omits named filters, the platform's conjuncts and the access filter, as the spec's
    `QuerySpec` does.

### Open risks

- `QueryWireDiagnostics` is the edge mapping from a located `QueryexDiagnostic` to
  `QueryDiagnostic`. PC-081 builds the same mapping for `InvalidQueryException`; the two should
  converge on this class when both land.
- The `Refusals` walk duplicates `Check`'s decisions without the step-up. If the traversal rule
  gains another refusal kind, both must take it.

### What reviewers should examine hardest

- That the query profile's diagnostics equal the query's for the same clauses, including a
  location the engine gives no clause (the ceilings), and that QX3007 is the only code dropped.
- `PermissionFilterRules` against the previous `RoleAccessRules.CheckFilter`: order (length first,
  then the missing root), codes and arguments.
- `LocateSite` and `Place` for named filters, nested filter paths and the having clause.
- The cached-connection path: nothing in discovery may open a batch when the connection is warm.

**R1-1 (major): warm discovery never re-validates the caller, so a deactivated member keeps a
200 answer with no time limit.**
`src/core/Tellma.Core/Api/QueryexService.cs:83` (and the member-only admission it relies on,
`src/core/Tellma.Core/Crud/Actions/ApiActionInvoker.cs:139`). Admission is
`IScopeConnection.CurrentAsync`. For a warm subject it returns the `ConnectCache` entry, and
that entry has no expiry: `ConnectCache` has no TTL, and `UserConnector.cs:114` documents that
"every batch's prologue re-validates it". Discovery runs no batch, so no prologue ever runs.
Nothing evicts the entry when a user is deactivated: `AccessEvaluator.Invalidate` has no caller
in `src/`, and `Drop` runs only from a prologue's or a persist's refusal.
- Scenario: user U has a warm entry on instance A. An administrator deactivates U, or removes U's
  membership, on any instance. U then calls only `queryex/discover` on A. Every call answers 200
  with the root's paths, the entities that parameters identify, and reachability decided from U's
  pre-deactivation set, indefinitely. Through the guarded path (`settings/client`, any query),
  the first prologue answers `TenantNotFoundException` (404).
- The same gap also skips three things. The fast-deny re-check is skipped, so a path a fresh
  grant now admits stays `PathNotReachable`, while `query` would re-check and succeed. A set past
  `PermissionsMaxAge` is never reloaded. Activity is never stamped, although spec 0029 §9 says
  the endpoint "stamps activity" and the throttle in `UserConnector.StampAllowed` expects a
  prologue to do it.
- A non-member (no entry for the tenant and subject, so a cold connect) and a tenant-not-found
  caller (refused at the edge or by the cold connect) do get the same answer as the guarded path.
  Only the warm, revoked case differs.
- Fix: keep 0 round trips only for a recently validated set. After `CurrentAsync`, if
  `time.GetUtcNow() - user.Access.ValidatedAt > AccessOptions.FastDenyWindow` (or the set is aged,
  or a stamp is due), call `connection.RevalidateAsync(user, ct)`. That is one prologue-only round
  trip: it throws `TenantNotFoundException` for a deactivated user, stamps when due, and advances
  `ValidatedAt`. Use the returned user for the decisions.
- Tests: an integration test that warms U, deactivates U in an administrator scope, advances the
  clock past the window and expects `TenantNotFoundException`, next to the existing
  zero-round-trip test (inside the window).

**R1-2 (minor): the permission profile's length rule measures untrimmed text, while the role save
trims first.**
`src/core/Tellma.Core/Api/QueryexService.cs:203-221`. `SaveRun` (`Crud/Save/SaveRun.cs:353-366`)
trims every written string that is not `[PreserveWhitespace]`, and `Permission.Filter` is not
marked. So `RoleAccessRules` judges the trimmed text, but discovery passes `shape.Filters[0].Text`
as sent.
- Scenario: a filter of exactly `MaxFilterLength` characters, followed by a trailing space or
  newline from the editor, is reported `Permissions.FilterTooLong`, yet the role save accepts it.
  This breaks "validates its filter as role save does" (spec 0029 §9 step 3) at the boundary.
- Fix: apply the length rule to the trimmed text (for example, pass `filter.Trim()` to
  `PermissionFilterRules.Check` and add the leading-whitespace count back to every span, so ranges
  still index the editor's text).
- Test: at the boundary with surrounding whitespace, assert no `FilterTooLong` and compare
  against `PermissionFilterRules` on the trimmed text.

**R1-3 (minor): `QueryDiagnostic.Code`'s contract no longer covers the codes discovery answers.**
`src/core/Tellma.Core.Abstractions/Api/QueryDiagnostic.cs:18` says a code is "a compiler code
such as QX3001, or one of the pipeline's Query.* validation codes". The permission profile now
answers `Permissions.FilterTooLong` and `Permissions.FilterInvalid`
(`QueryexService.cs:216-231`), and spec 0029 §9 "Messages" names only the `Queryex_<code>` and
`Query_*` keys for the client.
- Scenario: a client written to that contract (`TmServerText.message` over `Queryex_`/`Query_`)
  has no key for these two codes, and the record's own docs say it cannot happen.
- Fix: widen the XML doc to name the role save's permission-filter codes. State the spec-0029
  Messages gap under Deviations so the spec can be aligned. This needs no code change if the
  client's renderer is keyed generically by code.

**R1-4 (minor): one touched integration suite is missing from the commit's test list.**
`Tellma.Core.Abstractions` changed, so under PLAN.md §7.1 item 4 every integration suite counts
as touched. That includes `test/core/Tellma.Core.Testing.Tests`, whose
`SqlDatabaseCreationServerTests` and `SqlDatabaseDropServerTests` carry `Category=Integration`.
The commit message lists Core, EFCore, Queryex, Identity, Acme and connectors, but not this suite.
The reviewer ran it (4/4 green), so there is no defect.
- Fix: name it in the integration message's suite list.

### Responses

All fixes are in the "PC-102: review 1 fixes" commit (child of c586d072).

- **R1-1: fixed.** `IScopeConnection` gains `IsPrologueDue(user)`, implemented by `UserConnector`
  from its own rules: the set's `ValidatedAt` is older than `FastDenyWindow`, the set is past
  `PermissionsMaxAge` (`IsAged`), or, for a connection by subject, `StampAllowed` holds. When it

  `TenantNotFoundException` after one round trip); the zero-round-trip test now runs on the same
  frozen clock, so a slow machine cannot push it past the window; unit
  `A_caller_the_cache_cannot_vouch_for_is_confirmed_by_one_prologue_only_batch_whose_set_decides`
  (a due prologue whose guard finds a fresh grant: two statement-less read batches, and the path

  (a filter at the maximum once trimmed, padded past it, answers nothing; an indented broken filter

  `Permissions.FilterTooLong` and `Permissions.FilterInvalid`. Deviation for the spec: spec 0029 §9
