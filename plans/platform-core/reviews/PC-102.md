# PC-102: queryex/discover server endpoint

## Implementer notes

### What was built

Spec 0029 §9: `POST /{tenantId}/api/web/queryex/discover`, a member-only, idempotent read with no
securable, hidden from MCP, projected through the route model and the access witness like every
other routed action.

- **Wire records** (`Tellma.Core.Abstractions/Api/`). `QueryexDiscoverRequest`,
  `QueryexParameterInput`, `QueryexProfile` (`query`, `permission`), `QueryexDiscoverResult`,
  `QueryexParameterInfo`, `QueryexPathInfo`, `QueryexSite` and `QueryexConjunct` (its literal a
  `JsonElement` in the wire's own encoding). Both top-level records are in `TellmaApiJsonContext`.
- **`QueryexTypeJsonConverter`**, first in `TellmaJson`'s converter list. A `QueryexType` is written
  as its name without the `Qx` prefix (`Date`, `Numeric`) and read case-insensitively; the prefixed
  name, a number, an undefined value and null are refused. `QueryRowSetJsonConverter`'s column
  types and `ContractDescriber`'s enum description use the same names, so the row set, the
  discovery answer and the route fingerprints cannot disagree.
- **The service** (`Tellma.Core/Api/QueryexService.cs`, `[ApiRoute("queryex")]`, registered in
  `CoreFeature`). The steps run in the spec's order:
  1. Admission (`Api/DiscoverShape.cs`), with no I/O: the root (blank is 400, unknown in the widest
     schema or the tenant's schema is 404), the profile, the measures, a having without an
     aggregate, the confirmed parameter types, and the permission profile's single filter.
  2. The caller's connection (`IScopeConnection.CurrentAsync`): no round trip when it is cached.
  3. Query profile: `DiscoverQuery` and `CompileQuery` under the pipeline's ceilings, over the
     caller's clauses only, with the confirmed types declared (else the inferred ones, when they do
     not conflict). The compile's diagnostics are located exactly as the query locates them
     (`QueryDiagnostics.Locate` over a `CompositionMap` of user filters), carried to the wire
     through the new `QueryWireDiagnostics`, and an undeclared parameter (QX3007) is left out.
  4. Query profile: the traversal rule's new `Refusals` (the walk without the step-up) decides each
     path from the connected user's set. A refused path is `reachable: false` and adds a
     `Query.PathNotReachable` diagnostic at the path's own site, with `entity` and `path`.
  5. Permission profile: `PermissionFilterRules.Check`, extracted from `RoleAccessRules.CheckFilter`
     so the role save and the editor judge a filter with the same code. Too long is a
     `FilterTooLong` diagnostic over the excess; the engine's diagnostics are carried verbatim
     (QX3007 included, since a stored filter takes no parameters); invalid with no diagnostic is a
     bare `FilterInvalid`.
  6. The answer: each parameter with its sites, type, conflicts, the paths it is compared with, and
     the entity a key or foreign key it meets identifies; each path with its entity; and, when
     asked, each filter's top-level comparisons with their literals.
- **`QueryDiagnostics.LocateSite`** places a discovery site (a location in the composed filter) in
  the caller's clauses, the same way `Locate` places a diagnostic. `CallerFilterClause` is public.
- **`QueryWireDiagnostics`** maps a located location to the wire's clause and item: `filters[i]`
  and `namedFilters[i]` with the path below the root, `select`/`orderBy`/`measures` with the
  engine's item, `having` with the path below it, and a location in no clause placed where the
  query places it.

### Tests

- `Tellma.Core.Tests/Api/QueryexServiceTests` (QueryRig, through `IApiActionInvoker`): the same
  diagnostics as the query for the same clauses; clause placement; parse failures still answering
  paths; the having clause; inferred and confirmed types, conflicts, unconstrained parameters,
  sites and identified entities; a filtered grant's refused path; a sensitive path asking for no
  step-up; conjuncts across filters; the permission profile against `PermissionFilterRules`, too
  long, valid and blank; 404; 13 malformed requests refused with no batch; no batch composed.
- `RouteContractsTests`: the route is member-only, idempotent, hidden from MCP and has no

- `Tellma.Core.Abstractions.Tests`: the converter order, the two records' metadata, the request's
  defaults, the result's JSON (unprefixed type names, nulls omitted), a decimal literal's encoding,
  and `QueryexType`'s names, case-insensitive reading, dictionary keys and refusals.
- `Tellma.Core.IntegrationTests/Crud/QueryexDiscoverTests` (real tenant database): 404 and 400

  inferred parameters; a tree position refused by a filtered grant on the nodes; the permission
  profile's codes equal to a real role save's `FilterInvalid` codes; conjunct literals in the
  wire's encoding; no round trip once the caller is connected.

### Deviations

1. No guarded runner. A runner with no statement still executes its prologue batch, so discovery
   reads the caller's connection through `IScopeConnection.CurrentAsync` instead: no round trip
   when warm, one when cold. There is no fast-deny re-check, since nothing is read.
2. The service is `internal sealed`: its constructor takes internal types (`SettingsService` is the
   precedent).
3. Measures are deferred: non-blank `measures` is 400 (with an aggregate, "not supported yet";
   without, "an aggregate query only").
4. A filter leaf's wire `location` is null, by `QueryDiagnostic`'s own rule, where the spec's
   example shows the engine's `Filter.And[0]`. The select and the ordering are each one text, so
   the engine locates their diagnostics at the clause and the wire location is null too.
5. With no select, the compile selects the root's key by its own name, not a literal `Id`.
6. Discovery's own diagnostics are not added to the answer, so it equals what the query refuses.
7. A having without an aggregate, a confirmed parameter that is unnamed, named twice, or typed as a
   hierarchy position or geography, and any clause but one filter in the permission profile are
   each 400.
8. The permission profile keeps QX3007, reports `FilterTooLong` over the excess span, and marks
   every path reachable (a stored filter is not held to the editor's own access).
9. A sensitive path is reachable and asks for no step-up; a filtered grant's refusal is the only
   unreachability.
10. A root the caller cannot read is not special-cased: the root's own columns are not decided, only
    the navigations past it, as the traversal rule decides them for a query.
11. `QueryexType` is written without the `Qx` prefix everywhere through one converter. This changes
    the enum's description in contract fingerprints.
12. `PermissionFilterRules` is extracted from `RoleAccessRules`, so the two cannot disagree.
13. The compile omits named filters, the platform's conjuncts and the access filter, as the spec's
    `QuerySpec` does.

### Open risks

- `QueryWireDiagnostics` is the edge mapping from a located `QueryexDiagnostic` to
  `QueryDiagnostic`. PC-081 builds the same mapping for `InvalidQueryException`; the two should
  converge on this class when both land.
- The `Refusals` walk duplicates `Check`'s decisions without the step-up. If the traversal rule
  gains another refusal kind, both must take it.

### What reviewers should examine hardest

- That the query profile's diagnostics equal the query's for the same clauses, including a
  location the engine gives no clause (the ceilings), and that QX3007 is the only code dropped.
- `PermissionFilterRules` against the previous `RoleAccessRules.CheckFilter`: order (length first,
  then the missing root), codes and arguments.
- `LocateSite` and `Place` for named filters, nested filter paths and the having clause.
- The cached-connection path: nothing in discovery may open a batch when the connection is warm.
