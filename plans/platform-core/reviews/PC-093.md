# PC-093: InitialTenant migration, deployed bootstrap and distribution parity

## Implementer notes

### What was built

- **The deployed invitation (spec 0018 §6.1).** `src/core/Tellma.Core/Users/TenantAdministratorInviter.cs`
  implements the `ITenantAdministratorInviter` seam. PC-034 left the seam unimplemented, and
  `TenantMigration.AdministerAsync` already resolves it in the system scope after the steps and before
  the tenant turns `Active`. The inviter:
  - finds the administrator the bootstrap made, by the address trimmed and lower-cased, with one raw read;
  - skips one who has `Joined` (the action would refuse with `Users.AlreadyJoined`);
  - runs `EntityService<TUser,int>.ExecuteActionAsync(UserService<TUser>.InviteAction, [id])` as the
    platform, so the identity call, the write-back, `core.user.added`, the welcome email (spec 0022's
    outbox) and the membership hint are the action's own;
  - throws `InvalidOperationException` with the refusal text when the single result has no status, so
    the tenant fails with its steps recorded (`TenantOutcome.Failure`).

  It is registered scoped and closed over the user leaf in `UsersRuntimeComposition.Register(services, record)`,
  which `CompositionPipeline` now passes the record to. Three log events were added to `UsersLog`:
  `TenantAdministratorInvited`, `TenantAdministratorNotInvited` (warning) and
  `TenantAdministratorAlreadyJoined`.
- **Resume hint.** `ProvisionCommand`'s "resume it with provision --tenant N" line now carries the
  `--admin-email` / `--admin-subject` the line named. Without them, a resume after a refused invitation
  would turn the tenant `Active` with nobody invited, because the step runner schedules the bootstrap and
  the invitation by the run's administrator, not by the tenant's record.
- **IdentityServerClientOptions in the migrator host.** These were already bound in every host by
  `IdentityComposition.Register` (CoreFeature), so nothing new was needed. The inviter reads them to
  decide whether it can invite at all.
- **InitialTenant migration.** `distributions/acme/src/Tellma.Distro.Acme.Migrator/Migrations/Tenant/20261122021122_InitialTenant.cs`
  (with Designer and snapshot) was already generated by dotnet-ef in an earlier checkpoint. I
  hand-reviewed it against the composed model:
  - schemas dbo, core, gl and acme;
  - 28 tables, including `__TellmaProvisioning`, `__TellmaSchema`, `gl.Centers` and the seven `acme` tables;
  - 7 temporal tables;
  - 37 versioned UDTTs;
  - `InsertData` for CalendarMonths, JobWorkerState, Users, Roles, Schedules, Settings, UserStamps,
    Permissions, RoleMemberships and ScheduleStates;
  - no IDENTITY, rowversion, trigger, MERGE or raw `Sql()`.

  The `dotnet ef migrations script` output contains only EF's conditional `SET IDENTITY_INSERT`
  guards around seed inserts. `HasPendingModelChanges` is false, so I did not regenerate it.
  Regenerating would only churn the timestamp and conflict with every open lane.
- **Parity pins.** `distributions/acme/test/Tellma.Distro.Acme.Web.Tests/TenantMigrationTests.cs`
  checks three things:
  - there are no pending model changes against the composed model;
  - there is exactly one migration, `*_InitialTenant`;
  - the generated script creates `gl.Centers` and no identity column, rowversion, trigger or MERGE.
- **Tests.**
  - `test/core/Tellma.Core.IntegrationTests/Migrator/AdministratorInvitationTests.cs` uses a scripted
    identity server. It covers an invite with link, hint and pending welcome; a refusal followed by a
    resume; a sandbox refused with `Users.SandboxRequiresExistingIdentity`; and the skips for joined
    and subject-named administrators.
  - `test/core/Tellma.Core.Tests/Users/TenantAdministratorInviterTests.cs` covers the plan, and
    `AccessRuntimeCompositionTests` gained the leaf-closure assertion.
  - `distributions/acme/test/Tellma.Distro.Acme.IntegrationTests/ProvisioningTests.cs` runs against
    the real in-proc engine. It checks that migrate from empty creates every mapped table, the UDTTs
    and the steps at version 1, with no identity, rowversion or trigger. It also checks that
    `admin@localhost` is bound and `Invited`, then `Joined` after sign-in. The deployed-style
    `provision --admin-email` creates the account through the engine, sends the invitation email,
    records the hint and queues the welcome, and the tenant turns `Active`; a rerun reports
    `Reinvited`. Finally, a sandbox provision for an unknown address fails, creating no account and
    sending no mail.
  - `AcmeMigrator.Services` is a new hook that routes the migrator's identity-server HTTP client to
    the test host.
  - The existing bootstrap test in Core `MigratorTests` now asserts the three invitations it causes.
  - The "bumped step version re-runs idempotently" requirement is already pinned by Acme `MigratorTests`
    (the bumped step runs again on every tenant, ReadOnly included) and by Core `MigratorTests`.
    "No tracked secret" is already pinned by Acme `Web.Tests` `ConfigurationTests`.

### Deviations

1. **Development without a service secret logs instead of failing.** An in-proc Development host may
   lack `Tellma:Identity:ServiceClientSecret` (D-080), and then the migrator cannot authenticate to any
   identity server. A Development `provision --admin-email` without `--admin-subject` therefore logs
   `TenantAdministratorNotInvited` and leaves the invitation to the users' page. It does not fail the
   tenant. Configuring the secret in both hosts gives the deployed flow, which `ProvisioningTests` exercises.
2. **The invitation runs in a provisioning frame of its own (`core.invite-administrator`).** Without one,
   a `ReadOnly` tenant refused the action (`tenant-read-only`), although it admits the bootstrap step
   before it. The existing read-only bootstrap test caught this.
3. **The migration was not regenerated.** Its timestamp and operation order are dotnet-ef's (20261122021122),
   and the model has not changed since it was generated.
4. **The parity test lives in Acme `Web.Tests`** (the unit tier, run on both OSes on every PR) rather than
   in the integration suite. It needs no database.
5. **CI smoke deployment deferred.** No deployment environment exists (WATCHLIST c05 item 14,
   human-only). `ProvisioningTests` stands in as the end-to-end provisioning check.
6. **The resume hint now names the administrator** (see above). This is a behaviour change to the
   migrator's report line.

### Open risks

- The inviter's lookup is a raw read on `[core].[Users].[Email]`. It relies on the bootstrap's
  normalisation (trim, lower-invariant) matching the stack's stored form, which `TenantBootstrapper`
  shares today.
- A Development operator who configures a secret in the migrator but not in the web host gets a
  token failure, not the warning. The failure surfaces as the tenant's failure line.
- `ProvisioningTests` waits up to 30 s for the engine's invitation email. That wait is real wall-clock
  time under load.

### Examine hardest

- `TenantAdministratorInviter.InviteAsync`: the order of skip, frame and throw, and whether a partially
  answered invite (none possible for one target) or a mismatch (`Users.SubjectMismatch`) should do
  more than fail.
- Whether the NoSecret skip (deviation 1) is the right reading of "keep the Development path as
  PC-092 left it".
- `ProvisionCommand`'s resume line: whether an operator copying it ever re-registers or double-invites.
