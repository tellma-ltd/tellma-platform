# PC-082: Limits, rate and concurrency policies, timeouts, compression, caching, OpenAPI

## Implementer notes

### What was built, and where

All under `src/core/Tellma.Core.AspNetCore/` unless stated.

- **Options.** `Hosting/ApiOptions.cs` gains every §1.3 limit (rates, concurrencies, queues,
  `RequestTimeout`, `LongRequestTimeout`, `EnableCompression`), validated: limits positive, queues
  not negative, `RequestTimeout > 0`, `RequestTimeout <= LongRequestTimeout <= 1 day`.
  `Hosting/McpLimitOptions.cs` (internal, `Tellma:Mcp`) holds `ToolCallsPerMinutePerUser` 120 and
  `ToolTimeout` 60 s until `Tellma.Core.Mcp` owns its options (see decisions).
- **The seam for later specs** (`src/core/Tellma.Core.Abstractions/Api/`): `TellmaRatePolicies`
  (the nine names, pinned in `WireNameTests`), `IRatePolicyMetadata { Policy, HonorsPriority }` and
  `[RatePolicy(name)]`. `RequireRatePolicy(name, honorsPriority)` on any convention builder, and
  `WebApiProjection` copies every `IRatePolicyMetadata` from a projected action's method onto its
  endpoint, so a reports/export/telemetry/blob endpoint takes its policy by metadata alone.
- **Rate limiting** (`Limits/`):
  - `RatePartitionKeys`: tenant id normalised to digits (`01` = `1`; a non-tenant segment shares
    `-`), caller `u:{sub}` or `c:{azp|client_id}`, client address (IPv4-mapped → IPv4, IPv6 → /64),
    lane from exactly one `Tellma-Priority` value equal to `low` (trimmed of SP/HTAB).
  - `RatePolicies`: definitions, `Resolve` (each policy once, fixed order route policy → user →
    tenant, the stand-alone policies dropping user and tenant) and `Audit` (run from
    `TellmaEndpointAudit`).
  - `RatePolicyRouter`: the middleware's one `GlobalLimiter`. Per endpoint (a
    `ConditionalWeakTable` cache, chains shared by signature) it runs
    `PartitionedRateLimiter.CreateChained` over one `PolicyLimiter` per policy, each over a
    per-policy `PartitionedRateLimiter<RatePartition>` store. `AttemptAcquire` returns a never-
    acquired lease for a limited endpoint, so the middleware's attempt-then-wait charges a window
    once. A refusal is a `RefusedLease` naming policy and lane, carrying the window's
    `Retry-After` or, for a sliding window (which names none), its 10 s segment.
  - `RateRejection.OnRejectedAsync`: 429 `rate-limited` through `ProblemWriter` with `Retry-After`
    (at least 1 s), `tellma.api.requests.rejected{reason=rate_limited[, lane]}`, `ApiRequestRejected`
    with reason `rate_limited` and the policy and lane in its log scope (review 1).
- **Timeouts.** `LimitsComposition` registers `tellma-web`, `tellma-long` and `tellma-mcp`
  (504 `timeout` via `ProblemWriter`) before `UseRequestTimeouts` (D-124). `TimeoutAbortMiddleware`
  just inside it aborts the connection when the timeout fires after the response started. Web, Blobs
  and Hub groups carry `tellma-web`; a long action's own `tellma-long` wins (endpoint metadata is
  later than group metadata). The data cancellation already is `RequestAborted`, which the timeout
  middleware links, so reads cancel on timeout; a sent persist already runs to completion
  (`DataBatchTests`).
- **Compression.** Brotli then Gzip at Fastest, HTTPS on, MIME set `application/json` and
  `application/problem+json`. `JsonResponseCompressionProvider` additionally refuses the Blobs
  group, a declared body under 1 KB, and everything when `EnableCompression` is false (read per
  response, see risks).
- **Output caching.** `PublicDocumentCachePolicy` (1 min distribution-info, 5 min PRM and
  OpenAPI): GET/HEAD, varies by path only (not Host, not query, not the caller), stores only a 200
  without `Set-Cookie`. Tenant routes name no policy.
- **Pipeline.** `UseTellma` steps 6 (compression) and 10-12 (rate limiter, timeouts + abort,
  output cache) in spec 0011 §5.1 order. `ProblemWriter` now buffers the body, sets
  `Content-Length` and writes with `CancellationToken.None` (needed inside `WriteTimeoutResponse`,
  where `RequestAborted` is already cancelled; it also lets the 1 KB minimum apply to problems).
- **Groups and public routes.** Web and Blobs: `tellma-user` + `tellma-tenant` + `tellma-web`; Hub:
  `tellma-web` only; Api: nothing (the Tellma.Api policy and an empty group already existed; spec
  0016 §12.2's public API owns its limits). Distribution-info, both health probes, PRM, OpenAPI and
  `/bff/login`: `tellma-anonymous`.
- **Unknown members** (`Api/UnknownMembers.cs`, D-020): a resolver modifier on the HTTP JSON options
  adds to every object contract without extension data a synthetic extension-data member whose
  dictionary counts `tellma.api.unknown_members{type}` and keeps nothing; never serialized, invisible
  to the OpenAPI schemas (asserted) and to `TellmaJson.Options` (contract fingerprints unchanged).
- **OpenAPI** (`OpenApi/WebOpenApi.cs`, Development only): `AddOpenApi("web")`, OpenAPI 3.1, Web
  group only; decimal → `["string","number"]`/`decimal`, long → `["string","integer"]`/`int64`;
  `x-tellma-securable` per operation; one tag per projected route segment, unused tags pruned;
  `readOnly` on every non-editable member plus `x-tellma-write-once`/`x-tellma-derived`;
  `x-tellma-related-select` per navigation. `Microsoft.AspNetCore.OpenApi` 10.0.11 added to CPM.
- **Tests.** `test/core/Tellma.Core.AspNetCore.Tests/Limits/` (keys, router, host-level 429/504,
  compression, caching), `OpenApi/WebOpenApiTests.cs`, `Api/UnknownMembersTests.cs`;
  `distributions/acme/test/.../LimitsTests.cs` (429 with Retry-After; 504 over a one-minute
  `WAITFOR` read with the batch cancelled, guarded by the same `SkipUnless` as the other Acme
  tenant-read tests and running today; the Development OpenAPI document over Acme's composition, cached).
  `WebApiProjectionTests` now expects `tellma-web` on non-long routes.

### Deviations (also in the commit message)

1. IPv6 clients are partitioned by /64 for `tellma-anonymous` (the spec says "client IP"); a
   per-address bucket is no bound for a client holding a /64.
2. The 1 KB compression minimum applies to a declared `Content-Length` only; streamed JSON
   (`Results.Json`, row pages) has no length when the decision is made and is compressed by type.
3. The whole Blobs group is excluded from compression (the spec excludes "blob downloads").
4. Output caching ignores the caller, the Host header and the query string, and refuses to store a
   non-200 or a `Set-Cookie` response.
5. `/bff/backchannel-logout` is not under `tellma-anonymous` (§8.2 lists "BFF login" only): its
   caller is the identity server, one address, and dropping a logout token is a security failure.
6. `tellma-blobs`, `tellma-telemetry`, `tellma-anonymous` and `tellma-mcp` each replace
   `tellma-user`/`tellma-tenant` on an endpoint; §8.2 says so only for blobs ("a bucket apart").
7. `Tellma-Priority` is parsed strictly: exactly one value, `low` after trimming SP/HTAB, ordinal.
8. A sliding-window refusal's `Retry-After` is the window's segment (10 s): the framework's sliding
   window names no wait. A concurrency refusal names 1 s.
9. `ProblemWriter` buffers and declares `Content-Length`, writing with `CancellationToken.None`.
10. `TimeoutAbortMiddleware` is an addition: the framework rethrows when the response has started.
11. `ApiOptions` validation bounds (`LongRequestTimeout` ≥ `RequestTimeout`, ≤ 1 day) and
    `ApiTelemetryNames.TypeTag` are additions.
12. `tellma-mcp`'s limits bind from an interim internal `McpLimitOptions` (`Tellma:Mcp`).
13. No early declared-length 413 middleware: the access guard wraps the endpoint's delegate, so it
    runs before body binding; an oversized body to a missing tenant and to a refused one already
    answer the same 404, and the same holds for chunked bodies and malformed JSON.
14. The OpenAPI snapshot test is not here: CHECKPOINTS assigns it to 0016-f.
15. (Review 1) An implied `tellma-user-across-tenants` policy, keyed by caller alone, runs just ahead
    of `tellma-user` wherever that runs. It is bounded by the new `RequestsPerMinutePerUserAcrossTenants`
    (1,200 by default, validated at least `RequestsPerMinutePerUser`). No endpoint names it, and the
    audit does not accept it as a name.
16. (Review 1, pending Ahmad) Spec 0016's order is kept: the limiter runs ahead of the tenant
    middleware. So a stranger can still spend a tenant's `tellma-tenant` permits, and a full tenant
    can serve as a busy/missing oracle for it, within the stranger's own cap across tenants.
17. (Review 1, carried to PC-089) `tellma-web` (30 s) on the whole Blobs group cuts any blob download
    still streaming at 30 s. The blob GET should be mapped without the request timeout, or with a
    time-to-first-byte bound (§8.3 vs spec 0017 §5.3).

### Open risks

- `MapTellma` (pre-existing, `TenantGroup`) reads `IOptions<ApiOptions>.Value` while mapping, so an
  invalid `Tellma:Api` value surfaces as an `OptionsValidationException` from `MapTellma` rather than
  a startup-gate problem. My new code reads the options lazily (router partitions, compression
  provider, timeout policies), so it adds no second eager read; the existing one is untouched.
- The startup audit refuses an unknown policy name, but a later endpoint mapped after the audit runs
  (none today) would throw from `RatePolicies.Resolve` on its first request.
- Health probes are under `tellma-anonymous` (60/min per address) as §8.2 says; an orchestrator
  probing more often than once a second from one address would be refused.
- The PRM document is cached per tenant id in its path, so a caller walking ids fills the output
  cache with copies; the store's own size limit (100 MB) evicts, and the route is under
  `tellma-anonymous`.
- `DateTimeOffset` members render without `type` in the OpenAPI schemas (the scalar converter is
  opaque to the exporter); not in scope of §12.1's listed transforms, noted for 0016-f's snapshot.

### What reviewers should examine hardest

- `RatePolicyRouter.AttemptAcquireCore` / `AcquireAsyncCore` against `RateLimitingMiddleware`'s
  attempt-then-wait: a window must be charged once, an unlimited endpoint never waits, and a
  refused chain releases earlier permits (`A_refusal_later_in_the_chain_releases_...`).
- That a 429 cannot distinguish a missing tenant from a refused one (the limiter runs before the
  tenant middleware, partitions only on the route value), and that `/99` keys cannot grow memory
  without bound (idle partitions are disposed by the partitioned limiter's own timer).
- The timeout path: `WriteTimeoutResponse` runs with `RequestAborted` cancelled, hence the
  `ProblemWriter` change; the abort middleware's filter (`HasStarted` and the timeout's own token).
- `UnknownMembers`: the synthetic member's effect on every HTTP JSON contract (constructor-bound
  records, `JsonUnmappedMemberHandling.Disallow`, types with their own extension data).

Checked and found conforming, with no finding:

- **Refusals and tenant existence.** 429 and 504 go through `ProblemWriter`. The limiter runs
  before the tenant middleware and partitions on the route value alone, so its answer is the same
  for a missing tenant and for a non-member (the host test asserts status, header names and body).
  An oversized body to a missing tenant and to a refused one both get 404, because
  `TenantAccessFilter.Wrap` is the outermost `RequestDelegate` wrapper and runs before minimal-API
  binding. Unauthenticated requests are challenged by `UseAuthorization` before the limiter, so they
  never spend a tenant's buckets. Tenant resolution reads the registry snapshot, so walking tenant
  ids costs no database round trip.
- **Chain mechanics.** The deferred attempt charges a window once. `CreateChained` releases
  earlier leases on a later refusal and returns the refusing `RefusedLease` unwrapped, which the
  lane-tag host test confirms. A lane is part of the partition key, and queues are oldest-first.
- **Deviations accepted:** 1, 2, 3, 4, 7, 8, 9, 10, 11, 12, 13 and 14.
  - 5: the spec lists only BFF login under `tellma-anonymous`, so this is conformance rather than a
    deviation.
  - 6: MCP is mapped on its own `Mcp` group, and telemetry and anonymous routes are tenantless, so
    the replacement is defensive and changes no spec-listed chain.
- **Timeouts.** Policies are registered in `AddTellma`, before `UseRequestTimeouts` (D-124). An
  endpoint's `tellma-long` wins over the group's `tellma-web`. `Response.Clear()` precedes the 504
  write, and the abort middleware only filters on `HasStarted` and the timeout's own token.
- **Compression (BREACH).** It covers JSON alone, the problem body included. The Web group needs
  `Tellma-Client`, and the cookie is `SameSite=Lax`, so a cross-site page cannot choose the requests
  a victim's browser sends. Hub negotiate is origin-checked, and blob responses are excluded.
- **Output caching.** It is limited to three caller-independent documents: distribution-info is
  built from configuration alone, and PRM is keyed by its tenant path. Only a 200 is stored. The
  `Set-Cookie` check runs before the cookie handler's `OnStarting` renewal, but the cache captures
  headers at that same point, so no caller's cookie is stored either.
- **Interim options.** The interim `McpLimitOptions` binding does not collide with a later
  `McpOptions` binding, because bound options are keyed per type and nothing checks for unknown
  keys.
- **ARCHITECTURE.md.** The line 353 change is accurate.
- **AGENTS.md / PLAN §7.1 item 5.** No spec, PC or decision references appear in XML docs,
  messages or test names.

### Findings

**R1-1 (major, spec-level, for Ahmad): `tellma-tenant` and `tellma-user` are spent by callers the
tenant has not admitted, before membership is known.**
`src/core/Tellma.Core.AspNetCore/TellmaApplicationBuilderExtensions.cs:135` installs the limiter
ahead of `TenantMiddleware` (line 145), as spec 0011 §5.1 orders. `Limits/RatePolicies.cs:78-79`
keys `tellma-user` by `{tenantId}:{sub}` and `tellma-tenant` by `{tenantId}` from the raw route
value. This follows 0016 §8.2 to the letter, and causes three problems:
- **Cross-tenant starvation.** Any signed-in user of the distribution can send a burst to
  `/5/api/web/...`. The sliding window admits up to 600 at once, and each request holds one of
  tenant 5's 64 concurrency permits until its 404 is written; holding the 404's write open, for
  example with an HTTP/2 window of 0, keeps it longer. While that lasts, tenant 5's own members get
  429. A few accounts can repeat this every minute.
- **Existence and load oracle.** Tenant 99, which does not exist, never refuses a stranger's 64
  concurrent requests. A busy real tenant does, because members hold some of the permits. This is
  the same class of oracle D-137 raised for suspended tenants.
- **No per-caller bound across tenant ids.** Each distinct tenant id gives the same user a fresh
  600/min bucket, so one account's total rate is unbounded. It is also unbounded in memory: each
  sliding-window partition is retained about 70 s after its last use.

Suggested fix (needs a ruling, since it changes the spec's "one chain per endpoint"):
- Take the `tellma-tenant` permit, and charge `tellma-user`, only after the guard has admitted the
  caller. For example, acquire them inside `TenantAccessFilter.Wrap`, once membership holds, so a
  non-member always gets 404 and never touches a tenant's buckets.
- Keep a cheap per-`sub` cross-tenant cap in the global chain.
- At minimum, record the trade-off in DECISIONS and in spec 0016 §8.2.

**R1-2 (major): the seam the Done-when depends on, a `[RatePolicy]` on an action method, has no
test.**
`src/core/Tellma.Core.AspNetCore/Api/WebApiProjection.cs:230-236` copies `IRatePolicyMetadata`
from the declared method onto the projected endpoint. This is how specs 0019 and 0033 will attach
`tellma-export`, `tellma-import` and `tellma-reports`; the checkpoint's Done-when says "policies
attachable to routes owned by later specs ... via metadata without code change here". No test
covers it: a repo-wide search finds no `[RatePolicy(...)]` use in any test. The host-level lane
test uses `RequireRatePolicy` on a hand-mapped endpoint, which never reaches this loop.
- **Failure scenario:** deleting lines 230-236, or breaking `DeclaredMethod`, for example for an
  inherited or explicitly implemented action method, passes every suite. The first report or
  export checkpoint then ships an unlimited endpoint.
- **Suggested fix:** add an action to `ProjectionModel` carrying
  `[RatePolicy(TellmaRatePolicies.Export)]`, plus one carrying
  `[RatePolicy(TellmaRatePolicies.Reports, HonorsPriority = true)]`. In `WebApiProjectionTests`,
  assert that each projected endpoint's metadata resolves to `[export, user, tenant]` and to a
  priority-honoring `[reports, user, tenant]`. A built-in action should carry none.

**R1-3 (minor): the rate-limit refusal's log event is not the one §10.1 names.**
`src/core/Tellma.Core.AspNetCore/Api/ApiLog.cs:36` adds `ApiRequestRateLimited`, and
`Limits/RateRejection.cs:45` logs it. Spec 0016 §10.1 defines one event,
`ApiRequestRejected(reason)` at Information, for both `rate_limited` and `client_outdated`. The
contract middleware already logs `ApiRequestRejected` (ApiLog.cs:25).
- **Failure scenario:** a log query or alert keyed on `ApiRequestRejected` sees client-outdated
  refusals but never a rate-limit refusal. The commit lists no deviation for this.
- **Suggested fix:** log the refusal through the existing `ApiRequestRejected` event with reason
  `rate_limited`, and keep policy and lane as extra structured fields (a second parameterised
  message under the same EventName, or a logger scope). Otherwise, declare the event name as a
  deviation.

**R1-4 (minor): the OpenAPI write-once, derived and `$ref` paths are not tested.**
`src/core/Tellma.Core.AspNetCore/OpenApi/WebOpenApi.cs:267-332` emits `x-tellma-write-once` and
`x-tellma-derived`, and marks a `$ref` member (`OpenApiSchemaReference`, for example an enum-typed
server-owned member) `readOnly` with sibling extensions. `ProjectionModel` has no `[WriteOnce]`,
`[Derived]` or enum-typed non-editable member. The document test therefore checks only `readOnly`
on two inline audit members, and the decimal encoding is checked only by calling `ScalarSchemas`
directly, never through the generator.
- **Failure scenario:** a wrong ownership-to-flag mapping goes unnoticed. So would Microsoft.OpenApi
  2.x dropping `readOnly` or extensions written beside a 3.1 `$ref`, which is plausible because a
  reference's sibling keywords are serialised selectively. So would the generator handing the schema
  transformer a decimal member under a type other than `decimal`. In each case §12.1's
  annotations silently vanish from the document the SPA's coding agent reads.
- **Suggested fix:** give a projection entity a `[WriteOnce]` member, a `[Derived]` member, a
  `decimal` member and a server-owned enum member, and assert them in
  `An_entity_schema_marks_what_a_save_never_takes_and_encodes_its_long_key`: the flags, `readOnly`
  beside the `$ref`, and `["number","string"]` with format `decimal`.

**R1-5 (minor, spec-level, carry to PC-089 and flag for Ahmad): `tellma-web` on the whole Blobs
group cuts every blob download at 30 s.**
`src/core/Tellma.Core.AspNetCore/TellmaEndpointRouteBuilderExtensions.cs:160-163` stamps
`tellma-web` (`RequestTimeout`, 30 s) on the Blobs group, as §8.3 says. The timeout links into
`RequestAborted`, which `Results.Stream`'s copy uses, so a response still streaming at 30 s is
cancelled. `TimeoutAbortMiddleware` then aborts the connection.
- **Failure scenario:** any download of a 100 MiB file (the `MaxUploadSize`) slower than about
  27 Mbit/s fails part-way, as does a moderately large export file on a slow link. Spec 0017 §5.3
  states no timeout for the GET, so nothing overrides the group's.
- **Suggested fix:** PC-089 maps the blob GET with `DisableRequestTimeout()`, or with a policy that
  bounds the time to first byte rather than the whole transfer. The concurrency queue and the
  connection's minimum data rate already bound abuse. Record the misalignment with §8.3 for Ahmad.

### Responses

All fixes are in the "PC-082: review 1 fixes" commit (child of 7b5075e).

- R1-1: fixed in the "PC-082: review 1 fixes" commit, in part, per the orchestrator's interim
  ruling. Spec 0016's middleware order is kept, so the limiter is not moved into the access guard.
  - **The cap.** An implied `tellma-user-across-tenants` policy, keyed by `u:{sub}`/`c:{client}`,
    is chained ahead of `tellma-user` wherever `tellma-user` runs (`RatePolicies.Resolve`). Its limit
    is `RequestsPerMinutePerUserAcrossTenants` (1,200, sliding minute, `Retry-After` 10 s).
  - **What it bounds.** It sits ahead of the per-tenant links, and `CreateChained` stops at the first
    refusal. So once it refuses, a walk over tenant ids opens no further `{tenantId}:{sub}` or
    `{tenantId}` partitions. One account's total rate, and the partitions it can create per window,
    are therefore bounded.
  - **Tests.** `RatePolicyRouterTests` covers the chain order, the cap's absence where `tellma-user`
    is absent, its refusal on the third tenant id with a 10 s wait, another account unaffected, and
    the options refusing a cap below the per-tenant rate. `RateLimitingTests` checks through the
    host that a stranger walking `/100`-`/103` gets 404, 404, 404, then 429.
  - **Open.** The tenant-permit drain and the busy/missing oracle remain, as deviation 16, for Ahmad.
- R1-2: fixed in the "PC-082: review 1 fixes" commit. The projection model's `inbox/export` now
  carries `[RatePolicy(Export)]`, and a new `inbox/report` carries
  `[RatePolicy(Reports, HonorsPriority = true)]`. In `WebApiProjectionTests`, resolving their
  projected endpoints' metadata gives `[export, user-across-tenants, user, tenant]`, and a
  priority-honoring `[reports, user-across-tenants, user, tenant]`. `inbox/summary` (an action that
  names none) and `centers/get-by-parent-ids` (a built-in action) resolve to the group's chain alone.
  Every standard operation carries exactly the group's two names.
- R1-3: fixed in the "PC-082: review 1 fixes" commit. `ApiRequestRateLimited` is gone, and the
  refusal logs through the existing `ApiLog.RequestRejected` (`ApiRequestRejected`, Information) with
  reason `rate_limited`.
  - **Why a scope.** The policy and lane go in a log scope (`RatePolicy`, `RateLane`) rather than a

  - **Test.** The host test asserts the event name, the level, the reason and both scope members.
- R1-4: fixed in the "PC-082: review 1 fixes" commit. `PjLedger` gains a `[WriteOnce]` `Code`, a
  `[Derived]` `decimal Balance`, an editable `decimal CreditLimit` and a `[ServerOwned]` enum `State`.

  - the enum as a `$ref` with `readOnly` beside it, its shared component carrying no `readOnly`.
- R1-5: carried to PC-089, per the orchestrator. No blob endpoint is built here. It is recorded as
  deviation 17, and in the commit message, for Ahmad.
