### Deviations

1. **`JobItem<TItem>` and `JobBatch<TItem>` are sealed classes, not records** (§3.2 sketches
   records). An item has identity and mutable marks; a `with` copy would carry marks the worker never
   reads. A record `JobBatch` would also synthesise a `ToString` that reads `Single`, which throws
   for several items.
2. **`TItem : class`**, and `IEntityJobHandler<TEntity> where TEntity : class, IJobEntity`. The spec
   leaves `TItem` unconstrained; `IDataBatch.Query<T>` (what the claim uses for entity rows)
   requires `class`, and `Job` is a class.
3. **`JobHandlerAttribute`** takes the key in its constructor and every option as a settable
   property, is `Inherited = false`, and carries `FindProblems()` as the deliverable's "attribute
   range validation helper". The attribute itself validates nothing (Abstractions README:
   "declarations are data").
4. **The argument-size guard also checks the key/code length** (≤ 64, the `nvarchar(64)` columns),
   and treats an empty argument bag as null (no `{}` stored). An unserialisable argument is
   rethrown as `ArgumentException` (inner exception kept), so every guard path is one exception type.
5. **`Arguments<T>()` with a null `ArgumentsJson`** returns a fresh empty instance for object,
   dictionary and collection types (read from `{}`/`[]`), the default for value types, and null for
   other reference types such as `string`. The spec says "the type's default"; nullable reference
   annotations cannot be seen at run time, and an empty shape spares every handler a null check.
6. **Tolerant reading also clears `required`** (a missing `required` member keeps its default),
   which "missing members defaulted" implies for types written with `required`.
7. **`JobsOptions` upper bounds** for `GapThreshold` (`int.MaxValue` minutes) and the retentions
   (`int.MaxValue` seconds): the statements bind them as 32-bit integers. §12.1 gives lower bounds
   only. The `DrainTimeout < HostOptions.ShutdownTimeout` rule is left to the worker host (0020-b),
   because `Tellma.Core` does not see the host's options at bind time; the options document this.
8. **`IJobProgress.FlushAsync` and `IJobQueue.EnqueueAsync` take a `CancellationToken`**;
   `ExecuteAsync` does not (round trips observe the scope token, per §3.2).
9. **Table types are not registered** with `TableType<T>()` in `CoreFeature`. As in D-061 for the
   notification lists, registration would regenerate the Acme and fixture migrations; it belongs with
   the statements that bind them (0020-b/0020-c).
10. **Contract tests live in `Tellma.Core.Abstractions.Tests/Jobs`** (mirroring the source), not
    §16's `Tellma.Core.Tests/Jobs`; the options test, which goes through composition, is in
    `Tellma.Core.Tests/Jobs`.
11. **`JobLimits`** is a public static class not in the spec, holding the numbers the contract and
    the runtime share (64, 4,000, 500, 15, 100, 30 days).
12. **Not done here** (named so a reviewer does not look for them): `FeatureContribution.JobHandler`
    / `RetiredJobKey` items and the handler registry (0020-b); the TypeScript mirror of
    `ClientJobHandler` (client checkpoints); a `JobsTelemetryTagValues` class (the tag values are
    documented on `JobsTelemetryNames`).

### Decisions for the orchestrator

- PC-062 (0015-a) can reference `IJobQueue` and `IJobProgress` from
  `Tellma.Core.Abstractions.Jobs` for `PersistContext`/`SaveOptions.OnPersist`; nothing in 0015 was
  seeded here.
- 0020-b should call `JobHandlerAttribute.FindProblems()` from its composition check, enforce
  `DrainTimeout < HostOptions.ShutdownTimeout` in the worker host, register the five table types
  and configure `Job`'s columns fluently.
- `KeyGrammar` is now the single key grammar; later registries (schedules, retired keys) should use
  `JobHandlerKeys.IsValid` rather than another regex.

### Open risks

- **Marks are internal.** A distribution's handler unit test cannot read what its handler marked
  without going through the worker. A public test seam (or `Tellma.Core.Testing` helper) may be
  wanted once 0020-b lands.
- **`Arguments<T>` for a reference type never returns null**, so a handler cannot tell "enqueued
  without arguments" from "enqueued with `{}`" except through `Job.ArgumentsJson`; documented on the
  method.
- **`JobItem.CancellationToken` is init-only and not validated**: the worker must set it from the
  item's linked source. A default token would make the item uncancellable.
- **`JobRequest` is a plain record**; every §4.1 rule (key registered, entity id positive, 64 KB
  arguments, one entity type per call) is enforced at enqueue by 0020-b, not at construction.

### What reviewers should examine hardest

- `JobItem.TrySetCancellationReason`: the CAS loop and the escalation table (None → any;
  CancelRequested/HostStopping → LeaseLost only; LeaseLost final), and the throw on an undefined
  stored value.
- `JobJson.ReadArguments<T>`: the `JsonTypeInfoKind` dispatch on a null column, and whether the
  tolerant options (a copy of `TellmaJson.Options` with a modifier) keep every platform converter.
- `JobFailedException`: the guard runs in a property initializer of a primary-constructor
  exception; the null check is duplicated so a null error throws `ArgumentNullException` whichever
  of the base call and the initializers runs first.
- `JobsOptions.Validate`: one bad value reports once (the min/max interplay was fixed during
  implementation after a test caught a double report).
- `NotificationNames` after the move to `KeyGrammar`: the existing notification tests pass
  unchanged, which is the evidence the grammar did not drift.
