### Deviations

1. **`JobItem<TItem>` and `JobBatch<TItem>` are sealed classes, not records** (§3.2 sketches
   records). An item has identity and mutable marks; a `with` copy would carry marks the worker never
   reads. A record `JobBatch` would also synthesise a `ToString` that reads `Single`, which throws
   for several items.
2. **`TItem : class`**, and `IEntityJobHandler<TEntity> where TEntity : class, IJobEntity`. The spec
   leaves `TItem` unconstrained; `IDataBatch.Query<T>` (what the claim uses for entity rows)
   requires `class`, and `Job` is a class.
3. **`JobHandlerAttribute`** takes the key in its constructor and every option as a settable
   property, is `Inherited = false`, and carries `FindProblems()` as the deliverable's "attribute
   range validation helper". The attribute itself validates nothing (Abstractions README:
   "declarations are data").
4. **The argument-size guard also checks the key/code length** (≤ 64, the `nvarchar(64)` columns),
   and treats an empty argument bag as null (no `{}` stored). An unserialisable argument is
   rethrown as `ArgumentException` (inner exception kept), so every guard path is one exception type.
5. **`Arguments<T>()` with a null `ArgumentsJson`** returns a fresh empty instance for object,
   dictionary and collection types (read from `{}`/`[]`), the default for value types, and null for
   other reference types such as `string`. The spec says "the type's default"; nullable reference
   annotations cannot be seen at run time, and an empty shape spares every handler a null check.
6. **Tolerant reading also clears `required`** (a missing `required` member keeps its default),
   which "missing members defaulted" implies for types written with `required`.
7. **`JobsOptions` upper bounds** for `GapThreshold` (`int.MaxValue` minutes) and the retentions
   (`int.MaxValue` seconds): the statements bind them as 32-bit integers. §12.1 gives lower bounds
   only. The `DrainTimeout < HostOptions.ShutdownTimeout` rule is left to the worker host (0020-b),
   because `Tellma.Core` does not see the host's options at bind time; the options document this.
8. **`IJobProgress.FlushAsync` and `IJobQueue.EnqueueAsync` take a `CancellationToken`**;
   `ExecuteAsync` does not (round trips observe the scope token, per §3.2).
9. **Table types are not registered** with `TableType<T>()` in `CoreFeature`. As in D-061 for the
   notification lists, registration would regenerate the Acme and fixture migrations; it belongs with
   the statements that bind them (0020-b/0020-c).
10. **Contract tests live in `Tellma.Core.Abstractions.Tests/Jobs`** (mirroring the source), not
    §16's `Tellma.Core.Tests/Jobs`; the options test, which goes through composition, is in
    `Tellma.Core.Tests/Jobs`.
11. **`JobLimits`** is a public static class not in the spec, holding the numbers the contract and
    the runtime share (64, 4,000, 500, 15, 100, 30 days).
12. **Not done here** (named so a reviewer does not look for them): `FeatureContribution.JobHandler`
    / `RetiredJobKey` items and the handler registry (0020-b); the TypeScript mirror of
    `ClientJobHandler` (client checkpoints); a `JobsTelemetryTagValues` class (the tag values are
    documented on `JobsTelemetryNames`).

### Decisions for the orchestrator

- PC-062 (0015-a) can reference `IJobQueue` and `IJobProgress` from
  `Tellma.Core.Abstractions.Jobs` for `PersistContext`/`SaveOptions.OnPersist`; nothing in 0015 was
  seeded here.
- 0020-b should call `JobHandlerAttribute.FindProblems()` from its composition check, enforce
  `DrainTimeout < HostOptions.ShutdownTimeout` in the worker host, register the five table types
  and configure `Job`'s columns fluently.
- `KeyGrammar` is now the single key grammar; later registries (schedules, retired keys) should use
  `JobHandlerKeys.IsValid` rather than another regex.

### Open risks

- **Marks are internal.** A distribution's handler unit test cannot read what its handler marked
  without going through the worker. A public test seam (or `Tellma.Core.Testing` helper) may be
  wanted once 0020-b lands.
- **`Arguments<T>` for a reference type never returns null**, so a handler cannot tell "enqueued
  without arguments" from "enqueued with `{}`" except through `Job.ArgumentsJson`; documented on the
  method.
- **`JobItem.CancellationToken` is init-only and not validated**: the worker must set it from the
  item's linked source. A default token would make the item uncancellable.
- **`JobRequest` is a plain record**; every §4.1 rule (key registered, entity id positive, 64 KB
  arguments, one entity type per call) is enforced at enqueue by 0020-b, not at construction.

### What reviewers should examine hardest

- `JobItem.TrySetCancellationReason`: the CAS loop and the escalation table (None → any;
  CancelRequested/HostStopping → LeaseLost only; LeaseLost final), and the throw on an undefined
  stored value.
- `JobJson.ReadArguments<T>`: the `JsonTypeInfoKind` dispatch on a null column, and whether the
  tolerant options (a copy of `TellmaJson.Options` with a modifier) keep every platform converter.
- `JobFailedException`: the guard runs in a property initializer of a primary-constructor
  exception; the null check is duplicated so a null error throws `ArgumentNullException` whichever
  of the base call and the initializers runs first.
- `JobsOptions.Validate`: one bad value reports once (the min/max interplay was fixed during
  implementation after a test caught a double report).
- `NotificationNames` after the move to `KeyGrammar`: the existing notification tests pass
  unchanged, which is the evidence the grammar did not drift.

## Review 1

### Findings

Scope checked: every deliverable of the PC-036 entry against 0020 §2.2-§2.5, §3.1-§3.3, §3.7,
§4.1, §12.1 and §13, and the 12 listed deviations (all justified; 7 and 9 carry orchestrator notes
for 0020-b). Verified locally on 2e5de44: `dotnet build Tellma.slnx` printed Build succeeded with
0 warnings and 0 errors; `Tellma.Core.Abstractions.Tests` passed 710/710; `Tellma.Core.Tests`
filtered to Jobs|Notification passed 83/83; `dotnet format --verify-no-changes` over the changed `.cs` files is clean, and they
have no BOM and no CRLF. The
commit's integration-suite list matches every `Category=Integration` project in the repo, as PLAN
§7.1 item 4 requires when Abstractions changes. `KeyGrammar` accepts exactly what the two removed
`\z`-anchored regexes accepted. The `TrySetCancellationReason` escalation table matches §3.3. The
tolerant options copy `TellmaJson.Options`, converters and resolver chain included. The contracts
leave 0020-b/c the access they need through the existing `InternalsVisibleTo("Tellma.Core")`:
setting `StateJson`, reading the marks and notifications, setting the reason, and reading
`JobFailedException.ArgumentsJson`. Each later addition (cancellation tokens, `TItem : class`) is
additive or already in place, so I found no shape that 0020-b/c would have to break.

**R1-1 (minor): the `GapThreshold` upper bound admits values that make every poll fail.**
`src/core/Tellma.Core.Abstractions/Jobs/JobsOptions.cs:42` caps the threshold at
`TimeSpan.FromMinutes(int.MaxValue)`, about 4,083 years, on the grounds that the gap check binds it
as 32-bit minutes. But the statement computes `DATEADD(minute, -@tb{b}_p0, @tb{b}_now)` (§6.10),
and `datetimeoffset` cannot go below 0001-01-01. Any threshold above about 1.06 × 10⁹ minutes
(roughly 2,025 years from now) passes validation, then fails every poll's first block with SQL
error 517 (DATEADD overflow), so the worker never claims anything. An operator who "turns off" the
gap hold with a huge value (for example `1000000.00:00:00`, about 2,738 years) hits exactly this
case. The test pins the bad bound as valid:
`test/core/Tellma.Core.Tests/Jobs/JobsOptionsTests.cs:69`. The retention bound (`int.MaxValue`
seconds, about 68 years) is safe.
*Fix:* cap the threshold at a span the statement can subtract from any plausible now, for example
`TimeSpan.FromDays(36_500)` (100 years). Update the remark ("what the statements' 32-bit minutes …
can carry"), the message, and lines 69 and 71 of the test to that bound.

**R1-2 (minor): handlers outside `Tellma.Core` cannot unit-test what they mark.**
`JobItem.Mark`, `StateJson` (setter) and `TrySetCancellationReason`
(`src/core/Tellma.Core.Abstractions/Jobs/JobItem.cs:85-92,212`) are internal. The Abstractions
csproj grants internals only to `Tellma.Core` and `Tellma.Core.Abstractions.Tests`. So the test of
a handler in any other assembly cannot do three things:
- assert the outcome its handler marked;
- seed a checkpoint to test resume;
- put an item in `CancelRequested`/`HostStopping` to test the "throw `OperationCanceledException`,
  never return normally" rule of §3.4.

Two kinds of handler are affected: spec 0022's outbox handler in `Tellma.Core.Email` (its tests
have no `InternalsVisibleTo`), and every module or distribution handler. `Tellma.Core.Testing`
also has no access. The implementer lists this as an open risk. It is minor rather than major only
because the fix is additive and changes no public contract.
*Fix (now or as a planner note for 0020-b):* grant `InternalsVisibleTo("Tellma.Core.Testing")` and
ship a small public probe there. It would let a test build a `JobItem<T>` with a checkpoint, set
its cancellation reason, and read its mark and its queued success notifications. 0022's outbox
tests can then use it instead of each assembly asking for its own `InternalsVisibleTo`.

**R1-3 (minor): no test pins that tolerant reads keep the platform's converters.**
`JobJson.CreateTolerantOptions` (`src/core/Tellma.Core.Abstractions/Jobs/JobJson.cs:147-161`)
copies `TellmaJson.Options`, which is correct today. But no test would fail if the copy were
replaced by fresh options that keep only case-insensitivity: the `JobItemTests` cases exercise
camelCase matching, `required` and integers only. A queued job's `long` or `decimal` argument
(written as a string by `TellmaJson`) would then fail to read. So would an enum stored by its member name, and the
strict enum and decimal rules would no longer apply. The implementer asked reviewers to check
exactly this.
*Fix:* add one `JobItemTests` case. Through `Arguments<T>()`, it reads an argument type with a
`decimal` and a `long` written as strings (`{"amount":"12.50","big":"9007199254740993"}`) and an
enum by name, and asserts that an undefined enum name throws `JsonException`.

### Responses

- R1-1: fixed in commit 2 (`PC-036: review 1 fixes`). `GapThreshold` is capped at 100 years
  (`TimeSpan.FromDays(36_500)`). The remark, the message, the property doc and both READMEs are
  updated. The test pins both bounds and a `1,000,000`-day "turn it off" value refused with the
  100-year message.
- R1-2: fixed in commit 2. The Abstractions csproj grants `InternalsVisibleTo("Tellma.Core.Testing")`,
  and `Tellma.Core.Testing.Jobs.JobItemProbe` ships with these members:
  - `ForJob` and `ForItem` build an item, with an optional checkpoint, progress reporter and token;
  - `SetCheckpoint` stores a checkpoint under `TellmaJson.Options`, and null clears it;
  - `SetCancellationReason` sets the reason with the worker's escalation rule;
  - `OutcomeOf` reads the mark back as the public `JobItemOutcome`/`JobItemOutcomeKind`;
  - `SuccessNotificationsOf` reads the queued notifications.

  `Tellma.Core.Testing.Tests/Jobs/JobItemProbeTests` drives a sample handler through the probe:
  - a fresh item retries with its error;
  - a seeded checkpoint resumes to success with a notification;
  - a requested cancel stops the handler and leaves the item unmarked;
  - the reason escalation holds, and the stored checkpoint has the platform's shape.

  The probe never applies the worker's settle rules to an unmarked item. Its doc and the README
  say so.
- R1-3: fixed in commit 2. `JobItemTests.Arguments_and_state_read_with_the_platforms_converters`
  reads a decimal and a long written as strings, and an enum by name, through both `Arguments<T>()`
  and `State<T>()`. It also asserts that an undefined enum name and a numeric enum each throw
  `JsonException`.
