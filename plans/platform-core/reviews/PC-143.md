# PC-143: Notification surfaces of the users stack

## Implementer notes

### What was built, and where

  `UserService.Notifications.cs`, `UserService.Welcome.cs`): the users the invite answered with a

### Deviations

- The notice is raised as one `NotificationRequest` per `MaxRecipientsPerRequest` users rather
  than one per user: the notifier writes the same rows, and the cap would otherwise throw on a
  large invite.
- A test send the transport answers `Rejected` is raised as the `email` dependency unavailable
  (503), like a transient failure; the spec names only "a transport failure".
- A caller whose address the outbox would not store (`EmailAddressList.IsWellFormed` false)
  answers `NoContactAddress`, as one with none does.
- `me/test-notification` runs a prologue-only Read batch first when the connect prologue is due,
  so its "0 round trips" holds once the caller's connection is warm.
- The administrator's save locks the target's `core.UserStamps` row (`UPDLOCK, ROWLOCK`) before
  replacing the rows, mirroring the preference bag's statement.
- `Users_NotIndividual` is reworded (it named only invitations).
- Email is now a delivering channel in every composition (core registers its sender); test
  fixtures that stand in their own email senders (`InboxDatabase`, `NotificationsDatabase`,
  `NotifierTests`' plain harness via `NotificationTestModel.WithoutSenders`) remove the platform's
  first. `BatchHarness` gained an optional `configure` callback for that.
- The existing `Another_user_s_bag_is_read_set_and_deleted_under_the_preferences_filter_within_its_budgets`
  now seeds an administrator: a user action is a security write held to the last-administrator
  invariant, and the test only passed when an administrator-seeding test happened to run first in
  the class's database (it fails when run alone, through a path this checkpoint does not touch; the new notification-settings
  test had the same dependency).

### Decisions for the orchestrator

- D-177: the 0007 pipeline itself does not refuse a garbage recipient. `EmailRouter` and the
  message validation are structural; `EmailAddressList.IsWellFormed` refuses only white space,
  control characters and angle brackets. The refusal comes from the transport: the SMTP adapter
  pre-checks every address with `MailboxAddress.TryParse` (`SmtpEmailSender`) and answers
  `Rejected`; SendGrid and ACS answer 400 → `Rejected`; the Development log sink and the
  capturing transport accept anything. `OutgoingEmailHandler` records `Rejected` with
  `Email.Rejected` and the detail, which the new test pins. If the outbox should refuse at
  enqueue, that is a spec 0022 change.

### Open risks

- Email being delivering everywhere changes delivery-job enqueueing for compositions that relied
  on email having no sender (the default preference is off, so only opted-in users are affected).
- The test send's `sentAt` is formatted in the tenant's zone even when the caller's preferred zone
  differs, as the spec says; a reader in another zone may find it surprising.

### What reviewers should examine hardest

- The `Added` predicate shared by the notice and the welcome email (statuses, subject match) and
  the recompose path asserting one notice.
- `NotificationPreferenceRules.Save` for another user: the interpolated id, the TVP for the tag
  bump, and the lock.
- `EmailNotificationChannel.SendTestAsync`'s outcome mapping and that no log carries the address.

### Findings

**R1-1 (minor) — the commit's test list omits the existing integration tests of the invite's
System-scope path, and no test pins the System-scope notice.**
`src/core/Tellma.Core/Users/UserService.Invite.cs:107` now raises `core.user.added` with
`ActorUserId = request.IsSystem ? null : caller.UserId` on the provisioning path
(`TenantAdministratorInviter`, which runs `invite` in the platform's scope). The existing tests of
that path are `test/core/Tellma.Core.IntegrationTests/Migrator/AdministratorInvitationTests.cs`.
They are outside the Users, Notifications and Outbox namespaces the commit ran, so PLAN §7.1
item 4 ("the existing tests of the code it changes") was not met for them. I ran them: 4 passed.
So the path works today, but neither they nor any unit test assert the System-scope notice. If
the `null` branch were dropped (the actor became the system user's id) or the notice were skipped
for the platform's scope, nothing would fail. Fix: in
`A_provisioned_tenant_invites_its_administrator_once_links_the_account_and_queues_the_welcome`,
assert one `core.user.added` row for the administrator with `ActorUserId IS NULL`. Name the
Migrator class in the commit's test list.

**R1-2 (minor) — the partial-failure test does not pin the prefix's notice (or welcome email).**
In `test/core/Tellma.Core.IntegrationTests/Users/UserIdentityActionTests.cs:325`
(`An_invite_the_identity_server_answered_in_part_commits_the_prefix…`), 0018 §3.3 says the
composed persist batch, which now includes the notices, executes before the
`PartialFailureException` surfaces. The test checks the row, the hint and the round trips, but not
that Ada was noticed and Bob was not. A refactor that raised the notice after `context.Persisted`,
or only on the full-success path, would pass every test. Fix: add
`_ = Assert.Single(await NoticesAsync(ada)); Assert.Empty(await NoticesAsync(bob));` and the same
for `WelcomesAsync`.

**R1-3 (minor) — a refused test email and an email outage are one telemetry outcome.**
`src/core/Tellma.Core/Users/UserService.Notifications.cs:102-104` counts every
`DependencyUnavailableException` as `outcome = Unavailable`. `EmailNotificationChannel.SendTestAsync`
(`EmailNotificationChannel.cs:313-314`) raises the same exception for `Rejected` (a permanent,
per-address refusal, such as a mistyped contact address or a provider suppression) as for
`TransientFailure` and a throwing transport. An operator watching
`tellma.users.test_notifications{outcome=Unavailable}` for outages then sees users' bad
addresses. The users see "email temporarily unavailable" for an address that will never work. The
spec does not enumerate the outcome tag values, so a distinct tag is within it. Fix: let the
channel signal the refusal (for example, `DependencyUnavailableException.Arguments`, or an inner
exception type the endpoint recognises) and count `outcome = Rejected`. Add a
`UsersTelemetryNames.TestNotificationRejected` constant and a unit case. For Ahmad: 0021 §4.4's
`TestNotificationResult` has no value for "the transport refused your address". A `Rejected`
member answered 200 would let My settings tell the user to check their address instead of
retrying.

**R1-4 (minor) — two XML docs state what the code does not do.**
- `src/core/Tellma.Core/Users/UserServiceDependencies.cs:210-212`: `ChannelSender` says "the
  host's other senders are never created for it". It enumerates
  `Services.GetServices<INotificationChannel>()`, which creates every registered sender in the
  scope. Fix: say that the senders are resolved only when a test message needs one, or resolve the
  one wanted without creating the rest.
- `src/core/Tellma.Core/Notifications/NotificationsLog.cs:90` ("The address is not logged; the
  transport's detail is") and `src/core/Tellma.Core/README.md:1396` ("never the address"):
  `TestEmailNotSent` logs `result.Error` at Warning, and the SMTP adapter's details quote the
  recipient (`SmtpEmailSender.cs:217`, `'{address}' is not a valid mailbox address.`, and `:249`,
  the 5xx mailbox). Spec 0007 §9.2's PII rule accepts error texts that quote the address, so the
  behaviour is fine, but the docs promise more. The unit test only passes because its scripted
  detail holds no address. Fix: say that the channel adds no address of its own and that the
  transport's detail may quote one.
