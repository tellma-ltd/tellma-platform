# PC-035: Notification and realtime contracts, registries and null publisher

## Implementer notes

### What was built, and where

**Contracts** (`src/core/Tellma.Core.Abstractions/`):

  - the registries `INotificationTypeRegistry` and `INotificationChannelRegistry`;
  - `INotificationRenderer`;

  - `NotificationsOptions` (§9.1), whose data annotations carry the §9.1 bounds. `IValidatableObject`

  - The converter writes `[text, text2|null, text3|null]` under any options. It refuses every other

  - `In(slot)` takes slots 1 to 3 and falls back to `Text` when the slot is null or empty.

    bypass the null check.
- `TableTypes/`: `NotificationRowList`, `NotificationSliceList` and `NotificationPreferenceList`
  (§3.2, §4.3).
- `Composition/`: the three item records `NotificationTypeContributionItem`,
  `NotificationChannelContributionItem` and `ClientEventContributionItem`. `FeatureContribution`
  gains the sugar `NotificationType(descriptor)`, `NotificationChannel(descriptor)` and
  `ClientEvent(name)`, each refusing null.
- `Crud/` and `Validation/`: contract-first seeds of spec 0015's write frame, which
  `INotificationChannel.DeliverAsync` names. These are `IWriteHost`, `WriteHostKind`,
  `IOpenWriteHost` (`PersistAsync(CancellationToken)`), `EnlistmentOutcome` and `IConfirmations`.
  Each is shaped as spec 0015 §13.3/§7.5 sketch it, plus the token; see "Decisions for the
  orchestrator".
- `Data/IDataBatch`: gains `IsComposing`, true until the batch executes (and false once a
  contributor's failure left it incomplete), so the publisher can refuse an executed batch on every
  publish.

**Runtime** (`src/core/Tellma.Core/`):

- `Notifications/`:
  - `NotificationTypeRegistry`, `NotificationChannelRegistry` and `ClientEventRegistry`. Each keeps
    realisation order and the first item of a key, skips null items and keyless ones, and does
    ordinal lookups. `Categories` lists each category once, in the order of its first type. A null
    key passed to `Find` or `IsRegistered` gives null or false.
  - `NotificationsClientAssetContributor` writes `notificationTypes`, `notificationChannels` and
    `clientEvents`, in that order, into the Core chunk, with `TellmaJson.Options`.
  - `ClientEventPublisher` is a public abstract base, and `NullClientEventPublisher` derives from
    it. The base holds:
    - the refusals: null event (`ArgumentNullException`), null `UserIds` (`ArgumentException`),

      `JsonSerializer.SerializeToUtf8Bytes(payload, TellmaJson.Options)`. Both refusals are
      `InvalidOperationException`, thrown synchronously by `Publish` and `PublishAsync` before
      anything is registered.
    - a `protected virtual ValidateScope(ClientEvent)` hook. The SignalR publisher will refuse a
      tenantless scope through it.
    - the coalescing. A `ConditionalWeakTable<IDataBatch, …>` under a `Lock` gives one `OnCommitted`

      batch, committed or failed, is refused whether or not events were already published on it.
      That one callback sends each distinct
      (name, sorted distinct user ids, payload JSON) once, in first-publish order.
    - failure handling: a failed delivery, thrown or faulted, is logged as `ClientEventFailed` at
      warning and never thrown.
    - Without a batch, an event is sent fire-and-forget.
  - `NullRealtimeStatus`, which is internal.
  - `NotificationNames`, the four grammars.
  - `NotificationsLog`.
  - `NotificationsComposition`, called from `CompositionPipeline.Realise` after `DataComposition`.

    null publisher and `TryAddSingleton` of the null status.

### Deviations

1. The three realizers live in `Tellma.Core.Composition.Realizers`, beside every other realizer.
   §1.1 lists them under the `Tellma.Core.Notifications` row.
2. The check names carry the `core.` prefix of every built-in check (`core.notification-types`,
   `core.notification-channels`, `core.client-events`). §11 names them without it.
3. §11's `notification-options` check is not a separate check. `NotificationsOptions` binds through
   `OptionsRegistrar`, and `core.options` validates it with every other options type. This is the
   D-016 pattern.
4. A `TargetResource` must name a stack resource. §11 also accepts "a registered securable
   resource". No securable registry exists yet, so a non-entity securable target is refused today.
   The seam is commented in `NotificationTypesCheck.CheckTargets`.
5. The three table types are classes only. They are not contributed to the model (`TableType<…>()`
   in `CoreFeature`), because that would regenerate the Acme and fixture migrations and change the
   model fingerprints. The checkpoint asks only for the classes, and §11's "the three standalone
   table types on the model" belongs with the statements that bind them (0021-b).
6. `ClientEventPublisher` is a public abstract base that is not in the spec. It keeps the refusals,
   the coalescing and the failure logging in one place for the null publisher and the future SignalR
   one. The tenantless-scope refusal of §6.4 goes into its `ValidateScope` hook. The null publisher
   applies only the §6.3 refusals, as §6.4 says.
7. A `ClientEvent` with null `UserIds` is refused with `ArgumentException`. The spec says nothing;
   an empty list means "every connected user", so null cannot.
8. `NotificationTypesCheck` also refuses an undefined `Severity`, which the spec does not list. A
   cast value has no name to store in `Severity varchar(8)`, and `StrictEnumJsonConverter` refuses
   it in the client metadata.
9. `NotificationsOptions` validates the two retention periods (at least 1 s, at most
   `int.MaxValue` s). §9.1 bounds only the counts.
10. Spec 0015 frame types are seeded here as contracts: `IWriteHost`, `WriteHostKind`,
    `IOpenWriteHost`, `EnlistmentOutcome` and `IConfirmations`. §4.4's `INotificationChannel`
    names `IOpenWriteHost`, which did not exist.
11. `TellmaCompositionRecord.Services` records every service registration with its feature, so
    `core.notification-channels` can name a sender's feature, as §11 requires.
12. `IDataBatch` gains `IsComposing` (review 1). The publisher needs it to refuse a publish on an
    executed batch uniformly, as `IClientEventPublisher.Publish` documents.
13. `IOpenWriteHost.PersistAsync` takes a `CancellationToken` (review 1), which spec 0015's sketch
    omits by convention.

### Decisions for the orchestrator

- PC-062 still lists `WriteHostKind`, `IWriteHost`, `IOpenWriteHost`, `EnlistmentOutcome` and
  `IConfirmations` as deliverables. They are seeded here, so a planner note on PC-062 should read
  "extend the seeded write-frame types, do not re-declare them".
- The tenant-free constructor constraint on notification channel senders binds 0018-f and 0022-a
  (`EmailNotificationChannel`), and belongs as a planner note on those checkpoints.

### Open risks

- **The senders are resolved in the gate's tenantless scope.** This is the only way to read
  `INotificationChannel.Key`. A future sender whose constructor needs a tenant (or anything
  request-bound) fails the gate with "could not be created". `EmailNotificationChannel` (spec 0018)
  must keep its constructor tenant-free, or resolve tenant-bound dependencies lazily. The fix text
  says so.
- **The Guid-key rule is unreachable through composition.** `Entity<TKey>` constrains the key to
  `IBinaryInteger<TKey>`, and `SequenceConvention` refuses anything but `int` and `long`. So a
  target with a Guid key is tested on hand-built metadata. Through composition, such an entity
  fails `core.entity-metadata` first, and the target check is skipped.
- **The `PublishAsync` delivery of the SignalR publisher must still count `tellma.realtime.events`**
  and resolve the tenant. Both belong in its `DeliverAsync` and `ValidateScope`. The base does
  neither.
- **The coalescing table is per publisher instance, which is scoped.** A batch published on from two
  scopes would get two callbacks. Batches are scope-bound, so this cannot happen today.

### What reviewers should examine hardest

- `ClientEventPublisher.Publish`: the callback is registered before the batch is remembered, and the
  flush removes the entry under the lock. Every publish checks `IDataBatch.IsComposing` first. Is
  there any path where an event is silently held on an executed batch?
- The dedup key: user ids as a sorted distinct set, and the payload as its serialised JSON.
  Anonymous objects with the same members in another order are different payloads.
- `NotificationChannelsCheck.SenderOwners`: a sender created by a factory matches no implementation
  type, so it is attributed to every feature that registered a factory sender ("one of the
  features").
- The `LocalizedText.Names` cache key (type, anchor name). `Attribute.GetCustomAttribute(…,
  inherit: true)` walks overridden properties, and the tests cover an override that does not
  restate `[Multilingual]`.

## Review 1

### Findings

**R1-1 (major): `core.notification-types` refuses every stack resource that is not a `TopLevelEntity`, including targets the spec's own catalogue declares.**
`src/core/Tellma.Core/Composition/Checks/NotificationTypesCheck.cs:117-142` builds the accepted
targets from `metadata.All.Where(entity => entity.IsTopLevel)`. `IsTopLevel` means "derives from
`TopLevelEntity<>`" (`src/core/Tellma.Core/Data/EntityShapes.cs:38`). But a stack resource is any
entity contributed through `Entity<T>()`, which has no `TopLevelEntity` constraint
(`FeatureContribution.cs:183`). The system-written entities are stacks that derive from
`Entity<int>`: spec 0020's `Job` ("stack resource core.Job") and 0021 §2.2's own `Notification`.
The test suite already composes such a stack (`Entity<MdJob>()` in `EntityMetadataCheckTests`).
- Failure scenario: when 0020 registers `core.job.failed` or `core.job.pending-confirmation`
  (§2.3 catalogue, target `core.Job`), the gate fails with "targets 'core.Job', which is not a
  top-level entity of the model". Every composition then refuses to start. A distribution that
  targets its own `Entity<int>` stack fails the same way.
- The rule is also loose in the other direction. A `TopLevelEntity` mapped only through `Model<T>`
  (no stack, no route) passes, although §11 asks for a target "the client can route".
- Fix: derive the stack resources from `record.Entities`, resolved through `record.Leaves`, then
  `metadata.Get(leafType).Name`. Keep the int/long key rule on that metadata. Reword the problem and
  fix texts and the README row (`src/core/Tellma.Core/README.md:610`) from "top-level entity" to
  "stack resource". Add a test that targets an `Entity<int>` stack (an `MdJob`-like fixture
  contributed with `Entity<T>()`), and one that refuses a model-only entity.
- Ruling on "TargetResource is checked only against top-level entities": rejected for this reason.
  Refusing a non-entity securable until the securable registry lands is fine; the seam comment
  stands.

**R1-2 (minor): the commit does not list the integration suites as run, though every one counts as touched.**
The commit changes `src/core/Tellma.Core.Abstractions`. By PLAN.md §7.1 item 4, every integration
suite therefore counts as touched and must run with
`Category=Integration&Category!=Nightly&Live!=true`. The commit message lists unit suites only.
- I ran them on c49c44f after a clean `dotnet build Tellma.slnx` (Build succeeded, 0 warnings):
  - Tellma.Core.IntegrationTests: 131/131 passed;
  - Tellma.Core.EntityFrameworkCore.IntegrationTests: 10/10 passed;
  - Tellma.Core.Queryex.IntegrationTests: 289/289 passed;
  - Tellma.Identity.IntegrationTests: 205/205 passed.
- So nothing is broken. But the composition change (three new built-in checks, sender resolution
  in the gate scope, `NotificationsComposition` in `Realise`) runs in every integration host, so
  these runs were required.
- Fix: list the four suites and their counts under "Tests:" in the final commit message.

**R1-3 (minor): the write-frame seed has no `CancellationToken` on `IOpenWriteHost.PersistAsync`, and PC-062 still lists these types as its own deliverables.**
- `src/core/Tellma.Core.Abstractions/Crud/IOpenWriteHost.cs:23` declares `Task<EnlistmentOutcome> PersistAsync();`.
  - Spec 0015 §1 omits cancellation tokens from every sketch by convention. This commit's own async
    contracts add them (`INotifier.NotifyAsync`, `INotificationChannel.DeliverAsync`/`SendTestAsync`).
  - The job frame's persist must observe the job's lease and host-stop cancellation (0020's job
    frame). So 0015-a would have to change the seeded signature.
  - Fix: declare `Task<EnlistmentOutcome> PersistAsync(CancellationToken cancellationToken = default);`
    now, while nothing implements it.
- The other four types match 0015 §7.5/§13.3 member for member, so a later checkpoint can extend
  them without breaking them. Ruling on "write-frame contract types": accepted, with this one fix.
- CHECKPOINTS.md PC-062 (0015-a) still lists `WriteHostKind, IWriteHost, IOpenWriteHost, …,
  EnlistmentOutcome` and `IConfirmations` as deliverables.
  - Implementer notes line 40 points to a "Decisions for the orchestrator" section that the review
    file does not contain.
  - Fix: add that section and ask the orchestrator for a PC-062 planner note: "extend the seeded
    write-frame types, do not re-declare them" (the pattern PC-015 used for the notification
    descriptors).

**R1-4 (minor): a sender registered through a factory is attributed to no feature.**
`NotificationChannelsCheck.SenderOwners` (`NotificationChannelsCheck.cs:145-161`) matches a sender
to its feature only by `ImplementationType`.
- Failure scenario: a feature registers `Scoped<INotificationChannel>(sp => new SmsChannel(…))` with
  a typo'd key. The problem then reads "registered by a registration outside the features". §11
  requires that "a failed check names the feature that contributed the offending item".
- Fix: when no implementation type matches, fall back to the features that registered
  `INotificationChannel` by factory (`ImplementationType is null`), worded as "one of the features
  …". Only when there are none, keep "outside the features". Add a test with a factory-registered
  sender of an unregistered key.

**R1-5 (minor): a publish on a batch that failed is silently accepted, contrary to the documented contract.**
`IClientEventPublisher.Publish` documents `InvalidOperationException` when the "batch already
executed". `ClientEventPublisher.Publish` (`ClientEventPublisher.cs:69-82`) calls
`batch.OnCommitted` only for the first event of a batch.
- Failure scenario: an event is published on a batch, the batch's execution throws (no commit, so
  no `Flush`), and the caller publishes again on that batch. The cached `PendingEvents` takes the
  event and nothing throws. The implementer notes acknowledge this case.
- Nothing wrong is ever sent, but the contract and the behaviour disagree.
- Fix: either narrow the XML doc ("refused when the batch executed before any event was published
  on it"), or probe the batch on every publish so that the refusal is uniform.

### Rulings

- **Write-frame contract types:** accepted; see R1-3 for the one signature to fix and the planner
  note.
- **Notification table types off the model until 0021-b:** accepted. The checkpoint asks for the
  classes only.
  - Standalone table types map composite `[Key]`s through the extension's own annotation path
    (`TableTypesModelBuilderExtensions`), not EF's `KeyAttributeConvention`. So
    `NotificationPreferenceList`'s two `[Key]`s will map when 0021-b adds it.
- **Check ids folded into `core.options` and `core.*`-prefixed:** accepted. This is consistent with
  D-016 and every built-in check.
- **TargetResource against top-level entities only:** rejected; see R1-1.
- **Channel senders created in the gate's tenantless scope:** accepted.
  - `INotificationChannel.Key` is an instance member, so the gate must create the senders, and
    `ITenantDatabase` and its peers resolve lazily.
  - The constraint binds 0018-f and 0022-a (`EmailNotificationChannel` must keep a tenant-free
    constructor). It should become a planner note on those checkpoints, not only an implementer
    open risk.
- **`ClientEventPublisher` as the SignalR seam:** accepted.
  - The refusals, the coalescing and the logging are shared.
  - `ValidateScope` runs at publish time, before registration, as §6.3 demands.
  - The tenant resolution and the `tellma.realtime.events` count belong in the SignalR subclass's
    `ValidateScope` and `DeliverAsync`.
- **Guid-keyed targets unreachable through composition:** accepted.
  - `Entity<TKey>`'s `IBinaryInteger` constraint and `SequenceConvention` leave int and long as
    the only composable keys.
  - Exercising `CheckTargets` on hand-built metadata is an adequate pin for the §12 row.
