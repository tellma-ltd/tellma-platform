### Deviations

1. **`IImageProcessor` carries `kind` (both methods) and `timeout` (`ThumbnailAsync`).** §10.1 tags
   both image instruments by `kind`, §10.2's `BlobImageRender` names the kind, and only the processor
   can tell a render that ran out of time (`reason=timeout`) from a file it cannot render (both are
   null), or knows when native work starts (after the PDF gate is acquired). So the processor records
   both instruments and the render event itself, and needs the kind. `BlobOptions.ThumbnailTimeout`
   lives in `Tellma.Core`, which the processor cannot reference, so the budget is a parameter rather
   than a second option. **Seam for PC-083:** `BlobService` passes the kind and
   `BlobOptions.ThumbnailTimeout`, and must not record `image.duration`/`image.failures` again.
2. **`CoverSquare` never upscales**: the output side is `min(MaxDimension, shorter side)`; §3.6 says
   "scales to MaxDimension" while `Contain` says "without upscaling". Upscaling invents no detail and
   stores and serves more bytes; a 200-pixel avatar stays 200 x 200. Thumbnails of images never
   upscale either; a PDF page (vector) is always fitted to `Size`.
3. **Managed signature gate before Skia.** The input's leading bytes must be one of the four image
   signatures (or `%PDF-` for a PDF thumbnail) before any native call, and Skia's codec must then
   report the same format. This keeps Skia's BMP/ICO/WBMP/raw decoders and PDFium's leading-junk
   tolerance out of reach of uploads.
4. **The time budget cancels for real.** Native decoders read the input through `GatedReadStream`;
   when the budget (or the caller's token) fires, the call returns at once and the view reads as end
   of input, so a streaming decode in flight (JPEG, PNG, GIF, PDFium's lazy reads) stops at its next
   read. No view member a native reader calls ever throws (a managed exception through a reverse
   P/Invoke frame would kill the process). After `ThumbnailAsync` returns no new read of the caller's
   stream starts. The budget covers the wait for the PDF gate; a render that is still waiting when it
   runs out never starts. A render already inside PDFium keeps the gate until it returns (§3.6).
5. **`ThumbnailAsync` requires a readable, seekable stream** (`ArgumentException` otherwise), reads
   from its current position, and leaves it open. PDFtoImage requires seeking.
6. **A `core.imaging` startup check** (not in §9): Skia encodes and decodes a 2 x 2 WebP and PDFium
   opens a one-page PDF (behind the render gate), so a missing or mismatched native asset fails
   startup with a fix hint instead of the first upload with a 500. `RequiresInfrastructure = false`,
   like `core.globalization`. Registered by `AddTellmaSkia` with `TryAddEnumerable`.
7. **Rejection shape**: code `Image.Rejected`; arguments `reason`, plus `width`, `height`,
   `maxPixels` for `too-many-pixels`. `BlobService` maps it to `Blob.ImageRejected` (§8.2).
8. **Encrypted PDFs**: a PDF that needs a password (or uses an unsupported security handler) yields
   null and counts `decode-failed`; one encrypted with an empty user password (owner restrictions
   only) opens and renders, since nothing secret is needed to show it.
9. **Two log events beyond §10.2**: `BlobImageFailed` (Debug; kind, operation, reason, detail,
   exception) and `BlobThumbnailUnexpectedFailure` (Warning) for an exception type the processor does
   not anticipate; such a thumbnail still yields null and counts `decode-failed`, since §3.2 step 6
   makes every non-render null.
10. **Output choices the spec leaves open**: WebP lossy q80, JPEG q85 4:2:0, PNG default zlib;
    colour profiles converted to sRGB at decode and the output untagged (so no ICC is written);
    JPEG output (no alpha) composites transparency over white; truncated/incomplete images are
    refused (`decode-failed`) rather than stored half-decoded.
11. **Project and pin set beyond §1.1's list**: the project also references
    `Microsoft.Extensions.DependencyInjection.Abstractions`, `.Diagnostics` and
    `.Logging.Abstractions` (registration, `IMeterFactory`, `[LoggerMessage]`), as every Core-layer
    package does; the Skia Win32/macOS natives and the three PDFium packages are pinned (not
    referenced) so every native moves in lockstep with its managed library under transitive pinning.
12. **The `IImageProcessor` remarks** now state that an implementation records the image
    instruments and the render event itself.

### Open risks

- **PDFium memory is not capped.** The output bitmap is bounded (`Size` squared), but PDFium decodes
  an embedded image at its own resolution while rendering; a PDF carrying a huge flate-compressed
  image can make it allocate gigabytes in-process. The time budget bounds the caller's wait, not
  PDFium's memory. Review flag 23's out-of-process renderer is the structural fix.
- **`ProcessAsync` has no time budget** (§3.5 gives one to thumbnails only). Within the pixel cap a
  hostile progressive JPEG with very many scans can cost seconds of CPU; only the caller's
  cancellation (request abort) stops it, through the gated view. Suggest applying the same budget
  to normalisation (a decision for the orchestrator, see return value).
- **A slow PDF holds the process-wide gate**: while one render is stuck in PDFium, every other PDF
  thumbnail waits out its budget and stores none. Degrades thumbnails, never uploads.
- **Native symbol weight**: `SkiaSharp.NativeAssets.Win32` ships a ~100 MB `libSkiaSharp.pdb` per
  Windows RID, copied into every output that references the package (~300 MB RID-less, ~100 MB in a
  win-x64 publish). Not trimmed here; a build target removing the pdb from the copy-local items would
  need its deps.json effect verified first.
- **The handle-leak probe reads a SkiaSharp internal** (`HandleDictionary.instances`); an upgrade
  that renames it fails the probe loudly, never silently. Mutation-checked: dropping one `using`
  fails it (9 live objects expected, 34 found).
- **linux-arm64** natives are verified present in the output, not executed (no arm64 runner).
- **Versions**: SkiaSharp 4.152.5 / 4.155.0 and newer PDFium builds exist (published 2026-11-06 and
  later); the spec's 4.152.1 and PDFtoImage's PDFium 152.0.7961 are kept. PDFium security fixes need
  a PDFtoImage bump.

### Findings

**R1-1 (blocking): `ProcessAsync` has no time budget, and image work has no concurrency limit (D-030).**
- Where:
  - `src/core/Tellma.Core.Imaging/SkiaImageProcessor.cs:124-135`: normalisation runs inline with
    only the caller's token.
  - `src/core/Tellma.Core.Imaging/SkiaImageProcessor.cs:222-228`: every image thumbnail is a fresh,
    unbounded `Task.Run`.
  - `src/core/Tellma.Core.Abstractions/Blobs/IImageProcessor.cs:45-46`: no budget on the contract.
- Scenario: a member fires N parallel uploads of the `Photo` or `Avatar` kind. Each stays within
  `MaxSize` and the 50 MP cap.
  - Memory: a flat 7000 x 7000 PNG compresses to a few hundred KB. It decodes at full size (§3.5)
    into a 196 MB RGBA frame, plus about 65 MB of mipmaps for the trilinear downscale draw
    (`SkiaPipeline.cs:32` and `:296`). For an interlaced PNG, Skia's interlaced path also buffers
    all rows in the source format, up to 8 B/px for 16-bit RGBA.
  - CPU: a progressive JPEG with tens of thousands of tiny EOB-run scans makes libjpeg sweep every
    block once per scan. It pins a core for as long as its input lasts, and only a request abort
    stops it.
  - Nothing bounds N, so N x (260-600 MB) and N cores are taken. Timed-out thumbnails make it
    worse: each abandoned decode keeps its thread and its frame until it ends, while new uploads keep
    starting more.
- Can the implementation stop native work? Only partly. The gated view does stop a streaming decoder
  at its next read. That is effective where CPU tracks input consumption: JPEG scans, PNG and GIF
  data, and PDFium's lazy object loads.
  - My probe on a 4 MB noise WebP: Skia's WebP codec had already pulled 54 % of the input at
    `SKCodec.Create`. JPEG pulled 1 KB and PNG 56 bytes at that point.
  - No read happens at all during the post-input phases: final IDCT and colour conversion, the
    mipmap build, the resample and the encode.
  - So an abandoned call keeps burning CPU and holding its frame for an interval the pixel cap
    bounds but nothing ends. The budget alone cannot bound the damage.
- Fix:
  1. Give `ProcessAsync` a `TimeSpan timeout` like `ThumbnailAsync`. Link it into the
     `GatedReadStream` token. Running out records `failures{reason=timeout}` and throws
     `ImageRejectedException` with `reason=timeout` (or whatever the orchestrator rules; see the
     return value). BlobService (PC-083) passes a `BlobOptions` value.
  2. Add one process-wide image-work gate, a `SemaphoreSlim` with N = max(1, ProcessorCount / 2)
     or an option. `ProcessAsync` and the image-thumbnail path both acquire it within their budget,
     and the work itself releases it in a `finally`, as `PdfRenderGate` is released. An abandoned
     decode then keeps its slot until it truly ends. A hostile file wastes one slot, and memory is
     bounded by N x (frame + mipmaps + output).
  3. Either document the extra third for mipmaps against §3.5's "MaxInputPixels x 4" as a
     deviation, or drop mipmaps for full-size PNG/GIF decodes.
  4. Tests on `FakeTimeProvider`:
     - `ProcessAsync` over a blocking stream yields the timeout rejection at the budget.
     - With N slots held by blocked decodes, call N+1 waits and then times out without starting.
     - A slot is released only when the abandoned work ends.

**R1-2 (blocking): PDFium's decoded raster size and page size are not capped before rendering (D-030).**
- Where: `src/core/Tellma.Core.Imaging/PdfRasterizer.cs:62-82`.
- Already in place:
  - Only page 1 is opened, through lazy loading.
  - The output bitmap is fitted to `Size`.
  - The page size is checked only for being finite and positive.
- Exposure:
  - Memory: PDFium decodes each embedded image at its own resolution, whatever the output size.
    Flate and DCT decode through scanline decoders, but JPX (OpenJPEG) and JBIG2 decode whole
    images into memory. A JPX or JBIG2 stream of a few KB can declare tens of thousands of pixels
    per side. That allocates gigabytes in-process, outside the GC and beyond any timeout, and on a
    memory-limited Linux container it OOM-kills the web host. Any member can trigger it with an
    `Attachment` upload.
  - CPU: a form-XObject fan-out (each form draws the next k times, depth d) makes one
    `FPDF_RenderPage` call draw on the order of k^d objects.
  - The gate: PDFtoImage offers no pause callback, so the gate stays held until restart. Every later
    PDF upload then waits the full 5 s budget and stores no thumbnail.
  - Page count is not an exposure, since only page 1 is loaded.
  - Page size does not drive output memory, but PDFium accepts absurd MediaBoxes, so a cap is cheap
    hygiene.
- Mitigation:
  1. Before `Conversion.ToImage`, pre-walk page 1 through PDFium's own exported API with a small
     `LibraryImport` binding to the same bblanchon binary: `FPDF_LoadMemDocument64` or the custom
     loader, `FPDF_LoadPage`, `FPDFPage_CountObjects`/`GetObject`, `FPDFPageObj_GetType`,
     `FPDFImageObj_GetImagePixelSize`, `FPDFImageObj_GetImageFilter`, and `FPDFFormObj_CountObjects`
     to recurse. Hold the gate while doing so. Yield null (decode-failed) when:
     - any image declares more than `DefaultMaxInputPixels`;
     - a JPX or JBIG2 image declares more than a smaller cap, for example 16 MP;
     - the object total across forms exceeds a cap, for example 100,000;
     - page 1 is larger than 14,400 pt x UserUnit.
  2. Cap the input length for PDF thumbnails, for example 32 MiB, so a damaged-xref rebuild scan
     stays bounded.
  3. Fail fast, with null and `reason=timeout`, without waiting out the budget, while the gate is
     held by a render whose caller has already given up. This needs one flag set and cleared around
     the abandoned render.
  4. Record the residual risk (non-image content memory, PDFium bugs) against the out-of-process
     renderer (review flag 23).
  5. Tests through the rasterizer seam: a PDF whose image XObject declares 20000 x 20000 and one
     with a fan-out of forms both yield null, and the render is never called.

**R1-4 (major): "No new read of the caller's stream after return" is a check-then-act race. A late native read can move the stream position while the caller is writing the primary.**
- Where:
  - `src/core/Tellma.Core.Imaging/GatedReadStream.cs:97-111` and `:164-170`;
  - `src/core/Tellma.Core.Imaging/SkiaImageProcessor.cs:262-267`;
  - the contract text at `src/core/Tellma.Core.Abstractions/Blobs/IImageProcessor.cs:55-57`.
- Scenario:
  1. The thumbnail budget runs out while a decoder thread has passed the `IsClosed` check, or is
     already inside `_inner.Read`. `TimeBudgetTests.An_image_decode_in_flight_stops_reading_the_input_once_the_budget_runs_out`
     exercises exactly this: its blocked read completes after the call has returned.
  2. `ThumbnailAsync` returns null.
  3. BlobService (PC-083, §3.2 steps 6 then 9) is likely to rewind the same stream and copy the
     primary into the store. That stream is either the in-memory buffer or the delete-on-close temp
     `FileStream`.
  4. The native thread then runs `_inner.Position = _origin + _position; _inner.Read(...)` and moves
     the position under the store's sequential copy.
  5. The stored primary is silently corrupted: bytes are skipped or re-read, while the SHA-256 was
     taken in step 3. Neither stream type is thread-safe anyway.
  6. The contract says "the caller may dispose the stream", which invites exactly this reuse.
- Fix:
  - Hold one lock across the closed check and the inner `Position` + `Read` in `Read(Span<byte>)`.
    Take the same lock in `CloseGate`/`Dispose`.
  - After `Dispose` returns, no inner access is then in flight and none can start. Inner reads are
    single bounded calls, so the wait is short.
  - Reword the remark to "once the call returns, the processor no longer touches `input`".
  - Test: a stream that blocks inside `Read`. `ThumbnailAsync` must not complete until that read
    returns, and the stream sees no `Position` set after completion. The existing in-flight test has
    to release before awaiting.

### Responses

- **R1-1: fixed in 8c01d52** (orchestrator ruling D-030 addendum).
  - `IImageProcessor.ProcessAsync` takes a `TimeSpan timeout`. It bounds the wait for a slot and,
    separately, the work.
    - No slot within the budget throws the new `ImageProcessingBusyException(RetryAfter)` in
      `Tellma.Core.Abstractions.Blobs`. It is an infrastructure exception like `BlobStoreException`,
      for the web surface to map to 503 with `Retry-After`. It is logged as `BlobImageBusy` (Warning)
      and not counted as an image failure.
    - Work past its budget records `failures{reason=timeout}` and throws `ImageRejectedException`
      with the new `ImageRejectedException.TimeoutReason` (`timeout`), mapped to `Blob.ImageRejected`.
  - Image work now runs in `SkiaImageProcessorOptions.ImageConcurrency` slots (a `SemaphoreSlim`).
    Normalisations and image thumbnails both acquire a slot within their budget, and the work releases
    it in a `finally` when its native part ends.
    - The option is bound by `AddTellmaSkia` from `Tellma:Blobs:ImageConcurrency`, the key the ruling
      names. Its default is max(1, ProcessorCount / 2), and an `IValidateOptions` refuses zero.
    - The processor binds the value itself because `BlobOptions` lives in `Tellma.Core`, which it
      cannot reference. PC-083's `BlobOptions` carries `ImageProcessTimeout` (15 s) and passes it
      per call. Any `ImageConcurrency` there only documents the same key.
  - Mipmaps are kept and documented (README and remarks): a decode costs four bytes per pixel under
    the cap, plus a third for the mipmaps of the downscaling draw.
  - Tests (`TimeBudgetTests`, fake clock):
    - normalisation past its budget is a timeout rejection that keeps its slot until the decode ends;
    - with every slot busy, an upload is refused as busy and never starts;
    - an image thumbnail waiting for a slot yields null and never starts;
    - a mid-decode cancellation stops the decode and counts no failure.
  - An `openInput` seam on the internal constructor lets the suite block a decode inside its input.
- **R1-2: fixed in 8c01d52.**
  - New `PdfPreflight` binds PDFium's exports through `LibraryImport` to the same `pdfium` library.
