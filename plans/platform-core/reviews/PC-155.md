# PC-155: /attention model: TmAttention, TmArrivals, TmAttentionText, banner host

## Implementer notes

### What was built

Spec 0028 §5.2–§5.4, §8.1–§8.3, §9.4 and §11, in `client/projects/core/tellma-core/attention/`
(the eager `@tellma/core/attention` entry point and two lazy chunks of it).

- **Attention model** (`src/tm-attention.ts`, eager). `TmAttention`, root.
  - `inbox` and `assignments`: the routed tenant's stored copies (`TmCacheRefresher.ɵpartition` +
    `TmClientStore.doc`), the inbox with this tab's overlays applied.
  - `bell`/`tray` badges: the count capped at 100 (`99+` through core-ui's `counter.overflow`
    string and `TmL10n.formatNumber`), the bell's `attention` tone for an unseen Warning/Error, the
    jobs that are `Pending`/`Running` (not `Held`/`PendingConfirmation`), and each accessible name
    joined with the language's separator (`, ` / `، `).
  - Verbs `read`, `readAll`, `clear`, `clearRead`: guarded by `writable` (not Frozen and online),
    an overlay `{ id, verb, ids, version: null }` in the same frame, then the write; the answer's
    version is stamped on the overlay, which is released (and pruned by an effect) once a copy's
    version is ≥ it by `TmDecimals.compare`. A copy read before the verb committed but saved after
    its response therefore keeps the overlay. A failure drops the overlay at once and toasts sticky
    (`tm.attention.toasts.failed`, key `tm.attention.failed`, Try again re-runs the verb).
  - `stopJob`: a stopping overlay (`cancelRequestedAt` = now) until a copy shows the request or no
    longer lists the job; a failure drops it.
  - Read-only and capped counts: `lower()` never lowers a count at the cap, whose true value is
    unknown.
  - `toggle(panel, via)`: closes the open panel (aborting its read), emits `tm.attention.panel-opened
    { panel, via, badge: 0 | 1-9 | 10+ }`, and opens. Opening with something new and `writable`
    sets a `pending` seen hold in the same frame, sends `inbox/seen` / `assignments/seen`, then
    holds by the answer's version (bell) or seenAt (tray). Not writable, or a failed seen: an `own`
    hold that lifts with the panel's own read (its send time) or when the panel closes. Then the
    panel reads its registered document once, stamped with the send time.
  - `refresh(document)`, `live` (paused after 5 s neither connected nor disabled), `writable`, `open`.
  - A tenant change aborts the reads and drops the overlays, the holds and the open panel.
- **Server calls** (`src/tm-attention-calls.ts`, lazy chunk `tm-attention-calls`). The writes with
  `tm.attention.verb { verb, outcome }` telemetry and the failure toast, the seen, and the panel's
  read. The model imports it with its first call; every overlay stays in the eager model, so the
  same-frame rule holds before the chunk loads.
- **Arrival engine** (`src/tm-arrivals.ts`, eager). `TmArrivals`, root, created by the tenant shell.
  - Watches `inbox`, `assignments` and `tenant` per routed tenant. Each tenant entry starts its
    own clock, and the first copy observed is `previous` whatever its `savedAt` (fix1, D-257; it
    replaced the first-copy-after-start baseline); every copy moves `previous` on, in every tab, and only a
    visible, focused tab (`visibilityState === 'visible' && hasFocus()`) hands a copy on, so a tab
    that gains focus replays nothing.
  - `tmNotificationToastsKey` (`notifications.toasts`, curated, `true`) switches notification and
    assignment toasts off; tenant-state toasts ignore it.
  - Installs the toasts' overflow pill through `TmToasts.ɵsetOverflow`: inside a tenant
    "{n} more · Open notifications" navigating to `TmUrls.search('core.Notification')`; outside,
    it declines and the configured pill shows. Uninstalled on destroy.
- **Arrival toasts** (`src/tm-arrival-toasts.ts`, lazy chunk `tm-arrival-toasts`), loaded with the
  first copy handed on; registers `tm.arrivals` strings and the lucide `inbox` icon.
  - Notifications: newer `createdAt` than the previous copy's newest, unread, of a `toast: true`
    type, shown oldest first; tone by severity, Error sticky else 6 s, key `n:<id>`; Download (an
    anchor click on `blob('export-file', fileId, { download: true })`) for `core.export.ready`,
    else View (`notifications/<id>/open`) when the row has a target.
  - Assignments: newer `assignedAt`, `assignedById` not the user. One: accent, icon `inbox`, title
    "{caption} assigned/returned to you", key `a:<id>`, Open to `TmUrls.target`. Several: "{n}
    documents assigned to you", key `a:many`, View opens the tray (`toggle('tray', 'toast')` unless
    it is open).
  - Tenant: a change to ReadOnly or Frozen toasts warning with the tenant's name in the content
    slot, key `t:state`.
  - `tm.attention.toast { kind, outcome }` on every close but `api`.
- **Server text** (`src/tm-attention-text.ts`, eager). `TmAttentionText`, root, every result a
  signal that follows the language and content slot with no request.
  - `notification(type, json)`: `Notification_<type>` / `_Detail`; a missing title renders the
    type's key, a missing detail `null`.
  - `job(source)`: the job's own label key, then the handler's metadata `labelKey`, its
    `labelFallback`, its key; an `entity` argument naming an entity renders as its plural label.
  - `jobMessage(key, json)`.
  - `caption(row)`: title from `tm.attention.assignment.title` with the code split out into
    `titleSegments` for a `<bdi>`, `#<targetId>` without a code; detail from
    `Assignment_<Resource>_Detail` only when both the key and the caption's detail exist; amount
    exact at its own scale through Intl with `currencyDisplay: 'code'`, bidi controls stripped.
  - `isolate(key, args, isolated)`: any platform message split around its isolated arguments
    (private-use placeholders, then `split`).
  - Stored arguments follow the server's ICU rules (`src/tm-icu-arguments.ts`): booleans → `true`
    / `false`, a 3-element LocalizedText passes for `TmServerText` to resolve, other arrays and
    objects → JSON text, non-object JSON → no arguments.
- **Outcome toasts** (`src/tm-outcome-toasts.ts`, eager). `TmOutcomeToasts.jobStarted(jobId)`
  (accent, 4 s, key `job:<id>`, Track to `target('core.Job', id)` when the job has a page) and
  `exporting(cancel)` (neutral, sticky, Cancel).
- **Banner host** (`src/tm-banner-host.ts`): a dismiss that empties the row while focus was in it
  moves focus to `main` (with `tabindex="-1"` added when absent, `preventScroll`) after the render.
- **Strings**: `src/tm-attention-strings.ts` registers `tm.attention` (bell, tray, separator,
  assignment title, overflow pill, failure toast, outcomes) through `ɵregisterStrings`; Arabic in
  `locale-ar/strings/strings-tm-ar.ts` under `attention` and `arrivals`.
- **Shell stand-ins** (`shell/src/tm-tenant-shell.ts`, `tm-tenant-picker.ts`): render
  `<tm-banner-host />` above `main`; the tenant shell creates `TmArrivals`.
- **Core-ui** (`tellma-core-ui/toast/tm-toasts.ts`): `ɵsetOverflow(overflow | null)`, an installed
  pill that wins over the configured one and may decline (`null`) per count.
- **Core** (`src/l10n/tm-server-text.ts`): a LocalizedText argument falls back to slot 1 when its
  slot is empty, not only null, as the server's `LocalizedText.In` does (0 bytes on the primary).
- **Size gate** (`client/scripts/bundle-size.mjs`): the static-graph check walked from the first
  esbuild output with an `entryPoint`, but with splitting every `import()` target is an entry
  output too, in no fixed order. After this build the first was `/recents`' dynamic entry, so the
  primary falsely "reached" `/recents`. The walk now starts from the output built from the entry
  point's own FESM, and fails if there is none.
- **Testing** (`tellma-core-testing`): `TmBannerHostHarness` (`getBar` through core-ui-testing's
  `TmBannerBarHarness`, `isOpen`, `isEmpty`, `getAnnouncement`, `getPoliteness`); peers
  `@angular/cdk` and `@tellma/core-ui-testing` added; the attention specs' app rig is
  `src/attention/tm-attention.testing.util.ts`.

Added by fix1 (review 1):

- **The arrival baseline (R1-2, ruled by D-257), against spec 0028 §8.2 step 1.** §8.2 makes the
  first copy saved at or after the tab's start a silent baseline; in a follower tab that copy is
  usually the leader's first real refresh, so its arrivals, and the first ReadOnly or Frozen
  change, never toasted. Now the first copy observed becomes `previous`, whatever its `savedAt`.
  When `previous` was saved before the start, the next copy's arrivals are only the rows created
  (`createdAt`) or assigned (`assignedAt`) at or after the start, so a start-up refresh toasts no
  backlog. The tenant's state is compared with `previous` whatever its `savedAt`, and toasts only
  from a copy saved at or after the start. §8.2 needs that sentence at the next spec revision.
- **The start is per tenant entry (R1-3).** §8.2 speaks of "the tab's start"; `TmArrivals` takes
  `TM_NOW()` each time the routed tenant changes, so returning to a tenant after hours elsewhere
  toasts none of what arrived meanwhile, as a fresh tab would not.
- **A caption without `detail` renders no detail line (R1-6), against spec 0028 §11.3**, which
  drops line 2 only when `Assignment_<Resource>_Detail` is missing. A detail resource formatted
  with no arguments would render its placeholders raw, so a caption must carry `detail` for the
  key to apply; a fixed-text detail resource needs an empty `detail` object.
- **A failed `seen` after the panel closed lifts the overlay at once (R1-1).** With the panel open
  it still waits for the panel's own copy (deviation 6); once the panel has closed no read
  follows, so the badge shows the stored count again.

**Counts: blocking 0, major 2, minor 5.**

**R1-1 (major). Closing the bell while its `seen` is in flight, then the `seen` failing, hides the
bell's count until the bell is opened again.**
- *Where.* `tm-attention.ts:495-505` (`#opened`) and `:520-527` (`#close`). `holds()` at `:130-131`
  holds an `own` hold with `sentAt: null` forever.
- *Failure scenario.* The user opens the bell with 3 unseen, which sets a `pending` hold and sends
  `inbox/seen`. The user closes the bell before the answer. `#close` clears only an `own` hold, so
  `pending` stays. The `seen` then fails (network drop, 5xx, or the calls chunk failing to load).
  The continuation still finds its `pending` hold and replaces it with
  `{ kind: 'own', sentAt: null }`. The read is skipped because `abort.aborted` is now true, so
  nothing ever stamps `sentAt`. The bell's count is `null` from then on, through every new copy,
  until the user opens and closes the bell again or changes tenant. The probe confirmed it: put
  unseen 3 at version 5, fail `inbox/seen` after the close, put unseen 4 at version 6, and
  `bell().count` is still `null` instead of 4.
- *Fix.* In the continuation, fall back to no hold when the panel has closed:
  `this.#seen[panel].set(release ?? (abort.aborted ? null : { kind: 'own', sentAt: null }))`.
  A successful `seen` keeps its version or seenAt hold even after a close, which is correct. Add
  this scenario as a unit test.

**R1-2 (major; spec misalignment to flag). The baseline rule swallows the first real arrival in
every follower tab, and the first tenant-state change.**
- *Where.* `tm-arrivals.ts:141-148`. The first copy with `savedAt >= #start` becomes the baseline
  and never toasts. Spec 0028 §8.2 step 1 says exactly this, so the code is faithful to the text.
- *Failure scenario.* Spec 0025 §8.6 says the leader refreshes its documents on election, on a
  (re)connect, on events and on degraded polls. Followers never call these routes on hub events.
  Picture Farah with one tab leading over a connected hub, who then opens a second tab. Tab 2's
  first copy is the stored one, saved before it started. The next copy written is the one the
  leader stores for Sara's assignment, so it becomes tab 2's baseline and toasts nothing, even
  with tab 2 focused. That is §8.2's own example, and the badge moves while the toast is lost.
  The `tenant` document is similar. The leader syncs it on election and on `cache.changed`
  (spec 0025 §7.2 step 2, §8.7). So in a follower tab where no sync has rewritten it since the
  tab started, the first ReadOnly or Frozen change is the baseline and never toasts. The
  existing test pins this behaviour: `tm-arrivals.spec.ts:83-93` treats a post-start copy holding
  a new row as a silent baseline.
- *Fix.* Rule with Ahmad, since §8.2 needs a sentence. A rule that keeps the intent ("what arrived
  before the tab started never pops up"):
  - The first copy observed, whatever its `savedAt`, becomes `previous`.
  - When `previous` was saved before the tab's start, the arrivals in the next copy are only the
    rows whose `createdAt`/`assignedAt` is at or after that start. A leader's start-up refresh
    then still toasts no backlog.
  - For `tenant`, compare the state with the previous copy whatever its `savedAt`, but toast only
    when the new copy's `savedAt` is at or after the tab's start.

  Replace the test at `:83-93` with one tab whose first post-start copy carries a row created
  after the start (it toasts) and one created before it (it does not).

**R1-3 (minor). After a tenant switch, the new tenant's backlog toasts.**
- *Where.* `tm-arrivals.ts:81` takes `#start` once, when the engine is created. `:133-137` resets
  `baseline` and `previous` on a tenant change, but not the start.
- *Failure scenario.* The tab starts in tenant 17 and visits tenant 18 at 10:00, which stores
  18's inbox. From 10:05 to 14:00 it works in 17. Back in 18, the stored 10:00 copy is after
  `#start`, so it becomes the baseline at once. Entering 18 elects this tab leader, and the
  leader's refresh then toasts the four hours of notifications that arrived while the tab was
  elsewhere. A fresh tab would toast none of them.
- *Fix.* Keep the start per tenant entry: set it to `TM_NOW()` when the key changes. With R1-2's
  rule, the start is the cut-off for rows. Add a tenant-switch case to `tm-arrivals.spec.ts`.

**R1-4 (minor). The stand-ins' hand-offs are not recorded, and no test pins them.**
- *Where.* The commit adds no WATCHLIST lines. `shell/src/tm-tenant-shell.ts:35-39` is the only
  place that creates `TmArrivals`, and no spec fails if that line goes. PC-118's deliverables do

- *Failure scenario.* Each of these breaks something without a red test or a written hand-off:

  - PC-207 registers `assignments`. `tm-attention.spec.ts:300-301` ("not read until the app
    registers it") and `:350-351` (`refresh('assignments')` makes no call) then fail. Neither is
    in the PC-109 → PC-207 checklist.
  - PC-156 inherits 0.07 KB of `/attention` room (see the questions below). `stopJob` leaves the
    `commitsInSteps` confirmation to its caller. The tray button's `inbox` glyph is registered
    only by the lazy arrival-toasts chunk, so the button must register it itself.
- *Fix.* Add WATCHLIST lines PC-155 → PC-116/PC-118 (render `<tm-banner-host />` in the row and
  inject `TmArrivals` in the tenant shell), PC-155 → PC-207 (the two assertions above), and

  entering a tenant creates `TmArrivals`, for example that the overflow pill is installed.

**R1-5 (minor). Several model rules have no test that fails when they break.**

**R1-6 (minor). An undocumented deviation: a caption without `detail` renders no detail even
