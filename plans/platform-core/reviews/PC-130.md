# PC-130: Images, files, child grids and child files

## Implementer notes

### What was built, and where

All client paths are under `client/projects/core/` unless noted.

**Image and file fields (spec 0031 §6.3)**

- **`tellma-core/uploads/src/tm-uploads.ts`.** `TmUploads` now tracks each upload's progress
  (`progress(path)`, the share sent, 0 to 1). `start(path, (signal, progress) => …)` hands the
  upload a progress callback. `removeRow(collection, index)` follows a child row's removal: the
  row's uploads abort, its staged blobs clear, and the later rows' entries move up one index. An
  upload that finishes after its row moved stages under the row's new path.
- **`tellma-core/uploads/src/tm-upload-failure.ts`** (new, exported). `tmUploadFailure(error,
  serverText)` says what a failed upload means:
  - An abort (`AbortError`, or a `cancelled` TmApiError) is `aborted` and shows nothing.
  - A 4xx with a problem (`blob-rejected` included) is `rejected`, with the server's text for the
    first item, else the problem's title.
  - Anything else is `failed`, which a retry may mend.
- **`tellma-core/entity-editing/src/tm-value-editor.ts`.** Changes to the image and file pickers:
  - A progress ring beside the image or after the chip, fed by `TmUploads.progress`.
  - The refusal's reason through `tmUploadFailure`, and Try again only for `failed`.
  - The staged blob's descriptor, through a new `blob` input from `tm-field-editor.ts`, for the
    chip's name and the preview.
- **`tellma-core/details/src/tm-field.ts`, `tm-field-cell.ts`.**
  - An image's cell has a 72 px value box.
  - `#blobOf` gives the view and the editor the blob: the related row, else the staged descriptor.
- **`tellma-core/entity/src/tm-value.ts`, `tm-blob-check.ts`.**
  - The details thumbnail is 72 px, matching the editor.
  - A file shows its size, through `ɵtmByteSize`, which is new and exported.
- **`tellma-core/details/src/tm-details-controller.ts`.** Save waits until the record's uploads
  settle (`#uploadsSettled`) before it writes. It returns `false` if the record or page goes away
  first.
- **`src/core/Tellma.Core/Resources/Strings*.resx`.** `Blob_NotAttachable` is an ICU select on the
  server's `reason` argument:
  - `expired` and `missing` say "This file expired. Choose it again." (§6.3 step 4).
  - Any other reason keeps the old text.

**Child grids (spec 0031 §6.4)**

- **`details/src/tm-child-grid.ts`** (eager). `TmChildGrid` (`tm-child-grid`) takes `collection`,
  `columns`, `totals`, `defaults`, `readonly` and `maxRows`. It holds:
  - The frame, whose height is set at each landing, and never while typing (after review 1: not
    at a mode change either). The height covers the rows plus the placeholder row, between 4 rows
    and `maxRows`, plus the header, border and status band, reserved in view mode too.
  - The same-geometry placeholder, shown while the record loads and until the chunk renders.
  - The `@error` message.
  - The exact totals under the grid (`ɵtmChildGridTotal` in `tm-child-grid-totals.ts`, on
    `TmDecimals`).
  - The collection's invalid state, held on the enclosing card or tab from creation.
- **`details/src/tm-child-grid-view.ts`** (deferred chunk). One `tm-grid`:
  - It binds to `form.<collection>`, with gridId `details:<entity>:<collection>` and contentKey
    set to the record id, or `new`.
  - It is read-only in view mode. View-mode navigation cells and blob cells render `tm-value`
    (links).
  - The edit columns come from `tmEditableGridColumnFor`, through a cached `import()` of
    `@tellma/core/entity-editing`, once the record may be edited.
  - New rows come from `record.ɵnewChildRow(child, defaults())`.
  - After the first render it registers the collection: `ready`, `visible` (at most 50 columns
    and 200 rows) and `reveal(rowId, { flash, column })`. `reveal` expands the card, scrolls,
    flashes the row and focuses the cell.
- **`details/src/tm-details-record.ts`.**
  - `ɵnewRowId()`: −1, −2 and so on, always below every negative id the collections already hold.
  - `ɵnewChildRow()`: a completed row, with its id last and the parent key left absent.
- **`details/src/tm-details-defer.ts`** (new, internal). `ɵtmDeferTriggers(prefetch)` gives the
  `visible` signal (an IntersectionObserver on the host) and runs an idle-callback prefetch
  (`import()` of the block's module). The grid and the files read it with `@defer (when
  defer.visible())`. See deviation 1.
- **`tellma-core-testing/src/tm-child-grid-harness.ts`** (new, exported). `TmChildGridHarness`
  reads the collection, the state (placeholder, grid or failed), whether it edits, the height and
  the totals, and gives access to the grid itself (`getGrid`).

### Deviations

1. **`@defer (when …)`, not `on viewport; prefetch on idle`.** I kept the semantics: load once the
   host intersects the viewport, prefetch on the browser's idle callback. The built-in triggers'
   code lives in @angular/core, which an app's first frame carries. With them, Acme's initialJs
   went from 227.78 to 229.02, over the run's own 228 KB warn line. With `when` it is 227.90. Both
   figures are under spec 0024 §12's 230 KB warn level, so the deviation keeps the run's internal
   line, not a spec budget. A
   `prefetch when` beside `when` raises NG8021, so the prefetch is a plain `import()` of the same
   module on idle.
2. **The child files' whole body is deferred**, not only its edit side. Keeping the chips on the
   route cost +2 KB of `/details`, which would have taken it to 23.48, over the spec's 23 KB. The
   chips render once the list enters the viewport, behind a placeholder one chip high. The
   placeholder also shows while the record loads. A file list that wraps to several rows of chips
   still moves the content below it when its body renders.
3. **Totals render as a list under the grid**, not as a footer row aligned with its columns. The
   grid has no footer row, and they sit outside the fixed-height frame.
4. **`TmUploads` changed shape.** `start`'s callback takes a progress reporter. `progress`,
   `removeRow`, `cancelAll` (fix1), and `failed`, `failures` and `dismiss` (fix2) are new.
   `tmUploadFailure` is new in `@tellma/core/uploads`.
5. **Save waits for uploads without the 'Finishing uploads…' overlay label.** That label belongs
   to PC-133's overlay.
6. **`Blob_NotAttachable` is an ICU select** on the server's `reason` argument. "This file
   expired. Choose it again." covers expired and missing blobs, and the old text covers the rest.
7. **The picker modal's `picker.details:…` gridId prefix is not applied.** No picker modal renders
   a details layout yet (§15).
8. **The drop zone keeps its own hint** (the component library's drop-or-paste line), not
   "Add files". `tm-dropzone` takes no label.
9. **`columns` is required** on `tm-child-grid`, as the spec's declaration types it. There is no
   default column set.
10. **A new row's id goes last**, so a layout's `defaults()` cannot set it.
11. **Images are 72 px** in the details view and editor. The value's details surface was 96.
12. **The entity rig gained a `summaries` option.** A child entity's columns are reachable only
    when its summary is in the Core metadata.
13. **A failed upload stops Save (a spec gap, for Ahmad).** Spec 0031 §8.1 step 2 waits for the
    uploads but does not say what a failure does to the save. The rule, in edit and create mode
    alike:
    - Save writes nothing while a file's upload has failed and may be retried. The row or field
      shows "Upload failed" with Try again, and the page announces "Nothing was saved: a file
      didn't upload." Retrying or removing the file lets Save through.
    - Save writes nothing when an upload it waited for fails in any way, including a refusal.
      The edit stays, with the failure shown on its field.
    - A refused child file leaves the model, so no row without a file is saved. Its reason joins
      the drop zone's refusals as "{name}: {reason}".
    - A refused image keeps the field's previous value, so the next Save goes on.

### Open risks

- A grid or files list inside a collapsed card or an unselected tab never intersects, so it never
  registers until it is shown. A save error's reveal of such a row needs §6.6's tab instantiation
  (PC-133).
- `ɵnewRowId` reads each row's `id` member by name, not the child key's JSON name. Every child
  entity today keys on `Id`.
- Deleting a child grid row that has an image or a file column does not call
  `TmUploads.removeRow`, so its upload keeps its old index. No grid column uploads yet; the child
  files editor does call it.
- I did not run any e2e. No Acme details e2e exists yet; PC-133 plans one.

### Findings

**R1-1 (major): Cancel does not abort a running upload, and the upload then writes into the view-mode record.**
- Where: `client/projects/core/tellma-core/details/src/tm-details-controller.ts:483-505` (`cancel`)
  and `client/projects/core/tellma-core/entity-editing/src/tm-value-editor.ts:642-650` (the
  success handler).
- Scenario:
  1. In edit mode, pick an image. Its upload runs through the record's `TmUploads`.
  2. Press Cancel (it is enabled, because `busy` is false). Cancel restores the model to the base
     and switches to view mode. Nothing aborts `record.uploads`.
  3. When the upload resolves, the destroyed editor's handler still runs
     `untracked(this.fieldState).value.set(blob.id)` on the record's form, so the view-mode model
     gains `imageId = <staged id>`.
  4. `tm-field`'s `#blobOf` then shows the staged image as though it were saved.
  5. The next Edit sets the base to that mutated model, so the record is not dirty. Save goes back
     to view mode and sends nothing. The user believes the image was saved, and the page shows a
     value the server never had.
- Orphaned uploads also stay in `running`: a later Save waits for them, and a new child-files row
  at the same index shows the orphan's ring until its own `start` cancels it.
- Spec: §6.3 step 2 ("Replacing or removing the file aborts the upload"). Cancel discards the file.
- Fix:
  - Add `TmUploads.cancelAll()`, which aborts every running upload and clears every staged blob.
  - Call it from `cancel()`, before restoring the base, and on create-mode leave.
  - As a second guard, have the value editor's success handler skip the write once the record is
    in view mode.
- Test: start an upload, Cancel, resolve it. The model equals `entity()`, `running` is empty, and
  the field shows the old image.
- If the orchestrator places this under PC-133's "§3.4 (Cancel interplay)", carry it there. The
  defect exists because of this checkpoint's upload paths.

**R1-2 (major): the child grid's frame grows on Edit, which is an unflagged layout shift.**
- Where: `client/projects/core/tellma-core/details/src/tm-child-grid.ts:111-121` (the status band
  is added only in edit mode) and `:304-311` (one more row in edit mode).
- Scenario:
  1. On every record, Edit adds `--grid-status-height` (30 px) to the frame. A record with 4 or
     more rows also gains one row height.
  2. The totals, every card below the grid and the aside's flow all move down on Edit, and back up
     on Cancel or Save.
- Spec: §6.4 says one grid serves every mode "so a mode switch changes rule colours only". §18's
  stable-layout rule requires the grid's box to stay identical "across load, Edit, typing, adding
  a row, a failed Save, fixing fields and Cancel", pinned by `details-geometry.spec`.
- `tm-child-grid.spec.ts:286` asserts `editHeight > viewHeight`, so the test pins the shift
  instead of catching it. The commit lists no deviation for it.
- Fix: reserve the same geometry in both modes.
  - Count the placeholder row in view mode too: `count + 1` always.
  - Reserve the status band's height in view mode, as an empty band under the read-only grid, or
    as padding in the frame.
  - The height then changes only at landing.
  - If the "set … at each mode change" wording in §6.4 is read as allowing the shift, record that
    as a deviation and flag the §6.4/§18 contradiction for Ahmad.

**R1-3 (major): tm-child-files says "No files" while the record loads, then jumps to the chips.**
- Where: `client/projects/core/tellma-core/details/src/tm-child-files.ts:56-63` and
  `client/projects/core/tellma-core/details/src/tm-child-files-body.ts:228-230` and `:339`.

### Responses

**R1-1: fixed.**
- `TmUploads.cancelAll()` aborts every upload in flight and clears the running and staged maps.
- `cancel()` calls it once the Discard question passes, before both the edit-mode restore and the
  create-mode leave. The fake details' `cancel()` does the same.
- `start` re-checks `throwIfAborted()` after the upload's promise settles. A result that arrives
  after Cancel therefore rejects with an `AbortError`: no editor's success handler runs, and
  nothing stages. This holds even when the upload ignores its signal.
- I did not add the second guard (skip the write once the editor is destroyed). An editor
  destroyed mid-edit, such as a recycled grid row, would then drop an upload that should land.
  The abort already covers Cancel.
- A related hole is also fixed. A clean edit whose only change was an upload in flight used to go
  back to view mode at Save and orphan the upload. Save now waits for the uploads first. It writes
  when one landed, and keeps the edit when every one failed.
- Tests:
  - `tm-uploads.spec.ts`: cancelAll; a late resolve rejects and stages nothing.
  - `tm-details-host.spec.ts`: Cancel during an upload. The upload is aborted, `running` is empty,
    the late result writes nothing, `model()` is `entity()` (so `#blobOf` shows the old image), and
    nothing is staged. The next Save writes at once.
  - `tm-details-host.spec.ts`: a clean edit with an upload waits for it, then writes
    `imageId: 88`.

**R1-2: fixed. §18 wins, and no deviation is needed.**
- View mode reserves the placeholder row and the status band: the count is `rows + 1`, and the
  band's height is `--grid-status-height`, in every mode. So the frame's box changes only when a
  record lands.
- A `readonly` grid reserves neither. It has no mode change to absorb.
- In view mode the read-only grid fills the reserved space as empty body.
- §6.4's "set … at each mode change" and §18 now agree, because a mode change sets the same
  height.
- `tm-child-grid.spec.ts`:
