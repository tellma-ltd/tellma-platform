# PC-044: VersionedCache and [Cacheable] entities

## Implementer notes

### What was built, and where

- **`Tellma.Core.Caching.VersionedCache<TKey, TValue>`** (public, `src/core/Tellma.Core/Caching/VersionedCache.cs`):
  the process-wide store of one kind. It holds a private `MemoryCache` with `SizeLimit` in the
  kind's unit and `TrackStatistics = true`. Entries are `(Tag, Value)`.
  - Members: `GetAsync`, `Peek(key, tag)`, `Peek(key, isCurrent)`, `Set(…, aged)`, `Remove`,
    `Dispose`, `protected virtual LoadAsync`, `protected virtual SizeOf` (default 1),
    `protected Lookup` (no metering) and `protected RecordRequest`.
  - `VersionTag.None` never matches, either as the current tag or as a stored one.
  - Every key implements `ITenantCacheKey`. The key types are `TenantCacheKey`,
    `TenantUserCacheKey` and `CacheableEntityKey`.
  - `CacheKinds` is the closed set of kinds: settings, preferences, permissions, entities. The
    constructor refuses any other kind.
- **Single flight**: a `ConcurrentDictionary<(TKey, VersionTag), Flight>`, where each flight wraps a
  `TaskCompletionSource`. The caller that wins `GetOrAdd` runs the load on its own handle and token.
  It then stores the value, removes the flight, and only after that completes the TCS. A failed
  load is removed before the exception is set or rethrown. Joiners wait with
  `WaitAsync(own token)`. If the starter cancels and a joiner is still waiting, the joiner loops and
  becomes a starter itself.
- **Instruments** (`CacheInstruments.cs`): one set per `Meter`, kept in a `ConditionalWeakTable`, so
  two stores never create duplicate instruments. The observable gauges yield one measurement per
  live store, tagged `cache.kind`.
  - Evictions are counted only from `PostEvictionCallback`:
    - `Capacity` → `capacity`. This includes an entry the runtime refused for lack of room.
    - `Removed` → `removed`, or the `replaced`/`age` mark that `Set` wrote on the displaced entry
      before removing it (`Set` removes and then adds).
    - `Replaced` → `replaced`. This only happens when two `Set`s race.
  - One store per kind per meter. A second store of the same kind throws until the first is disposed.
- **Entities kind**:
  - `CacheableEntityStore` (singleton) holds the qualifying `[Cacheable]` entities, resolves
    `MaxRows` (0 → `EntityMaxRowsDefault`) and sizes entries in rows (`max(1, rows)`).
  - `CacheableEntityType<TLeaf>` is built with `MakeGenericType` once per entity. It owns the probe:
    `EntityQuery<TLeaf>` with every scalar property the tenant's query schema declares (so shape
    twins appear only for tenants that have them), `AllProperties = true`, `OrderBy Id` and
    `Take MaxRows + 1`.
  - `CachedEntityList` is the stored value. It holds the leaf `CachedEntitySet` plus a view per base
    class, built once (`ReadOnlyCollection` and `FrozenDictionary` over the same instances).
  - `LoadAsync` runs one Read batch on the passed handle. It takes the tag from
    `BatchOutcome.VersionTags`, and refuses an outcome whose snapshot belongs to another tenant than
    the key.
  - Overflow → `Oversized`, nothing stored, and `CachingLog.CacheableEntityOverflow` logged once per
    entity per store.
- **`CacheableEntities`** (scoped `ICacheableEntities`) takes the tenant from
  `IRequestContextAccessor`, the tag from `IVersionTagSnapshots.Current(tenant)[entity:<Name>]`, and
  the handle from the scope's `ITenantDatabase`. `GetWireTagsAsync` reads the snapshot only.
- **`DataBatch.FromCache<T>`** (`Data/Batches/DataBatch.Caching.cs`):
  - Refusals: `NotSupportedException` when the store is not composed; `ArgumentException` when the
    type is not cacheable; `InvalidOperationException` when the batch already declared a write to
    the entity's table.
  - Shared per write epoch through `_sharedQueries`.
  - On a hit, the result is completed at once and the batch declares
    `DependsOn(entity:<Name>, snapshotTag, VersionTagPolicies.For(name, Purpose))`.
  - On a miss, the probe is appended through a new `PlanEntityQuery` (extracted from `Query<T>`, so
    the two share one plan path). Its reader stages `ResultSetCursor.Settle(result, () => store.Settle(…))`,
    a new overload that defers the settle to `ApplyCompletions`. The list therefore lands in the
    store when the counted attempt's results complete, before the handle completes. A re-run attempt,
    or a read discarded by `StaleContextException`, stores nothing.
- **Startup check `core.cacheable-entities`** (`Composition/Checks/CacheableEntitiesCheck.cs`,
  registered after `core.securables`). It reports:
  - an entity that is not a `TopLevelEntity<int>`;
  - an entity with a child collection;
  - a resolved `MaxRows` outside `[1, EntityMaxRowsCeiling]`. This is skipped when the cache options
    fail validation, since `core.options` reports those;
  - a registered `Read` securable with a `FilterRoot`. An entity with no registered securable is
    not judged.
- **Executor**: `DataExecutor` exposes `Snapshots` (it was a private field) and `CacheableEntities`
  (lazily resolved, so the store reads `CacheOptions` only after the gate has validated them).
- **Composition**: `CoreFeature` registers the store (singleton) and `ICacheableEntities` (scoped).
- **READMEs**: the Core README has a new "The versioned cache" section, a check-table row and an
  updated folder row. Both test READMEs are updated.
- **Fixture entity**: `fixture.Lookups` (`Lookup`, `[Cacheable(MaxRows = 50)]`) already existed from
  PC-038 with its migration, and no model changed, so no migration was regenerated. The core
  TestDistribution composes only Core and the probe feature, so it is unaffected.

### Deviations from spec 0013 §3.1/§4

1. **`LoadAsync` signature**: it is
   `Task<CacheLoad<TValue>> LoadAsync(TKey, ITenantDatabase, CancellationToken)`, not a tuple
   `(Value, Tag, Size)`.
   - A `CacheLoad` is either `Loaded(value, tag)` or `Oversized(tag)`. A tuple cannot express
     Oversized cleanly.
   - Size comes from `protected virtual SizeOf(TValue)`, because `Set` must size values too (for
     example a save's warm entry) and the size needs one source.
   - `GetAsync` also gains an optional `CancellationToken`.
2. **Single flight is keyed by (key, current tag)**, not by key alone. A caller that already knows a
   newer tag never joins a load that started under an older one and would hand it rows stamped with
   the old tag. Callers that agree on the tag still share one load. A load cancelled under its
   starter, by the token the starter passed or by any token its batch links (the starter's scope's
   `DataCancellation`, which the entities façade also passes), stores nothing and does not fail the
   joiners still waiting: they load again. A joiner's own cancellation ends only its own wait.
   (Corrected after review 2: before, only a cancellation of the passed token was treated as one,
   and the façade passed none.)
3. **`FromCache` on a miss declares no dependency.** §4.4 says "declares
   `VersionTagDependency(entity:<Name>, tag, Rerun)`" without separating hit from miss. On a miss
   the rows are the batch's own read, ordered after its prelude, so nothing cached was used.
   Declaring the snapshot's tag would only re-run a batch whose data is already fresh. On a hit the
   dependency is declared exactly as specified.
4. **`FromCache` is refused after a write to the entity's table in the same batch.** The probe would
   read the batch's own uncommitted rows and stamp them with the pre-bump tag. The spec is silent
   on this case.
5. **The cache kind is a closed set** enforced by the constructor (§11 "closed sets"). A second
   live store of one kind on a meter is refused, so the gauges stay one series per kind.
6. **`load.duration` is recorded only for loads the store runs itself** (`GetAsync`). A `FromCache`
   probe rides the consumer's batch and has no separable duration. Its outcome is still counted in
   `tellma.cache.requests`.
7. **Evictions are metered from the runtime's callbacks, asynchronously.** An entry the runtime
   refuses for lack of room counts as a `capacity` eviction.

### Open risks

- `MemoryCache` compaction is asynchronous and refuses entries that do not fit. At the limit, a
  freshly loaded value may be served but not stored until compaction frees room; the existing
  snapshot store already documents this behaviour. The capacity test asserts only that drops are
  `capacity` and the count stays within the limit.
- Cached entity instances are mutable classes shared by reference across scopes. The collections are
  read-only wrappers, but nothing stops a caller from setting a property. The spec accepts this
  ("a bug the value types prevent"); entity classes cannot prevent it.
- `CacheableEntityType.Create` uses `MakeGenericType` and `Activator`. This is fine under JIT, and
  the repo has no AOT target for Core.
- Spec 0013 §4.2 judges `FilterRoot == null` through spec 0014's registry. Today no stack registers
  entity securables (spec 0015 does), so in practice the rule only fires for hand-registered pairs.

### What reviewers should examine hardest

- `VersionedCache.LoadOnceAsync`: the ordering of store → remove flight → complete TCS, the
  cancellation and retry loop, and whether any path leaves a flight behind or an exception unobserved.
- The `FromCache` miss path. The settle runs inside `ApplyCompletions`, after `ReplaceSnapshots`
  and the stale-rerun check. It reads `ReadVersionTags`, which the prelude reported during the same
  attempt. Check the persist path in particular, where the connect prologue absorbs the prelude.
- Eviction-reason mapping and the remove-then-set in `Store` under concurrent `Set`/`Remove`.
- The `core.cacheable-entities` check's handling of the options and the securable registry when they
  fail to build.

### Findings

**R1-1 (major): a `FromCache` miss on a `Persist` batch leaves the list's tag out of the write guard, so a validator can commit against a row that changed under it.**
`src/core/Tellma.Core/Data/Batches/DataBatch.Caching.cs:69-77`, where the miss path declares
nothing for any purpose.

- **Why it matters.** On a hit, a `Persist` batch declares `entity:<Name>` with `Rerun`.
  `PersistChecks` then reads that tag row under `REPEATABLEREAD` and holds the lock to the commit,
  so a concurrent writer of the table waits at its own guard's `XLOCK` on the same row. On a miss
  the name never enters `@tm_expectedTags`, so the probe's rows are protected by nothing past the
  statement that read them.
- **Failure scenario.**
  1. A cold persist batch that writes `fixture.Widgets` calls `FromCache<Lookup>()`. It finds
     lookup 5 active and keeps the reference.
  2. A concurrent batch deactivates lookup 5 and commits between the probe and this batch's
     `COMMIT`. That batch bumps `entity:fixture.Lookup`, and nothing blocks it.
  3. This batch commits a reference to an inactive row.

  The same interleaving on a warm instance is serialised. This contradicts the spec 0012 §5.2
  `FromCache` row ("On a Validate or Persist batch the dependency is declared with Rerun… a
  validator never accepts a row from a list that changed under it").
- **Suggested fix.** Enter the name into the guard on a `Persist` miss as a lock-only row, with a
  NULL expected tag. That is the path `PersistChecks.Compose` already uses for bumped names it
  does not compare (`NoExpectation`), for example through an internal `DataBatch.LockTag(name)`
  that `Compose` reads. Do not declare the snapshot's tag: on a cold instance `VersionTag.None`
  would fail the guard every time.
- **Tests to add.** A unit test that a cold `FromCache` on a writing `Persist` batch binds the
  name with a NULL tag in `@tm_expectedTags`. An integration test of the persist miss path,
  which also covers the open risk the implementer named: the settle reads `ReadVersionTags` from
  the prelude that the connect prologue absorbed, and no test exercises that path today.

Deviation 3 stays justified for `Read` and `Validate` batches. There the rows are the batch's own
read after its prelude, and the consumer still gets the prelude's tag in `CacheResult.Tag`, so it
can re-declare it.

**R1-2 (major): a cached list depends on the tenant's `MultilingualShape`, but neither its key nor its tag does, so a language change keeps serving the old columns.**

- **Where.** The probe's select is the tenant schema's properties:
  - `CacheableEntityType.Select` (`src/core/Tellma.Core/Caching/CacheableEntityType.cs:351-358`);
  - called with `database.Schema` (`CacheableEntityStore.cs:227`);
  - called with `Map.Schema` (`DataBatch.Caching.cs:73`).

  `TenantDatabase.Schema` is `GetSchema(Settings().Shape)`. The entry, however, is keyed
  `(TenantId, EntityName)` (`CacheableEntityKey.cs`) and validated by `entity:<Name>` alone.
- **Failure scenario.**
  1. A tenant on `Primary` loads `Lookups`, with no `Name2` column read.
  2. An admin adds a second language. Per spec 0013 §6.3 the settings save bumps `settings` and
     `permissions`, not `entity:*`.
  3. Every later request runs under the new shape. `GetAsync`, `Peek` and `FromCache` still hit
     the old list, so every row's `Name2` is null until someone writes the table.

  The reverse also happens: removing a language keeps serving twin values. During the switch, two
  scopes with different shapes also share one flight (keyed `(key, tag)`), and a joiner gets the
  other shape's rows.
- **Suggested fix.** Make the shape part of the entry's validity: add it to `CacheableEntityKey`
  (and so to the flight key), or record it on `CachedEntityList` and treat a mismatch as `Stale`
  in `Lookup`/`Find`.
- **Test to add.** Settle a list under `Primary`, then read through a scope whose schema is
  `All`, and expect a miss.
- **For the orchestrator.** The client's list is keyed by the same wire tag, which a language
  change does not move either (see the decisions in the summary).

**R1-4 (minor): no test pins the entities kind's size unit.**

### Deviations (Reviewer 1's judgement)

1. **`CacheLoad` with `SizeOf` instead of a tuple: justified.** A tuple cannot carry Oversized,
   and `Set` needs the same sizing source.
2. **Single flight keyed by (key, current tag): justified.** Joining across tags could hand a
   caller that knows a newer tag rows stamped with an older one. The number of flights is bounded
   by the number of distinct tags in play.
3. **No dependency on a miss: justified for `Read`/`Validate`, not for `Persist`** (R1-1).
4. **`FromCache` refused after a write to its table: justified.** A hit would hide the batch's own
   writes, and a probe would stamp uncommitted rows with the pre-bump tag. The shared-result reset
   on a write (`DataBatch.cs:609`) makes the refusal reach a repeated call too.
5. **Closed `CacheKinds`, one store per kind per meter: justified for the closed set.** One caveat:
   the refusal throws at DI resolution, and `DataExecutor` resolves the store through a `Lazy`
   that caches the exception. If two root providers ever share one `IMeterFactory`, `FromCache`
   would fail for the life of the process. No such sharing exists today; I searched `src/`.
6. **`load.duration` only for `GetAsync` loads: justified.** A probe has no separable duration,
   and its outcome is still counted.
7. **Evictions metered from callbacks, refusal as capacity: justified.** The spec's thrash signal
   wants exactly that. The async delivery is handled in the tests with `WaitForMeasurementsAsync`.

  and observed after the flight is removed. Keying by `(key, tag)` bounds flights by the number of
  tags in play. A load whose prelude saw a newer tag is stored under that tag, which converges.
- **Eviction callbacks.** The callback only meters; it never touches the cache. So a callback that
  runs after a newer `Set` cannot drop the newer entry. The only effect of a racing `Set` or
  `Remove` is the reason a displaced entry is metered under.
- **Partial outages.** A probe that fails mid-batch stores nothing: completions are staged and
  applied only for the counted attempt. A refused or failed load is forgotten, and the next caller
  retries. The startup check needs no database: `RequiresInfrastructure` is false and the store's
  constructor reads only the model.
- **Public text and Windows/Linux.** No spec, `docs/`, PC, decision or finding references appear in
  XML docs, messages, logs or test names. Nothing is OS-specific: ordinal comparisons, and no paths.

### Findings

**R2-1 (major): a cold load whose starter's scope is cancelled faults every caller that joined it; the claimed "joiners load again" holds only when the token is passed explicitly, and the only production caller never passes one.**

- **Where.**
  - `src/core/Tellma.Core/Caching/CacheableEntities.cs:31-33`: the façade calls
    `store.GetAsync(...)` with no token. Its comment says "The batch a miss runs links the scope's
    cancellation itself."
  - `src/core/Tellma.Core/Caching/VersionedCache.cs:388`: the starter treats an
    `OperationCanceledException` as a cancellation only `when (cancellationToken.IsCancellationRequested)`,
    which tests the passed token, here `default`.
  - `VersionedCache.cs:395-399`: any other exception, that one included, faults the flight's TCS
    through `TrySetException`.
  - `VersionedCache.cs:364`: a joiner loops only when `flight.Completion.Task.IsCanceled`. A TCS
    faulted with an `OperationCanceledException` is `IsFaulted`, not `IsCanceled`. I checked this
    with a scratch script: `IsFaulted=true IsCanceled=false`, and the joiner rethrows.
- **Failure scenario.**
  1. A fresh instance after a deploy. Request A misses `entity:gl.Currency` and starts the load on
     its handle. Requests B…Z miss the same key under the same tag and join.
  2. A's client disconnects. The front door sets the scope's `DataCancellation.Token` to the
     request's aborted token, as the type's own docs say it will. `DataBatch` links that token
     (`DataBatch.cs:136`, `DataExecutor.cs:175`), so A's read batch throws
     `OperationCanceledException`.
  3. That exception faults the flight, and B…Z all fail with `OperationCanceledException`, although
     none of them was cancelled. Their front doors cannot tell this from their own abort.

  A job scope's stopping token does the same to every request waiting on a load a job started. The
  same gap means a joiner's own abort never ends its wait, because the façade passes it no token.
  - This contradicts deviation 2 ("a starter's cancellation makes waiting joiners load again rather
    than fail") and the README's single-flight paragraph.
  - The only test, `A_caller_that_joined_a_load_its_starter_cancelled_starts_its_own`, passes the
    starter's token to `GetAsync` directly, a path no production code takes.
  - Nothing sets `DataCancellation` yet, so this is not live today. It is not blocking, but the
    first front door that sets the token switches it on.
- **Suggested fix.** Do both:
  - Have the façade take the scoped `DataCancellation` and pass its `Token` to `store.GetAsync`.
  - In `LoadOnceAsync`, complete the flight with `TrySetCanceled` for any
    `OperationCanceledException` from the starter's load, whatever token it carries. Joiners then
    loop, and a joiner whose own token fired still throws at its own `WaitAsync`.
- **Test to add.** A store-level test whose loader throws `OperationCanceledException` for a token
  other than the one passed to `GetAsync`, asserting that the joiner starts its own load. A façade
  test whose scope's `DataCancellation` is cancelled mid-load.

**R2-2 (minor): storing a probed list runs inside the batch's completions, so a store failure surfaces as a failure of a persist batch that already committed.**

- **Where.**
  - `src/core/Tellma.Core/Data/Batches/DataBatch.Caching.cs:85-87`: the probe's result is staged
    with `cursor.Settle(pending, () => store.Settle(...))`.
  - `ResultSetCursor.cs:120-125`: `Settle` runs that closure inside `ApplyCompletions`, which
    `DataExecutor.cs:218` calls after the commit.
  - `CacheableEntityStore.cs:227`: `Settle` calls `Set`, which throws `ObjectDisposedException` once
    the singleton store is disposed.
- **Failure scenario.**
  1. At host stop, a worker's persist batch is sent and, by design, runs to completion.
  2. The host's stop timeout elapses and the root provider disposes the store.
  3. The batch commits, then `ExecuteAsync` throws from the completion. The completion steps and
     `OnCommitted` callbacks (spec 0013's `cache.changed` publish among them) are skipped, and the
     caller sees an error for a committed write.

  Only disposal can make `Set` throw today, so the window is narrow. But a cache is an optimisation
  and must never turn a committed write into a failure.
- **Suggested fix.** In `CacheableEntityStore.Settle`, store best-effort: catch
  `ObjectDisposedException` around the `Set`, or any non-fatal exception and log it, and still
  return the rows.

**R2-3 (minor): the façade's refusal when the scope's settings are not loaded is untested.**
`src/core/Tellma.Core/Caching/CacheableEntities.cs:61-62`. This is new behaviour 2. Every façade
test uses a context that carries `TenantSettings`, so nothing pins that `GetAsync` and `Peek`
refuse, or that `GetWireTagsAsync` (which needs no shape) still answers.
- **Suggested fix.** Add one unit test with a context that has a tenant and no settings: `GetAsync`
  and `Peek` throw `InvalidOperationException`, and `GetWireTagsAsync` answers from the snapshot.

### Deviations (Reviewer 2's judgement)

1. **`CacheLoad` with `SizeOf` instead of a tuple: justified**, as Reviewer 1 found. `Loaded` refuses
   a null value, so `IsOversized => Value is null` cannot be confused with an empty load.
2. **Single flight keyed by (key, current tag): justified.** The cancellation half of the claim does
   not hold on the façade path (R2-1).
3. **No dependency on a miss: justified now.** On `Read` and `Validate` the consumer still gets the
   prelude's tag in `CacheResult.Tag`. On `Persist` the lock-only row (D-076) protects the read from
   the guard to the commit, and that is stronger than a compared dependency would be. The probe reads
   after the lock, so its rows cannot change before the commit under a guarded writer.
4. **`FromCache` refused after a write to its table: justified.** A `FromCache` composed before the
   write is still allowed, and it is correct: it reads the pre-write rows and stores them under the
   pre-bump tag, which the post-batch snapshot immediately makes stale.
5. **Closed `CacheKinds`, one store per kind per meter: justified.** With R1-5, the startup gate
   creates the store, so the `Lazy` in `DataExecutor` cannot cache a refusal on a started host.
6. **`load.duration` only for `GetAsync` loads: justified.**
7. **Evictions metered from callbacks: justified.** A racing `Set`/`Set` or `Set`/`Remove` can meter
   one displaced entry as `removed` instead of `replaced`, or the reverse. That is accepted noise in a
   thrash signal.
8. **D-076: the shape in `CacheableEntityKey`: conforms to the ruling.** The keys, the flights and
   the three tests cover both directions of a language change and a mixed-shape flight.

### New behaviour beyond the rulings

1. **`LoadAsync` refuses a handle whose shape differs from the key's: sound.**
   - It is defensive. On the façade path it can never fire: the key's shape and the handle's shape
     come from the same accessor at the same moment.
   - Through a joiner it cannot fire either: the load always runs on the starter's own handle, under
     the starter's own key.
   - It is checked before the batch is created, so a refused load costs no round trip.
   - A factory handle throws from `Shape` instead of being refused. Such a handle cannot create a
     read batch anyway, so this does not matter.
2. **The façade refuses when the scope's settings are not loaded: sound.** It mirrors
   `TenantDatabase`, which already refuses `Schema` and `Context` in that state. No platform path
   reads a cached list before the settings load: the connect prologue and the cold settings load use
   none. It is untested (R2-3).
3. **The startup check creates the store: sound.**
   - The gate resolves it from a scope of the host's own root provider, so the singleton it creates
     is the one `DataExecutor` later finds.
   - Any other exception from a check becomes a gate problem rather than a crash.
   - `emit-client-assets` runs the same check on its own provider, with its own meter factory. Its
     store is created and disposed with that provider, and the migrator tests in `Tellma.Core.Tests`
     (all green) exercise that path.
   - It needs no infrastructure, so a database outage at startup does not affect it.
