# PC-189: MCP server: host, authentication, request filter, read tools

## Implementer notes

### What was built, and where

- **`src/core/Tellma.Core.Mcp`** (new project, in `Tellma.slnx`; references `Tellma.Core.AspNetCore`
  and `ModelContextProtocol.AspNetCore` 2.2.0, pinned in `Directory.Packages.props`):
  - `McpTellmaBuilderExtensions.AddMcp(configure?)` is the entry point. It adds `McpFeature`
    (`FeatureName = "mcp"`, it only declares `McpOptions` at `Tellma:Mcp` through the gate). It
    registers the per-request services (`McpRequestAccess`, `McpCallState`), the singletons
    (`McpMetrics`, `McpEntities`, `EntityDescriber`, `DescribeCache`), the startup check
    `core.mcp-tool-names`, and the surface source. It attaches `McpBearerEvents` to `Tellma.Bearer`
    and registers the five read tools and the syntax resource. It then calls `AddMcpServer`
    (`ScopeRequests = false`), `WithHttpTransport(Stateless = true)` with `ConfigureSessionOptions`
    setting serverInfo and instructions, the request filters, and `WithTools(ToolTypes)` for the
    distribution's own tools. Calling `AddMcp` twice throws.
  - `Hosting/McpSurfaceSource` implements the new `ITenantSurfaceSource` seam in
    `Tellma.Core.AspNetCore` (`Routing/ITenantSurfaceSource.cs`). `MapTellma` maps its sources on the
    tenant group, so the route lives at `/{tenantId}/mcp`. It wraps `MapMcp` with `Tellma.Mcp`, the
    MCP rate and timeout policies, the body limit, and the hand-written Origin allow-list
    (`McpOrigins`). The SDK's stateless mapping serves only POST, so GET and DELETE answer 405.
  - `Authentication/McpBearerEvents` checks the audience in `OnTokenValidated`: the token must carry
    `{PublicOrigin}/{tenantId}/mcp` for the tenant in the route, or the request fails as 401
    `invalid_token`. Its `OnChallenge` writes `resource_metadata` naming that tenant's PRM, and
    `OnForbidden` writes 403 `insufficient_scope`.
  - `Hosting/McpRequestAccess` memoizes the access guard per request (`IsMutation = false`) and
    refuses service accounts. `McpServerIdentity` builds the instructions, naming the tenant only to
    an admitted caller, and a sandbox as a copy.
  - `Hosting/McpToolCallFilter`:
    - Call filter: guard, cultures (MessageLanguage, Calendar), exception to an `isError` result
      through `ProblemMapper` plus the JSON problem text, metrics and a log line.
    - List filter: platform tools first in the `McpToolNames` order, then the rest by name;
      `ttl` 5 min and `cacheScope` public.
  - Tools:
    - `tellma_whoami`: one guarded read round trip, then the access matrix over the visible entities;
      structured content plus its output schema.
    - `tellma_describe`: the catalogue with search, or one entity's Markdown description, gated by the
      tenant shape and cached.
    - `tellma_query` and `tellma_aggregate` (`RowTools`): rendered as a table or as objects, truncated
      row by row under the character cap; `includeInactive`; child entities through the child query.
    - `tellma_get`: the header first, child windows, and paging through one collection.
  - `Resources/QueryexSyntaxResource` serves `tellma://queryex/syntax` (embedded Markdown).
- **`Tellma.Core.AspNetCore`**:
  - `ProtectedResourceEndpoint` and `DistributionInfoEndpoint` give `resource_name` and the resource
    URL helpers.
  - `McpLimitOptions` is no longer bound from configuration. `AddMcp` sets it from `McpOptions`.
  - `ProblemWriter.Localize` became internal, so the filter renders problem text in the request's
    language.
  - The `composeWeb` docs now say the delegate may add a feature, but never an entity, a securable
    or a table.
- **Acme:**
  - `AcmeWebComposition` calls `tellma.AddMcp()`.
  - The Web project references `Tellma.Core.Mcp`.
  - The integration tests reference the SDK's client package.

### Deviations

1. **Integration coverage lives in Acme.** It is `McpTests` in
   `Tellma.Distro.Acme.IntegrationTests`, against the real composed host and SQL Server, not a new
   `Tellma.Core.Mcp.IntegrationTests`. PC-190 owns that suite. The trust in the test issuer is
   appended through `PostConfigure<JwtBearerOptions>`.
2. **"Lists 8 tools": five are listed.** This checkpoint ships the five read tools. save, delete and
   action are PC-190's.
3. **The bearer challenge and the audience check run through the `Tellma.Bearer` JwtBearerEvents**
   (`OnTokenValidated`, `OnChallenge`, `OnForbidden`), not the SDK's authentication handler. A wrong
   audience gets 401 `invalid_token`.
4. **The Origin check is hand-written** (`McpOrigins`) and answers 403 `forbidden`. An absent Origin
   passes, and so does a listed one, ignoring case.
5. **The describe cache is a private `MemoryCache`**, not a `VersionedCache`, because `CacheKinds` is
   a closed set. It holds 2048 entries with a 30-minute sliding expiration, and each hit is checked
   against the settings `VersionTag`. Its key adds the UI culture to (TenantId, Entity), because the
   description carries localized labels.
6. **Child entities.**
   - aggregate accepts them, as query does.
   - The catalogue lists each one under its owner.
7. **Service accounts are refused** with `individual-required` (ARCHITECTURE: individual users only
   this release).
8. **The guard runs once per request and is memoized.** serverInfo and the instructions name the
   tenant only after the guard admits the caller.
9. **`McpLimitOptions` is set from `McpOptions`**, not bound separately.
10. **The PRM document stays in `Tellma.Core.AspNetCore`.** Its `resource_name` is the display name
    alone.
11. **The distribution-info MCP surface is `/{tenantId}/mcp`.**
12. **Rendering choices.**
    - A full page with no count adds the hint "The page is full, so more rows may follow".
    - The objects format is a JSON array keyed by column.
    - get windows collections under a `$collections` member that gives total, returned and truncated
      for each collection.
13. **Whoami.**
    - The matrix covers only the entities the caller may see, and leaves out sensitive grants.
    - Language, calendar and zone come from the request context and the user's preferences.
14. **Argument errors are `bad-request`** with the argument's `path`.
15. **The list filter also orders the tools**, so the list is deterministic whatever order DI gives.
16. **describe refuses `entity` and `search` together** as a bad request.
17. **A second `AddMcp` call throws.**
18. **The `isError` problem text** is JSON holding status, code, title, detail, errors, errorDetails,
    arguments and retryAfterSeconds.
19. **`ProblemWriter.Localize` is internal** (it was private), shared with the MCP filter.
20. **The feature is named `core.mcp`** as spec 0016 §11.1 says (review 1, R1-4); it was `mcp`.
21. **`tellma_get` windows on the typed records.** `RecordShape` names each collection of an entity
    (from its metadata, by the `List<T>` property it is held in), and the collections are cut at
    every depth on shallow copies before any JSON is written. Each record, `related` and `extras`
    is then written through `BoundedJson`, which stops once its room is spent. The service's details
    read still loads the aggregate it loads (spec 0016 §11.5 accepts that); what the tool adds is
    bounded by the result (review 1, R1-5).
22. **The audience rule is the MCP events' alone.** `McpBearerEvents` requires exactly one `aud`
    value, equal to the tenant's resource; the shared `AudienceRequirement` in `BearerRequirements`
    is unchanged, since the events fail the token before any policy runs (review 1, R1-1, D-232).

Answers to the orchestrator's questions:

- **(1) Tenant isolation.**

    API audience. Both answer 401 `invalid_token` and are tested.
  - A token without `tellma_api` gets 403 `insufficient_scope`, which is tested.
  - An expired token is refused by `ValidateLifetime`, but no test covers it.

- **(2) The describe cache is not permission-dependent.**
  - `EntityDescriber.Describe` reads the registry, metadata, the schema for the tenant's shape, the

  - The timeout is `tellma-mcp`: 60 s.
  - All three are what spec 0016 §8.1-§8.3 states. None is exercised by a test here.
  - The memory risk is in `tellma_get`, not in the request body (R1-5).

- **(6) Integration coverage in Acme.**

  - Its refusal coverage is thin, though. No test covers an expired token, a token with several

### Findings

**R1-1 (major): a token carrying several audiences is accepted at each tenant it names, and at the MCP endpoint while it also names the API.**
`src/core/Tellma.Core.Mcp/Authentication/McpBearerEvents.cs:91-97` checks only that the resource is
among the `aud` values (`Any`). So does the policy's `AudienceRequirement` in
`src/core/Tellma.Core.AspNetCore/Authentication/BearerRequirements.cs:52`.

The identity server lets such a token exist.
`src/apps/Tellma.Identity/Services/ResourceGrantValidator.cs:188-195` lets an interactive grant
combine resources of one distribution: its origin and any of its tenants' `/{id}/mcp`.

- **Scenario.** A client authorizes with `resource=https://acme.example.com/1/mcp` and
  `resource=https://acme.example.com/2/mcp`, and the origin may be added as well.
  - The one access token works at `/1/mcp` and at `/2/mcp`.
  - It will also work on the public API once that surface ships.
  - Spec 0016 §11.2 requires the opposite: "The token's `aud` must equal it exactly … an MCP-audience
    token is refused on the public API — a token for tenant A is structurally invalid at tenant B".
    Spec 0010 §A.2 says "Tenant 18's MCP endpoint refuses a token whose `aud` is `<origin>/17/mcp`
    by audience alone".
  - Membership is still checked, so this does not open data the user cannot already see. But it
    removes the audience wall the spec makes the first defence. For example, a token leaked from
    one tenant's configured client is replayable at the user's other tenants.
- **Fix.** In `ValidateAudience`, fail unless the token carries exactly one `aud` value and that
  value is the resource. Mirror this in `AudienceRequirement` for `TenantMcp`. Add a test with a
  two-audience token (Live and Sandbox) that expects 401 `invalid_token` at both tenants.
  - Alternatively, if the identity server's combination rule is intended, flag the misalignment
    between spec 0016 §11.2 and the identity validator to Ahmad. One of them has to move.

**R1-2 (major): the checkpoint's listed unit tests are partly missing, so several security rules have no test that fails when they break.**
CHECKPOINTS.md names entity matching, Hidden gating and the describe catalogue and search among the
unit tests. `test/core/Tellma.Core.Mcp.Tests` (29 tests) has none of the following:

- `McpEntities`: matching that ignores case, a `Hidden` stack or child surface answered as unknown,
  and child surfaces carrying the root's exposure.
- `EntityDescriber.Describe`:
  - columns gated by the multilingual shape (`Gated`: no `Name2`/`Name3` under `PrimaryOnly`);
  - sensitive operations and actions left out (`Operations`, `Actions`, `IsSensitive`);
  - Hidden actions left out.
- `WhoamiTool.Matrix`: sensitive and Hidden pairs left out, and `filtered` listing only Filtered
  decisions.
- `McpToolCallFilter`:
  - `Problem` and `Render`: the code, errors, errorDetails and retryAfterSeconds text;
  - the Denied versus Error classification;
  - a cancellation propagating while other exceptions are mapped.
- `McpBearerEvents`: inert on a non-MCP endpoint, so the web, API and control-plane challenges stay
  untouched. The implementer named this as the top risk.

As things stand, a change that made `Hidden` stacks visible, or listed `core.User` save in describe
or in whoami, would pass every test. The Acme test covers only the happy path of these rules.

On the integration side, `McpTests` has no expired-token case, no case for a valid token of a
non-member or deactivated user (the `McpRequestAccess` guard path, which must give an `isError`
result and a title with no tenant name), and no service-account (`individual-required`) case.

- **Fix.**
  - Add unit tests over a small hand-built registry for the five areas above.
  - Add an expired token, and a non-member with a valid token, to the refusals test.

**R1-3 (minor): the call filter fails open when the request carries no services.**
`src/core/Tellma.Core.Mcp/Hosting/McpToolCallFilter.cs:44` sends any call whose
`request.Services` is null straight to `next`. That skips the tenant front door, the cultures, the
problem mapping and the metrics.

- A platform tool then throws, in `McpTool.InvokeAsync`.
- A distribution's `ToolTypes` tool would run unguarded, under the bearer only. Its services would
  come from wherever the SDK resolved them.
- Today the SDK always supplies the services, but on an authentication surface an unexpected state
  should be refused, not passed.
- **Fix.** Keep the bypass only for `MatchedPrimitive is null`, which is the SDK's unknown-tool
  error. When a matched tool has no services, return an `isError` result, or throw
  `InvalidOperationException`.

**R1-4 (minor): the feature name departs from the spec without a declared deviation.**
`src/core/Tellma.Core.Mcp/McpFeature.cs:19` sets `FeatureName = "mcp"`. Spec 0016 §11.1 says
`Name = "core.mcp"`, which `CompositionNames.IsValidFeatureName` accepts. The commit's Deviations
list does not mention it. Feature names are a composition-wide key, used by `[Requires]` and in
problems.

- **Fix.** Rename it to `core.mcp`, or list the deviation with its reason.

**R1-5 (minor): `tellma_get` builds the whole result as a JSON DOM before windowing, so one call can hold far more memory than it returns.**
`src/core/Tellma.Core.Mcp/Tools/StackInvoker.cs:94` serializes the whole `EntitiesResult` to a
`JsonNode` tree. `Rendering/EntityRendering.cs:231` and `:258` then deep-clone each record's header
and windows, and `Fit` re-clones on every halving.

- With `MaxIdsPerCall` 100 and `[MaxChildren]` 10,000 per collection, one call can make the DOM
  hold about 1M rows to return 60,000 characters.
- One user may make 120 such calls per minute per instance.
- Grandchild collections inside a kept line are not windowed at all. A kept line keeps every
  sub-row, which forces the narrowing to fall to a header-only render.
- Spec 0016 §11.5 accepts what the server loads. It does not ask for a DOM of all of it.
- **Fix.**
  - Window on the typed entities, by trimming the child lists, before serializing.
  - Or serialize record by record and stop once the budget is spent.
  - Window nested collections as well.

**R1-6 (minor): the trailing lines of `tellma_get` can push the text past `MaxToolResultChars`.**
`Rendering/EntityRendering.cs:32` holds back a fixed 1,500 characters. The two trailing lines at
`:105` and `:119` list every id that was left out or absent: up to `MaxIdsPerCall` = 100 ids of up
to 19 digits, plus separators. That is about 2,100 characters on top of the fixed text. So a
result can exceed the cap that spec 0016 §11.7 says bounds every text block.

- **Fix.** Compute the trailer before setting the record budget. Or cap the listed ids, for
  example "and N more", so the trailer always fits the reserve.
