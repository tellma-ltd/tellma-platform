# PC-066: Validation engine: context loader, parking scheduler, confirmations, attribute walker

## Implementer notes

### What was built, and where

All runtime types are internal to `Tellma.Core` under `src/core/Tellma.Core/Crud/Validation/`
until the write pipeline (PC-072 onwards) drives them.

- **Context loader** (`ContextLoader.cs`, `ContextLoader.Groups.cs`, `ContextRound.cs`, `SelectSet.cs`):
  - `IContextLoader` with DataLoader semantics. Each request is deduplicated by a structural key: a `QueryStatementKey` for engine statements, a `SqlStatementKey` for raw text.
  - `ByIds`, `ByKey` and `ByParentIds` are model-emitted `Query<T>` statements with a `KeySetRestriction` over a TVP. The TVP is `IdList`, `BigIdList`, `GuidList`, `StringList` or `DateList`, chosen by key type. One group per (entity, key) unions its keys and its selects (`SelectSet`) into one statement per round.
  - Missing keys are cached as absences. A key already answered is served from the cache, unless the new request selects more; then it is read again under the union.
  - `Prime` seeds rows the operation holds, and primed rows win over reads.
  - String keys compare as the platform collation `Latin1_General_100_CI_AS` does (`CollationKeyComparer`): case, kana type, width and trailing spaces are ignored, accents are not, and `ß` is spelled `ss`. The key-set TVP, the cache and the answer dictionaries all use this comparer (review 1).
  - `Query`, `Rows`, `Count`, `Exists` (the cap-0 count, shared) and `Sql` merge identical requests.
  - `Visible` conjoins the read decision: `Denied` reads nothing, `Filtered` adds `And`, `Unrestricted` adds nothing.
  - `Ancestors` reads a tree's ancestor chain and caches complete chains.
  - `Sql` refuses declared writes. The analyzer handles the call site (see below).
  - `BeginRound` / `DispatchAsync(IDataBatch, ct)` appends every pending group to one batch, executes it, and completes the refs. A round with nothing pending sends nothing.
- **Scheduler** (`ValidationScheduler.cs`):
  - Validators are tasks tagged with an `AsyncLocal` participant. `LoadAsync` parks the caller, and the scheduler dispatches once every participant is parked or finished, i.e. one dispatch per quiet point.
  - Tasks registered during a dispatch join the next round.
  - `MaxRounds` counts dispatches. Asking for one more throws `InvalidOperationException` naming the parked tasks.
  - A faulting task or a failing dispatch tears down the parked tasks, and so does cancellation. The abort uses a volatile flag plus a pre-cancelled token, with no disposable.
  - `LoadAsync` is refused, and the rounds fail with it, when it comes from a flow that outlived its task (fire-and-forget work a validator started) or outlived the rounds. The rounds are closed under the same gate that decides they are over (review 1).
  - `tellma.crud.validation.rounds` records the count, with `crud.outcome` `ok` or `exceeded` (`CrudMetrics.cs`).
- **Confirmations** (`Confirmations.cs`, `ConfirmationFrame.cs`, `DeclaredConfirmations.cs`, `ValidationOutcome.cs`, `CrudLog.cs`):
  - Scoped `IConfirmations`, seeded once per scope.
  - Declared keys come from `record.Confirmations`. An undeclared key is `InvalidOperationException`.
  - Under `PrincipalKind.System` every declared key counts as confirmed.
  - `Frame(resource, operation)` opens one write's frame, and `Dispose` closes it. The scope keeps a stack of open frames. `Require` on a frame, or on the scope while that frame is the innermost open one, collects the write's warnings (review 1). So an enlisted group that raises through the scope's `IConfirmations` is raised with its host:
    - A confirmed one logs `ConfirmationAccepted` (user, key, operation, resource, ids).
    - An unconfirmed one becomes a `ConfirmationRequest`.
    - `tellma.crud.confirmations` counts both outcomes.
  - Outside every frame, `Require` counts the warning and carries on:
    - An unconfirmed warning is kept in `Unframed`, which no outcome raises.
    - A confirmed one logs `ConfirmationAcceptedOutsideFrame`.
  - `ValidationOutcome.Raise` throws, in order: the stale stamp, then the errors, then every unconfirmed warning in key order.
  - Registered in `CrudComposition` with `AttributeWalker` and `CrudMetrics`.
- **Attribute walker and step 1 shape** (`AttributeWalker.cs`, `SaveShape.cs`):
  - Per-type cached plans check metadata facets first: MaxLength, and Precision/Scale, never rounded.
  - Then come BCL `ValidationAttribute`s on client-owned properties, plus class-level attributes.
  - It recurses into children with structured paths and leaves the parent key alone. `IValidatableObject` is ignored.
  - `CheckBody` walks request bodies through public properties and visits a cycle once.
  - Attributes map to existing codes. Anything else maps to the new `Validation.Invalid` code (`property`, `attribute` arguments; resx en/ar, the Abstractions golden and the pin test are updated).
  - `SaveShape.Check` handles step 1:
    - An empty payload or a null row is `BadRequestException`.
    - The ceilings checked are MaxSaveCount, MaxChildren and MaxRowsPerSave.
    - `Entity.DuplicateId` is raised on every repeat of a positive id, at its path.
- **Analyzer** (`src/core/Tellma.Core.Analyzers/`): TELLMA0003 now also covers `IContextLoader.Sql`. It applies the batch rules, plus three loader rules:
  - The text may write only to table variables it declares itself.
  - An explicit (Listed) `SqlOptions` write is refused. An Opaque set is left to the run-time check.
  - Any reserved name (`@tm_`, `@qx<n>_`, `@tb<n>_`) is refused even when only read, and that includes code in Tellma.Core.
  - No procedure is executed, not even the batch's two (`sys.sp_sequence_get_range`, `sys.sp_getapplock`) (review 1).
  - `KnownNames`, the name pins, the diagnostic description and the README are updated.
- **Scripted batch double** (`test/core/Tellma.Core.Tests/Crud/Scripted/`): `BatchScript`, `ScriptedBatch : IDataBatch` and `ScriptedStatement`.
  - It records every appended call in order: its kind, entity, statement, arguments, options and name.
  - It answers each from a canned response per (kind, entity), which can read the statement's TVP key set.
  - It throws on an unscripted result before completing anything, and counts round trips.
  - An `OnExecute` hook can hold an execution open, fail it, or observe its cancellation.
  - It completes results and runs commit callbacks.
  - `InternalsVisibleTo Tellma.Core.Tests` was added to Abstractions so the double can construct and complete `BatchResult`s.
- **Docs:**
  - The Tellma.Core README gains a "The validation stage" subsection and a `Crud/Validation/` layout row.
  - The Tellma.Core.Tests README gains rows for `Crud/Scripted/` and `Crud/Validation/`.
  - The ARCHITECTURE.md context-loading row now says what keyed loads are (see below).

### Deviations (also in the commit message)

1. A new code, `Validation.Invalid`, for a BCL attribute with no platform code. The spec names no fallback.
2. `IsConfirmed` with an undeclared key throws, like `Require`. The spec states this only for `Require`.
3. (Replaced in review 1; the scope-level `Require` now records, as §7.5 says.) Outside every write frame, an unconfirmed warning is kept in `Confirmations.Unframed`, which no validation outcome raises, because §7.5 leaves code outside validation to test `IsConfirmed` and throw. Its consent is logged under its own event name, `ConfirmationAcceptedOutsideFrame`, with no resource or operation, because no frame names them and the log generator refuses two methods under one event name. A warning raised on the scope lands in the innermost open frame, a stack per scope.
4. Under System, the counter still counts warnings, as confirmed, but no consent is logged, because no user consented.
5. A confirmation request is made for each `Require` call (keys sorted ordinally, stable within a key), rather than one request per key.
6. **Contradicts §6.6 step 5 (for Ahmad).** `ByKey` refuses a property that is unique only within its parent. §6.6 step 5 tells the write pipeline to issue "one `ByKey` load ... on a child, scoped to the parent key in C#". But the spec's `IReadOnlyDictionary<TK, T>` answer holds one row per value, while a per-parent `[Unique]` value can recur once per parent. So that call throws `ArgumentException` for every child `[Unique]`. What replaces it is in the Later seam note below.
7. `ByParentIds` answers every requested parent, with an empty list for a parent that has no children.
8. String keys compare as `Latin1_General_100_CI_AS` does, through `CollationKeyComparer` (culture comparison ignoring case, kana type and width, trailing spaces trimmed, `ß` spelled `ss`), so the TVP's primary key, the cache and the database's matches agree (review 1). The spec names no comparer.
9. `LoadAsync` with nothing pending completes immediately, and an empty round sends no batch.
10. `Visible` reads its decision through a constructor seam (`Func<Type, AccessDecision>`) until the access engine is wired. Without the seam it throws.
11. The rounds histogram records the dispatched count even when the ceiling is exceeded.
12. Attributes are not judged on non-client-owned properties, or on a child's parent key, which the pipeline sets.
13. TELLMA0003 is extended to `IContextLoader.Sql`. This is beyond the deliverable list, following spec 0015 §7.2's "the analyzer refuses DML here". Reserved names are refused even when only read, and no procedure is executed, not even the two a persist batch may run.
14. ARCHITECTURE.md's context-loading row said keyed loads are "model-emitted SQL" that never go through the engine. It now says they are model-emitted entity queries restricted by a TVP key set, with no authored text, and that Queryex text enters only as a user- or permission-authored filter.
15. §7.3 "re-homing basics" is not built here (review 1). There is no view yet that maps an enlisted participant's errors through `MapPath` and tags them with `enlistedResource`, and `ValidationErrors.Add` cannot be intercepted. It moves to PC-077, the enlistment checkpoint, whose deliverables already list an "error re-homing view". The coverage line drops §7.3. The §18.1 pin "an enlisted target's warning raised through its host" is covered here, because confirmations need no re-homing.

### Later seam: the per-parent uniqueness load (for the write pipeline)

§6.6 step 5's child `[Unique]` pre-check cannot use `ByKey` (deviation 6). The write-pipeline checkpoint should add an internal keyed load by value that answers every matching row per value: `ByValues<T, TK>(property, values)` returning `IReadOnlyDictionary<TK, IReadOnlyList<T>>`. It would go through the same `KeySetRestriction` and the same `CollationKeyComparer`, and the pipeline would then scope the answer by parent key in C#, as step 5 already says. A cheaper alternative is a `Query<TChild>` over the payload's values with the parent ids in the filter. Either way the spec's signature needs amending, so this is flagged for Ahmad, not built here.

### Open risks

- A null value for a non-nullable string column that carries no `[Required]` passes the walker. It then fails in SQL with error 515. Pipeline defaults (PC-072) may cover it.
- An overlong value in an unconfigured multilingual twin column is judged against the column's MaxLength at step 1, even if no language uses that twin.
- MaxLength counts UTF-16 code units, matching `nvarchar(n)`, not user-perceived characters.
- EF takes the column MaxLength from `[StringLength]` when both `[MaxLength]` and `[StringLength]` sit on a mapped string. The walker follows the metadata, so it reports one failure, not two.
- A validator that awaits another validator's task, rather than `LoadAsync`, can deadlock the round. The scheduler cannot see that wait. Only cancellation or the caller's timeout ends it.
- The validation tests compose a model per test class, about 5–10 s each.
- `CollationKeyComparer` approximates `Latin1_General_100_CI_AS` with the en-US culture comparison (ICU on Linux and current Windows), plus explicit folds for trailing spaces and `ß`. Several cases could still disagree with the database:
  - other expansions the collation makes, such as `æ`/`ae` or `œ`/`oe`;
  - a column with its own collation (`_BIN2`, `_CS_`);
  - a process running with invariant globalization.
  Any of these lets a request and the stored row miss each other, and the cost is a late 2601 or a missed context row. Only a duplicate that the collation sees and the comparer does not reaches the TVP's primary key.
- Frames are a stack per scope, and the innermost open one takes the scope's warnings. Two sibling write frames open at once on concurrent flows of one scope would share whichever was opened last. Nothing in this checkpoint opens frames concurrently. If PC-072 does, the current frame should move to an `AsyncLocal`.

### What reviewers should examine hardest

- The `ValidationScheduler.DriveAsync` quiet-point detection and teardown paths. Look at the interaction of late registration, `RequestRound`, a fault during a dispatch, and cancellation. Check that no participant can be left parked forever.
- The `ContextLoader` cache rules:
  - absence caching versus a later wider select;
  - primed rows versus read rows;
  - the collation key comparer used consistently in the TVP, the cache and the answer dictionaries.
- The analyzer's loader rules in `DataBatchAnalyzer.CheckLoaderWrites` / `CheckReservedNames`, for false negatives on writes spelled through interpolation holes.
- Whether the scripted batch's surface (`BatchScript.On*`, `ScriptedStatement.KeySet<T>`) is enough for PC-072 and later checkpoints to reuse without change.

**R1-1 (major). The scoped `IConfirmations` breaks its own public contract.**
`src/core/Tellma.Core/Crud/Validation/Confirmations.cs:103-108`: `Require` always throws.
`CrudComposition` registers this class as the scope's `IConfirmations`. The contract says
otherwise in two places:
- `src/core/Tellma.Core.Abstractions/Validation/IConfirmations.cs:8-11,35-43` calls the object "one
  per request scope, shared by every write frame and enlisted group in it". It says `Require`
  "records a warning ... the operation carries on", and documents an exception only for an
  undeclared key.
- `src/core/Tellma.Core.Abstractions/Crud/IWriteHost.cs:32` says `IWriteHost.Confirmations` is
  "the scope's confirmations".

- *Failure:* a pack author injects `IConfirmations`, as `JobQueue` already does, into an
  `[ApiAction]` handler or a hook and calls `Require` with a declared key. The call throws
  `InvalidOperationException` "outside every write frame". By the documented contract it should
  record the warning. A frame that later exposes "the scope's confirmations", as the
  `IWriteHost` doc describes, would make every `Require` throw.
- *Fix:* choose one model and make the published docs match it:
  - Keep deviation 3. Then rewrite the `IConfirmations` and `IWriteHost.Confirmations` XML docs:
    warnings are recorded through the frame's view (`IWriteHost.Confirmations`), and the scope's
    instance refuses `Require`. Add that `<exception>`, and flag the §7.5 sketch comment for
    Ahmad.
  - Or let the scope instance record warnings, and let each frame raise the warnings recorded
    under it.
- *Test:* a test that pins whichever behaviour is documented.

**R1-2 (minor). A flow that outlives its validator can still park, and that breaks the quiet-point
count.**
`src/core/Tellma.Core/Crud/Validation/ValidationScheduler.cs:225-250`: `ParkAsync` refuses only a
participant that is already `Parked`. A `Completed` participant passes: it is set to `Parked`,
added to `_parked`, and `Leave()` decrements `_running` a second time. The `AsyncLocal` flows into
any un-awaited `Task.Run`, or into an async helper the validator started.

- *Failure:* I ran a probe against the built `Tellma.Core.dll`:
  - Validator `v1` starts a fire-and-forget flow that awaits `LoadAsync` 300 ms later, then
    completes.
  - Validator `v2` awaits a 1.5 s delay.
  - The probe printed "dispatch 1; v2 active = True": the round was dispatched while `v2` was
    still active. That breaks the §7.2 "never dispatch early" property.
  - If such a flow parks after the rounds have ended, it waits forever.
- *Same class, at `:316-320` and `:197-203`:* `DriveAsync` decides the rounds are over under the
  gate, but `RunAsync` sets `_finished` only under a later lock. A `Run` from a stray flow in that
  window registers a task that can park on a round nobody dispatches, and then
  `Task.WhenAll(tasks)` hangs.
- *Fix:*
  - `ParkAsync` throws `InvalidOperationException` when the participant is `Completed` ("LoadAsync
    awaited by a flow that outlived its validator; await the work you start") or when `_finished`
    is set.
  - `DriveAsync` sets `_finished = true` inside the terminating branches, under the same lock.
  - Add a unit test with a fire-and-forget load that expects the refusal and no early dispatch.

**R1-3 (minor). `IContextLoader.Sql` still allows the batch's two procedures, and one of them
writes.**
In loader mode, `CheckStatements` (`src/core/Tellma.Core.Analyzers/DataBatchAnalyzer.cs:375-378`)
still lets `execution.IsAllowed` through. That is `EXEC sys.sp_sequence_get_range` and
`EXEC sys.sp_getapplock`. Nothing else in the loader branch (`:289-293`) refuses them. The run-time
check only looks at `SqlOptions.Writes`.

- *Failure:* `loader.Sql($"DECLARE @f sql_variant; EXEC sys.sp_sequence_get_range @sequence_name = N'dbo.Ids', @range_size = 1000000, @range_first_value = @f OUTPUT; SELECT 1;")`
  compiles cleanly. Every validation round then consumes a million sequence values. The
  allocation is outside any transaction, so it is never undone. This contradicts §7.2 ("a
  `Validate` batch never writes; the analyzer refuses DML here") and the new README line "No
  statement writes any table other than a table variable". `sp_getapplock` with a session owner
  also holds a lock past the read.
- *Fix:* when `api == LoaderSql`, report every `EXEC`, allowed or not ("IContextLoader.Sql reads
  only; it executes no procedure"). Add an analyzer vector for each of the two procedures.

**R1-4 (minor). The string key comparer does not match the key-set table's primary key or the
collation.**
`src/core/Tellma.Core/Crud/Validation/ContextLoader.Groups.cs:655-658,686-691,698-708` (deviation
8): keys are de-duplicated and matched with `OrdinalIgnoreCase`. The `[StringList]` table type has
a `PRIMARY KEY` on `Id`, and that key compares under `Latin1_General_100_CI_AS`, the platform
collation. The collation ignores trailing spaces and width, and expands `ß` to `ss`.

- *Failure 1:* `ByKey<T, string>("Code", ["A1", "Ａ1"])` (full-width A), or `["X", "X "]` from a
  validator or a `[PreserveWhitespace]` property. The ordinal comparer passes both, so filling the
  TVP violates its primary key (2627), and the whole validation round fails with an untranslated
  `SqlException` (500).
- *Failure 2:* a request for `straße` matches the database row `STRASSE`. `KeyedGroup.Finish`
  (`:180-193`) stores it under `STRASSE` and caches `straße` as missing. The §6.6 step 5
  uniqueness pre-check then misses the duplicate, which surfaces only later as a race-path 2601.
- *Fix:*
  - Fold string keys the way the collation does: trim trailing spaces, and use a comparer from
    `CompareInfo.GetCompareInfo("en-US")` with `IgnoreCase | IgnoreKanaType | IgnoreWidth`.
  - Answer requested keys through the same comparer.
  - Add a test with a width or trailing-space pair.
  - At minimum, record this under Open risks.
