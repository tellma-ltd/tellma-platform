# PC-066: Validation engine: context loader, parking scheduler, confirmations, attribute walker

## Implementer notes

### What was built, and where

All runtime types are internal to `Tellma.Core` under `src/core/Tellma.Core/Crud/Validation/`
until the write pipeline (PC-072 onwards) drives them.

- **Context loader** (`ContextLoader.cs`, `ContextLoader.Groups.cs`, `ContextRound.cs`, `SelectSet.cs`):
  - `IContextLoader` with DataLoader semantics. Each request is deduplicated by a structural key: a `QueryStatementKey` for engine statements, a `SqlStatementKey` for raw text.
  - `ByIds`, `ByKey` and `ByParentIds` are model-emitted `Query<T>` statements with a `KeySetRestriction` over a TVP. The TVP is `IdList`, `BigIdList`, `GuidList`, `StringList` or `DateList`, chosen by key type. One group per (entity, key) unions its keys and its selects (`SelectSet`) into one statement per round.
  - Missing keys are cached as absences. A key already answered is served from the cache, unless the new request selects more; then it is read again under the union.
  - `Prime` seeds rows the operation holds, and primed rows win over reads.
  - String keys compare `OrdinalIgnoreCase`.
  - `Query`, `Rows`, `Count`, `Exists` (the cap-0 count, shared) and `Sql` merge identical requests.
  - `Visible` conjoins the read decision: `Denied` reads nothing, `Filtered` adds `And`, `Unrestricted` adds nothing.
  - `Ancestors` reads a tree's ancestor chain and caches complete chains.
  - `Sql` refuses declared writes. The analyzer handles the call site (see below).
  - `BeginRound` / `DispatchAsync(IDataBatch, ct)` appends every pending group to one batch, executes it, and completes the refs. A round with nothing pending sends nothing.
- **Scheduler** (`ValidationScheduler.cs`):
  - Validators are tasks tagged with an `AsyncLocal` participant. `LoadAsync` parks the caller, and the scheduler dispatches once every participant is parked or finished, i.e. one dispatch per quiet point.
  - Tasks registered during a dispatch join the next round.
  - `MaxRounds` counts dispatches. Asking for one more throws `InvalidOperationException` naming the parked tasks.
  - A faulting task or a failing dispatch tears down the parked tasks, and so does cancellation. The abort uses a volatile flag plus a pre-cancelled token, with no disposable.
  - `tellma.crud.validation.rounds` records the count, with `crud.outcome` `ok` or `exceeded` (`CrudMetrics.cs`).
- **Confirmations** (`Confirmations.cs`, `ConfirmationFrame.cs`, `DeclaredConfirmations.cs`, `ValidationOutcome.cs`, `CrudLog.cs`):
  - Scoped `IConfirmations`, seeded once per scope.
  - Declared keys come from `record.Confirmations`. An undeclared key is `InvalidOperationException`.
  - Under `PrincipalKind.System` every declared key counts as confirmed.
  - `Frame(resource, operation)` collects one write's warnings:
    - A confirmed one logs `ConfirmationAccepted` (user, key, operation, resource, ids).
    - An unconfirmed one becomes a `ConfirmationRequest`.
    - `tellma.crud.confirmations` counts both outcomes.
  - `ValidationOutcome.Raise` throws, in order: the stale stamp, then the errors, then every unconfirmed warning in key order.
  - Registered in `CrudComposition` with `AttributeWalker` and `CrudMetrics`.
- **Attribute walker and step 1 shape** (`AttributeWalker.cs`, `SaveShape.cs`):
  - Per-type cached plans check metadata facets first: MaxLength, and Precision/Scale, never rounded.
  - Then come BCL `ValidationAttribute`s on client-owned properties, plus class-level attributes.
  - It recurses into children with structured paths and leaves the parent key alone. `IValidatableObject` is ignored.
  - `CheckBody` walks request bodies through public properties and visits a cycle once.
  - Attributes map to existing codes. Anything else maps to the new `Validation.Invalid` code (`property`, `attribute` arguments; resx en/ar, the Abstractions golden and the pin test are updated).
  - `SaveShape.Check` handles step 1:
    - An empty payload or a null row is `BadRequestException`.
    - The ceilings checked are MaxSaveCount, MaxChildren and MaxRowsPerSave.
    - `Entity.DuplicateId` is raised on every repeat of a positive id, at its path.
- **Analyzer** (`src/core/Tellma.Core.Analyzers/`): TELLMA0003 now also covers `IContextLoader.Sql`. It applies the batch rules, plus three loader rules:
  - The text may write only to table variables it declares itself.
  - An explicit (Listed) `SqlOptions` write is refused. An Opaque set is left to the run-time check.
  - Any reserved name (`@tm_`, `@qx<n>_`, `@tb<n>_`) is refused even when only read, and that includes code in Tellma.Core.
  - `KnownNames`, the name pins, the diagnostic description and the README are updated.
- **Scripted batch double** (`test/core/Tellma.Core.Tests/Crud/Scripted/`): `BatchScript`, `ScriptedBatch : IDataBatch` and `ScriptedStatement`.
  - It records every appended call in order: its kind, entity, statement, arguments, options and name.
  - It answers each from a canned response per (kind, entity), which can read the statement's TVP key set.
  - It throws on an unscripted result before completing anything, and counts round trips.
  - An `OnExecute` hook can hold an execution open, fail it, or observe its cancellation.
  - It completes results and runs commit callbacks.
  - `InternalsVisibleTo Tellma.Core.Tests` was added to Abstractions so the double can construct and complete `BatchResult`s.
- **Docs:**
  - The Tellma.Core README gains a "The validation stage" subsection and a `Crud/Validation/` layout row.
  - The Tellma.Core.Tests README gains rows for `Crud/Scripted/` and `Crud/Validation/`.
  - The ARCHITECTURE.md context-loading row now says what keyed loads are (see below).

### Deviations (also in the commit message)

1. A new code, `Validation.Invalid`, for a BCL attribute with no platform code. The spec names no fallback.
2. `IsConfirmed` with an undeclared key throws, like `Require`. The spec states this only for `Require`.
3. The scope-level `Confirmations.Require` always throws ("outside every write frame"). Warnings are raised through a `ConfirmationFrame`, which carries the resource and operation that the consent log needs.
4. Under System, the counter still counts warnings, as confirmed, but no consent is logged, because no user consented.
5. A confirmation request is made for each `Require` call (keys sorted ordinally, stable within a key), rather than one request per key.
6. `ByKey` refuses a property that is unique only within its parent.
7. `ByParentIds` answers every requested parent, with an empty list for a parent that has no children.
8. String keys compare `OrdinalIgnoreCase`, matching the database's case-insensitive collation.
9. `LoadAsync` with nothing pending completes immediately, and an empty round sends no batch.
10. `Visible` reads its decision through a constructor seam (`Func<Type, AccessDecision>`) until the access engine is wired. Without the seam it throws.
11. The rounds histogram records the dispatched count even when the ceiling is exceeded.
12. Attributes are not judged on non-client-owned properties, or on a child's parent key, which the pipeline sets.
13. TELLMA0003 is extended to `IContextLoader.Sql`. This is beyond the deliverable list, following spec 0015 §7.2's "the analyzer refuses DML here". Reserved names are refused even when only read.
14. ARCHITECTURE.md's context-loading row said keyed loads are "model-emitted SQL" that never go through the engine. It now says they are model-emitted entity queries restricted by a TVP key set, with no authored text, and that Queryex text enters only as a user- or permission-authored filter.

### Open risks

- A null value for a non-nullable string column that carries no `[Required]` passes the walker. It then fails in SQL with error 515. Pipeline defaults (PC-072) may cover it.
- An overlong value in an unconfigured multilingual twin column is judged against the column's MaxLength at step 1, even if no language uses that twin.
- MaxLength counts UTF-16 code units, matching `nvarchar(n)`, not user-perceived characters.
- EF takes the column MaxLength from `[StringLength]` when both `[MaxLength]` and `[StringLength]` sit on a mapped string. The walker follows the metadata, so it reports one failure, not two.
- A validator that awaits another validator's task, rather than `LoadAsync`, can deadlock the round. The scheduler cannot see that wait. Only cancellation or the caller's timeout ends it.
- The validation tests compose a model per test class, about 5–10 s each.

### What reviewers should examine hardest

- The `ValidationScheduler.DriveAsync` quiet-point detection and teardown paths. Look at the interaction of late registration, `RequestRound`, a fault during a dispatch, and cancellation. Check that no participant can be left parked forever.
- The `ContextLoader` cache rules:
  - absence caching versus a later wider select;
  - primed rows versus read rows;
  - the case-insensitive string key comparer used consistently in the TVP, the cache and the answer dictionaries.
- The analyzer's loader rules in `DataBatchAnalyzer.CheckLoaderWrites` / `CheckReservedNames`, for false negatives on writes spelled through interpolation holes.
- Whether the scripted batch's surface (`BatchScript.On*`, `ScriptedStatement.KeySet<T>`) is enough for PC-072 and later checkpoints to reuse without change.
