# PC-021: Entity metadata, startup validation, natural keys, display-name metadata and fingerprints

## Implementer notes

### What was built, and where

- **`Tellma.Core.Abstractions.Data`** (contracts, 0012 §3.1, §3.3):
  - `EntityMetadata` (sealed class; public constructor; `Children`, `References` and
    `SchemaFingerprint` come from factories run once, on first read, because entities name each
    other and themselves; `ResetServerOwned`/`ResetDerived` copy from a fresh instance per call),
    `PropertyMetadata`, `PropertyOwnership`, `ChildCollectionMetadata`, `ReferenceMetadata`,
    `NaturalKeyMetadata`, `MultilingualGroup`, `UniqueIndexMetadata`, `TreeMetadata`,
    `BlobReferenceMetadata`, `DisplayNameMetadata` (`Separator = " - "`), `TableName` (validated,
    `Delimited` form), `IEntityMetadataProvider`, `IDisplayNames` (contract only).
  - `QueryColumn`, `QueryRowSet` with a working `Builder(columns, fieldTypes, capacity)`:
    `AppendRow(DbDataReader)` and `Build()`; the buffer per (query type, field type) is §11.3's
    table, anything else is an `InvalidOperationException` naming the column; a hierarchy column
    reads `GetValue(i)` as its path string. `RowPage`, `RelatedEntities` (+ `RelatedEntitySet`).
- **`Tellma.Core.Data.Metadata`** (runtime):
  - `EntityMetadataBuilder` (three partial files): phase 1 selects the leaves (definition order,
    then Core-configuration-only types by name); phase 2 describes each leaf (table, capability
    columns, parent key, mapped members, ownership, facets, accessors, groups, unique indexes,
    natural keys, blob references, tree, table type, display name, `[RelatedSelect]`); phase 3
    entity names and the lookup from any base below the platform's bases; phase 4 children,
    aggregate rules, references, navigation names; phase 5 warnings. The provider is created only
    when no problem was reported; every lazy part is forced before it is returned.
  - `EntityMetadataProvider`, `EntityMetadataSource` (lazy, one build per host; catches a model
    that cannot be built and turns the convention's message into one problem), `Fingerprints`
    (`Schema`, `Storage`, `FingerprintWriter`: length-prefixed UTF-8 tokens into SHA-256),
    `PropertyAccessors` (compiled getter/setter/collection getter/factory), `EntityMetadataLog`.
  - `core.entity-metadata` (`EntityMetadataCheck`, built-in, `RequiresInfrastructure = false`):
    returns the build's problems and logs its warnings. `TellmaModelFactory.Register` adds the
    source and `IEntityMetadataProvider` (which throws, listing the problems, for an unsound model).
  - `TellmaModelDefinition` now carries the leaf substitutions (`Leaves`, `LeafOf`), and
    `Create` takes the substitution map instead of a resolver function, so the builder can name a
    leaf after its default and recognise a replaced default in the model.
- **Tests**: `Tellma.Core.Tests/Data/Metadata/` (sound model: 59 cases over every part;
  `Malformed/`: one entity per rule, 58 cases; `Fingerprinted/`: 12 cases with pinned values),
  `Composition/Checks/EntityMetadataCheckTests` (6: gate pass/fail, provider identity and refusal,
  warning logged, model that cannot be built, web host vs migrator parity),
  `Tellma.Core.Abstractions.Tests/Data/` (`QueryRowSet`, `RelatedEntities`, `TableName`,
  `EntityMetadata`). `StartupGateTests` lists the new check.
- Docs: `Tellma.Core` README (check row, Entity metadata section, layout), Abstractions README
  (Data row), both test READMEs, ARCHITECTURE.md (leaf-only mapping: TPT refused for now; the
  realised gate builds the model).

### Deviations (also in the commit message)

1. Rules beyond §3.2's list, each an obvious consequence of a stated rule: every entity declares
   `[Table]` in a schema other than `dbo` (without it the table takes the leaf's class name and
   moves with a substitution; §4.1 keeps `dbo` for platform tables); a derived entity type (TPH
   or TPT) is refused, since the conventions shape roots only and `EntityMetadata` has one table;
   a contributed class not deriving `Entity<TKey>`, a generic entity class, two entities sharing a
   name, a mapped non-public member, a composite or shadow foreign key, a foreign key whose name
   does not end in `Id`, a `[MaxChildren]` below 1, a child no collection carries, a cycle of child
   collections, a column annotation on an unmapped property or on a non-string for the string-only
   annotations, and `[Defaulted]` on a non-editable property are refused.
2. "Every `[ParentKey]` is a foreign key to a top-level table" is read as "its aggregate's root is
   top-level": §2.3 allows grandchildren, whose parent key references a child table.
3. The unkeyed-reference warning skips blob and job columns (neither travels in a spreadsheet, so
   `core.Blobs`/`core.Jobs` would warn in every composition). Warnings are logged by the check
   (`EntityMetadataWarning`, Warning), never problems.
4. `StorageFingerprint` also covers computed-column definitions and every table type's physical
   name: a type version the database lacks fails every save of its entity, exactly like a missing
   column. Tables, columns, indexes, sequences and types are each sorted ordinally (the relational
   model's own column order is by name), so declaration order never moves the value.
5. `TableTypePhysicalName` is `string?`: system entities (`Entity<int>`, never saved) have no table
   type. Format `<schema>.<name>_<hash8>`, undelimited, as §3.1 writes it.
6. `NaturalKeyMetadata.Order` is the key's rank in `NaturalKeys` (declared keys sorted by their
   `Order`, then declaration order, then the inferred ones).
7. A navigation name derives from the foreign-key property's name (equal to its column for every
   platform and default-leaf column, which the gate enforces), not from a renamed leaf column.
8. `PropertyMetadata.ValueSet` is always null: spec 0013's `[ValueSet]` (PC-019) does not exist
   yet. The blob kind-registry rule (§3.2 "the kind is registered") waits for PC-083's registry;
   until then the kind's grammar and its uniqueness are checked and the policy comes from the
   declaration (`BlobReferenceAttribute.CreatePolicy`).
9. `RelatedEntities.Add` to an existing set requires the same CLR type and narrows the projection
   to the columns both adds carry (a set's projection is what every instance holds).
10. `QueryRowSet.Builder` is implemented here with `AppendRow(DbDataReader)` and `Build()` (the
    spec gives only the constructor); `Date` reads `DateOnly.FromDateTime(GetDateTime)` and
    accepts a `DateOnly` field type too.
11. `TellmaModelDefinition.Create` takes the leaf map (changed PC-018 code and its four test
    callers).

### What reviewers should examine hardest

1. `EntityMetadataBuilder.Parts.cs` `Ownership` and `DescribeProperty`: the derivation order
   (computed > server-owned by derivation > annotation > editable) and the fixed-column-name rule
   (`member.DeclaringType.IsAssignableFrom(leaf.DefaultType)`).
2. `CollectCapabilities`/`Implementation`: interface-declared members via the interface map
   (matched by method handle, since the map reflects through the class).
3. `DescribeNaturalKeys`: inference order, the child-scoped backing and the declared-key checks.

5. `SelectLeaves`/`IndexByBase`: replaced defaults in the model, derived types, the shared-base
   reduction to the most derived shared class.

Orchestrator questions:
- **Entity inheritance (TPT/TPH).** No spec in 0010-0035 maps entity inheritance. Every extension
  is plain CLR inheritance substituted by `UseEntity<TDefault, TLeaf>()`: 0012 §2.8, 0014 `MyUser`,
  0015 §3, 0018 §5.2 and decision 8 ("every entity extends by plain inheritance"), and 0011's
  `MyInvoice : SalesInvoice`. No spec declares an abstract entity base or a `Document` root. TPT
  appears only in 0012's refusals: §1.3 `TemporalConvention`, §3.2 "Temporal" and §4.2 "never on
  TPT". Those rules presume TPT could exist but rely on nothing, and §3.2's "Leaf uniqueness"
  already refuses a default re-added "beside the leaf under a discriminator". So refusing every
  derived entity type is consistent with the specs, and no finding is raised. Only
  ARCHITECTURE.md's old `Document (TPT root)` bullet described otherwise, and the implementer
  corrected it.
- **`[Table]` outside `dbo`.** This matches 0012 §4.1 (`dbo` holds only the three platform tables
  and the standalone table types) and §2.2/§2.8 (`[Table]` is how a pack declares its table, and
  a leaf inherits it). Every entity declaration in 0014, 0018, 0021, 0028, 0033 and 0035 carries
  `[Table(..., Schema = "core"|"gl")]`. 0017's `Blob`, 0020's `Job`/`Schedule`, 0019's
  `Export`/`Import`, 0022 and 0026 state their table only in a comment, so those checkpoints must
  add the attribute. The gate's message says exactly what to write. Nothing existing breaks: there
  is no concrete entity under `src/`, and `distributions/` does not exist yet. The only entities
  are test fixtures, and they pass.

Confirmed correct, no finding:
- **Leaf substitution and lookup.** `TellmaModelDefinition.Create` takes the map, and all five
  callers (four tests plus `From`) were updated; the build proves it. Get(base) resolves through
  the chain up to the platform bases. A replaced default still in the model, a leaf replacing two
  defaults and a base shared by two leaves (reported at the most derived shared class) are all
  refused. The name is `<schema>.<DefaultType.Name>`, and names collide case-insensitively.
- **Natural keys.** Declared keys come by `Order`, then declaration order. Inference order is the
  `Name` anchor, then `Code`, then required unique strings, then nullable ones, all
  unique-index-backed, with `(ParentKey, Property)` on a child. The checks cover a key's CLR type,
  JSON and binary columns, and a missing index. Deviation 6 (`Order` = rank) is harmless to 0019,
  which reads the list order only.
- **Display names.** Declared source/prefix validation, the Name → first key → Id fallback and the
  `[RelatedSelect]` minimum (all twins + prefix + Code) match §2.5/§3.2.
- **Ownership derivation.** The order is computed > derivation > annotation > editable, with
  interface members found through the interface map (explicit implementations refused) and
  `[Defaulted]` refused on a non-editable property. The fixed-name rule covers the platform base,
  capability and default-leaf members.
- **StorageFingerprint.** Length-prefixed UTF-8 tokens with an explicit null marker, every list
  sorted ordinally, defaults written with the invariant culture and the value's type name. That
  is deterministic across runs and OSes (the implementer pinned values on Linux too). Every
  physical item §4.3 lists is covered, plus computed SQL/stored and table-type physical names
  (deviation 4, justified). Design-time and runtime equality is asserted.
- **`core.entity-metadata`.** It is a built-in check (so it runs even when contributed checks
  cannot be resolved) and needs no infrastructure (so `emit-client-assets` runs it). A model that
  cannot be built becomes one problem, a check that throws is caught by the gate, and warnings are
  logged at Warning, never as problems. `IEntityMetadataProvider` resolved for an unsound model
  throws, listing every problem.
- **Seams.** `ValueSet = null` (PC-019, one line), blob kind registration (PC-083), and for PC-033

  and contract-compatible with 0013/0016/0033. `QueryColumn`, `QueryRowSet`, `RowPage`,
  `RelatedEntities` and the records match §3.1/§3.3 member for member.
- **AGENTS.md / PLAN §7.1.** XML docs and section comments are present. No §, spec, PC or

R1-1 (major) — `ResetServerOwned` wipes temporary ids.
`src/core/Tellma.Core.Abstractions/Data/EntityMetadata.cs:118` (`_serverOwned` includes the
key) and `:217`. `Id` is `ServerOwned` by derivation (§2.4), so `ResetServerOwned` restores `Id`
to the fresh instance's `0`. The test pins this
(`test/core/Tellma.Core.Tests/Data/Metadata/EntityMetadataTests.cs:217`, `account.Id == 0`).
- Failure scenario: spec 0015 §6.3 resets server-owned members during preprocessing (step 3),
  before §6.4's assignment (step 4). That assignment, and 0012 §7.3's, rewrites every temporary
  id (`Id < 0`) in self-typed foreign keys, child parent keys and grandchild `[ParentKey]`s. Take
  a save of two new centers, where `-2.ParentId = -1`, or a new parent whose new child carries a
  parent key of `-1`. Every new row's `Id` becomes `0` before assignment, so the `-1` references
  point at nothing and come back as `Entity.NotFound`, or rows get mis-paired. Nothing fails until
  the 0015 pipeline exists.
- Fix: leave the key out of the reset set (`... && !ReferenceEquals(property, Key)`). The key
  stays `ServerOwned` in `Properties`, which is what the SET list and the emitter need. Say so in
  the XML doc ("the key, which the id allocator owns, is kept"), and change the test to assert a
  temporary `Id = -5` survives the reset. Record it as a deviation, since 0012 §3.1 says "every
  `ServerOwned` property" while §7.3 and 0015 §6.3-§6.4 need the temporary id to survive.

R1-2 (minor) — a view- or query-mapped entity crashes the whole check.
`src/core/Tellma.Core/Data/Metadata/EntityMetadataBuilder.Parts.cs:160`: `GetTableName()!`.
- Failure scenario: EF returns null when an entity type is mapped to a view, a SQL query or a
  function rather than a table, for example by a Core configuration's `ToView`. `new
  TableName(schema, null)` then throws an `ArgumentException` out of the builder. The gate
  reports only "The check failed with ArgumentException ... (Parameter 'Name')" and loses every
  other problem, which defeats "a malformed model fails startup listing every problem".
- Fix: when `GetTableName()` is null, report "The entity X is not mapped to a table" (fix: remove
  the `ToView`/`ToSqlQuery`/`ToFunction` mapping), leave the leaf's metadata null and return. Add
  one malformed case.

R1-3 (minor) — several rules have no test that fails if the rule breaks.
Under `test/core/Tellma.Core.Tests/Data/Metadata/`, no test hits these messages or behaviours:
- `EntityMetadataBuilder.cs:186-189`: the derived-type refusal without a replaced default, for
  example contributing both `Party` and `Customer : Party` (table-per-hierarchy). This is the rule
  ARCHITECTURE.md now cites. The only derived-type test goes through a replaced default and ends
  as "the model cannot be built".
- `EntityMetadataBuilder.cs:218-223`: a leaf registered for two defaults.
- `EntityMetadataBuilder.cs:234-241`: one leaf per table.
- `EntityMetadataBuilder.Relations.cs:34-40` and `:52-57`: a collection whose child maps no leaf,
  and a parent key that is not a foreign key to the carrying parent.
- `EntityMetadataBuilder.Parts.cs:115-122`: an entity without a parameterless constructor.
- Fingerprint sensitivity to a computed column's SQL or `IsStored` (deviation 4's own addition)

  Failure scenario: any of these checks could be deleted or inverted and the suite would stay

  unreachable because the conventions or EF refuse the model first, say so in a comment and

### Responses
- R1-1: fixed in the "PC-021: review 1 fixes" commit, per the orchestrator's ruling. `ResetServerOwned`
  restores every server-owned property except the key, which the id allocator owns, so a temporary
  `Id < 0` survives until assignment rewrites it and the references to it. The XML doc says so, and
  the test now asserts that `Id = -5` survives the reset. Recorded as a deviation from 0012 §3.1
  ("every `ServerOwned` property").
- R1-2: fixed in the "PC-021: review 1 fixes" commit. An entity with no table name (a `ToView`,
  `ToSqlQuery` or `ToFunction` mapping) reports "is not mapped to a table" and gets no metadata, and
  the other problems are still reported. New case: `Viewed` + `ViewedConfiguration`.
- R1-3: fixed in the "PC-021: review 1 fixes" commit. New failing models:
  - a derived type without a replaced default (`Customer` + `VipCustomer`);
  - a leaf registered for two defaults;
  - one leaf per table, reachable through table splitting (`SplitOwner` + a sibling on its table);
  - no parameterless constructor (`Constructed`).
  New fingerprint variants:
  - the computed column's SQL, and its `stored` flag;
  - an added sequence.
  Two branches were unreachable, so I removed them and explained why in a comment in `PairChildren`:
  - "a collection whose child maps no leaf": the model definition maps every child a collection
    carries;
  - "a parent key that is not a foreign key to the carrying parent": the child convention always adds
    that foreign key, and a configuration's own foreign key over the column only adds a second one.
  A child that has no metadata is now skipped silently, because its own problem was already reported.
