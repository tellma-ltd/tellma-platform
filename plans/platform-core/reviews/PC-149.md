# PC-149: Dispatch handler

## Implementer notes

### What was built, and where

- **Dispatch** (`src/core/Tellma.Core/Outbox/OutgoingEmailHandler.cs`, which resolves `IEmailSender`
  on each claim): the §5 claim in six steps, each a section of `RunAsync`.
  1. Triage of the rows as the claim loaded them: a settled row succeeds unsent; a `Sending` row is
     interrupted (`Failed`, `Email.Interrupted`, logged `OutboxSendInterrupted`); a pending row whose
     job is `CancelRequested` is left unmarked.
  2. Attachments: one read round trip joined to `core.Blobs`, then `IBlobStore.OpenReadAsync` per
     object; a missing object rejects its row unsent with `Email.AttachmentMissing`.
  3. Pre-mark: one maintenance round trip (`TransactionMode.None`) that moves the pending rows to
     `Sending`, counts the attempt and returns the rows now `Sending`, so a re-run returns the same
     rows (`OutboxStatements.PreMark`).
  4. Send: one `IEmailSender.SendAsync` with `CancellationToken.None`, each message correlated as
     `("outbox", rowId, tenantId)`; a throw is a transient failure of every message.
  5. Settle: one maintenance round trip over `OutgoingEmailOutcomeList`, matched on
     `State = 'Sending'`, committed before any item is marked; `Verdict` maps every
     `EmailSendOutcome` (`Sent`, `Sandboxed`, `Rejected`, transient with retry or exhaustion at
     `MaxAttempts`).
  6. Notify: one `core.email.failed` notice (`NotifyOnSuccess`, inbox-only, `DedupKey` with
     `Replace`) to the tenant's administrators when any row settled rejected or failed.
- **Text helpers** (`Outbox/OutgoingEmailText.cs`): the mailbox, subject and HTML helpers the
  email channel already used, shared with the welcome email.
- **Telemetry** (`Tellma.Core.Abstractions/Email/OutboxTelemetryNames.cs`,
  `Outbox/OutboxMetrics.cs`, `Outbox/OutboxLog.cs`): `tellma.outbox.enqueued` (tag `source`, from
  `EmailOutbox.EnqueueAsync`, one per row — the D-164 carry), `tellma.outbox.settled` (tag
  `state`) and `tellma.outbox.latency` (seconds, database clock, clamped at 0); the log events.
- **Startup check** (`Outbox/OutboxSenderCheck.cs`, `CoreCheckNames.OutboxSender`): a host whose
  job worker runs with no `IEmailSender` registered.
- **Alert queries** (`infra/monitoring/outbox/`): interrupted sends, failure rate and latency p95,
  checked back against the instruments by `OutboxAlertQueryTests`.
- **Welcome email** (`Users/UserService.Welcome.cs`, called from `UserService.Invite.cs` after the
  write-back is composed — the D-164/D-159 carry): every answered user with a status whose loaded
  row holds no account or the one answered is enqueued a welcome email through `IEmailOutbox` with
  the action's frame, in their own negotiated language and content slot
  (`Email_UserAdded_Subject/_Text/_Html` in `ServerStrings(.ar).resx`).
- **Job entity load** (`Jobs/JobClaim.cs`, `Data/Batches/DataBatch.Queries.cs`): see deviation 1.
- **Resources**: `Notification_core_email_failed` and `NotificationType_core_email_failed` in
  `Strings(.ar).resx`; the three welcome texts in `ServerStrings(.ar).resx`.
- **README**: `src/core/Tellma.Core/README.md` outbox and invite sections.

### Deviations

1. `JobEntityLoad` selected only the job key, so every claimed row reached its handler with empty
   columns (0020 §5.1 hands the handler the owning rows). It now selects every declared property
   through the new `DataBatch.DeclaredSelect`. The regression test
   `JobRunTests.A_handler_receives_each_owning_row_with_every_column_as_stored` fails on a
   defaulted row. This is the D-170 carry. `EntityQuery.AllProperties`' doc promised every root
   property, but the property adds only the root's JSON columns (collections do get every
   column). Its doc is corrected rather than its behavior: `DetailsComposition` and
   `CacheableEntityType` pass a narrowed root select with `AllProperties`, and widening the root
   would override them. Every other caller already names the declared properties. The dispatch
   tests did catch the bug: nine of them failed on rows with an empty `To`, `Subject` and `State`,
   which is how it was found here.
2. Extra warning logs the spec does not list: `OutboxSendFailed` (the sender threw; the exception
   type only), `OutboxNoticeRecipientsFailed` (the administrator lookup failed; only the notice is
   lost) and `WelcomeEmailSkipped`.
3. A stored row whose addresses no longer parse is rejected unsent with `Email.InvalidMessage`.
4. `EmailOutbox.EnqueueAsync` refuses a `Source` other than `api` or `notification` before anything
   is staged, so the `source` tag stays a closed set.
5. A transient retry records the job error `Email.TransientFailure`.
6. The administrators are looked up only when a notice is due, after the settle committed.
7. The `outbox.sender` check is `RequiresInfrastructure = true`.
8. The integration tests simulate a cancel by setting the job's status in SQL; the cancel verb is
   0022's later checkpoint.
9. The Acme provision's welcome pin is not possible yet: the provision's invite is not built.
10. The email channel's text helpers moved into `OutgoingEmailText`.
11. Three of the four outbox alert queries were pulled forward; the unmatched-events query stays
    with the delivery-events checkpoint.
12. The invite budget tests warm the outbox's id buffers first (budgets count warm caches; a cold
    buffer adds one round trip to the first welcome per instance).
13. The interrupted rows settle in the step-5 round trip rather than in one of their own.
14. A claim whose host is stopping or whose lease was lost throws `OperationCanceledException`
    before the pre-mark, every row still pending.
15. A sender that answers another number of results than messages fails the claim with the rows
    still `Sending`, so the next claim fails them rather than send any twice.
16. The invite's recompose test now uses a refused answer, which enlists no welcome; see the first
    open risk.
17. The handler resolves `IEmailSender` from the job scope on each claim instead of taking it in its
    constructor. Every host composes the handler, so a constructor dependency failed DI validation on
    every host with no email pipeline, including web-only hosts and test compositions. A claim on
    such a host throws before anything is written. `outbox.sender` reports a worker that would run
    these jobs without a sender.
18. The startup-gate tests now expect `outbox.sender`, because their compositions run the worker
    with no sender. The notification-registry tests expect `core.email.failed` in CoreFeature's
    registration order.

### Open risks

- **0018 §3.3 vs 0015 §5.1 (for the orchestrator).** 0018 says a recompose of the invite's persist
  replays "the emails". But the outbox's enlisted save validates (core's blob-reference validator
  sits on every stack with a blob column), so when the caller's permission set moves while the
  identity server answers, `EnsureGroupsJudgedUnder` fails the re-entry closed: the request fails
  `StaleContextException`, nothing commits, and the identity server has already acted. This is
  pinned by `A_permission_move_under_an_enlisted_welcome_fails_the_invite_closed_and_commits_nothing`.
  With a cold id buffer the enlisted save's validators have not started at the re-entry, so the same
  scenario replays and commits. The outcome therefore depends on cache warmth.
- Settled metrics are lost on a re-run of a claim that settled but failed before marking its jobs.
- The welcome email does not show dates, so the negotiated calendar is not visible in it.
- PC-147 also touches `CoreFeature`.

### What reviewers should examine hardest

- `OutgoingEmailHandler.RunAsync`'s ordering. Nothing should be marked before the settle commits,
  and the pre-mark should be idempotent on a re-run. Check the `State = 'Sending'` match in
  `OutboxStatements`.
- `Verdict`'s attempts arithmetic at `MaxAttempts` and on retries.
- `DataBatch.DeclaredSelect`: every handler of a job entity now receives every column.
- `UserService.Welcome`: who is welcomed (answered, with a status, the loaded row's subject null or
  equal) and the language and content-slot choice per user (`LocalizedText.In` is 1-based).
