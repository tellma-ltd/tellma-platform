# PC-111: Page-context registry, page actions and dispatcher (primary)

## Implementer notes

### What was built, and where

All client-side; no C# changes. Paths are under `client/projects/core/` unless noted.

- **Types (spec 0026 §9.1, §9.4)**, `tellma-core/src/context/`:
  - `tm-page-context.ts`: `TmPageContext`, `TmVisibleData` with the named `TmVisibleColumn` and
    `TmVisibleRow`, `TmContextError`, `TmFormContext`, `TmFormField`. `TmPageKind` was already
    there.
  - `tm-page-action.ts`: `TmPageAction`, `TmPageActionInput`, `TmActionResult`,
    `TmActionOrigin`. `confirm` reuses the entity declarations' `TmActionConfirmation`.
  - `tm-help-articles.ts`: `TM_HELP_ARTICLES`, declared and provided by nothing (§9.8).
- **Registry and dispatcher (§9.2, §9.5)**, `tm-page-registry.ts` (internal):
  - `TmPageScope`, the injectable `provideTmPageScope` provides. It holds the scope's host
    element and drops every registration of the scope when the scope's injector ends.
  - `TmPageRegistry` (root) holds every live context and every action registered through
    `TmPageActions`. It publishes each context as a copy whose `actions` is a computed merge.
  - The merge is the context's own actions, then the own actions of the routed contexts it
    replaced in its scope (newest first), then the scope's registered actions. Actions
    registered outside any scope join the current routed context. The list is sorted stably:
    `primary` first, then `order` (default 100), then registration order.
  - `current` is the newest live routed context, `overlays` the dialog contexts in
    registration order, `top` the last overlay or else `current`.
  - The dispatcher runs steps 1-6. After a confirmation (fix1), the id is looked up again: the
    context that offered it must still be the first to offer it, and that context's current
    action is the one that runs. Step 1 searches the top dialog, the dialogs beneath, then the
    routed page. Step 2 refuses a disabled action with its `disabledReason` as `message`, and
    announces the reason politely (cdk `LiveAnnouncer`) for `user` and `shortcut`. Step 3
    refuses a busy id. Step 4 asks `TmConfirm` in its danger form for a destructive action,
    whatever the origin. Step 5 runs it with the id in `running`, and turns a throw into
    `failed`. Step 6 emits `tm.action.invoked` `{action, origin, outcome, ms}`, sampled.
  - An effect keeps the top context's shortcuts registered in `TmShortcuts` while it is on top.
    A dialog's shortcuts are registered against its scope's host element, so they run only
    while that dialog is the top modal.
  - `TmConfirm` loads through `import('@tellma/core-ui/confirm')` at the first question.
    `TmLocalization` is read lazily, so the registry needs no Transloco to exist.
- **Public faces**: `tm-page-contexts.ts` (`TmPageContexts`: `current`, `overlays`, `top`,
  `register`) and `tm-page-actions.ts` (`TmPageActions`: `running`, `register`, `invoke`). Both
  are root services, and `provideTmPageScope()` also provides an instance of each per scope.
  The scope is resolved when the instance is injected, not where `register` is called.
- **`provideTmPageScope`** (`tm-page-scope.ts`) now returns `[TmPageScope, TmPageContexts,
  TmPageActions]`. The route host already provided it.
- **Snapshots (§9.6)**, `page-snapshot/src/tm-page-snapshot.ts`, the lazy entry point
  `@tellma/core/page-snapshot`, which was in the primary until the move after Review 1: `tmSerializePageContext` and
  `TmPageContextSnapshot` with the named sub-types `TmVisibleSnapshot`, `TmFormSnapshot`,
  `TmFieldSnapshot`, `TmErrorSnapshot` and `TmActionSnapshot`.
  - Without page data, the snapshot drops `visible.rows`, form `value`s and error `message`s.
  - It masks every string, at any depth, in `state.query.{q, filter, columnFilters, custom}`
    and `state.parameters`.
  - It replaces a `details` title with `TmEntities.label(entity)`, or with `…` when there is no
    entity.
- **Route host (§2 hatches 2 and 3; spec 0024)**, `src/routes/`:
  - `tm-routes.ts` stamps every page route with an internal `ɵtemplate`, such as `/:t`,
    `/:t/settings`, `/:t/:segment` or `/:t/<path>`.
  - `tm-route-host.ts` registers a default context on every page route (fix1: on declared pages
    before). Its kind comes from the route data. Its template is the route's, with the entity's
    segment in place. Its title is the one `TmTitleStrategy` gives that route. Its status is
    `loading` until the view paints, then `ready`, or `error` with one `client` error while the
    host renders an error view. It has no state and no actions. A reused route that shows
    another entity registers it anew.
  - A page component registers its own context through the injected `TmPageContexts`. That
    context replaces the host's and keeps the actions registered in the host's scope.
- **Shortcuts** (`src/nav/tm-shortcuts.ts`): the internal `ɵregisterInDialog(dialog, shortcut,
  destroyRef)` became `ɵregisterPage(shortcut, dialog | null)`, which returns the remover (or
  `null` when production refuses it). The registry owns the lifetime, so no `DestroyRef` is
  involved.
- **Harness**, `tellma-core-testing/src/tm-page-context-harness.ts`: `TmPageContextHarness`
  (root). It offers `current`/`overlays`/`top` snapshots (page data by default), `actions()`,
  `action(id)`, `invoke(id, args = {}, origin = 'user')` and `running()`.
- **Carries:**
  - D-216: `TM_ROUTED_PAGE` and `TmRoutedPage` are removed. `TmRecents` reads
    `TmPageContexts.current()`, with the URL from the router and a navigation counter so that
    a new path under the same context counts. A context replaced on the same path is one visit,
    and the title is read when the 2 s end.
  - D-218: the core entry-point table now lists `./memory` for `./search`, `./details`,
    `./admin`, `./reports` and `./report-studio`, and `./recents` for `./dashboards`. A test
    pins these lists and checks that no eager entry point reaches either.
- **Docs**: the `tellma-core` README (route host, shortcuts, a new "Page context and page
  actions" section, seams and recents) and the `tellma-core-testing` README.

### Deviations

1. **Scope-bound service instances.** The spec shows root `TmPageContexts`/`TmPageActions`
   "resolving" the scope. Here `provideTmPageScope()` provides scoped instances, and the scope
   is fixed at injection. This is the only way a root service can know its caller's node
   injector without an injector argument.
2. **`tmSerializePageContext` options gain `injector?`.** The details-title mask needs
   `TmEntities`, so outside an injection context (the harness, the future dump) the caller
   passes an injector.
3. **Confirming counts as busy.** While a destructive action's question is open, a second
   invocation is refused `busy`, though the id is not yet in `running`. After the answer, the
   action is looked up again: an action gone meanwhile is `not-found`, and one disabled
   meanwhile is refused with its reason.
4. **Production fallback for a destructive action without `confirm`.** Development throws, at
   registration through `TmPageActions` and at invocation for a context's own action.
   Production asks with the action's label as title and its description (else its label) as
   message. The confirm button always carries the action's label.
5. **A non-`TmApiError` throw is reported** through `TmTelemetry.error(error, {action})`, beside
   the `failed` result. An API error is the action's to present.
6. **No usage event for `not-found`.** Step 6 reports only found actions, so a stale assistant
   id does not count as usage.
7. **A shortcut on a refused action still consumes the key**, since its `run` cannot report
   refusal to `TmShortcuts`. The refusal is announced as in step 2.
8. **The route host registers a default context on every page route, not only on `tmPage`
   routes** (fix1, D-244). Spec 0026 §9.2 says "on `tmPage` routes".
   - The kind comes from the route data, and the title from `TmTitleStrategy`.
   - The template is the route's, with the entity's segment in place, such as `/:t/centers` or
     `/:t/centers/:id`. The drill-through list keeps `/:t/list/:segment`.
   - The search, details, report, dashboard and admin hosts replace it under the same-scope
     rule when they land. Until then, recents count those pages as PC-107 did.
9. **Named sub-types** (`TmVisibleColumn`, `TmVisibleRow`, the snapshot member types) in place
   of the spec's inline object types, and reuse of `TmActionConfirmation`.
10. **Internal `TmShortcuts.ɵregisterInDialog` replaced** by `ɵregisterPage` (the signature
    changed and it returns a remover).

### Open risks

- **The default context's title on a reused route**: when a reused route shows another entity,
  the host registers a new default context. It is titled from that route's snapshot through
  `TmTitleStrategy.ɵtitleOf`, so it never shows the previous page's title.
- **The overlay shortcut element** is the scope's host element (`ElementRef` in the scope
  provider). A context-bearing dialog must provide `provideTmPageScope()` on a component
  rendered inside the modal's host, which spec 0023's `TmModal` content components are. A
  scope provided on an element outside the modal would never run its shortcuts.
- **The shortcut effect throws in development** when a top context's own action has a
  shortcut and required params, or when `TmShortcuts` refuses its keys. The error goes to the
  `ErrorHandler`, not to the publisher's call site, because a context's actions are a signal
  read later.

### What reviewers should examine hardest

- `#merged` in `tm-page-registry.ts`: replacement only within a scope and only for routed
  contexts. Root actions join only the current entry. Check what happens when a replaced
  context comes back after its replacement ends.
- The dispatcher's re-check after the confirmation, and the `#confirming` set's cleanup on
  every path.
- The shortcut effect's diffing: a refused registration keeps a noop placeholder so that it is
  not retried on every list change, and a top change resets the whole map.
- The route host's `#painted`/`#status` currency across superseded loads.
- `TmRecents`' new trigger: the context, the navigation counter and the URL. Also its timer's
  re-check of the current context's kind when the 2 s end.

### Findings

**R1-1 (major): the re-check after a confirmation compares object identity, so it can drop a confirmed destructive action that still exists.**
- Where: `client/projects/core/tellma-core/src/context/tm-page-registry.ts:372`,
  `if (this.#find(id) !== action) return NOT_FOUND;`.
- What fails: §9.1 lets a publisher's `actions` be any `Signal<readonly TmPageAction[]>`. A
  framework that builds its actions in a `computed` creates new objects each time the computed
  reruns. For example, a details page derives `details.delete` from `mode()`, `status()` or the
  loaded record. Suppose a re-read, a status flip, or any other dependency changes while the
  question is open. The user clicks Delete, so `#find` returns an equal action that is a new
  object, and the dispatcher answers `refused: not-found`. Nothing runs, and nothing is announced.
- Why it matters: this check goes beyond §9.5. Nothing in `TmPageContext.actions`' TSDoc says that
  action objects must stay stable. No test covers an action that is recreated while its question
  is open.
- Fix:
  - At step 1, remember the context (the published view) in which the action was found.
  - After the answer, look the id up again in that same context, and require the context to be
    live and still reached by `#find`'s order.
  - Gate and run that context's current action with the id.

  A dialog that closed then still answers `not-found`, and a same-id action on the page beneath
  is never run in its place. A recreated action on the same context runs.
- Test to add: a `computed` action list that recomputes while the question is open. It must end
  `done`, and the closed-dialog case must still end `not-found`.

**R1-2 (major): recents no longer count search, report, settings, dashboard or access pages.**
- Where: `client/projects/core/tellma-core/src/routes/tm-route-host.ts:315`. The default context
  registers only when `data.ɵtemplate` is set, which `tm-routes.ts` sets only for `tmPage`
  routes.
- What PC-107 tested: before this commit, `TmRecents` counted every routed page by its route data.
  Its whole-app test, "reads the deepest route: its kind, the list mark and the displayed title",
  checked that `/17/centers` (search) counted and `/17/list/centers` did not.
- What this commit does: `recents/src/tm-recents.spec.ts:320` replaces that test with one that
  covers only a feature page. In the real app, a visit to `/17/centers`, `/17/reports/42` or
  `/17/settings/general` now stores nothing in `nav.recent`. The registered kinds appear in the
  recents logic only through the unit rig's hand-registered contexts.
- Why it matters: D-216 asked to *replace* the seam with `TmPageContexts`, not to narrow what
  counts. Deviation 8 and the open risk name the gap, but no checkpoint is assigned to close it.
  The launcher (PC-115) may land before the search, details, reports and admin frameworks do.
- Fix: register the route host's default context on every page route, not only on `tmPage` ones.
  - Kind: from the route data.
  - Template: the route's path with the matched segment in place, such as `/:t/centers` or
    `/:t/list/:segment`.
  - Title: the one `TmTitleStrategy` already resolves for that route.
  - Status and errors: as now.

  Each framework host, when it lands, registers its own context in the same scope, and §9.2's
  replacement rule makes it current. So recents keep PC-107's behaviour, and nothing in recents
  needs a fallback. This deviates from §9.2's "on `tmPage` routes" only until the framework hosts
  land, and should be recorded as such.
- Alternative: keep deviation 8 and record a carry on each framework checkpoint.
- Either way, restore a whole-app test that a search route counts and the list route does not.

**R1-3 (minor): `tmSerializePageContext` calls `inject(Injector)` even when it needs no injector.**
- Where: `client/projects/core/tellma-core/src/context/tm-page-snapshot.ts:184`,
  `options.injector ?? inject(Injector)`.
- What fails: the call runs before it is known whether a label is needed. A caller outside an
  injection context that passes no injector gets NG0203, even though only a `details` context
  without page data reads `TmEntities`. That caller might be the dump building in a promise
  callback, or an assistant adapter with `includeData: true`. This makes the deviation-2 option
  mandatory for every out-of-context caller, not only for the masked details title.
- Fix: resolve the injector inside the masked-details branch only, as
  `(options.injector ?? inject(Injector)).get(TmEntities)`.
- Test to add: serialize a `custom` context outside an injection context with no injector.

**R1-4 (minor): the snapshot is the one primary addition with no first-frame caller.**
- Where: `client/projects/core/tellma-core/src/context/tm-page-snapshot.ts`, and the "." raise in
  `client/projects/core/tellma-core/package.json`.
- The cost: `tmSerializePageContext` and its masks cost about 0.5 KB of the 2.10 KB raise. I

- Also worth knowing: this checkpoint uses 2.10 KB of 0026's 6 KB primary share. That leaves about
  3.9 KB for PC-112 and PC-113: the telemetry pipeline, `TmErrorHandler`, redaction,
  `TmRequestLog` and `TmAppVersion`.

**R1-5 (minor): the claimed real-dialog test does not exist, so the dispatcher's real confirmation path is untested.**
- Where: `client/projects/core/tellma-core/src/context/tm-page-actions.spec.ts:23-26`. The header

- Fix: add the whole-app test the header describes. Under `tmAppRig()`, invoke a registered
