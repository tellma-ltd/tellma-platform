# PC-F109: Identity passkey E2E tests probe instead of wait-then-click

## Implementer notes

### Root cause

The CI failure (45834807715, ubuntu identity-e2e, on pc/PC-122 f51b883f) is **not** in the sign-in
ceremony that PC-F16's follow-up named. The stack trace puts it in
`SyncedPasskeyTierTests.EnrollPasskeyAsync` (line 155), at the `WaitForPathAsync` after pressing
"Create a passkey". The aria snapshot shows the enrollment page with no error. So the press did
nothing.

It is the same class of race as PC-F16's R1-1, on a different button. "Create a passkey"
(`_PasskeyEnrollment.cshtml`) is `type="button"`. Its only behaviour is the click listener that
`register-passkey.page.js` attaches. That script, with `helpers.js` and `passkey.js`, is a
parser-blocking classic `<script>` at the end of the body. The enrollment page was reached by
clicking the "Add a passkey" link. Playwright returns from that click at the latest when the
navigation commits, and the next locator click only needs the button to be visible, stable, enabled
and hit-testable. All of that holds while the parser still waits on the script fetch. So on a slow
runner the press lands on a button with nothing behind it, and the test waits 30 s for a navigation
that never starts.

Reproduced locally and deterministically: holding back every `.js` response by 1.5 s through a
temporary `page.RouteAsync` (never committed) made the unchanged test fail at the same line, with
the same URL (`/Identity/Account/RegisterPasskey?returnUrl=%2FIdentity%2FManage%2FPasskeys`) and
the same symptom.

RegisterPasskey and Invitation) and `#passkey-button` ("Sign in with a passkey", on Login). Every
other button the suite presses is a native form submit. Press sites found:

| Site | Before | Racy? |

### What was built (all in `test/apps/Tellma.Identity.E2E`)

- `Infrastructure/PageNavigation.cs`: `WaitForScriptsAsync`. It waits for
  `document.readyState === 'complete'` in the document the browser is showing. `complete` holds
  only once every script has run, however it is loaded (parser-blocking, defer, async, module).
  It is evaluated in the live document, so it cannot be answered by a lifecycle event already
  reported for an earlier one (the README's `WaitForURLAsync` trap). Its precondition, documented:
  call it after an address wait for an address the previous page did not have.
- `Infrastructure/PasskeyCeremonies.cs`, now the single home of every passkey-button press:
  - `EnrollPasskeyAsync(page, prefix)`: "Add a passkey", wait for the RegisterPasskey URL (query
    allowed), `CreatePasskeyAsync`, wait for the list.
  - `CreatePasskeyAsync(page)`: `WaitForScriptsAsync`, then press.
  - `StartPasskeySignInAsync(page, url)`: PC-F16's probe, moved out of `RegisterThenSignInAsync`.
    Probe on the settled page, then `GotoAsync` with `Commit` (conditional) or `DOMContentLoaded`
    (explicit) and press. Returns the navigation's response, which StepUp needs.
- `StepUpTests`, `SyncedPasskeyTierTests`, `InvitationTests`: every press goes through the helpers.
  `DriveCeremonyAsync`, `DriveCeremonyUntilRefusedAsync`, and Synced's duplicate
  `EnrollPasskeyAsync`/`SignInWithEmailCodeAsync` are removed. Synced now waits for the refusal
  with the locator default (30 s). Before, that was 15 s, then a press, then another 15 s. StepUp
  waits 15 s for the callback (before: 5 s, then a press, then 10 s).
- Permanent guard: `Infrastructure/LateScripts.cs`, `HoldBackScriptsAsync`, holds every `.js`
  response back by 1 s. `PasskeyTests` (standalone) and `SyncedPasskeyTierTests` install it, so any
  flow that stops waiting for the scripts fails there on every run, not once in a while.
  `InProcPasskeyTests`, `StepUpTests` and `InvitationTests` keep the full pace, so both paces are
  covered. No extra sign-in codes are spent (the suite shares 10 per IP per hour).
- `README.md`: a rule bullet. Press the two passkey buttons only through `PasskeyCeremonies`, and
  never wait a fixed time and then press.

### Open risks / what reviewers should examine hardest

- `WaitForScriptsAsync` waits for `complete` (the `load` point), not `DOMContentLoaded`. That is
  stricter than needed, and a hung subresource would delay a press. No identity page has such a
  resource. `interactive` was rejected because it comes before deferred scripts run.
- `StartPasskeySignInAsync` in StepUp: in the explicit branch it presses before the caller asserts
  that the response was the login page. A wrong redirect would then show up as a locator timeout,
  not as the `stepUp=true` assertion. That branch is never taken in CI's Chromium.
- The 1 s hold-back assumes Chromium paints the already-parsed button while a body script is
  pending. The negative control confirms this locally on Windows. On Linux CI the original failure
  shows the same behaviour.
