# PC-181: Measures, partial columns and the C# measure evaluator

## Implementer notes

### What was built

Spec 0010 §F.14 (measures and partial columns) and §F.15 (the measure evaluator), wired into the
data layer's `Rows` (spec 0012 §11.3) and into `queryex/discover` steps 1-2 (spec 0029 §9). The
0029-f measure tests are deferred, as planned.

**Engine (`src/core/Tellma.Core.Queryex`).**

- `QuerySpec.Measures` and `QueryDiscoverySpec.Measures` hold a comma-separated list. It binds in
  Aggregate mode, each item at `Measures[<i>]` with spans into the whole text (`Binding/Binder.Measures.cs`,
  `BindingContext`, `DiagnosticLocation`, `DiagnosticSink`). Without `Aggregate` it is a caller
  error (`ParamName = "spec"`), and blank it is absent.
- The codes:
  - QX4011 (a stray path or no aggregation) replaces QX4007 in measures.
  - QX4010 carries `construct`: the operator or function name, or `text comparison`.
  - Both are in `DiagnosticCodes`.
- Partials live in `Measures/PartialColumns.cs` and `Pipeline/QueryClauses.cs`:
  - each is a sum, count, min or max; an average splits into a sum and a count of the same values;
  - they are deduplicated by bound structure across every measure;
  - a partial equal to a select item reuses its column;
  - the rest are appended after the select items as `QueryexColumn`s.
- `CompiledQuery.Measures` (`CompiledMeasures`: `Partials`, `Items`, `Prepare`) is null with no
  measures, and the statement bytes are then unchanged. Every existing golden is untouched.
- The cache key's L3 layer gains the measures text (`Caching/CacheKeys.cs`, and the probe mirror).
- The evaluator is in `Measures/`:
  - `MeasureTreeBuilder` builds an immutable IR from the lowered plan, mirroring the lowerer's folds.
  - `NumericShape` and `MeasureArithmetic` hold the backend's decimal and whole-number type rules and the arithmetic.
  - `MeasureRun` evaluates lazily: `and`/`or` stop at the deciding operand, and `if`/`coalesce` evaluate only their branch.
  - `MeasureOrders` gives the backend's ordering for min and max over every type.
  - `PartialTable` handles cells, `Add` from a reader-shaped buffer, and `Merge`.
  - `MeasureEvaluator` handles `Evaluate` and `ResultTypes`.
  - `MeasureValue` and `QueryexEvaluationException` (QX6001, QX6002) are public.

**Data layer and API (`src/core/Tellma.Core`).**

- `QueryStatementKey` keys on `Measures`, so a measured and a plain spec never share a statement.
- `Rows` reads the partial columns like any other column. Their decimal precision and scale come
  from `DbColumn`, which is what `MeasureContext.DecimalTypes` takes.
- A grouped capped count compiles without the measures.
- `DiscoverShape` now admits measures with `Aggregate` (`400` without it). `QueryexService`
  passes them to both the discovery and the compile, and `QueryWireDiagnostics` already mapped
  `Measures[<i>]` to clause `measures`.
- New resx keys `Queryex_QX4010` (`{construct}`) and `Queryex_QX4011`, in en and ar.

**Tools and docs.**

- `eng/queryex-inspection` gains a measures input and a pane listing the measures and their partials.
- The READMEs of Queryex, Core, the Queryex testing library, the Queryex integration tests and the
  inspection tool are updated.
- ARCHITECTURE.md now names the measure evaluator where it describes Queryex.

### Tests

- **Unit (`Tellma.Core.Queryex.Tests`, 1548 pass).**
  - Six `measure-*` goldens plus a refusal corpus (QX4011 at several sites; QX4010 for `%`, `||`,
    text comparison, cast, the calendar parts, guid, and a nested construct).
  - `DiscoveryTests`: measure sites, and the caller errors.

- **Differential against SQL Server (`MeasureDifferentialTests`, `MeasureFixture`).**

    every optional column null.
  - 59 hand-written measures, and 500 generated from fixed seed 20 261 121 on every PR (not nightly).
  - Each must hold three identities: the leaf (evaluated over that leaf's partials), each branch
    (merged leaves against the server's branch grouping) and the grand total.
  - Each identity compares value, precision and scale. An error has to be the code mapped from
    the server's (8134 → QX6001, 8115 → QX6002).
  - Locally I also ran seeds 1–6 with 2000 measures each, and they pass.
- **Core.**
  - `QueryexServiceTests` gains a test that measures are checked at their items in clause

  - `DataQueryTests` gains a test that a grouped page carries its partials after its own columns,
    typed and valued like the same aggregations spelled out, and counts the same groups.

### Deviations

1. A guid or geography value outside an aggregation is QX4010 with construct `guid`/`geography`.
   The spec's subset table does not list these types, and the evaluator has no arithmetic for them.
2. The plan's store types now follow the backend where they did not before:
   - negating a `tinyint` gives `smallint`;
   - `abs`, `round`, `floor` and `ceiling` of `tinyint`/`smallint` give `int`;
   - `floor` and `ceiling` of `decimal(p,s)` give `decimal(p,0)`.

   The evaluator reads these types, and no emitted byte changes.
3. A whole-number measure reports its `ResultTypes` entry as `(w,0)`, the width's digits at scale 0.
4. The evaluation codes are public consts on `QueryexEvaluationException`, not entries in
   `DiagnosticCodes`. The spec says they are never diagnostics, and this also keeps them out of the
   resx coverage test.
5. A `MeasureValue` accessor throws on a type mismatch or on null rather than returning a default.
6. Membership (`in`) evaluates every element, as the backend does, so an element that fails fails
   the test.
7. The measure IR mirrors the lowerer's folds, so a measure folds exactly as its SQL would.
8. Sums, products and quotients use exact `BigInteger` mantissa arithmetic with one rounding (or
   truncation, for division). `SqlDecimal`'s operators truncate a sum whose scale shrinks to fit 38
   digits, where the backend rounds it. For example, `decimal(38,0)` 1002 + 2.5 is 1005 on the
   server and 1004 through `SqlDecimal`; the generated differential found this.
9. **Emitter fix (spec 0008 emission).** A `count()` that reads no column, inside an equality's
   or a membership's `INTERSECT` subquery, now carries the root-key anchor
   (`COUNT_BIG([T].[key])`), as it already did in scalar subqueries. Before, `COUNT_BIG(*)` there
   counted the subquery's single row, so `if(count() > 1, count(), null) = 2` was wrong. Seed 1 of
   the generator found it. The new corpus case `emit-count-in-set-test` pins it, and it passes the
   corpus differential.
10. A grouped capped count compiles without `Measures`. Partials add columns and never groups, so
    compiling them into the count would only cost work.

### Open risks and decisions for the orchestrator

- **Pre-existing, not fixed:** an Aggregate query whose every aggregation folds away (e.g. select
  `count() is null` alone, which folds to a constant) emits no `GROUP BY` and returns one row per
  fact row rather than one. The measure differential's grand-total statement avoids it by also
  selecting `count()`.
- Deviation 9 changes emitted SQL for existing queries of that shape. The change only corrects
  wrong results, but it is a spec 0008 emission change.
- LocalDB here is SQL Server 2019, which has no `LEAST`. The 16 calendar cases of the
  differential suites that emit it fail locally and are unrelated to this change; CI's server runs
  them. Every other differential case, the new emit case included, passes locally.

### What reviewers should examine hardest

- `Measures/MeasureArithmetic.cs` and `NumericShape.cs`: precision and scale per operator, the
  38-digit collapse (minimum scale 6 for products and quotients; addition keeps the integer digits
  first), rounding against truncation, whole-number range checks, and `Fitted`.
- `Measures/MeasureTreeBuilder.cs` against `Lowering/`: every fold the lowerer makes has to be
  mirrored, or the evaluator and the SQL will disagree on a constant-folded measure.
- `Pipeline/QueryClauses.cs` partial deduplication and reuse: structural equality across
  measures, an average's sum and count against an explicit sum and count, and conditional
  aggregates.
- `PartialTable.Merge` over sparse cells (a null sum against a count of zero) and min/max of each
  type, `MeasureOrders` in particular for text: the least and greatest text are taken
  invariant-culture ignoring case with an ordinal tie-break, a stand-in for the column's
  collation, which the evaluator does not model. The fixture's labels agree with the server's
  collation, but a host's own collation may not.
- `PlanEmitter` `_subqueries` around `WriteSetComparison` and `WriteSetMembership`.

## Review 1

### Findings

Scope: commit 19eb6762 only. Runs: `Tellma.Core.Queryex.Tests` filtered to
`Measures|DiscoveryTests|Corpus` (449 pass); `MeasureDifferentialTests` on LocalDB 2019 (60 pass:
59 hand-written plus the 500-measure generated case, 34 s). The pc/PC-181 CI run (44940576487)
was skipped, so there is no CI evidence yet. Probes were a scratch console against the built
assemblies, plus direct `sqlcmd` queries on LocalDB.

**R1-1 (major): measure folds and `CompiledMeasure.Nullity` use group-level nullity, which is wrong for an empty cell.**
- Where: `src/core/Tellma.Core.Queryex/Pipeline/QueryClauses.cs:431` binds the measures under
  `Context(...)`, which carries `HasGroupingKeys = _hasGroupingKeys`. The resulting nullity drives
  the folds in `Measures/MeasureTreeBuilder.cs:160-170` (`is null`), `:214-242` (comparison
  against an always-absent side), `:247-297` (membership) and `:174`. It also drives the reported
  `CompiledMeasure.Nullity` at `QueryClauses.cs:526`.
- What is wrong: in a grouped statement every group has a row, so `sum(Amount)` over a NOT NULL
  column is NotNull. A cell from `PartialTable.AddCell` that nothing is merged into is empty, and
  there the sums and extremes are null (§F.15 Accumulation and Nulls). spec 0033 §8.4 evaluates
  exactly such a cell: a summary's totals row over an empty result (Skip 0, every row returned).
- Probe (`Select = "Leaf"`), evaluating one empty cell:
  - `sum(Amount)` reports `Items[0].Nullity = NotNull` but evaluates to null.
  - `sum(Amount) is null` evaluates to false.
  - `if(sum(Amount) is null, 0, 1)` evaluates to 1.
  - `max(Day) is null` evaluates to false.
- SQL's grand total with no `GROUP BY` over zero rows gives true, 0 and true for these. The same
  measures compiled with `Select = "count()"` report `Nullable` and evaluate `is null` as true. So
  identity 3 (grand total) fails on an empty input, and the answer depends on the statement's
  grouping.
- Why it is worse here: under deviation 5 a host that trusts `Nullity = NotNull` and reads
  `.Number` gets an `InvalidOperationException`.
- The differential cannot catch this, because its fixture always has rows.
- Fix:
  - Build the measure trees' nullity, and `CompiledMeasure.Nullity`, as a grand total does
    (`HasGroupingKeys = false`), since a measure is evaluated over combined cells that may be empty.
  - Keep the statement's own nullity for the partial columns (`QueryClauses.cs:513`).
  - Tests: an empty-cell unit test (`sum(x) is null` is true; `Nullity` is Nullable), and a
    grand-total differential case over a filter that matches no row.

**R1-2 (major): `max(length(Label))` cannot be loaded from the reader, and its arithmetic is typed as `bigint`.**
- Where: `src/core/Tellma.Core.Queryex/Functions/FunctionLibrary.cs:647` types `LEN(...)` as
  `QxBigInt`. This checkpoint now types whole partials from the plan:
  - `Pipeline/QueryClauses.cs:578` (`WidthOf(value.StoreType.Family)`) chooses
    `PartialStorage.Whole`/`BigInt`;
  - `Measures/MeasureRun.cs:191` then requires a `long[]` buffer.
- What SQL Server returns: `LEN` of a non-`max` text is `int`. Checked on LocalDB:
  `SQL_VARIANT_PROPERTY(LEN(@nvarchar50), 'BaseType')` is `int`, and only `nvarchar(max)` gives
  `bigint`.
- Failure: spec 0012 §11.3's reader hands the partial over as `int[]`. In the probe,
  `PartialTable.Add` with an `int[]` throws: "The partial is read from an array of Int64, not of
  Int32." So a measure the engine accepts cannot be evaluated over a `Rows` page.
- It is also wrong once loaded. `ResultTypes` is `(19,0)` where SQL gives `int (10,0)`. And
  `max(length(Label)) * max(length(Label)) * 50000` overflows (8115) in SQL but not in C#.
- Fix:
  - Type `length` as `QxInt`, and `QxBigInt` only when the argument's store type is a `(max)` text,
    following the argument.
  - Add `max(length(Label))` to the hand-written measures and to `MeasureGenerator.NumericPartials`.
    The differential's reader-shaped `Load` would then have failed.
  - Have the differential assert that each whole partial's plan width matches the reader's
    `DataTypeName`, so any other plan-versus-server type gap surfaces generically.

**R1-3 (minor): the `Rows` → evaluator seam is untested.**
- Where: `test/core/Tellma.Core.IntegrationTests/Data/DataQueryTests.cs` (new case at about line 122).
- What is missing: the test checks the partial columns' types and values against a spelled-out
  select. It never prepares an evaluator from `QueryColumn.Precision`/`Scale` and never `Add`s
  from `QueryRowSet.GetBuffer`. That seam is what the planner note wires for spec 0033, and R1-2
  is exactly the kind of mismatch it would have caught.
- Fix: in the same test, `Prepare` from `rows.Columns` and load every partial from
  `rows.GetBuffer` (skipping `IsNull` rows). Evaluate each measure against the oracle row,
  including a whole-typed `min` and a `length()` partial.

**R1-4 (minor, a fix item; not this checkpoint's to fix): a grand total whose aggregations all fold away answers row by row.** This is the implementer's item 1.
- Spec violation: yes.
  - spec 0008 §2.1 says the one degenerate shape is a select list "with neither an aggregation
    nor a grouping key".
  - With an aggregation present, the same shape is a grand total, and §11.3/§13 say a grand
    total has no keys and gives one row.
  - `Select = "count() is null"` is written with an aggregation, but lowering folds it to
    `CASE WHEN (1 = 0) ...`. The plan then has no aggregate and no `GROUP BY`
    (`Emit/StatementEmitter.cs:169-180`), so it returns one row per fact row.
- Origin: pre-existing in 0008 lowering and emission, and not introduced here.
- Exposure through measures: only when the select list has no key and no surviving aggregate. In
  the probe, `Select = "count() is null"` with `Measures = "if(false, sum(Amount), 1)"` appends no
  partial and emits per-row SQL. The differential works around it at
  `MeasureDifferentialTests.cs:164`.
- Fix: as a fix item, emit `GROUP BY ()` when `Aggregate` is set, no key is derived, and no
  aggregate survives lowering. On LocalDB, `SELECT CASE WHEN (1 = 0) THEN 1 ELSE 0 END FROM (3
  rows) GROUP BY ()` returns exactly one row, and every other statement's bytes stay unchanged.
  Add a corpus case.

**R1-5 (minor): `Round` overflows `Int128` when 38 digits are dropped.**
- Where: `Measures/MeasureArithmetic.cs:330`.
- What is wrong: when `dropped == 38` (`unit = 10^38`), `Int128.Abs(remainder) * 2` can reach
  about 2·10^38. That is past `Int128.MaxValue` (about 1.7·10^38), so it wraps, and a merged total
  of 8.5·10^37 or more is never rounded up.
- Failure: SQL raises 8115 for `ROUND` of such a total at `-38` places (`decimal(38,0)`), and the
  evaluator returns 0. The comment at `:335` ("the product fits") is right only for the product.
  Practically reachable only with absurd digit counts.
- Fix: compare `Int128.Abs(remainder) >= unit - Int128.Abs(remainder)`, or work in `UInt128`.

**R1-6 (minor, test adequacy): spec 0010 §F.14 asks for QX4010 "for each refused row of §F.15's table, with span and construct"; two rows have no corpus case.**
- Where: `test/shared/Tellma.Queryex.Testing/Corpus/QueryCorpus.Measures.cs:98-116`.
- Missing: a HierarchyId comparison or membership (`if(max(Node) = min(Node), 1, 0)`, which
  `Binder.Measures.cs:158` refuses as `text comparison`), and `local` (`local(max(PostedOn))`).
- Fix: add both refusal cases.

**On the implementer's items and deviations.**
- (1) See R1-4: a spec 0008 violation that predates this checkpoint, so it becomes a fix item.
- (2) Deviation 9 is right. On LocalDB, over groups of 3 rows and 1 row:
  - the old form `EXISTS (SELECT CASE WHEN COUNT_BIG(*) > 1 THEN COUNT_BIG(*) END INTERSECT
    SELECT 3)` gave 0 for the 3-row group, because `COUNT_BIG(*)` binds to the FROM-less
    subquery and counts its one row;
  - the anchored `COUNT_BIG(T.K)` is an outer reference, aggregates at the outer query, and gives
    1.

  The anchor is the root key, which is never null, so it counts every row. `emit-count-in-set-test`
  pins the new bytes. No existing golden changed.
- (3) Agreed that it is environmental. LocalDB 2019 lacks `LEAST`, and the calendar cases are
  untouched by this change. But CI on pc/PC-181 has not run (the run was skipped), so the
  integration CI run is still the only evidence.
- Deviations:
  - (1), (3), (4), (6), (7), (8) and (10) are justified.
  - (2) is confirmed on LocalDB: `ABS`/`CEILING(tinyint)` and `ROUND(smallint)` are `int`,
    `-tinyint` is `smallint`, and `FLOOR(decimal(5,2))` is `decimal(5,0)`.
  - (5) is acceptable only once R1-1 is fixed. Until then, a reported NotNull can throw on an
    empty cell.

- R1-4: fixed in the same commit, with a different emission than the review proposes.

    answers one row over no row too. `SELECT CASE WHEN (1 = 0) THEN 1 ELSE 0 END FROM sys.objects

  - **When.** An aggregate query emits `HAVING (1 = 1)` when it has no grouping key and no
    group-level predicate (a surviving one already groups), it wrote an aggregation in its select
    list or has measures, and no aggregation survived lowering.
  - **The degenerate shape stays as written.** A select list with no aggregation at all, such as
    `Select = "1"`, stays per row as spec 0008 §2.1 says. The reference interpreter answered it as
    a grand total, which contradicted that paragraph, so it now answers it once per row.
  - **New corpus cases**, each run against the server by the corpus differential:
    - `emit-grand-total-folded` (one row);
    - `emit-grand-total-folded-over-nothing` (one row under a `false` filter);
    - `emit-aggregate-without-aggregation` (per row, bytes unchanged).

    Every other golden's bytes are unchanged.
  - The differential's `, count()` workaround is dropped: the grand total is the measure alone.
- R1-5: fixed in the same commit. `Round` now compares `|remainder| >= unit - |remainder|`, so it
  never doubles the remainder. `MeasureTypeTests.Rounding_FollowsEachRule` covers

- R1-6: fixed in the same commit. New refusal cases:
  - `refuse-measure-position-equality`: `if(max(AltNode) = min(AltNode), 1, 0)`, QX4010 `text
    comparison` at (3, 27);
  - `refuse-measure-zone`: `local(max(PostedAt))`, QX4010 `local` at (0, 20).
