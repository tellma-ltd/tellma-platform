# PC-085: Reference distribution Acme and the Azure defaults bundles

## Implementer notes

### What was built, and where

- **`src/defaults/Tellma.Defaults.Azure`**: `UseAzureDefaults()` composes the email pipeline
  (`AddTellmaEmail`) with the ACS and SendGrid transports. It is idempotent through a marker
  registration. Blobs and imaging join it with spec 0017.
- **`src/defaults/Tellma.Defaults.Azure.AspNetCore`**: `UseAzureWebDefaults()`, also idempotent,
  composes four things:
  - the webhook receivers (`AddTellmaWebhooks`), mapped by `MapTellma` through a new internal seam,
    `IPlatformEndpointSource`, in `Tellma.Core.AspNetCore` (the core grants IVT to the bundle);
  - the host's `TokenCredential`, with `TryAdd` falling back to `DefaultAzureCredential`;
  - `AzureKeyRing`, which keeps the Data Protection ring in a blob wrapped by a Key Vault key when
    both `Tellma:DataProtection:BlobUri` and `KeyId` are https URLs;
  - the Azure Monitor exporter alone (`UseAzureMonitorExporter`), when
    `APPLICATIONINSIGHTS_CONNECTION_STRING` is set.
- **Core changes**:
  - `DataProtectionHostOptionsValidator`: both URLs or neither, each an absolute https URL, and
    never beside `KeyRingPath`.
  - `DevelopmentPorts`: in Development, `.dev-ports.local` is looked up from the content root up to
    the first `.git`. Its `<SLUG>_WEB` and `<SLUG>_CLIENT` lines set `urls` and `Tellma:PublicOrigin`
    in a memory source inserted just above the last file source.
  - `TellmaSeedOptions` (public, startup-validated) replaces the migrator's internal `SeedTenant`
    binding.
  - `TellmaMigrator.RunAsync(…, MigratorRunSettings, …)` and `MigratorRunSettings` are now public.
  - `SpaHosting` maps the static assets inside an unprefixed route group (see the deviations).
  - `InProcIdentity`: an anonymous engine endpoint now carries a policy that authenticates the
    engine's sign-in cookie and requires nothing (see the deviations).
- **`distributions/acme/src`**:
  - `Tellma.Distro.Acme`: `AcmeComposition.Slug` and `Compose`, which runs `UseAzureDefaults` and
    sets the languages en-GB and ar-SA.
  - `Tellma.Distro.Acme.Web`:
    - a three-call `Program.cs` and `AcmeWebComposition.Compose`, which runs `UseAzureWebDefaults`
      and, in Development, `LocalMigratorProvisioningTrigger` (`dotnet run --project <migrator>
      --no-launch-profile -- provision --tenant <id>`);
    - `appsettings*.json` with seed tenants 1 and 2 and the in-proc identity engine with development
      keys;
    - a tracked `launchSettings.json` at port 7052;
    - framework-dependent publishing (`SelfContained` and `PublishSingleFile` set to false).
  - `Tellma.Distro.Acme.Migrator`:
    - a one-line `Program.cs`;
    - `AcmeDesignTimeFactory`;
    - the tenant migration `InitialTenant`, generated by dotnet-ef, with the snapshot under
      `Tellma/Distro/Acme/Migrator/Migrations/Tenant/`;
    - links to the Web project's two appsettings files.
- **`distributions/acme/test`**:
  - `Web.Tests` (24 unit tests): composition parity (`ToDebugString` of the two design-time
    models), emit in process with an unreachable catalog, the audit in Development and in
    Production, the webhook route, one-way dependency, the reference closure and `deps.json` (no
    `Tellma.Identity.Migrations` or `*.Design`), the secret scan of tracked JSON, `Program.cs`
    statements, the collation pin, and the Development trigger and its Production fallback.
  - `IntegrationTests` (11 tests): see its README.
  - `E2E`: an empty Playwright scaffold.
- **Test support**:
  - `OidcFlowClient` moved to `test/apps/Tellma.Identity.TestSupport`, with a public
    `(createClient, emails, pathBase)` constructor. The identity suite's factories gained
    `CreateFlowClient()`; the 70 call sites changed mechanically.
  - `test/shared/Tellma.Testing.Support/Observability/AlertQueries` generalizes the alert-query
    cross-check. The email suite now uses it, and `Tellma.Core.AspNetCore.Tests` checks the new
    `infra/monitoring/host/*.kql` (7 queries) against `TenancyTelemetryNames`,
    `HostTelemetryNames`, `TenancyMetrics`, `HostMetrics` and `CsrfRules`.
- **CI**: a new `integration-windows` job runs `Tellma.Core.IntegrationTests` and
  `Tellma.Distro.Acme.IntegrationTests` against LocalDB, installing LocalDB with choco when the image
  lacks it. It is added to `all-checks-passed`. The Linux `integration` job already runs every suite
  in the solution.
- **Docs**: ARCHITECTURE.md (the bundle text, the exporter, `.dev-ports.local`, the migrator
  sharing the web configuration, the SPA proxy deferred, `Tellma:Seed` validated), CONTRIBUTING.md
  (LocalDB and `TELLMA_TEST_SQL`), and the READMEs of every new project and of the touched core
  projects.

### Deviations

1. **The SPA proxy and the Client esproj are deferred** to spec 0024's checkpoint, per the planner.
   `launchSettings.json` sets no SpaProxy hosting assembly.
2. **`.dev-ports.local` derives only `urls` and `Tellma:PublicOrigin`.** `DB_SUFFIX` is not read:
   ARCHITECTURE.md leaves the per-worktree suffix to the `dotnet tellma` CLI.
3. **`AcmeWebComposition.Compose` replaces the spec's inline lambda**, because it also registers the
   Development trigger.
4. **`MigratorRunSettings` and the settings overload of `TellmaMigrator.RunAsync` are public**, so a
   distribution's suite can run its migrator in process.
5. **Webhook stamping uses an internal seam plus IVT** rather than a public contract. A distribution
   that composes webhooks without the bundle cannot map them through `MapTellma`.
6. **Azure Monitor uses the exporter package (new pin 1.8.0)**, not the distro: the distro would add
   a second instrumentation that keeps SQL text.
7. **`SpaHosting` fix (a platform bug, found by the Acme audit test).** With a build's static web
   assets manifest (`dotnet run`, test hosts), `MapStaticAssets` also maps a development endpoint,
   `{**path:file}`, that its convention builder never reaches. That endpoint failed
   `host.endpoint-audit`, so the Acme web host could not start from a source checkout. The assets
   are now mapped inside an unprefixed group whose convention stamps that endpoint as well.
8. **`provision --tenant 1000 --name …` cannot produce `tenant-registration-refused`** once 1000
   exists: the command refuses it as "already registered as …", a `MigratorFailureException`. The
   suite asserts that, and also asserts the band refusal with `--tenant 1001` ("a requested id lies
   in 1-999"). The code itself never reaches the report line, only the message.
9. **Integration items not built here, deferred to 0011-h:**
   - `__TellmaProvisioning` with the platform steps: Acme composes no step yet, so a probe step is
     composed beside Acme's.
   - The first tenant request binding `UserId`, and suspension on the next request and on a second
     host. Both need the users stack (PC-049 and the 0018 user rows): no member principal exists
     yet.
   - The Frozen and ReadOnly rows.
10. **`Tellma:ScratchPath` validation is left to its first consumer**, spec 0017.
11. **In-proc engine fix (a platform bug, found by the Acme back-channel test).** The host's
    fallback policy names the session scheme. ASP.NET Core evaluates the fallback policy's
    authentication even for an `[AllowAnonymous]` endpoint that states no `[Authorize]`, and its
    result replaces `HttpContext.User`. Every anonymous engine page therefore saw the platform's
    session, or nobody, instead of the engine's sign-in. The direct sign-out page then found no
    `sid`, ended nothing and told no distribution. The sign-in service's same-user merge (step-up)
    read the same wrong principal. Anonymous engine endpoints, controllers and pages alike, now
    carry `InProcIdentity.AnonymousEnginePolicy`: the engine's scheme, with no requirement. A
    regression test in `InProcIdentityTests` fails without the fix.

### Open risks

- **The `integration-windows` job cannot be verified locally.** The choco `sqllocaldb` package and
  its `Tools\Binn` path on `windows-latest` are assumptions. Both suites were run here against
  LocalDB through `TELLMA_TEST_SQL`: Acme 11/11. Core passed 213/213 on a second run. The first
  run, while a `dotnet format` was also running, failed once in
  `RegistryCatalogTests.A_missing_catalog_fails_startup_in_Development_and_starts_not_ready_elsewhere`:
  no exception after 3 s, and the test passes alone. The reader classifies the missing database
  by error 4060 only. Under load LocalDB apparently reported another error, which the first load
  logs and swallows. This was not touched here, but the new job could expose it as a flake.
- **The refresh-rejection test relies on `Tellma:Session:RefreshSkew = 1 day`**, which makes every
  request refresh. It also drops the engine's logout tokens, so only the refresh can learn of the
  revocation.
- **The Acme suite's in-process hosts keep the platform's Serilog console sink**, so a run prints
  every host's log. `WarningLog` joins after `AddTellma`, because the platform's logging removes
  every provider registered before it.
- **`DevelopmentPorts` also applies to the integration suite's in-process hosts.** Their in-memory
  settings sit above it, so they win.

### What reviewers should examine hardest

- `SpaHosting.Map`'s group plus the idempotent `StampMetadata`: the order of the group's and the
  assets' conventions, and headers on index and hashed files (the existing `SpaHostingTests` pass).
- `DevelopmentPorts.IndexAboveFiles`: where the source lands relative to the environment and
  command-line sources in a real `WebApplicationBuilder`.
- `AzureKeyRing` and `DataProtectionHostOptionsValidator` together: a half-configured ring is
  refused at startup and wires nothing meanwhile.
- `TellmaSeedOptions` validation against the migrator's former behaviour (names, sandbox
  cross-references, the 1–999 band).
- The `OidcFlowClient` move: the identity suites still use the same flows through
  `CreateFlowClient()`.
- `InProcIdentity.AnonymousEnginePolicy`: that no engine endpoint which states `[Authorize]` gains
  it, and that the endpoint audit still accepts every engine endpoint.
