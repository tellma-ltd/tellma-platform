## Implementer notes

### Deviations

1. **The SPA proxy and the Client esproj are deferred** to spec 0024's checkpoint, per the planner.
   `launchSettings.json` sets no SpaProxy hosting assembly.
2. **`.dev-ports.local` derives only `urls` and `Tellma:PublicOrigin`.** `DB_SUFFIX` is not read:
   ARCHITECTURE.md leaves the per-worktree suffix to the `dotnet tellma` CLI.
3. **`AcmeWebComposition.Compose` replaces the spec's inline lambda**, because it also registers the
   Development trigger.
4. **`MigratorRunSettings` and the settings overload of `TellmaMigrator.RunAsync` are public**, so a
   distribution's suite can run its migrator in process.
5. **Webhook stamping uses an internal seam plus IVT** rather than a public contract. A distribution
   that composes webhooks without the bundle cannot map them through `MapTellma`. Kept after
   review 1: `Tellma.Core.AspNetCore` referencing `Tellma.Core.Webhooks` would make an optional
   Core-layer package part of every web host, which ARCHITECTURE.md's "composed, never inherited"
   rule forbids; ARCHITECTURE.md now records the seam.
6. **Azure Monitor uses the exporter package (new pin 1.8.0)**, not the distro: the distro would add
   a second instrumentation that keeps SQL text.
7. **`SpaHosting` fix (a platform bug, found by the Acme audit test).** With a build's static web
   assets manifest (`dotnet run`, test hosts), `MapStaticAssets` also maps a development endpoint,
   `{**path:file}`, that its convention builder never reaches. That endpoint failed
   `host.endpoint-audit`, so the Acme web host could not start from a source checkout. The assets
   are now mapped inside an unprefixed group whose convention stamps that endpoint as well.
8. **Resolved in review 1.** `provision` now checks the 1-999 band before the existing-row check, so
   `--tenant 1000 --name …` and `--tenant 1001` are both refused as `tenant-registration-refused`.
   A tenancy refusal's report line carries its code (`provision: failed (<code>: <message>)`), and
   the suite asserts the code.
9. **Integration items not built here, deferred to 0011-h:**
   - `__TellmaProvisioning` with the platform steps: Acme composes no step yet, so a probe step is
     composed beside Acme's.
   - The first tenant request binding `UserId`, and suspension on the next request and on a second
     host. Both need the users stack (PC-049 and the 0018 user rows): no member principal exists
     yet.
   - The Frozen and ReadOnly rows.
10. **`Tellma:ScratchPath` validation is left to its first consumer**, spec 0017.
11. **In-proc engine fix (a platform bug, found by the Acme back-channel test).** The host's
    fallback policy names the session scheme. ASP.NET Core evaluates the fallback policy's
    authentication even for an `[AllowAnonymous]` endpoint that states no `[Authorize]`, and its
    result replaces `HttpContext.User`. Every anonymous engine page therefore saw the platform's
    session, or nobody, instead of the engine's sign-in. The direct sign-out page then found no
    `sid`, ended nothing and told no distribution. The sign-in service's same-user merge (step-up)
    read the same wrong principal. Anonymous engine endpoints, controllers and pages alike, now
    carry `InProcIdentity.AnonymousEnginePolicy`: the engine's scheme, with no requirement. A
    regression test in `InProcIdentityTests` fails without the fix.
12. **Migrator fix (a platform bug, found by the Acme readiness test under load, in review 1's
    gate run).** A fresh database's `ALTER DATABASE CURRENT SET READ_COMMITTED_SNAPSHOT ON` waits
    for every other connection to leave. A web host started before its catalog exists polls it
    every refresh, and its pooled connection stays in the new database, so `migrate` failed with
    an execution timeout. The statement now ends such connections (`WITH ROLLBACK IMMEDIATE`);
    it runs only in a fresh database, which holds nothing yet. A regression test in
    `Tellma.Core.IntegrationTests` (`MigratorTests`, a connection held open in an empty catalog)
    fails without the fix.

### Open risks

- **The `integration-windows` job cannot be verified locally.** The choco `sqllocaldb` package is
  an assumption; its `Tools\Binn` folder is now located rather than assumed. The warm-up step
  assumes a `sqlcmd` on the image, or choco's Go `sqlcmd`, that reaches the instance by its pipe
  name. The job does not gate until it has run green. Both suites were run here against
  LocalDB through `TELLMA_TEST_SQL`: Acme 11/11. Core passed 213/213 on a second run. The first
  run, while a `dotnet format` was also running, failed once in
  `RegistryCatalogTests.A_missing_catalog_fails_startup_in_Development_and_starts_not_ready_elsewhere`:
  no exception after 3 s, and the test passes alone. The reader classifies the missing database
  by error 4060 only. Under load LocalDB apparently reported another error, which the first load
  logs and swallows. This was not touched here, but the new job could expose it as a flake.
- **The refresh-rejection test relies on `Tellma:Session:RefreshSkew = 1 day`**, which makes every
  request refresh. It also drops the engine's logout tokens, so only the refresh can learn of the
  revocation.
- **The Acme suite's in-process hosts keep the platform's Serilog console sink**, so a run prints
  every host's log. `WarningLog` joins after `AddTellma`, because the platform's logging removes
  every provider registered before it.
- **`DevelopmentPorts` also applies to the integration suite's in-process hosts.** Their in-memory
  settings sit above it, so they win.

### What reviewers should examine hardest

- `SpaHosting.Map`'s group plus the idempotent `StampMetadata`: the order of the group's and the
  assets' conventions, and headers on index and hashed files (the existing `SpaHostingTests` pass).
- `DevelopmentPorts.IndexAboveFiles`: where the source lands relative to the environment and
  command-line sources in a real `WebApplicationBuilder`.
- `AzureKeyRing` and `DataProtectionHostOptionsValidator` together: a half-configured ring is
  refused at startup and wires nothing meanwhile.
- `TellmaSeedOptions` validation against the migrator's former behaviour (names, sandbox
  cross-references, the 1–999 band).
- The `OidcFlowClient` move: the identity suites still use the same flows through
  `CreateFlowClient()`.
- `InProcIdentity.AnonymousEnginePolicy`: that no engine endpoint which states `[Authorize]` gains
  it, and that the endpoint audit still accepts every engine endpoint.

### Findings

**R1-1 (major) — The documented Development run cannot sign in.**
`distributions/acme/src/Tellma.Distro.Acme.Web/appsettings.Development.json:6` and
`distributions/acme/README.md:38-46`.
- The fallback `Tellma:PublicOrigin` is `https://localhost:4200`, the Angular dev server's origin.
  The Client esproj and the SPA proxy are deferred, and Acme has no client app, so nothing
  listens on 4200.
- In-proc mode derives the issuer, the OIDC authority (`{PublicOrigin}/id`) and the redirect URIs
  from that origin. So `dotnet run` on the Web project at 7052, then `/bff/login`, sends the
  browser to `https://localhost:4200/id/...`.
- The README's step 3 ("Sign in as `admin@localhost`") therefore fails from a fresh clone. The
  checkpoint's Done-when ("in-proc sign-in works") holds only in the suite, whose `AcmeHost`
  overrides the origin. `DevelopmentPorts` keeps the same gap whenever `.dev-ports.local` names
  `ACME_CLIENT`.
- Fix: until the client and its proxy land, set the Development fallback origin to the web host's
  own, `https://localhost:7052`. Derive `Tellma:PublicOrigin` from `<SLUG>_WEB` until a client
  exists, or record the gap as a deviation. Either way, correct the README's Running and Ports
  sections to say what works today.

**R1-2 (major) — The new `integration-windows` job is unverified, and it already gates every merge.**
`.github/workflows/ci.yml:83-105` and `:277`.
- When the image lacks LocalDB, the step installs choco `sqllocaldb`. The package's current
  version, 16.0.1000.6, is on the SQL Server 2022 (16.x) line, so it installs under `...\160\...`.
  The step appends a hard-coded `...\150\Tools\Binn` to the session PATH.
- The MSI's own PATH change does not reach the running shell. So `sqllocaldb create` would fail
  with "not recognized", and under the runner's `$ErrorActionPreference = 'stop'` the job goes red.
- The job sits in `all-checks-passed`, so a red run stops the line (PLAN §7.1 item 8).
- Fix:
  - Locate the tool instead of guessing the folder. For example, run
    `Get-ChildItem "$env:ProgramFiles\Microsoft SQL Server\*\Tools\Binn\SqlLocalDB.exe" | Select-Object -First 1`,
    then add its directory to `$env:PATH` and `$env:GITHUB_PATH`.
  - Prove the job green on one run (PR or `workflow_dispatch`) before adding it to the gate's
    `needs`.
  - The YAML is otherwise sound: the action versions match the other jobs, `draft` is skipped,
    build and test are split, and the filter is the PR-tier one.

**R1-3 (minor) — Nothing pins the platform's sampler against the Azure Monitor exporter.**
`src/defaults/Tellma.Defaults.Azure.AspNetCore/AzureWebDefaultsTellmaBuilderExtensions.cs:70` and
`test/defaults/Tellma.Defaults.Azure.Tests/AzureDefaultsTests.cs:108`.
- `UseAzureMonitorExporter` sets its own `RateLimitedSampler` (probe b). The platform's
  `ParentBased(AlwaysOn)` survives only because `ObservabilityComposition.Register`
  (`TellmaWebApplicationBuilderExtensions.cs:162`) runs after `composeWeb`.
- If those calls are reordered, or a host composes the bundle after `AddTellma`, sampling
  silently becomes rate-limited. That breaks spec 0011 §9's rule that the server's sampler decides
  over the adopted trace id. No test would fail.
- The exporter test only checks that some registration comes from the exporter's assembly.
- Fix: add a test that builds a host composing `UseAzureWebDefaults` with a connection string and
  asserts the resolved `TracerProvider`'s sampler is the platform's. Optionally, re-assert the
  platform's sampler in `ObservabilityComposition` with a comment naming the exporter.

**R1-4 (minor) — The composition-parity test never builds the web host's model through the web host.**
`distributions/acme/test/Tellma.Distro.Acme.Web.Tests/CompositionTests.cs:27-39`.
- The "web" side runs `AcmeComposition.Compose` and `AcmeWebComposition.Compose` through the
  migrator's own design-time factory, so both sides share one realisation path.
- The test cannot catch a model difference introduced by `AddTellma`. Candidates are
  `AddTellmaAspNetCore`, the in-proc engine's registrations, or anything `composeWeb` adds that
  the design-time path treats differently.
- Fix: build the real host with `AcmeWebApplication.Build("Development")`. Resolve its
  `TellmaDbContext`'s design-time model and compare its `ToDebugString(LongDefault)` with the
  `AcmeDesignTimeFactory` model.

**R1-5 (minor) — Deviation 8: the spec's refusal code is never asserted.**
`distributions/acme/test/Tellma.Distro.Acme.IntegrationTests/MigratorTests.cs:83-92`.
- Spec 0011 §10's Acme row requires `tenant-registration-refused`. The suite asserts English
  fragments only ("is already registered as", "a requested id lies in 1-999"), because the
  outcome line drops the exception's code.
- Spec §6.1 makes `--tenant` with `--name` a `requestedId` "in 1–999". So `--tenant 1000 --name …`
  is first a band violation, and the command's "already registered" pre-check answers it with a
  less accurate reason.
- Fix:
  - Put the `TellmaException.Code` in the per-tenant failure line, so the report carries the code
    an operator or script can match. Assert the code for the 1001 case.
  - Run the band check before the existing-row check, so `--tenant 1000 --name` also yields
    `tenant-registration-refused`, as the spec row states.
  - Otherwise keep the deviation, but assert the code where one exists.

**R1-6 (minor, for Ahmad) — Deviation 5: the IVT seam works but leaves gaps.**
`src/core/Tellma.Core.AspNetCore/Tellma.Core.AspNetCore.csproj:38` and
`src/core/Tellma.Core.AspNetCore/Routing/IPlatformEndpointSource.cs`.
- An internal seam is the right call against forgery: a public source would let any distribution
  stamp an anonymous, tenantless "platform" endpoint past the audit. Two costs remain:
  - (a) Spec 0011 §1.3 lets a distribution "compose those calls itself instead of the bundles".
    Such a distribution can register `AddTellmaWebhooks()`, but cannot map the route: `/api` is
    reserved, and the seam is closed to it. Each future bundle (the on-prem pair) needs its own
    IVT line.
  - (b) The IVT hands the whole internal surface of `Tellma.Core.AspNetCore` to an unsigned,
    distribution-layer assembly, identified by name alone.
- Suggested alternative: have `MapTellma` map the webhook endpoint itself whenever the webhook
  fronting is registered. This adds a `Tellma.Core.AspNetCore → Tellma.Core.Webhooks` edge; both
  are ASP.NET packages, and Webhooks references only Abstractions.
- That needs no IVT, serves every composition, and stays unforgeable. Record the choice in
  ARCHITECTURE.md either way.

**R1-7 (minor) — The new Windows job will surface the known `RegistryCatalogTests` flake.**
`test/core/Tellma.Core.IntegrationTests/Catalog/RegistryCatalogTests.cs:82`, run by the job at
`.github/workflows/ci.yml:104`.
- Question 10 answered: detection by 4060 is not a production bug.
  - `SqlCatalogReader` checks every error in the collection, not only the first.
  - Outside Development, a missing catalog and an unreachable one both start the host not-ready,
    so a misclassification changes only the log text.
  - In Development (LocalDB, integrated security, a sysadmin login) a missing database always
    reports 4060.
- The flake: the first load fails with some other error under load, such as a login timeout while
  LocalDB warms. The load swallows it, and the test's Development assertion then fails. With the
  job gated, that becomes a red CI.
- Fix: before the suites, warm the instance with a probe query against `master` in the Start
  LocalDB step. Track the test in LEDGER "Flaky" and root-cause it per D-018, rather than let it
  flip the gate.

### Judgement of the implementer's deviations and decisions

1. **Public, startup-validated `TellmaSeedOptions` in `Tellma.Core.Tenancy`.** Accepted.
   - It matches `TellmaCatalogOptions` and `TellmaSqlOptions`, which are also public.
   - It is bound through the gate's `core.options` check (D-016) in both hosts, which satisfies
     §8's "every option validated".
   - The rules match the former migrator behaviour, and they are tested. Removing the
     `MigratorFailureException` catch is safe, because the gate refuses a nameless seed first.
2. **IVT seam.** Workable; see R1-6.
3. **`Azure.Monitor.OpenTelemetry.Exporter` 1.8.0.** Accepted.
   - The version exists (restored to the NuGet cache) under an MIT licence.
   - It is the exact version `Azure.Monitor.OpenTelemetry.AspNetCore` 1.5.0 depends on, so it
     causes no NU1605.
   - It is a central-package-management (CPM) entry with a rationale comment. See R1-3 for the
     sampler.
4. **Public `MigratorRunSettings` and `RunAsync` overload.** Accepted: a documented in-process
   seam, with no production caller harmed.
5. **`SpaHosting` fix.** Accepted; it does not weaken the audit.
   - The unprefixed group holds only the endpoints `MapStaticAssets` maps.
   - A published manifest maps no development endpoint, so production's endpoint set and stamps
     are unchanged.
   - `StampMetadata`'s early return fires only for endpoints already stamped by the same code.
6. **`InProcIdentity.AnonymousEnginePolicy`.** Accepted, with no bypass found.
   - When an endpoint carries a policy and no `IAuthorizeData`, ASP.NET Core does not merge the
     fallback policy in (probe a). Such an endpoint authenticates `Identity.Application` alone, and
     the platform session never reaches it. That also closes a pre-fix hole:
     `AuthorizationController.Accept` (`connect/authorize`, consent) read `User`, which was the
     platform session's principal.
   - `Stamp` and `EnginePageConvention` add the policy only when the endpoint states no
     `IAuthorizeData`. So no `[Authorize]` engine endpoint gains it, and step-up `Login` reads the
     engine's principal.
   - The engine uses attribute authorization only, with no folder conventions to race against.
   - Host endpoints cannot gain the policy, because both stamps filter on the engine's assembly and
     the `/id` prefix.
   - CSRF stays exempt, as the endpoints are anonymous.
7. **`provision --tenant 1000` answered "already registered".** See R1-5.
8. **Deferrals to 0011-h.** Accepted. They need the users stack (0014 and 0018) and
   mutation/job semantics (0015, 0016 and 0020).
9. **The LocalDB CI job.** See R1-2 and R1-7.
10. **4060-only detection.** Not a production bug; see R1-7.
11. **`Tellma:ScratchPath` validation left to spec 0017.** Accepted: it has no consumer yet.

The other deviations are also accepted:
- The SPA proxy and esproj deferral (planner's ruling), but see R1-1.
- `DB_SUFFIX` left out.
- `AcmeWebComposition.Compose`: `HostShapeTests` pins the three calls.

Secrets (e): no tracked file holds a secret.
- Development uses integrated-security connection strings and self-signed development keys.
- Secrets that are absent are generated per boot.
- `ConfigurationTests` scans every tracked JSON under `src`.
- The suites' `test-client-secret` and SQL-login strings are test-only and not tracked as
  configuration.
