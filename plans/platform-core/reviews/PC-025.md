### Deviations (also in the commit message)

1. `RequestContext.Tenantless` is a factory `Tenantless(ICalendarSystem, DateTimeOffset now)`, not a
   static property: the Gregorian calendar system is implemented in `Tellma.Core`, and `Now` has to
   come from the host's clock. `CalendarSystem` is `required`; `Calendar` derives from it (one fact,
   one member). Member rules (defined `Kind`, non-blank codes, `ContentLanguageIndex` 1..3) throw in
   the init accessors, and `CultureInfo` is stored read-only so the record is immutable in depth.
2. Cancellation tokens added to `IRequestContextInitializer.InitializeAsync`,
   `ITenantAccessGuard.EnsureAccessAsync` and `ITenantScopeFactory.CreateScopeAsync` (the sketches
   omit them). The guard also takes the `RequestContextInputs` (the sketch gives it no way to
   receive what it must pass to the initializers), and `TenantAccessRequirement` gains
   `AllowWhenReadOnly` (§3.3 and §4.3 rely on it; the record lacked it).
3. A background scope refused for a `Provisioning` or `Retired` tenant throws
   `TenantUnavailableException` with the code `tenant-not-found` (State tells the truth): §3.3 says
   it throws that exception but the exception's code set had no fitting member. The problem mapper
   must map that code to 404.
4. `AddTellma` registers `ISandboxContext` → `TenantSandboxContext` with `AddScoped` (not `TryAdd`),
   so a host's earlier `SandboxContext.Never` no longer wins silently in a tenant host. A
   registration after `AddTellma` still overrides.
5. The guard refuses a `System` principal (`InvalidOperationException`: it skips membership, so no
   request may carry it) and an `Anonymous` one (`TenantNotFoundException`, before the state
   verdict, so an unauthenticated caller learns nothing of the tenant's state). The guard and the
   factory fail closed (`InvalidOperationException`) when no initializer bound `UserId`.
6. Initializers may not change the tenant id, the kind or the subject (refused), and may not return
   null. The holder is set after every initializer rather than once at the end, so a later
   initializer's services already read what an earlier one bound (the connection, then the
   negotiation). The holder refuses rebinding a tenant-bound scope to another tenant or to none.
7. The guard meters `served | read_only | frozen | suspended | not_member | catalog_unavailable`
   (and `provisioning`/`not_found` defensively); the outcomes the middleware decides before binding
   and `scopes{kind=request}` are left to the middleware's checkpoint. `served` is counted before
   the assurance bar: step-up is a verdict on the session, not on the tenant.
8. `ITellmaLinks.Target` reads stacks through `IStackRouteSource` (an internal seam with an empty
   default) because the stack registry does not exist yet. `Tenant` throws for a tenant id below 1
   and for an unset `Tellma:PublicOrigin`; `Target` answers the tenant link for a non-positive
   record id; the resource segment is URI-escaped.
9. `TenantScope` is a sealed class over `(IServiceProvider services, IAsyncDisposable owner)` with
   idempotent disposal, not a record whose equality and `with` would be meaningless.
10. The tenantless context of a scope is stamped lazily on its first read and then kept; both
    writers build their binding from `holder.Current with { … }`.
11. The scope factory opens no logger scope (it could not outlive the async call that opened it);
    the caller opens it, as it owns the activity.
12. `ISessionTerminationListener` ships as a contract only: its callers (later checkpoints) own the
    "log, never throw" loop.
13. (Review 1) Spec 0013 §9.3 step 5 cannot be met inside an initializer: the current cultures do
    not flow back out of `EnsureAccessAsync`/`CreateScopeAsync`. The contracts of
    `IRequestContextInitializer`, `ITenantAccessGuard` and `ITenantScopeFactory` say so, and
    `RequestContext.ApplyCultures()` is the one way the caller applies the completed context.
14. (Review 1) The holder also refuses rebinding a tenant-bound scope to another principal (kind or
    subject) and replacing or dropping a user once one is bound; an initializer that replaces the
    connected user is refused by name.
15. (Review 1) A tenant the snapshot does not hold makes the scope factory throw
    `TenantUnavailableException` (`tenant-not-found`, no state), as a retired one does;
    `TenantNotFoundException` from the factory means only "the run-as user is not an active member".

### Open risks and seams for later checkpoints

- **Thread cultures (spec 0013 §9.3 step 5).** An initializer cannot set
  `CultureInfo.CurrentCulture`/`CurrentUICulture` "for the request": it runs inside the async
  `EnsureAccessAsync`/`CreateScopeAsync`, and `AsyncLocal` changes made inside an async method do
  not flow back to the caller. The front door (tenant filter, MCP filter, the worker after
  `CreateScopeAsync`) must set them from `RequestContext.CultureInfo` after the call returns.
- **The middleware checkpoint** needs the write side (`IRequestContextHolder` is public) and the
  metrics (`TenancyMetrics` is internal: InternalsVisibleTo or a seam) for the pre-binding outcomes
  and `scopes{kind=request}`. It binds `Tenant`, `Kind`, `Subject`, `ClientId`, `SessionId`,
  `SessionHandle`, `Assurance`, `Client` from `holder.Current with { … }` and then calls the guard.
- **The problem mapper (0016)** must map `StepUpRequiredException` and a
  `TenantUnavailableException` carrying `tenant-not-found` (404).
- **The user connection initializer** (0014) is what binds `UserId`; until it exists every guard
  call and every scope without a snapshot `UserId` fails closed. Spec 0014's runner "re-runs" the
  negotiation initializer: a type in `Tellma.Core` that takes `IRequestContextHolder` trips the
  reflection pin in `RequestContextHolderTests` and has to be added to its allow-list knowingly.
- **In-process identity** needs a sandbox answer for tenantless mail (invitations): it must not
  override `ISandboxContext` host-wide with `Never`; `TenantSandboxContext` throws outside a tenant
  by design.
- **The stack registry's checkpoint** replaces `NoStackRoutes` with an adapter over the registry
  (register it before or instead of the `TryAddSingleton` default).

`Tellma.Core.Abstractions.Tests` (582/582); and `Tellma.Core.IntegrationTests` 37/37 on
Testcontainers, the five new `TenantScopeTests` among them. The suite list in the commit message
covers every integration project with non-Live tests (Core, EntityFrameworkCore, Queryex, Identity).

What I checked and found sound:
- **The guard's order.** It refuses an unbound scope, then System, then Anonymous (before the state
  verdict). Next come the state verdict, the initializers and the fail-closed `UserId` check, then
  `served`, then the assurance bar. Every state × mutation × `AllowWhenReadOnly` cell matches
  §3.3. Frozen refuses a mutation even when it is `AllowWhenReadOnly`. A suspended tenant refuses a
  non-member with the state, and a non-member of a serving tenant gets 404, as §3.3 says. The
  assurance rule (`AcrAuthTime ?? AuthTime`, inclusive bound, a missing time failing a `MaxAge`
  bar, ordinal acr) matches §4.3 step 3.
- **The scope factory.** The door is refused before any scope exists. The state table is right
  with and without `allowNonActive`. Every exception after `CreateAsyncScope` is inside the
  `try`/`catch` that disposes, including cancellation inside an initializer and the `UserId` check.
  Nothing starts an activity.
- **Tenant isolation.** Nothing uses `AsyncLocal` or a static. The holder is scoped, behind both
  interfaces as one instance. `RequestContextDefaults` caches nothing. `TenantConnectionProvider`
  never takes a tenant id from a caller. No singleton consumes the accessor.
- **The thread-culture claim is correct.** `AsyncMethodBuilder.Start` restores the caller's
  `ExecutionContext`, so a `CultureInfo.CurrentCulture` set inside `InitializeAsync` (an
  `AsyncLocal`) is gone when `EnsureAccessAsync` or `CreateScopeAsync` returns. Spec 0013 §9.3 step
  5 cannot be met inside the initializer. See R1-1 for how that reaches the people who need it.
- **No current host loses a path.** No production host calls `AddTellma` yet. `Tellma.Identity.Web`
  composes `AddTellmaIdentity` plus `SandboxContext.Never` and is untouched. Nothing outside the
  new files resolves `ITenantAccessGuard`, `ITenantScopeFactory` or `IRequestContextHolder`, so
  failing closed without a `UserId` initializer breaks nothing that runs today. The only consumer of
  `ISandboxContext` in a tenant host is the scoped `EmailRouter`, which is compatible with
  `AddScoped`.
- **The 12 deviations.** I accept all 12.
  - Deviation 3 is the right call given spec 0020 §6.2/§8: the worker reads
    `TenantUnavailableException` as "let the lease lapse" and `TenantNotFoundException` as "run-as
    user inactive". See R1-3 for the one case it misses.
  - Deviation 4 is safe today (above).
  - Deviation 5's Anonymous refusal fails closed behind the 401 that authorization already gives.
  - Deviation 7's split of the metering is consistent: the middleware owns the pre-binding outcomes.
  - The seams the implementer left are named accurately. The stack-route seam fits PC-063, since
    the stack registry lives in the same assembly.

### Findings

**R1-1 (minor) — The thread-culture seam lives only in the review notes, while PC-049's entry
still asks for the impossible.**
`src/core/Tellma.Core.Abstractions/Tenancy/IRequestContextInitializer.cs:13-31`;
`ITenantScopeFactory.cs:12-27`; `src/core/Tellma.Core/Tenancy/ITenantAccessGuard.cs` (remarks):
- **What happens.** CHECKPOINTS.md's PC-049 lists "the Order-200 IRequestContextInitializer setting
  … CurrentCulture/CurrentUICulture" as a deliverable. Neither the contract that implementer will
  read nor the commit's Deviations says that this cannot work.
- **Failure scenario.** PC-049 sets the thread cultures inside `InitializeAsync`. The tests inside
  the initializer pass. Then every handler, and every worker job after `CreateScopeAsync`, formats
  under the host's culture. Server text in the wrong locale fails silently.
- **Suggested fix.**
  - Add a remark to `IRequestContextInitializer`: a step must not set thread cultures, because
    they do not flow back to the caller.
  - Add a remark to `ITenantAccessGuard` and `ITenantScopeFactory`: the caller sets
    `CurrentCulture`/`CurrentUICulture` from `Current.CultureInfo` after the call returns.
  - Add it to the commit's Deviations as a spec 0013 §9.3 step 5 misalignment, so it reaches the
    LEDGER merge-time tasks and a planner note on PC-049 and on the front-door checkpoints (tenant
    filter, MCP filter, 0020 worker).
  - Optionally, ship one small helper the front doors share (for example, an extension that
    applies a context's cultures), so they do it one way.

**R1-2 (minor) — The holder pins the tenant but not the principal.**
`src/core/Tellma.Core/Tenancy/RequestContextHolder.cs:49`:
- **What happens.** `Set` refuses another tenant or none. It accepts the same tenant with a
  different `Kind`, `Subject` or `UserId`. Only `RequestContextInitialization` checks the principal,
  so a direct `Set` can swap it: from a later front door, from spec 0014's runner that "re-runs"
  the negotiation, or from any code that takes the public `IRequestContextHolder`.
- **Failure scenario.** A scope bound to user A in tenant 17, after the guard passed, is re-set to
  `Kind = System` or to user B's `UserId`. Every later service then runs as someone the guard never
  admitted. Neither writer needs this: the middleware and the factory each bind tenant and principal
  in one `Set`.
- **Suggested fix.** Once `current.Tenant` is bound, also refuse a change of `Kind` or `Subject`,
  and a change of a non-null `UserId` to a different value (null to a value stays allowed for the
  connect step). Add the cases to `A_bound_scope_keeps_its_tenant_for_its_whole_lifetime` or a
  sibling test.

**R1-3 (minor) — A tenant missing from the snapshot raises a different exception type than a
retired one.**
`src/core/Tellma.Core/Tenancy/TenantScopeFactory.cs:46`; `ITenantScopeFactory.cs:43`; test
`TenantScopeFactoryTests.cs:214-222`:
- **What happens.** `registry.Get` throws `TenantNotFoundException` for an id the snapshot does not
  hold. `Provisioning` and `Retired` throw `TenantUnavailableException(tenant-not-found)` (deviation
  3).
- **Failure scenario.** Spec 0020 treats `TenantNotFoundException` from scope creation as "run-as
  user inactive": every item of the partition becomes `Failed` with `Jobs.UserInactive`, and
  `core.job.failed` is raised for each. A tenant dropped from the catalog (the `OnRemovedAsync`
  path) between a poll and the scope's creation would therefore fail its in-flight jobs as
  user-inactive, instead of letting the lease lapse as a retired tenant's do.
- **Suggested fix.** Use `registry.Find` and throw
  `TenantUnavailableException(id, null, TenantProblemCodes.NotFound, null)` for an absent tenant,
  matching deviation 3. Keep `TenantNotFoundException` for the membership refusal only, and update
  the `<exception>` docs and the test.

**R1-4 (minor) — Two failure paths are not pinned as disposing the scope.**
`test/core/Tellma.Core.Tests/Tenancy/TenantScopeFactoryTests.cs:274-287` (and `:239-249`):
- **What happens.** `A_scope_no_user_was_bound_for_is_disposed_and_never_handed_out` asserts the
  message and the metric, but not the disposal its name claims. No test cancels the token while an
  initializer runs. Only the `TenantNotFoundException` path checks `DisposalLog`.
- **Failure scenario.** A refactor moves the `UserId` check, or a cancellation check, after the
  `try`/`catch`. The scope and its scoped services, including any open connection, then leak on
  every misconfigured or cancelled background call, and the suite stays green.
- **Suggested fix.** Register `DisposalProbe` and `DisposalLog` in that test and assert `(1, 1)`.
  Add a case whose initializer cancels the token (or throws `OperationCanceledException`) and
  assert the same.

**R1-5 (minor) — The "two writers" reflection pin has blind spots.**
`test/core/Tellma.Core.Tests/Tenancy/RequestContextHolderTests.cs:127-199`:
- **What happens.** The pin scans only the `Tellma.Core` assembly and only fields, parameters,
  return types and IL locals.
  - A chained call such as `sp.GetRequiredService<IRequestContextHolder>().Set(ctx)` creates no
    local in most code shapes, so it escapes the pin.
  - `IRequestContextHolder` is public, so any module or adapter assembly can take it unseen.
- **Failure scenario.** A third writer appears in `Tellma.Core` (or in a later
  `Tellma.Core.AspNetCore`) through a service-locator call, and the pin stays green.
- **Suggested fix.**
  - Also flag a method whose IL calls `IRequestContextHolder.Set` or `RequestContextHolder.Set`:
    scan `call`/`callvirt` tokens with `Module.ResolveMethod`, or simpler, flag any
    `GetRequiredService`/`GetService` generic instantiation over the write side.
  - Extend the scan to every loaded `Tellma.*` runtime assembly, so the AspNetCore front door is
    allow-listed knowingly when it lands.

**R1-6 (minor) — The in-process identity mode contradicts §3.9's sandbox rule, and no deviation
records it.**
`src/core/Tellma.Core/Tenancy/TenancyComposition.cs:74`; `TenantSandboxContext.cs`:
- **What happens.** §3.9 says the identity engine's invitation mail "runs in the identity engine's
  own composition, which registers its own `ISandboxContext`". §5.7's in-process mode has
  `AddTellma` call `AddTellmaIdentity` in the same container. There, `AddScoped<ISandboxContext,
  TenantSandboxContext>` is what the engine's scoped `EmailRouter` resolves, in a tenantless scope.
- **Failure scenario.** Once the in-process checkpoint lands, every invitation or sign-in-code
  email from the in-process engine throws `InvalidOperationException` from `IsSandbox`.
- **Suggested fix.** No code change here. Record it under Deviations as a §3.9/§5.7 misalignment,
  and route it as a planner note to the in-process identity checkpoint. That checkpoint needs a
  tenantless answer that does not override the tenant host's registration, for example a keyed
  `ISandboxContext` the engine's email pipeline resolves, or a `TenantSandboxContext` that defers to
  an engine-scoped flag.

### Responses

- **R1-1: fixed in the review 1 fixes commit.**
  - **The contracts.** `IRequestContextInitializer` says a step sets nothing ambient and never the
    current cultures. `ITenantAccessGuard` and `ITenantScopeFactory` say they set no culture and
    that the caller applies the completed context after the call returns, in its own method.
  - **One way to do it.** `RequestContext.ApplyCultures()` sets `CurrentCulture` and
    `CurrentUICulture` from the context's `CultureInfo`; its remarks carry the flow rule.
  - **Pinned.** `A_culture_an_initializer_sets_never_reaches_the_caller_which_applies_the_completed_context`
    (an initializer sets both cultures; after the guard returns the caller's are unchanged; after
    `ApplyCultures` an awaited callee runs under the negotiated one) and
    `Applying_a_contexts_cultures_sets_the_current_culture_and_the_current_ui_culture`.
  - **Recorded** as deviation 13 here and in the fix commit's Deviations. The planner notes are the
    orchestrator's.
- **R1-2: fixed in the review 1 fixes commit.** Once a tenant is bound, `RequestContextHolder.Set`
  refuses another `Kind` or `Subject` (the text names the kind and the tenant, never a subject) and
  a bound `UserId` replaced or dropped; null to a value stays allowed. `RequestContextInitialization`
  refuses the same for the connected user first, so the error names the step. A tenantless scope may
  still be bound to any principal in one write. Tests:
  `A_bound_scope_keeps_its_principal_and_its_user_for_its_whole_lifetime`,
  `A_scope_bound_to_no_tenant_may_still_be_bound_to_any_principal`,
  `An_initializer_that_replaces_the_connected_user_is_refused`,
  `An_initializer_that_drops_the_connected_user_is_refused`.

- **R1-5: fixed in the review 1 fixes commit, with one limit.**
  - **Bodies.** The pin now reads every method body's instructions and resolves each member or

    `The_search_for_writers_sees_a_write_made_without_a_local_a_field_or_a_parameter` proves the

  - **Assemblies.** It searches every `Tellma.*.dll` in the suite's output but the suite itself

  - **The limit.** An assembly this suite does not reference is not in its output and cannot be
    searched from here. `Tellma.Core.AspNetCore` gets pinned when its checkpoint either adds it to

    as §4.2 declares it.
- **R1-6: pushed back: routed by the orchestrator.** No cheap fix keeps both sections true here:
  `TenantSandboxContext` throwing outside a tenant is §3.9's rule and this checkpoint's test, and
