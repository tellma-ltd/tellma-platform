### Deviations

1. **Each field cell renders its own `dl`.** axe's `dlitem` / `definition-list` rules refuse a
   `dt`/`dd` pair whose `dl` is a card's grid with other elements in it.
2. **The working copy is completed with `null`** for client-written members the read omitted, on
   land and on create, so `entity()` is the completed copy.
   - Without this, an omitted member has no node, so a required member the read left out is never
     required.
   - A save now sends `null` for those members (see the open risks), except a defaulted member
     that is not nullable, which the save body leaves out while it is empty (fix 2).
3. **`tmDetailsPlatformSchema` takes a third `options` argument**: the child descriptors, the
   mode, the uploads and the recorded errors. With none it applies the context-free rules.
4. **Dropped in fix 1.** Tabs that are a direct child of a card now render in the card's section
   slot, so spec 0031 §6.6's example works. Tabs nested in another element inside the card still
   raise §6.1's development error.
5. **`TmUploads` moved from `/entity-editing` to `/entity`.** The record provides it in every
   mode, and `/details` may not statically reach the edit side.
6. **Upload pending is reached only once the sync rules pass**, as Signal Forms runs async
   validators after the sync ones.
7. **The new error kind `precision`** adds `errors.precision` to the core-ui table (English and
   Arabic) and raises the core-ui primary's ceiling by 0.02 KB.
8. **The field's edit mode lives in `@tellma/core/entity-editing`** as `ɵTmFieldEditor`, not in a
   `/details` chunk of its own. `tm/core-import-boundary` forbids `/details` from importing
   `/entity-editing` statically, even from a file only `import()` reaches. A dynamic import of
   the entry point is allowed and keeps the edit stack out of the details route.
9. **The aside and title extras are registered on the record and rendered by the frame**, so the
   layout never renders them in place.
10. **The frame is not encapsulated**, so the layout's host is `display: contents` through a
    descendant rule and the cards sit on the frame's grid.
11. **A navigation field registers under its foreign key's name** (`Currency` registers as
    `CurrencyId`), the member the server's errors name.
12. **Child rows skip the rules on their parentKey**, which the server writes.
13. **Acme's layout omits the Contacts child grid card.** `tm-child-grid` belongs to the next
    checkpoint, so the layout is the customer card and the audit.
14. **The aside's lg and xxl breakpoints read the band's container width**, not the viewport,
    because the shell's navigation narrows the band.
15. **Budgets raised** (below). `/details` stays within spec 0031's 23 KB for the whole entry
    point.
16. **`validate` is a loader, not the schema function (fix 1, for Ahmad).** Spec 0029 §3 and spec
    0031 §7.2 declare `validate: (path) => void`. It is now
    `validate: () => Promise<rules | { default: rules }>`, where the rules are a `TmEntityRules<T>`
    schema function, so a distribution's rule file imports `@angular/forms/signals` exactly as
    §7.2's example does, outside the initial bundle.
    - The controller loads the rules beside the layout and renders the layout once both are in
      hand.
    - A record that started before the rules arrived rebuilds its form with them once, before
      the layout renders. Records started later take them at creation.
    - Acme ships §7.2's rule this way (`customer-rules.ts`).
    - Fix 2: spec 0032 §9 declares `validate: tmJsonTextSchema('argumentsJson')` on the
      schedules declaration, and PC-136's deliverables put `tmJsonTextSchema` in the primary.
      Under this shape that is a type error, and a primary helper that calls Signal Forms'
      `validate` would pull `@angular/forms/signals` into the initial bundle. The lazy form is
      `validate: () => import('…')` over a rules module, with the helper out of the primary (for
      example in `/details`, or the schedules' own rules file).

### Open risks

- **Null completion on save.** A save sends `null` for every client-written member the read
  omitted. That is the same value the server holds when the member was absent because it was
  null, but a server that treats an absent member as "unchanged" and `null` as "clear" would now
  clear it. Read plans that omit members on purpose would need the completion narrowed to what
  the layout shows.
- **The frame is not encapsulated.** Its rules are all under `.tm-details`, but a layout's own
  styles can now meet them.
- **The edit side is one entry point.** The first edit loads all of `/entity-editing` (12 KB),
  not just the field editor. It is prefetched once `can.edit()` holds.
- **The `CurrencyId` registration key.** A layout that calls `focus('Currency')` or reads
  registrations by the navigation's name finds nothing.
- **Upload pending only after the sync rules pass.** A form with a sync error and a running
  upload shows the error, not the pending state.

## Review 1

### Findings

**R1-1 (blocking). The null completion writes `null` into child rows' parent keys, so a clone with child rows can no longer be saved.**
`client/projects/core/tellma-core/details/src/tm-details-model.ts:66-71` adds `null` for every `editable`/`write-once` member a row lacks, and a child row's parent key is `editable` in the descriptor (the model spec's completion test even expects `customerId: null`). `tmDetailsCloneStrip` (`tm-details-model.ts:147`) deletes the parent key from every cloned row, as spec 0031 §3.6 step 4 says. Then `TmDetailsRecordState.start` (`tm-details-record.ts:380-383`) completes the copy and puts `customerId: null` back on each contact.

- Failure scenario: on Acme, clone a customer that has contacts and press Save. The body carries `"contacts": [{ "id": -1, "customerId": null, … }]`. `CustomerContact.CustomerId` is a non-nullable `int` (`distributions/acme/src/Tellma.Distro.Acme/Entities/CustomerContact.cs:19`), and System.Text.Json refuses `null` for an `int`. I checked this with a .NET 10 console run: `JsonException: The JSON value could not be converted to System.Int32. Path: $.customerId`. So the save is a 400, where it used to work before this checkpoint.
- The same thing happens to rows from `declaration.defaults` (which `start` completes with the real child descriptors), and later to new rows in a restored draft, since a restore also goes through `start`.
- The tests miss it because `tm-details-host.spec.ts`'s clone test now compares `valued(model)`, which drops the nulls.
- More generally, a JSON `null` for any non-nullable value type is a 400. At the root, `required` blocks such a save, except for a `[Defaulted]` non-nullable value type (allowed by `EntityMetadataBuilder`, though unused today).
- Suggested fix:
  - Never complete a child row's parent key: pass `child.parentKey` down the recursion and skip it, as `tmDetailsPlatformSchema` already does.
  - Leave out members that are `defaulted` and not nullable.
  - Add tests:
    - a clone of a customer with contacts whose raw `model()` rows hold no `customerId` key (not compared through `valued`);
    - a host test that checks the save body of that clone.

**R1-2 (major). A failed load of the edit side is never retried, so edit mode shows values with no controls and no message.**
In `client/projects/core/tellma-core/details/src/tm-field.ts:448-456`, `const wanted = this.#record.can.edit() || this.#record.mode() !== 'view'` short-circuits: while `can.edit()` holds, the effect never reads `mode()`. `loadEditor`'s rejection (`:146-150`) resets the cache, but the effect is then left depending only on `can.edit` and `editor`, and neither changes. The comment says "A failed load tries again on the next mode change", which does not happen.

- Failure scenario: the view-mode prefetch fails, for example offline, or a stale tab after a deploy changed the chunk hash. The user then clicks Edit. Every cell takes the `editing(cell)` branch with `editor() === null`, so it renders the unlocked value cell (`:315`): no control, no lock, no error, and no retry.
- `#focus`'s fallback (`:564-566`) calls `loadEditor()` again but never sets `this.editor`, so even a successful reload there leaves the field without its control.
- Suggested fix:
  - Read both signals unconditionally, so a mode change re-runs the load.
  - Have `#focus`'s fallback set `this.editor` on success.
  - Report a final failure (the app's chunk-load error path, or a field error state) instead of swallowing it with `() => undefined`.
  - Add a test with a rejecting import, then Edit.

**R1-3 (major, needs a ruling). §7.2's `validate` cannot be used within spec 0024 §12's initial budget, and spec 0031 §18's Acme rule is not shipped.**
The record applies `declaration.validate` after the platform schema (`client/projects/core/tellma-core/details/src/tm-details-record.ts:314-320`), so the mechanism meets §7.2. But the contract's shape (`client/projects/core/tellma-core/src/entity/tm-entity-declaration.ts:372`, `(path) => void`, from spec 0029 §3) makes a distribution import `required` and the other rules from `@angular/forms/signals` in its feature file. That file is in the initial bundle. The implementer measured initialJs going from 223.13 to 241.09 against the 230 warn level, so §7.2's own example is unusable as written. Spec 0031 §18 lists "`customer-details` … with §7.2's rule" among what Acme adds, so deviation 16 drops a spec'd deliverable rather than deferring it.

- Suggested fix (for the orchestrator's ruling): let the platform hand the rule functions in, `validate?: (path, rules) => void`, where `rules` is the `{ required, maxLength, min, max, pattern, validate, … }` set from `@angular/forms/signals`.
  - The record passes the real functions. The feature file then imports only types, which are erased, and Signal Forms stays in the details route.
  - That keeps §7.2's "a Signal Forms schema function" and spec 0029's declaration member, with one extra parameter.
  - Then ship the corporate credit-limit rule in `acme.feature.ts` and a test that shows its message on touch.
  - A lazy `validate: () => import(…)` also works. But the form is built synchronously when the record is created, so it would need an async seam.

**R1-4 (major). Several spec rules in scope have no test that would fail if they broke.**
The kit spec and the host spec do not exercise:

- `*tmDetailsExtra` beyond its development error (`tm-details-extra.ts`):
  - the three skeleton lines while the record loads with nothing held;
  - a missing extra rendering nothing;
  - `rowsOf`, which turns a QueryRowSet's `columns`/`rows` into objects keyed by column name: non-trivial logic that distributions bind to (§6's `let rows` example);
  - re-rendering when the extra's value changes.
- The tab error dot and ", has errors" (§6.6), selected or not, from a field on the tab and from the tab's `collection` (`tm-details-tabs.ts:125-137`). `tm-card.spec.ts` tests the card's dot, but nothing tests the tab's.
- `tm-details-audit` (§6.8):
  - the four fields' values ("Created by" as a link, instants with the zone label);
  - nothing at all on an entity without audit columns.
- `selected` as a two-way model (§6.6): a parent binding `[(selected)]` drives the tab, and a click writes back.
- §8.5's walk to the deepest node. The test at `tm-details-schema.spec.ts:199` is named "…and on the nearest node a path's end lacks", but it asserts `contact().errors()` is `[]`. It never shows an error landing on the nearest node, because its recorded value (`undefined`) never equals the row.

Suggested fix: add these cases to `tm-details-kit.spec.ts` and `tm-details-schema.spec.ts`. In the schema test, record the row node's value, as §8.5 step 3 does for the deepest node reached, and assert the error shows on `contacts[0]`. Then rename the test, or split it in two.

**R1-5 (minor). The done-when is tested on a copy of Acme's layout, not on Acme's component.**
`tm-details-kit.spec.ts:192-206` (`TmTestCustomerLayout`) re-types Acme's markup, and Acme's only unit spec is `app.config.spec.ts`. So `distributions/acme/src/Tellma.Distro.Acme.Client/src/app/customers/customer-details.ts` can drift without any test failing. For example, a misspelt path is a runtime development error that the AOT build does not catch.

- Suggested fix: add an Acme unit spec that renders the real `CustomerDetails` over `tmFakeDetails` (core-testing) in view and edit mode, with a required message on blur.

**R1-6 (minor). §6.6's example could be made to work instead of being ruled out.**
Deviation 4 resolves §6.6 against §6.1 by requiring `tmDetailsCardSection`, so the spec's own invoice example (`<tm-details-card flush><tm-details-tabs>`) throws. Spec 0031 §18 says the sales invoice layout uses "§6.6's tabs".

- Suggested fix: also project a direct `tm-details-tabs` child into the section slot (`tm-details-card.ts:146`: `select="[tmDetailsCardSection], tm-details-tabs"`), and have `TmDetailsTabs` accept a direct child of the card as a section.
  - §6.1's rule still holds: tabs never render inside the field grid, and tabs nested in a wrapper still raise the development error.
  - Both spec examples then work.
- If the ruling keeps the current behaviour, the deviation stands as written.

**R1-7 (minor). The implementer notes describe an Acme change that is not in the commit.**
Line 85 of this file says "`src/app/acme.feature.ts`: `validate` adds 'a corporate customer needs a credit limit'". The commit does not touch `acme.feature.ts`, and deviation 16 says the rule was reverted.

- Suggested fix: drop that bullet, or point it at deviation 16.

### Responses

  leaves out every member that is `defaulted` and not nullable. The recursion passes each child's
  `parentKey` down, as `tmDetailsPlatformSchema` does.
  - Tests (`tm-details-model.spec.ts`): completion leaves the parent key out (the raw rows with
    `toStrictEqual`, not `valued`); a defaulted non-nullable member is left out; rows from the
    defaults and a restored draft's new rows hold no `customerId`; a clone's rows after the strip
    and the completion hold none (`JSON.stringify` of the raw model).

    contacts are exactly `[{ id: -1, name: 'Huda', email: null }]`. On f9a42802 the completion put

  load is tried again on the next mode change.

    field couldn't be loaded for editing.", with Arabic) and a Try again button. The field never

  - The loaded editor is shared, so one field's Try again or `focus()` serves every field.

  - Tests (`tm-details-kit.spec.ts`, "when the edit side fails to load", through a loader seam

  - Acme ships spec 0031 §7.2's rule in `customer-rules.ts`, importing `required` from

  - The first form of a record rebuilt this way is not disposed until the record is; it is never
    rendered.
