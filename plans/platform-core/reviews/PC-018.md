### Deviations (also in the commit message)

1. Enum string conversion is a finalizing convention over every enum and nullable enum property,
   not `Properties<Enum>().HaveConversion<string>()` in `ConfigureConventions`; all conventions ship
   with `UseTellmaSqlServer` (options extension + `IConventionSetPlugin`) so any context built
   through it gets them, and run at the head of model finalizing (after Core's configurations,
   before EF's key-generation/temporal/cleanup conventions and the table-type derivation).
2. Foreign keys are added as explicit configuration: EF's `ModelCleanupConvention` removes every
   navigation-less FK below Explicit, and the platform maps no navigations. An FK a Core
   configuration declared over the same column/principal is left alone.
3. EF's `ForeignKeyIndexConvention` is removed: only conventions or Core configurations create
   indexes. The audit FKs therefore carry no index (§1.3/§4.2 list IX only for child, reference
   and tree keys; `ModifiedById` changes on every save).
4. `[Flags]` enums are sized for every single-bit flag joined with `", "`, the string the
   conversion writes for a combination.
5. `UseTellmaSqlServer` takes the `DeploymentIdentity` (to set `Application Name`) and a sweep
   scope defaulting to `tellma.tenant`; the spec names neither the parameter nor any scope.
6. `StackContributionItem`, its sugar and a recording realizer ship here (0011 §2.1/0015 §2.1
   types) because the model's leaf input needs them; `TService` is constrained to `class` only.
7. Every table type, entity row image and standalone, grants `EXECUTE` to `tellma_app` (0011 §3.5
   "AddTellma sets tellma_app as the default principal set"); fixtures must create the role first.
8. A standalone type with no attribute schema is mapped in `dbo` explicitly (0012 §4.4 physical
   `[dbo].[<Name>_<hash8>]`), under its class name; its enums become `varchar(n)` and its
   `[ExcludeFromTableType]` properties are dropped, via the two new `TableTypeBuilder` methods.
9. The binder pins every text column's `SqlMetaData` to LCID 1033 with CI/AS options (the
   platform collation) instead of the thread culture SqlClient defaults to, and refuses a
   `varchar`/`char` column in a non-Latin1 or UTF-8 collation (cannot be encoded faithfully);
   `DateOnly`/`TimeOnly` are handed to the record as `DateTime`/`TimeSpan`.
10. Conventions throw `InvalidOperationException`, naming the class and declaration, for what the
    model cannot be built with: a `[References]`/`[Sibling]`/child target absent or mapped twice,
    a non-`int`/`long` reference or blob column, an unknown `[TableIndex]` property, a key neither
    `int` nor `long`, missing `core.Users`/`core.Jobs`/`core.Blobs`, a child carried by two parent
    types, a temporal TPT root or leaf. Everything else is left to PC-021's validation.
11. `dbo.__TellmaSchema`/`__TellmaProvisioning` are internal row classes with closed Core
    configurations; `CoreFeature` also registers `VersionTagList` (0012 §4.4 "registered by
    CoreFeature").
12. Model-wide `UseNamedDefaultConstraints()` beside the explicit `DF_` names; the period columns
    come out `HIDDEN` (EF's rendering of shadow period properties); EF omits `AS bigint` on a
    `long` key's sequence (the SQL Server default type).
13. Conventions shape root entity types only (leaf-only mapping); TPH/TPT derived types are not
    shaped, apart from the temporal TPT refusal.
14. `ReservedSqlNames` (§1.4 constants) and `DatabaseRoles` are names of this checkpoint's
    choosing: the spec gives the values, not a type.

Verified, not redone (planner note): the Abstractions → `Tellma.Core.Queryex` project edge and
ci.yml's design-e2e packing `Tellma.Core.Queryex` (PC-015).

### Open risks and seams for later checkpoints

- **The model builds lazily.** Nothing at startup resolves `IModel` until PC-021's metadata gate
  does; until then a model that cannot be built fails at first use, not in the gate. Forcing a
  build inside `core.model-contributors` would cost every composition test a model build, so it
  was left to PC-021 (the gate reports a throwing check as a problem).
- **`dotnet ef database update` without `tellma_app`.** The table-type migrations emit an unguarded
  `GRANT … TO [tellma_app]`; 0011 §6.1 says a design-time database "has no tellma_app", which would
  then fail with Msg 15151. PC-027 (fixture "role pre-creation") and PC-034
  (`TellmaDesignTimeDbContextFactory`) must create the role or guard the grant.
- **HierarchyId design-time services** are not injected into a migrator assembly (the package's
  `build/` targets are not transitive). The scaffold test runs without them and passes, so
  `migrations add` works; reverse engineering would not need them.
- **D-015 / Msg 468**: `StringList.Id` takes the database collation; key-set restrictions over a
  BIN2-collated natural key (e.g. a `Subject`) will need a collated list type (PC-033, 0010 §F.1).
- **§4.1 "every other timestamp `datetimeoffset(3)`"** has no convention in §1.3; non-audit
  `DateTimeOffset` columns stay `datetimeoffset(7)` unless declared.
- **No default-leaf naming**: a leaf's table comes from `[Table]` (inherited); a default without
  `[Table]` gets EF's class-name default (the leaf's name). PC-021 may want to require `[Table]`.
- The model cache keys on the definition instance, so each composition in a process builds its own
  model (tests compose many; a host composes one).

### What reviewers should examine hardest

1. `TellmaConventionSetPlugin` + `ConventionModel.AddForeignKey`: the ordering at the head of model
   finalizing, explicit FKs, and the removed FK-index convention (deviations 1-3), against EF 10
   source (`ModelCleanupConvention`, `ForeignKeyIndexConvention`, `SqlServerTemporalConvention`).
2. `TemporalConvention`: period properties are created before `IsTemporal`, because EF's temporal
   convention creates them only when the finalizing batch completes; check the TPT/TPH tests.
3. `TellmaModelDefinition.Close` and `ModelContributorsCheck`: open configurations closed over the
   leaf of the parameter's class constraint.
4. `TableTypeBinder`/`StoreTypeMetadata`: the column ↔ property match through table mappings on
   the runtime model, converters, the LCID choice, and the `DateTimeOffset` scale (EF puts a
   temporal precision in `Precision`).
5. The SQL in `DataModel.Sql` (`MigrationScaffoldTests`, `ConventionTests`): every name of §1.3.

Orchestrator questions:
- **datetimeoffset precision.** §4.1 means every non-audit timestamp. It says "every timestamp is
  an instant stored as `datetimeoffset` … audit columns `datetimeoffset(7)`, every other timestamp
  `datetimeoffset(3)`". The exceptions are those spelled out: the audit pair, `IdStampList` (7),
  and the `datetime2(7)` periods. The current behaviour is R1-1.
- **ForeignKeyIndexConvention.** Leaving the audit FKs unindexed is what the spec intends.
  - §4.2 lists an `IX_` for every column set that has one (child, reference, tree, job, blob)
    and only the FK for `CreatedById`/`ModifiedById`.
  - §1.3's `AuditConvention` row names only the FKs.
  - 0014 §3.9 allows deleting only `State = New` users. Such a delete costs one scan of each
    audited table per audit FK and per statement: rare, admin-only, and bounded.
  - The global removal also means a Core configuration's FK gets no index unless the
    configuration declares one. That is consistent with the specs, whose table definitions list
    every index explicitly.
- **tellma_app grants.** This matches 0011 §3.5: "`EXECUTE ON TYPE` for every table type …
  (`AddTellma` sets `tellma_app` as the default principal set)". The catalog's type grants it too
  (0011 §6.4), and 0011's integration row expects the role to exist before the first migration.
  The unguarded grant is therefore the spec's design. 0011 §6.1's design-time database "has no
  `tellma_app`", and that contradiction is real: Msg 15151 reproduced on LocalDB.

**Blocking:** none.

**Major**

- **R1-1 — Non-audit timestamps are mapped as `datetimeoffset(7)`, but §4.1 requires
  `datetimeoffset(3)`.**
  - *Location:* `src/core/Tellma.Core/Data/Conventions/TellmaConventionSetPlugin.cs:32-55` (no
    convention sets it); `AuditConvention.cs:49-52` sets only the audit pair;
    `TableTypeConvention.cs:102-136` does not shape standalone `DateTimeOffset` columns.
  - *Failure:* a pack property `public DateTimeOffset? DueAt { get; set; }` becomes a
    `datetimeoffset(7)` column and row-image column. So does any Core table whose configuration
    omits `HasPrecision(3)`: the job, notification, blob and outbox timestamps of 0017/0020-0022
    list dozens of `datetimeoffset(3)` columns. Packs cannot fix this themselves, because they may
    declare only annotations (§2.2). After the first tenant migration ships, the correction becomes
    an `ALTER COLUMN` on every affected table, a new UDTT version for each, and a
    `StorageFingerprint` change.
  - *Fix:* add a convention that gives every `DateTimeOffset`/`DateTimeOffset?` property precision
    3 at data-annotation source, but only when no precision or column type is configured.
    - Run it before `AuditConvention`, so the audit pair's (7) overrides it at the same source.
    - In `AddStandalone`, give each `DateTimeOffset` property without `[Column(TypeName)]` the
      type `datetimeoffset(3)` with precision 3. `IdStampList` keeps its declared (7).
    - Since §1.3's table has no row for this convention, list it under Deviations.
    - Tests: a `DateTimeOffset?` on `Widget` maps to `datetimeoffset(3)` in the column, the row
      image and the binder (scale 3). A `[Column(TypeName = "datetimeoffset(7)")]` property keeps
      7. A standalone `DateTimeOffset` column maps to (3). The audit pair stays (7).

**Minor**

- **R1-2 — `ReservedSqlNames.IsReserved` reserves `@tb*`, `@tm*` and `@qx*`. §1.4 reserves only
  `@tb{b}_`, `@tm_` and `@qx{b}_`.**
  - *Location:* `src/core/Tellma.Core.Abstractions/Data/ReservedSqlNames.cs:77`, `:89`. The test
    `test/core/Tellma.Core.Abstractions.Tests/Data/ReservedSqlNamesTests.cs:27` pins `@tmx` as
    reserved.
  - *Failure:* a distribution's raw SQL commonly declares `@tmp`, `@tbl`, `@tbOrders` or
    `@qxRate`. Every one of these is reported reserved, so once TELLMA0003 uses this API it
    refuses legitimate SQL that §1.4 leaves free.
  - *Fix:* match `@tm_` literally, and `@tb`/`@qx` only when followed by one or more digits and
    `_` (case-insensitive). Turn the `@tmx` case to false, and add `@tmp`, `@tbl` and `@qxRate`
    (false) and `@tb12_x` (true).
- **R1-3 — Two kinds of constraint name are still left to EF's implicit naming.**
  - *Location:* `src/core/Tellma.Core/Data/Conventions/ConventionModel.cs:147-151` (early return);
    `ConstraintNames.cs` has no primary-key name.
  - *Failure:*
    - Every `PK_<Table>` comes from EF's default name, against §1.3 ("the conventions emit them"),
      ARCHITECTURE's determinism rule and `ConstraintNames`' own summary. §6.4 maps 2627 on
      `PK_<Table>` by name.
    - A Core configuration that declares an FK without `HasConstraintName` keeps EF's
      `FK_<Dep>_<Principal>_<Col>`. §6.4's pipeline maps 547 only for `FK_<Table>_<Column>`, so
      `Fk.NotFound`/`Fk.InUse` would never fire for that key.
  - *Fix:* give the primary key `HasName(PK_<Table>, fromDataAnnotation: true)` (add
    `ConstraintNames.PrimaryKey`). On the early-return path, call
    `existing.Builder.HasConstraintName(name, fromDataAnnotation: true)`; an explicit name still
    wins.
- **R1-4 — The generated SQL fragments do not escape `]`.**
  - *Location:* `ConventionModel.cs:207` (`NotNullFilter`), `PositiveKeyConvention.cs:41`, and
    `src/core/Tellma.Core/Data/TableTypes/TableTypeBinding.cs:38-39` (`TypeName`).
  - *Failure:* a pack column named with a `]`, such as `[Column("Code]x")]`, gives an invalid
    filtered-index or check SQL, although EF delimits the same name correctly elsewhere in the
    statement.
  - *Not an injection risk:* every name comes from compiled attributes or Core configuration, and
    no runtime or tenant input reaches these strings. Grants use a constant principal, and the
    library delimits type names.
  - *Fix:* double `]` (or use `ISqlGenerationHelper.DelimitIdentifier`) in all three places.
- **R1-5 — An unmapped capability column fails the model with a `NullReferenceException`.
  Deviation 10 promises a named `InvalidOperationException`.**
  - *Location:* `AuditConvention.cs:44`, `TreeConvention.cs:39`, `SequenceConvention.cs:48` and
    `PositiveKeyConvention.cs:38` (`FindProperty(...)!`).
  - *Failure:* a Core configuration's `Ignore(u => u.ModifiedById)`, or a leaf hiding a base
    member with `[NotMapped] new`, throws a bare NRE at model build. §3.2's "mapped capability
    columns" rule never gets to report it, and nothing names the class.
  - *Fix:* throw `InvalidOperationException` naming the entity and the column, as the other
    refusals do, and add one `ConventionFailureTests` case.
- **R1-6 — Nothing tests that an explicit model configuration wins over the conventions.**
  - *Location:* `ConventionModel.cs:147-151` (FK left alone), `EnumStringConvention.cs:33`
    (explicit conversion), and `TableTypeConvention.cs:61-74` ("a fluent opt-out still wins").
  - *Gap:* if the precedence broke, Core's configurations (`User`, `Role`, jobs) would be
    overwritten silently and every test would still pass. For example, a setter switched from
    data-annotation source to explicit would do it.
  - *Fix:* add a closed Core configuration to the test model that declares an FK with its own
    name and delete behaviour, `HasConversion<int>()` on an enum, and a fluent table-type
    opt-out. Assert that all three survive.
