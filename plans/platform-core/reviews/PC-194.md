# PC-194: tm-chart core-ui entry point (ECharts facade)

## Implementer notes

### What was built

`@tellma/core-ui/chart` (`client/projects/core/tellma-core-ui/chart/`), spec 0034 §1 (chart row),
§7.1–§7.8 and §14.

- **Public surface.**
  - `TmChart` (`tm-chart`): inputs `spec`, `asTable` (model), `gridId`, `activatable`; output
    `pointActivate`.
  - `TmChartSpec` and its parts (`tm-chart-types.ts`).
  - `TM_CHART_SPEC_SCHEMA` and `tmValidateChartSpec` (`tm-chart-schema.ts`). A golden
    (`tm-chart-spec.schema.json`) is generated from the schema and compared in the schema spec.
  - `TM_CHART_STRINGS_EN`, registered beside the core table through `ɵtmRegisterUiStrings`.
    `@tellma/locale-ar` translates it under `chart`.
- **Four views.**
  - **No data**: the projected content.
  - **Card**: one value and its label, and a badge for the reached threshold. It is a `button`
    when activatable.
  - **Table**: a `tm-grid`, with one column per dimension and a value column, and row activation
    when activatable. It shows when `asTable` is set, when the type cannot be drawn, or when the
    engine fails to load or render.
  - **Plot**: a `<figure dir="ltr">` around a `div role="img"`, whose name is "title, type" and
    whose description is the ICU point summary.
- **Engine boundary.**
  - `internal/chart-engine.ts` is the only module that imports ECharts values. A lint block
    enforces this in `eslint.config.mjs`.
  - The component loads the engine with `import()` on its first plot. A card, a table or no data
    never downloads it. The e2e "the engine" test checks this.
  - `internal/chart-option.ts` is a pure option builder (ECharts types only).
  - `internal/chart-theme.ts` reads the `--chart-*` tokens and normalizes each colour through a
    1×1 canvas readback.
  - `internal/chart-text.ts` adds the canvas-text LRM/RLM marks.
- **The four canvas-text guards (§7.5).**
  - The canvas renderer only.
  - `tooltip.renderMode: 'richText'`.
  - `aria.label.enabled: false`. Decals stay on.
  - Clicks resolve by `seriesIndex`/`dataIndex`. Series, categories and slices are named by
    private ids, so no label text is ever used as a key.
- **Tokens.** A `chart` group in the default preset holds:
  - `series1-8`, `sequential1-7` and the diverging poles;
  - the grid, axis and label inks;
  - the positive, warning and negative tones;
  - the surface, tooltip, decal, font size and height;
  - the card metrics.

  `tokens.spec.ts` validates the palette in both schemes and in every preset:
  - opaque, chroma ≥ 0.1;
  - adjacent normal-vision ΔE ≥ 15, protan/deutan ΔE ≥ 8;
  - series and tones ≥ 3:1 against the card surface.

  The identity server's `tokens.css` copy is regenerated.
- **Size gate.** `scripts/bundle-size.mjs` and `tools/bundle-measure.mjs` gain
  `"tellma".lazyChunkBudgetsInKb`:
  - A lazy chunk is found as `<entry>-<module>-<hash>.mjs`.
  - It is kept out of its entry's measure, then measured alone, with ECharts bundled in and the
    entry point external. "The entry point" here is the FESM plus every chunk the FESM imports
    statically, because the build splits out the code the entry and the engine share.
  - A budget naming an unknown entry point or chunk fails.
- **Testing and showcase.**
  - `TmChartHarness` in `@tellma/core-ui/testing`.
  - Showcase stories `chart` (the gallery), `chart-bidi` (the canvas-text battery) and
    `chart-lazy`.
  - Usage examples in `chart/tm-chart.examples.ts`, compiled by `docs-examples.spec.ts`.
- **ECharts 6.1.0.** Added to the pnpm catalog and to `@tellma/core-ui`'s dependencies and
  `allowedNonPeerDependencies`.

### Deviations

1. **A Trusted Types shim, against §7.5's claim that ECharts makes no policy-relevant assignment.**
   - zrender's canvas painter runs `root.innerHTML = ''` in its constructor and in `dispose()`.
   - Under the host's Trusted Types CSP that throws.
   - The engine defines an own `innerHTML` accessor on the chart's root element only: `''`
     becomes `replaceChildren()`, and any other value goes to the native setter, where Trusted
     Types still refuses it.
   - `tm-chart.csp.spec.ts` fails without the shim and passes with it.
   - ARCHITECTURE.md now says this.
2. **Engine chunk budget is 200 KB, not 170.**
   - Spec 0024 §12 sets 170 KB.
   - The chunk measures 199.74 KB gz (level 9), with the entry point and the code it shares
     external.
   - ECharts 6.1.0 alone, with the modules the chart draws, weighs 194.38 KB under the same
     minify and gzip. That set is bar, line and pie; grid, tooltip, legend, markLine and aria;
     and the canvas renderer.
   - Core plus the canvas renderer plus one chart type alone is 122.03 KB.
   - Dropping any one module saves 1.1–16.9 KB, and each module is a feature the chart draws.
     The adapter is the remaining 5.4 KB.
   - Measurements: `.tmp/pc194-echarts-weight.log`. The note is in `package.json` `budgetNotes`.
   - The `./chart` entry is 6.56 KB, so its ceiling is 6.6, under the spec's 9.
3. **Extra chart tokens** beyond the series and ramps:
   - `positive`/`warning`/`negative`;
   - `surface`, `tooltipBg`, `tooltipBorder`, `decal`;
   - `fontSize`, `height`, and the `card*` metrics.

   The canvas cannot read `var()`, so every colour the engine paints is a token the theme bridge
   resolves.
4. **The holder div carries `role="img"`, not the canvas.** ECharts owns the canvas and recreates
   it on init, so the accessible name and description live on the stable holder. The figure is
   `dir="ltr"` so the plot never mirrors, and a class gives the canvas the page direction for its
   text.
5. **The canvas-text marks are refined for Arabic-Indic signs.** Inside an LTR run that holds
   Arabic-Indic digits, a sign gets an LRM on each side. The bidi algorithm treats a sign beside Arabic-Indic digits
   by their AN class, not the run's LTR embedding. Without the marks, the sign drifts to the other
   side of the number in a right-to-left base. The `chart-bidi` cases `negative-arabic` and
   `percent-arabic` compare this pixel for pixel.
6. **A local `TmChartJsonSchema` type.** `@tellma/core-ui` cannot import `@tellma/core`'s JSON
   Schema type.
7. **One `point` template serves both** tooltip lines and pie labels ("{label}: {value}"), and
   `share` serves percent labels. They are the same sentence, so I used one key rather than two.
8. **The diverging palette applies to a single non-pie series only.** It colours by sign. With
   several series or a pie it falls back to categorical, because sign colour would collide with
   series identity.
9. **Percent ticks** for percent measures and for normalized stacks. A normalized stack plots
   shares of the absolute total.
10. **The table view stands in when a plot can't be drawn**: for an unknown type, or when the
    engine fails to load or render. Render errors are also written to `console.error`.
11. **Pies drop slices whose value is ≤ 0.** The table still lists them.
12. **Lines take no decals; an area's fill does.** Line identity comes from symbols and dashes
    (8 symbols, with the dash per cycle). Where decals do not apply, the style carries no `decal`
    key. ECharts 6.1.0 types allow `decal: 'none'`, but its style visual assigns `.dirty` to the
    value, which throws on a string. That bug sent every single-series column or bar to the table
    until the render-matrix unit test caught it.
13. **`ɵtmCanvasText` / `ɵTmCanvasPiece` are exported** (ɵ-prefixed) so the showcase's bidi
    battery draws exactly what the engine receives.
14. **The table view imports `@tellma/core-ui/grid` statically.** It is a sibling entry point the
    app usually already has, and the table is the accessible fallback that must not wait on a
    chunk.
15. **'chart' is classified in `OLDER_FOLDERS`** in `additions-axe.spec.ts`, as pivot was.
16. **The visual check uses pixel-colour assertions** per type and theme, not screenshot goldens:
    - a token colour must paint more than 40 px;
    - the first column must not move in RTL;
    - the canvas computed direction is checked.
17. **`chart-lazy` story added** for the engine-loading test.
18. **The size gate's lazy-chunk extension** (`lazyChunkBudgetsInKb`) is new tooling that no spec
    names. Spec 0024 §12 budgets the engine chunk at the app level; this gate holds it per package.
19. **Line markers do not wait for `markers: true` (Review 1).** Every line series shows its
    marker shape whenever the chart has two or more line series, under `forceDecals`
    (`forced-colors`, `prefers-contrast: more`), or with the diverging palette, so that §7.7's
    "lines differ by marker shape" always holds. `markers` now decides only for a single,
    categorical line. Area fills keep their decals, as before.
20. **The sequential ramp skips its faint steps (Review 1).** Series spread over the steps that
    meet 3:1 against the chart surface (§7.8) in the active scheme: steps 4–7 on the light card and
    the passing steps on the dark one. With fewer than two passing steps, all seven are used, so
    the series still differ. `tokens.spec.ts` requires at least three passing steps, step 7, and
    both diverging poles at 3:1 in every scheme and preset.
21. **A normalized stack ignores `min`, `max` and `thresholds` (Review 1).** Shares and values do
    not share an axis. `tmValidateChartSpec` accepts such a spec rather than reporting it: a user
    who switches a saved chart's stack mode would otherwise lose the thresholds or face an invalid
    spec. The TSDoc on the three options says so.
22. **The bidi battery's facade cases (Review 1) compare glyph placement, not text borders.**
    `chart-bidi` now draws two `tm-chart`s (a column chart and a pie, under `ar` and `ar-EG`) in
    each direction. Its probe reads the engine's own display list and compares, pixel for pixel,
    every text span zrender paints (categories, legend entries, ticks, the threshold label, and
    negative data labels in `ar` and `ar-EG`) with its runs drawn apart at the span's transform,
    font and alignment, over the scene repainted without it. Its limits:
    - Text borders (the data labels' white halo) are taken off every span while the probe draws.
      zrender strokes the whole marked string, and the canvas composites a border's overlap where
      the runs it shapes apart meet differently from separate strokes. That leaves up to ~100 px of
      halo alpha that differ, with the glyph fill equal. The halo says nothing about the order of
      the runs.
    - Pixels painted by later elements (a threshold line across a label) are excluded.
    - Spans drawn through a clipping path are skipped.
    - The rich-text tooltip (drawn only on hover) and a label truncated by `overflow: 'truncate'`
      are not drawn in the battery.

    It runs on Chromium in the PR tier; Firefox and WebKit run nightly.
23. **`./chart` raised from 6.6 to 6.78 KB under D-031 (Review 1).** The review fixes add 0.18 KB:
    - the table fallback for engine errors after the first draw, cleared per spec, behind an
      injectable engine loader;
    - the drawable check on placeable points;
    - the range read in one loop.
    The dev-mode validation is dropped from production builds. The spec's ceiling is 9. The engine
    chunk measures 199.96, under 200: the line markers and the ramp filter were paid for by a
    narrower colour parser.
24. **No host-facing signal for the table fallback.** A host cannot yet tell that the facade fell
    back to the table, for example to disable Show as chart. No spec names such an output, so none
    was added.

### Open risks

- **Pixel equality in `chart-bidi`** may need tolerance on Firefox or WebKit if kerning across a
  mark differs from drawing runs apart. It ran on Chromium only here.
- **The Trusted Types shim** depends on zrender writing `innerHTML` to the element passed to
  `init`. A zrender upgrade that writes elsewhere would surface as a CSP spec failure, not
  silently.
- **The 200 KB engine ceiling** leaves 0.26 KB headroom. Any ECharts upgrade will need a
  re-measure.

#### Major

**R1-1 — Line series are told apart by colour alone. Contrast settings do not change this.**
`chart/internal/chart-option.ts:303`, `:640-642`; `chart/internal/chart-option.spec.ts:190-201`.

What the code does:
- `decals` is false for `line`.
- Each line series gets its own `symbol`, but `showSymbol` is `options.markers === true`. The default spec, with no `markers`, draws no marker.
- `LINE_TYPES` changes the dash only per cycle of eight.

Failure scenario:
- A two-series line chart, such as the gallery's `line`, draws two solid lines that differ only by hue. Spec §7.7 says "Lines differ by marker shape". WCAG 1.4.1 also applies.
- `forceDecals`, under `forced-colors` or `prefers-contrast: more`, changes nothing for lines, against §7.7's "always apply".
- The legend shows eight distinct symbol icons that appear nowhere on the plot.
- The diverging palette on a `line` colours only the hidden symbols, so it has no visible effect.

The unit test pins `showSymbol: false` for a two-series line, so it locks the gap in.

Suggested fix:
- Show the symbols whenever there are two or more line series, or when `forceDecals` is set. `markers` would then decide only for a single series.
- Or give each series in the first cycle its own dash.
- Add an option test for two series without markers, and one for `forceDecals` on a line.
- If the spec meant that `markers: false` has no shapes, flag the conflict instead of shipping colour-only lines.

**R1-2 — The `sequential` palette draws its first series below 3:1.**
`chart/internal/chart-option.ts:293-299`.

What the code does: `slotColor` spreads steps `0 … steps-1`, so the first series always takes `sequential.1`, the faintest step.

Failure scenario:
- In light, `--sequential-1` is `teal.100` `#CBE6EC`, about 1.3:1 on the white `surface.card`. In dark it is `teal.900` on the dark card, also far below 3:1.
- A two-series sequential column chart therefore draws its first series as near-invisible bars, against §7.8's "Marks meet 3:1 (WCAG 1.4.11)". The decal, 60 % surface on that fill, is invisible too.
- The gallery's sequential doughnut has the same problem for its first slice.
- `chart.spec.ts:104` checks only `ramp7`, and the token test checks only the series, so nothing catches it.

Suggested fix:
- Spread over the steps that meet 3:1 against the surface. For example, start at the first step that passes, resolved per scheme from the theme.
- Or give sequential marks an outline in the `axis` ink.
- Add an option test and a token-level contrast check for the steps the palette can pick. Otherwise, flag the §7.7/§7.8 tension for a ruling.

**R1-3 — `chart-bidi` never draws through the facade, and the case for a negative Arabic data label is missing.**
`showcase/src/app/chart/chart-bidi-story.ts:156-163`; `e2e/specs/chart-bidi.spec.ts:74-96`.

What the code does: the "together" canvas is drawn with the browser's own `fillText(ɵtmCanvasText(...))` on a plain canvas.

What the spec asks: §14 asks for "a mixed label drawn by the facade equal in pixels to its runs drawn apart", and "a negative data label in `ar`".

Failure scenario: nothing tests the marked strings as zrender actually draws them. That path includes:
- `Text` layout and `textAlign` per component;
- the horizontal-bar axis labels and vertical legend that use `overflow: 'truncate'`, where zrender cuts the string and can drop a closing mark;
- the rich-text tooltip, which zrender splits into tokens.

An ECharts upgrade that changes any of these passes the battery. The negative-arabic case formats with `ar-EG` outside the chart, not as a data label of a chart in `ar`. This narrowing is not among the Deviations.

Suggested fix:
- Add facade cases: a `tm-chart` in each direction whose category label, legend entry, data label (a negative value under `ar`) and threshold label are mixed. Compare a crop of its canvas against the same runs drawn apart at the position and font the engine used. Alternatively, render one ECharts `graphic` text per case through the adapter's option path.
- At minimum, record the narrowing under Deviations, with what it leaves untested.

**R1-4 — No test redraws on a live theme, direction, locale or contrast change.**
`e2e/specs/chart.spec.ts:115-121`; `chart/tm-chart.spec.ts`.

What §7.4 requires: re-reading the tokens and redrawing "on every theme, direction or locale change".

What the tests do:
- "switches the colours with the theme" loads the page twice and compares the resolved `--chart-series-1` token in light and dark. It never looks at the canvas and never switches live.
- No unit or e2e test flips `data-theme`, `dir` or the locale on a drawn chart and checks the pixels or the option.
- The direction unit test only checks the computed CSS `direction` of the canvas.
- No test exercises the `forced-colors` and `prefers-contrast` media path that turns on `forceDecals`.

Failure scenario: dropping `this.environment.theme()` from `request`, or breaking the `MutationObserver` filter, still passes every suite. A user who toggles the theme then sees the light palette on a dark card.

Suggested fix:
- An e2e that draws in light, switches the theme through the showcase toggle and asserts `series1` dark pixels on the canvas.
- A unit test that flips `document.documentElement.dir` and checks the legend's order or side.
- A locale switch that checks the tick text through the option, for example with a spy on the engine's `setOption`.
- An `emulateMedia({ forcedColors: 'active' })` case that checks decals on a single-series column.

#### Minor

**R1-5 — Error paths: an engine error after the font wait is unhandled, the table fallback sticks, and neither path is tested.**
`chart/internal/chart-engine.ts:224-229`; `chart/tm-chart.ts:266`, `:312`, `:436-442`, `:472-477`.

- When `document.fonts.check` fails, which is likely on the first Arabic chart of a page, `draw()` runs again from `fonts.load(...).then(done, done)`.
  - A throw from `ɵtmBuildChartOption`, `init` or `setOption` there becomes an unhandled rejection.
  - The chart stays blank instead of falling back to the table, as deviation 10 promises.
- `engineFailed` is never cleared. After one failed render, every later spec bound to the same instance shows as a table, even a valid one. That includes a report host re-running into the same `tm-chart`.
- The host also has no way to know the facade fell back, for example to disable Show as chart.
- No test covers:
  - a rejected `import()`;
  - a render throw;
  - a destroy while the chunk is loading.

Suggested fix:
- Route the async redraw's errors to the same fallback. For example, have the engine take an `onError` callback, or return a promise from `render`.
- Reset a render failure, but not a load failure, when the spec changes.
- Add unit tests for all three paths.

**R1-6 — A paged horizontal legend keeps left-to-right order on a right-to-left page.**
`chart/internal/chart-option.ts:362-375`.

When the wrapped lines exceed `maxRows`, the one `scroll` legend lists `entries` in logical order with no reversal. Many series in RTL then read with the first item at the left, against §7.6 ("the legend's … item order" follows the page). The wrapped-lines path reverses them correctly.

Suggested fix: reverse `data` for RTL, starting the pager at the last page with `scrollDataIndex`. Or always use the wrapped lines and cap them with a "+n" entry. Add an RTL test.

**R1-7 — Normalized stacks silently drop thresholds and the fixed `min`/`max`, and this is not declared.**
`chart/internal/chart-option.ts:548`, `:565-566`.

A spec with `stack: 'normalized'` plus `thresholds` or `min`/`max` passes `tmValidateChartSpec`, then draws without them. The behaviour is reasonable, because shares and values do not share an axis. But it is neither a validation code nor a listed deviation.

Suggested fix: list it under Deviations. Either document it on `TmChartOptions`, or make `tmValidateChartSpec` report it with a code such as `normalized-axis`.

**R1-8 — A spec that was not validated can draw empty axes or throw.**
`chart/tm-chart.ts:294-302`, `:322-331`.

- `drawable` looks only at the type and at whether a value exists. A `column` or `pie` spec with `dimensions: []`, or with row indexes past the member lists, reaches the plot and draws empty axes or an empty disc. §7.2 says "never empty axes".
- A spec missing `measure` throws inside a computed.
- `Math.min(...values)` and `Math.max(...values)` throw a `RangeError` on WebKit past 65,536 points. JavaScriptCore caps a call's argument count, and the facade advertises large mode from 2,000 points.

Suggested fix: compute the range with a loop. Base `drawable` on the points the builder can place, so that anything else falls to the table. In dev mode, run `tmValidateChartSpec` and `console.error` its problems.

**R1-9 — The lazy-engine e2e would pass without the engine chunk.**
`e2e/specs/chart.spec.ts:229-244`.

The test passes if any script request follows the click. It never checks that the request is the engine chunk, or that no ECharts code loaded with the card. A static import that put the engine in the story's chunk could still pass, if anything else loads on click.

Suggested fix: assert that the URLs requested before the click include none matching `/chart-engine|echarts/`, and that a request matching it follows the click. The equivalent check over `performance.getEntriesByType('resource')` would also do.

**R1-10 — Interface members without TSDoc (AGENTS.md).**

- `chart/internal/chart-engine.ts:44-47`: the members of `Hovered`.
- `chart/internal/chart-option.ts:47-53`: the five members of `DecalPattern`.
- `chart/internal/chart-option.ts:111-114`: the members of `PointParams`.
- `chart/tm-chart-schema.ts:288-293`: the four members of `ValidSpec`.

Suggested fix: add a one-line TSDoc to each.
