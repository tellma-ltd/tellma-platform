### Deviations

1. Each retention statement binds only its own period, as `@tb{b}_p0`; the spec numbers the succeeded period `p0` and the failed period `p1` across statements that never share a batch.
2. A band's delete page declares as writes `core.Jobs`, `core.ScheduleStates` and every job entity's table: the FKs' `ON DELETE SET NULL` writes them, and the change-tracking audit refuses undeclared writes.
3. Each confirmation key's blank/length check runs in the hook (no element-level attribute exists); the list's presence and count are attributes (`[Required, Length(1, 16)]`; an empty list reports `Validation.Invalid` with attribute `Length`). The key length bound is `JobLimits.MaxConfirmationKeyLength = 100`.
4. The `Confirm` securable action is declared by the service (`JobService.Confirm`), not added to `AccessActions`; it ranks after the platform's actions.
5. Progress keys are dotted (`Jobs.RetentionProgress`, `Jobs.TreeVerifyProgress`), rendered from `Jobs_*` resources, like the platform's error codes.
6. `core.tree-verify` keeps the default lease (the spec names none).
7. `JobLabels` is registered with no server consumer yet: the browser renders labels from the string pack and `jobHandlers` (spec 0028); the server renderer is the contract a server-rendered surface (mail, export title) will use.
8. Action label resources: `Action_Retry` ("Retry"), `Action_Cancel` ("Stop"), `Action_Resume` ("Resume") as the shared fallbacks, and `Core_Job_Action_Confirm`.

### Open risks

- The held-requester withdrawal is best effort across RT1 and the persist (spec's Decisions record 22).
- PC-146 adds built-in 2 and `core.Notification` self-scope; whichever integrates second regenerates the three migrations and merges `AccessModelTests`'s seeded list and `AccessEvaluationTests`'s `SelfScoped` (both written in PC-146's shape to keep the merge mechanical).

### What reviewers should examine hardest

- The withdrawal decisions in `JobService.WithdrawHeld` (null requesters, chunking, the empty-list gap rule).
- `ValidateActionAsync`'s per-target refusals and the confirm coverage check against the statement's repeat.
- `JobRetentionHandler`'s loop termination, cancellation between pages, and the declared writes.

#### Minor

**R1-1 (minor). A requested cancel can stop a committed retention-stop page's withdrawals.**
- *Where.* `JobRetentionHandler.cs:93-99`: the page runs, then
  `notifier.WithdrawAsync(..., item.CancellationToken)`.
- *Failure scenario.* An administrator stops the running `core.job-retention` job (a renewal
  reports `CancelRequestedAt`) while a stop page is in flight.
  1. The page commits. Its rows are now `Pending` and flagged.
  2. The item token is cancelled, so `WithdrawAsync` throws before it sends anything.
  3. The next run's stop page cannot find those rows again, because they left
     `PendingConfirmation`.
  4. Their `core.job.pending-confirmation` notices stay in the requesters' inboxes, saying a job is
     waiting for them, until notification retention. Meanwhile the job ends `Cancelled`.

  §6.6 cancels only the item token for a requested cancel precisely so that a handler can finish
  what it committed. The scope token already guards every round trip the handler starts (§3.2).
- *Fix.* Withdraw a committed page's notices with `CancellationToken.None`, or with no explicit
  token so the scope token applies. Keep `ThrowIfCancellationRequested` at the top of each loop.
  Add a test: cancel the item token from a fake notifier's first withdrawal call, or between two
  stop pages, and assert that all of the committed page's withdrawals were sent.

**R1-2 (minor). The statements' repeats are pinned only as text; the integration tests' repeats
stop at the validation hook.**
- *Where.* `JobServiceTests.cs:70-72, 143-146, 186-187, 208-211`. Each "repeat" goes through the
  service, whose hook refuses it, so the statement never runs a second time. At
  `JobServiceTests.cs:143-146` the running job is cancelled twice, but the test asserts only its
  status.
- *Failure scenario.* §16 pins "each statement's repeat (no row matched, save a `Running` row's
  cancel flag)", and "a repeat of the statement matches no row" for `confirm`. The batch's
  `Idempotent = true` relies on that property when the executor re-runs an ambiguous persist. A
  regression in a `WHERE` that keeps the text's shape would pass the goldens and every
  service-level test, because the hook refuses the repeat first. Examples: a mistyped literal that
  still matches, the coverage `NOT EXISTS` inverted to `EXISTS`, or a wrong alias in the requester
  check. The same gap covers the second `cancel` re-stamping the flag.
- *Fix.* Add a statement-level integration test in the style of `JobRunTests.Statements`:
  - run each of `JobStatements.Retry`, `Cancel`, `Resume` and `Confirm` on a `Persist` batch over
    stored rows, run it again, and assert the second run matched no row;
  - assert that `Confirm` matches no row for a caller other than the requester, or when a recorded
    key is missing;
  - assert that a second `Cancel` of a `Running` row advances `CancelRequestedAt`.

**R1-3 (minor). Several in-scope behaviours have no test that fails when they break.**
- *Where.* `JobServiceTests.cs`; `JobService.cs:77, 125, 156` (`Queue().Nudge`).

  - Removing any `Queue().Nudge(context.Batch)` fails no test, although §11.1 says `retry`,
