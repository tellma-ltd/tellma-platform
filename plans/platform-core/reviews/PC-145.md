# PC-145: Job admin surface, labels and platform maintenance handlers

## Implementer notes

### What was built, and where

- **The jobs' stack** (`src/core/Tellma.Core/Jobs/JobService.cs`): `JobService : EntityService<Job>` with `retry` (`Retry`), `cancel` (`Cancel`, `Destructive`, `AllowWhenReadOnly`), `resume` (`Resume`) and `confirm` (`Confirm`, `Mcp = Hidden`, arguments `ConfirmJobArguments([Required, Length(1, 16)] Keys)`). Each method loads the targets (RT1), appends its fixed statement over the loaded ids, publishes `job.changed` per target requester, and `retry`/`resume`/`confirm` nudge the local poller on commit (`JobQueue.Nudge`, recording-batch aware). `cancel`/`resume` declare the RT1 load of the distinct requesters of `Held` rows outside the targets (raw `Loader.Sql`, status spelled as a literal so `IX_Jobs_Held` matches) and withdraw `core.job.held` per released requester (chunks of 1,000) and `core.scheduler.gap` when no held row is left; `confirm` and the cancel of a `PendingConfirmation` row withdraw its `core.job.pending-confirmation`. `ValidateActionAsync` judges each target (`Jobs.NotRetryable`, `Jobs.NotCancellable`, `Jobs.NotHeld`, `Jobs.NotPendingConfirmation`, `Jobs.NotInitiator`) at the target's position, and each confirmation key (blank → `Required`, over 100 characters → `MaxLength`) under `Arguments.Keys[i]`.

### Deviations

1. Each retention statement binds only its own period, as `@tb{b}_p0`; the spec numbers the succeeded period `p0` and the failed period `p1` across statements that never share a batch.
2. A band's delete page declares as writes `core.Jobs`, `core.ScheduleStates` and every job entity's table: the FKs' `ON DELETE SET NULL` writes them, and the change-tracking audit refuses undeclared writes.
3. Each confirmation key's blank/length check runs in the hook (no element-level attribute exists); the list's presence and count are attributes (`[Required, Length(1, 16)]`; an empty list reports `Validation.Invalid` with attribute `Length`). The key length bound is `JobLimits.MaxConfirmationKeyLength = 100`.
4. The `Confirm` securable action is declared by the service (`JobService.Confirm`), not added to `AccessActions`; it ranks after the platform's actions.
5. Progress keys are dotted (`Jobs.RetentionProgress`, `Jobs.TreeVerifyProgress`), rendered from `Jobs_*` resources, like the platform's error codes.
6. `core.tree-verify` keeps the default lease (the spec names none).
7. `JobLabels` is registered with no server consumer yet: the browser renders labels from the string pack and `jobHandlers` (spec 0028); the server renderer is the contract a server-rendered surface (mail, export title) will use.
8. Action label resources: `Action_Retry` ("Retry"), `Action_Cancel` ("Stop"), `Action_Resume` ("Resume") as the shared fallbacks, and `Core_Job_Action_Confirm`.
