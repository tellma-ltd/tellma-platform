### Deviations

1. **Spec 0035 §1.1: the main module's budget.** The spec states 9 KB. The new figure is 11 KB
   (measured 10.59 after fix1; 10.47 before it), within 1.25 × 9 = 11.25. This needs Ahmad's
   ruling.
   - The bytes' cause: about 4.2 KB of code §1.1 places in this module. That is the tile header
     and status line, the widget context, the assignments body, the home page context and the
     `tm.home.*` telemetry. Fix1 adds 0.12 KB: the stale marker held until the next success,
     the cleared refresh applied once per generation, the grid's states for every laid-out
     tile, and the gated "View all".
   - Headroom: only about 0.66 KB is left under D-414's 11.25 (0.78 before fix1). §1.1 still places
     `tmDashboardModel`, `tmBindWidgetArguments`, `tmDashboardPage` and the grid's four deferred
     inputs (`dashboardId`, `dashboardParameters`, `view`, `refreshMinutes`) in this module. The
     dashboards checkpoints will probably reach the ceiling.
2. **No e2e arrival.** The assignments document is not a leader document until PC-207, so no
   server event can deliver it. "An arriving assignment updates its list and count in place; no
   other tile moves" (§15.4) is pinned at harness level instead: the store's copy changes, only
   the to-me list and count change, every tile keeps its placement, and the other bodies are the
   same elements. Real pixel boxes are checked only from skeleton to page (`home-geometry`).
   Until PC-207, Acme's assignment lists show their skeleton rows online.
3. **`TmDashboardWidgetModel.report` is not added.** `TmReportRef` does not exist yet.
4. **Grid inputs deferred.** The grid has no `dashboardId`, `dashboardParameters`, `view` or
   `refreshMinutes`; the reports and dashboard-page checkpoints add them.
5. **The menu holds Refresh only.** Open report and Export to Excel belong to the report widget.
6. **`TmHomePage` renders every home widget.** PC-123's declared-types filter is removed, now that
   all three types ship.
7. **`tm.home.rendered` starts at the route host's load start.** The spec says "route start". The
   route host's load start is read through the new `ɵTmLaunchTimer` export from the primary.
8. **Home rows are single-line.** The home variant of `tm-assignment-list` puts the title and the
   second line on one 31 px line, to fit ten rows in the 350 px tile (§15.3).
9. **"View all" accessible name.** "View all" is named "View all: {title}", because three tiles
   carry the same link text.
10. **initialJs warn lines.** The fixture app's line rises from 227.5 to 229, and Acme's from 228
    to 229.5. These are distribution-set warn lines, not spec numbers; the 260 KB error line is
    unchanged. See the open risks.

### Open risks, and what reviewers should examine hardest

- **First-frame regression of about 1 KB gzip, caused by chunking.** Only about 0.7 KB of raw
  bytes in the initial files changed (the core declarations and the route host's seam). However,
  because `./dashboards` now imports `@tellma/core/attention` (for `TmAttention`), Angular's chunk
  optimizer splits /attention out of /shell's chunk into a modulepreloaded file of its own. That
  split costs gzip, and the fixture's figure moved from ≤227.5 to 228.56, and Acme's from 227.80 to
  229.28. I confirmed this by diffing esbuild stats for the fixture at base and on this branch:
  the same eight initial files, +732 raw bytes, with /shell and /attention in two files instead
  of one. PC-163 re-measures the warn lines.
  - An alternative is a primary-level seam for the assignments copy, so that `./dashboards` does
    not import `/attention`. It needs a decision (D-number) because it moves attention state into
    the primary.
- **Ticks.** The tile's `linkedSignal` tick: a grid tick and a tile Refresh must each be exactly
  one new generation. The assignments body re-reads on any generation other than the first.
- **The `home` page context's `when`.** It is `assignedAt` for assignments and the visit time for
  recents.
- **`tm.home.rendered` waits for every tile to leave `loading`.** A list widget never reports a
  run, so it is "ready" once its chunk loads, and the event measures the frame with every body
  rendered (lists still in their skeleton until PC-207).
- **The skeleton-to-page geometry.** Check it at other widths: `home-geometry` covers only 1440
  and 390 px.

Findings:

**R1-1 (minor) A cleared refresh's `clear` flag stays on the tick, so any later `loading` report
drops the held time.** `client/projects/core/tellma-core/dashboards/src/tm-dashboard-tile.ts:531`.
`#report` clears `#executedAt` whenever the body reports `loading` while `untracked(this.#tick).clear`
is true. After Refresh (or `refreshAll`), the tick keeps `clear: true` until the next tick. So
when the body later reloads for any other reason, the tile drops the held "Updated {time}", shows
the pending bar again and marks the section `aria-busy` (`busy`, line 387), as if the user had
pressed Refresh. Reloads like this include a `parameters` or `settings` change, which §9.3 lets
a body key its `resource()` on, and a body's own retry. Spec 0034 §3.4's held result and §8.5
keep the time over a pending run that is not a forced refresh. The report widget will hit this
as soon as parameters feed it.
Fix: clear on the tick, not on the report. For example, keep the generation of the last cleared
tick, and drop the held time only on the first `loading` report of that generation. Or set
`#executedAt` to `null` in the same place that issues a clearing tick (`refresh()`, and a grid
tick with `clear`), which also clears the line in the click's frame (§18 "Instant feedback").
Pin it with a grid test: Refresh, ready, then a `parameters` change whose `loading` report keeps
the time.

**R1-2 (minor) The stale marker disappears while the next run is pending, not at the next
success.** `tm-dashboard-tile.ts:436`. `stale` is `run?.status === 'error'`. So after a failed
silent run over held data, the next run's `loading` report removes the marker, and it comes back
only if that run fails too. §8.5 says spec 0034 §3.4's marker "follows the time until the next
success". A wall display that retries every minute against a down server would blink the marker
off for each pending run. The test at `tm-dashboard-grid.spec.ts:559` goes from error straight to
ready, so it does not cover this.
Fix: keep a `#stale` signal that an `error` report sets while `#executedAt` is held, and that only
a report carrying a new `executedAt` (or a cleared refresh) resets. Extend the test with a
`loading` report between the error and the next result.

**R1-3 (minor) "View all" shows in present mode and on a denied list tile, against the code's own
comment and §12.4.** `tm-dashboard-tile.ts:125-129`. The comment says "neither on a denied tile,
nor in present mode", and the implementer notes say the header has none "on a denied tile or while
presenting". But the `@if (tile().list; as list)` branch checks neither `presenting()` nor
`tile().denied`: only the options menu does (`menuShown`, line 400). §12.4 makes present mode
"display only … so a stray tap never strands a lobby screen on a list page", and "View all" goes
to exactly such a page. A list type redeclared with `requires` and shown with `denied="show"`
would also offer a link beside its lock. The presenting test at `tm-dashboard-grid.spec.ts:621`
checks only the menu.
Fix: gate the link like the menu (`!presenting() && tile().denied === null`), and add a
presenting assertion for a list tile.

**R1-4 (minor) `tm.home.rendered` never fires if a home widget is left out.**
`client/projects/core/tellma-core/dashboards/src/tm-home-page.ts:57` waits for
`tiles.length === this.widgets.length`. Declarations merge by key with the last feature winning
(§4.3, spec 0024 §2.3), so an app can redeclare a core list type with `requires`. The grid then
hides that tile for users without the permission (`denied` defaults to `'hide'`, §2.3). That
leaves two tiles for three widgets, so the effect never settles and the visit is never timed,
with no error.
Fix: compare against the tiles the grid laid out, not the widget list. For example, read
`grid().tiles()` once it is non-empty and every status has left `loading`, or expose the laid-out
count. Pin it with a home test whose app redeclares `core.recents` with a `requires` the user
lacks.

**R1-5 (minor) The home lists' loading state adds two identically named region landmarks.**
`client/projects/core/tellma-core/attention-rows/src/tm-assignment-list.ts:156`. The home variant's
loading state is `role="region" aria-label="Loading assignments"`. Both assignment tiles show it,
and on Acme they always will until PC-207 serves the document. A screen reader's landmark list
then reads "My assignments, Loading assignments, Recently visited, Assigned by me, Loading
assignments", inside regions that are already labelled. The tray variant uses a busy, named `ul`
instead (`tm-attention-skeleton-rows`). axe's `landmark-unique` is a best-practice rule, and the
repo's scans run only the WCAG tags, so nothing catches this.
Fix: drop the landmark role. Mirror the tray: a busy `ul` or a `div aria-busy="true"` holding a
visually hidden "Loading assignments" text, with the bars `aria-hidden`. Then update the
`tm-assignment-list.spec.ts:137` expectation.

**R1-6 (minor) Three §16 and §9.2 behaviours have no test.** First, `tm.home.view-all` is never
asserted, and neither is "View all"'s in-app navigation with modifier-click left to the browser
(`tm-dashboard-tile.ts:506-516`). The grep finds no `view-all` in any spec, and no test clicks
the link. Second, recents' `tm.home.item-opened` (`tm-recents-widget.ts:122-126`) is untested;
only the to-me row is. Third, the assignments body's forced refresh, "Only a forced refresh ticks
them" (§9.2), calls `TmAttention.refresh('assignments')` (`tm-assignments-widget.ts:112-116`), but
no test runs `refreshAll()` over a list tile or checks that the first tick does not read. A
regression in any of these would pass the suite.
Fix: in `tm-home.spec.ts`, route `core.Assignment` and click "View all" on both lists. Assert the
event with `{ list }` and the navigation to the `by-me` tab, and assert that a ctrl-click does not
navigate. Click a recents row and assert `{ list: 'recents', position: '1' }`. Call the grid's
`refreshAll()` and assert one `assignments` refresh (and none before it).

**R1-7 (minor) Nothing pins §15.3's "a full list never scrolls", which is deviation 8's reason.**
§15.3 says a 33 px header and ten 31 px rows fit the 350 px tile from `sm` up, so "a full list
never scrolls and an empty one keeps its box". §8.4 says the header is 33 px "and neither depends
on data". Two things are tested: two rows of 31 px (`tm-assignment-list.spec.ts:151`), and the
tiles' outer boxes against the skeleton's in e2e, which are fixed whatever the content is. No test
renders ten rows with a count and "View all" in the header and checks the header height and that
the body does not overflow. A count, a link or a row that grows by a pixel would add a scrollbar
silently.
Fix: add a harness test over ten stored assignments with `open` > 0 and `core.Assignment`
routed. Assert that the header is 33 px (34 with its rule, matching the skeleton frame's header)
and that the card body's `scrollHeight <= clientHeight`. Below `sm`, assert that 44 px rows
scroll.

**R1-8 (minor) The budget deviation omits the bytes' cause, and the test list omits two touched
suites.** First, D-414 asks every budget left above the spec's number to be listed "with the spec
section, the stated number, the new figure and the bytes' cause". The commit's first deviation
and implementer notes item 1 give §1.1, 9 and 10.5 (10.47), but no cause; the cause is only in

Fix: add the cause to the deviation (the tile header and status line, the widget context, the

Ahmad as well: `./dashboards` now has 0.78 KB left under D-414's 11.25. §1.1 still places
