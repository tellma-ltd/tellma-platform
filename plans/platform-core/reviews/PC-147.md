# PC-147: TellmaHub, SignalR publisher and hosting modes

## Implementer notes

### What was built, and where

- **Hub** (`src/core/Tellma.Core.AspNetCore/Realtime/TellmaHub.cs`): internal, no invocable
  method. `OnConnectedAsync` reads the claims from `Context.User` alone (`TellmaHubClaims.TryRead`:
  `sub`, `tellma_tid`, `tellma_uid`, `tellma_sh`, each exactly once, ids positive with no sign),
  adds the connection to the tracker under the memo lock, then joins `HubGroups.Of(claims)`. A
  connection without the claims or under a remembered close is counted `connects{refused}`,
  logged `HubConnectionRefused` and aborted; one under a remembered close is first sent
  `session.ended` with the close's reason through `Clients.Caller`. Invocations and streams are
  refused by the protocol
  decorator (`TellmaJsonHubProtocol`, the one `json` protocol), counted
  `connects{invocation-refused}`.
- **Claims** (`TellmaHubClaims.cs`): `Create(RequestContext)` mints the `Tellma.Hub` identity from
  a bound context; `Select(principal)` is Azure SignalR Service's `ClaimsProvider`, the subject and
  the three hub claims and nothing else.
- **Front door** (`HubFrontDoor.cs`, `Tenancy/TenantMiddleware.cs`): on the Hub surface the
  middleware runs the guard, then one prologue-only Read through `IGuardedBatchRunner` (always,
  not only on a cold cache), then adds the hub identity. Every refusal from tenant parse to guard
  to prologue is counted and logged (`Refused`), unless the client went away. A Hub-surface
  request the pipeline answers 401 or 403 before the door (authentication, authorization, the CSRF
  control) is counted and logged the same way by `HubRefusalMiddleware`, ahead of
  `UseAuthentication`, with the code of the problem written (`ProblemWriter.WrittenCode`).
- **Groups** (`HubGroups.cs`): `t{tid}`, `t{tid}.u{uid}`, `t{tid}.s{subject}`, `t{tid}.x{handle}`.
- **Tracker** (`HubConnectionTracker.cs`): singleton, `ISessionTerminationListener` and
  `ITenantStateListener`; does nothing when `Enabled` is false. Each close remembers its key for
  5 minutes, tells `session.ended` to the local connections one by one, then aborts them, counting
  `closes{reason}` and logging `HubConnectionsClosed`. Session end and revoke run on one instance,
  so when the mode reaches every instance they also send to the session group (in every tenant of
  the local connections and of the subject's membership hints, read only then) or the subject
  group, with `GroupExcept`. Suspended, Retired and removed run on every instance, so each tells
  its own connections alone. Each send has its own `try`. Any other state sends
  `cache.changed {tag:'tenant'}` to the tenant's local connections and closes nothing.
- **Publisher** (`SignalRClientEventPublisher.cs`): the tenant group, or the distinct user groups
  in the scope's tenant; a tenantless scope is refused before anything is sent.
- **Options and naming** (`RealtimeOptions.cs`, `RealtimeApplicationName.cs`): `Tellma:Realtime`
  (`Enabled`, 15 s keep-alive, 150 s client timeout at least twice the keep-alive,
  `ExpectedInstances`); the Azure application name is the deployment id with `_` for `-`.
- **Composition** (`TellmaRealtimeServiceCollectionExtensions.cs`): `AddTellmaRealtime(configure)`,
  idempotent, called by `AddTellma`; registers SignalR, the hub's options through
  `AddHubOptions<TellmaHub>` (so the 4 KB frame limit, detailed errors off and filters take
  effect), the intervals read unvalidated from configuration (the handler is built at `MapTellma`,
  before the options gate), `TellmaUserIdProvider`, the tracker, the publisher and status
  factories honouring `Enabled`, and the hosting check. Every call strips the framework's plain
  `JsonHubProtocol` the builder delegate may add.
- **Mapping** (`TellmaEndpointRouteBuilderExtensions.cs`): `MapHub<TellmaHub>` on the Hub group
  with `CloseOnAuthenticationExpiration`, `NoActivityStampMetadata`, `AllowMember()`, skipped when
  `Enabled` is false.
- **Hosting** (`RealtimeHosting.cs`, `RealtimeHostingCheck.cs`): the mode from the registered
  lifetime manager (in-process, Azure, Redis, unknown); `host.realtime-hosting` fails an unknown
  manager, a connection string without Azure, another application name, a deployment id that
  cannot name one, and an in-process hub with Jobs off; warns for App Service or
  `ExpectedInstances > 1` without a backplane.
- **Azure line** (`src/defaults/Tellma.Defaults.Azure.AspNetCore/AzureWebDefaultsTellmaBuilderExtensions.cs`):
  `AddAzureSignalR` through `AddTellmaRealtime`'s delegate, `ClaimsProvider = Select`, a 5-minute
  token, the application name from `DeploymentIdentity` (`RealtimeApplicationName.TryFrom`, left
  unset for an id that cannot name one, which the check reports); `Microsoft.Azure.SignalR` 1.33.1
  pinned.
- **Telemetry**: `RealtimeMetrics.cs`, `RealtimeLog.cs`; KQL alerts in `infra/monitoring/realtime/`
  (refused connects per instance, access-revoked closes untold).
- **Core**: `SessionEndedEvent` (name, reasons, payload) registered as a client event in
  `CoreFeature`.
- **Test layout** (after review 1): the shared web test host (`TellmaTestHost`, its fakes and
  probes, `RealtimeTestHost`, `HubClient`, `ConnectedProbe`) is `test/shared/Tellma.Testing.WebHost`;
  the offline Azure composition test is `test/defaults/Tellma.Defaults.Azure.Tests`; the live suite
  is `test/defaults/Tellma.Defaults.Azure.AspNetCore.IntegrationTests`. `Tellma.Core.AspNetCore.Tests`
  no longer references the Defaults bundle.
- **Live suite**: `test/defaults/Tellma.Defaults.Azure.AspNetCore.IntegrationTests/AzureSignalRLiveTests.cs`
  (`Category=Integration`, `Live=true`), skipped unless `TELLMA_SIGNALR_TEST_CONNECTIONSTRING` is
  set; the `signalr-live` job in `.github/workflows/nightly.yml` (environment
  `live-realtime-tests`, secret `SIGNALR_TEST_CONNECTIONSTRING`, a require step so a missing
  secret fails rather than skips), off until the repository variable `SIGNALR_LIVE_ENABLED` is
  `'true'`. Each test runs under a random environment name, so its application name on the shared
  instance is its own.
- **Docs**: READMEs of `Tellma.Core.AspNetCore`, `Tellma.Defaults.Azure.AspNetCore`, the test
  projects and `Tellma.Testing.WebHost`; `ARCHITECTURE.md` (the Azure bundle's hub line, the
  hosting check under Real-time and Redis, the nightly workflow's comment).

### Deviations

1. The session group is `t{tid}.x{handle}`, not `x{handle}`: the client drops envelopes whose
   `tenantId` is not its own, so an untenanted group cannot carry a correct envelope to tabs in
   two tenants. A session's end is therefore sent per tenant: the tenants of the local connections
   plus the subject's membership hints (a hint read failure is logged, `HubSessionTenantsUnread`).
2. `session.ended` goes to the instance's own connections one by one and to the rest of the group
   with `GroupExcept`, rather than one group send. On Azure SignalR Service a direct send to a
   local connection is written on that connection's own server connection, the one its abort's
   close follows (verified in the SDK 1.33.1 source); a group send may take another server
   connection and be overtaken by the close. It also tells a connection that is admitted but still
   joining its groups.
3. The check is `host.realtime-hosting` (the host checks' prefix), not `realtime-hosting`.
4. `OnRemovedAsync` is treated as tenant-unavailable (reason `tenant-unavailable`).
5. A 5-minute memo of ended sessions, revoked (tenant, subject) pairs and unavailable tenants
   refuses late joiners whose negotiate passed before the close; a user reactivated within the
   window is refused for up to 5 minutes. A ReadOnly, Frozen or Active change clears the tenant's
   memo.
6. The hosting check passes everything when `Enabled` is false, and fails an unknown lifetime
   manager.
7. `RealtimeApplicationName.From` throws when the deployment id does not start with a letter (the
   service's rule); `TryFrom` answers false, the Azure line then leaves the name unset, and the
   hosting check fails it as `host.realtime-hosting`.
8. The Azure application name is set with `AddOptions<ServiceOptions>().Configure<DeploymentIdentity>`
   rather than inside the `AddAzureSignalR` lambda, which has no service provider.
9. `WEBSITE_INSTANCE_ID` is read through `IConfiguration` (environment variables are a source), so
   tests set it without touching the process environment.
10. `TellmaHub` is internal (SignalR activates it with `ActivatorUtilities`).
11. `CoreFeature`'s client-event literals became constants (`SessionEndedEvent.Name`).
12. Withdrawn after review 1: the Hub surface's 401 and 403 answered before the tenant middleware
    are now counted in `connects{refused}`.
13. The hub's intervals are read from configuration unvalidated for `HubOptions<TellmaHub>`, so a
    bad value fails at the options gate as a composition problem rather than as an
    `OptionsValidationException` when `MapTellma` builds the handler.
14. The live suite lives in `test/defaults/Tellma.Defaults.Azure.AspNetCore.IntegrationTests`,
    not 0021 §12's `test/core/Tellma.Core.AspNetCore.IntegrationTests`: it composes the Azure
    bundle, so it is the Defaults line's integration suite.
15. The tenant-state rows of 0021 §6.5 ("to `t{tenantId}`") are sent to the instance's own
    connections of the tenant, not to the tenant group: every instance's registry runs the change,
    so a group send through a backplane or the service would reach each connection once per
    instance. In the in-process mode no close sends to a group, which would reach only the
    connections the tracker already told.

### Open risks

- On Azure a service token minted before a revocation can open a connection for up to its
  5-minute lifetime; the memo that refuses it is per instance, so a connect routed to another
  instance is refused only by the closes that instance itself ran (its own listener calls).
- Long polling runs the prologue on every poll request.
- The live suite has never run: it needs the `live-realtime-tests` environment, its secret and
  the `SIGNALR_LIVE_ENABLED` variable. Until the variable is set, the nightly's `signalr-live` job
  is skipped; once it is, a missing secret fails the require step.
- A tenant-state change reaches a connection only through the instance that hosts it, so an
  instance whose registry refresh fails leaves its own connections untold until a later refresh
  or their ticket's expiry.
- Ordering between two separate sends is not guaranteed on Azure; the live suite asserts absence
  after a barrier plus a 3-second settle, not by order.

### What reviewers should examine hardest

- Hub authentication: that no path reaches `OnConnectedAsync` with claims the front door did not
  mint (`HubFrontDoor.EnterAsync` throws if the principal already carries hub claims; `TryRead`'s
  exactly-once rule; the `/bypass` test).
- Tenant isolation of groups: every group name is tenant-qualified; the publisher's groups come
  from the scope's tenant only; envelopes name the connection's own tenant.
- What a client can subscribe to: nothing (no invocable method, invocations refused, groups only
  from claims).
- The tracker's memo and snapshot under one lock, and the direct-send-then-abort order.
- `RealtimeHosting.From`'s type-name matching of the Azure and Redis lifetime managers.

## Review 1

Reviewer 1 (Opus), commit dac43255. I built `Tellma.Core.AspNetCore.Tests` with Build succeeded,
0 warnings. `dotnet test … --filter "FullyQualifiedName~.Realtime.&Category!=Integration"` passed
69 of 69. I checked the Azure SignalR SDK 1.33.1 source for deviation 2, and the ASP.NET Core 10
`HubConnectionHandler` source for the `AddHubOptions` question.

Verified and sound:
- **No path reaches `OnConnectedAsync` with claims the front door did not mint.** `TryRead`
  requires each claim exactly once, and the door's `Carries` guard throws before it adds the
  identity. The `/bypass` test pins `claims-missing`. Claims are minted per request on a fresh
  ticket: `CatalogSessionStore.Materialize` deserializes per read, and the cookie handler clones the
  principal for renewal. So `AddIdentity` never leaks the hub identity into a stored session.
- **Groups are tenant-qualified and cannot collide.** Each family letter follows the fixed
  `t{tid}.` prefix.
- **The publisher addresses the scope's tenant alone.** It never uses `Clients.User`.
- **A client can subscribe to nothing.** The hub declares no method. Binding failures are counted,
  and both invocation kinds are tested.
- **No connection of another tenant or session can receive `session.ended`.** Every group send
  names one `(tenant, handle)`, `(tenant, subject)` or tenant. The direct sends go only to local
  connections filtered on the same key, and `GroupExcept` excludes exactly those.
- **`AddHubOptions<TellmaHub>` is required, and a test fails without it.**
  `HubConnectionHandler<THub>` takes the receive limit, detailed errors and filters from
  `HubOptions<THub>` only when `UserHasSetValues`, which only `AddHubOptions`'s
  `HubOptionsSetup<THub>` sets. Every realtime test waits on `ConnectedProbe`, a filter added to
  `HubOptions<TellmaHub>` (`RealtimeTestHost.cs:82`). Without `AddHubOptions` the filter never runs
  and every `ConnectAsync` times out. The 4 KB limit itself is not exercised at runtime (R1-3).
- **Deviation 2's ordering claim holds in the SDK 1.33.1 source.**
  - `ServiceLifetimeManager.SendConnectionAsync` writes a local connection's message with
    `clientConnection.ServiceConnection.WriteAsync`.
  - `ServiceConnection.ProcessClientConnectionAsync` writes the `CloseConnectionMessage` with
    `SafeWriteAsync` on the same server connection (`this`), and only after the application ends
    and the transport drains (`CancelOutgoing(true)`, then `await transport`).
  - A direct send that was awaited before `Abort()` is therefore ahead of the close on one ordered
    server connection.
  - A group send goes through `WriteAsync` on any server connection and can be overtaken.
  - One caveat: on `ServiceConnectionNotActiveException` the SDK falls back to another server
    connection. That connection's clients are dropping anyway.

### Findings

**R1-1 (minor): the live suite and the offline Azure composition test live in a core unit project
that now references a Defaults bundle**
- **Where:**
  - `test/core/Tellma.Core.AspNetCore.Tests/Tellma.Core.AspNetCore.Tests.csproj:13-15` (the
    `Tellma.Defaults.Azure.AspNetCore` reference)
  - `Realtime/AzureSignalRLiveTests.cs`
  - `Realtime/AzureSignalRCompositionTests.cs`
  - `Realtime/AzureSignalRTestHost.cs`
- **Problem:** This is deviation 14. ARCHITECTURE.md's package rules 1–8 govern shipped packages,
  and a test project is referenced by nothing, so no package edge breaks. The change does break two
  other rules:
  - ARCHITECTURE.md line 290 says `test/` mirrors `src/`, and that "*.IntegrationTests is reserved
    for suites needing external resources". Every other `Live=true` suite (SendGrid, ACS, Marmin
    UAE) is in a `*.IntegrationTests` project.
  - Spec 0021 §12 places the realtime live suite in `test/core/Tellma.Core.AspNetCore.IntegrationTests/`.
- **Consequence:** The PR-tier unit project of the adapter now carries `Microsoft.Azure.SignalR`
  and the whole Defaults bundle. Its offline Azure test starts the SDK's background server
  connections, against `offline.invalid`, in a unit run.
- **Right home:** The thing under test is `UseAzureWebDefaults()`'s realtime line, so:
  - The offline composition test belongs in `test/defaults/Tellma.Defaults.Azure.Tests`, which
    already references the bundle and holds `AzureRealtimeTests`.
  - The live suite belongs in a new `test/defaults/Tellma.Defaults.Azure.AspNetCore.IntegrationTests`.
  - `TellmaTestHost`, `RealtimeTestHost`, `HubClient` and `ConnectedProbe` move into a `test/shared/`
    project that both test projects reference.
  - The Defaults reference comes out of `Tellma.Core.AspNetCore.Tests`.
- **Spec flag (0021 §12):** The live suite's location should be the Defaults integration project,
  because it composes the Azure bundle.

**R1-2 (minor): the offline Azure composition test cannot tell a front-door refusal from a lost
route**
- **Where:** `Realtime/AzureSignalRCompositionTests.cs:154-158`.
- **Failure scenario:** The stranger case asserts only 404 and no `accessToken`. If the SDK's
  negotiate replacement dropped the endpoint's `TenantEndpointMetadata` or route, the request would
  also answer 404, from no match or from a non-Hub surface. The test would stay green while the
  Azure negotiate ran with no front door.
- **Fix:**
  - Assert the problem code (`TenantProblemCodes.NotFound`) and one `connects{refused}`, as
    `HubConnectTests.A_refused_negotiate_is_counted_and_logged_with_its_code` does.
  - Add a positive control: a member's negotiate passes the door and reaches the SDK. Offline it
    answers the SDK's not-connected 500, which `AzureSignalRTestHost.ConnectAsync` already relies
    on, and the door's prologue count rises by one.

**R1-3 (minor): the 4 KB receive limit is pinned only as an option value**
- **Where:** `Realtime/RealtimeCompositionTests.cs:104`.
- **Problem:** The `MaximumReceiveMessageSize` the handler enforces comes from
  `HubOptions<TellmaHub>` only through `UserHasSetValues`. A later change could restore the plain
  global options (for example, moving the limit to `AddSignalR(o => …)` while a filter stays on the
  hub options). The value would still read 4096 on `IOptions<HubOptions<TellmaHub>>`, but the
  handler would apply 32 KB.
- **Fix:** Add a runtime test: a connected client invokes with a 5,000-character argument, and the
  connection closes with an error. `EnableDetailedErrors = false` is likewise asserted only as a
  value. The invocation test's `DoesNotContain("t2")` covers that one in practice.

**R1-4 (minor): one failed group send leaves every local connection untold**
- **Where:** `src/core/Tellma.Core.AspNetCore/Realtime/HubConnectionTracker.cs:308-327`.
- **Failure scenario:** `TellAsync` runs the `GroupExcept` send and then the per-connection
  direct sends inside one `try`. On Azure SignalR Service the group send can fail on its own, for
  example with no server connection available for routing. When it does, the loop never runs, and
  `Close` then aborts the instance's connections without `session.ended`. Those connections are
  exactly the ones whose direct send would have succeeded on their own server connection. The client
  sees a bare close and reconnects into a refusal.
- **Fix:** Give each stage its own `try`, or send the direct sends first (they are independent),
  logging each failure. Add a test with a failing `IHubContext` group proxy, asserting that the
  local connection is still told and that `ClientEventFailed` is logged.

**R1-5 (minor): every session end reads the catalog, even when the read cannot help**
- **Where:** `src/core/Tellma.Core.AspNetCore/Realtime/HubConnectionTracker.cs:156-167`.
- **Problem:** `SessionsTerminatedAsync` calls `ITenantMembershipDirectory.ListAsync(subject)` on
  every sign-out, back-channel logout and revocation. It does so in two cases where the result is
  useless:
  - With `Tellma:Realtime:Enabled = false`, where the tracker stays registered as a listener.
  - In the in-process mode, where a group send reaches only this instance's connections, all of
    which are already in `local`.
- **Fix:** Read the hints only when the hub is enabled and `RealtimeHosting.ReachesEveryInstance`
  holds. Inject `RealtimeHosting` and `IOptions<RealtimeOptions>`, which the tracker can take.

**R1-6 (minor): a deployment id that starts with a digit fails the Azure line by an exception, not
by the startup gate**
- **Where:**
  - `src/core/Tellma.Core.AspNetCore/Realtime/RealtimeApplicationName.cs:340-344`
  - `src/defaults/Tellma.Defaults.Azure.AspNetCore/AzureWebDefaultsTellmaBuilderExtensions.cs:229-230`
- **Problem:** `DeploymentIdentity` admits applications such as `3m` or `-acme`
  (`IsLowercaseKebabCase` allows any first character). This is deviation 7.
  `RealtimeApplicationName.From` throws `ArgumentException` for them, and the bundle calls it inside
  the `ServiceOptions` configure delegate. The first resolution of `IOptions<ServiceOptions>`
  therefore throws. Most likely that is the SDK's own resolution while `MapTellma` maps the hub,
  ahead of the gate. The result is a bare exception rather than a `host.realtime-hosting` problem.
  The check would have reported it, since a check that throws is reported as a problem. Such a slug
  can never run on Azure SignalR Service.
- **Fix:** In the bundle, set `ApplicationName` only when the id is valid, and let the hosting
  check report the invalid id with its fix. Add a test with a digit-first slug.
- **Spec flag (0021 §6.6 / 0007):** The mapping is not total over the deployment-id grammar. Either
  0007 requires a letter first, or 0021 defines an injective escape.

**R1-7 (minor): the refusals the `connects{refused}` alert exists for are not counted**
- **Where:**
  - `src/core/Tellma.Core.AspNetCore/Tenancy/TenantMiddleware.cs:65-78` (counting starts at the
    tenant's resolution)
  - `infra/monitoring/realtime/connects-refused.kql`
- **Problem:** This is deviation 12. Spec 0021 §10.1's alert is "`connects{refused}` per minute (a
  stale SPA or an attack)". The two commonest signals of each never reach the tenant middleware:
  - a stale SPA's expired cookie is answered 401 by authorization;
  - a cross-origin negotiate is answered 403 by the CSRF control.
  
  So the alert watches only member, tenant-state and claims refusals, which are the rarest. The
  other instruments the deviation points to are not hub-specific, so the hub's share cannot be
  read from them.
- **Fix:** Count Hub-surface 401/403 answers into `connects{refused}`, for example with a small
  middleware on the Hub group's endpoints, or an `IAuthorizationMiddlewareResultHandler` decorator
  plus the CSRF control's refusal hook, tagged with the same reasons. If the alert is meant to be
  narrower, reword its comment and flag 0021 §10.1 instead.

**R1-8 (minor): a memo refusal is aborted untold, and most memo paths are untested**
- **Where:**
  - `src/core/Tellma.Core.AspNetCore/Realtime/TellmaHub.cs:54-60`
  - `HubConnectionTracker.cs:109-129`, `:211-214`
- **Failure scenario:** A connection refused by the memo is aborted without `session.ended`. Take
  a user deactivated and reactivated within 5 minutes (deviation 5):
  - Each reconnect passes the negotiate, which the user now may.
  - The connect then aborts it, with nothing to tell the client to stop.
  - The client loops for up to 5 minutes, counting `connects{refused}` on every attempt.
  
  The same holds for an Azure token minted before a close.
- **Fix:** Send `session.ended {refusal}` to the caller (`Clients.Caller` / `Clients.Client(id)`)
  before `Context.Abort()`. The refusal string is already the reason.
- **Tests missing:** Only the ended-session memo is tested
  (`A_connection_joining_under_an_ended_session_is_refused`). None of these is tested:
  - the revoked `(tenant, subject)` memo;
  - the unavailable-tenant memo;
  - its clearing by a ReadOnly, Frozen or Active change;
  - the 5-minute expiry. The tracker takes `TimeProvider`, and the host's `FakeTimeProvider` can
    advance past `MemoLifetime`;
  - the `HubSessionTenantsUnread` path when `ListAsync` throws.
  
  A regression that never expired the memo would lock a reactivated user out of realtime until the
  process restarts, and no test would fail.

**R1-9 (minor): tenant-state events are delivered N times on N instances**
- **Where:** `src/core/Tellma.Core.AspNetCore/Realtime/HubConnectionTracker.cs:199-236`.
- **Problem:** `OnStateChangedAsync` and `OnRemovedAsync` run on every instance, because every
  registry refreshes. Each instance sends to the tenant group through the backplane or the service:
  - `GroupExcept(t{tid}, own)` for a close;
  - `Group(t{tid})` for `cache.changed`.
  
  With Redis or Azure and N instances, every tab therefore receives N `session.ended` or N
  `cache.changed {tag:'tenant'}`. The repeated `cache.changed` means N tenant re-reads per tab per
  state change. The session and revocation listeners run on one instance and need the group send;
  these two do not.
- **Fix:** When `ReachesEveryInstance`, the tenant-state calls tell only this instance's
  connections, directly. Every other instance tells its own. Keep the group send in the in-process
  mode, where it is local anyway.
- **Spec flag (0021 §6.5):** The table says "to `t{tenantId}`" for these rows; the per-instance
  listener makes that a fan-out of N.

### Rulings on the orchestrator's points

1. **The nightly `signalr-live` require step should fail, not skip.**
   - **Repo convention:** `sendgrid-live`, `acs-live` and `marminae-live` all fail at a require
     step when their secrets are missing, and the workflow's header gives the reason: a skipped
     live suite reports green, "the exact silence this workflow exists to break". The new job
     follows that convention exactly.
   - **Current runs:** The workflow is `disabled_manually` today. Its last runs (2026-08-15 to
     08-17) were already red at the SendGrid require step and at ACS's `azure/login`. Scheduled
     runs come from `main`, so this job runs nowhere until `platform-core` merges and the workflow
     is re-enabled. It adds no red run now.
   - **The real risk:** A job that is red by design buries real failures, because `report-failure`
     comments on one standing issue. That risk is the same for all four jobs. The cure is not a
     skip. It is to keep an unprovisioned suite explicitly off, for example a job-level
     `if: vars.SIGNALR_LIVE_ENABLED == 'true'` set when the environment is created, so the job is
     red only when it was provisioned and fails.
   - **Not a finding here.** PLAN §6 lists the Azure SignalR live suite as Deferred. It belongs in
     LEDGER.md's deferred list, with the `live-realtime-tests` environment and its
     `SIGNALR_TEST_CONNECTIONSTRING` secret as the provisioning step. The checkpoint's done-when
     ("wired nightly behind the secret") is met as wiring only. The live suite has never run, so
     every Azure-specific claim it pins is unverified, including the claim set on the rebuilt
     principal (`AzureSignalRLiveTests.cs:77-79`).
2. **Session group and ordering: deviations 1 and 2 are accepted.** The ordering claim is verified
   in the SDK source above. The isolation of `session.ended` holds by construction (see "Verified
   and sound"). Proposed wording for the spec flag:
   - **0021 §6.2:** "the session group is `t{tenantId}.x{handle}`, tenant-qualified like the
     others, because the envelope (§6.3) names one tenant and the client drops an envelope of
     another tenant."
   - **0021 §6.5, session row:** "`session.ended { session-terminated }` to `t{tenantId}.x{handle}`
     for each tenant among this instance's connections of the session and the subject's membership
     hints (`ITenantMembershipDirectory.ListAsync`)."
   - **0021 §6.5, all close rows:** "the event goes to this instance's connections one by one and
     to the rest of the group with `GroupExcept`, so on Azure SignalR Service it travels ahead of
     the abort's close on the connection's own server connection; a connection whose tenant is in
     neither set closes at ticket expiry."
3. **The Defaults reference:** no package rule breaks, but the test-layout rule does. The right
   home is given in R1-1.
