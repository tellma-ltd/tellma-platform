# PC-071: TmApi HTTP layer

## Implementer notes

### What was built, and where

All client paths are under `client/projects/core/`.

- **The public contract** (`tellma-core/src/api/tm-api.ts`): the abstract `TmApi` (root default
  `inject(TmHttpApi)`), its option types (`TmReadOptions`, `TmWriteOptions`, `TmDownloadOptions`,
  `TmUploadOptions`, `TmSendOptions`), `TmDownload` and `TmBlobDescriptor` (0017's descriptor;
  `size` is a `TmDecimal`). `tm-api-error.ts` holds `TmApiError`, `TmApiErrorKind`, `TmProblem`,
  `TmProblemError` and `TmApiErrorInit`. All are exported from the primary.
- **The implementation** (`tm-http-api.ts`, internal): `TmHttpApi implements TmApi` structurally
  and imports `tm-api.ts` for types only, so `tm-api.ts` can name it as the root default without a
  module cycle. One pipeline serves every call:
  `#exchange`/`#upload`/`#fetchBlob` prepare a `TmCall` (tenant, the dev checks, the Contracts
  lookups, then `#admit`: session state → user check → offline write), `#run` loops attempts and
  retries (one request-log entry per call, one trace id, a fresh span per attempt), `#attempt`
  sends over `fetch` under one controller that follows the call's cancel signal and the watchdog,
  `#xhrAttempt` does the same for uploads, `#unanswered` classifies a call with no answer, and
  `#conclude` → `#refusal` → `#verdict` implement §10.3 steps 4-6, §10.6 and §5.6.
- **Pure wire rules** (`tm-api-wire.ts`): `tmKindOf` (§10.6, with an internal `outdated` marker for
  §5.6), `tmParseProblem`, `tmRetryAfterMs` (seconds or HTTP date), `tmParseVersionTags`,
  `tmParseStepUp` (PC-032's `WWW-Authenticate` shape), `tmDispositionFileName` (`filename*` first),
  `tmRandomHex` (never all zero), `tmCompareBuilds` (SemVer 2.0 precedence; identical → 0, same
  precedence with another sha or unparseable → unordered).
- **Reachability** (`tm-api-online.ts`): `TmApiOnline`, the `online` signal and the `/health/live`
  probe (5 s doubling to 30 s, 10 s probe timeout, visible tabs only, an `online` event probes at
  once, one probe at a time).
- **The browser** (`tm-api-host.ts`): `TM_API_HOST`, the one place the layer touches `fetch`,
  `XMLHttpRequest`, `navigator.onLine`, visibility, `crypto.getRandomValues` and `isDevMode`, so the
  specs script all of them, including production mode.
- **Seams to later owners** (`tm-api-seams.ts`, internal): `TM_API_LOCALE` (PC-104;
  default: `document.documentElement.lang`, no calendar), `TM_API_CACHE` (PC-096; default no-op)
  and `TM_API_UPDATES` (PC-110; default `disabled`). WATCHLIST lines tell each owner.
- **Wiring.** `provideTellma` now provides the internal `TM_METADATA_LOADERS` (added to
  `src/metadata/tm-metadata-loaders.ts`; the layer loads the Contracts chunk through it, once,
  sharing concurrent loads) and replaces `TM_BLOB_FETCHER`'s HttpClient default with
  `TmHttpApi.blobFetcher`. `tmRoutedTenant` moved out of `TmLaunch` into
  `src/launch/tm-routed-tenant.ts`, shared by both.
- **Testing package.** `tellma-core-testing/src/tm-fake-api.ts`: `TmFakeApi` (scripted answers per
  route, `calls()` signal, `setOnline`, `setFingerprint`, pending-write count, `cancelled` on abort,
  uploads keyed `blobs/<kind>`); `provideTellmaTesting()` puts it behind `TmApi`.
- **Specs.** `tm-http-api.spec.ts` (fake host, fake XHR, fake clock; every §13 TmApi bullet),
  `tm-api-wire.spec.ts`, `tm-api-online.spec.ts`, `tm-fake-api.spec.ts`. The fakes live in
  `src/api/tm-api.testing.util.ts`.

### Deviations

1. `TmApiError.challenge` (the parsed step-up challenge) is a member §10.1 does not list; §10.6
   says the step-up kind carries "the challenge parsed", and the presenter needs it.
2. Named option types `TmDownloadOptions` and `TmSendOptions` replace §10.1's inline types, and
   `TmApiErrorInit` is exported as the constructor's argument.
3. Internal seams with interim defaults stand in for `TmLocalization`, `TmCacheRefresher` and
   `TmUpdates`; `TmAppVersion` (PC-113) is not created, and the verdict uses `tmCompareBuilds` with
   `TM_CLIENT_METADATA`'s UI version.
4. Anonymous routes skip the user check: `/api/distribution-info`, `/health/*` and
   `/.well-known/*`. The spec says "for an authenticated call" without listing them.
5. Uploads: besides `Tellma-Client` and `traceparent` they send `Accept-Language` and
   `Tellma-Calendar` (§10.2's "every call" / "tenant calls"); a file with an empty type is declared
   `application/octet-stream` (the web host refuses an undeclared body); an upload while offline is
   not sent (`offline`/`not-sent`); a network failure is `offline`/`network`; an upload's 60 s
   watchdog restarts at each progress event and ends a stall or a lost answer as
   `offline`/`outcome-unknown` (the spec is silent; fix round 1).
6. A download's watchdog restarts at each received chunk, so only a stall ends a long export.
7. A `429` without `Retry-After` waits 1 s before its retry (§10.5 gives no wait for that case).
8. Reads, downloads, uploads and blob fetches in flight are aborted when the session leaves
   `active` (the spec says "aborts its reads" on signing-out), and new calls are rejected
   `cancelled` in `expired` as well as `signing-out` (except the sign-out write and sends).
9. A refusal with no problem body: `401` is `unauthenticated`, `429` `rate-limited`, `503`
   `unavailable`; any other is `server`/`unexpected-response`, empty bodies (405, 415) included.
10. `send` is dropped, starting no session path, unless the user check answers `same`, and when
    the client metadata is not loaded; it carries `Tellma-Contract` only once the chunk is loaded,
    and is not logged.
11. The blob fetcher stays out of the request log, and rejects a status other than 2xx/304 with a
    `TmApiError` mapped by §10.6.
12. A `contract-mismatch` is reported through `TmTelemetry.error` (context `route`, `build`), not as
    a `tm.api.client-outdated` event.
13. A Contracts chunk that fails to load rejects the call `offline` (`network` for a read,
    `not-sent` for a write), unsent.
14. Development-only checks beyond the spec's: a `GET` read with a body, and confirmations over 16
    keys or outside 1-100 visible ASCII characters without a comma.
15. (Fix round 1.) `TmApi.fetchBlob(url, options?)` and `TmFetchBlobOptions` are public members
    §10.1 does not list. `provideTellma` points `TM_BLOB_FETCHER` at `TmApi`, so `TmFakeApi`
    answers image fetches; a fetch aborted by its caller rejects with `signal.reason` (0010 §D.6).
16. (Fix round 1.) The sign-out write skips the response check of §10.3 step 4: its `200` clears
    the profile cookie by design (0011 §5.5), so the check would always find `missing`.
17. (Fix round 1.) A `401` for a session the cookie no longer names rejects `cancelled`, not
    §10.6's `unauthenticated`, since no expiry path runs.
18. (Fix round 1.) An older-build verdict within 30 s of that build's first one counts as the same
    first verdict (`server-outdated`, no worker); only a later one is §5.6's second verdict.
19. (Fix round 1.) `@tellma/core-ui/image`'s HttpClient default of `TM_BLOB_FETCHER` loads
    `@angular/common/http` by a dynamic import at its first fetch, instead of a static import.
20. (Fix round 2.) A tenantless route, a tenant URL, an upload URL or a blob URL that is not a path
    on this origin (a second leading `/` or `\`, a tab or line break, a `.` or `..` segment) throws
    in development and rejects `server` (`invalid-url`) unsent in production; the spec is silent.

### Open risks

- **Body reads and the fake clock.** The specs flush with five zero-advances of the fake clock,
  because `Response.text()` takes Chromium a few real tasks. If a future Chromium needs more, the
  symptom is a spec reading `undefined` from a settled-looking call.
- **`TM_CLIENT_METADATA` read lazily.** The `Tellma-Client` value is read at the first call. A call
  made before the boot loads the Core chunk rejects with the store's own error, and Angular then
  marks the token as cyclic for the rest of the tab (its injector does not reset a throwing
  factory). The spec forbids calls before the Core chunk; `send` swallows the failure.
- **Retry-After dates** are only parsed when the value has a letter, because V8's lenient
  `Date.parse` reads `1.5` or `-3` as years.

### What reviewers should examine hardest

- `#conclude`/`#refusal` ordering against §10.3: the response check before any observer, version
  tags one task after delivery, `settle` on every tenant 2xx, the `401` path passing the send-time
  `sh`.
- `#verdict` against §5.6's table and the rollback rule (`#judgedOlder` is tab-wide and never
  cleared).
- Abort plumbing: the caller's signal, the session effect and the watchdog share one controller
  per attempt; check that no listener leaks across retries and that an abort during a retry wait
  ends at once.
- The deviation list above, especially 5, 8 and 9.

## Review 1

### Findings

**R1-1 (blocking) — the sign-out write always rejects `unauthenticated`.**
`client/projects/core/tellma-core/src/api/tm-http-api.ts:919-925` (response check), with the
exception at `:614` and the anonymous-route rule at `:87`.
Spec 0011 §5.5 says `POST /bff/logout` answers `200 LogoutResult` and clears both cookies, the
profile cookie included (spec 0024 §8.4's diagram: "200 {redirectUrl}, profile cookie cleared").
`/bff/logout` is not an anonymous route, so the call is `authenticated`. Step 4 then runs
`#check()` on the answer, sees `missing`, calls `expired('cookie')` (a no-op, because the state
is `signing-out`) and throws `TmApiError('unauthenticated')`. So `write('/bff/logout')` never
delivers `redirectUrl`, and §8.4 can never complete. Its failure branch returns the tab to
`active` with the "Couldn't sign out" toast. The request log also records the logout as an
error.
The spec at `tm-http-api.spec.ts:956-970` answers the logout with 200 but leaves the cookie jar
alone, so it cannot catch this.
Fix: skip the response check for the sign-out write. For example, set the call's response-side
check to `false` when `route === LOGOUT_ROUTE`, or accept `missing` for it. Add a spec in which
the logout answer also clears the cookie jar (`sessionHost.cookieJar = ''` before `answer`) and
the write resolves to `{ redirectUrl }`.

**R1-2 (minor) — a retry skips step 1's gates.** `tm-http-api.ts:754-771`, `:787-803`.
`#admit` runs once per call: the session state, the user check and the offline gate. A retry
sent after its wait (up to 30 s for `server-outdated`, 30 s for a `503`) goes straight to
`#attempt`. Suppose another user signs in elsewhere during the wait. The interim changed-user path
does not broadcast, and the effect aborts only when `state` changes, so the retry goes out on
user B's cookie. Step 4 discards the answer, but the request has already run under B's session.
§10.3 step 1 says the check runs before a call is sent.
Fix: before each retry attempt, re-run the session-state and user-check part of `#admit`, and
turn a throw into the call's result.

**R1-3 (minor) — concurrent outdated answers from one burst count as a rollback.**
`tm-http-api.ts:1038-1047`.
`#judgedOlder` is set by the first `server-outdated` verdict, so every other call answered by
the same older build makes a "second verdict" and asks the worker. Take a page that fires
several reads at once during a slot swap. It gets one `server-outdated` (retried after 30 s) and
`client-outdated` for the rest whenever the worker answers anything but `none`. Without a worker
(`serve`, unsupported browsers, and today's `disabled` default) that is always. With a worker
whose `ngsw.json` fetch reaches the old instance, the worker sees a different manifest and
answers `ready`. Either way the user gets Reload in the middle of a slot swap, which is the case
`server-outdated` exists to ride out quietly. §5.6 means the tie-break for a rollback, when the
server stays older for good.
Fix: count the second verdict only after the first one's 30 s retry window. For example, store
`build → firstVerdictAt` and treat answers within `SERVER_OUTDATED_WAIT_MS` as the same first
verdict. Add a spec with two concurrent reads.

**R1-4 (minor) — a `401` from an already-replaced session rejects `unauthenticated` with no
path.** `tm-http-api.ts:994-996`.
When the call's `sh` no longer matches the cookie (the same user signed in again in another
tab), `expired('401', sh)` rightly does nothing. The call still rejects with kind
`unauthenticated`, which §10.6 says is "presented by the expiry path". No such path runs, so a
read's inline error view or the presenter has nothing correct to show, although the session is
fine. The spec at `tm-http-api.spec.ts:380-392` pins the kind as `unauthenticated`.
Fix: when `call.sh` differs from the current profile's `sh`, reject `cancelled`. Better still,
let a read retry once under the new session.

**R1-5 (minor) — `provideTellma` now pulls `@angular/common/http` into every app's initial
bundle.** `client/projects/core/tellma-core/src/app/provide-tellma.ts:7,55`, with
`client/projects/core/tellma-core-ui/image/tm-blob-fetcher.ts:7,38-59`.
The value import of `TM_BLOB_FETCHER` keeps the token. Its `providedIn: 'root'` factory refers
to `HttpClient`, `HttpHeaders` and `HttpErrorResponse`, so the bundler keeps them, and their own
dependencies, in the eager chunk even though the factory never runs once `provideTellma`
overrides it. `tm/no-raw-http` forbids HttpClient in apps anyway. The `@tellma/core` primary
budget does not see this, because externals are not measured, but the app's 230/260 KB
initial-JS budget does. The size is not measured here.
Fix: remove the HttpClient default from `core-ui/image`. Leave the token factory-less, or give it
a plain-`fetch` default. Move the HttpClient fetcher into an opt-in provider that the showcase
uses.

**R1-6 (minor) — the blob fetcher's contract.** `tm-http-api.ts:291-295`, `:880-881`, and
`provide-tellma.ts:55`.
(a) Spec 0010 §D.6 says that on abort "a fetcher rejects with `signal.reason`" and that 0024's
fetcher "passes the signal straight through". This one rejects with a new
`TmApiError('cancelled')`. When spec 0010 §D.6 lands, a blob cache that recognises an abort by
`error === signal.reason`, or by `AbortError`, will show the error placeholder for an aborted
image. That is the case §D.6 says must show none.
(b) `TM_BLOB_FETCHER` is bound to the concrete `TmHttpApi`, not to `TmApi`. An app test using
`provideTellma` with `provideTellmaTesting()` therefore sends image fetches through the real
layer and `window.fetch`, past `TmFakeApi`.
Fix: (a) reject with `options.signal.reason` when the caller's signal aborted, or state the
difference under Deviations and add a WATCHLIST line for the §D.6 owner. (b) Let the fake
intercept these fetches: either add the blob fetcher to `TmFakeApi` (scripted per URL) and
provide `TM_BLOB_FETCHER` in `provideTellmaTesting()`, or document that tests must provide
their own fetcher.

**R1-7 (minor) — an upload can hang forever.** `tm-http-api.ts:534`, `:837-868`.
Uploads have no watchdog (deviation 5). Say the request body is fully sent and the answer never
comes, as with a NAT drop or a proxy black hole. Then the field sits at 100 % until the user
removes the file, and nothing reports `outcome-unknown`. Deviation 6 already gives downloads a
progress-rearmed watchdog.
Fix: arm the same 60 s watchdog, re-armed on each `upload.onprogress`, and abort the XHR into
`offline`/`outcome-unknown` when it fires. Add a fake-clock spec for it.

**R1-8 (minor) — deviation 8 is only half pinned.** `tm-http-api.spec.ts:955-983`.
Both session specs drive `signing-out` only. Nothing pins these:
- new calls rejected in `expired`;
- in-flight reads aborted on `expired`;
- uploads and blob fetches aborted when the session leaves;
- `/health/*` and `/.well-known/*` skipping the user check (only `/api/distribution-info` is
  tested).

If `!== 'active'` were mutated to `=== 'signing-out'`, every spec would still pass.
Fix: parametrise the two specs over `expired` and `signing-out`. Add an upload and a blob fetch
to the abort spec, and the two other anonymous prefixes to the anonymous-route spec.

**Checked, no finding.**
- `TmApiError.challenge`: justified. §10.6 requires the step-up kind to carry the parsed
  challenge, it is additive, and its type is the session's `TmStepUpChallenge`.
- The internal seams `TM_API_LOCALE`, `TM_API_CACHE` and `TM_API_UPDATES`: acceptable. They are
  not exported, their defaults are safe, and WATCHLIST lines name their owners.
- The primary's raise from 6.5 to 12.5 KB comes from the layer itself, not from avoidable
  imports. Everything new that the primary imports is either type-only or already in the
  primary, apart from R1-5, which falls outside the primary's measurement. It leaves about
  1.7 KB of 0024's 14 KB own-services share for TmLocalization, TmUpdates, TmUrls and
  TmErrorPresenter, which is worth watching.
- Abort listeners are removed on every path (`#cancellableCall`, `#attempt`, `#wait`, the XHR
  settle). Every call sets `credentials: 'same-origin'` and XHR leaves `withCredentials` off. No
  header or token reaches an error message, a log or telemetry. Nothing assigns `location` from
  response data, so there is no open-redirect surface.
- No TSDoc, error message or test name cites a spec, `docs/` or a PC id. No scripts changed.

### Responses

**R1-1 (blocking): fixed.** The sign-out write's answer skips the response check. The call carries
its own `checksAnswer` flag, which is false only for `POST /bff/logout`. The send-time check, the
`401` path (a no-op while signing out) and the request log are unchanged. A new spec, "delivers the
sign-out's answer, which clears the session cookie", empties the cookie jar before answering `200`.
It asserts `{ redirectUrl }`, an `ok` log entry, and no expiry or reload. The parametrised
session-leaving spec answers the sign-out too. This is deviation 16.

**R1-2: fixed.** After each retry wait, `#run` calls `#admit` again and ends the call with whatever
that throws. `#admit` checks the call's cancellation, the session state and the user. It has no
offline gate, because only reads retry. Two new specs:
- Another user signs in during a `503` wait: the call rejects `cancelled`, the changed-user path
  runs, and nothing more is sent.
- The cookie disappears during a `429` wait: the expiry path runs, and the call rejects
  `unauthenticated`.

**R1-3: fixed.** `#judgedOlder` now maps each build to the time of its first verdict, read from
`TM_NOW`.
- A verdict within `SERVER_OUTDATED_WAIT_MS` of the first counts as the same first verdict:
  `server-outdated`, source `build`.
- Only a later verdict asks the worker. An example is the read's own retry answered by the same
  build. At exactly 30 s the verdict counts as the second one, so that retry still signals a
  rollback.

A new spec sends three concurrent reads, each answered `412` by an older build. All three get
`server-outdated` with no worker check, then each retries after 30 s and succeeds. The rollback
spec now waits 30 s before its second verdict. The specs' `TM_NOW` now follows the faked `Date`,
which is set to the fixed instant at setup, so waits move it. This is deviation 18.

**R1-4: fixed as `cancelled`; the retry pushed back.** A `401` rejects `cancelled` when, after the
response check, the call's `sh` differs from the profile's `sh`. It keeps status 401 and code
`unauthenticated` for the log, and runs no path. A retry under the new session would conflict with
spec 0024 §10.5:
- "Only reads retry, on the failures below", and that list has no `401`.
- Each retry must emit `tm.api.retry`, whose reason comes from the closed set network, 429, 503 and
  server-outdated.

A cancelled read stays in its loading state until its owner reads again; §10.6 treats `cancelled`
as silent. The spec was renamed to "cancels, ending nothing, a 401 for a session the cookie no
longer names". This is deviation 17.

**R1-5: fixed in `@tellma/core-ui/image`.** The default `TM_BLOB_FETCHER` still rides HttpClient, as
spec 0005 §7.1 and 0010 §D.6 both describe it. It now loads `@angular/common/http` with
`await import(...)` at its first fetch, and gets HttpClient from the root `Injector`. The token no
longer has a static value import of HttpClient, so an app that overrides it never ships HttpClient
in its eager bundle. Every `provideTellma` app overrides it. Apps on the default still need
`provideHttpClient()`; the showcase and the docs-examples spec already provide it.

Measurements:
- **Plain esbuild** (minified, gzip level 9, without the CLI's Angular optimizations). An entry with
  only `InjectionToken` is 115.9 KB. Adding the old token's static HttpClient factory makes it
  161.3 KB (+45.3 KB), most of it `@angular/core` code that any app already ships. Over a
  `bootstrapApplication` + `provideRouter` baseline it adds 13.5 KB.
- **Angular CLI production build of the showcase**, with `provideHttpClient()` removed so that only
  the token could bring HttpClient in:
  - static import (before): initial total 275.12 kB estimated transfer, 1.20 MB raw, in three
    initial chunks;
  - dynamic import (after): 271.13 kB, 1.24 MB raw, in one main chunk.

  The fix saves about 4 KB of transfer. The raw growth comes from the different chunk layout.
  HttpClient's code does not leave the initial bundle, though: `HttpErrorResponse`'s message is in
  `main` in both builds. The reason is that `@angular/platform-browser` itself imports
  `@angular/common/http` statically, for the hydration transfer cache, so the module is in every
  app's graph whatever this token does. So the leak R1-5 describes costs about 4 KB of transfer, not
  the whole HttpClient. The rest belongs to Angular. This token no longer adds anything eagerly.

The alternative was to move the default into an opt-in provider. That would change 0005 §7.1's
zero-config default and the text of 0010 §D.6, so it was not done. This is deviation 19.

**R1-6: fixed.**
- (a) `TmHttpApi.fetchBlob` rethrows `options.signal.reason` when the caller's signal aborted. An
  abort caused by the session leaving the tab still rejects `TmApiError('cancelled')`, since no
  caller signal fired.
- (b) `TmApi` gains `fetchBlob(url, options?: TmFetchBlobOptions)`, and `provideTellma`'s
  `TM_BLOB_FETCHER` factory calls `inject(TmApi).fetchBlob`. `TmFakeApi.fetchBlob` answers from the
  script under the URL, with call kind `fetch-blob`, and rejects an abort with `signal.reason`. So
  with `provideTellma` and `provideTellmaTesting()` together, image fetches go to the fake.

New specs:
- the provider delegates to `TmApi`;
- `TmFakeApi` answers `TM_BLOB_FETCHER` under `provideTellmaTesting`;
- an aborted fetch rejects `toBe(signal.reason)`;
- the fake's own abort spec.

The PC-059 WATCHLIST line was updated. This is deviation 15.

**R1-7: fixed.** Uploads now have the 60 s watchdog, armed at the send and re-armed at each
`upload.onprogress`. When it fires, the XHR is aborted and `onabort` maps the timeout to
`offline`/`outcome-unknown`, which is never retried. A user's abort still rejects `cancelled`,
because `#unanswered` checks the cancel signal first. The new fake-clock spec sends three progress
events 50 s apart, which keep the upload alive. After the last byte, 59.999 s pass with no answer,
and the 60th second ends the upload. Deviation 5 was updated.

**R1-8: fixed.**
- Both session specs are parametrised over `signing-out` and `expired`.
- In the new-calls spec, a read, a write, a download, an upload and a blob fetch all reject
  `cancelled`, and the upload opens no XHR. The sign-out and a send still go out.
- In the in-flight spec, a read, a download, a blob fetch and an upload are all aborted and reject
  `cancelled`. The write is neither aborted nor settled.
- The anonymous-route spec is parametrised over `/api/distribution-info`, `/health/ready` and
  `/.well-known/openid-configuration`.

**Also:** a WATCHLIST ## 0024 line records how much of 0024's 14 KB own-services share remains for
TmLocalization, TmUpdates, TmUrls and TmErrorPresenter: about 1.6 KB. The fixes took the
`@tellma/core` primary from 12.27 to 12.42 KB gzip, within its 12.5 KB budget. `./image` measures
9.96 KB against its unchanged 10 KB budget.

## Review 2

### Findings

**R2-1 (minor) — a URL that is not a local path is treated as the platform's own server.**
`client/projects/core/tellma-core/src/api/tm-http-api.ts:563-587` (`#fetchBlob`, behind the new
public `TmApi.fetchBlob`), `:600-602` (a route with a leading `/` is sent as is), `:88` with `:631`
(the anonymous test runs on the raw string).
Neither `fetchBlob` nor a tenantless route checks that its URL is a path on this origin.
`https://cdn.example/logo.png`, `//host/x` and `/\host/x` all reach `fetch` as foreign URLs. The
cookies stay home (`credentials: 'same-origin'`), but the rest of the layer treats the foreign
server as ours:
- The call carries `Tellma-Client`, `traceparent` and `Accept-Language`, so it needs a CORS
  preflight. Under the production CSP (`connect-src 'self'`), or when the preflight fails, `fetch`
  throws, `#unanswered` calls `connectivity.failed()` (`:923`), and `TmApi.online()` stays false
  until the next answer or `/health/live` probe. So one `tm-image` with an external `src` marks
  the server unreachable each time it loads. On the HttpClient default the same image only fails
  to load.
- Where nothing blocks it (`serve`, a loosened `connect-src`) and the foreign server allows the
  headers, its answer is judged as the platform's. A `401` runs `expired('401')` (`:1037-1039`)
  and ends the session. A `412 client-outdated` with a `Tellma-Build` enters `#verdict` and
  `#judgedOlder`. Any answer calls `connectivity.answered()`.
- Dot segments defeat the anonymous test. `/health/../17/blobs/attachment/9` matches
  `ANONYMOUS_ROUTE`, so the user check is skipped at both ends, yet the browser sends the call to
  `/17/blobs/attachment/9` with the cookie.

Image URLs come from blob descriptors today, so reaching any of this takes a developer's mistake
or a second bug. It is defence in depth, but the layer is security-bound and deviation 15 made the
URL a public parameter.
Fix: in `fetchBlob` and for tenantless routes, admit only a local path: one leading `/`, the next
character neither `/` nor `\`, and no `.` or `..` segment. Throw in development; in production

### Responses

**R2-1: fixed.** `#local(url)` admits a URL only when all three hold:
- it starts with one `/`, and the next character is neither `/` nor `\`;
- it has no tab or line break (the URL parser drops those, so `/\t/host` would become `//host`);
- its path has no `.` or `..` segment, plain or as `%2e` (case-insensitive), with `/` or `\` as
  separators.

A dot inside a segment, or anything in the query, is allowed.

The check runs first, before the tenant's Contracts load, any gate or the user check, on:
- every tenantless route and every tenant URL (through `#urlOf`, so `read`, `write`, `download`
  and `send`);
- the upload URL (the kind is a path segment);
- `fetchBlob`.

In development it throws. In production it rejects `server` (`invalid-url`) unsent, and never
touches `connectivity`. A send drops the call, as for a missing tenant.

New specs:
- `fetchBlob` throws in development for `https://…`, `//host`, `/\host`, `/\t/host`,
  `/health/../17/blobs/…`, `/health/%2E%2E/…` and `/17/blobs/./9`.
- In production, a read, a blob fetch and a send of each tenantless case reject or drop unsent.
  `online()` stays true and the session stays `active`.
- A tenant route `centers/../../../bff/user` and an upload of kind `..` are refused.
- `/17/blobs/v1.2/9..png?name=a/../b` is still sent.

The bytes are paid for by tighter development-only messages (see Budget below).

**R2-2: fixed, lazily.** TmHttpApi now resolves these at each use, through private getters over
`#injector`, never in a field initialiser:
- TmSession, TmSessionPaths, TmLaunch and TmTelemetry;
- `TM_API_LOCALE`, `TM_API_CACHE` and `TM_API_UPDATES`.

Only the host, connectivity, router, request log, loaders, injector and clock stay eager. The
injector caches each instance, so a use costs a lookup.

A new spec provides the locale seam, the cache seam and TmTelemetry through factories that
`inject(TmApi)` first, and runs a read with a `429` retry and version tags through all three. With
the old eager fields it fails at the first injection, with Angular's circular-dependency error.
setUp now starts TmSession before navigating, since the boot creates it before any call. A new
WATCHLIST line tells the owners they may inject `TmApi` eagerly, and that TmHttpApi must not
regain an eager injection of anything that calls it.
