# PC-072: Save pipeline, pre-persist: ownership, preprocessing, ids, child sync, RT1 and validation

## Implementer notes

### What was built

Spec 0015 §6.1 steps 1 to 6 for a stack's save, up to the persist step. A save whose validation
passes throws `NotSupportedException` at the persist seam, which PC-074 replaces.

- **Wiring.** `EntityPipeline.SaveAsync` checks its arguments and the stack's `Save` operation, then
  delegates to `SaveOperation` (scoped, registered by `CrudComposition`; `EntityPipelineFactory`
  passes it). `SaveOperation` runs inside `CrudOperations.RunAsync` with
  `crud.source` = `CrudMetrics.Source(options.Source)` (`web`, `public_api`, `agent`, `import`,
  `system`) and the lane from the payload's row count. `DataAccessRetryExhaustedException` becomes
  `DependencyUnavailableException("database", 1 s)` in the pipeline itself (D-108).
- **`SaveRun<TEntity, TKey>`** (`Crud/Save/SaveRun*.cs`) holds one save's state, in three parts:
  - `SaveRun.cs`, the steps up to round trip 1:
    1. `SaveShape.Check`, which makes zero round trips.
    2. `RequireAsync(resource, Save)`.
    3. The `ConfirmationFrame`.
    4. The walk.
    5. `Normalize` on every row: the echoed stamp is read first, then `ResetDerived` and
       `ResetServerOwned`, trimming (an empty nullable string becomes null; `[PreserveWhitespace]` is
       honoured), the parent key from the nesting, dropping unconfigured twins
       (`Import.LanguageNotConfigured` under `SaveSource.Import`), and the value set's spelling.
    6. `PreprocessAsync`, then a re-walk.
    7. `[Defaulted]` left empty is `Required` with argument `property`.
    8. An undefined temporary id is `Entity.NotFound` at the reference.
    9. The reference, uniqueness and tree requests.
    10. `ReserveIds`, then the first round, the validators, `scheduler.RunAsync`, the settle when no
        round ran, `CheckValueSets`, and `ValidationOutcome.Raise`.
    11. The `finally` disposes the reservation, so the ids go back to the buffer.
  - `SaveRun.Rounds.cs`: `DispatchAsync` runs each round's loads on one guarded
    `BatchPurpose.Validate` runner call. That call sets `Composer` to the connected user and
    `batch.Limits` to `PipelineLimits`. After the call it does `ApplyCultures()` (PC-050/D-108) and
    `Complete()`. Round 1 then settles, and in deferred mode starts the validators. The `FirstRound`
    load group composes:
    - the reservation statement (deferred mode; a recomposition reserves afresh);
    - the before images: `EntityQuery<TEntity>` with every declared property and `AllProperties`,
      the Read filter, a key-set restriction, `Children` set to every collection the payload
      carries on an update root at any depth (dotted, parents first), and `OrderBy` the key;
    - the Save filter's capped `Count` over the same ids;
    - one keyed `Rows` per reference target under that target's Read decision.
  - `SaveRun.Checks.cs`, `SettleAsync`, in the order of §6.6:
    1. Deferred ids are assigned.
    2. Existence: `NotFoundException` with invariant ids, then `ForbiddenException(OutsideFilter)`.
    3. Before images are matched: absent collections are nulled, children matched by id, and
       unmatched stored children recorded as deleted, recursively.
    4. Early concurrency under `Check`:
       - A default stamp is `Concurrency.StampRequired` at `[i].ModifiedAt`.
       - A differing stamp raises `ConcurrencyException("concurrency-conflict")`. The conflict's
         stamp has seven fractional digits and its offset. The modifier's name is in the reader's
         content language, falling back to `Name`.
    5. The roots' before images are primed and set as `context.BeforeImages`.
    6. Ownership:
       - Server-owned values are restored from the before image.
       - A `WriteOnce` value the client left default is kept; one that differs is `WriteOnce`.
       - A prefix holding `" - "` is `DisplayName.PrefixSeparator` (`property`, `separator`).
    7. Child identity: `Entity.NotFound` at the child's key, never re-parented.
    8. References: a new or changed reference to a sensitive target first asks for the step-up;
       one the caller cannot see is `Fk.NotFound` (`entity`, `id`).
    9. Uniqueness:
       - Payload duplicates are found per scope under the collation comparer.
       - Then the loaded holders, skipping: the row's own id, children the sync deletes, other
         parents for a per-parent probe, and a row the payload updates away from the value when
         the row taking it is an update root or a child (deviation 18).
       - At most one `Unique` is raised per row and property.
    10. `TreeCycleValidator<TEntity>.Report`.
- **Supporting types** (`Crud/Save/`):
  - `RowRules`: per-entity rules, built once per `EntityMetadata`.
  - `SaveRow`: a payload row with its path, owner, collection, original id and before image.
  - `UniqueProbe<T, TK>` with `CollationObjectComparer`.
  - `PipelineWriteHost`: `IWriteHost` with kind `Pipeline`.
- **Changes elsewhere:**
  - `IdAllocator` implements the new internal `IIdBuffer.ReserveBuffered`. It returns an immediate
    reservation, or null after giving every take back unmetered. `DataComposition` registers it.
  - `ContextLoader`:
    - `ByValues<T, TK>(property, values, select)` is the internal seam D-095 asked for.
    - `EntitiesGroup` takes `Visible`'s read decision when its round is composed, for the
      connected user.
    - `Enqueue` and `ReadDecision` are added.
  - `ValidationScheduler.AddPipelineRound()` and a settable `MaxRounds`.
  - `TreeCycleValidator`: `Request`/`Report` split, and `Report` is static.
  - `CrudMetrics.Source`.
  - The Tellma.Core README has a new "The save pipeline" section.
- **Tests:**
  - Unit (`test/core/Tellma.Core.Tests/Crud/Save/`, model `PipelineSaveModel`): 21 cases over the
    scripted batch, with a `TestIds` that serves a warm or cold buffer from the real allocator.
  - New unit cases: `ValidationScheduler.AddPipelineRound`; `IdAllocator.ReserveBuffered` warm and
    short; `ContextLoader.ByValues`; `Visible` deciding at compose time.
  - Existing cases adjusted: `CoreResourceAuditTests` drops `Problem_concurrency_conflict` and its
    `_Detail` from the pending keys (the save pipeline now raises them), and
    `QueryOperationTests`' "not built yet" case uses `DeleteByIdsAsync`, since `SaveAsync` now runs.
  - Integration (`test/core/Tellma.Core.IntegrationTests/Crud/SavePipelineTests.cs`): against
    SQL Server, a cold-buffer save in one round trip with sequence ids and nesting keys; unique
    values under the collation; a stale stamp naming the system user; a stored-tree cycle.
  - Gate: the full Core integration run passed 408 of 409. The one failure,

### Deviations

1. **The references' visibility pre-load reads keys, not `Loader.Visible`.** The checkpoint names
   `Loader.Visible` for the FK targets. Instead, round trip 1 carries one keyed `Rows` of the key
   per target, under that target's Read decision taken at compose time.
   - A denied target loads nothing, so every reference to it is `Fk.NotFound`.
   - A child entity without a query surface (so without a Read securable of its own) is read under
     its owner's Read decision, the owner's filter rebased through the child's navigation, up to
     the first owner with a securable (review 1, D-111). A child query surface's own securable
     already composes its owner in the evaluator.
   - Only an entity no grant can reach (no stack serves it, or its stack serves no operation) is
     checked for existence alone.
   - A new or changed reference to a target read under a sensitive securable asks for the step-up
     (`AssuranceCheck.Ensure`) a direct read asks for, before any reference to it is judged. An
     unchanged reference is not judged and asks nothing; a denied target reveals nothing and asks
     nothing (review 1, D-111).
   - The decisions come from the set the batch is composed under, whose prologue guard validates
     the permissions tag; a moved tag recomposes the round from the fresh set. So no separate
     fast-deny re-check is called.
   - Why keys: `Visible` loads whole entities under a filter and no key restriction; the check
     needs only the visible keys.
2. **Uniqueness reads through `ContextLoader.ByValues`, not `ByKey`.** This is D-095's seam: ByKey
   refuses a property unique only within its parent. The signature in §6.6 step 5 still needs
   amending (for Ahmad, as in D-095).
3. **`Visible`'s read decision is taken when its round is composed** (for the connected user the
   runner composes for), not when it is requested. So a denied `Visible` load resolves at its
   round, and a round holding only that load still sends an empty batch.
4. **The immediate reservation is a separate internal probe.** It is `IIdBuffer.ReserveBuffered`,
   not a mode of `IIdAllocator.Reserve`, so `IIdAllocator` in Abstractions is unchanged. `Reserve`
   takes a batch, which a warm one-round-trip create does not have.
5. **The pipeline runs the tree check itself.** Its load is requested on round trip 1 and reported
   in the ordered checks, so `TreeCycleValidator` is not registered as an `IEntityValidator`.
6. **`[PreserveWhitespace]` is read by reflection** in `RowRules`, because `EntityMetadata` carries
   no facet for it and Abstractions is left untouched.
7. **Server-owned columns are reset on every row, then restored on update rows from their before
   images after round trip 1.** The `ResetServerOwned` doc speaks of new rows only.
   `PreprocessAsync` therefore sees default server-owned values on update rows (§6.2 lets the hook
   see neither the client's values nor stale ones).
8. **The modifier's name for an early conflict costs one extra unfiltered `Validate` round trip**
   on `core.User`, made only when a conflict is found.
9. **In deferred mode the round ceiling is raised by one, and `context.Round` leaves that round
   out.** Round trip 1 is then the pipeline's alone, and the validators keep every round of theirs.
10. **A unique property of a type no key-set table holds is skipped**, for example `decimal` or
    `DateTimeOffset`.
11. **Child before images are not primed into the loader.** The roots are.
12. **`Unique`, `WriteOnce` and `Import.LanguageNotConfigured` carry no arguments**, as
    `ValidationCodes` documents them today.
13. **The early conflict is not metered.** The concurrency instruments of §16.1 are PC-074's.
14. **Value-set values are canonicalised again at §6.6 step 8**, so a value a hook or a validator
    wrote takes the set's spelling too.
15. **Rows a `PreprocessAsync` hook adds skip the shape check and normalisation**, which run
    before the hook. The re-walk does give them their paths, their nesting parent key at
    assignment, uniqueness and references.
16. **A deleted child's own children count as deleted only when their collection loaded**, that
    is, when the payload carries that collection on some update row.
17. **In immediate mode, validators start before round trip 1.** Until their first `LoadAsync`
    returns, they see reset server-owned values and no before images; the tests' validators park
    on a load first.
18. **Uniqueness frees a value only where the persist's statement order frees it** (review 1).
    §6.6 step 5 reads "a loaded row whose id is not the payload row's is `Unique`", on create and
    update alike. The persist inserts new roots, then synchronises children (delete, update,
    insert), then updates existing roots. So a stored holder is skipped when:
    - it is a child the synchronisation deletes; or
    - the payload updates it to another value (its value after ownership, under the probe's
      comparer), and the row taking the value is an update root (one `UPDATE` holds both) or a
      child.
    A new root taking a value an updated root gives up or keeps is `Unique`.

### Open risks and what reviewers should examine hardest

- **The ordering inside `DispatchAsync` (round 1).** `SettleAsync` must run before any validator
  continuation resumes. It runs inside the dispatch, so continuations resume only after it. A
  throw there (404, 403 or concurrency) fails the scheduler and tears down the parked validators;
  `A_stamp_the_stored_row_has_moved_past_…` covers this.
- **Deferred reservation with recomposition.** `ComposeFirstRound` disposes a prior reservation
  before reserving afresh, for when the guarded runner recomposes the batch. Only the real
  `DataBatch` path exercises this (integration test 1); a forced recompose is not tested.
- **The uniqueness skip rules** (own id, sync-deleted children, scope, and updated holders that
  give the value up to an update root or a child) decide false negatives. Check `CheckUniqueness`
  against §6.6 step 5 and the emitter's statement order (deviation 18).
- **`CheckChildIdentity` skips children of an unmatched update owner.** Their owner is reported
  instead. Check that no path double-reports or misses a row.
- **The read-denied branch of the before images** (no images query, every id not found) cannot be
  reached in practice: a Save grant implies Read with the same filter. It stays as a guard.
- **The test rig's `TestIds`** stands in for the reservation statement in the unit suite: it
  serves the deferred reservation from the warmed buffer. The real statement is covered only by
  the integration tests, which also show a refused cold save giving its id back.
- **The active flag on insert.** `IActivatable`'s and `ActivatableConvention`'s docs say the insert
  writes the column's default (1), but `IsActive` must stay in the table type and the emitter's
  insert writes every table-type column. The pipeline therefore sets a new row active in
  preprocessing; the persist step should keep the two consistent.
- **The before images of a stack whose `Read` is sensitive** are read under the `Read` filter with
  no step-up of their own; only the `Save` pair's sensitivity is asked (by `RequireAsync`).
  Review 1 did not raise it; it is the same question D-111 answered for references.

**R1-1 (major): the uniqueness check passes a new root that takes a value an updated root
gives up, which the persist batch cannot write.**
`src/core/Tellma.Core/Crud/Save/SaveRun.Checks.cs:405` and `:445-449`
- **What the code does.** It skips every stored holder whose id the payload updates
  (`!updated.Contains(stored.Id)`). It does this for every payload holder, new rows included.
- **Why that fails at persist.** The emitter writes the root insert before the root update
  (`src/core/Tellma.Core/Data/Saves/SaveText.cs:166-172`: `WriteRootInsert`, then the
  synchronise, then `WriteRootUpdate`). SQL Server checks `UX_<Table>_<Col>` per statement.
- **Failure scenario.** Stored widget 5 has `Code = "A"`. One save renames 5 to `"B"` and
  creates a new widget with `Code = "A"`.
  1. Validation passes, because holder 5 is "updated".
  2. The INSERT statement then hits 2601 while row 5 still holds `"A"`.
  3. That costs RT2, the persist attempt keeps the ids (§6.4), and the error comes from the race
     map ("at path or Root") instead of from validation.
- **Spec conflict.** §6.6 step 5 says "a loaded row whose id is not the payload row's is `Unique`
  ... on create and update alike". That rule would have refused this payload. The skips for
  updated rows and sync-deleted children relax the spec, and neither is listed under Deviations.
- **Where the skips are right.** Child synchronisation deletes, then updates, then inserts
  (`SaveText.cs:279-327`). So for child probes, skipping deleted and updated holders is correct.
  An update-to-update swap on roots is also correct, because one `UPDATE` statement holds both
  rows.
- **Suggested fix.**
  - Skip an updated stored holder only when the payload row is itself an update, or the probe is
    over a child entity.
  - For a new root, count an updated stored holder as taken.
  - Add a unit case for "rename 5 from A to B and create A", and list the remaining skips (the
    swap, and sync-deleted children) as a deviation from step 5's literal rule.

**R1-2 (minor): a `[WriteOnce][Unique]` value that an update leaves empty frees the stored
value in the check, though the row keeps it.**
`src/core/Tellma.Core/Crud/Save/SaveRun.cs:414-436` and `SaveRun.Checks.cs:323-330`, `:405`, `:447`
- **What the code does.** `RequestUniqueness` collects holders before round trip 1. An update
  row whose write-once unique property arrives default is therefore not a holder. After round
  trip 1, `CheckOwnership` restores the stored value. But the row's id is in `updated`, so its
  stored value is skipped as a holder.
- **Failure scenario.** Stored row 5 has `Code = "A"` (write-once and unique). The save updates
  5 without sending `Code`, and adds a new row with `Code = "A"`. Validation passes, and the
  persist hits the unique index whatever the statement order.
- **Suggested fix.** Skip an updated stored holder only when the updating row's value after
  `CheckOwnership` differs from the stored one under the probe's comparer. This rule also
  subsumes part of R1-1.
  - Alternatively, add the restored write-once values to the holders before `CheckUniqueness`.

**R1-3 (minor; for the orchestrator): deviation #1's reference checks skip step-up, and
check child-entity targets for existence only.**
`src/core/Tellma.Core/Crud/Save/SaveRun.Rounds.cs:181-207` and `:289-294`
- **Step-up.**
  - Reference visibility is decided through `Evaluator.DecideFrom`. That call skips step-up and
    the FastDenyWindow re-check that a direct `Read` of a sensitive pair gets.
  - D-108 (PC-068 R1-6) ruled that a traversal decision must not bypass them. This check is the
    save-side counterpart: an existence oracle on a sensitive resource with no step-up.
  - The deviation states this ("no step-up is asked"), but does not reconcile it with D-108.
- **Child-entity targets.**
  - A child-entity target (today `Permission` and `RoleMembership`, and any pack line entity)
    has no securable of its own. It is therefore checked for existence alone.
  - So a reference to a child of a root the caller cannot read passes validation, and the
    database FK then accepts it.
  - §7.4 says foreign keys are validated "under the target's `Read` filter". The code comment
    "no grant could ever reach it" is wrong for children: grants reach them through their root.
  - No current entity references a child row, so nothing is exposed today.
- **Suggested fix, step-up.** Either take the decision through the same step-up and re-check
  path as a direct Read, or record the exception next to D-108.
- **Suggested fix, child targets.** Either apply the owning root's Read filter, re-rooted
  through the parent path, or refuse such references at startup until that exists. Correct the
  comment and the deviation's wording either way.
