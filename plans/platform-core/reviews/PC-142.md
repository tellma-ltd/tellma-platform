# PC-142: StackConformanceTests base, instrument pins, docs

## Implementer notes

### What was built, and where

- `src/core/Tellma.Core.Testing/Crud/StackConformanceTests.cs` (and its partials `.Operations`,
  `.Budget`, `.Rows`, `.Values`, `.Recipes`): the abstract conformance base
  `StackConformanceTests<TEntity, TKey>`, closed per stack over an `IStackConformanceHarness`. Its
  cases, every one driven by the stack's descriptor:
  - operations: every declared operation (query, get, get-by-ids, all, save, delete,
    delete-by-query, get-by-parent-ids, delete-with-descendants, activate, deactivate, each declared
    entity action) reaches the pipeline, every absent one throws `InvalidOperationException`, and so
    does an undeclared action;
  - securables: `ISecurableRegistry.ForResource` equals the descriptor's implied set (plus any
    routed-service securable naming the resource), under the stack's feature with no owner, and each
    child query surface registers Read with its own filter root, its owner and the root's feature;
    a caller holding none of the stack's grants is refused each standard operation with
    `NoGrant` naming the securable;
  - enlistment: an `Enlist` stack takes a row from a declared writer through the closer's frame at
    the round trips of the host write alone, and refuses a nested writer the registry holds no pair
    for; a stack without `Enlist` is the target of no pair;
  - budget (spec 0015 §16.2): query, details by id and by ids, a child surface's query 1; a
    cached list 0 once filled; a create 1, or 2 when the payload has a unique value or a written
    reference anywhere in its aggregate (or the closer says its validators load), plus dependent
    rounds; an update 2; delete and the built-ins 1, or 2 when judged (the service's hook overrides
    by reflection, overridable for component validators). Each count is also held to the driver's
    `ServerRoundtrips` when the harness observes it;
  - hidden-equals-missing: a row the caller's grants hide (every filterable grant carries
    `Id != hidden`) answers exactly as a missing id (same refusal text, id aside, same round trips)
    on get, save, delete, delete-with-descendants, activate and deactivate; a read by ids answers the
    visible row alone for both;
  - concurrency: a stale stamp is `ConcurrencyException` naming the writer, its stamp and name; the
    override saves past it; a default stamp is `Concurrency.StampRequired`; a row deleted since its
    read is `NotFoundException` under both modes;
  - ownership: each write-once property refused on change; every server-owned value but the key
    and the stamp perturbed on an update and stored unchanged;
  - collections (each direct child collection): absent keeps the rows, a foreign child id is
    `Entity.NotFound` at `[0].<Collection>[0].Id`, empty deletes the rows;
  - keys: each unique or declared natural-key root value another row holds is `Unique` at its path,
    and each child unique value repeated within the payload's collection is `Unique` on that row;
    each incoming reference in the model (not a collection's parent key, a sibling's shared key, a
    blob column or a server-owned key) refuses the target's delete as `Fk.InUse` at `Ids[0]` naming
    the entity and key;
  - recipes: activatable (created active whatever the payload says, an action on a row already in
    the state leaves it unstamped, inactive rows only with `IncludeInactive`, an update keeps the
    stored flag), tree (children by parent, `Tree.Cycle`, a subtree deleted whole), cacheable (0 round
    trips once filled, a stored row reaching the list once a batch reads the tags), searchable (each
    property finds its row, an absent term finds nothing);
  - instruments: every measurement within its closed shape, and the operations run counted and timed
    with their outcomes, a save's entities and rounds counted.
  A case that does not apply is skipped with its reason (`Assert.Skip*`), one needing the closer's
  help fails naming the member to override.
- `src/core/Tellma.Core.Testing/Crud/CrudInstrumentCollector.cs`, `CrudMeasurement.cs`: the
  `MetricCollector` pins over all eleven `tellma.crud.*` instruments, each with its required and
  optional tags and each closed tag's value set (§16.1's table); `AssertClosed` reports every
  measurement outside its shape.
- `IStackConformanceHarness`, `StackConformanceCaller`, `StackGrant`: the harness contract (root
  services, seeded callers, connected scopes, an optional driver round-trip count).
- `Tellma.Core.Testing.csproj`: references `Microsoft.Extensions.Diagnostics.Testing` (already

- `test/core/Tellma.Core.IntegrationTests/Crud/Conformance/`: `ConformanceDatabase` (the harness

- `test/shared/Tellma.Testing.Entities/FixtureEntities.cs`: `Lookup.Code` `[Searchable(Prefix)]`,

### Findings

**R1-1 (major): the budget case skips five of §16.2's rows that the descriptor can drive.**

Where: `src/core/Tellma.Core.Testing/Crud/StackConformanceTests.Budget.cs:21-95`.

§18.3 says "the round-trip budget", and §18.2 says "the round-trip budget of §16.2 for every row".
The base asserts query, details by id and by ids, a child surface, the cached list, create,
update, delete by ids and activate/deactivate. It never measures these rows:
- query with count and with ancestors (1);
- get by parent ids (1, tree stacks);
- delete by query (1, or 2 when judged);
- delete with descendants (1, or 2 when judged; tree stacks);
- a custom entity action (2, plus dependent rounds).

Every one of them is reachable from the descriptor, and the base already calls each operation in
the reachability case. So a stack whose delete-by-query or get-by-parent-ids regresses to an extra
round trip, for example from a per-id pre-check or a second read for the roots, passes every
conformance class.

Fix: add these rows to the budget case, warm first as the others are:
- `QueryAsync` with a count, and with ancestors on a tree;
- `Pipeline.GetByParentIdsAsync` on the stored row's id;
- `DeleteByQueryAsync` over `Id = <stored>` with expected count 1;
- `Pipeline.DeleteWithDescendantsAsync` on a stored subtree;
- each non-built-in `EntityActionDescriptor` on a stored row with `ActionArguments(action)`.

Use `ValidatesDeletes`/`ValidatesActions` and `DependentValidationRounds` as the existing rows do.

**R1-2 (major): collections at depth are not exercised, although §18.3 names every child
collection.**

Where: `src/core/Tellma.Core.Testing/Crud/StackConformanceTests.Values.cs:71`. It iterates
`Stack.Children` only, so `fixture.WidgetPartNotes` is never tested.

Failure scenario: synchronisation at depth breaks, and every conformance class still passes. For
example:
- an updated part sent with `PartNotes = null` drops its notes;
- `[]` under a kept part leaves the notes in place;
- a note id belonging to another widget's part is moved rather than refused.

The unit pins run over a scripted batch and do not reach a distribution's real schema. Future
aggregates in distributions (documents, then lines, then entries) are exactly the shape at risk.

Fix: recurse through `ChildCollectionMetadata.Child.Children`. For a nested collection, load the
stored root, pick the first row of the parent collection, and apply the same three steps on its
nested collection: absent, foreign id from another root's first parent row, then empty. The
expected path is `[0].<Parent>[0].<Nested>[0].Id`. Keep the "fill each collection" guard at
every depth.

**R1-3 (major): no closer exercises the base's action and validator branches, so those branches of
the base are untested.**

Where:
- `test/core/Tellma.Core.IntegrationTests/Crud/Conformance/WidgetConformanceTests.cs:18` and
  `ConformanceDatabase.cs:144-146`: Widget runs on `DefaultEntityService`, as the golden shows.
- `src/core/Tellma.Core.Testing/Crud/StackConformanceTests.Operations.cs:59-63`: the custom-action
  loop.
- `StackConformanceTests.cs:96-121`: the validator facts.
- `StackConformanceTests.cs:299-301`: the API-action securable branch.

None of the five closed stacks declares a custom entity or API action. None overrides
`ValidateDeleteAsync` or `ValidateActionAsync`, or has a loading or multi-round validator. So all
of the following run zero times:
- the custom-action reachability loop;
- the API-action branch of `ExpectedSecurables`;
- the `ValidatesDeletes`/`ValidatesActions` 2-trip budgets;
- `ValidatorsLoad`;
- `DependentValidationRounds`.

§18.2 registers Widget through a `WidgetService` with an `[EntityAction]`, an `[ApiAction]` and a
validator with dependent loads across three rounds. That is the shape these branches exist for. A
wrong expectation in any of them first surfaces when spec 0018 closes the base over `User` and
`Role`, which have actions and validators. At that point it is a base bug found by a consumer.

Fix: close one more class over a widget host whose service has an `[EntityAction]`, an
`[ApiAction]`, a `ValidateActionAsync`/`ValidateDeleteAsync` override and a three-round loading
validator (`WritePipelineDatabase`'s `WidgetService` or an equivalent). Override `ValidatorsLoad`
and `DependentValidationRounds = 2` there, so each branch runs at least once.

**R1-6 (minor): the `large` lane is never driven, so a broken lane rule passes.**

Where: `test/core/Tellma.Core.IntegrationTests/Crud/Conformance/CrudInstrumentTests.cs:118-120`.
It asserts `small` only.

`AssertClosed` would still pass if the lane rule broke, for example rows counted at the root only
rather than "entities at every depth", or `>` changed to `>=`. That is because `large` is admitted
whether or not it is right.

Fix: drive the large lane cheaply in the same test:
- `GetByIdsAsync` or `DeleteByIdsAsync` over `LargeBatchThreshold + 1` missing ids, one round
  trip each; or
- a host with a lowered `DataOptions.LargeBatchThreshold` (say 2) and a save of one widget with
  two parts. This also pins "at every depth".

Then assert `get_by_ids … large` or `save web large` in the superset.

**R1-7 (minor): the reachability case accepts any exception but `InvalidOperationException` as
"reachable".**

Where: `StackConformanceTests.Operations.cs:48-51` and `:61-62`.

A declared operation that crashes with `NullReferenceException`, `NotSupportedException` or an
`ArgumentException` deep in the pipeline counts as reachable. For `delete_by_query`, nothing else in
the base calls the operation, so this case is its only pin (R1-1). The outcome of each call is
known: a query or save answers, and every id-naming call on `MissingId()` is a `NotFoundException`
for the stack's resource.

Fix: assert the expected outcome per row:
- `null` for query, save, all and delete-by-query (expected count 0);
- `NotFoundException` naming the resource for get, delete, delete-with-descendants and
  activate/deactivate;
- for get-by-ids and get-by-parent-ids, an empty answer.

**R1-8 (minor): the Gadget activatable skip and the server-owned `Fk.InUse` exclusion are both
broader than their reasons.**

Where:
- `StackConformanceTests.Recipes.cs:33`;
- `StackConformanceTests.Values.cs:215`.

Two gaps:
- A read-only activatable stack skips the whole recipe ("serves no save, so it has no activation
  actions"). The recipe's read rule still applies: inactive rows are read only with
  `IncludeInactive`. Its rows can be stored inactive through `CreateAsync`. So Gadget never pins
  the activatable conjunct.
- A server-owned incoming reference is dropped before `ReferToAsync` is consulted, so a closer
  cannot opt in. Spec 0018's `User` closure is the stack whose rows every audit FK references.

Fix:
- Split the recipe. Run the `IncludeInactive` part whenever the stack is activatable: store an
  inactive row through `CreateAsync` with the flag false, and let the Gadget closer's SQL honour
  it. Skip only the create, action and update parts without activation.
- Expose a virtual predicate, such as `protected virtual bool ExercisesReference(EntityMetadata,
  ReferenceMetadata)`, that defaults to the current exclusions, so a closer can widen it.

**R1-9 (minor): the cached-list assertions expect 0 round trips even when the table exceeds
`MaxRows`.**

Where: `StackConformanceTests.Budget.cs:41-45` and `StackConformanceTests.Recipes.cs:113-114`.

§16.2 says a cached list on a table beyond `MaxRows` takes 2 round trips on every call, and is not
cached (`CacheOutcome.Oversized`). The base creates rows in every case. So a distribution's
cacheable reference table seeded near its limit is pushed over it by the suite itself, and both
cases then fail against a budget the spec says is correct. The fixture's Lookup (`MaxRows = 50`)
is safe today only because each class creates about 15 rows.

Fix: read the stack's row count with a counted query (`IncludeInactive`), and expect 2 trips and
no cache when it exceeds the cacheable `MaxRows`. Or skip the 0-trip assertions with that reason.

### Findings

**R2-1 (major): the base pins a delete by query that skips the stack's delete validators, which
lets a judged stack's delete rules be bypassed.**

Where:
- `src/core/Tellma.Core.Testing/Crud/StackConformanceTests.Budget.cs:134-141` asserts 1 round trip
  whether or not deletes are judged.
- `src/core/Tellma.Core/Crud/Delete/DeleteRun.cs:254-256` is the cause.
- `src/core/Tellma.Core/Crud/StackRegistry.cs:266-271` shows the consequence was known, but only for
  security tables. Its comment reads "A delete by query runs no validation hook, so a stack over a
  security table would let it delete past the rules…".

Failure scenario:
- Every `TopLevelEntity` stack serves `delete-by-query` by default (spec 0015's capability table).
  The startup gate refuses it only over security tables.
- Any other stack whose `ValidateDeleteAsync`, or a component's, enforces a rule loses that rule on
  `delete-by-query`.
- The concrete case is spec 0020's `ScheduleService`, a full `TopLevelEntity` stack. Its
  `ValidateDeleteAsync` refuses built-in schedules, yet a caller with `core.Schedule`/`Delete` can
  remove a built-in through `DeleteByQueryAsync("Id = <built-in>")`.
- The same holds for every distribution rule of the form "row X cannot be deleted while Y".

The conformance base is where a distribution would find this, but it asserts the bypass as the
budget. D-131's "align §16.2 to §10.2" would then write the bypass into the spec.

Fix:
1. This is a decision for Ahmad. Either:
   - (a) extend the `StackRegistry` gate from security tables to every stack whose deletes are
     judged (`HookOverrides.ValidatesDeletes`), so such a stack cannot keep `DeleteByQuery`; or
   - (b) give a judged delete by query §16.2's RT1: collect the keys under the filter, load the
     `DeleteContext`, validate, then persist, at 2 round trips.
2. Until he decides, the base should not pass a judged stack that serves `DeleteByQuery` at 1
   round trip. One way is a case that fails, naming the conflict, when `ValidatesDeletes` and
   `Serves(StackOperations.DeleteByQuery)` both hold. The JudgedWidget closer would then declare
   its operations without `DeleteByQuery`, as (a) would require anyway.
3. Amend D-131's note to say that the §16.2/§10.2 choice decides whether delete rules apply to
   `delete-by-query`.

**R2-2 (major): every budget row is measured at a cardinality of one, so a round trip per row or
per id is invisible.**

Where:
- `src/core/Tellma.Core.Testing/Crud/StackConformanceTests.Budget.cs:36-59` reads details by ids
  with one id, gets by parent ids with one parent, and reads one row for the query and child-surface
  rows.
- `:107-113` creates and updates one entity, which has one part with one note.
- `:120-155` runs each action, the delete and the delete with descendants on one id.

§16.2's rows say "Details, one or many", "Save — any update" and "Delete by ids". The regression a
budget pin exists to catch is a statement issued per row or per id, and at n = 1 that costs exactly
the budget. Examples:
- the details round trip loading child FK targets per row, instead of D-109's one grouped `Rows`
  per expand level;
- a pre-check or a stamp read per id in a delete or an action;
- a key probe per child row in a save.

Each of these passes every conformance class today.

Fix: keep the budgets and raise the cardinality to two at every level:
- `GetByIdsAsync([a, b])`;
- `GetByParentIdsAsync` over two parents;
- `DeleteByIdsAsync([a, b])` and `DeleteWithDescendantsAsync([a, b])`;
- each action on `[a, b]`;
- a create of two `NewValidEntity` rows and an update of two loaded rows.

Also add one of these:
- a guard that fails, naming `NewValidEntity`, when an entity's collections hold fewer than two
  rows at any depth; or
- a second, ordinal-driven child row that the base adds through `SetRows`, as the unique case
  already does.

**R2-3 (minor): the searchable recipe does not pin the search kind.**

Where: `src/core/Tellma.Core.Testing/Crud/StackConformanceTests.Recipes.cs:174-187`.

The case searches each property for its whole stored value, which matches under both `Prefix` and
`Contains`. Two regressions therefore pass:
- `Lookup.Code`'s `[Searchable(Prefix)]` compiled as a contains search, which loses the sargable
  seek the kind exists for;
- a contains property compiled as a prefix search.

Fix: also search each property for a fragment from inside its value, such as `term[1..]`. Expect 0
rows for `Prefix` and 1 for `Contains`. Fail, naming `NewValidEntity`, when a searchable value is
shorter than 2 characters.

**R2-4 (minor): unique values are checked only at the root and its direct children, and only on
create.**

Where: `src/core/Tellma.Core.Testing/Crud/StackConformanceTests.Values.cs:173-198`.
`childUnique` iterates `Metadata.Children` only, the same limit R1-2 fixed for collections.

Two gaps:
- A `[Unique]` on a grandchild is never exercised, for example a future distribution's
  document → line → entry.
- The update path is not exercised. §18.2 pins the key-load pre-check "on create and on update",
  and the update path is a separate pre-check that must exclude the stored row's own value. A
  pre-check that compares an update against its own row, or skips updates, passes.

Fix:
- Walk `CollectionPaths(Metadata)` for the child cases, setting the two rows on
  `Owner(entity, path)`.
- For each root unique property, add an update case: store A and B, load B, give it A's value, and
  expect `Unique` at `[0].<Property>`.
- Also save B unchanged, which must pass, so a row is never a duplicate of itself.

**R2-5 (minor): the `tellma.crud.save.entities` lane is never pinned at `large`.**

Where: `test/core/Tellma.Core.IntegrationTests/Crud/Conformance/CrudInstrumentTests.cs:124` and
`:136-137`.

That instrument's lane is computed on its own, from `_rows.Count`
(`src/core/Tellma.Core/Crud/Save/SaveRun.Persist.cs:379`). The duration's lane comes from
`SaveOperation.CountRows` instead (`SaveOperation.cs:188`). The superset asserts only `web small`
and `import small`, so that lane could report `small` for three rows, or count only root rows, and
stay green.

Fix: in the two widget lane calls, also read `CrudTelemetryNames.SaveEntities`. Assert `web small`
for the two-row save and `web large` for the three-row save.
