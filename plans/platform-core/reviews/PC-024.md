### Deviations (also in the commit message)

1. Registration's statement draws the id in its own statement (`IF @id IS NULL SET @id = NEXT VALUE
   FOR …`): SQL Server forbids `NEXT VALUE FOR` inside `COALESCE`, so §7.5's statement cannot run. It
   also computes the default database name `CONCAT(@databasePrefix, '.', @id)` in SQL, where the id
   is known.
2. Rename throws `50404 tenant-not-found` when no row matched (→ `TenantNotFoundException`) instead
   of committing a version bump that changed nothing.
3. `SetStateAsync`/`RelocateAsync` pre-read the row from the store: a missing tenant is
   `TenantNotFoundException` (not a refusal), and the transition is validated against the stored
   state; the statement's `@from`/state guard still settles races (→ `50409`).
4. `ITenantRegistry` adds `bool IsAvailable` (readiness reads it rather than re-deriving the rule);
   `SnapshotLoadedAt` means "last confirmed" (load or unchanged probe), which is what the staleness
   bound counts from. `Find`/`Get` throw `catalog-unavailable` when stale or never loaded; `Tenants`
   never throws. `Retry-After` is the refresh interval in whole seconds (15 by default, the spec's
   literal).
5. The warm-profile warning is the registry's (`WarmTenantsExceeded`, after every reload including
   the first): `core.sql-profiles` runs in the gate before any snapshot exists.
6. `core.sql-profiles` also applies the Encrypt, password and Key Vault rules to the catalog
   connection string; requires a `default` profile and well-formed profile names and
   AllowedServers entries; requires `Encrypt` to be present **and** true/strict (not
   `Encrypt=False`). In Development the pool-bound rule still applies.
7. Rows refused from the snapshot also include an unknown profile, a malformed profile, a malformed
   database and an unknown category/state (each logged at Error), besides `TenantServerRefused`.
   Registration and relocation also refuse an unconfigured profile. The server grammar is strict
   (`[tcp:]host[\instance][,port]`); other protocol prefixes, named pipes and IPv6 literals are
   refused.
8. Subjects must be printable ASCII **without spaces**: SQL Server ignores trailing spaces in `=`
   even under BIN2, so `'alice '` would match alice's hints. Membership writes deduplicate
   `(TenantId, Subject)` before binding (the TVP has no key).
9. Membership writes do not bump `CatalogState.Version` (§7.5's statements do not; no snapshot holds
   hints). `RecordAsync` treats a malformed record like any failure (logged, metered, not thrown).
   `ReconcileAsync` and the source-tagged `RecordAsync` are internal methods of the directory
   (InternalsVisibleTo `Tellma.Core.Migrator`); the reconcile service in `Tellma.Core.AspNetCore`
   will need its own IVT or a public seam.
10. `CatalogState` is seeded with a fixed version (`…0001`) and timestamp by `HasData`, not
    `NEWID()`/`SYSUTCDATETIME()`: migrations are generated, never hand-edited, and the registry
    compares versions for inequality only.
11. `ITenantStateListener` is declared here (listed in PC-025): the registry's fan-out needs it.
    Listeners are not called for the process's first snapshot.
12. `CatalogDesignTimeFactory` creates `tellma_app` through a connection interceptor before
    migrating (never in `master`), resolving D-033's contradiction for the catalog: §6.1's
    design-time database otherwise fails on the table type's unguarded grant.
13. The history check opens its connection with `ConnectRetryCount=0`: SqlClient retries a login to a
    missing database (4060) for 10 s, which would let the first-load bound expire and hide the
    Development "run migrate" failure. Outside Development a 4060 (transient on Azure) starts the host
    not ready and logs the command (Error); a missing history table or a history without
    `Latest` fails startup in every environment (`TellmaCompositionException`, source
    `core.catalog`). A catalog found behind only after startup fails closed (no tenant served).
14. Catalog writes after commit never throw for a failed local refresh (logged
    `TenantWriteRefreshFailed`): reporting a committed write as failed invites a retry.
15. `TenantProblemCodes` (constants) and the explicit codes of `TenantUnavailableException` are
    additions; HostTelemetryNames is left to the AspNetCore checkpoints.
16. The `catalog.Sessions` table ships in the first migration (its statements stay with 0011-f), so
    the catalog has one initial migration.

### Findings

**R1-1 (major) — Listener fan-out runs inside the registry's single flight, unbounded.**
`src/core/Tellma.Core/Tenancy/TenantRegistry.cs:365-370` (and `NotifyAsync`, `:492-528`):
- **What happens.** `NotifyAsync` is awaited inside `RefreshCoreAsync`, before `ExecuteAsync`
  clears `_running`, and nothing bounds a listener call (the interface has no token).
- **Failure scenario.** A listener that is slow or never completes stalls the run. Examples: the
  hub (spec 0021) closing connections through a stalled SignalR service, or the worker (spec 0020)
  awaiting a lock. Every later probe joins it (`RefreshAsync(force: false)` returns
  `running.Task`), so the snapshot is never confirmed again. After `MaxStaleness` this instance
  answers `catalog-unavailable` for every tenant and reports not ready. The catalog write that
  triggered the reload (`RefreshAfterWriteAsync`) never returns either.
- **Re-entry deadlocks at once.** A listener that calls `ITenantRegistry.RefreshAsync(true)` or
  any `ITenantCatalog` write queues a run behind the running one, which is waiting for that
  listener.
- **Suggested fix.** End the flight before notifying: publish the snapshot, clear `_running`,
  then dispatch the changes to an ordered, serialized notification queue, which the write path may
  still await. Also bound each listener call with a timeout that is logged, and say in
  `ITenantStateListener`'s docs that a listener must not wait on the registry.
- **Tests to add.** A listener that never completes must not stop the next probe from confirming
  the snapshot. A listener that calls `RefreshAsync(true)` must not deadlock.

**R1-2 (minor) — A location can alias another tenant's database, or name the catalog itself.**
`src/core/Tellma.Core/Tenancy/TenantCatalog.cs:83-94, 247-250, 458-465`; `CatalogDbContext.cs:178`:
- **What happens.** `UX_Tenants_Location` compares `Server` as text. So `tcp:sql1`, `sql1,1433`,
  `SQL1` against `sql1.contoso.local`, and `sql1` all pass, and all reach one database.
  `RefuseLocation` also never compares a location with the catalog's own (`CatalogConnection.Server`
  plus its `Initial Catalog`).
- **Failure scenario 1.** `provision --server tcp:<tenant 1's server> --database <tenant 1's
  database>` registers a second tenant on tenant 1's database.
- **Failure scenario 2.** `--database <catalog name>`, or a `RelocateAsync` to it, points a
  tenant at the catalog. The migrator would then run tenant migrations into the catalog. In SaaS,
  the web identity is a `tellma_app` member there with DML on schema `catalog`.
- **Why minor.** Only operator paths take a location: the admin surface never passes one (§5.9).
  The schema guard would refuse tenant reads in the catalog.
- **Suggested fix.** Canonicalize `Server` before storing and comparing it: drop `tcp:`, drop
  `,1433`, lower-case the host. Refuse a location equal to the catalog's (server, database) with
  `tenant-registration-refused` / `tenant-location-refused`. Add a misuse test for each, since
  today no test covers an aliased location.

**R1-3 (minor) — A reloaded profile bypasses `core.sql-profiles`.**
`src/core/Tellma.Core/Tenancy/TenantRegistry.cs:96-98, 349-353, 531-544`:
- **What happens.** `OnProfilesChanged` forces a reload that composes every tenant string from
  `IOptionsMonitor<TellmaSqlOptions>.CurrentValue`. The profile rules (`Encrypt`, no password
  outside Development, `Max Pool Size` within the bound, no Key Vault literal) exist only in the
  startup check.
- **Failure scenario.** A configuration reload outside Development silently puts every tenant on
  an unchecked profile: a file change, or Key Vault's 15-minute `ReloadInterval`, delivering
  `Encrypt=False`, a password, or `Max Pool Size=200`. That defeats the transport and pool
  invariants of §3.5.
- **Suggested fix.** Factor the fragment rules out of `SqlProfilesCheck` into a shared validator.
  Apply it when the snapshot is composed: refuse rows on a profile that breaks the rules (logged at
  Error, like `ProfileMalformed`), or keep the last valid options and log the rejected change.

**R1-4 (minor) — One shared scope for all listeners contradicts the published contract.**
`src/core/Tellma.Core/Tenancy/TenantRegistry.cs:499` against
`src/core/Tellma.Core.Abstractions/Tenancy/ITenantStateListener.cs:25`:
- **What happens.** The contract says every registration is called "inside a service scope of
  its own". `NotifyAsync` creates one scope for every listener and every changed tenant of a
  reload.
- **Failure scenario.** A listener with a scoped dependency that caches per call sees state left
  by the previous tenant's notification in the same reload. That is a cross-tenant leak for any
  scoped cache keyed implicitly by tenant.
- **Suggested fix.** Create a scope per tenant notification, or per listener call. Or reword the
  XML doc to say one scope per reload.

**R1-5 (minor) — A tenant that leaves the snapshot is never announced.**
`src/core/Tellma.Core/Tenancy/TenantRegistry.cs:474-487`:
- **What happens.** `Changes` walks only `next.Tenants`. A tenant that the previous snapshot
  served and the new one does not is not reported. It drops out when its row now breaks the rules,
  for example when an operator removes its server from `AllowedServers` or its profile from
  `Profiles` to cut off a host.
- **Failure scenario.** The hub keeps that tenant's live connections open, and the worker keeps
  its in-flight polling, until they next resolve the tenant. Requests already return 404.
- **Suggested fix.** `OnStateChangedAsync(tenant, previous)` cannot express a removal. Either add
  a removal signal to `ITenantStateListener` before PC-025 consumes it, or record that removals
  are deliberately silent. Flagged for the orchestrator.

### Responses

- **R1-1: fixed in the review 1 fixes commit.**
  - **The fix.** `RefreshCoreAsync` publishes the snapshot and queues the reload's changes
    (`Enqueue`). It no longer waits for listeners, so the single flight ends before any listener
    runs. Deliveries go through an ordered, serialized chain (`DispatchAfterAsync`), one reload
    after another, in tenant order.
  - **The bound.** Each listener call is bounded by `TenantRegistryStartupOptions.ListenerTimeout`
    (10 s, on `TimeProvider`). A call that outlasts it is logged (`TenantStateListenerTimedOut`,
    Error) and the queue moves on; its scope is disposed when the call finally ends. A call that
    throws is logged and skipped.
  - **No write waits on the queue.** The write path does not await deliveries. That is what lets a
    listener refresh the registry, or write the catalog, without deadlocking.
  - **Docs.** `ITenantStateListener`'s docs now state the delivery model.
  - **Tests.**
    - `A_hung_listener_never_holds_the_refresh_and_times_out_into_the_next_notification`: the
      probe confirms while the listener hangs, and past the bound the next listener hears.
    - `A_listener_that_refreshes_the_registry_does_not_deadlock`.
- **R1-2: fixed.**
  - **Canonical servers.** `TenantLocations.Canonicalize` drops `tcp:` and the default `,1433` and
    lower-cases the value. Registration and relocation store the canonical server, so
    `UX_Tenants_Location` treats spellings of one server as one location.
  - **The catalog's own location.** `RefuseLocation` refuses a location equal to the catalog's own
    (canonical server, database compared without case), with `tenant-registration-refused` or
    `tenant-location-refused`.
  - **Limit.** A short host name and its fully qualified name, which only DNS unifies, are still
    two servers. Only operator paths take a location.
  - **Tests.**
    - The canonical-form unit tests.
    - Integration: `Another_spelling_of_a_tenants_server_cannot_alias_its_database` (three
      aliases, register and relocate) and `No_tenant_may_be_located_at_the_catalog_itself` (two
      spellings, register and relocate).
- **R1-3: fixed.**
  - **One validator.** The fragment rules moved into `SqlProfileRules`, which `core.sql-profiles`
    now calls.
  - **Applied on reload.** `TenantRowComposer` uses a profile only when the same rules pass. A
    reloaded profile that breaks them carries no tenant: the rows are refused as `ProfileMalformed`
    and logged `TenantProfileRefused` at Error.
  - **Tests.**
    - `A_profile_that_breaks_the_startup_checks_rules_refuses_its_rows`: encryption off, no pool
      bound, a pool bound too high, a password.
    - `A_reloaded_profile_that_breaks_the_connection_rules_carries_no_tenant`.
- **R1-4: fixed.**
  - **The fix.** Every listener call gets a scope of its own (`CallAsync`); the contract is
    unchanged.
  - **Test.** `Every_listener_call_runs_in_a_scope_of_its_own`: a scoped listener sees two
    instances for two changed tenants.
- **R1-5: fixed (orchestrator ruling).**
  - **The contract.** `ITenantStateListener` gains `OnRemovedAsync(TenantDescriptor tenant)`,
    called with the descriptor as the snapshot last held it. It covers a tenant that left the
    snapshot because its row was deleted or now breaks the deployment's rules.
  - **Delivery.** Removals ride the same ordered queue as changes, in tenant order.
  - **Tests.**
    - The listener test now covers a deleted row.
    - `A_tenant_that_leaves_the_snapshot_by_breaking_a_rule_is_announced_as_removed`.
- **Model.** The catalog model did not change, so the migration is not regenerated.
