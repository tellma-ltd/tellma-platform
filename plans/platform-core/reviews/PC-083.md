# PC-083 review

## Implementer notes

### What was built

Spec 0017 §2.1–§2.4, §3 (staging), §6.4 and §9 (all but the Azure option rules). The `core.Blobs`
table, its EF configuration, the Queryex `core.Blob` entity and the store, sniffer and file-name
primitives already existed from earlier checkpoints; this one adds everything between an upload and
a `Staged` row.

- **Contracts** (`Tellma.Core.Abstractions.Blobs`): `IBlobService` (StageAsync only),
  `BlobStageRequest`, `BlobDescriptor`, `IBlobKindRegistry`, `BlobKindDescriptor`, the new
  `BlobRejectedException` codes and arguments, the `busy` upload outcome tag, and
  `FeatureContribution.BlobKind(kind, transform)` with its `BlobKindContributionItem`.
- **Kind transforms and the registry** (`Blobs/BlobKindTransform.cs`, `BlobKindRegistry.cs`,
  `Composition/Realizers/BlobKindContributionRealizer.cs`, `Data/Metadata/EntityMetadataBuilder.Parts.cs`).
  Features' transforms in contribution order, then the host's (`TellmaBuilder.Blobs(...)`), are
  applied once in the entity-metadata build, so the registry and the metadata hold the same policy
  instance. The planner's "blob kind is registered" rule lives in the entity-metadata check: a
  `[BlobReference]` on an entity that is neither a stack's root nor a child of its aggregate is a
  composition problem. The registry walks every stack's aggregate; a child without a query surface
  (`[ApiResource(Queryable = false)]`) is owned by its nearest queryable ancestor with the
  navigation path up to it (`Spread.Album`).
- **Options and builder** (`BlobOptions`, `BlobsBuilder`, `ScratchDirectory`, `BlobRegistrations`).
  `BlobOptions` binds `Tellma:Blobs` through `OptionsRegistrar`; its remarks document the keys the
  image processor binds itself (`ImageConcurrency`, `PdfWorkerConcurrency`, `PdfWorkerMemoryLimit`),
  per the planner note, and nothing binds a second `ImageConcurrency`. The builder is sealed when the
  composition returns.
- **The `blobs` startup check** (`Blobs/BlobsCheck.cs`, `RequiresInfrastructure = true`): exactly one
  store; at most one processor and exactly one when an image kind exists; a transform for an
  undeclared kind; every policy field; every option positive and the 32-bit-seconds ceiling on spans
  a statement binds; every kind's `MaxSize` within `MaxUploadSize`; an absolute scratch path; and,
  for the file-system store, its options' validation (reusing
  `FileSystemBlobStoreOptionsValidator`) plus `FileSystemBlobStore.ProbeCreateOnlyPublish` at host
  start, per the planner note.
- **Staging** (`Blobs/BlobService.cs`, `UploadBody.cs`, `BlobStatements.cs`, `BlobUploadMetrics.cs`,
  `BlobServiceLog.cs`). Declared length against `min(policy.MaxSize, MaxUploadSize)` before reading;
  an image kind or a body of at most 64 KiB read into memory, anything larger spooled to a
  delete-on-close scratch file with SHA-256 computed while streaming; at most one byte past the
  declaration is read. Sniff, then for an image kind `ProcessAsync(kind, …, ImageProcessTimeout)`
  and the digest over the normalised bytes; otherwise `ThumbnailAsync(kind, …, ThumbnailTimeout)`
  where the policy asks for one (a null or failed thumbnail stores none and drops the `thumb`
  variant). The service never records the `tellma.blobs.image.*` instruments (the processor does).
  Then the stage statement through `IGuardedBatchRunner` (`BatchPurpose.Persist`): the soft quota
  (unexpired staged rows and bytes of `@tm_UserId`, read without locks; `THROW 50422` with the code),
  the id from `NEXT VALUE FOR core.sq_Blobs`, the deadline from `SYSUTCDATETIME()`; the platform's
  own scope (`IsSystem`) composes no quota. Row before bytes: the store write follows the commit,
  and a store failure leaves a staged row for the sweep.
- **Provisioning** (`Blobs/BlobContainerStep.cs`): `core.blob-container`, order 20, version 1,
  `IBlobStore.EnsureTenantAsync`. The store is resolved in `RunAsync`, not the constructor, so a
  composition without a store (client-asset emission, a migrator test host) still creates the step.
- **Resources**: six `Blob_*` strings in `Strings.resx` and `Strings.ar.resx`, the
  `Blob.ImageRejected` message selecting on `format`, `too-many-pixels`, `timeout` and `other`.
- **Test support** (`Tellma.Core.Testing/Blobs`): `InMemoryBlobStore` (passes the store
  conformance suite), `StubImageProcessor`, and `AddInMemoryBlobs()`. Every test host that composes
  the core model now calls it, because the core user kinds make the blobs gate require a store and
  a processor.
- **Defaults** (`Tellma.Defaults.Azure`): `UseAzureDefaults` now calls `AddTellmaSkia()` and, in
  Development, `AddFileSystemBlobStore()`, so Acme keeps starting (see Deviations).

### Tests

- Unit (`test/core/Tellma.Core.Tests/Blobs`): `BlobKindRegistryTests`, `BlobsCheckTests` (one case
  per rule), `BlobStatementsTests` (golden text with and without the quota, parameter types,
  reader), `BlobServiceTests` (every refusal code with its arguments, memory and spooled bodies,
  short and long bodies, normalisation, thumbnails, busy, quota translation, other assertion,

- `Tellma.Core.Testing.Tests/Blobs`: the in-memory store under the conformance suite, and

- Integration (`test/core/Tellma.Core.IntegrationTests/Blobs/BlobStagingTests.cs`, over

  quota and the bytes quota refusing as `Blob.StagingQuotaExceeded`, an expired row no longer
  counting, and the platform's scope staging past the quota as user 1. The migrator suite now
  expects `core.blob-container` among the provisioned steps.

### Deviations

1. **Split with PC-084.** The original 0017-c entry listed ResolveAsync/BlobDownload, the
   validator, the effect and its realizer, reconcile, the RCSI race test, the FK exemption and
   `fixture.BlobOwners`; PC-084's deliverables carry all of them, so none is here.
2. **Azure-only §9 rules** (Azure options, connection checks) are left to PC-089 with the adapter.
3. **Pull-forward from PC-089:** `UseAzureDefaults` registers `AddTellmaSkia()` and, in
   Development, `AddFileSystemBlobStore()`. Without it every Acme host fails the new gate, since
   the core user kinds need a store and a processor. Outside Development an Acme host still fails
   the gate ("No blob store is registered") until PC-089 adds `AddAzureBlobStore`.
4. **A body shorter than its declared length is `Blob.LengthRequired`** (411). The spec names only
   a missing length and a longer body (`Blob.TooLarge`).
5. **The check is named `blobs`** as the spec says, while the other core checks are `core.*`.
6. **`BlobContainerStep` resolves the store at run time** rather than through its constructor, so
   a composition without a store still builds; the blobs check reports the missing store.
7. **Test hosts compose `AddInMemoryBlobs()`** (core test composition, AspNetCore test host,
   catalog host, migrator harnesses, Acme web and migrator harnesses), so no suite writes under a
   developer's application data and none needs Skia.
8. **`core.blob-container` (spec 0017 §6.4) is pulled forward from PC-089**, to which D-096 had
   assigned it; accepted as D-120.
9. **Review 1:** the check is split into `blobs` (composition-only, run by the emit) and
   `blobs.deployment` (needs infrastructure). `core.imaging` now declares that it needs
   infrastructure. A new `BlobThumbnailFailed` warning event joins the spec's list of log events.

### Open risks

- Acme hosts now start the Skia processor and its PDF worker probe through `core.imaging`; the
  Acme suites replace both with the in-memory pair, so the real pair is exercised only by the
  imaging suites and a developer's `dotnet run`.
- The quota is soft by design: two concurrent uploads by one user can both pass at the limit.
- `UploadBody` spools to `Tellma:ScratchPath`; on Windows the delete-on-close file depends on the
  handle closing, which `DisposeAsync` guarantees on every path through `StageAsync`.

### What reviewers should examine hardest

- `BlobService.ReadAsync`: the one-byte overrun probe, the short-body path, and that the scratch
  file is disposed on every exception path.
- `BlobStatements` stage text: the quota predicate (`>= maxCount`, `bytes + size > maxBytes`), the
  `THROW` number and message the service maps, and that `@tm_UserId` is the system user's in the
  platform scope.
- `BlobKindRegistry` owner resolution for nested non-queryable children, against spec 0017 §2.3.
- `BlobsCheck` messages and fixes, and the `RequiresInfrastructure = true` choice (the probe creates
  the root and hard-links a file).

Scope: commit fe0edcc6 only. Rebuilt Tellma.Core.Tests, Tellma.Core.IntegrationTests,
Tellma.Core.Testing.Tests, Tellma.Distro.Acme.Web.Tests and Tellma.Distro.Acme.IntegrationTests
(Build succeeded, 0 warnings). Ran: Core.Tests filtered to Blobs, StartupGateTests,
TellmaMigratorTests, TenancyCompositionTests (430 passed); Core.Testing.Tests Blobs (60 passed,
1 skipped); Acme.Web.Tests (50 passed, including the Production builds and the in-process emit);
Core.IntegrationTests BlobStagingTests plus the migrator step-list case (5 passed); the Acme
integration suite (17 passed, 6 seam skips, among them the provisioning-record row, which still
needs core.bootstrap-administrator).

Judgements on the implementer's choices:

1. **Pull-forward into UseAzureDefaults: accepted.** Nothing in CI runs an Acme host outside
   Development that would now fail. `WebHostTests` (the one Production start) adds
   `AddInMemoryBlobs`. The Production `WebApplication`s in Acme.Web.Tests are built but never
   started, and they pass. `acme-client` runs the emit in Production, but `blobs` is
   `RequiresInfrastructure = true`, so the emit skips it. `identity-e2e` hosts Tellma.Identity.E2E
   and `design-e2e` hosts the EF MigrationsHost, so neither composes Acme. No deployment-shaped test
   exists (deferred tier). One side effect: `AddTellmaSkia` also adds the `core.imaging` check,
   which is not an infrastructure check, so the emit now loads Skia. On a Linux runner in
   Production it also spawns a PDF worker probe, both in `acme-client` and in Acme.Web.Tests'
   in-process emit. I could verify this only on Windows, where PDF thumbnails are off outside
   Development. Watch the first Linux CI run.
2. **BlobContainerStep here, and resolving the store in RunAsync: accepted on the code.** The
   premise that no checkpoint lists it is wrong, though: D-096 gave §6.4 to PC-089 (see R1-2).
3. **A short body is Blob.LengthRequired: accepted.** Over HTTP, Kestrel ends a body that is cut
   short with a bad-request or IO error, not a short read. So this path mainly guards in-process
   callers (server-generated blobs), and 411 with "cut short" in the message is a reasonable fit.
4. **The check is named `blobs`: accepted.** §9 names it, and `jobs.schedules` already breaks the
   `core.*` pattern.
5. **AddInMemoryBlobs in every test host: accepted.** It replaces both the store and the processor,
   and the gate and stage paths are still exercised against them. The real store is covered by its
   conformance suite. The real processor runs only in the imaging suites, which the open risks
   already state.

### Findings

**R1-1 (minor): a processor's thumbnail failure fails the upload.**
`src/core/Tellma.Core/Blobs/BlobService.cs:289-292` rethrows every exception from
`ThumbnailAsync` except a cancellation, after counting it as `failed`. Spec 0017 §3.2 step 6 says a
missing thumbnail is never a rejection. D-030 addendum 2 says "a failed or refused thumbnail never
fails the upload". The implementer notes claim "a null or failed thumbnail stores none".

Failure scenario: a processor registered through `tellma.Blobs(b => b.ImageProcessor<T>())` throws
on a hostile PDF. Every upload of that attachment kind is then a 500, after the whole body was
spooled. Skia hits the same path with an `ArgumentOutOfRangeException` from `Budget()` when
`Tellma:Blobs:ThumbnailTimeout` exceeds what a timer accepts (about 49.7 days). `BlobsCheck` admits
that value, since it only requires a positive timeout.

No test covers a throwing `ThumbnailAsync`.

Fix: catch any exception other than a cancellation, log it at Warning, and continue with no
thumbnail (an empty `Variants`). Do not count the upload as `failed`. Add a BlobServiceTests case
with a throwing processor. Optionally cap `ThumbnailTimeout` and `ImageProcessTimeout` in
`BlobsCheck` at what a timer accepts.

**R1-2 (minor): BlobContainerStep is pulled forward from PC-089 without recording it.**
D-096 assigns spec 0017 §6.4 (`core.blob-container`) to PC-089. It also puts on PC-089 the carry
for Acme's `The_provisioning_record_holds_the_platform_steps_with_their_versions`
(`distributions/acme/test/Tellma.Distro.Acme.IntegrationTests/MigratorTests.cs:166-184`, keyed on
`PlatformSeams.ComposesPlatformSteps`). This commit builds the step. Its message lists §6.4 under
Spec coverage, but not the pull-forward under Deviations, and the review notes do not mention it.

Failure scenario: PC-089's status row still claims §6.4 and the carry. If PC-078
(`core.bootstrap-administrator`) lands after PC-083, the seam-keyed provisioning-record test starts
running in PC-078's integration. PC-078 is not the checkpoint the carry names, so nobody is told to
watch it run green.

Fix: add the pull-forward as a deviation (commit message and implementer notes). The orchestrator
should move D-096's carry to whichever of PC-078 and PC-083 lands last, and drop §6.4 from PC-089.

**R1-3 (minor): XML docs cite the spec, against PLAN.md §7.1 item 5.**
- `src/core/Tellma.Core/Blobs/BlobService.cs:20`, `:216` and `:266` ("spec 0017 §3.2", "§3.6",
  "§3.2 step 6")
- `src/core/Tellma.Core/Blobs/BlobStatements.cs:30` ("spec 0017 §3.4")
- `src/core/Tellma.Core/Blobs/BlobKindRegistry.cs:22` ("spec 0017 §2.4")

Fix: drop the citations from the `///` text, and put them in inline `//` comments where they help.

**R1-4 (minor): Blob.UnsupportedType names the client's declared type when that type was not believed.**
`src/core/Tellma.Core/Blobs/BlobService.cs:105-109` passes `decision.ContentType` as the
`contentType` argument. For bytes that are always rejected or do not match their declaration, that
is the declaration. `BlobServiceTests.cs:247-251` pins it: an `MZ` executable declared
`application/pdf` is refused with `contentType = application/pdf`.

Failure scenario: the user reads "Files of type “application/pdf” can’t be uploaded here" for a
kind that accepts PDFs. The wording is the same in Arabic.

Fix: when the bytes contradict the declaration, report the sniffed type (for example
`application/x-msdownload`, `text/html` or `image/svg+xml`), or `application/octet-stream` when
nothing was sniffed. Keep the declared type only when it was itself the reason for the refusal.
Update the test.

**R1-5 (minor): the new UseAzureDefaults blob wiring has no test.**
`src/defaults/Tellma.Defaults.Azure/AzureDefaultsTellmaBuilderExtensions.cs:56-63` now registers
`AddTellmaSkia()` always and `AddFileSystemBlobStore()` only in Development. Its XML docs also
promise that a second call changes nothing. `test/defaults/Tellma.Defaults.Azure.Tests/AzureDefaultsTests.cs`
covers none of this: its only double-call test inspects the email transports.

Failure scenario: a regression goes unnoticed, such as the store registered outside Development,
or a second `UseAzureDefaults()` adding a second processor (which the gate refuses).

Fix: add cases for the Development and Production environments, asserting exactly one
`IImageProcessor` (`SkiaImageProcessor`) and one `IBlobStore` (`FileSystemBlobStore`) or none,
after `UseAzureDefaults().UseAzureDefaults()`. In BlobServiceTests, also assert that
`ThumbnailAsync` receives the kind and `BlobOptions.ThumbnailTimeout` (only the call count is
asserted today). The planner note makes that hand-off a rule.

**R1-6 (minor): the emit skips the blobs check's composition-only rules.**
`BlobsCheck.RequiresInfrastructure` is true for the whole check (`src/core/Tellma.Core/Blobs/BlobsCheck.cs:43`)
because of the store probe. So `emit-client-assets`, which runs only the checks that need no
infrastructure, also skips these rules:
- a transform of an undeclared kind;
- an unsound final policy;
- a kind above `MaxUploadSize`;
- a missing or second image processor.

Failure scenario: `tellma-client build` succeeds and emits client blob policies (spec 0029 §16) from
a composition the host then refuses at startup. For example, a kind whose `MaxSize` exceeds
`MaxUploadSize` gives the client a pre-check the server contradicts.

Fix, either:
- move the probe, file-system root and scratch rules into a second, infrastructure check, and keep
  the rest in `blobs` with `RequiresInfrastructure = false`. The store-count rule must stay with the
  infrastructure part while Production Acme has no store (until PC-089).
- or record this trade-off as a deviation.

### Responses

  on its own budget is treated the same way. `BlobsCheck` now also caps `ThumbnailTimeout` and
  `ImageProcessTimeout` at what a timer accepts (4294967294 ms). Tests: a throwing render and a

  - markup as `text/html` or `image/svg+xml`;

  A declaration the bytes contradict is never named. The sniffer and service tests are updated,
