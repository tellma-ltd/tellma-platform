# PC-083 review

## Implementer notes

### What was built

Spec 0017 §2.1–§2.4, §3 (staging), §6.4 and §9 (all but the Azure option rules). The `core.Blobs`
table, its EF configuration, the Queryex `core.Blob` entity and the store, sniffer and file-name
primitives already existed from earlier checkpoints; this one adds everything between an upload and
a `Staged` row.

- **Contracts** (`Tellma.Core.Abstractions.Blobs`): `IBlobService` (StageAsync only),
  `BlobStageRequest`, `BlobDescriptor`, `IBlobKindRegistry`, `BlobKindDescriptor`, the new
  `BlobRejectedException` codes and arguments, the `busy` upload outcome tag, and
  `FeatureContribution.BlobKind(kind, transform)` with its `BlobKindContributionItem`.
- **Kind transforms and the registry** (`Blobs/BlobKindTransform.cs`, `BlobKindRegistry.cs`,
  `Composition/Realizers/BlobKindContributionRealizer.cs`, `Data/Metadata/EntityMetadataBuilder.Parts.cs`).
  Features' transforms in contribution order, then the host's (`TellmaBuilder.Blobs(...)`), are
  applied once in the entity-metadata build, so the registry and the metadata hold the same policy
  instance. The planner's "blob kind is registered" rule lives in the entity-metadata check: a
  `[BlobReference]` on an entity that is neither a stack's root nor a child of its aggregate is a
  composition problem. The registry walks every stack's aggregate; a child without a query surface
  (`[ApiResource(Queryable = false)]`) is owned by its nearest queryable ancestor with the
  navigation path up to it (`Spread.Album`).
- **Options and builder** (`BlobOptions`, `BlobsBuilder`, `ScratchDirectory`, `BlobRegistrations`).
  `BlobOptions` binds `Tellma:Blobs` through `OptionsRegistrar`; its remarks document the keys the
  image processor binds itself (`ImageConcurrency`, `PdfWorkerConcurrency`, `PdfWorkerMemoryLimit`),
  per the planner note, and nothing binds a second `ImageConcurrency`. The builder is sealed when the
  composition returns.
- **The `blobs` startup check** (`Blobs/BlobsCheck.cs`, `RequiresInfrastructure = true`): exactly one
  store; at most one processor and exactly one when an image kind exists; a transform for an
  undeclared kind; every policy field; every option positive and the 32-bit-seconds ceiling on spans
  a statement binds; every kind's `MaxSize` within `MaxUploadSize`; an absolute scratch path; and,
  for the file-system store, its options' validation (reusing
  `FileSystemBlobStoreOptionsValidator`) plus `FileSystemBlobStore.ProbeCreateOnlyPublish` at host
  start, per the planner note.
- **Staging** (`Blobs/BlobService.cs`, `UploadBody.cs`, `BlobStatements.cs`, `BlobUploadMetrics.cs`,
  `BlobServiceLog.cs`). Declared length against `min(policy.MaxSize, MaxUploadSize)` before reading;
  an image kind or a body of at most 64 KiB read into memory, anything larger spooled to a
  delete-on-close scratch file with SHA-256 computed while streaming; at most one byte past the
  declaration is read. Sniff, then for an image kind `ProcessAsync(kind, …, ImageProcessTimeout)`
  and the digest over the normalised bytes; otherwise `ThumbnailAsync(kind, …, ThumbnailTimeout)`
  where the policy asks for one (a null or failed thumbnail stores none and drops the `thumb`
  variant). The service never records the `tellma.blobs.image.*` instruments (the processor does).
  Then the stage statement through `IGuardedBatchRunner` (`BatchPurpose.Persist`): the soft quota
  (unexpired staged rows and bytes of `@tm_UserId`, read without locks; `THROW 50422` with the code),
  the id from `NEXT VALUE FOR core.sq_Blobs`, the deadline from `SYSUTCDATETIME()`; the platform's
  own scope (`IsSystem`) composes no quota. Row before bytes: the store write follows the commit,
  and a store failure leaves a staged row for the sweep.
- **Provisioning** (`Blobs/BlobContainerStep.cs`): `core.blob-container`, order 20, version 1,
  `IBlobStore.EnsureTenantAsync`. The store is resolved in `RunAsync`, not the constructor, so a
  composition without a store (client-asset emission, a migrator test host) still creates the step.
- **Resources**: six `Blob_*` strings in `Strings.resx` and `Strings.ar.resx`, the
  `Blob.ImageRejected` message selecting on `format`, `too-many-pixels`, `timeout` and `other`.
- **Test support** (`Tellma.Core.Testing/Blobs`): `InMemoryBlobStore` (passes the store
  conformance suite), `StubImageProcessor`, and `AddInMemoryBlobs()`. Every test host that composes
  the core model now calls it, because the core user kinds make the blobs gate require a store and
  a processor.
- **Defaults** (`Tellma.Defaults.Azure`): `UseAzureDefaults` now calls `AddTellmaSkia()` and, in
  Development, `AddFileSystemBlobStore()`, so Acme keeps starting (see Deviations).

### Tests

- Unit (`test/core/Tellma.Core.Tests/Blobs`): `BlobKindRegistryTests`, `BlobsCheckTests` (one case
  per rule), `BlobStatementsTests` (golden text with and without the quota, parameter types,
  reader), `BlobServiceTests` (every refusal code with its arguments, memory and spooled bodies,
  short and long bodies, normalisation, thumbnails, busy, quota translation, other assertion,
  system scope, failing store, the upload instrument per outcome), `BlobContainerStepTests`.
- `Tellma.Core.Testing.Tests/Blobs`: the in-memory store under the conformance suite, and
  `AddInMemoryBlobs`.
- Integration (`test/core/Tellma.Core.IntegrationTests/Blobs/BlobStagingTests.cs`, over
  `ConnectDatabase`): the stored row and its id equal to the sequence's current value, the count
  quota and the bytes quota refusing as `Blob.StagingQuotaExceeded`, an expired row no longer
  counting, and the platform's scope staging past the quota as user 1. The migrator suite now
  expects `core.blob-container` among the provisioned steps.

### Deviations

1. **Split with PC-084.** The original 0017-c entry listed ResolveAsync/BlobDownload, the
   validator, the effect and its realizer, reconcile, the RCSI race test, the FK exemption and
   `fixture.BlobOwners`; PC-084's deliverables carry all of them, so none is here.
2. **Azure-only §9 rules** (Azure options, connection checks) are left to PC-089 with the adapter.
3. **Pull-forward from PC-089:** `UseAzureDefaults` registers `AddTellmaSkia()` and, in
   Development, `AddFileSystemBlobStore()`. Without it every Acme host fails the new gate, since
   the core user kinds need a store and a processor. Outside Development an Acme host still fails
   the gate ("No blob store is registered") until PC-089 adds `AddAzureBlobStore`.
4. **A body shorter than its declared length is `Blob.LengthRequired`** (411). The spec names only
   a missing length and a longer body (`Blob.TooLarge`).
5. **The check is named `blobs`** as the spec says, while the other core checks are `core.*`.
6. **`BlobContainerStep` resolves the store at run time** rather than through its constructor, so
   a composition without a store still builds; the blobs check reports the missing store.
7. **Test hosts compose `AddInMemoryBlobs()`** (core test composition, AspNetCore test host,
   catalog host, migrator harnesses, Acme web and migrator harnesses), so no suite writes under a
   developer's application data and none needs Skia.

### Open risks

- Acme hosts now start the Skia processor and its PDF worker probe through `core.imaging`; the
  Acme suites replace both with the in-memory pair, so the real pair is exercised only by the
  imaging suites and a developer's `dotnet run`.
- The quota is soft by design: two concurrent uploads by one user can both pass at the limit.
- `UploadBody` spools to `Tellma:ScratchPath`; on Windows the delete-on-close file depends on the
  handle closing, which `DisposeAsync` guarantees on every path through `StageAsync`.

### What reviewers should examine hardest

- `BlobService.ReadAsync`: the one-byte overrun probe, the short-body path, and that the scratch
  file is disposed on every exception path.
- `BlobStatements` stage text: the quota predicate (`>= maxCount`, `bytes + size > maxBytes`), the
  `THROW` number and message the service maps, and that `@tm_UserId` is the system user's in the
  platform scope.
- `BlobKindRegistry` owner resolution for nested non-queryable children, against spec 0017 §2.3.
- `BlobsCheck` messages and fixes, and the `RequiresInfrastructure = true` choice (the probe creates
  the root and hard-links a file).
