# PC-049: Tenant settings: tables, keys, store, cold load, provisioning step, negotiation initializer

## Implementer notes

### What was built

- **Tables** (spec 0013 §5.2, §8.2).
  - `Settings` (`src/core/Tellma.Core.Abstractions/Settings/Settings.cs`): sealed, `[TableType]`, `[Temporal]`, `[BumpsVersionTag("settings")]`. Typed `varchar` columns carry the value sets (Language, Calendar, TimeZone, Region); `Digits` is a `DigitStyle?`.
  - `SettingEntry` (`Settings/SettingEntry.cs`): unique `nvarchar(128)` `Key`, `[JsonColumn]` `Value`.
  - `SettingsConfiguration` (`src/core/Tellma.Core/Settings/SettingsConfiguration.cs`):
    - the three checks, `CK_Settings_SingleRow`, `CK_Settings_Languages` and `CK_Settings_Calendars`;
    - the `gc` default on `PrimaryCalendar`;
    - the `HasData` placeholder: TenantId 0, `en`/`gc`/`UTC`, authored by the system user at `AccessSeeds.SeededAt`.
  - `CalendarMonthRow` and its configuration (`src/core/Tellma.Core/Calendars/CalendarMonthRow.cs`): `core.CalendarMonths`, keyed (Calendar, Year, Month), with `UX_CalendarMonths_Calendar_StartDate`. It is seeded with 2,196 Umm al-Qura rows computed from `UmAlQuraCalendar`. It is not an entity: no Id, audit columns, history or UDTT.
- **Keys** (§5.3, §1.3).
  - `contribution.SettingKeys(typeof(Holder))` adds a `SettingKeysContributionItem`. `SettingKeysContributionRealizer` records each closed holder type once and refuses an interface or an open generic.
  - `DeclaredSettingKey.Discover` reads the public static `SettingKey<T>` fields in declaration (metadata-token) order, with nullability from `NullabilityInfoContext`.
  - `SettingValueShape` is the admitted type set.
  - `SettingKeyRegistry` provides `Keys`, `Find` and `Categories` (general first, then by first appearance), plus a lazily built `Describe()`. `DescriptionKey` is set only when `INeutralStringKeys.Declares` it.
  - `SettingKeysCheck` (`core.setting-keys`) holds every §5.3 rule.
  - `ConventionalStringKeys` now emits the derived group's `SettingGroup_` key as well as a stated one.
- **Store and cold load** (§5.6, §5.7).
  - `TenantSettingsStore` is the `settings` kind of `VersionedCache`. It holds a `TenantSettings` plus the client view pre-serialized with `TellmaJson.Options`. `Build` does the following:
    - applies the routing guard;
    - resolves the typed columns with the en/gc/UTC fallbacks and `SettingsValueUnresolvable` (Critical);
    - converts the zone from IANA to Windows;
    - parses the digits by name only;
    - drops undeclared entries and those that do not read as their key (counted in `tellma.settings.entries.invalid`);
    - keeps secrets protected.
  - `SettingsColdLoadContributor` runs at Order 60, after the prelude, and appends `SettingsColdLoad.Text` to the store's own read batch.
  - `TenantSettingsCache` is the scoped façade: `GetAsync`, `GetForClientAsync` and `Peek`.
- **Secrets.** `SettingSecrets.For(provider, tenantId)` creates the protector with purpose `Tellma.Core.Settings.Secret` plus the tenant id. `TenantSettings.Get<T>` unprotects on first read.
- **Provisioning.** `SettingsProvisioningStep`: `core.settings`, Order 15, Version 1.
  - It completes the placeholder through a persist batch's `Save<Settings>`, which brings history, audit stamps and the settings tag bump.
  - It takes the tenant's languages and calendars from `Tellma:Seed:Tenants`, validated as the editor would: offered, distinct, at most 3 languages and 2 calendars. Otherwise it uses the distribution's first language and `gc`.
  - A row already completed for the tenant is left alone.
- **Negotiation.** `LocaleNegotiationInitializer` runs at Order 200. It sets Language, Culture, CultureInfo, CalendarSystem, TimeZone, TenantTimeZone, Today, ContentLanguageIndex and TenantSettings. Stored preferences come from the new internal `IUserLocalePreferences` (optional).
- **Client metadata.** `SettingsClientAssetContributor` writes four Core-chunk sections: `languages` (`nativeDigits` written as null when the digits are Latin), `calendars`, `settingKeys` and `settingCategories`.
- **Test support.** `Tellma.Core.Testing` gains `FixedTenantSettingsCache` and `UseFixedTenantSettings()`. Every host over an in-memory catalog now runs the Order-200 initializer, which reads settings, so `TellmaTestHost`, `TenantContextHarness` and the integration suite's `CatalogHost` (whose tenant databases are created empty) use it.
  - The migrator integration tests now see the platform's first own provisioning step: the two-names test counts `core.settings` among four steps, and the version-tag test of a migration with no step removes Core's steps from its record.
- **Migrations.** The three unreleased initial migrations were regenerated with dotnet-ef and their BOMs stripped:
  - the fixture (`Tellma.Testing.Entities`);
  - the migrator test distribution;
  - Acme (`InitialTenant`).
- **Docs.** The `Tellma.Core` README has a new "Tenant settings" section, and the `Tellma.Core.Testing` README has an entry for the fixed cache. ARCHITECTURE.md needed no change: it states nothing this checkpoint contradicts.

### Deviations

1. The cold load is appended to the settings store's own read batch only, not to every unmarked batch.
   - §5.7 "bare on loader batches" is read as the loader's batch.
   - A caller's marked batch is absorbed through the seam `SettingsColdLoadContributor.Absorb(batch)`. It returns the `@tm_LoadSettings` parameter (true when a load is pending or the cached entry is not current) and a reader factory that settles the pending load or offers the rows to the store.
   - PC-050's connect prologue calls the seam. Nothing calls it yet.
2. The placeholder (TenantId 0) is never cached. The façade re-checks it on every hit and join (`Admit`), so a user scope can never be served a placeholder that a System scope loaded.
3. The Order-200 initializer does not set `CurrentCulture`/`CurrentUICulture`.
   - The CHECKPOINTS wording asks for it. WATCHLIST (PC-025) records that a culture set inside an initializer does not flow back to the caller.
   - `RequestContext.ApplyCultures()` at the front door owns it. The initializer's remarks say so, and a test pins that no ambient culture changes.
4. A user's stored locale preferences come through a new internal seam, `IUserLocalePreferences`, which is optional in the initializer.
   - Nothing registers it yet. The connect initializer or user-preferences owner (PC-050 or later) must register it.
   - Until then a scope negotiates from the request and the tenant only.
5. The provisioning step saves `Settings` through its own persist batch in the step's system scope. It does not use a provisioning-frame API: none exists for a non-stack entity, and the emitter still writes the history row and bumps the tag.
6. `TenantSettings.TenantId` is the routed tenant's id, which for the placeholder is not the row's 0.
7. `Tellma.Core.Testing` gains `FixedTenantSettingsCache` and `UseFixedTenantSettings()`, which the deliverables do not list. Every host over an in-memory catalog now runs the Order-200 initializer, and without them its tenant scopes would reach for a tenant database.
8. `LocalizationContext` gains `Language` and `CultureTag` beyond the spec's sketch (which an earlier checkpoint had already extended with `ContentLanguages`). They carry the negotiated language and `<language>-<region>` tag, because a host without the pair's culture data resolves it to a culture whose name is the language alone or empty.

Not a deviation: the settings securables (§5.5, `core.Settings.<category>` × Read/Save) are not registered here, because PC-079 lists §5.5 (securables) among its sections. The categories' `Resource` names are already the §5.5 names.

### Open risks and what to examine hardest

- **The routing guard and the placeholder.** `TenantSettingsStore.Build` accepts the placeholder only when `allowPlaceholder`. The contributor passes `accessor.Current.IsSystem` from the scope that runs the load, and the façade re-admits on hits and joins.
  - A placeholder load (only a System scope's can produce one) is served under `VersionTag.None` and never stored; a user scope that joins such an in-flight load is refused by `Admit`.
  - Please confirm there is no path that stores a placeholder.
- **`Absorb`'s contract for PC-050.** The reader factory settles a pending store request, or else offers the rows (`Offer`, best effort).
- **Fallback logging.** `SettingsValueUnresolvable` is Critical and fires on every cold load of a row the composition cannot resolve, for example a language the distribution stopped offering. This is spec-mandated, but it is noisy by design.
- **D-076 carry.** A language change moves only the `settings` tag. Cacheable entities key by shape, so they are safe. Any other cache that reads the shape from settings needs the same care; PC-079 should bump entity tags on a language change or fold the shape into the wire tags.
- **Shared fixture and Acme EF model.** Both changed (new tables, seed rows and UDTTs), and all three migrations were regenerated. PC-042 (slot pc-4) also touches them, so these commits must be serialized.

**R1-1 (major): no assertion covers the seeded-languages half of the provisioning rule.**
- Where: `test/core/Tellma.Core.IntegrationTests/Settings/TenantSettingsTests.cs:218-237`, against `src/core/Tellma.Core/Settings/SettingsProvisioningStep.cs:88,97-101,118-138`.
- The CHECKPOINTS test line asks for "provisioning completes the placeholder with seeded languages/calendars". The test seeds only `languages: ["en"]`, because the fixture offers English alone. So these paths have no assertion that would fail if they broke:
  - the seed's second and third codes landing in `SecondaryLanguage`/`TertiaryLanguage`;
  - `Name2`/`Name3` taken from the descriptor only within the seeded shape;
  - the "twice" and "more than three" language refusals.
- Spec 0013 §5.7's own example is not pinned anywhere: Acme's seed `["en","ar"]` / `["gc","uq"]` gives tenant 1 English primary, Arabic secondary, Gregorian primary and Umm al-Qura secondary. Acme's `MigratorTests` provisions exactly that seed but reads nothing back.
- Failure scenario: a regression such as `SecondaryLanguage = codes.Count > 2 ? …`, or dropping `Name2`, passes every suite.
- Suggested fix, either of:
  - In `distributions/acme/test/Tellma.Distro.Acme.IntegrationTests/MigratorTests.cs`, after the first `migrate`, assert tenant 1's `core.Settings` row: `TenantId` 1; languages `en`/`ar`/NULL; calendars `gc`/`uq`.
  - Add a unit test of the step over a composition that offers `en` and `ar`, covering the ordered languages, `Name2`, and the duplicate and four-language refusals.

**R1-2 (minor): `Today` comes from a second clock read, not from the context's `Now`.**
- Where: `src/core/Tellma.Core/Localization/LocaleNegotiationInitializer.cs:86`.
- `RequestContext.Today` is documented as "the date of `Now` in `TenantTimeZone`", and `Now` is fixed once when the scope is stamped. The initializer instead sets `Today = tenant.Today(time)`, which reads the clock again after at least one awaited settings load. It will read it again each time PC-050's runner re-runs the initializer after `SettingsStale`.
- Failure scenario: a request stamped at 23:59:59.9 tenant time whose cold settings load takes a few hundred ms gets `Now` on day D and `Today` on day D+1. Then `today()` filters and messages disagree with `now()` and with the context's own contract. The unit tests hide this: they give the initializer a `FakeTimeProvider(Evening)` that differs from the harness clock behind `Now`, so `completed.Now` and `completed.Today` already come from different instants (`LocaleNegotiationInitializerTests.cs:66,70`).
- Suggested fix: `Today = DateOnly.FromDateTime(TimeZoneInfo.ConvertTime(context.Now, tenant.TimeZone).DateTime)`, and drop the `TimeProvider` dependency. Add a test that sets `Now` just before midnight in the tenant zone with the clock past it, and asserts that `Today` follows `Now`.

**R1-3 (minor): `Language` and `Culture` are sliced out of `CultureInfo.Name`, which is not always `<language>-<region>`.**
- Where: `src/core/Tellma.Core/Localization/LocaleNegotiationInitializer.cs:80-81,95-100`.
- When the host's ICU lacks a pair, `NegotiatedCultures.New` falls back to the language-only culture or to a clone of the invariant culture. That can happen for a language a distribution added with `AddLanguage` under predefined-cultures-only mode.
- Failure scenarios:
  - For the invariant fallback, `Name` is `""`. Both `Culture` and `Language` are set to `""`, and `RequestContext`'s `NotBlank` init throws `ArgumentException`. Every request of a tenant whose primary language is that language then fails, although the negotiator "never throws".
  - For the language-only fallback, `Culture` is `"xx"` rather than the `<language>-<region>` that §9.2 requires.
  - A language code with a subtag of its own (`zh-Hant`) whose pair fell back to the language-only culture gives `Language = "zh"`: `LanguageOf` cuts the last subtag whether or not it is a region.
- Suggested fix: carry the negotiated language code and region out of the negotiation, from the matched `LanguageInfo` and region, rather than parsing `Culture.Name`. Set `Culture` to `<code>-<region>` from them. Add a test with a negotiator stub that returns an invariant-named culture.

**R1-4 (minor): the derived-group `SettingGroup_` key added to `ConventionalStringKeys` has no test.**
- Where: `src/core/Tellma.Core/Localization/ConventionalStringKeys.cs:228-230`.
- The only case is `ConventionalStringKeysTests.cs:82-95`, which states `group: "widgets"` on `fixture.widgets.autoNumber`. Its derived group is also `widgets`, so the old `key.Group` code produced the same set.
- Failure scenario: reverting to `key.Group` drops `SettingGroup_gl_posting` for an ungrouped `gl.posting.autoNumberOnPost`, and no test fails. The resource audit would then call a pack's derived-group label an orphan.
- Suggested fix: add a case with no stated group and three segments (`fixture.widgets.autoNumber`, no `group:`) expecting `SettingGroup_fixture_widgets`, plus a two-segment key expecting no group key.

**R1-5 (minor): the "host without data protection" rule of §5.3 is untested.**
- Where: `src/core/Tellma.Core/Settings/TenantSettingsStore.cs:175,190`.
- `TenantSettingsStore` with `protection: null` binds no `Unprotect`, and every secret should read as its default with `SettingsSecretUnreadable` (Critical) and one `tellma.settings.entries.invalid`. `TenantSettingsStoreTests` always builds the store with `PurposeProtection`, and the integration host has no secret key.
- Failure scenario: a change that makes a provider-less host throw, or skip the event, passes.
- Suggested fix: one unit case in `TenantSettingsStoreTests` over a store created without a provider. Assert that `Get(SampleKeys.ApiKey)` is null, that one Critical `SettingsSecretUnreadable` is logged, and that the counter moves by 1.
