# PC-029: Access tables, entities, seeds and fixture migrations

## Implementer notes

### What was built, and where

- **Abstractions** (`src/core/Tellma.Core.Abstractions/Access/`): the enums `UserKind`, `UserState`,
  `InviteStatus`, `Gender`; `WellKnownIds` (ids 1, band end 999); `AccessActions` (13 actions + `*`);
  `CoreResources`; the unsealed default leaves `User` (TopLevelEntity, IActivatable, temporal, stack
  with `Enlist`, `[ApiResource]`, per-user preferences tag bump), `Role` (permissions tag bump),
  the children `RoleMembership` (per-user permissions tag bump) and `Permission`; the standalone
  table type `UserPreferenceList`. Server-owned: `Subject`, invite evidence, `JoinedAt`,
  `IsActive`; write-once `Kind`; derived `Permission.FilterQueryexVersion`; database-owned `State`.
- **Abstractions, blobs** (`Blobs/Blob.cs`, `Blobs/BlobState.cs`): the `core.Blobs` row (0017 §2.1),
  declared now because the fixture's stand-in `core.Blobs` was removed and every `[BlobReference]`
  (User.ImageId/SignatureId) needs the production table. Never a stack.
- **Core** (`src/core/Tellma.Core/Access/`): open configurations `UserConfiguration<TUser>`,
  `RoleConfiguration<TRole>`, `RoleMembershipConfiguration<T>`, `PermissionConfiguration<T>` (State
  computed column, `UX_Users_Subject` covering, the five `CK_Users_*`, `IX_Users_IsActive_Name`,
  `IX_Roles_IsPublic`, window check, the two membership indexes, the two permission checks and
  covering `IX_Permissions_RoleId`, and the §3.8 seeds); `UserStamp` + configuration (one-to-one,
  cascade, NEWID defaults, seed row with fixed tags, Queryex read-only annotation `core.UserStamp`);
  `UserPreference` + configuration (composite PK, cascade); `AccessSeeds`. `Blobs/BlobConfiguration.cs`
  (shadow `StorageKey`/`Sha256`, audit FK to the user leaf, the three indexes). All contributed by
  `CoreFeature` (`Composition/CoreFeature.cs`).
- **Conventions**: `ConventionModel.Leaf(IReadOnlyModel, …)` overload (configurations find the leaf
  at configuration time); `ChildConvention` no longer adds `IX_<Table>_<ParentKey>` when an explicit
  index leads with the parent key; `TellmaAnnotationNames.QueryexReadOnlyEntity`.
- **Fixture** (`test/shared/Tellma.Testing.Entities`): the `core.Users`, `core.Blobs`,
  `core.UserStamps` stand-ins removed (Jobs and VersionTags remain); migration regenerated with
  dotnet-ef (`20261111230341_Initial`).
- **Tests**: unit `test/core/Tellma.Core.Tests/Access/` (AccessModelTests, AccessLeafTests,
  AccessVocabularyTests) plus fallout across the Data/Composition tests (test models now extend
  Core's `User`); integration `test/core/Tellma.Core.IntegrationTests/Access/AccessSchemaTests`
  (36 cases) and the tracked-tables list in `DataBatchTests`.

### Deviations

1. `State` SQL is `ISNULL(CAST(CASE … END AS varchar(8)), 'New')` rather than the bare `CASE`, so
   the persisted column is `varchar(8) NOT NULL` as §3.1 declares (a bare CASE yields a nullable
   `varchar(7)`).
2. `ChildConvention` skips its own parent-key index when a configuration declares one leading with
   the parent key. Without it `RoleMemberships` gets a redundant `IX_RoleMemberships_UserId` beside
   `IX_RoleMemberships_UserId_RoleId`, and `Permissions` gets two indexes named `IX_Permissions_RoleId`.
3. `Blob`/`BlobState`/`BlobConfiguration` declared here (0017 §2.1 shape) rather than by the blob
   checkpoint; that checkpoint should extend these files, not recreate them.
4. `UserStamp`/`UserPreference` are internal non-entity classes in `Tellma.Core.Access`; the
   read-only Queryex exposure of `core.UserStamp` is an annotation the schema provider must honour
   when it lands (no provider implementation exists yet).

### Open risks

- A distribution leaf that adds a non-nullable column without a default to `User`, `Role`,
  `RoleMembership` or `Permission` cannot build: Core's `HasData` rows have no value for it. The
  model build reports it through `core.entity-metadata` with EF's message. Documented in the leaf
  test; worth a dedicated startup-check message later.
- `IX_Blobs_StagedBy` keys on `CreatedById`, so the audit FK on `core.Blobs` is indexed while other
  audit FKs are not (by design per 0017).

### Examine hardest

- The five `CK_Users_*` expressions against §3.1's evidence table (the integration theory covers
  one bad row per clause).
- `ChildConvention`'s new skip rule: it keys on `ConfigurationSource.Explicit` and the first index
  property only.
- The seeds' self-reference (system user created/modified by itself) and the EF `IDENTITY_INSERT`
  wrapper in the generated migration.
