# PC-029: Access tables, entities, seeds and fixture migrations

## Implementer notes

### What was built, and where

- **Abstractions** (`src/core/Tellma.Core.Abstractions/Access/`): the enums `UserKind`, `UserState`,
  `InviteStatus`, `Gender`; `WellKnownIds` (ids 1, band end 999); `AccessActions` (13 actions + `*`);

  declared now because the fixture's stand-in `core.Blobs` was removed and every `[BlobReference]`
  (User.ImageId/SignatureId) needs the production table. Never a stack.
- **Core** (`src/core/Tellma.Core/Access/`): open configurations `UserConfiguration<TUser>`,
  `RoleConfiguration<TRole>`, `RoleMembershipConfiguration<T>`, `PermissionConfiguration<T>` (State
  computed column, `UX_Users_Subject` covering, the five `CK_Users_*`, `IX_Users_IsActive_Name`,
  `IX_Roles_IsPublic`, window check, the two membership indexes, the two permission checks and

  `CoreFeature` (`Composition/CoreFeature.cs`).
- **Conventions**: `ConventionModel.Leaf(IReadOnlyModel, …)` overload (configurations find the leaf
  at configuration time); `ChildConvention` no longer adds `IX_<Table>_<ParentKey>` when an explicit
  index leads with the parent key; `TellmaAnnotationNames.QueryexReadOnlyEntity`.
- **Fixture** (`test/shared/Tellma.Testing.Entities`): the `core.Users`, `core.Blobs`,
  `core.UserStamps` stand-ins removed (Jobs and VersionTags remain); migration regenerated with

- **Tests**: unit `test/core/Tellma.Core.Tests/Access/` (AccessModelTests, AccessLeafTests,

### Deviations

1. `State` SQL is `ISNULL(CAST(CASE … END AS varchar(8)), 'New')` rather than the bare `CASE`, so
   the persisted column is `varchar(8) NOT NULL` as §3.1 declares (a bare CASE yields a nullable
   `varchar(7)`).
2. `ChildConvention` skips its own parent-key index when a configuration declares one leading with
   the parent key. Without it `RoleMemberships` gets a redundant `IX_RoleMemberships_UserId` beside
   `IX_RoleMemberships_UserId_RoleId`, and `Permissions` gets two indexes named `IX_Permissions_RoleId`.
3. `Blob`/`BlobState`/`BlobConfiguration` declared here (0017 §2.1 shape) rather than by the blob
   checkpoint; that checkpoint should extend these files, not recreate them.
4. `UserStamp`/`UserPreference` are internal non-entity classes in `Tellma.Core.Access`; the
   read-only Queryex exposure of `core.UserStamp` is an annotation the schema provider must honour
   when it lands (no provider implementation exists yet).

### Open risks

- A distribution leaf that adds a non-nullable column without a default to `User`, `Role`,
  `RoleMembership` or `Permission` cannot build: Core's `HasData` rows have no value for it. The
  model build reports it through `core.entity-metadata` with EF's message. Documented in the leaf
  test; worth a dedicated startup-check message later.
- `IX_Blobs_StagedBy` keys on `CreatedById`, so the audit FK on `core.Blobs` is indexed while other
  audit FKs are not (by design per 0017).

### Examine hardest

- The five `CK_Users_*` expressions against §3.1's evidence table (the integration theory covers
  one bad row per clause).
- `ChildConvention`'s new skip rule: it keys on `ConfigurationSource.Explicit` and the first index
  property only.
- The seeds' self-reference (system user created/modified by itself) and the EF `IDENTITY_INSERT`
  wrapper in the generated migration.

### Findings

**R1-1 (minor) — The commit message omits integration suites PLAN.md §7.1 item 4 counts as touched.**
- Where: commit c3bce14 message, `Tests:` line; implementer notes "Tests".
- What: the checkpoint changes `src/core/Tellma.Core.Abstractions` and `test/shared/*`, so every
  integration suite counts as touched. The commit reports only Tellma.Core.IntegrationTests.
  That leaves out the EF integration suite, the Queryex integration suite (both reference
  Abstractions directly) and the Identity integration suite (through Tellma.Testing.Support,
  which references Abstractions). Reviewers check this list, and an unrun touched suite would
  only show up red on CI.
- Status: I ran all three (results above) and none regresses, so the substance holds and only
  the record is wrong.
- Fix: list the three suites and their counts in the fix-round commit message.

**R1-2 (minor) — The ChildConvention skip also fires on filtered indexes, which cannot serve a parent's reads.**
- Where: `src/core/Tellma.Core/Data/Conventions/ChildConvention.cs:50-51`.
- What: the skip test is
  `index.GetConfigurationSource() == ConfigurationSource.Explicit && index.Properties[0] == parentKey`.
  It ignores the index's filter.
- Failure scenario: a pack or distribution configuration declares a filtered index on a child
  that leads with the parent key, such as `HasIndex(l => new { l.DocumentId, l.State }).HasFilter("[State] = 'Draft'")`.
  The convention's unfiltered `IX_<Table>_<Parent>Id` then silently disappears. Every load of
  a parent's children (the child query, the synchronising delete, the emitter's
  children-first deletes) loses its seek and scans the child table. Nothing in the startup gate
  reports it.
- The rationale comment (lines 47-49), "serves the same seeks", holds only for an unfiltered
  index.
- No current table is affected: the two access configurations declare unfiltered indexes.
- Fix: add `&& index.GetFilter() is null` to the condition. Add a ChildConvention unit test
  covering both cases: an explicit unfiltered index leading with the parent key suppresses
  `IX_<Table>_<Parent>Id`, and a filtered one does not. Today the rule is pinned only
  indirectly, by AccessModelTests' index-name lists.

**R1-3 (minor) — Two CHECK boundaries are untested.**
- Where: `test/core/Tellma.Core.IntegrationTests/Access/AccessSchemaTests.cs:229-235`
  (window) and `:197-210` (service evidence).
- Window check:
  - The only window case is `EndsAt < StartsAt`. The spec's half-open window makes
    `EndsAt = StartsAt` the boundary that must be refused, yet a mutant
    `[EndsAt] >= [StartsAt]` passes the suite.
  - A row with one null bound, which "a null bound passes" requires, is never inserted. Only
    the seed's both-null row exercises the null case.
- Service evidence check:
  - `CK_Users_ServiceEvidence`'s `InviteStatus IS NULL` clause has no refusing row. The one
    service row with invite evidence also sets `InvitedAt`, so the clause could be deleted
    without a test failing.
- Fix:
  - Add a refusal case with equal bounds.
  - Add an accepted insert, rolled back, with `StartsAt` set and `EndsAt` null, and one with
    the reverse.
  - Add a service row with `InviteStatus = 'Invited'` and `InvitedAt` null, expecting
    `CK_Users_ServiceEvidence`.

**R1-4 (minor) — No test that saving a `core.Users` row writes a history row.**
- Where: `test/core/Tellma.Core.IntegrationTests/Access/AccessSchemaTests.cs:239-268`.
- What: the checkpoint's test list (and 0014 §14) asks for history rows per save. The history
  test covers Roles, Permissions and RoleMemberships but not Users.
- Why it matters: Users is the one versioned table with a persisted computed column (`State`)
  inside a covering index. Its history table therefore takes `State` as a plain column, and an
  update that changes `JoinedAt` must write the old `State` to `UsersHistory`. Nothing pins that
  shape.
- Fix: in the same test, update a user's evidence (e.g. `Invited` → `Joined`) and assert that
  `core.UsersHistory` holds one row with `State = 'Invited'`. Clean up afterwards, as the role
  rows are.

### Responses

- R1-1: fixed in the review 1 fix commit. Its message lists every integration suite with its
  count, each re-run one at a time on Testcontainers.
- R1-2: fixed in the review 1 fix commit. `ChildConvention` now stands down only for an
  unfiltered explicit index (`index.GetFilter() is null`). The class remarks, the rationale
  comment and the Core README row say so. The new `Data/ChildIndexTests` pins both cases: an
  unfiltered configured index leading with the parent key suppresses `IX_<Table>_<Parent>Id`; a
  filtered one leaves the convention's full index (no filter, `INCLUDE (Id)`) in place.
- R1-3: fixed in the review 1 fix commit.
  - The window refusal is a theory over equal and reversed bounds.
  - `A_membership_with_one_open_bound_is_accepted` inserts, then rolls back, one row with only
    `StartsAt` and one with only `EndsAt`.
  - `A_service_account_with_an_invitation_status_is_refused` sets `InviteStatus = 'Invited'`
    with `InvitedAt` null and expects `CK_Users_ServiceEvidence`.
- R1-4: fixed in the review 1 fix commit. The history test now commits an invited individual
  and joins it. It asserts that `core.UsersHistory` holds exactly one row for it, with
  `State = 'Invited'` and `InviteStatus = 'Invited'`, and that the current row reads `Joined`.
  The user is removed in the `finally` with the role rows.
