# PC-040: Analyzers TELLMA0001–0006 and their packaging

## Implementer notes

### What was built, and where

- **`src/core/Tellma.Core.Analyzers`** (new; netstandard2.0, `EnforceExtendedAnalyzerRules`, Microsoft.CodeAnalysis.CSharp 5.0.0 private, ScriptDom 170.191.0 copied to output; not packable).
  - `TellmaDiagnostics.cs` holds the six descriptors. Every one is an Error, category `Tellma`, with a message built per finding.
  - `KnownNames.cs` lists every namespace, metadata name and assembly name the rules match. `SymbolExtensions.cs` holds the shared name tests. Nothing matches by symbol identity, so the assembly references no platform assembly.
  - `OrdinalBindingAnalyzer` (TELLMA0001). `new SqlDataRecord`, `SqlDataRecord.Set*` and `GetOrdinal` outside a type, or an enclosing type, marked `[TableTypeBinder]`.
  - `TenantContextAnalyzer` (TELLMA0002). `Set<T>()`, `Find`/`FindAsync`, a `DbSet<>` property read, `Database.SqlQuery*`/`ExecuteSql*`, and `SaveChanges*` over `TellmaDbContext` or a type derived from it. Exempt: `Tellma.Core` and assemblies whose name ends in `.Migrator`.
  - `ActionCallAnalyzer` (TELLMA0004). Invocations and method-group references of `[ApiAction]`/`[EntityAction]` methods outside the declaring type (and its nested types) and `Tellma.Core`. A derived type may call one on `this`/`base`.
  - `NestedPipelineAnalyzer` (TELLMA0005). The seven `EntityService<,>` front-door methods called from a hook override (an override of a virtual declared on `EntityService<,>`), an `[EntityAction]` method, or any member of an `IEntityValidator<>`/`IPersistEffect<>` implementer. `[ApiAction]` methods may call them.
  - `DataBatchAnalyzer` (TELLMA0003 and TELLMA0006). It shares one per-compilation scope: the runtime flag and a lazy `EntityTables` index.
    - `Sql/SqlText.cs` reads the interpolated string. Each hole becomes a stand-in: a quoted name for a `SqlIdentifier` whose name is constant, `[__tellma_holeN]` for one that is not, and `@__tellma_holeN` for everything else. It keeps a segment map so that every finding maps back to the exact source characters where it can.
    - `Sql/SqlHole.cs` classifies holes: value, identifier, table-type rows, alignment/format, bare `nameof`.
    - `Sql/SqlInspector.cs` is a `TSqlFragmentVisitor` over `TSql170Parser(initialQuotedIdentifiers: true)`. It finds:
      - write targets, resolved through `FROM` aliases, CTEs and derived tables;
      - refused statements;
      - `EXEC` against the allow-list;
      - variable declarations and assignments;
      - `THROW`/`RAISERROR`.
    - `Sql/SqlOptionsShape.cs` reads the `SqlOptions` argument: whether `Writes` is absent, opaque or spelled out (collection expression or `HashSet` initializer of constant `TableName`s), and whether users are named.
    - `Sql/ReservedNames.cs` mirrors `ReservedSqlNames.IsReserved`. The analyzer suite pins the parity.
    - `Entities/EntityTables.cs` indexes mapped `Entity<>` classes by their (inherited) `[Table]`, from the compilation and every referenced assembly that is or references `Tellma.Core.Abstractions`. It records child-collection tables under their root, and `[BumpsUserVersionTag]`. A type parameter resolves through its constraints.
  - `IsExternalInit.cs` is a polyfill for records on netstandard2.0. `README.md` covers the rules table, what TELLMA0003 checks, what the rules cannot see, and the layout.
- **Packaging.**
  - `Tellma.Core.Abstractions.csproj` gains a build-order `ProjectReference` to the analyzer (`ReferenceOutputAssembly=false`, `PrivateAssets=all`). It also gains two `None Pack=true` items placing `Tellma.Core.Analyzers.dll` and `Microsoft.SqlServer.TransactSql.ScriptDom.dll` under `analyzers/dotnet/cs`. Its description and README say so.
  - The root `Directory.Build.targets` gains `TellmaAddPlatformAnalyzers`, which runs after `ResolveAssemblyReferences`. When `@(ReferencePath)` holds `Tellma.Core.Abstractions` with `ReferenceSourceTarget == 'ProjectReference'`, directly or transitively (or the project is Abstractions itself), the target adds both DLLs from the analyzer's `bin/$(Configuration)/netstandard2.0/` as `Analyzer` items. A missing DLL is a build error outside design-time builds. Package consumers get the analyzer from the nupkg instead, because their reference does not come from a project.
  - `Directory.Packages.props` pins Analyzer.Testing 1.1.4, CSharp.Workspaces 5.0.0 and ScriptDom 170.191.0. `Tellma.slnx` gains both new projects.
- **Tests.**
  - `test/core/Tellma.Core.Analyzers.Tests` (new; 92 tests) uses Microsoft.CodeAnalysis.Testing with net10.0 reference assemblies resolved from the running host, plus `Tellma.Core.Abstractions` and `Queryex`. This works offline.
    - There is one file per rule: positive and negative cases for each condition. TELLMA0003 has about 50 cases, covering every hole kind, every refused statement, each write shape and the span mapping.
    - `NamePinTests` pins every `KnownNames` entry to the real type, pins the reserved-name parity, and pins the runtime assembly name.
    - `Infrastructure/PlatformStubs.cs` stubs the 0015 pipeline types that have not shipped yet: `EntityService<,>`, `EntityService<>`, their extensions, `IEntityValidator<>` and `IPersistEffect<>`. These go when PC-062 ships the real types. It also stubs `TellmaDbContext`, because test compilations reference only Abstractions and Queryex. `NamePinTests` holds that stub to the real type's name.
  - `test/core/assets/Tellma.Core.Analyzers.Probe` (new) is a project that references only `Tellma.Core` and holds one violation of each rule. Its build must fail with exactly TELLMA0001–0006, which proves the in-repo flow reaches a transitive project-reference consumer. `PipelineStubs.cs` stands in for the pipeline contract until PC-062.
    - The probe is left out of the slnx so the solution build stays clean. `SolutionCoverageTests.DeliberatelyExcluded` lists it next to the package-flow host, with the reason.
- **CI** (`.github/workflows/ci.yml`).
  - **build-test** (both OSes): an "Analyzer probe" step expects the probe build to fail and greps for each `error TELLMA000n:`.
  - **design-e2e**: after the pack, `unzip -l` asserts both DLLs are under `analyzers/dotnet/cs` in the Abstractions nupkg. After the package host builds, `-getItem:Analyzer` asserts exactly one `Tellma.Core.Analyzers.dll`, loaded from the package cache path. Queryex was already packed there.
- **Docs.** CONTRIBUTING.md documents the probe command. ARCHITECTURE.md's two analyzer passages (tier-2 SQL and the validation surface) now describe what is built: the `SqlIdentifier` holes with a bare `nameof` refused, the table-valued parameter holes, the ScriptDom checks, writes required for every permanent table, and the check of a spelled-out set.
- **Suppressions.** `Tellma.Core.Tests` and `Tellma.Core.IntegrationTests` add `TELLMA0003;TELLMA0006` to `NoWarn`, with a comment.
  - Before suppression there were 68 TELLMA0003 and 106 TELLMA0006 findings. All are true positives in test code that drives the data layer directly: statements held in fields or built to provoke run-time refusals, and fixture tables written by test classes that own no stack.
  - Every `src` project, and every other test project, builds clean under all six rules.

### Deviations

1. **A bare `nameof` hole is refused (TELLMA0003).** This follows the PC-027 ruling rather than the spec 0012 §12.3 text. `IDataBatch.Sql` binds a `nameof` string as a parameter, so the analyzer demands `{new SqlIdentifier(nameof(...))}`. ARCHITECTURE.md was updated.
2. **TELLMA0003 refuses more than §12.3 lists.** Each item closes a way around the executor's run-time contract:
   - more than one batch (`GO`);
   - a hole inside a string literal, a comment or a quoted name;
   - `EXECUTE AS`;
   - `BEGIN`/`COMMIT`/`ROLLBACK`/`SAVE TRANSACTION`;
   - `SET XACT_ABORT` and `SET IMPLICIT_TRANSACTIONS`;
   - a reserved name assigned (not only declared);
   - an assigned value hole;
   - `RAISERROR` above severity 10, or at a non-constant severity (D-056);
   - `IDataBatch.Sql` taken as a delegate.
   - It also counts `TRUNCATE`, `SELECT INTO` and `OUTPUT INTO` as writes, checks a spelled-out `Writes` set against the text, and requires `UserIds`/`ForCaller` for a write into a `[BumpsUserVersionTag]` entity's table.
3. **TELLMA0003 is lenient where it cannot be sure.**
   - DML into table variables, `#temp` and batch tables needs no `Writes`.
   - An identifier hole with a non-constant name, an opaque `Writes` set, and a non-constant `THROW` number are left to run time.
   - The legacy `RAISERROR n 'msg'` form does not parse in ScriptDom 170, so it surfaces as a parse error rather than a dedicated message.
4. **TELLMA0002 also covers `Find`/`FindAsync` and raw EF SQL** through `Database.SqlQuery*`/`ExecuteSql*`. Both reach the tenant context around `IDataBatch`.
5. **TELLMA0004 lets a derived type call an action on `this`/`base`.** An override chain is the declaring type's own code path, not a caller going around the invoker.
6. **TELLMA0006 treats every mapped entity table as stack-owned.** Stack registration happens at composition, which the analyzer cannot see. So system tables such as `Job`'s count too, and writing them from outside `Tellma.Core` needs their owner. A companion is generic over its entity, so it passes. A generic leaf resolves through its constraints. See decision 1 below.
7. **The in-repo flow is a root target, not `OutputItemType="Analyzer"` project references.** `OutputItemType` does not flow to transitive references and does not bring ScriptDom along, so every consumer would need its own two references. The target attaches both DLLs to every project that reaches Abstractions through project references.
8. **`Tellma.Core.Tests` and `Tellma.Core.IntegrationTests` suppress TELLMA0003 and TELLMA0006.** See "Suppressions" above. "Every platform project builds clean" holds for the shipped code and the other suites.
9. **The 0015 pipeline types are stubbed** in the analyzer suite and the probe, because their contract has not shipped. The names they take are the ones `KnownNames` pins. They are deleted at PC-062, where `NamePinTests` gains the pipeline rows.
10. **CI gains a probe step in build-test,** in addition to the design-e2e package checks. It proves on both OSes that the six rules fire as errors in a consumer build.

### Open risks

- **Transitive NuGet reach.** A package that depends on `Tellma.Core.Abstractions` gets `exclude="Build,Analyzers"` in its nuspec dependency by NuGet's default, so its consumers do not run the rules unless they reference Abstractions directly. No platform package does that today; the EF Core packages do not depend on Abstractions. Packs and distributions should reference Abstractions directly, or the rule should be stated in the packaging docs.
- **TELLMA0006 strictness** (deviation 6) may need an escape hatch once system services outside `Tellma.Core` exist. Today no `src` project trips it.
- **ScriptDom parse coverage.** Valid SQL Server 2025 syntax that ScriptDom 170 rejects becomes a hard error with no suppression short of `#pragma`. The parser was pinned at 170.191.0 for that reason.
- **Analyzer load cost.** `EntityTables.Build` scans the referenced assemblies' types once per compilation, lazily, and only when a `Save`/`Update`/`Delete` or raw statement is seen. The full-solution build showed no measurable slowdown, but it is not benchmarked.
- **Not built:** ARCHITECTURE.md line 779 says "A Roslyn analyzer bans navigations without explicit FK declarations". No checkpoint of this run builds that rule, and it was left untouched. See decision 2 below.

### What to examine hardest

- `DataBatchAnalyzer.CheckWrites` and `SqlInspector`'s target resolution: aliases, CTEs, derived tables, `OUTPUT INTO`, and an unaliased schema-qualified table referenced by its base name. A wrong resolution is either a false error or a silently missed write.
- `SqlText.LocationOf`'s mapping from parser offsets to source spans, across escapes (`{{`), verbatim and raw strings, and multi-line literals.
- `EntityTables`: which assemblies are scanned, `[Table]` inheritance, child-collection ownership, and `TableOf` over constrained type parameters.
- The `TellmaAddPlatformAnalyzers` condition. `ReferenceSourceTarget` is used because `NuGetPackageId` is set on transitive project references too. Check also the design-time build skip, and that the analyzer project itself is excluded.
- Whether deviations 2, 4 and 6 are rulings the orchestrator wants, rather than obvious corrections.

### Decisions for the orchestrator

1. Accept TELLMA0006's strict reading (every mapped table is stack-owned, `Job` included), or name the tables that are exempt.
2. ARCHITECTURE.md line 779 promises an FK-navigation analyzer that no checkpoint builds. Either schedule it or drop the line.
3. Transitive NuGet consumers do not get the analyzers. Either require a direct Abstractions reference in packs and distributions, or accept the gap.
