# PC-040: Analyzers TELLMA0001–0006 and their packaging

## Implementer notes

### What was built, and where

- **`src/core/Tellma.Core.Analyzers`** (new; netstandard2.0, `EnforceExtendedAnalyzerRules`, Microsoft.CodeAnalysis.CSharp 5.0.0 private, ScriptDom 170.191.0 copied to output; not packable).
  - `TellmaDiagnostics.cs` holds the six descriptors. Every one is an Error, category `Tellma`, with a message built per finding.
  - `KnownNames.cs` lists every namespace, metadata name and assembly name the rules match. `SymbolExtensions.cs` holds the shared name tests. Nothing matches by symbol identity, so the assembly references no platform assembly.
  - `OrdinalBindingAnalyzer` (TELLMA0001). `new SqlDataRecord`, `SqlDataRecord.Set*` and `GetOrdinal` outside a type, or an enclosing type, marked `[TableTypeBinder]`.

  - `NestedPipelineAnalyzer` (TELLMA0005). The seven `EntityService<,>` front-door methods called from a hook override (an override of a virtual declared on `EntityService<,>`), an `[EntityAction]` method, or any member of an `IEntityValidator<>`/`IPersistEffect<>` implementer. `[ApiAction]` methods may call them.
  - `DataBatchAnalyzer` (TELLMA0003 and TELLMA0006). It shares one per-compilation scope: the runtime flag and a lazy `EntityTables` index.
    - `Sql/SqlText.cs` reads the interpolated string. Each hole becomes a stand-in: a quoted name for a `SqlIdentifier` whose name is constant, `[__tellma_holeN]` for one that is not, and `@__tellma_holeN` for everything else. It keeps a segment map so that every finding maps back to the exact source characters where it can.
    - `Sql/SqlHole.cs` classifies holes: value, identifier, table-type rows, alignment/format, bare `nameof`.

      - `EXEC` against the allow-list;
      - variable declarations and assignments;
      - `THROW`/`RAISERROR`.
    - `Sql/SqlOptionsShape.cs` reads the `SqlOptions` argument: whether `Writes` is absent, opaque or spelled out (collection expression or `HashSet` initializer of constant `TableName`s), and whether users are named.

### Deviations

1. **A bare `nameof` hole is refused (TELLMA0003).** This follows the PC-027 ruling rather than the spec 0012 §12.3 text. `IDataBatch.Sql` binds a `nameof` string as a parameter, so the analyzer demands `{new SqlIdentifier(nameof(...))}`. ARCHITECTURE.md was updated.
2. **TELLMA0003 refuses more than §12.3 lists.** Each item closes a way around the executor's run-time contract:
   - more than one batch (`GO`);
   - a hole inside a string literal, a comment or a quoted name;
   - `EXECUTE AS`;
   - `BEGIN`/`COMMIT`/`ROLLBACK`/`SAVE TRANSACTION`;
   - `SET XACT_ABORT` and `SET IMPLICIT_TRANSACTIONS`;
   - a reserved name assigned (not only declared);
   - an assigned value hole;
   - `RAISERROR` above severity 10, or at a non-constant severity (D-056);
   - `IDataBatch.Sql` taken as a delegate.
   - It also counts `TRUNCATE`, `SELECT INTO` and `OUTPUT INTO` as writes, checks a spelled-out `Writes` set against the text, and requires `UserIds`/`ForCaller` for a write into a `[BumpsUserVersionTag]` entity's table.
3. **TELLMA0003 is lenient where it cannot be sure.**
   - DML into table variables, `#temp` and batch tables needs no `Writes`.
   - An identifier hole with a non-constant name, an opaque `Writes` set, and a non-constant `THROW` number are left to run time.
   - The legacy `RAISERROR n 'msg'` form does not parse in ScriptDom 170, so it surfaces as a parse error rather than a dedicated message.
4. **TELLMA0002 also covers `Find`/`FindAsync` and raw EF SQL** through `Database.SqlQuery*`/`ExecuteSql*`. Both reach the tenant context around `IDataBatch`.
5. **TELLMA0004 lets a derived type call an action on `this`/`base`.** An override chain is the declaring type's own code path, not a caller going around the invoker.
6. **TELLMA0006 treats every mapped entity table as stack-owned.** Stack registration happens at composition, which the analyzer cannot see. So system tables such as `Job`'s count too, and writing them from outside `Tellma.Core` needs their owner. A companion is generic over its entity, so it passes. A generic leaf resolves through its constraints. See decision 1 below.
7. **The in-repo flow is a root target, not `OutputItemType="Analyzer"` project references.** `OutputItemType` does not flow to transitive references and does not bring ScriptDom along, so every consumer would need its own two references. The target attaches both DLLs to every project that reaches Abstractions through project references.
8. **`Tellma.Core.Tests` and `Tellma.Core.IntegrationTests` suppress TELLMA0003 and TELLMA0006.** See "Suppressions" above. "Every platform project builds clean" holds for the shipped code and the other suites.
9. **The 0015 pipeline types are stubbed** in the analyzer suite and the probe, because their contract has not shipped. The names they take are the ones `KnownNames` pins. They are deleted at PC-062, where `NamePinTests` gains the pipeline rows.
10. **CI gains a probe step in build-test,** in addition to the design-e2e package checks. It proves on both OSes that the six rules fire as errors in a consumer build.

### Open risks

- **Transitive NuGet reach.** A package that depends on `Tellma.Core.Abstractions` gets `exclude="Build,Analyzers"` in its nuspec dependency by NuGet's default, so its consumers do not run the rules unless they reference Abstractions directly. No platform package does that today; the EF Core packages do not depend on Abstractions. Packs and distributions should reference Abstractions directly, or the rule should be stated in the packaging docs.
- **TELLMA0006 strictness** (deviation 6) may need an escape hatch once system services outside `Tellma.Core` exist. Today no `src` project trips it.
- **ScriptDom parse coverage.** Valid SQL Server 2025 syntax that ScriptDom 170 rejects becomes a hard error with no suppression short of `#pragma`. The parser was pinned at 170.191.0 for that reason.
- **Analyzer load cost.** `EntityTables.Build` scans the referenced assemblies' types once per compilation, lazily, and only when a `Save`/`Update`/`Delete` or raw statement is seen. The full-solution build showed no measurable slowdown, but it is not benchmarked.
- **Not built:** ARCHITECTURE.md line 779 says "A Roslyn analyzer bans navigations without explicit FK declarations". No checkpoint of this run builds that rule, and it was left untouched. See decision 2 below.

### What to examine hardest

- `DataBatchAnalyzer.CheckWrites` and `SqlInspector`'s target resolution: aliases, CTEs, derived tables, `OUTPUT INTO`, and an unaliased schema-qualified table referenced by its base name. A wrong resolution is either a false error or a silently missed write.
- `SqlText.LocationOf`'s mapping from parser offsets to source spans, across escapes (`{{`), verbatim and raw strings, and multi-line literals.
- `EntityTables`: which assemblies are scanned, `[Table]` inheritance, child-collection ownership, and `TableOf` over constrained type parameters.
- The `TellmaAddPlatformAnalyzers` condition. `ReferenceSourceTarget` is used because `NuGetPackageId` is set on transitive project references too. Check also the design-time build skip, and that the analyzer project itself is excluded.
- Whether deviations 2, 4 and 6 are rulings the orchestrator wants, rather than obvious corrections.

### Decisions for the orchestrator

1. Accept TELLMA0006's strict reading (every mapped table is stack-owned, `Job` included), or name the tables that are exempt.
2. ARCHITECTURE.md line 779 promises an FK-navigation analyzer that no checkpoint builds. Either schedule it or drop the line.
3. Transitive NuGet consumers do not get the analyzers. Either require a direct Abstractions reference in packs and distributions, or accept the gap.

## Review 1

### Findings

Verification done for this review: `dotnet build test/core/Tellma.Core.Analyzers.Tests` printed "Build succeeded", 0 warnings. The analyzer suite passed 92/92. The probe failed with exactly TELLMA0001–0006. `dotnet format` on the analyzer suite's closure is clean. Every "confirmed" below comes from a scratch library under `.tmp/pc040-r1-scratch` (ignored by git) that references `Tellma.Core`, so the root target loads the analyzers into it.

**R1-1 (major): transitive package consumers, the reference distribution's shape among them, run no rule.**
- Where: `src/core/Tellma.Core.Abstractions/Tellma.Core.Abstractions.csproj:21-33`. The open risk "Transitive NuGet reach" covers it.
- Scenario: NuGet writes `exclude="Build,Analyzers"` on every package dependency by default.
  - `Tellma.Core`'s nuspec depends on Abstractions that way, so a project that references only the `Tellma.Core` package gets no analyzers.
  - That is exactly how `distributions/acme/src/Tellma.Distro.Acme` is wired (ProjectReference to `Tellma.Core` only). An external distribution built from the same template, with packages, gets none of TELLMA0002–0006. Those are the rules written for distribution code.
  - Spec 0015 §13.3 calls TELLMA0004 and TELLMA0006 its compile-time bypass-resistance layer, and TELLMA0004 has no run-time backstop (0015 §11.3).
  - Nothing in CI would notice. The design-e2e host references Abstractions directly.
- Fix:
  - Add `buildTransitive/Tellma.Core.Abstractions.targets` to the Abstractions pack. buildTransitive flows through the default exclude.
  - The targets adds `$(MSBuildThisFileDirectory)../analyzers/dotnet/cs/{Tellma.Core.Analyzers,Microsoft.SqlServer.TransactSql.ScriptDom}.dll` as `Analyzer` items, unless an `Analyzer` item with that file name is already present (a direct consumer gets them from `analyzers/`).
  - Extend design-e2e with a consumer that references a package which depends on Abstractions (Tellma.Core, or a tiny packed shim) and assert exactly one `Tellma.Core.Analyzers.dll`.
  - See ruling 3 below.

**R1-2 (major): generated code is exempt from every rule, which bypasses TELLMA0004 and TELLMA0006 silently.**
- Where: `ConfigureGeneratedCodeAnalysis(GeneratedCodeAnalysisFlags.None)` at:
  - `OrdinalBindingAnalyzer.cs:27`
  - `TenantContextAnalyzer.cs:32`
  - `ActionCallAnalyzer.cs:32`
  - `NestedPipelineAnalyzer.cs:44`
  - `DataBatchAnalyzer.cs:54`
- Scenario:
  - Any file named `*.g.cs`, `*.designer.cs` or `*.generated.cs`, or carrying an `// <auto-generated>` header, is skipped. So is any source-generator output.
  - Confirmed: a scratch file whose first line is `// <auto-generated/>` holds `batch.Save<Job>([])` and a `MERGE`, and builds with no TELLMA diagnostic.
  - Scaffolders, T4 templates, OpenAPI/gRPC/MCP client generators, or a future Tellma generator would call actions directly or write stack tables without anyone choosing to suppress a rule.
  - For TELLMA0004 the analyzer is the only gate (0015 §11.3).
- Fix:
  - Use `GeneratedCodeAnalysisFlags.Analyze | GeneratedCodeAnalysisFlags.ReportDiagnostics` in all five analyzers. The repo's generated code (EF migrations and designers, LoggerMessage, Regex and STJ generators) calls none of the matched APIs.
  - Re-confirm the solution build stays clean.
  - Add one test per analyzer with an `// <auto-generated/>` source.

**R1-3 (major): the touched integration suites were not run (PLAN §7.1 item 4).**
- Where: the commit message's "Tests:" list.
- Scenario: the commit changes `Directory.Packages.props`, `Directory.Build.targets` and `Tellma.Core.Abstractions`. By §7.1 item 4, that makes every integration suite touched:
  - `Tellma.Identity.IntegrationTests`
  - `Tellma.Core.EntityFrameworkCore.IntegrationTests`
  - `Tellma.Core.Queryex.IntegrationTests`
  - `Tellma.Core.IntegrationTests`
  - the acme distribution suite under `distributions/acme/test`
  - the connector suites under `test/connector/*`

  Only `Tellma.Core.IntegrationTests` was run. The run-time risk is low, since the change adds only compile-time items, but the gate is explicit and reviewers are told to check the list.
- Fix: run each suite with `--filter "Category=Integration&Category!=Nightly&Live!=true"`, one at a time, and list them in the commit message.

**R1-4 (minor): a write through a multi-table CTE or derived table escapes TELLMA0006 and the listed-writes check once any writes are declared.**
- Where: `DataBatchAnalyzer.cs:413-441` and `:470-477`.
  - `Unresolved` targets are reported only when `Writes` is absent.
  - `Unresolved` targets are never reported for TELLMA0006.
- Scenario (confirmed): `WITH c AS (SELECT j.[State] FROM [core].[Jobs] AS j JOIN [dist].[Ledger] AS l ON l.[Id] = j.[Id]) UPDATE c SET [State] = N'x';` with `Writes = { dist.Ledger }` gives no diagnostic.
  - SQL Server allows an UPDATE through a join CTE when the assigned columns come from one base table, so this writes `core.Jobs`.
  - The run-time authority check (0012 §5.2) reads declared writes only, so it does not catch it either.
- Fix: when a write target is `Unresolved`, report TELLMA0003 whatever the `Writes` shape, with a message such as "write the base table directly; a write through a multi-table expression cannot be checked".

**R1-5 (minor): a schema-qualified identifier hole of unknown name is taken for a permanent table named after the stand-in.**
- Where: `Sql/SqlInspector.cs:391-393`. `UnknownHole` requires `SchemaIdentifier is null`.
- Scenario (confirmed): `UPDATE [dist].{table} SET [A] = 0;` with a listed `Writes = { dist.Ledger }` reports "The text writes [dist].[__tellma_hole0] (UPDATE), which its SqlOptions.Writes does not list".
  - `{schema}.{table}` with two unknown holes does the same.
  - The runtime accepts both forms (each hole is bracket-quoted on its own). The lenient rule the README states for unknown identifier holes says this should pass.
- Fix: classify a target as `UnknownHole` when any part of the name (`SchemaIdentifier` or `BaseIdentifier`) is a stand-in.

**R1-6 (minor): any list of reference-type elements passes as a table-valued-parameter hole.**
- Where: `Sql/SqlHole.cs:214-218`.
- Scenario (confirmed): `WHERE [Code] IN (SELECT [Id] FROM {codes})` with `List<string> codes` builds clean.
  - At run time `StatementDraft.TryTable` dispatches to `Tvp<string>`, which refuses it.
  - Spec 0012 §12.3 refuses a hole that is "neither a SqlIdentifier, a nameof, a Tvp result nor a value". §5.2 limits row holes to a list of a `[TableType]` row type.
  - `IN ({list})` over a list of strings or objects is one of the most natural mistakes in raw SQL.
- Fix: classify as `Table` only when the element type carries `[TableType]` (`Tellma.Core.Abstractions.Entities`, inherited) or derives from `Entity<>`. Otherwise mark it `Unsupported`, with a message pointing at `IdList`/`StringList` rows.

**R1-7 (minor): DDL and BULK INSERT on permanent tables pass with no declared writes.**
- Where: `Sql/SqlInspector.cs`. Only `TRUNCATE`, `SELECT INTO` and `OUTPUT INTO` are added to the DML targets.
- Scenario (confirmed): each of these builds clean with `SqlOptions.None`, and none raises TELLMA0006 on `core.Jobs`:
  - `DROP TABLE [core].[Jobs];`
  - `ALTER TABLE [core].[Jobs] DROP COLUMN [State];`
  - `BULK INSERT [core].[Jobs] FROM 'x.csv';`
  - `USE [master]; SELECT 1;`

  `BULK INSERT` is a plain write. The DDL forms change a stack-owned table outside every rule, and `USE` moves the rest of the batch to another database. The implementation already goes beyond §12.3 for `TRUNCATE`, and the same reasoning covers these.
- Fix: refuse, as `SqlRefusal`s:
  - `CREATE`/`ALTER`/`DROP` of any object other than a `#temp` table;
  - `BULK INSERT`/`INSERT BULK`;
  - `USE`;
  - `GRANT`/`DENY`/`REVOKE`;
  - `DBCC`.

  Alternatively, count the DDL forms as writes of their table. State it under Deviations.

**R1-8 (minor): a companion whose entity parameter is constrained to a mapped class is refused, though the message names companions as owners.**
- Where: `DataBatchAnalyzer.cs:164-195`. `OwnedEntities` knows only `EntityService<,>`, `IEntityValidator<>` and `IPersistEffect<>`.
- Scenario (confirmed): `class ProbeCompanion<TEntity> where TEntity : ProbeEntity { batch.Save<TEntity>([]) }` reports TELLMA0006, and its message says "written by its own service, validators, effects and companions".
  - Deviation 6 ("a companion is generic over its entity, so it passes") holds only while the constraint carries no `[Table]`.
  - A `UserCompanion<TUser> where TUser : User` (0011 §2.1 / 0015 §11.3 shape) would fail the build.
- Fix: treat as owner a type whose own type parameter is the written type argument (the companion is closed over the entity at registration, 0015 §11.3). Add a positive test with a constrained companion.

**R1-9 (minor): the pipeline stubs will keep shadowing the real contract after PC-062, with nothing failing.**
- Where: `test/core/Tellma.Core.Analyzers.Tests/Infrastructure/PlatformStubs.cs:33-83` and `test/core/assets/Tellma.Core.Analyzers.Probe/PipelineStubs.cs`.
- Scenario: once `Tellma.Core.Abstractions.Crud.EntityService`2`, `IEntityValidator`1` and so on ship, source and metadata declare the same names. The source type wins with CS0436, a warning.
  - The harness checks compiler errors only by default, so the suite keeps passing against the stubs. Their shapes are not the contract's (`SaveAsync(IReadOnlyList<TEntity>)`, with no options).
  - The probe gets CS0436 as an extra error, which the CI step ignores (R1-10).
  - Deleting the stubs and adding `NamePinTests` rows then depends on memory.
- Fix: add a tripwire test that fails once the contract assembly defines `Tellma.Core.Abstractions.Crud.EntityService`2` (`typeof(SqlOptions).Assembly.GetType(...) is not null`), with a message saying to delete the stubs and pin the names. The orchestrator should add the matching carry to PC-062.

**R1-10 (minor): the CI probe step does not check for "exactly" the six errors.**
- Where: `.github/workflows/ci.yml:49-55`.
- Scenario:
  - The step passes as long as each `error TELLMA000n:` appears, whatever else fails: CS0436 from R1-9, a CS0246 after a contract rename that still leaves six findings, or an MSB/NU error after the analyzers ran.
  - The commit message claims "fails with exactly TELLMA0001–0006", but only this machine-local run checked that.
- Fix: also fail when the log holds an `error` whose code is not one of the six (for example `grep -E ": error [A-Z]+[0-9]+:" | grep -vE ": error TELLMA000[1-6]:"`).

**R1-11 (minor, carry): the loader's raw statement is not covered.**
- Where: `DataBatchAnalyzer.cs:115-121`. `IsRawStatement` matches `IDataBatch.Sql` only.
- Scenario: spec 0015 §7.2's `IContextLoader.Sql(FormattableString, SqlOptions?)` says "the analyzer refuses DML here", and adds "no `@qx`, `@tb`, `@tm` names". It is not in this checkpoint's sections, and the type does not exist yet. When it ships, its raw text will pass unchecked.
- Fix: either match `Sql(FormattableString, SqlOptions?)` on the loader interface by name now, refusing any write target, or record the carry against the checkpoint that ships `IContextLoader` (0015's validation checkpoint).
