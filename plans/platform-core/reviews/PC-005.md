# PC-005: Column collations on class-derived standalone table types

## Implementer notes

### What was built, and where

- **`TableTypeBuilder.UseCollation(string column, string collation)`**
  (`src/core/Tellma.Core.EntityFrameworkCore/TableTypes/TableTypeBuilder.cs`), public virtual,
  per spec 0010 §G.1. Calls are recorded in order and applied in `Build(name, schema)` (the
  registration step, after the class columns and the build action have run), so:
  - the call's position against `Column(…)` does not matter;
  - the last call for a column wins, over earlier calls and over `Column(…, collation)`;
  - names match case-insensitively (`OrdinalIgnoreCase`, as the duplicate-column and key checks)
    and the column keeps its declared spelling;
  - a name that matches no column throws `InvalidOperationException` from `HasTableType(…)`
    itself, naming the type (`[schema].[name]`), the column, the collation and the type's columns.
  - Guards: `ThrowIfNullOrEmpty(column)`, `ThrowIfNullOrWhiteSpace(collation)` (a blank collation
    would render `COLLATE ` and break the `CREATE TYPE`).
  - The collation is written onto the column's `StandaloneColumnConfiguration.Collation`, which
    already existed. No new member was added to any serialized record, so the registration
    annotation and the canonical definition JSON of a type without a collation are byte-identical
    to before.
- **The character-column check** (`TableTypeFinalizingConvention.ResolveStandaloneColumn`): a
  standalone column with a collation (from either route) must resolve to `char`, `varchar`, `nchar`
  or `nvarchar` (base name before `(`, case-insensitive, `FrozenSet`). Anything else, `json`
  included, fails model finalization with an `InvalidOperationException` naming the column, the
  type, the collation and the store type. It runs on the resolved store type *before* the JSON
  wire-form rewrite, so a `json` column with a collation is refused instead of silently taking
  `Latin1_General_100_BIN2_UTF8`. Table-derived types are untouched (spec 0010 Part G).
- **Docs.** The library README's standalone paragraph; the XML docs on `UseCollation` and on the
  `buildAction` parameters of `HasTableType<T>`/`HasTableType(Type, …)`. ARCHITECTURE.md already
  names `UseCollation` where it describes standalone table types (Data Layer → UDTT generation),
  so it needed no change.
- **Migrations host.** A class-derived `SubjectEntry` (`[TableType(Name = "SubjectsList")]`,
  `[Key][MaxLength(255)] Subject`, `[MaxLength(200)] DisplayName`), registered in `dbo` with
  `UseCollation(nameof(SubjectEntry.Subject), SubjectCollation)` and `HasGrants("public")`;
  `MigrationsHostContext.SubjectCollation = "Latin1_General_100_BIN2"`. Scaffolded with dotnet-ef
  10.0.11 as a second migration, `20261108142105_AddSubjectsList`, not by regenerating `Initial`.
  The scaffold is itself the hash-stability evidence: it holds exactly one `CreateTableType`
  (`SubjectsList_48f699b9`) and the cleanup, and its keep-list repeats the eight physical names of
  `Initial` unchanged. The snapshot diff is the new `HasTableTypeDefinition` plus
  `ProductVersion` 10.0.9 → 10.0.11.
- **The integration fixture** (D-017): verified, not changed. `SqlServerFixture.CreateDatabaseAsync`
  runs `CREATE DATABASE [<name>] COLLATE {DatabaseCollations.Platform}`, which is spec 0011 §6.7's
  SQL Server statement.

### Tests

- Unit, `Tellma.Core.EntityFrameworkCore.Tests/Standalone/StandaloneColumnCollationTests.cs` (new):
  class column keeps store type/facets/nullability; the collation reaches the `CREATE TYPE` SQL;
  `Column(…)` column with the call before/after (theory); a `Column(…)` added to a class-derived
  type; last call wins; wins over `Column(…, collation)` before/after (theory); case-insensitive
  match keeping the declared spelling; unknown column throws at registration for both routes;
  argument guards; `char`/`varchar`/`nchar`/`nvarchar` (with and without facets, any case) pass;
  `int`, `datetimeoffset`, `json` (ad hoc and class-derived) and a class `int` column fail
  finalization naming type, column and store type; `json` without a collation still takes the wire
  form; adding a collation emits one create + the cleanup (keep-list only the new version) and no
  drop; changing/removing it versions too; **canonical JSON golden** for `StringList` and a
  `DocumentStatesList` shape without a collation, whose physical names equal those in the
  committed `Initial` (`StringList_7e92fa5c`, `DocumentStatesList_93a0c43e`); the registration
  annotation without a collation has no collation member and `UseCollation` changes only the named
  column.
- Design, `SnapshotRoundTripTests`: the round-trip model gains a class-derived `CollatedSubject`
  with `UseCollation`; asserts the snapshot writes `collation: "Latin1_General_100_BIN2"` and the
  replayed model carries it (the empty diff covers byte equality).
- Integration, `ColumnCollationTests` (new): `sys.columns.collation_name` reads

### Deviations

1. The host's migrations were extended with a scaffolded second migration rather than a
   regenerated `Initial`. "Re-scaffolded" is ambiguous; an added migration is what a real model
   change produces and proves in the committed scaffold that no existing hash moved.
2. `UseCollation` rejects a whitespace-only collation (`ThrowIfNullOrWhiteSpace`); the spec states
   no argument rule.
3. The unknown-column message also lists the type's columns and the collation, beyond the spec's
   "naming the type and the column".

### Open risks

- The character check recognises only the four canonical base names. An explicit store type
  written as an ISO synonym (`national character varying(50)`, `character varying(10)`) or
  bracketed (`[nvarchar](50)`) with a collation is refused, although SQL Server would accept it.
  EF's type mapping always yields the canonical names, so only hand-written `Column(name,
  storeType, …)` calls can hit this, and the message names the store type.
- `StringList` (`nvarchar(450)`, no collation) still meets the Msg 468 seam that D-015 records for
  Queryex string key sets against binary columns. This checkpoint supplies the mechanism only;
  spec 0012's `[Collation]` convention and the two `Subject` columns (specs 0011, 0018) are out of
  scope per Part G's DoD.

### What reviewers should examine hardest

- That `Build()` is the only path to a `StandaloneTableTypeConfiguration` from a `TableTypeBuilder`
  (both `HasTableType` overloads go through it), so no route skips the collation application or
  the unknown-name check.
- The golden JSON / physical-name pins and the scaffolded keep-list as the "no existing hash
  changes" evidence.
- The check's placement before `NormalizeJsonColumn`, and that table-derived JSON columns (which
  carry the wire collation) never reach it.

### Findings

**R1-1 (minor). The `collation` parameter docs on `Column(…)` predate this change.**
- Where:
  - `src/core/Tellma.Core.EntityFrameworkCore/TableTypes/TableTypeBuilder.cs:40` (`Column<T>`)
  - `src/core/Tellma.Core.EntityFrameworkCore/TableTypes/TableTypeBuilder.cs:77` (`Column(name, storeType, …)`)
- Both still read "The explicit collation, when one is wanted."
- Failure scenario: this commit makes that argument fail model finalization on any
  non-character store type, `json` included. Before this commit, a `json` column silently took the
  wire collation. `UseCollation` also now overrides the argument. A caller reading IntelliSense on
  `Column(…)` sees neither the new failure mode nor the override. Only `UseCollation`'s remarks
  describe them.
- Suggested fix: extend both `<param name="collation">` docs to say the following:
  - Only char, varchar, nchar and nvarchar columns take a collation; any other store type fails
    model finalization.
  - A later or earlier `UseCollation` call for the column wins.
  - Add `<see cref="UseCollation" />` to both docs.

No blocking or major findings.

### Responses

- R1-1: fixed in the "PC-005: review 1 fixes" commit (child of 6b6f48f). The `collation` parameter
  docs on both `Column<T>(…)` and `Column(name, storeType, …)` now say that only a column
  resolving to `char`, `varchar`, `nchar` or `nvarchar` takes a collation, that any other store
  type (`json` included) fails model finalization, and that a `<see cref="UseCollation" />` call
