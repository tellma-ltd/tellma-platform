# PC-F111: One vitest/vite module instance in Acme's unit run

## Implementer notes

PC-F111 has no CHECKPOINTS.md entry. It is a fix item scoped by its LEDGER row, D-378, D-385, the
brief, and PC-F110's R1-8. No spec section is in scope, and no product code changed.

### The split, read on disk before the fix

- One sass version too many. `@angular/build` 22.0.5 pins `sass: 1.99.0`; ng-packagr 22.0.1 asks
  `^1.81.0` and resolved 1.101.0. Vite takes sass as an optional peer, so the graph held two vite
  7.3.5 copies, and on top of them two vitest 4.1.9, two `@vitest/browser`, two
  `@vitest/browser-playwright` and two `@vitest/mocker` copies.
- `@angular/build` has one snapshot (its peer id records only `vitest@4.1.9`), shared by the
  client and Acme importers, and it links the sass-1.99 vitest (`vitest@…7caf…`).
- The Acme importer resolved its own `vitest` and `@vitest/browser-playwright` to the sass-1.101
  copies (`vitest@…9f4f…`, `@vitest/browser-playwright@…d691…`). The client importer resolved the
  sass-1.99 ones, so the client workspace had one copy.
- So in Acme's unit run, Angular's builder ran Vitest's core from `7caf` on vite `d8b0`, and
  `@vitest/browser` (loaded through the provider, which the builder resolves from the project)
  started the browser server with `createViteServer` from `vitest@…9f4f…`, on vite `b984`. The
  browser server, its dependency optimizer and its HTTP and WebSocket handlers ran on a second
  Vite and a second `vitest/node` module instance.
- The split dates from PC-094 (the first commit with both sass versions in the lockfile) and was
  in every CI run since, green ones included, on both OSes.

### What was built

1. **`pnpm-workspace.yaml`**: a new `overrides:` block with `sass: 1.99.0`, the version
   `@angular/build` pins. The graph now holds one sass, so one copy of vite, vitest,
   `@vitest/browser*` and `@vitest/mocker`. It is an override, not a catalog entry, because no
   workspace package depends on sass, and so that the catalog hunk PC-F110 adds (`std-env`) does
   not meet a second hunk beside it.
2. **`pnpm-lock.yaml`**: regenerated by `pnpm install`: the override, sass 1.101.0 and the
   sass-1.101 snapshots of vite, vitest, `@vitest/browser`, `@vitest/browser-playwright` and
   `@vitest/mocker` removed, Acme's two importer entries moved to the sass-1.99 ones, and vite's
   peer range shown as the override.
3. **`client/tools/vitest-instances.mts`** (new): finds every pnpm workspace package whose
   `angular.json` has an `@angular/build:unit-test` target (the `packages` globs of
   `pnpm-workspace.yaml`, read line by line), and follows, by Node's own node_modules lookup from
   real paths, every route a unit run takes to vitest and to vite: `@angular/build > vitest`,
   `@angular/build > vite`, `> vitest > vite`, `> vitest > @vitest/mocker > vite`, the workspace's
   own `vitest`, and for each `@vitest/browser-*` provider the workspace resolves, its `vitest`,
   its `@vitest/browser > vitest` and `> vite`, and its `@vitest/mocker > vite`. A problem is more
   than one real folder for either package (each copy listed with its routes), a route that does
   not resolve, or `@angular/build` resolving a sass other than the exact version it pins (an
   override left behind by an Angular upgrade).
4. **`client/tools/tests/vitest-instances.spec.mts`** (new, in lint:test, so it runs in the
   client and client-windows jobs): over the installed repository, it asserts that `client` and at
   least one `distributions/` workspace are found and that each has no problem; over hand-made
   node_modules trees in a temp folder (plain folders, no links, so it runs alike on Windows and
   Linux), that the check passes one copy, fails a builder-side vitest copy and a provider-side
   vite copy naming both folders and their routes, fails a sass that differs from the pin, fails
   routes that do not resolve, leaves out a workspace with no unit-test target, and reads the
   globs (quotes, comments, CRLF, the next top-level key).
5. **Docs**: client README (lint:test line and a paragraph on the check and the override) and
   ARCHITECTURE.md's repository-layout paragraph (the override and why).

### Proof that the check fails on the old install

With `pnpm-workspace.yaml` and `pnpm-lock.yaml` put back to `d1e2b461` and a frozen install, the
spec failed on Acme alone, with two problems:

- vitest: `node_modules/.pnpm/vitest@…7caf…` (`@angular/build > vitest`) and
  `node_modules/.pnpm/vitest@…9f4f…` (`vitest; @vitest/browser-playwright > vitest;
  @vitest/browser-playwright > @vitest/browser > vitest`);
- vite: `vite@…d8b0…` (the builder's four routes and `@vitest/browser > vite`) and `vite@…b984…`
  (`@vitest/browser-playwright > @vitest/mocker > vite`).

The client workspace passed. With the fix restored, all 10 tests pass.

### Does the second instance explain the Windows hang (CI 45834807715)?

I read the acme-client (windows-latest) job log with `gh run view --job 139960721409 --log`. The
install was frozen from the same lockfile (`Lockfile is up to date`), so that run had the split
above. The Angular test build finished at 14:06:24.68, Vitest printed `RUN v4.1.9` at 14:06:25.21
and the browser server's optimizer printed `Failed to resolve dependency: @microsoft/signalr,
present in client 'optimizeDeps.include'` at 14:06:25.29. Nothing followed until the cancel at
14:46:18.

My answer: plausible as a condition, not shown as the cause, and weak on its own.

- For: the log stops in the browser server's start, and that server ran on the second Vite and
  the second `vitest/node` (the optimizer warning came from that copy). Acme was the one suite with
  the split, and the one that hung.
- Against: the split is deterministic and has been in every Acme run since PC-094, on Linux and
  Windows, and green in all of them (PC-F110 ran 30 cold local runs on it without a hang). A
  duplicated module alone does not hang one run in many; it would need a race that the duplication
  feeds. I found no state the two copies share that the core waits on: the core talks to the
  browser server only over its RPC, and `@vitest/runner` and the other non-peer packages are one
  copy for both.
- One mechanism I ruled out: a mid-run dependency re-optimization and page reload, a known
  browser-mode hang. Angular's builder sets `optimizeDeps.noDiscovery: true`, so the optimizer
  never re-runs during a run.
- The signalr warning is in every green run too, and with `noDiscovery` it does not start a
  re-optimization. It is not the hang.

So the fix removes one variable from the place the hang happened, at no cost, and the next hang
(if any) reports through PC-F110's watchdog on a single-copy run. The flaky row should stay open.

### Deviations

None from a spec; no spec covers it.

- The brief offered "pin sass or the peer set through the pnpm catalog or overrides". I used an
  override (not a catalog entry), for the reasons in item 1.
- Beyond the brief, the check also fails when `@angular/build` resolves a sass other than the one
  it pins. Without it, the override would silently hold a newer `@angular/build` on an older sass
  after an upgrade.
- ng-packagr now resolves sass 1.99.0 instead of 1.101.0, inside its `^1.81.0` range. No file in
  `client/projects` or `distributions` is SCSS, so neither builder runs sass today.

### Files PC-F110 also touches

- `pnpm-workspace.yaml`: PC-F110 adds `std-env` to the catalog; I add an `overrides:` block after
  `catalogMode`. Different hunks, so no textual conflict expected.
- `pnpm-lock.yaml`: both change it. The later lander regenerates it with `pnpm install`. After

- I did not touch ci.yml, the vitest configs, angular.json or any test script.

### Open risks

- The check covers the platform repository's workspaces only. A distribution in its own repository
  has its own lockfile and could split the same way. A `tellma-client test` (or a build-time) check
  would carry it to them; that is a product change and is left to a later item.
- The routes are the ones Angular 22.0.5 and Vitest 4.1.9 take today. A new import path (another
  package that starts a Vite server) would not be followed until it is added to the list.
- Overrides apply to transitive peers too: vite's peer range for sass reads `1.99.0` in the
  lockfile. That is intended.

### What reviewers should examine hardest

- That the routes in `unitRunInstances` are the ones the builder and the provider actually take
  (`executor.js` imports `vitest/node` and `vite` from @angular/build; `browser-provider.js`
  imports the provider through the project resolver; `@vitest/browser` calls `createViteServer`
  from `vitest/node`).
- That Node's lookup from real paths matches what Node does for these imports under pnpm (no
  `preserveSymlinks` anywhere in the unit-test targets).
- The plausibility judgment above.
