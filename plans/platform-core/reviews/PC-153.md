# PC-153: TmHub realtime connection

## Implementer notes

### What was built

The lazy entry point `@tellma/core/realtime` (`client/projects/core/tellma-core/realtime/`), its
wiring into `@tellma/core/leader`, and the test fake in `@tellma/core-testing`.

- `realtime/src/tm-hub.ts`: `TmHub` (implements `TmHubConnection`), the reconnect loop over an
  attempt seam (`TmHubConnect` → `TmHubAttempt { start, stop, refusal }`), `tmHubDelay` and
  `tmHubEvent`.
  - Schedule (after review 1, spec 0025 §8.3's table): the first start goes at once; after a drop
    or a failed start, attempt 1 goes at once too, then 2 s, 10 s, 30 s, then doubling to a 5 min
    cap; every wait but the first × (0.8 + 0.4·random). The count starts over when a connection
    that lasted 60 s closes or is stopped. Every wait is a `setTimeout`, even 0 ms.
  - `nudge()` cuts a wait short. While `TmApi.online` is false the loop reports `offline` and
    waits; an effect on `online` nudges whenever it reads true while the loop waits in `offline`
    (state-based since review 1). The leader already nudges on
    `leader.probe`; election starts the hub anyway.
  - Terminal: a refusal (negotiate 401/403/404, or a failed user check) halts the loop and calls
    `sink.refused`. `session.ended` with a known reason hands the event on, reports
    `reconnecting`, stops itself, then calls `sink.ended(reason)`. Unknown reasons are only handed
    on. A network error, 429 or 5xx is never terminal.
  - Each attempt has a 100 s deadline (no transport timeout exists in the library: a WebSocket
    that never opens would otherwise hang the loop). `stop()` is idempotent, mutes the logger,
    aborts HTTP in flight and settles within 5 s even if the library's stop hangs (it awaits
    `_startInternalPromise`). Stale callbacks are ignored by run token and attempt identity.
  - Telemetry: `tm.realtime.connected` (timing from attempt start, `attempt` '1' | '2-4' | '5+'),
    `tm.realtime.disconnected { reason: offline | error | closed | ended }`,
    `tm.realtime.refused { status: 401 | 403 | 404 | user-check }`.
- `realtime/src/tm-hub-signalr.ts`:
  - `TmHubHttpClient extends DefaultHttpClient`: `TmSession.check()` before every send (not
    `same` → refusal `'user'`, nothing sent); a per-request abort signal chained to the library's
    (the library sends the negotiate without one, so this is the only way a stop can end a hung
    negotiate); `close()` aborts all in flight and refuses later sends; records 401/403/404 only
    for `/negotiate` URLs, because `HttpConnection` wraps the `HttpError` in
    `FailedToNegotiateWithServerError` and the status is lost.
  - `TmHubLogger`: Warning and above (not None) → `TmTelemetry.error(TmHubLogError, { source:
    'tm-hub', level })`, `access_token=` masked, muted after stop. `logMessageContent` stays off.
  - `tmSignalRConnect`: `HubConnectionBuilder().withUrl(url, { httpClient, withCredentials: true
    })`, server timeout 30 s, keep-alive 15 s, default JSON protocol, the library's transports in
    its order, no `withAutomaticReconnect`; `on('event')` and `onclose`.
- `realtime/src/tm-create-hub.ts`: `tmCreateHub(tenantId, sink, injector)` (TSDoc `@internal`,
  which the golden shows), URL `/{t}/hub`, the session, telemetry, `TmApi.online` and `TM_NOW`
  from the injector.
- `leader/src/tm-leadership.ts`:
  - `TM_HUB_FACTORY`'s default is now `import('@tellma/core/realtime').then(m => m.tmCreateHub(…))`
    (still `| null` for a test app without realtime).
  - `#terminal` restarts the hub on the first sync stamped at or after the signal, from any
    source (the terminal refresh, a poll, another tab), once the stop has settled, unless the
    generation changed or realtime went off. Before, only the terminal refresh's own sync could
    restart it, so a terminal refresh that failed (offline) left the hub stopped forever while
    polls succeeded.
  - `tmAccessEnded(event)`.
- `leader/src/tm-leader-election.ts`: a follower that receives a relayed `session.ended` with
  `access-revoked` or `tenant-unavailable` runs `refresh(t, ['tenant'], 'terminal')`, whether or
  not its build lists the event. `session-terminated` reaches followers as the leader's
  `session.signed-out` (unchanged path, spec 0024 §8.5).
- `tellma-core-testing/src/tm-fake-hub.ts`: `TmFakeHub` (registry; `factory`, `connections`) and
  `TmFakeHubConnection` (counts starts/stops/nudges; `connect`, `drop`, `emit`, `refuse`, `end`).
  `provideTellmaStateTesting()` provides it behind `ɵTM_HUB_FACTORY`. The leader rig now uses it
  instead of its own local fake.
- Package and gates: `@microsoft/signalr` 10.0.11 in the catalog, `client/package.json` and
  `tellma-core/package.json` (and `allowedNonPeerDependencies`); budgets `./realtime` 16 (born at
  15.78, of which ~14 is the library) and `./leader` 3.9 → 4.1 (3.84 → 4.05, D-031, note in
  `budgetNotes`); `staticGraphExcludes`: `./realtime` excluded from `.`, `./shell`, `./attention`
  and `./leader`; an ESLint block that bans `@microsoft/signalr` everywhere under `projects/` but
  `tellma-core/realtime/`. READMEs (core, core-testing) and the ARCHITECTURE.md `@tellma/core` row
  updated.
- First frame: the primary `.` is unchanged at 49.89 (cap measure 49.79 of 50) on a clean build;
  the hub client adds 0 bytes to the first frame. The leader loads `./realtime` only once a tab
  leads (after first render).

### Deviations

1. A failed user check is reported to the sink as `refused(401)`. The sink type admits only
   401 | 403 | 404, and a changed or missing user is what a 401 means; the terminal refresh then
   reaches spec 0024 §8.6. Telemetry keeps it apart as `status: 'user-check'`.
2. An attempt that has not connected in 100 s is abandoned (counted as a failure) and a stop
   settles within 5 s. Not in the spec; without them a hung WebSocket or a library stop that awaits
   a hung start would stall the loop or the leader's release.
3. Restart after a terminal signal waits for any sync stamped at or after the signal, not only the
   terminal refresh's own (see above). This matches §8.5's "a sync that succeeds restarts the loop"
   more closely than the previous check.
4. `session.ended` with a reason this build does not know is handed on but does not stop the
   connection.
5. Attempt numbering (aligned with §8.3's table in review 1): the count is of drops and failed
   starts; the first start goes at once and is not counted, and attempt n after a failure waits
   0, 2 s, 10 s, 30 s, then 30 s × 2^(n−4) capped at 5 min. A refusal counts as a failed start and
   keeps the count, so the start after the terminal sync waits as the next attempt. The count
   resets when a connection that lasted ≥ 60 s closes or is stopped. `tm.realtime.connected`'s
   `attempt` reports the first start and the first retry both as '1'.
6. `./realtime` budget is 16 (measured 15.78 rounded up to the next 0.5 KB), under the spec's 18.
7. `TmFakeHub` is a registry plus `TmFakeHubConnection` objects rather than one class, so a test
   can see every connection a leader opened.
8. The 4 KB `hub.event` limit stays server-side only; the client does not re-check it.

### Open risks

- The library's `HttpConnection.stop` awaits a hung start; after the 5 s grace the old connection
  object may live on until the browser fails its socket. It is muted and ignored, and closes itself
  if it ever opens (the library checks for `Disconnecting`).
- The refusal capture depends on the negotiate URL containing `/negotiate` followed by `?` or the
  end; SignalR 10's `_resolveNegotiateUrl` builds `…/negotiate?negotiateVersion=1`.
- `hub-hang.spec` on the Acme host belongs to PC-216; this checkpoint pins it at unit level
  (`tm-create-hub.spec.ts`: a hung negotiate does not delay two router navigations, and the stop
  aborts it).

### What reviewers should examine hardest

- `TmHub`'s run/attempt identity checks (`live()`), the shared `#timer` for both the wait and the
  attempt deadline, and the counter reset in `#settle` when `stop()` ends a stable connection.
- `#terminal`'s effect lifecycle in `tm-leadership.ts`: the `#signals` counter that lets only the
  latest signal's wait count (its stop may settle after a later signal's), destruction on
  `#disconnect` and `stop`, and the self-destroy inside the effect.
- `TmHubHttpClient`'s signal chaining: the library sets `onabort` on the signal we pass, and we set
  `onabort` on the library's own signal.

### Findings

**R1-1 (minor): the attempt numbering is one step behind §8.3's table (deviation 5).**

- Where: `client/projects/core/tellma-core/realtime/src/tm-hub.ts:126-132`, `:257` and `:276`.
- What the spec says: the table's heading is "Attempt after a drop or a failed start", and attempt 1
  waits 0 s. The initial start is not an attempt after anything, so the first retry after a failed
  initial start should go at once.
- What the code does: `#connect` counts the initial start as attempt 1, so the first retry is
  attempt 2 and waits 2 s ±20 %. Every later wait is one row late. For example, a connection that
  lasted under a minute and dropped waits 2 s where the table says 0 s.
- The commit records this as a deviation but gives no reason beyond the numbering itself.
- Fix, either of:
  - align with the table: count only the attempts made after a drop or failed start, so the initial
    start and the first retry both go at once, and keep the `attempt` telemetry buckets on the same
    count;
  - or keep the current numbering and record it for Ahmad as a spec 0025 §8.3 wording question,
    since a 2 s first retry is arguably kinder to a struggling server.

**R1-2 (minor): the offline wait nudges only on a false→true change the effect sees.**

- Where: `client/projects/core/tellma-core/realtime/src/tm-hub.ts:201-215`, with `#ready` at
  `:266-269`.
- What goes wrong: the effect nudges only when it sees `online` go from false to true.
  - Angular effects run with the latest value only. Suppose `online` goes false, the waiting
    `#ready` timer fires and parks the loop in `offline`, and `online` goes true again, all before
    the effect's next flush. The effect then sees true→true and never nudges.
  - This can happen in a hidden tab, where the effect's scheduler and the loop's timer share one
    throttled timer batch, and one request fails at network level while another answers.
  - In a hidden tab, the probe that sets `online` back is not running.
- Result: the loop stays in `offline` until a follower's probe nudges it. `TmLeadership.visibility()`
  does not nudge, so a single-tab user's hub stays down for the whole leadership, and degraded
  polling only papers over it.
- How likely: the window is narrow. A spec I wrote to provoke it (since deleted) did not hit it under
  vitest's faked scheduler. The code depends on an interleaving it does not rule out.
- Fix: make the effect state-based rather than edge-based, for example
  `if (online() && this.#reported === 'offline' && this.#waiting) untracked(() => this.nudge())`, and
  drop `was`.

**R1-3 (minor): `#terminal` accepts a sync stamp ahead of the clock.**

- Where: `client/projects/core/tellma-core/leader/src/tm-leadership.ts:414`.
- What goes wrong: after the device clock is set back, the stored `sync.at` can be ahead of the
  clock. `at >= requested` then holds at once, and the connection restarts without waiting for any
  sync after the signal.
- The same file's constructor (`:209-211`) and the refresher's `#sentSince` both treat such a stamp
  as proving nothing.
- Impact is bounded: the terminal refresh still runs, and the attempt counter keeps backing off. But
  §8.5's "a sync that succeeds restarts the loop" is bypassed.
- Fix: `const at = sync()?.data.at ?? -Infinity; if (at >= requested && at <= this.#now()) …`. A
  later real sync (`at` ≥ `requested`, `at` ≤ now) then restarts it.

**R1-4 (minor): `TmHub` acts on `session.ended` without checking the envelope's tenant.**

- Where: `client/projects/core/tellma-core/realtime/src/tm-hub.ts:387-400`.
- What goes wrong: §8.4 step 1 drops an event whose `tenantId` is not `t` before step 3 acts on it.
  `TmLeadership.#event` drops such an event. But `TmHub.#event` stops the connection and calls
  `sink.ended(reason)` for any tenant's `session.ended`, and the leader's `ended` does not check
  the tenant either.
- Result: a `session.ended` for tenant 18 on tenant 17's connection stops it. With
  `session-terminated`, it signs every tab out. With `access-revoked`, it runs a terminal refresh
  for the wrong tenant's reason.
- The server is meant never to send one (D-163), so this is defence in depth, against what the spec
  states.
- Fix: pass `tenantId` from `tmCreateHub` into `TmHubOptions`, and act on `session.ended` only when
  `event.tenantId === tenantId`. Still hand the event to the sink, which drops it. Add a test.

**R1-5 (minor): the `@microsoft/signalr` ban is lost in six folders, and its comment says otherwise.**

- Where: `client/eslint.config.mjs:223-246`.
- What goes wrong: flat config replaces a rule's whole setting with the last matching block. The
  later `no-restricted-imports` blocks therefore replace this ban for their files, and none of
  their lists names `@microsoft/signalr`. The affected folders:
  - `tellma-core-ui/contracts/**`, at `:251`;
  - `icon/**` and `kbd/**`, at `:284`;
  - `grid-engine/**`, at `:468`;
  - `calendar-*/**`, at `:577` and `:596`;
  - `l10n/**`, at `:621`.
- Checked: an `import { HubConnectionBuilder } from '@microsoft/signalr'` piped to
  `eslint --stdin` as `projects/core/tellma-core-ui/l10n/x.ts` reports nothing, and as
  `…/button/x.ts` it reports the ban.
- The comment's "keep their own, stricter lists" is not true for this import.
- Fix: hoist the path entry into a shared constant and add it to each of those blocks' `paths`.
  Otherwise, correct the comment to say where the ban does not reach.

**R1-6 (minor): two of the behaviours named as most delicate have no test that would fail.**

- (a) `stop()` restarting the count after a stable minute
  (`client/projects/core/tellma-core/realtime/src/tm-hub.ts:227` → `#settle` at `:355-360`) is
  untested. No spec stops a connection that has been open for 60 s: the only stable-minute case
  closes it through `handlers.closed`, and the leader specs run on the fake. Yet that path decides
  the restart delay after `ended` on a long-lived connection.
- (b) "the connection starts again only once it has closed"
  (`client/projects/core/tellma-core/leader/src/tm-leadership.ts:387-388`, `:407`) is untested.
  `TmFakeHubConnection.stop()` resolves at once, so `#terminal` could ignore `stopped` and
  `tm-leadership.spec.ts`'s "stops the connection when the server ends the user's access" would
  still pass.
- Fix:
  - a `tm-hub.spec` case: connect, advance 60 s, `stop()`, `start()`, expect the next attempt at
    0 s;
  - a leadership case whose connection's `stop()` stays pending: the sync lands first, there is no
    start, then the stop settles and the start follows. That needs a way to hold the fake's stop
    open (see R1-7).

**R1-7 (minor): `TmFakeHubConnection.end()` does not report what a real connection reports.**

- Where: `client/projects/core/tellma-core-testing/src/tm-fake-hub.ts:105-114`.
- What goes wrong: the TSDoc says "as a real connection does", but a real `TmHub` reports
  `state('reconnecting')` between the event and `ended` (tm-hub.ts:396).
  - A later checkpoint's spec that reads `hubStatus` after `end()` sees `connected` on the fake
    and `reconnecting` in the app.
  - `stop()` always resolves at once, so no consumer can test the stop-settles ordering.
- Fix:
  - call `this.sink.state('reconnecting')` before `this.sink.ended(reason)`;
  - optionally give the connection a settable `stopResult` promise, as tm-hub.spec's fake attempt
    has. That is a core-testing API golden change.

**R1-8 (minor): rewritten TSDoc keeps a spec reference (PLAN.md §7.1 item 5).**

- Where: `client/projects/core/tellma-core/leader/src/tm-leadership.ts:395`.
- What goes wrong: this commit rewrote the TSDoc on `#terminal`, and it still says
  "decides what it means (§8.5)". §7.1 item 5 allows § only in inline comments.
- Fix: drop the parenthetical, or move it into an inline `//` comment in the body.
