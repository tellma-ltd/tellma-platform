# PC-153: TmHub realtime connection

## Implementer notes

### What was built

The lazy entry point `@tellma/core/realtime` (`client/projects/core/tellma-core/realtime/`), its
wiring into `@tellma/core/leader`, and the test fake in `@tellma/core-testing`.

- `realtime/src/tm-hub.ts`: `TmHub` (implements `TmHubConnection`), the reconnect loop over an
  attempt seam (`TmHubConnect` → `TmHubAttempt { start, stop, refusal }`), `tmHubDelay` and
  `tmHubEvent`.
  - Schedule: attempt 1 at once, then 2 s, 10 s, 30 s, then doubling to a 5 min cap; every wait
    but the first × (0.8 + 0.4·random). The count starts over when a connection that lasted 60 s
    closes or is stopped. Every wait is a `setTimeout`, even 0 ms.
  - `nudge()` cuts a wait short. While `TmApi.online` is false the loop reports `offline` and
    waits; an effect on `online` nudges when it turns true. The leader already nudges on
    `leader.probe`; election starts the hub anyway.
  - Terminal: a refusal (negotiate 401/403/404, or a failed user check) halts the loop and calls
    `sink.refused`. `session.ended` with a known reason hands the event on, reports
    `reconnecting`, stops itself, then calls `sink.ended(reason)`. Unknown reasons are only handed
    on. A network error, 429 or 5xx is never terminal.
  - Each attempt has a 100 s deadline (no transport timeout exists in the library: a WebSocket
    that never opens would otherwise hang the loop). `stop()` is idempotent, mutes the logger,
    aborts HTTP in flight and settles within 5 s even if the library's stop hangs (it awaits
    `_startInternalPromise`). Stale callbacks are ignored by run token and attempt identity.
  - Telemetry: `tm.realtime.connected` (timing from attempt start, `attempt` '1' | '2-4' | '5+'),
    `tm.realtime.disconnected { reason: offline | error | closed | ended }`,
    `tm.realtime.refused { status: 401 | 403 | 404 | user-check }`.
- `realtime/src/tm-hub-signalr.ts`:
  - `TmHubHttpClient extends DefaultHttpClient`: `TmSession.check()` before every send (not
    `same` → refusal `'user'`, nothing sent); a per-request abort signal chained to the library's
    (the library sends the negotiate without one, so this is the only way a stop can end a hung
    negotiate); `close()` aborts all in flight and refuses later sends; records 401/403/404 only
    for `/negotiate` URLs, because `HttpConnection` wraps the `HttpError` in
    `FailedToNegotiateWithServerError` and the status is lost.
  - `TmHubLogger`: Warning and above (not None) → `TmTelemetry.error(TmHubLogError, { source:
    'tm-hub', level })`, `access_token=` masked, muted after stop. `logMessageContent` stays off.
  - `tmSignalRConnect`: `HubConnectionBuilder().withUrl(url, { httpClient, withCredentials: true
    })`, server timeout 30 s, keep-alive 15 s, default JSON protocol, the library's transports in
    its order, no `withAutomaticReconnect`; `on('event')` and `onclose`.
- `realtime/src/tm-create-hub.ts`: `tmCreateHub(tenantId, sink, injector)` (TSDoc `@internal`,
  which the golden shows), URL `/{t}/hub`, the session, telemetry, `TmApi.online` and `TM_NOW`
  from the injector.
- `leader/src/tm-leadership.ts`:
  - `TM_HUB_FACTORY`'s default is now `import('@tellma/core/realtime').then(m => m.tmCreateHub(…))`
    (still `| null` for a test app without realtime).
  - `#terminal` restarts the hub on the first sync stamped at or after the signal, from any
    source (the terminal refresh, a poll, another tab), once the stop has settled, unless the
    generation changed or realtime went off. Before, only the terminal refresh's own sync could
    restart it, so a terminal refresh that failed (offline) left the hub stopped forever while
    polls succeeded.
  - `tmAccessEnded(event)`.
- `leader/src/tm-leader-election.ts`: a follower that receives a relayed `session.ended` with
  `access-revoked` or `tenant-unavailable` runs `refresh(t, ['tenant'], 'terminal')`, whether or
  not its build lists the event. `session-terminated` reaches followers as the leader's
  `session.signed-out` (unchanged path, spec 0024 §8.5).
- `tellma-core-testing/src/tm-fake-hub.ts`: `TmFakeHub` (registry; `factory`, `connections`) and
  `TmFakeHubConnection` (counts starts/stops/nudges; `connect`, `drop`, `emit`, `refuse`, `end`).
  `provideTellmaStateTesting()` provides it behind `ɵTM_HUB_FACTORY`. The leader rig now uses it
  instead of its own local fake.
- Package and gates: `@microsoft/signalr` 10.0.11 in the catalog, `client/package.json` and
  `tellma-core/package.json` (and `allowedNonPeerDependencies`); budgets `./realtime` 16 (born at
  15.77, of which ~14 is the library) and `./leader` 3.9 → 4.1 (3.84 → 4.04, D-031, note in
  `budgetNotes`); `staticGraphExcludes`: `./realtime` excluded from `.`, `./shell`, `./attention`
  and `./leader`; an ESLint block that bans `@microsoft/signalr` everywhere under `projects/` but
  `tellma-core/realtime/`. READMEs (core, core-testing) and the ARCHITECTURE.md `@tellma/core` row
  updated.
- First frame: the primary `.` is unchanged at 49.89 (cap measure 49.79 of 50) on a clean build;
  the hub client adds 0 bytes to the first frame. The leader loads `./realtime` only once a tab
  leads (after first render).

### Deviations

1. A failed user check is reported to the sink as `refused(401)`. The sink type admits only
   401 | 403 | 404, and a changed or missing user is what a 401 means; the terminal refresh then
   reaches spec 0024 §8.6. Telemetry keeps it apart as `status: 'user-check'`.
2. An attempt that has not connected in 100 s is abandoned (counted as a failure) and a stop
   settles within 5 s. Not in the spec; without them a hung WebSocket or a library stop that awaits
   a hung start would stall the loop or the leader's release.
3. Restart after a terminal signal waits for any sync stamped at or after the signal, not only the
   terminal refresh's own (see above). This matches §8.5's "a sync that succeeds restarts the loop"
   more closely than the previous check.
4. `session.ended` with a reason this build does not know is handed on but does not stop the
   connection.
5. Attempt numbering: the initial start is attempt 1 at 0 s; the delay for attempt n is 0, 2 s,
   10 s, 30 s, then 30 s × 2^(n−4) capped at 5 min. A refusal keeps the count, so the start after
   the terminal sync waits as the next attempt (§8.3's "the restart keeps the attempt counter").
   The count resets when a connection that lasted ≥ 60 s closes or is stopped.
6. `./realtime` budget is 16 (measured 15.77 rounded up to the next 0.5 KB), under the spec's 18.
7. `TmFakeHub` is a registry plus `TmFakeHubConnection` objects rather than one class, so a test
   can see every connection a leader opened.
8. The 4 KB `hub.event` limit stays server-side only; the client does not re-check it.

### Open risks

- The library's `HttpConnection.stop` awaits a hung start; after the 5 s grace the old connection
  object may live on until the browser fails its socket. It is muted and ignored, and closes itself
  if it ever opens (the library checks for `Disconnecting`).
- The refusal capture depends on the negotiate URL containing `/negotiate` followed by `?` or the
  end; SignalR 10's `_resolveNegotiateUrl` builds `…/negotiate?negotiateVersion=1`.
- `hub-hang.spec` on the Acme host belongs to PC-216; this checkpoint pins it at unit level
  (`tm-create-hub.spec.ts`: a hung negotiate does not delay two router navigations, and the stop
  aborts it).

### What reviewers should examine hardest

- `TmHub`'s run/attempt identity checks (`live()`), the shared `#timer` for both the wait and the
  attempt deadline, and the counter reset in `#settle` when `stop()` ends a stable connection.
- `#terminal`'s effect lifecycle in `tm-leadership.ts`: the `#signals` counter that lets only the
  latest signal's wait count (its stop may settle after a later signal's), destruction on
  `#disconnect` and `stop`, and the self-destroy inside the effect.
- `TmHubHttpClient`'s signal chaining: the library sets `onabort` on the signal we pass, and we set
  `onabort` on the library's own signal.
