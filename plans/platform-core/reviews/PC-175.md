# PC-175: Exports: planners, manifest and the synchronous export operations

## Implementer notes

### What was built

The synchronous half of spec 0019's exports: the request-to-source mapping (§2.1), the display and
editable planners over the codec of PC-173 (§4, §5, §8), the manifest's same-source test (§5.4),
`ExcelOperations<TEntity>.ExportAsync`/`ExportForImportAsync` and
`ChildExportOperations<TChild>.ExportAsync` (§2.2), the Excel composition and its startup checks
(§1.2), and the export instruments and log events (§14.3). Spec coverage: 0019 §1.2, §2.1, §2.2
(the synchronous actions only), §4.1-§4.3, §5, §8, §14.3.

- **`src/core/Tellma.Core/Excel/`** (new files).
  - `ExportSources`: `ExportRequest`/`ExportForImportRequest` to `ExportSource` (`ByIds` or
    `ByQuery`), with every §2.1 refusal as `BadRequestException` naming the clause (`ids`,
    `filters`, `namedFilters`, `search`, `arguments`, `includeInactive`, `columns`); the empty id
    list only for the template; named filters refused on a child surface; 1-100 columns and headers
    of at most 255 characters.
  - `ExportPlanner` (behind `IExcelExporter.PlanDisplay`/`PlanEditable`): the display plan of one
    sheet; the editable plan of the parent sheet and a sheet per selected collection at every depth
    (leading `Id`/`Stamp`, the owner link, editable columns in metadata order, references in their
    reference keys: the request's override, else the target's natural key, else its `Id`), the
    value-set choice lists, the cleaned and de-duplicated sheet names, the `ExcelQuery` tree with
    the parent sheet's `Take = cap + 1` and `CountCap`, the manifest's header block and column
    table, and the file name.
  - `DisplayColumns`: a display column's expression expanded into the select paths it reads (a
    navigation into its display-name terms, a multilingual group into the reader's content slot
    with the fallback, a value set into its label), typed through the Queryex engine; and
    `FoldingRowSource`, which folds each read row back to one cell per column.
  - `ExcelExports` (scoped): runs both shapes. It maps the request, plans, writes through
    `IExcelExporter.WriteAsync` to a scratch file opened only when the first page passes the cap,
    rewinds it into an `ExportOutcome`, records `tellma.excel.export.rows`/`duration` and logs
    `ExportCompleted`; at the parent sheet's cap it records `tellma.excel.export.rejected`, logs
    `ExportRejected` and rethrows the `LimitExceededException` with the background route
    (`export/start`, `export-for-import/start`) as its remedy.
  - `ExcelOperations<TEntity>` (`export`, `export-for-import`, both `Read`, long, idempotent, under
    the `Export` rate policy) and `ChildExportOperations<TChild>` (`export` under the child
    surface's `Read`), each built by an internal `Create(IServiceProvider)` factory.
  - `ExcelCompanions`: which stacks carry the companion, the closed classes, the child surfaces
    that get `ChildExportOperations`, and their scoped registrations.
  - `ExcelContextFactory` (the request's `ExcelContext`: tenant, deployment, clock, calendar, time
    zone, languages, labels, catalog), `ExcelExporter` (the `IExcelExporter` singleton),
    `ExcelMetrics`, `ExcelLog`, `ExcelCheck`, `ExcelComposition`.
- **`ExcelManifest.IsSameSource`**: deployment compared ordinally, the tenant id parsed invariantly;
  a missing manifest or key is foreign.
- **Pipeline seams.** `IStackExcelRows` (internal, Abstractions) is how the companion reaches a
  stack's row source; `EntityService` implements it. `StackComposition` attaches
  `ExcelOperations<TLeaf>` as the stack's first companion when it serves `Export` or `Import`;
  `StackDescriptorBuilder` adds `ChildExportOperations<TChild>` to each exportable child surface's
  actions; `CrudComposition` registers them.
- **Composition**: `CompositionPipeline` calls `ExcelComposition.Register` after the CRUD
  composition. It binds `ExcelOptions` from `Tellma:Excel`, reuses `ScratchDirectory`
  (`Tellma:ScratchPath`), and adds the `excel` (model) and `excel.deployment` (scratch directory)
  checks to the gate.
- **`LimitExceededException.Remedy`** (Abstractions): the route that runs the refused request.
- **Conformance** (`Tellma.Core.Testing`): `ApiActionArguments` gives the two workbook requests
  default bodies (a missing id with the key column; the template) and `InvokeAsync` disposes an
  `IAsyncDisposable` result, so every stack's suite invokes the new actions.
- **Fixtures and goldens**: the gadget fixture's own `export` action became `tally` (the platform
  now owns `export`); the route, route-description and descriptor goldens and the client entity
  fixture gained the two actions per stack and `export` per exportable child surface.
- **Tests**: `test/core/Tellma.Core.Tests/Excel/` (`ExportRequestTests`, `ExportPlannerTests`,
  `DisplayColumnsTests`, `ExportManifestTests`, `ExcelCheckTests`, with `ExportScope`), and
  `test/core/Tellma.Core.IntegrationTests/Excel/ExcelExportTests.cs` over `ExcelRowSourceDatabase`,
  invoking each action through `IApiActionInvoker` so the securable is evaluated as on the wire.
  `WebApiProjectionTests` counts child surfaces, not their endpoints, now that an exportable
  surface projects two; `ChildQueryDescriptor.Actions`' doc no longer says "two".
- **Docs**: the Tellma.Core README's Excel section gains the planner and the operations; both test
  READMEs list the new suites; ARCHITECTURE.md lists `Tellma:Excel` among the configuration
  sections (nothing in it disagreed).

### Deviations

1. `IExcelExporter.PlanDisplay` takes the expanded column specs and the built `ExcelQuery`, and
   `PlanEditable` takes the request and the cap, rather than the §1.1 sketch's arguments: the
   display columns are typed through the Queryex engine and the schema of the tenant's language
   shape, which the singleton exporter does not hold.
2. `LimitExceededException` gains `Remedy` (and a constructor taking it), so the refusal at the
   synchronous cap names the background route (§4.3). It is carried in the message and the
   exception's arguments; there is no localized web detail resource for it.
3. `ExcelOperations<TEntity>` is attached by `StackComposition` to every stack serving `Export` or
   `Import`, not through `contribution.EntityCompanion<TEntity, ExcelOperations<TEntity>>()` (§1.2):
   the companion is per stack, and the contribution item names one entity at a time.
4. The operations classes take internal collaborators, so their constructors are internal and each
   declares an internal static `Create(IServiceProvider)` that `ExcelCompanions.Scoped` binds.
5. `Tellma:ScratchPath` already existed as `Tellma.Core.Blobs.ScratchDirectory`; it is reused, not
   bound again.
6. The stack's row source admits `Import` as well as `Export`, so an import-only stack has a
   template and an editable export.
7. The reader's content slot is the first tenant content language on the culture's parent chain
   (`ar-SA` finds `ar`), else the primary.
8. A tenant without stored settings takes the descriptor's languages.
9. The `Stamp` column is typed `String`: it carries the wire string of `ModifiedAt`.
10. The `Id` and `Stamp` headers are literal, never localized: the import matches them by name.
11. A `Columns` subset of the editable export accepts a foreign key, its navigation, `Nav.Key` and a
    multilingual twin name for the same column.
12. Value-set choice lists come from `IValueSetRegistry`.
13. A projected standard segment (`query`, `export`, ...) stays reserved against every companion
    except the platform's Excel companion, which declares the workbook segments; the gadget
    fixture's own `export` was renamed `tally`.
14. The conformance suite gives the workbook actions default bodies and disposes their outcome.
15. The startup checks are two: `excel` (the redundant `[ExcludeFromExcel]` warning, model-only)
    and `excel.deployment` (the scratch directory exists and takes a file, needing
    infrastructure). The directory must already exist: an export never creates it.
16. An aggregate display column is refused by the Queryex engine itself (`InvalidQueryException`):
    the value mode groups by row. The planner has no aggregate branch.

### Ordering where `OrderBy` is null (D-176, unchanged)

- An unsorted display export (stack or child surface) comes out in ascending `Id` order, not the
  grid's `DefaultOrderBy ?? "Id desc"` (spec 0019 §4.1 says it runs exactly the grid's query).
- The editable export orders by `request.OrderBy ?? Id` explicitly.

### Open risks

- The synchronous cap reads one page of `cap + 1` rows before refusing; a by-query export also
  counts on its first page. A large cap costs one large read before the refusal.
- The display column's content-slot choice depends on the reader's UI culture; a culture outside
  the tenant's languages exports the primary language.
- Every stack serving `Export` or `Import` now projects `export`/`export-for-import`; a module
  companion that already declared either segment is refused at startup, as the gadget fixture's
  was.

### What reviewers should examine hardest

- `ExportPlanner.PlanEditable`: the reference-key choice per column (override, natural key,
  surrogate), the owner link per depth, and the `ExcelQuery` tree's caps.
- `DisplayColumns.Expand`/`Resolve` and `FoldingRowSource`: that every column folds back to
  exactly one cell, at the position the plan gives it.
- `ExcelExports.WriteAsync`: that no scratch file exists unless the first page passed the cap, that
  the file goes with its handle on every failure, and which refusals get the remedy.
- `StackDescriptorBuilder`'s reservation change: that only the platform's companion takes the
  workbook segments.
