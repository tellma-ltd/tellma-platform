### Deviations

The commit message lists all 14 with reasons. In short: `panel` added to `tm/lazy-layouts`;
`indexedDB`/`caches` added to `tm/no-web-storage`; `/private`'s place in the entry-point graph and
only two lazy-to-lazy edges; the boundary rule's outside-package scope; abstract-class seams with
quiet defaults, `TmPageContexts` not seeded, `TmRequestEnd` named; the CLI stub's exit 2; the
preset's prefix read from `angular.json`; strictest `restrict-plus-operands`; `parse` keeps the
scale and drops the sign of zero, exponent cap 1000; core-testing's first members shipped early;
only imported peers declared; core-tools in TS with `prepare`/`pre` hooks; the breakpoint rule
moved into core-tools; the `client-windows` CI job.

Also fixed on the way: `scripts/serve.mjs`'s build-freshness inputs named the old
`client/pnpm-lock.yaml` (silently ignored once the file moved); it now reads the root lockfile and
skips `*.tsbuildinfo` caches, which the new `pre` hooks rewrite.

### Open risks

- Other in-flight client lanes that change `client/package.json` dependencies or the lockfile will
  conflict at integration: they must move the version into the root `catalog`, name it `catalog:`,
  and regenerate the root lockfile with `pnpm install`. A lane that adds a client-side
  `pnpm-lock.yaml` change will see a modify/delete conflict on `client/pnpm-lock.yaml`: take the
  delete and regenerate.
- `catalogMode: strict` makes `pnpm add <pkg>` in any package require a catalog entry.
- The `client-windows` CI job is new; its unit suites already pass locally on Windows (every
  agent runs on Windows), but its first CI run is the first time on a Windows runner.
- The ESLint preset's default export derives the selector prefix from the nearest `angular.json`
  above the current directory; run from elsewhere, selectors are checked for style only.
