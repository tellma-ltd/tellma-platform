### Findings

**R1-1 (major) — `tm/lazy-layouts` refuses spec 0029's object form of `details`.**
`client/projects/core/tellma-core-tools/src/eslint/rules/lazy-layouts.ts:107-111`. Spec 0029 §3
types the member `details?: TmLazyComponent | TmDetailsDeclaration<N>`, where
`TmDetailsDeclaration` is `{ page: TmLazyComponent; create?: TmLazyComponent; edit?; refresh?;
header?; createdUrl? }`. The rule treats `details` as a layout leaf and requires a lazy loader, so
`tmEntity('acme.Customer', { details: { page: () => import('./d'), create: () => import('./c'),
header: 'compact' } })` is refused with "'details' must be () => import('…')" (reproduced by
linting with the built rule). Every distribution or pack that uses the compact header,
`edit: 'page'` or a create layout fails lint, with only an eslint-disable as a way out. The nested
`page`/`create` are also left unchecked, so `details: { page: EagerComponent }` gives the same
generic message instead of naming `page`. Fix: when a layout member's value is an object literal,
walk it (so its `page`/`create` are checked as layout members) instead of reporting the member;
add valid and invalid vectors for the object form.

**R1-2 (major) — `tm/lazy-layouts` judges arbitrary-key records inside any `tm*` call.**
Same file, `:33` (`DECLARATION_FUNCTION = /^tm[A-Z]/`) and the recursive `walk` at `:87-114`. The
rule enters every object and array literal in the arguments of any function whose name starts
`tm` plus a capital letter, and checks every key that matches a layout name. Two of
`tmFeature`'s own spec'd members are records with free keys. One is `icons?: Record<string,
TmIconSource>` (0024 §2.2), where `icons: { search: searchIcon, home: homeIcon }` is refused twice.
The other is `providers` (the "anything Angular" hatch), where `providers: [{ provide: T,
useValue: { display: 'compact', page: 20 } }]` is refused twice. Helper calls are caught too:
`tmFormatNumber(v, { display: 'short' })` is refused. All four were reproduced with the built
rule. Fix: name the declaration functions explicitly (`tmEntity`, `tmPage`, `tmFeature`,
`tmWidget`, `tmOverride`, `tmCodedReport`, as `literal-declaration-keys` already does), and do not
descend into `icons`, `providers` or other non-declaration members. Add vectors for `icons` and
`providers`.

**R1-3 (major) — The new unit-test targets break the `*.csp.spec.ts` convention (PC-F06).**
`client/angular.json:28-36` (`core` → `test`) and the `core-testing` → `test` target at `:57`.
Neither excludes `**/*.csp.spec.ts`, and neither has a `test-csp` target. The workspace rule
`tm/csp-only-in-csp-specs` (applied to `projects/**/*.spec.ts`) steers any spec that installs a
Content-Security-Policy into a `*.csp.spec.ts` file. In `@tellma/core`, the home of 0024 §6's
CSP/Trusted Types and `tm-boot.js` code, that file then runs inside the shared `core` run. That
reintroduces exactly the order-dependent CSP leak PC-F06 fixed: lint stays green, and a later
spec that needs JIT fails on whichever machine orders it second. Fix: give both targets
`"exclude": ["**/*.csp.spec.ts"]`. Also make the convention self-checking: either add a
`test-csp` target to each, or have `scripts/test.mjs` fail when a project holds a
`*.csp.spec.ts` but declares no `test-csp` target, so an excluded spec can never be silently
skipped.

**R1-4 (minor) — `client-windows` skips `build:showcase`.**
`.github/workflows/ci.yml:205-229`. The job comment, the commit message (Deviation 14) and D-032
say it runs every client gate except e2e. It omits `pnpm run build:showcase`, the one gate that
runs `scripts/inject-font-preloads.mjs` over built output paths, the kind of path-separator code
the job exists to catch on Windows. Fix: add `- run: pnpm run build:showcase` after `size:check`,
or narrow the claim in the comment, the commit message and D-032.

**R1-5 (minor) — The published stylelint preset cannot find the breakpoints outside this repo.**
`client/projects/core/tellma-core-tools/src/stylelint/allowed-breakpoints.ts:45-58`. The rule
resolves `@tellma/core-ui/breakpoints.json` from `process.cwd()`'s `package.json`. The fallback
walks `../../../tellma-core-ui/` relative to the package, which exists only in this monorepo.
`@tellma/core-tools` declares no dependency or peer on `@tellma/core-ui`. So with pnpm's strict
layout, a distribution that does not list `@tellma/core-ui` directly (it arrives through
`@tellma/core`), or a lint run from another folder, throws ENOENT when stylelint loads the
preset. Inside this repo the fallback works through the workspace symlink, so nothing fails
today. Fix: declare `@tellma/core-ui` as a peer dependency of `@tellma/core-tools` and resolve it
with `createRequire(import.meta.url)` first, keeping the source-tree fallback for the platform
workspace.

### Responses

- R1-4: fixed in the review 1 fixes commit. `client-windows` runs `pnpm run build:showcase` after
