# PC-F107: In-memory TmClientCache for core tests

## Implementer notes

PC-F107 has no CHECKPOINTS.md entry. It is a fix item scoped by its LEDGER row, D-341 and the
brief. The rules it follows are spec 0010 §D.5 (`TmClientCache.clearAll({ keep })`), spec 0025
§2.6 (the session clean-up's order and what it keeps) and spec 0024 §8.4-§8.6 (the paths that run
it). No product code changed.

### What was built

- `client/projects/core/tellma-core-testing/src/tm-fake-client-cache.ts`: `TmFakeClientCache`,
  a `TmClientCache` over stores kept in memory. A test adds names per area (`add`, `names`).
  `clearAll` deletes the names the real naming rule matches (`tm-` for caches and databases, `tm.`
  for web-storage keys), minus what `keep` keeps. A throwing `keep` goes to the `ErrorHandler`, and
  that name is deleted, as in the real cache. Each sweep is recorded in `sweeps()` with what it
  deleted. The sweep settles in microtasks, and it never rejects. `clearResult`, like
  `TmFakeHubConnection.stopResult`, lets a test hold a sweep open. The fake implements every
  public member of `TmClientCache` through a mapped surface type, as `TmFakeSession` does.
- `provide-tellma-state-testing.ts`: `tmMemoryStoreProvider()` became `tmMemoryStorageProviders()`.
  It is the in-memory store host plus `TmFakeClientCache` behind `TmClientCache`, and it is part of
  both `provideTellmaTesting()` and `provideTellmaStateTesting()`. Both providers already promised
  that no test touches the browser's storage, so the fake goes in both. Using both registers the
  class twice in one injector, which still gives one instance; a spec asserts that.
- Exported from `@tellma/core-testing` with `TmFakeClientCacheSweep`. The API golden is
  regenerated and reviewed: it adds only those two declarations.
- `tm-fake-client-cache.spec.ts` (new): a **parity check against the real cache**. The same names
  go into the page's real CacheStorage, IndexedDB and both web storages, and into the fake. The
  same `keep` (keeps some names, throws on two) runs on both. The survivors, the names `keep` was
  asked about, and the reported errors must match, and the spec pins the expected outcome so two
  sweeps that both did nothing cannot pass. Further tests cover the per-sweep record, settling
  before the page's next task without touching real storage, and `clearResult` holding a sweep
  without rejecting.
- `tm-session-flows.spec.ts`: the rig hands out the fake. The expiry, self sign-out, signed-out
  elsewhere and follow-another-tab tests now seed one store of each kind and assert what the
  clean-up leaves. Before this, no test checked the `keep` rules: `tm-app` and `tm.boot` are kept
  on every path; drafts are kept on expiry only; the following tab sweeps session storage only.
  "Shows another tab's expiry" also asserts no sweep ran. Two tests are new:
  - "leaves only once the browser's stores are swept…": holds the sweep and checks that the tab
    neither leaves nor posts `session.signed-out`, and that the boot record still names the user.
    This is spec 0025 §2.6's step order and spec 0024 §8.4's wait before leaving.
  - "over the browser's own stores": **the one spec that keeps the real `TmClientCache`**
    (`{ provide: TmClientCache, useClass: TmClientCache }` after the rig). On expiry it checks
    that the page's real `tm-test-flows` cache, database and both web-storage keys are gone and the
    real draft key survives. It waits on state (`tmSettleUntil`) and removes what it created.
- The PC-F106 comment in "asks after a minute of a save…" no longer describes real storage. The
  `tmWaitUntil` wait stays, as CONTRIBUTING.md prescribes.
- Docs: the core-testing README (table entry, the in-memory paragraph, and how to opt back into the
  real cache), ARCHITECTURE.md's `@tellma/core-testing` row, and CONTRIBUTING.md's wait rule.

### Who relied on the real sweep

A temporary probe in `clearAll` (reverted) logged every caller during a full `ng test core` run
with the default reporter (the agent reporter hides passing tests' console output). There were 18
calls, all from `tm-session-flows.spec.ts` (13 tests) and `tm-session-tabs.spec.ts` ("waits for a
busy tab…", 3 calls, one per tab). Nothing else in core reaches `TmClientCache`. The tabs spec's
child injectors inherit the fake from TestBed's environment injector, as tabs share one origin's
stores, and it passes unchanged.

### Open risks and what to examine hardest

- **Parity of the duplicated naming rule.** The fake has its own copy of `tm-`/`tm.`. The parity
  spec is what keeps the two in step. Check that it would fail on any drift: area mapping, prefix,
  `keep` semantics, throwing `keep`.
- **One fake for all areas, shared across "tabs".** `tm-session-tabs.spec` gives every tab one
  fake, so one tab's session-storage sweep removes names another tab's would hold. Real tabs have
  separate session storage. The spec never seeds the fake, so nothing depends on this today.
- **The drafts storage is separate from the fake's session-storage list.** In the flows spec,
  drafts live in the rig's map (`TM_DRAFTS_STORAGE`) and are removed by `#clearDrafts`. The
  fake's `tm.draft:` name only tests the `keep` predicate. The real-cache test covers the real
  session storage.
- **The real-cache test still sweeps the shared page's `tm` stores,** as every clean-up did
  before. It is now the only core test that does.

## Review 1

Reviewer 1 (Opus), on 098c9d57. Counts: 0 blocking, 0 major, 4 minor.

What I checked and confirmed:

- **Parity with the real cache.** `TmFakeClientCache.clearAll` and the real one in
  `tellma-core-ui/cache/tm-client-cache.ts` match on: the prefix of each area, `keep` asked once
  per matching name and never for a non-matching one, `!== true`, and a throwing `keep` reported to
  the `ErrorHandler` with that name deleted. The fake also never rejects. The mapped
  `TmClientCacheSurface` follows `TmFakeSession`'s precedent, and the golden adds only the two

  user of the old name outside core-testing (no distribution, the showcase or e2e), and no project
  outside `projects/core` uses either testing provider.
- **Keep rules against spec 0025 §2.6 and 0024 §8.4-§8.6.** `#cleanUp` keeps `tm-app`, `tm.boot`

**R1-2 (minor). The parity spec seeds no `tm.` IndexedDB database, so a drift of the fake's
IndexedDB rule passes.**

- **Where:** `client/projects/core/tellma-core-testing/src/tm-fake-client-cache.spec.ts:22`, whose
  `indexeddb` names are only `tm-fake-cache-a`, `tm-fake-cache-b` and `not-tm-fake-cache`.
- **Failure:** in `tm-fake-client-cache.ts:33` I changed `matches` so that IndexedDB accepts any
  `tm` prefix (`area === 'indexeddb' ? name.startsWith('tm') : …`). The spec still passed 4/4. The
  fake would then sweep a `tm.x` database that the real cache leaves alone. The notes call this spec
  the only guard on the copied rule, and they list area mapping first. The other three areas each
  seed a name of the other prefix (`tm.fake-cache-dot` for caches, `tm-fake-cache-dash` for both
  web storages). IndexedDB does not.
- **Fix:** add `'tm.fake-cache-dot'` to `NAMES.indexeddb`. Add it to the pinned outcome's
  `indexeddb` list as a survivor, and the cleanup loop already deletes it.

**R1-3 (minor). The held-sweep test pins the clean-up's steps 2→3, but not step 1→2, nor the
drafts after the clean-up.**

- **Where:** `client/projects/core/tellma-core/src/session/tm-session-flows.spec.ts:560-577`
  ("leaves only once the browser's stores are swept…"). Spec 0025 §2.6 says the clean-up "makes
  these calls in order": `sweep('session-ended')`, then `clearAll`, then the boot patch. Spec

  called with `'session-ended'` (it runs first, so it has been called by then). Seed a draft
  (`draft(rig, …)`) and assert `drafts(rig)` is still 1 while the sweep is held and 0 after
  `release()`.
