# PC-056: Popup cell editors and final grid ceilings

## Implementer notes

### What was built, and where

All paths are under `client/projects/core/` unless noted.

- **Public surface** (`tellma-core-ui/grid`):
  - `TmGridEditorPopup { minWidth?, maxHeight? }` (defaults 320 and 360) in `tm-grid-types.ts`.
  - `tm-grid-column`'s `editorPopup` input; `null` keeps the in-cell editor.
  - `TmGridEditorContext.readonly`, which a `*tmGridEditor` template reads to show the cell read-only.
- **Keys** (`grid/internal/grid-keymap.ts`):
  - `tmResolvePopupKey`, the pane's table:
    - Escape cancels.
    - Mod+Enter commits and keeps the cell.
    - Enter and Shift+Enter resolve to `enter`, and Tab and Shift+Tab to `tab`, each with its direction; the core decides whether the editor keeps the key.
    - Alt+ArrowDown opens a built-in editor's dropdown.
    - An open dropdown owns every key.
    - The arrows, Home, End, the page keys and F2 stay with the editor.
  - The grid table gains the `popup` condition, so F2 opens a popup cell the user cannot edit, including in a readonly grid without row activation. Typing there still opens nothing.
- **Core** (`grid/internal/grid-core.ts`):
  - `onKeydown` routes a keydown whose nearest overlay surface is the pane (`[data-tm-popup]`) to `onPopupKeydown`. Overlays nested in the pane, such as an editor's dropdown, keep their own keys.
  - The rest of the old body branch became `onBodyKeydown`, which a read-only view reuses after it closes, so its Enter and Tab keep their readonly meaning.
  - Enter belongs to the editor when the target is editable text, an editable `textarea`, or a button, link, select or choice role (`POPUP_ENTER_OWNERS`). Otherwise Enter commits and moves down.
  - Tab commits and moves only from the pane's first or last tab stop (`atPopupEdge`), and the browser moves focus among the others.
  - Every popup editor opens in edit mode, a typed seed included.
  - The read-only view (`popupViewSignal`) has no engine session. It opens on F2 when the column is a popup column and the cell is not editable (`opensPopupView`).
  - The read-only view closes on Escape, Enter, Tab, a press, a tap, focus leaving the grid, the active cell moving, or a mode flip. Before the editing code arrives it waits as `pendingPopupView`.
  - The cell error anchor stays null while a pane is open.
  - A readonly grid with a popup column preloads the editing code.
- **Editing entry point** (`tellma-core-ui/grid-editing`):
  - `editor-pane.ts` and `editor-pane.css` (new) hold `ɵTmGridEditorPane`. It is a `cdkConnectedOverlay` through `tmCreateAnchoredOverlay`, with `popoverHost: parent` on the cell's editor box, so the pane stays a DOM descendant of the gridcell.
    - Positions: over the cell growing down, else up from the cell's bottom edge, both at the inline start, with `keepOnScreen` and an 8 px margin.
    - Width is `max(cell, minWidth)`, least height the cell's, and greatest height `min(maxHeight, 100vh - 2 × margin)`.
    - A ResizeObserver on the cell and the pane re-places it.
    - `ScrollDispatcher.ancestorScrolled` hides it, with opacity 0 and no pointer events, while its cell is out of the scroller's view below the sticky header. Its state and focus are kept.
    - A MutationObserver counts the controls. With more than one, the pane becomes `role="group"` labelled by the header.
  - `editor-session.ts`: `stage(config, readonly, popup)`. A popup mount creates the pane in the cell outlet, renders it synchronously, and mounts the editor into the pane's own outlet. Teardown destroys both.
  - `editing.ts`: `mount(cell, seed, opts, readonly)`, plus `view(cell)` and `closeView()` for the read-only open. A readonly mount never cancels a session and never opens the enum dropdown.
  - `editors.ts`: each of the five built-in editors forwards `readonly` to its control.
- **Harness** (`tellma-core-ui-testing/grid-harness.ts`): `TmGridEditorPopupHarness` (`isReadonly`, `isHidden`, `isGroup`, `getLabel`) and `TmGridHarness.getEditorPopup()`.
- **Showcase and docs:**
  - The `grid-popup-editor` story has a two-field Window sub-form and a multi-line Filter (read-only on Administrator rows), a View/Edit toggle, 30 rows and the model dump.
  - The `PopupCellEditor` docs example: a single `input tmInput` editor in a wide pane over the example host's `lineForm` (review 1 corrected a `textarea tmInput`, which never registers as a cell editor). `docs-examples.spec.ts` gains the `TmGridEditorDef` and `editorPopup` markers, and imports `TmGridEditorDef`. It also stops expecting what a `*tmGridEditor` element hosts to instantiate on first render, since an editor template renders only while its cell is edited.
  - The ARCHITECTURE.md grid paragraph: the readonly preload, and where the pane lives.

### Deviations

1. **The pane's popover parent is the cell's editor box, not the gridcell itself.** §C.15 names `popoverHost: { type: 'parent', element: cell }`. The pane is now created by `grid-editing` in the cell's editor outlet, inside `.tm-grid__editor`. That box fills the cell's padding box (`position: absolute; inset: 0` inside the relatively positioned cell), so the geometry matches except at the cell's bottom gridline. A flipped pane's bottom edge sits 1 px above the cell's outer edge, and the e2e flip assertion allows that pixel. The pane is still a DOM descendant of the gridcell: focus, commit-on-blur and the top layer are unchanged. This is what let the pane leave `./grid`.
2. **The pane is labelled only while it is a group.** §C.15: "The pane is labelled by the column header. With more than one control it is `role="group"`." An `aria-label` on a role-less `div` fails axe (`aria-prohibited-attr`). A single-control pane therefore takes its name from the control, which the built-in editors label with the header.
3. **The read-only view also opens on a readonly *column's* cell** (Administrator rows in the story), not only in a readonly grid or row. §C.15 lists "a readonly grid or row". A readonly column's cell is just as uneditable, and spec 0032 §5.3's filter needs it.
4. **A readonly grid with a popup column preloads `grid-editing`.** §C.15 is silent. The read-only pane mounts the column's editor, which is editing code. Without the preload, the first F2 would wait on a network fetch.
5. **`./menu` stays at 7.86, not §C.11's 7.** That spec figure was already superseded (D-042, and D-067's re-baseline). Nothing here touches the menu.
6. **`./grid` lands at 41.93 against §C.11's 42 + 1.** The 43 holds. The ceiling is 42.03 under the raise rule (measured + 0.1).
7. **Composite editors keep the last-registration-wins `TM_CELL_EDITOR_HOST`.** A sub-form that hosts tm-* form controls (each self-registers) would have its last control registered as the cell editor. The story and tests use plain inputs, as a composite should, or shield their children with their own `TM_CELL_EDITOR_HOST` provider. Spec 0032 §4's window editor should do the same (see Open risks).

### Open risks, and what reviewers should examine

- **Composite editors and `TM_CELL_EDITOR_HOST`** (deviation 7): spec 0032's window and filter editors must not embed self-registering tm-* controls unshielded. A small shielding helper may be worth adding when spec 0032 lands.
- **Synchronous pane mount** (`editor-session.ts` `mountIfReady`): the pane is created and `detectChanges`d, then the editor is created in its `outlet()`, which the overlay's template portal provides. Check that the editor's focus and the IME path hold when the pane's overlay attaches in the same task (the unit seed test and the e2e cover the common path).
- **The error-popover unit test** asserts the cell's error state and the bubble's absence while the pane is open. It does not assert that the bubble reappears after Escape. The unit runner loads no token sheet, so the bubble's in-view measurement is unreliable past the first column.
- **Hidden-pane focus:** while its cell is scrolled away, the pane is transparent but keeps focus. A keystroke reveals the cell first (`revealActiveCell` in `onPopupKeydown`). Pointer events are off while it is hidden.
- **`atPopupEdge`** reuses the header's interactive-content selector to find tab stops. A custom editor with a positive `tabindex` order, or tab stops inside shadow roots, would confuse it.

## Review 1

### Findings

Reviewed commit ea33ed13 against §C.15 and §C.11, D-042, D-057, D-060 and D-067. Scratch and logs are under `.tmp/pc056-r1-*`. A throwaway Playwright probe, `.tmp/pc056-r1-probe/probe.spec.ts`, ran on Chromium against a fresh `build:showcase` (prod serve). It is not part of the change.

**R1-1 (major): a hidden pane still takes the pointer, so it swallows clicks on whatever it covers.**
- **Where:** `grid-editing/editor-pane.css:46-49` and `editor-pane.ts:76`.
- **Why:** `.tm-grid__popup--hidden` sets `pointer-events: none` on the pane's body only. The CDK's `.cdk-overlay-pane` wrapper keeps `pointer-events: auto`, and it is sized to the body, so hit testing lands on the wrapper. The grid's `onPointerDown` and `onClick` ignore any target in `.cdk-overlay-pane` (`inOverlay`), so the press does nothing. The pane is invisible and sits in the top layer.
- **Scenario (probe, reproduced):** open the Filter pane on row 0. Scroll the grid one row (rowHeight + 2), so cell (0,3) is behind the sticky header and the pane hides. The pane still spans rows 1 to 4 of the visible body. `elementFromPoint` at the centre of visible cell (3,3) returns `DIV.cdk-overlay-pane`. A real click there leaves the active cell on row 0, and the pane stays open. The same happens wherever a hidden pane sits: over the header (no sort or resize), over page content above or below the grid, or pushed to the viewport edge (see R1-2).
- **Fix:** while hidden, make the overlay pane itself inert to the pointer. For example, an effect on `hidden()` can set `this.overlay()?.overlayRef?.overlayElement.style.pointerEvents = hidden ? 'none' : ''`, or a panel class can toggle it.
- **Test:** extend the e2e hide test so that, with the pane hidden over visible rows, a click on a visible cell activates that cell and commits the pane. Today the test asserts only the class, which passes with the bug.

**R1-2 (major): on a page scroll, the pane leaves its cell and stays visible, pinned to the viewport edge.**
- **Where:** `grid-editing/editor-pane.ts:140-141` (`keepOnScreen: true`) and `editor-pane.ts:193-205` (`measureInView` tests only the grid scroller's box).
- **Spec:** §C.15 says "The pane follows its cell when the grid or the page scrolls."
- **Why:** when the page scrolls the whole grid up, the cell stays inside its scroller's box, so `hidden` stays false. Once the cell is above the viewport, neither placement fits, and the CDK's push (re-applied on every reposition, since the position is not locked) moves the pane back on screen.
- **Scenario (probe, reproduced):** use a 1280×330 viewport, open the Filter pane on row 0, and scroll the document 335 px. The cell is at y = -95, and the pane is at y = 8, visible (`class="tm-grid__popup"`, not hidden) and detached from its cell. It floats over unrelated page content, and once R1-1 is fixed it should not stay clickable there.
- **Fix:** have `measureInView` also intersect the cell with the viewport (`0..innerWidth` × `0..innerHeight`), so the pane hides whenever its cell is off screen, which `ancestorScrolled` already re-checks on a window scroll. Alternatively, apply the push only while the cell is in view. Keep the push for the open-time placement near an edge, which is what §C.15 asks for.
- **Test:** add an e2e that scrolls the page, not the grid, with a pane open. The pane should be hidden, or off screen with its cell, and reappear on its cell when scrolled back.

**R1-3 (major): a press on a pane's non-focusable content moves focus to the gridcell, typing is then lost, and ArrowDown commits and moves.**
- **Where:** `grid-editing/editor-pane.ts:70-84`. The pane body has no pointer handling or tabindex.
- **Spec:** §C.15 says "Always edit mode … the arrows move inside the editor and never commit and move."
- **Why:** a mouse press on text or padding inside the pane (the story's hint paragraph, the grid gap between fields, the sub-form's padding) runs the browser's click-focus steps. The nearest focusable DOM ancestor is the gridcell (the pane is its DOM descendant), so focus moves from the editor's control to the cell. `onFocusOut` sees a related target inside the scroller and keeps the session open. Keys now come from the gridcell, outside the pane, so they take the in-cell editing path rather than `onPopupKeydown`.
- **Scenario (probe, reproduced):** open the Filter pane on row 1, click `.filter-editor__hint`, and type "xyz". `document.activeElement` is the `gridcell`, the textarea is unchanged (""), and the pane stays open. Then press ArrowDown. The pane closes and the active cell moves to row 2. Clicking inside a sub-form's whitespace is an ordinary gesture, and this happens with no in-cell analogue, since an in-cell editor fills its box.
- **Fix:** add a `mousedown` handler on the pane body that calls `preventDefault()` when the target is not inside focusable or interactive content (for example, not matched by `closest('input, textarea, select, button, a[href], [tabindex], [contenteditable]')`). Focus and the caret then stay where they were. Leave label clicks alone, since they forward focus to their control. Alternatively, give the body `tabindex="-1"` and refocus the editor (`editing.focus()`) when the body itself takes focus.
- **Test:** add a unit or e2e test: press the hint, type, and expect the text in the editor and the pane still open. Then press ArrowDown and expect the pane still open.

**R1-4 (minor): the spec's main use case, a sub-form, needs an undocumented pattern to register correctly.**
- **Where:** `grid-editing/editor-session.ts:252-257` (last registration wins), the `TmGridEditorPopup` TSDoc at `grid/tm-grid-types.ts:38-55`, and the `TmGridEditorDef` TSDoc at `grid/tm-grid-templates.ts:63-69`.
- **Why:** §C.15 motivates popups with "a small sub-form", and spec 0032 §4's window is two date pickers. A consumer who puts two `tm-date-picker`s (or `tmInput`s) in a composite has each one self-register through `TM_CELL_EDITOR_HOST`. Unless the composite shields them, the last one becomes the cell editor and commits its own value as the cell's value. That fails silently, with no dev error, since something did register. The public docs say only "a control that implements `TmCellEditor`". The implementer's deviation 7 records the rule, but nothing in the shipped API tells a consumer.
- **Fix:**
  - Document the composite pattern in the `TmGridEditorDef` and `TmGridEditorPopup` TSDoc: the composite provides its own `TM_CELL_EDITOR_HOST` to its children and registers itself with `inject(TM_CELL_EDITOR_HOST, { skipSelf: true })`.
  - Make a second registration in one mount a dev-mode warning or error in `register`, so the mistake surfaces.
  - The shielding helper the implementer suggests can wait for spec 0032.

**R1-5 (minor): gaps in what the tests would catch.**
- `tm-grid-popup-editor.spec.ts:414-442` (error popover): the test runs with an editor session open, which the effect already closed the bubble for (`session === null`) before this change. It passes with the new `popupView === null` gate removed. The new gate matters only for the read-only view on an editable grid's readonly cell in error, and nothing tests that case. Add a read-only-view variant: a readonly cell with a field error, F2, then expect no bubble.
- `POPUP_ENTER_OWNERS` (`grid/internal/grid-core.ts:230-232`) and the `isContentEditable` branch (`grid-core.ts:2915`) have no test. Enter on a button inside a pane, or in a contenteditable editor, should leave the pane open, and nothing pins that. Add one unit case with a `<button>` in the window editor that asserts Enter leaves the pane open.
- The e2e hide test (`grid-popup-editor.spec.ts:134-153`) scrolls only the grid scroller (see R1-1 and R1-2 for what it misses).

**R1-6 (minor): the pane's viewport margin is set in two places.**
- **Where:** `grid-editing/editor-pane.ts:141` hard-codes `viewportMargin: 8`. `editor-pane.ts:120` and `editor-pane.css:26` cap the size with `var(--popover-viewport-margin)`.
- **Why:** if the token changes, the CDK pushes to 8 px while the size caps use the token. The pane then overflows the push margin, or leaves a gap that differs from the one its size assumes.
- **Fix:** read the token once at open (`getComputedStyle(cell).getPropertyValue('--popover-viewport-margin')`) and pass it to the overlay, or say in a comment that the two must agree.
