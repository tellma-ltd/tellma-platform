# PC-F110: Acme Windows vitest hang: fail fast, then root-cause

## Implementer notes

PC-F110 has no CHECKPOINTS.md entry. It is a fix item, scoped by its LEDGER row, D-369, D-372 and
the brief. No spec section is in scope, and no product code changed.

### The failure

CI 45834807715 (pc/PC-122 at f51b883f), job acme-client (windows-latest), step
`pnpm --dir distributions/acme/src/Tellma.Distro.Acme.Client test`. The Angular build finished at
14:06:24, vitest printed its `RUN v4.1.9` banner at 14:06:25.21 and
`Failed to resolve dependency: @microsoft/signalr, present in client 'optimizeDeps.include'` at
14:06:25.29. Then nothing until the 45 min job limit cancelled it at 14:46:18. The same two lines
appear in every green run (PC-F91's 45859734290 printed the file's result 3.3 s after them), so the
warning is not the hang. No test file result was printed, so the run stopped before the one test
file's end.

### What Vitest bounds and what it does not (read in vitest 4.1.9, @vitest/browser-playwright 4.1.9, @angular/build 22.0.5)

- A test (5 s) and a hook (10 s) time out inside the page.
- Opening a session is bounded by `browser.connectTimeout` (60 s): `BrowserSessions.createSession`
  rejects, `_openBrowserPage`'s `Promise.all` rejects, and the run ends with an "Unhandled Error"
  that the reporters print. So a Chromium launch or a `page.goto` that hangs prints within about a
  minute; it does not match the log.
- Nothing bounds the rest: `project._initBrowserProvider()` (the browser server's
  `vite.listen()`, which awaits the dependency optimizer's first run, then the provider), the
  tester frame's import of a test file, `cleanupTesters` between files, or `vitest.close()`.
  `teardownTimeout` applies only in `vitest.exit()`, which Angular's builder never calls:
  `startVitest` ends with `ctx.close()`. `page.goto` runs with `timeout: 0`.
- The default reporter prints a file's line only at its end, so a run stuck in any of those phases
  prints nothing.

The log therefore puts the hang in one of: the browser server's start (the optimizer's bundling,
its rename of `deps_temp_*` on Windows), the spec's import (an optimized dependency or a chunk
request the server never answers), or the page's own code.

### Reproduction attempts (local Windows, other slots building in parallel)

- 10/10 cold runs as CI runs them (`CI=true`, `node_modules/.vite` and `.angular/cache` deleted
  before each, `DEBUG=vitest:browser*,vite:deps`), 42-68 s each with the build. (A planned 25 were
  cut at 10 by my own package.json edit, which pnpm's verify-deps step refused, rc=1 in 3 s.)
- 20/20 cold runs the same way with the watchdog wired in, 50-72 s each; none tripped it.
- No hang reproduced. The cause is not proven. The DEBUG timeline of a green run shows the
  order: optimizer bundles, renames `deps_temp` to `deps`, "provider is ready", session created,
  browser launched, page created and opened, orchestrator connected, tester connected, file run.

### What I built

1. **`@tellma/core-tools/vitest`** (new export; `src/vitest/watchdog.ts`, `src/vitest/index.ts`):
   - `TmVitestWatchdog`, a Vitest reporter. Progress is a test file queued, collected, started or
     finished, a test or hook starting or finishing, a browser server becoming ready. After 5 min
     without progress (`stallMs`), or 2 min after the run ended outside watch mode while the
     process has not exited (`exitMs`), it writes a report to standard error and calls
     `process.exit(1)`. It is off while the inspector is on (`--debug`).
   - The report: the last 25 events with times; every unfinished file, test and hook and how long;
     per browser project, connected sessions, the browser's launch state, each session page's URL,
     each frame's `document.readyState` or "did not answer within 5.0 s", the page's open requests
     (followed from `request`/`requestfinished`/`requestfailed` events, attached within 500 ms of
     the page opening), its page errors and failed requests, and the browser server's dependency
     optimizer (scan running, dependencies still bundling); a browser project whose server never
     became ready; the Node handle kinds keeping the process alive.
   - It reads Playwright provider fields (`pages`, `browser`, `browserPromise`) and the optimizer
     structurally, each guarded, so a shape change drops details, never the run.
   - `tmVitestConfig(options)` and the default export: `reporters: ['default', (on GitHub Actions)
     'github-actions', watchdog]`, the defaults Vitest picks itself when none are named.
2. **Wiring:** `client/vitest-base.config.mjs` and the Acme app's `vitest-base.config.mjs`
   re-export the preset; every unit-test target in `client/angular.json` (14) and Acme's names it as
   `runnerConfig`. `client/scripts/test.mjs` refuses a target that does not, beside its CSP check.
3. **CI (`ci.yml`):** the client and client-windows unit steps get `timeout-minutes: 15` (normal
   about 3 min; a hang in the last run ends by about 8 min); the Acme unit step gets
   `timeout-minutes: 10` (normal under 1 min) and `DEBUG: vitest:browser*,vite:deps` (about 40
   lines per run), so the next hang shows the last phase that started. YAML parsed with Python's
   yaml; actionlint is not installed.
4. `@tellma/core-tools` gains `vitest` as a dev and peer dependency (types only; the lockfile adds
   one importer entry that reuses an existing vitest resolution). API golden
   `client/api/core-tools.vitest.api.md` added. READMEs (core-tools, client, Acme) and
   ARCHITECTURE.md's client-gates bullet describe the watchdog.

### Proof that it fails fast with evidence

A temporary spec whose top-level `await` never settles (reverted), run through `ng test` with
the Acme config:

- with `stallMs: 150000`, no Vitest limit ended it in 150 s; the watchdog did, exit code 1;
- with `stallMs: 20000` the report named `src/hang.spec.ts` queued 20.4 s, one session connected,
  the browser launched and connected, both frames answering `document complete`, no open
  requests, the optimizer idle: the signature of a promise that never settles in the page.

### What the next CI hang will log

- The Acme step: the `vitest:browser:*` and `vite:deps` debug lines up to the last phase that
  started (optimizer run and rename, provider ready, session, launch, page, goto, orchestrator and
  tester connected, file run), then within 5 min the watchdog's report, then exit 1. A server-side
  hang shows open requests (an optimized dependency or a chunk); a blocked page shows a frame that
  did not answer; an optimizer hang shows the browser server not ready, or dependencies still
  bundling, with the last `vite:deps` line.
- The client steps: the watchdog's report, without the debug lines.

### Deviations

None from a spec; no spec covers it. The brief asked for "vitest browser-mode limits
(connect/teardown/hook as applicable)": the applicable native limits already apply at their
defaults (connect 60 s, hook 10 s, test 5 s), none of them logs what was pending or covers the
silent phases, and `teardownTimeout` does not apply under Angular's builder. So the limit that
logs is the watchdog, not a vitest setting.

### Open risks

- The cause is not found. One occurrence in the CI history I sampled; the green Windows Acme runs I
  checked took 3.45 s (PC-F91) and 3.68 s (PC-F94).
- A false stall: a legitimate gap over 5 min with no test event. The longest in the browser
  suites is a 60 s `beforeAll` (tm-chart.spec.ts); `lint:test`'s long node specs do not use this
  config.
- Observation, not acted on: Acme's unit run mixes two peer variants of vitest. `@angular/build`
  links the vitest built against sass 1.99 (the client's), while the Acme project resolves
  `vitest`, `@vitest/browser-playwright` and `@vitest/browser` built against sass 1.101, so the
  browser server and its vite come from a different module instance than Vitest's core. It works
  in every run seen; I found no path from it to a hang, so I left the lockfile alone.

### What reviewers should examine hardest

- That the watchdog cannot fire on a healthy run (deadline moved on every event; unref'd poller;
  watch mode and inspector exemptions) and cannot keep a finished process alive.
- That `process.exit(1)` after `process.stderr.write`'s callback flushes the report on Windows pipes.
- The claims above about which phases Vitest leaves unbounded.
