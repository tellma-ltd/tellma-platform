# PC-F110: Acme Windows vitest hang: fail fast, then root-cause

## Implementer notes

PC-F110 has no CHECKPOINTS.md entry. It is a fix item, scoped by its LEDGER row, D-369, D-372 and
the brief. No spec section is in scope, and no product code changed.

### The failure

CI 45834807715 (pc/PC-122 at f51b883f), job acme-client (windows-latest), step
`pnpm --dir distributions/acme/src/Tellma.Distro.Acme.Client test`. The Angular build finished at
14:06:24, vitest printed its `RUN v4.1.9` banner at 14:06:25.21 and
`Failed to resolve dependency: @microsoft/signalr, present in client 'optimizeDeps.include'` at
14:06:25.29. Then nothing until the 45 min job limit cancelled it at 14:46:18. The same two lines
appear in every green run (PC-F91's 45859734290 printed the file's result 3.3 s after them), so the
warning is not the hang. No test file result was printed, so the run stopped before the one test
file's end.

### What Vitest bounds and what it does not (read in vitest 4.1.9, @vitest/browser-playwright 4.1.9, @angular/build 22.0.5)

- A test (5 s) and a hook (10 s) time out inside the page.
- Opening a session is bounded by `browser.connectTimeout` (60 s): `BrowserSessions.createSession`
  rejects, `_openBrowserPage`'s `Promise.all` rejects, and the run ends with an "Unhandled Error"
  that the reporters print. So a Chromium launch or a `page.goto` that hangs prints within about a
  minute; it does not match the log.
- Nothing bounds the rest: `project._initBrowserProvider()` (the browser server's
  `vite.listen()`, which awaits the dependency optimizer's first run, then the provider), the
  tester frame's import of a test file, `cleanupTesters` between files, or `vitest.close()`.
  `teardownTimeout` applies only in `vitest.exit()`, which Angular's builder never calls:
  `startVitest` ends with `ctx.close()`. `page.goto` runs with `timeout: 0`.
- The default reporter prints a file's line only at its end, so a run stuck in any of those phases
  prints nothing.

The log therefore puts the hang in one of: the browser server's start (the optimizer's bundling,
its rename of `deps_temp_*` on Windows), the spec's import (an optimized dependency or a chunk
request the server never answers), or the page's own code.

### Reproduction attempts (local Windows, other slots building in parallel)

- 10/10 cold runs as CI runs them (`CI=true`, `node_modules/.vite` and `.angular/cache` deleted
  before each, `DEBUG=vitest:browser*,vite:deps`), 42-68 s each with the build. (A planned 25 were
  cut at 10 by my own package.json edit, which pnpm's verify-deps step refused, rc=1 in 3 s.)
- 20/20 cold runs the same way with the watchdog wired in, 50-72 s each; none tripped it.
- No hang reproduced. The cause is not proven. The DEBUG timeline of a green run shows the
  order: optimizer bundles, renames `deps_temp` to `deps`, "provider is ready", session created,
  browser launched, page created and opened, orchestrator connected, tester connected, file run.

### What I built

1. **`@tellma/core-tools/vitest`** (new export; `src/vitest/watchdog.ts`, `src/vitest/index.ts`):
   - `TmVitestWatchdog`, a Vitest reporter. Progress is a test file queued, collected, started or
     finished, a test or hook starting or finishing, a browser server becoming ready. After 5 min
     without progress (`stallMs`), or 2 min after the run ended outside watch mode while the
     process has not exited (`exitMs`), it writes a report to standard error and calls
     `process.exit(1)`. It is off while the inspector is on (`--debug`).
   - The report: the last 25 events with times; every unfinished file, test and hook and how long;
     per browser project, connected sessions, the browser's launch state, each session page's URL,
     each frame's `document.readyState` or "did not answer within 5.0 s", the page's open requests
     (followed from `request`/`requestfinished`/`requestfailed` events, attached within 500 ms of
     the page opening), its page errors and failed requests, and the browser server's dependency
     optimizer (scan running, dependencies still bundling); a browser project whose server never
     became ready; the Node handle kinds keeping the process alive.
   - It reads Playwright provider fields (`pages`, `browser`, `browserPromise`) and the optimizer
     structurally, each guarded, so a shape change drops details, never the run.
   - `tmVitestConfig(options)` and the default export: `reporters: ['default', (on GitHub Actions)
     'github-actions', watchdog]`, the defaults Vitest picks itself when none are named.
2. **Wiring:** `client/vitest-base.config.mjs` and the Acme app's `vitest-base.config.mjs`
   re-export the preset; every unit-test target in `client/angular.json` (14) and Acme's names it as
   `runnerConfig`. `client/scripts/test.mjs` refuses a target that does not, beside its CSP check.
3. **CI (`ci.yml`):** the client and client-windows unit steps get `timeout-minutes: 15` (normal
   about 3 min; a hang in the last run ends by about 8 min); the Acme unit step gets
   `timeout-minutes: 10` (normal under 1 min) and `DEBUG: vitest:browser*,vite:deps` (about 40
   lines per run), so the next hang shows the last phase that started. YAML parsed with Python's
   yaml; actionlint is not installed.
4. `@tellma/core-tools` gains `vitest` as a dev and peer dependency (types only; the lockfile adds
   one importer entry that reuses an existing vitest resolution). API golden
   `client/api/core-tools.vitest.api.md` added. READMEs (core-tools, client, Acme) and
   ARCHITECTURE.md's client-gates bullet describe the watchdog.

## Review 1

Scope: commit 00bead59 only, a fix item with no CHECKPOINTS entry (LEDGER row, D-369, D-372). No
spec section is in scope. The pc/PC-F110 CI run (45873466694) was skipped by the push gate, so
there is no CI evidence yet, Linux included. The integration run is the gate.

What I checked, and what held:

- **The clock and the thresholds.** In @angular/build 22.0.5, `VitestExecutor.execute` builds
  first and calls `initializeVitest` and `startVitest` after that. In vitest 4.1.9, `start()`
  reports `onInit` before `runFiles`, which starts the run and then initialises the browser
  server. So the stall clock starts after the Angular build, and the server's start is covered.
  `onBrowserInit` fires once `serverFactory` (the vite server) resolves, before the provider
  launches the browser. Green runs, read with `gh run view --json jobs` on 45821565934,
  45845091482, 45848910132, 45859734290, 45865466176 and 45869763518:
  - client unit step: 160-198 s;
  - client-windows unit step: 181-222 s;
  - Acme unit step: 11-26 s on both legs;
  - jobs: client up to 20.1 min, client-windows up to 13.2, acme-client up to 7.8.

  The 15/15/10 step limits are above five minutes of stall plus each step's normal time, and well
  under the 45 min job limit (worst case is client: 20.1 - 3.3 + 15, about 32 min). No browser
  spec has a limit near 5 min. The longest is tm-chart's 60 s `beforeAll`, and the 300 s and
  1 200 s limits belong to lint:test node specs, which do not load this preset.
- **D-011.** This is not a retry, a quarantine or a looser assertion. Every path ends with
  `exit(1)`, including a report that cannot be written.
- **Hang probes, Windows.** I ran browser-mode vitest 4.1.9 with the built preset, the config

  - a test that never settles;
  - a top-level `await` that never settles;

- **Other runs.** The Acme `pnpm test` run as CI runs it (`CI=true`, the step's `DEBUG`) was green

### Findings

**R1-1 (major): the exit limit ends a healthy process that keeps working after a run, such as a
multi-project `ng test`.**
`client/projects/core/tellma-core-tools/src/vitest/watchdog.ts:406-411` (`onTestRunEnd` arms
`now + exitMs`), `:285-296` (`onInit` never clears `ended`), `:424-430`.

- The rule assumes that once a run ends, nothing legitimate is left for the process to do. Angular
  CLI's `ng test` is a multi-target command (`TestCommandModule.multiTarget = true`). Without a
  project, `ArchitectCommandModule.run` runs every project's test target in turn, in one process.
  With `--watch=false` or under `CI=true`, run 1 ends, and the next project's Angular build then
  runs in the same process before its Vitest's `onInit`.
- The watchdog of run 1 still holds its `now + 120 s` deadline. Its poller is unref'd but alive,
  because the build keeps the loop busy. So a later project whose build takes over 2 minutes ends
  the whole command with exit 1 and "The test run ended … but the process has not exited", on a
  healthy run.
- The window is real. In my multi-target probe of the client workspace (`ng test --watch=false`,
  other slots building), core's test build alone took 119.4 s.
- It also applies to any distribution workspace with two or more test projects, which will run
  `ng test` in CI, since the preset is published API.
- Repro of the mechanism (scratchpad script): `startVitest('test', …, { run: true })` with the
  preset at `exitMs: 5000`, then 20 s of idle in the same process, as a second build would take.
  It exits 1 after 5 s with the ended-run report.
- `onInit` does not set `ended = false` either. Its `progress('initialised')` is dropped for the
  second Vitest, and the stale exit deadline governs until that run's `onTestRunStart`.
- The client CI step (test.mjs runs one process per target) and Acme (one project) are not
  affected, so CI is safe today.
- Suggested fix:
  - Bound what the exit limit is meant for, a Vitest that does not finish closing. Register
    `vitest.onClose(() => …)` in `onInit` (public in vitest 4.1.9). Once close completes, disarm
    (`deadline = undefined`). The step timeout backstops a process that lingers after a clean
    close.
  - In `onInit`, reset `ended = false` before `progress`.
  - Add a spec: run end, then `onInit` of a second instance with no further events within
    `exitMs`, expect no exit; and an `onClose` that never resolves, expect the exit-limit report.
  - Reword the README and TSDoc ("2 minutes after its run") to match.

**R1-2 (minor): the builder's `reporters` option silently removes the watchdog, and test.mjs does
not refuse it.**
`client/scripts/test.mjs:107-110`; README "The Vitest preset".

- When the unit-test builder gets `reporters` (`options.reporters`, a configuration, or
  `ng test --reporters=…`), @angular/build's `createVitestConfigPlugin` (plugins.js:130-131)
  runs `delete testConfig?.reporters`, which drops the whole runnerConfig reporter list,
  watchdog included.
- test.mjs checks only `options.runnerConfig`. So a target that sets `reporters` (for a JUnit
  file, say), or a `configurations.*` entry that sets either option, passes the guard and runs
  without the watchdog.
- Suggested fix: in test.mjs, also refuse a target whose `options` or any `configurations` entry
  sets `reporters`, or any `configurations` entry that sets `runnerConfig`. Add one README sentence
  saying `reporters` replaces the preset's list.

**R1-3 (minor): the preset does not pick the reporters Vitest itself would, although the README
and TSDoc say it does.**
`client/projects/core/tellma-core-tools/src/vitest/index.ts:40-41, 55`; README "names Vitest's
default reporters".

- vitest 4.1.9 `resolveConfig` (coverage.DM_a_rWm.js:454-457) picks `isAgent ? "agent" :
  "default"`, then `github-actions`. Under a coding agent, which is how this repo's work runs, the
  preset forces `default`, which prints every file. Vitest would print failures only.
- Suggested fix: mirror the rule, using `isAgent` from `std-env` (a vitest dependency; add it to
  core-tools), or drop the claim of parity from the README and TSDoc.

**R1-4 (minor): the entry point's TSDoc names a `.mts` file; everything else says `.mjs`.**
`client/projects/core/tellma-core-tools/src/vitest/index.ts:6, 9, 14, 48`.

- The module and `tmVitestConfig` examples say `vitest-base.config.mts`. The README, both
  workspaces and test.mjs (`RUNNER_CONFIG`) use `vitest-base.config.mjs`. A platform target that
  followed the TSDoc would be refused by test.mjs.
- Suggested fix: use `.mjs` in the TSDoc.

**R1-5 (minor): on the client steps, a hang in the browser server's start leaves almost no
evidence.**
`.github/workflows/ci.yml:264-266, 313-315`; `watchdog.ts:546-550`.

- The report describes the optimizer only for a project whose server became ready. Before
  `onBrowserInit`, the vite server is the private `_parent._parentBrowser`, and the report says
  only "its server has not become ready". That phase covers the optimizer's bundling and the
  `deps_temp` rename on Windows, which the implementer notes name as a candidate.
- Acme gets the `vite:deps` timeline for it; client and client-windows do not. The LEDGER row asks
  for those steps to be checked for the same exposure.
- Suggested fix: give the client steps `DEBUG: vite:deps,vitest:browser:playwright`. Leave out
  `vitest:browser:pool`, which logs each file's options and would be long over 150+ files.

**R1-6 (minor): a running test in a blocked page is not listed, and the README says every started
test is.**
`watchdog.ts:363-366`; README "every test file, test and hook that started and has not finished".

- The page batches test events over its RPC. In my `for (;;) {}` probe, the report showed the file
  `running` and "Tests not finished: none", although the test had started; both frames "did not
  answer". The frames line gives the right answer, but the test list reads as "between tests".
- Suggested fix: when any frame does not answer, add a line under "Tests not finished" saying the
  page may hold events it could not send. Say in the README that the test list reflects what the
  page reported.

**R1-7 (minor): the pending-hook listing is untested, though a test name claims it.**
`client/projects/core/tellma-core-tools/src/vitest/watchdog.spec.ts:115-137`.

- "…listing the file, test and hook still running" starts and ends its `beforeAll`, then asserts
  "Hooks not finished: none". No test leaves a hook pending, so a broken `hookLabel`, for example
  the owner of a suite-level hook, would pass.
- Suggested fix: leave one hook open (a module-level `beforeAll`, plus one on a test or suite) and
  assert its line, `beforeAll of src/app.spec.ts [app (chromium)]: running for 60.0 s`.

**R1-8 (minor; asks for a fix item, not a change here): Acme's unit run does load two vitest
module instances.**
`pnpm-lock.yaml:286` (client: vitest built against sass 1.99.0) against `:403, :415` (Acme:
`@vitest/browser-playwright` and vitest against sass 1.101.0).

- I confirmed the implementer's observation on disk:
  - `@angular/build` links `vitest@…7caf…`, so `startVitest`, the Vitest core and its vite run
    from the sass-1.99 variant;
  - the Acme project links `vitest@…9f4f…` and `@vitest/browser-playwright@…d691…`. Angular
    loads the provider through the project's resolver, so its `@vitest/browser` and browser vite
    come from the sass-1.101 variant.
  - The client workspace resolves one variant.
- Is it plausible as the cause? Weakly. The split is deterministic and the hang happened once. But
  Acme is the one place that hung and the one place with two Vitest and two Vite module instances
  in one run. Each instance keeps its own module state, such as debug namespaces, `vitest/node`
  singletons and Vite's optimizer, and no other suite tests that combination.
- It is cheap to remove: pin `sass` once (a catalog entry, or a `pnpm.overrides` to
  @angular/build's 1.99.0), so both importers resolve one variant. Add a CI or lint:test check
  that `require.resolve('vitest/package.json')` from `@angular/build` and from the Acme app give
  the same real path.
- Suggested fix: open a fix item for it, and keep it out of this commit.

### Responses

**R1-1: fixed.**
- `onInit` now starts over. It disarms anything left by an earlier Vitest instance and clears
  the events, files, tests, hooks, browser projects and pages. It also resets `ended` and
  re-reads the inspector.
- It registers `vitest.onClose`. Vitest calls its close handlers as its close begins, beside the
  closing of its projects, so the handler does not disarm straight away. In a microtask it takes
  `vitest.close()`, which returns the cached closing promise, and disarms when that settles: it
  clears the deadline and the poller, and records `closed`.
- A close that never finishes still meets the exit limit, whose headline now reads "…but Vitest
  has not finished closing". The microtask lets `close()` store its promise first. Called
  directly from a handler that nothing awaited before, it would begin a second close.
- A close that settles after a later `onInit` does not disarm the later instance.
- Run end still swaps the stall limit for the exit limit, as before.
- TSDoc (`TM_VITEST_EXIT_MS`, `exitMs`, the class), the core-tools README and the client README
  now describe the exit limit as "Vitest has not finished closing". They also say that a process
  lingering after a clean close is left to the step's limit.
- New specs:
  - "disarm once Vitest has closed, so a process that goes on to build the next project is left
    alone". This is the reviewer's case: no timer is left, and 10x the stall limit of idle passes
    without an exit.
  - "start over for a later Vitest instance in the same process, and still catch its stall". The
    first instance's exit limit is gone, the first close settling late does not disarm the
    second, and the second's stall fires with only its own file listed.
  - "…end a process whose Vitest has not finished closing" (renamed). The close begins and never
    finishes, and the exit-limit report appears.
- I also checked against real vitest 4.1.9 (scratch probe: `startVitest` run mode, the built
  watchdog at `exitMs: 5000`, then 20 s of idle in the same process). After `startVitest`
  returned, the deadline was undefined, the poller cleared and the last event `closed`. The idle
  passed and the exit code was 0.

**R1-2: fixed in test.mjs.** I confirmed that the builder drops the file's reporters
(`createVitestConfigPlugin` deletes `testConfig.reporters` whenever the builder's `reporters` is
set), so test.mjs now refuses:
- a target whose options set `reporters`;
- any `configurations` entry that sets `reporters`;
- any `configurations` entry that names a `runnerConfig` other than `vitest-base.config.mjs`.

A scratch harness checked all six cases (ok, missing, options reporters, configuration reporters,
other runnerConfig, same runnerConfig). The core-tools README says that `reporters`, or
`ng test --reporters`, replaces the preset's list, watchdog included. The client README and
test.mjs's header describe the refusal. Acme runs `ng test` on its own and its target sets
neither option.

- The spec mocks `std-env` and covers all four combinations. The TSDoc now states the rule.

**R1-4: fixed.** The entry point's TSDoc examples now say `vitest-base.config.mjs`, and the
