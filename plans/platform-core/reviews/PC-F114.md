# PC-F114: action-field twins carry slot 1's label key

## Implementer notes

### The defect

Spec 0029 §2.4 says "Twins carry slot 1's key; the client adds the suffix (§4.2)". The emit followed
this for entity properties, but not for an action's argument fields. `ClientEntityModel.Field`
resolved every argument through its own name, so `core.User`'s `me/save` fields `name2` and `name3`
got the conventional keys `Core_User_Action_MeSave_Name2` and `_Name3`, each with a "Name2"/"Name3"
fallback. PC-F103 declared those two keys (its Deviation 4, from its R1-1) instead of fixing the emit.

A second problem sat under the first. `TmActionField` carried no slot, so even a twin with slot 1's
key could not get its suffix, and a twin beyond the tenant's content languages could not be left
out. If only the key had been fixed, a generated dialog would read "Name", "Name", "Name".

### What was built

- **Twin detection for arguments** (`src/core/Tellma.Core/Client/ActionArguments.cs`).
  - `ActionArguments.Members` finds an arguments type's multilingual groups the way the entity
    metadata does. The anchor `P` carries `[Multilingual]` (on a positional record,
    `[property: Multilingual]`), and its twins `P2`/`P3` are found by name.
  - Each `Member` gains `Multilingual` (`ClientMultilingualSlot`: group = the anchor's C# name,
    slot 1-3).
  - A member named like a twin with no anchor is an ordinary member (`Address2`).
  - A malformed group throws `InvalidOperationException` when the model is built. That covers an
    anchor that is not a string, a twin the wire does not carry as a nullable string, and a member
    in two groups. These match the entity metadata's rules.
- **The emit** (`ClientEntityModel.Field`). A grouped field resolves the action-field chain by its
  group's name, which is the anchor's name, so every twin reads slot 1's key chain
  (`Core_User_Action_MeSave_Name` → `Core_User_Name` → `Name`). It also writes
  `multilingual: { group, slot }` on each member of the group, the anchor included, as properties do.
- **`ClientActionField`** (`src/core/Tellma.Core.Abstractions/Client/ClientActionField.cs`) gains
  `ClientMultilingualSlot? Multilingual`. It is null and omitted for a field in no group.
- **`MeSaveRequest.Name`** is marked `[property: Multilingual]`. It is the only argument type in the
  platform, GL or Acme with twins: a scan of the recorded model found no other twin-named field.
- **The resource audit's derived keys** (`ConventionalStringKeys.AddStacks`) skip slots 2 and 3, as
  `AddEntities` already skips entity twins. `Core_User_Action_MeSave_Name2/3`, `Core_User_Name2/3`
  and the shared `Name2`/`Name3` are no longer conventional keys. Before, they were derived only
  because of me/save's fields.
- **The client** (`client/projects/core/tellma-core`):
  - `TmActionField.multilingual?` mirrors `TmPropertyMetadata.multilingual`.
  - New `TmActionFieldDescriptor`, exported from `@tellma/core`: a field with `label` and, for a
    slot, `contentDir`.
  - `TmEntityActionDescriptor.fields` is now `TmActionFieldDescriptor[]`. The entity model gates
    the fields by the tenant's shape, so a twin beyond it is left out of the descriptor and of the
    generated dialog's form and body. It labels them like properties ("Name (ع)" with two or three
    languages, bare with one) through one shared `#slotted` helper, which the property path now
    uses too.
  - The generated action dialog reads `field.label` for its form fields and for error items,
    instead of looking up the key itself.
- **Fixtures re-recorded** with the repo's command: `TELLMA_UPDATE_GOLDENS=1 dotnet test
  test/core/Tellma.Core.Tests --no-build --filter FullyQualifiedName~ClientEntityFixturesTests`,
  then a clean run. Only `entities-chunk.json` changed: me/save's three name fields gain
  `multilingual`, and `name2`/`name3` move from their own keys and fallbacks to `Name`. The
  summaries and both `.d.ts` fixtures are unchanged.
- **API golden** `client/api/core.api.md` approved after reading the diff: the new descriptor
  type, the `multilingual` member and the narrowed `fields`.
- **READMEs.** `src/core/Tellma.Core/README.md` covers the action-field row of the chain table and
  argument groups. `client/projects/core/tellma-core/README.md` covers field gating and labels.

### Deviations

1. **`TmActionField` / `ClientActionField` gain `multilingual`.** Spec 0029 §2.2's `TmActionField`
   has no slot, yet §2.4 makes the client add a twin's suffix. Without a slot it cannot do that,
   nor leave out a twin beyond the tenant's languages (§4.2). The member mirrors
   `TmPropertyMetadata.multilingual`.
2. **An argument group is declared with `[Multilingual]` on the arguments type**, the entity rule
   (`P` anchored, `P2`/`P3` found by name). The spec does not say how an argument is known to be a
   twin. The rejected alternative was to infer twins from the resource entity's groups by matching
   names. That would be implicit, and it would miss an action whose arguments carry a group its
   entity lacks. The guard test still catches an arguments type that mirrors its entity's twins
   without the anchor.
3. **`TmEntityActionDescriptor.fields` are descriptors** (`label`, `contentDir`), gated by the
   tenant's shape. Spec 0031 §10.4 says the generated dialog labels each field "by `labelKey`". It
   now labels by the descriptor's label, which is that key plus §4.2's suffix.

### The PC-F103 keys (coordination)

platform-core's `Strings.resx`/`Strings.ar.resx` carry no `Core_User_Action_MeSave_Name2`/`_Name3`.
Only pc/PC-F103 adds them, so this checkpoint removes nothing. Whichever of PC-F103 and PC-F114
lands second must drop those two keys (en and ar), and the gates enforce it. With both merged, the
emit no longer looks the keys up. `ConventionalStringKeys` no longer derives them, so
`CoreResourceAuditTests` fails them as orphans, and `PlatformLabelsTests` is unaffected because the
twins resolve to `Name` with no fallback.

### Open risks / what to examine hardest

- **The refusals in `ActionArguments.Members`** run when the client model is built, at the first
  emit. A distribution that marks a non-string argument `[Multilingual]` fails its
  `tellma-client build` and `The_model_passes_the_startup_checks`-style tests, not its compile.
  This matches the entity rule, but check that the message is clear enough.
- **The guard's heuristic** (a field named like its entity's twin must be that twin) assumes an
  argument whose wire name equals an entity twin's is a translation. An action that takes, say,
  `name2` with another meaning on an entity with a `Name` group would be flagged. None exists, and
  such a name would be confusing anyway.
- **`fields` narrowed on `TmEntityActionDescriptor`.** Code that builds a descriptor by hand now
  needs `label` on each field. Nothing outside the model does (grep). Tests build metadata, not
  descriptors.

### Findings

**R1-1 (minor): the generated dialog never gives a twin's input its content direction.**
- **Where:** `client/projects/core/tellma-core/entity/src/tm-action-dialog.ts:252` passes
  `property: generated.field.value`, the bare `TmValueDescriptor`. `tm-value-editor.ts:390` reads
  `contentDir` off its `property` input, and `:154`/`:157` bind it as `[attr.dir]`.
- **Correction to the implementer's note:** the note says "`ɵTmValueFormField` takes no direction",
  but it does. It forwards `property` to `tm-value-editor` unchanged
  (`tm-value-form-field.ts:34`).
- **Failure scenario:** this change now admits twins into generated dialogs. Take an `entity` action
  with a `[property: Multilingual] Title` group on an `en` + `ar` tenant. Its `title2` input renders
  with no `dir`, so it does not get spec 0029 §4.2's "an Arabic `Name2` input is `dir="rtl"` on an
  English page". The descriptor computes the right `contentDir`, but nothing passes it on. No
  shipped generated dialog has twins today, so the defect is latent.
- **Fix:**
  - Pass the direction with the value, for example
    `property: generated.field.contentDir === undefined ? generated.field.value : { ...generated.field.value, contentDir: generated.field.contentDir }`.
  - Better, compute it once per field in `fields` so the template does not spread on every check.
    It must still read the getter inside a `computed`, so that a change of the tenant's languages
    shows.
  - Then drop the open-risk note.

**R1-2 (minor): no test drives the generated dialog with a multilingual argument.**
- **Where:** `tm-entities.spec.ts:155-171` proves the descriptor's gating, labels and `contentDir`.
  The fixture actions in `tm-entity-actions.spec.ts` (`:86-111`) have no grouped field, and the only
  recorded action with twins (`me/save`) is an `api` action that the dialog never opens.
- **Failure scenario:** each of these regressions keeps every test green:
  - reverting `tm-action-dialog.ts:337` or `:434` to `this.#localization.ɵtext(field.labelKey, …)`,
    so a 2-language dialog reads "Name", "Name";
  - the dialog building its form from metadata rather than from the gated descriptor;
  - R1-1's missing `dir`.
- **Fix:** add a `tm-entity-actions.spec` case.
  - Set up an entity action whose `fields` carry a `title`/`title2`/`title3` group, on a 2-language
    rig.
  - Assert that the generated dialog shows exactly two controls, labelled "Title (En)" and
    "Title (ع)", and no `title3` control.
  - Assert that the `title2` input has `dir="rtl"`.
  - Assert that the arguments sent carry no `title3`.
  - Assert that a 422 item at `arguments.title2` that the form cannot place is listed with the
    suffixed label.
