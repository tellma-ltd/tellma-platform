# PC-212: Sweep, reconcile, built-in schedules, blobs verify and alert queries

## Implementer notes

### What was built, and where

- **Statements** (`src/core/Tellma.Core/Blobs/BlobStatements.cs`):
  - `Claim(batch, size, reclaimAfter)` is the §7.1 claim: a `TOP (@size)` CTE on
    `IX_Blobs_Expiry` over `Staged`/`Released`/`Deleting` rows whose `ExpiresAt` is before an
    instant the statement declares from `SYSUTCDATETIME()`. The `UPDATE … OUTPUT` sets `Deleting`
    and `ExpiresAt = now + reclaim` and returns each row's kind, key, variants and `deleted.[State]`.
    It is not idempotent.
  - `DeleteSwept(batch, ids)` deletes through an `IdList` with `WHERE State = 'Deleting'`,
    `OUTPUT deleted.[Id]`. It is idempotent.
  - `Segment(batch, kind, segment)` reads one fan-out segment's rows for verification, with
    `StorageKey LIKE '{kind}/{k0k1}/%'`, and writes nothing.
- **Sweep** (`Blobs/BlobSweepHandler.cs`, `core.blob-sweep`):
  - Runs with `BatchSize=1`, `MaxConcurrency=1`, `RunsWhenReadOnly`, lease 600 s and 3 attempts.
  - **Each round:**
    1. Checks cancellation.
    2. Claims on a `Maintenance` batch in `TransactionMode.None`.
    3. Makes one `IBlobStore.DeleteAsync` call for every claimed row's primary and variants. On a
       `BlobStoreException` it falls back row by row (parallelism 8), so only the failing rows are
       kept.
    4. Deletes the rows whose objects are gone, with `CancellationToken.None`. On a
       `ForeignKeyViolationException` it deletes them one by one and keeps each violator, logging
       `BlobSweepRowRetained` and metering it as a failure.
    5. Meters `sweep.deleted{state}` by the state each row left.
    6. Logs `BlobSweepBatch` and reports progress (`Blob.SweepProgress`).
    - A short round ends the loop.
  - Then `PurgeIncompleteAsync(now - 24 h)` runs once. A failed purge is logged and metered, not
    thrown.
- **Reconcile** (`Blobs/BlobReconcileHandler.cs`, `core.blob-reconcile`):
  - Runs one `Maintenance` batch per registered kind, in ordinal order, through the existing
    `BlobStatements.Reconcile`.
  - A positive count is metered (`reconcile.released{kind}`) and warned about
    (`BlobReconcileReleased`).
  - Progress carries a percent (`Blob.ReconcileProgress`).
- **Supporting pieces:**
  - `BlobMaintenanceMetrics` and `BlobMaintenanceLog` hold the instruments and events.
  - `BlobObjectNames.Of` gives a row's object names, or null when they fall outside the grammar.
  - `BlobVerifier` runs the verification (below).
  - The metrics are registered in `BlobsRuntimeComposition`.
- **Built-in schedules** (`Composition/CoreFeature.cs`): `BuiltInSchedule(4, core.blob-sweep,
  */15 * * * *)` and `(5, core.blob-reconcile, 0 2 * * 6)`. The three serialized migrations were
  regenerated with dotnet-ef (fixture, test distribution, Acme). Their only diff is the
  `Schedules` and `ScheduleStates` seed rows.
- **Labels and progress text:** `JobHandler_core_blob-sweep`, `JobHandler_core_blob-reconcile`,
  `Blob_SweepProgress` and `Blob_ReconcileProgress`, in English and Arabic `Strings*.resx`.
- **`blobs verify --tenant <id> [--delete-orphans]`** (`src/core/Tellma.Core.Migrator`):
  - Code: `CommandLine/MigratorCommandLine.cs`, `Commands/BlobsVerifyCommand.cs` and
    `TenantOutcome.Verified`.
  - Opens the tenant's system scope (non-active allowed) and runs `BlobVerifier` per kind and per
    `00..ff` segment.
  - Each segment's objects are **listed before its rows are read**, the mirror of staging, which
    writes the row before the bytes. That makes the orphan delete race-safe.
  - Reports `orphan {name}` and `missing {name} (blob {id}, {state})`, then a one-line summary.
  - Never writes a row.
- **Alert queries** (`infra/monitoring/blobs/*.kql` and a README):
  - `sweep-failures` (`sweep.failures > 0` per 15 min)
  - `reconcile-released` (`> 0` per day, by kind)
  - `attach-rejected-rate` (by kind and reason)
- **Test support:**
  - `InMemoryBlobStore` gains `FailDeletes`, `Purges` and `ClearPurges`.
  - `FixtureTenant.State` is settable.
  - `JobPollDriver` now skips the handlers that do not run on a read-only tenant when the registry
    holds the tenant as read-only, as the worker's `TenantPoller` does.

### Deviations

1. **Reclaim span:** the claim binds it in seconds (`DATEADD(second, …)`), not minutes, so a
   sub-minute `SweepReclaimAfter` is honoured.
2. **Row delete output:** the row delete returns the deleted ids (`OUTPUT deleted.[Id]`), so the
   sweep meters by each row's previous state and counts only rows actually deleted.
3. **Verify's missing report and segment walk:**
   - It skips `Deleting` rows (the sweep is mid-erase) and rows staged in the last 5 minutes
     (bytes still uploading).
   - It walks 256 fan-out segments per kind, listing before reading, to bound memory and make the
     orphan delete race-safe.
4. **`JobPollDriver` read-only filter:** it applies the worker's read-only handler filter, and
   `FixtureTenant` gains a settable `State`. This test-harness change affects every suite that
   uses them; none before this one set a read-only state.
5. **Claim tests:** they seed instants relative to `SYSUTCDATETIME()` rather than using a
   `TimeProvider` fake, because the claim reads the database clock.
6. **New log event:** `BlobSweepStoreFailed` (Warning) covers a failed store delete or purge, beyond
   the events the spec lists.
7. **Failed purge:** it is counted in `tellma.blobs.sweep.failures`, so the sweep-failure alert
   covers it.
8. **Out-of-grammar rows:** a claimed row whose names fall outside the grammar is left `Deleting`
   and counted as a failure, rather than deleted blind.
9. **Row delete and cancellation:** the row delete ignores job cancellation. Once objects are gone,
   their rows are removed so they are not re-claimed with nothing to delete. Cancellation is
   checked between rounds.
10. **Progress messages:**
    - `Blob.SweepProgress {claimed, deleted}` has no percent (the total is unknown).
    - `Blob.ReconcileProgress {reconciled, total, released}` carries one.
11. **Verify refusals:** `blobs verify` refuses a Suspended or Retired tenant through the scope
    factory, where `allowNonActive` admits ReadOnly. The unknown-tenant failure is exit 2.
12. **New outcome word:** `verified` is added to `TenantOutcome`.
13. **Label wording:** the resource labels' English and Arabic wording is my choice.

### Open risks

- **`IJobProgress` and the fixture audit:** a percent jump renews the job in the background, and
  that can overlap the reconcile's next kind batch. The fixture's change-tracking audit then blames
  the batch for the `core.Jobs` write. The reconcile test suspends the audit, as the tree-verify
  test does. In production this is harmless, but any other percent-reporting handler under the
  audit will hit it too.
- **Verify cost:** verify lists 256 prefixes per kind on every run. That is fine for an operator
  command, but slow on a store with millions of objects.
- **Re-claim after a failed row delete:** if the process dies after the store delete and before the
  row delete, the row is re-claimed after `SweepReclaimAfter`. The store delete of missing names
  must stay a no-op, which the conformance suite requires.

### Where reviewers should look hardest

- `BlobSweepHandler.RoundAsync`: the store-failure fallback and FK-retain paths, and the metering
  arithmetic (deleted rows by previous state, failures counting store rows, grammar rejects and FK
  violators exactly once).
- `BlobVerifier`: the list-before-read order and the missing-object grace rules.
- The claim text against §7.1: lock hints, the `IX_Blobs_Expiry` seek and the `OUTPUT deleted.[State]`.
- `JobPollDriver`'s read-only filter, against `TenantPoller`.

### Findings

Counts: 0 blocking, 0 major, 3 minor.

Verified locally on a4fc6e1a: `dotnet build` of `Tellma.Core.IntegrationTests` and `Tellma.Core.Tests`
printed Build succeeded with 0 warnings. `Tellma.Core.Tests` filtered to `BlobAlertQueryTests`,
`BlobMaintenance*` and `MigratorCommandLineTests` passed 72/72. `Tellma.Core.IntegrationTests` (integration

**R1-1 (minor): the sweep's cancellation rules have no test.**
- Code: `src/core/Tellma.Core/Blobs/BlobSweepHandler.cs:83` checks the token between rounds (spec 0017 §7.1).
  `BlobSweepHandler.cs:252` runs the row delete with `CancellationToken.None` (deviation 9).
- Failure scenario: someone passes the job token to the row delete, or drops the between-rounds check. No
  test fails. In the first case, a cancel that lands after the store delete leaves rows whose objects are
  gone sitting in `Deleting` for the reclaim span. In the second, the run ignores a cancel until the
  backlog is drained.
- Fix: add a `BlobSweepTests` case that seeds more than one round of due rows. A store hook (an
  `InMemoryBlobStore` delete callback, or a wrapping store) cancels the host token passed to
  `JobPollDriver.PollOnceAsync` during round 1's store delete. Assert that:
  - round 1's rows are deleted;
  - the remaining due rows are still in their seeded state, never claimed;
  - the job ends as a stop, not Succeeded.

**R1-2 (minor): the deviations' failure paths have no tests.**
- Code:
  - a failed purge is logged as `BlobSweepStoreFailed` (operation `purge`, rows 0) and counted in
    `tellma.blobs.sweep.failures` (deviations 6 and 7): `BlobSweepHandler.cs:262-272`;
  - a claimed row whose names fall outside the grammar stays `Deleting` and counts as a failure
    (deviation 8): `BlobSweepHandler.cs:137-141`.
- Failure scenario: a refactor that rethrows the purge failure (failing a run that already erased every
  row) or stops metering it stays green. That would silence the `sweep-failures.kql` alert the README
  promises covers purges. The same goes for a refactor that deletes an out-of-grammar row blind. Only
  `BlobObjectNames.Of` is unit-tested, not the handler path.
- Fix:
  - Give `InMemoryBlobStore` a `FailPurges` switch, in the same shape as `FailWrites`. Add a sweep test:
    the job Succeeded, one failure measured, one `BlobSweepStoreFailed` with `Operation = purge`.
  - Add a test that seeds a due row with an out-of-grammar `StorageKey` (for example an uppercase key).
    It must stay `Deleting` with a fresh reclaim instant, `BlobSweepBatch` must report it as failed, and
    the other rows must be swept.

**R1-3 (minor): the README says every round logs `BlobSweepBatch`, but the code logs only rounds that claimed something.**
- Code: `src/core/Tellma.Core/README.md` ("each round logs `BlobSweepBatch` (claimed, deleted, failed)")
  against `BlobSweepHandler.cs:98-101` (`if (rows.Count > 0)`).
  `A_sweep_with_nothing_due_reports_one_empty_round_and_still_purges` asserts that no record is written.
- Failure scenario: an operator or a later checkpoint relies on the README and treats a missing
  `BlobSweepBatch` line as a sweep that did not run.
- Fix: change the README to "each round that claimed rows logs `BlobSweepBatch`" (spec 0017 §10.2 allows
  either), or log every round.

**On the orchestrator's items:**
1. **Shared harness change.** It is sound, and no other suite changes meaning.
   - The `JobPollDriver` filter matches `TenantPoller.PollOnceAsync`'s `(!readOnly || RunsWhenReadOnly)`.
   - `FixtureTenantRegistry` starts `Active`, and only `BlobSweepDatabase` moves it, resetting it to
     `Active` in `ResetAsync`. Every other consumer polls an `Active` tenant, so their claims are
     unchanged.
   - `CreateScope` now reads the registry's current descriptor, which equals `Info.Descriptor` while
     the state is `Active`.
   - `TenantScopeFactory` reads `registry.Find` on every scope, so the job scope really does carry the
     read-only state. The read-only sweep and reconcile tests therefore test what they claim.
   - All four other `JobPollDriver` suites pass (above).
2. **`BlobSweepStoreFailed`, and purge failures in `sweep.failures`.** The spec allows both, so no ruling
   is needed.
   - Spec 0017 §10.2 lists events but does not close the set.
   - §7.1 says a storage failure "is metered", and a purge is a store operation. The instrument
     description and the README document it.
   - This follows the D-128 precedent (0020 §9's added log events). Ahmad should get it as a
     spec-amendment note: add the event to §10.2, and say in §10.1 that purge failures count.
3. **The reconcile test suspending the audit.** It is a correct test seam, not a hidden product defect.
   - `JobItemProgress.Report` starts a fire-and-forget renewal on a percent jump. That renewal writes
     `core.Jobs` on its own connection, lease-fenced, while the next kind's batch runs.
   - Only `ChangeTrackingAudit`, which "is exact while one batch at a time writes the database", blames
     the batch for it. This is the same class as the PC-145 tree-verify ruling.
   - No coverage is lost: the reconcile statement's declared writes are still audited in
     `BlobLifecycleStatementTests`.
   - The sweep reports no percent, so it never races, and its suite keeps the audit on.
   - With the audit suspended there is no flake. The class will recur in every later percent-reporting
     handler suite (export, import). A harness-level fix should be ledgered rather than repeated per
     suite, for example an audit that ignores lease-fenced `core.Jobs` renewals when a batch does not
     declare `core.Jobs`.
4. **Migrations.** All three (fixture, test distribution, Acme) are renames to new dotnet-ef timestamps.
   The only content diff is the `Schedules` and `ScheduleStates` seed rows for ids 4 and 5, in
   generator layout, plus the `[Migration]` id. Nothing was edited by hand.

**Accepted deviations:**
- Deviations 1–5 and 9–13 are justified against 0017 §7.1–§7.3 and 0020 §3.1, §3.3 and §7.9.
- In 3, list-before-read is race-safe: rows commit before bytes, and the sweep deletes objects before
  rows. A reported orphan whose row the sweep removes between the listing and the read is deleted
  harmlessly.
- Deviation 5 is the WATCHLIST lead (`TimeProvider` cannot move the database clock).
- Deviations 6–8 are covered by item 2 and R1-2.

### Responses

- R1-1: fixed in the "PC-212: review 1 fixes" commit (child of a4fc6e1a), per the orchestrator's
  ruling. The new test `A_cancel_during_a_rounds_store_delete_finishes_that_round_and_claims_nothing_more`
  seeds five due rows (a full round of three, then two). The store's new `Deleting` callback, during
  round 1's store delete, sets `CancelRequestedAt` and runs a renewal, so the item's token is
  cancelled mid-round. The test asserts that:
  - round 1's three rows and objects are gone;
  - the other two are still `Released`, past their seeded deadline and stored, never claimed;
  - no purge ran;
  - one `BlobSweepBatch` "3|3|0" was logged;
  - the job ends `Cancelled`.
  Passing the job token to the row delete fails the row assertion, and dropping the between-rounds
  check fails the claimed-nothing-more and Cancelled assertions.
  - **Why not a host stop, as suggested.** I first wrote the test with a host stop, and it showed
    the row delete does **not** survive one. A host stop, like a lost lease, cancels the lease's
    scope token, which `DataExecutor` links into every batch of the scope, so `CancellationToken.None`
    cannot keep that round trip alive. The rows then stay `Deleting` and are claimed again after
    `SweepReclaimAfter`; their objects are already gone, and deleting missing names is a no-op. A
    requested cancel cancels only the item's token, and that is the case `CancellationToken.None`
    covers.
  - **Doc correction.** The `DeleteRowsAsync` remark now says exactly this, and deviation 9 should
    read "the row delete ignores a requested cancel; a host stop or lost lease ends the scope and
    the rows are reclaimed".
- R1-2: fixed in the same commit, per the orchestrator's ruling.
  - `InMemoryBlobStore` gains `FailPurges`, in the shape of `FailWrites`: the purge is recorded,
    then the exception is thrown. `A_failed_purge_is_metered_and_warned_of_and_the_sweep_still_succeeds`
    asserts that the job Succeeded with its rows swept, one purge recorded, one
    `tellma.blobs.sweep.failures` measurement of 1, and one `BlobSweepStoreFailed` carrying the
    store's exception, `Operation = purge` and `Rows = 0`.
  - `A_claimed_row_whose_names_are_outside_the_grammar_stays_claimed_and_is_metered_while_the_others_are_swept`
    seeds an earlier due row whose key is upper-cased (through `SeedAsync`'s new `storageKey`
    parameter), beside a well-formed one. The malformed row stays `Deleting` with a fresh reclaim
    instant (59-60 minutes) while the other row and its object are gone. The test also asserts
    `BlobSweepBatch` "2|1|1", one failure measured, and no `BlobSweepStoreFailed`.
  - The test fixture's reset clears `FailPurges` and `Deleting`.
- R1-3: fixed in the same commit. The README now says "each round that claimed rows logs
  `BlobSweepBatch`", and lists the out-of-grammar row among the failures that stay claimed.
