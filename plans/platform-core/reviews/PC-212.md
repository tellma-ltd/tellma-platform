# PC-212: Sweep, reconcile, built-in schedules, blobs verify and alert queries

## Implementer notes

### What was built, and where

- **Statements** (`src/core/Tellma.Core/Blobs/BlobStatements.cs`):
  - `Claim(batch, size, reclaimAfter)` is the §7.1 claim: a `TOP (@size)` CTE on
    `IX_Blobs_Expiry` over `Staged`/`Released`/`Deleting` rows whose `ExpiresAt` is before an
    instant the statement declares from `SYSUTCDATETIME()`. The `UPDATE … OUTPUT` sets `Deleting`
    and `ExpiresAt = now + reclaim` and returns each row's kind, key, variants and `deleted.[State]`.
    It is not idempotent.
  - `DeleteSwept(batch, ids)` deletes through an `IdList` with `WHERE State = 'Deleting'`,
    `OUTPUT deleted.[Id]`. It is idempotent.
  - `Segment(batch, kind, segment)` reads one fan-out segment's rows for verification, with
    `StorageKey LIKE '{kind}/{k0k1}/%'`, and writes nothing.
- **Sweep** (`Blobs/BlobSweepHandler.cs`, `core.blob-sweep`):
  - Runs with `BatchSize=1`, `MaxConcurrency=1`, `RunsWhenReadOnly`, lease 600 s and 3 attempts.
  - **Each round:**
    1. Checks cancellation.
    2. Claims on a `Maintenance` batch in `TransactionMode.None`.
    3. Makes one `IBlobStore.DeleteAsync` call for every claimed row's primary and variants. On a
       `BlobStoreException` it falls back row by row (parallelism 8), so only the failing rows are
       kept.
    4. Deletes the rows whose objects are gone, with `CancellationToken.None`. On a
       `ForeignKeyViolationException` it deletes them one by one and keeps each violator, logging
       `BlobSweepRowRetained` and metering it as a failure.
    5. Meters `sweep.deleted{state}` by the state each row left.
    6. Logs `BlobSweepBatch` and reports progress (`Blob.SweepProgress`).
    - A short round ends the loop.
  - Then `PurgeIncompleteAsync(now - 24 h)` runs once. A failed purge is logged and metered, not
    thrown.
- **Reconcile** (`Blobs/BlobReconcileHandler.cs`, `core.blob-reconcile`):
  - Runs one `Maintenance` batch per registered kind, in ordinal order, through the existing
    `BlobStatements.Reconcile`.
  - A positive count is metered (`reconcile.released{kind}`) and warned about
    (`BlobReconcileReleased`).
  - Progress carries a percent (`Blob.ReconcileProgress`).
- **Supporting pieces:**
  - `BlobMaintenanceMetrics` and `BlobMaintenanceLog` hold the instruments and events.
  - `BlobObjectNames.Of` gives a row's object names, or null when they fall outside the grammar.
  - `BlobVerifier` runs the verification (below).
  - The metrics are registered in `BlobsRuntimeComposition`.
- **Built-in schedules** (`Composition/CoreFeature.cs`): `BuiltInSchedule(4, core.blob-sweep,
  */15 * * * *)` and `(5, core.blob-reconcile, 0 2 * * 6)`. The three serialized migrations were
  regenerated with dotnet-ef (fixture, test distribution, Acme). Their only diff is the
  `Schedules` and `ScheduleStates` seed rows.
- **Labels and progress text:** `JobHandler_core_blob-sweep`, `JobHandler_core_blob-reconcile`,
  `Blob_SweepProgress` and `Blob_ReconcileProgress`, in English and Arabic `Strings*.resx`.
- **`blobs verify --tenant <id> [--delete-orphans]`** (`src/core/Tellma.Core.Migrator`):
  - Code: `CommandLine/MigratorCommandLine.cs`, `Commands/BlobsVerifyCommand.cs` and
    `TenantOutcome.Verified`.
  - Opens the tenant's system scope (non-active allowed) and runs `BlobVerifier` per kind and per
    `00..ff` segment.
  - Each segment's objects are **listed before its rows are read**, the mirror of staging, which
    writes the row before the bytes. That makes the orphan delete race-safe.
  - Reports `orphan {name}` and `missing {name} (blob {id}, {state})`, then a one-line summary.
  - Never writes a row.
- **Alert queries** (`infra/monitoring/blobs/*.kql` and a README):
  - `sweep-failures` (`sweep.failures > 0` per 15 min)
  - `reconcile-released` (`> 0` per day, by kind)
  - `attach-rejected-rate` (by kind and reason)
- **Test support:**
  - `InMemoryBlobStore` gains `FailDeletes`, `Purges` and `ClearPurges`.
  - `FixtureTenant.State` is settable.
  - `JobPollDriver` now skips the handlers that do not run on a read-only tenant when the registry
    holds the tenant as read-only, as the worker's `TenantPoller` does.

### Deviations

1. **Reclaim span:** the claim binds it in seconds (`DATEADD(second, …)`), not minutes, so a
   sub-minute `SweepReclaimAfter` is honoured.
2. **Row delete output:** the row delete returns the deleted ids (`OUTPUT deleted.[Id]`), so the
   sweep meters by each row's previous state and counts only rows actually deleted.
3. **Verify's missing report and segment walk:**
   - It skips `Deleting` rows (the sweep is mid-erase) and rows staged in the last 5 minutes
     (bytes still uploading).
   - It walks 256 fan-out segments per kind, listing before reading, to bound memory and make the
     orphan delete race-safe.
4. **`JobPollDriver` read-only filter:** it applies the worker's read-only handler filter, and
   `FixtureTenant` gains a settable `State`. This test-harness change affects every suite that
   uses them; none before this one set a read-only state.
5. **Claim tests:** they seed instants relative to `SYSUTCDATETIME()` rather than using a
   `TimeProvider` fake, because the claim reads the database clock.
6. **New log event:** `BlobSweepStoreFailed` (Warning) covers a failed store delete or purge, beyond
   the events the spec lists.
7. **Failed purge:** it is counted in `tellma.blobs.sweep.failures`, so the sweep-failure alert
   covers it.
8. **Out-of-grammar rows:** a claimed row whose names fall outside the grammar is left `Deleting`
   and counted as a failure, rather than deleted blind.
9. **Row delete and cancellation:** the row delete ignores job cancellation. Once objects are gone,
   their rows are removed so they are not re-claimed with nothing to delete. Cancellation is
   checked between rounds.
10. **Progress messages:**
    - `Blob.SweepProgress {claimed, deleted}` has no percent (the total is unknown).
    - `Blob.ReconcileProgress {reconciled, total, released}` carries one.
11. **Verify refusals:** `blobs verify` refuses a Suspended or Retired tenant through the scope
    factory, where `allowNonActive` admits ReadOnly. The unknown-tenant failure is exit 2.
12. **New outcome word:** `verified` is added to `TenantOutcome`.
13. **Label wording:** the resource labels' English and Arabic wording is my choice.

### Open risks

- **`IJobProgress` and the fixture audit:** a percent jump renews the job in the background, and
  that can overlap the reconcile's next kind batch. The fixture's change-tracking audit then blames
  the batch for the `core.Jobs` write. The reconcile test suspends the audit, as the tree-verify
  test does. In production this is harmless, but any other percent-reporting handler under the
  audit will hit it too.
- **Verify cost:** verify lists 256 prefixes per kind on every run. That is fine for an operator
  command, but slow on a store with millions of objects.
- **Re-claim after a failed row delete:** if the process dies after the store delete and before the
  row delete, the row is re-claimed after `SweepReclaimAfter`. The store delete of missing names
  must stay a no-op, which the conformance suite requires.

### Where reviewers should look hardest

- `BlobSweepHandler.RoundAsync`: the store-failure fallback and FK-retain paths, and the metering
  arithmetic (deleted rows by previous state, failures counting store rows, grammar rejects and FK
  violators exactly once).
- `BlobVerifier`: the list-before-read order and the missing-object grace rules.
- The claim text against §7.1: lock hints, the `IX_Blobs_Expiry` seek and the `OUTPUT deleted.[State]`.
- `JobPollDriver`'s read-only filter, against `TenantPoller`.
