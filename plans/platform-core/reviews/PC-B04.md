The same outage on a stack query or save answers 503 dependency-unavailable with Retry-After: 1. settings/client is on the boot path, so a brief failover shows every booting tab a hard error instead of a retry. For the settings persist the ambiguous case is also unhandled: a commit whose response was lost (verdict Committed) answers 500 although the save committed, and the user's retry then conflicts with their own write; PC-079's review accepted this as "as elsewhere in the pipeline", but the pipeline does translate it (SaveRun.Persist.cs:80-88), so that note rests on a false premise.
- Fix: Move the translation to one shared helper and apply it where non-pipeline batches enter: wrap the frame run in ApiActionInvoker.InvokeAsync (covering every [ApiAction], SettingsService included) and the runner calls of BlobStager and BlobResolver, mapping DataAccessRetryExhaustedException, and DataAccessAmbiguousException with an Unknown verdict, to DependencyUnavailableException("database", 1 s). In SettingsService.PersistAsync handle the Committed verdict as SaveRun does (treat as committed and answer from a fresh read) instead of letting it escape. Add unit tests that a runner faulting with each exception inside an [ApiAction] and inside the blob services yields 503 with Retry-After, and one web test that asserts no data-layer exception type reaches ProblemMapper's internal backstop.
