# PC-178: Background exports and chunked, resumable background imports

## Implementer notes

### What was built

- **The start routes** (`src/core/Tellma.Core/Excel/ExcelOperations.cs`, `ChildExportOperations.cs`, `ExcelJobStarts.cs`, `ExcelJobArguments.cs`, `ExcelJobs.cs`):
  - `export/start` and `export-for-import/start` on every stack that serves the exports, and `export/start` on every exportable child surface. All of them run under `Read`, `Mutation = true`, `AllowWhenReadOnly = true` and are not idempotent. `import/start` runs under `Save`.
  - Each start checks the request's structure exactly as its synchronous twin does (sources, column count, headers, sheet and column overrides). It then serializes the job arguments. Those carry the resource, the caller's `ExcelJobCulture` (culture, calendar, zone and language) and the request, and are refused as a `BadRequestException` (`bytes`, `maxBytes`) past `JobLimits.MaxHandlerArgumentsBytes`.
  - Export arguments are a discriminated union (`DisplayExportJobArguments` / `ForImportExportJobArguments`) whose `kind` discriminator is written first.
  - An export start enqueues `core.export` through the action frame and answers `JobAccepted(jobId, null)`.
  - An import start inserts its `core.Imports` row, which owns the upload. The row's persist enqueues `core.import` (`ImportService.ContributeAsync`), so the answer is `JobAccepted(jobId, importId)`.
  - Job labels are `Excel.Export.Label` / `Excel.Import.Label`, with the entity's label as the argument.
- **The export handler** (`ExportJobHandler.cs`). Options: `BatchSize = 1`, `RunsWhenReadOnly`, `ResultEntity = core.Export` via `JobId`, 3 attempts.
  - The handler re-negotiates the stored localization (`ExcelContextFactory.Localize`) and checks the run-as user's `Read` again. Child surfaces skip this check because their row source checks the owner.
  - It writes through the same `ExcelExports` run as the synchronous path, reporting progress per page (`Excel.Export.Progress {rows}`), with `MaxExportRows` as the cap.
  - It stages the file as `export-file`, then inserts the `core.Exports` row (server-owned `JobId`, `ExpiresAt` = now + `ExportFileRetentionDays`) as an enlisted write, which commits the blob.
  - It notifies the requester with `core.export.ready` (`fileName`, `rowCount`, `fileId`, target the Export row).
  - These refusals fail the job with their code and arguments: forbidden, row cap, blob rejected, and a query's arithmetic failure. After fix1, a bad request and an invalid query (first diagnostic) do too, as a backstop to the start's own planning.
- **The import handler** (`ImportJobHandler.cs`, `ExcelImports.Background.cs`). Options: `CommitsInSteps`, `ResultEntity = core.Import` via `JobId`, 3 attempts.
  - Pass 1 parses the committed upload whole.
  - The handler then checks the atomic ceilings. Above `MaxAtomicImportRows` the import fails as `Import.TooLargeForAtomic`. Above the save's parent ceiling or its row ceiling it fails the same way, with that ceiling.
  - It checks `OrderHash` against the checkpoint (`Import.ResumeMismatch`).
  - Pass 2 saves chunk after chunk. `ImportSession.ChunkEnd` gives each chunk `ImportChunkRows` parent rows, grown to the next boundary that no row's references reach past, within the save's ceilings.
  - Each chunk's checkpoint (`ImportCheckpointState`) is appended to the stack save's own batch through `SaveOptions.OnPersist` → `IJobProgress.Append`. The chunk and its checkpoint therefore commit or roll back together, behind the lease fence.
  - `CommittedNewIds` keeps only the new rows' ids that later rows still reference (`ReferencedFrom(next)`), so the state stays small.
  - Cancellation:
    - The chunk save runs with `CancellationToken.None`, so a requested cancel lets the chunk in flight commit. The handler then records a stopped outcome (`Stopped = true`, committed ranges) and leaves the item unmarked; the runner cancels it.
    - A lost lease or a host stop cancels through the ambient scope token and rolls the chunk back.
    - A lease loss reported by the fence as `Job.LeaseLost` inside the save is mapped to `OperationCanceledException`.
  - Warnings in a chunk become a `ConfirmationRequiredException` with one request per warning × row, adding `sheet` and `row`. The runner turns that into `PendingConfirmation`, and confirming it resumes at that chunk.
  - Errors in a chunk:
    - The handler records `ImportFailure` (errors capped at `MaxReportedErrors`, `totalErrors`, and the committed ranges) on the row.
    - It then fails the job with `Excel.Import.Failed`.
    - A forbidden or bad-request result becomes one error at no cell.
  - On success the handler records the `ImportOutcome` on the row and notifies with `core.import.completed`.
- **Session support** (`ImportSession.cs`, `ImportModel.cs`, `ImportParser.cs`, `ImportSession.Resolve.cs`):
  - `ChunkEnd`, `CommittedRanges`, family sizes and a reach prefix (the furthest position any row's in-sheet references point to).
  - `ImportCycle.Referrers`.
  - The PC-177 R1-4 carry: child-sheet references to new parent rows are now order edges. A child row naming a new parent row orders the named row first, and a cycle through child rows is refused at each child cell that closes it.
- **Instruments and logs**:
  - `tellma.excel.import.chunks` (histogram) and `tellma.excel.import.resumed`.
  - `ImportChunkCommitted` and `ImportResumed`.
- **Composition**:
  - `CoreFeature` registers both handlers and both notification types.
  - `ExcelComposition` registers `ExcelJobStarts`.
  - `StackRegistry.LeafOf` lets the handler find the stack's leaf service.
- **Fix to PC-177 code** (`ExcelImports.RowsById`): it indexed `chunk.Entities` by the session position, which only works for a chunk that starts at 0. It now indexes by chunk index. The fault showed up as an `ArgumentOutOfRangeException` when a second chunk raised a warning.

### Deviations

1. `/start` validates the request's structure before it enqueues, so a malformed request is a 400 at the start instead of a failed job.
2. An oversized request is a `BadRequestException` with `bytes` / `maxBytes`. The spec names no code for this.
3. A chunk can grow past `ImportChunkRows` to reach a safe boundary, where no row's in-sheet reference points past the chunk end. Otherwise a reference to a later new row could not be bound.
4. Child-sheet references to new parent rows are ordering edges (the PC-177 carry). This changes the order, and with it `OrderHash`, for files whose child rows name new parent rows. The cycle error sits on the referring child cell.
5. Resource strings were added for the new progress, label and notification keys, and for codes that lacked them.
6. `ImportCycle` carries `Referrers`, and `StackRegistry.LeafOf` was added.
7. A Forbidden or BadRequest raised inside a background import is recorded as one `ImportError` at no cell rather than failing the job with its own code. This keeps the outcome on the row.
8. A child-surface export skips the handler's explicit `RequireAsync(Read)`, because the row source checks the owner's read.
9. A handler that finds no stack for its resource throws `InvalidOperationException`, which retries and then fails as internal. That only happens when a composition changes under a queued job.
10. `ExcelImports.RowsById` was fixed (see above).
11. `tellma.excel.import.chunks` counts across attempts by replaying `ChunkEnd` from row 0 to the checkpoint's next row under the current chunk size, because the checkpoint keeps no chunk count. If the size changed between attempts, the count is what the current size would have committed. A stop handed over before the parse records the count only when no chunk committed, since counting needs the parse.
12. Background scenarios not driven (fix1), one line each:
    - The requester cancelling a pending export: the jobs' cancel statement ends a pending job with no checkpoint at once (kind `C`), so no handler runs. That statement belongs to the jobs suite.
    - The retention stop of an import, and an `Export` row's delete releasing its blob: both are `core.file-retention`'s paths (PC-213), which will drive them. The `Export.FileId` release is the ordinary blob-reference capture.

### Open risks

- The localization of a job scope depends on the tenant settings being loaded in that scope (`Localize`). This is covered only through the fixture tenant.
- The AspNetCore start-route tests (`ExportTests`, `ImportTests`, `ProjectedRouteTests`) check only the hand-off answer and the Import row. They do not poll the jobs through the composed host.

### What reviewers should examine hardest

- `ImportJobHandler.Checkpoint` and its interplay with `OnPersist` replay: the checkpoint must be appended exactly once per committed chunk, including when the save pipeline re-enters.
- `ImportSession.ChunkEnd`'s safe-boundary rule against upsert cycles and cross-chunk references.
- Pruning `CommittedNewIds` (`ReferencedFrom(to + 1)`): a pruned id that a later row still needs would bind wrongly.
- The cancel and stop paths: cancel lets the chunk in flight commit, while a lease loss or host stop rolls it back.

**Major**

- **R1-1. Child-sheet references now refuse mutually linked new rows as a "parent cycle", in synchronous imports too.**
  - Where: `src/core/Tellma.Core/Excel/ImportParser.cs:797-812` (edges from every row of a family), `:845` and `:884-913` (`RefuseCycles` over those edges), `ImportSession.Resolve.cs:466` (the deferred upsert variant). The test `test/core/Tellma.Core.Tests/Excel/ImportSessionTests.cs:355` pins the refusal.
  - Scenario: two new nodes A and B, where A's `Links` row names B (`OtherNode.Id = -2`) and B's names A. One save persists this fine: the emitter inserts every parent before any child row and binds negative ids in either direction (`SaveEmitterTests.cs:284`, where the earlier row of the payload references a later one). Before this commit the file imported. Now the parse raises `Excel.Import.ParentCycle` at both link cells, so a synchronous import is refused with a misleading code. A background import is refused the same way, although `ChunkEnd` (`ImportSession.cs`, the reach loop) would already keep A and B in one chunk. An upsert by code is refused at resolution once both rows are new.
  - Only a cycle of parent self-references is a real tree cycle. A cycle that runs through a child row is only an ordering constraint between chunks.
  - Fix:
    - Refuse a strongly connected group only when every edge on it is a parent-row self-reference.
    - Leave a group that contains a child edge unplaced, in Excel order after the rest, as today's leftovers are, and let `ChunkEnd`'s reach keep it in one chunk.
    - When the save's ceilings cannot hold such a group, fail at that chunk with a code that says so (or with the forward reference's not-found, as the comment at `ImportSession.Resolve.cs:453-455` already accepts).
    - Turn the unit test into an import that succeeds, and add a synchronous integration test of mutually linked new nodes.
    - The `named` dedupe at `:797`/`:805` keeps only the first referrer's edge per target. With the fix it matters only for where an error is placed.
