# PC-150: Server relay POST /api/client-telemetry

## Implementer notes

### What was built

- **Contract (`Tellma.Core.Abstractions.Api`).** `ClientTelemetryBatch` and `ClientTelemetryItem`
  (§6.1, registered in the source-generated `TellmaApiJsonContext`), `ClientTelemetryNames` (§6.4),
  and `ClientTelemetryOptions`, moved here from `Tellma.Core.AspNetCore.Hosting` where an earlier
  checkpoint had put it, so the code matches §6.1's namespace. The binding (`Tellma:ClientTelemetry`,
  `HostOptionsBinding`) and `DistributionInfo.telemetry` are unchanged.
- **The endpoint (`src/core/Tellma.Core.AspNetCore/Observability/ClientTelemetryRelay.cs`).**
  `MapTellma` maps `POST /api/client-telemetry` after the BFF with `RequireAuthorization(Web)`,
  `AsTenantlessEndpoint("client-telemetry")`, `RequireRatePolicy(tellma-telemetry)`,
  `JsonBodySizeMetadata(32 KB)` and `PlatformEndpointMetadata`. The tracing filter and the session's
  background rule already named the path, so it stays untraced and never renews the session.
  - Turned off (`Enabled = false`): `204` at once, the body unread.
  - The body is read with a bound of its own, at most 32 KB plus one byte, because TestServer does
    not enforce `IRequestSizeLimitMetadata` the way Kestrel does. A stated `Content-Length` past the
    limit is refused unread. Past the limit it throws `BadHttpRequestException(413)`, which the
    problem mapping answers `413 limit-exceeded`. A `JsonException` becomes
    `BadHttpRequestException(400)`, which the mapping answers `400 bad-request` with `reason`
    `malformed-json`.
  - The envelope (`ClientTelemetryRules.Refusal`) answers `400 bad-request` with a detail sentence.
- **Rules (`ClientTelemetryRules.cs`).**
  - The tab id, name and key regexes are source-generated with `\z` anchors, so a trailing newline
    never passes.
  - Item drops: kind, then name (an error must be named exactly `tm.error.captured`), then time.
    The time is checked as `At − SentAt` ∈ [−24 h, +1 min], which never overflows.
  - Properties: the first 16 that pass, in the client's order. A failed property does not take a
    place. Keys match the camelCase rule.
  - Values: a long, else a finite double; a bool; or a string within its key's cap (`message` 256,
    `stack` 4,096, others 128). Null, objects and arrays are dropped.
- **Masks (`ClientTelemetryMasks.cs`).** These are ports of `tm-error-capture.ts`'s `URLS` and
  `EMAILS`.
  - They use `RegexOptions.NonBacktracking`, so a hostile 4 KB stack costs linear time.
  - That engine has no lookbehind, so the client's `\b` and `(?<![\w/.])` become a captured
    "lead" character (start of text or an ASCII non-word character), which is written back ahead of
    `<url>`.
  - URLs are masked first, then e-mail addresses.
  - A masking timeout drops the property.
- **Emission (`ClientTelemetryWriter.cs`, `ClientTelemetryLog.cs`).** The writer logs under the
  `Tellma.ClientTelemetry` category.
  - The batch scope holds `Subject`, `UserAgent`, `ClientVersion`, `ClientOutdated`, `ClientTabId`,
    `ClientTenantId` (when non-null) and `tellma.deployment.id`.
  - Each item's scope holds:
    - `ClientAt`: `At + (received − SentAt)`, as an invariant `"O"` string;
    - the kept properties, with `route`, `pageKind` and `sampleRate` renamed to `ClientRoute`,
      `ClientPageKind` and `SampleRate`;
    - on error items, `source`, `kind`, `code`, `status`, `fingerprint`, `stack`, `message` and
      `recentTraceIds` renamed to `ErrorSource`, `ErrorKind`, `ErrorCode`, `Status`, `Fingerprint`,
      `Stack`, `Message` and `RecentTraceIds` (`errorClass` is the message's own `ErrorClass`);
    - `DroppedProperties`, when properties were dropped.
  - Events and timings use `LoggerMessage.Define` with the template
    `{microsoft.custom_event.name}`. CA1727 is suppressed with a justification, because the
    attribute's name is fixed and dotted.
  - Errors use `[LoggerMessage]` at Warning: `Client error {ErrorClass} on {ClientRoute}`, with
    `(none)` for a missing value.
  - The drop record (Information, `Client telemetry dropped {Count} items`) carries `DroppedKind`,
    `DroppedName` and `DroppedTime` in its scope.
  - An item with a valid trace id is logged while a `new Activity("Tellma.ClientTelemetry.Item")`
    is current, W3C, parented to `(TraceId, random span id, flags None)`. It is disposed after the
    record, and `Activity.Current` is restored explicitly, because stopping an activity with a
    remote parent leaves none current.
- **Counters (`ClientTelemetryMetrics.cs`, internal).** `tellma.client.errors` (source, kind) and
  `tellma.client.requests.slow` (outcome) live on the `Tellma.Core.AspNetCore` meter.
  - A tag value is taken from its `FrozenSet` via `TryGetValue`, so the tag is always the set's own
    string instance, never the client's. The test checks this with `Assert.Same`.
  - An absent `kind` tags `none`. Any other value outside its set, or any value that is not text,
    tags `other`.
  - The error-kind set is held to the client's `TmApiErrorKind` union: the test reads
    `tm-api-error.ts`, which the test csproj links.
- **Alerts.** `infra/monitoring/client/` holds `client-errors.kql` (render and global errors more
  than 25 in 15 min) and `slow-requests.kql` (more than 50 in 15 min), with a README. They are
  cross-checked by `ClientAlertQueryTests`.
- **Registration.** `ClientTelemetryMetrics` and `ClientTelemetryWriter` are singletons in
  `AddTellmaAspNetCore`.

### Client batch shape against PC-113's pipeline (orchestrator check)

`tm-telemetry-pipeline.ts`'s batch matches §6.1 and the relay. No mismatch found.

- **Version.** `version` is `metadata.distribution.version`, the same value as the
  `Tellma-Client: web/<version>` header.
- **Tab id.** `tabId` is `crypto.randomUUID()`: 36 characters, which pass `^[A-Za-z0-9_-]{8,40}$`.
  The relay tests use a UUID tab id for this reason.
- **Tenant.** `tenantId` is a number, or null on tenantless pages.
- **Times.** `sentAt` and `at` are `toISOString()` (milliseconds, `Z`), which TellmaJson's offset
  converter accepts.
- **Items.** A batch carries at most 100 items in at most 16 KB, under the relay's 32 KB.
- **Property values.**
  - Strings are at most 64 characters, under the relay's 128.
  - `message` is at most 200 characters (relay: 256) and `stack` at most 4,096 (relay: 4,096).
  - `recentTraceIds` is three ids comma-joined, 98 characters.
  - The error properties' keys are exactly the ones §6.4 renames.
- **Error kinds.** `TmApiErrorKind` equals the server's closed set, and a test enforces it.

### Deviations

1. **A batch without `sentAt` is refused `400`.** The §6.2 table has no row for it. Skew correction
   and the time check both need it, and a missing member reads as `default`.
2. **Message and stack caps and masks apply to any item.** The `message` 256 and `stack` 4,096 caps
   and the backstop masks follow the §6.2 table literally, so they apply to any item's `message` or
   `stack` key. §3.2 says only error items carry those keys. The error-extra renames (§6.4) apply to
   error items alone.
3. **The masks are non-backtracking ports.** They use a captured lead character in place of
   lookbehind and `\b`, so they are linear-time. A masking timeout drops the property, which the
   spec leaves unstated.
4. **Property drops are counted on the item.** Each item's record carries a `DroppedProperties`
   member. The drop record carries the per-reason item counts in its scope and is written only when
   items were dropped, as §6.2 says.
5. **`tellma.deployment.id` is a scope member on every relay record.** The host otherwise sets it
   only as a request-span tag, and the relay is untraced. §6.3 asks for it as a server dimension.
6. **`UserAgent` is capped at 512 characters,** to bound record size.
7. **The relay tests run in the unit tier.** They live in `Tellma.Core.AspNetCore.Tests`, as this
   project's other TestHost tests do; no database is involved. §13 and the checkpoint call them
   "integration".
8. **The exporter in the tests is a recording `BaseProcessor<LogRecord>/<Activity>`**
   (`TelemetryRecorder`), not `OpenTelemetry.Exporter.InMemory`. The watchlist notes that package is
   not in `Directory.Packages.props`. The recorder also snapshots each record, which a pooled
   `LogRecord` needs.

### Open risks

- Application Insights' mapping of `microsoft.custom_event.name` to `customEvents` depends on the
  Azure Monitor exporter (1.8.0). That is verified here only as far as the OpenTelemetry record:
  the attribute is a plain string, and the dimensions are raw strings, longs and ints.
- The dimensions reach OpenTelemetry as attributes because Serilog flattens dictionary scopes into
  event properties and forwards them (`writeToProviders`). `IncludeScopes` itself sees no scope on
  this path. The tests prove the attributes arrive. A change to the Serilog wiring would show up
  there.
- The drop record is Information, so a deployment's level filter on `Tellma.ClientTelemetry` can
  hide it together with the custom events.

### What to examine hardest

- `ClientTelemetryMasks` against the client's patterns: the lead-character rewrite, the ASCII word
  class, and URL-then-e-mail ordering (for example, `mailto:a@b.c` is masked as `<email>`, as on the
  client).
- `ClientTelemetryWriter.WriteItem`: activity parenting and restoring, the rename tables, and
  `ClientAt` arithmetic and formatting.
- `ClientTelemetryRelay.ReadAsync`: the bounded read loop, and the 413 and 400 mapping through
  `BadHttpRequestException`.
- The test `An_exporter_sees_custom_events_and_warning_traces_under_the_item_s_trace_and_no_span`:
  whether "no span" is proven well enough. It waits for a later probe request's span before
  asserting that no span carries the items' or the relay's trace ids.
