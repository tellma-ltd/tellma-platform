# PC-133: Save flow, error summary, server-error mapping, conflict/deletion dialogs and the leave guard

## Implementer notes

### What was built, and where

All client paths are under `client/projects/core/` unless noted.

**The save flow (spec 0031 §8.1–§8.3, §8.6, §8.7)**

- **`tellma-core/details/src/tm-details-save.ts`** (new, a lazy chunk of `./details`). One
  `TmDetailsSaveRun` per Save, which the controller loads with `import()` and prefetches as the
  record enters edit or create mode. Its steps:
  - The recorded errors and the summary clear (first, since fix 1, R1-5).
  - A file whose upload failed refuses the write (see Deviations); a clean edit with no upload in
    flight returns to view mode and sends nothing.
  - Uploads in flight run under `TmBusyOverlay` with "Finishing uploads…", in one run that the
    write's own run takes over with "Saving…" (fix 1, R1-7); a record whose mode changed
    meanwhile ends the Save.
  - `source.validate` problems are recorded on their
    nodes; Signal Forms' `submit` marks the tree touched and runs the action only while valid.
  - `beforeSave` runs on a structured clone of `ɵsaveBody()`; the body gets the base's
    `modifiedAt` (edit) or loses its key and stamp (create).
  - One write through `TmConfirmations.run` under the overlay ("Saving…"), with `beforeunload`
    armed only while it is in flight. The keys of the attempt that ended the loop are kept, so
    Overwrite resends them (§9.3).
  - Success (§8.3): remember the display names, clear the draft, cancel uploads, clear errors,
    `markStale({ tenantId, entity })`. An edit lands the read-back in view mode, resets the form,
    announces "Saved" and focuses Edit. A routed create remembers a `TmDetailsSnapshot` under the
    target's page-state key (the details URL or `createdUrl`) and navigates there with
    `replaceUrl` and state `{ tmSaved, tmPageFocus: false }`.
  - Failures (§8.6): `concurrency-conflict` → the conflict dialog; `not-found` on an update → the
    deletion dialog; `validation` → §8.5's mapping and the summary; anything else →
    `TmErrorPresenter.present(e, { kind: 'save', entity, retry? })`, with `retry` (save again) for
    `offline`/`outcome-unknown`, `unavailable` and `server`.
  - Telemetry: `tm.details.save` timing `{ mode: edit|create|clone, outcome, errors: 0|1-3|4+ }`,
    `tm.details.conflict` `{ choice, self }` (recorded by the dialog since fix 1, R1-9).
- **§8.5 mapping.** `#place` splits each path (`tmSplitErrorPath`), drops `entities[0]` (or uses
  the source's `errorSegments`), walks the form with `tmWalkErrorPath`, and records
  `{ segments, value, error }` in `record.errors`, which the platform schema's recorded-error rule
  (PC-130) reports while the node keeps that value. Root errors are listed, not recorded.
- **`tm-details-controller.ts`.** `save()` now guards, sets busy and delegates to the chunk;
  `#saveHost()` is the seam the chunk calls back through (announce, focus Edit, clear draft,
  present, navigate as the host's own navigation, leave clean, save again). `cancel()` clears the
  server errors and the summary and resets the form. A minimal snapshot restore: the routed
  page of a record whose fresh snapshot the tab remembers (read through the save chunk's
  `ɵtmRecallDetailsSnapshot`, taken when that chunk loads) lands it with no read, and announces
  "Saved" / focuses Edit when the opening navigation was the save's own (imperative, `tmSaved`).
  The leave guard registers here with the host's own navigations exempt (`#navigating`).

**The error summary (§8.4)**

- **`tm-details-summary.ts`** (new, in the save chunk). `tm-alert kind="error"` in the status strip
  (the frame renders it through `NgComponentOutlet`, first in the strip's order): the heading,
  focused (`tabindex="-1"`) on open, and Show problems (`aria-expanded`, `aria-controls`). The list
  drops over the band at most half its height, ten items then "and {n} more". Escape collapses
  and focuses the toggle, Tab past the last button collapses, activating an item collapses then
  runs it. Each item keeps a reserved "Fixed" box that shows a check once its error clears.
- **Items.** A registered field → button calling the field's `focus()`; a child row or cell →
  button that reveals the collection's tab/card (`TmDetailsCollectionPlace`, registered by
  `ɵtmHoldCollectionErrors` from `tm-child-grid` and `tm-child-files`), scrolls to it, waits for
  the grid's registration, then `reveal(rowId, { column })`; an unregistered field or the root →
  plain text.
- **Unvisited tabs.** When a problem has no registered field or collection, every
  `tm-details-tabs` is instantiated, the next render awaited, the form marked touched, and only
  then the summary opens.

**Dialogs and the leave guard (§9.1, §9.2, §11.3)**

- **`tm-details-dialogs.ts`** (eager, exported): `TmDetailsDialogs` (root) with `conflict`,
  `deleted`, `leave`, each loading **`tm-details-dialogs-body.ts`** (lazy) on first use:
  `TmConfirm.ask` alert dialogs with the other / self / no-author copy (relative time through
  `TmL10n.formatRelativeTime`), the deletion dialog's one Discard changes, and the leave dialog
  (Discard changes ghost, Stay primary and focused; Escape → stay).
- **`tm-leave-guard.ts`** (exported): `tmLeaveGuard({ dirty, busy?, discard? })` registers with
  the routed page's `ɵTmLeaveChecks` (no-op outside one): busy refuses, clean passes, dirty asks
  and records `tm.details.leave-guard { choice }`.
- **`tellma-core/src/routes/tm-page-focus.ts`.** An imperative navigation whose state carries
  `tmPageFocus: false` moves no focus, so the saved record's page keeps focus on Edit; a Back or
  Forward to that entry moves focus to the title (fix 1, R1-1).

**Strings, testing, docs**

- `tm.detailsSave` and `tm.detailsDialogs` English tables registered by their chunks; Arabic in
  `locale/tellma-locale-ar/details-strings` (the heading with Arabic plural categories).
- `tellma-core-testing`: `TmDetailsSummaryHarness`, `TmDetailsSummaryItemHarness`,
  `TmDetailsPageHarness.getErrorSummary()`.
- The rig (`tm-entity.testing.util.ts`) lets a test declare the customer's `details` (for
  `createdUrl`).
- READMEs: `tellma-core` (details section, strings section, entry-point table) and

**Tests**

- `details/src/tm-details-save.spec.ts` (new, 29 cases): edit 200 with stamp/Check/Saved/Edit
  focus/markStale/telemetry; clean Save sends nothing; create replacing the URL with the snapshot

- `tm-details-host.spec.ts`: fixtures fill the customer's required members; the "page left while

- `tm-route-host.spec.ts`: a navigation carrying `tmPageFocus: false` moves no focus.
- Acme e2e `specs/details-save.spec.ts`: edit + save (C-011), and a two-context conflict with

### Deviations

1. **A failed upload at Save.** The write is refused, the working copy and the other edits stay,
   the page says "Nothing was saved: a file didn't upload.", and the summary lists one item per
   failed file ("…: The file didn't upload. Try it again or remove it."), which shows Fixed once
   the file is tried again or removed. The spec does not say how Save treats a failed upload.
2. **`tmLeaveGuard` takes an optional `discard`**, run on Discard changes, so the host clears its
   draft as §11.3 says; the spec's signature has `dirty` and `busy` only.
3. **Chunking and string scopes.** The save flow and the summary are one lazy chunk of
   `./details` (`tm-details-save`), the dialogs' copy another (`tm-details-dialogs-body`); their
   strings are new scopes `tm.detailsSave` and `tm.detailsDialogs`.
4. **A minimal snapshot restore ahead of §13** (PC-135's scope) so a create lands on the new
   record with no request, as §8.3 requires.
5. **`tmPageFocus: false` navigation state** in the core primary's `TmPageFocus`: §8.3's "focus
   Edit" after a create conflicts with spec 0024 §4.4's focus move to the title on a path change.
6. **Conflict copy** names the author only when the server sends `modifiedAt` as well (the copy
   needs the time); otherwise the no-author copy.
7. **Root errors and the body's** are plain-text items that never show Fixed (they sit on no node).
8. **The error presenter is not awaited** by Save (its dialog awaits Try again), so busy ends at
   once and Try again can save again; a failed Reload in the conflict dialog is presented with
   kind `save`.
9. **Deletion dialog on a source page** (no search page): Discard changes ends the edit in place.
10. **The page turns inert when the write starts**, after the chunk resolves and the client checks
    pass, not in the click's frame; Save's pending state (the page action's `running`) is what
    shows in the click's frame (§10.1's trigger rule).
11. *Withdrawn in fix 1 (R1-2).* ~~Acme e2e on `chromium-ar` is skipped.~~ The Arabic project now
    runs the save flow as a fifth development principal that reads Arabic and holds customer Read
    and Save, an addition to spec 0018 §6.3's development principals.
12. **Budgets.** `./details` 22 → 22.5 kB (measured 22.42, from 21.90; within the spec's 23 and
    the 28.75 allowance); its lazy chunks are declared: `tm-details-save` 6.5 (measured 6.25),
    `tm-details-dialogs-body` 1 (measured 0.94). `@tellma/locale-ar/details-strings` 1 → 1.5 kB
    (measured 1.32; no spec figure), for the Arabic save and dialog strings. Core `.` measures
    54.69 of 55. Acme's `build:esproj`: `detailsRoute` 79.48 of 80 (78.65 after PC-130), initialJs
    238.44 (warn 238.5), searchRoute 104.03 of 110, corePrimaryFirstFrame 53.00 of 55. A first
    build gave `detailsRoute` 80.14 because the controller imported `@tellma/core/memory`; the
    snapshot recall now comes with the save chunk (only a Save remembers a snapshot, and the page
    state is per tab in memory), which keeps that entry point off the route. About 0.5 KB of
    `detailsRoute` is left for the checkpoints after this one.

### Open risks

- The leave guard's dialog runs inside `canDeactivate`; a second navigation while it is open is
  the router's to supersede (the dialog then answers into a cancelled navigation).
- `#reveal` waits on the child grid's registration through an effect; a grid that never loads
  (its chunk failing) leaves the activation pending until the record goes. Since fix 1 only a
  place a grid backs waits; the child files focus their row's control at once (R1-6).
- The "Saved" announcement after a create reads the opening navigation's state; a reload of that
  entry restores no state, so it says nothing (intended), but the snapshot restore is minimal
  until PC-135 adds scroll and stale rules.

### What reviewers should examine hardest

- `tm-details-save.ts` `#write`/`#failed`/`#conflict`: the confirmation keys carried into
  Overwrite, the `immediate` overlay after the dialog, and `#live()` checks after every await.
- `#place` and `#clientProblems`: path walking, the recorded values (taken before `beforeSave`),
  and the Fixed predicates.
- `#open`'s tab instantiation and touch ordering versus §8.4.
- The controller's `#snapshot`/`#params` interplay (a remembered fresh snapshot suppresses the
  read only for the generation it was computed at).
- `TmPageFocus`'s new opt-out in the core primary.

Findings:

**R1-1 (major) A Back or Forward to a record created in this tab moves no focus at all.**
`client/projects/core/tellma-core/src/routes/tm-page-focus.ts:75` reads
`lastSuccessfulNavigation()?.extras.state?.['tmPageFocus']`. The create's navigation stores
`{ tmSaved: true, tmPageFocus: false }` in that entry's `history.state`. On popstate, Angular's
`navigateToSyncWithBrowser` copies the restored state into `extras.state`
(`@angular/router/fesm2022/_router-chunk.mjs:4517-4525`, `extras.state = stateCopy`).
Scenario: create customer 9, open the search page, press Back. The navigation is a path change,
but `own` is true, so `#pending` stays false and focus is not moved to the title. The controller's
Edit focus (`tm-details-controller.ts:688`) runs only for `trigger === 'imperative'`, so nothing
takes focus. Focus is left on the removed page's element (the body). This breaks spec 0024 §4.4 for
every later visit to that history entry. The new `tm-route-host.spec.ts` case only checks the
imperative navigation.
Fix: honour the opt-out only for the navigation that carries it, for example
`navigation.trigger === 'imperative' && navigation.extras.state?.['tmPageFocus'] === false`. Add
the Back case to the route-host test: a navigation with the state, a navigation away, then
`location.back()`, and focus goes to the title.

**R1-2 (major) The Acme save e2e is skipped on chromium-ar.**
`distributions/acme/test/Tellma.Distro.Acme.E2E/specs/details-save.spec.ts:112-116`. Ruling in
point 1: in scope. Suggested shape:
- Add a fifth individual to `AcmeDevelopmentPrincipals` (`Individuals`) with a role that grants
  `acme.Customer` Read and Save (plus Currency Read for the edit form). For example, an "Arabic
  editor" in tenant 1, inserted by `AcmeSampleDataStep.RolesAsync` and the principals step.
- Update `SampleDataTests` for the extra role, permissions and principal.
- Add the principal to `ACME_ARABIC_READERS`, so `global-setup.ts` sets its language.
- Have the spec sign in as that principal when `lang === 'ar'`.
- Move the asserted copy (`'Saved'`, the dialog's title, its self copy, "Reload saved version",
  "Overwrite") into `ACME_TEXT` with the Arabic strings from `strings-details-ar.ts`.

The Sales role and `cast.user` stay as they are, so cold-deep-link's read-only assertion holds.

**R1-3 (major) Two §8.6 rows have no harness case, against this checkpoint's Done-when.**
`client/projects/core/tellma-core/details/src/tm-details-save.spec.ts` has no Save that a
confirmation Cancel declines. That case would pin: edit mode kept, one write sent, nothing more
sent, the draft kept, and `tm.details.save { outcome: 'declined' }` (`tm-details-save.ts:281-284`).
Every warning test chooses Continue. It also has no 422 whose items are `blob-rejected` (for
example `Blob.NotAttachable` at `entities[0].imageId`) landing on the image field as "This file
expired. Choose it again.", with its summary item. The `blob-rejected` cases in
`tm-details-host.spec.ts:944` and `tm-child-files.spec.ts:343` are upload-time refusals, not a
save's 422.
Fix: add both cases to the save spec.

**R1-4 (major) "A busy one refuses with history intact" is not pinned.**
`client/projects/core/tellma-core/details/src/tm-details-host.spec.ts:1095-1113` refuses an
imperative `navigateByUrl('/17')` and checks `Router.url`. A refused Back is the case that can
lose history: the router has to restore the index under `canceledNavigationResolution:
'computed'`. Nothing exercises a popstate while busy, or checks `Location` and the index after it.
Fix: open `/17`, then `/17/customers/5`, and edit. Hold the write and call `location.back()`.
Settle, then expect `Location.path()` to stay `/17/customers/5`. Answer the write, then call
`location.back()` again and expect `/17`, which shows the index never moved.

**R1-5 (minor) The upload-failure and clean-Save exits skip step 3's clearing, leaving a stale
summary and stale server errors.** `tm-details-save.ts:193-200`, `:212-218` and `#uploadFailed`
(`:480-498`) run before `#clear()` (`:223`). The controller's `#leaveClean`
(`tm-details-controller.ts:890`) clears neither `record.errors` nor `summary`.
- Scenario A: in a clean edit, pick an image whose upload fails (the model stays the base). Save
  shows the summary. Remove the file and Save again. The clean path returns to view mode with "Fix
  1 problem to save" still in the strip, and it stays into the next edit. §8.1 step 1 says a clean
  Save returns to view mode "as Cancel does", and Cancel removes the summary.
- Scenario B: a 422 records an error on Code, then an upload fails and the user saves. The new
  summary lists only the file, while Code keeps its old server error with no item. §8.5 step 4
  says "All server errors clear on the next Save".
Fix: call `#clear()` at the top of `run()`, before the upload check and the clean exits, or clear
the errors and the summary in `#leaveClean`.

**R1-6 (minor) A child-files row item waits forever for a grid that never registers.**
`tm-details-save.ts:701-714`. `#item` gives a row of any collection with a place a `#reveal`
activation. `tm-child-files` registers a place (`tm-child-files.ts:101`) but never
`registerCollection`, so `#until(... collections().get(name)?.ready())` never resolves. Each
activation shows and scrolls the section, then leaves an effect alive until the record goes, and
focus moves nowhere. This covers an `attachments[1].caption` 422 and the failed-upload items of
deviation 1 (`attachments.0.fileId`).
Fix: let the place say whether a grid backs it. For child files, focus the row's control (its
caption, else its remove button) after `#show`, or give `tm-child-files` a collection ref with a
`reveal`. Add a summary activation case on a child-files row.

**R1-7 (minor) "Finishing uploads…" and "Saving…" are two overlay runs, so the page unblocks
between them.** `tm-details-save.ts:206` settles the first run. That releases inert, returns focus
to the origin and drops the scrim. Client checks, `submit` and an async `beforeSave` then run on a
live page, and `#write` (`:272`) starts a non-immediate run. After an upload wait longer than
200 ms, the scrim vanishes and reappears 200 ms later, and edits typed in the gap are dropped when
the save lands. §8.1 step 5 says the label is "now" "Saving…", which reads as the same overlay.
Fix: hold one run across the whole Save with a signal label, or pass `immediate: true` to the
write's run when the uploads wait showed the scrim.

**R1-8 (minor) Summary and leave-guard rules without a test.** Deliverables in this checkpoint
with nothing that fails if they break:
- "and {n} more" past ten items (`tm-details-summary.ts:76-77`);
- Tab past the last button collapsing the list (`:323-329`);
- the list capped at half the band's height (`:333-336`);
- a client error's Fixed;
- the leave guard's Discard clearing the draft (deviation 2's reason). The test at
  `tm-details-save.spec.ts:841-847` checks only the navigation.
Fix: one case each, or extend the existing ones. For example, a 422 with 12 items; Tab from the
last item; `sessionStorage` empty after Discard.

**R1-9 (minor) `tm.details.conflict`'s `self` disagrees with the dialog, and a Save that ends at
the conflict after leaving logs no timing.** `tm-details-save.ts:337` sets `self` whenever
`modifiedById` matches. The dialog (`tm-details-dialogs-body.ts:69`) shows the self copy only when
`modifiedAt` is present too. So a conflict without a time logs `self: true` while showing the
no-author copy. Separately, `:339-341` returns without `#done`, so `tm.details.save` is not
recorded when the page goes while the dialog is open.
Fix: use one predicate, for example by exporting the dialog's decision or computing it in the
save, and call `#done('conflict')` on that exit.
