# PC-074: Save pipeline, persist and commit: assembly, post-check, read-back, re-entry, translation

## Implementer notes

### What was built

Spec 0015 §6.1 steps 7 to 10 for a stack's save. The `NotSupportedException` seam PC-072 left
after a passing validation is gone: a save now composes, sends, translates and commits.

- **Tenant-state verdict** (`Crud/PersistVerdict.cs`, `Crud/WriteFrames.cs`). Spec 0015 §5.1 runs it
  before the persist is composed:
  - A `Frozen` tenant refuses every persist (`tenant-frozen`).
  - A `ReadOnly` one refuses a mutation that does not allow the state (`tenant-read-only`), unless
    an open `WriteFrame` admits it (`AdmitsReadOnly`).
  - An API-action frame that does not admit it refuses, whatever the nested operation allows.
  - A tenantless (system) context passes.
  - `WriteFrames` is a scoped stack of frames that hosts push. Nothing pushes into it yet (see
    deviations).
- **Persist assembly** (`Crud/Save/SaveRun.Persist.cs`, `ComposePersistAsync`). There is one guarded
  `BatchPurpose.Persist` runner call under `QueryexProfiles.PipelineLimits`. Between the executor's
  prefix and suffix it composes, in this order:
  1. `DependsOn` for the tags the validation rounds' batches declared (`IBatchDependencies`),
     re-declared with `Rerun`.
  2. `IAccessGuards.ContributeLock`, when the stack's tables at any depth (`StackTableSet`) meet
     `core.Users`, `Roles`, `RoleMemberships` or `Permissions` and the context is not System.
  3. `batch.Save(entities, Concurrency)` under the stack's own authority (all of its tables, at
     every depth).
  4. The service's `ContributeAsync`, then each `IPersistEffect<T>` in registration order. These
     run inside a `ComposeFence` and append through a `RecordingBatch`.
  5. `SaveOptions.OnPersist`, once, through its own `RecordingBatch`, under the caller's authority.
  6. `ContributeInvariants`.
  7. Under a `Filtered` Save grant, the post-check: `batch.Assert` over the saved ids' key set
     (`@save{n}_saved`), with the filter, expecting `roots.Count`, raising `RowSecurity` (50403).
  8. The read-back: `DetailsPlanner.Compose(..., handle.SavedIds, ...)` inside the transaction.
     Without `ReturnEntities`, the result is ids only.
- **Write authority** (`Data/Batches/IBatchAuthority.cs`, `DataBatch.cs`). The batch now carries
  the set of stack-owned tables its current appender may write (`CallerAuthority` /
  `Authorize`). An append whose declared writes meet a table that `IStackTableOwners` assigns to
  another stack is refused at append with `InvalidOperationException`. The pipeline widens the
  authority to the stack's tables for the emitter and narrows it back to the caller's for
  `OnPersist` and the invariants.
- **Recording view and replay** (`Data/Batches/RecordingBatch.cs`).
  - Every append (`Sql`, `Read`, `Rows`, `AddRead`, `Assert`, `DependsOn`, `OnCommitted`,
    `NotifyAsync`, `Enqueue`, `Withdraw`) reaches the inner batch and is recorded.
  - `Execute`, `TransactionMode`, `Limits` and `Composer` are refused (`InvalidOperationException`).
  - `Seal()` closes the recording.
  - `Replay(batch)` re-appends into a recomposed batch. Each batch-local name must come out the
    same, and a cached result a participant read must answer alike; otherwise it throws
    `StaleContextException`.
  - `JobQueue.Enqueue` and `Notifier.Notify`/`Withdraw` recognise a recording view and record
    themselves, so a recomposed persist enqueues and notifies again.
- **Re-entry** (`RevalidateAsync`, `Access/RecomposeLog.cs`, `GuardedBatchRunner.cs`). The guarded
  runner now records why it re-entered a compose (`RecomposeCause`: permissions, settings,
  entity, guard) in the scope's `RecomposeLog`, and the frame `CrudOperations` opens around every
  CRUD operation counts it once (`tellma.crud.stale_context.reruns`, `crud.tag`), so a query, a
  details read, a validation round and a persist are all counted. The re-entry then works as
  follows:
  1. A served tag that the fresh snapshot moved past raises `StaleContextException`.
  2. The validators re-run in memory with `ContextLoader.AnswerOnly()`. A load the rounds did not
     serve raises `StaleContextException` through the fence.
  3. The re-run's `ConfirmationFrame` is unaudited, so confirmations are neither counted nor
     logged twice.
  4. A new error raises `ValidationException`, and a new unconfirmed warning raises
     `ConfirmationRequiredException`.
  5. The save grant is re-decided for the fresh user; `Denied` raises `ForbiddenException(NoGrant)`.
  6. The pipeline's own statements are recomposed, and the recordings are replayed.

  No participant is ever called twice. The read-back's details hooks are rebuilt (deviation 17).
- **Translation** (`Crud/PersistFailures.cs`), covering spec 0015 §14.2:

  | Failure | Becomes |
  | --- | --- |
  | Conflict rows | `ConcurrencyException`, with `ModifiedByName` in the content language and the primary name as fallback |
  | Every conflict row missing | `NotFoundException` |
  | Post-check | `ForbiddenException(OutsideFilter)` |
  | `50404` | `NotFoundException` with the batch's missing ids |
  | `50422` and `50600`–`50699` | `ValidationException` at the root with the assertion's code; `Blob.NotAttachable` with `reason=persist` |
  | Tree fence | `Tree.Cycle` / `Tree.TooDeep` at the root |
  | Unique index on the stack's tables | `Unique` at the one payload row carrying the value, else at the root with a `property` argument |
  | Blob-reference unique index | `Blob.NotAttachable` |
  | Open-assignment unique index | `Assignments.Concurrent` |
  | FK 547 a write raised (`FOREIGN KEY`) on the stack's tables | `Fk.NotFound` the same way, with arguments `entity` and `id` |
  | FK 547 a delete raised (`REFERENCE`) on any table referencing a row the child synchronisation deleted | `Fk.InUse` with `entity` and `property` (the referencing ones), at the one payload collection that dropped rows of the referenced entity, else at the root |
  | FK 547 whose message tells no side | `Fk.InUse` when the synchronisation deleted rows the key references, else `Fk.NotFound` |
  | Anything else | Passes through |

  The side of a 547 is read in `DataErrors` (`ForeignKeyViolationException.Conflict`): the
  message's `FOREIGN KEY` or `REFERENCE` keyword, else the conflict's table. Conflicts are metered
  by kind (`stamp`, `missing`, `cycle`). For an ambiguous commit, `Committed` re-issues a plain
  `Read` over the final ids (a bound key table, so the caller's Read filter drops none): the roots'
  `ModifiedAt`, and the details read only under `ReturnEntities`. A failing read is logged
  (`ProvenCommitReadFailed`) and the save answers its ids alone (deviation 20); the post-commit
  phase runs either way, with the default stamp then. Any other ambiguous verdict becomes
  `DependencyUnavailableException("database", 1 s)`.
- **Post-commit phase** (`AfterCommitAsync`). It runs after the commit, before the response is
  assembled, and whatever the caller's token says:
  1. `tellma.crud.save.entities` (rows at every depth, with `crud.source` and lane).
  2. `tellma.crud.concurrency.overrides` when an updated root's stored stamp differed from the one
     the caller echoed.
  3. The service's `AfterCommitAsync`, then each effect's.

  A failure, including a participant's `OnCommitted` callback, is logged (`PostCommitFailed`, with
  the trace id) and metered (`tellma.crud.effects.failures`, `crud.effect` = the component's type
  name). It never changes the response.
- **README.** `src/core/Tellma.Core/README.md` describes the save pipeline through steps 7 to 11.
  ARCHITECTURE.md holds no persist-pipeline detail that disagrees, so it is unchanged.

### Deviations

1. `IStackTableOwners` keeps its default registration (`NoStackTableOwners`); the real owner map
   belongs to the write-frames and enlisted-writes checkpoint. The append-time refusal is wired
   through the batch's caller authority and tested against a scripted owner map, but in a running
   host no table is owned yet, so a caller's `OnPersist` write into another stack's table is not
   refused there. The integration suite writes
   `core.Jobs` from `OnPersist` for this reason, under a `TELLMA0006` pragma.
2. `WriteFrames` is a seam with no producer: the API-action invoker, the job runner and
   provisioning push frames in later checkpoints. Until then, a `ReadOnly` tenant refuses every
   save.
3. Any admitting frame on the stack admits a nested persist. An API-action frame that does not
   admit refuses outright. Spec 0015 §5.1 does not say how nested frames combine; I chose the
   strictest reading for API actions.
4. The delete-only translation rows (`50413`/`50428`, and `Fk.InUse` for a delete operation's
   own rows) are left to the deletes checkpoint, which owns their batches. A save's child
   synchronisation delete does map to `Fk.InUse` (deviation 18).
5. A unique or FK violation whose value no single payload row carries is reported at the root with
   a `property` argument (the spec says only "at the root").
6. `Assignments.Concurrent` is a local constant in `PersistFailures`, because `ValidationCodes`
   carries no such member and Abstractions is outside this checkpoint.
7. The FK translation's `id` argument is widened to `long` (`PayloadRows.ValueOf`), matching the
   other key-valued arguments.
8. The re-run's confirmation frame is unaudited, so a confirmation is counted and logged once per
   save, not once per entry.
9. `tellma.crud.stale_context.reruns` is fed by the runner's new `RecomposeLog`, not by the runner
   itself. The frame `CrudOperations` opens around every CRUD operation counts each re-entry once,
   with its cause; a nested operation's re-entries are counted by the outermost frame.
10. No validation-round composer declares `entity:*` tags of its own yet. The persist re-declares
    whatever a round's batch declared (`IBatchDependencies`, which `DataBatch` and the scripted
    double implement), so the code is live and unit-tested, but a running host adds nothing until a
    round declares one.
11. The `ComposeFence` refuses a participant's own round trip with `InvalidOperationException` (an
    authoring bug). A validator's round trip during the in-memory re-run is refused with
    `StaleContextException`.
12. A `Save` role grant implies reading with the same filter (spec 0014 §5.2), so a caller whose
    Save comes from a role grant reads back what it saves; a unit test pins a Save-only role
    caller reading back its rows. A bespoke criterion contributes only to its own action or `*`,
    so a caller holding Save through a criterion alone is Denied Read: its `ReturnEntities` save is
    refused with `ForbiddenException(Read, NoGrant)` while the persist is composed, before any
    round trip, and nothing is written (it fails closed); the same save with
    `ReturnEntities = false` commits. A unit test pins both. Failing closed is the interim ruling
    (D-116); whether the read-back, which reads only the saved ids, should run without a Read
    decision is Ahmad's question.
13. On an ambiguous `Committed` verdict, the stamp for the post-commit phase comes from a plain
    `Read` over the final ids, not under the caller's Read filter, and the post-commit phase runs
    even when that read fails (with the default stamp; deviation 20). The lost batch's
    `OnCommitted` callbacks do not run (the executor never read its results), so the job wake-up
    and `inbox.changed` are missed on this path, and a participant's recorded `BatchResult` stays
    unanswered.
14. A participant's `OnCommitted` callback is contained and metered like a post-commit failure,
    rather than surfacing through the batch.
15. `tellma.crud.save.entities` counts rows at every depth. `tellma.crud.concurrency.overrides`
    counts a committed `Override` save once when an updated root's stored stamp (its before image)
    differed from the stamp the payload echoed.
16. Test-plan gaps:
    - `MaxRowsPerSave` and `[MaxChildren]` are refused before any round trip by the validation
      step's `SaveShape`, so no database is involved; they are pinned at unit tier, depth one in
      `AttributeWalkerTests` and depth two through the pipeline in `SaveOperationTests`.
    - `Fk.NotFound` under the target's Read filter is the validation step's round-1 check and is
      pinned at unit tier (a hidden target). The persist-side FK race deletes the target instead.
    - Stamp override under both concurrency modes is pinned at unit tier.
17. A recomposed `ReturnEntities` save, and the proven-commit read, call the service's
    `ContributeDetails` and every `IDetailsContributor<T>` again. These read-side hooks are pure
    and only compose reads, so they are rebuilt under the fresh grants with the pipeline's own
    statements (spec 0015 §5.1 step 2 lists the read-back among them). No persist participant is
    called twice.
18. A 547 that a delete raised is translated as the delete row's `Fk.InUse`, since only the
    save's child synchronisation deletes. The side comes from the server's message, which
    `DataErrors` reads into `ForeignKeyViolationException.Conflict` (a public member the data
    layer's exception gains): a write conflicts with the `FOREIGN KEY` constraint and a delete with
    the `REFERENCE` one, and without either keyword a conflict table other than the constraint's
    own is a write's. When the message tells no side (the constraint's own table, which a delete
    and a self-referencing write share), a key whose referenced entity had rows dropped is
    `Fk.InUse`, since round trip 1 proved every written reference and a missing target needs a
    delete in the window; otherwise `Fk.NotFound`. Spec 0015 §14.2's save row does not cover a
    delete the save itself makes; this is flagged for Ahmad (D-115).
19. A re-entered persist re-decides the Save grant (Denied refuses) and recomposes the post-check
    and the read-back under the fresh grants, but keeps what round trip 1 decided under the grants
    that moved: the before images read under the old Read filter (hidden equals missing), the Save
    pre-check over the stored rows, and the references read under each target's old Read filter.
    So when an administrator narrows a Save or Read filter between a save's two round trips, an
    update that round trip 1 passed commits if its new image is inside the narrowed Save filter,
    where a fresh request would be refused at the pre-check, and with `ReturnEntities` it reads back
    rows the caller may no longer read. Spec 0015 §5.1 says no row is written under a rule that
    moved, but its re-entry steps list only the persist batch's statements, and the pre-check is
    not one of them: the code follows the letter and the gap is the spec's. Deferred to the
    orchestrator (D-116). A candidate fix keeps round trip 1's Read and Save decisions and raises
    `StaleContextException` on a re-entry with update roots or checked references when a fresh
    decision differs; it adds a raise site §5.1 does not list, so it is not built.
20. A read after a proven commit that fails (a timeout, or the details plan refusing because the
    fresh user's Read is denied) is logged as `ProvenCommitReadFailed` (a warning, with the trace
    id), and the save answers its ids alone: `Entities` is empty even under `ReturnEntities`, where
    spec 0015 §6.9 makes it parallel to `Ids`. The post-commit phase runs on the default stamp.
    §8 does not say what a failed re-issued read answers. Any error here would answer a committed
    save with something a caller retries (a create retried inserts its rows again), so the review's
    `DependencyUnavailableException` under `ReturnEntities` is not used either; the caller reloads
    the ids it was given.

### Open risks

- **Blocking call in a test.** `SavePersistTests.Meanwhile` blocks the composing thread on another
  connection's commit (`Task.Run(...).GetAwaiter().GetResult()`). It is test-only and deadlock-free
  under xUnit v3, but it is the one sync-over-async in the suite.
- **Abort test timing.** The abort test cancels one second after compose, inside a three-second
  `WAITFOR`. On a very slow agent, a send that takes longer than a second would make it fail with
  `OperationCanceledException`, which is correct behaviour but a false failure of the test.
- **Replay equality.** Replay compares batch-local names and cached answers only. A participant
  that branches on wall-clock time or randomness would replay its first decisions, which is the
  intended semantics but not checked.

### What reviewers should examine hardest

1. `ComposePersistAsync`'s authority switching: emitter under the stack's tables, `OnPersist` and
   invariants under the caller's. Also the lock and invariants guard: security tables and
   `!IsSystem`.
2. `RevalidateAsync`: that nothing the first entry raised or logged repeats, and that the stale
   checks cover a moved served tag and an unserved load.
3. `PersistFailures`: the unique and FK attribution to the one carrying row (`OnlyCarrier`), and the
   pass-through of anything not on the stack's tables.
4. The post-commit containment: no exception escapes after the commit, and the cancellation token
   is not observed once the persist is sent.
5. `RecordingBatch.Replay`'s name-equality check, and `JobQueue`/`Notifier` recording themselves
   through it.

**R1-1 (major): on a commit the probe proved, the plain read can turn the committed save into an
error, skip its post-commit phase, or return the wrong ids.**
`src/core/Tellma.Core/Crud/Save/SaveRun.Persist.cs:96-100` and `:330-358`;
`src/core/Tellma.Core/Crud/Details/DetailsPlanner.cs:119-123`;
`src/core/Tellma.Core/Crud/Details/DetailsComposition.cs:172-215`
- **What the code does.** `AfterProvenCommitAsync` always runs a full details `Read` through
  `DetailsPlanner.Compose`. It runs whether or not `ReturnEntities` is set. It passes
  `idsSource: null`, so the read is filtered by the caller's Read filter. Only after that read
  succeeds does it call `AfterCommitAsync`.
- **Failure scenarios.**
  1. *A caller who holds Save but not Read.* An import chunk with `ReturnEntities = false` commits,
     and its connection drops around `COMMIT`. `Compose` throws
     `ForbiddenException(Read, NoGrant)`. The caller gets a 403 for a save that committed, and
     neither the hook's nor any effect's `AfterCommitAsync` runs. Deviation 12 guards only
     `ReturnEntities` saves, and only before the send. No test covers deviation 12 either.
  2. *The read itself fails.* This path is entered because a connection just dropped, so a second
     drop or exhausted retries is likely. The exception reaches the caller (503 or 500), and the
     post-commit phase is skipped. §8 says the pipeline "proceeds to post-commit effects".
  3. *A row outside the caller's Read filter.* A caller whose Save grant is wider than its Read
     filter saves such a row. `Complete()` keeps only the visible rows, so `EntitiesResult.Ids`
     lacks that id. §6.9 requires `Ids` in input order with every final id. The normal read-back
     returns it, because it reads through the saved-ids table.
  4. *Commit callbacks.* The executor throws `DataAccessAmbiguousException` before it runs any
     `OnCommitted` callback (`DataExecutor.cs:236-249`). So on this path the batch's callbacks
     never run: the job wake-up, `inbox.changed`, and the participants' own callbacks. §6.1 step 9
     names them as part of the post-commit phase. The `RecordingBatch` proxies also never
     complete, so a participant that reads a `BatchResult.Value` in `AfterCommitAsync` throws. That
     throw is contained but metered as an effect failure.
- **Suggested fix.**
  - Without `ReturnEntities`, skip the details read. Take the stamp from a narrow unfiltered read
    of `ModifiedAt` over the final ids, or accept an unknown stamp.
  - With `ReturnEntities`, read the final ids as the normal read-back does, so `Ids` stays
    complete.
  - Run `AfterCommitAsync` even when the read fails: run it first, or in a `finally`.
  - Either run or document the `OnCommitted` callbacks on this path, and document the proxies
    that stay incomplete.
  - Add unit tests for the Save-only caller and for a failing read on this path, and one for
    deviation 12.

**R1-2 (major): the access-guard wiring, a deliverable, has no test.**
`src/core/Tellma.Core/Crud/Save/SaveRun.Persist.cs:166-170` and `:203-207`
- **What is missing.** The host registers `NullAccessGuards`, so nothing exercises these lines.
  No unit test pins any of the following:
  - when the guards are called: a stack table, at any depth, among `core.Users`, `Roles`,
    `RoleMemberships` and `Permissions`, and a context that is not System;
  - `ContributeLock` before the emitter's first statement;
  - `ContributeInvariants` after `OnPersist` and before the post-check and the read-back;
  - that a System scope skips both calls;
  - that a recomposed persist calls both again.
- **Failure scenario.** A refactor moves `ContributeInvariants` before the replayed `OnPersist`, or
  checks only the root table. The suite stays green, and spec 0018's `Role` save (whose members
  live in a child table) loses its last-administrator invariant.
- **Suggested fix.** Add a recording `IAccessGuards` double to the rig. Add a scripted stack whose
  child table maps to `core.RoleMemberships`. Assert the lock's and the invariants' positions
  relative to the emitter, `OnPersist`, the post-check and the read-back, and assert that a System
  scope calls neither.

**R1-3 (minor): the override counter does not do what deviation 15 says.**
`src/core/Tellma.Core/Crud/Save/SaveRun.Persist.cs:371-374`
- **What the code does.** It counts every committed `Override` save that holds at least one
  existing root, whether or not any stored stamp differed.
- **What deviation 15 says.** It "counts only committed updates whose stored stamp differed".
- **Testing.** The unit test covers only a stale override, so it cannot tell the two readings
  apart.
- **Suggested fix.** Choose one rule. To match deviation 15, compare each updated root's before
  image `ModifiedAt` with its payload stamp. To keep the code, correct deviation 15 and the
  README. In either case, add an override with a matching stamp to the test.

**R1-4 (minor): the `entity:*` re-declaration and the moved-tag stale check never run in any
test.**
`src/core/Tellma.Core/Crud/Save/SaveRun.Persist.cs:160-163`, `:279-283` and `:437-451`
- **Why unit tests cannot reach it.** `Served` returns at once for any batch that is not a
  `DataBatch`. Every unit test runs on `ScriptedBatch`, so `_served` is always empty there.
- **Why integration tests cannot reach it.** Per deviation 10, no validation round declares an
  `entity:*` dependency.
- **Effect.** The `DependsOn` re-declaration and the `StaleContextException` for a moved served
  tag are unreachable, yet the README describes them as working. When a round first declares a
  list tag, this code goes live untested. A mistake in it would show either as a `50412` loop or
  as a stale list that is silently accepted.
- **Suggested fix.**

**R2-4 (minor): deviation 18 rests on a false premise, and the ambiguous case answers with the less

`src/core/Tellma.Core/Crud/PersistFailures.cs:201-224`;
`src/core/Tellma.Core/Data/Batches/DataErrors.cs:249-251` and `:283-293`

- **Failure scenario.** A stack holds `Lines` and `Allocations`, with `Allocations.LineId`

- **Judgement on R1-7.** Mapping the child synchronisation's 547 to `Fk.InUse`, with `entity` and
