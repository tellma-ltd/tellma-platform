# PC-074: Save pipeline, persist and commit: assembly, post-check, read-back, re-entry, translation

## Implementer notes

### What was built

Spec 0015 §6.1 steps 7 to 10 for a stack's save. The `NotSupportedException` seam PC-072 left
after a passing validation is gone: a save now composes, sends, translates and commits.

- **Tenant-state verdict** (`Crud/PersistVerdict.cs`, `Crud/WriteFrames.cs`). Spec 0015 §5.1 runs it
  before the persist is composed:
  - A `Frozen` tenant refuses every persist (`tenant-frozen`).
  - A `ReadOnly` one refuses a mutation that does not allow the state (`tenant-read-only`), unless
    an open `WriteFrame` admits it (`AdmitsReadOnly`).
  - An API-action frame that does not admit it refuses, whatever the nested operation allows.
  - A tenantless (system) context passes.
  - `WriteFrames` is a scoped stack of frames that hosts push. Nothing pushes into it yet (see
    deviations).
- **Persist assembly** (`Crud/Save/SaveRun.Persist.cs`, `ComposePersistAsync`). There is one guarded
  `BatchPurpose.Persist` runner call under `QueryexProfiles.PipelineLimits`. Between the executor's
  prefix and suffix it composes, in this order:
  1. `DependsOn` for the `entity:*` tags the validation rounds were served under.
  2. `IAccessGuards.ContributeLock`, when the stack's tables meet `core.Users`, `Roles`,
     `RoleMemberships` or `Permissions` and the context is not System.
  3. `batch.Save(entities, Concurrency)` under the stack's own authority (all of its tables, at
     every depth).
  4. The service's `ContributeAsync`, then each `IPersistEffect<T>` in registration order. These
     run inside a `ComposeFence` and append through a `RecordingBatch`.
  5. `SaveOptions.OnPersist`, once, through its own `RecordingBatch`, under the caller's authority.
  6. `ContributeInvariants`.
  7. Under a `Filtered` Save grant, the post-check: `batch.Assert` over the saved ids' key set
     (`@save{n}_saved`), with the filter, expecting `roots.Count`, raising `RowSecurity` (50403).
  8. The read-back: `DetailsPlanner.Compose(..., handle.SavedIds, ...)` inside the transaction.
     Without `ReturnEntities`, the result is ids only.
- **Write authority** (`Data/Batches/IBatchAuthority.cs`, `DataBatch.cs`). The batch now carries
  the set of stack-owned tables its current appender may write (`CallerAuthority` /
  `Authorize`). An append whose declared writes meet a table that `IStackTableOwners` assigns to
  another stack is refused at append with `InvalidOperationException`. The pipeline widens the
  authority to the stack's tables for the emitter and narrows it back to the caller's for
  `OnPersist` and the invariants.
- **Recording view and replay** (`Data/Batches/RecordingBatch.cs`).
  - Every append (`Sql`, `Read`, `Rows`, `AddRead`, `Assert`, `DependsOn`, `OnCommitted`,
    `NotifyAsync`, `Enqueue`, `Withdraw`) reaches the inner batch and is recorded.
  - `Execute`, `TransactionMode`, `Limits` and `Composer` are refused (`InvalidOperationException`).
  - `Seal()` closes the recording.
  - `Replay(batch)` re-appends into a recomposed batch. Each batch-local name must come out the
    same, and a cached result a participant read must answer alike; otherwise it throws
    `StaleContextException`.
  - `JobQueue.Enqueue` and `Notifier.Notify`/`Withdraw` recognise a recording view and record
    themselves, so a recomposed persist enqueues and notifies again.
- **Re-entry** (`RevalidateAsync`, `Access/RecomposeLog.cs`, `GuardedBatchRunner.cs`). The guarded
  runner now records why it re-entered a compose (`RecomposeCause`: permissions, settings,
  entity, guard), and the pipeline counts it once (`tellma.crud.stale_context.reruns`, `crud.tag`). The
  re-entry then works as follows:
  1. A served tag that the fresh snapshot moved past raises `StaleContextException`.
  2. The validators re-run in memory with `ContextLoader.AnswerOnly()`. A load the rounds did not
     serve raises `StaleContextException` through the fence.
  3. The re-run's `ConfirmationFrame` is unaudited, so confirmations are neither counted nor
     logged twice.
  4. A new error raises `ValidationException`, and a new unconfirmed warning raises
     `ConfirmationRequiredException`.
  5. The save grant is re-decided for the fresh user; `Denied` raises `ForbiddenException(NoGrant)`.
  6. The pipeline's own statements are recomposed, and the recordings are replayed.

  No participant is ever called twice.
- **Translation** (`Crud/PersistFailures.cs`), covering spec 0015 §14.2:

  | Failure | Becomes |
  | --- | --- |
  | Conflict rows | `ConcurrencyException`, with `ModifiedByName` in the content language and the primary name as fallback |
  | Every conflict row missing | `NotFoundException` |
  | Post-check | `ForbiddenException(OutsideFilter)` |
  | `50404` | `NotFoundException` with the batch's missing ids |
  | `50422` and `50600`–`50699` | `ValidationException` at the root with the assertion's code; `Blob.NotAttachable` with `reason=persist` |
  | Tree fence | `Tree.Cycle` / `Tree.TooDeep` at the root |
  | Unique index on the stack's tables | `Unique` at the one payload row carrying the value, else at the root with a `property` argument |
  | Blob-reference unique index | `Blob.NotAttachable` |
  | Open-assignment unique index | `Assignments.Concurrent` |
  | FK 547 on the stack's tables | `Fk.NotFound` the same way, with arguments `entity` and `id` |
  | Anything else | Passes through |

  Conflicts are metered by kind (`stamp`, `missing`, `cycle`). For an ambiguous commit, `Committed`
  re-issues the read as a plain `Read` and continues to the post-commit phase. Any other ambiguous
  verdict becomes `DependencyUnavailableException("database", 1 s)`.
- **Post-commit phase** (`AfterCommitAsync`). It runs after the commit and whatever the caller's
  token says:
  1. `tellma.crud.save.entities` (rows at every depth, with `crud.source` and lane).
  2. `tellma.crud.concurrency.overrides` for a committed override of a stored row.
  3. The service's `AfterCommitAsync`, then each effect's.

  A failure, including a participant's `OnCommitted` callback, is logged (`PostCommitFailed`, with
  the trace id) and metered (`tellma.crud.effects.failures`, `crud.effect` = the component's type
  name). It never changes the response.
- **README.** `src/core/Tellma.Core/README.md` describes the save pipeline through steps 7 to 11.
  ARCHITECTURE.md holds no persist-pipeline detail that disagrees, so it is unchanged.

### Tests

- **Unit** (`Tellma.Core.Tests`):
  - `Crud/Save/SaveOperationTests.Persist.cs`:
    - assembly order and post-commit order;
    - `OnPersist` called once, and never on a validation failure;
    - a participant executing the batch or changing its mode is refused;
    - a stack-owned write is admitted from the hook and refused from `OnPersist` at append;
    - the filtered post-check, then `Forbidden`;
    - the read-back over the saved ids;
    - the verdict refusals and a Job frame admitting the persist;
    - re-entry: replay, the stale metric, a new load being stale, a new error, a new warning, and a
      revoked grant;
    - every translation row, including content-language naming, the ambiguous `Committed` and
      `Unknown` paths, and the post-commit failures and their metering.
  - `Crud/PersistVerdictTests.cs`: the verdict matrix.
  - `Data/Batches/RecordingBatchTests.cs`.
  - `SaveOperationTests.cs` was adapted: a passing save now persists. The warm create asserts one
    round trip.
- **Integration** (`Tellma.Core.IntegrationTests/Crud/SavePersistTests.cs`):
  - a warm create takes 1 round trip and an update takes 2, each returning its committed rows;
  - server-owned values and `IsActive` are ignored on update;
  - a stamp conflict naming its modifier, and a missing row, each written by a second connection
    in the window;
  - the unique race and the FK race against a second connection, each one 422;
  - `OnPersist` committing with the save, and a distribution's `THROW 50650` rolling both back;
  - a moved permissions tag recomposing once, with the hook called once and the job committed once;
  - a read-only tenant refusing;
  - a client abort mid-persist that still commits and returns its rows.

  `SavePipelineTests` now asserts the second (persist) round trip, the committed rows and a
  grandchild in the database.

### Deviations

1. `IStackTableOwners` keeps its default registration (`NoStackTableOwners`); the real owner map
   belongs to the write-frames and enlisted-writes checkpoint. The append-time refusal is wired
   through the batch's caller authority and tested against a scripted owner map, but in a running
   host no table is owned yet, so a caller's `OnPersist` write into another stack's table is not
   refused there. The integration suite writes
   `core.Jobs` from `OnPersist` for this reason, under a `TELLMA0006` pragma.
2. `WriteFrames` is a seam with no producer: the API-action invoker, the job runner and
   provisioning push frames in later checkpoints. Until then, a `ReadOnly` tenant refuses every
   save.
3. Any admitting frame on the stack admits a nested persist. An API-action frame that does not
   admit refuses outright. Spec 0015 §5.1 does not say how nested frames combine; I chose the
   strictest reading for API actions.
4. The delete-only translation rows (`50413`/`50428`, `Fk.InUse`) are left to the deletes
   checkpoint, which owns their batches.
5. A unique or FK violation whose value no single payload row carries is reported at the root with
   a `property` argument (the spec says only "at the root").
6. `Assignments.Concurrent` is a local constant in `PersistFailures`, because `ValidationCodes`
   carries no such member and Abstractions is outside this checkpoint.
7. The FK translation's `id` argument is widened to `long` (`PayloadRows.ValueOf`), matching the
   other key-valued arguments.
8. The re-run's confirmation frame is unaudited, so a confirmation is counted and logged once per
   save, not once per entry.
9. `tellma.crud.stale_context.reruns` is fed by the runner's new `RecomposeLog`, not by the runner
   itself, so the pipeline counts each re-entry once, with its cause.
10. No validation-round composer declares `entity:*` tags of its own yet. The tags that ride the
    persist's guard are those the rounds were served from the cache under (`FromCache`).
11. The `ComposeFence` refuses a participant's own round trip with `InvalidOperationException` (an
    authoring bug). A validator's round trip during the in-memory re-run is refused with
    `StaleContextException`.
12. A `ReturnEntities` save whose fresh user is denied Read is refused before the send.
13. On an ambiguous `Committed` verdict, the rows and the stamp for the post-commit phase come from a
    plain `Read` under the caller's Read filter.
14. A participant's `OnCommitted` callback is contained and metered like a post-commit failure,
    rather than surfacing through the batch.
15. `tellma.crud.save.entities` counts rows at every depth. `tellma.crud.concurrency.overrides`
    counts only committed updates whose stored stamp differed.
16. Test-plan gaps:
    - The tree-cycle race and the ambiguous commit are pinned at unit tier only, since neither can
      be provoked deterministically against a real server.
    - `MaxRowsPerSave` and `[MaxChildren]` at depth two are refused before any round trip, by the
      validation step's `SaveShape`; they stay pinned at unit tier (`AttributeWalkerTests`, depth
      one).
    - `Fk.NotFound` under the target's Read filter is the validation step's round-1 check and is
      pinned at unit tier (a hidden target). The persist-side FK race deletes the target instead.
    - Stamp override under both concurrency modes is pinned at unit tier.

### Open risks

- **Blocking call in a test.** `SavePersistTests.Meanwhile` blocks the composing thread on another
  connection's commit (`Task.Run(...).GetAwaiter().GetResult()`). It is test-only and deadlock-free
  under xUnit v3, but it is the one sync-over-async in the suite.
- **Abort test timing.** The abort test cancels one second after compose, inside a three-second
  `WAITFOR`. On a very slow agent, a send that takes longer than a second would make it fail with
  `OperationCanceledException`, which is correct behaviour but a false failure of the test.
- **Replay equality.** Replay compares batch-local names and cached answers only. A participant
  that branches on wall-clock time or randomness would replay its first decisions, which is the
  intended semantics but not checked.

### What reviewers should examine hardest

1. `ComposePersistAsync`'s authority switching: emitter under the stack's tables, `OnPersist` and
   invariants under the caller's. Also the lock and invariants guard: security tables and
   `!IsSystem`.
2. `RevalidateAsync`: that nothing the first entry raised or logged repeats, and that the stale
   checks cover a moved served tag and an unserved load.
3. `PersistFailures`: the unique and FK attribution to the one carrying row (`OnlyCarrier`), and the
   pass-through of anything not on the stack's tables.
4. The post-commit containment: no exception escapes after the commit, and the cancellation token
   is not observed once the persist is sent.
5. `RecordingBatch.Replay`'s name-equality check, and `JobQueue`/`Notifier` recording themselves
   through it.
