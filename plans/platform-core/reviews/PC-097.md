### Deviations

- **D-1. `JobRequestList.OwnerId` is `bigint`, not `int`.** Job entities may be keyed by `long`, as the fixture's `Shipment` is. A 32-bit owner id would truncate or refuse their rows. Int-keyed owners widen losslessly.
- **D-2. `LOCK_ESCALATION` rides `UseTableTypes`.** It is implemented through an annotation-provider subclass that uses EF's internal `SqlServerAnnotationProvider`. The subclass is quarantined in the adapter file and pinned by a test of its base type and constructor. There is no public hook through which the differ can surface a custom table option.
- **D-3. Executor whitelist of `EXEC sys.sp_sequence_get_range`: not applicable.** The executor has no statement whitelist or analyzer to extend. The statement composes `sp_sequence_get_range` the way `IdAllocator` already does.
- **D-4. Log events:**
  - `JobNudgeFailed` (Warning) is new; it is logged when a wake subscriber throws.
  - The `jobs.handlers` warning reuses `SchedulerHandlerUnknown` from the spec's list.
- **D-5. `Entity<Job>()` and `Entity<Schedule>()` are contributed without services.** `JobService` and `ScheduleService`, and Core's own built-ins and handlers (`core.notification-delivery` and the others), land in their own checkpoints.
- **D-6. New constants:** `JobLimits.MaxHandlerArgumentsBytes`, `JobLimits.MaxCronExpressionLength` and `ReservedSqlNames.StatementNames.Count`. They name limits the spec states only in prose or SQL.
- **D-7. The check that an entity handler's entity is mapped runs in `jobs.handlers`, not in the realizer.** The tenant model exists only at the realised gate, after every realizer has run.
- **D-8 (revised in review 1). The "null or terminal `JobId`" rule is enforced in SQL, not on the in-memory member.** The statement text departs from §4.2 in three lines:
  - the owner `UPDATE` carries `WHERE [o].[JobId] IS NULL OR NOT EXISTS (… [core].[Jobs] WITH (READCOMMITTEDLOCK) … [Status] IN ('Pending','Running','Held','PendingConfirmation'))`;
  - `SET @…aff = @@ROWCOUNT`, and a count below the number of requests that name an owner throws `50422` with `Jobs.OwnerUnavailable` (`JobEnqueueCodes.OwnerUnavailable`), so a missing row and a row holding an active job both roll the batch back;
  - the statement opens with `IF @@TRANCOUNT = 0 THROW 50422, N'Jobs.EnqueueOutsideTransaction', 1`, so a batch switched to autocommit after the enqueue cannot commit the jobs without the stamps.
  - The in-memory `JobId` is not consulted, so the outbox retry of spec 0022 §7.1 (a `Failed` row whose member names its finished job) enqueues as specified. `READCOMMITTEDLOCK` makes a second enqueuer that waited on the row's update lock see the first's committed job under RCSI.
- **D-9. Validations beyond the spec's list:**
  - the handler shape must match the request's `Entity`;
  - the same row may not be named twice;
  - the batch must be `Persist` or `Maintenance`, in `Auto` or `Explicit` transaction mode (`None` is refused, revised in review 1);
  - ConfirmedKeys over the 2,000-character column throw `InvalidOperationException` instead of truncating;
  - a label over its column is refused.
- **D-10. `EnqueueAsync` keeps the `CancellationToken` parameter** of the existing `IJobQueue` contract.
- **D-11. No commit probe for the enqueue statement.** It is not idempotent and rides the caller's batch. Whether a batch whose commit outcome is unknown runs again is the batch's own decision (`MayRunTwice = false`).

### Rulings worth knowing

- **`jobs.schedules` zone resolution.** It resolves a built-in's zone with `TimeZoneInfo.TryFindSystemTimeZoneById` and falls back to UTC. The zone was already held to the `core.TimeZone` set at realisation, so an unresolvable zone here means the host's tzdata is stale. `core.time-zones` already warns about that.
- **`jobs.schedules` clock.** It reads "now" from the `TimeProvider` in services, else `TimeProvider.System`. The tests pin a clock.
- **Built-in seed rows.** They use the handler key as both `Code` and `Name`, and the system user as author and run-as user. Seeded values are never `UpdateData`'d.
- **The wake runs on every committed enqueue.** That includes arguments-only jobs; the callback runs once per batch, not per request.
- **The failed-batch case.** When the batch fails after the enqueue statement's reader ran, `BatchResult.IsCompleted` is already true, but `OnCommitted` never runs. So in-memory owners stay unstamped and nothing is woken. The integration test asserts the observable guarantees, not `IsCompleted`.

- **The cascade graph.** `ScheduleStates → Schedules` cascades, while `ScheduleStates.LastJobId → Jobs` and `Jobs.ScheduleId → Schedules` set null. It creates cleanly on SQL Server (no 1785), and the delete paths are tested. A later checkpoint that adds a cascading FK into this graph must re-run `JobSchemaTests`.
- **Integration flakes under suite load.**

    - The third full run passed every migrator test. Every one also passes alone, and the `Migrator`+`Data`+`Jobs` run under load passed 162/162.
    - The cause is not identified, because the bare `Assert.Equal(Converged, exitCode)` hid the migrator's output. `MigratorHarness.RunConvergedAsync` now fails with everything the command printed, and the 23 such assertions use it, so the next occurrence names its cause.
    - Each `migrate` takes 45–60 s on LocalDB under suite load, and the job tables enlarge the test distribution's schema, so a command timeout is the likeliest cause. Whether this flake predates this change is unknown.
  - **`Observability/SqlQueryTextTests.A_commands_span_carries_no_query_text`.** It failed once in the third run because it collected another test's `CREATE DATABASE` span (`scope_door_…`, from `TenantScopeTests`). Its process-wide listener sees other tests' SqlClient spans. This is unrelated to jobs; the test passes alone.

### Findings

**R1-1 (major): D-8 breaks a specified re-enqueue, and it does not stop the duplicate it is there to stop.**
`src/core/Tellma.Core/Jobs/JobQueue.cs:229-236` (the `entity.JobId is int` refusal in `OwnerId`).
- Spec 0020 §4.1 says `Entity.JobId` must be "null or refers to a terminal job". Spec 0022 §7.1 depends on that wording. The outbox `retry` loads a `Failed` row whose `JobId` names its finished job, then enqueues "one new job through `IJobQueue.Enqueue`, which allows a null or terminal `JobId`". Under D-8 that call throws `InvalidOperationException`. The documented workaround, clearing the member first, appears only in an exception message. It is not in the `IJobQueue`/`JobRequest` docs, and spec 0022 does not mention it.
- The in-memory check also misses the case it exists for. The member is often not the row's real state: a stub such as `new Shipment { Id = x }` (which the integration tests use), a row read without `JobId`, or a stale copy. In each case the member is null while the row in the database has an active job, and the check passes. The owner `UPDATE` then overwrites `JobId` with the new job. The old job's claim joins its entity through `KeySetRestriction("JobId", …)`, finds no row, and fails with `Jobs.EntityMissing`. So two active jobs are created for one row, and the first one dies.
- A second race has the same outcome. Two scopes enqueue the same row at the same time, both holding a null member. Both pass, the second commit wins the row, and the first job becomes an orphan.
- Suggested fix: allow any in-memory `JobId`, and enforce "null or terminal" inside the statement, where the row is locked. In the owner `UPDATE`, add `WHERE [o].[JobId] IS NULL OR NOT EXISTS (SELECT 1 FROM [core].[Jobs] AS [a] WHERE [a].[Id] = [o].[JobId] AND [a].[Status] IN ('Pending', 'Running', 'Held', 'PendingConfirmation'))`. Then compare `@@ROWCOUNT` with the number of owner rows in `@tb{b}_t0`, and `THROW` (a 50xxx assertion) on a mismatch. XACT_ABORT rolls back the job insert, and the U/X locks the `UPDATE` takes serialise concurrent enqueuers of the same row. A missing owner row would then be refused too, rather than leaving a job doomed to `EntityMissing`.
- Integration tests to add:
  - a row whose `JobId` names a `Succeeded` job is enqueued again and restamped;
  - a row whose job is `Pending` is refused, even when the in-memory member is null, and the refused batch leaves no job and no wake.
- Record the statement-text change against §4.2 as a deviation in place of D-8.

**R1-2 (minor): enqueue accepts a batch in `TransactionMode.None`, where the statement is neither atomic nor safe to re-run.**
`src/core/Tellma.Core/Jobs/JobQueue.cs:93-98` checks `Purpose` but never `TransactionMode`. D-9 also admits `Maintenance` batches, which is the purpose the poll uses with `None`.
- In a `None` batch the job `INSERT` and the owner `UPDATE` commit separately. If the `UPDATE` fails (a unique `JobId` collision, or a deadlock victim), the `Pending` jobs stay with no owner stamped.
- `RetryRules.AfterSend` re-runs the whole round trip after a reported transient failure ("Under XACT_ABORT the server rolled the batch back"). That assumption does not hold in autocommit. A deadlock in a later statement of the same round trip therefore re-runs the enqueue: a second set of jobs is inserted, and the owners are restamped to the new ids.
- Spec 0020 §1.4 gives enqueue the caller's `Auto` transaction.
- Suggested fix: refuse `TransactionMode.None` with the same before-anything-is-appended `ArgumentException`, keeping `Explicit`. Either drop `Maintenance` from D-9 or require it to be `Auto`. Add a unit test next to `A_batch_that_does_not_write_is_refused`.

**R1-3 (minor): no test for the §4.4 rule that a failing nudge is logged and never thrown, or for unsubscribing.**
`src/core/Tellma.Core/Jobs/TenantPollerWake.cs:64-84, 88-107`.
- `Once_the_batch_commits_the_batchs_tenant_is_woken_and_no_other` covers only the happy path.
- Nothing would fail if `Wake` stopped catching. `DataExecutor` would still swallow the exception, but the tenant's later subscribers would not be woken and `JobNudgeFailed` would not be logged.
- Nothing would fail if `Remove` broke either. A disposed poller would keep receiving wakes, and the copy-on-write arrays would leak per tenant.
- The seam is shared by the worker, `INotifier`, run-now and tick step 2 in later checkpoints, so pin it now.
- Suggested fix: add unit tests in which a throwing subscriber logs `JobNudgeFailed` once and the next subscriber is still woken, and in which a disposed subscription is not woken, with a second dispose doing nothing.

**R1-4 (minor): no test migrates a built-in schedule's seed rows into a database.**
`src/core/Tellma.Core/Jobs/BuiltInScheduleSeeds.cs:47-68` is tested only through `GetSeedData()` (`JobContributionTests.The_built_ins_are_seeded_into_the_schedules_with_their_states`). The fixture contributes no built-in, so neither the fixture migration nor `JobSchemaTests` contains a `core.Schedules`/`core.ScheduleStates` `InsertData`.
- The checkpoint's done-when is "all four tables create cleanly" with §7.9's `HasData` realised.
- A seed that the server refuses would surface only when the first Core built-in lands, in a later checkpoint. Examples: the temporal table's period columns, the anonymous object's columns against a distribution's `Schedule` leaf, or the `ScheduleStates` FK ordering.
- Suggested fix: have `FixtureFeature` contribute one built-in, such as `BuiltInSchedule(500, FixtureJobKeys.Probe, "0 1 * * *")`, and regenerate. Then assert in `JobSchemaTests` that the seeded `Schedules` row, with the system user as run-as and author, and its `ScheduleStates` row with a null `NextDueAt` are both present.

**The migrator first-migrate flake: not reproduced, and not a finding.**
- Three back-to-back full runs of `Tellma.Core.IntegrationTests`, with the integration filter, passed every migrator test.
- PC-097's fixture changes cannot be the cause:
  - The migrator tests compose `Tellma.Core.Migrator.TestDistribution`, which does not reference `Tellma.Testing.Entities`. Its only project reference is `Tellma.Core.Migrator`.
  - `fixture.Exports` and the three fixture handlers are therefore absent from the model and the migration those tests apply.
- What PC-097 did change for those tests:
  - the test distribution's own regenerated migration, which now creates Core's four job tables: a temporal `Schedules`, eight filtered indexes and a `LOCK_ESCALATION` statement;

- A slower migrate under heavy machine load is the only plausible link. That fits the implementer's 45–60 s per migrate against the 5–7 min I measured for the whole suite.
- The harness also caps each tenant pool at `MaxPoolSize = 5` (`MigratorHarness.cs`). Under load, a pool-acquisition timeout would surface as a per-tenant partial failure (exit 2). That cap predates this commit.
- `RunConvergedAsync` now prints the migrator's output on failure, so the next occurrence names its cause. Track it under LEDGER "Flaky" if it recurs. No change is needed in this checkpoint.

### Responses

R1-1: fixed in the "PC-097: review 1 fixes" commit (orchestrator ruling: adopt the reviewer's fix). The queue no longer reads the in-memory `JobId`. The owner `UPDATE` in `JobStatements.Enqueue` skips a row whose stored `JobId` names a `Pending`, `Running`, `Held` or `PendingConfirmation` job, read `WITH (READCOMMITTEDLOCK)` so a second enqueuer blocked on the row's update lock sees the first's committed job under RCSI. `@@ROWCOUNT` is compared with the number of owner requests and a mismatch throws `50422` `Jobs.OwnerUnavailable` (new `JobEnqueueCodes`). Integration tests in `JobEnqueueTests`: an owner holding a job in each active status is refused although its member is null (no job stored, stamp unchanged, no wake); an owner whose job is `Succeeded`/`Failed`/`Cancelled`, with the member still naming it, is enqueued again and restamped; a missing owner refuses the whole request. D-8 is rewritten as this rule.

R1-2: fixed in the "PC-097: review 1 fixes" commit. `JobQueue.Enqueue` refuses a batch in `TransactionMode.None` with an `ArgumentException` before anything is appended; `Auto` and `Explicit` are kept for both `Persist` and `Maintenance`. As a backstop for a mode switched after the call, the statement opens with `IF @@TRANCOUNT = 0 THROW 50422, N'Jobs.EnqueueOutsideTransaction', 1`. Tests: `A_batch_whose_statements_autocommit_is_refused` (both purposes), `A_batch_in_an_explicit_transaction_may_enqueue`, and the integration test `An_enqueue_whose_batch_was_switched_to_autocommit_refuses_to_run`. D-9 amended.
