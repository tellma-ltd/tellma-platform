# PC-097: Job schema, handler registry and enqueue

## Implementer notes

### What was built, and where

- **Contracts** (`src/core/Tellma.Core.Abstractions`):
  - `Jobs/`: the `Schedule` entity and `MissedPolicy`, `OverlapPolicy`, `SchedulePausedReason`. `JobLimits` gains `MaxHandlerArgumentsBytes` (65,536) and `MaxCronExpressionLength` (128).
  - `Composition/`: the three items `JobHandlerContributionItem`, `BuiltInScheduleContributionItem` and `RetiredJobKeyContributionItem`, with their `FeatureContribution` sugar: `JobHandler<T>()`, `BuiltInSchedule(...)` and `RetiredJobKey(...)`.
  - `TableTypes/JobRequestList.OwnerId` is now `long?` (see D-1).
  - `ReservedSqlNames.StatementNames.Count` is new.
- **EF extension** (`src/core/Tellma.Core.EntityFrameworkCore/LockEscalation/`):
  - `HasLockEscalation(LockEscalationMode)` and `GetLockEscalation()`, stored as the annotation `Tellma:LockEscalation`.
  - `TableTypesSqlServerAnnotationProvider` lives in `TableTypes/Internal/EfCoreInternalsAdapter.cs`. It subclasses EF's internal `SqlServerAnnotationProvider` so that the option is carried onto the table. `TableTypesOptionsExtension` replaces `IRelationalAnnotationProvider` with it.
  - `TableTypesSqlServerMigrationsSqlGenerator` emits `ALTER TABLE … SET (LOCK_ESCALATION = …)` in two cases: after a `CreateTable`, and on an `AlterTable` whose option changed. When the declaration is removed, it restores `TABLE`.
- **Model** (`src/core/Tellma.Core/Jobs/`):
  - `JobConfiguration` configures `core.Jobs`:
    - 8 filtered indexes and the `CK_Jobs_Lease`, `CK_Jobs_PendingConfirmations` and `CK_Jobs_Progress` constraints;
    - `LOCK_ESCALATION = DISABLE` and `sq_Jobs`;
    - the shadow columns `StateJson`, `LeaseToken` and `ConfirmedKeys`, which are excluded from the UDTT.
  - `ScheduleConfiguration<T>` configures `core.Schedules`: temporal, with a UDTT, `sq_Schedules`, `UX_Schedules_Code` and `IX_Schedules_HandlerKey`.
  - `ScheduleState(+Configuration)`: `IX_ScheduleStates_Due` and `IX_ScheduleStates_Lease`. The FK to `Schedules` cascades and the FK to `LastJobId` sets null.
  - `JobWorkerState(+Configuration)`: a single row, `HasData Id = 1`.
  - `BuiltInScheduleSeeds` adds the `HasData` rows for `Schedules` and `ScheduleStates`. It runs from `TellmaDbContext`, and `NextDueAt` stays NULL.
  - `CoreFeature` contributes the entities, the configurations and the five job table types.
- **Composition** (`Jobs/`, `Composition/`):
  - **Three realizers, each reporting every problem:**
    - Handler: attribute, concrete class, exactly one shape, key grammar, option ranges, the `core.` prefix reserved to Core.
    - Built-in: the id band and the platform's share of it, key grammar, cron presence and width, the zone being in `core.TimeZone` (an alias gets its canonical name), arguments that serialise and fit in 64 KB.
    - Retired key: grammar, and the `core.` prefix reserved to Core.
  - **Cross-feature checks** (`JobContributionChecks`, run after the realiser loop):
    - a key registered twice;
    - a built-in id or key declared twice;
    - a key that is both registered and retired;
    - a built-in that names a retired key.
  - `JobHandlerRegistry` is a singleton.
  - **Startup checks:**
    - `jobs.handlers`: an entity handler over an entity that the model does not map as a job entity is a problem. A built-in with no handler on this host is a `SchedulerHandlerUnknown` warning.
    - `jobs.schedules`: the expression must parse with Cronos `CronFormat.Standard` and have a next occurrence in its zone.
  - Cronos 0.13.0 is added to `Directory.Packages.props` and `Tellma.Core.csproj`.
- **Enqueue** (`Jobs/JobStatements.cs`, `Jobs/JobQueue.cs`, `Jobs/TenantPollerWake.cs`):
  - The statement:
    1. takes a range from `sp_sequence_get_range`;
    2. runs `INSERT … SELECT` from the `JobRequestList` TVP;
    3. runs a single `UPDATE [o] SET [JobId]` on the owner table, which is resolved from `EntityMetadata`;
    4. ends with `SELECT [Ordinal], [JobId] ORDER BY [Ordinal]`.
    
    It writes `core.Jobs` and, when there is one, the owner table. It is not idempotent.
  - `JobQueue` is scoped:
    - `Enqueue(batch, requests)` and `EnqueueAsync`.
    - RunAs defaulting: the request's user, else the system user in a system scope, else the scope's user, else a refusal.
    - ConfirmedKeys: the scope's confirmations, distinct, ordinal-sorted and comma-joined. None are stored in a system scope.
    - TraceParent: copied from the current W3C `Activity`.
    - DueAt is converted to UTC.
    - The label and the arguments are serialised through `JobJson`.
    - Every programmer error throws before anything is appended.
    - `OnCommitted` stamps the in-memory `Entity.JobId` and wakes the tenant.
  - `TenantPollerWake` is the internal singleton seam that wakes this host's pollers for one tenant (used later by the worker, `INotifier` and run-now). A subscriber that throws is logged as `JobNudgeFailed` and never propagates.
- **Fixture** (`test/shared/Tellma.Testing.Entities`):
  - `PlatformStandIns.cs` is removed: Core now contributes the real `core.Jobs`.
  - New: the `Export` job entity (int key) beside `Shipment` (long key), and three fixture handlers (`fixture.probe`, `fixture.ship`, `fixture.export`).
  - `FixtureDatabase.CreateAsync` has an overload that takes `readCommittedSnapshot`.
  - The migrations were regenerated with `dotnet ef`. The TestDistribution's migrations were regenerated too.

  - Unit (`test/core/Tellma.Core.Tests/Jobs/`):

    - `test/core/Tellma.Core.EntityFrameworkCore.Tests/LockEscalation/` and the pinning tests for the annotation provider.
  - Integration (`test/core/Tellma.Core.IntegrationTests/Jobs/`):
    - `JobSchemaTests`:
      - RCSI on and off;
      - lock escalation is `DISABLE` on `core.Jobs` alone;
      - the seeded worker row;
      - the delete paths of the cascade graph;
      - `CK_Jobs_Lease` and `CK_Jobs_PendingConfirmations` on insert and update.
    - `JobEnqueueTests`:
      - the stored columns, including `LabelKey` and `LabelArgumentsJson`;
      - 3,000 long-keyed owners named out of key order: one statement, ids in request order, stamped in the database and in memory;
      - an int-keyed owner through `EnqueueAsync`;
      - one wake, after the commit only;
      - a batch that fails after the enqueue leaves no job, no stamp and no wake;
      - two entity types are refused before anything is appended.
  - Existing tests were updated now that Core maps `core.Jobs`:
    - the `TestJob` and `MdJob` stand-ins were removed from the compositions that include Core;

### Deviations

- **D-1. `JobRequestList.OwnerId` is `bigint`, not `int`.** Job entities may be keyed by `long`, as the fixture's `Shipment` is. A 32-bit owner id would truncate or refuse their rows. Int-keyed owners widen losslessly.
- **D-2. `LOCK_ESCALATION` rides `UseTableTypes`.** It is implemented through an annotation-provider subclass that uses EF's internal `SqlServerAnnotationProvider`. The subclass is quarantined in the adapter file and pinned by a test of its base type and constructor. There is no public hook through which the differ can surface a custom table option.
- **D-3. Executor whitelist of `EXEC sys.sp_sequence_get_range`: not applicable.** The executor has no statement whitelist or analyzer to extend. The statement composes `sp_sequence_get_range` the way `IdAllocator` already does.
- **D-4. Log events:**
  - `JobNudgeFailed` (Warning) is new; it is logged when a wake subscriber throws.
  - The `jobs.handlers` warning reuses `SchedulerHandlerUnknown` from the spec's list.
- **D-5. `Entity<Job>()` and `Entity<Schedule>()` are contributed without services.** `JobService` and `ScheduleService`, and Core's own built-ins and handlers (`core.notification-delivery` and the others), land in their own checkpoints.
- **D-6. New constants:** `JobLimits.MaxHandlerArgumentsBytes`, `JobLimits.MaxCronExpressionLength` and `ReservedSqlNames.StatementNames.Count`. They name limits the spec states only in prose or SQL.
- **D-7. The check that an entity handler's entity is mapped runs in `jobs.handlers`, not in the realizer.** The tenant model exists only at the realised gate, after every realizer has run.
- **D-8. The enqueue refuses an `Entity` whose in-memory `JobId` is set; the spec says "null or terminal".** The queue cannot know the row's job status at call time without a read. A caller re-enqueues a row whose job ended by clearing the member first. This is flagged for the orchestrator.
- **D-9. Validations beyond the spec's list:**
  - the handler shape must match the request's `Entity`;
  - the same row may not be named twice;
  - the batch must be `Persist` or `Maintenance`;
  - ConfirmedKeys over the 2,000-character column throw `InvalidOperationException` instead of truncating;
  - a label over its column is refused.
- **D-10. `EnqueueAsync` keeps the `CancellationToken` parameter** of the existing `IJobQueue` contract.
- **D-11. No commit probe for the enqueue statement.** It is not idempotent and rides the caller's batch. Whether a batch whose commit outcome is unknown runs again is the batch's own decision (`MayRunTwice = false`).

### Rulings worth knowing

- **`jobs.schedules` zone resolution.** It resolves a built-in's zone with `TimeZoneInfo.TryFindSystemTimeZoneById` and falls back to UTC. The zone was already held to the `core.TimeZone` set at realisation, so an unresolvable zone here means the host's tzdata is stale. `core.time-zones` already warns about that.
- **`jobs.schedules` clock.** It reads "now" from the `TimeProvider` in services, else `TimeProvider.System`. The tests pin a clock.
- **Built-in seed rows.** They use the handler key as both `Code` and `Name`, and the system user as author and run-as user. Seeded values are never `UpdateData`'d.
- **The wake runs on every committed enqueue.** That includes arguments-only jobs; the callback runs once per batch, not per request.
- **The failed-batch case.** When the batch fails after the enqueue statement's reader ran, `BatchResult.IsCompleted` is already true, but `OnCommitted` never runs. So in-memory owners stay unstamped and nothing is woken. The integration test asserts the observable guarantees, not `IsCompleted`.

### Open risks

- **EF upgrades.** The annotation provider subclass depends on an internal EF type. The pinning test fails loudly on an EF upgrade that changes its base type or constructor.
- **The cascade graph.** `ScheduleStates → Schedules` cascades, while `ScheduleStates.LastJobId → Jobs` and `Jobs.ScheduleId → Schedules` set null. It creates cleanly on SQL Server (no 1785), and the delete paths are tested. A later checkpoint that adds a cascading FK into this graph must re-run `JobSchemaTests`.
- **Integration flakes under suite load.**
  - **Migrator tests.** Two of the three full runs of `Tellma.Core.IntegrationTests` had one `Steps`-based migrator test fail because its first `migrate` on a fresh tenant returned a partial failure (exit 2): `A_cancellation_raised_inside_one_tenants_step_fails_that_tenant_alone` in the first run, `Migrate_migrates_a_suspended_tenant_and_defers_its_steps_until_reactivation` in the second.
    - The third full run passed every migrator test. Every one also passes alone, and the `Migrator`+`Data`+`Jobs` run under load passed 162/162.
    - The cause is not identified, because the bare `Assert.Equal(Converged, exitCode)` hid the migrator's output. `MigratorHarness.RunConvergedAsync` now fails with everything the command printed, and the 23 such assertions use it, so the next occurrence names its cause.
    - Each `migrate` takes 45–60 s on LocalDB under suite load, and the job tables enlarge the test distribution's schema, so a command timeout is the likeliest cause. Whether this flake predates this change is unknown.
  - **`Observability/SqlQueryTextTests.A_commands_span_carries_no_query_text`.** It failed once in the third run because it collected another test's `CREATE DATABASE` span (`scope_door_…`, from `TenantScopeTests`). Its process-wide listener sees other tests' SqlClient spans. This is unrelated to jobs; the test passes alone.
- **The fixture changed.** A new table (`fixture.Exports`) and handlers were added. Only `Tellma.Core.IntegrationTests` consumes the fixture.
