### Deviations

1. **The bag reads add `ORDER BY [Key]`**, so the bag in the envelope and the action answers is deterministic. The spec names no order.
2. **The access summary is decided synchronously.** It uses `AccessEvaluator.DecideFrom` on every registered securable, over the permission set the `me` round trip's prologue validated, rather than a separate `EvaluateAllAsync`. The result is the same and costs no further round trip.
3. **me/save's RT1 also reads the last modifier's names** (Name, Name2, Name3) so that the 409 body's `ModifiedByName` is in the reader's content language, with a fallback to the primary name. It also reads the bag, which the envelope answers.
4. **The own-route key cap (`Users.TooManyPreferenceKeys`, asserted inside the statement) is a 422 at the request root.** A statement-level THROW has no item to name.
5. **me/locale shape rules.**
   - A member both set and reset yields a single `LocaleResetConflict` error at `Reset`, not one per member.
   - An empty-string member is normalized to "not set".
   - A request with nothing set and nothing reset is `LocaleEmpty` at `Language`.
6. **`VersionTagWire.Items` (public, Abstractions).** It is the header's items by name. `HeaderValue` now formats them. `MeResult.Tags` and the `me/preferences` answers use the same wire forms, so the envelope and the `Tellma-Version-Tags` header cannot drift.
7. **`UserServiceDependencies` grows.** It gains the write frames, the open-write host, the access options, the entity metadata and the Queryex schema provider. The stored-row read selects the schema's declared properties as the CRUD reads do. `EntityQuery.AllProperties` alone adds only the JSON columns, and the audit stamp would otherwise read as default.
8. **`ComposeStatusRead` is generalized to `ComposeVisibleRead`**, so `preferences/get` reuses the filtered read.
9. **`UserPreferencesRequest.Id` is `int`**, the users' key type, as the rest of the users' stack is.
10. **The activity contributor is registered closed over `User`** in `CoreFeature`, beside the existing users registrations. A distribution's derived user type would register its own.
11. **Labels.** Core's resources gain English and Arabic labels for the eight new actions and their arguments' members. No action Descriptions were added: the existing users actions carry none.

### Open risks

- A write to `core.Users` (me/save, me/locale) fails the existing `Access.LastAdministrator` invariant (50422) when the tenant has no human administrator. This is platform behavior and not new. The integration tests seed an administrator for it. In production a tenant always has one, but a member's own locale change is refused in that degenerate state.
- D-163 item 9: the activity extra reads `core.UserStamps.LastActiveAt` exactly as the connect prologue stamps it, and the prologue and connect cache are unchanged. On a warm connect cache only the cold connect stamps, so the extra can lag a busy user's latest request by up to the cache's lifetime. Acme's `A_read_on_a_read_only_tenant_stamps_the_user_s_activity` passes.
- In the integration fixture, a users save that sets only `Name2` did not move the stamp, because the fixture's shape keeps no secondary names. The stale-stamp test moves `ContactMobile` instead and asserts that the stamp moved.

### What reviewers should examine

- `UserService.Me.cs` `SaveMeAsync`: the stamp check before enlistment, the `Override` path, and that `Apply` leaves the memberships null so the enlisted save writes no membership rows.
- `SetMyLocaleAsync`: the single Persist batch, which must contribute the guards' lock and invariants for `core.Users` exactly as a save does, and its `AllowWhenReadOnly` admission.
- `UserService.Preferences.cs`: the path mapping between the own routes (`items[i].key`) and the admin routes (`Arguments.Items[i].Key`), and that each admin write moves the target's tag rather than the caller's.
- `UserActivityContributor`: the extra is restricted to the read's admitted ids, so a hidden user gets no row.

## Review 1

### Findings

Reviewed commit 17267a1c. Summary: 0 blocking, 2 major, 3 minor.

Checked and found sound (no finding):

- **`Access.LastAdministrator` on a self-service write.** Spec 0014 §8.3 makes L1–L3 state invariants: `ContributeLock` and `ContributeInvariants` run on every non-System Persist batch whose written tables meet `core.Users`, `core.Roles`, `core.RoleMemberships` or `core.Permissions`. That covers "save, action or delete alike", whatever the columns. Spec 0018 §3.5 lists `ContributeInvariants` in me/locale's batch by name, and me/save is a `core.Users` save. So firing on a name or locale edit is specified behaviour, not a bug. The only reachable state with no Invited-or-Joined permanent administrator is the deployed window between bootstrap (`State = New`) and the first successful invite. No member can be connected in that window. The WATCHLIST 0014 entry already records that fixtures must seed an Invited or Joined administrator. Not a finding.
- **Self-service scope.** me/save loads the row by the prologue's `@tm_UserId` and enlists `[stored]`. `Apply` copies exactly `MeSaveRequest`'s eight members and nulls `RoleMemberships`. Email, Kind, State, IsActive, Subject and the locale columns keep their stored values. The `UserAccessRules` and §3.2 rules still run. me/locale's `Update<TUser>.ByIds([user.UserId], …)` assigns only the five `Preferred*` columns. No path takes a target id from the request. The integration test asserts that Email, the locale members and State are untouched.
- **`core.User × Preferences`.** It is registered with `FilterRoot = core.User` and `IsSensitive = false`, as §3.1 requires. It is pinned in `SecurablesCheckTests` and `SecurablesClientAssetContributorTests`.
- **Stored-row read.** `ComposeOwnRow` selects `map.Declared(leaf)` plus `AllProperties`, the same pattern as `WriteRun`, `SaveRun.Enlisted`, `DeleteRun.Enlisted` and `DetailsOperation`. The cache probe selects the declared list too. The one other caller with the defaulted-columns bug is outside this commit: see R1-2.
- **Activity extra.** It reads `core.UserStamps.LastActiveAt` joined to `plan.IdsSource`, as §3.1 gives it. No file under the connect prologue or the connect cache changed, so D-163 item 9 is untouched.
- **D-096 carry.** `TenantStateTests.An_action_allowed_when_read_only_succeeds_on_a_read_only_tenant` is reached: `PlatformSeams.ServesTheLocaleAction` holds now that `users/me/locale` is projected. Its result is in the run list at the end.
- **Everything else checked.** Round-trip budgets: integration asserts me 1, me/save 3, me/locale 1, own bag 1, preferences/get 1 and admin set/delete 2. The 409 is raised before enlistment. Override is passed through to `EnlistSaveOptions`. `AccessSummary` built through `DecideFrom` matches `EvaluateAllAsync` (`AccessEvaluator.cs:203-216` runs the same loop). Unchanged locale values are skipped null-safely (`DataBatch.Updates.cs:451`, the `EXCEPT` form). The admin key-cap 50422 maps to a 422 through `PersistFailures.Assertion`. The `MeResult` family matches 0016 §3.4 exactly. No spec or decision references appear in XML docs or error texts.

**R1-1 (major): the deferred 0014 §14 race test "a role save racing a membership edit and a me/locale write completes with no deadlock" is still not written.**
PC-078's done-when (CHECKPOINTS.md, PC-078) defers it "to 0018 where me/locale exists", and this checkpoint creates me/locale. WATCHLIST 0014 ("defer to 0018's checkpoint, then keep under a Concurrency trait") points here too. No test in `test/core/Tellma.Core.IntegrationTests` covers it (search for `me/locale` or racing tests in `Access/`). No LEDGER row carries it, so after this checkpoint it has no owner.
Why it matters: me/locale is a new kind of security-table writer. It is a raw `Update<TUser>`, not a save. Its batch carries the applock marker, a `core.Users` write with a Preferences rule (so the prologue's `UserStamps` arm takes `UPDLOCK`), and the invariants. 0014 §14 has this test to pin that the applock comes before the version-tag guard, so the three writers serialise instead of deadlocking. If the marker were ever dropped or reordered in `SetMyLocaleAsync` (`UserService.Me.cs:146-160`), no test would fail.
Fix: add the integration test now. Run a role save, a membership edit of user U, and U's me/locale concurrently behind a barrier (the fixture's `HoldWhileAsync` pattern from `UserWriteTests`). Assert that all three complete with no 1205 or `Access.LockDeadlock`. Keep it under the Concurrency trait the watchlist names. If it truly cannot land here, the orchestrator needs a LEDGER carry so it does not lose its owner.

**R1-2 (major, pre-existing, outside this commit): `JobEntityLoad<TEntity>` loads entity-backed jobs' rows with every non-key scalar defaulted. This is the same bug deviation 7 fixed for me/save.**
`src/core/Tellma.Core/Jobs/JobClaim.cs:46-51` queries `Select = nameof(IJobEntity.JobId), AllProperties = true`. `EntityQuery.AllProperties`'s XML doc (`src/core/Tellma.Core.Abstractions/Data/EntityQuery.cs:45-49`) promises "every mapped property … the JSON columns included". The implementation (`src/core/Tellma.Core/Data/Batches/DataBatch.Queries.cs:273`) adds only `map.JsonColumns(metadata)` as undeclared columns, plus the key from `Completion`.
Failure scenario: spec 0020 §5.1's entity join load hands every `IEntityJobHandler<TEntity>` rows holding only `Id`, `JobId` and the JSON columns. When `OutgoingEmailHandler`'s dispatch replaces its `NotSupportedException` body (spec 0022), every claimed `OutgoingEmail` arrives with a null `Subject`, recipients and bodies. Exports and imports (0019) will hit the same problem. It is latent today only because no handler reads a non-key property: `ShipJobHandler` and `ExportJobHandler` in `FixtureJobHandlers.cs` do nothing, and no job test asserts a loaded entity's columns.
Fix (a fix item, not PC-090): have `JobEntityLoad` select `string.Join(", ", map.Declared(metadata)…)` as the other loaders do, and add a job integration test that asserts a non-key column of the claimed entity. Separately, either make `AllProperties` mean what its doc says (add the declared scalars) or correct the XML doc to "adds the JSON columns a declared select leaves out". The misleading doc is what set both traps.

**R1-3 (minor): an empty `timeZone` is refused as `TimeZoneUnknown`, while deviation 5 says an empty-string member means "not set".**
`UserService.Me.cs:202` takes `request.TimeZone` as is. `Language`, `Calendar` and `Region` go through `UserRules.Language/Calendar/Region`, which map `""` to null. So `{ "timeZone": "" }` answers `TimeZoneUnknown` at `TimeZone`, while `{ "language": "" }` answers `LocaleEmpty`. The unit test `A_zone_outside_the_set_an_alias_included_is_refused_at_the_time_zone` pins `""` as refused, so the code and the commit message's deviation 5 disagree. The device time-zone prompt (spec 0024 §7.8) is the caller most likely to send an empty zone when the browser reports none.
Fix: pick one rule. Either normalise the zone like the others (`string.IsNullOrEmpty(request.TimeZone) ? null : request.TimeZone`) and change the unit test's `""` row to expect `LocaleEmpty`, or narrow deviation 5 to the three members it covers and say why the zone differs.

**R1-4 (minor): the administrative routes' key cap and delete-key checks have no action-level test.**
§3.5 says the key grammar, the caps and the per-request checks "apply as for `me/preferences/set`". The integration suite covers the admin path's bad key on `preferences/set` only (`Another_user_s_bad_key_is_refused_at_the_action_s_arguments`). No test calls `preferences/set` over `MaxPreferenceKeys` through `ExecuteActionAsync`, so nothing pins that the 50422 from the action's persist reaches the caller as a 422 `Users.TooManyPreferenceKeys` with nothing written. `UserWriteTests` pins only the statement's `BatchAssertionFailedException`. Nothing calls `preferences/delete` with a bad or duplicate key at `Arguments.Keys[i]` either, or covers the value-size cap on the admin path. If `ValidatePreferenceArguments`'s delete branch (`UserService.Preferences.cs:186-189`) broke, or the persist mapping changed, no test would fail.
Fix: in `Users/UserSelfServiceTests` (integration), add an admin `preferences/set` against a capped instance (`MaxPreferenceKeys = 2`) that expects `ValidationException` at the root with `Users.TooManyPreferenceKeys` and the bag unchanged. Add an admin `preferences/delete` with `["ok", "OK"]` that expects `Users.PreferenceKeyDuplicate` at `Arguments.Keys[1]`.

**R1-5 (minor): the D-096 carry and the acme self-service test can still pass by not running.**
`TenantStateTests.An_action_allowed_when_read_only_succeeds_on_a_read_only_tenant` keeps `Skip = NeedsProjectedActions, SkipUnless = nameof(PlatformSeams.ServesTheLocaleAction)` (`distributions/acme/test/Tellma.Distro.Acme.IntegrationTests/TenantStateTests.cs:190`). The seam is detected by matching the route pattern `"/users/me/locale"` (`Infrastructure/PlatformSeams.cs:27, 83`). The seam has now landed, but a route rename or a projection change would silently turn the D-096 row back into a skip, which CI reports as green. D-096's point was that the landing checkpoint makes the row run.
Fix: now that the locale action is in the platform, drop the conditional skip from this row, making it a plain `[Fact]` as `SelfServiceTests` already is. Alternatively, add an assertion elsewhere (for example in `SelfServiceTests`) that `PlatformSeams.ServesTheLocaleAction` is true, so a lost seam fails loudly.
