### Deviations

1. Mail drop configuration: `Email:Provider` = `development-drop` and
   `Email:DevelopmentDrop:Directory`, not the planner's `Tellma:Email:DevelopmentDropDirectory`.
   The transport is selected through the platform's existing `Email:Provider` switch, so it is
   registered always and refused outside Development by the startup check (and by the sender).
2. Port: `ACME_WEB_E2E` from `.dev-ports.local`, else OS-assigned, not `ACME_WEB`: the dev host
   holds `ACME_WEB`, and reusing it would collide with a running dev host.
3. Linux SQL Server: a throwaway container via the Docker CLI, not the Testcontainers library
   (the host is a Node script; Testcontainers for Node would be a new dependency for one
   `docker run`).
4. Lighthouse on Slow 4G is replaced by CDP network/CPU throttling and an LCP observer, recorded
   as a warn-only annotation (no Lighthouse dependency; the budget is not yet a gate).
5. The `Tellma.Distro.Acme.E2E.csproj` placeholder is replaced by a TypeScript pnpm package.
6. Route feedback pins the skeleton to the frame after the click's (§14's "next frame"); the
   click's own frame (§4.4's wording) is the one the click event runs in, before any render.
7. One Chromium project. `@cross-engine` Firefox and WebKit projects join with the first
   cross-engine flow (zone-labels, pending on 0032).
8. The warm launch's "first request after the shell renders" is checked at the call: a `fetch`
   wrapper records whether `tm-app`'s routed view was in the DOM. The `/tenants` case is a
   `test.fail()`: the launch cache revalidates `tenants` as soon as a tenantless route is routed,
   before the first render (see open risks).
9. Sign-in retries a round trip that ends at a server error, up to three times (see open risks).
10. The e2e host raises `Tellma:Api:AnonymousRequestsPerMinutePerIp`, `RequestsPerMinutePerUser`
    and `RequestsPerMinutePerUserAcrossTenants` to 100 000: every worker comes from one loopback
    address and parallel tests share the principals, so the default 60 anonymous requests a
    minute per address refused `/bff/login` mid-run.
11. Route feedback is two tests: the PR tier checks the skeleton shows while the documents are
    held and the page then replaces it; the exact "frame after the click" check is `@perf`
    (nightly), since six parallel workers on one machine missed the frame once in four runs.

### Open risks, and what reviewers should examine hardest

- **Concurrent sign-ins of one user race in the identity engine.** On a host whose permanent
  authorization does not yet cover the grant's resources (every fresh origin, so every run on a
  new port), parallel grants of one user each try to add the resources; the losers get
  `temporarily_unavailable` ("try again"), which the BFF's OIDC callback turns into a 500 problem
  page. `roundTrip` in `tm-sign-in.ts` retries. A real user with two tabs signing in at once would
  meet the same 500; the BFF could retry or redirect instead. Not fixed here.
- **`/tenants` issues `GET /bff/user` before the first render** on a warm launch (the launch
  cache's tenantless-route effect). The render does not wait on it; only spec 0024 §15's order
  is broken. The `test.fail()` flips to a failure when it is fixed.
- The admin's stored language preference is English, so the Arabic warm flows sign in as the
  sales representative, whose preference is unset; the boot record's language then holds.
- `warmUp` waits on the worker's shell cache and the store's launch documents by name
  (`settings`, `me`, `tenant` / `tenants`, version suffix stripped); a renamed document makes it
  time out with a clear message.
- The host script's process-tree cleanup on Windows (`taskkill /T /F`) and the container cleanup
  on Linux; check a Ctrl+C mid-migration.
- **The nightly warm-chrome gate fails today.** Locally, alone (one worker, Windows), a warm
  launch of `/1` at 4× CPU throttling shows its chrome 740–840 ms after navigation start, against
  the 300 ms budget (unthrottled, every route family stays under the PR tier's 1 s budget). The
  gate is left strict, so the nightly tier reports it until the boot path gets faster.
- The tenant-picker `test.fail()` failed as expected in each of five runs; the order it checks is read
  inside one task (the `fetch` wrapper reads the DOM at the call), not from the clock, so it
  should stay deterministic. A pass would fail the run and mean the read moved.
