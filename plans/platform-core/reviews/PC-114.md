### Open risks, and what reviewers should examine hardest

- **Concurrent sign-ins of one user race in the identity engine.** On a host whose permanent
  authorization does not yet cover the grant's resources (every fresh origin, so every run on a
  new port), parallel grants of one user each try to add the resources; the losers get
  `temporarily_unavailable` ("try again"), which the BFF's OIDC callback turns into a 500 problem
  page. `roundTrip` in `tm-sign-in.ts` retries. A real user with two tabs signing in at once would
  meet the same 500; the BFF could retry or redirect instead. Not fixed here.
- **The Arabic project's account** (review 1). The development seed creates every account in
  English, so the suite's global setup sets the sales representative's identity language to
  Arabic through the identity engine's profile page, once per run, on the suite's own databases.
  In the Arabic project the sales representative is the signed-in user and the centers
  accountant the "other user"; the sandbox principal stays English in both projects, and the
  steps that sign in as the other user or the sandbox principal check language-free facts
  (addresses, names, emails). The responsive flow (its languages per test), the right-to-left
  boot (Arabic in both) and the nightly gates run in the English project only.
- `warmUp` waits on the worker's shell cache and the store's launch documents by name
  (`settings`, `me`, `tenant` / `tenants`, version suffix stripped); a renamed document makes it
  time out with a clear message.
- The host script's process-tree cleanup on Windows (`taskkill /T /F`) and the container cleanup
  on Linux; check a Ctrl+C mid-migration.
- **The nightly warm-chrome gate fails today.** Locally, alone (one worker, Windows), a warm
  launch of `/1` at 4× CPU throttling shows its chrome 740–840 ms after navigation start, against
  the 300 ms budget (unthrottled, every route family stays under the PR tier's 1 s budget). The
  budget is unchanged (review 1 leaves it to Ahmad); the gate now takes the median of three
  launches and scales by the CI multiplier, so the nightly tier reports it until the boot path
  gets faster.
- The request-order check is read inside one task (the `fetch` wrapper reads the DOM at the
  call), not from the clock, so it should stay deterministic.
