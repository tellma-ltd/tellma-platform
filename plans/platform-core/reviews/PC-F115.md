# PC-F115: Shell-frame skip-link focus flake

## Implementer notes

PC-F115 has no CHECKPOINTS.md entry. It is a fix item, scoped by its LEDGER row, the flaky-tests
row for the skip-link test, D-406 to D-410 and the brief. No spec section is in scope, and no
product code changed.

### Root cause

`moves focus to main from the skip link, leaving the URL alone` calls
`HTMLAnchorElement.prototype.click()` on the skip link. Two core specs replace that method with a
`vi.spyOn(...).mockImplementation(...)` and never restore it:

- `client/projects/core/tellma-core/support/src/tm-support-dump.spec.ts`, "downloads through a
  temporary link and an object URL revoked later, and records whether it holds page data";
- `client/projects/core/tellma-core/support/src/tm-diagnostics-panel.spec.ts`, the last test of its
  first `describe` (the support dialog's "Download diagnostic file").

The unit-test builder runs a browser project with `isolate: false`: each worker is one Playwright
page whose one tester iframe runs its share of the files one after another. Vitest's Node runner
calls `vi.restoreAllMocks()` after every file ("mocks should not affect different files",
`vitest/dist/chunks/base.*.js`), but its browser tester (`@vitest/browser` `executeTests`) does
not, and the workspace preset did not set `restoreMocks`. So when either support spec ran earlier in
the same page as the shell-frame spec, with no file in between whose own `afterEach` happened to
call `vi.restoreAllMocks()`, the skip link's `click()` was the leftover mock: no click event was
dispatched, `skip()` never ran, focus stayed on `body` (id `''`), and the URL was unchanged, so
only line 60 failed. Exactly the CI signature.

That explains every observation in the evidence: the failure follows the file schedule (CI orders
by size with no results cache, so any spec's size change moves files between workers), it never
reproduced in serial orders that did not put a support spec first, PC-123's diagnostics in the
spec or a setup file changed the schedule or wrapped `click` themselves, and the first local
failure (2026-11-25) came in PC-154's own fix run, the checkpoint that added both support specs.

Reproduction, one worker, files in a forced order (scratch config, not committed):

- `tm-support-dump.spec.ts` then `tm-shell-frame.spec.ts`: fails 1/1, deterministic; the silent
  focus recorder shows no click event and no focus call at all, `activeElement` `body`,
  `hasFocus()` true.
- `tm-diagnostics-panel.spec.ts` then `tm-shell-frame.spec.ts`: fails 1/1, the same.
- Both pairs with the fix: pass.

### The fix

`@tellma/core-tools/vitest` (the preset every client workspace's `vitest-base.config.mjs`
re-exports, the platform's and Acme's) now sets `restoreMocks`, `unstubGlobals` and `unstubEnvs`.
Vitest then restores every `vi.spyOn` spy and every `vi.stubGlobal`/`vi.stubEnv` stub before each
test, so no test inherits a mock from an earlier test or an earlier file in its page, whichever
worker the schedule gives it. This closes the class, not just the two specs: a spec that forgets to
restore a spy can no longer reach another file. The two support specs need no change, and the
shell-frame spec is unchanged (D-011: no retry, quarantine, loosened assertion or timeout).

- `client/projects/core/tellma-core-tools/src/vitest/index.ts`: the three options, TSDoc on why.
- `client/projects/core/tellma-core-tools/src/vitest/watchdog.spec.ts`: "the Vitest preset" pins
  the three options.
- `client/projects/core/tellma-core-tools/README.md`, `client/README.md`, both
  `vitest-base.config.mjs` comments: what the preset now does, and that a spy several tests share
  must be made in `beforeEach`.

### Deviations

None from a spec. The fix is in shared test tooling rather than in the shell frame, because the
shell frame and its spec were correct.

### Open risks

- A leaked spy is restored before the next test, not at the end of its file, so for the time
  between one file's last test and the next file's first test (the next file's module evaluation
  and its `beforeAll` hooks) it is still in force. Nothing in the client depends on a patched
  prototype there today. Closing that window too would need a setup file shipped with the preset
  that restores at each file's end, which the builder's setup-file merge makes fiddly; I judged it
  not worth it.
- Spies or stubs made in `beforeAll` or at a file's top level are now restored before the first
  test. None exists in the client today (checked by inspection and by the full unit run); the
  README states the rule for new ones.
- The explicit `vi.restoreAllMocks()`/`vi.unstubAllGlobals()`/`vi.unstubAllEnvs()` calls in
  existing specs' `afterEach` hooks are now redundant but harmless; they were left in place to keep
  the change to the cause.

### What reviewers should examine hardest

- Whether the root cause is fully established: the two forced-order reproductions, and whether any
  other leaked mock (for example `vi.useFakeTimers` without `useRealTimers`) could also reach the
  skip test. Fake timers would not stop a synchronous `click()`/`focus()`, so I found no other
  candidate for this signature.
- That no spec relied on a spy surviving into a later test (the full client unit run below).

### Tests run locally

The CI run on the integrate commit is the gate; the flake's frequency there (about every other

## Review 1

### Findings

Reviewer 1 (Opus), on commit 5b02fd55. Verified locally:

- **The cause, reproduced independently.** A scratch runner config outside the repo (one worker,
  `fileParallelism: false`, a sequencer that orders files by an environment list, the three
  restore options toggled) passed to `ng test core --runner-config=... --include=...`:
  `tm-support-dump.spec` then `tm-shell-frame.spec` with restore off fails exactly line 60
  (`expected '' to be 'tm-main'`); `tm-diagnostics-panel.spec` then `tm-shell-frame.spec` fails the
  same; both pairs pass with restore on; and both pass through a second scratch config that spreads
  the committed preset's own `test` block (built `dist/vitest`), so the builder does carry the
  options into the project. The reverse order (`tm-shell-frame.spec` first) passes with restore
  off. Vitest 4.1.9 source agrees: the Node runner calls `vi.restoreAllMocks()` after each file
  (`vitest/dist/chunks/base.*.js`), the browser tester's `executeTests` does not, and
  `clearModuleMocks` runs in `onBeforeTryTask`, before the `beforeEach` hooks
  (`@vitest/runner` `chunk-artifact.js`).
- **Semantics of the options in 4.1.9.** `restoreMocks` calls `vi.restoreAllMocks()`, which runs
  only the restore callbacks `vi.spyOn` registers (`@vitest/spy` `MOCK_RESTORE`); `vi.fn()`
  implementations and call state, and automocks, are untouched (`mockReset`/`clearMocks` stay off).
  No browser or Acme unit spec uses `vi.mock`.
- **Blast radius.** A TypeScript-AST scan of every `.ts`/`.mts` file under `client/projects` and
  `distributions` found 242 `vi.spyOn`/`vi.stubGlobal`/`vi.stubEnv` calls: 205 in `it` bodies, 11 in
  `beforeEach`, 26 in helper functions, and none at module scope, in a `describe` body or in
  `beforeAll`. Every call site of those helpers is inside an `it`, a `beforeEach` or another helper.
  The 17 `beforeAll` hooks only import chunks, register strings or add token sheets. No non-spec
  file creates a spy or stub.
- **Runs.** `CI=true node scripts/test.mjs` twice, all green both times (core 158 files, core-testing
  9, core-ui 137, core-ui test-csp 3, core-ui-tokens 1, locale-ar 1, showcase 1); Acme client
  `ng test` twice, 2 files green both times; the tools Vitest project for `src/vitest`, 14/14. The
  pc/PC-F115 push run 46000032837 was skipped, so there is no CI run on the branch yet.

R1-1 (major). **Nothing fails if the restore stops reaching the tests.**
`client/projects/core/tellma-core-tools/src/vitest/watchdog.spec.ts:397` checks only the object
`tmVitestConfig()` returns. The fix works only because `@angular/build`'s Vitest plugin merges the
runner config's `test` block into the project it creates (`runners/vitest/plugins.js`,
`mergeConfig(projectDefaults, { test: testConfig })`), and because no workspace's
`vitest-base.config.mjs` overrides it. Failure scenario: a builder upgrade that picks the project
options differently, or a workspace that wraps the preset and drops or overrides the three keys.
This test stays green, every unit run stays green on most schedules, and the skip-link flake (or
the next one like it) comes back intermittently, which is the cost this item exists to remove.
Suggested fix: add a browser-mode canary in a project that runs under the preset (core-testing or
core), two tests in one file, which Vitest runs in order: the first replaces
`HTMLAnchorElement.prototype.click` with `vi.spyOn(...).mockImplementation(() => {})` and a
`vi.stubGlobal` of a probe name, and restores neither; the second asserts that
`vi.isMockFunction(HTMLAnchorElement.prototype.click)` is false, that clicking a connected link
dispatches a `click` event, and that the probe global is gone. With restore off, the second test
fails deterministically (the same mechanism as my forced-order runs).

R1-2 (minor). **The two specs that caused the flake still leak their spies into the next file's
set-up, and the docs say the leak is closed.**
`client/projects/core/tellma-core/support/src/tm-support-dump.spec.ts:322` (and its
`URL.revokeObjectURL` spy at :325) and
`client/projects/core/tellma-core/support/src/tm-diagnostics-panel.spec.ts:204` still leave
`HTMLAnchorElement.prototype.click` mocked after their last test. The restore runs in
`onBeforeTryTask`, so the mock stays in force while the next file in the page is imported and runs
its top-level code and `beforeAll` hooks. Failure scenario: a file scheduled after either support
spec that triggers a download or a link click in a `beforeAll` (a shared fixture, a chunk warm-up
that navigates) silently gets the no-op, only on the schedules that put it there. No current
`beforeAll` does this, so it is latent. `client/README.md` ("would otherwise reach whichever files
the run happens to put after it") and the core-tools README describe the cross-file reach as closed
without that exception. Suggested fix: have both specs restore their own spies (in
`tm-support-dump.spec.ts`, `mockRestore()` both spies in the existing `finally`; in
`tm-diagnostics-panel.spec.ts`, keep the spy and call `onTestFinished(() => spy.mockRestore())` or
use a `try`/`finally`), and add one sentence to the core-tools README that a spy is restored before
the next test, not at its file's end, so a file must not leave a global patched after its last test.

### Responses

R1-1: fixed in fix1 (the commit titled "PC-F115: fix1 (R1-1, R1-2)"). Two behavioural canaries now
run in the projects that consume the preset: `client/projects/core/tellma-core/src/tm-unit-runner.spec.ts`
(core's unit project) and `distributions/acme/src/Tellma.Distro.Acme.Client/src/unit-runner.spec.ts`
(Acme's `vitest-base.config.mjs` re-exports the preset on its own, so it is a separate consumer).
In each, the first test mocks `HTMLAnchorElement.prototype.click` with `vi.spyOn` and stubs a probe
global with `vi.stubGlobal`, and restores neither. The second asserts that the prototype's method is
not a mock, that `click()` on a connected link dispatches one click event, and that the probe global
is gone. Verified with scratch runner configs that spread each workspace's preset and set the three
options to false: core's canary fails at the `isMockFunction` assertion, Acme's the same; with
`restoreMocks` on and `unstubGlobals` off, core's fails at the probe-global assertion; with the
committed preset, both pass. No env probe: `vi.stubEnv` writes the worker's internal `metaEnv`,
which the Angular-built spec can read only through Vitest internals, so it is not cheap; the
`unstubEnvs` option stays pinned by the tools-project preset test. The canary depends on Vitest's
default in-file order (`sequence.shuffle` off), which no config here changes.

R1-2: fixed in fix1. `tm-support-dump.spec.ts` keeps both spies and calls `mockRestore()` on each in
its existing `finally`; `tm-diagnostics-panel.spec.ts` keeps its click spy and restores it with
`onTestFinished(() => click.mockRestore())`, the pattern `tm-search-host.spec.ts` already uses. The
core-tools README now says the restore runs before the next test, not at a file's end, so a spy a
file's last test leaves is live during the next file's import and `beforeAll`, and a spec restores
spies it makes on shared page state at the end of the test that made it; client/README.md says the
same in one sentence and names the canary.

Fix 1 tests: the canary on/off runs above; every client unit project with `CI=true pnpm run test`
(core 159 files / 2983 tests, core-testing 9/49, core-ui 137/2778, core-ui test-csp 3/3,
core-ui-tokens 1/40, locale-ar 1/13, showcase 1/1), Acme `ng test` (3 files / 10 tests) and its
`pnpm run lint`, the tools Vitest project for `src/vitest` (14/14), client `pnpm run lint` and
`pnpm run api:check`: all green.
