# PC-042: Update and delete statements and the tree statements

## Implementer notes

### What was built, and where

- **Shared write plumbing** (`src/core/Tellma.Core/Data/Batches/DataBatch.Writes.cs`): the target entity (refused on Read and Validate batches), id validation (integral, distinct, in the key's range), `IdList`/`BigIdList` binding, the keys-only compile (`Select = key`, a `KeySetRestriction` when given, `OrderBy = key` + `Take` when capped), the not-found check, the count check, the recompile hint, and `AppendWrites`, which checks the parameter budget for all of a call's statements before appending any, sets each statement's `EntityType`, and marks the batch as needing its transaction.
- **Update** (`DataBatch.Updates.cs`, spec 0012 §9.1): `ByIds` (keys = ids ∧ `Filter`), `AllOrNothing` (a not-found statement under `ReadFilter`, then `50403` when the keys do not cover every id), and `ByQuery` (cap + 1 keys, then `50413`/`50428`, codes `Update.CapExceeded`/`Update.CountMismatch`). One `UPDATE … OUTPUT inserted.[Id]` skips rows already holding the values, null-safe, character columns compared under the binary collation. Stamps `ModifiedAt`/`ModifiedById` unless `Stamp = false`. Refuses the key, the audit and tree columns, `ParentId` of a tree, blob references, write-once, derived and database-owned columns, unknown names, an empty set, and values the column cannot hold. An activatable tree recounts (T3b, T5a, T5b over the keys) when `IsActive` is assigned.
- **Delete** (`DataBatch.Deletes.cs`, `Data/Writes/DeletePlan.cs`, `Data/Writes/DeleteText.cs`, spec 0012 §9.2): `ByIds` (UPDLOCK/ROWLOCK capture under `ReadFilter`, missing-ids result set + `50404`, the `Filter` count check, the stamp check with the save's conflict set and message), `ByQuery` (cap and count, `Delete.CapExceeded`/`Delete.CountMismatch`), `WithDescendants` (the roots' not-found check, the closure by `IsDescendantOf`, the `Filter` check over the closure). Then a tree's old nodes, the collections deepest first, the root with `OUTPUT deleted.[Id]`, the blob captures (`OUTPUT … INTO`, directly for one blob column, through a capture table for several), and a tree's recount. `DeleteHandle` names the keys table and the captures. The plan is cached per entity and declares the sibling tables, whose rows go by cascade.
- **Tree statements** (`Data/Trees/TreeText.cs`, spec 0012 §10.2–§10.3): T1–T5b after a save's root update (wired into `SaveText`; the save template's CTE names carry the `tb#_` marker the emitter replaces with the ordinal), `CaptureOld` + `Recount` for updates and deletes, and the whole-table recount for verify. `TreeShape` holds a tree table's columns and depth.
- **Verify** (`Data/Trees/TreeStatements.cs`, `TreeStatementsLog.cs`, §10.4): `TreeStatements.Verify(DataBatch, EntityMetadata)` appends the whole-table T5b on the internal channel, idempotent, and reads `[Repaired]`. Once it ran, it meters `tellma.data.tree.recomputes` and `tellma.data.tree.repairs`, and logs `TreeVerify.Repaired` at Warning when the count is positive. Registered as a singleton in `DataComposition`.
- **C# cycle check** (`Data/Trees/TreeCycleValidator.cs`, §10.4): `TreeCycleValidator<TEntity>` loads `(Id, ParentId)` of the whole table through `Loader.Rows` (skipped when every payload row is a root) and overlays the payload. It reports `Tree.Cycle` on each saved row that lies on a cycle (a self-parent included) and `Tree.TooDeep` when the row's depth plus its subtree's height passes `MaxDepth`, at `[i].ParentId`. Not registered: spec 0015's tree recipe does that.
- **Metrics** (`DataMetrics`): `tellma.data.rows.deleted` (root rows), `tellma.data.tree.recomputes` (one per write statement that ran tree text: saves, activations, deletes and verifies), and `tellma.data.tree.repairs`.
- **Errors**: `TellmaSqlErrors` gained the four update/delete cap and count codes. `DataBatch.Update`/`Delete` lost their `NotSupportedException` stubs. The transaction-mode refusal now names saves, updates and deletes.
- **Tests**:
  - Unit (`test/core/Tellma.Core.Tests/Data/Writes`, `Data/Trees`): golden SQL for every update and delete shape, the tree text after a save, the verify of an activatable and a plain tree; the parameters in order; the recompile threshold; receipts, missing ids and conflicts from canned result sets; metrics and the repair log; every refusal; and the validator against a fake loader.
  - `SaveModel` gained `Region`, a plain tree of depth 4 with a write-once column.
  - Integration (`test/core/Tellma.Core.IntegrationTests/Data/WriteStatementTests.cs`): not-found (absent and hidden), row security, stale stamps, children/grandchildren/sibling/blob captures in one round trip, delete by query cap and count, a referenced row (547), all-or-nothing updates, a repeated deactivation writing no history row, tree paths after a move, the cycle fence, the depth limit at exactly `MaxDepth`, counts after deactivation and a delete with descendants, a parent deleted without its descendants (547), and verify repairing injected drift.
  - `SaveEmitterTests`' tree test now asserts real paths (`/root/`, `/root/leaf/`) instead of provisional ones. `SaveStatementTests`' provisional-node test now allows the one node assignment, the re-path.

### Deviations

1. **A call is one or two statements.** A check that embeds a compiled body sits in its own statement, so each body binds its engine parameters (`@qx{b}_…`) at its own ordinal. Two bodies at one ordinal would collide. So: an all-or-nothing update is a not-found statement, then the update; a delete by ids or with descendants is the key capture and its 404, then the delete. A by-ids update without all-or-nothing and either by-query shape stay one statement. The whole call is still one round trip (§5.6).
2. **The not-found check is `SELECT … NOT IN (…)` then `IF @@ROWCOUNT > 0 THROW 50404`.** The spec compares counts, and for `WithDescendants` it repeats the body inside `IF EXISTS`. This form reads the body once, and keeps a recompile hint on the one statement that embeds it.
3. **The grant check counts into a variable** (`SELECT @tb{b}_n = COUNT(*) FROM (<body>) AS [q] [OPTION (RECOMPILE)]`, then `IF @n <> …`). This follows the assert pattern: a body that needs `RECOMPILE` cannot carry the hint inside an `IF`.
4. **A by-query capture uses the compiled query's own `Take` (cap + 1, ordered by key) rather than `TOP (@p + 1)` around it.** The engine binds `@qx{b}_take`. The cap and the expected count are still statement scalars that the checks compare against.
5. **`MAXRECURSION` is `MaxDepth − 1`, not `MaxDepth`.** A walk takes one recursion step per level below its first row, and T5a climbs from every affected node to its root. With `MaxDepth − 1`, exactly a row deeper than the limit raises 530. With `MaxDepth`, a row one level too deep would pass. The integration test saves a chain of exactly 8 under `[Tree(MaxDepth = 8)]` and refuses the ninth.
6. **The update's skip-unchanged predicate is `EXISTS (SELECT stored EXCEPT SELECT assigned)`, binary-collated for strings**, rather than `t.[IsActive] <> @p0`. It is null-safe, covers several assignments, and matches the save's comparison.
7. **The update recount runs only when an activatable tree's `IsActive` is assigned.** Other assignments cannot change the counts, and `ParentId` is refused (a save re-paths). The spec appends the recount to every tree update.
8. **Assigning a tree's `ParentId` through `Update` is refused**, since the re-path is a save's (T1–T4). The spec does not say either way.
9. **Delete stamps need an `int` key.** There is no `BigIdStampList` table type, so a long-key entity with `ExpectedStamps` is refused at compose time. A null stamp, or a stamp count that differs from the id count, is refused too.
10. **A delete declares its sibling tables in its writes.** The cascade writes them, and the batch's write set (the tags, the fixtures' change-tracking audit) must include them.
11. **`tellma.data.rows.deleted` counts root rows**, the receipt's ids, not the collection rows that went with them.
12. **`TreeStatements.Verify` takes the batch it appends to** (`Verify(DataBatch, EntityMetadata)`, returning `BatchResult<int>`). The spec writes `Verify(metadata)`. A statement needs a batch, and spec 0020's job supplies a maintenance batch.
13. **`TreeCycleValidator<T>` lives in `Tellma.Core.Data.Trees`** (internal), not `Tellma.Core.Data`. It reports `Tree.Cycle` only on rows that lie on a cycle, not on rows that merely sit under one: the rows that close it are always in the payload, and an error on a row that only points into the cycle would misdirect the user.
14. **`SubtreeCount` and `ActiveSubtreeCount` assignments are refused** with the stamps. The spec lists only write-once and blob references, but these are the tree statements' to keep.
15. **The `WithDescendants` closure is captured `WITH (UPDLOCK, ROWLOCK)`**, on the descendants and on the roots, as a by-ids capture is. The spec gives no hint. Without one, a concurrent move out of the subtree between capture and delete is undone (review 1, R1-3).
16. **A delete checks write authority over the aggregate's own tables only.** A sibling's table stays among the declared writes, for tags and change tracking, but its rows go by the cascade its owning feature declared, so a stack that owns a sibling never has to authorize its owner's deletes (review 1, R1-4).

### Open risks

- **The stamp comparison names `[ModifiedAt]` literally**, as the save's guard does, not the mapped column of the `ModifiedAt` property. The two agree across the model today.
- The update's T3b capture reads the same nodes the recount anchors on, since an update moves no row. It is redundant but harmless, and keeps T5a's text identical for every caller.
- `TreeCycleValidator` holds the whole table's parents in memory: O(rows) per validated save. The spec chooses that, but it matters for a very large tree.

### What reviewers should examine hardest

- **Ordinal arithmetic in `DataBatch.Updates.cs` and `DataBatch.Deletes.cs`.** The second statement refers to the first statement's `@tb{k}_t0` and `@tb{k}_keys`, compiles for `ordinal + 1`, and `AppendWrites` asserts that each draft's ordinal matches. A prologue statement appended later than expected would break the plan, so `WriteTarget` runs `EnsurePrologue()` before ordinals are read.
- **Parameter order versus the text's numbering** (`@tb{b}_p0…`): assignments, then the user, then cap and count. `BindIds`/`draft.Table` and `draft.Scalar` must run in that order. The goldens pin it.
- **The depth arithmetic** (`MaxDepth − 1`) in T2 and T5a, and the claim that T5a bounds absolute depth for every tree save, update and delete.
- **The readers**: a delete's conflict set appears only before its `THROW`. The missing-ids set is always present, empty on success.
- **`DeletePlan`'s sibling discovery** (`SiblingAttribute.Owner.IsAssignableFrom`) and its capture naming, which `DeleteHandle.Captures` exposes to later statements.

**Major**

- **R1-1 (major, PLAN.md §7.1 item 4): every integration suite counts as touched, but the commit
  lists one.** `src/core/Tellma.Core.Abstractions/Data/TellmaSqlErrors.cs:73-83` adds four

  `Tellma.Core.Queryex.IntegrationTests`, `Tellma.Distro.Acme.IntegrationTests` and the
  connector suites (acs-email, marmin-ae, sendgrid) are missing from it. The risk to those suites
  from four new constants is close to nil, but the gate is explicit and reviewers check the list.
  Fix: run each of those suites with
  `--filter "Category=Integration&Category!=Nightly&Live!=true"`, one at a time, and list them in
  the commit message.

- **R1-2 (major, test adequacy, 0012 §13.3 Trees): no test covers "a saved row whose parent is a
  descendant of another saved row is pathed once".** The checkpoint's test list names this case,
  and it is the reason T1 exists (0012 §10.2: otherwise such a row "would read a stale parent node
  and be pathed twice"). `WriteStatementTests` never saves two existing rows in one payload. The
  move test (`test/core/Tellma.Core.IntegrationTests/Data/WriteStatementTests.cs:219-236`) saves
  `child` alone. `SaveEmitterTests.A_tree_payload_with_temporary_ids_…` saves two new rows whose
  parent is itself in the payload. Neither covers an existing row whose parent is not in the payload
  but is a descendant of a moved row in it. A regression there would pass every current test:
  for example, T1 dropping the `IsDescendantOf` arm, or T2 anchoring on rows whose parent is in the
  affected set. Fix: an integration test that builds `root → a → b → c` plus `other`, then saves
  `[a (ParentId = other), c (renamed)]` in one payload. Assert `c`'s path is `/other/a/b/c/`, that
  `b`'s path moved too, and that the counts of `root` and `other` are right.

**Minor**

- **R1-3 (minor, correctness under concurrency): the `WithDescendants` closure is captured
  without locks, so a concurrent move out of the subtree is silently undone.** See
  `src/core/Tellma.Core/Data/Batches/DataBatch.Deletes.cs:290-295`, already listed under the
  implementer's open risks. Scenario: transaction A deletes root R with descendants, and its
  statement 1 captures X, which sits under R, into `@tb{b}_keys`. Transaction B then saves X under a
  parent outside R's subtree (T4 re-paths it) and commits. A's `DELETE … WHERE t.[Id] IN (keys)`
  then deletes X. B reported success, X is gone, and no FK fires, because X's new parent survives.
  No serial order gives that outcome. Under `ByIds` the `UPDLOCK, ROWLOCK` capture blocks the same
  race. Fix: take `WITH (UPDLOCK, ROWLOCK)` on `d`, and on the roots `a`, in the closure insert.
  `IsDescendantOf` against an indexed `hierarchyid` (`UX_<Table>_Node`) is a range seek per root,
  so the U locks stay on the closure's rows. Under read committed, a U lock on a scanned row that
  fails the predicate is released at once. Record it as a deviation, since the spec text has no hint here. If it
  stays as is, record the race in DECISIONS for Ahmad.

- **R1-4 (minor, deviation 10 interacting with write authority): a delete is refused when its
  owner's sibling table is owned by another stack.** `DataBatch.Deletes.cs:35` runs
  `CheckAuthority(plan.Writes)`, and since deviation 10, `plan.Writes` includes the `[Sibling]`
  tables (`Data/Writes/DeletePlan.cs:34-42`). Per 0012 §2.2, a sibling's writer is "the feature
  that owns it". If that feature exposes the sibling as a stack root, `IStackRegistry.OwnerOf` maps
  the table to that stack. Every caller-channel delete of the owner is then refused at append, with
  a message telling the caller to enlist a write that it cannot enlist: the database cascade
  performs it. No such stack exists yet, so nothing fails today. Fix: check authority over the
  aggregate's own tables (`plan.Nodes`), and keep the siblings in the declared writes for tags and
  the change-tracking audit. Alternatively, raise it with the 0015 owner as a question.

- **R1-5 (minor, error path): an assigned value too long for its column reaches SQL as a 500.**
  `Assigned` (`src/core/Tellma.Core/Data/Batches/DataBatch.Updates.cs:268-276`) checks only the
  CLR type, although its summary and the implementer notes say values "the column cannot hold" are
  refused. Assigning a 300-character string to `Name` (`[MaxLength(255)]`) composes cleanly. At
  execution it raises SQL error 2628, which surfaces as a final `DataAccessException` (500) instead
  of a compose-time `ArgumentException`. `PropertyMetadata.MaxLength` is available. Fix: refuse a
  `string` (or `byte[]`) whose length exceeds `property.MaxLength`, and add an `InlineData` row to
  `A_value_its_column_does_not_hold_is_refused`.

- **R1-6 (minor, test adequacy, 0012 §13.3 "Deletes and updates"): an update by query is never
  run in SQL except for its cap refusal.** The integration test
  (`WriteStatementTests.cs:184-188`) asserts only `Update.CapExceeded`. Two cases run only as
  golden text (`UpdateStatementTests.cs:120-154`): `Update.CountMismatch` (50428), and a successful
  by-query update. The successful case is where the cap-plus-one `OFFSET 0 ROWS FETCH NEXT
  @qx{b}_take` capture feeds the `UPDATE`. A wrong scalar index in `CapChecks` (the cap sits at
  `assigned.Count + 1` when stamping) would bind the user id as the cap and still match a golden
  regenerated from the code. Fix: in the integration test, add a by-query update with a wrong
  `ExpectedCount` (assert 50428 and no row changed) and one that matches (assert `UpdatedIds` and
  the stored values).
