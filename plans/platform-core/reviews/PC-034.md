### Rulings (not obvious from the spec)

1. **Locks.** Both applocks are session locks held on a catalog connection:
   `tellma:migrate:catalog` and `tellma:migrate:tenant:<id>`. The catalog lock covers the role,
   principal, catalog and identity migrations, grants, the registry reload and seed registration,
   and is released before tenants fan out, so a fleet run and a `provision` only serialise per
   tenant.
2. **Registry load.** The migrator host sets `LoadOnStart=false` because `migrate` may have to
   create the catalog; every command force-refreshes when it needs the registry.
3. **`provision`.** `--server` requires `--database`; `--database` alone means the catalog's
   server. Rerunning on an `Active` or `ReadOnly` tenant prints `provisioned (already)` and exits 0;
   any other non-`Provisioning` state exits 2.
4. **Principal, RCSI and Query Store** are applied only to a database this run found fresh (no
   catalog schema / no history table), never re-imposed on an operator-tuned database. RCSI on the
   catalog likewise.
5. **Fingerprint retention.** "The two newest" is the current model's row plus the newest other row.
   "Ahead" is decided from the history table after `Migrate()`: a database whose history does not
   end at this migrator's last migration gets no fingerprint row and is reported `ahead`, and no
   seed, step or scan runs on it; `provision` refuses one (exit 2).
6. **Exit 3** covers every composition exception on every command (at `AddTellma`, at the gate,
   and in emit). `status` exits 3 on `TellmaComposition.Validate` problems and 2 when a database
   cannot be read.
7. **`set-state`**: a malformed `--reason` is a usage error (exit 1); an illegal transition or an
   unknown tenant is exit 2.
8. **Emit.**
   - The defaults cover all three chunks (core sections, `entities`/`enums`, `fingerprints`/
     `long`/`idempotent`) so a composition with no contributor still yields a loadable bundle.
   - A contributor file at the module path or under `assets/`, or a core section named
     `formatVersion`, is a composition problem.
   - Stale emitted assets (names matching the emitted pattern) are swept; unchanged files are not
     rewritten, so the output directory's timestamps stay stable.
   - `strings: {}` until string packs exist; the emit composes as `Production` unless the settings
     say otherwise; an IO failure is exit 2.
9. **Test distribution.** The slug is `acme` because the Development taxonomy check refuses any
   slug `taxonomy.json` does not list. The three-migrations fingerprint test uses synthetic history
   rows plus `SchemaFingerprints.RecordAsync`, because only one real migration exists. The executor
   guard that refuses an unlisted fingerprint is already covered by `DataBatchTests`.
10. **Job worker.** No worker exists yet; the test asserts the flag is forced to false in the
    host's configuration after every distribution source.

### Deviations

- Spec 0011 says a `dotnet ef database update` design database "has no `tellma_app`". The planner
  note (and the catalog factory pattern) requires the design-time factories to create the role,
  since every table type's migration grants `EXECUTE` to it; the factories do, and the README
  says so.
- The version-tag seed, drift scan, administrator invitation and step write frame are internal seams
  with no implementation yet (their checkpoints come later); the migrator skips each while none is
  registered.

### ARCHITECTURE.md

  host with the job flag forced off, and its exit codes are stated.
- The concurrency guard is two named session applocks held in the catalog, not a lock in each
  tenant database.

### Findings

**R1-1 (major): the tenant's state is decided before its tenant lock is taken, so overlapping runs re-provision an active tenant.**
`src/core/Tellma.Core.Migrator/Commands/ProvisionCommand.cs:64-76` reads the row and branches on
`Provisioning` before `TenantMigration.ProvisionAsync` takes the lock
(`src/core/Tellma.Core.Migrator/TenantMigration.cs:50-52`). Nothing re-reads the state under the
lock. `MigrateCommand.cs:58-60` (seeds) and `:69-96` (fan-out) do the same.
- Scenario: two `provision --tenant 5` runs, a pipeline retry, or the self-serve starter racing an
  operator. Both see `Provisioning`. A takes the lock and turns the tenant `Active`. B then takes
  the lock and runs the whole flow again: `isNew: true`, a second membership hint, a second
  administrator invitation once `ITenantAdministratorInviter` is registered, and finally
  `SetStateAsync(Active)` from `Active`. `TenantStateTransitions.IsLegal` refuses that, so B exits
  2 although the tenant converged.
- The same applies to two overlapping `migrate` runs with seeds.
- In the fan-out, a tenant frozen for relocation between `ListAsync` and its lock is still migrated
  as `Active`. §6.1 says a frozen tenant is skipped.
- The concurrency guard exists precisely for overlapping runs.
- Fix: re-read the tenant row (`ITenantCatalog`, not the snapshot) right after
  `MigrationLock.AcquireAsync` in both `ProvisionAsync` and `MigrateAsync`, and dispatch on that
  state. Under the lock, `Active`/`ReadOnly` in provision means "provisioned (already)", and
  `Frozen`/`Provisioning` in migrate means the corresponding report.
- Test: two concurrent `provision --tenant` runs end with exit 0 and the step run once.

**R1-2 (major): a `TaskCanceledException` that is not the run's cancellation aborts the whole fleet run.**
`TenantMigration.cs:205` filters `when (exception is not OperationCanceledException)`, and
`MigrateCommand.cs:44` does the same.
- Scenario: an `HttpClient` timeout throws `TaskCanceledException`. Sources include the
  administrator invite, a step calling the identity server, or a blob-container step. So does a
  SqlClient-internal cancellation that is not the run's token.
- That exception escapes `GuardAsync` and faults `Parallel.ForEachAsync`, which cancels every other
  tenant in flight.
- `TellmaMigrator.cs:163` then prints "stopped before it finished" with no per-tenant report.
- This breaks "continues past failures, per-tenant report" (§6.1).
- `ProvisioningStepRunner.cs:100` already uses the right filter, but only for logging.
- Fix: thread the token into `GuardAsync` and catch
  `when (exception is not OperationCanceledException || !cancellationToken.IsCancellationRequested)`,
  in `MigrateCommand`'s catalog catch as well.
- Test: a probe step that throws `new TaskCanceledException()` on tenant 1 still lets tenant 2
  migrate, and the run exits 2 with both lines.

**R1-3 (major): `provision --tenant <id> --name … --category …` does not converge on a rerun.**
`ProvisionCommand.cs:46-57` always calls `RegisterAsync` when `--name` is given.
- Scenario: the first run registers tenant 5 and then fails in a step or a migration, leaving the
  row `Provisioning`. Rerunning the same command line hits the PK in `RegisterAsync`
  ("the requested id 5 is taken"), and the run exits 2.
- The same command after success also exits 2, where ruling 3 promises `provisioned (already)`.
- §6.1 says "Idempotent: rerunning converges".
- `MigratorTests.cs:136` only reruns with `--tenant` alone, so the suite does not see this.
- Fix: with `--tenant` and `--name`, read the row under the catalog lock first. When it exists with
  the same name and category, skip the registration and fall through to the resume/already path.
  Refuse only a mismatching existing row.
- Test: rerun the exact registering command line after a failed step and after success.

**R1-4 (major): several spec rules have no test that would fail if they broke.** Each missing test
below is in `test/core/Tellma.Core.IntegrationTests/Migrator/MigratorTests.cs`.
- §6.4/§6.7: `provision` turns Query Store on in a fresh tenant database. Nothing asserts
  `sys.database_query_store_options.actual_state_desc = 'READ_WRITE'` or its settings.
- Ruling 4 / §6.7: RCSI, Query Store and the principal are applied only to a fresh database.
  Nothing provisions into an existing database that already has history, or has RCSI/QS off, and
  asserts they are left alone.
- §6.4: `Sql:ApplicationPrincipal` creates the user `FOR LOGIN` and adds it to `tellma_app`. There
  is only a text test. LocalDB can create a SQL or Windows-mapped login for the test.
- §6.1: a `Frozen` tenant is skipped and reported `frozen`, even when named. `provision` refuses an
  ahead database (ruling 5).
- §7.5: two overlapping runs serialise on the tenant lock. This would also have caught R1-1.
- §6.4 "recomputed after every run": nothing revokes a grant, reruns `migrate`, and asserts it is
  back.
- The fingerprint "two newest" test drives `SchemaFingerprints.RecordAsync` directly, which is an
  accepted deviation.
- Fix: add these tests.

**R1-5 (minor): some failures escape `RunAsync` instead of mapping to the 0/1/2/3 exit codes.**
- `EmitClientAssetsCommand.cs:99` (`WriteAsync`) is not wrapped. `TellmaMigrator.cs:95` calls the
  emit outside any try, so an `IOException` or `UnauthorizedAccessException` (read-only or locked
  `generated/`) is an unhandled exception, not the exit 2 that ruling 8 states.
- `builder.Build()` (`TellmaMigrator.cs:139`) is outside every try. Development's `ValidateOnBuild`
  throws `AggregateException`.
- A non-composition exception from `host.StartAsync` (`:142-148`) also escapes, for example a
  hosted service that fails to start.
- Each crashes the process with the runtime's unhandled-exception code instead of a documented one.
- Fix:
  - Catch IO exceptions around the emit's writes and return `PartialFailure` with the message.
  - Move `Build()` into the try.
  - Add a general catch after the `TellmaCompositionException` catch at start that returns
    `PartialFailure`, or `CompositionProblems` for build validation errors.

**R1-6 (minor): a lost lock session goes unnoticed.**
`src/core/Tellma.Core.Migrator/Sql/MigrationLock.cs:66-97` holds each lock on an idle, non-pooled
connection for the whole tenant run (migrations may take up to an hour, `TenantMigration.cs:30`).
- Scenario: the catalog fails over, or the connection is reset mid-run. SQL Server releases the
  session lock, but the migrator keeps going and writes the fingerprint, the steps and the `Active`
  state, while a second run can take the same lock. `DisposeAsync` swallows the resulting
  `SqlException`.
- Fix: add `MigrationLock.EnsureHeldAsync()`
  (`SELECT APPLOCK_MODE('public', @resource, 'Session')` on the lock's connection, expecting
  `Exclusive`). Call it before the fingerprint, before the steps and before `SetStateAsync`, and
  fail the tenant when the lock is gone.

**R1-7 (minor): the same step class contributed by two features is silently merged.**
`src/core/Tellma.Core/Composition/Realizers/ProvisioningStepContributionRealizer.cs:42-46` drops
the second registration.
- §6.2 says "a step with the same name registered twice is a composition problem".
- The commit's own XML doc on `FeatureContribution.ProvisioningStep<TStep>()` says "a second step
  with the same name anywhere in the composition is a startup problem".
- `ProvisioningStepsCheck` only sees distinct classes, so it never reports this case.
- Fix: report a composition problem when a class is contributed again by a different feature (or
  twice by one). Otherwise state the merge as a deviation and correct the XML doc.
- Test: add the case to `ProvisioningStepsCheckTests`.

**R1-8 (minor): spec references in XML docs (PLAN §7.1 item 5).**
New `///` comments cite `spec 0011 §…` / `spec 0012 §4.3` / `spec 0024 §3.x` in:
- `Commands/EmitClientAssetsCommand.cs:21-22`
- `Commands/MigrateCommand.cs:23`
- `Commands/ProvisionCommand.cs:18`
- `Commands/SetStateCommand.cs:14`
- `Commands/StatusCommand.cs:22`
- `Emit/ClientAssetBundle.cs:21,51`
- `Sql/ApplicationGrants.cs:16`
- `Sql/MigrationLock.cs:15`
- `Sql/SchemaFingerprints.cs:20-21`
- `Sql/TargetDatabase.cs:16`
- `TenantMigration.cs:24`

All are under `src/core/Tellma.Core.Migrator/`.

Fix: drop the citations from the XML docs, keeping them as `//` comments where useful.

**R1-9 (minor): a step's completion is not recorded in its own transaction, contrary to the notes.**
The implementer notes say each step runs "in one transaction with its `dbo.__TellmaProvisioning`
row". In `ProvisioningStepRunner.cs:96-111`, the step's writes commit first, and the record is then
written in a separate transaction on a new connection. A crash or connection failure between the
two re-runs a step that completed. That is tolerable only because steps must be idempotent, and
ARCHITECTURE.md calls the steps "transactional".
- Fix: correct the notes and the runner's remarks to say a completion is recorded after the step
  commits, so a crash in between re-runs the step.
- Also add a WATCHLIST lead for PC-077: enlist the record write in the step's Provisioning frame,
  so step and record commit together.
