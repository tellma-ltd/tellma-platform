### Rulings (not obvious from the spec)

1. **Locks.** Both applocks are session locks held on a catalog connection:
   `tellma:migrate:catalog` and `tellma:migrate:tenant:<id>`. The catalog lock covers the role,
   principal, catalog and identity migrations, grants, the registry reload and seed registration,
   and is released before tenants fan out, so a fleet run and a `provision` only serialise per
   tenant.
2. **Registry load.** The migrator host sets `LoadOnStart=false` because `migrate` may have to
   create the catalog; every command force-refreshes when it needs the registry.
3. **`provision`.** `--server` requires `--database`; `--database` alone means the catalog's
   server. Rerunning on an `Active` or `ReadOnly` tenant prints `provisioned (already)` and exits 0;
   any other non-`Provisioning` state exits 2.
4. **Principal, RCSI and Query Store** are applied only to a database this run found fresh (no
   catalog schema / no history table), never re-imposed on an operator-tuned database. RCSI on the
   catalog likewise.
5. **Fingerprint retention.** "The two newest" is the current model's row plus the newest other row.
   "Ahead" is decided from the history table after `Migrate()`: a database whose history does not
   end at this migrator's last migration gets no fingerprint row and is reported `ahead`, and no
   seed, step or scan runs on it; `provision` refuses one (exit 2).
6. **Exit 3** covers every composition exception on every command (at `AddTellma`, at the gate,
   and in emit). `status` exits 3 on `TellmaComposition.Validate` problems and 2 when a database
   cannot be read.
7. **`set-state`**: a malformed `--reason` is a usage error (exit 1); an illegal transition or an
   unknown tenant is exit 2.
8. **Emit.**
   - The defaults cover all three chunks (core sections, `entities`/`enums`, `fingerprints`/
     `long`/`idempotent`) so a composition with no contributor still yields a loadable bundle.
   - A contributor file at the module path or under `assets/`, or a core section named
     `formatVersion`, is a composition problem.
   - Stale emitted assets (names matching the emitted pattern) are swept; unchanged files are not
     rewritten, so the output directory's timestamps stay stable.
   - `strings: {}` until string packs exist; the emit composes as `Production` unless the settings
     say otherwise; an IO failure is exit 2.
9. **Test distribution.** The slug is `acme` because the Development taxonomy check refuses any
   slug `taxonomy.json` does not list. The three-migrations fingerprint test uses synthetic history
   rows plus `SchemaFingerprints.RecordAsync`, because only one real migration exists. The executor
   guard that refuses an unlisted fingerprint is already covered by `DataBatchTests`.
10. **Job worker.** No worker exists yet; the test asserts the flag is forced to false in the
    host's configuration after every distribution source.

### Deviations

- Spec 0011 says a `dotnet ef database update` design database "has no `tellma_app`". The planner
  note (and the catalog factory pattern) requires the design-time factories to create the role,
  since every table type's migration grants `EXECUTE` to it; the factories do, and the README
  says so.
- The version-tag seed, drift scan, administrator invitation and step write frame are internal seams
  with no implementation yet (their checkpoints come later); the migrator skips each while none is
  registered.

### ARCHITECTURE.md

- The migrator now has five commands (`emit-client-assets` added), runs inside a started generic
  host with the job flag forced off, and its exit codes are stated.
- The concurrency guard is two named session applocks held in the catalog, not a lock in each
  tenant database.
