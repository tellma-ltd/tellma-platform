# PC-F100: Route skeleton on first tenant entry

## Implementer notes

### Root cause (confirmed)

The tenant route's `loadComponent` is `tmShellRoute('TmTenantShell')`. It returns the component
itself only once `loaded.TmTenantShell` is set, and only the `TmTenantShell` loader sets it. On
`/tenants` the shell module is in memory (the picker came through it), but nothing had called that
loader: `TmUrls.preload`'s `#loadersOf` returned `[TM_ROUTE_HOSTS.home]` for a `home` match and
nothing that warms the tenant shell for any tenant match. So the click's navigation waited on
`import('@tellma/core/shell')` and its `.then` hops, and the tenant shell with its route host and
`tm-page-skeleton` activated a task later, in frame 2 or 3.

A new unit spec reproduces it: with the fix to `tm-urls.ts` reverted, `tmShellRoute('TmTenantShell')()`
after `preload('/17')` and its idle callback is still a promise (failed alone and again in an
8-file run beside `tm-urls.spec` and `tm-route-hosts.spec`, which load the shell, so the runner
keeps module state per file and the test cannot pass by another file's load).

### What was built

- `client/projects/core/tellma-core/src/routes/tm-route-hosts.ts`: `TM_TENANT_SHELL`, one shared
  `tmShellComponent('TmTenantShell')` loader (internal; not exported from the public API).
- `client/projects/core/tellma-core/src/urls/tm-urls.ts`: `#loadersOf` puts `TM_TENANT_SHELL`
  first for every match with a `tenantId`. It is one function, so `#preloaded` loads it once for
  every route. TSDoc of `preload` updated.
- `client/projects/core/tellma-core/shell/src/tenantless/tm-tenant-picker.ts`: an effect that,
  once the first frame has rendered (`#rendered`) and the rows hold a Connect, calls
  `TmUrls.preload` once with the first enabled row's home. It covers the stored list (first frame)
  and the no-cache path (when the read brings the first Connect). Hover and focus preloads are
  unchanged. One preload suffices: every tenant's home needs the same chunks (`#loadersOf` for a
  `home` match is tenant-independent).
- Tests:
  - `src/urls/tm-urls-preload.spec.ts` (new, own file because the shell's `loaded` map persists
    for a file and `tm-urls.spec` enters a tenant before every test): after `preload('/17')` runs
    at idle, `tmShellRoute('TmTenantShell')()` returns the `TmTenantShell` type, not a promise.
  - `tm-tenant-picker.spec.ts`: the render preloads `/17` once, skipping a first row without
    Connect, and not again when the read re-renders the rows; with nothing stored it preloads only
    once the read brings the first Connect; the hover test now clears the render's preload before
    it hovers, so it still proves the hover preload.

### Deviations

- Spec 0024 §9.4 lists what `preload` loads (the host's chunk, the declaration's layout and hatch
  chunks, the Entities chunk) and not the tenant shell, though §4.4's first frame needs it. Fixed
  in code: `preload` also loads the tenant shell on every tenant route.
- Spec 0027 §6.2 says hover and focus on Connect call `TmUrls.preload`. The picker also calls it
  once at idle after its first frame shows a Connect (spec 0024 §4.3 step 4's idle preloads), since
  a click can beat a hover's idle callback.

### Open risks

- The render preload is still `requestIdleCallback`-based. On a main thread that never goes idle
  between the picker's first frame and the click, the first entry can still miss the frame. In a
  real browser the tenant shell's load on the picker is microtasks only (its module is already
  evaluated, since the picker came through it), so the idle callback is the only wait.
- Under the lazy-delay harness the gate misses 3 runs in 14 (frame `Infinity`, the skeleton not
  within 10 frames). The harness delays every `import()` by 300 ms, including the
  `import('@tellma/core/shell')` of a module already in memory, so the preload's load lands about
  300 ms after the picker's first idle; Playwright's click sometimes comes before that. This is the
  same harness artifact as the warm-launch:82 ruling: no real browser waits on an import of an
  evaluated module, and the plain run passes 6 of 6. I did not change the gate or add a second
  mechanism for it.
- Local Windows only: `automatic-entries.spec.ts:107` ("a typed tenant that is not the user's …")
  failed in 3 of 5 chromium runs (0 of 5 in chromium-ar). It goes straight to `/99` and never
  touches the picker or a preload. The host answered every `/99` call with `404 tenant-not-found`
  within 200 ms, and the page stayed on `/99`. This is the known local flake whose cause is the
  service worker holding requests on localhost until its prefetch group ends, fixed on
  pc/PC-123 (fix1, `serviceWorkers: 'block'`), not yet on platform-core.

### What reviewers should examine hardest

- Whether `#rendered` is the right gate for "after the first render" (it flips in a microtask
  after `afterNextRender`, which also starts the read), and that the effect never preloads twice.
- That `TM_TENANT_SHELL` and the route table's `tmShellRoute('TmTenantShell')` share the `loaded`
  map, so a preload makes the route synchronous.
