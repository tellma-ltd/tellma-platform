# PC-113: TmRequestLog, TmAppVersion, Copy diagnostics text and platform measurements

## Implementer notes

### What was built

Spec 0026 §5, §7 and §8.1–§8.3 in the `@tellma/core` primary and three of its lazy chunks
(`client/projects/core/tellma-core/src/`).

- **`TmAppVersion`** (`requests/tm-app-version.ts`, primary). `ui`, `display`, `label`, `commit`,
  `platform`, `features` are getters over `TmClientMetadataStore.peek()` (empty before the Core
  chunk loads); `server` and `serverNewer` are signals; `compare(build)` is SemVer 2.0 precedence
  ignoring build metadata, `null` for the same version from another commit. `tmCompareBuilds`
  moved here from `api/tm-api-verdict.ts`; `tmBuildVerdict` now takes the order, and
  `TmHttpApi.#verdict` gets it from `TmAppVersion.compare`, so the order ships once.
- **`TmRequestLog`** (`requests/tm-request-log.ts`, primary). The quiet default is replaced by
  `TmAppRequestLog` (root `useFactory`): a signal ring of 100, newest first; `begin` adds a pending
  record and a 3 s timer that marks it slow; `end` (second call a no-op) records duration,
  outcome, status, code, keeps `slow` sticky, and hands `serverBuild` to `TmAppVersion.ɵserver`.
  Timers clear on the root `DestroyRef`. `diagnosticsText(count = 10)` and `copy(trigger =
  'button')` are primary code (fix1, R1-1): `copy()` calls `navigator.clipboard.writeText`
  synchronously inside a try, then one toast (success 4 s, failure sticky, shared toast key) and,
  on success, `tm.support.diagnostics-copied { via }`. `ɵstart()`, called from `tmStartup` before
  the first navigation, registers the global shortcut `tm.support.copy-diagnostics`
  (`Mod+Alt+Shift+D`, `inFields`, `overModals`).
- **Copy diagnostics text** (`requests/tm-diagnostics.ts`, primary). `tmDiagnosticsInput(injector,
  requests)` reads every source untracked; `tmDiagnosticsText(input, count)` is a pure formatter
  (English, Latin digits, device local time with the offset in the header, `tmStripBidiControls`
  over the result). The `tm.diagnostics` strings (`copy`, `copied`, `copyFailed`) are in
  `TM_STRINGS_EN`; Arabic strings added to `@tellma/locale-ar/platform-strings`
  (`strings-tm-ar.ts`).
- **Page visits** (`observe/tm-page-visits.ts`, primary, started in `tmStartup` before the first
  navigation). One sampled `tm.page.visit` timing per routed page, ended at the next
  `NavigationStart` or `pagehide`: `ms` to the context's first status away from `loading`,
  `chromeMs` to `afterNextRender` + one rAF after the context registers, `visitS` in tenths,
  `entry` `load|navigation`, `outcome` `ready|error|left`.
- **Load metrics** (`observe/tm-load-metrics.ts`, lazy chunk `tm-load-metrics`, loaded at idle).
  Buffered `PerformanceObserver`s for `paint` and `largest-contentful-paint`; finalised once at
  the first `keydown`/`pointerdown` or `visibilitychange` to hidden (with `takeRecords`); emits
  sampled `tm.vitals.load` with only the metrics the browser exposes.
- **Request outcomes** (`requests/tm-request-measures.ts`, statically imported by the pipeline, so
  inside the `tm-telemetry-pipeline` chunk). The pipeline's host gains `requests()`; an effect in
  `tmStartTelemetry` calls `pipeline.measure()` on every change of the log; each `flush()` first
  records the window's `tm.api.requests` (20 busiest routes); slow requests become `tm.api.slow`
  as they settle (20 per tab per 10 min, the rest counted as `throttled` drops); `pipeline.pagehide()`
  records slow requests still pending before flushing. Both events are unsampled and go through the
  pipeline's reserved-property guard.
- **Docs.** `tellma-core/README.md` (entry-point table row, the HTTP layer's chunks, a platform
  measurements list, a new "The request log and Copy diagnostics" section, the Seams paragraph);
  `ARCHITECTURE.md` `@tellma/core` row (the new chunks and what stays in the primary).
- **Budgets** (`tellma-core/package.json`, as of fix1). Primary 50.17 → 53.22 (51,364 B before,
  53.21 KB after, gzip 9 cap 53.12 of 55); `tm-telemetry-pipeline` 5 → 5.5 (4.50 → 5.32); new
  `tm-load-metrics` 1 (0.80); `tm-api-verdict` lowered 1 → 0.5 (0.51 → 0.17). Arabic `./platform-strings` 3.45 → 3.54 of 4, no raise.

### Deviations

1. Withdrawn in fix1 (R1-1): Copy diagnostics is primary code again, as §1 and §8.3 place it.
2. `TmRequestLog.copy(trigger?)` takes what triggered it (`TmDiagnosticsTrigger`, default
   `button`) for the event's `via`; the spec's `copy()` has no parameter.
3. `TmAppVersion.commit` accepts 7–40 hex digits (lowercased) rather than exactly 40; `label`
   shows the first 7. Members are getters over the metadata store, empty before it loads.
4. The SemVer order moved from the `tm-api-verdict` chunk into `TmAppVersion.compare`;
   `tmBuildVerdict` takes the order instead of the two builds.
5. Request outcomes live in the telemetry pipeline's lazy chunk. `tm.api.requests` is per tenant
   and route (a batch carries one tenant); `api` is the route without its query; `failed` is an
   error the server answered (a status), `network` one with no status. A slow event's `at` is the
   request's settle time.
6. A slow request reported `pending` at `pagehide` is not reported again if the page comes back
   and it settles.
7. Page visits: a `left` visit's `ms` is how long it was waited for (the visit's length); a
   visit that registered no context but whose navigation got past its guards and resolvers, or
   was skipped or redirected (the launch page's redirect), is not reported and passes its start
   and entry to the next; one abandoned before that is reported as `left` (fix1, R1-3); a
   navigation that keeps its page (a reused route) adopts the kept context one render after the
   navigation ends, if it is still the latest navigation (fix1, R1-4).
8. Diagnostics text beyond the spec's example: a `Features` line when there are features,
   `Dialog` lines for overlays, `session <state>` when not active, `No tenant`/`Page none`/
   `No requests`, an `error` flag, and the error code after the status.
9. Withdrawn in fix1 (R1-5): `controlled` reads `navigation.workerStart > 0`, omitted where the
   entry has no `workerStart`.

### Open risks

- The pipeline reads the log through an effect; more than 100 requests settling between two
  effect runs would lose the oldest from the summaries (not seen in practice; the ring is 100).
- Page visits run in every app rig, so a spec asserting an exact telemetry list may see
  `tm.page.visit` items; the core suite passed in full.

### What reviewers should examine hardest

- `TmPageVisits` boundaries: the `kept`/`#settled` adoption for reused routes, the fold of
  context-less visits, and the first visit starting at the time origin.
- `TmRequestMeasures.collect`'s seen/reported bookkeeping against the ring, and the flush
  re-entrancy when the drained summaries push the queue to 50.
- The size decision: the primary rise of 1.43 KB (page visits 0.51 KB of it) and whether page
  visits should be lazier.

**R1-1 (major): Copy diagnostics before the tm-diagnostics chunk has loaded breaks §8.3's
synchronous, toast-once contract**

Locations: `client/projects/core/tellma-core/src/requests/tm-request-log.ts:198-206` and `:256-261`;
`client/projects/core/tellma-core/src/requests/tm-diagnostics.ts:273-284`;
`client/projects/core/tellma-core/src/app/tm-app-init.ts:207-211`.

Spec 0026 §8.3, the checkpoint's deliverable ("synchronous copy()") and §14 ("Copy diagnostics is
synchronous") require `writeText` to run inside the key or click handler. Deviation 1 moves the
copy, the toasts and the shortcut into a chunk loaded at `requestIdleCallback`, which has no
timeout. Until that callback runs, four things go wrong:
- (a) `Mod+Alt+Shift+D` is not registered at all, so pressing it does nothing: no copy and no toast.
- (b) `copy()` from a button or dialog writes after an `import()`, outside the gesture:
  - WebKit refuses `writeText` after such an async boundary (`NotAllowedError`).
  - Firefox allows it only while its roughly 5 s transient activation lasts.
  - Chromium needs only focus.
- (c) When the chunk fails to load, `ɵstart()` resolves `undefined` and `diagnostics?.copy(trigger)`
  is skipped. The user gets neither the copy nor the failure toast that §8.3 requires ("Success and
  failure each toast once"). This happens offline before the worker has the shell group, or on a
  deploy skew without a worker. A `tmStartDiagnostics` that throws is swallowed the same way, and
  nothing reports it to telemetry.
- (d) `diagnosticsText()` returns `''`. A caller that shows or sends it gets empty text with no
  signal.

No spec calls `copy()` before `ɵstart()` has resolved, and none covers a failed load.

On the trade-off: the saving is 1.77 KB against 3.5 KB of headroom under the 55 KB cap. D-267
prefers moving bytes off the first frame, so a lazy chunk is acceptable, but only if the copy path
stays gesture-safe and the failure still toasts. As built, it trades a spec'd guarantee for 1.77 KB.

Suggested fix, either of:
- (1) Put the copy, the shortcut and the failure toast back in the primary. The text formatter can
  stay lazy only if `copy()` never needs it asynchronously, which it does, so in practice this means
  the whole chunk returns to the primary. Re-measure under D-031.
- (2) Keep the chunk, and make the unloaded path gesture-safe:
  - The primary registers the `tm.support.copy-diagnostics` shortcut from the start, and its `run`
    calls `copy('shortcut')`.
  - When the chunk is not loaded, `copy()` calls `navigator.clipboard.write([new ClipboardItem({
    'text/plain': this.ɵstart().then(…Blob of text(10)…) })])` synchronously in the gesture. This is
    WebKit's documented deferred-write pattern. Verify it on the Firefox and WebKit
    `@cross-engine` legs.
  - A failed load or start shows the failure toast from the primary and goes to
    `TmTelemetry.error`.

With either fix, add specs for a copy before the chunk loads (delay the import) and for a failed
load (failure toast, and a retry on the next copy).

**R1-2 (major): The page-visit stamps that the checkpoint's Tests line names ("chromeMs/ms stamps")
are not pinned, and three of deviation 7's paths have no test**

Location: `client/projects/core/tellma-core/src/observe/tm-page-visits.spec.ts:50`, `:58-62`.

Both visits assert only `ms: expect.any(Number)` and `chromeMs: expect.any(Number)`, plus
`ms <= visitS*1000+50`. The following regressions would all still pass:
- `ms` stamped at the visit's end instead of the first status away from `loading`;
- `chromeMs` taken before the context registered, or without the rAF;
- `ms` measured from the navigation's end rather than its start;
- a first visit that does not start at the time origin.

These paths have no test at all:
- outcome `error`;
- the fold of a context-less visit (the launch redirect);
- the reused-route (`kept`) adoption.

The `tmStartTelemetry` wiring is also untested: the effect that calls `pipeline.measure()` on each
log change, and `pagehide` → `pipeline.pagehide()`. The pipeline spec calls those methods directly.

Suggested fix:
- Hold the page in `loading` for a known delay. Assert that `ms` is at least that delay and below
  `visitS*1000` minus a later wait before `pagehide`, and that `chromeMs` is at most `ms` on a page
  that registers before its data.
- Add specs for `error`, the context-less redirect (its start and `entry: 'load'` carried) and a
  reused route.
- Add one rig spec in which a request ending through the real log appears in a flushed
  `tm.api.requests`.

**R1-3 (minor): A navigation abandoned before it activated passes its start to the next visit,
which inflates that page's `ms`, `chromeMs` and `visitS`**

Location: `client/projects/core/tellma-core/src/observe/tm-page-visits.ts:95-103`, `:147-151`.

The fold carries the start and entry of every visit that adopted no context, not only the launch
redirect's. Take A → B, where B waits in a guard, a resolver or a route-level `loadComponent`. While
it waits, `current()` is still A (the kept context, not adopted before settle). If the user then
clicks C, `#end()` returns B's context-less visit, and C's visit starts at B's NavigationStart.
C's data time then includes the seconds spent waiting on B, and nothing reports B as `left`. In a
cold launch whose first navigation is superseded, the same path also labels the next page
`entry: 'load'`.

Suggested fix: carry only when the context-less visit's navigation activated a route. Record
`ActivationEnd` or `NavigationEnd` for it: that covers a rendered redirect page. A navigation
superseded before it activated starts nothing, and the next visit starts at its own
NavigationStart.

**R1-4 (minor): A stale `#settled` from an earlier navigation can make the next visit adopt the
previous page's context**

Location: `client/projects/core/tellma-core/src/observe/tm-page-visits.ts:105-113`.

Each NavigationEnd, Cancel, Skipped or Error schedules `afterNextRender(() => settled.set(true))`
without checking that the navigation is still the current one. Suppose a page registers its context
and then navigates to another page within the same render, for example a canonical-URL or
default-page redirect in `ngOnInit`. The first navigation's callback then sets `settled` after the
second NavigationStart has cleared it. The new visit adopts the kept (old) context, stamps `ms` and
`chromeMs` from it, and never adopts the real page's context, because `visit.own` is already set.

Suggested fix: capture `event.id` and set `settled` only when it is still the latest navigation id
seen at NavigationStart.

**R1-5 (minor): `controlled` reports `true` for a first visit that the network served**

Location: `client/projects/core/tellma-core/src/observe/tm-load-metrics.ts:89`.

Deviation 9 reads `navigator.serviceWorker.controller` when the event is built, at the first input
or on hide. Angular's worker calls `clients.claim()` on activate (`ngsw-worker.js`, Angular 22). On
a first visit, the worker registers once the app settles, installs, and then claims the page. Any
input after that reports `controlled: true` for a load no worker served. §5.2 asks "whether a
service worker served the page".

Suggested fix: use `navigation.workerStart > 0`, which is set only when a worker handled the
navigation request, and fall back to omitting the property where that field is absent. Pin it with
the fake page.
