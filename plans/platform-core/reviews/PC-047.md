# PC-047: Sessions, BFF, back-channel logout, timers and in-proc identity mode

## Implementer notes

### What was built, and where

All production code is in `src/core/Tellma.Core.AspNetCore`.

- **Contracts (root)**: `ICatalogSessionStore` (an `ITicketStore` with `RevokeBySidAsync`,
  `RevokeBySubjectAsync` and `SweepAsync`), `IAuthenticationPolicyProvider` with `LoginPolicy` and
  the internal `DefaultAuthenticationPolicyProvider` (`TryAdd`, so a distribution replaces it), and
  `LogoutResult`. `StepUpChallenge.Write` was already in place and is unchanged.
- **`Sessions/`**:
  - `SessionKeys`: a 32-byte random key in base64url (43 characters). The handle is the first 16
    bytes of the key's SHA-256, in base64url (22 characters).
  - `SessionProperties`: the ticket items for the handle, the tokens version and the creation stamp,
    plus the `expires_at` token. `ExpiryAt` is `min(now + idle, created + absolute)`, floored to
    whole seconds.
  - `ISessionRows` / `SqlSessionRows`: the §7.5 statements exactly as written, with typed
    parameters.
  - `CatalogSessionStore`:
    - The protected ticket goes into `catalog.Sessions`, and each instance keeps a `MemoryCache` of
      50,000 entries with a TTL of `min(CacheTtl, time remaining)`.
    - `RenewAsync` is guarded by `TokensVersion`; when it writes zero rows it evicts the entry and
      re-reads the row.
    - Revoke-by-sid and revoke-by-subject use `OUTPUT`, then notify the listeners.
    - The sweep runs in batches of 1,000.
    - The profile cookie (version 2) is appended on store and on renew.
  - `SessionTerminationNotifier`: calls each listener in registration order, in a fresh scope,
    passing handles only. A listener that throws is logged as `SessionListenerFailed`.
  - `SessionRefresher`:
    - Single flight per key, per instance.
    - Steps: re-read the row bypassing the cache, adopt if the version moved, redeem, then write
      with the CAS. A lost CAS re-reads and adopts.
    - A refused refresh, a missing refresh token or a subject mismatch ends the session.
    - An unreachable authority defers until `MaxAuthorityOutage`.
  - `OidcTokenRedeemer`: the refresh grant over the OIDC scheme's back channel. It validates the
    returned id_token against the issuer, the audience (the client id) and the signing keys.
  - `TellmaSessionEvents` (cookie events):
    - `SigningIn`: persistent, stamped, the expiry capped.
    - `ValidatePrincipal`: refreshes within the refresh skew and enforces the absolute lifetime.
    - `CheckSlidingExpiration`: no renewal for background activity.
    - API-style 401/403/204 answers instead of redirects.
  - `ProfileCookie`, `BackgroundRequests`, `SessionCookieSecurity` and `SessionSweepService`.
- **`Bff/`**:
  - `BffEndpoints`: `GET /bff/login`, `POST /bff/logout`, `GET /bff/user` and
    `POST /bff/backchannel-logout`.
  - `BffOidcEvents`:
    - `RedirectToIdentityProvider` builds the public `redirect_uri` and forwards acr, ui_locales,
      max_age and allowed methods.
    - `TokenValidated` requires `sub` and `sid` and keeps only the platform's claims.
    - `TicketReceived` handles the sign-in rotation and the landing (`BffLandingFailed` on
      failure).
    - The sign-out event captures the end-session URL instead of redirecting.
  - `BackchannelLogoutValidator`.
- **OIDC scheme** (`TellmaAuthenticationComposition`):
  - The flow: code flow, PAR required, PKCE, query response mode.
  - Scopes: `openid profile email offline_access tellma_api`.
  - Tokens and claims: tokens saved; no inbound claim mapping; claim actions cleared, so `acr`
    survives.
  - Paths: the callback at `/signin-oidc`; signed-out at `/signout-callback-oidc` then
    `/signed-out`.
  - Correlation and nonce cookies: Lax, Secure according to the public origin.
- **Timers**:
  - `SessionSweepService`.
  - `Tenancy/MembershipReconcileService`:
    - First run 5 minutes after the registry's first snapshot, then every
      `Tellma:Tenancy:MembershipReconcileInterval` (default 1 day, options in
      `Hosting/TenancyHostOptions`).
    - Only the holder of `sp_getapplock 'tellma:membership-reconcile'` (Session owner, timeout 0,
      in `SqlMembershipReconcileStore`) runs; it reconciles every Active tenant.
    - A failed tenant is logged and the run continues.
- **In-proc mode** (`Hosting/InProcIdentity`, `IdentityClientSecrets`, `IdentityCheck`):
  - `AddTellmaIdentity`, `UseTellmaIdentity` and the page convention are bound by reflection on
    the `Tellma.Identity` assembly.
  - The engine's configuration is the `TellmaIdentity` section overlaid with:
    - mode, `/id`, the issuer and the composed catalog connection string;
    - migrations off, plus the migrate command;
    - a `Distribution` seed client carrying the BFF secret, the service secret and the
      back-channel logout URI.
  - Endpoint stamping:
    - Engine controllers that state no authorization of their own are made anonymous; engine
      pages get the same treatment from an `IPageApplicationModelConvention`, because a page
      model's attributes are only known at compile time.
    - Every engine endpoint is stamped tenantless and platform.
    - Endpoints with `[Authorize]` keep the engine's default scheme.
  - `UseTellma` step 7 and `MapTellma` call the engine's entry points.
  - `host.identity` checks the BFF secret, the service secret (in-proc, outside Development) and,
    in-proc, that an `IEmailSender` is registered.
- **Wiring**:
  - `AddTellmaAspNetCore` registers everything above.
  - `MapTellma` maps the BFF endpoints: login and back-channel as anonymous platform endpoints;
    logout and user under `Tellma.Web`.
  - The endpoint audit gains one rule: a non-platform, non-anonymous endpoint whose policy names
    no scheme is refused.
- **Telemetry**:
  - `HostMetrics`: session operations by source, refresh outcomes, back-channel logouts.
  - `HostLog` events: SessionListenerFailed, SessionUnreadable, SessionRefreshRejected,
    SessionRefreshDeferred, BackchannelLogoutRejected, BffLandingFailed,
    BffGlobalSignOutUnavailable, SessionSweepFailed and the three reconcile events.

### Decisions the reviewers should check

1. **The default authorization policy is no longer the session policy.**
   - It is now the framework default, which names no scheme. In-proc, the engine's own
     `[Authorize]` endpoints (Manage pages, `AccountController`, device verification) must
     authenticate the engine's cookie through its default scheme. The old default turned them
     into session-cookie endpoints: the wrong scheme, and subject to CSRF.
   - The fallback policy is still the session policy.
   - The audit now refuses any distribution endpoint under a policy without a scheme, so a plain
     `RequireAuthorization()` fails startup instead of silently using the host's default scheme.
2. **A sign-in rotates the session.**
   - Over an existing cookie, the cookie handler would call `RenewAsync(oldKey)` and keep the old
     key, which is session fixation.
   - `TicketReceived` marks the sign-in; during a marked request, `RetrieveAsync` returns null and
     remembers the old session; `StoreAsync` writes a fresh key and ends the old session (deletes
     its row and notifies its handle).
3. **The cookie value is the framework's protected reference ticket** carrying the key claim, not
   the bare key, because `CookieAuthenticationHandler` gives no other way to store a session key.
   Data Protection still covers it.
4. **Refresh across instances.**
   - Within an instance, single flight guarantees exactly one redemption (unit test with 8
     concurrent requests; integration test with 5 concurrent refreshes against SQL).
   - Across instances, the CAS lets one write win and the loser adopt that ticket (integration
     test). An instance that starts after the write adopts without redeeming.
   - Two instances that read version 0 at the same time both redeem. Spec 0011 §5.5 accepts this,
     relying on the authority's 30 s reuse leeway. The checkpoint's "exactly one redeems" is
     therefore tested per instance.
5. **What counts as unreachable.**
   - A catalog or database failure during a refresh is handled like an unreachable authority:
     deferred within the allowance.
   - A 4xx from the token endpoint is a refusal and ends the session. A 5xx, a transport failure
     or a malformed 200 counts as unreachable.
   - The outage allowance runs from the access token's `expires_at`.
6. **Back-channel receiver.**
   - It answers 503 when the authority's metadata cannot be read, so the identity server retries,
     and 400 for every invalid token.
   - It deletes by `sid`, or by `sub` when there is no `sid`, exactly as the spec says. It does not
     additionally check that `sub` matches the `sid`'s rows.
7. **The front-channel sign-out is off** (`RemoteSignOutPath` is empty); the back channel is the
   only path.
8. **Global logout** builds the end-session URL before the local sign-out, because it needs the
   session's id_token. The event captures the URL rather than redirecting, since the caller is a
   fetch. If the authority is unavailable, the sign-out falls back to local.
9. **Login refuses repeated parameters.** A repeated `returnUrl`, `acr_values`, `max_age` or
   `ui_locales` gets 400, as does a non-local return URL, a negative or non-numeric `max_age`, or
   unprintable values.
10. **Client secrets.** `ClientSecret` is required in standalone mode in every environment. In-proc
    in Development, both secrets are generated per boot when they are not configured.
11. **The stored ticket is serialized without the tokens-version item**, which is stamped from the
    row on read, so the version always comes from the row.
12. **A ticket is rejected** (signed out) when it lacks the key, handle, subject, creation stamp or
    access-token expiry, or is past its absolute lifetime.
13. **The engine is bound by reflection**, so `Tellma.Core.AspNetCore` takes no compile-time
    dependency on `Tellma.Identity`. A distribution's web host references the engine package, and
    the composition fails with `host.identity` if it is missing.
14. **The fallback policy needed no change.** The analysis suggested `EndpointPolicies.ResolveAsync`
    missed the fallback policy. It does not: `AuthorizationPolicy.CombineAsync` returns the
    fallback, and the existing CSRF test on a fallback endpoint confirms it, so nothing changed
    there.

### Open risk, not fixed here

- **In-proc mail outside a tenant.** The engine sends mail outside any tenant, for example
  invitations from the management API and sign-in codes. In a distribution, `ISandboxContext` is
  `TenantSandboxContext`, which throws when no tenant is bound. The engine's email path may hit it.
  The unit suite cannot show this, because it registers a stub `IEmailSender`. It needs the email
  pipeline's owner to decide what the sandbox answers in a tenantless scope.
