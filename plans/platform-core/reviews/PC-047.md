# PC-047: Sessions, BFF, back-channel logout, timers and in-proc identity mode

## Implementer notes

### What was built, and where

All production code is in `src/core/Tellma.Core.AspNetCore`.

- **Contracts (root)**: `ICatalogSessionStore` (an `ITicketStore` with `RevokeBySidAsync`,
  `RevokeBySubjectAsync` and `SweepAsync`), `IAuthenticationPolicyProvider` with `LoginPolicy` and
  the internal `DefaultAuthenticationPolicyProvider` (`TryAdd`, so a distribution replaces it), and
  `LogoutResult`. `StepUpChallenge.Write` was already in place and is unchanged.
- **`Sessions/`**:
  - `SessionKeys`: a 32-byte random key in base64url (43 characters). The handle is the first 16
    bytes of the key's SHA-256, in base64url (22 characters).
  - `SessionProperties`: the ticket items for the handle, the tokens version and the creation stamp,
    plus the `expires_at` token. `ExpiryAt` is `min(now + idle, created + absolute)`, floored to
    whole seconds.
  - `ISessionRows` / `SqlSessionRows`: the §7.5 statements exactly as written, with typed
    parameters.
  - `CatalogSessionStore`:
    - The protected ticket goes into `catalog.Sessions`, and each instance keeps a `MemoryCache` of
      50,000 entries with a TTL of `min(CacheTtl, time remaining)`.
    - `RenewAsync` is guarded by `TokensVersion`; when it writes zero rows it evicts the entry and
      re-reads the row.
    - Revoke-by-sid and revoke-by-subject use `OUTPUT`, then notify the listeners.
    - The sweep runs in batches of 1,000.
    - The profile cookie (version 2) is appended on store and on renew.
  - `SessionTerminationNotifier`: calls each listener in registration order, in a fresh scope,
    passing handles only. A listener that throws is logged as `SessionListenerFailed`.
  - `SessionRefresher`:
    - Single flight per key, per instance.
    - Steps: re-read the row bypassing the cache, adopt if the version moved, redeem, then write
      with the CAS. A lost CAS re-reads and adopts.
    - A refused refresh, a missing refresh token or a subject mismatch ends the session.
    - An unreachable authority defers until `MaxAuthorityOutage`.
  - `OidcTokenRedeemer`: the refresh grant over the OIDC scheme's back channel. It validates the
    returned id_token against the issuer, the audience (the client id) and the signing keys.
  - `TellmaSessionEvents` (cookie events):
    - `SigningIn`: persistent, stamped, the expiry capped.
    - `ValidatePrincipal`: refreshes within the refresh skew and enforces the absolute lifetime.
    - `CheckSlidingExpiration`: no renewal for background activity.
    - API-style 401/403/204 answers instead of redirects.
  - `ProfileCookie`, `BackgroundRequests`, `SessionCookieSecurity` and `SessionSweepService`.
- **`Bff/`**:
  - `BffEndpoints`: `GET /bff/login`, `POST /bff/logout`, `GET /bff/user` and
    `POST /bff/backchannel-logout`.
  - `BffOidcEvents`:
    - `RedirectToIdentityProvider` builds the public `redirect_uri` and forwards acr, ui_locales,
      max_age and allowed methods.
    - `TokenValidated` requires `sub` and `sid` and keeps only the platform's claims.
    - `TicketReceived` handles the sign-in rotation and the landing (`BffLandingFailed` on
      failure).
    - The sign-out event captures the end-session URL instead of redirecting.
  - `BackchannelLogoutValidator`.
- **OIDC scheme** (`TellmaAuthenticationComposition`):
  - The flow: code flow, PAR required, PKCE, query response mode.
  - Scopes: `openid profile email offline_access tellma_api`.
  - Tokens and claims: tokens saved; no inbound claim mapping; claim actions cleared, so `acr`
    survives.
  - Paths: the callback at `/signin-oidc`; signed-out at `/signout-callback-oidc` then
    `/signed-out`.
  - Correlation and nonce cookies: Lax, Secure according to the public origin.
- **Timers**:
  - `SessionSweepService`.
  - `Tenancy/MembershipReconcileService`:
    - First run 5 minutes after the registry's first snapshot, then every
      `Tellma:Tenancy:MembershipReconcileInterval` (default 1 day, options in
      `Hosting/TenancyHostOptions`).
    - Only the holder of `sp_getapplock 'tellma:membership-reconcile'` (Session owner, timeout 0,
      in `SqlMembershipReconcileStore`) runs; it reconciles every Active tenant.
    - A failed tenant is logged and the run continues.
- **In-proc mode** (`Hosting/InProcIdentity`, `IdentityClientSecrets`, `IdentityCheck`):
  - `AddTellmaIdentity`, `UseTellmaIdentity` and the page convention are bound by reflection on
    the `Tellma.Identity` assembly.
  - The engine's configuration is the `TellmaIdentity` section overlaid with:
    - mode, `/id`, the issuer and the composed catalog connection string;
    - migrations off, plus the migrate command;
    - a `Distribution` seed client carrying the BFF secret, the service secret and the
      back-channel logout URI.
  - Endpoint stamping:
    - Engine controllers that state no authorization of their own are made anonymous; engine
      pages get the same treatment from an `IPageApplicationModelConvention`, because a page
      model's attributes are only known at compile time.
    - Every engine endpoint is stamped tenantless and platform.
    - Endpoints with `[Authorize]` keep the engine's default scheme.
  - `UseTellma` step 7 and `MapTellma` call the engine's entry points.
  - `host.identity` checks the BFF secret, the service secret (in-proc, outside Development) and,
    in-proc, that an `IEmailSender` is registered.
- **Wiring**:
  - `AddTellmaAspNetCore` registers everything above.
  - `MapTellma` maps the BFF endpoints: login and back-channel as anonymous platform endpoints;
    logout and user under `Tellma.Web`.
  - The endpoint audit gains one rule: a non-platform, non-anonymous endpoint whose policy names
    no scheme is refused.
- **Telemetry**:
  - `HostMetrics`: session operations by source, refresh outcomes, back-channel logouts.
  - `HostLog` events: SessionListenerFailed, SessionUnreadable, SessionRefreshRejected,
    SessionRefreshDeferred, BackchannelLogoutRejected, BffLandingFailed,
    BffGlobalSignOutUnavailable, SessionSweepFailed and the three reconcile events.

### Decisions the reviewers should check

1. **The default authorization policy is no longer the session policy.**
   - It is now the framework default, which names no scheme. In-proc, the engine's own
     `[Authorize]` endpoints (Manage pages, `AccountController`, device verification) must
     authenticate the engine's cookie through its default scheme. The old default turned them
     into session-cookie endpoints: the wrong scheme, and subject to CSRF.
   - The fallback policy is still the session policy.
   - The audit now refuses any distribution endpoint under a policy without a scheme, so a plain
     `RequireAuthorization()` fails startup instead of silently using the host's default scheme.
2. **A sign-in rotates the session.**
   - Over an existing cookie, the cookie handler would call `RenewAsync(oldKey)` and keep the old
     key, which is session fixation.
   - `TicketReceived` marks the sign-in; during a marked request, `RetrieveAsync` returns null and
     remembers the old session; `StoreAsync` writes a fresh key and ends the old session (deletes
     its row and notifies its handle).
3. **The cookie value is the framework's protected reference ticket** carrying the key claim, not
   the bare key, because `CookieAuthenticationHandler` gives no other way to store a session key.
   Data Protection still covers it.
4. **Refresh across instances.**
   - Within an instance, single flight guarantees exactly one redemption (unit test with 8
     concurrent requests; integration test with 5 concurrent refreshes against SQL).
   - Across instances, the CAS lets one write win and the loser adopt that ticket (integration
     test). An instance that starts after the write adopts without redeeming.
   - Two instances that read version 0 at the same time both redeem. Spec 0011 §5.5 accepts this,
     relying on the authority's 30 s reuse leeway. The checkpoint's "exactly one redeems" is
     therefore tested per instance.
5. **What counts as unreachable.**
   - A catalog or database failure during a refresh is handled like an unreachable authority:
     deferred within the allowance.
   - A 4xx from the token endpoint is a refusal and ends the session. A 5xx, a transport failure
     or a malformed 200 counts as unreachable.
   - The outage allowance runs from the access token's `expires_at`.
6. **Back-channel receiver.**
   - It answers 503 when the authority's metadata cannot be read, so the identity server retries,
     and 400 for every invalid token.
   - It deletes by `sid`, or by `sub` when there is no `sid`, exactly as the spec says. It does not
     additionally check that `sub` matches the `sid`'s rows.
7. **The front-channel sign-out is off** (`RemoteSignOutPath` is empty); the back channel is the
   only path.
8. **Global logout** builds the end-session URL before the local sign-out, because it needs the
   session's id_token. The event captures the URL rather than redirecting, since the caller is a
   fetch. If the authority is unavailable, the sign-out falls back to local.
9. **Login refuses repeated parameters.** A repeated `returnUrl`, `acr_values`, `max_age` or
   `ui_locales` gets 400, as does a non-local return URL, a negative or non-numeric `max_age`, or
   unprintable values.
10. **Client secrets.** `ClientSecret` is required in standalone mode in every environment. In-proc
    in Development, both secrets are generated per boot when they are not configured.
11. **The stored ticket is serialized without the tokens-version item**, which is stamped from the
    row on read, so the version always comes from the row.
12. **A ticket is rejected** (signed out) when it lacks the key, handle, subject, creation stamp or
    access-token expiry, or is past its absolute lifetime.
13. **The engine is bound by reflection**, so `Tellma.Core.AspNetCore` takes no compile-time
    dependency on `Tellma.Identity`. A distribution's web host references the engine package, and
    the composition fails with `host.identity` if it is missing.
14. **The fallback policy needed no change.** The analysis suggested `EndpointPolicies.ResolveAsync`
    missed the fallback policy. It does not: `AuthorizationPolicy.CombineAsync` returns the
    fallback, and the existing CSRF test on a fallback endpoint confirms it, so nothing changed
    there.

Checked and found sound:
- **Ruling 1** (the default policy names no scheme; the fallback is the session policy; the audit
  refuses scheme-less distribution endpoints).
  - It matches §5.7: an engine endpoint with `[Authorize]` keeps its own policy and scheme, and
    `AddIdentity`'s default schemes stay.
  - `AddIdentity` sets `DefaultAuthenticateScheme = Identity.Application`. Under the old default
    policy, the engine's Manage pages and `AccountController` would have been session-cookie
    endpoints, so the engine's users got 401 problems and CSRF refusals there.
  - Every Tellma policy and the fallback name their scheme. `PolicyEvaluator` then replaces
    `HttpContext.User` with the session principal alone, so the engine's SSO cookie never reaches a
    `Tellma.Web` endpoint.
  - The new audit rule (`TellmaEndpointAudit.cs:124`) closes the remaining hole, a distribution's
    bare `RequireAuthorization()`.
  - The ruling is sound. Its test coverage is R1-4.
- **Ruling 2** (a sign-in rotates the session). Checked against the cookie handler.
  `ReadCookieTicket` sets `_sessionKey` only after `RetrieveAsync` returns a ticket, so a null
  during a marked request makes `HandleSignInAsync` call `StoreAsync`, not `RenewAsync`.
  `TicketReceived` runs before `SignInAsync(SignInScheme)`, and nothing authenticates the cookie
  scheme earlier in the callback request: `UseAuthentication` returns after the remote handler, so
  the in-proc default authenticate scheme never runs. The fixation path is closed, and the test
  covers it.
- **Ruling 3** (single flight per instance; the `TokensVersion` CAS across instances). It is what
  §5.5 states. The flight runs on `CancellationToken.None` and is removed only by its creator.
  A renewal at an old version can never overwrite a refresh, because the CAS increments the version.
  The integration test covers the two-instance adopt.
- **Ruling 4** (the engine bound by reflection). It is acceptable. The real engine is exercised by
  `InProcIdentityTests`, and a missing assembly is a composition problem. R1-10 has a small
  message issue.
- **Ruling 5** (`host.identity` requires `IEmailSender` in-proc). It is sound. The engine's own
  `EmailDispatchHostedService.StartingAsync` already refuses to start without one, so the check
  only moves that refusal into the gate's aggregated report.
- **Ruling 7** (no change to policy resolution). Correct: `AuthorizationPolicy.CombineAsync`
  returns the fallback policy when there is no authorize data and no policy.
- **Back-channel logout validation**, checked rule by rule:
  - the signature against the JWKS (`RequireSignedTokens`, so `alg: none` is refused);
  - `iss` and `aud` (the slug), and `typ = logout+jwt` through `ValidTypes`;
  - `iat` within ±5 min, and the event member;
  - no `nonce`, and a `sid` or `sub` present, with shape checks on both;
  - 400 with no body on failure, 200 on a replay, and a delete by `sid`, else by `sub`.
  - The logged reason is a fixed text or an exception type name, never the token.
- **CSRF**:
  - `/bff/logout` sits under `Tellma.Web`, so all four rules apply, and the test covers it.
  - `/bff/login` and the back-channel receiver are anonymous by design. The callback is protected
    by the correlation cookie, state and PKCE.
  - `RemoteSignOutPath` is empty, so `HandleRemoteSignOutAsync` never runs.
  - Without a `state`, `/signout-callback-oidc` redirects to `/signed-out` alone, so it is no open
    redirect.
- **The login's return URL**: `IsLocalUrl` refuses `//`, `/\` and control characters after query
  decoding.
- **Cookies and headers**:
  - `Clear-Site-Data: "cache"` is sent on every sign-out.
  - The persistent cookie's `Expires` equals the row's `ExpiresAt` (whole seconds) at sign-in and on
    renewal, with the profile cookie alongside. Both are tested.
- **No key or token in a log or a listener**:
  - Listeners get handles only; `EndedSession.Key` is used for cache eviction alone.
  - Every new log event takes a handle, a fixed reason, a sanitized OAuth error code (at most
    64 printable ASCII characters) or an exception.
  - The client secrets sit in a non-record class.
- **The §7.5 statements** are reproduced as written, with typed parameters.
- **The reconcile**: the zero-timeout `Session` applock is released on lease disposal.
- **The timers**: on `TimeProvider`, as PLAN §6 requires.

### Findings

**R1-1 (blocking): `BackchannelLogoutTests` compares an unsorted expectation against sorted
handles, so it fails half the time.**
- Where: `test/core/Tellma.Core.AspNetCore.Tests/Bff/BackchannelLogoutTests.cs:39`.
- The test sorts the actual handles but not the expected ones:
  `Assert.Equal([first.Handle, second.Handle], [.. handles.Order(StringComparer.Ordinal)], …)`.
- Handles derive from random keys, so the test passes only when `first.Handle` happens to sort
  first. It failed in my full-suite run, and in 2 of 4 isolated reruns. On integration it would turn
  the PR tier red about every other run, which is a stop-the-line flake.
- Fix: order both sides, for example
  `Assert.Equal([first.Handle, second.Handle].Order(StringComparer.Ordinal), handles.Order(StringComparer.Ordinal))`,
  or compare as sets.

**R1-2 (major): ruling 6's "open risk" is a certain failure. In-proc, every mail the engine sends
throws.**
- The chain:
  - The engine sends from `EmailDispatchHostedService` in a fresh scope with no tenant bound
    (`src/apps/Tellma.Identity/Services/Email/EmailDispatchHostedService.cs:82-94`).
  - The platform's sender is `EmailRouter`, whose `SendAsync` reads `_sandboxContext.IsSandbox`
    first (`src/core/Tellma.Core.Email/EmailRouter.cs:89`).
  - In a distribution, that is `TenantSandboxContext`, which throws `InvalidOperationException`
    when no tenant is bound (`src/core/Tellma.Core/Tenancy/TenantSandboxContext.cs:26`).
- So with the composition that `IdentityCheck.cs:65-72` now requires (`AddTellmaEmail`), every
  sign-in code, invitation and password reset fails and is logged by the dispatcher.
- This is not a hypothesis that needs a test to surface. It breaks:
  - §5.7's Development path ("the first sign-in is the email-code path, with the code in the
    console");
  - the planned "against the in-proc identity server … a real send through the email log sink"
    tests of the 0018 checkpoint and the Acme checkpoint.
- The spec is self-contradictory here: §3.9 says the engine "registers its own `ISandboxContext`",
  which a shared container cannot do. That makes it a decision for Ahmad. But D-066 and WATCHLIST
  record it as an open risk owned by "the email pipeline", with no gate.
- Fix, either of:
  - **(a)** Fix it here. In in-proc mode, have the engine's dispatch scope answer the sandbox
    question explicitly. For example, give `TenantSandboxContext` a tenantless answer of "live" for
    work marked as the identity engine's: a scoped marker the in-proc wiring sets through a
    decorated `IEmailSender` that the engine resolves. Then add an `InProcIdentityTests` case that
    composes the real email pipeline with the log sink and sends one code.
  - **(b)** At minimum, record it as a defect, not a risk:
    - add a DEPS gate so PC-085 and the 0018 in-proc integration checkpoint cannot be `done` before
      the decision lands;
    - correct the README and implementer notes, which describe in-proc mail as working.

**R1-3 (major): a caller's `acr_values` and `max_age` replace the distribution's login policy
instead of being bounded by it.**
- Where: `src/core/Tellma.Core.AspNetCore/Bff/BffEndpoints.cs:115-127` computes
  `(acrValues ?? policy.AcrValues)`, and the query's `max_age` likewise wins over `policy.MaxAge`.
- `IAuthenticationPolicyProvider` is the seam for login-time constraints. A distribution that
  returns `LoginPolicy("urn:tellma:acr:mfa", TimeSpan.FromHours(1), …)` is bypassed by any user
  who opens `/bff/login?acr_values=urn:tellma:acr:pwd&max_age=999999`.
- The authority enforces what the PAR body carries (spec 0003), so the weaker request is honoured.
  Only `tellma_allowed_methods` cannot be overridden.
- The default provider returns none, so this is latent. But the seam exists to be a constraint, and
  no test covers the policy path at all.
- Fix:
  - When the policy names `AcrValues`, send the policy's value. Accept the query's only when the
    policy names none, or when it equals the policy's.
  - Send the smaller of the two `max_age` values.
  - Add tests with a stub provider for acr, max_age and allowed methods: forwarded, and not
    overridable.

**R1-4 (major): ruling 1, the checkpoint's central security ruling, has no test that would fail if
it were reverted.**
- Restoring `.SetDefaultPolicy(SessionPolicy())` in `TellmaAuthenticationComposition.cs:66` still
  leaves every test green.
- `InProcIdentityTests` only reaches anonymous engine endpoints:
  - authorize and token;
  - discovery;
  - the login page;
  - the login form post.
- No test reaches an `[Authorize]` one: `Identity/Manage/*`, `AccountController`, or the device
  verification actions.
- The opposite isolation is not tested in in-proc mode either: an engine SSO cookie must not
  authenticate `/bff/user` or the session fallback.
- Fix: add to the in-proc fixture:
  - `GET /id/Identity/Manage/Index` with no cookie answers the engine's challenge (302 to
    `/id/Identity/Account/Login`), not a 401 problem;
  - the same request carrying only a valid Tellma session cookie is still challenged by the engine;
  - an engine `[Authorize]` POST is not refused by the platform's CSRF (no 403 `csrf-rejected`);
  - `/bff/user` with only an engine SSO cookie answers 401.

**R1-5 (major): `OnTokenValidated`'s rules (§5.5) are untested.**
- Where: `src/core/Tellma.Core.AspNetCore/Bff/BffOidcEvents.cs:97-130`. The handler:
  - refuses an id token without `sub` or `sid`;
  - refuses a malformed subject;
  - trims the principal to the nine kept claims.
- No test exercises any of these.
- The `sid` rule is security-relevant. A session stored with `Sid = NULL` cannot be ended by a
  `sid`-only logout token, which is the authority's normal form. It would survive back-channel
  logout until its refresh fails.
- `FakeIdentityServer.SessionId` is already settable, so the tests are cheap.
- Fix:
  - Sign-in flows where the identity token lacks `sid`, or lacks `sub`, or carries a subject with a
    space: the callback fails and no row is written.
  - One flow whose identity token carries extra claims (`nonce`, `at_hash`, a custom claim): the
    stored principal holds only the kept set, with `acr`, `amr` and `auth_time` present.

**R1-6 (minor): during an outage, every request of a session re-attempts the redemption and waits
for the back channel's timeout.**
- Where: `src/core/Tellma.Core.AspNetCore/Sessions/SessionRefresher.cs:245-255`, with
  `OidcTokenRedeemer.cs:64-74`.
- A deferred outcome is not remembered. Each later request within the skew starts a new flight.
- Against a black-holed authority, `OpenIdConnectOptions.BackchannelTimeout` defaults to 60 s.
  So for the whole `MaxAuthorityOutage` hour, every SPA request of an affected session hangs about
  a minute before it is served. The session is "kept", but unusable.
- Fix: remember a deferral per key, for example in a small `MemoryCache` entry for 15–30 s. Within
  it, `ValidatePrincipal` serves the current tokens without redeeming. Bounding the redeemer's
  back-channel timeout (for example 10 s) would also help.

**R1-7 (minor): several refresh, logout and receiver rules have no test that would fail if they
broke.**
- Untested:
  - the subject-mismatch end (`SessionRefresher.cs:173-177`);
  - an invalid refreshed identity token ending the session (`OidcTokenRedeemer.cs:132-135`);
  - the refreshed `acr`, `tellma_acr_auth_time`, `name` and `locale` replacing the principal's
    (`SessionRefresher.cs:198-216`). No test asserts the claims, the stored new tokens, or the
    profile cookie re-issued with a changed name;
  - a malformed 200 deferring (`OidcTokenRedeemer.cs:107-116`);
  - the back-channel receiver's 503 when metadata is unavailable (`BffEndpoints.cs:335-340`);
  - the global sign-out falling back to local, with `BffGlobalSignOutUnavailable`
    (`BffEndpoints.cs:183-187`);
  - the global sign-out's `id_token_hint` and `Clear-Site-Data`;
  - a hub request renewing nothing (only the header and telemetry cases exist);
  - "listener before delete": no test checks that the row still exists when the listener runs.
- Fix: one focused test per rule above. For the ordering, the recording listener can assert that
  `host.Rows.Keys()` still contains the key when it is called.

**R1-8 (minor): a refreshed identity token signed with a newly rolled key ends the session.**
- Where: `OidcTokenRedeemer.cs:122-135` validates against the cached
  `configuration.SigningKeys`, and treats any failure as `Refused`, which deletes the row.
- After the authority rolls its signing key and before the configuration manager's next refresh,
  every refreshing session is signed out.
- `BackchannelLogoutValidator.cs:84-89` already handles this case with one `RequestRefresh` and a
  retry.
- Fix: on `SecurityTokenSignatureKeyNotFoundException`, request a refresh and validate once more.
  If the metadata is still stale, answer `Unreachable` rather than `Refused`.

**R1-9 (minor): the public contracts differ from §5.5's, and the commit lists no deviation for it.**
- Where: `ICatalogSessionStore.cs` and `IAuthenticationPolicyProvider.cs`. The revocation and
  sweep methods and `GetLoginPolicyAsync` gain a `CancellationToken` parameter.
- `LogoutResult` is declared but never used: `/bff/logout` writes its JSON by hand
  (`BffEndpoints.cs:196-201`).
- These are harmless, but PLAN §7.1 item 1 wants contract changes listed.
- Fix:
  - Add one Deviations line for the parameters.
  - Serialize `LogoutResult` in the endpoint, so the type and the wire shape cannot drift.

**R1-10 (minor): a binding failure is reported as a missing assembly.**
- Where: `src/core/Tellma.Core.AspNetCore/Hosting/InProcIdentity.cs:112-118`.
- When `Tellma.Identity` is referenced but `AddTellmaIdentity(IServiceCollection, IConfiguration)`
  is not found, the problem still says the assembly is not referenced. A version skew between the
  platform and engine packages is the likely case, which is exactly what the reflection binding
  cannot catch at compile time.
