# PC-214: Delivery events, verbs, retention and telemetry

## Implementer notes

### What was built

Spec 0022 §6 (delivery events), §7.1 (retry, cancel, delete precondition), §7.3 (retention), §8
(the stack's verbs), §9.2 (`delivery_updates`, `retained`, the delivery log events, the alerts) and
§11 (observability, docs).

- **Delivery events** (`src/core/Tellma.Core/Outbox/`).
  - `DeliveryEventSelection` (new, pure): maps the event type to a status (Opened, Clicked and
    Other drop), groups by the correlation's tenant (`SortedDictionary`, so tenants run in id
    order), keeps per row the strongest event (higher status, then later `Timestamp` with null
    earliest, then later position), numbers the TVP rows by id, and cuts the provider's text to the
    column widths (recipient 255, reason 512, event id 100). A classified event with no tenant or a
    reference that is not a positive invariant integer is set apart as unaddressed.
  - `OutgoingEmailDeliveryHandler` (new, scoped `IEmailDeliveryEventHandler`, owner key
    `outbox`): the tenant-state policy over `ITenantRegistry.Find`: missing, Provisioning and
    Retired drop with `OutboxDeliveryTenantSkipped`; Active, ReadOnly and Suspended apply; Frozen
    is deferred and throws `TenantUnavailableException(tenant-frozen)` after every other tenant
    was applied. A tenant whose update throws is captured and rethrown at the end (alone as it
    was, or with other failures and the freeze in an `AggregateException`), so one broken tenant
    database does not starve the others; the receivers map either to 503 and the provider
    redelivers, which the dedup makes safe. Each unmatched id is logged
    (`OutboxDeliveryEventUnmatched`); counts go to `delivery_updates` by result.
  - `OutboxDeliveryWriter` (new, scoped, behind internal `IOutboxDeliveryWriter` so the policy is
    unit-testable): opens an `ITenantDatabaseFactory` handle on the caller's scope, one
    Maintenance batch in `TransactionMode.None`, disposes the handle.
  - `OutboxStatements.DeliveryUpdate`: the §6 statement verbatim in shape: the monotonic `CASE`
    rank (generated from `EmailDeliveryStatus`'s values), dedup on `LastProviderEventId`,
    `SELECT @@ROWCOUNT`, then the unmatched ids; `EmailWrites`, idempotent. Result record
    `DeliveryUpdateResult(Applied, Unmatched)`.
- **Verbs** (`OutgoingEmailService`).
  - `retry` (`AccessActions.Retry`) and `cancel` (`AccessActions.Cancel`, destructive,
    `AllowWhenReadOnly`). `ValidateActionAsync` loads the targets and, for retry, their jobs'
    statuses (one raw SQL load joined through the stored `JobId`) in the first round, refusing
    `Email.NotRetryable` / `Email.NotCancellable` at `Ids[i]`.
  - Retry: `context.Update(RetryAssignments, RetryCondition)` (State Pending, the nine send and
    delivery columns null, `ExpectsDeliveryEvents` false), then `IJobQueue.Enqueue(context.Batch,
    …)` with the same request as the insert path (system run-as, no requester, due at
    `SendAfter`). The enqueue's own owner check under its update lock refuses a row whose job is
    live (`Jobs.OwnerUnavailable`), which closes the race between validation and persist.
  - Cancel: `context.Update(CancelAssignments, "State = 'Pending'")`.
  - Delete precondition: now one round (the job-status load rides the targets' load) instead of
    two; same refusal, `Email.NotDeletable`.
  - Public static predicates `IsSettled`, `IsLive`, `IsOrphaned`, `IsRetryable`, `IsDeletable`.
- **Conditional action update seam** (`Tellma.Core.Abstractions/Validation/ActionContext.cs`,
  `Crud/Actions/ActionRun.Persist.cs`). New overload
  `ActionContext.Update(assignments, FilterTree condition)`: composes
  `UpdateSpec.ByIds(ids, read, read ∧ grant ∧ condition, …, Stamp: true, AllOrNothing: false)`,
  so a target that no longer meets the precondition at persist time is left as it is instead of
  being overwritten. `ActionContext.Updates` is now a list of `ComposedUpdate(Assignments,
  Condition)` (internal); the one internal test that read it was adjusted.
- **Retention**: `OutgoingEmailRetentionHandler` (`core.outgoing-email-retention`, lease 600 s,
  runs when read-only), built-in schedule 7 at `45 3 * * *`. `OutboxStatements.RetentionPage`
  reads up to 500 ids (`CreatedAt < DATEADD(second, -retention, SYSUTCDATETIME())`, settled, or
  unsettled with no live job) through the guarded runner; each page is deleted by
  `EntityService<OutgoingEmail, int>.DeleteByIdsAsync`, so the delete's precondition and the blob
  release run. Loop ends on a short page or a page that deleted nothing; progress per page
  (`Outbox_RetentionProgress`, `{deleted}`); a refused delete (Validation/NotFound) re-reads the
  page once (`OutboxRetentionPageReread`), a second refusal fails the run.
- **Telemetry**: `OutboxTelemetryNames.DeliveryUpdates`, `Retained`, `ResultTag`;
  `OutboxMetrics.RecordDeliveryUpdates(result, count)` (closed set `applied | stale | unmatched |
  tenant_skipped`, nothing for zero) and `RecordRetained`. New log events in `OutboxLog`.
- **Alerts**: `infra/monitoring/outbox/unmatched-delivery-events.kql`; README updated;
  `retained` backs no alert (sizing only), excluded beside `enqueued` in `OutboxAlertQueryTests`.
- **Composition**: CoreFeature registers the writer, the handler, the retention handler and its
  built-in schedule. Resources `JobHandler_core_outgoing-email-retention` and
  `Outbox_RetentionProgress` (en, ar).
- **Migrations**: the three Initial migrations regenerated with dotnet-ef (only the schedule 7
  `HasData` rows in `core.Schedules` and `core.ScheduleStates` changed); BOM and CRLF stripped.
- **Docs**: `src/core/Tellma.Core/README.md` (stack verbs, delivery handler, retention),
  ARCHITECTURE.md (the outbox's jobs and the delivery handler's tenantless database handle).
- **Goldens and fixtures regenerated** (reviewed diffs: only the two new actions, routes and
  securables, the new `Update` overload, the new handler and schedule 7): the Validation public
  API golden, `fixture-routes.txt` / `gadget-routes.txt`, `fixture-stacks.txt` /
  `gadget-stacks.txt`, the client entity-model fixture `entities-chunk.json` (the two actions;
  shape as Job's), `JobLabelsTests`, `AccessModelTests` (seeded rows 7), the two securables tests.
- **Tests**:
  - Unit: `DeliveryEventSelectionTests`, `OutgoingEmailDeliveryHandlerTests` (fake registry and
    writer: the state policy, Frozen last, failure aggregation, every result counted, the
    closed result set, `retained`), `OutgoingEmailPreconditionTests`, `OutboxAlertQueryTests`
    additions, `ValidationContextTests` (the conditional overload).
  - Integration (`OutboxManagementTests`, on `OutboxDatabase`, which gained an administrator role
    over `core.OutgoingEmail` and `UserScopeAsync`): repeats, out-of-order and unknown references
    through the real dispatcher; the writer's applied count and unmatched ids; retry on Failed
    (new job, columns cleared, stamped, sent again), retry on Rejected and on a live-job row
    refused; cancel on a ReadOnly tenant (stamped, job then sends nothing); cancel of a sent row
    refused; delete of a Pending row with a live job refused, allowed after cancel; retention
    deletes settled and orphaned rows, releases the blob, keeps the live-job and recent rows,
    counts `retained`.

### Deviations

1. **No delete-by-query** on `outgoing-emails` (D-132): the spec's §8 list includes it, but the
   delete is validated row by row. Unchanged from PC-148; flagged again for the spec.
2. **The delivery handler applies every tenant before it raises failures** (spec §6 says
   exceptions propagate). Same outcome for the receiver (503), but healthy tenants are not starved
   by one broken database.
3. **`ActionContext.Update(assignments, condition)`** is a new public API: rows that changed
   between validation and persist are skipped, not refused (the spec says "filtered by the grant
   and the precondition", which this implements literally). Goldens updated.
4. **Delete validation in one round** instead of two (the job-status load rides the first round).
5. **Tenantless or non-integer references count as unmatched** (logged with their raw reference).
6. **Extra log events** beyond §9.2's three Warnings: `OutboxDeliveryEventsStale` (Debug),
   `OutboxDeliveryTenantFrozen` (Information), `OutboxRetentionPageReread` (Information).
7. **Provider text truncated** to the column widths before the TVP, so a long bounce reason never
   fails the update.
8. **Retention re-reads a refused page once** before failing.
9. **Retry's new job is due at `SendAfter`** (as the insert path), not "now"; past `SendAfter` this
   is the same.
10. **`retained` backs no alert**; `delivery_updates` backs the unmatched alert.
11. **(Review 1) `ActionContext.Update(assignments, condition, refusalCode)`** is a second new public
    API, and `UpdateSpec<TEntity>.ByIds.StampUnchanged` a new data-layer option (D-187). Retry
    refuses the whole action when a target no longer meets its precondition at persist time
    (`Email.NotRetryable` at the root, nothing committed), and stamps every target even when its
    columns already held the cleared values; cancel keeps deviation 3's skip. A target deleted
    between the rounds is refused with the code rather than as not found.

### Open risks

- Frozen tenants' events are not counted until redelivery; a tenant frozen past the provider's
  redelivery window loses them (logged at Information with the count).
- The retention runs through the full delete pipeline per page (validation load plus delete); at
  500 rows a page this is two round trips per page plus the blob effect.

### Review focus

- `ActionRun.ComposeUpdates`' conditional branch (`AllOrNothing: false`, the conjoined filter) and
  whether skipping a changed row silently is acceptable for cancel and retry.
- The retry's enqueue race: validation sees no live job, persist's owner check is the backstop.
- `OutboxStatements.DeliveryUpdate`: the rank `CASE`, the `DeliveryAt < Timestamp` tie rule with a
  null `Timestamp` (stored as `SYSUTCDATETIME()`), and dedup on `LastProviderEventId`.
- The handler's exception aggregation and `when (!cancellationToken.IsCancellationRequested)`.
- D-177 carry: retry does not re-validate addresses (the stored row is re-sent as is; a bad stored
  address is rejected by the sending job as `Email.InvalidMessage`), so no throw path is added.

**R1-1 (major): the conditional update's skip has no test that would fail if it broke.**
`src/core/Tellma.Core/Crud/Actions/ActionRun.Persist.cs:296-303`;
`src/core/Tellma.Core.Abstractions/Validation/ActionContext.cs:294`.

- No test executes the new `AllOrNothing: false` / `Conjoin(read, grant, condition)` branch with a
  target that fails the condition.
  - `ValidationContextTests` checks only that the record keeps the condition.
  - In `OutboxManagementTests`, the validation round refuses every row that fails the condition,
    so the persist never meets one.
- Failure scenario: a later change drops `condition` from `Conjoin`, or composes the conditional
  spec with `AllOrNothing: true`. Every test still passes, yet `cancel` would overwrite a row the
  sending job has just pre-marked `Sending` (the email is sent while the row says `Cancelled`), or
  the action would fail with RowSecurity.
- This is a new public API in Abstractions, and its one behavioural promise (skip, do not refuse,
  do not stamp) is unpinned. §7.1's "filtered by … the precondition" has no test either.
- Suggested fix: add an integration test in the action pipeline suite. A fixture entity action
  composes `Update({…}, condition)` over two targets, only one of which meets the condition
  (validation does not judge it, so no race is needed). Assert three things:
  - the matching row is updated and stamped;
  - the other row's columns and `ModifiedAt` are unchanged;
  - the action commits with no RowSecurity or not-found error.

**R1-2 (minor): `retry` enqueues a new job for a target its conditional update skipped.**
`src/core/Tellma.Core/Outbox/OutgoingEmailService.cs:145-150`.

- The enqueue covers every `context.Entities` row, whatever the conditional update did.
- The one reachable skip: an orphaned `Pending` row is cancelled by another administrator between
  retry's validation and its persist. The update leaves it `Cancelled` (unstamped). The enqueue's
  owner check still accepts it, because its `JobId` names an ended job. So the row gets a new
  `JobId`, and a job runs that triage then succeeds unsent. The retry answers success for a row it
  did not retry.
- Benign (nothing is sent), but the action's answer is wrong, and a spurious job appears on the
  Jobs page.
- The plain `Update(assignments)` is not the fix. With no condition it would overwrite
  `Cancelled` back to `Pending`, and the email would be sent despite the cancel.
- Suggested fix: refuse rather than skip for retry. Either add an all-or-nothing conditional mode
  (a target failing the condition fails the action as a conflict), or check the state in the
  enqueue's owner update. Failing that, record the behaviour under Deviations and in the
  `RetryAsync` comment.

**R1-3 (minor): the new overload's contract overstates the skip and gives callers no feedback.**
`src/core/Tellma.Core.Abstractions/Validation/ActionContext.cs:283-298`;
`src/core/Tellma.Core/Crud/Actions/ActionRun.Persist.cs:338-346`.

- (a) The XML doc says a target that no longer meets the condition *or the grant's filter* "is left
  as it is rather than failing the action". For an action with `PostCheck`, `ComposePostCheck`
  still asserts that every target id (`expected: _ids.Length`) is under the grant filter. A target
  that left the grant filter between rounds therefore fails RowSecurity, so the documented skip is
  false there.
- (b) The overload returns nothing and exposes no receipt. A caller cannot scope a dependent write
  (an enqueue, a notification) to the rows actually updated, which is exactly R1-2's defect. The
  next caller that composes a follow-on write will repeat it.
- Suggested fix:
  - Either state in the doc that `PostCheck` still refuses a target outside the grant, or exclude
    skipped targets from the post-check.
  - Either expose the updated ids (for example a `ContextRef<UpdateReceipt>`, readable after
    `Persisted`), or document that dependent writes must not assume every target was updated.

**R1-4 (minor): a retry of an orphaned row whose outcome columns are already clear is not stamped.**
`src/core/Tellma.Core/Outbox/OutgoingEmailService.cs:145`, through
`src/core/Tellma.Core/Data/Batches/DataBatch.Updates.cs:451`.

- `WriteUpdate` skips a row that already holds every assigned value (`EXISTS (… EXCEPT …)`), and
  the stamps are skipped with it.
- Reachable path: an administrator cancels the sending job on the Jobs page before any claim, or
  the job ends `Jobs.Internal` before the pre-mark. The row is then `Pending` with every retry
  column null, and a retry enqueues the new job but leaves `ModifiedAt` and `ModifiedById`
  unchanged.
- §1.3 principle 3 and §10 ("`retry` and `cancel` stamp `ModifiedAt`") are not met for that row,
  and the implementer lists it only as an open risk, not under Deviations.
- Suggested fix: list it as a deviation and pin it with a test. Alternatively, give the data
  layer's `ByIds` a way to stamp regardless of the value comparison (for user actions with
  `Stamp: true`).

**R1-5 (minor): `delivery_updates` counts extra events of an unmatched row as `stale`.**
`src/core/Tellma.Core/Outbox/OutgoingEmailDeliveryHandler.cs:137-151`.

- `unmatched` counts distinct row ids from the writer's result. `stale` is
  `Weighed − Applied − unmatched`, where `Weighed` counts every classified event.
- Failure scenario: a deleted row receives Deferred and Bounced in one call. The counter records
  1 `unmatched` and 1 `stale`, not 2 `unmatched`.
- The instrument's doc (`OutboxTelemetryNames.DeliveryUpdates`: "each counted once by what became
  of it … unmatched (no row has its reference)") and the README say per event, and the unmatched
  alert under-reads.
- Suggested fix: carry each row's event count in `TenantDeliveryEvents` (for example a per-row
  weight beside `Rows`). Count `unmatched` as the sum of the unmatched rows' weights, and derive
  `stale` from what remains. Add the two-events-for-a-missing-row case to
  `Each_event_is_counted_applied_stale_unmatched_or_tenant_skipped`.

**R1-6 (minor): the retention's own control flow is untested.**
`src/core/Tellma.Core/Outbox/OutgoingEmailRetentionHandler.cs:79-83, 100-113`.

- Only a single short page is exercised. Three paths are unpinned: the multi-page loop, the
  `deleted == 0` guard against re-reading the same full page forever (a 600 s lease spent
  spinning), and the one re-read after a `ValidationException` or `NotFoundException` (deviation 8).
- Failure scenario: a change breaks the guard or the re-read, and no test fails.
- Suggested fix: add an integration case with 501 eligible rows (one `INSERT … SELECT`), asserting
  two pages, 501 retained and progress `deleted = 501`. Pin the re-read either with a seam that
  makes the first delete refuse, or by making `PageSize` internal-settable so a unit test can
  drive a fake stack.

Accepted without finding:

- Deviation 2 (failures aggregated after every tenant) gives the receiver the same 503 and
  strictly more progress.
- Deviation 7: the text cut keeps column widths. A truncated provider event id that collides is
