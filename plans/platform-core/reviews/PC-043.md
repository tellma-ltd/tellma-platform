# PC-043: Evaluation core: UserAccess.Decide, composition, owners, drift classification

## Implementer notes

### What was built, and where

- **Contracts** (`src/core/Tellma.Core.Abstractions/Access/`), the §5.1 set:
  - `AccessOutcome` (`Denied` is the default), `AccessProblemCode`.
  - The `AccessGrant` family: `RoleAccessGrant`, `BespokeAccessGrant`, `SystemAccessGrant`.
    `AccessGrant` is polymorphic JSON under `kind` (`role`, `bespoke`, `system`; an unknown kind
    fails), registered in `TellmaApiJsonContext`.
  - `AccessProblem`, `AccessDecision`, `AccessCriterion`, `IAccessCriteriaProvider`
    (`[CollectionService]`), `PermissionRow` (§7.1's shape).
  - Every record validates in its property initializers, so no shape can be built that
    contradicts the contract:
    - a filtered decision carries a filter and no other outcome does;
    - a denial lists no grant; an undefined outcome is refused;
    - a filtered role grant carries a supported stamp and an unfiltered one none;
    - a filter is never blank;
    - lists are copied and refuse null items.
  - Properties are get-only, so `with` cannot bypass the checks.
- **Evaluation**:
  - `AccessComposition` holds the §5.2 contract (steps 2–5) and §5.5's owner rule.
    - `Compose` is the stateless form for "who holds this".
    - `Matches`, `Direct` and `Finish` are shared with the set, so the two cannot disagree.
  - `UserAccess` is the cached set. Its members:
    - `Decide(securable, criteria, owner, now)` and `NextBoundary(now)`;
    - `MarkValidated`, a compare-and-swap max, ignored by `System`;
    - `ValidatedAt`, which defaults to `ComputedAt`;
    - `UserAccess.System`.
  - The direct side of each securable's decision is memoised until the next window boundary,
    keyed by securable and bounded at 4096 entries. Criteria and owner decisions are composed
    over the memo on every call.
  - Equality is identity, and a `with` copy gets a memo of its own.
- **Helpers** (Abstractions):
  - `AccessFilters`: `CurrentMembership` as a leaf, and `CurrentMembershipSql(alias)`, which
    refuses any alias that is not a plain ASCII identifier of at most 128 characters.
  - `QueryexProfiles`: `AccessLimits` and `PipelineLimits` (§12.2).
  - `AccessOptions` (§12.1), `AccessTelemetryNames` and `AccessEvents` (3100–3107).
  - `FilterTreeText` (internal) renders a criterion's tree for `BespokeAccessGrant.Filter`.
- **Build** (`src/core/Tellma.Core/Access/`):
  - `PermissionClassifier` runs the drift table in order. It validates each filter with
    `HasUser = true`, no parameters and `AccessLimits`, against the root's own entity, once per
    (root, text, stamp) per build.
  - `UserAccessBuilder.Build(tenantId, userId, tag, userTag, rows, schema)`:
    - classifies each distinct row shape once;
    - nulls public rows' windows;
    - drops memberships that have ended by `TimeProvider.GetUtcNow()`;
    - interns filters and role names (`AccessInterner`, bounded);
    - dedupes exact duplicates;
    - orders the grants (role, permission, start null-first, end null-last) and the problems
      (permission, code);
    - reports drift.
  - `AccessMetrics`: the set-build histograms and `permissions.unresolved` by `problem`.
  - `AccessLog`: `PermissionDrift` (Warning) and `AccessSetBuilt` (Debug).
  - `SecurableFilterRoots`: the root of a pair, or for `*` the root the resource's securables
    share.
  - `AccessRuntimeComposition` binds the options and registers the singletons. It is called
    from `CompositionPipeline`.
- **Registry and check**:
  - `ISecurableRegistry.FindResource` is new.
  - `core.securables` gains the shared-filter-root rule (see D3).

### Deviations

1. **D1: `AccessProblem` carries `Resource` and `Action`.** Spec §5.1 has
   `(PermissionId, RoleId, Code, Diagnostics)`. The pair is what lets a decision list the problems
   whose pair would have matched it. It is also what the drift log needs to name.
   - It holds the pair as far as it resolved: an alias resolved, the action's registered spelling
     once known, the stored text otherwise.
   - Problems are listed on every outcome, windows ignored.
2. **D2: `ISecurableRegistry.FindResource(resource)`.** It is alias-aware and returns the
   registered spelling. `Find(resource, action)` cannot resolve a `(FormerName, *)` row, and
   grants must carry the registered spelling so that matching and leaf dedup see one name.
3. **D3: New `core.securables` rule.** The securables of one resource that take a filter must
   share one filter root.
   - Spec §3.7 rule 2 binds an `(R, *)` filter against "the" root, which assumes one exists.
   - At run time, mixed roots classify `(R, *, filter)` as `FilterUnsupported`, which fails
     closed.
4. **D4: New `AccessProblemCode.WildcardResourceOnPublicRole`.** Spec §3.5 forbids `Resource = '*'`
   on a public role at save (`Permissions.WildcardResourceOnPublicRole`, which PC-078 owns). The
   build refuses such a row too, as defense in depth: a public role reaches every user, so a row
   saved before the rule, or written around it, would grant everyone everything.
5. **D5: `(*, A)` with an action no resource registers is `UnknownAction`.** §9's table speaks of
   `(R, A)` only. Without this, a misspelt action on `*` would still imply `Read` on every
   resource through the implied-read rule.
6. **D6: `AccessOptions` is validated by the `core.options` startup gate**
   (`OptionsRegistrar.Bind`, D-016), not `ValidateOnStart` as §12.1 says.
7. **D7: `PermissionRow` is declared here**, with §7.1's exact shape, because the builder consumes
   it. PC-050 should extend this declaration, not re-declare it.
8. **D8: Bespoke criteria and an owner's filter never reach a securable without a filter root.**
   §5.2 prunes only filtered role grants there. Extending the pruning fails closed: a filter that
   cannot bind must not become an unrestricted allow.
9. **D9: `UserAccess.IsSystem` has a private `init`.** §5.1 declares `{ get; init; }`. Only
   `UserAccess.System` and its `with` copies are system sets, so no code outside the type can mint
   a set that holds everything with an object initializer.
10. **D10 (review 1, R1-1; recorded as D-073): the implied read of a wildcard-resource grant is
    narrowed.** §5.2 step 2 lets a grant on another action than `Read` match `(R, Read)`. On the
    wildcard resource, `(*, A')` now matches `(R, Read)` only when `R` registers `A'`. This fails
    closed: a grant holding an action on one resource no longer reads every other resource.
    - `(R, A')` on a concrete resource is unchanged, since the build drifts any row naming an action
      `R` does not register.
    - The registry's action-to-resources map (`ActionResourceMap`) is frozen once by the classifier
      and carried by every set (`UserAccess.ActionResources`). `AccessComposition.Compose` takes it
      as a sixth argument, so "who holds this" composes exactly as `Decide` does.
    - A set without the map (`ActionResourceMap.Empty`, the default) implies no read through `*`.
11. **D11 (review 1, R1-4): the inactive-role case of the Decide matrix moves to PC-050.**
    `PermissionRow` carries no activity flag, because the load excludes inactive roles, so the
    test belongs to the load checkpoint.

### Rulings worth a second look

- **A set without a user** (`UserId <= 0`) denies everything, criteria included. Since criteria
  grant on their own, PC-052 must short-circuit no-user callers before `Decide`.
  - Excluding inactive roles is the load's job (PC-050). `Decide` never sees an inactive role.
- **`Decide` throws** (`ArgumentException`) on programmer errors instead of denying silently:
  - a wildcard securable;
  - a null criterion;
  - an owner decision passed for a securable without an owner;
  - a missing owner decision for one with an owner;
  - an owner decision for another pair.
- **The evaluator passes a denial for an owner pair the registry does not hold** (the remark on
  `Decide`). The owner rule is then the direct side alone.
- **An engine exception during validation** (a defect, never bad input) classifies the row as
  `FilterInvalid`, carrying the exception on the drift log event.
- **The drift counter uses the same dedupe as the log**: once per (tenant, permissions tag,
  permission, code).
  - The memory is bounded at 16384 entries and clears when full, so a problem may be reported at
    most once more after a reset.
  - The interner clears the same way.
- **`BespokeAccessGrant.Filter`** is a rendering for display, not Queryex: each child is
  parenthesised, and `Via` and `Exists` print as `via(Nav, …)` and `exists(Entity, Nav, …)`.
- **The memo** is keyed by `SecurableDescriptor` value equality. Two descriptors that differ only
  in `IsSensitive` or `Feature` memoise separately, which costs space only.

### Open risks, and what to examine hardest

- **Fail-closed paths in `AccessComposition.Finish` and `Direct`**:
  - the `FilterRoot`-null pruning of grants, criteria and owner filters;
  - absorption only by an unfiltered candidate that is actually current;
  - the owner `Via` added only when the owner is `Filtered`.
- **`PermissionClassifier`'s order and the `*` cases**: `(*, *)`, `(*, A)`, `(*, A, filter)`,
  `(R, *, filter)` with mixed or no roots, and public rows.
- **The memo** (`UserAccess.DirectAt` and `IntervalAt`): a side memoised for `[From, Until)`
  must never serve an instant outside it, including instants before `From` after a later

- **`AccessFilters.CurrentMembershipSql`**: the alias reaches SQL text.
- **JSON deserialisation of grants** goes through the constructors, so every invariant holds on

  server-produced.
- **Not covered**: stamp ordering across two versions is untestable while only version 1 exists.

### Findings

**R1-1 (major; spec ruling needed). A wildcard-resource grant on any action implies unrestricted
`Read` on every resource, including resources that do not register that action.**
- Where: `src/core/Tellma.Core.Abstractions/Access/AccessComposition.cs:137-146` (`Matches`). The
  test `test/core/Tellma.Core.Abstractions.Tests/Access/UserAccessDecideTests.cs:119-125` pins
  this behaviour.
- Scenario: a non-public role holds `(*, Invite)`, which is registered only on `core.User`, or
  `(*, Approve)`, which is registered on one document type. `Matches("*", "Invite", (core.Role,
  Read))` is true, so the holder gets unrestricted `Read` on `core.Role`, `core.Settings.General`,
  `core.Report` and every other resource. The row itself grants its action on one resource only.
- Why it matters: this is the same hazard D5 closes for an unregistered action ("a misspelt action
  implies Read on every resource"). D5 does not close it for an action that is registered on some
  other resource. §5.2 explains the implied read as "a grant on (R, A' ≠ Read) also matches
  (R, Read)". That reasoning holds for a concrete R. For `*`, it widens `Read` beyond the
  resources where the row grants anything.
- Status: the code follows §5.2's wording literally, so this needs a ruling, not a quiet change.
- Suggested fix, if the ruling narrows it: for a grant whose resource is `*` and whose action is
  concrete, the implied `Read` reaches only resources that register that action. `Decide` has no
  registry, so the build would compute this set once from the registry and keep it in
  `UserAccess`. For example, an internal map from each wildcard-resource action to the resources
  that register it, which `Matches` consults only in the implied-read branch. Add a Decide test:
  `(*, Approve)` does not reach `(fx.Kind, Read)` when only `fx.Widget` registers `Approve`.
- Owner: orchestrator. A spec amendment to §5.2 step 2 would be needed.

**R1-2 (minor). The run time relies only on the startup gate when one resource's securables use
different filter roots. The classifier fails closed for `(R, *)` but not for the implied read of
a concrete action.**
- Where: `src/core/Tellma.Core/Access/PermissionClassifier.cs:111` binds a concrete-action filter
  against that pair's own root. `AccessComposition.Matches` (`AccessComposition.cs:145`) then
  applies the same leaf to `(R, Read)`, whose root can differ.
- Scenario: the builder fixture has this registry already (`UserAccessBuilderTests.cs:50-51`,
  with `fx.Mixed` `Read` on `fx.Widget` and `Save` on `fx.Kind`).
  - `(fx.Mixed, Save, "Name = 'x'")` validates against `fx.Kind` and becomes a grant
    (`UserAccessBuilderTests.cs:191`).
  - `Decide(fx.Mixed:Read)` then emits the leaf `Name = 'x'`, which compiles against
    `fx.Widget`. A filter judged against one entity silently binds to a column of another.
- Today only `core.securables` (D3) stops this, and test compositions and any path that skips
  the gate do not run that check.
- Suggested fix: in `Classify`, for every filtered row on a concrete resource, require
  `SecurableFilterRoots.Shared(registry.ForResource(registered))` to be non-null and equal
  (ignoring case) to the pair's root, and return `FilterUnsupported` otherwise. This is the same
  fail-closed treatment D3 already gives `(R, *)`. Add a builder test: the `fx.Mixed` `Save` row
  drifts, or at least never reaches `fx.Mixed:Read`.

**R1-3 (minor; test adequacy). The engine-exception path has no test.**
- Where: `src/core/Tellma.Core/Access/PermissionClassifier.cs:173-194`.
- Reading the code, the `catch` fails closed (`FilterInvalid`, exception passed to the drift
  log). Nothing pins that, though. A later refactor could narrow the `catch` or let the exception
  escape `Build` without any test failing. An escaped exception would deny the user's whole set,
  which contradicts §9: "a drifted row never affects the user's other rows". The implementer
  notes say `QueryexEngine` is sealed, which is why no test exists.
- Suggested fix: give `PermissionClassifier` an internal seam for the validate call, for example
  an internal constructor that takes a `Func<string, ValidationOptions,
  QueryexResult<ValidatedExpression>>`, with the public path passing `engine.Validate`. Add a
  builder test where the seam throws for one text. It should assert:
  - that row is `FilterInvalid` with no diagnostics;
  - the user's other rows still grant;
  - the drift record's `Exception` is the thrown one;
  - an `OperationCanceledException` propagates.

**R1-4 (minor; PLAN.md §7.1 item 1). A test the checkpoint lists is deferred without a
Deviations entry.**
- Where: the commit message's Deviations, and the CHECKPOINTS.md Tests line ("Decide matrix — …
  inactive and public roles").
- No test covers inactive roles. The implementer notes explain why: `PermissionRow` has no
  activity flag, so the load (PC-050) excludes inactive roles. That reasoning is sound, but it

- Suggested fix: add a Deviations line in the fix commit, for example "inactive-role exclusion is

**Judgement on the implementer's deviations**
- **D1, justified.** §5.2 step 5 requires `Problems` to be "the excluded rows that would have
  matched". That cannot be computed from `(PermissionId, RoleId, Code, Diagnostics)` alone. The
  added fields are additive on the wire, and listing problems on every outcome is harmless.
- **D2, justified.** `Find(resource, action)` cannot resolve a `(FormerName, *)` row, and grants
  need one spelling so that matching and leaf dedupe stay sound.
- **D3, justified.** It makes "the root" in §3.7 rule 2 well-defined. Every registration in §4.2
  uses `FilterRoot = Resource` or null, so no spec registration is refused. See R1-2 for applying
  the same rule at run time.
- **D4, justified.** It is defense in depth for a save rule that PC-078 owns, and it fails
  closed.
- **D5, justified, because it fails closed.** It leaves a gap with §3.7 rule 1, which accepts
  `(*, A)` at save: an administrator can save a row that drifts as soon as it is saved. See
  decisions for the orchestrator.
- **D6, justified.** D-016 rules that declared options are validated by `core.options`, not by
  `ValidateOnStart`.
- **D7, justified.** The builder consumes the type, and PC-050 must extend it rather than
  re-declare it.
- **D8, justified, and it closes a real fail-open.** Without it, a bespoke criterion or an
  owner's filter on a securable with no filter root would yield `Filtered`. `IsAllowed` would
  then be true for an action that no pipeline applies a filter to.
- **D9, justified.** No caller in the specs needs to mint a system set by initializer. Only
  `ConnectAsSystem` does, and it uses `UserAccess.System`.
- **`Decide` throwing `ArgumentException`** on a wildcard securable or a missing, extra or
  mismatched owner decision: justified. These are programmer errors, and throwing fails closed.
- **`UserId <= 0` denies everything, criteria included:** consistent with the §5.1 `Evaluate` row
  ("a caller context with no user is Denied for everything").

**Checked and found sound (security focus)**
- Absorption happens only through an unfiltered candidate that is current at `now`.
- A filtered row never reaches a securable with no filter root, through any path: the role
  grant, `(R, *)`, a criterion or the owner.
- `(*, *, filter)`, `(*, A, filter)` and `(R, *, filter)` with mixed roots or no root all drift.
- A public `*` resource always drifts.
- Drifted rows never feed the outcome.
- Windows are half-open `[StartsAt, EndsAt)`. The memo holds `[From, Until)` between two
  adjacent boundaries, so it never answers an instant outside its interval, whichever way time
  moves.
- Each memo entry is written as one self-consistent unit, and losing a race only recomputes.
- `MarkValidated` is a correct compare-and-swap max, and `ValidatedAt` is never below
  `ComputedAt`.
- A `with` copy gets a fresh memo and boundary cache.
- `CurrentMembershipSql` refuses every alias that is not an identifier.
- Grants deserialise only through validating constructors, and an unknown `kind` fails.

- Filters: one leaf per `(text, stamp)`, compared ordinally. A blank filter never becomes a grant,
  since the classifier and the constructor both refuse it. Each leaf is parsed on its own under
  its own stamp, so no text can widen a neighbour.
- Owner union: an owner's filter joins only when the child takes a filter, and only as
  `Via(navigation, filter)`. An owner decision for another pair is refused.
- No user: `UserId <= 0` denies before grants, criteria or the owner are read.
- `IsSystem`: the setter is private, the type is sealed, and System.Text.Json does not write a
  non-public setter. Only `UserAccess.System` and its copies are system sets.
- `CurrentMembershipSql`: the alias is the only input and must be a plain ASCII identifier, which
  is then bracketed. No filter text reaches it.
- Fail-open paths: an engine exception, a missing root in the tenant's schema and a failed
  validation all leave the row a problem. `Decide` throws on a malformed call instead of allowing.
- Races: a memo entry is one immutable object, the boundary array is recomputed identically by
  any racer, `MarkValidated` is a compare-and-swap maximum, and a `with` copy shares neither.
- New public API: `ActionResourceMap` can only be built from securables and only narrows when
  empty. `FindResource` returns a name and decides nothing. See R2-1 for `Compose`.
- Logs: the drift warning carries ids, the pair and diagnostic codes, not the filter text.
- Nothing here differs between Windows and Linux.
