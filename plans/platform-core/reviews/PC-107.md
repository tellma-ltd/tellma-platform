# PC-107: Preferences, page state, drafts, tree expansion and recents

## Implementer notes

### What was built, and where

All client-side, in `client/projects/core/tellma-core/src/state/` unless noted. No C# changes:
the users' stack already carries `users/me/preferences/set` and `/delete` (D-210).

- **Preferences (spec 0025 §9)**, `prefs/`:
  - `tm-preference-key.ts`: `tmPreferenceKey(key, kind, fallback, validate?)` and the
    `TmPreferenceKey<T>` / `TmPreferenceKind` types. A development build refuses a key off the
    grammar or past 128 characters.
  - `tm-preferences.ts`: `TmPreferences` (`get`, `set`, `reset`). Reads overlay, then the stored
    `me.preferences` bag, then the fallback; each stored string is parsed once (a capped cache),
    and an invalid value falls back with one `tm.prefs.invalid` count per family. `set` encodes
    JSON, deletes when equal to the fallback, refuses a value past 32 KB in UTF-8 bytes, shows it
    at once in the overlay and broadcasts `prefs.changed` to the other tabs. Flushes: curated at
    once (a microtask), write-behind 2 s after the last change and at most once per 10 s, at once
    on hidden or past 8 KB pending, `nav.recent` at most every 5 min. On pagehide one keepalive
    send per tenant, capped at 16 KB across all tenants, newest first. Failures by kind: offline,
    unavailable, server and cancelled retry after 10 s or on going online; read-only drops; the
    key cap (`Users.TooManyPreferenceKeys`) drops the write; other validation drops only the
    named paths; a frozen tenant holds every flush. A sync's bag is adopted through
    `TmCacheRefresher.adopt(t, { preferences })`, and an overlay entry is settled away once the
    stored bag agrees (it stays while the key is dirty in this tab).
  - A development build checks a key's first segment against the platform's list or the app's
    declared features, at the first `get` or `set`.
- **Page state (§10)**, `memory/tm-page-state.ts`: `TmPageState` (`remember`, `recall`,
  `isStale`, `markStale`, `forget`), `tmPageStateKey(path)`. An LRU of 20. `markStale` by entity
  goes through `TmUrls.describe`, a hatch's key by its host page's. A permissions-tag move marks
  the tenant's pages stale; a languages change forgets them.
- **Drafts (§11)**, `memory/tm-drafts.ts` and `memory/tm-draft-keys.ts`: `TmDrafts` (`key`,
  `save`, `load`, `clear`, `clearAll`, `flush`, `dirtyCount`) over session storage
  (`ɵTM_DRAFTS_STORAGE`). Key `tm.draft:<sub>:<t>:<entity>:<id>`, value `{v:1,at,data}`, 300 ms
  debounce, flush on pagehide and hidden. On a full storage the oldest other drafts move to
  memory until the draft fits (`tm.drafts.quota-exceeded`); a draft of another user is refused.
  `TmSession`'s sign-in sweep now uses the shared `tmRemoveDrafts`.
- **Tree expansion (§12)**, `memory/tm-tree-expansion.ts`: `TmTreeExpansion` (`expanded`,
  `toggle`, `replace`) in the session partition's `tree:<page>` document `{ids}`, 250 ms
  debounce, at most 500 ids. Pending changes are kept as operations over the stored ids, so
  another tab's write in between is not lost.
- **Recents (§13)**, `memory/tm-recents.ts`: `TmRecents.pages`. A page of kind search, report,
  dashboard, settings, access or custom (never the drill-through list) counts after 2 s current
  and visible; stored as `[{p,k,t,n}]` under write-behind `nav.recent`, at most 10; filtered by
  access on read. Started at startup in `app/tm-app-init.ts`.
- **State dump**, `tm-state-dump.ts`: `ɵTmStateDump.read()` with the store's documents (names,
  tags, times), the refresher's last sync, the dirty preference keys, the draft keys and the page
  state keys; never a value.
- **Store** (`store/tm-client-store.ts`): `ɵlist()` for the dump, and the boot step now reads the
  session partition too, so tree expansion reads warm.
- **API** (`api/tm-api.ts`, `api/tm-http-api.ts`): `TmSendOptions.tenantId`, so a pagehide send
  reaches the tenant it names, not the routed one.
- **Testing** (`tellma-core-testing`): the state-testing providers give drafts an in-memory
  storage; `TmMapStorage` gained `length` and `key`.

### Deviations

1. `TmSendOptions.tenantId` added: §9's pagehide sends one call per tenant with pending keys,
   which the routed-tenant send could not do.
2. `remember(key, state, { keepStale })`: a host restoring a stale page can re-remember its
   scroll without clearing the mark (the planner's note).
3. A value another tab writes while this tab's write of the same key is in flight stays dirty
   here and is re-sent after the write lands, so the last writer wins on the server too.
4. The boot step reads the session partition with the user partition (§2.6 step 2 names only
   the user's); tree expansion would otherwise read cold.
5. The feature-segment check runs at the first `get`/`set` of a key, not in `tmPreferenceKey`,
   since keys are module constants created before injection; it is skipped without
   `TM_APP_DECLARATIONS`.
6. `TM_ROUTED_PAGE` and `TM_RECENTS_NAVIGATION` (internal seams) stand in for the page context
   and the launcher, which land later; recents name a page by its title until the launcher's
   entries exist.
7. The dump has no leader member yet, and is not registered with support's dump, which is
   spec 0026's.
8. On a full storage, evicted drafts move to memory instead of being lost.
9. The dump lists draft keys without the user part.
10. The `drafts.reply` answer to another tab is not here (the tab-coordination work).
11. The pagehide 16 KB cap is shared across tenants, not per tenant.
12. A validation answer naming paths drops only those keys; the rest are re-sent.
13. Tree expansion also flushes on pagehide.
14. Unauthenticated, step-up and client-outdated failures keep the keys until the next set,
    going online, or pagehide; an unknown error kind drops as rejected.

### Budget

`@tellma/core` "." measured 30.87 KB before and 36.00 KB after on the linked measure (+5.13 KB).
The ceiling went from 31 to 36.5, which is the addition rounded up to 0.5 KB. `budgetNotes` gives
the split, measured as each part's marginal gzip: preferences about 2.6, drafts 0.8, recents with
their seams 0.6, page state 0.5, tree expansion 0.5, and the rest 0.1.

**Spec 0025's primary services now weigh about 13.2 KB against their 9 KB share.** That share did
not budget §9's flush engine at its specified depth. It needs a ruling: raise the share, or accept
the overrun until the re-split.

Savings taken:
- The draft-key helpers are shared with the session's sweep.
- Recents use the page-state key for the path.
- The development checks sit behind ngDevMode.
- One dirty map per tenant serves every flush path.
- State is kept in private fields.

Moving the key check's guard to its call sites grew the measure by 0.13 KB, so it was reverted. "."
was not re-split.

### Open risks

- An overlay for a tenant that is not routed can stay shown over a newer stored value, if an
  administrator changes the value before the tab next syncs that tenant.
- `nav.recent`'s 5-minute spacing means a tab closed without pagehide (a crash) loses up to
  5 minutes of visits; by design, but worth knowing.

### What to examine hardest

- `TmPreferences.#settle` and `#received`: the overlay's lifetime against the stored bag, the
  in-flight resend rule, and the cross-tab broadcast.
- `#flush`/`#failed`: timing rules (2 s / 10 s / 8 KB / 5 min) and each failure kind.
- `#pagehide`: the 16 KB newest-first cut across tenants.
- `TmDrafts.#evict`: quota fallback ordering.
- `TmPageState`'s watch: marking on a tag move and forgetting on a languages change, and that a
  page remembered after the move is not marked.

### Findings

**R1-1 (major; needs a ruling under D-214): about 1.8 KB of the 5.13 KB raise has no first-frame
consumer, and the dump as written would pull 1.2 KB more onto the first frame when it is registered.**
`client/projects/core/tellma-core/package.json:32` (the 36.5 ceiling), `public-api.ts:101-131`,
`src/state/tm-state-dump.ts:37-39`, `src/app/tm-app-init.ts:206`.
- *Belongs on the first frame:* TmPreferences, about 2.47 KB. §15's "Badges, columns and view render
  from the store before first render" and the shell's `nav.pinnedBarVisible` (0027 §8.11) need
  `get()`, the overlay and the `prefs.changed` receiver before first render. The flush engine
  (`#schedule`, `#fire`, `#flush`, `#write`, `#failed`, `#drop`, `#pagehide`, about half of the
  class by eye, not measured) could load with `import()` at idle or at the first `set`. The dirty
  map and the overlay would stay in ".", so a `set` stays synchronous and a `pagehide` before the
  chunk loads can still send. That is a refactor of §9's design, so it belongs to PC-F69, not here.
- *No first-frame consumer:*
  - TmRecents with TM_ROUTED_PAGE and TM_RECENTS_NAVIGATION, about 0.56 KB. Its readers are the
    launcher (0027 §9.3, opened on demand) and the home page (0035 §15.3, a lazy page chunk). Only
    the visit count needs to start at launch, and a visit needs a 2 s dwell anyway. `tmStartup`
    could `import()` it after first render instead of `injector.get(TmRecents)` (tm-app-init.ts:206),
    from a secondary entry point. Today that startup call is also what puts TmPreferences on the
    first frame (33.60 against 30.57).
  - TmDrafts, TmPageState and TmTreeExpansion, about 1.69 KB together. Their consumers are 0030's
    search host, 0031's details host and 0034/0035's report and dashboard hosts, all lazy page
    chunks. A `@tellma/core/memory` entry point holding the three takes them out of "." (≈ 34.3 KB
    after the move). TmSession's sign-in sweep uses only `tm-draft-keys.ts`, which can stay in ".".
  - TmStateDump, ≈ 0.1 KB of its own. As written it injects TmDrafts, TmPageState and TmPreferences
    (tm-state-dump.ts:37-39). Once 0026's primary `TmSupport.registerDumpSection` registers it at
    startup, it will pull drafts and page state onto every first frame (+1.35 KB measured), whichever
    entry point they live in.
- Each move is a deviation from 0025 §1 ("Everything ships in the `@tellma/core` primary entry
  point") and an API-golden change, so it needs Ahmad (D-214). The raise itself follows D-031: the
  addition, 5.13 KB, rounded up to 5.5, measured as claimed. No accidental growth was found: no new
  dependency and no duplicate code, and the draft-key helpers really are shared.
- *Suggested fix:* in this checkpoint, at least make the dump read without injecting the services.
  For example, each service registers its own part when it is constructed, or the dump reads an
  internal registry the services fill, so that registering the section later costs ≈ 0.1 KB on the
  first frame and not 1.35 KB. Then either (a) move TmRecents (lazy start) and the three memory
  services into secondary entry points now, taking "." to about 33.7 KB (ceiling 34) with a
  deviation entry, or (b) keep the 36.5 raise and record these moves, with the sizes above, as
  PC-F69's first items. The orchestrator rules which.

**R1-2 (minor): two tree-expansion flushes that overlap lose a later toggle.**
`client/projects/core/tellma-core/src/state/memory/tm-tree-expansion.ts:168-187`. A flush sends
*every* pending change, including those an earlier flush still has in flight, and its `settle`
removes the first `changes.length` entries of whatever the list holds when the patch lands.
- *Failure:* toggle c1, and the 250 ms flush 1 sends [c1]. Its patch is slow: IndexedDB under load,
  or queued behind another tab's sync. Toggle c2, and flush 2 sends [c1, c2]. Toggle c3 before patch
  2 lands. Settle 1 leaves [c2, c3], then settle 2 slices 2 and leaves []. c3 has left the pending
  list without being written, and c3's armed timer finds nothing to flush, so the node snaps back
  and the expansion is lost. Flush 2 also re-applies c1 on top of a copy that may already hold
  another tab's later change of the same id (an open re-applied over that tab's close).
- *Suggested fix:* keep a per-page count of changes already sent, and send only the changes after
  it. Or tag each change and have `settle` remove exactly the changes it sent (`list.filter((change)
  => !sentSet.has(change))`). Add a test with a patch held open across two debounces and a third
  toggle.

**R1-3 (minor): deviations 11 and 14, and the failure kinds outside §14's list, have no test.**
`client/projects/core/tellma-core/src/state/prefs/tm-preferences.spec.ts` (whole file). Nothing
covers:
- a `pagehide` with dirty keys in two tenants: one send per tenant, each with its own `tenantId`,

- the `unauthenticated` / `step-up` / `client-outdated` keep-until-next-set-or-online path

- an unknown kind such as `forbidden` or `tenant-unavailable` dropping as `rejected` (:600-601);
- a validation error on a delete flush naming `keys[i]` (:587).

A regression in any of these, such as the routed tenant used for every pagehide send or an
unauthenticated failure retried every 10 s, would pass the suite. *Suggested fix:* one test each.

**R1-4 (minor): some private members have no TSDoc (AGENTS.md: "every ... member").** The build does
not enforce this for `#` fields, but the rule covers them:
- `tm-preferences.ts:175` `#lastRecent` (it shares `#lastFlush`'s comment);

### Findings

**R2-1 (minor; a correction to D-217's record): the "30.48 KB" first frame leaves out
TmPreferences, which still ships on every first frame, and nothing now creates it at startup.**
`client/projects/core/tellma-core/package.json:40` (the "." budgetNotes), this file's R1-1
response (lines 304-317), `src/app/tm-app-init.ts:127-134`.
- The recents chunk imports `TmPreferences` from `@tellma/core`. The primary's FESM is one module,
  and esbuild puts any export a lazy chunk uses into the shared chunk that the entry imports
  statically (Review 1's own check). So `TmPreferences` and its flush engine are on the first frame.
  - The first frame is ≈ 33.2 KB in the split build above, not 30.48. The saving over the 33.60
    before is ≈ 0.4 KB, not 3.1.
  - The response's claim that the first frame holds none of `pagehide-cap`,
    `Users.TooManyPreferenceKeys` or `nav.recent` is wrong for an app: all three are in the shared
    chunk. The other three probes are right.
- budgetNotes also keeps the superseded sentence "Split by spec, roughly: spec 0025's primary
  services now about 13.2 KB, over their 9 KB share by about 4.2 KB …" right after the new "about
  11.0 KB" one, so the note gives two different shares.
- The bytes are paid, but the service does not run. The only production `inject(TmPreferences)` is
  TmRecents' (tm-recents.ts:198). Until the recents chunk resolves, or for the whole launch when it
  fails, the tab has no `prefs.changed` receiver. A value another tab sets in that window shows
  here only once that tab's write lands and the store shows it: seconds for write-behind, up to
  5 min for `nav.recent`.
- *Suggested fix:*
  - Correct the note and the response table to the split-build figure, or teach measure3 to follow
    the `import()`.
  - Delete the stale split sentence.
  - Have D-217's record say that the first frame went from 33.60 to about 33.2.
  - Optionally, `inject(TmPreferences)` in `tmStartup` again. It is on the first frame anyway, so
    it costs nothing, and the receiver then runs from the start.

**R2-2 (major; needs a ruling, as a gap in 0025 §13): a new tab's first visit erases the visits
that other tabs have not flushed yet.**
`client/projects/core/tellma-core/recents/src/tm-recents.ts:267-272`, with
`src/state/prefs/tm-preferences.ts:407-428`.
- `#visit` builds the new list on this tab's view of `nav.recent`. A tab opened after another
  tab's visits never received their `prefs.changed`, so its view is the stored bag. Its `set`
  broadcasts the whole list, and `#received` in the other tab deletes that tab's unsent value
  (§14's "a received value drops the dirty one").
- *Failure:*
  - Tab A visits Centers, and the list is flushed about 2 s later.
  - At 30 s and at 60 s, A visits Agents and then Report 42. The 5-minute spacing holds both, the
    hidden flush included (§9.4's table).
  - At 90 s, the user opens Units in a new tab B. B's visit sets `[Units, Centers]`.
  - A receives it and drops `[Report 42, Agents, Centers]`. Agents and Report 42 are gone from
    every tab and are never written.
  - A user who opens pages in new tabs loses most visits this way, since each new tab starts from
    the stored list.
- That breaks §13's "the next visit in any tab builds on that list". The spec's mechanism (each
  `set` reaches every tab) covers only the tabs that were open at the time. No test has a tab that
  missed earlier broadcasts.
- *Suggested fix (for the ruling):*
  - Merge in TmRecents. Keep this tab's visits since its last flush. When `#stored` changes and
    lacks one of them, `set` the union by `p` again, newest `t` first, capped at 10. Tabs converge
    after one exchange, since the merged list holds the sender's visits.
  - Alternatives: a query and reply on the bus when a tab starts (a new message in 0025 §6.2), or a
    per-key merge hook in `#received` that `nav.recent` uses in place of the drop.
  - Add a two-tab test in which tab B starts after tab A's unsent visits.

**R2-3 (minor): a dropped write's broadcast can revert another tab's successful write of the same
key.**
`client/projects/core/tellma-core/src/state/prefs/tm-preferences.ts:610-622` (`#drop`), with
`:416-420` (deviation 3).
- `#drop` broadcasts the stored strings of the keys it drops as an ordinary `prefs.changed`. A tab
  whose own write of the key is in flight takes that as a later choice (deviation 3). Once its
  write lands, it re-sends the old stored string, so the bag ends on the old value although its
  write succeeded.
- *Failure:*
  - Tab A's write adds several new keys, among them K, and goes past the server's key cap. At the
    same time, tab B's write of K alone is in flight and fits.
  - A's key-cap drop broadcasts K's stored string, null.
  - B keeps null as the later choice. After its write lands, B sends null and deletes the value it
    has just saved. Both tabs show the fallback.
  - An unknown-kind drop does the same. The triggers are rare, hence minor.
- The same `#drop` also discards a later value held on the in-flight entry (from `set`, or from
  another tab through deviation 3), without sending it.
- *Suggested fix:*
  - In `#drop`, keep an entry whose value changed after it was sent: set `sending` to false and
    `retryAt` to 0, and leave it out of the broadcast.
  - Mark the broadcast of the dropped keys as a revert (for example, a `revert: true` flag), which
    a receiver applies to its overlay but never keeps as a later choice.
  - Add one test for each half.

**R2-4 (minor): the boundary rule's test-rig exception lets production code cross entry points in
two hops.**
`client/projects/core/tellma-core-tools/src/eslint/rules/core-import-boundary.ts:89-91`
(`isTestFile` counts a `*.testing.util` as a test file) and `:172` (the exception).
- The exception lets any `*.testing.util.ts` reach another entry point's `*.testing.util.ts`. A
  relative import within an entry point is never checked for its target's name.
- So a production file in `memory/src` can chain three hops, each of which passes in the probe
  above:
  - it imports `./y.testing.util`, which is allowed;
  - that file re-exports from `../../src/routes/tm-app.testing.util`, which the exception allows;
  - that file re-exports primary production code, which is allowed.
- `tsconfig.lib.json` excludes only `**/*.spec.ts`, so the build would compile a second copy of
  primary classes into `./memory`, with their own injection tokens. That is the failure the rule
  exists to stop.
- Today no `*.testing.util.ts` exists outside `src/`, and every user of the exception is a spec.
- *Suggested fix:*
  - Limit the exception to `*.spec.ts` importers, since nothing uses more, or also refuse a
    non-test file that imports any `*.testing.util`.
  - Add the chained case as an invalid test.

**R2-5 (minor; carries for the orchestrator): the moved services' later consumers cannot reach
them as the boundary table stands, and two readers must count drafts in a tab that has not loaded
`./memory`.**
`client/projects/core/tellma-core-tools/src/eslint/core-entry-points.ts:46-57`, and
`client/projects/core/tellma-core/src/state/tm-state-dump.ts:71`.
- The launcher's recent-pages band reads `TmRecents.pages` (0027, line 965), and `TmLauncher`
  ships in `./shell` (0027, line 82). `./shell` is eager, and "No eager entry point imports a lazy
  one", so the launcher must `import()` `./recents` or read it through a primary seam. The home
  page's `core.recents` widget (0035, line 770) has the same need.
- `./search` and `./details` list only `./entity`, and `./reports` and `./dashboards` list nothing.
  0030's, 0031's, 0034's and 0035's hosts need `./memory` in those lists, and the home page's host
  needs `./recents`.
- `TmDrafts.dirtyCount` counts session-storage drafts, which survive a reload. A tab that has not
  loaded `./memory`, such as one reloaded onto a report, has no TmDrafts.
  - PC-110's `drafts.reply` (0025 §6.2: `dirty = TmDrafts.dirtyCount`) must count those drafts
    without the service. Otherwise sign-out's confirm ("a draft is still dirty", 0024 §8.4) is
    skipped.
  - The dump's drafts part likewise reads `[]` in such a tab (tm-state-dump.ts:71), though storage

- *Suggested fix:*
  - Add WATCHLIST carries to the owners of 0027's launcher, of the 0030, 0031, 0034 and 0035

  - For the dump here, default the drafts part to `ɵtmStorageKeys` over `TM_DRAFTS_STORAGE` with
    the draft prefix. Both stay in ".". Strip the `sub` as deviation 9 does.

**R2-6 (minor): the lazy start of TmRecents has no test, and no type contract ties it to the module
it loads.**
`client/projects/core/tellma-core/src/app/tm-app-init.ts:45-48` and `:127-134`.

- The rejection handler is the `then`'s second argument, so an error while creating the service
  escapes it as an unhandled rejection, not as `tm-recents` telemetry. That covers both the rename

- *Suggested fix:*
  - Move the handler to a `.catch` after the `then`.
  - Add the three tests with the module stubbed, plus one that loads the real chunk, which also

**R2-7 (minor): `TmDrafts.flush()` is public API, although its doc calls it internal and 0025 §11

`client/projects/core/tellma-core/memory/src/tm-drafts.ts:188-189` and
