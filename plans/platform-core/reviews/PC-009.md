# PC-009: Resource grant evaluator, control-plane audiences, ThirdParty seeds

## Implementer notes

### What was built, and where

All in `src/apps/Tellma.Identity` unless stated.

- **The rule** — `Services/IResourceGrantEvaluator.cs`, `Services/ResourceGrantEvaluator.cs`
  (singleton). `IsGranted(granted, requested)`: ordinal exact match, or exactly
  `<origin>/<id>/mcp` where `<origin>` is a granted value that is a *canonical* origin
  (`IsOrigin`: http/https, host, no userinfo, `value == new Uri(value).GetLeftPart(Authority)`, so
  no trailing slash, no default port, lowercase host) and `<id>` is ASCII digits, first digit 1-9,
  at most ten digits, `int.TryParse` within `int`. Membership is always an ordinal loop, never the
  set's comparer. `IsGrantedExactly` is the exact half alone (for the control plane).
- **The one decision point** — `Services/ResourceGrantValidator.cs` (scoped).
  `FindRefusedAsync(ResourceGrantRequest)` returns the first refused resource (null = all granted;
  an empty request is never refused) and audits each refusal as `ResourceRefused`
  (`AuditActions.ResourceRefused`; client id, IP, details `{requested (≤512 chars), truncated,
  grantType, storedGrant}`) plus an Information log. What a request is evaluated against:
  - `StoredResources` set (code exchange, device-code redemption, refresh): those resources alone.
  - Otherwise the client's `rsrc:` permissions; a client with `tellma:document_client`
    (new `TellmaClientProperties.DocumentClient`, the seam PC-217 sets) also gets the
    distribution-origin list.
  - A control-plane client = one whose stored registration holds `scp:tellma_control_plane`: exact
    matching only, never the pattern; on `client_credentials` with the `tellma_control_plane` scope
    in the request, also the distribution-origin list, exactly.
  - Unknown client: everything refused. Distribution-origin list = the `tellma_api` scope's
    resources filtered through `IsOrigin`.
- **Pipeline handlers** — `Handlers/ResourceGrantHandlers.cs`, registered in
  `Hosting/OpenIddictConfigurator.cs`, which now also calls `IgnoreResourcePermissions()` (the three
  built-in rsrc checks — authorize, PAR, token — are off; `DisableResourceValidation` stays):
  `ValidateAuthorizationResourcesHandler`, `ValidatePushedAuthorizationResourcesHandler` (slots
  +500 after the disabled built-ins), `ValidateDeviceAuthorizationResourcesHandler` (OpenIddict has
  no resource check there), `ValidateTokenResourcesHandler` (picks the stored principal by grant
  type; a stored-grant grant type with no stored principal refuses everything). Every refusal is
  `invalid_target` with one fixed description. `AttachDeviceAuthorizationResourcesHandler` builds
  the device principal OpenIddict would (unauthenticated identity + scopes) plus the validated
  resources, so the device and user codes carry them (before this, a device grant could never carry
  a `resource` at all — OpenIddict keeps only scopes).
- **Narrowing** — `Handlers/NarrowAccessTokenAudienceHandler.cs` (ProcessSignIn, after every
  Prepare*Principal, before Generate*): for code / device / refresh grants at the token endpoint
  with request resources, sets the **access token's** audiences to them. The refresh token keeps
  the grant's resources, so every later refresh is evaluated against the original authorization.
- **Machine audiences** — `Services/MachineTokenAudiences.cs`, used by `TokenController` for both
  `client_credentials` and token exchange: explicit resources are the whole audience (no platform
  audience union any more); without one, the scopes' platform audiences; `tellma_api` without a
  resource is `invalid_target`.
- **Own-API audiences** — `Infrastructure/ApiPolicies.cs`: `HasAudience` (ordinal over every `aud`
  claim) beside `HasScope`; `IdentityScope` requires the issuer origin, `ControlPlaneScope` requires
  `urn:tellma:control-plane` (`HasControlPlaneAuthority` = scope + audience).
  `Configure(options, issuerOrigin)` is registered via `AddOptions<AuthorizationOptions>().Configure
  <IOptions<TellmaIdentityOptions>>` so it reads the final issuer. `ClientProvisioningService`'s
  "control plane sees every service account" widening now uses `HasControlPlaneAuthority`.
- **Authorize refusals** — `Controllers/AuthorizationController.cs`: `Authorize` (right after its
  unknown-client and PAR guards, which keep their own error codes) and `Accept` (first) call
  `RefusedByProtocol()`, re-raising any error OpenIddict already put on the transaction.
  See "Open risks" — this closes a pre-existing hole, and without it the resource refusal at the
  authorization endpoint was ignored (the action redirected to the sign-in page).
- **ThirdParty** — `TellmaIdentitySeedClientOptions.ThirdParty`; `ClientDescriptorFactory.SeededClient`
  omits `tellma:first_party` and forces explicit consent (even without `RequireConsent`), and throws
  on a non-Native kind; `TellmaIdentityOptionsValidator` refuses it on non-Native entries naming the
  entry.
- **Docs** — engine README ("Resources and audiences", the API table gains an Audience column),
  `Tellma.Identity.Web` README ("Seeded clients", with the interim agent entry template),
  ARCHITECTURE.md identity paragraph (one decision point; access-token-only narrowing; ThirdParty).

### Deviations (also in the commit message)

1. `IResourceGrantEvaluator` has a second member, `IsGrantedExactly`: §A.5 says the control plane
   is matched "exactly through" the evaluator, which one pattern-capable member cannot express.
2. The tenant id is bounded to a positive 32-bit integer (tenant ids are `int`, spec 0011 §3.1).
3. Only a canonical origin spelling anchors the pattern (no trailing slash, default port or upper
   case). Every origin the platform records is canonical, so this only refuses more.
4. Narrowing changes the access token only; the rotated refresh token keeps the original
   authorization's resources (RFC 8707 §2.2). §A.2 is silent on the rotated refresh token.
5. Device authorization now validates `resource` and carries it into the codes. Before, OpenIddict
   dropped it, so "device code" in §A.2's list had no path to apply to.
6. A resource refused at the authorization endpoint is rendered on the error page (400), not
   redirected to the client: OpenIddict never redirects a validation-stage error
   (`AttachRedirectUri` skips a rejected validation). OpenIddict's own check behaved the same.
7. Token exchange without a resource no longer takes every requested scope's resources: with
   `tellma_api` that was every distribution's origin at once (a cross-distribution token).
8. "The control-plane client stores no resource grant" is read as "no distribution grant": it keeps
   `rsrc:urn:tellma:control-plane` and `rsrc:<issuer origin>`, exact only. It is recognized by its
   `scp:tellma_control_plane` permission, not a new marker.
9. The service-account API's control-plane widening now needs the control-plane audience as well
   as the scope. `ServiceAccountApiTests` asked for its control-plane token with
   `resource=<issuer origin>`; it now asks without a resource (§A.5's token for the identity
   server's own APIs) and also pins that the issuer-only token gets no widening (404).
10. `ThirdParty` forces explicit consent even without `RequireConsent`, and is refused on
    non-Native entries (validation and the descriptor factory).
11. §A.4's interim entries are not shipped in `Tellma.Identity.Web/appsettings.json`; a template is
    in its README. See decisions below.
12. The document-client grant branch (`tellma:document_client` → distribution-origin list) ships
    now, unit-tested, as the seam PC-217 fills.
13. Errors that OpenIddict's built-in check answered as `invalid_request` are now `invalid_target`
    (the spec's "as before" assumed the latter).

### Open risks

- **Pre-existing, fixed here, worth a wider look:** with error pass-through on the authorization
  endpoint, a request OpenIddict refused (bad redirect URI, scope, resource, …) still reached
  `AuthorizationController.Authorize`, which started the interaction. The guard now re-raises the
  error in `Authorize` and `Accept`. The end-session endpoint has the same pass-through and its
  controller signs the user out without checking for a refusal (logout of the current user on a
  refused request; out of scope, not changed).
- An origin that is also the issuer's origin anchors tenant resources for clients granted it (the
  `-svc` backend, a CLI with `tellma_identity`). Harmless: the identity APIs require the exact
  issuer origin, and in-proc the issuer origin *is* the distribution origin, so excluding it would
  break in-proc MCP.
- A stored grant is evaluated against itself only; a later removal of the client's origin grant
  does not stop narrowing within an outstanding refresh token (as it does not stop a refresh
  without `resource`).
- The distribution-origin list is read per control-plane / document-client request (OpenIddict's
  entity cache serves it in production).

### What reviewers should examine hardest

1. `ResourceGrantValidator.FindRefusedCoreAsync`: control-plane detection, the exact-only path,
   the document-client branch, and that a stored grant never falls back to the client's grants.
2. `ValidateTokenResourcesHandler`: the grant type → stored principal mapping, and that it runs
   after OpenIddict's `ValidateAuthentication` has populated it.
3. `NarrowAccessTokenAudienceHandler`: that only the access token is narrowed, and only after the
   validator accepted the request's resources.
4. `AuthorizationController.RefusedByProtocol`: the pass-through gap and its fix.
5. `MachineTokenAudiences` + `ApiPolicies`: no path where a distribution-audience token passes an
   identity-server policy.
