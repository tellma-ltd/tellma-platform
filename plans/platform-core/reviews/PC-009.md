# PC-009: Resource grant evaluator, control-plane audiences, ThirdParty seeds

## Implementer notes

### What was built, and where

All in `src/apps/Tellma.Identity` unless stated.

- **The rule** — `Services/IResourceGrantEvaluator.cs`, `Services/ResourceGrantEvaluator.cs`
  (singleton). `IsGranted(granted, requested)`: ordinal exact match, or exactly
  `<origin>/<id>/mcp` where `<origin>` is a granted value that is a *canonical* origin
  (`IsOrigin`: http/https, host, no userinfo, `value == new Uri(value).GetLeftPart(Authority)`, so
  no trailing slash, no default port, lowercase host) and `<id>` is ASCII digits, first digit 1-9,
  at most ten digits, `int.TryParse` within `int`. Membership is always an ordinal loop, never the
  set's comparer. `IsGrantedExactly` is the exact half alone (for the control plane).
- **The one decision point** — `Services/ResourceGrantValidator.cs` (scoped).
  `FindRefusedAsync(ResourceGrantRequest)` returns the first refused resource (null = all granted;
  an empty request is never refused) and audits each refusal as `ResourceRefused`
  (`AuditActions.ResourceRefused`; client id, IP, details `{requested (≤512 chars), truncated,
  grantType, storedGrant}`) plus an Information log. What a request is evaluated against:
  - `StoredResources` set (code exchange, device-code redemption, refresh): those resources alone.
  - Otherwise the client's `rsrc:` permissions; a client with `tellma:document_client`
    (new `TellmaClientProperties.DocumentClient`, the seam PC-217 sets) also gets the
    distribution-origin list.
  - A control-plane client = one whose stored registration holds `scp:tellma_control_plane`: exact
    matching only, never the pattern; on `client_credentials` with the `tellma_control_plane` scope
    in the request, also the distribution-origin list, exactly.
  - Unknown client: everything refused. Distribution-origin list = the `tellma_api` scope's
    resources filtered through `IsOrigin`.
- **Pipeline handlers** — `Handlers/ResourceGrantHandlers.cs`, registered in
  `Hosting/OpenIddictConfigurator.cs`, which now also calls `IgnoreResourcePermissions()` (the three
  built-in rsrc checks — authorize, PAR, token — are off; `DisableResourceValidation` stays):
  `ValidateAuthorizationResourcesHandler`, `ValidatePushedAuthorizationResourcesHandler` (slots
  +500 after the disabled built-ins), `ValidateDeviceAuthorizationResourcesHandler` (OpenIddict has
  no resource check there), `ValidateTokenResourcesHandler` (picks the stored principal by grant
  type; a stored-grant grant type with no stored principal refuses everything). Every refusal is
  `invalid_target` with one fixed description. `AttachDeviceAuthorizationResourcesHandler` builds
  the device principal OpenIddict would (unauthenticated identity + scopes) plus the validated
  resources, so the device and user codes carry them (before this, a device grant could never carry
  a `resource` at all — OpenIddict keeps only scopes).
- **Narrowing** — `Handlers/NarrowAccessTokenAudienceHandler.cs` (ProcessSignIn, after every
  Prepare*Principal, before Generate*): for code / device / refresh grants at the token endpoint
  with request resources, sets the **access token's** audiences to them. The refresh token keeps
  the grant's resources, so every later refresh is evaluated against the original authorization.
- **Machine audiences** — `Services/MachineTokenAudiences.cs`, used by `TokenController` for both
  `client_credentials` and token exchange: explicit resources are the whole audience (no platform
  audience union any more); without one, the scopes' platform audiences; `tellma_api` without a
  resource is `invalid_target`.
- **Own-API audiences** — `Infrastructure/ApiPolicies.cs`: `HasAudience` (ordinal over every `aud`
  claim) beside `HasScope`; `IdentityScope` requires the issuer origin, `ControlPlaneScope` requires
  `urn:tellma:control-plane` (`HasControlPlaneAuthority` = scope + audience).
  `Configure(options, issuerOrigin)` is registered via `AddOptions<AuthorizationOptions>().Configure
  <IOptions<TellmaIdentityOptions>>` so it reads the final issuer. `ClientProvisioningService`'s
  "control plane sees every service account" widening now uses `HasControlPlaneAuthority`.
- **Authorize refusals** — `Controllers/AuthorizationController.cs`: `Authorize` (right after its
  unknown-client and PAR guards, which keep their own error codes) and `Accept` (first) call
  `RefusedByProtocol()`, re-raising any error OpenIddict already put on the transaction.
  See "Open risks" — this closes a pre-existing hole, and without it the resource refusal at the
  authorization endpoint was ignored (the action redirected to the sign-in page).
- **ThirdParty** — `TellmaIdentitySeedClientOptions.ThirdParty`; `ClientDescriptorFactory.SeededClient`
  omits `tellma:first_party` and forces explicit consent (even without `RequireConsent`), and throws
  on a non-Native kind; `TellmaIdentityOptionsValidator` refuses it on non-Native entries naming the
  entry.
- **Docs** — engine README ("Resources and audiences", the API table gains an Audience column),
  `Tellma.Identity.Web` README ("Seeded clients", with the interim agent entry template),
  ARCHITECTURE.md identity paragraph (one decision point; access-token-only narrowing; ThirdParty).

### Deviations (also in the commit message)

1. `IResourceGrantEvaluator` has a second member, `IsGrantedExactly`: §A.5 says the control plane
   is matched "exactly through" the evaluator, which one pattern-capable member cannot express.
2. The tenant id is bounded to a positive 32-bit integer (tenant ids are `int`, spec 0011 §3.1).
3. Only a canonical origin spelling anchors the pattern (no trailing slash, default port or upper
   case). Every origin the platform records is canonical, so this only refuses more.
4. Narrowing changes the access token only; the rotated refresh token keeps the original
   authorization's resources (RFC 8707 §2.2). §A.2 is silent on the rotated refresh token.
5. Device authorization now validates `resource` and carries it into the codes. Before, OpenIddict
   dropped it, so "device code" in §A.2's list had no path to apply to.
6. A resource refused at the authorization endpoint is rendered on the error page (400), not
   redirected to the client: OpenIddict never redirects a validation-stage error
   (`AttachRedirectUri` skips a rejected validation). OpenIddict's own check behaved the same.
7. Token exchange without a resource no longer takes every requested scope's resources: with
   `tellma_api` that was every distribution's origin at once (a cross-distribution token).
8. "The control-plane client stores no resource grant" is read as "no distribution grant": it keeps
   `rsrc:urn:tellma:control-plane` and `rsrc:<issuer origin>`, exact only. It is recognized by its
   `scp:tellma_control_plane` permission, not a new marker.
9. The service-account API's control-plane widening now needs the control-plane audience as well
   as the scope. `ServiceAccountApiTests` asked for its control-plane token with
   `resource=<issuer origin>`; it now asks without a resource (§A.5's token for the identity
   server's own APIs) and also pins that the issuer-only token gets no widening (404).
10. `ThirdParty` forces explicit consent even without `RequireConsent`, and is refused on
    non-Native entries (validation and the descriptor factory).
11. §A.4's interim entries are not shipped in `Tellma.Identity.Web/appsettings.json`; a template is
    in its README. See decisions below.
12. The document-client grant branch (`tellma:document_client` → distribution-origin list) ships
    now, unit-tested, as the seam PC-217 fills.
13. Errors that OpenIddict's built-in check answered as `invalid_request` are now `invalid_target`
    (the spec's "as before" assumed the latter).

### Open risks

- **Pre-existing, fixed here, worth a wider look:** with error pass-through on the authorization
  endpoint, a request OpenIddict refused (bad redirect URI, scope, resource, …) still reached
  `AuthorizationController.Authorize`, which started the interaction. The guard now re-raises the
  error in `Authorize` and `Accept`. The end-session endpoint has the same pass-through and its
  controller signs the user out without checking for a refusal (logout of the current user on a
  refused request; out of scope, not changed).
- An origin that is also the issuer's origin anchors tenant resources for clients granted it (the
  `-svc` backend, a CLI with `tellma_identity`). Harmless: the identity APIs require the exact
  issuer origin, and in-proc the issuer origin *is* the distribution origin, so excluding it would
  break in-proc MCP.
- A stored grant is evaluated against itself only; a later removal of the client's origin grant
  does not stop narrowing within an outstanding refresh token (as it does not stop a refresh
  without `resource`).
- The distribution-origin list is read per control-plane / document-client request (OpenIddict's
  entity cache serves it in production).

### What reviewers should examine hardest

1. `ResourceGrantValidator.FindRefusedCoreAsync`: control-plane detection, the exact-only path,
   the document-client branch, and that a stored grant never falls back to the client's grants.
2. `ValidateTokenResourcesHandler`: the grant type → stored principal mapping, and that it runs
   after OpenIddict's `ValidateAuthentication` has populated it.
3. `NarrowAccessTokenAudienceHandler`: that only the access token is narrowed, and only after the
   validator accepted the request's resources.
4. `AuthorizationController.RefusedByProtocol`: the pass-through gap and its fix.
5. `MachineTokenAudiences` + `ApiPolicies`: no path where a distribution-audience token passes an
   identity-server policy.

### Findings

**R1-1 (major) — A refused end-session request still signs the user out.**
`src/apps/Tellma.Identity/Controllers/EndSessionController.cs:37-62`. End-session pass-through and
error pass-through are both on (`OpenIddictConfigurator.cs:180-182`), so a request OpenIddict refused
(an unregistered `post_logout_redirect_uri`, an unknown `client_id`, a malformed or mismatched
`id_token_hint`) still reaches `EndSession`, which calls `signInManager.SignOutAsync()`,
`TerminateSessionAsync` (revoking the session's grants and fanning out back-channel logout to every
distribution) and audits `SessionTerminated`, before OpenIddict renders the error. Scenario: any page
can navigate a signed-in user to `/connect/endsession?post_logout_redirect_uri=https://evil/` and end
their SSO session and every distribution session, though the server refused the request. D-034
rules that a refused request never signs out. Fix: as in `AuthorizationController`, check
`HttpContext.GetOpenIddictServerResponse()` for an error first and return `Forbid` on the server
scheme with that error and description (the error page renders it); move the shared
`RefusedByProtocol` helper somewhere both controllers use. Add an integration test: a signed-in
browser hitting end-session with an unregistered `post_logout_redirect_uri` gets 400, no `Location`,
its identity cookie still authenticates, and no `SessionTerminated` row is written.

**R1-2 (major) — §A.4's interim agent clients are not shipped.**
`src/apps/Tellma.Identity.Web/appsettings.json` (no entries), `src/apps/Tellma.Identity.Web/README.md:41-68`
(template only), `src/apps/Tellma.Identity/Options/TellmaIdentitySeedOptions.cs:36`,
`src/apps/Tellma.Identity/Services/Seeding/IdentitySeeder.cs:65-79`. D-000b and D-034 say the
`claude-code`, `codex` and `cursor` entries ship (the hosted `claude-web` / `codex-web` stay out until
Ahmad supplies their callbacks). The implementer is right that they cannot go into the
`Seed:Clients` array; D-034 rules a key-addressed form instead. Scenario today: a standalone
deployment has no client a coding agent can use until each operator hand-writes three entries, which
§A.4 and Part A's DoD place in platform configuration.
Which form fits: a **dictionary section** fits the existing seeding code best, over code-defined
seeds. Every piece already works per entry: `ClientDescriptorFactory.SeededClient` (Native, `ThirdParty`,
`RequireConsent`, the loopback port relaxation of `PublicNativeClient`), the per-entry checks in
`TellmaIdentityOptionsValidator`, the converger's `CallsDistributionApis` resource union, and the
seeder's first pass, which must run before Distribution entries grant their origins. A dictionary only
adds a second source of entries to those loops. The Part A placement table and DoD put §A.4 in
`Tellma.Identity.Web` as configuration, and the retirement is "the entries leave the platform
configuration": both fit a config section and not seeds compiled into the engine, which would also
need config for the path override and for switching them off. Suggested fix:
- `TellmaIdentitySeedOptions.InterimClients`: `IDictionary<string, TellmaIdentitySeedClientOptions>`,
  keyed by client id (the key is the `ClientId`; a mismatching `ClientId` is a startup error), plus a
  per-entry `Enabled` (default true). Configuration layering can override a key but never delete one,
  so a deployment needs a way to turn an entry off.
- Ship the three entries in `Tellma.Identity.Web/appsettings.json`: `Kind: Native`,
  `RequireConsent` and `ThirdParty` true, `RedirectUris` `["http://127.0.0.1/callback"]`
  (RFC 8252 §7.3: port-less registration, any port accepted at runtime). The README documents
  `/callback` as the default path and the override key
  (`TellmaIdentity:Seed:InterimClients:claude-code:RedirectUris:0`).
- The seeder converges the enabled interim entries in the non-distribution pass. The validator
  applies the existing per-entry checks, naming `TellmaIdentity:Seed:InterimClients:<key>`, and refuses
  a key that is also in `Seed:Clients`.
- Tests: binding (a deployment's override of one key's redirect leaves the other two intact;
  `Enabled=false` seeds nothing), the seeded descriptors (explicit consent, no FirstParty, loopback
  redirect), and an integration check that onboarding grants a new origin to the three entries.
  Integration hosts built on `Tellma.Identity.Web` will now seed them too, so rerun the suite for
  count-sensitive assertions.
- Update the commit's Deviations, the Web README and the ARCHITECTURE.md sentence, which already
  describes them as shipped.

**R1-3 (minor) — One control-plane (or backend) token can span several distributions, or a
distribution and the operator API.**
`src/apps/Tellma.Identity/Services/ResourceGrantValidator.cs:153-172`,
`src/apps/Tellma.Identity/Services/MachineTokenAudiences.cs:53-56`. Each `resource` value is checked
on its own, and the explicit resources become the whole `aud`. So a `client_credentials` request from
the control plane naming `resource=https://acme…&resource=https://globex…` (or `…acme` plus
`urn:tellma:control-plane`) succeeds. The token then sits in acme's host and logs and is valid at
globex (or at the operator API). That is the property §A.5 and Decision 4 call structural ("a
control-plane token for one distribution is structurally invalid at another"). The same holds for a
`-svc` backend naming its origin plus the issuer origin with `tellma_identity`. The spec's text
("aud is exactly the named resources") permits it, and today it depends only on the caller behaving.
Fix: refuse with `invalid_target` a machine request whose resources include a distribution origin (or
a resource under one) together with any other resource, at least for the control plane. Pin it with a
unit test and an integration test. Decision for the orchestrator.

**R1-4 (minor) — An interactive CLI token naming a distribution resource also carries the
management audience.** `src/apps/Tellma.Identity/Services/AuthenticationPolicy/TellmaPrincipalFactory.cs:244-257`.
The interactive path still unions the platform audiences "unconditionally". A CLI (which holds
`tellma_identity`) authorizing `scope=tellma_api tellma_identity&resource=<acme>/17/mcp` without
narrowing at code exchange gets `aud = [<acme>/17/mcp, <issuer origin>]`. Acme's MCP endpoint
receives a bearer token that `ApiPolicies.IdentityScope` accepts at the management API, with the
CLI's client id as caller. §A.5 scopes the "whole audience" rule to machine tokens, so this conforms to
the spec, but it is the replay Decision 14 is about. Fix (decision for the orchestrator): apply the
whole-audience rule to interactive grants too (union platform audiences only when no `resource` is
named), or refuse `tellma_identity` together with an explicit distribution resource. Add an
integration test asserting the management API answers 403 to such a token.

**R1-5 (minor) — Device-code redemption has no end-to-end negative.**
`test/apps/Tellma.Identity.IntegrationTests/Flows/TenantResourceTests.cs:199-222` asserts the device
grant's `aud` and refuses a widening *refresh*, but no integration test redeems the device code
itself with a resource outside the device grant (for example the origin when `/17/mcp` was approved).
The rule is unit-tested in `ResourceGrantHandlersTests`, but the device path is the one this
checkpoint newly wired (principal attachment, verification-page resources), so it should be pinned
through the pipeline. Fix: add the redemption with `resource=<origin>` expecting `invalid_target` and
a `ResourceRefused` row, then redeem the same device code successfully without a resource.

  everything. The control plane is recognized from its stored `scp:` permission only, matched exactly, and
  reaches the distribution-origin list only on `client_credentials` with the control-plane scope.
- **Nothing changes between steps.** A code exchange or refresh naming a resource outside the code's or
  refresh token's own resources is `invalid_target` and redeems nothing (integration-pinned); the rotated
  refresh token keeps the original grant (`NarrowAccessTokenAudienceHandler` touches only
  `AccessTokenPrincipal`, after `PrepareUserCodePrincipal` and far before `GenerateAccessToken` at order
  100000). A PAR'd request is re-validated after `RestorePushedAuthorizationRequestParameters`; the consent
  `Accept` post is re-validated and re-raises a refusal. The device principal carries the validated
  resources (OpenIddict's fallback keeps only scopes), the user code carries them to the verification
  page, and redemption is held to them.
- **Machine and interactive whole-audience rule.** `MachineTokenAudiences` and
  `TellmaPrincipalFactory.SetAudiencesAsync` both make an explicit resource the whole `aud`; the BFF's
  derived origin is likewise alone and refused with `tellma_identity`; `tellma_api` without a resource is
  `invalid_target` for machine callers and for interactive clients without an origin. Token exchange is
  held by OpenIddict's `ValidateAuthorizedParty` to subject tokens that name the exchanging client as
  audience or presenter, so one client cannot re-target another's token.
- **Own-API audiences.** `IdentityScope` and `ControlPlaneScope` each require scope and audience;
  `HasAudience` is ordinal over every `aud` claim; the three management controllers use exactly these two
  policies; service-account widening uses `HasControlPlaneAuthority`. Standalone: a distribution token is
  403 at both APIs (integration-pinned, incl. the `-svc` backend naming its origin). In-proc: see R2-2.
- **Interim seeds.** OpenIddict's `ValidateRedirectUriAsync` relaxes only the port, and only when the
  registered URI is port-less, both are loopback with the same scheme, the same host
  (`localhost` and `[::1]` do not match `127.0.0.1`), the same userinfo, path, query and fragment; `..`
  is normalized away by `Uri.AbsolutePath` before the compare. `ThirdParty` forces `ConsentTypes.Explicit`
  and omits the first-party marker, whose only two readers (`ApplicationLinkResolver`,
  `InvitationReturnUrlValidator`) therefore refuse the agents; the agents hold no `tellma_identity`
  permission so OpenIddict refuses the management scope before any audience logic. A disabled or
  duplicate entry neither registers nor updates a row (validation refuses duplicates case-insensitively
  across both sections; a disabled entry is skipped). Seeding goes through the same per-write retry
  converger as every other seed, so concurrent hosts converge the same rows.
- **End session.** Error pass-through (`ProcessPassthroughErrorResponse` → `SkipRequest`) hands a
  refused request to `EndSession`, which now returns a bare 400 before `SignOutAsync`,
  `TerminateSessionAsync` and the audit row; OpenIddict's `AttachPostLogoutRedirectUri` reads only a
  non-rejected validation, so there is no redirect. The status-code page re-executes `/error`, which
  reads the transaction's error. Integration-pinned (cookie still authenticates, no `SessionTerminated`).
- **Leaks.** One fixed description for every refusal; the audit row quotes at most 512 characters; the
  refusal never says whether an origin is on the list. R1 fixes R1-1 to R1-5 all hold as described.

### Findings

**R2-1 (major) — An interactive grant may still name several distributions in one token.**
`src/apps/Tellma.Identity/Services/ResourceGrantValidator.cs:195-219`. `FindRefusedCombinationAsync`
applies the multi-resource rule only to `client_credentials` and token exchange
(`machine && RequestedResources.Count > 1`); an interactive request (authorize, PAR, device) is checked
only for `tellma_identity`. The CLI and the three interim agents hold every onboarded origin
(`tellma:calls_distribution_apis`), so
`GET /connect/authorize?client_id=tellma-cli&scope=openid offline_access tellma_api&resource=https://acme…&resource=https://globex…`
passes each value on its own and mints `aud = [acme, globex]`; the code exchange and every later refresh
without `resource` keep both. A user token sitting in acme's host and logs is then a valid user credential
at globex: the replay R1-3 closed for machine tokens, and the D-034 addendum names "more distributions"
as a refused combination. `ResourceGrantValidatorTests.cs:215-219` pins that the interactive path accepts
`[Origin, Origin/17/mcp]` ("the combination rule binds machine tokens"), so this is a conscious boundary
rather than an oversight, but the cross-distribution case is neither pinned nor refused. Fix: in
`FindRefusedCombinationAsync`, when an interactive request names a distribution resource, refuse any other
resource whose origin differs (or, for symmetry with the machine rule, any other resource at all); add the
unit vectors (`[acme, globex]`, `[acme/17/mcp, globex/17/mcp]`, both orders) and an integration test
(authorize with two origins → 400 `invalid_target`, one `ResourceRefused` row). Decision for the
orchestrator: whether same-origin combinations (`origin` + `origin/17/mcp`, `/17` + `/18`) stay allowed
interactively.

**R2-2 (minor, decision) — In-proc, the management audience is the distribution origin, so D-034's
one-place rule cannot hold there.** `src/apps/Tellma.Identity/Services/Seeding/IdentitySeeder.cs:91-99`
(in-proc: `tellma_api` resources = `[issuerOrigin]`, `tellma_identity` resources = `[issuerOrigin]`),
`src/apps/Tellma.Identity/Hosting/TellmaIdentityServiceCollectionExtensions.cs:145-147` (the policy
audience is `Issuer.GetLeftPart(Authority)`), `src/apps/Tellma.Identity/Services/Provisioning/ClientDescriptorFactory.cs:108-109`
(`-svc` holds `rsrc:origin` and `rsrc:issuerOrigin`, one value in-proc). Exposure, assessed: the
distribution-origin list is `{origin}`, so `IsDistributionResource(origin)` is true and a `-svc`
`client_credentials` request `scope=tellma_api tellma_identity&resource=<origin>` mints `aud=[origin]`
with both scopes, which spec 0011 §5.5's `Tellma.Api` (tellma_api + aud) and `ApiPolicies.IdentityScope`
(tellma_identity + aud) both accept; the combination rule sees one value and cannot fire. Every other
path is closed: the CLI's `resource` + `tellma_identity` is refused; the BFF, service accounts and tenant
tokens lack `tellma_identity` or carry a path; the CLI's management-only token (aud=origin, no
`tellma_api`) is refused by the distribution's scope check. So the real exposure is one client's own
dual-scope token, and in-proc both "places" are one process without an operator surface — low, but the
structural property is absent and nothing tests the in-proc policies with a token. Proposed fix, keeping
D-034's intent: make the management audience distinct from every distribution origin in both modes by
using the issuer *value* rather than its origin — `Issuer.AbsoluteUri.TrimEnd('/')`, which is
`https://acme.app.tellma.com/id` in-proc and the bare origin standalone (so standalone is unchanged) — as
the `tellma_identity` scope's resource, the `-svc` and control-plane `rsrc:` permission and the
`IdentityScope` audience; a URN (`urn:tellma:identity`, like the control plane's) is the alternative.
Both deviate from §A.5's "the issuer origin" wording: decision for the orchestrator. Pin with an in-proc
integration test (`InProcFactory`): a `-svc` token with `resource=<origin>` is 403 at
`/id/api/identity/v1/invitations/delivery-status`, and its `tellma_identity` token without a resource is
accepted.

**R2-3 (minor) — The token-endpoint resource check runs before OpenIddict has finished validating the
presented grant.** `src/apps/Tellma.Identity/Handlers/ResourceGrantHandlers.cs:187-191`
(`Exchange.ValidateResourcePermissions.Order + 500`). In OpenIddict 7.5.0 the token validation chain
continues after that slot with `ValidateProofKeyForCodeExchangeRequirement`, `ValidateAuthorizedParty`
(the presenter check), `ValidateRedirectUri`, `ValidateCodeVerifier` and `ValidateGrantedScopes`. So a
code exchange with a wrong PKCE verifier or `redirect_uri`, or a code/refresh token presented under
another public `client_id`, still has its `resource` evaluated against the stored grant: outside the grant
it is answered `invalid_target` and audited as `ResourceRefused` under that client id; inside it, OpenIddict
then answers `invalid_grant`. Scenario: an attacker holding an intercepted authorization code (no
verifier) probes `resource` values and learns which origin or tenant the code was authorized for from the
error code, and each probe writes an audit row attributed to the legitimate client; a failed exchange does
not consume the code, so probing repeats within its lifetime. Fix: order the handler after the last
built-in validation, `SetOrder(OpenIddictServerHandlers.Exchange.ValidateGrantedScopes.Descriptor.Order + 500)`,
extend `Every_check_runs_after_the_built_in_permission_checks_it_replaces` with `ValidateAuthorizedParty`
and `ValidateCodeVerifier`, and add an integration vector: wrong verifier plus an ungranted `resource` →
`invalid_grant` and no `ResourceRefused` row.

**R2-4 (minor) — `Enabled=false` on an interim entry leaves a live public client that keeps receiving
every new origin.** `src/apps/Tellma.Identity/Options/TellmaIdentitySeedOptions.cs:144-150`,
`src/apps/Tellma.Identity/Services/Seeding/IdentitySeeder.cs:66-67`,
`src/apps/Tellma.Identity/Services/Provisioning/ClientRegistrationConverger.cs:397-421`. A deployment that
sets `InterimClients:cursor:Enabled=false` after a first start keeps the `cursor` row, with
`tellma:calls_distribution_apis`, so `ListClientsCallingDistributionApisAsync` grants it each later
distribution's origin and anyone running software with `client_id=cursor` and a loopback redirect can
still mint tokens for every distribution, while the operator reads "turns it off" (D-034) and the README's
one sentence that it is not deleted. Nothing at runtime says so. Fix: when the seeder skips a disabled
entry whose client id exists in the store, log a Warning naming the client and that it must be deleted
to stop it (the seeder never deletes, as §A.1 says); say the same in the README's retirement paragraph.
Pin with an integration test (disable after a first start → the warning is logged, the row still
authenticates).

**R2-5 (minor, pre-existing, decision) — A parameterless end-session request still ends the SSO
session and fans out back-channel logout.** `src/apps/Tellma.Identity/Controllers/EndSessionController.cs:52-74`.
R1-1 closed the refused case, but a request OpenIddict has nothing to refuse — `GET /connect/endsession`
with no `client_id`, `id_token_hint` or `post_logout_redirect_uri` — is valid, so any page can force a
global logout (session termination, grant revocation, `logout_token` to every distribution) by top-level
navigation. OIDC RP-Initiated Logout 1.0 §6 says the OP should ask the end-user when it cannot verify the
request; spec 0003 §7.3 is silent, and this checkpoint did not introduce it. Fix (orchestrator decision,
outside this checkpoint's deliverables): when the request carries no `id_token_hint` whose `sid` matches
the cookie session, render a confirmation page instead of signing out at once; pin with an integration
test (bare request → confirmation, cookie still authenticates).
