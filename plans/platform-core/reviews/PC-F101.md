# PC-F101: Split the drafts code out of @tellma/core/memory

## Implementer notes

### The cause, confirmed

On a clean build of the measure-only merge of PC-126 with platform-core (`tmp/PC-126-merge-measure`,
15a8746f, which holds PC-126's fix2 and platform-core at 3ee3ab7d; the client and Acme sources
match 906d6306 apart from six spec files), Acme's `searchRoute` is **111.21 KB in 10 files**, as
PC-126 reported. One of the ten is a 2.62 KB chunk that both the search and details routes load:

| Module | Bytes in the chunk |
| --- | --- |
| `memory/src/tm-drafts.ts` | 2,470 |
| `memory/src/tm-page-state.ts` (`tmPageStateKey` only) | 42 |
| `core-ui/progress/tm-progress-bar.ts` | 3,582 |

Acme compiles core from its sources, so esbuild splits by source module. The search host imports
`tmPageStateKey` through `memory/public-api.ts`. That barrel re-exports `tm-drafts.ts`, so the
search route reaches that module statically. The details page uses `TmDrafts`, so its code is
live. esbuild therefore puts it in the chunk for the routes that reach it, which is search and
details, beside the progress bar that both routes render. An installed package gives the same
result, since one FESM is one module. `TmPageState` and `TmTreeExpansion` are not used yet (no
host remembers state or expands trees), so they shake out.

### Open risks

- When the details page starts reading `TmPageState` (spec 0031 §13), it will reach ./memory's
  barrel. `TmTreeExpansion`, which only tree search pages use, would then ride a chunk the details
  route loads. It was left in ./memory because the search page is its one user (spec 0030 §16.2),
  so moving it would not help the search route. If the details route's budget ever needs it, the
  same split applies.
- pc/PC-126 adds its own `"./search"` array to the same `"tellma".staticGraphExcludes` map in
  `client/projects/core/tellma-core/package.json` (the edit-stack guards: `./entity-editing`, the
  core-ui editors and `@angular/forms`). PC-126's integration must merge the two into one
  `"./search"` key that holds both lists. `JSON.parse` keeps only the last of a duplicate key and
  raises no error, so keeping both lines would silently drop one set of guards while `size:check`
  stays green.
- The narrowed allowances for `./admin` and `./report-studio` (no `./memory`) bind entry points
  that do not exist yet. A later checkpoint that needs page state there adds it back, with a
  reason.

### Findings

**Blocking:** none. **Major:** none.

**R1-1 (minor): the `./memory` budget note gives the pre-split measurement as both 2.55 KB and
2,606 B, which disagree.** `client/projects/core/tellma-core/package.json:85` says "measured 2.55
before (2,606 B) and 1.62 after (1,662 B), keeping 0.06 of headroom", and line 84 says "3.01
together against ./memory's 2.55 before". The commit message and the implementer notes repeat
2.55.

- `bundle-size.mjs` prints gzip bytes / 1024 with `toFixed(2)`, so 2,606 B prints as **2.54**.
  That matches the note's own "Born at 2.54" and the "0.06 of headroom" the note says it kept
  (2.6 - 2.54). With 2.55, the headroom kept would be 0.05.
- So either the figure or the byte count is wrong. A reader who checks the ratchet (D-031) from
  the note gets two different answers.
- Fix: write 2.54 on both lines (or correct the byte count if 2.55 was the printed figure), and
  check the 3.01 sum. 1,417 + 1,662 = 3,079 B, which is 3.01 KB, so only the "2.55" side changes.

**R1-2 (minor): the new `"./search"` key in `staticGraphExcludes` collides with PC-126's, and a
duplicate JSON key drops one guard without an error.** `client/projects/core/tellma-core/package.json:108`
adds `"./search": ["./drafts"]` after `"./leader"`. pc/PC-126 adds its own `"./search"` array
(`./entity-editing`, `@tellma/core-ui/entity-picker`, `date-picker`, `number`, `input`,
`multi-select`, `@angular/forms`) before `"./leader"`.

- Failure scenario: PC-126's integration resolves the conflict by keeping both lines. That is
  what "PC-126's exclusion lines plus `./drafts`" reads as. `JSON.parse` keeps only the last key
  and raises no error, and `size:check` stays green. Either the drafts guard or PC-126's seven
  edit-stack guards is then silently gone.
- The implementer notes' "Open risks" do not name this, so the integrator has no warning.
- Fix: add an open risk (and a line in PC-126's integration notes) saying the two `"./search"`
  arrays must merge into one key. Optionally make `bundle-size.mjs` refuse a library whose
  `staticGraphExcludes` names an entry point twice. That needs a raw-text scan, because
  `JSON.parse` cannot see duplicates.
