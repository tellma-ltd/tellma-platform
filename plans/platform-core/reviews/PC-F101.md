# PC-F101: Split the drafts code out of @tellma/core/memory

## Implementer notes

### The cause, confirmed

On a clean build of the measure-only merge of PC-126 with platform-core (`tmp/PC-126-merge-measure`,
15a8746f, which holds PC-126's fix2 and platform-core at 3ee3ab7d; the client and Acme sources
match 906d6306 apart from six spec files), Acme's `searchRoute` is **111.21 KB in 10 files**, as
PC-126 reported. One of the ten is a 2.62 KB chunk that both the search and details routes load:

| Module | Bytes in the chunk |
| --- | --- |
| `memory/src/tm-drafts.ts` | 2,470 |
| `memory/src/tm-page-state.ts` (`tmPageStateKey` only) | 42 |
| `core-ui/progress/tm-progress-bar.ts` | 3,582 |

Acme compiles core from its sources, so esbuild splits by source module. The search host imports
`tmPageStateKey` through `memory/public-api.ts`. That barrel re-exports `tm-drafts.ts`, so the
search route reaches that module statically. The details page uses `TmDrafts`, so its code is
live. esbuild therefore puts it in the chunk for the routes that reach it, which is search and
details, beside the progress bar that both routes render. An installed package gives the same
result, since one FESM is one module. `TmPageState` and `TmTreeExpansion` are not used yet (no
host remembers state or expands trees), so they shake out.

### What was built

- **`@tellma/core/drafts`**, a new lazy secondary entry point (`drafts/ng-package.json`,
  `drafts/public-api.ts`). `TmDrafts` and its spec move there unchanged (`git mv`); only the
  folder changes.
- **`@tellma/core/memory`** keeps `TmPageState`, `tmPageStateKey` and `TmTreeExpansion`. Its
  package doc names the drafts' new home.
- **Importers moved:** `details/src/tm-details-controller.ts`, `details/src/tm-details-source.ts`,
  `core-testing/src/provide-tellma-state-testing.spec.ts` (and the provider's TSDoc), and the
  `import()` calls in `src/session/tm-session-flows.spec.ts` and `src/state/tm-state-dump.spec.ts`.
  No distribution imports either entry point.
- **Entry-point table** (`core-tools/src/eslint/core-entry-points.ts`): `./drafts` is lazy and
  imports nothing.
  - `./details`, `./admin` and `./report-studio` may import it; `./search` and `./reports` may not.
  - `./admin` and `./report-studio` lose `./memory`, because the table's own comment granted it
    to them only for drafts.
  - A new spec test pins this.
- **Size gate** (`package.json`):
  - `./drafts` is born at 1.38 KB (1,417 B), with a ceiling of 1.5.
  - `./memory` goes down from 2.6 to 1.68: it measured 2.55 (2,606 B) before and 1.62 (1,662 B)
    after, keeping its 0.06 of headroom.
  - Both notes explain the split.
  - `staticGraphExcludes`: `"."` adds `./drafts`, and a new `"./search": ["./drafts"]` is added.
- **API goldens:** `core.drafts.api.md` is new, and `core.memory.api.md` loses `TmDrafts`.
  Nothing else changed in the `api:approve` run.
- **Docs:**
  - The core README: the entry-point table row, and the memory section (retitled, with the reason
    for two entry points and the guard).
  - The core-testing README.
  - The primary's `public-api.ts` comments, and the `tm-details-types.ts` comment.
  - ARCHITECTURE.md's `@tellma/core` row now lists `/drafts` beside `/memory`.

No runtime behaviour changes. The services, their injection scopes and the dump and session seams
(`ɵTM_STATE_PARTS`) are as before.

### Open risks

- When the details page starts reading `TmPageState` (spec 0031 §13), it will reach ./memory's
  barrel. `TmTreeExpansion`, which only tree search pages use, would then ride a chunk the details
  route loads. It was left in ./memory because the search page is its one user (spec 0030 §16.2),
  so moving it would not help the search route. If the details route's budget ever needs it, the
  same split applies.
- The narrowed allowances for `./admin` and `./report-studio` (no `./memory`) bind entry points
  that do not exist yet. A later checkpoint that needs page state there adds it back, with a
  reason.
