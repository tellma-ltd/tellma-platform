# PC-F106: Root-cause the tm-session-flows sign-out wait flake

## Implementer notes

PC-F106 has no CHECKPOINTS.md entry. It is a fix item, scoped by its LEDGER row, D-329, D-339 and
the brief. No spec section is in scope, and no product code changed.

### The failure

CI 45713926876 (pc/PC-F89 at edc6b4da), client-windows only: `tm-session-flows.spec.ts:410`,
"sign-out > asks after a minute of a save that never ends, and does not wait for it again",
`expected [] to deeply equal [ '/signed-out' ]` after `vi.advanceTimersByTimeAsync(100)`.

### Root cause

After the confirm, the sign-out runs `#leave`. Every step of it settles in microtasks under the
test rig (the fake API, the fake telemetry, the in-memory store's sweep), except one:
`#cleanUp` awaits `TmClientCache.clearAll`. The test rig does not replace `TmClientCache`, so it
enumerates and deletes in the page's real CacheStorage (`caches.keys()`) and IndexedDB
(`indexedDB.databases()`). Those answers come from the browser's storage backend, in real time.
No fake clock moves them.

The spec allowed that I/O a fixed number of real tasks. Vitest's `advanceTimersByTimeAsync`
(fake-timers `tickAsync`, checked in vitest 4.1.9's bundle) yields one real `setTimeout` task at
its start and one after each timer it fires. After the confirm, the rest of the 2,000 ms advance
fires no timer, and the 100 ms advance fires none either, since the sweep's 1 s time box is beyond
it. So the leave had about two real tasks to finish: a turn-count wait, the class CONTRIBUTING.md
forbids across chunk loads, here across storage I/O.

Measured locally (a temporary probe, reverted): `clearAll` took 2.9 ms of real time, and the window
from the confirm to the end of the 100 ms advance was 19.6 ms. Any storage round trip slower than
about 20 ms fails the assertion with CI's exact message. On a loaded Windows runner, with Chromium's
storage on disk, that is plausible.

### Reproduction

- **Storage latency probe:** a temporary 20 ms real delay (on `scheduler.postTask`, which no fake
  clock touches) before `caches.keys()` in `clearAll`. The spec file alone failed 1/23, only this
  test, with CI's exact message (`expected [] to deeply equal [ '/signed-out' ]`, line 410). After
  the fix, the same probe passes 23/23.
- **CPU load and the delay harness** did not reproduce it before the fix. The test was in each
  50-repeat run: 1,150/1,150 passed under 18 spinning worker threads (650 s), and 1,150/1,150 under
  the PC-F86 postTask harness (986 s). The race is on the storage backend's latency, which CPU load
  on this machine does not stretch past 20 ms. The harness delays only `import()`, and no import
  lies on the leave path: the flows chunk is loaded and cached by setUp.

### The fix (test only)

`client/projects/core/tellma-core/src/session/tm-session-flows.spec.ts`: after the confirm, the
spec waits on the leave itself, with `tmWaitUntil(() => rig.host.assigned.length > 0, () =>
vi.advanceTimersByTimeAsync(0), 'the tab left for the signed-out page')`. That is the wait
CONTRIBUTING.md prescribes under fake timers. The fake clock stays where the confirm left it, so
the test is stricter than before: the tab must leave with no fake time passing at all, where
before it had 100 ms. "Does not wait for it again" still fails if broken:

- **Mutation check:** making the confirmed sign-out always wait again
  (`if (answers.busy || !answers.busy)`, reverted) fails the test with "The condition did not hold
  within 4004 ms: the tab left for the signed-out page". The re-wait's first query window (300 ms
  of fake time) never ends under a zero advance. The query-count assertion is kept.

Product code is right as it is. A session's clean-up must wait for the browser's storage before
the tab leaves (spec 0024 §8.4), so there is no product cause to fix.

`CONTRIBUTING.md`: the wait rule's clause now names the browser's own storage (CacheStorage,
IndexedDB) next to `import()`. It also says that under fake timers an advance of any length is
still a turn count, since it yields one real task plus one per timer fired. No ARCHITECTURE.md
section describes this rule, so ARCHITECTURE.md is unchanged.

### The file's other sign-out and wait tests

I checked each test that fakes the clock or waits:

- "asks one question about both…": the confirm answers Cancel, so nothing on its path awaits
  storage. Its final `await signOut` waits on the promise itself, not on turns. Not affected.
- "shows another tab's sign-out, and lifts it after 15 s…" and "re-checks the cookie when another
  tab's sign-out overlay lifts": they assert only state set synchronously by the fired timer (the
  state, the overlay call, the expiry event). The expiry's storage clean-up that follows is not
  asserted. Not affected.
- The real-clock sign-out tests ("signs out with no question…", "asks once…", "waits for a running
  save…") and the expiry and changed-user tests already wait on state with `tmSettleUntil`, the
  real 4 s named deadline. "Waits for a running save" spends about 1 s of real time in the 1 s
  query loop by design, with about 3 s to spare. I left it on the real clock. Converting it is an
  optional speed-up, not a flake fix.

So the one site of this pattern in the file was the failing test.

### Open risks and what to examine hardest

- **The CI failure is not reproduced bit-for-bit.** The attribution rests on three things: the
  only real-time step on the path, the measured 20 ms window, and the probe reproducing CI's exact
  message. Check that nothing else on the leave path, after the confirm, needs real time: the fake
  API's microtask answer, the memory store's sweep, the bus posts and `TmUrls.signedOut()`.
- **Test isolation (a lead, not fixed here).** `provideTellmaStateTesting()` keeps the store in
  memory, but `TmClientCache` stays real. Every core spec whose path runs a session clean-up
  (sign-out, expiry, signed-out-elsewhere) therefore sweeps the shared test page's real `tm-*`
  CacheStorage caches and IndexedDB databases, and its `tm.*` localStorage and sessionStorage keys.
  A fake `TmClientCache` in the testing providers would make these paths microtask-only and keep
  specs from touching each other's browser storage. It changes a shared composition, so it is
  beyond this fix. The orchestrator may want an item for it.
