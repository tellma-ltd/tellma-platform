# PC-104: Localization, strings, server text and theme

## Implementer notes

### What was built, and where

Paths are under `client/projects/core/tellma-core/` unless noted.

- **`TmLocalization`** (`src/l10n/tm-localization.ts`, spec 0024 §7.1–§7.4, §7.7, §7.8's device zone): every §7.1 member as a signal (`language`, `dir`, `region`, `digits`, `locale`, `calendarCode`, `calendar`, `contentSlot`, `timeZone`, `deviceTimeZone`, `displayName`, `languages`, `calendars`, `localeSave`), and `setLanguage`, `setCalendar`, `setLocale`.
  - The resolution rules are pure functions in `src/l10n/tm-locale-resolution.ts` (language, switch list, content slot, calendar code, region, the step-4 locale string with the canonical `-u-nu-` rule, the once-per-tag browser check and its two-step fallback).
  - A switch loads first (the language's strings through Transloco, the calendar's entry point), then applies in one synchronous pass: the language and calendar `linkedSignal`s move only once their load is in, `<html lang dir>` and Transloco's active language follow, the boot record gets `{ lang, dir }`, and in a tenant the members go to the locale write. A `null` member returns to the tenant default; the language's `null` resolves to the tenant primary (when offered), so the boot record follows it.
  - A change stands at once through a per-tenant override that applies while the stored preference is still the one it was made over; the adopted write result (or another tab's) moves the stored value and the override lapses.
  - Telemetry: `tm.l10n.language-changed`, `tm.l10n.calendar-changed`, `tm.l10n.locale-changed` (only for a change within one place: entering another tenant is not a change) and `tm.l10n.locale-fallback { language }` once per language per launch.
  - It is also the app's message resolver (`ɵtext`, `ɵhas`): Transloco with the ambient `TM_UI_MESSAGE_CONTEXT` params, English per key, a caller fallback (entity labels), else the key with one development warning; every resolved message goes through `tmStripBidiControls`.
- **The locale write** (`src/l10n/tm-locale-write.ts`, §7.2): 600 ms coalescing, one write in flight, `reset` for `null` members, adoption through `TmCacheRefresher.adopt(t, { locale })`, `offline` → keep the queue and retry once when `TmApi.online` turns true, any other failure → `failed`; `pagehide` → `TmApi.send` with the answer unread; a queue left when the tab enters another tenant goes out at once to its own tenant.
- **Strings** (§7.3): `src/l10n/tm-translations.ts` is the loader `provideTellmaUi` gets: pack at the root, then `tmUi`, then `tm`; a pack key that is or begins with `tm`/`tmUi` is `string-key-collision`, dropped with a development warning; scoped loads return nothing. `tmEnglish()` (`src/l10n/tm-english.ts`) ships the platform's English `tm` table and the library's English; `tmArabic()` (`client/projects/locale/tellma-locale-ar/tm-arabic.ts`) ships `strings-tm-ar.ts` (gender-aware imperatives through `{gender}`) and the library's Arabic.
- **`TmServerText`** (`src/l10n/tm-server-text.ts`, §7.5): `problem` (`Problem_<code>` / `_Detail`, else the server's title and detail), `error` (code `.`→`_`, `arguments.property` → `<Schema>_<Entity>_<Property>` label, else the server's message), `message`, `has`; a three-text array argument renders the active content slot, else slot 1.
- **Argument formatter** (`src/l10n/tm-argument-formatter.ts`, D-023): `TM_UI_ARGUMENT_FORMATTER` formats `{d, date}` and `{t, time}` in the active calendar and display zone with the server's style mapping (none/`medium` → medium, `short` → numeric, `long` → long, `full` → weekday; time `short` → short, else medium); calendar dates and wall-clock times are not converted; numbers and unknown styles go to the library default.
- **Theme** (`src/app/tm-theme-sync.ts`, §7.6): `TmTheme` is seeded from `boot.read().theme` (through `provideTellmaUi({ theme })`), a setting change is written to the boot record, `boot.changes` applies other tabs' changes, and `<meta name="theme-color">` follows `--tm-theme-color` under `TmTheme.effective`.
- **Styles** (§7.6): `@tellma/core/styles.css` imports the tokens CSS, the core-ui fonts, the six directive stylesheets and the boot-page styles, and declares `--tm-theme-color: var(--ink-900)` in `@layer tm.base`; `@tellma/locale-ar/styles.css` imports the Arabic fonts. Package `exports` and `ng-package` assets carry the files; the workspace `client/tsconfig.json` and Acme's `tsconfig.json` map the CSS specifiers to the sources, which esbuild's CSS resolution honours.
- **`provideTellma`** (§2.2) now also provides `provideTellmaUi({ translations, availableLangs, theme })`, the theme glue, `ɵTM_APP_CONFIG`, `TM_ACTIVE_LOCALE` / `TM_CALENDAR` / `TM_TIME_ZONE` / `TM_DEVICE_TIME_ZONE` from `TmLocalization`, `TM_API_LOCALE` (`Accept-Language` = the step-4 string, `Tellma-Calendar` = `calendarCode`, §10.2), the argument formatter, the platform icons (`src/icons/platform-icons.ts`, the twelve directional glyphs with `mirrorInRtl`) and then each feature's `icons`.
- **Startup** (`src/app/tm-app-init.ts`): the boot language (`<html lang>`, else the default) and English load through `TmLocalization.ɵloadLanguage`, a failure still shows `load-failed`; after the store's boot step, `ɵready()` loads the language and calendar the launch documents resolve to (a failure keeps the boot language or `gc`).
- **`TmPlatformText` is gone.** The title strategy, the route error views, `TmEntities.label` and the shell stand-ins (tenant picker, signed-out page) read `TmLocalization`. The error views carry keys only; their English is `tmEnglish()`'s table.
- **Umm al-Qura** (`client/projects/core/tellma-core-ui/calendar-umalqura/`, D-029): the calendar is now the server's, self-contained: .NET's month table for AH 1318–1500 and the tabular arithmetic beyond it, generated vectors (`umalqura-vectors.json`) that both the client spec and `test/core/Tellma.Core.Tests/Calendars/UmAlQuraClientVectorsTests.cs` read. `TmCalendar` gained the internal `ɵownConversion` flag: such a calendar supplies the year, month and day itself and Intl only the names and the pattern (an anchor day mid-month), in `tmFormatDate`, `tmFormatDateTime`, the month names and the date popup.
- **Offered pairs** (§13): `client/e2e/fixtures/offered-pairs.json` (the catalogue's 243 pairs, pinned to `CultureDataSource.CataloguePairs()` by `test/core/Tellma.Core.Tests/Localization/OfferedPairsFileTests.cs`) and `client/e2e/specs/offered-pairs.spec.ts` (`@cross-engine`): every pair resolves exactly in `DateTimeFormat` and `NumberFormat`, apart from `om`, `ti` and `so` on Chromium.
- **Acme**: `tmEnglish()` / `tmArabic()` in `app.config.ts`, `angular.json` styles cut to `src/styles.css`, which imports `@tellma/core/styles.css` and `@tellma/locale-ar/styles.css`; README's stand-ins section removed.
- `TmClientMetadataStore` exposes `current`, a signal of the loaded Core chunk, so the formats follow its arrival.

### Deviations

1. `TmLocalization` resolves `TmLaunchCache`, `TmCacheRefresher`, `TmTelemetry` and `TmLocaleWrite` lazily: the router constructs `TmTitleStrategy`, which reads `TmLocalization`, and the refresher and the HTTP layer inject the router, so eager injection is a DI cycle.
2. At startup the routed tenant is known only after the first `NavigationEnd` (the refresher learns it from the router), so `ɵready()` resolves outside a tenant. A tenant preference that differs from the boot record's language therefore applies right after the first navigation. Every switch writes the boot record, so this shows only on a new device or after another device's change. Withdrawn in review 1 (R1-1): the refresher now reads the tenant from the address before the first navigation.
3. `§7.8`'s `pageshow` re-read runs on every `pageshow`, not only `persisted` ones: `TM_API_HOST.listen` passes no event. Reading the zone is cheap and idempotent.
4. `tmArabic()`'s tables are static imports: a dynamic `import()` inside one FESM cannot split, so a lazy form would only add an indirection. `@tellma/locale-ar` gains the `@tellma/core` peer (for `TmLanguageDefinition`). Withdrawn in review 1 (R1-6): the tables moved to the `@tellma/locale-ar/strings` entry point, which `tmArabic()` loads with `import()`.
5. The route error views carry keys only; their English moved to the `tm` table. The title strategy's English fallbacks went the same way.
6. `localeSave` reads `idle` until the first queued change creates the write.
7. The `theme-color` meta is created when the page has none.
8. The Umm al-Qura calendar no longer uses `@internationalized/date` or the browser's `islamic-umalqura` for its dates: ICU's table differs from .NET's on month starts in AH 1318–1419 and 1451–1500 (they agree on 1420–1450), so a client on ICU dates would disagree with the server's text. Intl still names the months; `ɵownConversion` and `ɵTmOwnDate` are new internal exports of `@tellma/core-ui/l10n`.

9. The `@tellma/core` primary's ceiling rose from 31 to 36 KB: measured 30.87 before and 35.61 after on the linked measure (+4.74 KB), rounded up to the next 0.5 KB. The development errors and warnings sit behind `ngDevMode` (−0.15 KB); the icon data is about 0.3 KB. The note in `package.json` carries the per-spec split.

### Open risks

- The offered-pairs e2e spec was not run through the Playwright suite (that needs the showcase server); its logic ran in a scratch Playwright script against the installed Chromium, Firefox and WebKit: Chromium misses exactly the eight `om`, `ti` and `so` pairs, Firefox and WebKit none.
- D-046: on Chromium, `om`, `ti` and `so` fall back past their default region to the default language's locale (`en-GB` in Acme), so those users see British day-first formats, not their own.
- Server: `UmAlQuraExtendedCalendar.DaysIn(9666, m)` throws for `m ≥ 5` (`HijriCalendar`'s range ends there), so the vectors stop at AH 9665's months; the client returns lengths there. Not changed here.
- In `ar-AE`, CLDR's default digits are Latin, so `Native` adds `-u-nu-arab` and `Latin` adds nothing; the unit tests pin that, against §7.7's table which uses `ar-SA` for the Latin row.

- The locale write's state machine (`#fire`'s offline requeue, the follow-up after an in-flight write, the tenant-change flush, `pagehide`).
- The own-conversion date path in `tm-date-engine.ts` (`ownDateParts`): the mid-month anchor and the day's padding probe, across locales and the date popup.
- The DI shape of `provideTellma` (the four library tokens and `TM_API_LOCALE` from `TmLocalization`) and the lazy services in deviation 1.

### Findings

**R1-1 (major): at startup the language and calendar resolve outside the tenant, so uq/et tenants paint Gregorian first. A tenant language preference also flips the page on every warm launch, not only once.**
- `client/projects/core/tellma-core/src/l10n/tm-localization.ts:516-521` (`ɵready`) and `:194` (`#tenantId` from `TmCacheRefresher.ɵpartition()`).
  - The refresher learns the routed tenant only on `NavigationEnd` (`tm-cache-refresher.ts:219-226`).
  - So `ɵready()`, awaited from `src/app/tm-app-init.ts:93` before the initial navigation, always resolves `#wantedCalendar()` to `gc` and the language to the boot record's.
- Failure scenario: a warm launch at `/17/...` for a user whose tenant calendar (or preference) is `uq`.
  - The first frame renders every date in Gregorian.
  - After `NavigationEnd`, the effect at `:368-371` imports `@tellma/core-ui/calendar-umalqura`, and `#calendarCode` flips: every date re-renders and its width changes.
  - The page's first tenant calls go out with `Tellma-Calendar: gc` (`TM_API_LOCALE.calendarCode()` is the loaded code). Server text in their answers is Gregorian.
  - This breaks §4.3 step 2 ("A cached calendar other than `gc` imports its entry point next", before first render) and §14's stable layout. The method's own TSDoc ("so a cached calendar or language never flashes another first") claims otherwise.
- The language half is worse than deviation 2 states. `boot.patch({ lang, dir })` runs only in `#apply` (`:570-572`), so a language that changes through the inputs (another device's change, adopted through `me`) never reaches the boot record. Every later warm launch on this device starts in the stale `record.lang` (§4.2: "Language, warm: `record.lang`") and flips after the first navigation, until the user switches on this device.
- Deviation 2's premise also does not hold at startup. The routed tenant is known from the path: the same initializer passes `tmRoutedTenant(document.location.pathname)` to the store's boot step, which has read that partition.
- Fix:
  - Resolve the startup inputs against the path's tenant. For example, seed the refresher's `#tenant` from `tmRoutedTenant(location.pathname)` at construction, or let `#tenantId` fall back to it until the first `NavigationEnd`. `ɵready()` then imports the tenant's calendar and loads its language before first render.
  - Patch the boot record's `{ lang, dir }` whenever the active language settles on a value other than `record.lang`, not only on a user switch.
  - Add a startup test: warm tenant 17 with `preferredCalendar: 'uq'`, and assert `calendarCode() === 'uq'` once the initializers resolve, before `tmNavigate`. The current `rig()` calls `ɵready()` after navigating (`tm-localization.spec.ts:140-142`), which hides this.

**R1-2 (major): D-046's om/ti day-first rule, routed to this checkpoint's §7.7 fallback, is not implemented. om/ti users see month-first dates on the client and day-first ones from the server.**
- `client/projects/core/tellma-core/src/l10n/tm-locale-resolution.ts:215-227` and the core-ui date engine apply no correction.
- D-046 (5) routes "the om/ti day-first rule ... to the client's 0024 §7.7 fallback", and the WATCHLIST lead says the client must apply it "or one user sees two date orders". The implementer's notes list only the Chromium fallback as a risk.
- Evidence: on CLDR 48 (Node 24, ICU 78.3), `new Intl.DateTimeFormat('om-ET' | 'om-KE' | 'ti-ET' | 'ti-ER', { timeZone: 'UTC' }).format(2026-03-05)` gives `3/5/2026`, and each resolves exactly. A browser on CLDR 48 passes the browser check, so `tmFormattingLocale` keeps `om-ET` and every numeric date, and its parsing, is M/d/y. The server pins d/M/y.
- On Chromium the fallback lands on the default language's locale. That is day-first only by accident in Acme (`en-GB`). A distribution whose default region is `US` sends om/ti users to `en-US`, which is month-first.
- Fix: mirror the server's correction on the client. For example, a small corrections table in the date engine's numeric pattern and field order for `om` and `ti` (day-first), applied to the formatting and the parser alike. Pin it with unit vectors for `om-ET`, `om-KE`, `ti-ER` and `ti-ET`. Or record it under Deviations for an orchestrator ruling.

**R1-3 (major): the locale write can send one tenant's queued members to another tenant, and its queue is per-writer, not per-tenant.**
- `client/projects/core/tellma-core/src/l10n/tm-locale-write.ts:137-146` with `:158`.
- Failure scenario:
  - In tenant 17 a write is in flight, and a second change is queued behind it.
  - The user enters tenant 18 and changes a member before 17's answer lands.
  - `queue(18, …)` calls `#fire()`, which returns at once because `#inFlight` is set.
  - Then `this.#tenantId = 18` and `this.#queue = { ...17's queue, ...members }`, so 17's member is written to the user's row in tenant 18.
- Related paths of the same state machine:
  - `:200`: `#sendNow` calls `TmApi.send` with no tenant. It goes to the routed tenant, not the queue's. It is the wrong tenant in the case above, and it fails outright on a tenantless page such as the picker.
  - `:176-180`: an offline failure for tenant 17 is dropped silently once tenant 18 has queued anything, against "offline keeps the queue".
  - `#awaitingOnline` is never cleared when a timer-fired write starts. After an offline failure followed by a successful send, the `finally` at `:189` no longer fires the changes queued during that send. They wait for an online false→true transition that may never come, and `localeSave` stays `saving`.
  - After a `pagehide` send, `localeSave` also stays `saving` forever on a back-forward-cache return.
- Fix:
  - Keep one queue per tenant (`Map<tenantId, TmLocaleQueue>`), and send each to its own tenant. That needs a `tenantId` on `TmSendOptions`, as reads and writes have.
  - Clear `#awaitingOnline` when any write of that tenant starts.
  - Settle `localeSave` after the pagehide send.
  - Add unit tests for the in-flight-then-other-tenant case and the offline-then-other-tenant case.

**R1-4 (major): the switch-atomicity test cannot fail when the rule breaks.**
- `client/projects/core/tellma-core/src/l10n/tm-localization.spec.ts:232-253`.
  - "Nothing changes before the strings land" is asserted synchronously right after `setLanguage`. `setLocale` always defers `#apply` to a microtask, and the test's string loaders resolve immediately (`:51`, `:97-113`).
  - An implementation that applied before the load, or that dropped both the `await` in `#apply` and the `linkedSignal` guards, passes the test.
- Nothing pins "one change-detection pass" either: no assertion sees `dir`, `<html lang>`, Transloco's active language, a message and `locale` flip together.
- This is a named CHECKPOINTS.md Tests item, and one the implementer asked reviewers to examine hardest.
- Fix:
  - Give `ARABIC.strings` (or the `ar` pack) a deferred promise. Call `setLanguage('ar')`, run `tmSettle()`, then assert that every member, the document, Transloco and a rendered `ɵtext` are unchanged.
  - Resolve the promise, settle, and assert that everything flipped.
  - Sample `(language(), dir(), locale(), contentSlot())` in an effect, and assert that no mixed tuple is ever observed.
  - Do the same for the calendar with a deferred `TmAppConfig.calendars` loader.

**R1-5 (major): §13's "the browser check's fallback, which leaves `Accept-Language` unchanged" has no test, and `tm.l10n.locale-fallback` has none.**
- `tm-locale-resolution.spec.ts:112-129` tests only `tmFormattingLocale`'s return value.
- `tm-localization.spec.ts` asserts `acceptLanguage()` once, on a resolving locale (`:202`).
- Wiring `TM_API_LOCALE.acceptLanguage` to `locale()` (the fallback) instead of `#requestLocale`, or dropping the once-per-language guard at `tm-localization.ts:392-395`, fails nothing.
- Fix: in `tm-localization.spec.ts`, offer `ZZ` among `en`'s regions in `METADATA` and give the user `preferredRegion: 'ZZ'`. Assert:
  - `locale()` is `en-GB`;
  - `TestBed.inject(TM_API_LOCALE).acceptLanguage()` is `en-ZZ`;
  - exactly one `tm.l10n.locale-fallback { language: 'en' }` is emitted across two re-resolutions.

**R1-6 (major): `tmArabic()` ships the Arabic tables in every user's initial bundle. The spec loads a language on its first switch.**
- `client/projects/locale/tellma-locale-ar/tm-arabic.ts:8-9,27`.
- §7.3 says "another language loads on its first switch", and §2.2's `strings: () => Promise<TmStringTable>` exists for it.
- The static imports put `TM_LOCALE_AR_STRINGS` and `TM_STRINGS_AR` into Acme's eager graph through `app.config.ts`. That is about 5.6 KB gzip (19.2 KB minified, UTF-8), measured on the two modules. Every English user pays it, against §12's 230/260 KB initial-JS budget, and each further locale pack adds its own.
- Deviation 4's premise is that one FESM cannot split a dynamic `import()`. That is true within an entry point, but it ignores the secondary-entry-point route that §7.4 uses for the calendars.
- Fix: move both tables into a secondary entry point (`@tellma/locale-ar/strings`), and make `tmArabic().strings` `() => import('@tellma/locale-ar/strings').then(...)`. Give that entry point a budget line, which the pack does not have today.

**R1-7 (minor): adoption is not pinned.**
