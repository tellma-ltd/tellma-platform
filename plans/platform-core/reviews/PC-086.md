# PC-086: Server emit: client entity model, enums, labels, action fields, .d.ts

## Implementer notes

### What was built

Spec 0029 §2 (all), §15, §16 (policy emission) and §5.1 (the display-name rule in each summary).

- **Abstractions** (`Tellma.Core.Abstractions/Client/`). `IClientEntityModel` (`Entities`, `Enums`,
  `Find`) and the part records: summary, full metadata, key, owner, property, navigation, child,
  action, action field, value descriptor, enum and enum value, display-name rule, limits, blob and
  image policy, multilingual slot, and their kebab/camel enums. Every record is in
  `TellmaApiJsonContext`. `SafeIntegerJsonConverter` writes `maxSize` as a JSON number and refuses
  one past 2^53 - 1.
- **Label chains** (`Localization/LabelChains.cs`). One pure function per label kind: entity,
  plural, create, property, navigation, collection, action, action field, enum value, plus
  `Resolve` (first declared key, else the chain's first key with a humanized fallback).
  `LabelProvider`, `ConventionalStringKeys` and the client model all walk these chains, so the
  server's labels, the resource audit's derived keys and the emitted keys cannot drift.
- **Named enums** (`Localization/NamedEnums.cs`). Each C# enum gets one name, `<schema>.<Type>`,
  from its home schema: the ordinally smallest schema among the entities and action arguments of
  the enum's own assembly that carry it, else among every site (entity properties, setting keys,
  stack and child-query action arguments). Every site's schema adds a key prefix, the home
  schema's first. The `core.value-sets` check reports two enum types of one name carried under one
  schema (review 1 changed both rules: R1-1, R1-2).
- **The model** (`Client/ClientEntityModel.cs`). It is built lazily, once, from
  `QueryexSchemaProvider.Map(MultilingualShape.All)`. It covers every root (stacks, children,
  read-only roots) with:
  - kinds, segments, operations, capabilities, owners and siblings;
  - multilingual slots, foreign keys, ownership, defaulted, long, precision and scale, value sets;
  - extras, limits (with Queryex's `maxFilterLength`) and blob policies;
  - actions, with argument fields and a JSON Schema (`ActionArguments`, through
    `GetJsonSchemaAsNode` with a transform that writes the wire's text forms of decimal and long).

  Entities and enums are sorted by ordinal name.
- **The contributor** (`Client/EntityClientAssetContributor.cs`). It writes the Core chunk's
  `entities` (summaries), the Entities chunk's `entities` and `enums`, and `tellma-entities.d.ts`
  (`EntityTypesWriter`). Every member of a summary comes before the full metadata's other members.
- **Client** (`@tellma/core`). `TmEntityTypes` and `TmEntityShapes` (empty augmentation targets) and
  `TmEntityType<N>`. Acme's three tsconfigs include `generated/*.d.ts`.

### Rulings worth a second look

- One name per C# enum type, from its home schema (R1-1). A type carried by two schemas is labelled
  by both schemas' keys (`Acme_CustomerType_Retail`, then `Gl_CustomerType_Retail`).
  `SettingKeyDescriptor.EnumType` now carries that qualified name (`acme.Cadence`).
- An `[EntityRef]` argument's key name drops `Id` (`AssigneeId` → `Assignee`), in the conventional
  keys too. Child-query actions' fields are included.
- Read-only roots have no CLR type:
  - their properties are server-owned and `excel: true`, with json names in camelCase and types
    from the store family;
  - hierarchy and geography columns are `binary`.
- `maxSize` is the kind's own `MaxSize` (R1-3; it was capped by the emitting machine's
  `Tellma:Blobs:MaxUploadSize` before review 1).
- The .d.ts includes read-only roots. It leaves navigations out of the wire interfaces, because the
  wire carries related rows apart; `TmEntityShapes` lists them.
- An action's schema has no `$schema` keyword.
- A child whose query surface opted out still carries `owner` from the metadata.

## Review 1

### Findings

Verified by the reviewer: `dotnet build Tellma.slnx` Build succeeded, 0 warnings; Tellma.Core.Tests
filtered to Client, LabelChains, ValueSetsCheck, Settings and Localization 1540 passed, 1 skipped;
Acme.Web.Tests ClientAssets 4/4; `client/tools/tests/entity-model.spec.mts` 4/4. Of the twelve
recorded deviations, nine are sound as written (Enums on the interface, qualified `EnumType`, which
spec 0032 §7.3's example already uses, the `[EntityRef]` `Id` drop, which is spec 0029 §2.4's own
rule, read-only roots, navigations left out of the wire interfaces, no `$schema`, summary-first
member order, the owner on an opted-out child, and the `.d.ts.txt` fixture, which the TS test still
compiles under its real name through a virtual host). The other three are R1-1, R1-2 and R1-3.

**R1-1 (minor) — an enum's public name depends on feature contribution order.**
`src/core/Tellma.Core/Localization/NamedEnums.cs:79-123` names each C# enum after the first site in
`IEntityMetadataProvider.All`, which is model (contribution) order. Scenario: a distribution adds a
feature, contributed before gl, whose entity carries gl's `CenterType`. The enum is then
`<thatschema>.CenterType` in that distribution. Its `enums` entry, every property's `enum`,
`SettingKeyDescriptor.EnumType` and the `.d.ts` type (`GlCenterType` is gone) all change, and a
pack that names `GlCenterType` or `'gl.CenterType'` stops compiling in that distribution only. The
label chain's first key also moves to the new schema. Within one composition the name is stable, so
nothing fails today. Spec 0029 §2.2 says an enum is "named by its type (`gl.CenterType`)", which
reads as the declaring module's schema. Fix: prefer the site whose owner belongs to the assembly
that declares the enum type (the feature that owns it), and fall back to the first site. At least
order the sites independently of contribution order. Pin it with a test that composes gl before and
after acme.

**R1-2 (minor) — two enum types of one simple name can share label keys undetected; README
overstates the check.** `src/core/Tellma.Core/Composition/Checks/ValueSetsCheck.cs:208-216` reports
only two enums with the same *name*. Scenario: `X.Status` is first carried by an acme entity
(`acme.Status`, prefixes `[Acme]`). `Y.Status` is first carried by gl and also by an acme entity
(`gl.Status`, prefixes `[Gl, Acme]`). No problem is reported, yet `Y.Status.Active`'s chain
(`Gl_Status_Active`, `Acme_Status_Active`) resolves to `Acme_Status_Active`, the key written for
`X.Status`. Both the server labels (`LabelProvider.EnumChain`) and the emitted `labelKey` silently
show the other enum's text. `src/core/Tellma.Core/README.md:99` already describes the stronger rule
("two C# enums of one type name are carried under one schema"), which the code does not enforce.
Fix: group by `(prefix, Type.Name)` over every `KeyPrefixes` entry, report a clash of two types, and
add a test with the cross-schema case.

**R1-3 (minor) — `maxSize` bakes the emitting process's upload limit into an immutable, public
chunk.** `src/core/Tellma.Core/Client/ClientEntityModel.cs:647` writes `Math.Min(policy.MaxSize,
blobOptions.MaxUploadSize)`. The emit composes from the Migrator's `appsettings.json` alone
(`src/core/Tellma.Core.Migrator/Commands/EmitClientAssetsCommand.cs`), so the result is
deterministic: no environment variables, no environment-specific files. It is still not the
deployment's value. `BlobsCheck`'s own remarks (`src/core/Tellma.Core/Blobs/BlobsCheck.cs:32-37`)
state that the blob options "are the deployment's" and that the emission skips the
`blobs.deployment` check, which holds the ceiling rule. Two consequences follow:
- On every host that starts, `blobs.deployment` refuses `MaxSize > MaxUploadSize`, so the min equals
  the kind's `MaxSize` and the cap can never bind correctly.
- It binds only when the Migrator's `appsettings.json` carries a smaller `Tellma:Blobs:MaxUploadSize`
  than a kind's size, a value the web host never enforces. Every client then refuses files the
  server would accept, until a rebuild.

`ClientEntityModelTests.cs:260` pins exactly that state, a composition whose `blobs.deployment`
check would fail. Fix: emit the kind's `MaxSize`, drop `IOptions<BlobOptions>` from the model,
replace the cap test with one that the kind's size is written, and record a deviation: spec 0029
§16's min is the kind's size on every host the startup gate admits.

**R1-4 (minor) — action fields and the schema ignore C# `required` and `[JsonRequired]`.**
`src/core/Tellma.Core/Client/ActionArguments.cs:82-86` decides `required` from nullability and
`[Required]` alone. It ignores `JsonPropertyInfo.IsRequired`, which STJ sets for a C# `required`
member or `[JsonRequired]`, and which makes deserialization refuse a body that omits the member.
Scenario: `public required string? Note { get; init; }` emits `required: false`, the generated dialog
omits an empty Note, and the server answers 400. Also, `Transform` (`:171-177`) writes `required`
only when its own list is non-empty. When every member is nullable but C#-required, the exporter's
own `required` survives, so `arguments` and `fields` disagree. Fix: `IsRequired(member) =>
member.Json.IsRequired || !IsNullable(...) || [Required]`, taking the `Member`. Always set
`required` from that list, removing it when empty, and add a fixture member with `required`.

**R1-5 (minor) — emit crashes on a child whose parent key has no navigation.**
`src/core/Tellma.Core/Client/ClientEntityModel.cs:182` calls
`entity.References.First(reference => reference.ForeignKey.Name == ownerKey)`. For a child that has
a query surface, `StackDescriptorBuilder.AddChildQueries` (`src/core/Tellma.Core/Crud/StackDescriptorBuilder.cs`,
the "owner rule" block) reports a missing navigation as a composition problem. A child with
`[ApiResource(Queryable = false)]` skips that block (`continue` before it), and so does a child of an
entity no stack serves. Scenario: such a child whose `[ParentKey]` is not named `<Target>Id` makes the
lazy model throw "Sequence contains no matching element", and the emit fails with an unexplained
contributor exception. Fix: `FirstOrDefault`, and leave `owner` null (or emit the owner without a
navigation) when none exists, with a test.

**R1-6 (minor, process) — a touched integration suite is missing from the commit's list.**
`test/core/Tellma.Core.Testing.Tests` carries `Category=Integration` tests
(`Sql/SqlDatabaseCreationServerTests.cs`, `Sql/SqlDatabaseDropServerTests.cs`). Its closure includes
`Tellma.Core.Abstractions`, which this commit changes, so PLAN.md §7.1 item 4 counts it as touched.
The commit's integration list (Core, EFCore, Queryex, Identity, Acme, connectors and E2E) omits it.
Reviewer's run: 4/4 passed, so only the record is missing. Fix: list it in the commit message.

**R1-7 (minor) — XML doc misstates the field key name.**
`src/core/Tellma.Core/Localization/ConventionalStringKeys.cs:58` says a field is "named as the wire
carries it less the trailing `Id`". The code (`LabelChains.FieldName`) uses the C# property name
(`Assignee`, not the wire's `assignee…`), as spec 0029 §2.4 requires. Fix: "named by its C# property
name, less …".

### Responses

- **R1-1: fixed in the "PC-086: review 1 fixes" commit.** An enum is named by its home schema: the
  ordinally smallest schema among the sites declared in the enum's own assembly (an entity's class,
  an action's arguments type), else among every site. Its key prefixes are the home schema's, then
  the others in ordinal order. Contribution order no longer moves the name, the `enum` of each
  property, `SettingKeyDescriptor.EnumType`, the `.d.ts` type or the first label key.
  - A setting key carries no declaring type in `SettingKey`, so a setting-only site counts for the
    fallback alone.
  - Within one assembly, two schemas resolve by ordinal order. The usual feature is one schema per
    assembly.
  - Tests:
    - `NamedEnumsTests.The_order_features_compose_in_changes_no_enums_name_or_keys` composes gl
      before and after acme; it fails on the old rule, which named `gl.CustomerType`;
    - `An_enum_is_named_by_the_schema_of_its_own_assembly_before_any_other`: an acme entity carries
      the platform's `Gender`, which stays `core.Gender` with keys `Core`, then `Acme`.
- **R1-2: fixed in the "PC-086: review 1 fixes" commit.** `core.value-sets` groups every enum's
  `(key prefix, type name)` over all its `KeyPrefixes`, ignoring case. It reports two types that
  share one:
  - as "both named" when their names match;
  - otherwise as label keys `<Prefix>_<Type>_<Member>` that would name the values of each.

  One report per pair of types. The README row now says what the check enforces. Test:
  `Two_enum_types_of_one_name_whose_label_keys_meet_under_one_schema_are_reported` (Dark.Shade is
  alpha.Shade, Light.Shade is beta.Shade, beta carries both).
- **R1-3: fixed in the "PC-086: review 1 fixes" commit** (orchestrator ruling). The policy's `maxSize`
  is the kind's `MaxSize`, and `IOptions<BlobOptions>` is gone from `ClientEntityModel`. The cap
  test became `A_blob_policys_size_is_its_kinds_whatever_the_emitting_hosts_upload_limit`: with
  `MaxUploadSize` 1000000, it still writes 10 MiB. The deviation is recorded in the fix commit:
  spec 0029 §16's min is the kind's size on every host `blobs.deployment` admits.
- **R1-4: fixed in the "PC-086: review 1 fixes" commit.** `ActionArguments.IsRequired(Member)` is
  `Json.IsRequired || !nullable || [Required]`, so a C# `required` member or `[JsonRequired]` member
  is required. The fields and the schema's `required` both read it. The transform always replaces
  the exporter's list, and removes it when empty. The fixture's `StatementRequest` gains a
  `required string? Layout` and a `[JsonRequired] string? Channel`, and the test asserts
  `["language", "layout", "channel"]` in the schema and `required: true` on each field.
- **R1-5: pushed back.** The crash cannot happen in a model that builds. `ChildConvention` always
  makes the parent key a foreign key (`AddForeignKey`). `EntityMetadataBuilder.Relations` gives
  every foreign key a `ReferenceMetadata`. When neither a model navigation nor an `Id` suffix
  yields its name, it reports instead: "The foreign key X.Y does not end in Id, so no navigation
  name derives from it". It does so whatever the child's query surface, so the model does not
  build and `core.entity-metadata` names the property. The emit reports that check's problem
  beside any contributor failure, and no host starts, so the lazy model never describes such a
  child.
  - Pinned with
    `EntityMetadataValidationTests.A_parent_key_whose_name_gives_no_navigation_is_refused_even_without_a_query_surface`:
    a `[ApiResource(Queryable = false)]` child whose `[ParentKey]` is `HolderRef` is refused.
  - `First` stays, with an inline comment naming that invariant.
- **R1-6: fixed in the "PC-086: review 1 fixes" commit.** `Tellma.Core.Testing.Tests`, run with the
  integration filter, is in the fix commit's Tests list, alongside every other touched suite.
- **R1-7: fixed in the "PC-086: review 1 fixes" commit.** The XML doc now reads "named by its C#
  property name, less the trailing `Id` of an entity reference".
