### Deviations

1. Six rows are written but skipped because their seams are not on platform-core (above). Not
   built here, per the orchestrator's instruction.
2. The suspension row asserts from a `ReadOnly` baseline rather than a served member request. A
   suspension's verdict applies to any authenticated caller, member or not (spec 0011 §3.3), and
   a served request needs the connect initializer. The test therefore stays valid after PC-050.
3. Tenant probes stand in for stack endpoints: no stack operation is projected onto the web API
   yet. The read probe runs a raw read batch rather than a projected `query`.
4. The two-host suspension test configures `Tellma:Identity:ClientSecret` and
   `ServiceClientSecret`. Without them each in-process Development host generates per-boot secrets
   and re-registers the engine's clients over the shared store at startup, so the earlier host's
   sign-in failed `invalid_client` (ID2055). A Development-only finding; a real multi-instance
   deployment configures the secrets anyway.

### Open risks

- The skipped bodies were not executed to green; whoever enables them must re-check the probe
  read's path once the guarded runner lands (spec 0014 §7.1 makes `IGuardedBatchRunner` the only
  way a service runs a batch for a caller, so the probe may need to go through it rather than a
  plain `ITenantDatabase` batch), the `me/locale` route and body shape, and the system-scope
  enqueue.
- `SqlConnection.ClearAllPools()` after `SET READ_ONLY WITH ROLLBACK IMMEDIATE` clears pools
  process-wide, which costs other classes running in parallel only a reconnect.

### What reviewers should examine hardest

- The suspension test's two-host setup: shared key ring and cookie jar, the 15 s bound against the

## Review 1

### Findings

**R1-1 (major) — the second-host bound cannot fail when the one-second refresh is not in effect.**
`distributions/acme/test/Tellma.Distro.Acme.IntegrationTests/TenantStateTests.cs:53` (bound 15 s),
`:226` (interval 1 s), `:265-273` (the poll). The test is named and documented as proving that a
suspension reaches a second host "within one refresh", but its bound (15 s) equals the default
`Tellma:Catalog:RefreshInterval` (`TellmaCatalogOptions.RefreshInterval = 15 s`), and
`TenantRegistryRefreshService.LoopAsync` starts its `PeriodicTimer` when host B starts, several
seconds (two host starts, the whole sign-in, two writes) before the suspension. Failure scenario:
the `Tellma:Catalog:RefreshInterval` setting stops reaching host B (key renamed, the host's options
bound before the test values, the loop reading a cached default): B's first tick still lands at
`15 s - (sign-in time)` after the suspension, inside the bound, and the test stays green while the
property it names ("within one refresh", 1 s here) is broken. It proves only "within 15 s", i.e.
within the default interval, not within the configured one. Fix: keep the bound clearly below the
default interval and a small multiple of the configured one (for example 5 s at a 1 s interval),
and assert what host B actually runs with (`second.Services` → `IOptions<TellmaCatalogOptions>`
→ `RefreshInterval == 1 s`, or the registry's `SnapshotLoadedAt` advancing once between the
suspension and the turn). If a tight bound is too timing-sensitive for the PR tier, PLAN.md §6
says timing-sensitive assertions go `@perf`/nightly with a CI multiplier; the PR-tier copy can then
keep the generous bound, but the bound that proves the rule must exist somewhere.

**R1-2 (minor) — host A's "very next request" can be answered by its own refresh, not by the local
write.** `TenantStateTests.cs:226`, `:234`, `:253-260`. Both hosts are started from the same
`acme.Values`, so host A also refreshes every second. The spec's "takes effect immediately on the
instance that received it" is `TenantCatalog.SetStateAsync`'s `RefreshAfterWriteAsync`; with a 1 s
loop on A, a tick landing between the catalog write and the next request also turns A, so a
regression in the after-write refresh is caught only most of the time, not deterministically.
Fix: start host A from a copy of the values with a long interval (e.g. `01:00:00`, the option's
maximum, with `MaxStaleness` raised to match), so A's `tenant-suspended` can only come from the
local write, and keep the 1 s interval on host B alone (which also sharpens R1-1).

**R1-3 (major) — nothing makes the six skipped rows run once their seams land.**
`TenantStateTests.cs:57`, `:94`, `:132`, `:153`, `:178`; `MigratorTests.cs:134`. The checkpoint's
Done-when ("every §10 Acme integration row green on both OSes") is not met, and the skips are
unconditional `[Fact(Skip = …)]`. The seam checkpoints' entries in CHECKPOINTS.md (PC-050, PC-078,
PC-080, PC-100, and the PC-049/PC-089 steps) say nothing about these Acme rows, and the implementer
notes name the seams but record no carries. Failure scenario: PC-050 lands the connect initializer,
its own suites go green, and `The_first_tenant_request_binds_the_signed_in_user`, the `Frozen` read
and the activity stamp stay skipped indefinitely, so a connect initializer that stamps activity on a
`Frozen` tenant (a write against a `READ_ONLY` database) or binds the wrong user ships unnoticed.
Fix (either, preferably both): (a) make each skip conditional with xUnit v3's `SkipUnless`, as
`test/connector/acs-email/Tellma.Connector.AcsEmail.IntegrationTests/AcsEmailLiveSendTests.cs:49`
already does, keyed on the seam's presence in Acme's composition (an `IRequestContextInitializer`
registered; a provisioning step named `core.bootstrap-administrator` composed; a projected
`users/me/locale` route; the job worker's hosted service registered), so each row turns on, and red
if wrong, the moment its seam integrates; (b) add explicit carry lines to "## Implementer notes"
(seam checkpoint → test name to un-skip) for the orchestrator to put on those checkpoints' status
rows, the way WATCHLIST.md records "PC-nnn → PC-mmm" carries.

### Responses


**R1-1 (fixed).** Host B now runs on an explicit `00:00:01` and host A on a separate copy of the
settings at `TellmaCatalogOptions.MaxRefreshInterval` (one hour, `MaxStaleness` raised to match).
The test asserts three things that the 15 s default cannot satisfy:
- each host's resolved `IOptions<TellmaCatalogOptions>.Value.RefreshInterval` (1 h on A, 1 s on B);
- B's actual loop cadence: before the suspension, the test watches `ITenantRegistry.SnapshotLoadedAt`
  until two refreshes confirm it, and asserts they lie less than 5 s apart (two confirmations within a
  10 s window, which a 15 s loop cannot produce);
- B's turn to `tenant-suspended` within 5 s, measured from just before the catalog write rather than
  after A's request. That is a third of the default and five of B's intervals.

I kept 5 s in the PR tier. B's path to the turn is at most one 1 s tick, then one catalog query, then
one in-process request, so 5 s leaves 4 s for a loaded runner. The cadence assertion separates the
settings deterministically on its own, so no nightly copy is needed. Spec 0011's "within one
interval" cannot be asserted exactly with a real clock; with a fake clock the host's other timers
would move too.

**R1-2 (fixed).** Host A runs on a one-hour interval, so its very next request after
`SetStateAsync` can only be refused by the after-write refresh.

**R1-3 (fixed, both parts).**
