# PC-006: Management API v1, tellma_kind, existingOnly

## Implementer notes

### What was built, and where

- **Versioned management routes (spec 0010 §A.8).** `src/apps/Tellma.Identity/Infrastructure/ManagementApi.cs`:
  - `ManagementApiVersions` (`V1 = 1`, `Segment(n)` → `v{n}`, `RoutePrefix(n)` → `api/identity/v{n}`).
  - `[ManagementApi(n)]` on a controller is both its `IRouteTemplateProvider` (the route prefix)
    and an `IFilterFactory` creating `ManagementApiCallFilter`, so the version that maps a route
    and the version that is counted cannot disagree.
  - `[ManagementApiEndpoint(name)]` names each action from the closed set `ManagementApiEndpoints`
    (`invitations.invite`, `invitations.delivery-status`, `service-accounts.create|get|delete`,
    `users.get`, `users.issue-temporary-access-pass`); an unknown name throws when MVC builds the
    model at startup.
  - `ManagementApiCallFilter` (an `IResourceFilter`, so after authorization and before model
    binding) records `tellma.identity.api.calls` (tags `version` = `v1`, `endpoint`) through
    `IdentityMetrics.ApiCall` and logs `Management API {Version} {Endpoint} called by client
    {ClientId}.` at Information. Instrument and tag names are consts on `IdentityMetrics`.
  - `ManagementApiCaller.ClientIdOf` (client_id ?? sub) replaces three copies in the controllers.
  - `InvitationsController`, `ServiceAccountsController`, `OperatorController` carry
    `[ManagementApi(V1)]` with relative action routes. The unversioned routes are gone. The
    in-proc route convention composes `/id` + `api/identity/v1/...` unchanged.
  - Callers repointed: every identity integration test, `eng/identity-ui-inspection/inspect.ps1`
    (CRLF kept) and `ui-inspection-guide.md`, the engine README. No caller exists in client code,
    distributions, templates, samples or other projects (`git grep api/identity` outside docs/ and
    plans/ now matches only `/v1/` paths and the three controller summaries).
- **`tellma_kind` (spec 0010 §A.6).** `TellmaClaims.Kind`, `TellmaKinds` (`individual`,
  `service`, `ForGrantType`) in `Services/AuthenticationPolicy/PolicyConstants.cs`;
  `Handlers/TellmaKindClaimHandler.cs`, a `ProcessSignInContext` handler registered in
  `OpenIddictConfigurator`, ordered after `PrepareUserCodePrincipal` (the last principal-preparing
  handler) and before `GenerateAccessToken` (the first generator). It:
  1. strips `tellma_kind` from every prepared principal (access, code, device code, id token,
     issued, refresh, request, user code);
  2. writes the grant type's kind into `AccessTokenPrincipal`, and into `IssuedTokenPrincipal` when
     a token exchange issues an access token;
  3. rejects the sign-in (`server_error`) when an access token would be signed outside the token
     endpoint or for a grant type with no kind, instead of signing one without the claim.
  `TellmaClaimDestinations` also gives the claim no destination, as defence in depth.
  Mapping: authorization_code, device_code, refresh_token → individual; client_credentials,
  token_exchange → service. A refresh is individual because the token endpoint refuses any refresh
  whose subject is not a stored active user; an exchange is service because it refuses any user
  subject token. Both refusals run before `SignIn`, so the handler never labels wrongly.
- **`existingOnly` (spec 0010 §A.7).** `InviteUserItem.ExistingOnly` (DTO),
  `InvitationRequestItem.ExistingOnly`, `InvitationErrors` (`unknown_email`,
  `existing_user_has_no_credential`), `ExistingOnlyOutcome` + `ExistingOnlyResolution.Resolve`
  (the pure outcome table), and `InvitationService.ResolveExistingOnlyAsync`, which runs before the
  return-URL check and never reaches token issuance or the mail list. `RefuseAsync`,
  `HasCredentialAsync` and `RestoreOrphanedAsync` were extracted and are shared with the ordinary
  path (no behaviour change there; refusal audit rows gain `existingOnly`).
- **README** (`src/apps/Tellma.Identity/README.md`): a "The management API" section (routes,
  versioning rules, counter, existingOnly, tellma_kind).
- **ARCHITECTURE.md**: already states the versioned routes, `tellma_kind` and `existingOnly`
  (Identity section); nothing disagrees, so it is unchanged.

### Deviations

1. ~~Calls are counted once authorized.~~ Withdrawn after Review 1 (orchestrator ruling D-026):
   every call is counted and logged with an `outcome` tag (`ok`, `error`, `unauthorized`,
   `forbidden`); see R1-1.
2. **`existingOnly` ignores `ReturnUrl`.** §A.7's table lists four outcomes; validating a return
   URL that no link carries would add a fifth refusal. The DTO docs say it is ignored. (Spec 0018
   sends the tenant link on sandbox invites; it stays harmless.)
3. **An orphaned user with a credential answers `Active` and is restored to `Active`** (spec
   silent; the table only says "an existing user who holds a credential"). Leaving the user
   orphaned would answer Active for a user who cannot obtain tokens (spec 0003 §10.5); the restore
   is the same audited write an ordinary invite makes, and no user, link or email results, which
   is what §A.7's "no side effects" enumerates. An orphaned user without a credential answers
   `existing_user_has_no_credential` and is not restored.

### Open risks

- `unknown_email` turns `existingOnly` into a silent directory probe for any `tellma_identity`
  caller. The exposure equals what an ordinary invite already gives for credentialed users
  (`Active` + `sub`, no email), the caller is a provisioned distribution, refusals are audited
  (`UserInvited` failure with `existingOnly: true`), and the batch is capped at 1,000. Successful
  lookups are not audited, like an ordinary `Active` result.
- The kind mapping for `refresh_token` and `token_exchange` relies on two token-endpoint
  refusals (no refresh for a subject that is not a stored active user; no exchange of a user
  token). The second is pinned by `Endpoint_refuses_a_user_token_even_from_the_client_that_holds_it`.
  For the first, no machine client descriptor holds the `refresh_token` grant permission
  (`ClientDescriptorFactory`), so OpenIddict refuses a machine refresh before the endpoint's own
  user lookup would. Changing either rule must revisit `TellmaKinds.ForGrantType`.
- A token exchange with `requested_token_type` other than an access token is refused by OpenIddict
  today (only `access_token` is enabled); if another type were enabled it would carry no kind.
- PC-009 adds `HasAudience` to `ApiPolicies`; the route attribute and filter do not touch policies.

### What reviewers should examine hardest

- `TellmaKindClaimHandler`: the order against OpenIddict 7.5's built-in handlers, the strip of
  every principal (especially refresh and authorization-code principals, which keep all claims),
  and the fail-closed rejection path.
- `InvitationService.ResolveExistingOnlyAsync`: that no `existingOnly` path can reach
  `tokens.IssueAsync` or `emails.Add`, including through the per-user exception handler, and the
  orphaned-restore ruling above.
- `ManagementApiAttribute` as route provider plus filter factory: that every management action is
  versioned (the reflection unit test), that nothing answers without the segment (the integration
  route tests, standalone and in-proc), and that the metric tags are a closed set.

## Review 1

Scope: commit e99eb6f only. Read the PC-006 entry, 0010 §A.6–§A.8 (with 0003 §10.5 for the
orphaned state and 0018 §3.3 for the consumer), PLAN.md §6–§7, WATCHLIST 0010-A, the live
DECISIONS.md and the full diff. Ran `dotnet build Tellma.slnx` (Build succeeded, 0 warnings),
`Tellma.Identity.Tests` with the unit filter (587/587) and `Tellma.Identity.IntegrationTests` with
the integration filter (140/140). E2E not re-run: sign-in codes are rate-limited, and the
suite calls no management route.

Checked and found sound (no finding):

- **tellma_kind spoofing.** Only `TellmaKindClaimHandler` writes the claim, from
  `Request.GrantType` at the token endpoint. A `tellma_kind` request parameter is ignored (pinned by
  `A_client_cannot_choose_the_kind_its_token_carries`). Unknown and custom grants are refused by
  `TokenController.Exchange` before `SignIn`, and the handler fails closed on them with
  `server_error`. No impersonation path exists. Token exchange refuses any subject that is a stored
  user (`TokenController.cs:80-83`), and refresh refuses any subject that is not a stored active
  user (`TokenController.cs:129-133`), so the `refresh_token → individual` and
  `token_exchange → service` mappings cannot mislabel.
- **Strip and placement.** Every prepared principal is stripped: access, code, device code, id
  token, issued, refresh, request and user code. The claim is written after the last
  `Prepare*Principal` and before the first `Generate*`, which the order test pins.
  `TellmaClaimDestinations` gives it no destination. Integration tests assert it on code, refresh,
  device, client-credentials and exchanged tokens, and its absence from the id_token.
- **existingOnly isolation.** `InviteOneAsync` returns before `returnUrls`, `tokens.IssueAsync` and
  `emails.Add`. The per-user exception handler only removes entries, so it cannot add one. The
  mixed-batch and sandbox-style integration tests use a recording dispatcher that sees every
  hand-off. The oracle it exposes is exactly §A.7's table (Active+sub, no credential, unknown, the
  refusal), and refusals are audited with `existingOnly`.
- **Authorization and routes.** All three controllers carry a class-level `[Authorize]` with the
  OpenIddict validation scheme, and every v1 route answers 401 anonymously. Unversioned and `v2`
  paths answer 404, standalone and in-proc. The 405 the tests suppress comes from the
  Development-only `{**path:file}` static-asset fallback: the HTTP-method policy runs before the
  `file` constraint, so a POST to any unmapped path gets 405. A Production host does not map that
  fallback, and no other catch-all route exists in the engine or `Tellma.Identity.Web`.
- **PII.** The tags are the closed `v{n}` segment and operation names. The log carries only the
  client id: `client_id` first, then `sub`, and every OpenIddict access token carries `client_id`.

Judgement of the implementer's open rulings:

- **Deviation 1 (count only once authorized): rejected**, per the orchestrator ruling. See R1-1.
- **Deviation 2 (existingOnly ignores ReturnUrl): accept.** No link, token or row stores the URL,
  so ignoring it opens nothing. Validating it would add a refusal outside §A.7's four outcomes, and
  spec 0018 §3.3 sends the tenant link on every sandbox invite. Worth a DECISIONS line.
- **Deviation 3 (an orphaned user with a credential answers Active and is restored): accept.**
  0003 §10.5 says orphaned users cannot obtain tokens. Answering Active without the restore would
  have the sandbox record a member who cannot sign in, and an error would block every returning
  user. §A.7's "no side effects" lists a user, a link and an email, and none of them results. The
  audit of that restore is weaker than the justification claims (R1-2), and its "not restored
  without a credential" half is untested (R1-3).
- **Endpoint tag values from a closed set of operation names: accept.** Operation names keep path
  parameters (`{sub}`, `{clientId}`) out of the tags. The attribute refuses a name outside the set
  when the model is built, and the reflection test pins that the names in use equal the set. Record
  the names in DECISIONS, since dashboards will key on them.

### Findings

**R1-1 (major): Rejected calls are neither counted nor logged, and the counter has no outcome tag.**
`src/apps/Tellma.Identity/Infrastructure/ManagementApi.cs:94-99` and `:185-208`;
`src/apps/Tellma.Identity/Infrastructure/IdentityMetrics.cs:110-114`;
`src/apps/Tellma.Identity/README.md:93-95`;
`test/apps/Tellma.Identity.IntegrationTests/Api/ManagementApiRouteTests.cs:115-122`, which pins the
opposite of the spec.

§A.8 says every call is counted and logged with the calling client. The orchestrator ruling keeps
that and adds an outcome tag.

Scenario: a distribution's identity client loses the `tellma_identity` scope, its token expires,
or it still holds a control-plane token with the wrong audience. Every call then gets 401 or 403.
The counter shows the version as silent and the log names nobody, which is exactly the signal the
metric exists to give ("who still calls it").

The filter pipeline cannot carry the fix. With endpoint routing, `AuthorizationMiddleware`
(`src/apps/Tellma.Identity.Web/Program.cs:182`) evaluates the controllers' `[Authorize]` and writes
the 401 or 403 before MVC's resource invoker runs. No MVC filter executes for a rejected call:
not the resource filter, not an authorization filter, not the `IFilterFactory` product.

Suggested fix:
- In the engine (`TellmaIdentityServiceCollectionExtensions`), register a decorating
  `IAuthorizationMiddlewareResultHandler`. It wraps the existing registration, or the default
  `AuthorizationMiddlewareResultHandler` when the host registered none.
  - Act when `context.GetEndpoint()?.Metadata` holds `ManagementApiAttribute` and
    `ManagementApiEndpointAttribute` (class and action attributes are both endpoint metadata) and
    the result is `Challenged` or `Forbidden`.
  - Record `ApiCall(segment, endpoint, outcome)` with `unauthorized` or `forbidden`, log the call,
    then delegate.
  - `PolicyEvaluator.AuthenticateAsync` assigns the policy scheme's principal to `context.User`,
    so a 403 names its client and a 401 logs without one.
  - This works whatever the host does. A middleware inside `UseTellmaIdentity` would also work
    standalone, but the in-proc host owns middleware order.
- Keep the resource filter for authorized calls, but record in `OnResourceExecuted`: `error` when
  `context.Exception` is set and unhandled or the status is 5xx, otherwise `ok`. A separate
  `invalid` outcome for 4xx is optional. Declare the outcome values as a closed set of consts beside
  `ApiVersionTag` and `ApiEndpointTag`.
- Tests:
  - Flip the anonymous assertion to one measurement with `outcome=unauthorized`.
  - Add a 403 case (a `tellma_api` token at `invitations/delivery-status`) that asserts
    `outcome=forbidden` and the client id in the log.
  - Add the `ok` tag to the existing case.
  - Unit-test that the result handler passes non-management endpoints through.
- Update the README paragraph and the attribute's remarks.

**R1-2 (minor): The existingOnly restore of an orphaned user is audited without the client that caused it.**
`src/apps/Tellma.Identity/Services/Invitations/InvitationService.cs:428` and `:507-513`.

On the existingOnly path, an orphaned user with a credential is restored and answered Active, and no
`UserInvited` success row is written (an Active result never writes one). The only audit row is
`UserLifecycleChanged` from `RestoreOrphanedAsync`, and it sets no `ClientId`.

Scenario: an operator asks why a retained, orphaned account became active again and can obtain
tokens. The audit cannot say which distribution's sandbox caused it. Deviation 3 rests on this
being "the audited write".

Fix: pass `createdByClientId` into `RestoreOrphanedAsync` and set `ClientId` on the row, for both
callers. Assert the row's client in the mixed-batch test.

**R1-3 (minor): No test pins that an orphaned user without a credential is not restored.**
`test/apps/Tellma.Identity.IntegrationTests/Api/InvitationExistingOnlyTests.cs:38-47` and
`:104-112`.

The pure table pins the answer `existing_user_has_no_credential` for (Orphaned, no credential).
Nothing pins that the service leaves that user Orphaned. A refactor that restores before resolving,
which is the ordinary path's order, would pass every test and turn a credential-less lookup into a
state change.

Fix: add an orphaned user without a credential to the mixed batch. Assert its error, and that its
state is still `Orphaned`.

**R1-4 (minor): The reflection guard against unversioned management routes ignores class-level routes.**
`test/apps/Tellma.Identity.Tests/Infrastructure/ManagementApiTests.cs:66-76`.

For a controller without `[ManagementApi]`, the test checks only `HttpMethodAttribute` templates.
A future controller with `[Route("api/identity/…")]` on the class and bare `[HttpGet]` actions
would map an unversioned, uncounted management route and still pass. The implementer notes say
the test shows that no other controller maps `api/identity…`.

Fix: also check every `IRouteTemplateProvider` on the controller type except `ManagementApiAttribute`,
and combine class and action templates.

**R1-5 (minor): The README's new section splits the email material.**
`src/apps/Tellma.Identity/README.md:75-110`.

"## The management API" sits between the invitation-delivery paragraph and the wordmark paragraph.
Line 110 ("the brand mark those emails carry") now follows the `tellma_kind` paragraph and refers
to nothing.

Fix: move the section after the email material, or give the email material its own heading.

### Responses

- R1-1: fixed in the "PC-006: review 1 fixes" commit (child of e99eb6f), per the orchestrator's
  ruling D-026 and the suggested design. `ManagementApiCallRecorder` (singleton) records
  `ApiCall(segment, endpoint, outcome)` and logs `Management API {Version} {Endpoint} called by
  client {ClientId}: {Outcome}.`. `ManagementApiAuthorizationResultHandler` decorates the
  registered `IAuthorizationMiddlewareResultHandler` (the framework default when the host
  registered none; the original lifetime is kept) and records `unauthorized` (client logged as
  `none`) or `forbidden` (client named) when the endpoint metadata carries both management
  attributes, then always delegates. The resource filter now records in `OnResourceExecuted`:
  `error` for an unhandled exception or a status >= 500, else `ok`. `ManagementApiOutcomes`
  holds the four values; `IdentityMetrics.ApiOutcomeTag = "outcome"`. A startup filter refuses a
  host whose resolved result handler is not the decorator (one registered after
  `AddTellmaIdentity`), so the refusal path cannot be silently bypassed. Tests: unit (filter ok
  for 200 and 404, error for an exception and a 503, no record before the call is answered;
  handler forbidden with client, unauthorized with `none`, pass-through for non-management
  endpoints, no endpoint and success; decoration keeps a host handler; the startup refusal);
  integration `Every_call_is_counted_on_the_identity_meter_with_its_outcome` (ok, forbidden with a
  `tellma_api`-only token, unauthorized, one measurement each with version and endpoint). The
  client-in-log assertion is in the unit suite: the standalone host logs through Serilog, which
  the integration factory does not capture. README and attribute remarks updated.
- R1-2: fixed in the same commit. `RestoreOrphanedAsync` takes the calling client and sets
  `ClientId` on the `UserLifecycleChanged` row, for both callers; the mixed-batch test asserts the
  row's subject and `acme-svc`.
- R1-3: fixed in the same commit. The mixed batch gains an orphaned user without a credential
  (`lapsed@example.com`): it answers `existing_user_has_no_credential`, stays `Orphaned`, has no
  single-use code, and is the reason the test asserts exactly one `UserLifecycleChanged` row.
- R1-4: fixed in the same commit. For a controller without `[ManagementApi]` the test now checks
  every `IRouteTemplateProvider` on the class, on each action, and each class + action
  combination (`AttributeRouteModel.CombineTemplates`) for an `api/identity` prefix. For a
  versioned controller it also asserts the version attribute is the class's only route provider,
  and that no action template is rooted (`/`, `~`) or `api/…`-prefixed.
- R1-5: fixed in the same commit. "## The management API" now follows the migrations paragraph,
  after all the email and UI material, directly before "## The store check and seeding".
