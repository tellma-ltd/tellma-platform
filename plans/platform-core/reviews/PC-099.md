# PC-099: Notifier, notifications schema and rendering

## Implementer notes

### What was built, and where

- **Contracts** (`src/core/Tellma.Core.Abstractions/Notifications/`):
  - `Notification`: the inbox row, `[Table("Notifications", Schema = "core")]`, `[TableType]`, a read-only stack (`Query | Details`), every property `[ServerOwned]`, with the column-width constants.
- **Model** (`src/core/Tellma.Core/Notifications/`):
  - `NotificationConfiguration` maps `core.Notifications`:
    - the four indexes `IX_Notifications_User` (UserId, CreatedAt DESC, Id DESC, INCLUDE ReadAt, Type, Severity), `IX_Notifications_Unread` (filtered on `ReadAt IS NULL`), `IX_Notifications_Dedup` (filtered on `DedupKey IS NOT NULL`, INCLUDE ReadAt) and `IX_Notifications_Retention`;
    - `LOCK_ESCALATION = DISABLE`, and `sq_Notifications` by convention;
    - the user and actor FKs to the user leaf with `NO ACTION`.
  - `NotificationPreferenceRow(+Configuration)` maps `core.NotificationPreferences`, keyed (UserId, Type, Channel), cascading from the user.
  - `CoreFeature` contributes the entity, both configurations, the three table types, `INotifier` and `INotificationRenderer`. `NotificationsComposition` adds the singletons `NotificationDeliveryChannels` and `NotificationsMetrics`.
- **Statements** (`NotificationStatements`), on the internal batch channel as `JobStatements` does:
  - **Notify**: the optional `Replace` update with `OUTPUT`, then one `sp_sequence_get_range` for every distinct recipient and the filtered insert with `OUTPUT`. The insert skips a recipient who is inactive, has muted a mutable type or holds a duplicate; under `Ongoing` the duplicate test drops its `ReadAt` term.
  - **Delivery enqueue**: the qualifying slices go into a table variable. A `core.sq_Jobs` range is taken only when some slice qualifies, then one `core.notification-delivery` job is inserted per slice with `OUTPUT`. The jobs run as the system user, with no requester, the slice's arguments and the trace parent.
  - **Channel-only types** run the enqueue alone.
  - **Transaction guard**: every statement that enqueues opens with `IF @@TRANCOUNT = 0 THROW 50422, N'Jobs.EnqueueOutsideTransaction', 1;` (D-074).
  - **Withdraw**: two forms, for everyone and for named recipients, each `DELETE … OUTPUT`.
  - `StatementDraft.Scalar(SqlDbType, value, size)` was added so that the scalars bind with exact types. `DataBatch.ParameterCount` was added for the up-front cap check.
- **Delivering channels** (`NotificationDeliveryChannels`):
  - The registered channels other than the inbox that a sender serves, in registration order. They are resolved once, on first use, in a scope of their own; a failure is not cached.
  - The condition gives one `COALESCE(preference, default) = 1` term per channel, with the keys inlined. It is null when there is none.
- **Notifier** (`Notifier`, scoped):
  - **Checks**: a writable, still-composing `DataBatch`, refused in `None` mode. Every request is checked and shaped before anything is appended:
    - the type is registered;
    - the policy and severity are defined;
    - the dedup key has the right length, and `Replace`/`Ongoing` require one;
    - for channel-only types, neither `InboxOnly` nor a key;
    - the target rules;
    - the arguments are a JSON object within `MaxArgumentsChars`;
    - the recipients are present and within `MaxRecipientsPerRequest`, deduplicated in first-seen order.
  - **Defaults**: the severity falls back to the type's, and the actor to the scope's user (null in a system scope).
  - **Slices** are cut at `DeliverySliceSize`. The whole call's parameters are checked against the batch cap before anything is appended.
  - **After commit**: one callback per batch, via a `ConditionalWeakTable`. It records the metrics and debug logs, wakes the tenant's pollers when a job was enqueued, and publishes one `inbox.changed` to the union of the inserted, refreshed and withdrawn users. It never throws; failures go to `InboxEventFailed`.
- **Renderer** (`NotificationRenderer`, scoped):
  - **Resource**: `Notification_<key with dots as underscores>` from the registering feature's assembly, or Core's for an unknown type.
  - **Formatting**: ICU named arguments by JSON kind, a `LocalizedText` triple in the reader's content slot, and the `_Detail` line when the neutral keys declare it. A missing resource renders the type key. Malformed arguments render the message without them and log `NotificationArgumentsInvalid` once per (type, text) per scope.
- **Metrics** (`NotificationsMetrics`): `created`, `suppressed`, `replaced`, `withdrawn` and `delivery_enqueued`, tagged by type.
- **Resources**: `Notification_core_user_added`, in English and Arabic.
- **Migrations**: regenerated with dotnet-ef in the fixture, the migrator test distribution and Acme's `InitialTenant`.
- **Fixture** (`test/shared/Tellma.Testing.Entities`):
  - `FixtureNotifications`, with three types and an `sms` channel that is on by default, registered by `FixtureFeature`.
  - `FixtureTenant.CreateAsync(readCommittedSnapshot:)`.

### Deviations

1. Notify refuses `TransactionMode.None` up front, and every enqueuing statement carries the D-074 guard. Withdraw accepts `None`, since it is a single statement that enqueues nothing.
2. Arguments must serialise to a JSON object, which is an added rule: the renderer and the client read top-level members.
3. The renderer's handling of argument kinds:
   - An ISO date-only string formats as a calendar date that never shifts.
   - A date-time without an offset stays text, because it names no instant.
   - A JSON null renders as nothing.
4. Booleans render as the strings `true`/`false`. The ICU engine compares a select on `Convert.ToString(bool)` (`True`), so a raw bool would never match a `true` key.
5. A type with no resource renders its type key. The detail line's presence is read from `INeutralStringKeys`, so a missing `_Detail` is not counted as a miss.
6. The delivery condition is built lazily on first use rather than at startup: the senders are scoped and are resolved once, in a scope of their own.
7. The recipient cap counts raw entries before dedup.
8. No `inbox.changed` is published when no inbox changed, because an empty user list would address the whole tenant.
9. `Notification` is composed as `Entity<Notification>()` with `[Stack(Query | Details)]` and no service; the access criteria are left to PC-146.
10. Acme's unreleased `InitialTenant` was regenerated rather than given a follow-up migration, following the PC-097 precedent.
11. `JobQueue.TraceParent()` became `internal static`, so the delivery jobs carry the same trace parent rule.
12. The shared fixture changed beyond the deliverables:
    - `FixtureTenant.CreateAsync` takes `readCommittedSnapshot`, for the RCSI-off run.
    - `FixtureFeature` registers three notification types and an `sms` channel.
    - The table and entity lists in five existing tests now include the new tables, types and entity.

### Findings

**R1-1 (minor): `NotifyAsync` and `WithdrawAsync` send a round trip when nothing was appended.**

- **Where:** `src/core/Tellma.Core/Notifications/Notifier.cs:158-165` and `:209-216`.
- **Scenario:** a caller passes requests that append nothing. Examples are every recipient list empty, a channel-only type with no delivering channel, or a withdrawal for an empty list. `ExecuteAsync` still runs. `DataBatch.ExecuteAsync` then calls `EnsurePrologue()` ("the prologue if nothing was appended"), so the executor sends a prologue-only round trip.
- **Effect:** the round trip does nothing. In a caller scope it can also fail the no-op with the prologue's refusals: a tenant that turned Frozen, or a caller deactivated since connect. Spec 0020's notice raisers compute their recipients (requesters, administrators), so an empty list is a realistic input.
- **Fix:** skip `ExecuteAsync` when the batch holds no statement, for example `if (((DataBatch)batch).Statements.Count == 0) return;`. Add a unit test that the empty forms of both calls execute nothing.

No blocking or major issues were found. Spec conformance (§1.4, §2.1, §2.2, §2.4, §3.3–§3.5, §4.2, §10.1, §10.2) was checked item by item against the statement texts, the migration and the tests. The deviations are justified, and each rule in scope has a test that fails if the rule breaks.
