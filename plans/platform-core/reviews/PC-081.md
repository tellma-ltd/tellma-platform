# PC-081: Problem details, exception mapping, headers and the telemetry filter

## Implementer notes

### What was built

Spec 0016 §5.5, §6.1-§6.4, §7.1-§7.6 and §10.1, in `src/core/Tellma.Core.AspNetCore` (plus three
small seams in `Tellma.Core` and `Tellma.Core.Abstractions`).

- **The mapping** (`Problems/ProblemMapper.cs`). It maps each exception by its exact type to a
  `ProblemDescription` (status, code, arguments, detail, errors, errorDetails, Retry-After, step-up).
  It covers every row of the §7.1 table:
  - `BadRequest` and `InvalidQuery` (one error per diagnostic, `path` = the clause, the diagnostics
    verbatim in `errorDetails.diagnostics`) answer 400. So does `BadHttpRequestException` with a
    `JsonException` cause (`reason = malformed-json`); 413 maps to `limit = body` and 415 to
    `unsupported-media`.
  - `StepUpRequired` answers 401, through the existing `StepUpChallenge`.
  - `Forbidden` and `IndividualRequired` answer 403.
  - `TenantUnavailable` maps by code: `NotFound` is 404, the catalog and schema codes are 503 with
    Retry-After 30 s by default, and the operator states are 403. `TenantNotFound` is 404. No
    tenancy row carries arguments.
  - `NotFound` answers 404.
  - `Concurrency` (`errorDetails.conflicts`), `ConfirmationRequired` (`errorDetails.confirmations`;
    the detail is the first key's message, falling back to the general one), `TenantState` and
    `CountMismatch` answer 409.
  - `LimitExceeded` answers 413.
  - `Validation` and `Import` answer 422. An import's items carry sheet, row, column, header and
    property; its `errorDetails` holds `totalErrors` and `committedRowRanges`.
  - `BlobRejected` maps by its blob code: 413, 415, 404, 411 or 422.
  - `PartialFailure` answers 502.
  - `StaleContext` (Retry-After 1 s, `errorDetails.dependencies`), `DependencyUnavailable` (its own
    hint, else 1 s) and `ImageProcessingBusyException` (`dependency = imaging`, its RetryAfter)
    answer 503.
  - Anything else is `500 internal`. In Development it adds `arguments.exception` (type and message,
    never the stack).
- **Path rendering** (`Problems/ValidationPaths.cs`). The camelCase grammar is
  `entities[i]…` for a save, `ids[i]` for an entity action, and `id` for a single-target action
  (its leading `[0]` or `Ids[0]`). It also renders `arguments.x`, and `body` for the empty path. The
  owner of the last property (CLR walk through list element types) lets the renderer label a
  `property` argument with `ILabelProvider` when that owner is a model entity.
- **The body** (`ProblemRenderer.cs`, `ProblemDocument.cs`, `ProblemWriter.cs`).
  - `type` is `ProblemTypeBase` plus the code.
  - `title` and `detail` come from `Problem_<code>` and `_Detail`, and each error's `message` from
    its code's key. They are rendered through a new `ResourceTexts` helper in `Tellma.Core`, over
    the composed string packs and the ICU localizer. `StringPackComposer.OwnerOf` and
    `StringResourceSource.AssemblyName` were added for it.
  - `instance` is the trace id. `errorDetails` is always written (null when absent); `arguments` is
    written only when present.
  - The writer enters the request's `LocalizationContext` itself, synchronously, so texts render in
    the request's language whatever culture the calling continuation runs under.
  - The writer records `tellma.api.problems{status, code}` and logs `ApiProblem` (Information for
    4xx, Warning for 5xx) under the tenant and API log scopes, for every problem body, mapped or
    written directly.
- **The handler** (`TellmaProblemExceptionHandler.cs`). It reads the endpoint from
  `IExceptionHandlerFeature` (the middleware clears it) to choose the path root and row type. It
  writes nothing for an abandoned request. It logs `ApiUnhandledException` (Error, with the trace
  id) for the backstop, and the middleware's own diagnostics are suppressed.
- **Framework problems** (`FrameworkProblems.cs`, `RouteMisses.cs`, `TellmaSessionEvents.cs`).
  - `UseStatusCodePages` turns an empty refusal into its status's problem. `AddProblemDetails` gets
    a customizer for the code and the instance, plus a platform `IProblemDetailsWriter`, so
    components that ask the service get the platform's body.
  - `ThrowOnBadRequest` makes binding failures reach the mapping.
  - Both skip the in-process identity paths and the platform's own endpoints, which answer bare
    statuses on purpose.
  - The SPA fallback now tells 405 (with `Allow`) and 415 apart from a route miss (see the
    rulings).
  - A bearer token on a cookie surface answers `401 unsupported-credential`. When a cookie is also
    present, `ValidatePrincipal` rejects the principal without signing out.
- **The telemetry stage** (`Api/ApiTelemetryFilter.cs`, `Api/ApiLogScope.cs`, `Api/ApiMetrics.cs`).
  - It is a request-delegate wrapper on the Web group, between the tenant guard and the witness.
    It sets the `Client`, `Resource` and `Operation` log scope (kept on the request, and added to
    the request-completion event through the Serilog enricher), the activity tags (now including
    `tellma.client`), and `tellma.api.operation.duration` for projected routes.
  - In `OnStarting` it stamps `Content-Language`, `Tellma-Calendar`, `Tellma-Version-Tags` and,
    when `Tellma:Api:ServerTiming` is on (default: Development), `Server-Timing`.
  - The version tags come from `DataAccessScope.LastOutcome`, a new member the executor sets after
    every batch. The user's tags are used only when the batch read the caller's own tags.
  - `DataAccessScope.DatabaseTime`, accumulated by the executor, feeds `Server-Timing`.
  - `WebRequestFilter` now seeds `Tellma-Confirm` alone; its activity tags moved here.
- **Headers in** (§6.1). The parsing of `Tellma-Time-Zone`, `Tellma-Calendar`, `Tellma-Client`,
  `Tellma-Activity` and `traceparent` into `RequestContextInputs`, with unparseable headers ignored
  and counted, already existed (`RequestInputs`, `LocalizationNegotiator`, the browser
  propagator). It was verified, not rebuilt. `Tellma-Priority` is not parsed (deviation 2).
- **Resources.** `Problem_provisioning_not_configured` (en and ar) was added. The pending entries
  for `method_not_allowed`, `unsupported_media` and `unsupported_credential` were removed from the
  core resource audit, since their raise sites now exist.
- **Carried items.** The early `BadRequest`→400 and `LimitExceeded`→413 mappings are folded into
  the full mapping. `settings/client` gets its version tags through the same last-outcome path
  (its prologue batch). Acme's `NeedsUserConnectionAndBootstrap` tests still cannot run: they
  need the real user connection initializer and the admin bootstrap, which this checkpoint does
  not touch.

### Deviations

1. `ImageProcessingBusyException` maps to `503 dependency-unavailable` with
   `arguments.dependency = "imaging"`. Spec 0016 §7.1 lists the dependency names as `database`,
   `identity` and `email`; the planner note asks for this exception to answer 503 with Retry-After,
   and `imaging` is the one name that says which dependency was busy.
2. `Tellma-Priority` is not parsed here. Its only consumer is the reports lane selection in the
   rate-limiting checkpoint, which owns the lanes; a parsed value with no reader would be dead code.
3. Spec 0016 §7.5 lists 405 and 415 as framework problems, but the SPA's `{*path}` fallback claims
   every path and verb, so routing never produced either: a wrong verb answered
   `404 route-not-found`, which the SPA reads as an outdated client. The fallback now matches the
   request against the mapped routes (pattern, constraints, verbs, accepted media types). A path a
   route serves under other verbs answers 405 with `Allow`; one served under the verb but not the
   media type answers 415. Everything else is the route miss it was.
4. The problems metric and the `ApiProblem` log are written by the writer, not only by the
   exception handler (§7.6 places them with the mapping). This counts every problem body
   (CSRF 403, 412 client-outdated, step-up, framework statuses) the same way.
5. The telemetry stage wraps the Web group only. Spec 0016 §5.1 gives the blob `GET` the same
   chain, and §6.2 puts the four headers on every tenant-surface answer that reaches the filter.
   The blob endpoints are built in the blob-endpoint checkpoint, so wrapping the Blobs group
   belongs there (review 2, R2-4). Until then, the blob `GET` carries no `Content-Language`,
   `Tellma-Calendar`, `Tellma-Version-Tags` or `Server-Timing`, and has no operation timing.

### Rulings (not obvious from the spec)

- `tenant-not-found` always renders in neutral English and never carries `Content-Language`, so a
  missing tenant and a non-member's refusal are byte-identical apart from `instance`, whatever
  `Accept-Language` says. The writer marks the answer on the request, and the telemetry stage
  stamps none of its headers on it, so a refusal raised inside the handler matches too.
- `route-not-found` answers only a request no endpoint took; a matched endpoint's bare 404 is
  `not-found`.
- `BadRequestException.Detail` is written verbatim (it is caller-authored, English); every other
  detail is localized.
- `errorDetails` is always present (null when the problem has none); `arguments` is omitted when
  empty.
- A query error's `path` is its clause (`select`, `filters[1]`, `orderBy`); the diagnostic's own
  `location` is kept verbatim in `errorDetails.diagnostics` for editors.
- The telemetry stage covers the Web group only. The blobs GET, the public API and MCP get no
  `Content-Language` or version tags here.
- `ThrowOnBadRequest` is on in every environment, so binding failures always reach the mapping
  rather than answering a bare 400.
- The status-code pages and the problem-details writer stay away from the in-process identity
  server's paths and from `PlatformEndpointMetadata` endpoints (webhooks, back-channel logout, MCP's
  401), which answer bare statuses where their protocol says so.

### Open risks

- There is no `infra/monitoring` alert on `tellma.api.problems{status=500}`. Spec 0016 §10.2 is not
  in this checkpoint's sections; the orchestrator should place it.
- `Server-Timing` tells a caller how long the server spent in the database. It is off by default
  outside Development, and a deployment that turns it on exposes that.
- The stage resolves `DataAccessScope` while the response starts. A Web request that never touched
  data (only test probes, in practice) now creates the recorder and records a zero round-trip
  measurement with an empty operation.
- `RouteMisses` indexes its candidates once, on the first fallback miss, by segment count and last
  literal (catch-alls tried for every longer path). An endpoint data source
  that changes after startup would not be seen. None does today.
- `429 rate-limited` carries no `Retry-After` from this checkpoint. The limiter's rejection callback
  in the rate-limiting checkpoint must set it.

### What reviewers should examine hardest

- Leakage: `ProblemMapper.Internal` and `Framework` (the framework's messages name parameters and
  readers and must never reach the wire). Also check that a 500 in Production carries only the
  trace id, and that `ForbiddenException` bodies carry only resource, action, reason and path.
- Tenant identity: `ProblemWriter.Localize`'s neutral culture for `tenant-not-found`, the telemetry
  stage running only after admission (so no `Content-Language` on the refusal), and `RouteMisses`
  reading the path alone (405 is identical for an existing and a missing tenant).
- Cultures: the writer's `LocalizationScope` against the ICU localizer's preference order, and the
  telemetry stage's `OnStarting` reading the completed request context.
- `TellmaSessionEvents.ValidatePrincipal`: rejecting the principal for a bearer header on every
  cookie surface (Web, Hub, Blobs, the BFF).
- `ApiTelemetryFilter.Stamp`'s tenant and user checks on the last outcome, so another tenant's or
  another user's tags are never reported.

## Review 1

### Findings

**R1-1 (major): a `tenant-not-found` raised inside the handler carries the telemetry stage's headers,
so a deactivated member's 404 is not identical to a stranger's.**
`src/core/Tellma.Core.AspNetCore/Api/ApiTelemetryFilter.cs:88-94, 118-143`, together with
`src/core/Tellma.Core/Access/UserConnector.cs:115-119` and
`src/core/Tellma.Core/Access/GuardedBatchRunner.cs:81-86`.

- **Scenario.** A user whose connection is cached (a warm `Connections.Find` hit) is deactivated or
  removed. Their next request passes the guard without a round trip; `UserConnector` says the cache
  is "re-validated by every batch's prologue". The handler's first batch then refuses with
  `TenantNotFoundException`. The same happens when `GuardedBatchRunner` maps `CallerInvalid` (a
  deactivation committed between the prologue and the persist). That exception is thrown after the
  telemetry stage registered its `OnStarting` stamp, and `ClearHttpContext` does not remove
  `OnStarting` callbacks.
- **Result.** The 404 now carries `Content-Language: ar` (or whatever was negotiated),
  `Tellma-Calendar`, `Server-Timing` where enabled, and `Tellma-Version-Tags` when an earlier batch
  of the request completed. A missing tenant, or a stranger refused by the guard, carries none of
  them.
- **Why it matters.** Spec 0016 §5.4 says the non-member and deactivated-user answers are
  "identical for both, so a membership is never disclosed". The implementer's ruling also says
  `tenant-not-found` "never carries `Content-Language`". The body is identical, because
  `ProblemWriter.Localize` neutralises it, but the headers are not.
- **Test gap.** The only test,
  `ResponseHeadersTests.A_missing_tenant_and_a_refused_member_answer_the_same_body_in_any_language`
  (`test/core/Tellma.Core.AspNetCore.Tests/Api/ResponseHeadersTests.cs:122`), uses a cold stranger
  refused in the guard, so it never reaches the stage.
- **Fix.**
  - Have the writer mark a `tenant-not-found` answer on the request, for example an `Items` key
    set in `ProblemWriter.WriteAsync` before the body starts.
  - Have `Stamp` write none of its headers when that mark is set.
  - Add a `tenant-not-found` entry to `ProblemMappingTests.Exceptions` and a test. It throws
    `TenantNotFoundException` from the admitted throwing endpoint with `Accept-Language: ar-SA-u-nu-latn`.
    It asserts no `Content-Language`, `Tellma-Calendar`, `Tellma-Version-Tags` or `Server-Timing`
    (with `ServerTiming` on), and a body equal to the missing tenant's apart from `instance`.

**R1-2 (minor): every bare 404 on a tenant path becomes `route-not-found`, including a 404 that a
matched endpoint answered itself.**
`src/core/Tellma.Core.AspNetCore/Problems/FrameworkProblems.cs:37` (via
`ProblemMapper.ForStatus`, `src/core/Tellma.Core.AspNetCore/Problems/ProblemMapper.cs:178`), and
`FrameworkProblems.Of` at `:68` for the problem-details service.

- **Scenario.** A route miss never reaches the status-code pages when the SPA fallback is mapped,
  because the fallback writes its own body (`SpaHosting.FallbackAsync`). So in practice a bare 404
  on a tenant path comes from an endpoint that did match: a hand-mapped tenant endpoint or a later
  checkpoint's handler answering `Results.NotFound()`. Such an endpoint is answered
  `404 route-not-found`.
- **Why it matters.** Spec 0016 §7.5 reserves `route-not-found` for a route miss, and the SPA reads
  it as a sign of an outdated client (a reload prompt): "an entity miss stays `not-found`".
- **Test that asserts it.** `FrameworkProblemsTests.A_bare_status_a_component_set_answers_its_problem`
  with `[InlineData(404, "route-not-found")]`
  (`test/core/Tellma.Core.AspNetCore.Tests/Problems/FrameworkProblemsTests.cs:72`) asserts exactly
  this behaviour, for an endpoint that matched and answered 404.
- **Fix.**
  - In the status-code pages and in `FrameworkProblems.Of`, pass `tenantPath` as true only when no
    endpoint matched (`http.GetEndpoint() is null`, the hosts without an SPA fallback). A matched
    endpoint's bare 404 should be `not-found`.
  - Change the test row to `not-found`, and keep the existing `/1/api/web/no-such-route` test for
    `route-not-found`.

**R1-3 (minor): `RouteMisses.Classify` runs a template match against every mapped endpoint on every
non-navigation miss, for anonymous callers too.**
`src/core/Tellma.Core.AspNetCore/Problems/RouteMisses.cs:45-62`.

- **Scenario.** The fallback is anonymous, and every non-navigation request to an unmapped path
  pays one `TemplateMatcher.TryMatch` per endpoint that names its verbs. That is every projected
  web route, the hub, blobs, admin, static assets and so on. It also allocates a
  `RouteValueDictionary` per candidate, and runs constraints for every pattern that matches. Before
  this change, a miss cost routing's DFA alone. An unauthenticated client can now buy a linear scan
  of the route table per request, and nothing in this checkpoint limits anonymous fallback traffic.
- **Fix (either).**
  - Index the candidates once by their first literal segment, or by segment count, and scan only
    the bucket the path falls in.
  - Or skip classification entirely for paths whose first segments name no mapped prefix.
  - Reuse one `RouteValueDictionary` (cleared) per call.

**R1-4 (minor): several §7.1 rows' body members are produced but never asserted through the edge,
and two tenancy rows are never thrown through it.**
`test/core/Tellma.Core.AspNetCore.Tests/Problems/ProblemMappingTests.cs:99-118`.

- **What is missing.** `Each_exception_answers_its_problem_body` checks the status, code, type,
  title, instance and the allowed member names, but not the row-specific members. No test would
  fail if any of these were dropped or renamed:
  - `count-mismatch`'s `arguments.expected` and `arguments.actual`;
  - `limit-exceeded`'s `arguments.limit`, `.actual` and `.maximum`;
  - `not-found`'s `arguments.ids` (only `resource` is checked, at `:128`);
  - the `concurrency-conflict` item shape: `id`, `modifiedAt`, `modifiedById`, `modifiedByName`,
    `isMissing`;
  - `partial-failure`'s `errorDetails.results` and `errorDetails.failed`;
  - `tenant-state`'s verbatim `detail`;
  - `confirmation-required`'s `errorDetails.confirmations[].ids` and `arguments`.
- **Rows not thrown through the edge.** `tenant-read-only`, `tenant-frozen`,
  `catalog-unavailable` and `TenantUnavailableException(tenant-not-found)` are covered only by the
  mapper unit test (`ProblemMapperTests.cs:147`), not by a test throwing the type at the edge, as
  the checkpoint's Tests line asks ("every 4xx row of §7.1 produced by a test throwing that type").
- **Fix.**
  - Add those entries to the throwing endpoint's table.
  - Add one assertion per row-specific member, for example a `TheoryData` of (name, JSON pointer,
    expected value).

Verified, no finding:

- **Build.** `dotnet build Tellma.slnx` printed "Build succeeded", 0 warnings.
- **Tests.** `Tellma.Core.AspNetCore.Tests` passed 719 of 719. `Tellma.Core.Tests` filtered to
  `Localization` passed 1365, with 1 skipped (the pinned-ICU generator check).
- **SPA deep links (orchestrator item 1).** `FallbackAsync` still serves `index.html` before
  `RouteMisses` runs (`ServesIndex` first), so deep links are unchanged.
- **405 and 415 disclosure (item 1).** These read the path, the verb and the content type alone.
  No constraint in the repository consults state; `ApiVersionRouteConstraint` is the only custom
  one. So a 405 is identical for an existing and a missing tenant, which
  `A_wrong_verb_answers_the_same_for_a_tenant_that_does_not_exist` pins. The `Allow` header reveals

- **Bearer credentials (item 3).** `TellmaSessionEvents` answers a bearer on every cookie surface

- **Closed-set mapping (item 4).** Every closed-set type maps by exact type to the §7.1
  status and code. The 500 body carries `arguments.exception` only in Development, with no stack,

- **Deviations.** Deviations 1, 2 and 4 are acceptable. Deviation 2 is already carried to PC-082
  in D-133.
- **Suites run.** The commit message's suite list covers all nine integration suites, as the

## Review 2

### Findings

Reviewed 8c405881 and 7e6c3bba together. No blocking or major finding. Five minor findings follow,
then what was verified with no finding, and a judgment on Review 1.

**R2-1 (minor): a bare `403 forbidden` writes the raw ICU pattern as its `detail`.**
`src/core/Tellma.Core.AspNetCore/Problems/ProblemMapper.cs:177` (`ForStatus`) and
`src/core/Tellma.Core.AspNetCore/Problems/ProblemRenderer.cs` (`Conventional`). It is reached from
`src/core/Tellma.Core.AspNetCore/Sessions/TellmaSessionEvents.cs:59` (`OnRedirectToAccessDenied`),
from the status-code pages (`FrameworkProblems.HandleStatusAsync`) and from `FrameworkProblems.Of`.

- **Scenario.** A session that fails the surface's policy (spec 0016 §5.2's "403 (a session that
  fails the policy)"), or any component that sets a bare 403, is answered `forbidden` with no
  arguments and no `Detail`. The renderer then formats `Problem_forbidden_Detail`, which is
  `{reason, select, no-grant {…} … other {…}}`, with an empty argument set.
- **Result.** MessageFormat 8.0.0 throws `VariableNotFoundException` for the missing `reason`. I
  checked this against the library in a scratch program; an explicit `reason = "other"` renders
  the `other` branch. `IcuStringLocalizer` passes `argumentsSupplied: true` for an empty
  dictionary, so `IcuMessageRenderer.Render` takes its formatting-failure branch: it returns the
  pattern itself and logs `MessageFormatMalformed`. The body's `detail` is the ICU source text, in
  every language. Before this checkpoint the writer rendered no `_Detail` for this answer.
- **Not observed on the wire.** The brief forbids changing other files, so I could not add a
  test. The finding is traced through the code and confirmed against the library only.
- **Test gap.** `FrameworkProblemsTests.A_bare_status_a_component_set_answers_its_problem` has no
  403 row. Only the two `ForbiddenException` rows check a `detail` for a leftover `{`.
- **Fix.** Have `ForStatus(403)` render the general sentence, for example by passing
  `reason = "other"` to the detail's rendering when the problem names no securable. Add
  `[InlineData(403, "forbidden")]` and assert the detail holds no `{`.

**R2-2 (minor): nothing tests that the executor feeds `Tellma-Version-Tags` and `Server-Timing`.**
`src/core/Tellma.Core/Data/Batches/DataExecutor.cs:236` (`LastOutcome`) and `:814`
(`DatabaseTime`); `test/core/Tellma.Core.AspNetCore.Tests/Api/ResponseHeadersTests.cs`
(`RecordBatch`).

- **Gap.** The only tests of the two headers set `DataAccessScope.LastOutcome`, `RoundTrips` and
  `DatabaseTime` by hand in a test endpoint. No test under `test/` or `distributions/` reads
  either member after a real batch. Deleting either executor line leaves every suite green, and
  the SPA's refresher silently loses its signal.
- **Why it matters.** "Tellma-Version-Tags from BatchOutcome" is a named deliverable, and the
  Tests line asks for the header "after a batch without prologue".
- **Fix.**
  - In the executor's unit suite, assert that `batch.Access.LastOutcome` is the returned outcome,
    and that `DatabaseTime` grows by the attempt's elapsed time under the fake clock.
