# PC-176: Import intake, reader and mapping; Export/Import entities; inspect-import

## Implementer notes

### What was built

- **Entities and stacks** (`src/core/Tellma.Core.Abstractions/Excel/Export.cs`, `Import.cs`; `src/core/Tellma.Core/Excel/Export*.cs`, `Import*.cs`):
  - `core.Exports` and `core.Imports`, each on its own sequence (`core.sq_Exports`, `core.sq_Imports`), with `FileId` a blob reference of the `export-file` and `import-file` kinds (owner-read), `JobId` a foreign key to `core.Jobs` with `ON DELETE SET NULL`, the indexes and default selects of §12.1, and the write-once columns.
  - `ExportService` and `ImportService` serve `Query | Details | Delete | Enlist`. `ExportAccessCriteria` and `ImportAccessCriteria` scope every grant to `CreatedById = me()`.
  - `ImportService.ValidateDeleteAsync` refuses (`Imports.JobActive`) the delete of an import whose job is `Pending`, `Running`, `Held` or `PendingConfirmation`, in the delete's one validation round, by a load riding the targets' load.
  - Registered in `CoreFeature` beside the outbox; the fixture's own `Export` entity was renamed `Parcel` because its name collided.
- **Workbook reader** (`WorkbookReader.cs`, `ZipDirectory.cs`, `BoundedPartStream.cs`, `SharedStringStore.cs`, `XlsxXml.cs`, `WorkbookSheet.cs`, `ImportFaults.cs`):
  - The checks of §7.2–§7.4 in the spec's order, before any sheet is parsed: the compressed size, then the central directory read by hand (one disk, ≤ 65,535 entries, ≤ 16 MiB of directory, the zip64 record held to the same bounds whenever it is located), then the declared uncompressed sum, then the structure (content types present, one workbook part, each sheet its own part, no external-link part or relationship, no relationship leaving the package).
  - Every part is read through `BoundedPartStream`: it refuses bytes beyond the part's declared length and any run over 4 MiB from one `<` to the next, a CDATA section, comment or processing instruction counted whole to its terminator. Every node an XML reader materialises (a start tag with its attributes, a text node, a section) lies inside one run, so a lying directory or a one-node flood cannot exhaust memory. Text is read in 4,096-character chunks and refused at the longest a cell may hold, or at what the row's and the workbook's text budgets have left, before it is read whole. `DtdProcessing.Prohibit` on every reader.
  - Shared strings are charged per entry (text bytes plus a fixed overhead), spill to a scratch file once the budget is spent, and the entry cap refuses a declared `uniqueCount` before reading, or counts the flood whole and refuses it.
  - `SheetReader` reads forward only: the dimension when declared, rows and cells in ascending order (a reference-less row or cell takes the next), and refuses misaddressed cells. A formula without a cached value is blank. `.xlsm` reads like `.xlsx`; chart and dialog sheets are listed and never read.
- **Manifest reader** (`ImportManifest.cs`): untrusted. Row 1 must be the marker at the codec's version. The header block is capped at 64 rows read (a dropped or repeated row counted too), first key wins; at that size it needs no cancellation check, and the loops after it check every 1,024 rows. The column table is located by its header names and capped at 65,536 rows; rows that lack a field, misname a column letter or language, or repeat a (sheet, header) pair are dropped.
- **Header index** (`HeaderIndex.cs`, `HeaderCandidates.cs`, `HeaderIndexCache.cs`):
  - Candidates of every kind the exports write: technical paths, labels, "label (path)", group labels with each catalogued language's symbol, reference forms ("Nav / Key", "Nav.Key", the bare foreign key), and a child sheet's parent link.
  - Rendered in every candidate culture: the reader's, each tenant language's, then English. Keys are NFC-composed, white space collapsed and dropped beside `/ ( )`, and compared ignoring case. A key two paths give is a collision: it matches neither and is offered as a suggestion.
  - Suggestions use a banded optimal-string-alignment distance bounded by a third of the header (at most 4). Only the first 50 unmapped columns get them, at most 3 each.
  - Cached per process (≤ 1,024 entries) by entity, collection and the candidate-culture list. Sheet names index the same way: the entity's plural, the child sheet names, and the collection paths.
- **Mapping** (`ImportPaths.cs`, `ImportMapper.cs`, `ImportMapping.cs`, `ImportRequests.cs`):
  - The path grammar of §8.3 against the metadata and the target tenant's slots (§8.2).
  - Sheets bind by override, then the manifest's table, then the name index, then the fallback first visible sheet when there is no manifest. Columns bind by override, then the manifest by exact header, then the header index. Duplicates are both marked. Server-owned and unconfigured-language columns are reported in the plan.
  - Identity columns of a file that is not same-source (including another deployment of the same application) are warned about; a stamp is ignored, and an `Id` is kept only to link a present child sheet.
  - The plan's row keys, totals, `RequiresBackground` and `AtomicAllowed` come from the sizes against `ExcelOptions` and the stack's save limits (parent ceiling = min(`MaxSaveCount`, `MaxIds`)).
  - Override errors (`UnknownSheet`, `UnknownColumn`, `UnknownPath`) are collected across the workbook, sorted in tab, row and column order, capped, and thrown together.
- **Operation** (`IExcelImporter.cs`, `ExcelImporter.cs`, `ExcelImports.cs`, `ExcelOperations.cs`):
  - `inspect-import` (Save securable, not a mutation, idempotent, long, import rate policy). The request's form is checked before the upload is touched.
  - The caller's own staged `import-file` upload is then resolved in the one round trip the connect prologue rides, size-checked, and copied, bounded, to a delete-on-close scratch file; the workbook is read locally from that copy.
  - The spill counter (`tellma.excel.sst.spilled`) and the `SharedStringsSpilled` log event were added.
- **Strings**: `Action_InspectImport`, the request field labels, `Core_Export_Plural`, `Core_Import_Plural`, `Imports_JobActive` and every import fault this checkpoint raises, in English and Arabic.
- **Conformance**: `StackConformanceTests` now drives `inspect-import` in the reachability case (a missing upload is not found, naming `core.Blob` and the id) and the securables case, and gives it a budget row: an editable export of the two rows, staged through the real blob service and inspected in one round trip. The conformance harness holds uploads in memory.

### Deviations

See the commit message; each is repeated here with its reason.

1. `IExcelImporter.InspectAsync` takes the stack's `StackLimits` and a `CancellationToken` beyond §10.4's signature: `RequiresBackground` and `AtomicAllowed` depend on the stack's save limits (§2.3), which the importer cannot otherwise see.
2. A plan column's suggestions are resolved paths (`Name2`, `Parent.Code`), not raw header keys, so a client can echo one back as an override.
3. The duplicate identity of a mapped column is the property it writes, so `Parent.Id` and `Parent.Code` on one sheet are both duplicates (they would write one foreign key twice).
4. The header and sheet-name indexes are cached by entity, collection and the candidate-culture list rather than a settings tag: the list is exactly what the candidates depend on, and it changes when the tenant's languages do.
5. A bare navigation column, as a display export writes it, is `ServerOwned` rather than `Unmapped`: the path is known, and the import never writes it.
6. A sheet override that binds the manifest sheet or a chart sheet is `UnknownSheet`, since neither holds rows.
7. A manifest without an `Entity` row is `MalformedWorkbook` with reason `entity`, as a manifest of another entity is.
8. A very hidden sheet binds only by an override (never by name, manifest or fallback).
9. `UnknownColumn` names the header row as its row, so the error is addressable.
10. An unconfigured-language column's plan path is null (its language is reported), since no slot of the target writes it.
11. The fixture entity `Export` is renamed `Parcel`; it collided with `core.Export`.
12. `ExcelImports` is registered through a factory, and `ExcelOperations` resolves it only when an inspection runs, so a composition without a blob store builds, validates and serves both exports; only an inspection fails to activate there. (Corrected in review 1: the first commit resolved it eagerly, so exports failed too.)
13. Override paths match case-sensitively, as every other Queryex path does; headers match ignoring case.

Added in review 1:

14. Each XML reader's name table is capped at 1 MiB of names per part, each new name charged its UTF-16 bytes plus 16, and a part past it is refused with the reader's existing `PackageTooLarge` (`bytes` the charge, `max` the cap). §7.2 sets no bound for names; real parts use under a hundred.
15. A workbook's decoded cell text is charged against a per-row budget (`MaxInMemorySharedStringBytes`, 32 MiB by default) and one budget for the whole workbook, every read of every sheet (`MaxImportUncompressedBytes`), and a row past either is `MalformedWorkbook` with reason `cells`. §7.2 and §14.1 name no such limits, so they reuse the two existing options rather than adding new ones. (Amended in review 2: the second budget was per sheet.)
16. A header longer than 255 characters (the most an export writes) is kept cut to 255, is `Unmapped` and offered no suggestion, unless an override maps it.
17. The manifest reader drops a header-block row or a column-table row holding a field longer than 255 characters, and stops the column table once its kept rows pass 32 MiB of charged text.
18. A dimension whose last row is at or before the header row (a placeholder a streaming writer never patched) is treated as absent, and the rows are counted forward by skimming each row for a filled cell without decoding its text. A skim counts an inline or formula string of escaped white space alone as filled, which errs toward the background.
19. The export and import stacks serve no `delete-by-query`. §12.1's prose lists it among the projected routes, but its own `[Stack]` sketch omits it, and D-134 forbids it for imports, whose deletes `ImportService` judges. The spec should be made consistent.
20. `ImportService` reads a target's live job by a raw SQL join through the stored `JobId`, not through the job's related projection as §12.1 says (spec 0020 §2.3). The two read the same status.
21. The §15 corpus of files saved by Excel, LibreOffice and Google Sheets is replaced by `SyntheticWorkbook`'s stand-ins, and the real files are deferred to the human milestone: this host has no LibreOffice, and Excel and Sheets need a human.

Added in review 2:

22. `BoundedPartStream`'s 4 MiB bound is on the bytes from one `<` to the next, a CDATA section, comment or processing instruction counted as one run to its terminator, not on any token. §7.2 names a token bound; this is the shape that holds it for every node the reader materialises.
23. A workbook in which two sheets name one worksheet part is `MalformedWorkbook` with reason `relationships`, the second sheet named. §7.3 does not list it; no producer writes it, and each such sheet would re-read the part.
24. A `Duplicate` sheet's header and columns are still mapped, so its plan lists them, but its rows are neither read nor counted (`Rows` is 0), since none is imported.
25. `ZipDirectory.Check` holds the zip64 record to the entry and directory bounds whenever its locator precedes the end record, and refuses an end record whose disk, entry count, directory size or directory offset is at its maximum when no zip64 record is located. §7.2 orders the check; the archive reader may take any field from either record.

### Open risks

- **The corpus is synthetic** (deviation 21, deferred to the human milestone). `SyntheticWorkbook` writes each producer's package as that application lays it out (documented in `Corpus/README.md`), but no file saved by Excel, LibreOffice or Google Sheets is checked in. A real file that differs in a way the builder does not model would not be caught.
- A dimension that ends below the header row but above the last data row cannot be told from a true one without reading the sheet, so it still undercounts the rows (deviation 18 catches only a placeholder at or before the header row).
- The header index renders labels under a `LocalizationScope` per candidate culture; a label provider that reads anything beyond the scope's culture could make cached candidates differ from what an export of that culture writes.
- The shared-string spill file and the upload's scratch copy are delete-on-close; a process killed mid-inspection leaves them for the scratch directory's own sweep.

### What reviewers should examine hardest

- `ZipDirectory.Check` and `BoundedPartStream`: the memory and disk bounds rest on them, and the directory is parsed by hand.
- `ImportMapper.GateIdentity` and `Plan`: the same-source gate and the row-key candidates decide whether a file from elsewhere can overwrite rows by id.
- `HeaderIndexCache.Cultures` and the collision rule: a missed collision would map a header to the wrong path silently.
- `ExcelImports.OpenAsync`: the caller-ownership of the upload rests on `IBlobService.ResolveAsync` for the import-file kind's owner-read access.

### Findings

**R1-1 (blocking): every export now fails in a composition without a blob store; the touched
`ExcelExportTests` were not run.**
- *Where.*
  - `src/core/Tellma.Core/Excel/ExcelOperations.cs:130` resolves `ExcelImports` whenever the
    companion is created.
  - `ExcelComposition.cs:70` builds `ExcelImports` with `ActivatorUtilities.CreateInstance`, which
    requires `IBlobStore`.
- *Failure scenario.* `export` or `export-for-import`, invoked on an instance with no store,
  throws `InvalidOperationException` before the method runs. `ExcelExportTests` composes exactly
  that instance (`ExcelRowSourceDatabase` registers no store), and 8 of its 9 cases fail, for
  example
  `A_display_export_by_query_reads_one_round_trip_per_page_of_the_take_ceiling`.
- *Process.* The commit's test list omits `ExcelExportTests`, although the change rewrote the
  constructor and factory of the class those tests drive (PLAN §7.1 item 4). Deviation 12 claims
  the opposite of what happens.
- *Fix.*
  - Resolve the import runner lazily: `ExcelOperations` takes the scope's `IServiceProvider` (or a
    `Lazy<ExcelImports>`) and resolves it in `InspectImportAsync`. Alternatively, `ExcelImports`
    resolves `IBlobStore` inside `OpenAsync`.
  - Pin it with a unit case: an export on a store-less composition succeeds, and an inspection
    fails.
  - Run `ExcelExportTests`, and list it in the commit.

**R1-2 (blocking): the XML readers' name table is unbounded, so a small upload can force
gigabytes of allocation.**
- *Where.* `src/core/Tellma.Core/Excel/XlsxXml.cs:81-91`. `XmlReader.Create` is given no
  `NameTable`, so each reader atomizes every distinct element name, attribute name, prefix and
  namespace URI it meets, and keeps them all until it is disposed.
- *Why the other bounds miss it.* The token bound caps one name. The part-length bound caps the
  part. Neither caps how many distinct names a part holds.
- *Measured.* 2,000,000 distinct names in a 20.9 MB part (4.5 MB deflated) retain 176.7 MB, about
  8.5× the part.
- *Failure scenario.*
  - `inspect-import` accepts any package up to the 100 MiB upload limit and 2 GB uncompressed.
  - A 100 MiB upload holds about 470 MB of such a part, which means about 4 GB resident while one
    reader reads it.
  - A shared-string part, a sheet, the workbook part or a relationships part each serve.
  - Any member with `Save` on any importable stack can exhaust a web host's memory. The
    checkpoint's "Parser limits bound memory and disk" is not met.
- *Fix.*
  - Give `XlsxXml.Open` a bounded name table: a `NameTable` subclass overriding both `Add`
    overloads that counts new entries and throws `ImportFaults.Malformed(XmlReason)` past a small
    cap. Real parts use under a hundred distinct names, so a cap of, say, 4,096 names or 1 MiB of
    name text leaves ample headroom.
  - Add a `WorkbookReaderTests` case with a distinct-element flood in a sheet and in the
    shared-string part.

**R1-3 (major): cell text is unbounded per row, outside the shared-string budget.**
- *Where.*
  - `src/core/Tellma.Core/Excel/WorkbookReader.cs:545-582`: `SheetReader.ReadCells` keeps every
    non-blank cell of a row. Inline strings and `<v>` values may each reach
    `XlsxXml.MaxTextLength` (1 Mi characters), and a row may hold 16,384 of them.
  - `ImportMapper.cs:324-351` keeps the whole header row. Without a dimension, it decodes every
    cell of every row only to count the rows.
- *Why the budget misses it.* The 32 MB budget charges shared strings only. Inline text is charged
  nothing.
- *Failure scenario.*
  - A header row of 2,048 inline cells of 1 Mi `a` each is a 2 GiB sheet part (the uncompressed
    limit), and it deflates to a few megabytes.
  - Inspection holds about 4 GiB of UTF-16 in the row's cells and again in the headers, then
    normalises each header into a further copy.
  - The same row, placed below the header in a sheet without a dimension, is decoded whole just to
    be counted.
- *Fix.*
  - Charge the text of a row's cells against a per-row budget (for instance
    `MaxInMemorySharedStringBytes`), and refuse a row above it as `MalformedWorkbook` (`cells`).
  - Cap header text: an export writes at most 255 characters, so past a small bound treat the
    header as unmapped, truncated for display.
  - Let the forward count test for a non-blank cell without keeping its text.
  - Add a test for each.

**R1-4 (major): the `core.Export`/`core.Import` routes are not driven, and the self-scope
criteria are untested.**
- *Where.*
  - `test/core/Tellma.Core.AspNetCore.IntegrationTests/Stacks/ProjectedRouteTests.cs:25-28` lists
    neither resource.
  - Acme now projects `exports/query`, `exports/get`, `exports/get-by-ids` and `exports/delete`,

**R2-1 (blocking): the 4 MiB token bound does not bound a token, so one text node, CDATA section
or attribute value from an upload under 1 MiB allocates gigabytes.**
- *Where.*
  - `src/core/Tellma.Core/Excel/BoundedPartStream.cs:168-199` (`ScanUtf8`) and `:267` (the UTF-16
    scan) end a run at every `<` **or** `>`.
  - XML allows a literal `>` in character data and in attribute values, and both `<` and `>`
    inside a CDATA section.
  - `XmlReader` materialises each of those whole: a text node or CDATA section on `Value`, and
    every attribute of a start tag, read or not, since the whole start tag must sit in the
    reader's buffer.
  - `src/core/Tellma.Core/Excel/XlsxXml.cs:228` (`string value = reader.Value;`) checks
    `MaxTextLength` only at `:240`, after the whole node is built. `ReadStringItem`
    (`:146-192`) inherits this through each run's `ReadText`.
  - `WorkbookReader.cs:685` (`<v>`), `:755` (`SharedStringFilled`, the skim's own decode) and
    `:654-660` (the row and sheet charges) all come after the decode.
- *Scenario.*
  - A member who may save any importable stack uploads a workbook whose one shared string, or one
    `<v>`, is 300,000 KiB of `a`s with a `>` every 1,024 bytes. The upload is 587 KiB.
  - The inspection allocates 1,760.6 MiB and peaks at 1,214 MiB before refusing it as `cells`.
  - The cost is linear (about 5.9 bytes allocated per character), up to the 2 GiB uncompressed
    sum. At that size the string approaches .NET's maximum length, the peak approaches 4 GB, and
    the upload is about 2 MiB.
  - A `>`-laden attribute (`workbookPr`, `row`, or any element the reader passes over) is never
    refused at all: about 587 MiB per 100 MiB of attribute.
  - The import rate policy allows one inspection per user per tenant at a time. So every member
    of every tenant on a host can each hold gigabytes at once, and an out-of-memory kill takes
    down every tenant's requests on that process.
  - This is the exact class R1-2 and R1-3 were fixed for, and the notes' claim that "a one-token
    flood cannot exhaust memory" does not hold.
- *Fix.*
  - In `BoundedPartStream`, bound the run between consecutive `<` bytes, not between any two
    delimiters. Neither character data nor an attribute value may hold a literal `<`, so every
    start tag (all its attributes) and every text node is then within 4 MiB of bytes.
  - Count a markup section that may hold `<` as one run, from its opener to its terminator:
    `<![CDATA[` to `]]>`, and, for safety, `<!--` to `-->` and `<?` to `?>`.
  - Apply the same rule in the UTF-16 path.
  - Optionally, make `ReadText` read through `ReadValueChunk` and refuse at `MaxTextLength` during
    the read. That bounds a text node to 1 Mi characters, not to the 4 MiB run.
  - Add `WorkbookReaderTests` cases in the style of the R1-2 tests: a shared string, an inline
    string and a `<v>` with a `>` every KiB past 4 MiB, a CDATA section with `<` every KiB, and an
    attribute with `>` every KiB on the workbook, a relationship part and a sheet row. Each should
    be refused while allocating under 16 MiB.
