# PC-091: Roles stack extras and AccessService

## Implementer notes

### What was built

- **Details plan (`Tellma.Core.Abstractions.Crud`, `Tellma.Core/Crud/Details`).**
  - `DetailsPlan.OmitExtra(name)`: a class that declares a requested extra may leave it absent on purpose. The planner's "requested but not added" authoring check now accepts an omitted extra. Omitting an undeclared, unrequested or already added/omitted extra is the same `InvalidOperationException` as adding one.
  - `DetailsPlan.Decide(resource, action)`: the caller's decision over the permission set the read is composed under (the planner's own `Decide`), so a producer's filter and the read's filters come from one snapshot.
  - `DetailsComposition` stores an omitted extra as a null producer; `Complete` skips it.
- **Roles stack (`src/core/Tellma.Core/Users`).**
  - `RoleService<TRole>` declares `[DetailsExtras("members", "problems")]` and takes a `RoleServiceDependencies` bundle (classifier, Queryex schema provider, entity metadata, logger), registered by `UsersRuntimeComposition`.
  - `members` (spec 0018 §4.3): one `AddExtra` query over `core.RoleMembership`, restricted on `RoleId` to `plan.IdsSource`, filter `EndsAt is null or EndsAt > now()` and, when the caller's `core.User` × `Read` is filtered, that filter rebased with `FilterTree.Via("User", …)`. Ordered `User.Name, UserId, Id`, `Take = 500`. Denied → `OmitExtra`, no statement. A users' filter the rebasing rejects is logged `FilterTooComplex` and thrown as `InvalidOperationException`, as the holders resolver does.
  - `problems`: `AddComputedExtra` over the loaded roles, via `RoleProblems.Of`, which runs the evaluator's own `PermissionClassifier` (shared validation cache across roles). A `FilterInvalid` permission carries its diagnostics through `QueryWireDiagnostics.ToWire` located at clause `filters[0]`, or one synthetic `Permissions.FilterInvalid` diagnostic when the engine produced none.
  - `PermissionProblem` record in `Tellma.Core.Abstractions.Access` (`PermissionId`, `Code`, `Diagnostics`).
- **`AccessService` (`src/core/Tellma.Core/Access/AccessService.cs`, route `access`, contributed by `CoreFeature`).**
  - `check`, member-only, idempotent, read-only: self (no `UserId`, or `UserId` = the caller) → `AccessEvaluator.EvaluateAsync`, 0 RT. Another user → `RequireAsync(core.Role, Read)`, one guarded Read of the user's key under the caller's `core.User` × `Read` filter (hidden or missing → `NotFoundException(core.User, [id])`), then `EvaluateForAsync` per pair, 2 RT in all. More than 200 pairs → `LimitExceededException(LimitNames.MaxSecurables)`; a null pair or member → `BadRequestException` with the index. Unknown resource or action → `Denied` with its problem (the evaluator's behaviour).
  - `holders`: `RequireAsync(core.Role, Read)` then `IAccessHoldersResolver.ResolveAsync`, 1 RT.
  - `LimitNames.MaxSecurables`.
- **Goldens.** Public API (`Crud`: `Decide`, `OmitExtra`; `Errors`: `MaxSecurables`), route goldens (`access/check`, `access/holders`), stack goldens (`core.Role` extras `members, problems, permissions`; the `access` service), client `entities-chunk.json` (role extras). `ClosedExceptionSetTests` pins the new limit name.
- **Docs.** `Tellma.Core/README.md` (details extras step 3, roles' extras, the access endpoints table) and `Tellma.Core.Abstractions/README.md` (`PermissionProblem`).

### Deviations

1. `DetailsPlan` gains `Decide` and `OmitExtra`. Spec 0015 §5.3's plan gave a producer no way to decide access or to leave a requested extra absent, and the planner refused a requested declared extra that was not added; spec 0018 §4.3's "absent when Denied" needs both.
2. The members' projection adds `Id` and `RoleId` (row identity, and attribution when the read spans several roles) and the order adds the tiebreak `UserId, Id`. `Name2`/`Name3` are selected only when the tenant's shape declares them.
3. `problems` reports `WildcardResourceOnPublicRole` as well (the classifier's sixth code), since it uses the same classifier as evaluation. `FilterInvalid` diagnostics are located at clause `filters[0]`, with a synthetic `Permissions.FilterInvalid` diagnostic when the engine gave none.
4. `AccessService` is `internal sealed` (the spec sketches it public); this matches the sibling API services, which the registry discovers through `ApiService<T>()`.
5. A `check` whose `UserId` equals the caller's own id is the caller's check (0 RT, no `core.Role` × `Read`).
6. New limit name `LimitNames.MaxSecurables` for the 200-securable cap.
7. `RoleService<TRole>`'s constructor takes `RoleServiceDependencies` (the `UserServiceDependencies` pattern), which changes a leaf role service's constructor.

### Open risks

- `UserAccessCriteria` grants every member Filtered `core.User` × `Read` (`Id = me()`), so in the stock composition the members extra is never Denied for a member: a caller without a users' grant sees only their own membership row, and the client's "You can't see this role's members" state is effectively unreachable. The denied tests remove the criteria providers to reach it. Needs an orchestrator/spec ruling on whether that is intended.
- The access endpoints' MCP exposure is the default (`Full`); spec 0018 does not say.

### What reviewers should examine

- `DetailsComposition`/`DetailsPlanner` omit bookkeeping: the authoring checks for every misuse, and that an omitted extra never reaches `Complete` or the result's `Extras`.
- `RoleService.AddMembers`: the filter rebasing through `User`, the restriction on `IdsSource`, and the `FilterTooComplex` path.
- `AccessService.EnsureVisibleAsync`: the hidden-user read's composition and that it is the only extra round trip; the self detection by caller id.
- `RoleProblems`: the diagnostic mapping to `filters[0]` and the synthetic diagnostic.
