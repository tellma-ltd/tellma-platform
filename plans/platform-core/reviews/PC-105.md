# PC-105: Primary entity registry: tmEntity, TmEntities, TmDisplayNames, TmPermissions

## Implementer notes

### What was built, and where

All paths are under `client/projects/core/tellma-core/` unless noted.

- **Declarations** (`src/entity/tm-entity-declaration.ts`, `tm-entity-types.ts`): `tmEntity` and
  the declaration types of 0029 §3, with `TmPath<N>` typed over the generated entity map (an
  unknown entity's paths widen to `string`; the type walks navigations, twins and the blob
  navigations' open-ended ends). The type tests are in `client/tools/tests/entity-model.spec.mts`.
- **`TmEntities`** (`src/entity/tm-entities.ts`): `summary`, `bySegment`, `declaration` and
  `label` answer from the Core chunk's summaries and the merged declarations; `load()` fetches the
  Entities chunk once, emits `tm.entity.metadata-loaded`, and imports the entity model with it.
  `get`, `enum` and `resolve` throw in a development app before the load (`ɵbeforeLoad`), and in
  production answer a summary-only descriptor.
- **The entity model** (`src/entity/tm-entity-model.ts`, `tm-entity-descriptors.ts`): the
  shape-gated descriptors (twins beyond the routed tenant's languages are not properties; with two
  or three languages each twin's label reads "Name (symbol)" and its `contentDir` follows the
  language's direction), named enums, `resolve` for value/text/navigation/image/file ends with the
  slash label and `fkPath`, the traversal rule behind `TmPermissions.reachable` (a child root's
  owner step skipped, `core.Blob` always refused), and the display names' background reads. This
  module is a lazy chunk of the primary (`tm-entity-model`), loaded by `TmEntities.load()`.
- **`TmDisplayNames`** and **`tm-display-name`** (`src/entity/tm-display-names.ts`,
  `tm-display-name.ts`): the plan per entity and shape (deduped columns, the navigation prefix),
  rendering in the active slot else slot 1, integers ungrouped in locale digits, dates numeric via
  `tmFormatDate`, the fixed " - ", the `Entity_DisplayNameFallback` "#id" fallback, bidi controls
  stripped; `label`/`labelParts` (a cacheable entity's list first, in both id forms, then the held
  rows), `remember`, `rememberRelated`, and `resolve` batched per frame (rAF, a task when hidden),
  ≤ 100 ids per read and the refresher's tenant signal as abort. The held rows are an LRU of 5,000
  per entity, dropped when the user, the tenant or the content-language codes change. The TS half
  of the golden is in `tm-display-names.spec.ts` against the shared golden file.
- **`tmRowsToObjects`** (`src/entity/tm-rows-to-objects.ts`): paths nest by the metadata's JSON
  names, camelCase without metadata, expression columns skipped.
- **`TmPermissions`** (`src/entity/tm-permissions.ts`): `can`, `filtered`, `allows` (the
  operation table; `details` needs a details page; `activate` needs `activatable` and `save`;
  `action:<name>` from the model's action metadata), `disabledReason` (tenant `ReadOnly`/`Frozen`
  with `allowWhenReadOnly`, then the missing permission), `sensitive`, `label` (through the
  securables section, `Securable_Settings` for `core.Settings.*`, else "resource: action"),
  and `reachable`; a system user's summary allows every securable. The route host's `securable` gate now asks it; the interim
  `TM_ROUTE_PERMISSIONS` seam (`src/routes/tm-route-permissions.ts`) is deleted.
- **`tmCheckEntityDeclaration`** (`config-check/src/tm-entity-checks.ts`): renamed from the
  internal `tmEntityFindings` and exported, with codes `unknown-path`, `unknown-action`,
  `operation-missing` and `entity-not-routable`; it takes the chunk or a `TmPathResolver` built
  once for many declarations.
- **`tmTestEntities()`** (`../tellma-core-testing/src/tm-test-entities.ts`): fresh copies of the
  recorded summaries and Entities chunk.
- **Strings:** the `entity` block of the English platform table and its Arabic twin
  (`client/projects/locale/tellma-locale-ar/strings/strings-tm-ar.ts`).
- **Docs:** the core and core-testing READMEs (entry-point table, the new "Entities, display
  names and permissions" section, the seams paragraph), ARCHITECTURE.md's primary entry line.
- **Bundle:** the primary measured 38.49 KB before and 42.34 KB after on the linked measure
  (+3.85 KB, within 0029's 6 KB share); the ceiling goes 38.5 → 42.5 and `tm-entity-model` gets a
  lazy-chunk budget. Moving the display names' reads into the lazy chunk saved 0.15 KB of the
  first frame. The figures are in `package.json`'s `budgetNotes`.

### Deviations

- The descriptor code lives in a lazy chunk of the primary (`tm-entity-model`), loaded with the
  Entities chunk, rather than in the primary's first frame as §1 says; `TmEntities.get` stays
  primary API and answers synchronously once loaded, as before.
- `resolve` sends `includeInactive: true` for an activatable entity, so a deactivated row still
  names itself where a record points at it.
- A 403 on a display-name read marks the ids missing, so they render as "#id" and are not asked
  again; other failures leave them unknown, so a later `resolve` asks again.
- A name that is empty after the bidi strip counts as empty and falls back.
- The fallback's id is written in Latin digits whatever the locale.
- `details` is allowed only when the merged declaration has a `details` member (a details page);
  an entity without one answers `false` though the server offers `details`.
- New public type `TmActionConfirmation` for an action declaration's confirmation;
  `TmSearchPageActionDeclaration.run` takes `search: unknown` until the search page's type lands.
- In production, `get` before `load()` answers a summary-only descriptor instead of throwing.

### Open risks

- `TmDisplayNames` stays on the first frame because the eager shell and the bell need it
  synchronously; making it lazy would make `label` asynchronous.
- The budgets in `package.json` will need a small merge with PC-F69.

### Where reviewers should look hardest

- `TmDisplayNames.#bucket` and `#read`: the scope clearing, the generation check that drops a read
  landing after a tenant or language move, and the LRU touch on read.
- `TmPermissions.reachable` against 0029's traversal rule (child roots, `core.Blob`).
- `TmPath<N>`'s recursion depth and its behaviour for unknown entities.

### Findings

**R1-1 (major): `reachable` skips the owner step from every child root, but the server skips it only when the child's read has no grant of its own. A user with a direct child grant is offered owner columns the server refuses with 403.**
- `client/projects/core/tellma-core/src/entity/tm-entity-model.ts:404-408`: the owner step is skipped whenever the root is a child and its first step is the owner navigation.
- The server's rule, `QueryTraversalRule.Owner` (`src/core/Tellma.Core/Crud/Query/QueryTraversalRule.cs:201-212`), treats the owner as root-like only when `decisions(child).Grants` holds no grant on the child itself or on the wildcard (spec 0015 §5.2: "whose decision has no direct child grant").
- Failure scenario: a role grants `Read` on `acme.CustomerContact` (or `core.RoleMembership`) directly, with no `Read` on the owner.
  - The client gives `reachable('acme.CustomerContact', 'Customer.CreditLimit')` = `true`.
  - The server's walk is not root-like. At `acme.Customer`, `CreditLimit` is outside the projection `[Id, Name*, Code, ImageId]` and the decision is `Denied`, so the server refuses with `ForbiddenException(RestrictedPath)`.
  - A grid or path picker built on `reachable` then sends a column that 403s the page, which §6.4 promises never happens.
- Fix:
  - Skip the owner step only when the owner's `Read` is granted, for example `!restricted(owner)` or a `granted(owner)` callback beside `restricted`. With no owner grant, the child's grant must be direct, so the server checks the owner's projection.
  - Add the vector `rig([grant('acme.CustomerContact', 'Read', true)])` → `Customer.CreditLimit` false, `Customer.Code` true.
  - One case stays undecidable: a direct child grant plus a filtered owner grant. `AccessSummary` composes owner grants into the child's entry, so the client cannot tell direct from inherited. Name it under Deviations as a spec/summary gap for Ahmad, for example a `direct` flag on `SecurableSummary`.
  - The server also continues root-likeness through a chain of child owners (`rootLike` at `:168-170`), while the client skips only step 0. That is a smaller under-grant, and the same change can follow the chain.

**R1-2 (major): the client checks the whole remaining path against each restricted entity's projection, but the server checks only the one segment read there. Paths the server admits through a projected foreign key are refused and dropped as `unreachable`.**
- `client/projects/core/tellma-core/src/entity/tm-entity-model.ts:396-414`: for a restricted step `i`, every read's suffix after `i + 1` segments must be in the target's `relatedSelect`.
- The server's `Refuser`/`Projects` (`QueryTraversalRule.cs:142-191`) walks segment by segment. At each entity past the root, only `segments[index]` is checked, and a navigation segment passes by its own name or its foreign key's. It then moves on to the target, whose own decision governs the next segment.
- `relatedSelect` holds flat names (`ImageId`, `Code`), so a multi-segment suffix can never match.
- Failure scenario on the recorded model: an unfiltered `Read` on `gl.Center` and no grant on `core.User`.
  - `reachable('gl.Center', 'Manager.Image.FileName')` is `false`, because the suffix `Image.FileName` is not in core.User's projection.
  - The server admits it: `Image` passes at `core.User` by `ImageId`, and `FileName` is in `core.Blob`'s projection.
  - The same happens for any `X.Y.Z` where `X`'s target is restricted but projects `YId`.
  - A projection that lists a navigation by name rather than by foreign key is also refused for a navigation end, since only `fkPath` is checked.
  - Spec §7 says `reachable` mirrors spec 0015 §5.2 step 4. The test vectors (`tm-permissions.spec.ts:233-283`) have no multi-hop case through a restricted entity, so this is unpinned.
- Fix:
  - Walk as the server does. For step `i` whose target is restricted (or `core.Blob`), check only the segment read at that target: the next step's navigation name or foreign key, or the end's property, slot or foreign key.
  - Add vectors that pin it: `Manager.Image.FileName` true and `Manager.Image.State` false under `[gl.Center Read]`. Add the child-owner chain as well, if R1-1 follows it.

**R1-3 (major): `TmPath` expands every path of up to three navigation steps into one literal union, and its type-check cost explodes on a modestly connected model.**
- `client/projects/core/tellma-core/src/entity/tm-entity-types.ts:62-90`, with `TmOrderInput` (`tm-entity-declaration.ts:201`) crossing that union with `:desc`.
- The union grows like (scalars + navigations) × navigations³ per root.
- Probe: the same type definitions over a synthetic shape map of 20 entities, each with 30 scalars and V navigations to other entities. One `TmPath<'e0'>` and one `TmOrderInput<'e0'>` annotation were checked with TypeScript 6.0.3 `tsc --noEmit`:

  | Model | Time |
  |---|---|
  | baseline file | 5 s |
  | V = 6 | 13 s |
  | V = 8 | 160 s |
  | V = 10 | 325 s, under load |

- The recorded fixture's entities have 4–5 navigations each, so the type test never sees this. But every Tellma entity carries `CreatedBy` and `ModifiedBy`, and document-like entities (centers, agents, resources, lines) commonly carry 8 or more navigations.
- Failure scenario: a distribution's `tellma-entities.d.ts` registers such an entity, and each `tmEntity` over it adds minutes to `typecheck`, the IDE and `ng build`. Near V ≈ 12, `${TmPath<N>}:desc` passes TypeScript's 100,000-member cross-product limit (TS2590).
- Fix:
  - Check the literal instead of enumerating paths. For example, `TmPath<N, P>` validates `P` segment by segment with `` P extends `${infer H}.${infer T}` `` against `TmEntityShapes`, which is linear in the path's length. `tmEntity` takes the declaration as a `const` type parameter, so its column, order, tile and picker literals are validated.
  - Keep a bounded union only for autocompletion, for example one level.
  - Add a type-cost regression: a synthetic shape with 10 navigations per entity in `entity-model.spec.mts` that must type-check within a fixed budget.
  - If the union form is kept, record the bound under Deviations.

**R1-4 (minor): the shared golden's rows run through a test-local plan builder, so they do not pin the production plan.**
- `client/projects/core/tellma-core/src/entity/tm-display-names.spec.ts:48-63` and `:87-97`: `goldenPlan` re-implements the twin selection (stopping at the first `null` twin), the key and the prefix. The expansion rows then compare `goldenPlan(...).columns`, with the navigation prefix added in the test itself.
- `ɵtmDisplayNamePlanOf` and `TmDisplayNames.select` (`tm-display-names.ts:113-142`, `:365-374`) are what production uses, and the golden never reaches them. That covers:
  - the twins taken from the descriptor's `multilingual` slots;
  - the key from `descriptor.key.property`;
  - the pre-load convention path.
- Failure scenario: a regression in `ɵtmDisplayNamePlanOf`, for example ignoring the shape for a descriptor's twins, or the pre-load branch reading `Name2` for a group with no second twin. The golden stays green, and only the fixture's two `select` vectors could catch it.
- §5.2 calls the golden normative for both sides, and spec 0012 §13's C# test reads the same file.
- Fix: build a minimal descriptor per golden rule, with properties carrying `multilingual: { group, slot }` for each non-null twin, the key property and the scalar types. Derive the plan with `ɵtmDisplayNamePlanOf(rule, shape, descriptor)`, and for expansion rows compare the result of the same prefixing `select` performs. Keep `goldenPlan` only if it is replaced by that call.

**R1-5 (minor): `resolve` reads ids that a loaded cacheable list already names.**
- `client/projects/core/tellma-core/src/entity/tm-display-names.ts:476-481`: an id is skipped only when the held bucket has it or a read is in flight. `labelParts` (`:409-416`), however, answers a cacheable entity's ids from `TmLaunchCache.entitySet()` first.
- Failure scenario: a page resolves the `Currency` ids of its rows (`acme.Currency` is `cacheable`) while the currency list is loaded. Every frame with new ids sends a `currencies/query` for rows `label` already answers from memory. That is a needless background request, against §5.3's "Until the list is present, the cache answers" and the "known ids are never asked" rule `resolve`'s own test pins.
- Fix: in `resolve`, skip a key that the entity's loaded `entitySet()` list holds (read untracked, in either id form), and add a test that a cacheable entity with its list present sends no query.

### Responses

- R1-1: fixed in the "PC-105: review 1 fixes" commit (child of 1a17e290), failing closed per
  D-233. `TmEntityModel.reachable` no longer skips a child root's owner step: the owner is judged
  like any other entity, so its columns pass only through its projection or under its unfiltered
  `Read`. The server skips the step only when the child's decision carries no grant of its own,
  and the access summary cannot show that. A filtered owner composes into the child's entry
  (0014 §5.5), so a filtered child grant may be the child's own or only the owner's; an
  unfiltered child grant over a filtered or absent owner must be the child's own; and an
  unfiltered owner already passes as an unrestricted entity. So no summary proves the skip, and
  the client never takes it. The cost is under-offering: from a child root whose owner `Read` is
  filtered, owner columns outside the owner's projection are unreachable, although the server
  admits them when the child has no direct grant. This summary/spec gap needs Ahmad, for example
  a `direct` flag on `SecurableSummary`. The server's chain of root-like child owners is
  therefore never followed either. Vectors in `tm-permissions.spec.ts` under "from a child root":
  - a direct filtered child grant: `Customer.Code` true, `Customer.CreditLimit` false;
  - an unfiltered child and owner: `Customer.CreditLimit` and `Customer.Currency.Code` true,
    `Customer.Currency.DecimalPlaces` false;
  - the ambiguous case, a filtered child and a filtered owner: `Customer.Code` true,
    `Customer.CreditLimit` and `Customer.Currency.Code` false.
- R1-2: fixed in the same commit. The walk now follows `QueryTraversalRule.Refuser`. At each
  entity after the root that is restricted (or `core.Blob`), only the segment read there is
  checked: the next step's navigation, by its name or its foreign key, or the end's property, each
  slot of a group anchor, or a navigation end by its name or its foreign key. No shared vector
  file exists for server/client traversal parity, so the vectors live only in
  `tm-permissions.spec.ts`. They run from an unfiltered `gl.Center` with no `core.User` grant:
  - `Manager.Image.FileName` true, `Manager.Image.State` false and `Manager.Image` true;
  - `Manager.Signature.FileName` false;
  - `Parent.Manager.Image.FileName` and `Parent.Manager.Name` true;
  - `Manager.ModifiedBy.Name` false.
- R1-3: fixed in the same commit. Paths are no longer enumerated past two segments.
  - **`TmPath<N>`** (the annotation form, same name) is a bounded union: scalars, groups,
    navigations, and `Nav.` followed by the target's scalars, groups, navigations or
    `Nav.${string}`. It is linear in navigations times their targets' members. **`TmOrderInput<N>`**
    crosses that union with `:desc`.
  - **`tmEntity`** now takes the declaration as a `const` type parameter `D`, checked by
    `D extends TmCheckedDeclaration<N, D> ? D : TmCheckedDeclaration<N, D>`. It checks every
    literal path (columns and their selects, `orderBy`, the tile's slots, the picker's description
    and order) segment by segment through `TmCheckedPath`. `TmCheckedOrder` checks an order's
    path apart from its `:desc`. Non-literal text passes unchanged, and so does an entity the
    emitted declarations do not register. An error names the valid continuations, for example
    `'"Currency.CreatedBy.Image.Nope"' is not assignable to '"Currency.CreatedBy.Image.Id" | …'`.
  - **What is lost:**
    - an annotation (a `TmPath<N>` or `TmOrderInput<N>` variable) checks only the first two
      segments exactly; previously it checked three navigation steps;
    - autocomplete offers two segments, where it offered three or more steps;
    - `tmEntity` checks the whole literal, with no depth limit.
  - **Regression test** in `client/tools/tests/entity-model.spec.mts`:
    - a synthetic model of 20 entities, each with 30 scalars, a group and 12 navigations;
    - it type-checks one `TmPath`, one `TmOrderInput` and a `tmEntity` with five-segment paths,
      with no diagnostics and therefore no TS2590;
    - measured at about 0.2 s (198–249 ms over three runs), against a 10 s budget;
    - new usage vectors pin deep `tmEntity` refusals in columns, selects, order, tile and picker,
      plus an annotation order refusal.
- R1-4: fixed in the same commit. The golden rows now run through `ɵtmDisplayNamePlanOf`:
  - `goldenDescriptor` builds a minimal descriptor per rule: the key property, each non-null twin
    with its `multilingual: { group, slot }`, the scalar source and the prefix;
  - `summaryRule` gives the summary's rule;
  - the expansion rows compare `ɵtmDisplayNameSelect`, the helper `TmDisplayNames.select` now
    uses for its navigation prefixing;
  - the expansion rows whose rule has every twin also run through the pre-load convention path
    (descriptor `null`).
- R1-5: fixed in the same commit. `resolve` skips a key that the loaded `entitySet()` list of a
  cacheable entity holds, read untracked and in either id form. The test "never asks about ids a
  cacheable entity's loaded list holds" pins it: no `currencies/query` for listed ids, and only
  `Id in (9)` for an unlisted one.
