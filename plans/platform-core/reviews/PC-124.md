# PC-124: Search query model, URL canonicalization and request builder (pure logic)

## Implementer notes

### What was built, and where

All paths are under `client/projects/core/tellma-core/`.

**Primary (types only)**

- **`src/search/tm-search-types.ts`.** `TmColumnPreference` (a path, or `{ expression }`) and
  `TmSearchSnapshot` (spec 0030 §4.3's page-state record: canonical URL, `supersedes`, entity,
  query, request, result with total and `capped`, ids, highlight, selection, expansion, scroll).
  Both are exported from `public-api.ts` with `export type`, so the first frame carries no bytes:
  `.` measures 49.88 KB (cap measure 49.78), the same as before.
- `TmTileDeclaration`, `TmCustomFilterDeclaration` and `TmSearchPageActionDeclaration` already
  exist from the entity declarations; they are reused unchanged, as the planner note asks.

**`@tellma/core/search` entry point**

- **`search/ng-package.json` and `search/public-api.ts`.** The scaffold. The entry exports nothing
  yet: everything below is internal until the search host lands. It was already in the ESLint
  boundary table as a lazy entry over `./entity`, `./memory` and `./column-filter`.
- **`search/src/tm-search-model.ts`.** The setting a page resolves under (mode `page`, `picker` or
  `list`, descriptor, declaration, width, the user's preferences, a picker's fixed leaves, a list's
  segment) and the state (canonical query, shown columns and where they came from, a list's payload
  filter). The defaults the URL is canonical against: the first tab, the declared columns or the
  generated ones (display name with its prefix, the other natural keys, `IsActive`), page size 50,
  the view by width class. The page-size arithmetic (§14): the offered sizes within `maxTake`, the
  last page under `maxSkipWindow`, and the page that keeps the first visible row on a size change.
  The tile's paths and the tree's keys for the select.
- **`search/src/tm-search-preferences.ts`.** The three preference keys (`search.<entity>.columns`
  write-behind, `.view` per width class with the list choice, `.pageSize`), their validators, and
  the column list's round trip, which gives an undeclared expression the generic label.
- **`search/src/tm-search-canonical.ts`.** The query's canonical form (§4.4): each column key
  rewritten to its canonical path and checked against the select plan, `f.` values reprinted
  through the filter leaf, custom filters in declaration order, `order` kept only on an orderable
  column (an explicit order on the default's column stays), `cols` only when every column is a
  path and the list differs from the default, `size`, `page` and `view` only away from their
  defaults, `list` only on a tree, `inactive` only on an activatable entity outside list mode.
  Every drop emits `tm.entity.column-dropped` with reason `invalid-value` and source `url`. The
  printed URL for each mode: the search page, the drill-through list over its payload, none for a
  picker.
- **`search/src/tm-search-resolve.ts`.** The §4.2 precedence: a snapshot whose `supersedes` is the
  URL's canonical form, then a URL that carries state, then the page state, then preferences and
  defaults. Only a snapshot of the same entity, and in a list the same payload filter, applies.
- **`search/src/tm-search-change.ts`.** Every change returns the next state, its canonical URL,
  the history verb (push only for a page change alone, replace otherwise, nothing when the URL is
  unchanged or in a picker) and the preference writes it implies. Changing the tab, text, a filter,
  inactive or the order sends the page back to 1; a size change keeps the first visible row. A
  resize re-resolves the view for the new width class.
- **`search/src/tm-search-request.ts`.** The select plan over the shown columns with the tile's
  paths and the tree's keys beside them, and the request (§5.1): leaves in the order tab, advanced
  filter, custom filters, column filters (by key), fixed leaves, each with its origin; named filters
  likewise; `orderBy` from the order column, else the declaration, else the entity's default;
  paging within the skip window; `includeInactive` and `includeAncestors`; a browse tree's single
  `get-by-parent-ids` call with the newest remembered expansion within `maxIds`.
- **`search/src/tm-search-diagnostics.ts`.** A refused query's diagnostics mapped back to the
  leaf or named filter they name, with each clause's localized messages in turn, and the page's
  state: the advanced filter (Edit filter), a list's fixed leaf (bad link), a leaf from code, or
  any other clause.
- **`search/src/tm-search.testing.util.ts`** and five specs (72 tests): §18's §4.2 vectors with
  supersedes and the `#d=`-only URL, list URLs keyed by their payload, canonical URLs (expression
  columns, view by width, drops, explicit order on the default's column), history per change, leaf
  order and diagnostic mapping, the page-size arithmetic, the §5.1 Arabic example request, and two
  seeded round trips (300 openings over customers and centers; 40 chains of 12 changes with the
  preference writes applied, where the canonical URL must reopen the same state).

**Other files**

- `package.json`: the `./search` ceiling at 0.5 (0.02 measured) with its note, and `./search` added
  to the primary's static-graph excludes.
- `client/api/core.api.md` (the two types) and `client/api/core.search.api.md` (empty).

### Deviations

1. A URL value at its code default (the default columns as `cols`, `size=50`, the width class's
   default view) reads as absent, so the user's preference applies, as does a `size` the entity
   does not offer. Without it the canonical URL was not idempotent under a differing preference: the
   canonical form drops the value, and reopening it then picked up the preference.
2. A `size` outside 20/50/100/200 or above `maxTake` is dropped; a `page` above
   ⌈`maxSkipWindow`/size⌉ drops to 1 before any read rather than waiting for the 413 fallback; the
   last page's `take` is clamped to what is left of the skip window.
3. `q` is cut to `maxSearchLength` without splitting a surrogate pair, after stripping bidi
   controls.
4. Column keys in `cols`, `order` and `f.` are rewritten to their canonical case; of two `f.`
   spellings of one column, the first in ordinal order wins. A non-orderable `order` or an `f.` on a
   column with no filter drops with reason `invalid-value`.
5. Picker mode writes the page-size and view preferences but never columns.
6. List mode: a snapshot applies only under the same payload filter; only query parameters count
   as carrying state (the fragment is the payload); `includeInactive` is always true; the payload's
   columns are used, not a `cols` parameter.
7. A browse tree's body sends `includeInactive` even when false, matching §16.2's example, and
   `orderBy` is always sent, falling back to the entity's default order.
8. The diagnosis picks one state by priority when diagnostics span origins: advanced filter, then a
   list's fixed leaf, then a leaf from code, then other.
9. The `./search` ceiling is born at 0.5 (its measurement rounded up), not §1's 16 KB, which the
   host should claim with its own measurement.

### Open risks and follow-ups

- Expression columns are orderable in the select plan, but an order on one cannot travel in the
  URL. The host should mark expression columns non-sortable.
- Adding a path column while an expression column shows leaves the URL unchanged (an expression
  list never prints `cols`), so the host must bump its refresh generation on that change.
- The tile's dropped paths are reported under the columns' source, and again each time the plan is
  rebuilt; the host should build the plan once per columns change.
- The `tm.search.expressionColumn` string is referenced but not registered; the host registers it
  with its other strings.
- `TmSearchPageActionDeclaration.run(search: unknown)` is still untyped; the host types it with
  `TmSearchContext`.

### Where to look hardest

- `stateOf` and `columnsOf` in `tm-search-resolve.ts`: the "value at its code default reads as
  absent" rule, and whether the precedence of URL, snapshot and preference holds in every mode.
- `transition` in `tm-search-change.ts`: the push-versus-replace rule and which preference writes a
  change implies.
- `tmSearchCanonical`: that the canonical form is a fixed point (the round-trip specs exercise it,
  but only over the fixture entities).
- `tmSearchRequest`: the leaf order, which the diagnostic mapping depends on.
