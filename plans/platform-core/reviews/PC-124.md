# PC-124: Search query model, URL canonicalization and request builder (pure logic)

## Implementer notes

### What was built, and where

All paths are under `client/projects/core/tellma-core/`.

**Primary (types only)**

- **`src/search/tm-search-types.ts`.** `TmColumnPreference` (a path, or `{ expression }`) and
  `TmSearchSnapshot` (spec 0030 §4.3's page-state record: canonical URL, `supersedes`, entity,
  query, request, result with total and `capped`, ids, highlight, selection, expansion, scroll).
  Both are exported from `public-api.ts` with `export type`, so the first frame carries no bytes:
  `.` measures 49.88 KB (cap measure 49.78), the same as before.
- `TmTileDeclaration`, `TmCustomFilterDeclaration` and `TmSearchPageActionDeclaration` already
  exist from the entity declarations; they are reused unchanged, as the planner note asks.

**`@tellma/core/search` entry point**

- **`search/ng-package.json` and `search/public-api.ts`.** The scaffold. The entry exports nothing
  yet: everything below is internal until the search host lands. It was already in the ESLint
  boundary table as a lazy entry over `./entity`, `./memory` and `./column-filter`.
- **`search/src/tm-search-model.ts`.** The setting a page resolves under (mode `page`, `picker` or
  `list`, descriptor, declaration, width, the user's preferences, a picker's fixed leaves, a list's
  segment) and the state (canonical query, shown columns and where they came from, a list's payload
  filter). The defaults the URL is canonical against: the first tab, the declared columns or the
  generated ones (display name with its prefix, the other natural keys, `IsActive`), page size 50,
  the view by width class. The page-size arithmetic (§14): the offered sizes within `maxTake`, the
  last page under `maxSkipWindow`, and the page that keeps the first visible row on a size change.
  The tile's paths and the tree's keys for the select.
- **`search/src/tm-search-preferences.ts`.** The three preference keys (`search.<entity>.columns`
  write-behind, `.view` per width class with the list choice, `.pageSize`), their validators, and
  the column list's round trip, which gives an undeclared expression the generic label.
- **`search/src/tm-search-canonical.ts`.** The query's canonical form (§4.4): each column key
  rewritten to its canonical path and checked against the select plan, `f.` values reprinted
  through the filter leaf, custom filters in declaration order, `order` kept only on an orderable
  column (an explicit order on the default's column stays), `cols` only when every column is a
  path and the list differs from the default, `size`, `page` and `view` only away from their
  defaults, `list` only on a tree, `inactive` only on an activatable entity outside list mode.
  Every drop emits `tm.entity.column-dropped` with reason `invalid-value` and source `url`. The
  printed URL for each mode: the search page, the drill-through list over its payload, none for a
  picker.
- **`search/src/tm-search-resolve.ts`.** The §4.2 precedence: a snapshot whose `supersedes` is the
  URL's canonical form, then a URL that carries state, then the page state, then preferences and
  defaults. Only a snapshot of the same entity, and in a list the same payload filter, applies.
- **`search/src/tm-search-change.ts`.** Every change returns the next state, its canonical URL,
  the history verb (push only for a page change alone, replace otherwise, nothing when the URL is
  unchanged or in a picker) and the preference writes it implies. Changing the tab, text, a filter,
  inactive or the order sends the page back to 1; a size change keeps the first visible row. A
  resize re-resolves the view for the new width class.
- **`search/src/tm-search-request.ts`.** The select plan over the shown columns with the tile's
  paths and the tree's keys beside them, and the request (§5.1): leaves in the order tab, advanced
  filter, custom filters, column filters (by key), fixed leaves, each with its origin; named filters
  likewise; `orderBy` from the order column, else the declaration, else the entity's default;
  paging within the skip window; `includeInactive` and `includeAncestors`; a browse tree's single
  `get-by-parent-ids` call with the newest remembered expansion within `maxIds`.
- **`search/src/tm-search-diagnostics.ts`.** A refused query's diagnostics mapped back to the
  leaf or named filter they name, with each clause's localized messages in turn, and the page's
  state: the advanced filter (Edit filter), a list's fixed leaf (bad link), a leaf from code, or
  any other clause.
- **`search/src/tm-search.testing.util.ts`** and five specs (72 tests): §18's §4.2 vectors with
  supersedes and the `#d=`-only URL, list URLs keyed by their payload, canonical URLs (expression
  columns, view by width, drops, explicit order on the default's column), history per change, leaf
  order and diagnostic mapping, the page-size arithmetic, the §5.1 Arabic example request, and two
  seeded round trips (300 openings over customers and centers; 40 chains of 12 changes with the
  preference writes applied, where the canonical URL must reopen the same state).

**Other files**

- `package.json`: the `./search` ceiling at 0.5 (0.02 measured) with its note, and `./search` added
  to the primary's static-graph excludes.
- `client/api/core.api.md` (the two types) and `client/api/core.search.api.md` (empty).
- The package README: the entry point's row and a section on the query model.

### Deviations

1. A URL value at its code default (the default columns as `cols`, `size=50`, the width class's
   default view) reads as absent, so the user's preference applies, as does a `size` the entity
   does not offer. Without it the canonical URL was not idempotent under a differing preference: the
   canonical form drops the value, and reopening it then picked up the preference. **Flagged for
   Ahmad (D-275(b)):** this contradicts §4.2's example row 3 ("exactly that, whatever the reader's
   preference") when a colleague's `cols` equals the code default; §4.2 should say that a value at
   its code default yields to the reader's preference.
2. A `size` outside 20/50/100/200 or above `maxTake` is dropped; a `page` above
   ⌈`maxSkipWindow`/size⌉ drops to 1 before any read rather than waiting for the 413 fallback; the
   last page's `take` is clamped to what is left of the skip window.
3. `q` is cut to `maxSearchLength` without splitting a surrogate pair, after stripping bidi
   controls.
4. Column keys in `cols`, `order` and `f.` are rewritten to their canonical case; of two `f.`
   spellings of one column, the first in ordinal order wins. A non-orderable `order` or an `f.` on a
   column with no filter drops with reason `invalid-value`.
5. Picker mode writes the page-size and view preferences but never columns.
6. List mode: a snapshot applies only under the same payload filter; only query parameters count
   as carrying state (the fragment is the payload); `includeInactive` is always true; the payload's
   columns are used, not a `cols` parameter.
7. A browse tree's body sends `includeInactive` even when false, matching §16.2's example, and
   `orderBy` is always sent, falling back to the entity's default order.
8. The diagnosis picks one state by priority when diagnostics span origins: advanced filter, then a
   list's fixed leaf, then a leaf from code, then other.
9. The `./search` ceiling is born at 0.5 (its measurement rounded up), not §1's 16 KB, which the
   host should claim with its own measurement.
10. (fix1) An expression column never orders: the canonical query drops an order on one with
    `tm.entity.column-dropped { reason: 'expression', source: 'url' }`, because `order` travels in
    the URL and the URL carries paths only (§4.3, the codec's path check). **Flagged for Ahmad
    (D-275(a)):** this contradicts §7.3, which makes sortable every column the select plan can
    order, and the plan orders expression columns. PC-126 marks expression columns non-sortable
    in the grid.
11. (fix1) A drill-through list whose `#d=` payload is missing or malformed has no canonical URL to
    write (`''`, as in a picker), takes no snapshot, and `tmSearchRequest` throws for it, so the
    host shows "This link's filter is not valid" rather than an unfiltered list.

### Open risks and follow-ups (carried to PC-126)

- **Refresh bump (with R1-6).** Adding a path column while an expression column shows leaves the
  URL unchanged (an expression list never prints `cols`), so the host must bump its refresh
  generation on that change. More broadly (R1-6), while an expression column shows the canonical
  query is not the result's identity: the grid's `contentKey` (§7.1), the anchor (§5.2) and §15.2
  step 1's snapshot match all key on it. PC-126 (the resource key) and 0030-g (page state) should
  also compare the snapshot request's `select`. This is a spec gap, flagged for Ahmad.
- **Build the plan once per columns change.** The tile's and the tree's dropped paths are now
  reported under `declaration` (fix1), but still once per plan built; the host should build the
  plan once per columns change.
- **Non-sortable expression columns** in the grid (deviation 10).
- The `tm.search.expressionColumn` string is referenced but not registered; the host registers it
  with its other strings.
- `TmSearchPageActionDeclaration.run(search: unknown)` is still untyped; the host types it with
  `TmSearchContext`.

### Where to look hardest

- `stateOf` and `columnsOf` in `tm-search-resolve.ts`: the "value at its code default reads as
  absent" rule, and whether the precedence of URL, snapshot and preference holds in every mode.
- `transition` in `tm-search-change.ts`: the push-versus-replace rule and which preference writes a
  change implies.
- `tmSearchCanonical`: that the canonical form is a fixed point (the round-trip specs exercise it,
  but only over the fixture entities).
- `tmSearchRequest`: the leaf order, which the diagnostic mapping depends on.

## Review 1

### Findings

Reviewed commit 1 (a302765d) against spec 0030 §1, §2.1, §2.4, §4.1–§4.4, §5.1, §5.3 (the mapping),
§14, the CHECKPOINTS entry and PLAN.md §7.1. I re-ran the five search specs (72 passed) and
measured sizes on a clean build (`rm -rf client/dist`, then build and size:check; figures below).
Counts: 0 blocking, 2 major, 6 minor.

**Major**

- **R1-1 (major): a malformed drill-through link is rewritten into a valid unfiltered list.**
  `search/src/tm-search-resolve.ts:96-100` sets `listFilter = null` when the `#d=` payload is
  missing or malformed. `tmSearchUrl` (`search/src/tm-search-canonical.ts:260-265`) then prints a
  `#d=` payload of `{ filter: null }` for that state. The resolution's `canonical` is the URL the
  host must write after every resolution (§4.3). Scenario: open `/17/list/customers#d=!!`. The
  page correctly reports `payloadInvalid`, but the address bar is replaced with
  `/17/list/customers#d=eyJmaWx0ZXIiOm51bGx9`. A reload, a copy or a pin of that URL now opens a
  valid list of every customer, with no fixed leaf and `includeInactive: true`, in place of §17's
  "This link's filter is not valid". `tmSearchRequest` would also build that unfiltered read for
  the invalid state, since it cannot tell a `null` filter from a malformed one. The only test,
  `tm-search-resolve.spec.ts:320-323`, checks the flag and nothing else.
  Fix: when `payloadInvalid`, return a `canonical` that leaves the address bar alone. Either echo
  the raw URL, or use `''` with "do not write" documented on `TmSearchResolution.canonical`. Keep
  the state marked so a request is never built from it: for example, `tmSearchRequest` throws, or
  the state carries `payloadInvalid` and the request builder refuses it. Add a test that a
  malformed payload's canonical is not a valid list URL.

- **R1-2 (major): Back/Forward cannot skip the page-state step.** §4.4 says that on Back or Forward
  the host "re-resolves from §4.2's steps 1 and 2". `tmSearchResolve`
  (`search/src/tm-search-resolve.ts:118-128`) always falls through to step 3 when the URL carries
  no state. `TmSearchOpening` (`:32-41`) has no way to ask for a popstate re-resolution. The host
  can only drop the snapshot, which also drops step 1, the supersedes step that a jump back to
  the list's history entry needs (§15.3). Scenario:
  1. Open `/17/centers` fresh. The canonical URL has no parameters.
  2. Page to 2. This pushes `?page=2`.
  3. Open a row, which remembers a `page=2` snapshot, and come back.
  4. Press Back to `/17/centers`.

  The live host re-resolves with its snapshot, step 3 applies `page=2`, and the URL is replaced
  with `?page=2`. Back never reaches page 1, against Decision 6's "Back steps by page". The same
  happens after "Clear all" brings the URL to no parameters: Back then shows the stale snapshot's
  `q`. Fix: add an opening flag, for example `navigation: 'open' | 'history'`, that skips step 3
  and keeps step 1. Pin it with a test: a snapshot with `q=jed`, a history re-resolve of
  `/17/centers` resolves to the defaults, and a superseding snapshot still applies.

**Minor**

- **R1-3 (minor): the resolution hides the snapshot that §15.2 restores selection from.**
  `TmSearchResolution.snapshot` (`search/src/tm-search-resolve.ts:51-52, 119-128`) is `null`
  whenever the URL or the defaults won. But §15.2 restores the selection and expansion "whenever
  this page has a snapshot, whatever the query's source". §4.2's own example row says the same:
  "the URL: that filter, … selection from page state". The test at `tm-search-resolve.spec.ts:64`
  asserts `null` for exactly that row. In list mode the page-state key is the list path (§17), so
  only the internal `belongs` check (`:159-169`) tells whether a snapshot is this payload's. The
  host cannot restore a list's selection without re-implementing it. Fix: return the snapshot
  that belongs, for example `owned`, separately from the one whose query applied. Extend the
  §4.2 example test to assert the selection source.

- **R1-4 (minor): `tm.entity.column-dropped` is reported twice per change, and tile drops under
  the wrong source.**
  - `tmSearchUpdate` canonicalizes the patched query twice, once for the provisional query and
    once for the final one (`search/src/tm-search-change.ts:100` and `:113`). Each canonicalization
    re-plans every `f.` key and the order, so a patch with a rejected `f.` value, or an order on an
    unknown or expression key (the `search.query` page action can send either), emits each event
    twice.
  - `tmSearchRequest` re-plans every `f.` key and the order on every build (`tm-search-request.ts:156`,
    `:217`). An unreachable key is then reported again on each read.
  - `tmSearchPlan` (`:91-94`) reports a bad tile path under the columns' source (`url` or
    `preference`). A tile path comes from the declaration or the descriptor.

  Fix: derive the paging rule without the first canonicalization, or give `tmSearchCanonical` a
  silent mode for it. Check the tile paths once against the declaration, which is the proposed
  "plan once per columns change" carry, but the source attribution is this checkpoint's code.
  Add a test that one invalid patch emits one event.

- **R1-5 (minor): ordering by an expression column conflicts with §7.3, and that should be on
  record.** §7.3 says sortable columns are those the plan can order. The plan orders expression
  columns, but `order` cannot carry one, by §4.3 and by the codec's `PATH` check. Today
  `keptOrder` (`search/src/tm-search-canonical.ts:165-176`) silently drops such an order as
  `{ reason: 'unknown', source: 'url' }`, a misreported drop. The proposed carry (the host marks
  expression columns non-sortable) is the right home for the fix. But it contradicts §7.3's rule,
  so it belongs in the commit's Deviations with a flag for Ahmad, not only in Open risks.

- **R1-6 (minor): the canonical query is not the result's identity while an expression column
  shows.** The proposed refresh-generation carry covers only the resource key. When an expression
  column shows, `cols` never prints, so two different column sets share one canonical query. Three
  things key on it:
  - the grid's `contentKey` (§7.1);
  - the anchor (§5.2);
  - §15.2 step 1's "snapshot `canonical` equals".

  Scenario: an expression column shows and another tab adds a path column to the preference. On
  return, the snapshot restores with no request, and its rows lack the new column's terms.
  This belongs in PC-126 (resource key) and 0030-g (page state): compare the snapshot request's
  `select` as well. It is a spec gap and should be flagged for Ahmad. It is listed here so that
  the carry covers more than the refresh bump.

- **R1-7 (minor): a page-state snapshot ignores the view preference after a width change.**
  `stateOf` with origin `snapshot` (`search/src/tm-search-resolve.ts:190-198`) fills nothing from
  the preferences. A snapshot taken on a wide window leaves `view` out, because grid was the width
  default. Returned to at narrow width with `{ narrow: 'grid' }`, it shows tiles. `tmSearchResize`
  (`tm-search-change.ts:160`) and §4.2 step 4 both give the class's preference half precedence
  over the width default. Fix: for a snapshot without `view`, take
  `preferences.view[width] ?? width default`, as a resize does.

- **R1-8 (minor): the seeded round trips do not check history or trees.** `tm-search-change.spec.ts:203-252`
  never asserts `change.history`. The brief asked for these to cover history, and they do not.
  Add these invariants:
  - `history === null` exactly when `canonical` equals the previous canonical URL (outside picker
    mode);
  - `'push'` only for a page-only patch whose URL changed.

  Neither round trip runs a tree entity, a `list` patch, a `list` or expression-column preference,
  or a resize. Add `gl.Center` with `list` patches to the change round trip, and an expression or
  list preference to the resolve round trip.
