# PC-125: Shared entity-action runner, generated action dialog and the confirmation loop (@tellma/core/entity)

## Implementer notes

### What was built

All in `client/projects/core/tellma-core/entity/src/` unless named otherwise.

- `tm-confirmations.ts` — `TmConfirmations` (root). `run(send, { entity, ids, confirmations })`
  sends once; on a `confirmation` `TmApiError` it imports the `tm-confirmations-dialog` chunk and
  hands over. Any other failure rethrows as is.
- `tm-confirmations-dialog.ts` (lazy chunk) — `ɵtmConfirmationRounds` and the alert dialog
  `ɵTmConfirmationsDialog` (`TmModal`, `sm`, `role: alertdialog`, `describedBy` the warning list,
  title "Confirm to continue"). Each warning: `TmServerText.error({ code: key, message, arguments },
  entity)` (fallback: the problem's `detail` for the first warning, the key for the others), up to 5
  rows by `TmDisplayNames.label` (after `resolve`), "and {n} more". Choices: Cancel
  (`cdkFocusInitial`), "Continue without these {n}" when the warnings name some but not all of the
  rows still sent, Continue (primary). Continue adds every warning's key; skip adds the named rows
  to `skip` and no key. A fifth 409, a 409 naming no warning, or more than 16 keys fails as a
  `server` `TmApiError` (status, code, trace id and problem of the last 409 kept). Strings
  `tm.confirmations.*` registered from the chunk.
- `tm-entity-actions.ts` — `TmEntityActions` (root):
  - `offered(entity, { record?, bulk? })`: the "which actions appear" filter and the development
    warning (once per entity, `console.warn` under `isDevMode()`).
  - `confirmation(entity, action, n)`: the declaration's `confirm` or the default
    `tm.entity.confirmAction` / `tm.entity.confirmActionMessage`, args `{ action: label, n, ...declared }`.
  - `run(...)`: imports the `tm-action-run` chunk.
  - `dialog(...)`: runs at once when the action takes no arguments and declares no dialog; throws
    when its arguments have no control and no dialog is declared; else imports `tm-action-dialog`.
  - Types `TmEntitiesResult`, `TmEntityActionOutcome`, `TmEntityActionOptions`,
    `TmActionDialogContext`, `TmActionDialogRunOptions`, `TmOfferedActionsOptions`;
    `injectTmActionDialog()` over the internal `ɵTM_ACTION_DIALOG` token.
  - Registers `ɵTM_ENTITY_STRINGS_EN` (`tm-entity-strings.ts`) under scope `entity`, merging the two
    default-confirm keys into `tm.entity`.
- `tm-action-run.ts` (lazy chunk) — `ɵtmActionBody` (§10.4's body table) and `ɵtmRunAction`
  (load, look up, send through `TmConfirmations` with `skip` applied to the ids, outcome mapping,
  job detection). The send's result is wrapped (`{ body }`) so a `null` action result is not read
  as a decline.
- `tm-action-dialog.ts` (lazy chunk) — `ɵtmOpenActionDialog` and the host `ɵTmActionDialog`
  (`TmModal md`, titled with the action's label). It loads a declared dialog before opening and
  renders it through `NgComponentOutlet` with an injector that provides the context; otherwise
  the generated form: one `tm-form-field` + `tm-value-editor` per field, `required()` per the
  metadata, Cancel and the action (primary or danger). The context's `run` runs under
  `TmBusyOverlay.run`, exposes `running` (the button's `pending`), closes with the outcome unless
  `keepOpen` or `declined`, rejects for `rethrow` kinds, else shows the failure:
  `arguments.*` items walked onto `form` and applied with `submit(form, { action: () => errors,
  ignoreValidators: 'all' })`; `ids[i]`/`id` items listed as "{row name}: {message}" against the
  rows actually sent; other items listed; heading/detail from `TmServerText.problem`, the offline
  strings for `offline`, else "The action couldn't be completed." A validation failure whose every
  item landed on a field shows no alert. Strings `tm.actionDialog.*` registered from the chunk.
- `tm-error-paths.ts` — `tmSplitErrorPath` (sticky-regex tokenizer; `null` for malformed) and
  `tmWalkErrorPath(root, segments, { entity, entities }?)` (by wire names; entity-guided through
  properties, navigations and child collections, PascalCase path, the path's entity; stops at the
  deepest field reached).
- `tm-value-editor.ts` — the type switch moved into `kindOf`, and `ɵtmEditable(of)` exported so the
  filter's "has a control" check is the editor's own rule, not a copy.
- Primary: `src/details/tm-details-types.ts` with the types-only `TmDetailsDraft` and
  `TmDetailsSnapshot`, exported from `public-api.ts` (no runtime bytes: "." stays 49.39).
- Arabic for every new key in `projects/locale/tellma-locale-ar/strings/strings-tm-ar.ts`.
- `src/entity/tm-entity.testing.util.ts`: the rig takes `actions` (acme.Customer's declarations).
- Docs: the package README's entry-point row, a new "Entity actions" section and the strings
  section; ARCHITECTURE.md's `/entity` description.

### Rulings and deviations

1. **Layering (planner ruling).** `TmEntityActions.run` wraps `TmConfirmations` only; the busy
   overlay and the destructive confirm stay at the call sites. The action dialog's own `run` takes
   the overlay, per §10.4.
2. **Job detection.** The client metadata's `result` has no job marker and `TmApi.write` returns
   only the body, so a `job` outcome is an `own` result whose body is exactly `{ jobId: integer,
   resourceId?: integer | null }` (the server's `JobAccepted`). Suggest adding `'job'` to the
   emitted `ClientActionResult` so this needs no shape test.
3. **Which actions appear excludes permission.** `offered` applies the structural rule and
   `visible`; `allows` is left to callers, who must render a refused action disabled with
   `TmPermissions.disabledReason` (§10.1's "Disabled with a reason", 0030 §12.2). The spec line
   "appears when the user allows it" would hide it instead.
4. **Warning suppression.** Any declaration entry for an action (such as spec 0032's
   `{ name: 'preferences/set', visible: () => false }`) silences the development warning for it;
   built-in actions are never named. API actions without an entry are named, as §10.4 says.
5. **`running` on `TmActionDialogContext`** (addition): a declared dialog's action button needs the
   pending state the generated one shows.
6. **A declined warning inside a dialog** keeps the dialog open and resolves `run()` to
   `{ kind: 'declined' }` (the spec does not say).
7. **More than 16 confirmed keys** fails as `server`, like the fifth 409, instead of tripping
   `TmApi.write`'s development throw.
8. **Result `none`** maps to `{ kind: 'own', result: null }` (the union has no member for it).
9. **The alert's text** is described locally (problem title/detail via `TmServerText`, offline
   strings, a generic fallback), since `TmErrorPresenter.describe` (PC-110) is not on
   platform-core yet. Carry: switch to `describe()` once it lands.
10. **Argument errors on a declared dialog's form** use Signal Forms submission errors, which clear
    when the field is edited but are not cleared by the next run when unedited (Signal Forms has no
    public reset); the generated dialog uses the same mechanism.
11. **"Continue without these {n}"** is an ICU plural in English ("Continue without this one" for
    one row); the spec gives the plain text.
12. **`TmDetailsDraft` / `TmDetailsSnapshot`** are in the primary as types only (§11.1, §13), in a
    new `src/details/` folder.
13. **Declared dialog size** is always `md`; a per-declaration size (spec 0034's transfer wants
    `sm`) is a later seam. **Telemetry** (`tm.details.confirm`, `tm.details.action`) belongs to
    the details checkpoints; the confirm choice is only known inside the confirmations chunk.

### Open risks

- A declared dialog's chunk that fails to load rejects `dialog()` (no retry UI), unlike
  `TmLazyPickerPage`.
- The `tm.entity` scope is registered from `./entity` into keys the primary also owns; this relies
  on `setTranslation(..., { merge: true })` flattening (verified by the test that
  `tm.entity.permission` still resolves).
- The Arabic ICU plurals (`two`, `few`, `many`) are not exercised by a test.

- `ɵTmActionDialog.#show`: `ids[i]` mapped against the rows actually sent after a skip, and the

- `offered` against §10.1 / 0030 §12.2 (permission left to callers).
- The bundle measurements and the budget notes (D-031).
