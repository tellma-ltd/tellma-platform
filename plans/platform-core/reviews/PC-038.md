### Rulings (not obvious from the spec)

1. **The guard locks the tag rows one at a time, in binary name order and in their final modes
   (deviation from §2.5's text; revised in reviews 1 and 2).** The spec's two
   `EXISTS … t.[Tag] <> e.[Tag]` arms have three defects:
   - The comparison sits in the seek as a residual predicate, and SQL Server releases the
     REPEATABLEREAD/UPDLOCK lock of every row that predicate rejects, i.e. every row that still
     matches. Observed in `sys.dm_tran_locks`: no key lock on a fresh row, and a concurrent bump of
     the tag committed under the guard.
   - Two lock modes per batch let a settings save (U on `settings`, S on `permissions`) and a role
     save (the reverse) each hold S on the row the other's bump converts: a real 1205 (review 1).
   - A lock the bump converts after the guard has locked the caller's stamp row inverts the order
     against a batch that holds S on the tags and writes that stamp: a settings save racing a write
     of the saver's preferences, by the saver or another user, was a real 1205 (review 2).

   The guard copies `@tm_expectedTags` into a table variable keyed in `Latin1_General_100_BIN2`
   order and loops over it, each step a seek.
   - Each iteration reads one row by a `FORCESEEK` seek on its name alone (no residual predicate,
     so the lock is kept), then compares.
   - A name the batch bumps is read under `XLOCK`, every other name under `REPEATABLEREAD`, so the
     bump converts no lock.
   - A bumped name the batch does not depend on binds a NULL tag: locked, never compared. An
     expectation of `VersionTag.None` (all zeros) is compared like any other.
   - Two expectations of one name that disagree bind an all-ones tag, which no row holds.
   - The caller's stamp row comes after every tag row, still summed (its seek is on the key
     alone), under `UPDLOCK` when the batch writes the stamps table.
   - The bump moves its rows one `UPDATE` at a time in the same order (a row-count total →
     `THROW 50422`); behind the guard they are already held exclusively.
   - The migrator's wholesale bump takes `TABLOCKX`, a single resource.

   What the tests prove (`VersionTagLockTests`): two writers of one tag serialise, the second
   failing stale; a settings save and a role save serialise; a settings save and a write of the
   saver's stamp, by the saver or another user, wait instead of deadlocking (the last fails with a
   real 1205 against the review-1 guard). Bumping persists serialise only on a name they both bump,
   or one bumps and the other reads.
   Not prevented, and resolved as 1205 → executor re-run → `50412` or a commit (pinned for a guarded
   victim): two batches that each write the other's caller's stamp row (a caller's row is locked in
   the guard, the others only in the bump, whose users the body produces); and a stamp lock taken
   before the guard, which PC-050's connect prologue would take in `TransactionMode.Explicit`
   (WATCHLIST). Spec 0013 §2.5 should be corrected.
2. **The bump plan is fixed when the epilogue stage starts**, from the writes of every statement
   but the connect prologue's own. The guard's `Bumped` marks and the bump statement agree by
   construction. Refusals (reviews 1 and 2):
   - An epilogue statement whose writes add a name or rule the fixed plan lacks fails the batch
     before it is sent.
   - A statement appended after the bump statement (an epilogue below the bump's order) whose
     writes resolve to any tag fails the batch: the bump must stay last and has read its users.
   - A `TransactionMode.None` batch with a non-empty plan is refused (the bump could not be atomic
     with the writes).
   - The connect prologue begins its statements with `DataBatch.BeginConnectPrologue`; their
     bookkeeping writes bump nothing (spec 0014 §7.3 bumps no tag for them). Any other prologue
     statement whose writes resolve to a tag is refused at append: it would commit before the
     transaction.
3. **Refusals at append, not at execution**:
   - A statement writing a table with a user-level rule and no user-id source (`UserIds`,
     `ForCaller`) throws.
   - `ForCaller` throws unless the batch carries a user's connect prologue, the only declarer of
     `@tm_callerIds` (review 1).
   - `BumpVersionTag` of an unregistered name throws, and so does `DependsOn` with a name the
     registry does not hold ordinally (review 2): an unknown name has no row to guard, and a
     case-only variant would collide with its twin in the guard's case-insensitive key.
   - A rule no source covers throws when the bump is composed.
4. **The `UserStamps` arm takes `UPDLOCK` whenever the plan writes the stamps table**, which is
   whenever the batch writes `core.UserStamps` or any table with a user-level rule. That is broader
   than §2.5, which names only `core.UserStamps` and tables with a `Preferences` rule: a
   `RoleMembership` write (a `Permissions` rule) also takes U on the caller's stamp row. This is a
   deviation, kept deliberately. An administrator editing their own membership writes their own
   stamp row in the bump, and §2.5's rule would leave an S → X conversion there, which is the
   same-row deadlock the arm exists to prevent. For other users' rows it costs one U lock on the
   caller's own row.
5. **`StaleContextException` is thrown by the executor** for a Read/Validate batch whose prelude
   disagrees with a `Rerun` dependency, after the snapshots are replaced and before any handle
   completes; 0014-d's runner owns the one re-run and the `exhausted` phase.
6. **Error mapping**: `50412` stays `BatchAssertionFailedException` (metered `write-guard`);
   `50422` becomes `InvalidOperationException` wrapping the `SqlException` (a defect → 500),
   metered by tag kind, with no event published and the missing name left out of the snapshot.
7. **Snapshots**: a batch's prelude read replaces the tenant's snapshot whether or not its body
   committed (the read is valid either way); a committed bump overlays the batch's tag without a
   read-back; no newer-wins comparison (the spec defines none). A committed body that wrote
   `core.VersionTags` directly (the migrator) leaves the empty snapshot, so every kind reads as
   uncached until the next prelude.
8. **`cache.changed`** is published through the scoped publisher on commit, tenant-wide for
   tenant names and to the affected users for user-level ones, including users without a stamp
   row (the stamps update skips them; the event still reaches them).
9. **Case-only name clashes** are refused by the registry; in practice the entity metadata already
   refuses two entities whose names differ in case alone, so the test feeds two models' entities.
10. **`core.NotificationPreferences`** is registered by table name ahead of the table (spec 0013
    §2.4's fixed rule); it resolves only once a feature contributes the table.
11. **New central package**: `Microsoft.Extensions.Caching.Memory` 10.0.11 (DEPS.md is not mine
    to edit; WATCHLIST lists it as an expected dependency).
12. **The bump is idempotent**: re-running the statement moves the same rows to the same
    `@tm_tag`, so the executor's re-run rules for idempotent writes are unaffected.

### Findings

`Tellma.Core.IntegrationTests` with the integration filter, 195/195; `VersionTagLockTests` alone five
times in a row, 4/4 each run (logs `.tmp/pc038r1-lock-*.log`); the touched `Tellma.Core.Tests`

**Verdicts on the points examined hardest**

- **The guard deviation holds.** Checked on LocalDB with a scratch database (`.tmp/pc038r1-locks.sql`).
  After the spec's `EXISTS … AND t.[Tag] <> e.[Tag]` guard, inside the open transaction,
  `sys.dm_tran_locks` shows no KEY lock on any fresh row. A stale row keeps its S lock. The
  `SUM(IIF(…)) > 0` arms hold S on each read-only expected row and U on each bumped expected row.
  The unexpected row (`entity:x`) is not locked, so FORCESEEK still seeks per name and no other
  row is touched. `VersionTagLockTests` pins both outcomes: a concurrent bump waits (test 2), and a
  second writer of one row is blocked, then fails 50412 (test 3). Same-row writers do not
  deadlock. Cross-row writers do (R1-1).
- **`VersionTagLockTests` is deterministic.** Every pause is a real lock wait on a gate row that a
  side transaction holds. The barrier polls `sys.dm_exec_requests` for `LCK%` waits in the class's
  own database (named per fixture by `NewDatabaseName`). It fails at once if a batch finishes
  instead of waiting. Its only timing is a 30 s ceiling.
- **The two-tenant deferral** is sound in substance but has no named owner (R1-6).
- **The bump epilogue** matches §2.5's statements. `cache.changed` is published only from the
  `OnCommitted` callback, which the executor runs only when the body ran, after the snapshots are
  replaced. A failed bump publishes nothing; the missing-row test asserts this.
- **The migrator seed and bump** call sites (PC-034's, unchanged here) follow §2.8 on a clean run.
  A failure mid-run can lose the bump (R1-3), and one rule is untested (R1-7).
- **`Microsoft.Extensions.Caching.Memory` 10.0.11** is needed: `VersionTagSnapshots` uses
  `MemoryCache`, and spec 0013 §1.1 names the package. The pin sits in `Directory.Packages.props`
  under CPM with transitive pinning on. It equals the version EF Core 10.0.11 already depends on, so
  no resolved version moves.

**R1-1 (major) — The guard now deadlocks a settings save against a role save (cross-row read/bump).**
`src/core/Tellma.Core/Data/Batches/PersistChecks.cs:43-48`. Locks the spec's text never held are
now held, so a lock cycle that the text never produced is now real.
- **Settings save:** U on `settings` (Bumped = 1), S on `permissions` (Bumped = 0).
- **Role save:** U on `permissions`, S on `settings`.
- **The cycle:** each bump epilogue needs X on the row the other holds S on.
- **Reproduced** on LocalDB with the exact arms (`.tmp/pc038r1-dlA.sql` and `-dlB.sql`): one session
  committed, the other died with Msg 1205.
- **The application lock does not help:** spec 0014 §8.3 takes it only for writes to the security
  tables, so a settings save never takes it.
- **The same cycle** forms for a settings save with a language change (U on both rows) against a
  role save, and for any two persists that each depend on the other's bumped `entity:*` list.
- **Today's outcome:** 1205 is retried (`DataErrors.cs:95`). The retry's guard then fails 50412, and
  the runner recomposes. That converges, but it costs the victim the deadlock-monitor delay (up to
  ~5 s) plus a recompose.
- **Not stated:** neither spec 0013 §2.5 nor the Deviation's "should be corrected" note says this. §2.5
  claims only that same-row writers serialise "instead of deadlocking", and §12 asks for "no
  deadlock".

Suggested fix:
- Pin today's behaviour with a `VersionTagLockTests` case: a `settings` bumper and a `permissions`
  bumper race; exactly one commits; the other surfaces `BatchAssertionFailedException` 50412, never
  1205 or `DataAccessRetryExhaustedException`.
- Extend the Deviation and the WATCHLIST guard entry so that the §2.5 correction also states the
  cross-row deadlock and its 1205 → 50412 resolution.
- Alternative, if the orchestrator prefers no deadlock: read every expected row under UPDLOCK
  whenever the batch bumps any expected name. This serialises bumpers that share any expected
  name.

**R1-2 (minor) — Writes made by epilogue contributors are silently left unbumped.**
- `src/core/Tellma.Core/Data/Batches/DataBatch.cs:420` fixes the plan before the epilogue stage.
  `VersionTagFrameTests.The_bump_plan_is_fixed_when_the_epilogue_starts_so_an_epilogues_own_writes_bump_nothing`
  pins the gap as intended behaviour.
- §2.5 makes the bump cover the batch's `WrittenTables`, as the last statement before COMMIT.
- A later epilogue contributor at Order > 50 that writes a cacheable or user-rule table (a spec
  0021/0022 contributor, a pack's) commits its rows with no bump. Caches then stay stale until some
  other write moves the tag. Nothing reports it.

Suggested fix: keep the fixed plan but fail loudly.
- In `VersionTagBumpContributor.Contribute` (or in `Assemble`), resolve the plan again over
  `WrittenTables`.
- Throw `InvalidOperationException` when the second plan has any name or rule the fixed plan lacks.
- Turn the test into a refusal test.

**R1-3 (minor) — A run that applied migrations and then failed before the bump never bumps.**
`src/core/Tellma.Core.Migrator/TenantMigration.cs:170-202` (and `:82-102` for provisioning).
- The bump runs only at the end, gated on `migration.Applied > 0 || steps.Count > 0` from this run.
- The losing case: migrations apply, then a stage before the step runner throws. Examples are the
  fingerprint or grants in `MigrateDatabaseAsync`, or `SeedAsync`.
- The next run applies 0 migrations, and usually runs 0 steps. Tags never move for the `HasData`
  and `migrationBuilder.Sql` changes already committed: the "stale forever" case §2.5 exists to
  prevent.
- A failed step is safe, because it is due again on the next run.

The call sites are PC-034's, but the "bump only after a run that applied something" semantics is
this checkpoint's deliverable.

Suggested fix: once anything has applied, bump best-effort on the failure path too.
- Track `changed = migration.Applied > 0`, and set it after any step completes.
- Wrap the remaining stages so a failure still runs `BumpAllAsync` when `changed` is set, before
  rethrowing.
- `MigrateDatabaseAsync` must report the applied count, or set the flag, before its own trailing
  stages can throw.

**R1-4 (minor) — Under `TransactionMode.None`, the bump is not atomic with the writes it covers.**
`src/core/Tellma.Core/Caching/VersionTagBumpContributor.cs:152-196` adds the bump to every batch
whose plan is non-empty, whatever its mode.
- In `None` mode (autocommit), each business write commits on its own.
- Any later failure means the bump never runs, and the rows stay committed: a statement error, a
  50422, or a lost connection after the writes.
- The result is again a committed write with no tag move.

Suggested fix: refuse it where the mode and the writes are both known (`DataBatch.Assemble`, or when
the plan is fixed). Throw `InvalidOperationException` for a batch whose mode is `None` and whose
bump plan is non-empty, since `None` exists for bookkeeping tables that carry no tag.

**R1-5 (minor) — `SqlOptions.ForCaller` on a batch without a user's connect prologue fails at SQL compile time, not at append.**
- The bump text reads `@tm_callerIds` (`VersionTagBumpContributor.cs:130`), and only a user's connect
  prologue declares that table.
- A `ForCaller` write in a System-scope or maintenance batch makes the whole batch fail with Msg 1087
  ("Must declare the table variable"). It surfaces as a generic data-access failure.
- In production, nothing declares `@tm_callerIds` until PC-050, so every `ForCaller` write fails this
  way until then.
- This departs from the commit's own ruling 3 (refusals at append).

Suggested fix: in `DataBatch.Sql` (next to `CheckUserIds`, `DataBatch.cs:268`), refuse
`options.UserIds` naming `ReservedSqlNames.CallerIds` unless the batch carries a user's connect
prologue (`Premises is GuardPremises { IsSystem: false }`). Add a unit test.

### Responses

    `@@ROWCOUNT` and keeps `THROW 50422` on a shortfall.
  - The settings save and the role save now meet at `permissions`, their first shared name in
    binary order, and the second waits for U there instead of holding S.
  - Tests:

**R2-1 (major) — A tenant-level bump still deadlocks against a write of the same user's stamp row; the "no deadlock" claim and the stated residual are wrong.**
`src/core/Tellma.Core/Data/Batches/PersistChecks.cs:147` and `:155`, with
`src/core/Tellma.Core/Caching/VersionTagBumpContributor.cs:52-63` and `:148`.

Consider a batch that bumps a tenant-level name.
- Its guard takes U on its tag rows, then the caller's stamp row: S when the batch writes no
  stamps.
- Only its epilogue converts the tag rows to X.

So its order is tags (U), then stamp, then tags (X). A batch that writes a user's stamp row and
bumps no tenant-level name has the order tags (S), then stamp (X). The two inversions meet in this
scenario:
- **V:** user 1 saves settings. It takes U on `permissions` and `settings`, S on stamp(1), then
  bumps `settings`.
- **A:** user 2, or a job, writes user 1's `core.UserPreferences` or `core.NotificationPreferences`
  rows, or edits user 1's `core.Users` row. Each carries a Preferences rule and no tenant-level
  name. A takes S on `permissions` and `settings` (every guard expects them), then U on its own
  stamp row, and its bump needs X on stamp(1).
- **Interleaving:** A's guard runs first. V's U requests are compatible with A's S. V then takes S
  on stamp(1). A's bump waits on that S, and V's `settings` U→X conversion waits on A's S.
- **Result:** Msg 1205 in 3/3 runs (`.tmp/pc038r2-dl-a.sql` against `-dl-v.sql`).
- **Same user, two requests:** user 1's own preference flush (a second tab, or a background
  flush) racing user 1's settings save forms the same cycle, because A's stamp arm takes U on
  stamp(1), which is compatible with V's S. That gave 1205 in 2/2 runs (`.tmp/pc038r2-dl-self.sql`).
- **Reasoned, not run:** an administrator's own role save (U on their stamp row, per R1-8) racing
  their own preference flush; and any stamp writer that depends on a name the other batch bumps
  (`entity:X`).
- **The application lock does not serialise these:** neither a settings save nor a list save
  takes it.

Today the cycle converges through the executor's re-run of the 1205 victim.
- If V is the victim, its re-run commits: the stamp arm compares `PermissionsTag` only.
