# PC-073: tellma-client CLI: emit, serve, build and checks

## Implementer notes

### What was built, and where

All paths are under `client/projects/core/tellma-core-tools/` unless stated.

- **The command line** (`src/cli/tellma-client.ts`): `tmRunCli(argv, streams, environment)` parses
  `emit [--configuration c|-c c] [--no-dotnet-build]`, `serve [--port n]` and
  `build [--configuration c] [--no-dotnet-build]`, with per-command help. Exit codes: 0 success,
  1 usage (unknown command or option, missing value, bad port), 2 failure (any `TmBuildFailure`
  or unexpected error, printed as `tellma-client <command>: <message>`), 3 problem. The third
  argument injects the working directory and the process runner, which every spec uses.
- **Shared plumbing** (`src/common/`): `problems.ts` (`TmBuildProblem`, `TmBuildFailure`, the
  one-line format `code key feature - message`, spaces in a field become `_`), `process.ts` (the
  `TmProcessRunner` seam and the real runner: no shell except Windows' `pnpm`/`npm`/`npx` shims; a
  program that cannot start is a `TmBuildFailure`), `files.ts` (posix relative paths, recursive
  listing, the Migrator's content hash, gzip-9/Brotli-11 sizes), `html.ts` (parse5 document and
  fragment parsing, element walk including `<template>` content).
- **The project** (`src/project/app-project.ts`): reads `package.json` (`tellma.migrator`,
  `tellma.budgets`) and the one application in `angular.json` (outputPath string or object, index,
  tsConfig, a `serve` target); fixed layout `src/app.config.ts`, `public/`, `generated/`,
  `dist/<slug>/{browser,sourcemaps,stats.json}`. `tmFindPackageDir` finds a package by Node's
  `node_modules` walk (ignoring `exports`, since `@tellma/core` does not export its
  `package.json`), else through the tsconfig `paths` (resolved with the TypeScript API, so
  `extends` chains work) up to the folder whose package.json carries the name.
- **Emit** (`src/emit/`): `tmRunEmit` runs `dotnet run --project <Migrator> --no-launch-profile
  [--configuration c] [--no-build] -- emit-client-assets <absolute generated/>` in the Migrator's
  folder (PC-034's command reads `appsettings.json` from its content root and resolves the folder
  against its working directory). `tmReadEmittedMetadata` reads `generated/assets/` back by
  PC-034's naming pattern, refuses a name whose hash is not the content's, a missing or doubled
  chunk, a malformed Core chunk (slug, display name, versions, languages, plain routing words) or
  a string pack that is not a flat string table.
- **Source checks** (`src/checks/`): `config-check.ts` + `config-check-runner.ts` (a child Node
  process: tsx `register({ namespace, tsconfig })`, `@angular/compiler` first, then
  `src/app.config.ts`, `@tellma/core` and `@tellma/core/config-check` imported in that one
  namespace so `tmAppConfigOf` finds the config; the string packs are passed, so
  `string-key-collision` is reported; the answer goes through a temp file; `label-missing` stays a
  warning); `index-html.ts` (the six `TM_INDEX_HTML_RULES` evaluated on a parse5 tree; the boot
  script must be the first `<script>` in `<head>`, `src="tm-boot.js"`, classic, no async/defer);
  `manifest.ts` + `png.ts` (members, grapheme-counted short names including the localized ones
  from the packs, PNG IHDR size vs `sizes`, `prefer_related_applications`); `brand.ts` (override
  over default, viewBox with positive size, no `<script>`, no `on*`, no `javascript:` href; a name
  neither folder provides is `brand-file-invalid`); `budgets.ts` (levels, raises from package.json
  with `budget-note-missing`, measuring, report table); `hashed-names.ts`.
- **Output steps** (`src/output/`): `stats.ts` (`TmBuildGraph` from the esbuild metafile: JS
  outputs only, static and dynamic edges; `tmEntryPointModule` matches an entry point by its
  fesm bundle name or its workspace source folder; `tmEchartsModule`); `boot.ts` (`TM_BOOT` from
  the Core chunk's languages and the packs' boot strings, English always, display name filling
  English's `Distribution_DisplayName`, a language with no boot string of its own left out;
  English missing a boot string is a failure); `preloads.ts`; `worker-config.ts`
  (`tmNavigationUrls`, `tmOnDemandChunks`: everything the initial scripts reach minus what they
  reach without entering an on-demand root by a dynamic import; `tmWorkerGroups`: explicit file
  lists; `tmWorkerConfig`); `source-maps.ts`.
- **Commands** (`src/commands/`): `build.ts` (the six steps; a source error returns before
  `ng build`), `serve.ts`, `context.ts`.
- **Fonts** (`src/fonts/index.ts`, new export `@tellma/core-tools/fonts`, golden
  `client/api/core-tools.fonts.api.md`): the fragment map moved from
  `client/scripts/inject-font-preloads.mjs`, now keyed by ISO 15924 script (a language's script
  from `Intl.Locale(code).maximize()`), `tmIsFontForFragments` (never an `-ext` subset),
  `tmBuiltFontUrls`, `tmInjectFontPreloads`. `client/scripts/inject-font-preloads.mjs` is a thin
  wrapper over it for the showcase build and `scripts/serve.mjs --prod`.
- **Fixture** (`fixtures/`): `app/` (a minimal distribution client: the §4.1 index.html, manifest,
  three real PNG icons, favicon, four brand SVGs, one feature with one lazy page, en+ar fonts,
  build and serve targets), `migrator/` (the stand-in Migrator's JSON: Core, Entities,
  Contracts, en and ar packs with the platform's real boot strings) and `fake-emit.ts` (writes
  what the emit writes, a recording runner that answers `dotnet run … emit-client-assets`, and
  `copyFixtureApp` to `fixtures/run-<name>/`, gitignored and ESLint-ignored).
- **Dependencies**: `@angular/service-worker` 22.0.5 (catalog, client), `parse5` 8.0.1 and `tsx`
  (catalog) as runtime dependencies of `@tellma/core-tools`.
- **Docs**: core-tools README (commands, steps, problem lines, budgets), fixture READMEs,
  core-ui README pointer, ARCHITECTURE.md's worker-group sentence (fonts and on-demand members).

### Deviations

1. **`ng build` runs with `NG_BUILD_OPTIMIZE_CHUNKS=false`.** Angular 22's chunk optimizer (on by
   default once a build has three lazy chunks) re-bundles the chunks with Rollup after esbuild has
   written the metafile. Measured on the fixture: `stats.json` then names chunks the output does
   not hold, an orphan chunk stays in the output importing chunks that no longer exist, and the
   merged chunks get base64url hashes (`chunk-Ci8p4wIT.js`) that fail §6's hashed-name rule. With
   the optimizer off the metafile is the true graph and every name is `[A-Z0-9]{8}`. Cost: a few
   more, smaller chunks.
2. `navigationUrls` also exclude the bare `/*/<w>` for each tenant word (§5.3 lists only
   `/*/<w>/**`); §6's fallback gives the server `/<int>/<w>` itself too.
3. `build` accepts `--configuration c` as `emit` does, so an esproj build of a Release Migrator
   with `--no-dotnet-build` finds the Release output.
4. Budgets: a `bootScript` row is added (3 KB + 0.4 KB per further table, the boot-template
   test's rule); the `@tellma/core` primary's 50 KB row is not measured in the app build (the
   package's `size:check` budgets its entry points); the route rows measure the closure of the
   chunks holding `@tellma/core/search|details` and `/entity` beyond the initial set, without the
   distribution's layout chunks, which the metafile cannot tell from other lazy chunks. Every
   lazily loaded chunk no row covers gets an informational line of its own,
   `lazy:<entry module>`, with no level (§12 gives `@defer` chunks a line but no level, and the
   metafile cannot tell a `@defer` chunk from a route's, so a distribution's routes get lines too;
   added after review 1, R1-4). Rows whose entry points do not exist yet measure zero files and
   print `-`.
5. Budget settings: an unknown budget name or a non-positive level is a build failure (exit 2);
   lowering a level, or setting a level the platform leaves empty, needs no note.
6. Fonts: `-ext` subsets (`latin-ext`, …) are never preloaded and are in neither worker group;
   fonts of scripts not offered are in neither group either, so the browser fetches them when a
   page needs them. The spec's shell lists "the Latin and offered-script fonts".
7. The localized short names (`Distribution_ShortName`) are checked in the source step, before
   `ng build`, rather than on the output manifest.
8. A brand name neither `public/brand/` nor `@tellma/core/brand/` provides is
   `brand-file-invalid`; a `javascript:` href is refused alongside `<script>` and `on*`.
9. `serve` requires a `serve` target on `@angular/build:dev-server` (§2.1's angular.json lists only
   build and test); a dev server that exits non-zero is exit 2. The certificate is exported once to
   `%APPDATA%/ASP.NET/https` (Windows) or `~/.aspnet/https` as `<slug>.pem`/`<slug>.key`, as
   ASP.NET Core's SPA templates do. The tenant-word proxy matches an integer first segment
   (`^/[0-9]+/…`), §6's fallback rule. In-repo detection: the nearest `pnpm-workspace.yaml` whose
   `package.json` has a `tokens:build-css` script.
10. Problem lines carry the message after the three fields: `code key feature - message`.
11. The worker groups list files by name rather than by glob; `ngsw-config.json` is written to
    `dist/<slug>/`, outside the deployable output.
12. An English string pack missing a boot string is a build failure (exit 2): the boot script
    embeds English as every language's fallback, and the renderer refuses an incomplete table.
13. The source maps step stays where §2.6 puts it (after the worker config): the explicit file
    lists never include a `.map`, so the hashes are unaffected.
14. `serve` writes `tm-boot.js` and the default brand files to `generated/root/`, which the
    application's angular.json must copy to the output root
    (`{ "glob": "**/*", "input": "generated/root", "output": "/" }`; `serve` fails without it).
    `build` refreshes that folder before `ng build`. Spec 0024 §2.1's asset list and §2.6's
    `serve` say nothing of it (added after review 1, R1-2). Inside the repository both `serve`
    and `lint:test` now write `@tellma/core`'s boot template (`assets:generate`,
    `prelint:test`).
15. `index.html` must hold `<base href="/">` before any element that loads a URL (a new
    `base-href` rule, checked in the source and the built file). Spec 0024 §4.1's sketch has no
    `<base>`, so with it a reload or deep link under a tenant (`/17/centers`) resolved
    `tm-boot.js` and the bundle to `/17/…` and the app never started (added after review 2,
    R2-1). Inside the repository `build` also runs `assets:generate`, as `serve` does (R2-9).

### Open risks

- **No real languages or string packs yet.** PC-034's emit writes `languages: []` in the Core
  chunk, so a real Migrator's emit makes `build` (and `serve`) exit 2 first with "offers no
  languages", until PC-049's settings contributor emits that section. Past that, PC-034 writes
  `strings: {}` and no `strings-*.json` until PC-046, and the build exits 2 with "The English
  string pack lacks …", because the boot script needs every English boot string. Acme (PC-094)
  is gated on PC-046 but not on PC-049, so its build exits 2 until both have landed (corrected
  after review 1, R1-5).
- **No default brand SVGs yet** (`@tellma/core/brand/`, PC-094): until they land, a distribution
  must override all four in `public/brand/`.
- `/shell`, `/attention`, `/search`, `/details`, `/entity`, `/report-studio`, `/support` and the
  ECharts engine do not exist yet: the modulepreloads, route budgets and on-demand group are
  covered by synthetic-graph unit specs only; the fixture build exercises the empty case.
- The fixture's real `ng build` took 4-12 minutes on this loaded machine (about a minute
  unloaded); `build.fixture.spec.ts` allows 20 minutes for its `beforeAll` and runs in `lint:test`.

## Review 1

Reviewed commit 2f3b1b4 only. I ran `tsc -b projects/core/tellma-core-tools`, the 23 non-fixture
core-tools spec files (121 tests, green) and `build.fixture.spec.ts` (9 tests, green; one real
`ng build` in about 170 s) on Windows, in this worktree, where `projects/core/tellma-core/boot/`
already existed from an earlier `pnpm run build`.

Rulings the implementer asked about:

- `NG_BUILD_OPTIMIZE_CHUNKS=false` **holds**. In `@angular/build` 22.0.5
  (`builders/application/chunk-optimizer.js`), the optimizer re-bundles with Rollup and names chunks
  `<name>-[hash].js`. Rollup's hash is mixed-case base64url, so those names fail §6's
  `-[A-Z0-9]{8}` rule. The server would then serve them as unhashed (`no-cache`), and
  `unhashed-asset` would fail every build that has three or more lazy chunks. In
  `environment-options.js`, `'false'` sets the threshold to `Infinity`, so the variable really
  turns the pass off.
- Exit 2 on a real Migrator **holds as policy**: English is every language's boot fallback, and
  the template check already refuses an incomplete English table. The open risk misstates the
  cause, though (R1-5).
- The brand rules (an override wins, and a name neither folder provides is
  `brand-file-invalid`) **hold**.
- The `bootScript` row **holds**. It matches D-048 (3 KB with English, plus 0.4 KB per further
  table) and counts tables the same way `tools/tests/boot-template.spec.mts` does.
- Fonts outside the worker groups **hold**. The worker passes unmatched requests to the network,
  and §6 serves fonts `immutable`, so the HTTP cache covers repeat use. Keeping `latin-ext` (168 KB)
  out of the prefetch is a reasonable cost call. The ARCHITECTURE.md sentence needs one more word
  (R1-7).

### Findings

**R1-1 (blocking): on a fresh CI checkout, the new build specs fail because the boot template is
not built before `lint:test`.**
`client/projects/core/tellma-core-tools/src/commands/build.ts:81-82` renders `tm-boot.js` at the
start of the source step. `src/output/boot.ts:74-77` throws a `TmBuildFailure` (exit 2) when
`<@tellma/core>/boot/tm-boot.template.js` is missing. That file is gitignored
(`client/.gitignore:57`), and only `client/scripts/build.mjs:36` (`pnpm run build`) generates it.
Both client CI jobs run `pnpm run lint:test` before `pnpm run build` (`.github/workflows/ci.yml:188`
and `:232`). `prelint:test` (`client/package.json:13`) only runs `tsc -b` on core-tools, and the
vitest config has no global setup.
- Failure scenario: on GitHub's clean runners, Ubuntu and Windows alike, every `build.spec.ts`
  case that expects exit 3 (index.html, manifest, brand, budget note, config, strings) gets exit 2
  with "…tm-boot.template.js does not exist". So does the "reaches ng build" case, which expects
  ng build to have run. `build.fixture.spec.ts`'s `beforeAll` build exits 2, so all 9 of its tests
  fail. CI goes red on the merge, which PLAN §7.1 item 8 calls a stop-the-line failure. Local
  gates passed only because `tokens:build-css` and `build` had already run in this worktree.
- Fix: make `lint:test` build the template itself. For example, set `prelint:test` to
  `tsc -b projects/core/tellma-core-tools && tsx tools/boot/build-boot-template.mts`, which is quick
  and needs no package build. Alternatively, give `tools/vitest.config.mts` a `globalSetup` that
  calls `buildBootTemplate()`. Then confirm with the template deleted:
  `rm -r client/projects/core/tellma-core/boot && pnpm run lint:test`.

**R1-2 (major): `tellma-client serve` never provides `tm-boot.js` or the default brand files, so
the dev loop runs without its boot script.**
`client/projects/core/tellma-core-tools/src/commands/serve.ts:154-201` emits, exports the
certificate and starts `ng serve`, and nothing more. The source `index.html` §4.1 mandates opens
with `<script src="tm-boot.js">`, and `index-html-invalid` enforces that tag. But only `build`
writes the file (`build.ts:141`). The dev server serves `public/**` and `generated/assets/**`
(as `tm-metadata/`), and neither holds it. The same applies to `brand/*.svg` whenever a
distribution relies on the `@tellma/core/brand/` defaults, which is the normal case once PC-094
ships them.
- Failure scenario: in Acme, `pnpm start` loads the page, and `/tm-boot.js` either 404s or comes
  back as index.html, a script error. Then `<html lang dir data-theme>` is never set before paint,
  and with no cookie there is no 3d redirect to `/bff/login`. `window.__tmBoot` is undefined, so
  `TM_BOOT_RESULT` is null. Once `bootstrapTellma` gates on `__tmBoot.state === 'run'` (§4.3 step 1),
  the app never starts under `serve`. The wordmark and mark also 404 in the shell.
- Fix: in `serve`, render `tm-boot.js` with the existing `tmBootConfig` and `tmBuildBootScript`,
  and copy the resolved brand files (`tmResolveBrandFiles`) into a generated folder the dev server
  serves at the root. For example, write to `generated/root/` and add the angular.json asset
  `{ "glob": "**/*", "input": "generated/root", "output": "/" }`. In the platform repository,
  `platformAssets` should then also build the boot template (see R1-1). Spec 0024 §2.1 (the asset
  list) and §2.6 (`serve`) say nothing about this, so flag the misalignment for Ahmad and add a
  `serve.spec.ts` case that asserts the served boot script exists.

**R1-3 (minor): a language without its own `Distribution_DisplayName` shows English's pack value
in the boot script instead of the config's `displayName`.**
`client/projects/core/tellma-core-tools/src/output/boot.ts:43-55` fills a missing
`Distribution_DisplayName` from `distribution.displayName` only for English. Every other language
without the key falls back, inside the script, to English's value. §4.2 says "the config's
`displayName` fills a missing one", per language. §3.1 makes the runtime name
`Distribution_DisplayName` in the active language, else `displayName`.
- Failure scenario: English's pack sets `Distribution_DisplayName` to "Acme Accounting", Arabic's
  sets nothing, and `Tellma:DisplayName` is "Acme". An Arabic user's `document.title` and boot page
  say "Acme Accounting". Once Angular starts, `TmLocalization.displayName` says "Acme", so the
  title changes after first paint.
- Fix: for each non-English language whose pack lacks the key, set it to `distribution.displayName`
  whenever that differs from English's resolved value. This costs bytes only in that case and stays
  within D-048's per-table allowance. Add an `output.spec.ts` case for it.

**R1-4 (minor): spec 0024 §12's "a `@defer`red chunk is budgeted on its own line" is dropped
without a reason.**
`client/projects/core/tellma-core-tools/src/checks/budgets.ts:183-201` measures route figures as
static closures, which leaves deferred chunks out of every row. Deviation 4 in the commit message
says only "`@defer` chunks get no own line", which PLAN §7.1 item 1 does not accept as a
justification.
- Failure scenario: a page that `@defer`s a 300 KB editor passes every budget, because no row
  measures that chunk.
- Fix: either report each lazy chunk that no other row covers (reached only by a dynamic import
  from a non-route chunk) as an informational line, or state in Deviations why the metafile cannot
  tell a deferred chunk from a route chunk, and record the gap in WATCHLIST.

**R1-5 (minor): the open risk misstates why a real Migrator exits 2, and PC-094 is not gated on the
checkpoint that fixes it.**
`client/projects/core/tellma-core-tools/src/emit/emitted-metadata.ts:156-162` refuses a Core
chunk with no languages. PC-034's emit writes `languages: []`
(`src/core/Tellma.Core.Migrator/Emit/ClientAssetBundle.cs:58`). PC-049's
`SettingsClientAssetContributor` emits that section. So today a real build fails with "offers no
languages" before it reaches the English-pack check that the review notes name. PC-094 ("Acme
`tellma-client build` exits 0 in CI on both OSes") is gated on PC-046, but neither directly nor
transitively on PC-049, according to CHECKPOINTS.md's gate lists.
- Failure scenario: PC-094 launches once its gates are met, but its Acme build exits 2 until
  PC-049 lands.
- Fix: correct the open risk. Have the orchestrator add PC-049 to PC-094's gates, or record the
  dependency in WATCHLIST ## 0024.

**R1-6 (minor): two behaviours have no test that would fail if they broke.**
- The `/shell` and `/attention` modulepreload set, and the `initialJs` set built from it, are
  computed inline at `client/projects/core/tellma-core-tools/src/commands/build.ts:183-208`. The
  fixture has no such chunks, and `output.spec.ts` tests only `tmAddPreloads` with a set it is
  handed. Replacing `staticClosure` with `reach`, which would also follow dynamic imports, or
  dropping the `!loaded.has(file)` filter, would pass every spec. Fix: move the computation into an
  exported function, such as `tmShellModulePreloads(graph, initial)`, and test it on a synthetic
  graph (shell chunk, its static import, an import already in the initial set, a dynamic import
  that must not be preloaded).
- `build -c Release --no-dotnet-build` (deviation 3) is never shown to reach `dotnet run`. The
  test at `src/commands/build.spec.ts:188` is named "…and passes the emit options through", but it
  asserts `run.started` is `[]`. Fix: assert the `dotnet run` arguments in a passing case, or
  rename the test.

**R1-7 (minor): the ARCHITECTURE.md worker-group sentence says the shell holds "the fonts of
Latin" while `latin-ext` is in neither group.**
At `ARCHITECTURE.md:886`, the rule in `src/output/worker-config.ts:244-253` and
`src/fonts/index.ts:93-99` keeps every `-ext` subset out of both groups. The sentence's exception
covers only "fonts for other scripts", and `latin-ext` is Latin.
- Failure scenario: a reader concludes that Latin Extended faces, such as Turkish or transliterated
  names, are prefetched for offline use. They are not.
- Fix: add "except their `-ext` subsets" after "the fonts of Latin and the offered scripts".

### Findings

**R2-1 (major): the deployable output has no `<base href="/">`, so a reload or deep link under a
tenant loads every script, preload and the manifest from the wrong path.**
`client/projects/core/tellma-core-tools/src/build/index-html-rules.ts:33-64` and
`src/checks/index-html.ts:29-53` neither require nor check a `<base>` element. `build.ts:124` runs
`ng build --stats-json` without `--base-href`, and `@angular/build` inserts one only when
`baseHref` is set (`augment-index-html.js:191-198`). The fixture's `src/index.html` copies spec
0024 §4.1's sketch, which has none. Every URL in the built page is relative: `tm-boot.js`,
`manifest.webmanifest`, Angular's `main-*.js`/`polyfills-*.js`/`styles-*.css`, and the
`tm-metadata/…`, font and modulepreload links this checkpoint adds.
- Failure scenario: a user reloads `/17/centers`, opens a bookmark, or returns from sign-in to
  step 3d's `returnUrl=/17/centers`. The server's fallback answers with `index.html`, and the
  browser resolves `tm-boot.js` to `/17/tm-boot.js` and `main-X.js` to `/17/main-X.js`. Those
  requests are not navigations, so `SpaHosting.FallbackAsync` answers each with
  `404 route-not-found`. The boot script never runs, the app never starts, and the page stays
  blank. Only `/` and `/{t}` work, because they have a single segment.
- The same happens warm: the worker serves the cached `index.html` for the navigation, but
  `/17/main-X.js` is not in its hash table, so it goes to the network and gets a 404.
- `serve` breaks the same way on any two-segment path.
- Fix: add a source-and-built rule that `<base href="/">` is the first element of `<head>` that
  carries a URL, before `tm-boot.js` and the manifest link, since a base inserted later does not
  re-resolve URLs that were already fetched. Add the element to the fixture and test the rule. An
  alternative for `build` is to pass `--base-href /` to `ng build`, which Angular inserts right
  after `<head>`, but `serve` would still need the element in the source. Flag spec 0024 §4.1's
  sketch to Ahmad as missing the element.

**R2-2 (minor): the brand check parses the SVG as HTML, so scripts that a browser runs when it
opens the file as `image/svg+xml` pass the check.**
`client/projects/core/tellma-core-tools/src/checks/brand.ts:65-92` walks a `parse5` HTML fragment
and matches `tagName === 'script'`, attribute names `^on` and `href` values starting
`javascript:`.
- Opened directly at `/brand/mark-on-dark.svg`, the file is parsed as XML. Under XML parsing,
  `<s:script xmlns:s="http://www.w3.org/2000/svg">…</s:script>` is an SVG script element, but
  parse5 reports its tag name as `s:script`.
- `<set attributeName="href" to="javascript:…"/>` and `<animate … values="javascript:…">` put a
  `javascript:` URL on a link without any `href` attribute.
- `href="java&#9;script:…"` decodes to a value with a tab, which the `^\s*javascript:` test
  misses but the URL parser strips.
- `SpaHosting.cs:246-257` sends the CSP only with `index.html`; `brand/*` gets none. Such a file,
  copied from a design tool or a third party, therefore runs script on the app's origin when it is
  opened, and the build reports it clean.
- Fix:
  - match elements by local name (`tagName.split(':').pop()`), including `<script>` in any
    namespace;
  - refuse `set` and `animate` elements whose `attributeName` is `href` or `xlink:href`;
  - remove ASCII tab, newline and control characters from a URL before the `javascript:` test.
  - Add a case for each to `brand.spec.ts`.

**R2-3 (minor): the worker's "explicit" file lists are globs to `ngsw-config`, so a file name with
a regex character drops out of the worker or crashes the step.**
`client/projects/core/tellma-core-tools/src/output/worker-config.ts:107-115` writes each output
file into `resources.files` as-is. `ngsw-config` turns each entry into `new RegExp('^' +
globToRegex(entry) + '$')`, which escapes only `.`, `+`, `*` and `?`. It also reads a leading `!`
as a negation (`@angular/service-worker/fesm2022/config.mjs:44-84, 173-196`).
- Failure scenario: a distribution ships `public/icons/icon(1).png` or `public/legal/terms
  [2026].pdf`. The pattern no longer matches the file, so it ends up in neither group and is not
  available offline, and nothing reports it.
- A name with an unbalanced `(` or `[` makes `RegExp` throw, so `ngsw-config` exits non-zero and
  the build fails with "ngsw-config exited with code 1" and no hint why.
- Fix: backslash-escape `( ) [ ] { } ^ $ | \` in each entry; `globToRegex` passes a backslash
  through to the regex. Either handle a leading `!`, or report a name the worker cannot express
  as a problem. Add a case to `output.spec.ts`.

**R2-4 (minor): an angular.json with `outputPath.browser: ""` puts the source maps,
`stats.json` and `ngsw-config.json` inside the deployable output.**
`client/projects/core/tellma-core-tools/src/project/app-project.ts:119-150` accepts an empty
`browser` and sets `browserDir` to `outputDir`. `sourceMapsDir` (`<out>/sourcemaps`),
`statsFile` and `build.ts:211`'s `ngsw-config.json` then all sit inside the folder that is
deployed.
- Failure scenario: a distribution sets `"outputPath": { "base": "dist/acme", "browser": "" }`,
  a layout Angular supports. `tmMoveSourceMaps` moves the hidden maps to `browser/sourcemaps/`,
  so they are still deployed and served.
- `stats.json` and `ngsw-config.json` land in the worker's `shell` group, and the client
  prefetches them. The metafile leaks the module paths.
- Fix: refuse an empty `browser` with a `TmBuildFailure`, because the layout assumes the
  deployable output is a subfolder. Cover it in `app-project.spec.ts`.

**R2-5 (minor): on Windows, `serve` prints Node 24's DEP0190 warning every time it starts.**
`client/projects/core/tellma-core-tools/src/common/process.ts:48-53` spawns `pnpm` with
`shell: true` and an argument array. Node 24 deprecates this at runtime. I reproduced it with
Node 24.18.0:
`[DEP0190] DeprecationWarning: Passing args to a child process with shell option true can lead to
security vulnerabilities…`.
- Failure scenario: every `pnpm start` in the repository on Windows prints a security warning,
  which `serve.ts:147` triggers through `pnpm run assets:generate`. Developers learn to ignore
  warnings from the tool.
- Fix: for the shim case, spawn
  `process.env.ComSpec ?? 'cmd.exe'` with `['/d', '/s', '/c', command, ...args]` and no `shell`
  option. Alternatively, join the fixed arguments into one command string with no array.

**R2-6 (minor): `build` deletes and recreates `generated/root/` under a running `serve`.**
`client/projects/core/tellma-core-tools/src/output/root-files.ts:46-53`
(`rmSync(dir, { recursive: true })`, then a rewrite) runs on every `build` (`build.ts:170`) and
every `serve` (`serve.ts:184`). That folder is an asset input that `ng serve` watches.
- Failure scenario: a developer keeps `pnpm start` running and runs `pnpm build` in another
  terminal to check the production output. The dev server sees `tm-boot.js` and the brand files
  disappear, and a reload in that window gets a 404 boot script.
- On Windows, recreating a directory that another process still watches can fail with `EPERM`
  while the directory is pending deletion. That fails the build with a stack trace (exit 2).
- The content is almost always identical, so the delete gains nothing.
- Fix: refresh in place. Write each file only when its bytes differ, which is the Migrator's own
  rule, and remove only names that no longer belong.

**R2-10 (minor): two contract seams have no test that would fail if they broke.**
- The config check's warnings are never tested end to end. `label-missing` is the only
  `TmConfigProblem` warning (`tellma-core/config-check/src/tm-config-problem.ts:205`). No spec
  shows it printing while the build still passes. If `config-check.ts:81-87` or the runner turned
  every severity into `error`, or dropped warnings, every spec would still pass. Fix: add a
  `build.spec.ts` case that answers the runner with one `label-missing` warning, and assert that

  content", and no test catches it. Fix: assert the same two vectors in a C# test of
  `ContentHash.Of`.

### Responses

- R2-1: fixed in the "PC-073: review 2 fixes" commit (child of 9812a0e), per the orchestrator's
  ruling. A new rule in `TM_INDEX_HTML_RULES`, `base-href`, is checked first in both the source
  and the built file. It requires `<base href="/">` in the head before any element that carries
  a `src` or `href`. The first `<base>` with an href counts, and one that comes too late fails.
  `build` requires the element rather than injecting it, because `serve` needs it in the source
  too. The fixture's `index.html` now has it. `index-html.spec.ts` covers a missing base, a wrong
  href, a late base, a URL element before it, and a target-only base. `build.fixture.spec.ts`

  resolves from the root to a file in the output, `tm-boot.js` and `main-*.js` among them. The

  web-host bullet names the base element.

  without their namespace prefix, so `<s:script>` and `x:onload` are caught. It refuses `<set>`
