### Calendar verification (authoritative references)

- **Ethiopian**: compared with ICU's `ethiopic` calendar (Node 24, ICU 78.3) on **every day from
  the epoch AD 0008-08-27 to 9999-12-31**: 3,649,264 days, 0 mismatches. Appendix A's 12 vectors
  pass both ways; the epoch is JDN 1724221; leap rule; New Year rule 1900–2099; century shifts taken
  from ICU (1745→1752-09-09 … 2492→2499-09-15). One correction to the Appendix's prose: the
  "12 September before a Gregorian leap year" rule must count 2100 as leap (ICU: 1 Meskerem 2092 is
  2099-09-12); the test encodes divisibility by four.
- **Umm al-Qura**: .NET's `UmAlQuraCalendar` (the spec's mandate) vs ICU's `islamic-umalqura`:
  identical for AH 1420–1450 (1999–2029, the officially published span), but **35,920 of 64,850
  days differ by a day outside it** (AH 1318–1419 and 1451–1500). Published anchors pinned in tests
  all match .NET: Ramadan 1445 = 2024-03-11, 10 Dhu al-Hijjah 1445 = 2024-06-16, Eid al-Fitr 1446 =
  2025-03-30, Muharram 1447 = 2025-06-26, Ramadan 1447 = 2026-02-18, and the historical
  1 Muharram 1400 = 1979-11-20 (Grand Mosque seizure; ICU says 1979-11-21).
- **Tabular fallback**: .NET `HijriCalendar { HijriAdjustment = 0 }` vs ICU `islamic-tbla` on every
  day 1880–2100 outside the table: 0 mismatches. At AH 1500/1501 the tabular calendar's 1501-01-01
  falls on the table's last day, so the day after the table is 1501-01-02 (no repeated day; TryParse
  refuses `1501-01-01` by its round-trip check). Before AH 1318 the two meet without a gap.
- All 398 calendar tests also pass in `mcr.microsoft.com/dotnet/sdk:10.0` (Ubuntu 24.04, libicu 74).

### Deviations (also in the commit message)

1. Goldens run over **pinned cultures** (en-GB, ar-SA, am-ET clones whose Gregorian formats are
   fixed to .NET 10 + ICU 74 values). Host ICU differs between Windows and Ubuntu (en-GB full date
   comma; am-ET Gregorian month spellings), so exact strings over host cultures cannot be green on
   both. Host cultures (31 of them) get property tests instead, plus a Gregorian oracle against the
   framework's own `ToString`.
2. Month-name **values** ship now (en, ar, am) rather than keys only; PC-022 extends the files.
   `MonthName(…, abbreviated: true)` for `uq`/`et` returns the one resource name per month (CLDR's
   abbreviated names are equal to it in ar/am, or English stand-ins).
3. Rendering details the spec leaves open: years always in full (four digits, never `yy`); the era
   token dropped; bidi controls removed and NBSP/NNBSP/thin spaces made plain; `Long` = the
   culture's long date without its weekday and joining punctuation, `Medium` = `Long` with the
   month abbreviated, `Full` = the long date (a weekday is prefixed when the culture's lacks one);
   date and time joined by one space; a date a calendar cannot represent (before AH 1, before the
   Ethiopian epoch) **renders in ISO `yyyy-MM-dd`** instead of throwing (Decompose still throws).
4. Gregorian names/patterns are read from a private DTFI clone switched to the culture's optional
   `GregorianCalendar` (ar-SA's own is Umm al-Qura). §8.1's "never assigned to a
   DateTimeFormatInfo" is about the rendered calendar; this is the same move §9.2 makes.
5. `TryParse`: any script's decimal digits, any non-letter separators, year in exactly four digits,
   ISO order when it reads `yyyy-MM-dd`, else the culture's order; a result only when it decomposes
   back to the same numbers.
6. `TenantSettings`: added `ReportProblem` (`Action<string, SettingEntryProblem>`) and the enum,
   because Abstractions cannot log: the loader binds it to `SettingsEntryInvalid` /
   `SettingsSecretUnreadable` and the counter. Non-nullable members are `required`; a private copy
   constructor gives `with` copies an empty memo; equality excludes the memo. `Unprotect` may return
   null or throw `CryptographicException`.
7. `SettingKey`: added `DeriveGroup`, `LabelKeyPrefix`, `MaxNameLength`, `MaxGroupLength`;
   `SettingKey<T>` adds `TypeInfo` and `TryRead` (null reads only for a null default). The constructor
   validates only a blank name; every grammar rule is the startup gate's (a static initializer must
   not throw).
8. Small hardening: `ToWire` refuses a format version below 1; `ForEntity` refuses blank or >128;
   `VersionTagSnapshot` copies its tags; `CacheOptions.SectionPath`; `CalendarCodes.MaxLength`.
9. `CachedEntitySet<T>` / `ICacheableEntities` constrain `T : class` until 0012's entity base
   exists (the cacheable checkpoint may tighten to `TopLevelEntity<int>`).
10. The calendar contribution item, its sugar and realizer, and CoreFeature's registrations land
    here (0011 §2.2 says "realised by spec 0013"; no checkpoint listed them). `CalendarRegistry`
    keeps the first system per code (ignoring case) and skips blank codes; the §1.3 calendar startup

11. Contracts added beyond the listed sections, per "all Abstractions-level contracts":

### Open risks and seams

- **uq client/server disagreement**: the SPA renders Umm al-Qura through the browser's ICU, which
  differs from .NET's table by a day on most dates before 1999 and after 2029. Spec 0013 mandates
  .NET; spec 0010 Part D/F (client and Queryex `core.CalendarMonths` from .NET) will disagree with
  the browser there. Needs an orchestrator ruling (e.g. ship .NET's month table to the client).
- **Host-ICU-dependent server text**: Gregorian names and patterns come from the host's ICU, so the
  same email can render differently on Windows and Linux hosts. If host independence is wanted,
  PC-019's negotiated culture clone is the place to pin CLDR data; the calendar systems read
  whatever the culture carries.
- `CacheOptions` is not bound yet (the cache runtime binds `Tellma:Cache`).
- The DTO shape-snapshot test of §2.7 is not here (not in this checkpoint's test list).

### Findings

Scope checked: every type the checkpoint lists against spec 0013 §1.1, §2.2, §2.9, §3.1, §4.3,
§5.3, §5.6, §7.1, §8, §9.2, §10.1, §10.4, §11 and Appendix A, and against the members other specs
use (0011 §2.2 and §4.1, 0012, 0014 §6.2-§6.3, 0019 §3.2, 0033); the 12 listed deviations; the
D-029 rulings. Everything not listed below checks out. The details:

- **Ethiopian calendar.** It matches Node 24's ICU 78.3 `ethiopic` calendar on every anchor I
  probed, both ways: the epoch (0008-08-27 is 1-01-01, the day before is out of range), 1752-09-08
  and 09-09, 2099-09-11 and 09-12, 2100-09-11 and 09-12, 2499-09-14 and 09-15, 2500-01-01, and
  9999-12-31 (9992-02-21). The `FromDayNumber` and `ToDayNumber` arithmetic is right by hand too:
  `y / 4` counts the leap years before year `y`, and the 1,461-day cycle closes on the leap day.
- **The Appendix A 2099 claim.** The implementer is right. 1 Meskerem 2092 is 2099-09-12, because
  Ethiopian 2091 is a leap year and 2100 is a Julian leap year. The prose rule would give
  2099-09-11. D-029 records this.
- **The framework calendar's arithmetic.** I probed it on the real type: Pagume 6 plus one year
  clamps to Pagume 5, plus one month gives Meskerem 6, Nehase 30 plus one month gives Pagume 5,
  and stepping back from year 1 throws.
- **Umm al-Qura and the tabular fallback.** The bounds, the tabular calendar's 1317 having 29 days
  in Dhu al-Hijjah, the seamless join at 1900-04-29/30, the skipped tabular 1501-01-01 and its
  refusal by `TryParse`, and the AH 1 floor all hold, on Windows and in
  `mcr.microsoft.com/dotnet/sdk:10.0` (libicu 74). Beyond the table, .NET's `HijriCalendar` with
  adjustment 0 equals ICU's `islamic-tbla` at every boundary I probed, not `islamic-civil`.
- **Rendering in the catalogue's languages.** Rendering in every predefined culture of the 15
  catalogue languages is clean on both ICUs: no leading or trailing joiner, no weekday left in
  `Long`, ASCII digits, no bidi controls.
- **The contracts.** `VersionTag`'s wire form and `None`, the ordinal frozen copy in
  `VersionTagSnapshot`, `CacheOptions`' limits and its default-to-ceiling rule, `StaleContextException`
  in the closed set (README updated), the calendar realizer's dedup and validation, and
  `TenantSettings`' copy constructor and memo-free equality are all sound. So is its secret path:
  read once, null or `CryptographicException` reported as unreadable, decrypted JSON of the wrong
  type reported as invalid.
- **D-029.** Nothing here blocks either ruling. See the end of this section.

**Minor**

- **R1-1 — `TryParse` does not invert `Format(…, Short)` when the culture's short pattern carries
  letters.** Location: `src/core/Tellma.Core/Calendars/CalendarFormatter.cs:128-132` (any letter
  refuses the text) with `DatePattern.ToNumeric` (`DatePattern.cs:147-152`), which keeps literal
  text.
  - *Scenario:* `bg`/`bg-BG` render Short as `5.03.2026 г.` in all three calendars, on Windows and
    on libicu 74. `TryParse` of that text returns null. I swept every culture on both hosts, and
    these are the only two that fail. None is a catalogue language, but `AddLanguage` can add one.
    Spec 0019 §3.2's Ethiopian text round trip relies on this inverse.
  - *Fix:* let `TryParse` skip the Short pattern's own literal text before refusing letters, or have
    `ToNumeric` drop letter-bearing literals, so Short renders `5.03.2026`. Then widen
    `The_numeric_style_reads_back_in_every_calendar` from the 31 host cultures to every predefined
    culture. It runs in well under a second per calendar.
- **R1-2 — A date before a calendar's epoch renders as ISO Gregorian, and `TryParse` reads that text
  back as a different date in the calendar.** Location: `CalendarFormatter.cs:35-37` (the ISO
  fallback) and `:154-157` (ISO order).
  - *Scenario:* `uq.Format(0600-01-01, …, Short)` is `0600-01-01`, and `uq.TryParse` of it is AH
    600-01-01, which is 1203-09-16. `et` turns 0005-01-01 into 0012-08-27. The round trip silently
    changes the date instead of failing.
  - *Fix:* make the fallback text unreadable as this calendar's numeric form, so it fails safe. For
    example, add a Gregorian marker such as an era or a `gc` suffix. Alternatively, state in
    `ICalendarSystem.TryParse`'s remarks that a pre-epoch rendering does not read back. Add a test
    that the fallback text does not parse to another date.
- **R1-3 — `TryParse` ignores text before the first digit group and after the last.** Location:
  `CalendarFormatter.cs:118-146`. A separator is only recorded between groups, so a leading or
  trailing run is dropped.
  - *Scenario:* in en-GB, `-05/01/2024`, `+05/01/2024`, `2024-01-05-` and `(05)/(01)/(2024)` all read
    as 5 January 2024. A spreadsheet cell holding a negative or annotated number becomes a date
    instead of `Excel.Import.InvalidCell`.
  - *Fix:* allow only whitespace (and the already-skipped bidi controls) outside the three groups.
    Keep the deliberate leniency between groups. Add these inputs to
    `Text_that_is_not_a_numeric_date_of_the_calendar_does_not_read`.
- **R1-4 — `WithoutWeekday` leaves the weekday's joining punctuation when that literal also holds
  letters.** Location: `src/core/Tellma.Core/Calendars/DatePattern.cs:156-178` and `IsJoiner`
  (`:298-302`), which requires the whole literal to be punctuation or space.
  - *Scenario:* this affects Long and Medium, and Full keeps its weekday:
    - a trailing comma: `lt-LT` `2026 m. kovo 5 d.,`, `eu-ES` `2026(e)ko martxoaren 5(a),`,
      `tt-RU` `5 март, 2026 ел,`, `sah-RU`;
    - a leading `, `: `rm-CH` `, ils 5 da mars 2026`, `ksh-DE`, `dz-BT`, `nnh-CM`, and `eo-001` on
      Linux.
    None is a catalogue language.
  - *Fix:* when the adjacent literal is not a pure joiner, trim the joining run (whitespace and
    comma-like punctuation, not `.` or closing brackets) from the edge that touched the weekday:
    `d., ` becomes `d.`. Add a property test over every predefined culture: Long neither starts
    nor ends with a comma-like character.
- **R1-5 — `UmAlQuraCalendarSystem.Calendar` covers only the table, while every other member works
  beyond it.** Location: `src/core/Tellma.Core/Calendars/UmAlQuraCalendarSystem.cs:41`. It inherits
  the interface's "A framework calendar for date arithmetic in this system".
  - *Scenario:* `Decompose`, `Format` and `TryParse` accept 1890-01-01 and 2078-01-01 through the
    tabular calendar. A consumer doing arithmetic in the same system gets
    `ArgumentOutOfRangeException`: `system.Calendar.GetYear(1890-01-01)`, or `AddMonths` from AH
    1500-12. Spec 0033's month buckets and spec 0019's text dates are such consumers.
  - *Fix:* document on the property that arithmetic is exact-range only and that callers beyond
    `MinSupported`/`MaxSupported` use `Decompose`. Or expose a composite `Calendar` with the
    table-then-tabular rule `Decompose` uses, skipped 1501-01-01 included.
- **R1-6 — `EthiopianCalendar` inherits the base `TwoDigitYearMax` of -1.** Location:
  `src/core/Tellma.Core/Calendars/EthiopianCalendar.cs:21-51`, which has no override.
  - *Scenario:* through the public `ICalendarSystem.Calendar`, `TwoDigitYearMax` is `-1` and
    `ToFourDigitYear(15)` returns `-85`. Every BCL calendar overrides both.
  - *Fix:* override `TwoDigitYearMax` with a sensible default and a setter, as the BCL calendars
    do. One choice is the Ethiopian year of Gregorian 2049, which is 2041. Pin it in
    `The_framework_calendar_answers_its_structure`.
- **R1-7 — Array-typed setting values are handed out shared and mutable.** Location:
  `src/core/Tellma.Core.Abstractions/Settings/TenantSettings.cs:124-141` (the memoised `StrongBox<T>`),
  and `key.DefaultValue` returned as is.
  - *Scenario:* spec 0013 §5.3 admits array forms (`int[]`, `string[]`, enum arrays). `Get<T>`
    returns the same array instance to every request of the tenant, because the `TenantSettings`
    is process-wide. One caller that sorts or edits it changes the setting for every request until
    the next `settings` bump. Spec 0013 §3.2 says shared cached values are immutable by
    construction.
  - *Fix:* return a copy when `T` is an array, for both stored and default values (setting arrays
    are small). Or ask the orchestrator to change the admitted forms to `ImmutableArray<T>`.
    Add a test that mutating a returned array does not change the next `Get`.
- **R1-8 — No non-generic way to read or check a stored value against a `SettingKey`.** Location:
  `src/core/Tellma.Core.Abstractions/Settings/SettingKey.cs:38-144`. Only `SettingKey<T>.TryRead`
  and `TenantSettings.Get<T>` exist.
  - *Scenario:* the loader holds `ISettingKeyRegistry.Keys` as `IReadOnlyList<SettingKey>` and
    must still:
    - parse every non-`Secret` entry at load and log `SettingsEntryInvalid` (spec 0013 §5.7,
      §5.3);
    - build `TenantSettingsForClient` with Client entries "stored or default" (§5.6), so an
      invalid stored value is replaced by the default.
    Today it can do that only through `MakeGenericMethod`.
  - *Fix:* add an abstract non-generic member now, such as
    `bool TryReadValue(JsonElement json, out object? value)`, which applies `Validate` too. It is
    safe because the `private protected` constructor admits no outside subclass. Adding it here
    is cheaper than a later Abstractions change, which makes every integration suite touched
    again.

**D-029 (nothing blocks the rulings):**

- **The client's Umm al-Qura month-start table.** It is easy to generate:
  `UmAlQuraCalendarSystem.Calendar` (or the BCL `UmAlQuraCalendar`) gives every month start for

- **Host-independent server text.** `CalendarCultureData` takes the culture's DTFI as is, with no
