### Deviations

1. **The kind grammar also refuses the Windows device names** (`con`, `prn`, `aux`, `nul`,
   `com0`–`com9`, `lpt0`–`lpt9`). The file-system store makes each kind a directory, and Windows
   reserves those names in every directory. No kind any spec names is affected.
2. **The Windows root cap is 153, not 160.** The deepest object path is root + 106 characters
   (`\t2147483647\` + a 40-character kind + `\xx\` + a 32-character key + `.` + a 16-character
   variant); staying within 259 (MAX_PATH less its terminator) allows 153. A test pins the
   arithmetic.
3. **Read streams share `FileShare.Read | FileShare.Delete`** (spec: `FileShare.Read`), so the sweep
   can delete an object on Windows while a download of it is still streaming; the open handle keeps
   reading to the end.
4. **A write's content must yield exactly its declared length**; fewer or more bytes fail the write
   with `BlobStoreException` and leave no object (contract addition, pinned by the conformance
   suite), so a row's `Size` can never disagree with its bytes.
5. **Listing prefixes are whole segments**, validated by a new `BlobName.IsValidPrefix` (a kind, or
   a kind and a two-digit fan-out segment); a kind never lists a longer kind that starts with it,
   and entries come in ordinal name order (Azure's order). Also new on `BlobName`: `IsValidKey`,
   `IsValidPrimary` and the length constants. The Azure adapter must list `prefix + "/"`.
6. **Content sniffing is broader than §3.3's minimum**: HTML is any WHATWG MIME-sniffing HTML
   signature (`<head`, `<script`, `<iframe`, `<body`, `<p`, `<br`, a leading comment, …), not only
   `<!DOCTYPE html`/`<html`, with a tag-name terminator rule so `<brand>` is text; markup is
   recognised behind a UTF-8 BOM and in BOM-marked UTF-16; SVG is also caught behind a leading
   `<!doctype`; the Mach-O universal container (`CA FE BA BE`, which Java class files share) counts
   as an executable; zip archives are recognised by all three `PK` record signatures.
7. **The file-name sanitiser also** replaces bidirectional controls (U+200E/F, U+061C,
   U+202A–202E, U+2066–2069) and unpaired surrogates, normalises to NFC, and **shortens** a name
   over 255 characters (keeping an extension of up to 16 characters, never splitting a text
   element) rather than refusing it: §8.2 has no error code for a long name, and the service is
   also called by jobs.
8. **Options validation runs on first resolution** (an `IValidateOptions` plus the same rules in the
   store constructor), not through a startup check: the `blobs` startup check belongs to the
   kind-registry checkpoint, which can call `FileSystemBlobStoreOptionsValidator.Describe` or resolve
   the options and collect the `OptionsValidationException`. The "`.tmp` crosses a volume" rule needs
   no check: `.tmp` sits inside the tenant directory by construction, so only a mount point inside a
   tenant directory could split them.
9. **The resolved root is logged when the store is created** (`BlobFileSystemRoot`), which is the
   first resolution of the singleton rather than host start; once the `blobs` check resolves the
   store, that is startup.
10. **Two log events beyond §10.2**: `BlobFileSystemRoot` (Information) and
    `BlobTenantMissingOnWrite` (Warning, a write that found the tenant directory missing).
11. **Additions to the contract types**: `BlobContentTypes`, `BlobTelemetryTagValues`, the unit
    constants on `BlobTelemetryNames`, `ThumbnailPolicy.VariantName`,
    `ImagePolicy.DefaultMaxInputPixels`, `BlobKindPolicy.For(BlobPreset)`,
    `BlobReferenceAttribute.CreatePolicy()`, and `ImageRejectedException`'s reason constants and
    its refusal of a missing `reason`.
12. *(Withdrawn after Review 1, R1-1: the declaration now only narrows.)* **`BlobReferenceAttribute.MaxSizeBytes` replaces the preset's size when above 0** (§2.3 says
    "narrows"). Clamping a larger value to the preset's would be a silent clamp; replacing honours
    the declaration, and §9's `MaxUploadSize` rule still bounds it. Reported to the orchestrator.

### Open risks

- **Durability of the rename.** The part file is flushed to the device before the move, but the
  directory entry is not fsynced (.NET has no API for it). After a power loss on Linux a just-moved
  object may revert to its `.part` file: the purge removes it and the row's `GET` answers 404. A
  blob store on a journalling file system makes this unlikely, not impossible.
- **Symlinks inside the root** are not detected: the containment check is lexical. An operator who
  plants a link under a tenant directory can redirect reads; the grammar keeps a client from doing
  so.
- **Purge vs. a long write**: a `.part` older than the cut-off (24 h) is assumed abandoned; on
  Windows an in-flight one cannot be deleted anyway (`FileShare.None`), which the purge reports as a
  failure.

## Review 1

Scope: commit e1133a6 only. Verified locally (Windows): `dotnet build Tellma.slnx` printed Build
succeeded with 0 warnings; `dotnet format --verify-no-changes` reported nothing; `Tellma.Core.Tests`
under the unit filter: 460 passed. The integration
suites were not re-run, because the change adds only new types. A Linux probe ran in
`mcr.microsoft.com/dotnet/sdk:10.0` (R1-2).

Deviations 1–11 check out. The 106-character depth and 153 + 106 = 259 are correct, the deepest
directory (root + 56) stays under CreateDirectory's 248, and `.tmp` paths reach root + 54.
FileShare.Delete is tested. The exact-length rule is pinned by conformance. Whole-segment prefixes
are pinned by conformance, including the longer-kind case. The broader HTML set and the sanitiser
additions are reasonable. Deviation 12 is rejected (R1-1, D-022).

The grammar is sound against traversal. It admits only `[a-z0-9-]`, one `.` and exactly two `/`.
That rules out `..`, rooted names, drive letters, UNC, `:`/ADS, trailing dot or space (a variant
cannot be empty), `~` 8.3 aliases, non-ASCII and case collisions. Device names are refused as
kinds; fan-out, key and variant cannot spell one. `ResolveContainedPath` is a sound lexical
backstop.

### Findings

**R1-1 (major) — `MaxSizeBytes` widens the preset instead of narrowing it.**
`src/core/Tellma.Core.Abstractions/Entities/BlobReferenceAttribute.cs:39-44` (doc) and `:68`
(`MaxSize = MaxSizeBytes > 0 ? MaxSizeBytes : preset.MaxSize`).
Spec §2.3 says MaxSizeBytes "narrows" MaxSize; §3.5 says "narrowed by `[BlobReference].MaxSizeBytes`";
§9 says "after narrowing". No spec rule supports widening.
Failure scenario: `[BlobReference("x", BlobPreset.Signature, MaxSizeBytes = 100L << 20)]`
silently produces a 100 MiB image kind. Image kinds are buffered whole in memory (§3.2 step 3,
"bounded by the policy's MaxSize"), so a declaration loosens an upload security limit.
The code also contradicts itself: `BlobKindPolicy.cs:17-19` says "narrowed by the attribute".
`BlobKindPolicyTests.cs:145` only tries a smaller value, so no test notices.
Fix (D-022):
- Keep min(attribute, preset).
- Refuse a larger value instead of clamping it: `CreatePolicy()` throws `InvalidOperationException`
  naming the kind, the declared value and the preset's limit, as the negative case does. The `blobs`
  startup check later reports it as a composition problem.
- Rewrite the XML doc to say "narrows".
- Rename the test, and add a case where a value larger than the preset is refused and one where a
  value equal to the preset is kept.
- Drop deviation 12.

**R1-2 (major) — Create-only is not atomic on Linux: a concurrent write of the same name silently
overwrites.**
`src/core/Tellma.Core/Blobs/FileSystemBlobStore.cs:526-580`.
On Unix, .NET 10's `File.Move(src, dest, overwrite: false)` runs `lstat(dest)` and, when dest is
absent, `rename(2)`. `rename` replaces an existing destination, so two moves racing to one name can
both pass the `lstat` and both succeed. link/unlink is only the fallback.
Measured with a scratch probe of two threads behind a barrier, 2000 trials:
- Windows: 0 trials where both moves succeeded.
- `dotnet/sdk:10.0` Linux container: 1313 of 2000 trials where both succeeded.

So on Linux the later writer replaces the bytes of an object the contract calls immutable. That
object is served `immutable`, and its row's `Size`/`Sha256` describe the first writer's bytes.
Neither writer gets `BlobAlreadyExistsException`. Two writers of one name can come from a replayed
or retried write, a key-generation bug, or two processes on one root (web and job host), and this is
exactly what create-only defends against.
The comments at `:526` ("the move below stays the authority") and `:575-579` are wrong on Linux.
Fix:
- On non-Windows, publish with `link(2)` (P/Invoke libc). `EEXIST` maps to
  `BlobAlreadyExistsException`; then delete the part file. Alternatively use `renameat2(...,
  RENAME_NOREPLACE)` with `link` as the fallback.
- Keep `File.Move(overwrite: false)` on Windows, where it is atomic.
- Cover it with the race case of R1-3.

**R1-3 (major) — The conformance suite never races two writes of one name, so it does not
constrain create-only.**
`src/core/Tellma.Core.Testing/Blobs/BlobStoreConformanceTests.cs:139-168` tests only a sequential
second write.
Failure scenario: an Azure adapter that checks `ExistsAsync` and then uploads with overwrite, with
no `IfNoneMatch = ETag.All`, passes every case. So does the Linux file-system store of R1-2.
In the file-system store, the move-time conflict branch (`FileSystemBlobStore.cs:575-579`) is
reached by no test, because the up-front `File.Exists` check always answers first. Changing
`overwrite: false` to `true` would fail no test.
Fix:
- Add a conformance case that writes one name from N tasks (for example 8, behind a barrier,
  repeated a few rounds) with distinct bytes. Assert that exactly one completes, every other throws
  `BlobAlreadyExistsException` with that name, the read-back equals the winner's bytes, and no
  incomplete artefacts remain.
- Add a file-system test that reaches the move-time branch: a content stream that blocks until a
  second write of the same name has completed.

**R1-4 (minor) — Invisible bidirectional characters are written literally in source.**
`src/core/Tellma.Core/Blobs/BlobFileNames.cs:87-89`. The char literals are raw U+200E, U+200F,
U+061C, U+202A, U+202E, U+2066 and U+2069 (confirmed with `od`).
Failure scenario: this is the Trojan Source pattern. A reviewer cannot see which range is tested,
editors and diff viewers reorder the rest of the line after U+202E, and GitHub flags the file as
containing hidden bidirectional text. An edit to these lines cannot be reviewed.
Fix: write them as escapes, `'‎'`, `'‏'`, `'؜'`, `'‪'`…`'‮'`,
`'⁦'`…`'⁩'`, as `BlobFileNamesTests` already does.

**R1-5 (minor) — The sanitiser lets line and paragraph separators through.**
`src/core/Tellma.Core/Blobs/BlobFileNames.cs:79-90`. U+2028 and U+2029 (categories Zl and Zp) are
not `char.IsControl`, so they survive.
Failure scenario: `"a b.pdf"` is kept as is and breaks the display name across lines in grids,
logs and the `Content-Disposition` fallback. It is the same class of display spoofing the bidi rule
exists for.
Fix: also replace `UnicodeCategory.LineSeparator` and `ParagraphSeparator`, and add them to the test
data. Do not widen this to all of category Cf: ZWJ and ZWNJ are needed by emoji sequences and
Persian.

**R1-6 (minor) — The "second failure throws" rule of the lazy retry has no test.**
`src/core/Tellma.Core/Blobs/FileSystemBlobStore.cs:542-557`. The spec (§6.1) says a missing tenant
directory is created once and the write retried once, and a second failure throws. Only the
successful retry is pinned (conformance `A_write_into_a_tenant_whose_storage_was_removed…`).
Failure scenario: a retry loop, a swallowed second failure, or a leaked part file on that path would
go unnoticed.
Fix: add a file-system test that makes the ensure fail. For example, remove the tenant directory,
then create `t{id}` with a regular file named `.tmp`. Assert that the write throws
`BlobStoreException`, logs `BlobTenantMissingOnWrite` once, and leaves no object.

### Responses

- R1-1: fixed in {SHA}. `CreatePolicy()` keeps a `MaxSizeBytes` at or below the preset's limit
  (0 keeps the preset's) and throws `InvalidOperationException` naming the kind, the declared value
  and the preset's limit when it is above; the XML doc says "narrows" and points to a composition
  transform for raising a limit. Tests: renamed `A_declared_size_narrows_the_presets_…`, added
  `A_declared_size_equal_to_the_presets_is_kept` and `A_declared_size_above_the_presets_is_refused`.
  Deviation 12 is dropped.
- R1-2: fixed in {SHA}. On Unix the publish is `link(2)` through a `[LibraryImport("libc")]`
  P/Invoke (`UnixHardLinks`): `EEXIST` becomes `BlobAlreadyExistsException`; then the part file is
  unlinked, and a failed unlink is logged (`BlobPartFileLeft`) and left for the purge, not reported
  to the writer. `EPERM`, `EXDEV` and the platform's `ENOTSUP`/`EOPNOTSUPP`/`ENOSYS` fail closed
  with a `BlobStoreException` that names the root; any other errno fails too, and there is no
  rename fallback. Windows keeps `File.Move(overwrite: false)`.
  `FileSystemBlobStore.ProbeCreateOnlyPublish(root)` hard-links a probe file under the root (Unix
  only) and returns the problem or null. The store runs it before its first `EnsureTenantAsync` or
  `WriteAsync`, caches only a success, and logs `BlobPublishUnsupported` on a failure; the `blobs`
  startup check will call the same method. The probe is not in options validation: validation also
  runs when the Development default resolves, and probing there would create directories under the
  developer's local application data folder from mere option resolution. Both comments are
  corrected, and the class remarks and README now explain the publish. `Tellma.Core` sets
  `AllowUnsafeBlocks` for the generated marshalling.
- R1-3: fixed in {SHA}. New conformance case
  `Concurrent_writers_of_one_name_leave_exactly_one_winner`: 8 writers behind a gate, 5 rounds,
  distinct bytes. Exactly one succeeds, the rest throw `BlobAlreadyExistsException` with the name,
  the read-back is the winner's bytes, and no incomplete artefacts remain. New file-system case
  `A_writer_that_loses_the_race_after_the_early_check_is_refused_by_the_publish`: a gated content
  stream holds a writer inside its copy, after the early check, while a second writer publishes.
  The first must then be refused at publish time, and the second's bytes remain. That case fails
  with `overwrite: true` or a plain rename. Linux run: the slot's tracked and untracked files (`git ls-files -co --exclude-standard`), copied
  to a scratch folder and mounted into `mcr.microsoft.com/dotnet/sdk:10.0` (SDK 10.0.400), running
  `dotnet test test/core/Tellma.Core.Tests --filter FullyQualifiedName~Blobs`: 341 passed, 1 skipped
  (the Windows-only drive-relative case). Control run: with the Unix publish swapped back to
  `File.Move(overwrite: false)`, the concurrent-writers case fails on Linux. The publish-time file-system case
  still passes, because the move's own existence check sees the already-published name; the
  concurrent case is what tells the rename from the link apart.
- R1-4: fixed in {SHA}. The bidirectional characters are written as `\u` escapes. A scan of every
  new source file finds no raw U+200B–U+200F, U+061C, U+2028/9, U+202A–U+202E, U+2066–U+2069 or
  U+FEFF.
- R1-5: fixed in {SHA}. `UnicodeCategory.LineSeparator` and `ParagraphSeparator` are replaced, and
  tests cover U+2028 and U+2029. ZWJ and ZWNJ are kept, pinned by a Persian name with ZWNJ and a
  ZWJ emoji family.
- R1-6: fixed in {SHA}. `A_write_whose_lazy_ensure_fails_throws_once_and_leaves_nothing`: a
  regular file sits where `t{id}/.tmp` belongs. The write throws `BlobStoreException`, logs
  `BlobTenantMissingOnWrite` exactly once, leaves no object, and does not retry again.
