# PC-177: Import semantics and the synchronous import

## Implementer notes

### What was built

- **The parse** (`src/core/Tellma.Core/Excel/ImportParser.cs`, `ImportDecoders.cs`, `ImportKeys.cs`, `ImportModel.cs`):
  - `ImportParser` reads every mapped sheet once, forward only, after `ImportMapper` has bound it. Each mapped cell is decoded by its mapped type through `ImportDecoders` and the cell codec: scalars, multilingual slots, value sets, calendars, references by natural key, and parent links.
  - Every cell error is collected across the file before anything reaches the database, sorted in tab, row and column order, and capped at `MaxReportedErrors` with the uncapped `TotalErrors`.
  - In-file checks:
    - uniqueness of row keys and `[Unique]` values (`DuplicateRowKey`);
    - links by `Id` at every depth (negative, duplicate and blank ids);
    - `OrphanChildRow` and `OwnerSheetAbsent`;
    - per-owner `TooManyChildren` at every depth, and `TooManyDescendants` against the stack's save ceiling;
    - `ReferenceAmbiguous` when one key value is given in two spellings;
    - `KeyTooLong` against the restriction TVP's column.
  - The synchronous path counts rows while reading, never trusting the sheet's dimension or the plan (D-236). It refuses beyond `MaxSynchronousImportRows`, or beyond the byte limits, as `TooLargeForSynchronous` before decoding further.
- **The session** (`ImportSession.cs`, `ImportSession.Resolve.cs`, `ExcelImportSession.cs`, `ExcelChunk.cs`):
  - Parents are ordered before the new rows that name them (Kahn), over the tree's parent and every self-reference. A cycle among new rows is `ParentCycle` at each row on it (Tarjan); rows outside the cycle are not flagged.
  - `OrderHash` is SHA-256 over the ordered rows' canonical content, so a background import can pin its chunks; a column read in another language changes it.
  - `LookupsFor(from, to)` builds one `ExcelQuery` per referenced entity and key, each restricted through `KeySetRestriction` ("@keys"). It covers natural-key references and natural row keys, minus what the chunk itself or `committedNewIds` binds.
  - `HydrationIds` lists the stored rows the chunk updates.
  - `Resolve(from, to, lookups, hydrated, committedNewIds)` works on each row in turn:
    - It overlays each row on a copy of its stored row.
    - It refuses a changed write-once value (`WriteOnceChanged`).
    - It matches child rows by id, then by natural key, else replaces the stored collection. Only a replacement over stored rows demands every column and descendant sheet (`IncompleteChildSheet`, once per collection).
    - It assigns temporary negative ids and binds in-chunk references, child references included, in the session's order.
    - It returns the `CoordinateMap` from every entity path back to its sheet, row and column.
  - `LaterReferencedIds` and `ReferencedFrom` serve the background import's chunking.
- **The synchronous import** (`ExcelImports.ImportAsync`, `ExcelOperations.ImportAsync`):
  - `import` is an `[ApiAction]` under the stack's `Save`: a long mutation with the import rate policy. It runs in one transaction in this order:
    1. the upload's read;
    2. the parse;
    3. one batch of every lookup through `ExcelRowSource(new ExportSource.All()).ReadAsync`, under the caller's read filter;
    4. one `GetByIdsAsync` hydration at every depth (`IStackExcelRows.HydrateAsync`);
    5. `Resolve`;
    6. the stack's own save with `Source = SaveSource.Import`, `Concurrency = Check`, `ReturnEntities = false` and `Details = None` (`IStackExcelRows.SaveImportAsync`).
  - A `ConcurrencyException` is retried up to `ImportConcurrencyRetries` times when no conflicting row was stamped by the file and none is missing. Each retry re-hydrates the conflicting ids and resolves again; every retry counts in `tellma.excel.import.retries` and is logged.
  - Errors are translated through the coordinate map:
    - a `ValidationException`'s errors go to their cells;
    - a `ConfirmationRequiredException` becomes one error per key and row, with the validator's arguments plus `confirmable = true`;
    - a conflict lands at the `Stamp` cell when the file gave the stamp, else at the row, and a missing row is `RowNotFound`;
    - `NotFoundException` of the stack's own resource becomes `RowNotFound`;
    - `ForbiddenException` passes through unchanged.
  - The outcome holds the inserted and updated counts at the root and children's depths, one `RowRange` over the sheet rows, and the session's warnings.
  - Instruments: rows, duration and lookups histograms, an errors counter and a retries counter, all tagged by entity, mode and synchronous/background. There are log events for completion, refusal and chunk retry.
- **Strings**: `Action_Import`, the request's new field labels (`Mode`, `RowKey`, `IgnoreUnmappedColumns`, `IgnoreSheetStamps`) and every import error this checkpoint raises, in English and Arabic. `TooLargeForSynchronous` names the `import/start` route.
- **Enum naming** (`Localization/NamedEnums.cs`): an action site now counts toward an enum's home schema only when the stack's entity is declared in the enum's assembly too. See deviation 14.
- **Conformance** (`Tellma.Core.Testing/Crud/StackConformanceTests*.cs`, D-131):
  - `import` is driven in the reachability case, where a missing upload is not found, and in the securables case.
  - A budget row covers a warm import updating the two rows by id: `1 + (lookups ? 1 : 0) + 1 + 2 + DependentValidationRounds` round trips, i.e. the upload, the lookups, the hydration, then the save's two and its dependent validation rounds (§1.4's `1 + L + H + 2`).

### Deviations

1. `IExcelImporter.ParseAsync` takes the stack's `StackLimits`, a `synchronous` flag and a `CancellationToken` beyond §10.4. The descendant cap needs the save ceiling, the synchronous path needs its row limit, and the parse needs cancellation.
2. `ExcelCell.Column` is nullable. A row-level error, such as a conflict on a row the file did not stamp, has no column.
3. `ImportPaths` does not accept a reference's natural key whose CLR type `KeySetRestriction` cannot carry. The path does not resolve, instead of failing at the lookup.
4. A blank cell in a non-nullable value-type column is the codec's `Required` at the cell, not a silent default.
5. A boolean text cell decodes only through the codec's invariant words; a real Excel boolean is always read. The server has no localized boolean labels to read.
6. An unmapped `RowKey` is a `BadRequest` of the request, not a per-row error.
7. `ReferenceAmbiguous` is raised at parse when one file spells one key value two ways, as well as at resolution.
8. Two file rows resolving to one stored row are a `DuplicateRowKey` at both rows. This covers a copied row with a stale id.
9. `IncompleteChildSheet` is raised only when a collection is replaced over stored rows. A collection matched by id keeps its absent descendants untouched.
10. In-chunk binding extends to child rows' references to new parent rows. A child sheet's references to the stack add no ordering edges, because children save with their owner.
11. `TooLargeForSynchronous` raised by a byte limit still reports the declared rows with the bytes.
12. `ReferenceNotFound` always carries `collation` (true/false), so the ICU message selects on it.
13. A confirmation's ids are mapped back to rows through the ids the pipeline assigned before its validators ran, not only the temporary ids.
14. `NamedEnums`: a platform action's arguments (here `ImportRequest.Mode`) count toward an enum's home schema only on a stack over an entity of the enum's own assembly. Otherwise `core.ImportMode` became `acme.ImportMode` in Acme, which is the composition-dependent naming R1-1 of PC-086 forbade. The Acme resource audit treats `Acme_ImportMode_*` as falling back to Core's labels, like the request's fields.
15. The route-contract test's "unmapped route" example moved from `gadgets/import`, which now exists, to `gadgets/no-such-action`.

### Open risks

- **A reference by a nullable natural key does not round-trip when the target's key is null** (raised to the orchestrator). The editable export writes a reference by the target's natural key; `core.Role.Code` is nullable. A user's membership of a role without a code therefore exports a blank `Role / Code` cell, and the import refuses it as `Required`. Spec 0019 §6 does not say what an export writes there. Options:
  - the export writes `Id` for such rows, which needs a per-row key kind;
  - the import treats a blank natural-key cell on a same-source file as "keep the stored reference";
  - only non-nullable natural keys become default reference keys.
  The host test gives its role a code; nothing else works around this.

- An Upsert by natural key hydrates every row that may exist, so lookups and hydration grow with the file. This is bounded by the synchronous row limit; the background path (PC-178) chunks it.
- The session holds every parsed row in memory. Its size is bounded by the synchronous limits; the background path must stream or spill.
- The errors counter counts reported (capped) errors, not `TotalErrors`.
- The conformance budget row decides whether the stack "looks up" (adds the lookup round trip) from the entity's natural-key references and parent key. This is a heuristic over the generic harness; a stack with an unusual shape may need its own override.

### Examine hardest

- `ImportSession.Resolve.cs`: child matching (id, then natural key, then replacement), the overlay onto a copy, and write-once detection on stored versus file values.
- `ExcelImports.SaveAsync`: the retry predicate (never retries a conflict the file's own stamp caused, nor a missing row), the `RowsById` mapping, and that each catch builds its rows after the failed attempt has assigned ids.
- `ImportParser`: the synchronous row count and the order the limits are checked in, against D-236.
- `NamedEnums.ActionSites`: the narrowed home rule (deviation 14).

- **R1-2. The test for the D-236 carry would pass even if the parse trusted the declared size.**
  - Where: `test/core/Tellma.Core.Tests/Excel/ImportSessionTests.cs:262-273`.
  - Gap: `A_synchronous_import_counts_the_rows_it_reads_whatever_the_sheet_declares_and_refuses_beyond_its_limit` builds its file through `WorkbookEdits.WithRows` over a real export. The exporter writes no `<dimension>` element (none of the export sources write one), so the mapper forward-counts. - **R1-3. A reference by a nullable natural key does not survive the export-fix-import loop.** This is decision (1), and it is a spec gap, not a defect of this checkpoint.
  - Where: `src/core/Tellma.Core/Excel/ExportPlanner.cs:446` (the default reference key is `target.NaturalKey ?? target.Key`) and `src/core/Tellma.Core/Excel/ImportSession.Resolve.cs:545-551` (a blank cell becomes null).
  - Failure scenario: a user holds a role with no `Code`. The editable export writes a blank `Role / Code` cell on the role-memberships sheet, and the same-source Update of that unchanged file fails `Required` at the cell. The checkpoint's done-when, "the export-fix-import loop round-trips at every depth", therefore fails for ordinary Acme data. Roles are created without codes through `roles/save`; the host test had to give its role one.
  - A worse variant: on a *nullable* foreign key to such a target, the blank cell does not fail. It silently clears the reference on Update. No importable stack has such a foreign key today: `core.ReportShare.RoleId`/`UserId` are nullable but Reports declares no Import. A distribution's entity could.
  - Why this is a spec gap: §6.1 allows nullable natural keys (the filtered unique index, the "nullable unique strings" inference; `core.User.Email` and `core.Role.Code` are both nullable). §6.2 makes `Target.NaturalKey` the default reference key. §9.4 says a blank cell is null, with "No sentinel exists". The import follows §9.4 exactly. No section says what an export writes for a null key value.
  - The implementer's three options, judged against 0019:
    - (a) Write `Id` for such rows. This needs a per-row key kind. It breaks §3.1 ("encodes by the property or column type, never by value, so a column is homogeneous") and the manifest's per-column `KeyKind` (§5.3). On a cross-tenant file the ids name nothing. Worst fit.
    - (b) Treat a blank natural-key cell as "keep the stored reference". This is the sentinel §9.4 forbids. It cannot serve a new row or a replaced collection, and it would make a user's deliberate blanking of a nullable reference a no-op. Poor fit.
    - (c) Only non-nullable natural keys become default reference keys. **Best fit.** It changes only §6.2's default, and it reuses §6.3's surrogate fallback (`KeyKind = Surrogate`) and §2.1's `ReferenceKeys` override unchanged. Columns stay homogeneous, and §9.4 keeps its no-sentinel rule.
  - Recommended form of (c): the default reference key is the first **non-nullable** member of `Target.NaturalKeys`, else the surrogate.
    - `core.Role` then exports by `Name` in the primary-language slot. Its `[Multilingual][Unique] Name` is an inferred natural key, so the file stays cross-tenant portable.
    - `core.User` falls back to `Id` unless it gains a non-nullable key.
  - Fix: for Ahmad, a §6.2 ruling. The code change then lands in `ExportPlanner.ReferenceColumn` (PC-176's code, so a fix item or a carry), with a round-trip test of a user whose role has no code. PC-177 needs no change beyond recording the open risk. The silent-clear variant should be part of the ruling.

### Verdicts on the two decisions for the orchestrator

- **(1) Null natural-key references.** This is a spec gap, not a defect of this checkpoint. Option (c) fits 0019 best, in the refined form "the first non-nullable member of `NaturalKeys`, else the surrogate". Details and the silent-clear variant are in R1-3.
- **(2) Deviation 14 (`NamedEnums.ActionSites`).** It keeps naming composition-independent and breaks no existing name or audit.
  - Why composition-independent: an action site now counts as the enum's own only on a stack whose entity is declared in the arguments' assembly. Such stacks belong to the feature that declares that assembly, so composing another feature can add only non-own sites, which never outrank own ones.
  - No existing name breaks: the regenerated goldens (`entities-chunk.json`, Acme `web.json`, `contracts.json`) only add lines. No `"enum": "<schema>.<Type>"` value changed. The only removed `labelKey` is `core.Import.Mode`'s `Core_Import_Mode`, which now resolves to the new shared `Mode` key, as designed. `NamedEnumsTests` (including the composition-order test) passes, and the Acme audit was updated to treat `Acme_ImportMode_*` as falling back to Core's labels.
  - A latent edge, not a finding: an enum carried only by action arguments declared in an assembly that declares no stack entity would get no own site, so its home would fall to the smallest schema overall. That is no worse than the old rule, which counted every stack. `ImportMode` is safe twice over: `core.Import.Mode` carries it, and the core stacks' entities share `Tellma.Core.Abstractions` with `ImportRequest`.
