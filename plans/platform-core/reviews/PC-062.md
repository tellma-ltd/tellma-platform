### Deviations from spec 0015 (each is also in the commit message)

1. **`where TKey : struct` is expanded to `struct, IBinaryInteger<TKey>`.** This applies wherever a
   signature closes over `Entity<TKey>`: `EntityService`, the factory, the extensions and
   `EnlistDelete`. `Entity<TKey>` already carries that constraint, so the spec's narrower one does
   not compile.
   - The contexts, plans and outcomes keep an unconstrained `TKey`, as the spec declares them.
   - `RecordPermissions<TKey>` keeps `struct`.
2. **Cancellation tokens.**
   - Every async operation takes `CancellationToken cancellationToken = default` last. This covers
     the `EntityService` operations, `IChildQueryService`, `IApiActionInvoker`, `IExcelRowSource`
     and the `IAssignments` async members.
   - `IEntityPipeline` and `IApiActionInterceptor` take the token without a default.
   - Hooks keep their one context parameter, so §17's "a minor adds members to a context, never
     parameters to a hook" still holds. The validation contexts carry a `CancellationToken`
     property instead.
   - `EnlistSaveAsync` takes no token: the host's cancellation governs an enlisted write.
3. **`IContextLoader` defaults and constraints.** The `select`, `arguments` and `options` parameters
   are optional and default to null. The keyed members (`ByIds`, `ByKey`, `ByParentIds`,
   `Ancestors` and `Prime`) add `where TK : notnull`, because they key a dictionary.
4. **Init-only members instead of the spec's `{ get; set; }`.**
   - Contexts, plans and outcomes use `required` init-only members that refuse null.
   - `DetailsRequest.Include` is init-only and copied, so the shared `DetailsRequest.None` cannot
     be changed by a caller.
   - Runtime-only state is `internal`: before images, new-row flags, the round, sinks, notifier,
     assignments service, resource and the persisted source. The pipeline (PC-070 and later) sets
     it through `InternalsVisibleTo` (`Tellma.Core`).
5. **Rows that have not loaded yet throw.** `DeleteContext.Entities` and `ActionContext.Entities`
   throw `InvalidOperationException` until the first round loads them. `SaveContext.Before` throws
   for an update row before the first round, and returns null for an insert. The spec leaves the
   pre-load state unspecified, and a silent empty list would read as "no rows".
6. **`ActionContext.Save` and `Update` record internally.** The runtime reads `SavedRows` and
   `Updates` and calls `Close()` when it assembles the persist batch. A later call throws.
   `Update` copies its dictionary and requires at least one entry.
7. **Closed kinds.** The abstract contexts, the plans and the outcomes are classes closed by
   `private protected` constructors. `ActionDescriptor` and `ExportSource` are records, whose
   compiler-generated protected copy constructor a derived record can always reach. Since review 1,
   each is closed instead by an `internal abstract` member (`Kind`, `Case`) that only this assembly
   can implement, as `PathSegment` already is.
   - The `ActionDescriptor` base properties are explicit and get-only, not positional. This keeps
     one validated constructor.
8. **`StackLimits` validates every ceiling as positive,** in the constructor and under `with`. It
   adds `StackLimits.Default`, which equals `[Stack]`'s defaults, and a test pins that equality.
9. **Named tuple elements.** `SearchableProperties` is
   `IReadOnlyList<(string Property, SearchKind Kind)>`. The spec has an unnamed tuple.
10. **`DetailsPlan` forwards to an internal sink.**
    - Each method validates its arguments, then forwards to an internal `IDetailsPlanSink<T>` that
      the details planner (PC-070) supplies.
    - Rules on extra names (duplicates, the `MaxExtras` ceiling, declared names) are left to that
      planner.
    - A plan with no sink throws `InvalidOperationException`.
11. **Enlistment entry points forward to an internal `IEnlistmentHost`.** A host must implement it,
    which only platform frames can do. Any other `IWriteHost` gets an `InvalidOperationException`
    that names the host's operation.
12. **Absent services throw `NotSupportedException`.** This applies to Assignments and to
    Notify/Withdraw on `PersistContext` and `ActionContext`, and follows the planner note.
    - A context whose `Resource` is unset gets an `InvalidOperationException` from `Assignments`:
      no pipeline prepared that context.
13. **Contract-first exceptions.** `BlobRejectedException` carries the dotted `Blob.*` code as its
    `Code` (D-020). `ImportException` uses the problem code `validation`, with `Errors`,
    `TotalErrors` (at least `Errors.Count`) and `CommittedRowRanges`.
14. **Service attributes.**
    - `[CollectionService]` is on `IEntityValidator`, `IPersistEffect`, `IDetailsContributor`,
      `INamedFilterContributor` and `IApiActionInterceptor`.
    - `[EditorBrowsable(Never)]` is on `IEntityPipeline` and `IEntityBehavior`, the platform's
      side of the service, which stacks never name. Since review 1 it is not on
      `IEntityPipelineFactory`, which every service constructor names.
15. **Golden location.** The golden lives in
    `test/core/Tellma.Core.Abstractions.Tests/PublicApi/`, beside the contracts it pins, instead
    of the `Tellma.Core.Tests/Crud/` that §1.1 names. Tellma.Core's suite would otherwise have to
    reflect over another project's assembly.
16. **`ValidationErrors` re-homing is not done here.** §7.3's re-homing basics belong to PC-066, so
    no re-homing members were added.

No ARCHITECTURE.md change was needed: its `IContextLoader` paragraph (around line 585) agrees with
what was built.

### Open risks

- **The renderer reads nullable metadata by hand.** The runtime's `NullabilityInfoContext` replaces
  an unannotated use of an unconstrained `T` with the parameter's own "maybe null" state, so every
  `T` would render as `T?`.
  - The renderer therefore reads the compiler's `NullableAttribute` and `NullableContextAttribute`
    bytes in pre-order. It does the same for `TupleElementNamesAttribute`, and renders `notnull` and
    `class?` from the type parameter's own byte.
  - The rule followed: one byte per reference type or type parameter, a placeholder for a generic
    value type, none for a non-generic value type.
  - A misread would show as a wrong `?` in a golden. I inspected all three files line by line, and
    a test pins the cases: `T Value`, `TEntity? Before`, `where TK : notnull`, and no `TKey?`.
- **Golden churn.**
  - The renderer sorts members by their rendered line, so a signature change can move a line within
    its type.
  - Records render their compiler-generated members (`EqualityContract`, `PrintMembers`,
    `Deconstruct`, operators), because those are callable surface too.
- **Tokens versus the spec.** Downstream checkpoints written from the spec's signatures will find
  an extra trailing `CancellationToken` everywhere (deviation 2). It is optional on every public
  service member, so call sites written from the spec still compile.

### What reviewers should examine hardest

1. **Fit for the 19 dependents.**
   - Read the internal seams the runtime fills: `IEnlistmentHost`, `IDetailsPlanSink`, the
     contexts' internal members, `ActionContext.Close`/`SavedRows`/`Updates`/`PersistedSource`, and
     `ContextRef.Complete`.
   - Check they are enough for PC-063/PC-070 to build without reopening the public surface. The
     golden makes any later change a reviewed diff.
2. **The renderer's nullability walk,** in `PublicApiRenderer.Annotations`. Check the byte-order
   rules against the generated goldens, especially generic value types and `Nullable<T>`.
3. **Thread-safety.**
   - `ActionContext` guards `Save`, `Update` and `Close` with one lock.
   - `ContextRef` is not synchronised: it relies on `LoadAsync` completing before any read.
4. **Messages.** Check the wording of the `InvalidOperationException` and `NotSupportedException`
   messages a module author will see: before load, not prepared, no service registered, and
   foreign host.

Judgements on the points raised:

- **D15 (golden location): acceptable.** The golden pins Abstractions' surface, so the Abstractions
  test project is the natural home, and it runs in the same PR tier. The deviation is stated. Spec
  0015 §1.1 and §18.1 still name `Tellma.Core.Tests/Crud`, so the orchestrator should record the
  move.
- **Renderer byte walk: correct.** I compiled a probe assembly and rendered it with a copy of
  `PublicApiRenderer`. These all render exactly as declared:
  - jagged arrays with nullable levels (`string?[]?[]`, `string[]?[]?`);
  - nested named tuples inside a nullable tuple (`(string? A, (int B, string? C)? D)?`);
  - a nullable array of nullable tuples;
  - `KeyValuePair<string?, int[]?>`, `G<string?>?` and `G<(string, string? X)>` over a generic
    struct;
  - `List<(string?, int)?>` and `Dictionary<int, List<string?>?>`;
  - `ref string?`, `out List<T?>` and `in G<U>`;
  - unconstrained `T`/`T?`, struct-constrained `T`/`T?`, and `class?`/`struct`/`notnull`
    constraints.

  The byte rules match the runtime's own parser: none for a non-generic value type or a
  struct-constrained type parameter, a placeholder for a generic value type, the argument only for
  `Nullable<T>`, and none for by-ref. Two cosmetic gaps exist, and neither occurs in the pinned
  surface: a pointer renders as `Int32*`, and `Outer<T>.Inner<U>` renders as `Outer.Inner<T, U>`
  (its bytes are still read correctly). Base-interface and constraint-type annotations render
  oblivious, a reflection limit.
- **Copy-constructor risk: real, and it defeats D7 for the two record kinds.** See R1-1.
- **EF-free/ASP.NET-free test: not transitive.** See R1-3.
- **D1 (TKey widened): consistent and forced.** `Entity<TKey>`, `TopLevelEntity<TKey>`,
  `TreeEntity<TKey>` and `ChildEntity` already carry `struct, IBinaryInteger<TKey>`, so C# requires
  that constraint on every signature that closes over them (CS0314). The contexts, plans, outcomes,
  `IEntityPipeline`, `IEntityBehavior` and `EnlistedDelete` keep the spec's unconstrained `TKey`.
  `RecordPermissions` keeps `struct`, as spec 0015 §5.3 declares. Spec 0012 §2.1 says only "TKey ∈
  int | long", so nothing in 0012 conflicts.

The other deviations are sound:

- **D2** keeps call sites written from the spec compiling, and it holds §17's one-parameter hooks.
- **D3** is needed for the dictionary keys.
- **D4/D5** turn a silent empty or default value into an authoring error at the point of misuse.
- **D6** is lock-guarded and copies its input.
- **D8:** see the note for PC-063 in the summary.
- **D9** is cosmetic at runtime.
- **D10/D11** are the right internal seams, and `Tellma.Core`, `Tellma.Core.Testing` and the tests
  have InternalsVisibleTo. Every open frame (job worker, step runner, invoker) lives in
  `Tellma.Core`, according to 0011, 0020 and 0015.
- **D12** follows the planner note and D-004.
- **D13** matches D-020 and 0016's mapping table (`blob-rejected`, `validation`).
- **D14:** see R1-2.
- **D16:** contexts typed `ValidationErrors<TEntity>` leave room for an internal re-homing view.

### Findings

R1-1 (minor) — `ActionDescriptor` and `ExportSource` are not closed; another assembly can add a kind.
`src/core/Tellma.Core.Abstractions/Crud/ActionDescriptor.cs:18,33-46`,
`src/core/Tellma.Core.Abstractions/Excel/ExportSource.cs:15-20`, and the test at
`test/core/Tellma.Core.Abstractions.Tests/Crud/CrudContractTests.cs:46-63`.
- **Scenario.** A private protected constructor does not close a non-sealed record, because the
  compiler-generated protected copy constructor is reachable. I verified it: a scratch consumer of
  the built DLL compiled `public sealed record EvilAction : ActionDescriptor { public
  EvilAction(ActionDescriptor o) : base(o) { } }`, and the same against `ExportSource`, and both ran.
  - `ExportSource` is the case that matters. Any module can pass such a kind to the public
    `EntityService.ExcelRowSource(ExportSource)` and `IChildQueryService.ExcelRowSource`.
  - The comment at ActionDescriptor.cs:45-46 ("a switch over a descriptor's kind is exhaustive") is
    therefore false.
  - The test whitelists the copy constructor, so it pins the gap rather than the guarantee.
- **Fix.** The repo already has the pattern: `PathSegment` (Validation/PathSegment.cs:15-28) closes
  its record kinds with an `internal abstract` member.
  - Add an `internal abstract` member (or `private protected abstract`) to `ActionDescriptor` and
    `ExportSource`, and implement it in each sealed kind. I verified that an outside
    `record X : Base` then fails with CS0534.
  - Change the closed-kind test for these two to assert an assembly-only abstract member, as
    `ValidationPathTests.The_two_segment_kinds_are_the_only_kinds` does.
  - Drop the copy-constructor open risk from the notes. The public golden does not change.

R1-2 (minor) — `[EditorBrowsable(Never)]` on `IEntityPipelineFactory` hides the type every service
author has to write. `src/core/Tellma.Core.Abstractions/Crud/IEntityPipelineFactory.cs:18`.
- **Scenario.** Every pack and distribution service names `IEntityPipelineFactory` in its constructor
  and passes it to the base (0015 §3.1, §3.3: `CenterService<TCenter>(IEntityPipelineFactory
  factory)`). Modules consume Abstractions as a package, so IntelliSense hides the attribute's
  target from completion in exactly the code every module author writes.
- **Spec.** 0015 §3.1 asks for `EditorBrowsable(Never)` on `IEntityPipeline<,>` and
  `IEntityBehavior<,>` only. The factory is "not for distributions" to implement, but distributions
  must name it.
- **Fix.** Remove the attribute from the factory (keep it on the other two) and regenerate the Crud
  golden. Keep "not for distributions to implement" in its summary.

R1-3 (minor) — The framework-free assembly check reads direct references only.
`test/core/Tellma.Core.Abstractions.Tests/PublicApi/PublicApiGoldenTests.cs:83-87`.
- **Scenario.** `Contracts.GetReferencedAssemblies()` lists Abstractions' own references. Suppose
  `Tellma.Core.Queryex`, Abstractions' one edge, ever gained an EF Core, SqlClient or ASP.NET Core
  reference, or a future edge did. A module referencing Abstractions would then pull that framework
  in, and the test would stay green. Today Queryex references nothing, so the gap is latent.
- **Fix.**
  - Walk the reference graph transitively from `Contracts`, keeping a visited set. Load each
  `AssemblyName` through `AssemblyLoadContext.Default.LoadFromAssemblyName`.
  - Fail on any forbidden name. Optionally fail on any non-framework assembly other than
  `Tellma.Core.Queryex`, which pins "the one edge" itself.

R1-4 (minor) — The golden does not pin the contract-first types that other owners build against.
`test/core/Tellma.Core.Abstractions.Tests/PublicApi/PublicApiGoldenTests.cs:41-46`.
- **Scenario.** The planner note seeds these under their owners' exact names:
  - `ExportSource`, `ExcelQuery`, `ExcelPage`, `IExcelRowSource`, `ImportException`, `ImportError`
    and `RowRange`;
  - `BatchAssignments`, `IAssignments`, `AssignmentRequest` and `AssignmentCaption`.

  0016-d maps them by type, and 0019-a and 0028-a "list them as already seeded". Today only unit
  assertions cover their shapes. A later checkpoint could rename a member or change its nullability
  (for example `ExportSource.ByIds.Ids` or `IExcelRowSource.ReadAsync`), and no reviewed golden diff
  would show it.
- **Fix.** Add `Tellma.Core.Abstractions.Excel` and `Tellma.Core.Abstractions.Assignments` to
  `Namespaces`. Both namespaces currently hold only this checkpoint's types, the renderer already
  handles them, and the owners' later additions show as additive diffs. `BlobRejectedException`
  shares `.Blobs` with 0017's seeded types, so leave it out, or pin it in a per-type assertion.
