### Deviations

1. `--popover-max-inline-size` 320 → 346 px: the panel is now border-box (so fixed widths and the
   block cap are whole-panel sizes), and the token became the whole-panel cap; `auto` panels
   render exactly as wide as before (320 content + 24 padding + 2 border).
2. Fixed-size popovers on a block side are shifted inward (CDK `offsetX`) to keep the 8 px
   margin; the spec states only the width clamp, but a full-width panel anchored mid-screen would
   otherwise hang off the edge. `auto` and inline sides keep their alignment.
3. The block cap and the viewport width clamp apply to `auto` too ("every size"); an `auto`
   popover that fits is unchanged.
4. Drawer: the scrim appears without its fade as well ("no motion").
5. `placeholderOnError`: the fallback is `role="img"` named by `alt` and the failure posts no
   status notice — my reading of "the error stays announced through alt" (an avatar list must
   not announce and paint a notice per failed photo).
6. Tooltip internals moved into `ɵTmTooltipController`; `TmTooltip` gained an internal `ɵreason`
   so a `tmButton` that also carries `tmTooltip` shows its tooltip text and then the reason on a
   second line (orchestrator ruling after Review 1, D-031; the spec is silent). The accessible
   name stays the button's own; the reason joins the description.
7. A reason on a link is a `console.error` in dev mode and is ignored (the library's dev-error
   convention, as `tm-icon`), not a throw.
8. "A docs page" for `./overlay`: components.json covers components and directives only, so the
   overlay's docs are its `@packageDocumentation` (in the golden) and the README row.
9. Harness/DOM hooks added for the required harness methods: `tm-modal--end` on the shell,
   `data-tm-tab` on tab panels; `TmButtonHarness.isLink()` added.

### Open risks / what to examine hardest

- **Budget pressure:** popover 9 B, grid 3 B, image 53 B, button 171 B, tooltip 164 B headroom.
  The next change to any of these needs a ceiling decision.
- **Popover geometry:** the cap is recomputed only when the CDK reports a position change; after
  a viewport resize or a scroll that keeps the same side, the cap and the inline offset are stale
  until the next open. An open popover does not follow a live direction flip (as before; §B.3
  says connected overlays follow at their next attach).
- **Tap detection** uses pointerdown/pointerup (the click is swallowed); check it against
  real devices' pointer sequences and the long-press interplay.
- **`instantiate()`** relies on aria 22.0.3 rendering an empty deferred view for an instantiated
  tab when selected; the visited-`preserveContent` tracking is ours, not aria's.
- **The tooltip refactor** moved host listeners to `addEventListener`; behaviour should be
  identical (the tooltip suites pass unchanged), but review the teardown order.
- **`injector.get(ViewContainerRef)`** after construction (lazy reason tooltip) — works in
  Angular 22's NodeInjector; it inserts the container's anchor comment only on first show.

### Findings

**R1-1 (minor) — the drawer's stable-layout and backdrop paths have no test.**
`client/e2e/specs/modal-drawer.spec.ts` (whole file); `client/projects/core/tellma-core-ui/modal/tm-modal.spec.ts:366-417`.
Part D's definition of done asks for "fixed popover sizes and the drawer never resize while
content loads (geometry e2e)", and §D.2 keeps "Escape and backdrop dismissal with `canDismiss`"
for the drawer. The drawer story's content is static, and no test clicks a drawer's backdrop. A
regression that tied the drawer's width to its content, for example a later `max-content` or
`fit-content` on `.tm-modal-panel--end` or its container, would pass. So would a broken
backdrop click on the drawer's distinct backdrop class. Suggested fix: give
`DrawerModalContent` a "load more" control (as the popover story has). Then add one e2e that
reads the pane box, loads wide and tall rows, and asserts the box is unchanged. Add one e2e or
unit test that clicks the drawer's backdrop and expects `{"via":"backdrop"}`, and is kept open
by a `canDismiss` returning false.

**R1-2 (minor) — on a classic-scrollbar desktop, a clamped fixed-size popover runs under the
scrollbar.** `client/projects/core/tellma-core-ui/popover/tm-popover.css:24`,
`client/projects/core/tellma-core-ui/popover/tm-popover.ts:375-378`.
The width clamp is `100vw − 2 × margin`, and `fitInline` mirrors it with `window.innerWidth`.
Both include a classic vertical scrollbar. The shift's viewport is
`documentElement.clientWidth`, which does not. Take a narrow Windows desktop window (classic
16–17 px scrollbar, client width below 656 px) on a page that scrolls. A `lg` panel is then
`clientWidth + s − 16` wide. `tmPopoverInlineShift` clamps its left to 8, so its end edge sits
`s − 8` px past the visible edge, under the scrollbar, with no end margin. The e2e passes only
because the phone viewport has no classic scrollbar. This follows the spec's letter (§D.3 says
`100vw`), but the comment at :373-374 already names the mismatch. Suggested fix: write the cap
from JS, as the block cap is written, using `clientWidth − 2 × margin` in a
`--tm-popover-inline-cap` custom property that the CSS uses in place of `100vw`, and pass the
same width to the shift. That costs about 20–30 B against 9 B of headroom, so it needs the
ceiling decision below. Alternatively, record it as a known limit.

**R1-3 (minor) — an icon-only button loses its only visible label while it has a reason.**
`client/projects/core/tellma-core-ui/tooltip/tm-tooltip.ts:84`,
`client/projects/core/tellma-core-ui/button/tm-button.ts:198-200`.
On `<button tmButton aria-label="Delete" tmTooltip="Delete" [disabledReason]="r">`, the
tooltip is the only visible name of the action. With a reason, hover, focus and tap show only
the reason, such as "Needs “Customers: Create and edit”…", so a sighted user cannot tell which
toolbar action the reason is about. The e2e at `button-reason.spec.ts:136-149` pins exactly
this. Screen-reader users are unaffected, because the name stays in `aria-label`. Suggested
fix: keep the description as the reason, but show both on the surface (the tooltip text, then
the reason on a second line), for example `ɵreason() === null ? text : \`${text}\n${reason}\``
with `white-space: pre-line` on the panel. Alternatively, record the replace-only behaviour as
a design decision. ./tooltip has 164 B of headroom.

**R1-4 (minor) — the block cap and the inline shift go stale while a popover stays open.**
`client/projects/core/tellma-core-ui/popover/tm-popover.ts:345-348, 291`.
The implementer flags this as an open risk, and it is real. The CDK emits `positionChange` only
when the chosen pair changes, and the reposition scroll strategy keeps the panel attached
while the page scrolls. Open a `md` popover near the top with tall content, then scroll the
page so the anchor moves down. The cap still reflects the old room below, the CDK keeps the
same side because no side fits better, and the panel's bottom (with its own scroll end) runs
off the viewport. A window resize, such as rotating a phone, leaves the clamp-derived inline
shift wrong in the same way. Suggested fix: re-run `fitBlock` (and `fitInline`) from the
overlay's reposition path while open, for example by subscribing to the CDK
`ScrollDispatcher.scrolled()` and window `resize` between attach and detach, and add a unit
test that scrolls the anchor and expects the cap to shrink. Its cost is the same ceiling
question as R1-2.

**R1-5 (minor) — new declarations without TSDoc (AGENTS.md).**
- `client/projects/core/tellma-core-ui/tooltip/internal/tm-tooltip-controller.ts:50-54`:
  `text`, `describedText`, `panelRef`, `showTimer`, `hideTimer`.
- The same file, :200, :204, :233: `showDelayMs`, `showNow`, `hideNow`.
- `client/projects/core/tellma-core-ui/tooltip/tm-tooltip.ts:73, 78`: `controller`,
  `viewContainer`.
- `client/projects/core/tellma-core-ui/popover/tm-popover.ts:190-191`: `host`, `direction`.

The controller is a new file, so moved members count as new declarations. The lint does not

on each. This adds no runtime bytes.
