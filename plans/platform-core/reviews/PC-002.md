# PC-002: Identity store on the platform collation + Distribution seed kind

## Implementer notes

### What was built, and where

- **`DatabaseCollations`** (`src/core/Tellma.Core.Abstractions/Hosting/DatabaseCollations.cs`),
  `Platform = "Latin1_General_100_CI_AS"`, listed in the Abstractions README. This checkpoint owns
  it; later checkpoints reference it.
- **The model and migrations.** `TellmaIdentityDbContext` calls
  `UseCollation(DatabaseCollations.Platform)`. `Tellma.Identity.Migrations` was re-baselined with
  dotnet-ef 10.0.9: the old `20260818225530_Initial` and snapshot deleted, a new
  `20261108054654_Initial` scaffolded. The regenerated `Initial.cs` is byte-identical to the old one
  apart from the hand-carried `IX_OpenIddictTokens_CreationDate` raw SQL, which was carried across
  verbatim (an initial migration carries no collation operation, as spec 0011 §6.7 says). The only
  scaffolded difference is `.UseCollation(...)` in the designer and snapshot.
  `TellmaIdentityConstants.LatestMigration = "20261108054654_Initial"`.
- **`TellmaIdentityStore.MigrateAsync`** (`src/apps/Tellma.Identity.Migrations/TellmaIdentityStore.cs`):
  two overloads, `(string)` — so the method group converts to spec 0011 §6.1's
  `Func<string, Task> migrateIdentityStore` — and `(string, CancellationToken)`. It builds the
  context through the same internal `CreateContext`/`CreateModelServices` the design-time factory
  now uses, so the two cannot drift.
- **The store check** (`src/apps/Tellma.Identity/Services/Seeding/IdentityStoreCheck.cs`, throwing
  `IdentityStoreCheckException : InvalidOperationException`), the seeder's first step:
  1. `IRelationalDatabaseCreator.ExistsAsync`; for an existing database,
     `DATABASEPROPERTYEX(DB_NAME(), 'Collation')` and `SERVERPROPERTY('EngineEdition')`, and on
     Azure (edition 5) `sys.databases.catalog_collation_type_desc` (must be `DATABASE_DEFAULT`).
     Runs before any migration, so a foreign collation is refused with ApplyMigrations on or off.
  2. With `Seed.ApplyMigrations`: refuses unless the context's `IMigrationsAssembly` contains
     `LatestMigration` (so a context with no migrations assembly fails before EF creates anything),
     then `Database.MigrateAsync`.
  3. `IHistoryRepository.ExistsAsync` / `GetAppliedMigrationsAsync` — the table the context is
     configured with, `dbo.__EFMigrationsHistory` by default. A missing database (ApplyMigrations
     off), missing history or missing row fails, naming the database, schema `idsvr`, the migration
     and `Seed.MigrateCommand` when set. Later rows pass.
  Database exceptions during the reads are wrapped in `IdentityStoreCheckException` naming the
  database (an unreachable catalog fails the check).
- **`Seed.MigrateCommand`** on `TellmaIdentitySeedOptions`; `Tellma.Identity.Web/appsettings.json`
  sets it to the operator's `dotnet ef database update …` command.
- **The `Distribution` seed kind.** `TellmaIdentitySeedClientKind.Distribution` and
  `Origin`/`BackchannelLogoutUri`/`ServiceClientSecret` on the seed entry.
  - Onboarding and the seed share one path: `IClientProvisioningService.ConvergeDistributionAsync`
    (new), which `CreateDistributionAsync` now calls with generated secrets. It builds both
    descriptors through `ClientDescriptorFactory.Distribution`/`DistributionService`, adds the
    origin to `tellma_api`'s resources and grants it to `CallsDistributionApis` clients.
  - Per client it is a true convergence: create if missing; otherwise validate the plain secret
    against the stored hash and compare every descriptor member (`HaveSameRegistration`, sets
    compared as sets, properties by `JsonElement.DeepEquals`). A match writes nothing (not even a
    fresh salt). A mismatch updates; when only non-secret members changed, the stored hash is
    carried so it is not re-hashed. Never deletes.
  - `ClientDescriptorFactory.SeededDistribution(seed)` maps an entry to a
    `DistributionClientRegistration` (token exchange off; back-channel default
    `{Origin}/bff/backchannel-logout`); `SeededClient` refuses the Distribution kind.
  - The seeder seeds non-Distribution entries first, then Distribution entries, so the grant
    reaches a CLI listed after the distribution.
  - `AuditActions.DistributionSeedApplied`, written only when the convergence changed something;
    details carry the per-client outcome (`created|updated|unchanged`), `audienceAdded`,
    `grantsAdded`, never a secret.
  - Startup validation (`TellmaIdentityOptionsValidator`): slug `^[a-z][a-z0-9-]{0,14}$`; origin
    absolute, no userinfo/path/query/fragment, `https` (`http` only in Development); back-channel
    URI absolute http(s) on the same scheme rule; both secrets non-empty outside Development; and,
    for every seed kind, no two entries registering the same client id (a Distribution entry
    claims `<slug>` and `<slug>-svc`). Each failure names `TellmaIdentity:Seed:Clients:{i} ('{id}')`.
    Seed entries are validated only by the start-up (`ValidateOnStart`) pass, where the environment
    is known, never by the eager registration-time snapshot check: their rules depend on the
    environment and they shape no registration-time decision. (Found the hard way: in
    `WebApplicationFactory` the eager snapshot reads the developer's user secrets, which
    `StandaloneFactory` strips only at `Build()`; on this machine they hold a `third-party` seed
    entry, so `ConsentTests` failed the duplicate check locally. That leak of user secrets into
    registration-time reads is pre-existing and remains — e.g. external providers configured in a
    developer's secrets are registered in local test hosts — and is invisible on CI.)
  - The store check re-runs the collation check after `MigrateAsync` on a database that was missing
    before it (EF or a concurrent start created it), as spec 0011 §6.7 does for the migrator.
- **The pins** (`src/core/Tellma.Core.Testing/Database/`): `CollationPin` (design-time model
  collation, `HasPendingModelChanges`, no collation-changing `AlterDatabaseOperation` in any up or
  down) and `LatestMigrationPin`. `Tellma.Core.Testing` now references
  `Microsoft.EntityFrameworkCore.Relational` (a new central pin at 10.0.9 in
  `Directory.Packages.props`). The pins themselves are tested in `Tellma.Core.Testing.Tests/Database`.
- **Fixtures moved onto the platform collation.** Identity integration: `ReserveDatabase` (names
  only; EF creates) and `CreateDatabaseAsync(prefix, collation = Platform)`; `DatabaseBackedFactory`
  is now synchronous (`CreateStandalone`/`CreateInProc`, 100 call sites updated, three helpers that
  became synchronous followed). Identity E2E: no `CREATE DATABASE`; EF creates the database. EF
  integration and Queryex integration fixtures: explicit `COLLATE Latin1_General_100_CI_AS`; the
  Queryex fixture also refuses a leftover `TellmaQueryexTests` in another collation.
- **Docs:** READMEs of Tellma.Identity, Tellma.Identity.Migrations, Tellma.Identity.Web,
  Tellma.Core.Abstractions, Tellma.Core.Testing and four test projects; ARCHITECTURE.md (the
  collation bullets, the identity paragraph, the Tellma.Core.Testing descriptions).

### Deviations (also in the commit message)

1. The checkpoint's deliverable says fixtures move "to EF-created databases, or to the platform
   COLLATE"; the identity integration and E2E fixtures use EF-created databases, the EF and Queryex
   fixtures (which have no platform model) state the COLLATE. PC-005's "the integration fixture
   creates databases with the platform COLLATE" is therefore already done here.
2. `TellmaIdentityStore.MigrateAsync` has a second overload with a `CancellationToken` (the sketch
   omits tokens by convention); the token-less one is kept for spec 0011's `Func<string, Task>`.
3. Startup validation additionally refuses two seed entries that register the same client id
   (including `<slug>-svc`), and requires the back-channel URI to be absolute http(s). Not in the
   spec; without it two entries silently overwrite each other on every start.
4. `DistributionSeedApplied` is recorded only when the entry changed the store, not on every
   start (the spec names the event, not its cadence).
5. A Distribution entry ignores `DisplayName`, `RedirectUris`, `Resources` and `RequireConsent`
   (the spec says so for two of them; the other two would break equality with onboarding).
6. In-proc, `tellma_api` keeps the issuer origin it already seeded, plus the entry's origin. Spec
   §A.1 says the in-proc list is "the Distribution seed entry's Origin alone"; with spec 0011 §5.7
   (`Issuer = {PublicOrigin}/id`, `Origin = PublicOrigin`) the two are the same value, so nothing
   was removed.

### Rulings for the orchestrator

- **Where the shared collation-pin helper lives** (WATCHLIST c01 item 4): `Tellma.Core.Testing`
  (`Database/CollationPin.cs`, `LatestMigrationPin.cs`), which spec 0011's catalog, Acme and
  `CatalogMigrations.Latest` pins can reuse. It adds an EF Core Relational dependency (not a
  provider) to that package and a `Microsoft.EntityFrameworkCore.Relational` 10.0.9 line to
  `Directory.Packages.props`. **PC-001 bumps EF to 10.0.11; whichever integrates second must bump
  this line too** (NU1605 otherwise).
- **A Development entry without secrets fails seeding** (`SeededDistribution` throws naming the
  entry). Validation lets empty secrets through in Development as the spec says, but the seeder
  never generates one, so a host (spec 0011 §5.7's `AddTellma`) must supply per-boot secrets.

### Open risks

- Pre-existing: `StandaloneFactory`/`InProcFactory` strip the developer's user secrets only at
  `Build()`, so registration-time reads in a local test host still see them (see above). Not fixed
  here; it does not reach CI.

- A moved origin leaves the old origin among `tellma_api`'s resources and in the CLI/native grants
  (onboarding never removed one either). The old origin stays requestable as an audience by those
  clients until an operator prunes it.
- The Azure catalog-collation branch is unit-tested only (no Azure SQL Database locally).
- `HaveSameRegistration` compares every member the platform sets; a future OpenIddict that
  populates a new descriptor member from the store would turn every start into an update (safe, but
  no longer a no-op). The idempotence unit test would catch it.
- EF 10.0.11 (PC-001) may change scaffolding output; the migration may need regenerating at
  integration (it is regenerated with dotnet-ef, never hand-edited, apart from the index block the
  README documents).

### What reviewers should examine hardest

- `IdentityStoreCheck`: step order (collation before migrate), the migrations-assembly guard, the
  history read through `IHistoryRepository`, and exception wrapping; that a refused store is never
  written to.
- `ClientProvisioningService.ConvergeAsync`/`HaveSameRegistration`: secret comparison via
  `ValidateClientSecretAsync`, carrying the stored hash, and whether any member could be compared
  wrongly (no-op when it should update, or the reverse). The onboarding path now goes through the
  same convergence; check `CreateDistributionAsync` still always rotates.
- Validation: the slug grammar, origin shape, and the Development-only relaxations (environment
  unknown in the eager registration-time pass, enforced at `ValidateOnStart`).
- The fixture changes across four suites, and the mechanical `CreateStandalone`/`CreateInProc`
  rename.
