# PC-002: Identity store on the platform collation + Distribution seed kind

## Implementer notes

  `Platform = "Latin1_General_100_CI_AS"`, listed in the Abstractions README. This checkpoint owns
  it; later checkpoints reference it.

  `UseCollation(DatabaseCollations.Platform)`. `Tellma.Identity.Migrations` was re-baselined with
  dotnet-ef 10.0.9: the old `20260818225530_Initial` and snapshot deleted, a new

  scaffolded difference is `.UseCollation(...)` in the designer and snapshot.
  `TellmaIdentityConstants.LatestMigration = "20261108054654_Initial"`.
- **`TellmaIdentityStore.MigrateAsync`** (`src/apps/Tellma.Identity.Migrations/TellmaIdentityStore.cs`):
  two overloads, `(string)` — so the method group converts to spec 0011 §6.1's
  `Func<string, Task> migrateIdentityStore` — and `(string, CancellationToken)`. It builds the
  context through the same internal `CreateContext`/`CreateModelServices` the design-time factory
  now uses, so the two cannot drift.
- **The store check** (`src/apps/Tellma.Identity/Services/Seeding/IdentityStoreCheck.cs`, throwing
  `IdentityStoreCheckException : InvalidOperationException`), the seeder's first step:
  1. `IRelationalDatabaseCreator.ExistsAsync`; for an existing database,
     `DATABASEPROPERTYEX(DB_NAME(), 'Collation')` and `SERVERPROPERTY('EngineEdition')`, and on
     Azure (edition 5) `sys.databases.catalog_collation_type_desc` (must be `DATABASE_DEFAULT`).
     Runs before any migration, so a foreign collation is refused with ApplyMigrations on or off.
  2. With `Seed.ApplyMigrations`: refuses unless the context's `IMigrationsAssembly` contains
     `LatestMigration` (so a context with no migrations assembly fails before EF creates anything),
     then `Database.MigrateAsync`.
  3. `IHistoryRepository.ExistsAsync` / `GetAppliedMigrationsAsync` — the table the context is
     configured with, `dbo.__EFMigrationsHistory` by default. A missing database (ApplyMigrations
     off), missing history or missing row fails, naming the database, schema `idsvr`, the migration
     and `Seed.MigrateCommand` when set. Later rows pass.
  Database exceptions during the reads are wrapped in `IdentityStoreCheckException` naming the
  database (an unreachable catalog fails the check).
- **`Seed.MigrateCommand`** on `TellmaIdentitySeedOptions`; `Tellma.Identity.Web/appsettings.json`
  sets it to the operator's `dotnet ef database update …` command.
- **The `Distribution` seed kind.** `TellmaIdentitySeedClientKind.Distribution` and
  `Origin`/`BackchannelLogoutUri`/`ServiceClientSecret` on the seed entry.
  - Onboarding and the seed share one path: `ClientRegistrationConverger.ConvergeDistributionAsync`
    (after review 1; first shipped on `IClientProvisioningService`), which `CreateDistributionAsync`
    calls with generated secrets. It builds both
    descriptors through `ClientDescriptorFactory.Distribution`/`DistributionService`, adds the
    origin to `tellma_api`'s resources and grants it to `CallsDistributionApis` clients.
  - Per client it is a true convergence: create if missing; otherwise validate the plain secret
    against the stored hash and compare every descriptor member (`HaveSameRegistration`, sets
    compared as sets, properties by `JsonElement.DeepEquals`). A match writes nothing (not even a
    fresh salt). A mismatch updates; when only non-secret members changed, the stored hash is
    carried so it is not re-hashed. Never deletes.
  - `ClientDescriptorFactory.SeededDistribution(seed)` maps an entry to a
    `DistributionClientRegistration` (token exchange off; back-channel default
    `{Origin}/bff/backchannel-logout`); `SeededClient` refuses the Distribution kind.
  - The seeder seeds non-Distribution entries first, then Distribution entries, so the grant
    reaches a CLI listed after the distribution.
  - `AuditActions.DistributionSeedApplied`, written only when the convergence changed something;
    details carry the per-client outcome (`created|updated|unchanged`), `audienceAdded`,
    `grantsAdded`, never a secret.
  - Startup validation (`TellmaIdentityOptionsValidator`): slug `^[a-z][a-z0-9-]{0,14}$`; origin
    absolute, no userinfo/path/query/fragment, `https` (`http` only in Development); back-channel
    URI absolute http(s) on the same scheme rule; both secrets non-empty outside Development; and,
    for every seed kind, no two entries registering the same client id (a Distribution entry
    claims `<slug>` and `<slug>-svc`). Each failure names `TellmaIdentity:Seed:Clients:{i} ('{id}')`.
    Seed entries are validated only by the start-up (`ValidateOnStart`) pass, where the environment
    is known, never by the eager registration-time snapshot check: their rules depend on the
    environment and they shape no registration-time decision. (Found the hard way: in
    `WebApplicationFactory` the eager snapshot reads the developer's user secrets, which
    `StandaloneFactory` strips only at `Build()`; on this machine they hold a `third-party` seed
    entry, so `ConsentTests` failed the duplicate check locally. That leak of user secrets into
    registration-time reads is pre-existing and remains — e.g. external providers configured in a
    developer's secrets are registered in local test hosts — and is invisible on CI.)
  - The store check re-runs the collation check after `MigrateAsync` on a database that was missing
    before it (EF or a concurrent start created it), as spec 0011 §6.7 does for the migrator.
- **The pins** (`src/core/Tellma.Core.Testing/Database/`): `CollationPin` (design-time model

### Deviations (also in the commit message)

1. The checkpoint's deliverable says fixtures move "to EF-created databases, or to the platform
   COLLATE"; the identity integration and E2E fixtures use EF-created databases, the EF and Queryex
   fixtures (which have no platform model) state the COLLATE. PC-005's "the integration fixture
   creates databases with the platform COLLATE" is therefore already done here.
2. `TellmaIdentityStore.MigrateAsync` has a second overload with a `CancellationToken` (the sketch
   omits tokens by convention); the token-less one is kept for spec 0011's `Func<string, Task>`.
3. Startup validation additionally refuses two seed entries that register the same client id
   (including `<slug>-svc`), and requires the back-channel URI to be absolute http(s). Not in the
   spec; without it two entries silently overwrite each other on every start.
4. `DistributionSeedApplied` is recorded only when the entry changed the store, not on every
   start (the spec names the event, not its cadence).
5. A Distribution entry ignores `DisplayName`, `RedirectUris`, `Resources` and `RequireConsent`
   (the spec says so for two of them; the other two would break equality with onboarding).
6. In-proc, `tellma_api` keeps the issuer origin it already seeded, plus the entry's origin. Spec
   §A.1 says the in-proc list is "the Distribution seed entry's Origin alone"; with spec 0011 §5.7
   (`Issuer = {PublicOrigin}/id`, `Origin = PublicOrigin`) the two are the same value, so nothing
   was removed.

- **Where the shared collation-pin helper lives** (WATCHLIST c01 item 4): `Tellma.Core.Testing`
  (`Database/CollationPin.cs`, `LatestMigrationPin.cs`), which spec 0011's catalog, Acme and

  never generates one, so a host (spec 0011 §5.7's `AddTellma`) must supply per-boot secrets.

### Open risks

- Pre-existing: `StandaloneFactory`/`InProcFactory` strip the developer's user secrets only at
  `Build()`, so registration-time reads in a local test host still see them (see above). Not fixed
  here; it does not reach CI.

- A moved origin leaves the old origin among `tellma_api`'s resources and in the CLI/native grants
  (onboarding never removed one either). The old origin stays requestable as an audience by those
  clients until an operator prunes it.
- The Azure catalog-collation branch is unit-tested only (no Azure SQL Database locally).
- `HaveSameRegistration` compares every member the platform sets; a future OpenIddict that
  populates a new descriptor member from the store would turn every start into an update (safe, but
  no longer a no-op). The idempotence unit test would catch it.
- EF 10.0.11 (PC-001) may change scaffolding output; the migration may need regenerating at
  integration (it is regenerated with dotnet-ef, never hand-edited, apart from the index block the
  README documents).

- `ClientProvisioningService.ConvergeAsync`/`HaveSameRegistration`: secret comparison via

- Validation: the slug grammar, origin shape, and the Development-only relaxations (environment

- The fixture changes across four suites, and the mechanical `CreateStandalone`/`CreateInProc`

**R1-1 (minor). The duplicate-client-id check compares ordinally, but the store does not.**
`src/apps/Tellma.Identity/Options/TellmaIdentityOptionsValidator.cs:161` builds `claimed` with
`StringComparer.Ordinal`. `OpenIddictApplications.ClientId` has a unique index, and the column now
uses the platform collation, which is case-insensitive.
- *Failure:* take a `Cli`/`Native`/`ControlPlane` entry `ACME-svc` and a `Distribution` entry `acme`.
  Validation passes. The seeder creates `ACME-svc` first. The distribution's `ConvergeAsync`
  (`ClientProvisioningService.cs:279`) then calls `FindByClientIdAsync("acme-svc")`. SQL finds the
  `ACME-svc` row, OpenIddict's ordinal post-filter drops it, and `CreateAsync` hits the unique index.
  The host fails at start with a raw `DbUpdateException`, not the validation message naming both
  entries that this check exists to give.
- *Fix:* build `claimed` with `StringComparer.OrdinalIgnoreCase`. Add a unit case: `acme`
  (Distribution) plus `ACME-svc` (Cli) fails naming both entries.

**R1-2 (minor). Several `HaveSameRegistration` members have no test that fails when their
comparison breaks.** The members are `Properties`, `Requirements`, `Settings`, `ConsentType` and
`PostLogoutRedirectUris` (`src/apps/Tellma.Identity/Services/Provisioning/ClientProvisioningService.cs:313`).
- *Coverage today:* the only change tests are `A_drifted_registration_is_converged_back_whoever_created_it`
  (`test/apps/Tellma.Identity.Tests/Provisioning/DistributionSeedTests.cs:191`), which changes
  `Permissions`, and `A_moved_origin_rewrites_both_clients_and_their_redirects`, which changes
  permissions, redirects and properties at once. So the `Permissions` comparison alone keeps both
  green. `AssertSameRegistration` (line 349) also skips `Settings`.
- *Failure:* suppose the `Properties` comparison regresses to vacuously true, for example a store
  that round-trips the bag differently. Then an entry whose only change is `BackchannelLogoutUri`
  reports `Unchanged` on every start, and logout tokens keep going to the old endpoint. The same
  holds for a PKCE or PAR requirement an operator deleted by hand: the drift would never be repaired,
  which is a security downgrade. Every test stays green.
- *Fix:* add a converge-twice unit test that changes only `BackchannelLogoutUri` and asserts
  `Client == Updated` with the new property stored. Add a drift test that removes
  `Requirements.Features.PushedAuthorizationRequests` from the stored BFF row and asserts it is
  restored. Compare `Settings` in `AssertSameRegistration`. A small table test over
  `HaveSameRegistration`, flipping one member at a time, would cover the rest.

**R1-3 (minor). Convergence of a changed entry is not safe when several instances start at once.**
`EnsureDistributionAsync` (`src/apps/Tellma.Identity/Services/Seeding/IdentitySeeder.cs:182-185`)
leads to `ConvergeAsync`. On a change, that method calls `UpdateAsync` (`ClientProvisioningService.cs:302`),
and on a first start it calls `CreateAsync` (`:279`). Both go through OpenIddict's EF store: updates
use its concurrency token, and creates hit the unique `ClientId` index.
- *Failure:* spec 0011 §5.7 keeps stable secrets because a standalone deployment may run several
  instances. Rotate `Tellma:Identity:ClientSecret` in App Service settings and every instance restarts
  together. Each reads the same row and concurrency token, and each issues the update; all but one
  fail with `OpenIddictExceptions.ConcurrencyException`. A first deployment with several instances
  races the same way on `CreateAsync`. Seeding failures stop the host, so those instances crash-loop
  once before they find the entry converged. It heals on its own, but rotation causes a start-up
  outage. The unchanged path writes nothing, so only changes are exposed.
- *Context:* the pre-existing `EnsureClientAsync` calls `UpdateAsync` on every start, so platform
  clients already have the same race on every concurrent boot. That part is out of scope here.
- *Fix:* in `EnsureDistributionAsync`, catch `OpenIddictExceptions.ConcurrencyException` and a
  unique-key `DbUpdateException`, then run `ConvergeDistributionAsync` once more. On the retry it
  finds the row converged, or the winner's values, and applies or no-ops. Alternatively, record the
  race as a known limit for the 0011 host checkpoints together with the `EnsureClientAsync` case.

**R2-1 (minor). The retry bound counts whole-convergence re-runs, but a distribution convergence has
more independent race points than the bound.** `ClientRegistrationConverger.MaxAttempts` is 4
(`src/apps/Tellma.Identity/Services/Provisioning/ClientRegistrationConverger.cs:55`), `WithRetryAsync`
(`:209-226`) re-runs the whole of `ConvergeDistributionOnceAsync` (`:229-256`) on any lost write, and
one run has 3 + G serial write points: the BFF create, the `-svc` create, the `tellma_api` resource
append, and one grant per client carrying `CallsDistributionApis` (`:384-419`). With the CLI plus one
`Native` entry that is five.
- *Failure:* a first deployment of a standalone engine with several instances and a `Distribution`
  entry. Instance B reads point 1 before A writes it and writes after: lost, attempt 2. It re-runs
  from the top in a fresh scope while A proceeds; the same one-step trail at points 2, 3 and 4 costs
  attempts 2, 3 and 4, and the fourth loss is thrown. B's host fails to start and crash-loops once
  before it finds everything converged. The probability is low (B falls further behind on each
  re-run), and the rotation case every instance restarts into has only two write points, so it is
  safe; but the class remark "a lost write is never an error here" does not hold for the
  distribution path, because the bound is below the number of points at which a write can be lost.
- *Also:* `IsConcurrentWriteConflict` (`:183-197`) treats every `OpenIddictExceptions.ValidationException`
  as a race. A descriptor the manager refuses for its own reasons (not reachable from a validated seed
  entry today, but reachable through `CreateDistributionAsync` from the onboarding API with an
  arbitrary slug or origin) is attempted four times and logs three "lost a write to a concurrent
  writer" lines at Information before the real error surfaces.
- *Fix:* count attempts per write point, not per convergence — keep the furthest step reached in
  `DistributionProgress` and count an attempt against the bound only when it loses at the same step
  as the previous one; or give each of the two clients, the scope append and the grant loop its own
  `WithRetryAsync`, as `ConvergeSeededClientAsync` and `ConvergeScopeAsync` already have. Treat a
  `ValidationException` as a race only when `FindByClientIdAsync`/`FindByNameAsync` now finds the row
  the attempt tried to create. Add a unit test in which the in-memory store loses at a different
  step on each of four attempts and asserts the convergence still succeeds.

**R2-2 (minor). A login that cannot open an existing store is reported as "does not exist".**
`IdentityStoreCheck.CheckAsync` decides existence with `IRelationalDatabaseCreator.ExistsAsync`
(`src/apps/Tellma.Identity/Services/Seeding/IdentityStoreCheck.cs:59-61`). EF's SQL Server creator
returns false on error 4060, which the server raises both for a database that is not there and for
a login that has no user in a database that is ("Cannot open database … requested by the login").
- *Failure:* the deployed standalone case §A.11 is written for. The operator does steps 1–3 but not
  step 4 (the engine's database user). With `ApplyMigrations` off the check throws "database '…'
  does not exist, so it holds no identity schema … Apply the engine's migrations …" (`:95-101`) and
  quotes `MigrateCommand`. The operator re-runs migrations that are already applied; the real cause
  — a missing database user — is not named, and the SQL error that would have named it was swallowed
  into `false`. The in-proc host (0011 §5.7) has the same message when `tellma_app` lacks `CONNECT`
  on the catalog. With `ApplyMigrations` on, EF instead attempts `CREATE DATABASE` and fails with a
  permission error, which is at least truthful.
- *Fix:* when `ExistsAsync` is false and `ApplyMigrations` is off, open the connection once more
  inside `ReadAsync` and let the wrapped `SqlException` be the message (it says which it was), or
