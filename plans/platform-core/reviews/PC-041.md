### How it works (the parts worth knowing before reading the code)

- **One aria menu per level.** `@angular/aria` 22.0.3 registers a `MenuItem` with the `Menu` it
  finds through DI, and a submenu parent is a `MenuItem` given `[submenu]`. So the submenu's
  `ngMenu` must exist for the parent row to be a parent at all. The submenu overlay is therefore
  attached for as long as its parent row exists (`[cdkConnectedOverlayOpen]="true"`), and the
  panel carries `tm-menu__panel--closed` (`display: none`) until `parent.expanded()` is true. It
  is re-measured in an `afterRenderEffect` each time it shows, since it was first placed while
  not displayed.
- **Inline popovers nest.** `tmCreateAnchoredOverlay` uses the CDK's inline popover host, which
  is inserted next to the origin. A submenu panel is thus a DOM descendant of the root list. That
  is what makes events bubble through the root panel (Tab, `contextmenu`), keeps a press inside a
  submenu from being an outside press, and satisfies axe (`menu` may own `menu`, checked in
  axe-core 4.12.1 `requiredOwned`).
- **Activation.** aria's root `itemSelected` fires for rows on every level and closes the tree
  first. Two cases must not go that way, so the row pre-empts aria with `stopPropagation` on its
  own element:
  - a `keepOpen` item (aria would close the submenu it sits in): the row marks itself active and
    calls the host directly;
  - a link: a modified click is left wholly to the browser and kept from aria (the menu stays
    open); Enter is kept from aria's key handler, which would `preventDefault` it and so stop the
    browser's own click; Space, which anchors do not answer, calls `click()`. A plain click
    reaches aria, which reports it; the row `preventDefault`s it only when the link has an
    `action`.
- **Keys and direction.** Expand/collapse arrows come from aria, which reads the live
  `Directionality` signal; the submenu side comes from the CDK's logical positions. Both are
  covered cold (`?dir=rtl`) and after a run-time flip of `<html dir>`.

### Deviations

Each is repeated in the commit message.

1. **The `./menu` ceiling is 8.5, not the 7 of §C.11 and of this checkpoint's done-when.**
   Measured 8.21 KB (baseline 4.38). The spec budgeted 1 KB over the old ceiling for the whole of
   §C.10; the real surface adds 3.8. I measured the parts (leave-one-out gzip on the minified
   bundle): row renderer ≈ 2.05 (its template alone ≈ 0.93, because the measured FESM carries
   templates as source text, twice, once in the class metadata), submenu ≈ 0.37, trigger ≈ 0.4,
   stylesheet growth ≈ 0.3, development messages ≈ 0.2, the rest in `TmMenu`. A trimming pass
   (shorter messages, the new-tab note moved into the name, ids on the view model, one CSS rule
   dropped) took it from 8.35 to 8.21; nothing short of dropping a spec'd entry kind gets to 7.
   The `budgetNotes` entry records the breakdown. `./icon` and `./kbd` set the precedent of a
   ceiling raised past the spec's estimate at birth with a note. **This needs the orchestrator's
   ruling**; if 7 is firm, the candidates to cut are the trigger (to its own entry point) or the
   development diagnostics.
2. **The entry object, not its id, is the aria value.** `itemSelected` must emit the
   `TmMenuItem`, and ids need not be unique across levels.
3. **A row whose name is more than its label gets an explicit `aria-label`.** With a `detail`:
   "Language, English". The spec says the detail "joins the accessible name"; name from content
   gives "Language English" with no pause (a hidden ", " text node came out as
   "Language , English" in Chromium). On a `_blank` link: "Documentation (opens in a new tab)".
   The spec asks for "a hidden (opens in a new tab)"; it is the tail of the `aria-label` rather
   than a visually hidden span, which also dropped a CSS rule. Every other row is named by its
   content as before.
4. **Focus lands on the first row on open** (real DOM focus), where the old menu focused the list
   element with no active row. APG menu-button behaviour needs it (Enter/ArrowDown → first row,
   ArrowUp → last) and the context menu follows for consistency. The existing unit test that
   asserted the old behaviour was updated.
5. **Checkable rows draw the check in the icon slot and ignore their own `icon`** ("a check glyph
   fills the icon slot"). An unchecked row keeps the slot empty so labels stay aligned.
6. **Group dividers.** The spec says "a divider above every group but the first". Implemented: a
   group draws a divider above itself whenever a non-separator entry precedes it. So a first
   group that follows plain rows is divided from them, a group that opens the menu is not, and a
   separator the caller placed before a group is not doubled.
7. **What the three development diagnostics do besides logging** (the spec names the messages
   only): `disabled` with `disabledReason` behaves as `disabledReason`; a submenu nested through
   a cast renders as a disabled row with no third level; a radio item outside a group still
   renders as a radio item.
8. **A modified click on a link leaves the menu open.** The spec says only that the click "stays
   native". Closing would move focus back to the invoker under a gesture whose whole point is to
   stay where you are (open several entries in background tabs).
9. **All-disabled levels stay navigable** by overriding aria's `isListDisabled` on each menu
   instance (`ɵTmMenuList`). Without it a menu whose every row is disabled (with or without a
   reason) takes no focus and reads nothing, which defeats "stays in the roving focus order". A
   unit test fails if aria renames or drops the internal.
10. **`menu.shortcutFontSize` (`--menu-shortcut-font-size`) is removed.** Shortcuts render as
    `tm-kbd` caps, which size themselves; the token had no remaining reader.
11. **`ViewEncapsulation.None` on `tm-menu`.** One consequence beyond the new markup: the
    existing rule `.tm-menu__icon > *` (size a template-provided icon to the icon box) was dead
    under emulated encapsulation and now applies. That is the rule's stated intent; the old unit
    test's unsized inline SVG needed explicit `width`/`height` because unit tests load no token
    CSS.
12. **Harness surface beyond the spec's list**: `TmMenuGroupHarness`, `getGroups`,
    `getHeaderText`, `getListId` and the item-harness getters. `TmMenuHarness.hostSelector` now
    also matches submenu panels (that is how `openSubmenu` returns one); a document-root
    `locatorFor(TmMenuHarness)` still resolves to the root panel, which comes first in the DOM.
13. **The grid's shortcut constants moved to `TmKeys` here**, not in the grid-keymap checkpoint
    that lists it, because `TmMenuItem.shortcut` changing type would not compile otherwise. The
    keymap table, `tmIsApplePlatform`, the icons and `ɵTmGridIcons` are untouched.
14. **Submenu `viewportMargin: 8`** so a submenu pushed back on screen at 390 px keeps a gutter.
15. **Test tiering.** The PR tier runs the new Playwright file on Chromium only. No
    `@cross-engine` tag was added, so Firefox and WebKit do not run it at all (see open risks).
    (Closed in review 1, R1-3: twelve tests across the three menu spec files carry the tag.)
16. **A menu that is already open does not re-lay-out on a live direction flip**; its arrow keys
    follow at once. See open risks. Covered by tests: cold RTL, and a flip before opening.
    (Review 1: not a deviation. §B.3 has overlays follow a flip at their next attach.)
17. **(Review 1, R1-4.) One Escape entry for the whole menu, not one per level.** §C.10 says
    each level pushes its own entry on the shared Escape stack. A submenu's entry could only be
    pushed after the render that follows its parent row expanding, so an Escape pressed in that
    moment closed the whole menu, and one pressed just after a collapse hit a stale entry. The
    menu's single entry now decides as the key arrives: an expanded submenu parent is collapsed
    and refocused, otherwise the menu closes. One Escape still closes one level, and the menu
    still sits on the shared stack in open order relative to tooltips, popovers and modals.

### Open risks

- **Reliance on aria internals.** `_pattern` (`first()`, `last()`, `close()`,
  `listBehavior.goto`, `listBehavior.isTyping`, `listBehavior.focusBehavior.isListDisabled`) and
  `Menu._items`. The old menu already used `_pattern`; this adds the override in deviation 9 and
  the two `goto` calls. `@angular/aria` is pinned by the catalog; an upgrade needs the unit suite
  green before anything else.
- **Always-attached submenu overlays.** Each submenu parent costs one hidden popover element and
  one aria menu for as long as the root is open. Fine for the handful of submenus a menu has; a
  menu with dozens of submenu parents would pay for all of them at open.
- **An already-open menu does not re-lay-out on a live direction flip.** The CDK writes `dir` on
  the overlay host at attach, so a flip of `<html dir>` while a menu is open changes the arrow
  keys at once (aria reads the live signal) but the panel and chevron only at the next open. The
  same holds for every CDK overlay in the library; a language switch from inside a menu closes
  the menu first, so the window is a programmatic flip under an open menu.
- **Firefox and WebKit are unexercised** for the new behaviour: native link gestures, `:focus` on
  anchors as menu items, popover nesting. The unit suite is Chromium too. (Review 1: the
  `@cross-engine` subset now runs on both; the whole of the three menu spec files was also run
  once on both, see the R1-2 response.)
- **(Review 1.) Whether a screen reader reads the header block on open is unverified.** Focus
  lands on a row, so the header reaches assistive technology only through the
  `aria-describedby` of the enclosing `role="menu"`. Needs one manual pass with NVDA and
  VoiceOver (R1-9, second half).
- **Hover-open timing** is aria's 100 ms expansion delay; the e2e waits on visibility, not time,
  except one deliberate 300 ms "it must not open" wait on the reason-disabled parent.

**R1-1 (major): a held Space or Enter activates a `keepOpen` item on every auto-repeat.**
`menu/internal/tm-menu-rows.ts:387-395` (`onItemKeydown`) and `:437-444` (`isActivationKey`).
The row-level pre-emption does not look at `event.repeat`. aria's own key handling, which this
replaces for `keepOpen` rows, is built with `ignoreRepeat: true`, so every other row ignores
repeats. Scenario: focus the "Line numbers" checkbox item in the `menu-rich` story and hold
Space; the OS repeats the keydown and each one toggles the item and emits `itemSelected`.
Measured with five keydowns (one press plus four repeats) on Chromium, Firefox and WebKit: the
item was activated 5 times (`menu-rich-selected` = 5) where a native checkbox and every other
menu row give 1. A real hold of one second is some 20 to 30 toggles, ending in an arbitrary
state, and a `keepOpen` item whose `action` has a side effect runs it that many times. A second
route follows from the same gap (inferred from this result plus a probe showing a held Enter on
the trigger delivers its repeats to the first row; not run separately): hold Enter on a
`tmMenuTriggerFor` button whose menu starts with a `keepOpen` item, and the repeats that arrive
after focus lands activate that item. Fix: in `onItemKeydown`, when the key is an activation key
and `event.repeat` is true, still `preventDefault` and `stopPropagation` but do not activate. Add
a unit test that dispatches a `repeat: true` keydown on a `keepOpen` row.

**R1-2 (major, pre-existing, not introduced by this commit): a menu opened by right-click closes
when the button is released, wherever `contextmenu` fires before `mouseup`.**
`menu/tm-menu.ts:122` (`(overlayOutsideClick)`) and `:233`
(`onOutsideClick: () => this.close({ restoreFocus: false })`); both lines predate this commit.
The CDK outside-click dispatcher listens for `click`, `auxclick` and `contextmenu` on the body
(`@angular/cdk` `_overlay-module-chunk.mjs:466`). Where the engine raises `contextmenu` on the
press, the release then produces an `auxclick` on the invoking element, which is outside the
panel, and the menu closes. Event logs from the grid story: Chromium on Windows
`mousedown, mouseup, auxclick, contextmenu` (opens and stays); Firefox and WebKit
`mousedown, contextmenu, [menu opens], mouseup, auxclick` (closes). The CDK's own context-menu
trigger carries a workaround for exactly this (`menu.mjs:1930-1937`, it skips the first
`auxclick`). Consequences seen here: this commit's new test "the grid's context menu follows:
44 px rows at 390 px" (`e2e/specs/menu-rich.spec.ts:217-229`) fails on Firefox and WebKit, and
19 of the 24 tests in `menu.spec.ts` + `grid-menu.spec.ts` fail on each (the five that pass open
by keyboard or from a button). No menu test carries `@cross-engine`, so nothing has ever run
this on a second engine. Not verified on a physical macOS or Linux browser; Blink also raises
`contextmenu` on the press on those platforms, so I expect Chromium there to behave like the
Firefox log, and the Linux PR-tier result for `grid-menu.spec.ts` would settle it. Fix: in
`TmMenu`, ignore the first outside `auxclick` after an open that came from a `contextmenu`
gesture (or ignore outside `auxclick` with `button === 2` until a `pointerdown` has been seen
since the open; the menu already dismisses on `pointerdown` capture, so nothing is lost). Since
the defect is outside this diff, the orchestrator may prefer to route it to its own checkpoint;
what belongs here is that the checkpoint's "Firefox and WebKit are unexercised" risk hides a
failing test of its own.
