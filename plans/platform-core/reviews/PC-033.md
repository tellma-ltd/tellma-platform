# PC-033: Queryex host integration: schema provider, Rows/Count/constants, entity queries, materializer, display names

## Implementer notes

### What was built, and where

- **Schema provider** (`src/core/Tellma.Core/Data/Queries/`).
  - `QueryexSchemaProvider` (registered also as `IQueryexSchemaProvider`) builds one
    `QueryexSchema` per `MultilingualShape` from the entity metadata and the runtime model, plus a
    `QueryexSchemaMap` per shape that maps descriptors to metadata both ways and keeps each
    entity's declared properties and withheld JSON columns.
  - Store types come from `QueryexStoreTypes` (the relational type mapping parsed into
    `QueryexStoreType`). JSON, period and platform-secret columns are withheld; only the group
    twins a shape admits are properties.
  - References and parent keys are navigations; a sibling is an optional navigation on the
    owner's id. This needed an engine amendment: `NavigationDescriptor.IsOptional`
    (`QueryexSchemaBuilder` parameter `isOptional`), which `RelationalPlan` emits as a `LEFT JOIN`
    and `NullityAnalyzer` treats as possibly missing. Pinned by
    `Tellma.Core.Queryex.Tests/Emit/OptionalNavigationTests`.
  - `Fingerprint` is a SHA-256 of the model's queryable surface.
- **Batch query statements** (`src/core/Tellma.Core/Data/Batches/DataBatch.Queries.cs`).
  - `Rows`: `[keys twin] → page → [count] → [ancestors]`, each its own statement and ordinal.
    The keys twin is `DECLARE @tb{a}_keys TABLE ([Id] int|bigint PRIMARY KEY); INSERT … <body>`
    under the spec's filter, restrictions and paging (ordering dropped unless paged). The page then
    reads only the captured keys. The count is `SELECT COUNT(*) FROM (<keys body, Take = cap+1>)`.
    Ancestors are `@tb{d}_anc`: the nodes strictly above the page's nodes and not on it
    (`IsDescendantOf`), read with the spec's select and order under `AncestorsFilter`.
  - `Count`, `EvaluateConstant`, `Assert` (with an `OPTION (RECOMPILE)` variant that counts into
    `@tb{b}_count` first; number must be platform or distribution band; code is restricted to
    `[A-Za-z0-9._-]`).
  - `Query<TEntity>`: completion (root key, and per navigation prefix the owner's FK and the
    target's key), computed items refused, collections as a tree from dotted names, children
    restricted on captured parent keys (or the caller's own id restriction), grandchildren on
    their parents' captured keys, `AllProperties` adding JSON columns as `UndeclaredColumns`,
    ancestors through `AddWhole` into `Related` under the root's name.
  - `QueryPlan` compiles every statement of a call at its predicted ordinal and checks the
    parameter budget before appending any, so a refusal leaves the batch unchanged.
  - Dedup through `QueryStatementKey`, cleared at each declared write. Context values and the
    schema map are read once per batch.
  - `internal SqlIdentifier? KeysOf(object handle)` returns a handle's capture table.
- **Slots** (`QueryexSlots`): binding by origin (literal, today, now, user, time zone,
  declared), typed by store family; text slots sized to the family bound unless the value is
  longer; decimal facets only when the slot states them. `BatchParameter` gained precision/scale.
- **Materializer** (`EntityMaterializer`): depth-1 columns onto the statement's entity, deeper
  ones onto one related instance per id per prefix, JSON columns by column name, enums by name,
  `DateTime → DateOnly`, unknown columns refused; `Stitch` by parent key (every parent gets a
  list); `Build` narrows each set's projection to what every instance carries.
- **Display names** (`DisplayNames`, `DisplayNameRule`): spec 0029 §5.2's layout and render;
  `client/projects/core/tellma-core/src/entity/display-name-golden.json` is linked into
  `Tellma.Core.Tests` and pinned by `DisplayNamesTests` (client-only native-digit row skipped).
- **Composition**: `DataComposition` registers the engine, provider, materializer,
  `QueryServices` and `IDisplayNames`; `DataExecutor` carries `QueryServices`;
  `IBatchConnection` gained `Shape` (the factory handle throws, as for `Context`).
- **Fixture**: `fixture.Widgets` gained `OptionalKind varchar(8) NULL` (a nullable enum) and
  `DueOn date NULL`; the fixture migration was regenerated with `dotnet-ef`.

### Rulings and open points for the orchestrator

- `KeysOf` is internal. Spec 0015's pipeline needs a public seam to restrict later statements on
  a `Rows(CaptureKeys)` handle's table.
- The `StringList` collation seam (Msg 468 against a column with an explicit collation) is not
  addressed; `StringList` restrictions work against default-collation columns.
- No startup check compares `QueryexSchemaProvider.Fingerprint` with anything yet.
- The golden's two date rows carry the .NET renderer's output (`3/15/2026`, `15/3/2026`); the
  client renderer must match them when it lands.
- Spec 0012 §13.2's fixture table lacks the two columns added to `fixture.Widgets`; §13.3's
  `DateList` restriction and nullable-enum assertion need them.

**R1-1 (major) — The planner note's Msg 468 seam is not built, and it is not under Deviations.**
CHECKPOINTS.md's PC-033 planner note assigns it here: "StringList.Id takes the database collation,
so a key set over a BIN2 natural key needs a collated list type here" (D-015: "spec 0012 must
honour it"). `Rows`/`Query` pass every `KeySetRestriction` straight to the engine, and the engine
emits `[T].[col] IN (SELECT [Id] FROM @tvp)` with no collation (no `COLLATE` anywhere in
`src/core/Tellma.Core.Queryex`). Failure: a restriction on `core.User.Subject`
(`varchar(255)`, `[Collation(DatabaseCollations.Binary)]`,
`src/core/Tellma.Core.Abstractions/Access/User.cs:58`) through a `StringList` TVP compares a BIN2
column with a TVP column in the database collation, and SQL Server fails the batch with Msg 468
at execution. The integration test only restricts `Widgets.Code`, which has the default
collation. The implementer lists this as an open point, but PLAN.md §7.1 item 1 requires a
planner note left out to be justified under **Deviations** in the commit message, and it is not
there. Fix: carry each column's explicit collation from the EF model into the schema (on the
property or its store type), and have the restriction's lowering emit
`SELECT [Id] COLLATE <collation> FROM <source>` (or bind a collated list type). Add an
integration test that restricts `core.Users.Subject`, which the fixture composes, through a
`StringList`. If it is deferred instead, record it under Deviations and get an orchestrator
ruling that names the owning checkpoint.

**R1-2 (major) — A grouped `Rows` refuses `CountCap`, which spec 0015 and spec 0016 pass for an
aggregate query.** `DataBatch.Queries.cs:59-65` throws `ArgumentException` when
`spec.Aggregate && options.CountCap is not null`. Spec 0016's `QueryRequest` carries
`Aggregate` and `IncludeCount` independently ("the capped count in the same round trip"). Spec
0015 §5.2 step 5 always appends `Rows(spec, arguments, RowQueryOptions { CountCap = IncludeCount ?
CountCap : null, … })` with `Aggregate` as sent. So a valid `aggregate=true&includeCount=true`
request becomes a compose-time `ArgumentException`, which is a composer bug and therefore a 500.
The deviation's reason ("those apply to rows of an entity") holds for `CaptureKeys` and
`IncludeAncestors`, which need a root key, but not for a count. For a grouped page the count of
groups is well defined: `SELECT COUNT(*) FROM (<grouped body, Take = cap + 1>) AS [q]`. Fix:
support `CountCap` on a grouped spec by counting its groups. Keep the refusal for `CaptureKeys`
and `IncludeAncestors`. The standalone `Count` (`DataBatch.Queries.cs:103-106`) may keep its
refusal, since §5.2 defines it over `Select = "Id"`. Otherwise, take the
spec 0015/0016 misalignment to the orchestrator, so that 0015 refuses the combination with a 400
before it reaches the batch.

**R1-3 (minor) — An entity query that selects the tree node compiles and runs, then fails in the
materializer after the round trip.** The schema declares the shadow `Node` as a property
(`QueryexSchemaProvider.cs:265-269, 307`). Entity metadata omits shadow properties
(`EntityMetadataBuilder.Parts.cs:364`). `Completion` (`DataBatch.Queries.cs:467-509`) and
`ComputedItem` therefore accept `Query<Node> { Select = "Code, Node" }` (or `"Parent.Node"`). The
batch executes, and then `EntityMaterializer.Property` (`EntityMaterializer.cs:246-250`, reached
from lines 82 and 100) throws `InvalidOperationException` from inside the last reader. A select
that `Query` cannot materialise is a compose-time refusal, by the same rule the computed-item
check applies. Fix: in `Completion`, refuse with `ArgumentException` any discovered path whose
last segment is not a metadata property of its entity. Add a unit test.

**R1-4 (minor) — After key capture, the page loses the deterministic tie order the paged twin
used.** `Restricted` (`DataBatch.Queries.cs:343-346`) drops paging, and the engine adds its key
tiebreak only to a paged ordering. The golden shows this: the twin orders
`[T].[Name] ASC, [c0] ASC` (`QueryStatementTests.cs:72`) while the page orders `[c0] ASC` only
(`:86`). Failure: a grid request with `IncludeAncestors` makes spec 0015 set `CaptureKeys`. Its
rows that tie on the sort column then come back in an arbitrary order, which can differ between
executions and from the same request without ancestors, whose order is broken by `Id`. The root
page of an entity query with children (`Query`) and the ancestors' read have the same issue.
Fix: give the page the twin's tiebreak, for example by appending the root key to `OrderBy` when
the ordering does not already end in it, or by asking the engine for its paged tie-break on an
unpaged compile. Pin the tiebreak in the golden.

**R1-5 (minor) — The `Recompile` composition paths are untested.** WATCHLIST (0012, "PC-012 →
spec 0012's batch composers") singles out exactly these composers. The new code handles
`CompiledQuery.Recompile` in three hand-written forms:
- the keys twin (`DataBatch.Queries.cs:561`);
- the capped count (`:595`);
- `Assert`'s count-into-a-variable form (`:183-192`).

No unit golden compiles a spec whose filter sets `Recompile`. A regression that drops the hint,
puts it inside the derived table or after the `IF`, or declares `@tb{b}_count` twice would pass
every test. Fix: add goldens for `Rows(CaptureKeys, CountCap)` and `Assert` over a filter that
reads a computed variable, for example a `'uq'` calendar function, which `QueryModel` already
compiles.

**R1-6 (minor) — §11.1's absences have no test that would fail if they broke.**

`byte[]`, `TimeOnly` and `double` columns and a filtered unique index, assert the column

### Responses

- **R1-1: fixed, through `COLLATE` on the list's side.** The restriction is now written
  `[T].[col] IN (SELECT [Id] COLLATE <collation> FROM @list)` when the column declares its own
  collation.
  - *Why the list's side rather than a collated list type.* The column stays bare, so its index
    still serves a seek. The text depends only on the schema, never on the call, so the plan stays
    cacheable. One `StringList` serves every text column. A collated list type would need one type
    per collation, and each caller would have to pick the right one per column; a wrong pick is
    still Msg 468. Putting `COLLATE` on the column's side would make the predicate non-sargable.
  - *Engine amendment, in the frozen package.* `PropertyDescriptor.Collation` and
    `EntityBuilder.Property(..., collation:)` are new. The builder refuses a collation on a
    non-text property and any name that is not `[A-Za-z0-9_]{1,128}`, because the name reaches
    the SQL as written. `PlanEmitter.WriteKeySetRestriction` emits the clause.
  - *How the provider finds the collation.* It reads each column's own `[Collation]` off the
    property, the way `CollationConvention` applies it. EF's runtime model keeps no collation:
    `GetCollation()` throws on a `RuntimeProperty`. The schema fingerprint now includes the
    collation. ARCHITECTURE.md (table types) records the choice.
  - *Tests.*
    - Engine: `Emit/CollatedKeySetTests`, covering the root, a navigation, the refusals and the
      default.
    - Statement: `A_restriction_on_a_column_of_its_own_collation_converts_the_keys_to_it`.
    - Provider: `A_column_that_declares_its_own_collation_carries_it_and_others_carry_none`.
    - Integration: `A_text_list_restricts_a_binary_collated_column_by_its_exact_bytes` restricts
      `core.User.Subject` through a `StringList`. The seed adds users 2 and 3 with subjects
      `Sub-A` and `sub-a`, and the test expects exactly user 2. With the emitter's `COLLATE`
      switched off, this test fails with "Cannot resolve the collation conflict between
      Latin1_General_100_CI_AS and Latin1_General_100_BIN2".
- **R1-2: fixed.** A grouped `Rows` with `CountCap` counts its groups:
  `SELECT COUNT(*) FROM (<grouped body, ordered, FETCH NEXT cap + 1>) AS [q]`.
  - An unordered grouped spec cannot be limited, because the language refuses a `Take` without
    an ordering. Its groups are counted whole, and the count is capped to cap + 1 as it is read.
    The server computes every group either way.
  - `CaptureKeys` and `IncludeAncestors` are still refused on a grouped spec, and the standalone
    `Count` still refuses one.
  - Tests: the unit golden `A_grouped_page_counts_its_groups_up_to_the_cap_plus_one`, which also
    pins `@qx1_take = 101`, both refusals and the unordered count's text, and the integration test
    `A_grouped_page_counts_its_groups`. That test expects two groups, two again when capped at
    one, and an unordered page of three groups capped at one to read two. Before the fix, both
    tests failed on the refusal.
- **R1-3: fixed.** `Completion` refuses, at compose time, a select path whose last segment is not
  a property of its owner's class, with an `ArgumentException` that names the path. Test:
  `An_entity_query_refuses_a_column_its_class_does_not_hold_and_a_rows_query_reads_it` covers
  `Code, Node`, `Zone.Node` and `Parent.Node`, checks the batch stays empty, and checks that
  `Rows` still reads `Node`.
- **R1-4: fixed.** The restricted page (`Rows` and `Query`'s root), a grandchild read and the
  ancestors' read now order by the spec's ordering with the root key appended, unless the
  ordering already ends in the key.
  - An unordered spec stays unordered. The language refuses to page one (QX4006), so it never had
    a paged order to keep.
  - The goldens now pin `ORDER BY [c0] ASC, [T].[Id] ASC` on the page and on the ancestors.
    `A_captured_page_ordered_by_its_key_or_unordered_gets_no_second_tiebreak` pins both
    exceptions.
- **R1-5: fixed.** `A_recompiled_filter_keeps_its_hint_on_each_statement_that_reads_the_body`
  pins three goldens, using `DueOn >= startOfMonth(today(), 'uq')`. A `year(..., 'uq')` filter
  sets no hint, because only a computed variable does.
  - The keys twin: its `DECLARE`s, then `INSERT … OPTION (RECOMPILE)`.
  - The capped count: the hint after the derived table.
  - `Assert`: one `DECLARE @tb0_count`, the count assigned under the hint, then the `IF … THROW`.
- **R1-6: fixed.**
  - `Gadget` gains a `byte[]`, a `TimeOnly`, a `double` and a binary-collated `Serial` with a
    filtered unique index.
  - `Columns_the_language_cannot_read_are_absent_and_a_filtered_unique_index_counts_as_unique`
    asserts the three absences and `IsUnique`.
  - The theory `A_store_type_the_language_has_no_type_for_maps_to_nothing` covers `varbinary`,
    `binary`, `time`, `float`, `real`, `sql_variant` and `xml`.
  - `Platform_secrets_are_withheld` now asserts both `core.Job` rows through
    `QueryexSchemaProvider.IsWithheld`.
- **R1-7: fixed.**
  - `A_query_call_over_the_parameter_budget_leaves_the_batch_as_it_was`: a 1,100-item list makes
    the twin and the count cross 2,000 parameters together. The call throws and `Statements`
    stays empty. A 500-item list then lands at ordinals 0–2.
  - The integration test `A_rows_query_reads_a_nodes_position_as_its_path` reads `/1/`, `/1/1/`,
    `/1/1/1/`, `/2/` and `/1/2/`.

  `tokens:build-css`, `lint`, `typecheck` and `build`.
