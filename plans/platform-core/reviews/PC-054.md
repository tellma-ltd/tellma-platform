# PC-054: scrollToRow and remembered tree expansion

## Implementer notes

### What was built, and where

All client-side, in `client/`:

- **`scrollToRow`** (spec 0010 §C.8).
  - `TmGridBase.scrollToRow(rowId, { flash, activate, align, column })` in `projects/core/tellma-core-ui/grid/tm-grid-base.ts` delegates to `ɵTmGridCore.scrollToRow` in `grid/internal/grid-core.ts`.
  - A tree expands the row's ancestors first, through `keepActiveRow` so the active cell stays on its row, then folds them into the kept expansion (`syncExpansion`). In the `'model'` source they emit.
  - It never requests focus. `activate` (the default) moves the active cell and collapses the selection to it.
  - `column` resolves a column key. An unknown key keeps the current column and warns in dev mode.
  - The reveal is a `revealTarget` consumed by `revealActiveCell`. The vertical row math moved into a shared `scrollRowIntoView(scroller, row, center)`, which `revealFindRow` now uses too. A far target's horizontal reveal takes a second pass, because its row renders only after the scroll.
  - The flash is a `flashRowId` signal, keyed by row id, and the row view model carries `flash`.
    - The view binds `tm-grid__row--flash`. Its CSS is in a new `grid/internal/grid-flash.css`, because grid-view.css sits near the per-file style budget.
    - A timer clears it after the `--grid-flash-duration` token, read from the host's computed style.
    - Under reduced motion the animation uses `step-end` (the tint holds, then clears). Under forced colors the row gets an outline.
  - Tokens `grid.flashBg: '{status.info.bg}'` and `grid.flashDuration: '1200ms'` are in `tellma-core-ui-tokens/presets/tellma-default.ts`. The Identity `tokens.css` was refreshed.
- **Remembered expansion** (spec 0010 §C.9).
  - `TmTreeGrid` gains `expansionSource` (`'store' | 'model'`) and the `expandedIds` model, and `loadChildren` is now `(rows: readonly T[]) => Promise<void>` (`tree-grid/tm-tree-grid.ts`). `ɵTmGridTreeConfig` carries the two new members.
  - The core keeps one unpruned set, `expansion`, for the bound content: the model's set, or the store slice, or a seed.
    - `bindExpansion` reads `expansionSource` at content bind. `applyExpansion` hands it to `engine.restoreExpansion`, which keeps the present, expandable part, and queues children loads.
    - `syncExpansion` (an effect, plus explicit calls) folds expansions the engine made itself into the kept set: find, error jumps, undo reveals, inserted children, and scrollToRow. Removals are explicit only: a user collapse, or a failed batch.
    - A consumer write in `'model'` replaces the set and applies like a restore. It is not echoed (`expansionWritten`).
    - `'store'` persists a copy of the kept set. `'model'` leaves the slice as stored.
  - Batching (`queueLoads` → microtask `flushLoads` → `settleLoads`):
    - one `loadChildren` call per task, holding the queued rows that are present, expanded, `hasChildren`, not loading and without a loaded child, in model order;
    - the three moments: the bind (`applyExpansion(true)`), the rows a resolved batch brings (via `syncRows` → `applyExpansion(false)`), and same-task user expands;
    - the generation guard drops stale completions on a content switch or destroy;
    - a rejection collapses the batch's rows, drops them from the kept set (emitting), and announces once.
  - `syncRows()` replaces the old first-rows flag and `applyPendingRestores`. It reconciles once per rows array, then re-applies the kept expansion and any deferred selection. The paths that change the expansion call it first, so a reconcile never remaps against a post-expansion order.
  - Removed: `treeExpansionPending`, `collapseUnloadedLazyRows`, `wantedExpansionIds`, and the `addTo`/`removeFrom` helpers.

### Deviations

1. **A loading row is `aria-expanded="true"`.** Under §C.9, a user expand adds the id at request time. Spec 0004 §13.3's "expands when the load lands" no longer holds. The re-collapse-during-load and expander-glyph code lost their pending-intent special cases.
2. **The `'store'` source keeps its slice unpruned too.** Only the bound set's unpruning is specified. Pruning the store slice would forget a remembered grandchild exactly as the model source must not, so both sources share one kept set. The `expandedRowIds` contract TSDoc was updated to match.
3. **`data-tm-key` on row elements.** `getExpandedIds()` needs row ids, and the DOM carried none. The method returns the expanded rows that are rendered, in view order, and its TSDoc says so.
4. **The lazy-gesture e2e tests moved.** The tree-grid story now loads its lazy root at mount (moment 1), so its spinner, re-collapse and failure e2e tests moved to the new restore story's spec. The tree-grid spec keeps a bind-load test, and its row counts went from 60 to 63.
5. **The flash CSS lives in `grid-flash.css`.** It is a third stylesheet on the view, because of D-060/D-067's per-file style budget.

### Open risks

- (Resolved in review 1, R1-3.) Re-flashing the row that is already flashing used to restart only the timer.
- `syncExpansion` relies on the expansion-sync effect, created after the store and rows effects, to fold in engine-made expansions. Paths that persist or apply explicitly call it first. Effect ordering within one flush is creation order.
- A store-kept content switch with no slice still seeds over whatever rows are bound at the switch (unchanged behaviour). Review 1's R1-8 fix defers only the loads. Deferring the seed too broke contents that share one rows array (see R1-8's response).
- R1-8's deferral is keyed on rows-array identity. A content switch that keeps the same rows array on purpose gets its remembered lazy rows' loads only at its next rows array. Until then those rows show expanded, with no children and no spinner.

### Findings

**R1-1 (major): `scrollToRow` called as §C.8 prescribes loses to the remembered scroll restore.**
`client/projects/core/tellma-core-ui/grid/internal/grid-core.ts:2051` (`scrollToRow`), with the reveal `afterRenderEffect` at `:6373` and the persisted-scroll restore `afterRenderEffect` at `:6429`.

Scenario:
- A content was visited before, so its state slice holds `scroll`. `restoreState` sets `pendingScroll`, and the restore waits for `totalHeight > 0`, that is, for the rows.
- The rows arrive. The consumer calls `scrollToRow(42, { flash: true })` from an effect on those rows, as §C.8's Timing note and spec 0031's deep link do.
- In the same render, the reveal effect runs first (it is registered first) and centres row 42. Then the restore effect finds `pendingScroll` set and `totalHeight` non-zero, and writes the remembered `scrollTop` over it.
- Result: the active cell is on row 42, but the view shows the old position. The flash plays off-screen and the deep link does not land.
- A content switch with `scrollToRow` in the same tick does the same with the `{ x: 0, y: 0 }` origin restore.

No unit or e2e test covers `scrollToRow` with a remembered scroll.

Fix: an explicit reveal supersedes a remembered position. In `scrollToRow`, drop `this.pendingScroll` (about 10 B). Add a unit test: persist a scrolled state for the content, remount with rows set asynchronously, call `scrollToRow` from an effect on the rows, and assert that the row is in view.

**R1-2 (minor): `flushLoads` can steal and drop the incoming content's first batch.**
`grid-core.ts:4544-4555` (`flushLoads`) and `:4521` (`queueLoads`).

Scenario:
- A queue forms (gen N, microtask M1 scheduled).
- In the same task the content switches. `resetContentTransientState` nulls `loadQueue` and bumps the generation.
- `bindExpansion` → `applyExpansion(true)` forms a new queue and schedules M2 (gen N+1).
- M1 runs: it takes the new queue, sets `loadQueue = null`, then returns on the generation mismatch. M2 finds `null`.
- The incoming content's bind batch is lost. Its rows stay expanded with no children, no spinner and no load until the user collapses and re-expands each one.
- In production a click's microtask usually drains before change detection, so this needs a synchronous switch. A test calling `detectChanges()` or a consumer switching `contentKey` from an `expandedIdsChange` handler hits it.

Fix: test the generation before touching the queue (return before `this.loadQueue = null` when `generation !== this.lazyLoadGeneration`), or keep the generation with the queue.

**R1-3 (minor): re-flashing a row that is already flashing does not replay the flash.**
`grid-core.ts:2095-2106` (`flash`) and `grid/internal/grid-flash.css:16-31`.

- `endFlash()` and then `flashRowId.set(rowId)` within one tick leave the class on the element, so the CSS animation never restarts.
- Under full motion the second flash is invisible.
- Under reduced motion, the `step-end` tint clears when the first animation ends, while the class (and `isRowFlashing`) stays on for the restarted timer.
- Reachable when a deep link or "show again" action fires twice within 1.2 s. The implementer listed it as an open risk.

Fix: alternate between two keyframe names on a re-flash of the same id (a `flashOdd` flag bound to an animation-name toggle), or clear `flashRowId` and set it again after the next render (`afterNextRender`).

**R1-4 (minor): the budgetNotes entry and the implementer notes misstate the headroom.**
`client/projects/core/tellma-core-ui/package.json` (the `./grid` budgetNotes entry) says the measure "leaves 0.06 KB under the 42 hard cap". The measured 41.84 KB (42,840 B, which I reproduced from a clean build) sits 168 B (0.16 KB) under 43,008 B. It is the 41.94 ceiling that sits 0.06 under the cap.

Fix: say "41.84 measured, 0.16 KB under the 42 cap; ceiling 41.94, 0.06 under it".

**R1-5 (minor; decision for the orchestrator): the tree-only expansion machinery is about 0.8 KB of `./grid` that every flat grid pays.**
Stubbing `setRowExpanded`, `syncExpansion`, `emitExpansion`, `applyExpansion`, `keepActiveRow`, `queueLoads`, `flushLoads`, `settleLoads`, `bindExpansion` and `persistedExpansion` in the built FESM takes the linked measure from 42,840 to 42,016 B (−824 B). The two tree effects and the tree branch of `syncRows` add a little more. The flash path is 136 B and belongs in `./grid`.

- `ɵTmGridTreeConfig` already carries the tree's bindings from `./tree-grid` (`tm-tree-grid.ts:130-140`).
- An expansion controller built in `./tree-grid` against a narrow core-host interface would hand most of this back to `./grid`. That interface needs the engine, `keepActiveRow`, `syncRows`, the loading-ids signal and the announcer.
- Nothing here breaks D-067: the measure is under 42.
- But the 168 B left must absorb this round's fixes, and every later `./grid` change outside §C.15's +1 KB needs a re-split under D-057(2).
- My recommendation: move it in this checkpoint's fix round, or record a fix item before the next `./grid` change.

Suggest remounting a store-kept lazy tree whose slice holds a grandchild id and asserting the level-2 batch and the slice after the remount.
- (b) The far-target second pass in `revealActiveCell` (`grid-core.ts:5530` onward, the `requestReveal()` in the `element === null && target !== null` branch) is never exercised. **R1-8 (minor): binding over the outgoing content's rows now issues `loadChildren` for them.**
`grid-core.ts:5857` (`bindExpansion`) → `:4429` (`applyExpansion(true)`).

Scenario:
- A tree switches `contentKey` while its rows signal still holds the outgoing content (the consumer fetches the new rows asynchronously).
- The bind restores the incoming set over the old rows, and `applyExpansion(true)` queues every applied id.
- Any old row whose id appears in the new set, has `hasChildren` and no loaded child is sent to `loadChildren` under the new generation, so its completion is accepted.
- This happens when ids overlap across contents, such as the same tree under different filters or options keyed as separate contents. The consumer then fetches and appends children for rows of a content it has left.
- Before this change a restore over old rows only collapsed unloaded lazy rows and never loaded. The store variant (seeding over old rows) is listed in the open risks; the load is new.

Fix: when the content switches while `rows` is still the array reconciled for the outgoing content, apply the bound set but defer its loads to the first new rows array (`syncRows` then runs the bind's `applyExpansion(true)`).
