### Deviations

1. **Declared options are validated by `core.options`, not the host's `ValidateOnStart`.** The host
   runs `ValidateOnStart` validators before any hosted service's `StartingAsync` and aborts at the
   first failure, so an invalid option would hide every other startup problem, against the
   aggregated realised gate. Options are bound with `ValidateDataAnnotations` and validated by the
   gate; `OptionsRegistrar.Bind<T>(path, "core")` is the seam the §8 platform options use.
2. **The §8 platform options are not bound yet.** No consumer exists; each lands with its checkpoint
   through `OptionsRegistrar`. `core.public-origin` reads `Tellma:PublicOrigin` from configuration.
3. **Contributions are collected before the graph gate.** `Contribute` is data-only, so each
   feature's items are collected right after the declarations and realised later in topological
   order. That is what lets a nested feature (`contribution.Feature(...)`) be "validated and ordered
   with the rest" as §2.1 requires; the spec's order (gate, then `Contribute`) cannot validate one.
   A nesting feature is realised after what it nests, as if it required it.
4. **Extra graph-gate problems**: a feature name outside the lowercase-dotted grammar, a second leaf
   for one default (`UseEntity` twice with different leaves, a rule of 0012 §3.x that the builder
   cannot otherwise represent), an environment name that makes no `DeploymentIdentity`, and the
   unknown-item problem, detected at collection so it aggregates with the graph problems.
5. **Realisation problems also throw from `AddTellma`**, after a clean graph gate; `Validate`
   returns them too (it runs realisation into a throwaway collection, still host-free). The spec
   limits `Validate` to steps 1–3.
6. **`[CollectionService]`** (new, Abstractions) marks the collection service types instead of a
   hard-coded list; `IStartupCheck` and `IClientAssetContributor` carry it. The owners of
   `IRequestContextInitializer`, `ITenantStateListener`, `ISessionTerminationListener`,
   `IAccessCriteriaProvider` and `INotificationChannel` must put it on their interfaces.
7. **Contract details the sketches leave open**: `IStartupCheck.CheckAsync` takes a
   `CancellationToken`; `FeatureDeclaration.RequiredFeatures` is get-only and an `OptionsBindings`
   list is added; `RealizationContext` has `Report(problem)` (its `Problems` is read-only);
   `ClientAssetContext` captures each section's JSON at once and exposes `Sections`/`Files`;
   `TellmaStartupGate.RunChecksAsync(provider, includeInfrastructure, ct)` is public for the
   migrator's `emit-client-assets`; `ITellmaFeature.Declare` suppresses CA1716 (a VB keyword).
8. **`core.taxonomy` finds the repository root** as the nearest ancestor of the content root with a
   `.git` entry (directory or worktree file); outside a repository it reports nothing.
9. **Built-in checks are registered before contributed ones**, so `core.*` problems come first.

### Findings

**R1-1 (minor) — a non-collection service registered by two unrelated features resolves silently
by add order.** `src/core/Tellma.Core/Composition/Realizers/ServiceContributionRealizer.cs:43`.
Replacement fires for any later-realised feature, not only for one that requires or nests the
earlier one. Scenario: a distribution adds packs `sales` and `inventory` (unrelated), and both
contribute `Scoped<IStockPolicy, …>()`. Whichever was added second wins, with no problem reported.
Swapping two `AddFeature` lines then changes behaviour. The spec grants the override only to "a
dependent feature" over "its dependency's" (0011 §2.1). The same silent win applies over a
registration the composition method made on `tellma.Services` (the realised one is added later).
Fix: when replacing, check that the replacing feature transitively requires or nests the replaced
one. If it does not, report a `core.composition` problem naming both features and the service type,
with the fix "require the feature whose service you replace, or register a different type". Add a
test for each outcome. If unrelated collisions should stay legal, record the add-order rule as a
deviation instead (the open risk already asks this).

**R1-2 (minor) — framework collection types cannot carry `[CollectionService]`, so a second
feature's `IHostedService` drops the first.**
`src/core/Tellma.Core/Composition/Realizers/ServiceContributionRealizer.cs:35` and
`IsCollectionService` (line 117). A feature never sees `IServiceCollection` (0011 §2.1), so
`Singleton<IHostedService, T>()` is the only way a pack contributes a background service. The host
resolves `IHostedService` as a collection, but the attribute can only mark Tellma's own interfaces.
Scenario: two packs each contribute a hosted service, and the first is removed from the collection
without any problem. The fixed list that deviation 6 replaced had the same hole. The attribute makes
it permanent for every BCL extension point (`IHostedService`, `IConfigureOptions<>`,
`IPostConfigureOptions<>`, `IValidateOptions<>`). Fix: treat a small built-in set of framework
collection types as collection services as well as the marked types, or report a problem when a
feature contributes one of them. Add a test with two features contributing `IHostedService`.

**R1-3 (minor) — "one message line per problem" breaks on a multi-line problem text.**
`src/core/Tellma.Core.Abstractions/Composition/TellmaCompositionException.cs:47` (with
`CompositionProblem.Describe`, `CompositionProblem.cs:32`). The gate embeds
`exception.Message` from a throwing check (`TellmaStartupGate.cs`, the catch in `RunChecksAsync`).
Messages such as `SqlException.Message`, which joins several server errors with newlines, span
lines. The rendered message then has more lines than problems, against 0011 §2.1 ("one message line
per problem") and the line-count assertion that
`GraphGateTests.Every_problem_is_thrown_at_once_in_one_exception_with_one_message_line_each`
relies on. Fix: in `Describe` (or the record's constructor), collapse `\r\n`, `\r` and `\n` to a
single space. Add a test with a check that throws an exception whose message has a newline.

**R1-4 (minor) — one startup check that fails to construct discards every other check.**
`src/core/Tellma.Core/Composition/TellmaStartupGate.cs:55-66`. `GetServices<IStartupCheck>()` is
resolved in one call. A single contributed check with an unresolvable dependency turns the run into
one "could not be created" problem, and the built-in `core.*` checks never run, which defeats the
aggregation the gate exists for. A constructor exception other than `InvalidOperationException`
(for example an `ArgumentException` thrown by the check's own constructor) escapes raw instead of as
a `TellmaCompositionException`. Fix: catch every non-cancellation exception there. Also run the
built-in checks even when the list fails: they are instances the pipeline creates, so the record can
hold them. Add a test with one unconstructible contributed check beside a failing built-in one.

**R1-5 (minor) — the platform-options seam silently keeps the first path for a type bound twice.**
`src/core/Tellma.Core/Composition/OptionsRegistrar.cs:55`. `Bind<TOptions>` deduplicates by type
alone. The comment there says the graph gate already refused different paths, but the gate only
compares feature declarations. The `Bind<T>(path, "core")` seam that deviation 2 reserves for the
§8 platform options bypasses it. Scenario: a later checkpoint binds `SqlOptions` from `Tellma:Sql`
while a feature declares it from `Tellma:Data`. One binding is dropped without a word, and the
options read the wrong section. Fix: when the type is already bound, compare the path
(OrdinalIgnoreCase) and report or throw on a mismatch. Add a unit test through the seam.

**R1-6 (minor) — `core.public-origin` refuses a trailing slash, which the spec does not, and the
commit lists no deviation for it.**
`src/core/Tellma.Core/Composition/Checks/PublicOriginCheck.cs:72` (`value.EndsWith('/')`), tested
at `PublicOriginCheckTests.cs:24`. 0011 §2.3 fails the check when the origin "carries a path". A
bare `https://acme.app.tellma.com/` has the root path `/`, so `Uri` reports no path, yet it fails
startup. The rationale (concatenation would double the separator) is reasonable, but PLAN §7.1(1)
requires such a choice under Deviations. Fix: either add the deviation, with the README table
wording, or accept the trailing slash and have consumers read a normalised origin (one accessor
that trims it).

**R1-7 (minor) — the §1.1 package edges of `Tellma.Core` are deferred without a deviation.**
`src/core/Tellma.Core/Tellma.Core.csproj:13-22`. The checkpoint's sections include "§1.1 (pins,
package edges)". The table there gives `Tellma.Core` edges to `Tellma.Core.EntityFrameworkCore`,
EF Core SqlServer (+ HierarchyId), `Microsoft.Data.SqlClient`,
`Microsoft.AspNetCore.DataProtection.Abstractions`, Cronos, OpenXml and MessageFormat. None is
added, and the commit's Deviations do not say so. Not adding unused references is right. Fix: add
one Deviations line saying that each edge lands with its first consumer (0012-a for EF and
SqlClient, and so on), so the PLAN §7.1(1) audit sees it.

**R1-8 (minor) — nothing pins `IClientAssetContributor` as a collection service.**
`src/core/Tellma.Core.Abstractions/Client/IClientAssetContributor.cs:20`. 0024 §3.2 requires that
"each registration adds one contributor, and none overrides another". `IStartupCheck`'s attribute
is pinned indirectly: two checks from one feature in `StartupGateTests` would collapse to one
without it. The only `[CollectionService]` test uses the sample `ISampleExtension`, so deleting the
attribute from `IClientAssetContributor` fails no test. Fix: assert in
`Tellma.Core.Abstractions.Tests` that both `IStartupCheck` and `IClientAssetContributor` carry
`CollectionServiceAttribute`, or add a realisation test with two features each contributing an
`IClientAssetContributor`.
