### Deviations

1. **Declared options are validated by `core.options`, not the host's `ValidateOnStart`.** The host
   runs `ValidateOnStart` validators before any hosted service's `StartingAsync` and aborts at the
   first failure, so an invalid option would hide every other startup problem, against the
   aggregated realised gate. Options are bound with `ValidateDataAnnotations` and validated by the
   gate; `OptionsRegistrar.Bind<T>(path, "core")` is the seam the §8 platform options use.
2. **The §8 platform options are not bound yet.** No consumer exists; each lands with its checkpoint
   through `OptionsRegistrar`. `core.public-origin` reads `Tellma:PublicOrigin` from configuration.
3. **Contributions are collected before the graph gate.** `Contribute` is data-only, so each
   feature's items are collected right after the declarations and realised later in topological
   order. That is what lets a nested feature (`contribution.Feature(...)`) be "validated and ordered
   with the rest" as §2.1 requires; the spec's order (gate, then `Contribute`) cannot validate one.
   A nesting feature is realised after what it nests, as if it required it.
4. **Extra graph-gate problems**: a feature name outside the lowercase-dotted grammar, a second leaf
   for one default (`UseEntity` twice with different leaves, a rule of 0012 §3.x that the builder
   cannot otherwise represent), an environment name that makes no `DeploymentIdentity`, and the
   unknown-item problem, detected at collection so it aggregates with the graph problems.
5. **Realisation problems also throw from `AddTellma`**, after a clean graph gate; `Validate`
   returns them too (it runs realisation into a throwaway collection, still host-free). The spec
   limits `Validate` to steps 1–3.
6. **`[CollectionService]`** (new, Abstractions) marks the collection service types instead of a
   hard-coded list; `IStartupCheck` and `IClientAssetContributor` carry it. The owners of
   `IRequestContextInitializer`, `ITenantStateListener`, `ISessionTerminationListener`,
   `IAccessCriteriaProvider` and `INotificationChannel` must put it on their interfaces.
7. **Contract details the sketches leave open**: `IStartupCheck.CheckAsync` takes a
   `CancellationToken`; `FeatureDeclaration.RequiredFeatures` is get-only and an `OptionsBindings`
   list is added; `RealizationContext` has `Report(problem)` (its `Problems` is read-only);
   `ClientAssetContext` captures each section's JSON at once and exposes `Sections`/`Files`;
   `TellmaStartupGate.RunChecksAsync(provider, includeInfrastructure, ct)` is public for the
   migrator's `emit-client-assets`; `ITellmaFeature.Declare` suppresses CA1716 (a VB keyword).
8. **`core.taxonomy` finds the repository root** as the nearest ancestor of the content root with a
   `.git` entry (directory or worktree file); outside a repository it reports nothing.
9. **Built-in checks are registered before contributed ones**, so `core.*` problems come first.

### Open risks, and what to examine hardest

- The service replacement rule in `ServiceContributionRealizer`: only feature-realised descriptors
  are removed; host registrations stay. Two unrelated features registering one service type resolve
  to the one added later, silently. Is that acceptable, or should it be a problem?
- The order and aggregation in `CompositionPipeline.Collect`/`CheckGraph` and the gate-first
  insertion (`services.Insert(0, …)`) under `HostApplicationBuilder` and `WebApplicationBuilder`.
- `IcuProbe` (sort-version heuristic from the .NET globalization docs) on Linux CI.
- `TellmaStartupGate.RunChecksAsync`'s exception filter (a check's `OperationCanceledException` is
  reported unless the run itself was cancelled).
