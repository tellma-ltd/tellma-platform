# PC-069: tm-boot.js, boot page, session and launch mark

## Implementer notes

### What was built, and where

All client paths are under `client/projects/core/`.

- **The boot decision** (`tellma-core/src/boot/`): `tmBoot(env)` in `tm-boot.ts`, a pure function

### Deviations

1. **3 KB holds with English strings only.** The template is about 2.85 KB gzip; rendered with the
   platform's English strings it is about 3.05 KB, under 3 KB (3,072 B). Each further language
   adds its strings: English plus Arabic is about 3.37 KB, plus Amharic about 3.70 KB. The test
   asserts the English-only figure. Getting here took deliberate size work (no `?.`/`??` in the
   bundled modules, which ES2017 would lower, shared JSON/storage helpers, reflected DOM
   properties). Spec 0024 §4.2 should say whether 3 KB covers the code with English strings or
   the whole file per distribution.
2. **`__tmBoot.showPage(reason, retry?)`** is added to the result, so the app shows the
   `load-failed` page (§4.3) in the boot language without bundling the page builder.
3. **3c clears the record's `sub` and `lastTenantId` before the delete starts**, not after: a
   delete cut short by the box or a closed tab still leaves a record naming no user, and the
   store's boot step then sweeps.
4. **A path no browser reads as local** (`//host/...`, or with a tab or line break) is treated as
   `/` in 3d and in `signIn()`. `tmIsLocalPath` also refuses tab, CR and LF anywhere.
5. **The profile cookie also needs a non-empty `sh`** (the spec lists only decode, `v` and `sub`):
   the session partition is named by it. A correctly padded value is accepted.
6. **`signIn()` keeps `location.hash` only when `returnUrl` is the current path and query**; a
   fragment belongs to the page it was on. It throws on a non-local `returnUrl` or a malformed
   step-up challenge (empty `acr`, `maxAge` not a non-negative integer).
7. **`check()` updates `profile`** when the same user's cookie carries new details (name, email,
   locale, `sh`).
8. **Interim paths.** `signOut()` is not here (§8.4 needs the tab bus, drafts and store, a later
   checkpoint). `TmSessionPaths.started` is a no-op (no tab bus), `expired` sets `state` to
   `expired` once, emits `tm.session.expired { source }`, deletes the stale profile cookie and
   reloads, so the boot leads to the sign-in (no store clean-up, broadcast or session-ended dialog
   yet), and `changedUser` emits `tm.session.changed-user` and replaces to `/` (no drafts
   clear or broadcast yet). `TmSession` does not write `boot.patch({ sub })` (the store owns the
   boot record's writer). The full paths replace these bodies, not their call sites.
9. **Language matching** uses the same rule everywhere: exact code, else the same primary subtag
   (for the record, the browser list and the profile locale).
10. **The mark and the record are validated, not rebuilt**, so an extra member written by this
    origin survives (size budget). The profile, which comes from the server, is rebuilt with known
    members only.
11. The renderer refuses a configuration the script would trust blindly (see above); the spec only
    describes the replacement.
12. **`@tellma/core` packaging:** `@angular/router` becomes a peer dependency (the guard and
    `TmLaunch`), and the `"."` entry point's size budget rises from 4.5 to 6.5 KB (measured 4.32
    before, 6.34 after review 2), with the reason and the savings taken in `budgetNotes`.

### Open risks

- The size budget is tight: about 20 bytes of headroom with English strings. Any change to the
  bundled modules (`tm-profile`, `tm-login-mark`, `tm-boot-record`, `tm-storage-json`,
  `tm-store-layout`, `src/boot/*`) moves it; the node test fails first.
- ES2017 is a target, not a guarantee: a browser older than that sees a blank page instead of the
  unsupported page.
- `__tmBoot` holds the profile (name, email) on `window`; it is no more exposed than the cookie it
  came from.
- The session's interim paths do not yet broadcast or clean the store; until the tab bus lands,
  another tab of the same user learns of an expiry only through its own check.

### What reviewers should examine hardest

- `tmIsLocalPath` and every place a URL is built or followed: `tmLoginUrl`, 3d's `returnUrl`,
  the hash-restore `replaceState`, `signIn()`. The hash restore runs only when
  `path + search === mark.returnUrl`, so a stored `returnUrl` can only ever equal a real pathname.
- The mark and record validators (`isLoginMark`, `isBootRecord`) and the profile decoder against
  hostile stored or cookie values.
- The expiry delete: that it never creates `tm-app`, that its key range cannot reach another user
  whose subject starts with the same characters (the `/` after the subject), and that nothing it
  does can throw out of the boot.
- The boot page: DOM calls only, no `innerHTML`, strings set as `textContent`, so a hostile string
  table cannot inject markup (tested).
- The loop guard's window (`0 ≤ now − at < 60 s`) and that a refused mark write still redirects.

### Findings

**R1-1 (major): the 3 KB boot-script budget is met only by a configuration no real distribution ships.**
- **Where:** `client/tools/tests/boot-template.spec.mts:132-135`, and the "Done when" of PC-069.
- **Problem:** Spec 0024 §4.2 says "a blocking classic script of at most 3 KB gzip", and the checkpoint is done when "the generated script fits in 3 KB gzip". The test asserts only an English-only rendering. Measured at gzip level 9 (§12's level), Acme's real en+ar output is 3,389 B, over 3,072 B, and en+ar+am is 3,712 B. The template alone is 2,863 B, so each language's boot strings (about 320 B) cannot fit in the remaining room.
- **Failure scenario:** every multi-language distribution, Acme included, ships a `tm-boot.js` over the spec's figure. No test watches the configuration that actually ships, so growth in the shared modules (`tm-profile`, `tm-login-mark`, `tm-boot-record`, `tm-storage-json`, `tm-store-layout`) or in the Arabic strings can push Acme's output higher with nothing failing. The 20 B of English-only headroom only guards a configuration nobody ships.
- **Why this needs a ruling:** D-031 covers package entry-point ceilings, not this spec figure, so the implementer cannot settle it alone.
- **Suggested fix:** get an orchestrator ruling first. One option is "3 KB for the code with English strings, plus at most 0.4 KB per further offered language". Then keep the English-only assertion and add a second one on Acme's real configuration (en+ar, from `Strings.ar.resx`) against the ruled ceiling. Record the ruling as a spec deviation.

**R1-2 (minor): the "." budget raise does not name the savings it took.**
- **Where:** `client/projects/core/tellma-core/package.json`, `budgetNotes["."]` (the second sentence group, "Raised from 4.5 to 6.5…").
- **Problem:** D-031 lets a checkpoint raise a ceiling by at most what it adds, rounded up to the next 0.5 KB, under three conditions. One is a budgetNotes entry that names the feature, the bytes it adds and the savings it took. The measurement holds: 4.32 to 6.18 KB is +1.86 KB, which rounds to 2.0 KB, so 6.5 KB is within the rule. The note names the weight but takes and records no savings. The previous raise in the same note did name its savings.

- **Suggested fix:** state the savings taken in the note, or state that none were found and what was tried. Candidates are the two `signIn` error messages and the `removeDrafts` loop.

**R1-3 (minor): the interim session gaps have no owner downstream.**
- **Where:** `client/projects/core/tellma-core/src/session/tm-session-paths.ts:34-58` and `src/session/tm-session.ts` (no `boot.patch({ sub })`).
- **Problem:** the deviations are disclosed, but nothing that PC-075 or PC-110 reads assigns the follow-ups:
  - **`sub` is never written.** 0025 §2.6 step 2 says "`TmSession` then patches `sub`", but PC-075's deliverables do not name it. Until someone adds it, every launch with a cookie is cold: the record is reset, `lastTenantId` is lost, and the store's backstop sweeps everything. The 3c expiry delete never runs, because `record.sub` is always null. Warm launch, a §14 Definition-of-Done row, is unreachable.
  - **`expired()` gives the user no way forward.** It only sets `state`, and the guard then denies every navigation. A tab whose cookie lapses becomes a dead end with no UI, and the user's last page stays on screen indefinitely. On the very first navigation the result is a blank page.
  - **Nothing tells a tab another user has signed in.** `changedUser()` and the missing §8.8 triggers mean that when user B signs in elsewhere, a tab of user A keeps showing A's rendered data until A's tab navigates. A's `tm.draft:<A>:*` keys also survive a changed-user restart, because no mark is consumed.
- **Exposure:** nothing ships before PC-110, so production is not affected. But PC-071 onward will render tenant data on `platform-core` while these windows are open.
- **Suggested fix:** the orchestrator adds WATCHLIST lines:
  - PC-075 adds `boot.patch({ sub })` in `TmSession`, strictly after the store boot step's sweep and `readAll`, never at construction, so a crash can never leave `sub = B` beside A's data.
  - PC-110 replaces the `TmSessionPaths` bodies (clean-up, stale-cookie delete, broadcast, drafts clear) and adds the §8.8 triggers.

  Optionally, until PC-110, `expired()` could call `location.reload()`, so the boot's 3c/3d deletes the user's data and offers sign-in instead of leaving a dead tab.

### Findings

**R2-1 (minor): the interim `expired('401')` has no loop guard, and it deletes the cookie unconditionally.**
- **Where:** `client/projects/core/tellma-core/src/session/tm-session-paths.ts:55-66`.
- **Problem:** the boot's loop guard (3b) only catches a sign-in that returns without a cookie. A sign-in that returns with a cookie consumes the mark at step 4. If the API then answers `401` again, `expired('401')` deletes the cookie and reloads, 3d finds no mark and leaves for `/bff/login`, the identity server signs the user in silently, and the cycle repeats with no user action. The spec's path stops at the session-ended dialog, which needs a click; the interim path removed that stop.
- **Failure scenario:** any state where `/bff/login` succeeds and the API still answers `401`: two instances that do not share data-protection keys, a failing session store, or a wrong `401` mapping while PC-071 is being built. Every open tab then cycles through the identity server without end, creates a session per cycle and emits `tm.session.expired` each time. In e2e this shows as a timeout, not as a failure with a cause.
- **Second effect:** the delete is unconditional. Tab 1 gets a `401`, signs in again and receives a fresh cookie. A slow `401` for a request tab 2 sent under the old session then deletes that fresh cookie, and tab 1's next check reads `missing` and reloads into another sign-in.
- **Reach today:** nothing calls `expired('401')` until PC-071, so this is latent.
- **Suggested fix:** break the loop where it starts. When this document itself came back from a sign-in (`TM_BOOT_RESULT.mark` is set) and the `401` arrives within the 60 s window, call `__tmBoot.showPage('sign-in-failed')` instead of reloading; D-048 allows the boot page as the alternative. For the second effect, PC-071 should call `expired('401')` only when the cookie's `sh` still equals the one the request went out under. If neither is fixed here, add a WATCHLIST line for PC-071. A note for the same line: once PC-075 writes `sub`, the reload runs 3c, whose mark carries `expired: true`, so one expiry is reported twice (`cookie` or `401`, then `boot`).

**R2-2 (minor): `TmSession` takes its user from the cookie at first injection, not from the boot script's decision.**
- **Where:** `client/projects/core/tellma-core/src/session/tm-session.ts:66` and `:160-177`.
- **Problem:** the boot script decides warm or cold, the record reset, the `/` rewrite and `auto` for the profile it read (`__tmBoot.profile`). `TmSession` reads the cookie again when it is first injected, which is after the main bundle has loaded. If the cookie changes in between, the tab runs as a user the boot never judged, and `check()` returns `same` from then on.
- **Failure scenario:** a tab boots warm for Farah (the record names her, the address is rewritten to her last tenant, `cold` is false). Before the bundle loads, Sara completes a sign-in in another tab. `TmSession.profile` is Sara, so the guard allows. Spec 0025 §2.6's boot step assumes the record's `sub` is null or the profile's; here it is neither, so no sweep runs, and `TmSession` (PC-075) then patches `sub` to Sara beside Farah's partitions. `#consumeSignIn` also compares the consumed mark with a profile the boot did not see. Farah's data stays on disk until Sara's next sign-out, expiry or cold launch.
- **Why minor:** the window is one bundle load, and it needs a sign-in as another user inside it. Spec §4.3 says "`TmSession` parses the cookie", so the code follows the text.
- **Suggested fix:** seed `#profile` from `TM_BOOT_RESULT.profile` when a boot result exists, and from the cookie only when none does. A cookie that changed since the boot then reads as `changed` at the first check, and the changed-user path restarts the boot, which sweeps. Add the spec case: boot result for one user, cookie for another at first injection, `check()` returns `changed`. Record it as a deviation from §4.3, or hand it to PC-075 as a WATCHLIST line.

**R2-3 (minor): the per-language budget counts offered languages, but the bytes come from string tables.**
- **Where:** `client/tools/tests/boot-template.spec.mts:53-55`; `client/projects/core/tellma-core/README.md:29-31`.
- **Problem:** `budget()` allows `3 + 0.4 × (languages − 1)` KB. The renderer always requires the English table, as the fallback, whether or not English is offered. So a distribution that offers only Arabic carries two tables and gets the allowance for one.
- **Measured:** Arabic only, with the required English fallback: 3,381 B at gzip level 9, against the 3,072 B the formula gives it. The script is as large as Acme's en+ar (3,389 B), which the formula allows 3,481 B.
- **Failure scenario:** nothing fails today, because both tested configurations offer English. The first distribution without English, or a build-time check in PC-073 that copies this formula, reports a correct script as over budget.
- **Suggested fix:** count the tables: `3 + 0.4 × (string tables other than en)`. Say the same in the README. The orchestrator may want D-048's wording aligned ("each further string table").

**R2-4 (minor): the two real browser seams are never exercised by a test.**
- **Where:** `client/projects/core/tellma-core/src/session/tm-session-host.ts:54-85`; `client/projects/core/tellma-core/src/boot/tm-boot-result.ts:16-19`.
- **Problem:** every spec provides `TM_SESSION_HOST` and `TM_BOOT_RESULT` as fakes. The default factories, which production runs, are not covered: the read of `window.__tmBoot`, `document.cookie` read and write, `<html lang>` and the session storage capture.
- **Failure scenario:** a misspelled `__tmBoot` in the factory leaves `TmSession` without a mark and `TmLaunch` without `auto`, and all 221 tests still pass. The same holds for a cookie write that the browser ignores: the spec asserts only the string the fake recorded.
- **Suggested fix:** two small browser specs with no fakes. One sets `window.__tmBoot`, injects `TM_BOOT_RESULT` and `TmLaunch`, and reads `automatic()`. The other writes a `tellma.profile` cookie on `Path=/`, calls the real host's `writeCookie` with the delete string, and checks that `cookies()` no longer holds it; it also reads `language()` and the session storage. Neither may call `reload`.

**R2-5 (minor): `check()` writes a signal it has just read in the caller's reactive context.**
- **Where:** `client/projects/core/tellma-core/src/session/tm-session.ts:86-101`.
- **Problem:** `check()` is documented as reading the cookie now. Since deviation 7 it also reads `#profile` tracked and may call `#profile.set(now)`. Inside a `computed` that write throws `NG0600`, and only on the rare call where the cookie's details changed (a new `sh` after a sign-in in another tab, a new name or locale). Inside an `effect` it makes the caller depend on the profile, so the effect runs again when the details change. Spec 0025 §2.5's write guard calls `check()` from `put` and `patch`, which effects are likely to call.
- **Failure scenario:** `computed(() => session.check() === 'same')` works in every test and throws once in production when the user's other tab signs in again.
- **Suggested fix:** run the body under `untracked`, which lifts both the dependency and the write restriction, and add a spec that calls `check()` inside a `computed` after the cookie's details change.
