## Implementer notes

### What was built, and where

- **Contracts** (`src/core/Tellma.Core.Abstractions/Email/`): `OutgoingEmailState`,

- **Outbox** (`Outbox/EmailOutbox.cs`, scoped `IEmailOutbox`): step 1 resolves every blob reference

  validates every request (`Email.InvalidMessage` alone for a malformed one, else
  `Email.TooManyRecipients` and `Email.TooLarge` together), all errors thrown at once; step 2 stages
  the message's own files, attaches a staged email attachment as it is, and copies a committed blob
  through the store; step 3 builds `Pending` rows with RFC 5322 address lists

  are resolved only when a call has attachments.
- **Enlistment** (`Crud/Enlistment/EnlistmentRounds.cs`): the outbox is a participant of every
  frame (0015 §13.3, the D-151 carry), so a channel sender, a hook or a handler can enqueue with any

- **Handler** (`Outbox/OutgoingEmailHandler.cs`): the §5 attribute and policy, registered so the
  queue accepts the key; its body fails closed (see deviation 1).
- **Email channel** (`Notifications/EmailNotificationChannel.cs`): the §4 delivery. Recipients with

  `LocalizationScope.Enter`, then the three `ServerStrings` resources with `tenantName` (settings

- **Composition**: `CoreFeature` registers the stack, model, `IEmailOutbox`, the handler, the blob

  `CompositionPipeline`.
- **Resources**: the eleven `Email_*` code messages, `JobHandler_core_outgoing-email` and the two
  plural labels in `Strings.resx` and `Strings.ar.resx`; the three `Email_Notification_*` texts in
  `ServerStrings.resx` and a new `ServerStrings.ar.resx`.
- **Migrations**: fixture, migrator test distribution and Acme tenant regenerated with dotnet-ef

- **Identity**: `Tellma.Identity.Data.Entities.EmailDeliveryStatus` now clashes by name with the

### Deviations

1. `OutgoingEmailHandler` is registered with a body that throws `NotSupportedException`: the job
   queue refuses an unregistered key, and the dispatch is the next checkpoint's. A claimed row stays
   `Pending` and its job retries with backoff. The handler is `internal sealed`, not `public`.
2. `EmailNotificationChannel` is built but not registered in `CoreFeature`; that line and
   `SendTestAsync` (which throws `NotSupportedException`) belong to 0018 §1.2's checkpoint. The
   integration harness registers the channel itself.
3. `Email.InvalidMessage` also covers checks the spec leaves implicit so that a row can be stored
   and sent safely: a subject on one line of at most 500 characters; addresses with no white space,
   control character or angle bracket and names with no control character; `From`/`ReplyTo`
   formatted within 512 characters; at most 20 attachments in all (the row's `MaxChildren`); a
   content id of at most 255 characters; a blob reference with a kind; a `RegardingEntity` of 1–128
   ASCII letters, digits and dots.
4. A staged blob of a kind other than `email-attachment` is refused as `Blob.NotAttachable`
   (reason `kind`) instead of being attached: the attachment column accepts only its own kind.
5. The subject takes the rendered text's first line (its title), and is cut to 500 characters
   with an ellipsis, never splitting a surrogate pair; control characters become spaces. The HTML
   body receives each argument HTML-encoded, with the text's line breaks as `<br>`.
6. The stack serves no delete by query: it validates deletes (D-132), so §8's endpoint list loses
   `DELETE outgoing-emails?filter`.
7. `tellma.outbox.enqueued` is not emitted yet; the telemetry ships with the dispatch (§9.2).
8. The metadata builder no longer counts a child's parent key as a reference that wants its
   target's natural key (`EntityMetadataBuilder.Relations.cs`): a sheet fills a parent key from
   its owner's `Id` (0019 §5.2), never by a lookup. Without it every host would log a startup
   warning that `core.OutgoingEmail`, which has no natural key, is referenced by its attachments.

### Findings

**R1-1 (major) — one recipient's address or name fails the whole delivery batch, unretried.**
`src/core/Tellma.Core/Notifications/EmailNotificationChannel.cs:100-149` passes each recipient's
`ContactEmail ?? Email` and `Name` straight into one `EnqueueAsync` call, and
`src/core/Tellma.Core/Outbox/EmailOutbox.cs:82-90` throws one `ValidationException` when any request
fails `IsWellFormed` (`EmailAddressList.IsWellFormed` refuses white space, control characters and
angle brackets in the address, and control characters in the name). Scenario: spec 0018 §3.2
accepts a `ContactEmail` that `MailAddress` parses with one `@`, which includes
`Ada <ada@acme.example>` and `"a b"@acme.example`, and it only trims `Name`, so a name with an
embedded tab or newline gets through. When that user has opted into email, `DeliverAsync` throws.
`NotificationDeliveryHandler.ExecuteAsync` (line 84) does not catch it, and `JobEnding.Of` maps a
`ValidationException` to `Invalid` (`src/core/Tellma.Core/Jobs/JobEnding.cs:67`), so every item of
the `core.notification-delivery` batch ends `Failed` with no retry. That is up to 4 notifications,
every addressed recipient of each, and every other channel's enlisted rows. Spec 0022 §4 step 2
sends one email per recipient that has an address, and §10 skips a recipient with no address. A
recipient whose address the outbox cannot store should be skipped the same way, not fail everyone
else's email.
Fix: in the channel, build each request and keep it only when `EmailOutbox.IsWellFormed(request)`
holds (or check `EmailAddressList.IsWellFormed` on the address). Drop a display name the outbox
would refuse rather than drop the recipient, and skip a recipient whose address is unusable with a
Warning that names the user id and no address. Add a unit test that passes a malformed contact
address and a name with a control character beside a good recipient, and asserts the good
recipient's request is still enqueued.

**R1-2 (minor) — the rollback half of the D-151 carry is pinned only before the persist.**
`test/core/Tellma.Core.IntegrationTests/Outbox/OutboxTests.cs:157-175` and `:238-251` both throw
before `Host.PersistAsync`, so the enlisted statements never reach the completion batch. The commit
half is pinned (tests at `:59` and `:205`). What is missing is a frame that persists its enqueue
and then fails: that is when the rows, the blob confirm and the jobs sit in the completion batch,
and they must roll back with it. If the job runner kept a persisted frame's statements after a
throw, no test here would fail.
Fix: add a probe that enqueues one email with a byte attachment, awaits `Host.PersistAsync`, then
throws. Assert no `core.OutgoingEmails` row, no `core.outgoing-email` job, and one `Staged` blob.

**R1-3 (minor) — the shared metadata rule change has no pin.**
`src/core/Tellma.Core/Data/Metadata/EntityMetadataBuilder.Relations.cs:191-196`. The rule is right:
`KeyedReferences` feeds only phase 6's `WarnUnkeyedTargets` (line 260). `References` and every
navigation are unchanged, and spec 0019 §5.2 fills a child sheet's parent reference from the
owner's `Id` without a lookup, so an owner without a natural key loses nothing. Its only effect is
to silence a startup warning for any parent without a natural key, in every module, and nothing
pins that. `EntityMetadataTests.The_one_warning_names_the_referenced_entity_without_a_natural_key_and_who_references_it`
(`test/core/Tellma.Core.Tests/Data/Metadata/EntityMetadataTests.cs:422-429`) passes with and
without the change, because the fixture's only parent-key target (`AccountLine`) has natural keys.
Fix: add a metadata fixture child under a parent with no natural key and assert it adds no warning.
Alternatively, assert that a Core composition's `Build.Warnings` names no `core.OutgoingEmail`.

**R1-4 (minor) — the welcome email has no owner, and no action frame enqueues in a test.**
PC-088's sections exclude "the welcome email". PC-143's done-when says the welcome email is
"explicitly left to 0022's checkpoint". This commit's open risks say it "cannot be wired yet", and
PC-149's deliverables do not list it. So spec 0018 §3.3's welcome email (and 0018 §9's
"`Pending` welcome email … committed with the write-back" pin) is not owned by any checkpoint.
PC-148's done-when ("0018's invite … can enlist OutgoingEmail rows that commit with their jobs") is
met only by argument. The invite runs in an API action frame (or the provisioning frame), and no
test enqueues from either.
Fix (orchestrator): give the welcome email and its §9 pins to a checkpoint gated on PC-148 and
PC-088, either PC-088's next round or PC-143. Have that checkpoint's integration test enqueue from
the invite's action frame.

**R1-5 (minor) — with the channel registered before dispatch lands, opted-in email piles up.**
Ruling on deviation 1: `OutgoingEmailHandler.ExecuteAsync` throws `NotSupportedException`, and
`JobOutcomeRules.Unmarked` (`src/core/Tellma.Core/Jobs/JobOutcomeRules.cs:176`) answers with a
backoff retry until `MaxAttempts`. Each job ends after 12 attempts. It does not loop, and nothing in
any deployed composition enqueues at this commit: the channel is unregistered, the invite is held,
and there is no save endpoint. But DEPS gates PC-143, which registers the channel in `CoreFeature`,
only on PC-093/088/090/035, not on PC-149. If PC-143 integrates first, every opted-in notification
leaves a `Pending` row whose job spends about 5 to 10 hours failing. It then ends with
`Jobs.AttemptsExhausted` and a `core.job.failed` notice to administrators, and the orphaned row
needs 0022-c's `retry` verb, which may not exist yet.
Fix (orchestrator): add a PC-149 gate to PC-143 for the channel registration, or have PC-143's
brief register the channel only once PC-149 is integrated.

### Responses

- R1-1: fixed in the "PC-148: review 1 fixes" commit (child of b01932b6). `EmailNotificationChannel`
  now builds each recipient's mailbox with the address trimmed and the name on one line (each
  control character a space, blank as none), skips a recipient whose mailbox fails
  `EmailAddressList.IsWellFormed`, and then keeps a request only when `EmailOutbox.IsWellFormed`
  holds, so the outbox's own rules decide. A skipped recipient logs
  `EmailNotificationRecipientSkipped` (Warning, the recipient's user id only, never the address),
  and an empty list enqueues nothing. Spec 0021 and 0022 name no recording for this beyond the log,
  so nothing else is written. Pinned by two unit tests in `EmailNotificationDeliveryTests`: a
  contact address `Ada <ada@acme.example>` skipped with one warning, beside a name carrying a tab
  and CRLF and an address with surrounding spaces, both still enqueued and well formed; and every
  address refused enqueuing nothing. One integration test in `OutboxTests` runs the delivery job:
  Dee (contact address `Dee <...>`) skipped, Ada and Eve (`Eve\tStone`) committed, the job
  `Succeeded`.
- R1-2: fixed in the same commit, with a different probe from the one suggested.
  - **Why not the suggested probe.** As written (persist, then throw), it fails, but the job runner
    is right. Spec 0020 §5.6 appends the enlisted groups where the handler awaited `PersistAsync`
    and sends the composed batch as it stands. §3.4 then maps the throw to `Retry` (`Jobs.Internal`).
    Its failure list discards the handler's work only when the completion batch itself fails.
    So a handler that throws after persisting commits its persisted enqueue with the retry. That
    is spec 0020's contract that handlers stay idempotent (§3.6), not an outbox leak.
  - **What pins the rollback instead.**
    `A_completion_that_fails_after_the_enqueue_persisted_rolls_back_the_row_its_job_and_the_blob_confirm`
    enqueues one email with a byte attachment, awaits `Host.PersistAsync`, then appends a statement
    that fails at execution. It asserts:
    - the attempt is recorded alone as `Pending` with `Jobs.Internal`;
    - there is no `OutgoingEmails` row, no attachment row and no `core.outgoing-email` job;
    - one `Staged` email-attachment blob remains.
- R1-3: fixed in the same commit. `EntityMetadataValidationTests.A_parent_without_a_natural_key_draws_no_warning_from_its_childrens_parent_key`
  builds `UnkeyedOwner` (no natural key) with its child `UnkeyedOwnerLine`. It asserts no problem,
  no warning, and the child's one reference to its owner. With the parent-key exclusion reverted
  locally, the test fails.
- R1-4: carry, no code here (orchestrator ruling). The welcome email (0018 §3.3 and its §9 pins,
  enqueued from an action frame) is recorded on PC-149.
- R1-5: carry, no code here (orchestrator ruling). PC-143's registration of `EmailNotificationChannel`
  is gated on PC-149.
