# PC-079: SettingsService: client, entity-tags, details, save, refresh-caches

## Implementer notes

### What was built, and where

- `src/core/Tellma.Core/Settings/SettingsService.cs` and `SettingsService.Save.cs`: the routed
  service (`settings`) with `client`, `entity-tags`, `details`, `save` and `refresh-caches`, every
  batch through `IGuardedBatchRunner`.
  - `client` and `entity-tags` run a Read batch holding only the prologue, then answer from the
    store and the snapshots.
  - `details`: one evaluation of `Read` over the general resource and every category's resource,
    then one Read batch (typed row when held, every entry, the related reads).
  - `save`: authorize `Save` per distinct resource of the listed fields, then one Validate batch
    (typed row only when a typed member is listed, the listed entries), the merge, then one Persist
    batch (typed row, entry inserts/updates, the delete of the reset entries with their stamps, the
    language-change bumps, and the closing editor reads). The store is offered the committed
    settings built from the closing reads, stamped with the batch's settings tag. The name mirror
    runs after commit.
  - `refresh-caches`: one Persist batch bumping every registered tenant tag and both user columns
    of every `UserStamps` row to the batch's tag, publishing `cache.changed` (preferences, no value).
- `src/core/Tellma.Core/Settings/SettingsPatchMerger.cs`: the pure merge, every §6.5 code, the
  stamps, the mirror decision and the entry write plan.
- `src/core/Tellma.Core/Settings/SettingsReads.cs`: raw-SQL reads of the typed row and the entries
  (with the modifier's names joined in), shared by the validate batch, the closing reads and the
  editor's view.
- `src/core/Tellma.Core/Settings/SettingsRelatedReads.cs`: the related reads of reference keys,
  grouped per referenced entity, one keyed query per entity.
- `src/core/Tellma.Core/Settings/SettingsSecurableContributor.cs`: the securables.
- `src/core/Tellma.Core.Abstractions/Settings/`: `TenantSettingsPatch`, `TenantSettingsDetails`,
  `SettingsSaveResult`, `SettingsValidationCodes`.
- A concurrent first write of a key surfaces as a unique violation on the entries' key index,
  translated to a conflict; the integration test holds the racing insert on a side connection
  until the save's insert waits on its key lock.
- Tests: `test/core/Tellma.Core.Tests/Settings/SettingsPatchMergerTests.cs` (unit) and
  `test/core/Tellma.Core.IntegrationTests/Settings/SettingsServiceTests.cs` with its fixture
  `SettingsDatabase.cs` (integration).

- Existing expectations updated for the new securables and routed service: the securables
  client-asset and check tests, the stack-registry and contribution tests (filter to their own
  service), and the regenerated route and stack goldens.

### Tests

- Unit: `SettingsPatchMergerTests` (patch mask, every §6.5 code, blame paths, shape nulling,
  mirror decision, typed and entry stamps, override, secrets).
- Integration (`SettingsServiceTests`, 20 tests): stale typed and entry stamps; entries-only save
  past a stale typed row; a concurrent first write (racing insert held on a side connection until
  the save waits on its key lock) is a conflict, not a unique violation; override; the settings
  tag equals the header's; a language change bumps `permissions` and every `entity:*` and switches
  the shape, and a save that keeps them does not; the name mirror, a save that mirrors nothing, and
  a failing mirror logged; refresh-caches; 403 for details and save without grants and for a save
  missing one category's grant; details holds only the held categories with related rows, a
  deleted target left bare; a save's details carry unlisted rows' stamps; a reset; the cached views
  after a save equal a cold instance's (Region and Digits round-trip); a save takes 2 round trips,
  3 after another instance's bump (the validate guard fails once), and a details read 1.
- Nightly-tier: none.

### Deviations

1. The reads are raw SQL (`SettingsReads`), not `Query<Settings>` / `Query<SettingEntry>`: the
   batch's shape is fixed while a save may change the languages, deletes need the entries' ids,
   and a conflict needs the modifier's name, joined in.
2. A language change bumps every `entity:*` tag besides `permissions` (D-076 carry); the bump plan
   adds `entities` with them.
3. An expected entry whose row is gone is a `ConcurrencyException` conflict (`IsMissing`, id 0 when
   it was gone before the read), never a not-found, even when it is the only conflict; the
   `ConcurrencyConflict.IsMissing` doc says so.
4. `details`, `save` and `refresh-caches` are `Mcp = Hidden`.
5. `client` answers `(byte[] Json, string WireTag)` as the spec's sketch has it; the edge (PC-080)
   must write the bytes raw rather than serialize the tuple.
6. Names carry a 255-character limit (the column's), refused as `MaxLength`.
7. A patch that writes nothing runs its closing reads on a Read batch, not a Persist batch.
8. The name mirror is skipped in a host that registers no `ITenantCatalog`.
9. `TenantSettingsPatch` members after `Fields` have defaults, so a client lists only what it sends.
10. `SettingsService` is internal; it is reached only through the invoker.
11. `TenantSettingsDetails.SetKeys` and `EntryStamps` include the held secrets' rows (never their
    values), so the editor can reset a secret under `Check`.

### Open risks

- ARCHITECTURE.md needed no change: it names no settings-service detail this contradicts.
- On a save that changes the languages, the related reads of the closing reads are projected with
  the request's (old) shape; the editor's related names may lack the new language until the next
  load.
- A `DataAccessAmbiguousException` from the persist propagates untranslated (as elsewhere in the
  pipeline).
- `HeldAsync` evaluates before the batch, so a recompose after a permissions bump does not
  re-evaluate the held categories inside that request.

### Examine hardest

- `client` and `entity-tags` keep the default MCP exposure (`Full`); `client` answers raw JSON
  bytes, which an MCP tool would serve poorly. Hiding them would be a one-word change.

- `SettingsPatchMerger.Merge`: blame paths of the cross checks, the refusal-before-conflict order,
  and the entry plan (reset of a missing row, unchanged non-secret values skipped, secrets always
  rewritten).
- `SettingsService.Save.cs` `Translate`: the mapping of `ConcurrencyConflictException`, the unique
  violation on the entries' key index and the not-found assertions to one `ConcurrencyException`.
- The store offer after a save: it must equal a cold load byte for byte (pinned by
  `The_cached_views_after_a_save_equal_a_cold_load`).

### Findings

**R1-1 (major) The persist-time conflict paths of `Translate` have no test.**
- Location: `src/core/Tellma.Core/Settings/SettingsService.Save.cs:298-316`. The two stale-stamp
  tests (`SettingsServiceTests.cs:54-85`) move the stamp before the save starts, so the merge
  (`SettingsPatchMerger.cs:96-103` and `:146-166`) raises the conflict and the persist never runs.
  Only the unique-violation branch is exercised (`SettingsServiceTests.cs:100-119`). The
  `ConcurrencyConflictException` branch and the `BatchAssertionFailedException` NotFound branch,
  which are the only path for a row changed or deleted between the validate and the persist
  round trip, are never run. The implementer lists this mapping under "Examine hardest", and spec
  §6.5 names the emitter's comparison as a source of the 409.
- Scenario: the emitter changes what it throws for a stale update or for a delete of a gone row
  (or the modifier-name mapping on line 309 breaks). A raced save then surfaces as an untranslated
  data-access exception, which is a 500 at the edge, and nothing fails.
- Fix: add two integration tests with `fixture.Connect.HoldWhileAsync`. First, hold an
  `UPDATE [core].[SettingEntries] SET [ModifiedAt] = …` of a stored entry so that the save's
  persist waits on the row's KEY lock. The validate read passes unblocked, as it already does under
  the concurrent-first-write test's held insert. Assert a `ConcurrencyException` naming the row's id, its new stamp and
  its modifier. Second, do the same with a held `DELETE` of the entry and a reset or update of it,
  and assert `IsMissing` and no not-found. Add a typed-row variant if it is cheap.

**R1-2 (minor) The refresh-caches test would pass without the action's own preferences event.**
- Location: `test/core/Tellma.Core.IntegrationTests/Settings/SettingsServiceTests.cs:245` asserts
  only that some `cache.changed` event was published. `VersionTagBumpContributor` publishes
  `cache.changed` for every bumped tenant name through the same publisher
  (`src/core/Tellma.Core/Caching/VersionTagBumpContributor.cs:250`). Deleting
  `SettingsService.cs:166` (the `{ tag: "preferences" }` event to the tenant group, §6.4) leaves
  the test green.
- Scenario: the event is lost in a refactor. Clients then never refresh `me` after a
  refresh-caches (spec 0025 keys its jittered `refresh(t, ['me'])` on it), and no test notices.
- Fix: assert an event named `cache.changed` with empty `UserIds` whose payload is
  `CacheChangedPayload(VersionTagWire.PreferencesItem, null)`.

**R1-3 (minor) `client` and `entity-tags` are never invoked by a test.**
- Location: `src/core/Tellma.Core/Settings/SettingsService.cs:86-102`. No unit or integration test
  invokes either action. The checkpoint's done-when is that every action behaves per §6 through
  the runner. §6.2 says both run on a Read batch through the runner, and on a warm instance
  neither adds a statement.
- Scenario: the prologue call is dropped, or the wrong cache member is returned. For example,
  `client` could start serializing instead of returning the cached bytes. Nothing fails.
- Fix: add an integration test that invokes both through `IApiActionInvoker`. For `client`,
  assert that the bytes and wire tag equal `ITenantSettingsCache.GetForClientAsync()`'s. For
  `entity-tags`, assert one entry per cacheable entity, each with its wire tag. Count one round
  trip for each on a warm instance.

**R1-4 (minor) `client` keeps `Mcp = Full` with a result that no tool can serialize.**
- Spec judgement: spec 0016's MCP section names `settings/details`, `settings/save` and
  `settings/refresh-caches` as never exposed. It is silent on `client` and `entity-tags`. The
  spec therefore does not decide the question, and `Full` is not a violation.
- The problem: `ClientAsync` answers `ValueTuple<byte[], string>`, and the route golden records
  that as its result type (`test/core/Tellma.Core.Tests/Api/Goldens/fixture-routes.txt`, the
  `settings/client` row). `TellmaJson.Options` does not include fields, so System.Text.Json
  writes a value tuple as `{}`. A `tellma_action` call reaches the method through
  `IApiActionInvoker` and serializes whatever it returns. On MCP, `client` would therefore answer
  an empty object, or base64 of UTF-8 JSON if fields were ever included. Either way it is useless
  to an agent, which can already read the tenant's settings it may see through the other tools.
  D-125 already makes the web edge special-case this tuple; MCP would need a second special case.
- Fix: mark `client` `Mcp = McpExposure.Hidden` and keep `entity-tags` (a plain string
  dictionary) at `Full`. Alternatively, record a carry to the MCP checkpoint to write the bytes
  raw as it does on the web edge. Either way, flag it for Ahmad so spec 0016's never-exposed list
  names `settings/client` explicitly or states the raw-bytes rule.

**R1-5 (minor) The concurrent-first-write conflict names neither the row nor its modifier, and
this is not stated as a deviation.**
- Location: `src/core/Tellma.Core/Settings/SettingsService.Save.cs:310-311` raises
  `ConcurrencyConflict(0, null, null, null, IsMissing: false)`. Spec §6.3 step 3 says the 409
  names `ModifiedById` and `ModifiedAt` when a row exists, and here a row does exist: the other
  writer's committed insert. The commit's Deviations list does not mention this. The amended
  `ConcurrencyConflict.IsMissing` doc (`src/core/Tellma.Core.Abstractions/Errors/ConcurrencyConflict.cs:23-28`)
  explains id 0 only for a missing entry. A client therefore cannot tell this shape (id 0, not
  missing, no stamp) from a malformed conflict.
- Scenario: spec 0032's editor opens the conflict dialog for a key another administrator has
  just created. It has no stamp to show and no author to name, and the documented contract does
  not tell it which case this is.
- Fix: add a Deviations line (no author because naming one would cost a round trip after the
  rollback). Extend the `ConcurrencyConflict` doc to cover id 0 with `IsMissing = false` for a
  settings entry that another save inserted first. Alternatively, run one Read batch on this rare
  path to fetch the row's stamp and modifier.

**R1-6 (minor) A save whose field mask names nothing is never authorized.**
- Location: `src/core/Tellma.Core/Settings/SettingsService.Save.cs:100-121`. With
  `Fields = []`, or with only unknown fields or undeclared keys, no resource is collected and
  `RequireAsync` is never called. An empty mask then skips the validate batch, merges to nothing,
  and runs the closing reads on a Read batch (`:225-232`). It also offers the store a rebuilt
  entry and answers 200 with `Client` to a member holding no settings grant. Spec §12's case,
  "`save` by a member holding no settings grant answers 403", does not hold for this request.
  An undeclared-only mask costs that member a validate round trip before its 422.
- Scenario: a member with no grants posts `{"fields": []}` and gets 200. Nothing leaks beyond
  what `client` already gives, but the action does work for a caller the spec refuses.
- Fix: before any batch, refuse a mask that names no typed member and no declared key. Either
  raise `Settings.FieldUnknown`, or a 422 with `Required` at `Fields` when the list is empty, or
  require at least one `Save` grant when nothing is collected. Add a case to
  `Details_and_save_by_a_member_without_grants_are_forbidden`.

**R1-7 (minor) PLAN §7.1 item 4: the commit message does not list the gates or the suites run.**
- 1d018296's `Tests:` block names the new and updated tests. It does not list the build, the
  format check, the PR-tier unit filter, or the integration suites run by name. Other checkpoints
  carry a Gates section listing each suite and its count.
- The commit changes `Tellma.Core.Abstractions`, so §7.1 counts every integration suite as
  touched. It also changes `CoreFeature`'s composition (a new routed service and new securables),
  which every composed host picks up, the Acme suites among them.
- Fix: run `dotnet format Tellma.slnx --verify-no-changes`, the PR-tier unit filter, and each
  integration suite one at a time with the §7.1 filter. Then add a Gates block listing them with
  their counts.
