# PC-077: IApiActionInvoker, write frames and enlisted writes

## Implementer notes

### What was built

Spec 0015 §11.3, §13.3, §14.2 (group attribution), §2.6 / §16.1 (the enlistments counter) and the
§18.2 enlistment and API action pins, over PC-076's write runs. Before this checkpoint the
pipeline's write host took no enlistment (`EnlistSaveAsync` and `EnlistDelete` refused every host),
and neither `IApiActionInvoker` nor `IOpenWriteHost` was registered.

- **Frames** (`Crud/Enlistment/`).
  - `EnlistmentFrame` is the shared base: the pair check against `IStackRegistry.Enlistments`, the
    participant check, the phase check, the self-pair rule, the duplicate-root-id refusal, the
    groups in call order. Every refusal is `InvalidOperationException` (`Admit`).
  - `PipelineFrame` is the `IWriteHost` of every save, delete and action (it replaces
    `PipelineWriteHost`): preprocessing refuses, id assignment to the last validation round
    composes, the persist hooks and post-commit refuse. Its participants are the host's service,
    companions and components (`StackRegistry.ParticipantsOf`) plus each group's own.
  - `OpenWriteFrame` is the open frame of an `[ApiAction]`, a job or a provisioning step. It owns a
    validation scheduler, a context loader and the host's error list; the work runs as one task of
    those rounds, so an enlistment that waits for a round (a cold id buffer, a before image) is
    served while the work awaits it. `PersistAsync` (`OpenWriteFrame.Persist.cs`) leaves the rounds,
    waits for them to end (the `_ended` completion carries their failure), raises the groups'
    errors and then their warnings, and sends one persist batch with every group; nothing enlisted
    is no round trip. A second `PersistAsync`, a persist while a nested pipeline frame composes, and
    work that returns with unpersisted groups are `InvalidOperationException`.
  - `FrameFlow` is the flow's frame chain (async-local): the innermost frame is what
    `IOpenWriteHost` (the scoped `OpenWriteHostProxy`) forwards to, and what the front door reads
    to refuse `SaveAsync`, both deletes, both `ExecuteActionAsync` overloads, activate, deactivate
    and `DeleteWithDescendantsAsync` while a pipeline frame of the flow composes.
  - `GroupFrame` / `RerunHost` are the host a group's own contexts see, so a group's enlistments
    nest under it (B ahead of A with C after B composes B, C, A) and `MapPath` composes along the
    nesting. On a re-entry the host's validators re-run in memory against a `RerunHost`, which
    answers the n-th enlistment from the first run's n-th group (same target, kind and row count,
    the first run's ids on the rows; anything else is `StaleContextException`); the first run's
    groups are recomposed and replayed at their positions.
- **Groups** (`Save/SaveRun.Enlisted.cs`, `Delete/DeleteRun.Enlisted.cs`, `EnlistmentRounds.cs`,
  `IEnlistedGroup.cs`). An enlisted save runs the target's shape checks, platform preprocessing and
  `PreprocessAsync` at once, reserves its ids (warm buffer at once, else parked at the host's next
  round), loads its update rows' before images unfiltered on the host's loader (a missing row is
  `Entity.NotFound` at the mapped path), re-applies the `ServerOwned` members the writer names, runs
  the target's validators and components as tasks of the host's scheduler, then composes its
  statements live on the host's batch under its target's authority and runs the target's post-commit
  after the host's. No grant and no reference visibility is asked of it. The default concurrency is
  `Override`; under `Check` a default stamp is `Concurrency.StampRequired` at the mapped path. An
  enlisted delete by ids loads its rows only when something validates the delete.
- **Error re-homing view** (`Tellma.Core.Abstractions/Validation/ValidationErrors.cs`). An internal
  constructor over a parent list, a path map and the enlisted resource: each participant writes its
  own payload's paths, the parent receives each error at the mapped path with `enlistedResource`
  added; views over views compose innermost first. A map returning null is refused and leaves both
  lists untouched.
- **Attribution** (`Data/Batches/IBatchOrdinals.cs`, `DataBatch.NextOrdinal`). Each group marks the
  ordinal range of its statements; a persist failure whose `StatementOrdinal` falls in a group is
  translated by that group's failure context and re-rooted onto the host's paths.
- **`ApiActionInvoker`** (`Crud/Actions/ApiActionInvoker.cs`): the registry's own descriptor by
  reference (`StackRegistry.MethodOf`), the handler resolved per request, `RequireAsync` or the
  connected-member check (System passes), the body's annotations walked at its own members, the
  scope's operation named after the action, the method run inside `OpenWriteFrame.ForApiAction`
  through every `IApiActionInterceptor`, the first registered outermost.
- **Provisioning and jobs.** `ProvisioningFrameOpener` runs each step inside
  `OpenWriteFrame.ForProvisioning` (the step's class is the frame's participant).
  `OpenWriteFrame.ForJob` is the seam spec 0020's worker opens: its `PersistAsync` appends the groups
  to the worker's completion batch, after the outcome statement, and `AfterCompletionAsync` runs
  their post-commit once the worker reports the commit. Open frames enter `WriteFrames`, so a
  read-only tenant admits the persists of a read-only-safe action, a `RunsWhenReadOnly` job and a
  provisioning step.
- **Stack table ownership** (`Crud/StackTableOwners.cs`). `CrudComposition` replaces
  `NoStackTableOwners` with the registry-backed owner map (every root and child table of every
  stack), so a public-member append whose declared writes include another stack's table is refused
  by `DataBatch.CheckAuthority`. The platform's composers keep the internal channel.
- **Telemetry** (`CrudMetrics`, `CrudOperationNames`). `tellma.crud.enlistments`, once per enlisted
  write, tagged with the host's operation, the write's kind and the host's outcome; the
  `api_action`, `job` and `provisioning` operation names.
- **Docs.** A "Write frames and enlisted writes" section in `src/core/Tellma.Core/README.md`; the
  ARCHITECTURE.md "Cross-stack posting orchestration" row now names the C# enlisted-writes model.

### Deviations

1. **`IProvisioningFrameOpener.Open` became `RunAsync(scope, stepName, stepType, step, ct)`.** An
   open frame drives its own rounds while its work runs, so the step must run as a task of those
   rounds; a frame opened before the step and left open could not serve an enlistment that waits
   for a round. The step runner hands the opener the step's creation and run.
2. **The job frame is a seam only.** No worker exists in this tree (spec 0020), so nothing opens
   `OpenWriteFrame.ForJob` yet. Its `PersistAsync` appends to the completion batch the worker
   passes and answers a provisional outcome; the commit is the worker's.
3. **`EmailOutbox`'s frame-wide admission is not built.** Spec 0015 §13.3 admits `EmailOutbox` as a
   writer in every frame; no such type exists yet. `ActionContext.Host` is a full pipeline frame,
   so an action's validators and method enlist through it today; the outbox's admission belongs in
   `EnlistmentFrame.Admit` beside the participant check, and its pair in the registry, with spec
   0022.
4. **The checkpoint's "FKs in each direction" are check constraints.** The fixture's EF model is
   unchanged: the serialized fixture migration is not claimed here. `EnlistmentDatabase` adds, on
   tenant A only, `CK_Widgets_ReferencedShipment` and `CK_Shipments_ReferencedWidget` over two
   scalar functions: a widget coded `ref:<x>` needs a shipment with payload `ref:<x>`, a shipment
   with payload `of:<x>` needs a widget coded `<x>`. They fail inside the offending statement as an
   FK would, so the ordering each way is proven; the failure surfaces as `DataAccessException`
   (a CHECK, not an FK, so not `ForeignKeyViolationException`).
5. **The self-pair API action lives on the shipment stack.** The fixture's Widget does not declare
   `Enlist`, and a self-pair needs the target stack to accept enlisted writes, so the `restamp`
   action is the shipment service's (`EnlistedShipmentService`); the fixture's `Shipment` now
   declares `StackOperations.All | StackOperations.Enlist`. The widget side is the test instance's
   `EnlistingWidgetService`, not a shared fixture service.
6. **`FixtureTenant` maps no table to a stack.** The data-layer suites append every statement
   through `IDataBatch`'s public members the way a stack's own pipeline does, so they keep
   `NoStackTableOwners`; the append refusal is exercised by the suites that run the full
   composition (`ConnectDatabase` instances use the real owner map).
7. **Tests moved off `core.Jobs`.** `SavePersistTests` and `WidgetSaveProbe` wrote `core.Jobs` as
   the caller's own table; it is the `core.Job` stack's now, so those appends are correctly refused.
   They write a test table `dbo.CallerRows` that no stack owns. `GuardedPersistTests` sets the
   caller authority explicitly before its raw appends.
8. **The invoker checks the body before it opens the frame.** Spec §11.3 lists the frame's
   registration before the walk; walking first means a refused body opens no frame and runs no
   interceptor. Nothing else observes the order.
9. **Enlisted saves record no save metrics of their own.** `RecordSaveEntities` and
   `CountOverride` count front-door saves; an enlisted write is counted once by
   `tellma.crud.enlistments` under its host.
10. **An open frame needs the tenant's settings in its scope** (the loader's schema map is built
    over the tenant's multilingual shape); a scope without them is `InvalidOperationException` at
    the frame's open. Every tenant scope of the full composition carries them.

### Open risks

- On a re-entry the groups' own validators are not re-run. The host's re-run validators are
  matched to the first run's groups by task and step (`RerunHost`, since review 1); an enlistment
  the first run made beside a parked flow of its own task always re-enters as stale.
- Groups share the host's `MaxValidationRounds`; a deep enlistment chain can exhaust it sooner than
  the host alone would.
- On an ambiguous commit (the proven-commit read failing) the groups' rows get no stamps back.
- An enlisted `Check` stamp is compared by the emitter only (no C# pre-check against the before
  image), so the refusal for a stale stamp is the statement's.
- Sequentially awaited enlistments on cold id buffers each cost a round; the 0 RT promise holds for
  warm buffers or enlistments made before the writer's last dispatch.

- `EnlistmentFrame.Admit` and the phase gates of `PipelineFrame`: every way to enlist from a stage

- Group composition and attribution in `SaveRun.Persist.cs`, `DeleteRun.Persist.cs` and

### Findings

**R1-1 (major): the re-run host matches enlistments to the first run's groups by position only.**

Where: `src/core/Tellma.Core/Crud/Enlistment/RerunHost.cs:30` (`_recorded = first.Groups`) and
`:94-102` (`Next`). It is used from `SaveRun.Persist.cs:289`, `ActionRun.Rounds.cs:427/435` and the
delete re-entry.

There are two ways it fails:

1. **Swapped ids.** In the first run, enlistments are recorded in the order the validation rounds
   interleave. In a re-run, `ContextLoader.AnswerOnly` answers loads synchronously, so validators run
   to completion in registration order.
   - Take two enlisting validators, A and B. A awaits a load before it enlists, and B does not. In
     the first run B's group is recorded first. In the re-run A enlists first and is given B's
     group.
   - If the target and the row count match, A gets B's ids silently. A validator that wires the
     host row's reference to its enlisted row's id then commits a wrong cross-reference. This is
     data corruption with no error.
   - If the target or count differ, the re-entry raises a spurious `StaleContextException`, and an
     unchanged save fails.
2. **Action hosts, every time.** On an action host the method's enlisted groups are in
   `_frame.Groups`, but the re-run calls `Start(..., withMethod: false)` (`ActionRun.Rounds.cs:435`).
   The method does not run again, yet its groups stay in `_recorded`. If the method enlisted before
   a validator did, the validator's re-run enlistment is matched against the method's group: a
   stale refusal, or the method's ids.

No test covers a re-entry with groups. The implementer lists this as an open risk, but the
consequence is worse than "reads as stale": ids can be swapped.

Fix:
- Record the writer's identity with each group (the scheduler task, or the validator instance or
  type) and a per-writer sequence number. `Next` should match on (writer, sequence, target, kind),
  not on global position.
- Exclude the groups the action method enlisted from `_recorded`, or replay them as they are.
- Add re-entry tests: two validators whose enlistment order differs between the runs, and an
  action whose method enlists before a validator does.

**R1-2 (major): several spec rules and this checkpoint's deliverables have no test, so breaking
them fails nothing.**

Each item below can be broken without any test failing:

- **The guards over the union of group writes** (`SaveRun.Persist.cs:150`,
  `OpenWriteFrame.Persist.cs:187`). No test has a group write a security table and asserts that
  `ContributeLock` and `ContributeInvariants` run. Dropping `.Concat(GroupTables)` or the
  `Rounds.GroupTables` argument passes the suite.
- **D-114's first half: ReadOnly admission through the real frames.** The only ReadOnly tests enter
  `WriteFrames` by hand (`SaveOperationTests.Persist.cs:264`). Nothing drives `ApiActionInvoker` or
  `ProvisioningFrameOpener` against a ReadOnly tenant to check that a nested save is admitted when
  the action is not a mutation or has `AllowWhenReadOnly`, and refused otherwise. Removing the
  `WriteFrames` entry in `OpenWriteFrame.RunAsync` passes the suite, and that regression is the
  original D-114 bug.
- **Enlistment from action and delete hosts.** All 25 unit tests and 7 integration tests use a save
  host or an open frame. Nothing enlists from an `[EntityAction]` method, from `ValidateActionAsync`
  or from `ValidateDeleteAsync`. `ActionRun.Persist.cs` and `DeleteRun.Persist.cs` compose groups
  untested.
- **`PersistAsync` refused while a nested pipeline frame composes** (the `_nested > 0` gate in
  `OpenWriteFrame.Persist.cs`).
- **`ServerOwned` re-application on enlisted rows**, and the refusal of audit columns and
  `IsActive` in `EnlistSaveAsync`.
- **`Source` recording** (`OpenWriteFrame.SourceOf`: System, PublicApi, Agent for `mcp`, Web).
- **StatementOrdinal attribution when two writers enlist the same target** (§14.2). The per-span
  `Translate` is tested only with one group per target.

Fix: add one focused test per item. The ReadOnly test should go through `IApiActionInvoker` and
`IProvisioningFrameOpener` as resolved from DI, with no frames entered by hand. The guard test can
use a fixture stack whose enlisted target is flagged as a security table and assert the lock and
invariant statements in the recorded batch.

**R1-3 (minor): the integration references prove statement order, not id flow.**

Where: `test/core/Tellma.Core.IntegrationTests/Crud/EnlistmentDatabase.cs` (`Seed`: the CHECK
constraints over the UDFs).

The constraints compare codes and payload strings. A bug that put the wrong ids on enlisted rows,
or failed to return the host's ids to the validator, would still pass. So would a bug that did not
skip the FK pre-load for in-batch references, or one that translated a 547 against the host rather
than the enlisted target.

Fix: make the UDF checks compare ids. For example, the validator sets the shipment payload to
`of:<widget.Id>` after ids are assigned, and the widget code to `ref:<EnlistedSave.Rows[0].Id>`.
The checks then join on the ids. Add one case where the enlisted row violates an FK and assert that
the error is re-homed to the enlisted resource.

**R1-4 (minor): the `crud.operation` and `IWriteHost.Operation` values are wrong for delete and
action hosts.**

Where: `src/core/Tellma.Core/Crud/Enlistment/PipelineFrame.cs:58`
(`Operation = $"{stack.Resource}:{operation}"`), with the run's `OperationName` passed in at
`DeleteRun.Persist.cs:50` and `ActionRun.Rounds.cs:113`.

- A delete-with-descendants host counts its enlistments under `crud.operation =
  "delete_with_descendants"`. That value is outside the closed set in §16.1 (save, delete, action,
  api_action, job, provisioning), so dashboards keyed on that set miss them.
- An action host's `Operation` reads `"<Resource>:action"`. The spec's form is
  `"<Resource>:<action name>"` (e.g. `gl.Invoice:post`), so a group that branches or logs on its
  host cannot tell which action enlisted it.

Fix:
- Map the run's operation to a §16.1 value for the counter (`delete_with_descendants` becomes
  `delete`).
- Build `Operation` from the action descriptor's name for action hosts.
- Assert both values in a test.

**R1-5 (minor): an enlistment outcome's `Stamp` can be the app clock rather than the batch stamp.**

Where: `src/core/Tellma.Core/Crud/Enlistment/OpenWriteFrame.Persist.cs:89`, `:148` and `:162`, and
`src/core/Tellma.Core/Crud/Delete/DeleteRun.Enlisted.cs:234`.

- When no group carries a stamp (a delete-only frame, a frame with only effects), or on the
  proven-commit path, the outcome takes `Time.GetUtcNow()`.
- The enlisted delete's AfterCommit outcome always does.

The spec says the outcome carries the batch's stamp. The app clock differs from the SQL-side stamp
written to `ModifiedAt`, so a caller that uses `Stamp` as the next `Check` stamp, or to correlate
with audit rows, gets a value that matches nothing stored.

Fix: take the stamp the batch used (from the persist result, or the value the batch bound for
`ModifiedAt`) for every outcome. Where a batch genuinely writes no stamp, say so in the outcome's
XML doc rather than inventing one.

### Responses

All fixes are in the "PC-077: review 1 fixes" commit (child of 6eada9d9).

- **R1-1: fixed** in the "PC-077: review 1 fixes" commit. Enlistments are matched by identity now,
  never by global position.
  - Each of the operation's own tasks is registered with a slot (`ValidationScheduler.Run(name,
    task, slot)`): the hook 0, each validator component 1.. in `GetServices` order. The first run
    and the re-run of save, delete and action register through the same code
    (`SaveRun.StartValidators(scheduler, context, wrap)`, `ActionRun.Start`, `DeleteRun.StartValidators`).
  - `PipelineFrame` records every direct group with its slot, the task's step (its count of
    enlistments so far) and `Raced`: the task had another flow parked at a load when it enlisted,
    so the re-run (whose loads answer at once) may take the two in the other order
    (`EnlistmentFrame.OnEnlisted`, `ValidationScheduler.CurrentSlot`/`IsCurrentTaskParked`).
  - `RerunHost` answers a re-run enlistment only from the record of the same slot and step, with
    the same target, kind and count; anything else is `StaleContextException`, and the refusal is
    kept even if the writer swallows it. `EnsureMatched()`, called after the re-run's validators
    and their errors, refuses as stale a first-run record the re-run never matched. A raced record
    is always stale.
  - An entity action's method runs at no slot: its groups are never matched and are replayed as
    they are, so a validator's re-run can no longer receive the method's ids.
  - Tests (`EnlistmentTests.Hosts.cs`): two tasks whose order flips between the runs keep their
    own ids and the host row's wiring (`hook 202`, `rules 201` on both runs); an action whose
    method enlists before its hook; a first-run enlistment beside a parked flow of the same task is
    stale; a re-run that skips an enlistment is stale. Under a positional `RerunHost` (mutation
    run, reverted) the first three fail.

**New deviations**

11. **A re-run that diverges from its first run is stale.** Spec §5.1 says the enlistments a re-run

### Findings

**R2-1 (major): an open frame's persist never re-decides the action's securable, so a re-entry
with fresh grants commits for a caller who lost them.**

Where:
- `src/core/Tellma.Core/Crud/Enlistment/OpenWriteFrame.Persist.cs:184-199` (`ComposeOntoAsync`)
  and `:237-251` (`FrameRun.Prepare`).
- The securable is evaluated once, at `src/core/Tellma.Core/Crud/Actions/ApiActionInvoker.cs:134`,
  and is not passed to the frame (`OpenWriteFrame.cs:148-154`).

Spec 0015 §5.1 says the batch runs under exactly the grants its prologue confirmed in the same
round trip. A stale `permissions` tag makes the runner re-enter `compose` with a fresh
`ConnectedUser`, so that "no row is written under a rule that moved".

The other three hosts honour this. Each compose re-decides the grant and throws
`ForbiddenException(NoGrant)` when the grant is gone (`SaveRun.Persist.cs:142`,
`DeleteRun.Persist.cs:244`, `ActionRun.Persist.cs:210`). The open frame uses the fresh user only
as `Composer`. `Prepare` checks only `entity:*` served tags (`WriteRun.EnsureServedTagsHold`), so
the re-entry composes and commits.

Failure scenario:
1. An administrator revokes `X:restamp` from a user whose set is still in the connect cache.
2. The user calls the `restamp` API action. `RequireAsync` answers from the cached set (§9.1,
   "Freshness") and admits the call.
3. The method enlists and persists. The persist batch's prologue sees the bumped permissions tag
   and refuses the batch.
4. The runner re-enters `ComposeOntoAsync` with a `ConnectedUser` that no longer holds the
   securable. Nothing checks it, and the groups commit.

A method that runs no validation round trip reaches its persist first. So every revocation admits
one more write per cached caller. The member-only path is not affected, because the prologue itself
refuses a deactivated caller.

Fix:
- Pass the action's `SecurableDescriptor` (null for a member-only action) to `ForApiAction`.
- In `ComposeOntoAsync`, when `user` is not null and the scope is not the system scope, decide the
  securable from `user.Access` as `WriteRun.Granted` does. Throw `ForbiddenException(NoGrant)` on a
  denial.
- The job frame (`user: null`) and the provisioning frame (no securable) stay as they are.
- Add a test using `RecomposeOnce` and `GrantOnRecompose` without the securable. The open frame's
  persist must raise `ForbiddenException`, and no second persist batch may be sent.

**R2-2 (minor; follows the spec; a decision for the orchestrator): on a re-entry, an enlisted
group's validators are never re-run, so a target rule that depends on grants is judged on the old
grants.**

Where:
- `src/core/Tellma.Core/Crud/Save/SaveRun.Persist.cs:262-303`: `RevalidateAsync` re-runs only the
  host's hook and components, and replays the groups. The action and delete hosts' re-entries do
  the same.
- `OpenWriteFrame.Persist.cs:186-188` re-runs nothing.

§5.1 step 1 names only the host's hook and components, and step 3 replays the enlisted groups, so
this follows the letter of the spec. For an open frame, though, it means nothing at all is judged
again under the fresh grants.

Once PC-078 lands, the core user and role stacks carry validators that read the caller's own set.
`UserAccessRules.ValidateAsync` calls `evaluator.GetAccessAsync` for its escalation test, and
`RoleAccessRules` does the same.

Failure scenario:
1. A frame, or a pipeline host, enlists a `core.User` save that adds a role membership.
2. Between the validation round and the persist, the caller loses a permission that the role holds.
3. The prologue refuses the persist, and the re-entry replays the group.
4. The escalation test is never repeated, and the membership commits.

Fix, for the orchestrator to choose one:
- Re-run each group's validators in memory on a re-entry, under a `RerunHost` of the group, as the
  host's validators are re-run.
- Or raise `StaleContextException` on a permissions re-entry whenever a group's target registers
  validators.

Either way, the spec should say whether §5.1's re-run covers the groups.

**R2-3 (minor): the injected `IOpenWriteHost` lets code inside a nested pipeline or group frame
enlist into the outer open frame.**

Where:
- `src/core/Tellma.Core/Crud/Enlistment/OpenWriteHostProxy.cs:31` and `:35-52` forward to
  `FrameFlow.InnermostOpen`, skipping any `PipelineFrame` or `GroupFrame` in between.
- `OpenWriteFrame.cs:276-283` (`EnsureAdmits`) checks only that the frame has not persisted.

The proxy's own message says a pipeline's hooks enlist with their context's `Host`, but nothing
enforces it. `IsParticipant` admits the handler and the participants of every group's target at any
depth. So a hook of any of those classes that injects the scoped host is admitted at the top level
of the open frame. Three failures follow.

1. **Duplicate group.**
   - The method calls its own stack's `SaveAsync` through the front door, and that stack's
     validator enlists through the injected host.
   - When the nested save's RT2 re-enters, `RevalidateAsync` re-runs the validator. Its host is not
     the `RerunHost`, so it enlists a second group into the outer frame, which is still open.
   - An insert commits twice. An update fails the duplicate-root-id claim with an
     `InvalidOperationException`. §5.1 says a re-run's enlistments are ignored.
2. **Wrong nesting.**
   - Group B's validator enlists C through the injected host. C becomes a sibling of B instead of
     nesting inside it.
   - B's `MapPath` is not applied to C's errors.
   - C is ordered after B rather than around it, so a B row that references C fails with a 547 at
     persist.
3. **Self-pair from a pipeline frame.** A hook of the action's own stack, running inside the
   front-door save the method started, enlists its own entity. The open frame admits the
   self-pair, which §13.3 refuses from a pipeline frame.

Fix:
- In `OpenWriteHostProxy` or `OpenWriteFrame.EnsureAdmits`, throw `InvalidOperationException`
  unless the flow's innermost frame is the open frame itself, and name the context's `Host` in the
  message.
- Await continuations restore the method's own chain, so the method, the handler and the step are
  not affected.
- Add a test where a nested front-door save's validator enlists through the injected host and is
  refused.

**R2-4 (minor): the guards over group tables are not tested on the action and delete hosts.**

Where: `src/core/Tellma.Core/Crud/Actions/ActionRun.Persist.cs:247` and
`src/core/Tellma.Core/Crud/Delete/DeleteRun.Persist.cs:286`
(`StackTables.Concat(enlistments.GroupTables)`).

- The R1-2 guard test (`EnlistmentTests.Hosts.cs:189-221`) covers only the pipeline save host and
  the open frame.
- The action and delete host tests enlist only `EnNote`, which is not a security table.
- So dropping `.Concat(enlistments.GroupTables)` at either site still passes the suite.

Failure scenario: an `[EntityAction]` or `ValidateDeleteAsync` that enlists a `core.User` write
then commits without the lock and the invariants. That is the regression D-119 was raised for, on
two of its four sites.

Fix: extend the guard test with an action host and a delete host.
- Action host: the `touch` hook or method enlists `Person("Cy")`.
- Delete host: `ValidateDeleteAsync` enlists one person.
- For each persist, assert `[Lock, Invariants]`, after every other statement.
