# PC-F113: HubConnectTests negotiate 503 after a fake-clock advance

## Implementer notes

### What was built

Fix item from PC-129's integration CI 45945997084 (build-test, windows-latest, on 424e67df; D-404).
Test-only change: a clock move on the shared web test host that waits for the tenant snapshot to be
confirmed again. The tests that move the clock past the snapshot's staleness bound and then run
work that reads the snapshot use it.

**Root cause (D-011).** `HubConnectTests.Neither_the_negotiate_nor_the_connect_renews_or_stamps_the_session`
moved the fake clock 4 days (`host.Time.Advance`) and sent the negotiate to `/1/hub/negotiate` at
once. The tenant snapshot was last confirmed at host start, so after the move it was 4 days old, far
past `Tellma:Catalog:MaxStaleness` (5 min). `TenantRegistry.Find` then throws
`TenantUnavailableException(catalog-unavailable)`, which `TenantMiddleware` answers 503, until a
refresh confirms the snapshot again. The move does fire `TenantRegistryRefreshService`'s
`PeriodicTimer` tick, but the loop's continuation and `TenantRegistry.RunAsync`'s `Task.Yield` put
the refresh on the thread pool, two hops away. The test thread, meanwhile, sends the negotiate
through the in-memory TestServer straight away. On an idle machine the refresh nearly always lands
first. On a loaded runner (`-m:2`, parallel assemblies), the negotiate can reach the tenant
middleware first and gets 503 `ServiceUnavailable`, which is the CI failure at line 324.

**The product is right.** Spec 0011 §3.4 (and §1.4 principle 1, "fail closed") says that beyond
`MaxStaleness` every tenant request answers `503 catalog-unavailable`. A snapshot unconfirmed for
4 days must not be served, because doing so could keep serving a suspension that was lifted, or an
access that was revoked. On a real clock the loop re-confirms every 15 s, so a request only sees
503 after 20 failed refreshes in a row, or for a moment after the host resumes from a long suspend.
That is the intended fail-closed behaviour, not a cache bug. The fault was in the test's
arrangement.

**Reproduced.** A scratch test (not committed) set `host.Catalog.Gate` before the 4-day move,
which held the tick's probe at the catalog read (`AtGate` signalled, proving the move fired the
tick), and then sent the same negotiate. It failed exactly as CI did: `Expected: OK`,
`Actual: ServiceUnavailable`.

**Fix.** `TellmaTestHost.AdvanceAsync(TimeSpan)` (test/shared/Tellma.Testing.WebHost) moves the
clock and then awaits `ITenantRegistry.RefreshAsync(force: true)` (bounded by `Patience`). A forced
refresh always starts after any refresh already running (the registry queues it), so the snapshot it
publishes is confirmed at the new reading, whichever of the tick's run and this one goes first. A
twin, `TellmaTestHost.AdvanceToAsync(mark, due, count)`, wraps `TestClock.AdvanceToAsync` (the
armed-timer move) the same way. Bare `Time.Advance` stays for the tests that want a stale snapshot
or that send no tenant request. The
test now moves the clock with `await host.AdvanceAsync(TimeSpan.FromDays(4))`. Its assertions are
unchanged: no retry, no quarantine, no longer timeout. A second scratch test (not committed) held
the gate across `AdvanceAsync`, checked that the move had not completed 500 ms later, then opened
the gate and showed the negotiate answers 200. So the helper waits out a delayed tick refresh
instead of racing it.

### Sweep of the siblings that move the clock

I checked every `Time.Advance` / `AdvanceToAsync` in the projects that use the web test host
(Core.AspNetCore.Tests; Mcp.Tests, Defaults.Azure.Tests and the Azure AspNetCore integration tests
move no clock). The pattern only matters where the total move passes 5 minutes and is followed by
work that reads the snapshot through the registry's staleness check. That work is a tenant request
(`TenantMiddleware`, `Find`), a background tenant scope (`TenantScopeFactory.CreateScopeAsync`, and
through it jobs and `OutgoingEmailDeliveryHandler`), a tenant connection's resolution
(`TenantConnectionProvider` and `TenantConnectionFactory`, `Get`) or the readiness check
(`HealthChecks`, `IsAvailable`). In these projects only tenant requests follow a long move; no
test drives a scope, a connection or `/health/ready` after one (corrected in fix 1, after R1-1):

- **Fixed: `HubConnectionTrackerTests.On_Azure_SignalR_Service_a_remembered_close_lasts_the_service_token_s_five_minutes`**
  (`AssertMemosExpireAsync`). It moves 4:59 and then 2 s, for 5:01 in total, past the bound. The
  admitted connect after the second move was served only because the 4:59 tick's refresh had
  usually landed during the refused connect in between: the same race with a wider margin. Both
  moves now use `AdvanceAsync`. The self-hosted variant (10 s memo) never crosses the bound and goes
  through the same helper.
- **Fixed: `SessionLifecycleTests.A_background_request_renews_neither_cookie_nor_row`**, `hub negotiate`
  kind. It moves 4 days, then POSTs `/1/hub/negotiate`. It asserts no status, and the renewal
  decision is made in cookie validation before the tenant middleware, so a 503 did not fail it. But
  the request could be refused as stale rather than served as a background request. Now it uses
  `AdvanceAsync`, so the arrangement matches what the test claims (the other two kinds are
  tenantless and are unaffected).
- **Fixed: `BlobEndpointTests.A_client_that_stops_reading_holds_the_tenant_s_one_permit_until_the_deadline_frees_it`.**
  Its transfer deadline is the 5-minute web timeout plus the object's length at the minimum rate,
  so the move to it passes the bound. The tenant downloads it then polls (`/1/blobs/...`) were
  answered 503 until the tick's refresh landed, and the poll loop, there to wait out the permit's
  release, silently absorbed those. The move now uses `host.AdvanceToAsync`, so the loop waits on
  the permit alone. Its sibling `A_transfer_past_its_deadline_is_aborted_and_lets_go_of_its_object`
  sends no request after the move and keeps `Time.AdvanceToAsync`.
- **Left as is, correct:** `TenantVerdictTests.A_stale_snapshot_answers_catalog_unavailable_with_a_retry_after`
  moves 6 min with the catalog failing on purpose, so every refresh fails and the 503 is
  deterministic. `SessionLifecycleTests` lines 43, 606 and 612 (`/bff/user`) and
  `ClientTelemetryRelayTests.A_batch_renews_neither_the_session_s_cookie_nor_its_row`
  (`/api/client-telemetry`) are tenantless and never read the registry. `TimerTests` drives the
  hosted services directly and sends no tenant request. The
  Core.Tests registry harnesses (`TenantScopeFactoryTests` line 39 already refreshes after its
  20-hour move; the others assert the stale refusal) run no refresh loop, so they are deterministic.

### Open risks

- `AdvanceAsync` forces a reload, not a probe. The reload reads the same catalog version and
  descriptors, so it tells no listener. A test that changes catalog rows and then calls
  `AdvanceAsync` would have that reload deliver the change. That is correct, and it is what the
  tick would do anyway.
- A future test that moves the clock past 5 minutes with a bare `Time.Advance` and then runs work
  that reads the snapshot brings the race back. The helper's XML doc and the README say when to use
  it. They also say that the forced refresh's failure is the move's failure, so a test that sets
  `Catalog.Failure` or `Catalog.Gate` keeps the bare move.

### What reviewers should examine hardest

- That the forced refresh cannot complete with a `ConfirmedAt` from before the move (the
  `RefreshAsync` queueing in `TenantRegistry`, and that the clock has moved before the call).
- Whether the sweep missed work that reads the snapshot after a move past the bound in a test
  project that uses `TellmaTestHost`.

## Review 1

Verified, not findings:

- **Root cause reproduced independently.** A scratch test (removed; worktree clean afterwards) set
  `host.Catalog.Gate` on a `RealtimeTestHost`, made the bare 4-day `Time.Advance`, awaited
  `AtGate` (the move fired the loop's tick), then sent the negotiate: `503` with problem code
  `catalog-unavailable`. A second scratch held the gate across `host.AdvanceAsync`: the move had
  not completed 500 ms later; after the gate opened it completed with
  `SnapshotLoadedAt == Time.GetUtcNow()` and the negotiate answered 200. An ungated loop of 40
  fresh hosts with the bare move gave 0 of 40 stale on this idle machine, consistent with a
  load-dependent race.
- **Product matches spec 0011 §3.4.** `TenantRegistry.IsFresh` (TenantRegistry.cs:275-278) refuses
  beyond `MaxStaleness` with `TenantUnavailableException(catalog-unavailable, Retry-After)`; the
  loop's tick runs `RefreshAsync(force: false)` after a `PeriodicTimer` continuation, and
  `RunAsync` yields first (TenantRegistry.cs:290-295), so the refresh lands on the thread pool. A
  snapshot four days unconfirmed must not be served; nothing is masked.
- **The helper awaits the real path and cannot finish early.** `ConfirmTenantsAsync` calls the DI
  `ITenantRegistry` (the same singleton `TenantMiddleware` reads, TenancyComposition.cs:51-52)
  `RefreshAsync(force: true)` after the move has returned. Every branch of `RefreshAsync`
  (TenantRegistry.cs:149-177) either starts a new run, queues one behind the running run, or joins
  a pending run that has not started, and `ConfirmedAt` is read in `RefreshCoreAsync` after the
  catalog read (TenantRegistry.cs:363, 377), so the published stamp is always at the new reading.
- **Sweep.** Every fake-clock move in the solution was checked. In the `TellmaTestHost` projects,
  only the four fixed sites pass 5 minutes and then need the snapshot; the others
  (SessionLifecycleTests and ClientTelemetryRelayTests on `/bff/user` and `/api/client-telemetry`,
  TimerTests, TenantVerdictTests' deliberate outage, the first blob deadline test which sends no
  request afterwards) are correct as they are. Core.Tests' `TenantContextHarness`/`RegistryHarness`
  start no refresh loop, so their stale refusals are deterministic, and TenancyCompositionTests'
  live loop moves 15 s at a time. The integration suites move a fake clock only in
  QueryexDiscoverTests (`FastDenyWindow` + 1 s = 6 s, under the bound). No other component pairs a
  background refresh with a fail-closed staleness bound (the other timers, in jobs, sessions and
  membership reconciliation, do not gate a request on freshness). No further site needs the helper.
- **Tests run by Review 1.** `dotnet build test/core/Tellma.Core.AspNetCore.Tests`: Build
  succeeded, 0 warnings (also rebuilt clean after the scratch file was removed). The touched
  classes plus TenantVerdictTests (HubConnectTests, HubConnectionTrackerTests,
  SessionLifecycleTests, BlobEndpointTests, TenantVerdictTests; unit filter, 214 tests): 5 runs in
  a row, all green. The implementer's listed runs match the touched tests (PLAN §7.1 item 4). CI
  on pc/PC-F113 (46006833443) was skipped, since this is not an integration push.

### Findings

**R1-1 (minor). The helper's documentation, and the sweep's premise, name only tenant requests,
but background scopes, connection resolution, the outbox and readiness also fail closed on a stale
snapshot.** The implementer notes state that "only `TenantMiddleware` reads the registry's
staleness-checked `Find`", and `TellmaTestHost.AdvanceAsync`'s summary
(test/shared/Tellma.Testing.WebHost/TellmaTestHost.cs:272-279) and the README row
(test/shared/Tellma.Testing.WebHost/README.md:17) tell a test to use it when it "sends a tenant
request". The registry's staleness check is also read by `TenantScopeFactory.CreateScopeAsync`
(src/core/Tellma.Core/Tenancy/TenantScopeFactory.cs:49), `TenantConnectionProvider.Tenant` and
`TenantConnectionFactory` (TenantConnectionProvider.cs:24, TenantConnectionFactory.cs:21, via
`Get`), `OutgoingEmailDeliveryHandler` (src/core/Tellma.Core/Outbox/OutgoingEmailDeliveryHandler.cs:80)
and the readiness check (src/core/Tellma.Core.AspNetCore/Surfaces/HealthChecks.cs:38,
`IsAvailable`). No current test hits these after a long move, so nothing is broken today. But a
future `TellmaTestHost` test that moves the clock past 5 minutes and then probes `/health/ready`, or
drives a job or outbox delivery through the scope factory, follows the documented guidance, uses
the bare move, and gets the same load-dependent `catalog-unavailable` race. Fix: say in the XML
summary and README that the helper is for any work that reads the tenant snapshot after the move
(tenant requests, background tenant scopes, connection resolution, readiness), and that the
forced refresh's failure propagates, so a test with `Catalog.Failure` or `Catalog.Gate` set keeps
the bare `Time.Advance`. Correct the sweep sentence in the notes to match.

**R1-2 (minor). Two of the fixed arrangements are not pinned, so a revert to the bare move would
bring the race back silently, and the helper's ordering guarantee has no committed test.**
`SessionLifecycleTests.A_background_request_renews_neither_cookie_nor_row`
(test/core/Tellma.Core.AspNetCore.Tests/Sessions/SessionLifecycleTests.cs:108-113) asserts no
status. A scratch run confirmed that the `hub negotiate` kind is answered 200 (by the probe
endpoint) after `AdvanceAsync`, and 503 `catalog-unavailable` when the tick is held after a bare
move. The theory passes in both cases. `BlobEndpointTests`' permit poll
(test/core/Tellma.Core.AspNetCore.Tests/Blobs/BlobEndpointTests.cs:287-298) still treats any
non-304, a 503 included, as a reason to keep asking. Neither test can therefore fail if the
snapshot is stale, which is the condition this change exists to rule out. The only evidence that
`AdvanceAsync` waits out a delayed tick refresh is the implementer's removed scratch test. Fix:
assert the expected success status per kind in the theory (at least `OK` for `hub negotiate`).
Make the poll loop fail on any answer other than `429` or `304`. Commit the held-gate check of the
helper in Tellma.Core.AspNetCore.Tests: set the gate, start `AdvanceAsync`, assert it has not
completed while the tick is held, open the gate, then assert
`SnapshotLoadedAt == Time.GetUtcNow()`.

### Responses

R1-1: fixed in the fix 1 commit. `AdvanceAsync`'s XML docs now name every kind of work that reads the
snapshot: a tenant request, a background tenant scope (job, outbox delivery), a tenant connection's
resolution, and the readiness check. They also say that the refresh's failure is the move's failure,
so a test that wants the snapshot stale, or holds or fails the catalog's reads, keeps the clock's
own move. `AdvanceToAsync` refers to the same work and failures. The Tellma.Testing.WebHost README
row says the same and names `Catalog.Failure` and `Catalog.Gate`. In the implementer notes, the
sweep sentence now lists the readers (TenantMiddleware, TenantScopeFactory,
TenantConnectionProvider/Factory, OutgoingEmailDeliveryHandler through the scope factory,
HealthChecks) and states that only tenant requests follow a long move in these projects. Open risks
and the reviewer pointers are widened to match.

R1-2: fixed in the fix 1 commit. `SessionLifecycleTests.A_background_request_renews_neither_cookie_nor_row`
now takes the status each kind is served with and asserts it: 200 for the activity header, 400 for
the telemetry relay's empty `{}` batch (its endpoint's own validation, past the tenant-free route),
and 200 for the hub negotiate (the probe endpoint). A stale snapshot's 503 now fails the
`hub negotiate` row. `BlobEndpointTests`' permit poll asserts each answer is 429 or 304, so a 503
fails at once instead of being retried. New `Tenancy/SnapshotConfirmationTests` (listed in the
project README) pins the helper. `A_long_move_ends_only_once_the_snapshot_is_confirmed_at_the_new_reading`
sets `Catalog.Gate`, starts `AdvanceAsync(4 days)`, waits for `AtGate`, and asserts that the move has
not completed and `IsAvailable` is false. It then opens the gate and asserts
`SnapshotLoadedAt == Time.GetUtcNow()` and `IsAvailable`; no sleep is involved, because the move
cannot end while the read is held. `A_move_whose_refresh_fails_fails_with_the_catalog_s_error` pins
the propagation named in R1-1: with `Catalog.Failure` set, `AdvanceAsync` throws that same exception
and the snapshot stays unavailable.
