# PC-F113: HubConnectTests negotiate 503 after a fake-clock advance

## Implementer notes

### What was built

Fix item from PC-129's integration CI 45945997084 (build-test, windows-latest, on 424e67df; D-404).
Test-only change: a clock move on the shared web test host that waits for the tenant snapshot to be
confirmed again, used by the tests that move the clock past the snapshot's staleness bound and then
expect a tenant request served.

**Root cause (D-011).** `HubConnectTests.Neither_the_negotiate_nor_the_connect_renews_or_stamps_the_session`
moved the fake clock 4 days (`host.Time.Advance`) and sent the negotiate to `/1/hub/negotiate` at
once. The tenant snapshot was last confirmed at host start, so after the move it was 4 days old, far
past `Tellma:Catalog:MaxStaleness` (5 min). `TenantRegistry.Find` then throws
`TenantUnavailableException(catalog-unavailable)`, which `TenantMiddleware` answers 503, until a
refresh confirms the snapshot again. The move does fire `TenantRegistryRefreshService`'s
`PeriodicTimer` tick, but the loop's continuation and `TenantRegistry.RunAsync`'s `Task.Yield` put
the refresh on the thread pool, two hops away. The test thread, meanwhile, sends the negotiate
through the in-memory TestServer straight away. On an idle machine the refresh nearly always lands
first. On a loaded runner (`-m:2`, parallel assemblies), the negotiate can reach the tenant
middleware first and gets 503 `ServiceUnavailable`, which is the CI failure at line 324.

**The product is right.** Spec 0011 §3.4 (and §1.4 principle 1, "fail closed") says that beyond
`MaxStaleness` every tenant request answers `503 catalog-unavailable`. A snapshot unconfirmed for
4 days must not be served, because doing so could keep serving a suspension that was lifted, or an
access that was revoked. On a real clock the loop re-confirms every 15 s, so a request only sees
503 after 20 failed refreshes in a row, or for a moment after the host resumes from a long suspend.
That is the intended fail-closed behaviour, not a cache bug. The fault was in the test's
arrangement.

**Reproduced.** A scratch test (not committed) set `host.Catalog.Gate` before the 4-day move,
which held the tick's probe at the catalog read (`AtGate` signalled, proving the move fired the
tick), and then sent the same negotiate. It failed exactly as CI did: `Expected: OK`,
`Actual: ServiceUnavailable`.

**Fix.** `TellmaTestHost.AdvanceAsync(TimeSpan)` (test/shared/Tellma.Testing.WebHost) moves the
clock and then awaits `ITenantRegistry.RefreshAsync(force: true)` (bounded by `Patience`). A forced
refresh always starts after any refresh already running (the registry queues it), so the snapshot it
publishes is confirmed at the new reading, whichever of the tick's run and this one goes first. A
twin, `TellmaTestHost.AdvanceToAsync(mark, due, count)`, wraps `TestClock.AdvanceToAsync` (the
armed-timer move) the same way. Bare `Time.Advance` stays for the tests that want a stale snapshot
or that send no tenant request. The
test now moves the clock with `await host.AdvanceAsync(TimeSpan.FromDays(4))`. Its assertions are
unchanged: no retry, no quarantine, no longer timeout. A second scratch test (not committed) held
the gate across `AdvanceAsync`, checked that the move had not completed 500 ms later, then opened
the gate and showed the negotiate answers 200. So the helper waits out a delayed tick refresh
instead of racing it.

### Sweep of the siblings that move the clock

I checked every `Time.Advance` / `AdvanceToAsync` in the projects that use the web test host
(Core.AspNetCore.Tests; Mcp.Tests, Defaults.Azure.Tests and the Azure AspNetCore integration tests
move no clock). The pattern only matters where the total move passes 5 minutes and is followed by a
tenant-routed request (only `TenantMiddleware` reads the registry's staleness-checked `Find`):

- **Fixed: `HubConnectionTrackerTests.On_Azure_SignalR_Service_a_remembered_close_lasts_the_service_token_s_five_minutes`**
  (`AssertMemosExpireAsync`). It moves 4:59 and then 2 s, for 5:01 in total, past the bound. The
  admitted connect after the second move was served only because the 4:59 tick's refresh had
  usually landed during the refused connect in between: the same race with a wider margin. Both
  moves now use `AdvanceAsync`. The self-hosted variant (10 s memo) never crosses the bound and goes
  through the same helper.
- **Fixed: `SessionLifecycleTests.A_background_request_renews_neither_cookie_nor_row`**, `hub negotiate`
  kind. It moves 4 days, then POSTs `/1/hub/negotiate`. It asserts no status, and the renewal
  decision is made in cookie validation before the tenant middleware, so a 503 did not fail it. But
  the request could be refused as stale rather than served as a background request. Now it uses
  `AdvanceAsync`, so the arrangement matches what the test claims (the other two kinds are
  tenantless and are unaffected).
- **Fixed: `BlobEndpointTests.A_client_that_stops_reading_holds_the_tenant_s_one_permit_until_the_deadline_frees_it`.**
  Its transfer deadline is the 5-minute web timeout plus the object's length at the minimum rate,
  so the move to it passes the bound. The tenant downloads it then polls (`/1/blobs/...`) were
  answered 503 until the tick's refresh landed, and the poll loop, there to wait out the permit's
  release, silently absorbed those. The move now uses `host.AdvanceToAsync`, so the loop waits on
  the permit alone. Its sibling `A_transfer_past_its_deadline_is_aborted_and_lets_go_of_its_object`
  sends no request after the move and keeps `Time.AdvanceToAsync`.
- **Left as is, correct:** `TenantVerdictTests.A_stale_snapshot_answers_catalog_unavailable_with_a_retry_after`
  moves 6 min with the catalog failing on purpose, so every refresh fails and the 503 is
  deterministic. `SessionLifecycleTests` lines 43, 606 and 612 (`/bff/user`) and
  `ClientTelemetryRelayTests.A_batch_renews_neither_the_session_s_cookie_nor_its_row`
  (`/api/client-telemetry`) are tenantless and never read the registry. `TimerTests` drives the
  hosted services directly and sends no tenant request. The
  Core.Tests registry harnesses (`TenantScopeFactoryTests` line 39 already refreshes after its
  20-hour move; the others assert the stale refusal) run no refresh loop, so they are deterministic.

### Open risks

- `AdvanceAsync` forces a reload, not a probe. The reload reads the same catalog version and
  descriptors, so it tells no listener. A test that changes catalog rows and then calls
  `AdvanceAsync` would have that reload deliver the change. That is correct, and it is what the
  tick would do anyway.
- A future test that moves the clock past 5 minutes with a bare `Time.Advance` and then sends a
  tenant request brings the race back. The helper's XML doc and the README say when to use it.

### What reviewers should examine hardest

- That the forced refresh cannot complete with a `ConfirmedAt` from before the move (the
  `RefreshAsync` queueing in `TenantRegistry`, and that the clock has moved before the call).
- Whether the sweep missed a tenant request after a move past the bound in a test project that uses
  `TellmaTestHost`.
