# PC-115: Navigation registry, core entries and the pins model

## Implementer notes

### What was built

Spec 0027 §3, §8.2–§8.3, §9.6 and §2, in `client/projects/core/tellma-core/`.

- **Navigation registry** (`src/nav/tm-navigation.ts`, primary). `TmNavigation` with `sections`,
  `items`, `byHref` and `resolve`.
  - Candidates come from `TM_APP_DECLARATIONS` after `hide`: stacks with a `query` operation and
    a segment (plural label, `file-text`, `createHref` when `allows(name, 'save')` and the entity
    has a details page), pages without a path parameter (`square-dashed`, behind `securable`),
    coded reports with their patches (`chart-column`, behind `securable`) and feature entries
    (`link`, any one of `requires`).
  - `visibleWhen`: hidden while `TmLaunchCache.distribution()` is absent; a predicate that throws
    hides its entry and reports `tm.nav.visible-when` once per entry (written through `untracked`,
    since the state is a `computed`).
  - Order: `order` (default 100), then the label in the active language (`Intl.Collator`), then
    the id. Sections without a visible entry drop out; an entry naming no shown section is
    search-only and follows the section entries in `items`.
  - The declarations are read only once `TmClientMetadataStore.current()` is set, because
    `TM_APP_DECLARATIONS` injects `TM_CLIENT_METADATA`, which throws before the Core chunk loads
    and stays failed once it has.
  - `resolve`: `unavailable` when `describe` finds no tenant route, when the URL's path is the
    `href` of an entry `visibleWhen` hides, or when `visibleWhen` hides the route's owner (the
    entity, page or coded report); `no-access` per §8.3's checks; stored reports and dashboards
    (`core.Report`/`core.Dashboard` details) are `ok`. A core route is gated by its core entry's
    `requires`, falling back to the core feature's own declaration when a distribution hides it.
- **Core navigation** (`src/nav/tm-core-nav.ts`, wired in `src/declarations/tm-core-feature.ts`).
  Sections `analysis` (800) and `administration` (900); entries `core.settings` (administration,
  40) and the search-only `core.me`, `core.me.profile`, `core.me.region`, `core.me.display`,
  `core.me.notifications`. `core.settings` has no `requires`: the registry shows it with `Read` on
  any `metadata.settingCategories[].resource` (that is, any `core.Settings.<category>`), unless a
  distribution gives it `requires`. Strings: `tm.nav.*` in `TM_STRINGS_EN` and the Arabic table
  (`tm.admin.settings.title` and `tm.admin.me.title` already existed).
- **Pins model.**
  - Primary (`src/nav/tm-pins.ts`): `TmPinsDoc`, `TmPinItem`, `TmPin`, `TmPinFolder`, `tmPinsKey`
    (`nav.pinned`, curated, fallback `{ v: 1, items: [] }`, validate = shape) and
    `tmPinnedBarVisibleKey` (`nav.pinnedBarVisible`, curated, `true`).
  - Shell (`shell/src/pins/tm-pin-rules.ts`, not exported yet): `TM_PIN_LIMITS`, `tmPinsView` (ids,
    lengths in code points, the 30/10 caps, one level, duplicate ids; returns the document itself
    when nothing drops), `tmPinUrl` (capture minus `page`, `#d=` kept), `tmPinHref`, `tmCurrentPin`,
    `tmPinLabel`, `tmNewPinId`. `TmPins` (spec 0027 §8.4) will consume them.
- **Launcher seam** (`src/nav/tm-launcher-providers.ts`, primary): `TM_LAUNCHER_PROVIDERS` (root
  factory `[]`), `TmLauncherProvider`, `TmLauncherItem`, `TmLauncherSearchContext`.
- **Launcher terms** (`shell/src/launcher/tm-nav-terms.ts`, not exported yet): `TmNavTermsReader`,
  an entry's label and synonyms in a language, split on `,` and `،`.
- **Recents** (`recents/src/tm-recents.ts`): the `TM_RECENTS_NAVIGATION` seam is gone; `TmRecents`
  injects `TmNavigation` (`byHref` for title and icon, `resolve` for the filter). The edit is
  limited to the seam swap.
- **Budgets.** `.` raised 45 → 47 (44.81 → 46.63 linked, +1.82 KB; note in `package.json`);
  `@tellma/locale-ar/strings` raised 6.5 → 7 (6.47 → 6.66, +0.19 KB). `./recents` dropped to 1.47.
  `./recents` added to `staticGraphExcludes["./shell"]`.
- **Test rig** (`src/routes/tm-app.testing.util.ts`): `tmAppRig` takes `features`, `languages` and
  `strings`.

### Deviations

1. `TmNavItem` adds `label` (the active language's) and makes `icon`, `order` and `synonymsKey`
   required with their defaults applied; `TmNavSectionView` adds `label`. The launcher, pins and
   recents need the resolved values, and resolving them once in the registry keeps them sorted by
   the same labels.
2. The pins key's `validate` checks the shape only (`v: 1`, an `items` array). The item rules (ids,
   lengths, caps, one level) live with the pinned bar in `/shell`. §8.2 says a failing item leaves
   the view but stays stored, which a boolean `validate` cannot express (it would turn the whole
   value into the fallback), and §1 places only the pins types and keys in the primary.
3. The synonyms split (§3.3 "the registry splits it") lives in the shell's `TmNavTermsReader`,
   next to the launcher index that reads it, not on `TmNavigation`. It keeps the primary to the
   §3.1 contract. This and deviation 2 took 0.89 KB off the primary.
4. Entity entries come from stacks only. A child entity with a segment (`acme.SalesInvoiceLine`)
   has no search page: its segment routes only to drill-through lists, so an entry would not
   route.
5. Strings are platform `tm.*` keys in `TM_STRINGS_EN` and the Arabic table, not resx: the
   platform client's own strings live in the `tm` tables. The labels stay in the primary because
   the registry resolves them for the pinned bar's and recents' first render. The three
   synonyms strings are the launcher's own (`tm.launcher.synonyms.*`), registered when its term
   reader loads (fix 1).
6. No icon glyphs registered for the default or core icon names (`file-text`, `square-dashed`,
   `chart-column`, `link`, `settings`, `user-cog`, `user`, `globe`, `sun-moon`, `bell`), against
   spec 0024 §2.2's one-place rule (`platform-icons.ts` registers every name a platform
   declaration uses, within §12's 4 KB icon share). Registering them costs 0.92 KB of the
   primary, and no first-frame surface draws them: pin chips show no icons and the launcher and
   Manage pins are deferred. The launcher, pinned bar, Manage pins and home recents checkpoints
   register the names they draw in their deferred chunks.
7. `byHref` also finds a feature entry whose own `url` has a query (`/17/customers?f.X=…`); the
   spec describes path-only lookups. Callers that pass a path get exactly the spec's behaviour.
8. **The outdated-client verdict's build rules load lazily** (integration, D-252), against spec
   0024's placement of the whole HTTP layer in the primary. `tmCompareBuilds` and the first-older
   window move from `tm-api-wire.ts` and `TmHttpApi` into `src/api/tm-api-verdict.ts`
   (`tmBuildVerdict`), a chunk of its own that `#verdict` imports at the first `412
   client-outdated` or `404 route-not-found` answer. No first-frame call needs it. If the chunk
   cannot load, the builds count as unordered, so the worker's update check decides, as §5.6 does
   for unordered builds, and the telemetry says `source: 'worker'`. Saves 0.34 KB of the primary
   on the merged base; the chunk weighs 0.51 KB alone against a 1 KB ceiling.
9. **The file transfers load lazily** (integration, D-252), against the same placement. A
   download's streamed read with its `Content-Disposition` name (`tmReadDownload`,
   `tmDispositionFileName`) and an upload's `XMLHttpRequest` send (`tmSendFile`) move into
   `src/api/tm-api-transfer.ts`, a chunk the layer imports at a download's answer or an upload's
   send. No first-frame call transfers a file. If the chunk cannot load, the attempt fails as a
   network failure would (a download, being a read, is retried as one). An upload cancelled while
   the chunk loads is not sent. Saves 0.35 KB of the primary on the merged base; the chunk weighs
   0.75 KB alone against a 1 KB ceiling.

**R1-1 (major, by the brief's budget criterion; 0.05 KB).** The launcher synonyms sit on the
first frame, though only the deferred launcher reads them.
- **Where:** `client/projects/core/tellma-core/src/l10n/tm-english.ts:48`, `:50` and `:52`
  (`profile_Synonyms`, `region_Synonyms`, `display_Synonyms`).
- **Why they are not needed eagerly:** only `TmNavTermsReader`
  (`shell/src/launcher/tm-nav-terms.ts`) reads them, for the launcher index. Spec 0027 §9.8 puts
  that index in a deferred chunk. `TmNavigation` never reads a synonyms string; it carries only
  `synonymsKey`. The primary therefore ships 0.05 KB that no first-frame code needs.
- **Fix, now that PC-117's `TmLocalization.ɵregisterStrings` is on platform-core:**
  1. Give the three core entries an explicit `synonymsKey` under a scope that the launcher owns,
     such as `tm.launcher.synonyms.meProfile`. The default `${labelKey}_Synonyms` would land in
     `tm.nav`, which the primary owns, and a scope belongs to one entry point.
  2. Have `TmNavTermsReader` register that English scope once, when it is created.
  3. Leave the Arabic in `strings-tm-ar.ts` under the new keys. A language table that holds a key
     wins over the registered English, so `@tellma/locale-ar` keeps them.
- **Placement:** `TmNavTermsReader` must land in the launcher's deferred chunk, not in `/shell`'s
  eager code. Otherwise the reader's own weight joins the first frame too.

**R1-2 (minor).** Deviation 6 (no glyphs registered) departs from spec 0024 §2.2, which the
deviation does not name, and no carry records the duty it moves.
- **Spec 0027:** it says only "a registered icon name".
- **Spec 0024 §2.2:** it makes `src/icons/platform-icons.ts` "the one place the platform registers
  icon names: every name a platform declaration … uses", and "a spec that uses a new name adds it
  there". Spec 0024 §12 budgets 4 KB of the primary for that icon data, of which about 0.3 KB is
  used today.
- **So on the text, this checkpoint should register** the ten names:
  - `file-text`, `square-dashed`, `chart-column`, `link`;
  - `settings`, `user-cog`, `user`, `globe`, `sun-moon`, `bell`.
- **Cost:** measured on the gate, registering them adds 0.92 KB to the primary (47.55, over the
  47 ceiling).
- **Why keeping them off the first frame is still right:**
  - No first-frame surface draws them: pin chips show no icons (§8.3), and the launcher and the
    Manage pins dialog are deferred.
  - Under D-247 the bytes matter.
- **Failure scenario:** a later launcher, Manage pins or home-page checkpoint draws these names
  without registering them. Each then renders an empty box with a dev-mode error (spec 0023 §3.1).
  Nothing forces that work, because the duty exists only in this commit's prose.
- **Fix:** keep the deviation, but:
  - name 0024 §2.2 and §12's icon share in it;
  - record a carry on the launcher, pinned bar and Manage pins checkpoints, and on spec 0035's home
    recents, to register these names through `TmIconRegistry.register` in their deferred chunks;
  - flag the one-place rule against the first-frame squeeze for Ahmad.

**R1-3 (minor).** Settings shows to every member when the metadata lists no settings category.
- **Where:** `client/projects/core/tellma-core/src/nav/tm-navigation.ts:406` and `:419`.
- **Cause:** for `core.settings` without its own `requires`, `#requires` maps
  `metadata.settingCategories` to `Read` refs. With an empty list it returns `[]`, and
  `#passes([])` treats an empty list as "needs none", so it returns true.
- **Effect:** the Settings entry shows to everyone, and `resolve('/17/settings')` is `ok`.
- **Spec:** 0027 §3.2 says it is visible "with `Read` on any `core.Settings.<category>`". With no
  category, nothing passes.
- **Fix:** tell "needs none" apart from "any of an empty list". For example, `#requires` returns
  `null` for no requirement, and `#passes` returns false for an empty list. Add a test with
  `settingCategories: []`.

**R1-4 (minor).** Three of the registry's rules have no test that would fail if the rule broke.
1. **Language switch.**
   - **Rule:** recomputation and re-sorting on a language switch (§3.1 "Recomputed when … the
     language … changes"; the deliverable's "language re-sort").
   - **Gap:** `tm-navigation.spec.ts:363` starts the app in Arabic. A registry that sorted once
     and never re-sorted would pass.
   - **Fix:** switch `en` → `ar` while running, then assert both the new labels and the new order,
     for example `sales: acme.Customer credit-review acme.overdue`.
2. **Tenant change.**
   - **Rule:** recomputation on a tenant change.
   - **Fix:** navigate `/17/...` → `/18/...` and assert that every `href` follows.
3. **An entry hidden by `visibleWhen`.**
   - **Rule:** `resolve`'s branch for "the entry whose `href` is the URL's path" hidden by
     `visibleWhen` (`tm-navigation.ts:217`, `state.hidden.has(…)`).
   - **Gap:** every `unavailable` case in the spec is also caught by `#ownerShown`, because the
     gated owner is the page or the entity itself. Deleting the `state.hidden` check leaves every
     test green. The broken-predicate test (`:322`) never resolves `/17/approvals`.
   - **Fix:** add a feature `entries` item at `/17/approvals` with `visibleWhen: () => false`. The
     page itself has no predicate. Assert that `resolve('/17/approvals')` is `unavailable`.

**R1-5 (minor).** The `.` budget note's "Savings taken" overstates a measure-only saving, and
deviation 5's reason is stale.
- **The 0.89 KB:** the note credits 0.89 KB to moving the pin rules and the term reader out

  - **The term reader** leaves the first frame only if it lands in the deferred launcher chunk.
- **Fix:** have the note say both of these points, as PC-103's own note did.
- **Deviation 5:** its reason ("the strings-registration seam is not on platform-core") is no
  longer true. It was never the operative reason either: `ɵregisterStrings` serves lazy entry
