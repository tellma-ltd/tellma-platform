### Non-obvious rulings

1. **"Nothing instantiated while loading with nothing held"** is read through spec 0031 §6.2 and §14:
   what must not be instantiated are the field templates of the layout kit (PC-129). The layout
   itself renders over an empty, not-landed record (status `loading`, `entity()` undefined, model
   `{}`), so its cards can draw their skeletons. The harness test asserts that: the layout renders,
   busy, no bar, a title skeleton, "Loading" in the status line and Edit disabled.
2. **Save is interim.** §10.1 here is registration only; Save writes through the source, lands the
   result, leaves edit mode and replaces `new` by the record's URL. The concurrency, confirmations,
   422 landing and leave guard are PC-133's.
3. **The Actions menu is a disabled placeholder** and the pager is an empty slot. They are the
   later checkpoints' contents.
4. **Cancel in create mode leaves the page**: Back when the router's history state shows an earlier
   in-app navigation (`navigationId > 1`), else the search page.
5. **A refresh that fails in edit mode keeps the edit.** The status strip says so ("This record
   couldn't be refreshed. Your changes are kept.") beside a Try again, and the failure never
   replaces the record after Save or Cancel. A refresh that fails in view mode, or the read of a
   record that has not landed (a clone's source among them), replaces the body with the error
   state.
6. **A layout chunk that fails to load** shows as an offline error state in the band.
7. **The document title** comes from the page through a new internal seam on the title strategy in
   the primary (`ɵsetPageTitle`), since the route's title is the entity's singular and spec 0024
   §4.4 titles the document by the page.

### Findings

**R1-1 (major): a clone whose read fails becomes a "ready" create form over `{}`, and Save is live
while the clone loads.**
`details/src/tm-details-controller.ts:216-219` (`status`), `:345-349` (the record-follow effect) and
`details/src/tm-details-frame.ts:508` (Save's `enabled`).

- `#start` opens `/new?clone=N` as a `create`-mode record that has not landed, with model `{}` and
  no defaults or child arrays.
- When the clone's read fails, `status` maps every read error under a non-view record to `ready`,
  and the effect keeps any non-view record.
- Scenario: `/17/customers/new?clone=999`, where 999 was deleted, or is outside the user's Read
  filter. The page shows "New customer" with an editable layout over `{}`. It shows no error state
  and no "Customers" way out. `error()` is null, so a `tenant-not-found` error is never presented
  either.
- Spec §3.3 step 5 says "A failed read shows the routed record's error state (§3.5), whatever the
  kind".
- Separately, while the clone's read is still running, Save's page action is enabled
  (`editing() && !busy()`), so Save or Mod+S writes `{ entities: [{}] }`.
- Fix:
  - The ready-under-an-edit rule should apply only to a record that has landed. In `status`, use
    `record?.landed() && record.mode() !== 'view' ? 'ready' : 'error'`.
  - The follow effect should drop a record that has not landed, whatever its mode.
  - Save should be enabled only once the record has landed.
- Add harness tests: a clone of a 404 record shows the not-found state with its link, and Save is
  disabled while the clone loads.

**R1-2 (major): a failed refresh in edit mode is never presented, and it resurfaces as the page's
error after a successful Save or Cancel.**
`details/src/tm-details-controller.ts:216-219`, `:227-237`, `:448-451` and `:488-491`.

- Deviation 7 and ruling 5 say a failed edit-mode refresh "keeps the edit and presents the error".
  Nothing presents it:
  - `status` reports `ready`, so `error()` is null and the frame's error slot never renders;
  - `#present` runs only for tenant errors.
- The resource stays in `error`. Once Save (`mode.set('view')`, then `land`) or Cancel returns the
  record to view mode, `status` reads that old error and the band swaps the freshly saved record for
  the stale error state.
- Scenario: a layout calls `injectTmDetails().refresh()` while editing (spec §4.1 allows it), and the
  read fails offline. The user sees nothing. They then save successfully, and the page shows the
  offline error state instead of the saved record.
- Fix:
  - Present an edit-mode read failure, through `TmErrorPresenter.present(error, { kind: 'read' })`
    or a strip notice.
  - Make the record's landing clear that failure. Either tie the error to the generation or key it
    was read under, and ignore it once a later land or save moved the record, or re-read on leaving
    edit mode.
- Add a harness test: a failed refresh in edit mode, then Save, shows the saved record.

**R1-3 (major): `tmFakeDetails({ mode: 'edit', record })` yields an empty, dirty context.**
`client/projects/core/tellma-core-testing/src/tm-fake-details.ts:224-247`.

- The record state is constructed with `mode: 'edit'`. `land()` then adopts `entity` and `model`
  only in view mode (`tm-details-record.ts:272-277`).
- The fake therefore has `entity()` undefined, `model()` `{}` and `base` null, so `dirty()` is true
  from the start.
- The options' own docs offer `edit`, and the testing export is a checkpoint deliverable that
  PC-129's layout tests will use. No test covers this mode.
- Fix: construct the record in `view`, land the record, then set `base` to the entity and `mode` to
  `edit`, as the host's `edit()` does. Add a record-spec case for the edit-mode fake.

**R1-4 (minor): Save's steps after the write run on a destroyed page.**
`details/src/tm-details-controller.ts:477-491` (and `:440-451` after the Discard question).

- If the user leaves during the write (the crumb, or New: there is no navigation lock yet), the
  write resolves after the frame and controller are destroyed.
- `record.land` then runs on a disposed record. `#afterRender` then calls `afterNextRender` with the
  destroyed page's injector. That registers on the destroyed view's `DestroyRef`, which throws
  NG0911 ("View has already been destroyed") inside the `try`. The error is rethrown as a non-API error,
  so `TmPageActions.invoke` rejects unhandled.
- `#present` already guards against this case by using the environment injector. The other
  post-await steps do not.
- Fix: keep a `destroyed` flag, set in the existing `onDestroy`, and return after each await when it
  is set. Clearing the draft can still run.

**R1-5 (minor): the write's `base` is not `null` in create mode.**
`details/src/tm-details-controller.ts:477` against `details/src/tm-details-source.ts:48-49`.

- `TmDetailsChange.base` is documented as "`null` in create mode". The controller passes the new
  record's start, which `#start` stores as `base`.
- A settings or custom source that tells create from edit by `base === null` misbehaves.
- Fix: pass `mode === 'create' ? null : record.base()`. Alternatively, reword the TSDoc and the
  spec's contract, but the spec's change object is the one PC-133 builds on.

**R1-6 (minor): an int-keyed id past the safe integers opens create mode at a record URL.**
`details/src/tm-details-host.ts:84` and `details/src/tm-details-model.ts:120-129`.

- `detailsMatch` admits any positive digit string (`tmIsIdSegment`).
- For an `int` key, `tmDetailsRouteId('99999999999999999', 'int')` returns `null`, and the host
  treats `null` as create mode. `/17/customers/99999999999999999` then shows "New customer", and
  Save creates a record.
- Fix: tell "no id input" (the `new` route) apart from "an id that names no record". The second
  should show the not-found state, for example by keeping the id as text so the read 404s, or by
  surfacing a `not-found` error at once.

**R1-7 (minor): a descriptor change re-reads the record and wipes a clone's edits.**
`details/src/tm-details-host.ts:90-96` and `details/src/tm-details-controller.ts:583-587`.

- `source` and `cloneSource` are computed over `descriptor()`. `TmEntities.get` returns a new
  descriptor when the tenant's shape changes, such as a settings sync that adds a content language.
- The recompute makes new source objects, so `#routed` changes and the resource re-reads:
  - in view mode, that is an unrequested Refresh, under the bar;
  - on `/new?clone=N`, the landing calls `record.start(copy)` on the record the user is editing, and
    their edits are replaced without a word.
- Fix:
  - Read the descriptor untracked in `cloneSource`, which only needs the id.
  - In `#land`, start a clone's copy only on a record that has not landed yet.

**R1-8 (minor): test gaps for rules this checkpoint implements.**

- None of these paths has a test:
  - the clone-read failure (R1-1);
  - a layout chunk that fails to load (deviation 8: the offline error state and its Try again);
  - a failed refresh in view and edit modes (ruling 5);
  - `TmErrorState`'s new `link` input in `errors/src` (it is tested only through the details host,
    and nothing asserts that the view's first action drops to `secondary` beside it);
  - the clone strip's recursion into a grandchild collection (§3.6 step 4 says "recursively", and
    the unit tests cover one level).
- The Acme e2e's "zero requests" check counts only `/1/api/web/customers/` URLs
  (`cold-deep-link.spec.ts`, the `page.on('request')` filter). The done-when is "View→edit→cancel
  round-trips with zero requests". Widen the filter to every `/api/` request, or every request after
  the page is ready.
- Fix: add the tests listed under R1-1, R1-2 and R1-3, plus a layout-failure test, a grandchild
  strip vector and a `link` case in the errors spec.

### Assessment of the orchestrator's points

1. **The details route budget, 121.01 KB with `TmValue`.**
   - **What the gate measures.** It overcounts against spec 0024 §12.
     - `tellma-core-tools/src/checks/budgets.ts:221-222` measures each route as the static closure
       of every output chunk that holds any `@tellma/core/entity` module.
     - `/entity` has its own on-use chunks: `tm-action-dialog`, `tm-action-run`,
       `tm-confirmations-dialog` and `tm-entity-paste`, all loaded by `import()`. `tm-action-dialog`
       statically imports `TmValueEditor`, and through it the entity field, the pickers,
       multi-select, the date picker, form-field and `@angular/forms/signals`. So the moment
       anything imports `/entity`, both `detailsRoute` and `searchRoute` count every one of those
       chunks. That is why both read the identical 121.01, though Acme has no search page.
     - Spec 0024 §12 defines a route's figure as "the closure of the route host's dynamic import
       plus the distribution's layouts", and says "a @defer'red chunk is budgeted on its own line".
       Spec 0031 §1 says "each dialog at most 4 KB, loaded on use".
     - The measure the spec supports is therefore the static closure of `TM_ROUTE_HOSTS.details`'s
       target plus the layout chunks. `/entity`'s on-use chunks would fall to the existing
       per-chunk `lazy:` lines at the end of `tmMeasureBudgets`.
     - `tm-value` itself is light: avatar, badge, icon, image and the formats. A view-only layout
       measured that way should sit well under 80.
   - **Splitting `/entity` into view and edit pieces** is neither supported nor needed.
     - Spec 0029 §1 places `tm-value` and `tm-value-editor` in one entry point.
     - esbuild already keeps the editor out of a chunk that only `tm-value` reaches.
     - PC-129's `tm-field` will import `tm-value-editor` and `tm-entity-field` statically for edit
       mode (§6.2). So the real closure grows legitimately whatever the split.
   - **Recommendation.** Fix the measure in `budgets.ts`, with a test, before PC-129. Then let
     PC-129 measure the honest figure. If `tm-field`'s edit controls take the route past 80, that is
     a D-031 or Ahmad budget ruling (or a `@defer` of the edit controls), not something to settle
     here.
   - **Must PC-127 act?** No. Its route measures 29.11 of 80, and deviation 15 (raw values, no
     `/entity`) is an acceptable interim until the kit lands. The fix belongs in a fix item on
     `tellma-core-tools`.
