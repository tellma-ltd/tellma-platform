# PC-157: Notifications section of My settings

## Implementer notes

### What was built

Spec 0028 §10.3 in the new lazy entry point `@tellma/core/attention-pages`
(`client/projects/core/tellma-core/attention-pages/`), plus its harness and the server labels the
grid needs.

- **`TmLatestSaver`** (`src/tm-latest-saver.ts`, internal): the self-saving rule. `want(value, waitMs)`
  restarts the wait; one save is in flight; a wait that ends during a save marks it due, and the
  latest value follows the save; a failed save keeps its value for `retry()` unless a newer value
  replaced it; a `reset` outcome (the 422 reload) drops what waited; `dispose()` sends a pending value
  at once (writes are never aborted). State: `idle | pending | saving | saved | failed`.
- **`TmNotificationSettingsModel`** (`src/tm-notification-settings-model.ts`, internal, one per user):
  - Layout from `TM_CLIENT_METADATA`: channels in registration order, cards by category in the order of
    each category's first type, cells `switch | locked | none` (inbox of a `!inbox` type is `none`, of a
    `!mutable` type `locked`). Labels through `TmServerText`: `NotificationCategory_<cat>`,
    `NotificationType_<key, . → _>`, `NotificationChannel_<key>`.
  - Values: every switch cell's value (stored row, else the channel default). The grid saver sends the
    whole set 600 ms after the last change, omitting cells at their defaults; a set equal to the last
    saved one is not sent. `tm.attention.settings-saved { changes: 1|2-5|6+, outcome: ok|failed }`.
  - 422 (`kind === 'validation'`): reload the set, present the save error dialog (`@tellma/core/errors`
    via `import()`), report `reset`. Any other failure: status failed, Try again.
  - `me`: reads `notification-preferences/get`, saves the bare array to `notification-preferences/save`;
    pop-ups through `TmPreferences` (`tmNotificationToastsKey`). Another user: `users/notification-preferences/get { userId }`
    with `users/preferences/get { userId }` in parallel, saves through
    `users/notification-preferences/save { id, arguments: { preferences } }` and, for pop-ups,
    `users/preferences/set { id, arguments: { items: [{ key, value: JSON }] } }` at once (its own saver,
    part of the status). Reads carry the tenant captured at creation and abort on dispose.
  - Reasons: `lockReason` = null while `TmAttention.writable()`, else offline (`tm.errors.offline.title`)
    or frozen (`tm.entity.tenantFrozen`); `testReason` = `lockReason` ?? read-only (`tm.entity.tenantReadOnly`).
  - Test delivery (`me` only): one row per non-inbox channel; the `email` row resolves `contactEmail ?? email`
    from the `me` launch document ("No address" when neither); `users/me/test-notification { channel }`,
    the row busy meanwhile, the result inline and announced through `LiveAnnouncer` (polite); a failed call
    presents the action error dialog without waiting on it.
- **`TmNotificationSettings`** (`tm-notification-settings`, `src/tm-notification-settings.ts`): inputs
  `user: 'me' | number` and `headingLevel` (2; 3 inside the Preferences dialog). Status line in a
  reserved box (`role="status"`, Try again outside the live region); skeleton cards while loading; a
  failed read renders `TmErrorState` (panel size) in a slot, else a plain line with Try again. Cards via
  `tm-card`; the grid is a `<table>` (column headers, row headers) that stacks below md with each
  switch's channel name shown. A locked switch is described by a visible "Always on"; a `none` cell shows
  an `aria-hidden` dash plus a visually hidden "{type}, {channel}: Doesn't show in the app". While locked,
  each control sits under a `tmTooltip` wrapper and is described by one hidden reason span. A model is
  created per `user` value in an effect and disposed on change or destroy.
- **`TmNotificationSettingsPage`** (`src/tm-notification-settings-page.ts`): holds the section for `me`
  and registers the page context (kind `settings`, `/:t/me/notifications`, title `tm.nav.me.notifications`,
  state `{ category: 'notifications', mode: 'edit', dirty }`, errors for a failed read or save) with
  `notifications.settings.set { type, channel, enabled }` (refuses a locked cell as `disabled` "Always on",
  an unknown or `none` cell through `accepts`) and `notifications.settings.test { channel }` (`done` with
  the result as `data`). It is exported only: `TM_ROUTE_HOSTS.me` is still the placeholder the hub
  (0032 §8) replaces, and 0032 §4.8's Preferences dialog mounts `tm-notification-settings [user]`.
- **Strings**: `tm.attentionPages` (`src/tm-attention-pages-strings.ts`), registered by the section and
  the page; Arabic in `@tellma/locale-ar/attention-strings` with a parity spec.
- **Server**: `Strings.resx`/`Strings.ar.resx` gain the three Core categories' labels
  (`NotificationCategory_jobs|users|reports`), the two channels' labels and the seven Core types'
  `NotificationType_*` labels; `ConventionalStringKeys.AddNotifications` now derives
  `NotificationCategory_<category>` for every registered category, so the resource audit holds them.
- **Testing**: `TmNotificationSettingsHarness` in `@tellma/core-testing` (status, Try again, lock
  reason, pop-up switch, category headings, cells by type and channel key, test rows and their results);
  `tmTestMetadata()`'s channels fixed from the invalid `core.inbox` to the platform's `inbox` and `email`;
  the attention rig gains the section's server labels.

6. `tmTestMetadata()`'s channels were the invalid key `core.inbox`; they are now `inbox` and `email`.

   back on, the key's fallback, sends `users/preferences/delete` instead, since spec 0025 §9.1 says

   section's shell and body show spec 0024 §4.4's inline failure views as the route host does.

### Findings

**R1-1 (major): the section takes 79% of the entry point that spec 0028 §1 shares among eight
members, and every later member's page will download it.**
`client/projects/core/tellma-core/package.json` (`budgetsInKb["./attention-pages"]` 8);
`attention-pages/public-api.ts`.

- *The budget.* Spec 0028 §1's 10 KB own-weight budget covers `TmNotificationSettingsPage`,
  `TmNotificationSettings`, `TmNotificationOpenPage`, four list cells (`TmNotificationTextCell`,
  `TmAssignmentTargetCell`, `TmJobLabelCell`, `TmJobProgressCell`) and `TmJobDetails`. This commit
  spends 7.89 KB of it, which leaves 2.11 KB, or 4.61 KB under D-414's 12.5 KB ceiling.
  `TmJobDetails` alone (progress block, poll, announcements, warnings, Confirm, result link) will
  very likely not fit.
- *Where the weight is.* I minified and gzipped the built module
  (`dist/core/fesm2022/tellma-core-attention-pages.mjs`) with esbuild, which gives 8.34 KB by that
  measure. Of that, the component styles are about 0.7 KB and the English strings about 0.26 KB.
  The rest is the compiled templates and the logic. Trimming won't recover several KB.
- *Why it is structural.* Spec 0028 §10.2's text cell is reached through
  `import('@tellma/core/attention-pages')`. With one flat entry point, the Notifications,
  Assignments and Jobs list pages download the whole settings section (model, saver, template,
  styles) with their first cell.

*Suggested fix:* keep the exported `TmNotificationSettings` and `TmNotificationSettingsPage` as thin
shells, and move the section's body (model, saver, template, styles, strings) into an internal lazy
chunk. That chunk can be an `@defer (on immediate)` child or an `import()` the shell awaits. Budget
it on its own line, as `./attention` does with its panels and `./search` with its tiles and filters.
The entry point's own weight then stays near the shells, and each later page pays only for its own
chunk. If you keep the flat layout instead, state the plan for the remaining 2.11 KB in the budget
note and hand it to the checkpoints that add the open page, the cells and the job details, so they
don't find the overrun themselves.

**R1-2 (major): no test pins the signed-in user's pop-up switch.**
`attention-pages/src/tm-notification-settings-model.ts:366-376` (the `me` branch of `setPopups`),
`tm-notification-settings.spec.ts`.

Spec 0028 §10.3 binds the pop-up switch to `notifications.toasts` through `TmPreferences` and has it
apply at once (spec 0025 §9). For `me`, the suite checks the switch's initial state (line 136) and
that it is disabled when the tenant is frozen (line 246), but never toggles it. Another user's
switch is toggled (line 311); the signed-in user's is not. If the `me` branch wrote the wrong key,
wrote nothing, or went through the saver, every test would still pass.

*Suggested fix:* toggle `getPopupSwitch()` for `me` and assert that:

- `TmPreferences.get(tmNotificationToastsKey)()` flips in the same frame;
- the preferences write-behind sends `users/me/preferences/set` with `notifications.toasts`, or
  deletes the key when the switch goes back on;
- no `users/preferences/set` is sent.

Also assert that the pop-up switch is disabled while offline; the offline test doesn't check it.

**R1-3 (major): "leaving sends what still waits" and the saver's failure interleavings have no
test.** `attention-pages/src/tm-latest-saver.ts:93-148`; `tm-notification-settings.ts:491-496`.

`TmLatestSaver` has no spec file. The component suite covers one in-flight save followed by the
latest state, and one failure followed by Try again. These paths are untested:

- a change made during the 600 ms wait, then the section destroyed or its `user` changed (the
  model's `dispose` must send at once);
- a failed save while a newer change waits (the newer set must be sent, and the status must follow
  it instead of sticking on "Couldn't save");
- a 422 with a change made during the failed save (`reset` must drop it along with the reload);
- `dispose` during a flight with a value due.

The implementer listed these paths under "examine hardest". The realistic regression: a user toggles
a switch and clicks another My settings section within 600 ms. Their change is silently lost, and no
test fails.

*Suggested fix:* add `tm-latest-saver.spec.ts` with fake timers, one case per path above, asserting
the values sent and the sequence of `state()` values. Add one component case that destroys the
fixture during the wait and asserts the `notification-preferences/save` body.

**R1-4 (minor): this commit closes PC-F117 only in part. The labels exist, but nothing checks that
a registered category has one.**
`src/core/Tellma.Core/Localization/ConventionalStringKeys.cs:251`;
`test/shared/Tellma.Testing.Resources/ResourceAudit.cs` (finding kinds `Orphan`, `SatelliteOnly`,
`StalePending`).

- *What is done.* The commit labels the three categories registered on this branch, in
  `Strings.resx` and `Strings.ar.resx`: `jobs` (from JobNotices and OutgoingEmailHandler), `users`
  (from CoreFeature) and `reports` (from ShareableContributionRealizer). It also labels both
  channels and seven types; `core.email.failed` already had a label. For today's registry, that
  part of PC-F117 is done.
- *What is missing.* Adding `NotificationCategory_<category>` to the conventional keys only stops
  the audit from reporting the new keys as orphans. The audit has no finding for a derived key that
  no file declares. So PC-178's `files` category, or spec 0026's `support`, would land with no
  label and every test green. The same holds for `NotificationType_*` and `NotificationChannel_*`:
  before this commit, seven registered types had no `NotificationType_` label and nothing failed.
  PC-F117 asks for exactly this check.

*Suggested fix:* add a Core unit test over the composed test model. For each entry in
`INotificationTypeRegistry.Categories`, each type in its `All` and each channel in
`INotificationChannelRegistry.All`, assert that the label key is declared in both `Strings.resx` and
`Strings.ar.resx`. The keys are `NotificationCategory_<c>`, `FromDottedKey("NotificationType_", key)`
and `FromDottedKey("NotificationChannel_", key)`. With that test, PC-F117 closes in full. Without
it, leave PC-F117 open for the check alone.

**R1-5 (minor): a 422 replaces the whole section with skeletons, so the focused switch is destroyed
and the layout shifts.** `attention-pages/src/tm-notification-settings-model.ts:431-434, 519-522`;
`tm-notification-settings.ts:97-108`.

On a 422, `#saveGrid` calls `reload()`, which sets `status` to `loading`. The template then replaces
the pop-up card, every category card and the test card with two skeleton cards, and restores them
when the read returns. The switch the user just toggled is removed, so focus falls to `body`. The
error dialog, which opens after the reload, also returns focus to `body` when it closes. The page
height jumps twice, against spec 0028 §13's stable-layout rule.

*Suggested fix:* keep `loading` and the skeletons for the first read only. A reload from the 422
path or from Try again should keep the cards rendered and replace only the values: `status` stays
`ready`, or a separate `refreshing` flag tracks the read. Disable the grid's controls while it runs
if needed.

**R1-6 (minor): turning another user's pop-ups back on stores the fallback value, unlike the user's
own path.** `attention-pages/src/tm-notification-settings-model.ts:538-541`.

For another user, `#savePopups` always sends `users/preferences/set` with
`notifications.toasts = "true"`. Spec 0025 §9.1 says "A value deep-equal to the fallback deletes the
key", and `TmPreferences` does that for `me` (`tm-preferences.ts:277`). So when an administrator
turns a user's pop-ups off and then on again, the user keeps a stored `true`. A later change to the
key's fallback never reaches them, and the two paths store the same choice in different ways. Spec
0028 §10.3 names `users/preferences/set` for the switch, so whichever reading is taken needs
stating.

*Suggested fix:* when `enabled === tmNotificationToastsKey.fallback`, send `users/preferences/delete`
with `{ id, arguments: { keys: ['notifications.toasts'] } }`. It is an `AllowWhenReadOnly` entity
action on the same grant. Otherwise, record a deviation that the administrator's path stores the
default.

**R1-7 (minor): Deviation 3 misstates spec 0021 §4.4.**
`attention-pages/src/tm-notification-settings-model.ts:275-276`; the commit message's Deviations.

The deviation says spec 0021 §4.4 "defines no other" address than email's. It does: "`ContactMobile`
for an SMS channel". The launch document's profile carries `contactMobile` (`tm-launch-docs.ts:70`).
Leaving it out is defensible, since no SMS channel key is registered or named in the specs (`sms`
appears only as an example in §4.1). The stated reason is wrong, though.

*Suggested fix:* reword the deviation to say that no SMS channel key exists yet, so only `email`
resolves an address. Or resolve `sms` to `contactMobile` alongside `email`.

**R1-8 (minor): some of the section's rules and error paths are untested.**
`tm-notification-settings.spec.ts`.

These have no test:

- a failed `users/me/test-notification` call, which must present the action error dialog and free
  the button with no inline result;
- a failed save of another user's pop-up value, which must show "Couldn't save your changes", with
  Try again resending it;
- `tm.attention.settings-saved` with `outcome: 'failed'`, on a 500 and on a 422;
- spec 0028 §10.3's "Below `md`, each type's switches stack under its label". The suite runs in a
  real browser, so a narrow-viewport case can assert the stacked layout and the visible channel
  labels.

*Suggested fix:* add one case for each.

### Findings

**R2-1 (major): a body chunk that fails to load leaves a permanent, silent skeleton.**
`attention-pages/src/tm-notification-settings.ts:137-147, 76-86, 128-131`;
`tm-notification-settings-page.ts:64-67`; `tm-notification-settings.spec.ts:153-160`; README line 837.

- *What happens.* The rejection only reaches `TmTelemetry.error`. The placeholder is
  `aria-hidden` and stays forever. `aria-busy="true"` stays forever. The page context reports
  `status: 'loading'` with no error and no actions, indefinitely.
- *Who sees it.* The user sees skeleton cards that never resolve, with no message and no Try
  again. A screen-reader user hears nothing. An assistant reading the context waits on a load that
  will never finish.
- *Nothing retries.* `afterNextRender` runs once, so "the next render of the section tries again"
  (the inline comment at line 36 and the README) only happens when the shell is created again, by
  navigating away and back.
- *The platform's rule.* Spec 0024 §4.4 ("A chunk that fails to load runs `TmUpdates.check()`... the
  host shows the error view `client-outdated` inline, and on any other result `offline`") is what
  the route host and `TmNavigationFailure` do. The shell draws the route host's skeleton but not its
  failure. This chunk exists only because of R1-1's split, so its failure should not be worse than
  the page chunk's.
- *The same gap one level down.* `tm-notification-settings-body.ts:655`: if `import('@tellma/core/errors')`
  rejects after a failed read, the error area stays empty. `fallbackError()` is false for a
  `TmApiError`, so the plain line does not show either.

*Suggested fix.*

- On rejection, run the update check (`ɵTM_API_UPDATES`), as the route host does.
- Replace the placeholder with a visible line that has Try again, which calls `#load()` again. Its
  text is `client-outdated` or `offline`, from the primary's `tm.errors` strings, because the body's
  strings ship in the chunk that failed.
- Clear `aria-busy`.
- Expose a failed state that the page reads, so its context says `status: 'error'` with an error
  entry.
- In `#showError`, fall back to the plain line when the errors chunk rejects.

Extend the failing-load test to assert:

- the visible message and the absence of `aria-busy`;
- that Try again loads the body;
- the page context's status, while the chunk loads and after it fails.

**R2-2 (minor): the body's own first-read skeleton collapses to the cards' padding, so every open
shifts twice.** `tm-notification-settings-body.ts:283-289` (`align-items: flex-start` on
`.tm-notification-settings__loading`), `:105-115`; compare `tm-notification-settings.ts:88-94`.

- *The cause.* `tm-card` is `display: block` with no width. As an item of a column flex container
  with `align-items: flex-start`, it sizes to its content. Its only content is skeletons with
  percentage widths, which contribute nothing to that size. So each loading card is about two card
  paddings wide, and the bars inside it are about 0 px.
- *Reproduced* with the same CSS in a browser: the stretched card (the shell's placeholder) measures
  800 px, and the `flex-start` one measures 33 px.
- *What users see.* On every open, the shell's full-width skeleton is replaced, when the chunk
  lands, by two narrow boxes. Those stay until the read returns, and then the full cards appear. The
  same happens on Try again after a failed read. This breaks the zero-shift skeleton rule that the
  shell's placeholder was built to keep (spec 0024 §4.4, spec 0028 §13 stable layout).

*Suggested fix.* Keep `align-items: flex-start` for `__failed` only. Add a test that compares the
placeholder's card rects with the body's loading cards (and with the loaded cards' width), holding
the read with a deferred.

**R2-3 (minor): a change still waiting when the page hides is lost.** `tm-latest-saver.ts:94-101`
(sends only from `dispose()`); `tm-notification-settings-model.ts:488-493`.

- *What happens.* The saver sends on component destruction only. Closing the tab, reloading, or
  following an external link within the 600 ms wait never destroys the component, so the change is
  dropped. No warning appears, even though the page context said `dirty: true`. A whole-set save
  that is in flight at unload is a plain fetch with no keepalive.
- *The platform's convention.* The sibling 600 ms self-saving section, Language & region
  (`TmLocaleWrite`, `src/l10n/tm-locale-write.ts:148`), sends its queue on `pagehide` through
  `TmApi.send` (keepalive). `TmPreferences` does the same (`tm-preferences.ts:192-199`).

*Suggested fix.*

- Have the model listen to `pagehide` through `TM_API_HOST`.
- On it, `TmApi.send` the grid's waiting set (and another user's waiting pop-up value) through the
  same route and body, with the model's tenant id. The bodies are far below `send`'s 16 KB.
- Test it with the fake host firing `pagehide` during the wait.

**R2-4 (minor): a tab on an older bundle deletes the preferences of types and channels it does not
know.** `tm-notification-settings-model.ts:511-521` (`#apply` drops rows whose cell the metadata
lacks), `:531-547`.

- *The server's rule.* Spec 0021 §4.3's `Save` takes the list as "the caller's complete set: rows
  absent from it revert to defaults".
- *The scenario.* A deployment adds a type or a channel. A user (or an administrator, through
  `users/notification-preferences/save`) stores a deviation for it from an up-to-date tab. A tab
  still on the old bundle then saves any change, because the update banner was ignored or the tab
  was left open. Its whole set omits the new type's rows, and the server deletes them silently.
- *Why keeping the rows is safe.* The server already filters types it does not know out of `Get`,
  so every row it returns is valid to send back.

*Suggested fix.*

- Keep the read rows whose key is not in `#cells`, and append them verbatim to every save.
- Count them in neither the `changes` bucket nor `same()`.
- Test it with a stored row for a type absent from the metadata, asserting that the row is sent
  back.

**R2-5 (minor): a 422 reload overwrites another user's pop-up switch while its own save is pending
or failed.** `tm-notification-settings-model.ts:462-474` (the reload also reads
`users/preferences/get` and sets `#otherPopups`), reached from `:551`. The pop-up saver is separate
(`:318`).

- *The scenario.* An administrator turns the user's pop-ups off. That save fails ("Couldn't save",
  with the saver holding `false`) or is still in flight. A grid save meanwhile answers 422. The
  reload sets the switch back to the stored `true`.
- *The result.* Try again, or the in-flight write, then stores `false` while the switch shows on.
  The admin's screen and the stored value disagree, and nothing reconciles them.

*Suggested fix.* On the 422 path, reload the grid's set alone, since the 422 is about the grid. Or
leave `#otherPopups` alone while the pop-up saver is not `idle` or `saved`.

**R2-6 (minor): the test call's likeliest failure, a transport outage, is untested.**
`tm-notification-settings.spec.ts:444-455`.

- *Why it matters.* Spec 0021 §4.4 makes a transport failure `DependencyUnavailableException`, a
  5xx. That is the error a real "Send a test" meets when email is down, and it takes the 5xx dialog
  path.
- *What the test does instead.* The only failure case uses a 403, because the rig's distribution
  document is malformed (see the R1-8 note above). So the section's 5xx path, which presents the
  dialog without waiting and frees the button, has never run.

*Suggested fix.* In this spec's `setUp`, answer `/api/distribution-info` with a well-formed document
that includes `support: { enabled: false, providerAccess: false }`, or fix the shared rig. Then add
a 503 case: the 5xx dialog opens, the button is free, there is no inline result, and the
announcer's last message is not a result.

**R2-7 (minor): one new deviation is unstated, and the budget plan contradicts itself.**

- *The deviation.* Fix1 says "No new deviation", but R1-6 replaced the route that spec 0028 §10.3
  names for another user's pop-up switch (`users/preferences/set`) with `users/preferences/delete`
  when the value equals the fallback. R1-6 itself said "whichever reading is taken needs stating",
  and PLAN §7.1 item 1 requires it. *Fix:* list it under Deviations in the fix2 commit and the

- *The budget note.* `client/projects/core/tellma-core/package.json`, `budgetNotes["./attention-pages"]`,
