# PC-028: Persist frame, error taxonomy, retry, commit probe, instruments and fault injection

## Implementer notes

### What was built, and where

- **The persist frame** (0012 §5.5), in `Tellma.Core/Data/Batches`:
  - `DataBatch.Assemble()` now emits, for a writing `Persist` batch that carries the connect
    prologue, the transaction head (statements in `BatchSection.TransactionHead`, such as spec
    0014's application lock, refused when the text opens no transaction), then `PersistChecks`
    (steps 4 and 5), then the
    body, the epilogue and `COMMIT`. `PersistChecks.Compose` builds the version-tag guard from
    `GuardPremises` (settings and permissions, or settings alone for `System`), every `DependsOn`
    dependency, and `Bumped` from the written tables resolved through `IVersionTagRegistry` plus
    the explicit bumps (two disagreeing expectations of one name become `Guid.Empty`, so the guard
    fails). The guard has a `REPEATABLEREAD` arm for names the batch only reads and an `UPDLOCK`
    arm for names it bumps; the user arm reads `core.UserStamps` (under `UPDLOCK` when the batch
    writes `UserStamps` or a table with a user rule) against `@tm_ExpectedUserPermissionsTag`.
    The caller re-check (`THROW 50401`) follows on a user batch only.
  - `GuardPremises` (`ForUser`/`ForSystem`), handed over by the prologue's contributor through
    `MarkConnectPrologue(GuardPremises)`; `DataBatch.TagParameter()` binds `@tm_tag` for spec
    0013's bump epilogue; `DataBatch.DeclareInsertedRoots(table, ids)` (int and long) names the
    commit probe's rows; `StatementDraft.EntityType` names the entity a tree statement maintains.
  - `IVersionTagRegistry`, `VersionTagEffects`, `UserVersionTagRule` in
    `Tellma.Core.Abstractions/Caching` (spec 0013's contract), resolved optionally by the
    executor.
- **The error taxonomy** (0012 §6.3–§6.4): `DataErrors.Classify` (reported transient,
  ambiguous, final) and `DataErrors.Translate` (platform band, distribution band, provider
  errors, out-of-band numbers → `InvalidOperationException`); the exceptions in
  `Tellma.Core/Data/DataAccessException.cs`, `DataStatementExceptions.cs` and
  `DataAccessFailureExceptions.cs`, every statement exception carrying `StatementOrdinal` from the
  line map. 50409 and 50404 read their preceding result set through `ResultSetCursor.NextIfAsync`
  and `ReadConflictsAsync` / `ReadMissingIdsAsync` (the conflict rows and the missing ids ride on
  the exception). `TellmaSqlErrors` gained the stable message codes.
- **Retry and the commit probe** (0012 §6.5): `RetryRules.Decide` / `Delay` (pure),
  `CommitProbe` (one autocommit `READCOMMITTEDLOCK` count over the first declared root table's
  ids, on its own connection, never cancelled), and `DataExecutor.RunAsync`, the attempt loop:
  per-attempt span, phase tracking (connecting, sent, committing), a lost connection detected on
  the client, rollback unless committing, the probe, the `PK_<Table>` collision after a

  produces are staged on the cursor and applied only on the attempt that settles the round trip,

- **Tests**: unit tests in `test/core/Tellma.Core.Tests/Data/Batches` (`RetryRulesTests`,

  connection; a client-side close after the server committed; a recording connection that hands

### Deviations (also in the commit message)

1. The version-tag registry contract (`IVersionTagRegistry`, `VersionTagEffects`,
   `UserVersionTagRule`) is declared here, in `Tellma.Core.Abstractions.Caching`, ahead of spec
   0013's checkpoint, because the guard's `Bumped` flags need it. The executor resolves it
   optionally; with none registered only explicit bumps are flagged.
2. Steps 4 and 5 are composed by the executor from `GuardPremises`, which the connect prologue's
   contributor passes to `MarkConnectPrologue(GuardPremises)`; the prologue still declares
   `@tm_UserId` and binds `@tm_ExpectedUserPermissionsTag` for a user.
3. The re-checks run on a writing persist in every transaction mode, not only in the frame of
   `Auto`; in `None` their lock hints last one statement, in `Explicit` they hold to the caller's
   commit. A persist that declares no write opens no transaction and carries no re-checks.
4. `TransactionHead` statements are refused when the text opens no transaction.
5. A non-SQL failure after the send of a writing batch (a reader's defect, for instance) is
   classified as ambiguous: `COMMIT` may have run, so the probe answers, or `Unknown` when there
   is nothing to probe. On a batch that writes nothing it surfaces as is.
6. A statement that declares no write counts as safe to run twice after a lost connection, as
   an `Idempotent` one does.
7. `Explicit`: a failure before the send (opening the connection) is re-run like a reported
   transient failure, since nothing reached the server; after the send a transient or lost
   connection surfaces at once as `DataAccessRetryExhaustedException` with `Attempts = 1`, and a
   connection lost while committing as `DataAccessAmbiguousException(Unknown)`.
8. 547 on a `CHECK` constraint is a plain `DataAccessException`; only a foreign key becomes
   `ForeignKeyViolationException`.
9. A final error before the send (a login failure, say) surfaces as the provider's exception,
   untranslated: no statement ran and there is no ordinal to attribute.
10. The `Committed` verdict after a `NotCommitted` probe is reached by 2627 on the primary key of
    the probed root table only, the one table whose keys the probe knows.
11. 50404 is `BatchAssertionFailedException(50404, "Entity.NotFound")` carrying the missing ids
    from the preceding result set (`MissingIds`), which the pipeline maps to `NotFoundException`.
12. `DataAccessRecorder` is created with a scope's first batch, so a scope that runs no batch
    records no `tellma.data.roundtrips` measurement.
13. A probe that itself fails yields `Unknown` (logged), which the spec leaves open.

### Open risks

- The fault tests depend on SQL Server's behaviour after `KILL`: the client sees a severe error
  or a closed connection, which the executor classifies as ambiguous. If a driver version starts
  surfacing a `KILL` as a class-11 error on an open connection, those tests would fail rather than
  pass silently.
- The deadlock test relies on the rival's `DEADLOCK_PRIORITY HIGH` to pick the batch as the
  victim; the lock monitor's detection interval (up to 5 s) bounds its duration.
- `Classify` treats every SQL error class ≥ 20 and a closed connection as a lost connection; a
  server that reports a severe error but keeps the session (rare) would be probed needlessly.
- The persist re-checks in `None` mode are best-effort (no lock outlives the statement); a
  composer that needs the guarantee must use `Auto`.

### What reviewers should examine hardest

- `DataExecutor.RunAsync` / `AttemptAsync`: the order of the cancellation check, classification,
  the PK-collision check and `RetryRules.Decide`; that persist cancellation is ignored once any
  attempt was sent; that rollback is skipped while committing; that `Settle` applies staged
  results only on the settling attempt.
- `RetryRules.Decide` against the table of 0012 §6.5, especially the `Explicit` and `None` arms.
- `PersistChecks.Compose`: the arms' lock hints, the conflict-to-`Guid.Empty` rule, the user arm's
  `UPDLOCK` rule, and the `System` differences.
- `DataErrors.Translate`: the band handling, the duplicate-key and foreign-key name extraction in
  non-English messages, and `StatementOrdinal` resolution (null inside a procedure).
- `DataBatchFaultTests`: whether each test injects its fault at the moment it claims (gate,
  ready statement, `IsBlockedByAsync`) and whether any can pass for the wrong reason. The class
  passed three consecutive runs locally (8 tests, 0.1–4 s each).
- `tellma.data.commit.probes` records every verdict, including the two reached without a probe
  round trip (`unknown` when nothing was declared to probe, `committed` from the duplicate key
  after a `not-committed` probe), as 0012 §6.5 lists them under the one instrument.

### Findings

**R1-1 (major) — Transient numbers raised at severity 20 are classified as lost connections, not
reported transients.** `src/core/Tellma.Core/Data/Batches/DataErrors.cs:139-149`. `Classify`
returns `Ambiguous` as soon as any error has `Class >= 20`, before it looks at the transient
numbers. Azure SQL raises several of §6.4's reported-transient numbers at severity 20: 40501
("service busy"), and the resource-governance errors 10928 and 10929. Failure scenario: during
throttling, a persist that updates rows (no inserted roots to probe) gets 40501. The spec says to
re-run it. Instead it surfaces as `DataAccessAmbiguousException(Unknown)`, which the pipeline
answers with a 503 and a reload instruction. A persist that inserts rows pays an extra probe round
trip before its re-run. On every batch the retry is metered as `class=ambiguous`. The unit theory
`A_transient_number_the_server_reports_is_reported` builds every error at class 16
(`DataErrorsTests.cs:235`), so it cannot catch this. Fix: when the primary error's number is in
`ReportedTransientNumbers`, return `Reported` before applying the class-20 rule, and keep the
lost-connection numbers and other severity ≥ 20 errors as `Ambiguous`. Extend the theory with class
20 for 10928, 10929, 40197 and 40501. If the conservative reading is intended instead, it is an
undeclared deviation from the §6.4 table and needs stating.

**R1-2 (major) — After a `NotCommitted` verdict, only a 2627 on the probed key proves the first
attempt committed, yet the frame's own re-checks fail first in the common case, so a committed
write can be recomposed and written twice.** `src/core/Tellma.Core/Data/Batches/DataExecutor.cs:242-249`,
`:256-264`. The probe answers `NotCommitted` whenever the first attempt has not yet reached its
insert. For example, it may still be waiting on the application lock or on the guard's `UPDLOCK`
behind another writer, while the server runs on after the client lost its socket. The re-run then
queues behind it on the same locks. When the first attempt commits, it has bumped the tags the batch
bumps. The re-run's guard (step 4, before the body's inserts) reads a moved tag on any expected name
the batch also bumps: `permissions` on a role or membership save, `settings` on a settings save, an
`entity:` dependency on a cacheable entity whose validators read its own list. It throws `50412`,
or `50409` from a concurrency guard in a mixed save, before its insert can hit 2627. The executor
treats that as final and surfaces `BatchAssertionFailedException(50412)`. Spec 0014's runner then
reconnects cold and recomposes the save, which writes it a second time, or the user gets a spurious
409 for a save that committed. This is a spec gap (§6.5 names only 2627), but the frame built here
makes it the likely path for exactly the saves that take `UPDLOCK`. Fix: once a `NotCommitted`
verdict was given, answer any final failure of a re-run by probing again before surfacing. Under
`READCOMMITTEDLOCK` the second probe waits for a first attempt that is still running. `Committed`
then becomes `DataAccessAmbiguousException(Committed)`; otherwise the re-run's own error surfaces.
Add a fault test modelled on the `MeterListener` one: on `not-committed`, insert the probed row and
move the `settings` tag of a batch marked with `DataBatchDatabase.Premises`, and expect
`Committed`. **Decision for the orchestrator:** a §6.5 deviation to record.

**R1-3 (minor) — A persist's retry waits and later opens ignore cancellation once any attempt was
sent. §6.1 lists "retry delays" among what the request token cancels, and the deviations do not
mention this.** `src/core/Tellma.Core/Data/Batches/DataExecutor.cs:212-218`, `:314`. After a
reported transient failure (rolled back under `XACT_ABORT`) or a `NotCommitted` verdict, nothing
committed. Even so, an aborted request's persist still waits up to 800 ms and sends a fresh round
trip whose commit nobody will read. Fix: pass `beforeSend` to `Task.Delay` and to the next
attempt's open on those two paths, and throw `OperationCanceledException` when it fires. A sent
round trip still completes. Alternatively, keep the behaviour and list it under Deviations.

**R1-4 (minor) — The rule "a client-side failure on a closed connection is a lost connection"
has no test that fails if it breaks.** `src/core/Tellma.Core/Data/Batches/DataExecutor.cs:340`;
`test/core/Tellma.Core.IntegrationTests/Data/DataBatchFaultTests.cs:108-136`. The only fault that
closes the connection on the client
(`A_connection_lost_after_the_server_committed_is_probed_and_reported_committed`) is a writing,
probeable batch. There, `Defect` and `Ambiguous` both lead to `Probe`, so the test still passes if
`ConnectionLost` is never set, or if line 340 always returns `Defect`. Every other fault uses
`KILL`, which takes the SQL-error path. Fix: add a `Read` variant that closes `connection.Current`
from the ready reader on attempt 1 and expects a re-run (one retry, `class=ambiguous`). A `Defect`
there would surface instead.

**R1-5 (minor) — The commit probe can block on unrelated writers and time out to `Unknown` on large
inserts.** `src/core/Tellma.Core/Data/Batches/CommitProbe.cs:38`. The probe reads the root table
under `READCOMMITTEDLOCK` with no `FORCESEEK`. For a large id list, such as an import chunk of up to
10,000 roots whose TVP cardinality is sniffed at compile time, the optimizer may scan the clustered
index. Under a locking read, a scan waits on every row any concurrent transaction holds, not only
on the first attempt's rows. Scenario: an ambiguous import chunk is probed while other users save
into the same table. The probe blocks behind them until its 30 s timeout, logs
`CommitProbeFailed` and answers `Unknown`, though the first attempt's outcome was knowable. Spec
0013's guard adds `FORCESEEK` for the same reason. Fix: `WITH (READCOMMITTEDLOCK, FORCESEEK)` (the
`[Id] IN (SELECT …)` semi-join seeks the primary key), stated as a deviation from the §6.5 text, and
updated in the unit test's expected text.

**R1-6 (minor) — Deviation 12 drops the zero-round-trip units of work from
`tellma.data.roundtrips`, the budget instrument §12.2 says observes "every scope".**
`src/core/Tellma.Core/Data/Batches/DataBatch.cs:107-108`;
`src/core/Tellma.Core/Data/Batches/DataComposition.cs:41-42`. The recorder is created only when a
scope creates a batch. A request served wholly from the caches (permissions, settings,
`FromCache` hits) records nothing. The histogram then over-states round trips per operation and
hides cache effectiveness, the thing the budgets of §5.6 exist to watch. Fix: create the recorder
with the scope's `DataAccessScope`, which every opener resolves to name `Operation`. For example,
register `DataAccessScope` through a factory that also resolves the recorder, or let the recorder
own the scope value. Then every scope that names an operation records, zeros included. The
alternative is to keep the deviation and say what it costs.

**R1-7 (minor; spec-level, for the orchestrator) — A read that times out (`-2`) is re-run three
times, so a slow query costs four command timeouts.**
`src/core/Tellma.Core/Data/Batches/DataErrors.cs:94`, `RetryRules.cs:103`. This conforms to §6.4
and §6.5 (`-2` is ambiguous; a read may run twice). The failure scenario: a read that exceeds the
30 s timeout under load runs four times, about 2 minutes of server work, before the caller sees an
error. That is past typical HTTP client timeouts, and it multiplies load on a server that is
already slow. Suggested ruling: a command timeout is re-run at most once, or not at all, for
`Read` and `Validate`. Throttling and lost-connection numbers keep the full budget. **Decision for
the orchestrator / Ahmad.**

### Responses

All seven findings are fixed, following the orchestrator's rulings. Every change is in the
"PC-028: review 1 fixes" commit.

- **R1-1 (fixed).** `DataErrors.Classify` now checks the primary error's number against the
  reported-transient list before the severity-20 rule. 40501, 10928, 10929 and 40197 raised at
  severity 20 are therefore `Reported` and re-run without a probe. The lost-connection numbers and
  any other error of severity 20 or more stay `Ambiguous`. The theory
  (`A_transient_number_the_server_reports_is_reported_at_any_severity`) now takes the severity as a
  parameter, adds rows at class 20 for those four numbers, and checks that a session-ending note
  after the transient error does not hide it. This conforms to §6.4, so it is not a deviation.
- **R1-2 (fixed; deviation).** After a `NotCommitted` verdict, the executor probes again before any
  error reaches the caller. That covers a final failure of the re-run (the 2627-on-the-probed-key
  shortcut still answers without a round trip), exhaustion of the attempts, and cancellation
  (R1-3). A `Committed` answer surfaces as `DataAccessAmbiguousException(Committed)`, with the first
  attempt's failure inside. `Unknown` surfaces as `DataAccessAmbiguousException(Unknown)`, and
  `NotCommitted` lets the re-run's own error surface. `DataExecutor.ReprobeAsync` implements this.
  The new fault test
  `A_re_run_that_fails_its_guard_after_a_not_committed_verdict_is_probed_again_and_reports_the_commit`
  marks the batch with `DataBatchDatabase.Premises`. Its listener inserts the probed row and moves
  the `settings` tag on the `not-committed` verdict. The re-run then fails its guard with 50412 and
  the second probe answers `Committed`. Without the fix, the test sees
  `BatchAssertionFailedException(50412)`. This is listed under Deviations, because §6.5 names only
  2627.
- **R1-3 (fixed; deviation for the cancellation rule).** The caller's token (`beforeSend`) now
  governs every open and every wait between attempts. It is no longer swapped for `None` once a
  persist has been sent. A sent persist command still runs to completion. A cancellation never
  turns an unknown write outcome into `OperationCanceledException` (`DataExecutor.CancelledAsync`):
  - After a `NotCommitted` verdict, the probe asks again, as in R1-2. `Committed` and `Unknown`
    surface as ambiguous, and `NotCommitted` lets the cancellation surface.
  - A writing attempt that was re-run without a verdict (an idempotent write after a lost
    connection) surfaces as `DataAccessAmbiguousException(Unknown)`.
  - A sent writing command that is not a persist and is cancelled midway (a `Maintenance` write)
    also surfaces as `DataAccessAmbiguousException(Unknown)`.

  Otherwise the cancellation surfaces as itself. A re-run is now counted (`Retries`,
  `tellma.data.retries`, the `retried` duration) only once its wait has passed. A wait that is
  cancelled records the attempt as `failed`. There are two new fault tests. In the first, a persist
  is killed, the probe answers `not-committed`, and the token is cancelled: the result is
  `OperationCanceledException` after a second `not-committed` probe, with no re-run. In the second,
  an idempotent write is killed and then cancelled: the result is
  `DataAccessAmbiguousException(Unknown)`.
- **R1-4 (fixed).** The new fault test
  `A_read_whose_connection_closes_on_the_client_is_re_run_because_it_may_run_twice` closes
  `connection.Current` from the ready reader on attempt 1. It expects one re-run, metered as
  `(ambiguous, connection-lost)`, and the second attempt's results. If the client-side
  lost-connection rule broke, the failure would be a `Defect` and would surface.
- **R1-5 (fixed; deviation).** The probe text is now `WITH (READCOMMITTEDLOCK, FORCESEEK)`, and the
  unit test's expected text is updated. Every fault test that probes runs the new text against SQL
  Server.
- **R1-6 (fixed; deviation 12 withdrawn).** `DataAccessRecorder` now owns the unit of work's
  `DataAccessScope`. The scope's `DataAccessScope` registration resolves the recorder, so the
  opener that names the operation creates it, and disposing the scope records the round trips, zero
  included. `DataBatch` takes the scope's `DataAccessScope` like any other consumer. The new unit
  test `A_composed_scope_that_names_its_operation_records_its_round_trips_even_with_no_batch` pins
  this. The registration is still a `TryAdd`, so a host that registers its own `DataAccessScope`
  first (none does) would bypass the recorder.
- **R1-7 (fixed; deviation, per the ruling).** `RetryRules.MayRerunAfterTimeout`: a `Read` or
  `Validate` batch whose command timed out (`-2`, now `DataErrors.CommandTimeout`) gets
  `RetryRules.ReadTimeoutReruns` = 1 re-run, then `DataAccessRetryExhaustedException`. Other
  purposes, and other failures that may run twice, keep `RetryAttempts`. There is a unit theory,
  plus an integration test (`DataBatchTimeoutTests`, on a `ShortTimeoutDatabase` whose host has a
  1 s command timeout) in which a read blocked past two timeouts reports `Attempts = 2`, one retry
  `(ambiguous, -2)`, and two round trips.

Deviations after review 1 (the implementer notes' list, amended):
- 12 is withdrawn: the recorder now records every scope that resolves its counters.
- New: after a `NotCommitted` verdict, any error that would reach the caller is preceded by a
  second probe (R1-2).
- New: a cancellation that leaves a write's outcome unknown surfaces as
  `DataAccessAmbiguousException` (R1-3).
- New: the probe adds `FORCESEEK` (R1-5).
- New: a timed-out read or validation batch is re-run once (R1-7).
- Changed: R1-1 removes the earlier, undeclared reading that sent severity-20 transients down the
  ambiguous path.

### Findings

- **R2-1 (minor): a `RAISERROR` at severity 11–18 in persist text commits but is reported as a
  failure.**
  - Where: `DataErrors.cs:230` (`>= ThrowMin => OutOfBand`), and `DataExecutor.cs:503-515`
    (only a non-`SqlException` cancels the command).
  - Scenario: `XACT_ABORT` does not abort the batch for `RAISERROR`; this was verified above. A
    body or epilogue fragment that signals with `RAISERROR(N'…', 16, 1)` instead of `THROW` lets
    the batch run on to `COMMIT`. The client meanwhile receives Msg 50000. `Translate` maps it to
    the out-of-band `InvalidOperationException`, `Decide` returns `Surface`, and the caller sees a
    500 for a write that committed. `TELLMA0003` checks only `THROW` literals against the bands,
    so nothing stops such text.
  - Fix: add a WATCHLIST line for PC-040 (the distribution-text analyzer) to refuse `RAISERROR`
    at severity 11 or higher in batch text. Optionally, on a writing batch, treat an out-of-band
    `SqlException` that arrives before the commit's result as a `Defect`, so that it probes or
    reports `Unknown` instead of claiming a plain failure.

- **R2-2 (minor): a failure while the request is being written is classed as "sent".**
  - Where: `DataExecutor.cs:493` (`phase = AttemptPhase.Sent` runs before `ExecuteReaderAsync`),
    and `TableTypeBinding.cs:94-105` (TVP records are built lazily, `record.SetValue` during
    `yield`).
  - Scenario: SqlClient enumerates TVP rows while it writes the request. A value that
    `SqlDataRecord.SetValue` rejects, such as an overflow or a type mismatch from a bad binding,
    throws partway through the write. The server never executes an incomplete request. The
    executor still sees a non-`SqlException` on an open connection after `Sent`, which is a
    `Defect` on a writing batch (`RetryRules.cs:126`):
    - A persist with no inserted roots, which cannot be probed, surfaces
      `DataAccessAmbiguousException(Unknown)`. The user gets a 503 and a reload prompt for a
      deterministic programming error.
    - An inserting persist pays for a probe before the defect surfaces.
  - Fix: mark `Sent` only once `ExecuteReaderAsync` has returned a reader. Alternatively, treat a
    non-`SqlException` thrown by `ExecuteReaderAsync` itself, on a connection that is still open,
    as not executed (`Final`, before the send). Add a unit or fault test that uses a binding which
    throws in `SetValue`.

- **R2-3 (minor): the commit probe is single-shot, so it fails in the outages it exists for.**
  - Where: `DataExecutor.cs:577-613` and `CommitProbe.cs:122-134`.
  - Scenario: the probe runs right after the connection dropped, which is when a failover or a
    throttling episode is most likely. If the open or the probe query fails with a reported
    transient (40613, 40501, 10928/10929, a pool timeout) or with -2, the verdict is `Unknown` at
    once. The ambiguity the probe exists to resolve is then reported as
    `DataAccessAmbiguousException(Unknown)`, even though the backoff budget (`RetryAttempts`,
    `RetryBaseDelay`) is unused. D-052 asks for a second probe after `NotCommitted`. Nothing asks
    for the probe to be retried when the probe itself hits a transient, and that is the common
    case.
  - Fix: retry the probe on `Reported` or `Ambiguous` failures of its own, with the same `Delay`
    schedule and attempt cap, and under the caller's token for the waits. Treat only `Final` or
    `Defect` probe failures, or exhaustion, as `Unknown`. Add a unit-level probe-retry test.

- **R2-4 (minor): after an idempotent write is re-run, exhaustion reports "nothing committed"
  although attempt 1 may have committed.**
  - Where: `DataExecutor.cs:310` sets `unresolved`, and `DataExecutor.cs:318-328` ignores it;
    compare `DataExecutor.cs:363-379`. The contract is at `DataAccessFailureExceptions.cs:10-13`.
  - Scenario: a `MayRunTwice` writing batch, such as a `Maintenance` upsert or a job claim,
    loses its connection after the send, so `unresolved` is set and the batch is re-run. The
    re-runs then exhaust on reported transients, or fail finally. The caller gets
    `DataAccessRetryExhaustedException`, whose contract says "Nothing it carried is committed",
    or the re-run's own error. Yet attempt 1 may have committed. A cancellation in exactly the
    same state surfaces `DataAccessAmbiguousException(Unknown)`, so the two exits disagree about
    the same uncertainty. Spec 0015 §14.2 maps both to 503, so HTTP callers are unaffected. A
    job handler or a caller that compensates on "nothing committed" is misled.
  - Fix: when `unresolved` is set, surface `DataAccessAmbiguousException(Unknown)` (inner: the

    exception's doc to "nothing committed unless an earlier attempt's outcome was unknown". Add a
    test either way.

- **R2-5 (minor, seam): a cancelled `Maintenance` write now surfaces as ambiguous, which changes

  - Where: `DataExecutor.cs:232-238` (`result.Sent && writes ? failure : unresolved`).
  - Scenario: under the spec 0020 outcome table, `OperationCanceledException` at host stop
    becomes `Released`, retried with after = 0. Any other exception becomes
    `Retry Jobs.Internal`, logs `JobHandlerFailed` at error level, and burns an attempt. With R1-3,
    a job handler whose sent `Maintenance` write is cancelled at host stop now throws
    `DataAccessAmbiguousException(Unknown)`. Each graceful shutdown during a job's write therefore
    logs an error and consumes a retry. For `TransactionMode.Explicit` the cancelled write was
    certainly rolled back (attention plus `XACT_ABORT`), yet it is still reported as `Unknown`.
  - Fix: add a WATCHLIST `## 0012` line for the spec 0020 worker checkpoint, so that the worker
    treats a `DataAccessAmbiguousException` thrown after its stopping token fired as `Released`.
    The test must use the token, not the inner exception: `CancelledAsync` wraps the attempt's
    failure, which can be SqlClient's cancelled-command `SqlException` rather than an
    `OperationCanceledException`. Separately, surface the cancellation itself for an `Explicit`

- **R2-6 (minor): several review 1 behaviours have no test.**

### Responses

- **R2-1 (fixed; WATCHLIST line plus a runtime rule).** WATCHLIST `## 0012` now tells PC-040 to
  refuse `RAISERROR` at severity 11 or above in batch text and to require `THROW`. I also took the
  optional runtime half. In a batch that commits its own transaction (`Auto` with a declared write),
  a server error whose number is outside both bands (`DataErrors.IsOutOfBand`: 50000 or above and
  neither platform nor distribution) is now a `Defect`, not `Final`. The probe settles it when the
  batch declared inserted roots: `Committed` surfaces as ambiguous, and `NotCommitted` surfaces the
  defect translated (the out-of-band `InvalidOperationException`). Without inserted roots it is
  `DataAccessAmbiguousException(Unknown)`. The reason: D-052 says an unknown writing outcome is
  reported as ambiguous, never as a failure, and the out-of-band number is the one signal the
  client gets that a non-aborting `RAISERROR` may have let the batch commit. The cost is small. An
  out-of-band `THROW` (which does abort) on a probeable persist pays one probe and surfaces as
  before. On an unprobeable write it becomes a 503 instead of a 500, and TELLMA0003 is specified to
  refuse out-of-band `THROW` literals. Reads, `None` batches and `Explicit` batches are unchanged. `None`
  has no single commit to protect, and an `Explicit` transaction is never committed after a body
  error. A distribution-band `RAISERROR` (through `sys.messages`) is still reported as an assertion,
  so the analyzer line remains the real fix. Tests:
  `An_out_of_band_raiserror_that_lets_its_batch_commit_is_probed_and_reports_the_commit` (the row
  commits; `Committed`, inner Msg 50000) and
  `An_out_of_band_throw_that_aborts_its_writing_batch_is_probed_and_surfaces_as_a_defect`
  (`NotCommitted`, then the translated `InvalidOperationException`). There is also a unit theory
  for `IsOutOfBand`.
- **R2-2 (fixed).** A failure thrown by `ExecuteReaderAsync` itself that is neither a
  `SqlException` nor an `OperationCanceledException`, on a connection that is still open, now
  marks the attempt `Unsent` (the renamed `Connecting` phase). It classifies as `Final` and
  surfaces as itself, with no probe and no re-run. SqlClient abandons a partly written request with
  an attention and keeps the connection open, and the server never runs an incomplete request. The
  new fault test confirms both points against SQL Server:
  `A_request_whose_rows_the_client_cannot_encode_never_ran_so_its_error_surfaces_unprobed` binds
  20,000 `IdList` rows (several packets) and then a null row, which the binding refuses during the
  write. The test runs with and without declared inserted roots. It expects the binding's own
  `InvalidOperationException`, no probe, no re-run and no rows. Before the fix, the probeable case
  paid a `not-committed` probe and the other case surfaced `DataAccessAmbiguousException(Unknown)`.
  A failure that also closed the connection stays `Sent`, so it is still treated as a lost
  connection.
- **R2-3 (fixed).** The probe now runs in a retry loop, `DataExecutor.ProbeUntilAnsweredAsync`,
  around `ProbeOnceAsync`. A probe attempt's failure is classified as any round trip's is (the
  shared `Classify`). `Reported` or `Ambiguous` runs again with `RetryRules.Delay` and up to
  `RetryAttempts` re-runs. A probe timeout (-2) runs again once at most, as a read does under D-052.
  The caller's token cancels the waits. `Final`, `Defect`, exhaustion or a cancelled wait leaves
  the verdict `Unknown`. The open and the query still use `CancellationToken.None`. Each probe
  attempt counts a round trip and gets its own span. Only the final verdict is metered on
  `tellma.data.commit.probes`, and a probe re-run is not counted in `tellma.data.retries`, which
  counts batch re-runs. Re-runs log the new `DataBatch.CommitProbeRetrying` event at Information;
  `CommitProbeFailed` logs once, when the answer is `Unknown`. There are seven unit cases in
  `CommitProbeTests`: re-run after a reported failure and after a lost connection, with the delay
  schedule asserted; `Unknown` at once after a final failure and after a defect; `Unknown` after
  the attempts run out; one re-run after a timeout; and a cancelled wait. One fault test,
  `A_probe_that_loses_its_connection_runs_again_and_answers`, closes the probe's first connection;
  the second probe answers `not-committed` and the batch re-runs (four round trips). I declined one
  sub-point: a pool timeout is SqlClient's `InvalidOperationException`, which no round trip
  classifies as transient. Making it one would change §6.4's classification for every batch, and
  the pool has already waited the whole connect timeout by then.
- **R2-4 (fixed).** Once `unresolved` is set (a sent writing attempt was re-run after a lost
  connection, with no verdict), every exit surfaces `DataAccessAmbiguousException(Unknown)`, with
  the last failure inside. That covers exhaustion, `Surface` (the re-run's own final error) and
  `GiveUp`. `GiveUp` is reached only by `Explicit` batches, which are never re-run, so that branch
  is defensive. `Unknown` and `CancelledAsync` already behaved this way, and the shared
  `UnknownOutcome` helper now meters all of them. This follows D-052 and does not conflict with
  §6.5, whose exhaustion rule covers re-runs of rolled-back attempts. The exception's documented
  contract ("nothing it carried is committed") now holds without narrowing. Test:
  `An_idempotent_write_re_run_after_a_lost_connection_never_reports_that_nothing_committed` kills
  attempt 1 of an idempotent update. In the transient case the re-runs throw 50503 until
  exhausted: three retries, then `Unknown` with inner 50503. In the final case the re-run throws
  50600: one retry, then `Unknown` with inner 50600.
- **R2-5 (fixed; WATCHLIST line plus the `Explicit` rule).** WATCHLIST `## 0012` tells the spec 0020
  worker checkpoint to map any exception thrown after its stopping token fired to `Released`, and
  to test the token, not the exception's type or inner exception. A cancelled sent write that is
  not `Explicit` stays `DataAccessAmbiguousException(Unknown)`, per D-052. Cancellation can arrive
  after the server's commit, and the worker rule restores the clean shutdown. For an `Explicit`
  batch cancelled before its commit phase, the cancellation itself now surfaces. The executor
  never commits that transaction, and the attention plus `XACT_ABORT` (and the executor's own
  rollback) undo it. A failure in the commit phase while the token is cancelled stays ambiguous,
  matching the `Unknown` rule for a lost commit. Test:
  `A_maintenance_write_cancelled_after_its_send_is_ambiguous_unless_its_explicit_transaction_rolled_back`
  cancels a gated `Maintenance` insert after its send. In `Auto` it expects
  `DataAccessAmbiguousException(Unknown)` with an `unknown` verdict metered. In `Explicit` it
  expects `OperationCanceledException` and no verdict. Both cases leave no row.
- **R2-6 (fixed).** One fault test per bullet:
  - Exhaustion re-probe:
    `A_re_run_that_runs_out_of_attempts_after_a_not_committed_verdict_is_probed_again_and_reports_the_commit`.
    Attempt 1 is killed and the probe answers `not-committed`, while the listener commits the
    probed row behind it. Each re-run then throws 50503 before its insert, so it never collides with
    the key. After three retries (ambiguous, reported, reported), the exhaustion re-probe answers

  - Defect after `NotCommitted`:
    `A_reader_defect_in_a_writing_batch_is_probed_and_surfaces_itself_when_nothing_committed`. The

  - Sent `Maintenance` write cancelled: the `Auto` case of the R2-5 test.
  - Handle reopen:
    `A_re_run_on_a_database_handle_reopens_its_connection_after_its_session_was_killed`. It opens a

  To keep the tests honest I mutated the code and confirmed that each new fault test fails. The
