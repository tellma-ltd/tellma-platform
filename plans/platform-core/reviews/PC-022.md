# PC-022: ICU localizer factory, LocalizationScope and Core resources

## Implementer notes

### What was built, and where

- **`Tellma.Core.Abstractions.Localization.LocalizationScope`**: `Enter(context)` pushes an
  async-local frame (nests; disposal restores the replaced frame, idempotent), `Current`. Beyond
  spec 0013 §10.2's surface: `ApplyRequest(context)` / `Request`, the request's localization
  beneath every scope (see Deviations 1).
- **`Tellma.Core/Localization`**:
  - `IcuStringLocalizerFactory` (public, `IStringLocalizerFactory`): wraps an internal
    `CultureResourceLocalizerFactory` (a `ResourceManagerStringLocalizerFactory` subclass whose
    localizers, `CultureResourceLocalizer`, expose the framework's protected `GetStringSafely` /
    `GetAllStrings` with an explicit culture). One wrapper per inner localizer, cached.
  - `IcuStringLocalizer`: culture = `LocalizationScope.Current?.Culture ?? CurrentUICulture`;
    arguments parsed first (`MessageArguments`), lookup through the parent chain, missing →
    key text, `ResourceNotFound`, `MissingResources.Report`; found → `IcuMessageRenderer.Render`.
    `GetAllStrings` returns raw values.
  - `IcuMessageRenderer`: the one shared `MessageFormatter(useCache: true, culture: null,
    CalendarValueFormatter)`; values without `{` skip it; swaps `CurrentCulture` to the target
    culture for the call (the library writes a plural's `#` and a select key through the current
    culture); malformed / unformattable → raw value + `MessageFormatMalformed` once per
    (base name, key, culture), bounded at 10,000 entries; a `VariableNotFoundException` with no
    arguments supplied → raw value, no log.
  - `CalendarValueFormatter` (`CustomValueFormatter`): `{d, date, short|medium|long|full}` (no
    style = medium) via `ICalendarSystem.Format` of the scope, else the request, else Gregorian/UTC;
    `DateOnly` and unspecified-kind `DateTime` are wall-clock dates, UTC/local `DateTime` and
    `DateTimeOffset` convert to the display zone. `{t, time, short|…}`: time of day (zone-converted
    for instants) in the culture's cleaned `ShortTimePattern` / new `LongTimePattern`
    (`CalendarCultureData.LongTimePattern` added). Numbers keep the library's behaviour.
  - `MessageArguments`: none, `IReadOnlyDictionary<string, object?>` as is, any `IDictionary` with
    text keys, or an object's public readable properties (cached per type); more than one object,
    or a lone value (string, `IConvertible`, `IFormattable`, `IEnumerable`) → `ArgumentException`.
  - `MissingResources`: `tellma.localization.missing` (`{lookup}`), once per (base name, key,
    culture), bounded at 10,000; `culture` tag = the offered language's code, else `other`;
    `MissingResourceString(baseName, key, culture)`.
  - `LocalizationComposition.Register`, called from `CompositionPipeline.Realise` before the tenant
    model: `AddLogging`, `AddMetrics`, `AddLocalization`, then `RemoveAll<IStringLocalizerFactory>`
    and the ICU factory as a singleton, so a host's earlier `AddLocalization` is replaced.
  - `LocalizationLog`: `MissingResourceString`, `MessageFormatMalformed` (Warning).
- **Resources** (`src/core/Tellma.Core/Resources`): `Strings.resx` / `Strings.ar.resx` rewritten
  with every Core key family of spec 0013 §10.1 (392 entries each, sectioned with XML comments):
  `Calendar_*`, the bare shared labels, `Action_*`, `Entity_New`, `Entity_DisplayNameFallback`,
  `SettingCategory_general`, `Access_Reason_self`, `Boot_*` (spec 0024 wording), `Problem_*` title
  and detail for all 34 problem codes (the `forbidden` detail is a select on `reason`), the
  `Settings.*` codes, the pipeline codes of spec 0015, the report/dashboard keys of specs
  0033/0035, `Queryex_<code>` for all 51 diagnostics (QX4009 added after the merge with platform-core), and 186 `Region_<code>` names. `Strings.am.resx`
  gained the regions only (its other keys fall back to English, as before). `ServerStrings.resx` +
  `ServerStrings` marker, empty. The `Strings` marker's remarks carry the author conventions.
- **`eng/region-names/generate-region-names.mjs`** (+ README): writes the `Region_` block of every
  `Strings(.<lang>)?.resx` from `Intl.DisplayNames`, refusing to run unless Node's CLDR is 48.0;
  `--check` exits 1 when stale. `node eng/region-names/generate-region-names.mjs [--check]`, the
  same on Windows and Linux.
- **Packages**: `Microsoft.Extensions.Localization` 10.0.11 (Directory.Packages.props), referenced
  with `MessageFormat` by Tellma.Core. ARCHITECTURE.md's Tellma.Core row lists it.
- **Tests** (`test/core/Tellma.Core.Tests/Localization/`): `IcuStringLocalizerTests` over the
  suite's own `TestMessages` resources (neutral, `ar`, `ar-SA`, `am`), `LocalizationScopeTests`,
  `CoreResourcesTests` (key grammar, every value formats as ICU with no ASCII apostrophe, `ar`
  complete, satellites ⊆ neutral, `Region_` = catalogued regions in every shipped language,
  `Problem_` title and detail for every problem code the exceptions declare, `Queryex_` = the
  engine's `DiagnosticCodes` read from source, `ServerStrings` empty). READMEs of Tellma.Core,
  Tellma.Core.Abstractions and the test project updated.

### Deviations

1. **The request's calendar and zone reach the singleton localizer through
   `LocalizationScope.Request`**, which `RequestContext.ApplyCultures()` sets together with the
   current cultures, from the new `RequestContext.Localization` (culture, calendar system, the
   display zone's IANA name resolved once per process, UTC when the host lacks it, content-language
   index). `LocalizationScope.ApplyRequest(context?)` is public, accepts null and returns the value
   that undoes it. (Review 1 wired this; the first commit left it to the request-context owner.)
2. **`MessageFormatMalformed(baseName, key, culture)`** is once per key *and culture*, and carries
   the culture: a malformed Arabic translation and a sound English value are different defects.
3. **The `culture` tag of `tellma.localization.missing`** is the offered language's code; a culture
   whose language is not offered is tagged `other`, keeping the tag a closed set.
4. **A value with placeholders read without arguments** renders raw without a log: callers that
   read a template (Identity's own ICU decorator, if composed in-proc) must not be reported as
   malformed. With arguments supplied, a missing variable is logged as malformed.
5. **A lone positional value** (a string, number, date or list as the single argument) is refused
   with `ArgumentException`, like the second object the spec names.
6. **`LocalizationOptions.ResourcesPath` is ignored**: addresses are the marker's full name, so a
   host setting cannot move every package's resources.
7. **Deferred keys**: the `Report.*`, `Sharing.*` and `Dashboard.*` codes, `Excel.*` codes and
   `Access_Problem_*` have no code constants or arguments yet; their owning checkpoints add them.
8. **`{t, time, …}`** is formatted too (spec 0013 §10.2 names `TryFormatTime` without detail): the
   time of day in the culture's pinned pattern, `short` vs every other style.
9. **Region names are generated by a Node script** (CLDR 48.0 via Node 24's ICU 78.x) rather than
   the .NET culture-data generator: the platform's .NET hosts read ICU from the OS, whose CLDR is
   not pinned, while Node bundles its own.

### Open risks

- `Queryex_` argument names follow the engine's raise sites, not spec 0008 Appendix A (which names
  none): QX3101 is raised with two argument shapes; QX3400's `type` is spelled `QxDate`-style
  (the engine's type name, not a label); QX3005's `signatures` includes `@index`. The messages
  read sensibly for every shape, but spec 0008 should name the arguments.
- Problem details that mention counts (`count-mismatch`, `limit-exceeded`) take `expected` /
  `actual` / `maximum` arguments the exceptions do not yet carry to a renderer; spec 0013 §10.1
  and the problem-details writer must agree on them.
- `Problem_forbidden_Detail`'s `{action}` may be absent for a resource-level refusal; the select
  on `reason` keeps every branch sound, but the renderer (spec 0032 §12.4) must pass a label.
- `Action_Activate` serves both an entity action and a generic button; a context-specific wording
  needs the entity-prefixed key.
- Node 24's ICU minor (78.3 locally) differs from the culture data's 78.2; both are CLDR 48.0 and
  the script pins on the CLDR version.

### What reviewers should examine hardest

- The culture swap in `IcuMessageRenderer.Render` and its interaction with async callers (it is
  synchronous and restored in `finally`).
- `CalendarValueFormatter`'s treatment of `DateTime` kinds and the Gregorian/UTC default.
- `LocalizationComposition`'s `RemoveAll` replacing a host's factory, and Identity's in-proc case.
- The Arabic wording of `Problem_*`, `Queryex_*` and the report keys, and the `Region_` block.

### Findings

**R1-1 (major): the request seam is unwired, and the wiring the deviation prescribes does not compile.**
`src/core/Tellma.Core.Abstractions/Localization/LocalizationScope.cs:73-77`,
`src/core/Tellma.Core/Localization/CalendarValueFormatter.cs:111-115`; implementer notes, Deviation 1
(this file, lines 67-72).
Spec 0013 §10.2 makes the date hook fall back to "the current request" when no scope is entered. Here
that fallback is `LocalizationScope.Request`, and only `ApplyRequest` sets it. Nothing calls
`ApplyRequest`: not this commit, and not `RequestContext.ApplyCultures()`, which is now on
origin/platform-core (`RequestContext.cs:236`) and sets only the two cultures. The deviation's reason
("RequestContext is not on platform-core yet") no longer holds. Its prescribed fix,
`ApplyRequest(context.Localization)`, names a member `RequestContext` does not have: the context
carries `CultureInfo`, `CalendarSystem`, `ContentLanguageIndex` and the display zone as an IANA
*string* (`TimeZone`), not a `LocalizationContext` or a `TimeZoneInfo`.
Failure scenario: once PC-022 merges, every request, and every background scope that calls
`ApplyCultures`, renders `{d, date}` in Gregorian and UTC whatever the tenant's calendar and the
user's zone. An Umm al-Qura tenant at +03 sees a 22:30Z instant as the previous Gregorian day. No
test fails, because the only test that covers the request path calls `ApplyRequest` by hand.
Suggested fix: do the wiring when this checkpoint integrates onto platform-core, rather than leaving it
to a later owner. `ApplyCultures()` should also call
`LocalizationScope.ApplyRequest(new LocalizationContext(CultureInfo, CalendarSystem, <display zone>, ContentLanguageIndex))`.
Prefer having the Order-200 initializer store the resolved `TimeZoneInfo`, or the negotiated
`LocalizationContext` itself, on the context. That way `ApplyCultures` never resolves an IANA id at
the front door, where a host with stale tzdata would throw `TimeZoneNotFoundException`. Add a test:
after `ApplyCultures()` on a `uq` / +03 context, `{d, date}` renders the Umm al-Qura date in +03.
Correct Deviation 1's wording in the commit message. If the wiring cannot land in this checkpoint,
record it as a merge-time task in LEDGER.md with an owner.

**R1-2 (minor): `ApplyRequest` cannot be undone, so a long-lived loop carries one unit's calendar and zone into the next.**
`src/core/Tellma.Core.Abstractions/Localization/LocalizationScope.cs:73-77`.
`ApplyRequest` takes a non-null context and returns nothing, and `LocalizationScope` has no way to
clear or restore `Request`. The value is an `AsyncLocal` written synchronously, so it holds for the
rest of the calling async method. Picture a worker loop that opens a tenant scope, calls
`ApplyCultures()`/`ApplyRequest` and runs a job, then runs a tenantless or system unit that applies
nothing (catalog maintenance, a registry refresh). That second unit renders dates in the previous
tenant's calendar and display zone. The same goes for a lazily started background loop or timer
created during a request: it captures the request's execution context and keeps that request's
localization for its whole life.
Suggested fix: make `ApplyRequest` return an `IDisposable` that restores the previous value, like
`Enter` does, or accept null to clear it. Document "apply inside the per-unit async method" next to
the rule `ITenantScopeFactory` already states for cultures. Add a test that a disposed apply
restores the previous request localization.

**R1-3 (minor): the resource audit validates against a different engine than production.**
`test/core/Tellma.Core.Tests/Localization/CoreResourcesTests.cs:40-52`.
`Every_value_is_a_well_formed_icu_message` formats every value with a bare
`new MessageFormatter(useCache: false, culture: info)`. That formatter has no `CalendarValueFormatter`,
and the test feeds the number 3 for every argument. Spec 0013 §10.2 requires `{d, date, medium}` and
`{d, date, long}` to work, and only the production hook supplies them; the library alone rejects
them. So the first legitimate Core message with a date argument, for example a report or a job
message showing a date, fails this audit even though it renders correctly in production. Meanwhile
the audit never exercises a date with a date value.
Suggested fix: run the audit through the production path, an `IcuMessageRenderer` or a
`MessageFormatter` built with `CalendarValueFormatter`. Have `AnyArgument` return a value that every
formatter accepts, for example a `DateOnly` when the placeholder's format is `date` or `time`, and 3
otherwise. Alternatively, assert parse-only validity and keep the formatting checks in the localizer
tests.

**R1-4 (minor): private fields without XML documentation.**
`src/core/Tellma.Core/Localization/IcuMessageRenderer.cs:44` (`_logger`);
`src/core/Tellma.Core/Localization/MissingResources.cs:30-32` (`_missing`, `_languages`, `_logger`).
AGENTS.md requires XML documentation on every class and member, and PLAN §7.1 item 5 says "on
everything". The other new types in this commit document their private fields; these four do not.
Suggested fix: add a one-line `<summary>` to each.

### Responses

- R1-1: fixed in "PC-022: review 1 fixes", the commit after the merge 3f2b60c. Merged platform-core (RequestContext with ApplyCultures). `RequestContext`
  gains `Localization` (a `LocalizationContext` of its culture, calendar system, display zone and
  content-language index); the zone's IANA name is resolved once per process in a static cache,
  falling back to UTC for a zone the host lacks (negotiation only yields zones the host resolves, so
  a front door never throws on stale tzdata). `ApplyCultures()` also applies it with
  `LocalizationScope.ApplyRequest`. The negotiation initializer at Order 200 does not exist on
  platform-core yet, so the zone stays the context's string member rather than a stored
  `TimeZoneInfo`, which would be a second source of truth for the same value. Tests: an Umm al-Qura
  context at Asia/Riyadh renders a 22:30Z instant as the Umm al-Qura date of 3 March after
  `ApplyCultures()` (fails under Gregorian or UTC); the contract test asserts the applied request
  localization and the zone resolution and fallback. Deviation 1 reworded.
- R1-2: fixed in "PC-022: review 1 fixes", the commit after the merge 3f2b60c. `ApplyRequest(LocalizationContext?)` accepts null to clear and returns an
  `IDisposable` restoring the request localization it replaced (idempotent). The per-unit rule is
  documented on `ApplyRequest` and `ApplyCultures`. Tests: two stacked applications undone in order,
  a double disposal, and null clearing until undone. `ApplyCultures` keeps its void signature: the
  cultures it sets have the same lifetime, and the per-unit rule covers both.
- R1-3: fixed in "PC-022: review 1 fixes", the commit after the merge 3f2b60c. The audit formats through a `MessageFormatter` built with the production
  `CalendarValueFormatter`, and its sample arguments give an instant to every placeholder the
  message formats as a date or time (3 otherwise). A theory proves it accepts every date style,
  `medium` and `long` included, and a time.
- R1-4: fixed in "PC-022: review 1 fixes", the commit after the merge 3f2b60c. The four fields are documented.
- Merge note: the platform-core merge brought diagnostic QX4009 (PathNotPermitted, argument `name`).
  `CoreResourcesTests` caught the gap; `Queryex_QX4009` is added in English and Arabic.
