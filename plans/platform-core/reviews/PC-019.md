### Deviations from the spec (also in the commit message)

1. **`ILanguageCatalog.All`** is added. The spec's interface cannot enumerate what is described
   but not offered, and `core.Language` / `core.Region` are defined over exactly that.
2. **The negotiated culture is named by the pair and carries pinned data**; it is not a literal
   clone of `<language>-<region>-u-nu-latn`. A culture created under that name is *named*
   `ar-SA-u-nu-latn`, which contradicts the same section's "`RequestContext.Culture` is
   `<language>-<region>`" and makes resources and `Content-Language` carry the extension. The
   culture is `new CultureInfo("ar-SA")` with the Latin-digit Gregorian formats applied field by
   field, native digits set to Latin and digit substitution off.
3. **The formats are pinned** (planner note, D-029) and the pin is wider than the planner's field
   list: every settable field of `DateTimeFormatInfo` and `NumberFormatInfo`, since server text
   prints numbers and currency too. Source: CLDR 48 through ICU 78.2
   (`mcr.microsoft.com/dotnet/sdk:10.0-resolute`).
4. **Two corrections to CLDR 48** in the generator (`CultureDataSource.Corrections`): the numeric
   date of `om-ET`, `om-KE`, `ti-ER`, `ti-ET` stays day-first (`dd/MM/yyyy`; CLDR 48 regressed it
   to `M/d/yy`), and `ar-SA` / `ar-SO` take `%` rather than U+066A with Latin digits.
5. **`MessageLanguage` is read as a tag.** A region it carries heads the Region row; the spec's
   table has no override for the region. With the bare language spec 0016 passes, nothing changes.
6. **What counts as a rejected header.** `Accept-Language`: once per header when any element is
   malformed, and its sound ranges are still used; a well-formed header naming nothing offered is
   not counted. Calendar: present and not one of the tenant's. Zone: present and not a value of
   `core.TimeZone` (matched ignoring case; an alias is not a value). A zone that is in the set but
   that this host cannot resolve is ignored and *not* counted: the header is valid and the host is
   at fault, which `core.time-zones` reports.
7. **A distribution that never calls `Languages` offers `en`**, and `Languages` called twice with
   different lists is a composition problem (the spec says "once" and gives neither rule).
8. **Enum-name clash rule.** "Differ from every emitted C# enum name" is checked against
   `<entity table schema>.<EnumTypeName>` for every enum-typed property of the model, the name form
   spec 0029 §2.2 gives; the emit itself does not exist yet.
9. **`core.time-zones` is `RequiresInfrastructure = true`**: it reads the host, so a build step
   that validates a composition skips it.
10. **`[ValueSet]` on a property the model does not map is refused** by the entity metadata, like
    every other column annotation (the spec names only the string rule).
11. **`Calendar_<code>` and `Region_<code>` resource values are not added here**; the sets carry
    the keys, and the strings are PC-022's deliverable.
12. **`CalendarGoldenTests` changed 51 expected strings** by moving to the negotiated cultures
    (planner note), as described above.

### Open risks

- **Satellite rule and added languages.** `core.languages` requires a `Tellma.Core` satellite for
  every offered language but English, literally as §1.3 says. A distribution that adds and offers
  a language the platform has no satellite for therefore cannot start, although §7.2 says strings
  fall back to English. Today only `ar` and `am` satellites exist, so offering `fr` fails too.
  This is the spec's rule; whether it should relax is a decision for the orchestrator.
- **`CultureInfo.Calendar` of `ar-SA`** remains the host's default (Umm al-Qura before ICU 78).
  Only `DateTimeFormat.Calendar` can be set, and it is Gregorian; formatting reads only that.
- **What is not pinned**: comparison, casing, era names and culture display names stay the
  host's. No pattern in the pinned data uses an era.
- **Pairs outside the catalogue** (an added language) take the host's Latin-digit formats, so
  their server text can differ between hosts.
- **The reproducibility test** (`CultureDataFileTests.The_embedded_data_is_what_the_generator_
  writes_on_the_pinned_ICU_release`) skips unless the host's ICU fingerprint equals the file's, so
  it runs only on the `sdk:10.0-resolute` image (and on CI's ubuntu-26.04 if its ICU is 78.2).
- **`InternalsVisibleTo` for the generator tool** from `Tellma.Core`.
- ICU's `NumberDecimalDigits` is 3 for most cultures, so `"N"` prints three decimals
  (`1,234,567.890`); `"N2"` prints the spec's `1,234,567.89`. Left as CLDR has it.

### Findings

**R1-1 (minor; spec flag) — the satellite rule makes `AddLanguage` + offer unusable, and its remedy
says so only implicitly.** `src/core/Tellma.Core/Composition/Checks/LanguagesCheck.cs:59-67`.
Scenario: a distribution calls `AddLanguage(ha…)` and `Languages(["en-GB", "ha"])`. Tellma.Core
can never ship `ha/Tellma.Core.resources.dll`, so startup fails, and the fix text ("stop offering
the language") defeats the purpose of `AddLanguage`. For catalogued languages the check is right
and should stay a failure (see the ruling below). Suggested fix: keep the problem for every offered
non-English language, but for an added language word the remedy as what it takes (a satellite of
Tellma.Core built from a `Strings.<code>.resx` whose manifest name is
`Tellma.Core.Resources.Strings.<code>.resources`, or not offering the language). Raise the
`AddLanguage` versus §1.3 tension to Ahmad as a spec question; do not relax the rule unilaterally.

**R1-2 (minor; test gap) — the "zone in the set but unresolvable on this host" branch is untested.**
`src/core/Tellma.Core/Localization/LocalizationNegotiator.cs:284-299`. Deviation 6 says such a header
is ignored, falls through to the preference, and is not counted; nothing pins that. A regression
that counted it, or that stopped falling through to `PreferredTimeZone`, would pass the suite. The
branch calls `TimeZoneInfo.TryFindSystemTimeZoneById` directly, but the negotiator takes
`IValueSetRegistry`, so a test can construct it over a fake registry whose `core.TimeZone` lists a
value no host resolves (`Mars/Phobos`). Assert: header `Mars/Phobos` with preference
`Europe/London` gives `Europe/London`, and the counter is empty. Do the same for a stored
preference that is in the set but unresolvable (falls to the tenant's zone).

**R1-3 (minor) — the reproducibility guard skips silently and its fingerprint is coarse; cheaper
host-independent guards are available.** `test/core/Tellma.Core.Tests/Localization/CultureDataFileTests.cs:89-102`,
`src/core/Tellma.Core/Localization/CultureDataFile.cs:72-75`,
`eng/culture-data/Tellma.CultureData.Generator/README.md:30-38`. CI's `build-test` leg runs
natively on `ubuntu-latest`, which D-029's addendum says is 26.04 with libicu 78.2, the same
Ubuntu release as `sdk:10.0-resolute`. So the test probably does run in CI today. The day the
runner's ICU moves, it turns into a skip that nobody sees. In the other direction, the fingerprint
is the collation version, which an ICU maintenance or CLDR point release need not change, so the
test can also fail falsely. Suggested fixes, all cheap:
(a) In `ci.yml`'s ubuntu leg, set an environment variable (e.g. `TELLMA_REQUIRE_PINNED_ICU=1`) that
turns the skip into a failure naming both fingerprints, so a runner-image change is noticed.
(b) Add a host-independent fixed-point test: every pinned date/time value equals
`CalendarText.Clean` of itself, and every number symbol equals `CultureText.StripBidi` of itself.
That catches a change to the cleaners that leaves the checked-in data stale, on every OS.
(c) Record the image digest, not only the floating tag, in the README command and the `# source:`
line, so that "the one ICU release" can be found again. The existing canonical-form round-trip,
pair-coverage and corrections tests already guard hand edits on every host.

**R1-4 (minor; deviation 8 follow-up) — the enum-name clash check covers entity-property enums only.**
`src/core/Tellma.Core/Composition/Checks/ValueSetsCheck.cs:165-182`. Spec 0029 §2.2 emits setting-key
enums (`SettingKeyDescriptor.EnumType`) and action-field enums into the same `enums` namespace. A
value set named like a setting-key or action-field enum passes this gate but would collide in the
emit. The schema prefix is also inferred from the entity's table, which an enum shared across
schemas makes ambiguous. Suggested fix: accept for now, but add a LEDGER follow-up so the emit
checkpoint (0029) re-points this check at the emit's own enum-name function.

**R1-5 (minor; cross-checkpoint) — the om/ti date correction must reach the client too.**
`src/core/Tellma.Core/Localization/CultureDataSource.cs:245-254`. With the correction, server text
for `om-*`/`ti-*` writes `dd/MM/yyyy`. The client's fallback for Chromium's missing `om`/`ti`/`so`
(spec 0024 §7.7), and any browser on CLDR 48, writes `M/d/y`, so one user would see two
orders. Suggested fix: record both corrections in DECISIONS.md and route them to the client
localization checkpoint, so its fallback data applies the same corrections.

### Rulings requested by the orchestrator

1. **Satellite rule: fail, as implemented.** The literal reading is the right one. §7.2's
   sentence ("Describing a language is not shipping its strings … a catalogue entry is safe
   before any translation exists") is about a catalogue entry that nobody offers. Offering is
   gated separately by §1.3. §7.3 confirms this: trimming satellites with
   `SatelliteResourceLanguages` is "not required for correctness", so the satellite that is
   present is what correctness depends on. The per-key English fallback of §10.3 covers keys
   missing from a satellite that exists, and packs (§7.3). It does not make a whole missing Core
   language acceptable. A warning would let `fr` ship as an all-English UI that advertises French.
   The only open point is `AddLanguage` (R1-1), which needs Ahmad.
2. **Negotiated culture named by the pair, with field-by-field pinned formats: accept.** §9.2
   contradicts itself ("`RequestContext.Culture` is `<language>-<region>`" against "a clone of
   `<language>-<region>-u-nu-latn`"). The pair name keeps resource fallback and `Content-Language`
   right. A literal clone would still read the host's ICU, which D-029 forbids. Latin native
   digits, `DigitShapes.None` and Gregorian `DateTimeFormat.Calendar` deliver what the bullet
   intends. `CultureInfo.Calendar` stays the host's for `ar-SA` (open risk): acceptable, since
   formatting reads only `DateTimeFormat.Calendar`. Record the deviation in DECISIONS.md.
3. **CLDR 48 via ICU 78.2, the two corrections, the generator and `InternalsVisibleTo`: accept.**
   Pinning one named CLDR release meets D-029's "chosen independently of either ICU": the data no
   longer follows the host. The corrections are well argued (day-first in ET/ER/KE; one percent
   sign across Arabic) and pinned by `The_platforms_corrections_to_the_source_are_pinned`. The
   generator is a non-shipped, non-packable `eng/` tool, and the `InternalsVisibleTo` keeps one
   writer and one reader of the format: acceptable. The cheaper guards are in R1-3: a required-run
   switch on the CI Linux leg plus a cleaner fixed-point test. The canonical-form round trip
   already catches hand edits on every host. The client side of the corrections is R1-5.
4. **`ILanguageCatalog.All`: accept.** `core.Language` and `core.Region` are defined over every
   described language. Without `All`, the public `ValueSetRegistry` would have to read Core
   internals or re-resolve the declaration. The member is additive, and no other implementation
   exists. Record it in DECISIONS.md as a spec contract addition, to be folded into 0013 §7.1.
5. **`CalendarGoldenTests`: verified, accept.** Exactly 51 of 153 strings changed: 12 en-GB `Full`
   rows (4 dates × 3 calendars, each only gaining ", " after the weekday) + 36 am-ET `Medium`/`Long`/
   `Full` rows (4 × 3 × 3, each only reordered from `yyyy MMMM d, dddd` to `dddd d MMMM yyyy` with
   identical month, weekday and digit text) + 3 am-ET instant rows (the same reorder; `1:30 ጥዋት`
   unchanged). All 51 ar-SA rows, every `Short` row and every en-GB `Short`/`Medium`/`Long` row are
   unchanged. The pinned `[en]` `longDate` is `dddd, d MMMM yyyy` (not overridden by `[en-GB]`) and
   `[am]` `longDate` is `dddd d MMMM yyyy`, which accounts for every change. Nothing else moved.
6. **Rejected-header counting and the smaller rulings: accept all.**
   - Count `Accept-Language` once per header with any malformed element, and use its sound ranges.
     Do not count a well-formed header that names nothing offered, since browsers send their OS
     languages and that would make the counter noise.
   - Count a calendar header outside the tenant's pair. That is the stale-client case §9.2 names.
   - Count a zone outside the set, matched ignoring case, where an alias is not a value. Do not
     count an in-set zone the host cannot resolve: the host is at fault, and `core.time-zones`
     reports it. That branch needs a test (R1-2).
   - Treat blank headers as absent.
   - `MessageLanguage` read as a tag is a no-op for spec 0016's bare codes.
   - An undeclared distribution offers `en`.
   - Two different `Languages` lists are a composition problem.
   - `core.time-zones` with `RequiresInfrastructure`: build-host tzdata says nothing about the
     deploy host.
   - `[ValueSet]` on an unmapped property is refused, consistent with every column annotation.
   - The `Calendar_`/`Region_` strings are deferred to PC-022, whose deliverables list them.
   - The enum-name approximation is accepted with the follow-up in R1-4.
