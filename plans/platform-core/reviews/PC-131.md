# PC-131: Tiles view, view toggle, tabs, column filters and the Filters popup

## Implementer notes

### What was built

Spec 0030 §2.3, §2.4, §3.2, §3.4, §8, §9 and §10 on the search host
(`client/projects/core/tellma-core/search/src/`).

- **Tiles** (`tm-search-tiles.ts`, `ɵTmSearchTiles`).
  - The host renders it in the grid's place while the view is tiles, in an `@defer (on immediate)`
    block with skeleton lines as its placeholder, so it is a lazy chunk of `/search`.
  - The layout maps the declaration's `tile` (or the undeclared default: the first image
    navigation, the display name, the first natural key not shown, and Active on an activatable
    entity) onto `tm-tiles`. The title is the display name, with its prefix and name parts. The
    top end is numeric for integer, decimal and float values. A boolean badge shows Active or
    Inactive for `IsActive`, and other booleans show their label when true.
  - Image thumbnails come through `TmUrls.blob(..., { variant: 'thumb' })` only when the blob
    policy has thumbnails and the row's variants include `thumb`.
  - A `{ component }` tile renders its component through `tmTileContent` with `value` (the id)
    and `row`.
  - The region's states render in the tiles' empty template. The field drives the tiles through
    the same `TmGridDriverTarget` it drives the grid with, and hover preloading reads a tile's
    `data-index`.
  - An undo anchor snapshots the tiles' scroll offset and restores it once the restore's rows
    land.
- **View toggle.** A `tm-segmented` (Grid `table-2`, Tiles `layout-grid`) after a separator at the
  toolbar's end. It writes `view` and the current width class's preference half through the
  existing `tmSearchUpdate` rule, re-renders the held rows with no request, and reports
  `tm.search.view-changed { view, list }`. `tm.search.query` timings and the page context now
  report the effective view. Its code loads after the first answer, over a stand-in with the
  control's exact geometry: the track, two segments that draw an icon's box each, and their
  labels, which fold to no width under the same `@container (width < 1200px)` rule. The current view's segment is raised.
- **Tabs.**
  - From `lg`: a segmented control after the title.
  - At `sm` and `md`: a menu button (`tm-search-tabs-menu.ts`, `ɵTmSearchTabsMenu`). All the
    labels are stacked in one grid cell, so the button is as wide as the widest. The button and
    its `tm-menu` are one `@defer (on immediate)` block over a stand-in of the control's height,
    so they are a lazy chunk of `/search`. The button is a `[tmMenuTriggerFor]` trigger, which
    gives it `aria-haspopup`, `aria-expanded` and, while the menu is open, `aria-controls`.
    ArrowDown and ArrowUp open the menu on its first or last row.
  - Below `sm`: a radio group in the Filters popup, counted by the Filters button when it is not
    the first tab.
  - Each change reports `filter-applied { kind: 'tab' }`.
- **Column filters.** Each filterable column's header carries a funnel button (`tmGridHeaderEnd`,
  `tmGridHeaderAction`) named by `tm.search.filterButton` and active while the column's filter
  applies or its panel is open. It opens a `tm-popover` (size sm) holding `tm-column-filter`.
  Apply closes the panel and returns focus to the button.
- **Filters popup** (`tm-search-filters-form.ts`, size md, end-aligned). Below `sm` both panels
  are end drawers (`TmModal`, placement end).
  - The sections are the tab (below `sm`), the filter expression (`tm-expression-editor`, clause
    filter; Mod+Enter applies), Active only, the custom filters, the applied column filters and an
    order on a hidden column as chips, and Add column filter, which opens a column's filter in
    place with Back.
  - The footer has Clear all and Apply. Edits are staged; Apply makes one `tmSearchUpdate`, so one
    URL write and one read on page 1, and reports `filter-applied` once per kind that changed. A
    dismissal destroys the body and discards what it staged.
  - Apply is disabled only when the draft's status is `checked` and the filter clause has
    problems.
  - The Filters button shows its label from `md`, keeps room for a two-digit count, and takes the
    error tone and an extended name while the held failure is the invalid filter's. Edit filter,
    in the invalid-filter and calculation states, opens the popup with the editor focused.
- **The panels are one lazy chunk** (`tm-search-filters.ts`, `ɵTmSearchFilterPanels`). The host
  loads it with `import()` on the first click of a filter button, creates it in a view container,
  and holds a `PendingTasks` task while it loads, so the app is not stable until the panel is
  there. The route therefore never carries `/column-filter` or `/expression-editor`.
  `tm-search-filters-host.ts` holds only the types the host and the chunk share.
- **`f.IsActive` on an activatable entity** is dropped by the canonical query as an invalid value,
  and that column has no filter button. Active only stands for it (`tmSearchFilterable`).
- **Strings.** New `tm.search.*` keys, in English and Arabic. Two select messages put their words
  around the select rather than inside it (`Filter {label}{active, select, …}`), which renders the
  same text as the spec's ICU and keeps the strings' argument-parity test meaningful.
- **Harnesses.** `TmSearchPageHarness` gained tiles, view, tabs, the Filters button, the column
  filter buttons and panels. The new `TmSearchFiltersHarness` is exported from
  `@tellma/core-testing`.
- **ARCHITECTURE.md.** The `@tellma/core` row now says that the tiles view and the filter panels
  are lazy chunks of `/search` with their own budgets.

### Deviations

1. **A `{ component }` tile selects the display name.** The model used to select nothing for a
   component tile. §2.3 does not say what it selects, but the tiles' checkbox and each tile's
   accessible name need the row's display name, so the select now carries its paths (`Code` and
   `Name` for customers).
2. **Options filters show an Any option first.** §10.1 item 4 asks for a radio group. A radio
   group cannot be cleared, so "Any" (`tm.search.any`) is its first option and stands for no
   value.
3. **The calculation state offers Edit filter but not Columns.** §5.3's table lists both. The column
   editor lands with the Columns work, which this checkpoint does not include.
4. **The tiles' first load uses `tm-tiles`' own skeleton** (its `loading` input) rather than a
   `tmTilesLoading` template. While the tiles' chunk loads, the placeholder shows skeleton lines.
5. **On return from a row, the tiles do not restore their offset.** §8 says the tiles apply the
   remembered offset on return and on an anchor restore. Only the anchor restore is done here. The
   host has no return path yet: the page state that would carry the offset and the opened row's
   highlight across a navigation is later work. A return renders the page anew, with the tiles at
   the top and no highlight.
6. **The `./search` route chunk is over budget.** Spec 0030 §1 gives the route chunk 16 KB of its
   own weight, and a product-owner ruling had already replaced that with 23.5. This checkpoint
   measures 26.41 KB after every cut, and the product owner ruled the budget raised (D-419). The
   ceiling is now 26.5. The figures and the savings are set out under Budgets below. This needs
   Ahmad's sign-off against the 16 KB.
7. **The hidden order's message is `tm.searchFilters.orderedBy`.** §10.1 names it
   `tm.search.orderedBy`. The popup's own strings moved into a scope of their own, which the
   filter panels' chunk registers, so they ship with that chunk and not with the route. The
   Arabic sits under the same scope.
8. **Two done-when items are shown on a test declaration, not on Acme.** These are "Sales
   invoices tabs render in their three forms" and "Customers show tiles below md". The host spec
   shows both on the customers of `TM_TEST_CUSTOMERS`, which declares a tile and three tabs (All,
   Open, and a named Starred). Acme has no sales-invoice entity, and its customers declare no tabs
   or tile, so the stack has no page to show them on yet.

### Findings

**R1-1 (major): the view toggle's stand-in is narrower than the toggle, so the toolbar shifts when
its chunk lands on a cold load.**
`client/projects/core/tellma-core/search/src/tm-search-host.css:151-153` gives the stand-in
`calc(var(--field-height) * 2)`, which is 76 px on the default tokens. The toggle it stands for
(`tm-segmented`, two icon segments) is wider:
- each segment is 42 px: `--field-padding-x` 12 px on each side, the 16 px icon and a 1 px border on
  each side;
- the track adds a 2 px gap, 2 px of inset on each side and a 1 px border on each side.

That makes 92 px below `xl`. At `xl` and up, where `labels="xl"` shows "Grid" and "Tiles", it is
wider again. `[tmPageToolbarEnd]` is packed against the row's end
(`tm-page-header.css:108-115`), so when the segmented chunk lands, the deferred span grows and
Refresh, the pager and the separator move 16 px or more towards the start. That chunk is fetched
only once the first answer arrives (`tm-search-host.ts:528-542`, gated on `!firstLoad()`), so on
every cold first load the swap follows the rows by a network round trip. This breaks the zero-shift
rule that §3.2 and spec 0024 §14 set for the page's chrome.

No e2e catches it:
- "a cold entry moves from its skeleton to its chrome with zero shift" stops judging two frames
  after the heading shows, before any rows land;
- "the pager's size select replaces its stand-in with zero shift" judges only the shifts after
  `select.release()`.

The second test now races, though. If the segmented chunk lands after `before` is taken (it is
fetched through the same `route.fetch()` proxy), `tm-pager .tm-pager__next` moves and the
bounding-box `toEqual(before)` fails. That would be a new flake in the PC-F116 test.

Fix:
- Give the stand-in the toggle's exact geometry: the track's border and inset, plus two segment
  boxes built from `--field-padding-x`, `--segmented-icon-size` and the borders. At `xl`, show the
  same two label strings under the same `@container (width >= 1200px)` rule, at the segment's font
  size and weight.
- Also consider rendering the deferred span from the first frame, so its chunk loads beside the
  read. The end slot is packed at its end, so the pager and Refresh arriving before it move
  nothing.
- Add a layout-shift e2e that holds the segmented chunk, as `holdSelectChunks` holds the select's,
  and judges the swap at `lg` and `xl`.

**R1-2 (major): several of the checkpoint's deliverables have no test that would fail if they
broke.**
The only tiles test (`tm-search-host.spec.ts:1663`) reads the tiles' titles. Nothing covers the rest
of §2.3's mapping in `client/projects/core/tellma-core/search/src/tm-search-tiles.ts:261-345`:
- the badge: Active as success and Inactive as neutral, another bool's label when true, and an
  enum's label;
- `topEnd` as `numeric` for integer, decimal and float;
- the thumbnail's `thumb` variant only when the policy has thumbnails and the row's `Variants` list
  it;
- the default parts when no `tile` is declared;
- a `{ component }` body receiving `value` = the id and `row`;
- the title's `href`, which is the row's target.

The Filters popup's own sections are also untested:
- column-filter chips built by `tmDescribeFilter`;
- a chip's activate opening the column's filter in place, with Back;
- Add column filter;
- Clear all staging the §10.1 defaults (including the first tab below `sm`);
- Mod+Enter applying.

Nothing tests the tiles' anchor offset restore (`tm-search-host.ts:2081`, `:2091-2098`) either. Each of
these could regress silently.

Fix: add a `tm-search-tiles` spec, or host cases, that reads each layout part through
`TmTilesHarness`, plus host cases for the chips, Back, Add column filter, Clear all, Mod+Enter and
an anchor restore in tiles view that checks `scrollOffset()`.

**R1-3 (minor): the filter panels' lazy load has three unguarded edges.**
In `client/projects/core/tellma-core/search/src/tm-search-host.ts:1948-1971` (`#loadPanels`) and
`:1870-1872` (`openFilters`):
1. If the page is left while the chunk loads, the success handler still calls
   `this.panelsSlot().createComponent(...)` on the destroyed host's container and runs
   `detectChanges()` on the result. The component either leaks or throws.
2. A throw inside that success handler is not caught by the same `then`'s rejection handler. So
   `#panelsLoad` stays a rejected promise for good (never retried, unlike a failed import), and
   `void load.finally(loaded)` leaves an unhandled rejection.
3. Two clicks on the Filters button before the chunk lands queue two `toggleFilters` calls, so the
   popup opens and at once closes.

Fix:
- Record destruction through `this.#destroyRef.onDestroy` and skip the attach when destroyed.
- Move the attach into a `try`, or put a `.catch` after the `then`, that resets `#panelsLoad` and
  reports.
- Drop a toggle that arrives while one from the same button is still pending, for example by
  keeping a pending-toggle flag that is cleared when the load settles.

**R1-4 (minor): three departures from the spec are not listed under Deviations.**
1. §3.2 names `tmMenuTriggerFor` for the tabs' menu button, but
   `client/projects/core/tellma-core/search/src/tm-search-tabs-menu.ts:40-59, 130-154` opens the
   menu by hand. The directive is already in this chunk's graph (the Filters form uses it) and is
   not a byte cost for the route. The hand-rolled button also lacks the `aria-controls` that
   `TmMenuTrigger` sets while the menu is open.
2. §10.1 names the hidden order's message `tm.search.orderedBy`, but it ships as
   `tm.searchFilters.orderedBy` (`tm-search-filters-strings.ts:26`).
3. The done-when items "Sales invoices tabs render in their three forms" and "Customers show tiles
   below md" are shown on a test declaration (`TM_TEST_CUSTOMERS`, with a Starred tab and Acme
   string keys) in the host spec. Acme has no sales-invoice entity, and its customers declare no
   tabs or tile.

Fix: use `[tmMenuTriggerFor]="menu"` on the button, keeping the stacked labels. Then list items 2
and 3 as deviations, with the reason for each (the chunk's string scope, and no sales-invoice
entity on the stack).

**R1-5 (minor): the `@tellma/core-testing` README does not list what this checkpoint exports.**
`client/projects/core/tellma-core-testing/README.md:8` does not mention `TmSearchFiltersHarness`,
and it still describes `TmSearchPageHarness` without the tiles, the view toggle, the tabs, the
Filters button and its popup, or the column filter buttons. `public-api.ts` exports the new harness
and `core-testing.api.md` gains both. AGENTS.md's README rule and the package's own export list are
then out of date.

Fix: add the harness and the page harness's new reads to the README row.
