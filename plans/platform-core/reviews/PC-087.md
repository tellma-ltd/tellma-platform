### Deviations

1. **Center's stack omits DeleteByQuery.** Spec §5.5 lists the full CRUD route set. However, the registry refuses at startup any stack that serves a delete by query while its service judges deletes, as Role's stack does. Center judges deletes (`HasChildren`), so it serves `All & ~DeleteByQuery`.
2. **`DeleteContext.WithDescendants` (platform contract addition).**
   - `DeleteWithDescendants` runs the same `ValidateDeleteAsync` as a plain delete, with nothing to tell the two apart. Spec §5.4's "delete-with-descendants is unaffected" needs that distinction.
   - The flag is an init property on the public context, set from the delete run's shape.
3. **HasChildren judges the delete, not just the target.**
   - A delete is refused only when a target keeps a descendant the delete does not name, so deleting a whole subtree by ids passes.
   - The integration test shows SQL Server accepts deleting a parent and its children in one statement under the self-FK.
   - The spec's literal rule (refuse any target with `SubtreeCount > 1`) would refuse the same rows that `delete-with-descendants` accepts.
4. **The type-change rule allows children that move away.** A center may stop grouping when every stored child moves away in the same payload. The rule still refuses when a payload row puts a child under it. The literal rule ("SubtreeCount > 1") would refuse a save that leaves the tree valid.
5. **`DeploymentIdentity.IsDevelopment`.** It replaces injecting `IHostEnvironment`. `AddTellma` always registers `DeploymentIdentity`, but a composition outside a generic host has no `IHostEnvironment`. The step reads the environment through the new property, which compares case-insensitively.
6. **What the step's list check refuses, and how it saves.**
   - Beyond the spec's unknown ParentCode, the check refuses:
     - a null list;
     - more than 512 centers (one read's parameter ceiling);
     - a blank code;
     - a duplicate code (case-insensitive, as the stored codes compare);
     - a missing or blank name;
     - a center under itself.
   - The save uses `ConcurrencyMode.Override`, because rows found by code carry no stamp and Check would refuse them.
   - The read sets `IncludeInactive`, so an inactive stored center is updated, not duplicated.
7. **The fixture composes GL.** Spec §9 places the centers integration tests in `Tellma.Core.IntegrationTests`, so its fixture database must hold `gl.Centers`. The fixture migration was regenerated and the fixture goldens updated. Acme is untouched.
8. **An extra resource key `Feature_gl`.** The platform derives a feature's display key by convention, so the module ships it.

2. **`DeploymentIdentity.IsDevelopment` is accepted.**
   - The composition builds `DeploymentIdentity` from the same `IHostEnvironment.EnvironmentName` (`CompositionPipeline.cs:222`; also `TellmaWebApplicationBuilderExtensions.cs:223`). So the flag agrees with §5.6's `IHostEnvironment.IsDevelopment()`, and it is reachable from a contract-only package.
   - Its missing test is R1-4.
3. **Leaving out `DeleteByQuery` is accepted.**
   - D-132 makes `StackRegistry` refuse at startup a stack that judges deletes and still serves delete by query.
   - The export and import routes of the §5.5 list are missing for a different reason: the platform does not project them on any stack yet (see `blob-folders` in `fixture-routes.txt`).
   - **For Ahmad:** §5.5's route list follows whichever D-132 option is chosen. Under option (b), centers get `delete-by-query` back.
4. **Both rule refinements are accepted, checked against §5.4's text.**
   - *HasChildren.*
     - §5.4 literally refuses any target with `SubtreeCount > 1`. §5.3, however, frames `HasChildren` as narrowing the self-FK failure for "a center whose children are not in the same delete". The implementation is exactly that.
     - `TargetedDescendants` counts only descendants reached through an unbroken chain of named targets. A gap (a grandchild named, its parent not) undercounts, so the delete is refused. It never overcounts.
     - The walk is bounded by the target count, and by `MaxDepth = 32` for real data.
   - *Type change.*
     - §5.4 refuses when the before image's `SubtreeCount > 1`. The WATCHLIST 0018 lead already shows that this refuses valid saves.
     - The implementation refuses when any payload row names the center as its parent. Otherwise it compares the stored descendants with the sum of the before `SubtreeCount`s of the stored direct children that the payload re-parents.
     - I worked through these cases, and the result is exact in each:
       - a child moved under a sibling that stays: kept, so refused;
       - a child moved under a sibling's descendant while the sibling also moves out: accepted;
       - a grandchild moved up to the center: caught by the direct `ParentId` check.
   - **For Ahmad:** both §5.4 rows need rewording to match §5.3 and the WATCHLIST lead.
5. **The hidden-parent non-leak is accepted. The mechanism is sound, but its test is only simulated (R1-2).**
   - `ContextLoader.ByIds` is never filtered by row-level access (`ContextLoader.cs:29-31`), so the skip is load-bearing.
   - `SaveRun.DispatchAsync` runs `SettleAsync` → `CheckReferences` in round 1, before any validator continuation resumes (`SaveRun.Rounds.cs:56-60`). That writes `Fk.NotFound` at `row.At("ParentId")` = `[i].ParentId`.
   - `ValidationPath` equality is structural (`ValidationPath.cs:59`).
   - Stored parents are judged only for new rows or rows that move. That matches `CheckReferences`, which judges new and changed references only. So an unchanged hidden parent is never judged either, which is why the narrowing in R1-1 is needed.
6. **The fixture migration is accepted.**
