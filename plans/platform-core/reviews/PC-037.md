# PC-037: Id allocator and the save emitter

## Implementer notes

### What was built, and where

- **Allocator** (`src/core/Tellma.Core/Data/Ids/`, contract in `Tellma.Core.Abstractions/Data/IIdAllocator.cs`
  and `IdReservation.cs`).
  - `IdAllocator` is a singleton holding one `SequenceBuffer` per (tenant, sequence): a locked
    list of contiguous `IdRange`s. Sequences come from the EF model (`FindSequence("sq_<Table>")`),
    so a sibling has none.
  - `Reserve` counts the exact deficit per table through `PayloadRows.Enumerate` (roots, then
    each collection, recursively). It refuses a temporary id shared within one table, serves what
    it can from the buffer, and appends one `sp_sequence_get_range` statement per short table,
    sized `pending + IdBufferLowWater`, which also reads `MAX([Id])`.
  - The statement's completion step (`DataBatch.OnExecuted`) settles the range. It heals when
    `First <= MaxId`, through one autocommit sibling batch, logging `IdAllocator.Healed` and
    counting `tellma.data.ids.healed`. It keeps the head for the hold and appends the tail to the
    buffer.
  - `ReservationHold` assigns in topological order and sets each child's parent key from the
    nesting. It rewrites temporary ids in references and a tree's parent key, and leaves an
    undefined temporary id negative.
  - Disposing returns the held ranges to the front of the buffer unless a persist was attempted.
    `DataBatch.ExecuteAsync` marks the holds of every save it carries before sending.
  - `AppendRefills` runs on every executing batch, after the caller's statements and before the
    epilogue. It refills buffers in use that are below low-water.
  - `OnDuplicateKey` drops the buffers whose `PK_<Table>` a `UniqueConstraintViolationException`
    names. The executor calls it and rethrows.
  - `TakeAsync` serves from the buffer, else from one `Maintenance` batch in `None` mode.
- **Emitter** (`src/core/Tellma.Core/Data/Saves/`).
  - `SavePlan`/`SaveNode` fix the tables in pre-order and number the TVPs: root `t0`/`t1`, then
    per child its parents, new rows and existing rows. They also fix the column roles from the
    UDTT definition plus metadata ownership: audit, set/compared, and text compared binary.
  - `SaveText` writes the statement under a placeholder ordinal. `SaveEmitter` caches the text per
    plan and recompile flag, and substitutes the ordinal on use.
  - `SavePayload` sorts the rows into new and existing per table. A row is new when a live
    reservation assigned it. It also collects the parents whose collection was supplied.
  - `DataBatch.Saves.cs` is `IDataBatch.Save`: it binds, declares the batch-local names, reads the
    conflict set or the stamped ids and the receipt, declares the inserted roots to the commit
    probe, and requires one transaction. After execution it stamps the in-memory roots and forgets
    the committed rows.
- **Executor and infrastructure.**
  - `DataExecutor` takes the allocator and the emitter. It runs the batch's completion steps once
    the body ran. They run after the audit and after the snapshots are replaced (changed in
    review 1), and before the outcome's `RoundTrips` (so a heal's round trip counts) and the
    commit callbacks.
  - New metrics: ids reserved, returned and refilled, heals, rows saved, conflicts.
  - `IBatchConnection.UserId` is the request context's user; the factory handle has none.
  - `StatementDraft.Table(Type, rows)` binds a payload typed at run time.
- **Fixture.**
  - `WidgetPart.DrawingId` is a child blob column. The migration was regenerated with dotnet-ef;
    the diff is the column, its FK and filtered unique index, and the UDTT hash.
  - `FixtureTenant.CreateScope(int? userId = null)`.
- **Tests.**
  - Unit: `test/core/Tellma.Core.Tests/Data/Saves/` (golden SQL, receipt, captures, refusals) and
    `Data/Ids/` (deficit, buffer, return arithmetic, rewriting, refills, PK drop).
  - Integration: `test/core/Tellma.Core.IntegrationTests/Data/SaveEmitterTests.cs` and
    `IdAllocatorTests.cs`, over `SaveDatabase`, whose reset also drops the buffers. The budgets use
    a statistics-enabled connection as the oracle.

### Deviations

1. `TakeAsync(ITenantDatabase database, Type, int, CancellationToken)`: spec 0012 §7.1 sketches
   `TakeAsync(Type, int)`. The singleton has no ambient tenant, and the caller (a job handler) holds
   a database.
2. The touched set holds root ids only. A grandchild's insert, update or delete goes through a
   capture table, mapped to the root through its ancestors' rows in the payload's TVPs. The spec's
   example covers level 1 only, and `OUTPUT parentKey INTO touched` at level 2 would record a child
   id that the root update never matches.
3. The child `UPDATE` adds `AND c.[ParentKey] = s.[ParentKey]`. A payload row that names a
   different parent is never re-parented: §8.2 says "neither deleted, updated nor re-parented",
   and the spec's text did not enforce it. `SavePayload` also refuses such a row up front.
4. `STRING_AGG(...) WITHIN GROUP (ORDER BY [Id])` in the conflict message. Without it the id order
   inside a capped list is unspecified.
5. A blob capture's `[RowId]` uses the table's key type (`bigint` for a long key).
6. Capture (`cap{n}`) and removed-rows (`gone{n}`) tables are declared just before the statement
   that fills them. The blob tables and the fixed sets are declared at the top.
7. `Assign` also sets every child's parent key from the nesting, so a new child under an existing
   parent needs no client-side key.
8. Refills ride a batch only for sequences whose buffer is already in use (reserved or taken from
   in this process). §7.2 says "any sequence whose table is in the batch's WrittenTables".
   Tables written only by fixed-text statements (`core.Jobs`, `core.Blobs`) never use the buffer,
   and would otherwise burn 64 ids on every such batch forever.
9. The fixture gains `WidgetPart.DrawingId`, a child blob column, to test capture on child delete.
10. `FixtureTenant.CreateScope` takes an optional user id. The default scope stays userless,
    because setting the system user globally changes `HasUser` for the query tests.

### Open risks

- **User-level tag bumps.** A save registers no `UserIdSource`, so a save of `core.Users` (or any
  table under a user-level rule) bumps nothing user-level. That belongs to the version-tag work
  (PC-038 territory). `Save` declares `plan.Writes` as its written tables, so tenant-level bumps by
  table work.
- **Contributor stage contract.** It is unchanged. Refill statements are appended after the
  caller's statements and before the epilogue contributors run. An epilogue sees them in
  `WrittenTables` only via their (empty) writes, i.e. not at all.
- **Tree re-parenting.** The root update sets `ParentId` but never `Node`. Until the tree
  statements land, a re-parent through `Save` leaves `Node` stale; a new tree row gets
  `/0/<id>/`.
- **Server-owned columns on insert** come from the row as given. `ResetServerOwned` is the
  pipeline's call (§2.4), not the emitter's.
- **Heal cost.** As §7.4 says, the heal discards the first range whole, even its part above
  `MaxId`.
- **Pre-existing flake seen in the gate (not touched).**
  `Observability/SqlQueryTextTests.A_commands_span_carries_no_query_text` failed once out of three
  core-suite runs. Its capture processor collects every SqlClient span in the process, so it also
  captured `CREATE DATABASE` spans from `TenantCatalogTests` and `TenantScopeTests` running in
  parallel; those spans started before its provider existed and kept their text. The test passed
  alone and on the full re-run. A fix would assert only on spans under a parent activity the test
  starts.
- **Completion-step token.** Completion steps run with the caller's token. A heal cancelled
  mid-flight fails the reservation (reported by `Assign`), never the batch.

### What to examine hardest

- `SaveText.PlanOutput` / `MappedTouched`: the `cap{n}` fan-out and the join that maps a grandchild
  write to its root. The golden in `SaveStatementTests` is the full text for a three-level
  aggregate with blobs on two levels.
- `ReservationHold`'s lock discipline between `Fill` (a completion step), `Dispose` and
  `MarkPersistAttempted`. Check that no id is both returned and assigned.
- `DataExecutor.ExecuteAsync`: the completion steps' placement relative to the audit, the outcome
  and the commit callbacks, and the `UniqueConstraintViolationException` hook (only around
  `RunAsync`).
- The racing-saves test (`Two_racing_saves_of_one_row_produce_exactly_one_conflict`) gates the
  first save on an application lock inside its transaction. Check that it proves the U-lock
  ordering rather than a timing accident.

### Findings

**R1-1 (minor).** `src/core/Tellma.Core/Data/Batches/DataBatch.cs:424-427` with
`src/core/Tellma.Core/Data/Ids/ReservationHold.cs:111-117`. `MarkPersistAttempted` does not look
at `_disposed`, and `SavePayload` (`SavePayload.cs:104`) checks `IsReturned` only when `Save`
composes. Scenario: the pipeline composes the persist batch (`Save` accepts the hold), then the
reservation is disposed (a `using` that ends before `ExecuteAsync`, or a validation step that
fails after composing): `Dispose` returns the ranges to the front of the buffer, and the persist
then executes and inserts those same ids. The next create on the instance is handed them and
fails with 2627 (or wins and the first persist fails), and the buffer is dropped. Fix: make the
mark atomic with the check. `MarkPersistAttempted` returns false (or throws) when the hold already
returned its ids, and `DataBatch.ExecuteAsync` refuses the batch with an
`InvalidOperationException` before sending, as `SavePayload` does at compose time. Add a unit test
for Save → Dispose → ExecuteAsync.

**R1-2 (minor).** `src/core/Tellma.Core/Data/Ids/IdAllocator.cs:509-517` (`Refilled`) and
`:473-493` (`SettleAsync`). A refill whose `MaxId >= First` has detected an out-of-band insert,
just as a reservation would. It trims the range silently, with no `IdAllocator.Healed`, no
`tellma.data.ids.healed` and no drop. Spec 0012 §7.4 alerts on every heal, and ARCHITECTURE.md
says every recovery event is logged and alerted. The refill also leaves the buffer's older ranges
in place, which may sit at or below that `MaxId`, and so does a reservation-time heal: the
ranges taken from the buffer for the same hold, and the buffer's remainder, are kept. Scenario: a
restore or import writes ids above the sequence. The next refills (one per create) each read a
range under `MaxId` and keep nothing. They log nothing while the buffer drains through ranges that
may collide. The first sign is a 2627 on a user's save. Fix: in `Refilled`, when
`read.MaxId >= read.First`, log `IdAllocator.Healed` (or a sibling event at Warning), count the
heal, and drop the buffered ranges at or below `MaxId`. In `SettleAsync`'s heal branch, also drop
the buffered ranges at or below `MaxId`. Optionally swap the hold's taken ranges at or below
`MaxId` for heal ids, since `Assign` has not run yet.

**R1-3 (minor).** `src/core/Tellma.Core/Data/Batches/DataExecutor.cs:187-203`. The completion
steps now run before the outcome replaces the tenant's snapshots. A heal runs a sibling
`Maintenance` batch inside a step. Once spec 0013's prelude rides `Maintenance` batches (§5.3), that
sibling reads the tags later than the outer batch's prologue did, and its own outcome replaces the
snapshot first. The outer batch then calls `_snapshots.Replace` with its earlier read.
`IVersionTagSnapshots.Replace` documents no monotonic guard, so the process snapshot regresses
until the tenant's next batch. Only a heal triggers this, and the regression is short-lived, but
this is the ordering interplay with the parallel 0013 work. Fix: replace the snapshots (and the
user snapshot) before running the completion steps, and keep only the `RoundTrips` computation
after them, so a heal's round trip still counts. Alternatively, have PC-038's `Replace` refuse an
older snapshot. Record whichever choice in the D-068 planner note.

**R1-4 (minor, test gap).** `src/core/Tellma.Core/Data/Ids/ReservationHold.cs:87-92`. The branch
that sends a statement-reserved range straight back to the buffer when the reservation was
disposed before its batch executed has no test, unit or integration. Deleting it would leak the
range to a disposed hold (a gap, not a duplicate), and no test would fail. Fix: add a unit test.
Reserve cold on a validate batch, dispose, then run the completion step with a canned
`SequenceRead` (or execute through the harness). Assert that the head returned to the front of
the buffer and that `ids.returned` counted it.

**R1-5 (minor, process).** Commit message, "Tests:" paragraph. The checkpoint changes
`Tellma.Core.Abstractions` (`IIdAllocator.cs`, `IdReservation.cs`) and `test/shared/*`

### Findings

**R2-1 (minor).** Ids at or below the table's largest id return to the buffer after a drop, and an
immediate reservation hands them out unchecked. `DropAtOrBelow` cleans the buffer only at that
moment. Afterwards `SequenceBuffer.Return` (`src/core/Tellma.Core/Data/Ids/SequenceBuffer.cs:124-135`)
accepts whatever comes back. Three paths put stale ids back:

- **(a) Another open hold's `Dispose`** (`src/core/Tellma.Core/Data/Ids/ReservationHold.cs:270-274`,
  through `IdAllocator.Return` at `src/core/Tellma.Core/Data/Ids/IdAllocator.cs:343-353`). Ids it took
  before a `Refilled` drop or a heal drop come back to the front. `Fill`'s re-drop
  (`ReservationHold.cs:108-111`) covers only the hold whose own heal ran.
- **(b) The "still behind" throw** (`IdAllocator.cs:512-517`). It comes after the drop (509) but
  before the caller trims what it held.
  - On the reservation path, `CompleteAsync` (463-466) records `Fail`, `need.Held` keeps the taken
    ids, and `Dispose` returns them.
  - On the take path, `TakeAsync`'s catch (211-216) returns the untrimmed `ranges`.
- **(c) A heal round trip that fails** (502). It drops nothing, although the first read already
  reported `MaxId`. The hold then fails and returns its taken ids, as in (b).

Scenario for (a):

1. The buffer holds 100..109. An import writes explicit ids up to 205, while the sequence is at 200.
2. H1 reserves 5 ids and is immediate: it takes 100..104.
3. A batch updating a widget refills: First 200, MaxId 205. `BehindOnRefill` drops 105..109 and
   appends 206..259.
4. H1's validation fails, and `Dispose` puts 100..104 back at the front.
5. The next create's reservation is immediate and takes 100..104 without a read. Its persist fails
   with 2627, the user-visible failure R1-2 set out to replace with a Warning. The PK drop then
   recovers.

Fix:

- Give `SequenceBuffer` a floor that only rises: the largest `MaxId` any read for it reported, set
  by `DropAtOrBelow`.
- Have `Return`, and defensively `Append`, discard ids at or below the floor and report the count
  through `BufferDropped`.
- In `SettleAsync`, drop at `maxId` before the heal round trip, and at the larger of the two reads
  after it.
- Unit test: replenish, take immediately, refill behind, dispose, then assert that the returned ids
  are not buffered.

**R2-2 (minor).** `src/core/Tellma.Core/Data/Ids/IdAllocator.cs:546-559`, with `AppendRefills` at
269-275. A refill that finds the sequence behind keeps only the ids above `MaxId`. Its size is
`LowWater - held`, at most 64, so with a larger gap it keeps nothing. The buffer then stays below
the mark, and every later batch writing the table appends another refill. Each logs another
`BehindOnRefill` Warning and counts another `tellma.data.ids.healed`, the alerted instrument.

Scenario: an import writes 100,000 explicit ids above the sequence. For a while the tenant then only
edits widgets; the buffer exists from an earlier create. Each update batch logs a Warning and an
alerted heal, about 1,500 of them. That stops only when the sequence walks past `MaxId` in 64-id
steps, or when a create heals. §7.4 promises "one detection, one cure" with an alert per heal;
instead one condition raises a stream of alerts.

Fix: when a refill finds the sequence behind, mark the buffer (R2-1's floor can serve) and skip its
refills until a reservation heals. The next create then pays the cold statement and heals once.
Alternatively, log and count only the first behind refill per floor.

**R2-3 (minor).** `src/core/Tellma.Core/Data/Ids/ReservationHold.cs:176-179`, with
`IdAllocator.cs:463-466`. `CompleteAsync` stores any failure of the heal round trip, and `Assign`
throws it wrapped in an `InvalidOperationException`. The stored failure is often not a bug:

- a `DataAccessRetryExhaustedException` after deadlocks on the heal;
- a `TenantUnavailableException` from the schema guard on the heal's sibling batch;
- an `OperationCanceledException` from the request's aborted token, the "Completion-step token"
  open risk.

Spec 0015 maps the first two to 503 with `Retry-After`, and it neither maps nor logs a cancellation.
It treats an `InvalidOperationException` as an authoring bug: a 500 with a trace id.

Scenario: a create whose reservation heals while the database sheds deadlocks answers 500 instead
of 503, and an aborted create logs an error.

Fix: in `Assign`, rethrow a stored `DataAccessException`, `TellmaException` or

**R2-4 (minor; a spec gap, for Ahmad).** `src/core/Tellma.Core/Data/Ids/IdAllocator.cs:62` and

behind a tenant id changes. Spec 0011 cuts a tenant over to a point-in-time restore under `Frozen`

after that point.

### Responses

- **R2-1: fixed in "PC-037: review 2 fixes", as the reviewer suggested.**
  - *The floor.* `SequenceBuffer` keeps a floor that only rises: the largest `MaxId` any read
    reported, set by `DropAtOrBelow`.
  - *What the floor filters.* `Return` and `Append` discard ids at or below the floor and report
    the count. A discarded return logs the new event `IdAllocator.StaleDiscarded` (Warning) rather
    than `BufferDropped`, whose message is about a duplicate primary key. `ids.returned` meters only
    the ids actually returned.
  - *The heal.* `SettleAsync` drops at `maxId` before the heal round trip, so a failed heal or the
    "still behind" throw still leaves the floor raised. It drops again at the larger of the two
    reads afterwards, and `Healed` reports the sum.
  - *Fill.* `Fill`'s re-drop for a disposed hold is gone, since the floor covers it.
  - Unit tests:
    - `Ids_another_reservation_held_across_a_refill_found_behind_never_return_to_the_buffer`: the
      reviewer's scenario (a), step by step;
    - `A_heal_that_fails_still_raises_the_floor_so_the_reservations_taken_ids_never_return`: paths
      (b) and (c). The harness refuses the heal's sibling batch.
- **R2-2: fixed in "PC-037: review 2 fixes".**
  - When a refill finds its sequence behind, it marks its buffer (`SequenceBuffer.MarkBehind`).
    Only the transition logs `BehindOnRefill` and counts `ids.healed`.
  - `AppendRefills` skips a marked buffer. A reservation that settles a range clears the mark,
    healing first when needed, so the next create pays the cold statement and heals once.
  - Unit test: `A_refill_found_behind_stops_the_buffers_refills_and_reports_once_until_a_reservation_reads_a_range`.
    The first refill is 100,000 behind and keeps nothing. The next writing batch carries no refill,
    and one heal is counted. A reservation then reads above the table, and the next writing batch
    carries a refill again.
- **R2-3: fixed in "PC-037: review 2 fixes".**
  - `Assign` rethrows a stored `DataAccessException`, `TellmaException` or
    `OperationCanceledException` as itself (`ExceptionDispatchInfo.Throw`), and wraps only the rest.
  - Unit test: `A_failure_the_caller_maps_surfaces_as_itself_and_any_other_is_wrapped`. It covers
    `DataAccessRetryExhaustedException`, `TenantUnavailableException`, `OperationCanceledException`,
    and a wrapped `KeyNotFoundException`.
- **R2-4: fixed in "PC-037: review 2 fixes" through the existing seam. The spec gap is reported.**
  - *The listener.* `IdBufferTenantListener` is registered with `TryAddEnumerable` beside the
    allocator. It is an `ITenantStateListener` from the 0011 tenant registry, which already
    delivers state changes and removals. It calls `IdAllocator.ForgetTenant` when the tenant enters
    `Frozen`, leaves `Frozen`, or leaves the registry.
    - The registry reports no database-identity change to listeners: `TenantDescriptor` carries no
      location. `Frozen`, which every relocation and restore passes through, is the hook.
    - Forgetting on leaving the freeze covers a range a batch read just before it.
    - `ForgetTenant` logs `IdAllocator.TenantForgotten` (Information).
  - *Forgotten buffers.* A forgotten buffer is removed, not emptied. Each reservation `Need`
    remembers the buffer it took from and returns its ids there. So an id held across a cut-over
    goes back to the forgotten buffer, never to the new database's, and the new buffer starts with
    a fresh floor.
  - No WATCHLIST line is needed, since the seam exists.
  - Unit tests:
    - `Freezing_a_tenant_forgets_its_buffers_and_no_other_tenants`: a rename keeps the buffers; a
      freeze forgets them; a hold disposed after the freeze returns nothing to the new buffer;
      leaving the freeze and removal forget again;
    - `Two_tenants_whose_databases_issue_the_same_ids_never_share_a_buffer`: the §13.3 assertion,
      at the allocator level.
  - *The spec gap for Ahmad.* Spec 0012 §7.3–§7.4 says nothing about what a relocation or a
    point-in-time restore does to the buffers. The behaviour built here is: forget on entering or
    leaving `Frozen` and on removal. §7.3–§7.4 should say so, or 0011 should report a
    database-identity change to listeners.
