# PC-217: Client ID metadata documents (document clients)

## Implementer notes

### What was built

All code is under `src/apps/Tellma.Identity/` unless noted.

- **Options.** `Options/TellmaIdentityClientMetadataOptions.cs` (`TellmaIdentity:ClientMetadata`): `Enabled`, `MaxBytes` (5120), `Timeout` (5 s), `MinCache` (1 min), `MaxCache` (24 h), `FetchesPerHostPerMinute` (10), `MaxClients` (10,000), `UnusedClientLifetime` (1 h).
  - `TellmaIdentityOptionsValidator` bounds every value, with hard ceilings on `MaxBytes` and `Timeout`.
  - It also refuses a seed entry whose `ClientId` is an `https` URL, so no seeded client can occupy a document client's id.
- **Contract.** `Services/ClientMetadataDocument.cs` (record) and `Services/IClientMetadataDocumentResolver.cs` (`ResolveAsync`, `RevalidateAsync`).
- **Recognising a client id.** `Services/ClientMetadata/ClientIdUrl.cs`. Any absolute `https` client id without a fragment is taken as a document URL. `FindProblem` then refuses it unless it is at most 100 characters, ASCII, already in canonical form (`AbsoluteUri`), free of userinfo and dot segments (encoded ones included), and named by a DNS host rather than an IP literal. `DisplayHost` is the host shown on the consent page.
- **Network guard.**
  - `ClientMetadataNetwork.cs` holds the named client's primary handler: a `SocketsHttpHandler` with `UseProxy=false`, `AllowAutoRedirect=false`, no cookies and a `ConnectCallback`.
    - The callback resolves the host through `IClientMetadataHostResolver` and refuses the whole connection if any resolved address is refused.
    - It then connects through `IClientMetadataSocketConnector` to the addresses it checked, never to a re-resolved name, which defeats DNS rebinding.
    - An IP-literal host is checked as one address.
  - `ClientMetadataAddressPolicy.cs` accepts only globally reachable unicast addresses.
    - IPv4: the IANA non-global ranges, multicast and reserved.
    - IPv6: only 2000::/3, minus its special ranges.
    - Mapped IPv4, NAT64 and 6to4 addresses are judged by the IPv4 address they embed.
  - `ClientMetadataHttp.cs` registers the named client `Tellma.Identity.ClientMetadata` with `Timeout=Infinite` (the fetcher owns the timeout) and no resilience handler.
- **Fetching.** `ClientMetadataFetcher.cs`.
  - The URL must be `https`. Each host is rate-limited (`ClientMetadataRateLimiter.cs`: one-minute window, at most 10,000 tracked hosts).
  - The fetch has a linked timeout, a `ResponseHeadersRead` request and a size cap on both the declared `Content-Length` and the bytes actually read.
  - Only a `200` is accepted (a `3xx` is reason `redirect`), and the media type must be `application/json` (a key set may also be `application/jwk-set+json`).
  - The response's lifetime comes from `Cache-Control`/`Expires` (`ClientMetadataCacheLifetime.cs`).
  - Every failure is a `ClientMetadataException` with a stable reason (`ClientMetadataRejectionReasons.cs`).
- **Validation.** `ClientMetadataDocumentParser.cs` checks the document and the key set. The rules are listed under Deviations 2.
- **Resolution.** `ClientMetadataDocumentResolver.cs` (singleton) and `ClientMetadataCache.cs` (bounded at `MaxClients`, evicting expired entries first).
  - Only one fetch per client id is in flight at a time.
  - The document's lifetime is clamped to `[MinCache, MaxCache]`, and a key set's clamped lifetime can only shorten it.
  - `RevalidateAsync` fetches early, ignoring the cached copy. If that fetch fails or is rate-limited, the unexpired cached copy is served (`servedCached` in the audit). A validation failure evicts the cached copy.
  - An expired copy is never served.
  - Outcomes:
    - Each outcome is audited by `ClientMetadataAuditor.cs` as `ClientMetadataFetched` or `ClientMetadataRejected`, recording the reason, the host and the client id truncated to 512 characters. The `ClientId` column is filled only when the id fits it.
    - Each outcome is counted on `tellma.identity.client_metadata.fetches` (`Infrastructure/IdentityMetrics.cs`), whose only tag is `outcome` = `fetched`|`rejected`|`failed`.
- **The row.**
  - `ClientDescriptorFactory.DocumentClient` builds the row:
    - The client is public for `none`, and confidential with the document's JWKS for `private_key_jwt`.
    - The application type is `native` when the document lists a loopback redirect, else `web`.
    - Consent is explicit and PKCE is required.
    - The permissions are the authorization, PAR, token and revocation endpoints, the code and refresh grants, `response_type=code`, and the scopes `email`, `profile` and `tellma_api`. OpenIddict itself admits `openid` and `offline_access`.
    - The row carries no `rsrc:` permission (resources come from the existing document-client branch of `ResourceGrantValidator`).
    - The properties are `tellma:document_client` and `tellma:created_utc`, and the display name is `client_name`, else the host.
  - `ClientRegistrationConverger.ConvergeDocumentClientAsync` converges the row with the existing retrying, fresh-scope converger.
    - At the cap, a new row is refused (`cap`).
    - A row that exists without the marker is never taken over (`registered`).
    - `CreatedUtc` is preserved on update.
    - Keys are compared by public parameters (`HaveSameKeys`), so an unchanged document never rewrites the row.
- **Pipeline.** `Handlers/DocumentClientHandler.cs` is a scoped `ProcessAuthenticationContext` handler at `ValidateRequiredTokens + 500`: after token extraction, before `ValidateClientAssertion` and `ValidateClientId`.
  - It covers the authorization, PAR, token and revocation endpoints only.
  - It takes the client id from `client_id`, else from the unvalidated `iss` of a `jwt-bearer` client assertion (OpenIddict validates the assertion afterwards against the row's keys).
  - At authorization and PAR, a `redirect_uri` that the cached document does not list (matched by `DocumentClientRedirects.Matches`, loopback on any port) triggers `RevalidateAsync` before the built-in redirect check.
  - Any failure is `invalid_client` with one generic description.
  - `AdvertiseDocumentClientsHandler` (same file) adds `client_id_metadata_document_supported: true` and `none` to discovery while the feature is enabled.
- **Prune.** `Services/ClientMetadata/DocumentClientStore.cs` (count and prune queries) and `DocumentClientPruneJob.cs`, an hourly Quartz job on the session prune's schedule (`Hosting/QuartzConfigurator.cs`). The prune rule is under Deviations 5.
- **Consent.**
  - `AuthorizationController` passes `ClientHost` for a marked document client.
  - `Views/Authorization/Consent.cshtml` shows it under the new `ConsentClientHost` string (en and ar), with `bdi dir="ltr"`.
  - `Infrastructure/CspFormAction.cs` now emits `http://127.0.0.1:*/callback` for a port-less loopback redirect (Deviations 6).
- **Docs.**
  - The `Tellma.Identity` README has a new "Document clients" section, including the test seam.
  - The integration-tests README describes `LocalDocumentServer`.
  - ARCHITECTURE.md already describes document clients consistently with this checkpoint, so it was not changed.

### Deviations

1. `IClientMetadataDocumentResolver` has a second method, `RevalidateAsync`, and both methods take a `CancellationToken`. An unlisted redirect URI must be able to bypass a fresh cached copy, so that a client that has just published a new callback is not refused for up to `MaxCache`.
2. Validation goes beyond the spec's list:
   - Redirect URIs:
     - `http` is allowed only on loopback, where `localhost` counts as loopback, as in OpenIddict's own relaxation.
     - Fragments, userinfo and `iss` parameters are refused, and so are the `javascript:`, `data:`, `file:` and `vbscript:` schemes.
   - Credentials and keys:
     - `client_secret` and `client_secret_expires_at` are refused.
     - Inline `jwks` is refused, and so is `jwks_uri` with `none`.
     - `jwks_uri` must be on the client id's origin.
     - The key set must hold public RSA keys of at least 2048 bits, or EC keys on P-256/384/521, with `use` absent or `sig`.
   - `grant_types` must be a subset of `{authorization_code, refresh_token}` that includes `authorization_code`.
   - `client_name` must be 1 to 100 characters, not blank, with no control or format characters.
   - Duplicate JSON members are refused at any depth.
3. A client id is limited to 100 characters (reason `client_id_length`), the width of OpenIddict's `ClientId` column, which holds the row. It must also be ASCII, in canonical form and named by a DNS host. Without the canonical-form rule, two spellings of one URL would be two clients, or one row under the case-insensitive collation.
4. A seed entry with an `https` `ClientId` fails startup.
5. The prune deletes a row with no authorization **and no unexpired token**, together with that row's expired tokens. The spec says only "no authorization". A pushed request is stored as a token with no authorization, and deleting a row out from under it ends a flow that is still in progress. Expired tokens also block the delete through the foreign key, so they go first.
6. `CspFormAction` emits `scheme://host:*path` for a port-less loopback redirect. Before this change, the consent page's `form-action` named only the default port, so a native client using an ephemeral port, which OpenIddict accepts, had its redirect blocked by the browser. This also changes the CSP for the seeded third-party and interim native clients, and their tests were updated.
7. Every refusal returns the same generic `error_description`. The reason is recorded only in the audit, so a probe learns nothing about the network.
8. With `Enabled=false`, an `https` client id is refused as `invalid_client` (audit reason `disabled`) rather than passed to the registry.
9. The fetch counter counts fetch outcomes only. Cap and takeover refusals (`cap`, `registered`) are audited but not counted.

### Open risks

- There is no global bound on concurrent fetches. The only limits are per host (10 per minute) and the single flight per client id, so many distinct hosts can drive many outbound fetches at once.
- In the worst case, the cache holds about `MaxClients` × (`MaxBytes` + a key set).
- The cap is soft under races: concurrent creates can overshoot it by the number of in-flight requests.
- Key rotation is picked up only when the copy expires or on a redirect-triggered revalidation. An assertion signed by a new key fails until then.
- The rate limiter and the cache are per instance.
- The integration seam replaces the primary handler, which also removes the address guard. The guard is covered only by the unit suite, through its two seams.

### Examine hardest

- `ClientMetadataNetwork.ConnectCallback` and `ClientMetadataAddressPolicy`: every IPv6 form, mapped and translated addresses, and that the connection goes to the checked address only.
- The handler's position against OpenIddict's authentication pipeline, and the per-scope cache of the application manager: the row is converged in fresh scopes before the request scope first reads it.
- The `registered` takeover guard, and the `HaveSameKeys` comparison.
- `DocumentClientRedirects.Matches` against OpenIddict's own native-app loopback relaxation.
- `DocumentClientStore.PruneAsync`: the in-memory `CreatedUtc` filter, and the re-checks inside each delete.
