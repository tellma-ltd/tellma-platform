# PC-152: Device time zone detection and prompt

## Implementer notes

### What was built

Spec 0024 §7.8: the device time zone's option, check, prompt and automatic update, as one
small class in the primary of `@tellma/core` and three lazily loaded chunks of it, with the
seams the testing package replaces, the Arabic in `@tellma/locale-ar/platform-strings`, and the
Acme device-zone e2e flows (carry D-266).

- **Primary** (`client/projects/core/tellma-core/src/l10n/tm-device-zone.ts`).
  - Types `TmZoneDoc` and `TmZoneUser` (`{ auto, seen, at }`), exported.
  - `TmDeviceZone` (root): `auto`, a computed over the device partition's `zone` document that
    reads defensively (a malformed document reads as off; false while signed out);
    `setAuto(on, source)`, which loads `tm-zone-doc` and writes there; `check()` and `ɵstart()`,
    which load the check's chunk once through `ɵTM_ZONE_CHECK_LOAD` and create its service. A
    failed load goes to telemetry (`where: 'tm.l10n.zone-check'`) and is retried on the next call.
  - `tm-app-init.ts`: the startup's idle `load()` (after first render, beside the telemetry
    pipeline) calls `TmDeviceZone.ɵstart()`.
  - `TmLocks.tryRun(name, work)` (`src/state/sync/tm-locks.ts`): Web Locks `ifAvailable`, or,
    without Web Locks, "no unsettled request of the name in this tab". Resolves `false` at once
    when taken, `true` once the work settles.
  - `TmErrorsModule`'s presenter type (`src/api/tm-api-seams.ts`) gained `describe(error,
    { kind: 'save', tenantId? })` (title, message and the server's items), which the prompt uses
    through `TM_ERRORS_LOAD`.
- **`tm-zone-doc` chunk** (`src/l10n/tm-zone-doc.ts`): one user's entry read defensively, the
  write of one entry with the cap of 20 (the oldest `at` dropped, never the current user), and
  `ɵtmSetZoneAuto` (no-op signed out; patches with `TM_NOW`; emits
  `tm.l10n.zone-option { on, source }`).
- **`tm-zone-check` chunk** (`src/l10n/tm-zone-check.ts`): `TmZoneCheck` (root).
  - Triggers: one check at start, an effect per tenant entry (keyed `sub:tenantId`, waiting for
    `me`, `settings` and the tenant facts), and `visibilitychange` to visible. Checks are
    serialized; a check's failure goes to telemetry and never rejects.
  - Context: only in a visible tab (`TM_API_HOST`), after `TmEntities.load()`; the device and
    the display zone both mapped through `core.TimeZone`'s aliases; `frozen` from the tenant
    facts' state.
  - Steps 1–7 as a pure `stepOf(context)`; same-offset compares `ɵtmZoneOffset` at the instant,
    an unknown id counting as different.
  - Prompt path: `TmLocks.tryRun('tm:<slug>:<sub>:zone-prompt')`; inside it, the dialog chunk is
    preloaded, then `TmInputIdle.whenIdle()` and no open modal are awaited (looping while a
    modal opens meanwhile), then steps 1–6 are re-run before the dialog opens. A tab that finds
    the lock taken queues one plain `TmLocks.run` on it in the background; once the holder
    frees it, the tab re-reads the device partition and runs the steps again under the lock, so
    a holder that gave up without asking (it turned hidden first) does not lose the prompt.
  - Automatic update: `users/me/locale { timeZone: device }` with the tenant, adopted through
    the refresher, then a neutral 4 s toast "Times now show in {zone} ({offset})." with Change →
    the tenant's `me/region`. `offline` retries once when `TmApi.online` returns;
    `Users.TimeZoneUnknown` records; other failures record nothing. The kinds the error views
    report when they show them (`server`, `unavailable`, `partial-failure`, and `offline`
    with `outcome-unknown`) go to telemetry with `source: 'api'`, from the automatic update and
    from the prompt's write alike.
  - Telemetry `tm.l10n.zone-change { action }`, `tm.l10n.zone-prompt { answer, auto }`,
    `tm.l10n.zone-auto { outcome }`: no zone id or offset in any.
- **`tm-zone-prompt` chunk** (`src/l10n/tm-zone-prompt.ts`): `ɵTmZonePrompt` and
  `ɵtmAskZone`. `TmModal` `sm`, `role: 'dialog'`, described by the message; checkbox with its
  hint as its description; Keep current (secondary) and Change time zone (primary, initial
  focus, busy in the click's frame, the dialog undismissable while busy); an inline assertive
  `tm-alert` for `Users.TimeZoneUnknown`, else the error views' `describe(error, { kind: 'save' })`
  with the server's errors listed under it.
  The title follows a language switch while open.
- **Testing package**: `TmFakeLocks.tryRun` (taken while any request of the name is granted or
  queued); `provideTellmaStateTesting` replaces `ɵTM_ZONE_CHECK_LOAD` with a loader of nothing,
  so test apps never run the check.
- **Arabic** (`strings-tm-ar.ts`): the `zone` and `zonePrompt` blocks, imperatives through
  `imperative()`.
- **Acme e2e** (`distributions/acme/test/Tellma.Distro.Acme.E2E/specs/device-zone.spec.ts`,
  serial, chromium and chromium-ar): the device moved with `Emulation.setTimezoneOverride`.
  Each flow starts and ends with the user's time zone preference cleared (`reset: ['TimeZone']`
  through the page, as My settings sends it), so the display zone is the tenant's whatever an
  earlier run left. Flow 1: a silent first run; a second tab; a move away; the prompt waits
  while the mouse moves; message and axe; Change; the second tab asks nothing for the handled
  change; the device moves on in the second tab, whose own prompt names the first tab's new zone
  as the one it shows (its localization followed); tick + Change there; back home in the first
  tab, the automatic update and its toast, whose Change opens `/1/me/region`. Flow 2: an
  override to `Asia/Kolkata`, asserted to be reported as `Asia/Calcutta`, offered and saved as
  `Asia/Kolkata`.
  The two device-zone fixmes left `language-errors.spec.ts` (the zone-labels one stays).
- **Docs**: ARCHITECTURE.md's `@tellma/core` row; the core README's primary row and a new
  "The device time zone" section; the e2e README.

### Deviations

1. The check also waits for the tenant facts document (the state for step 4), beside `me` and
   `settings`. The lock name's slug is the distribution's, from the client metadata.
2. The re-check after the wait runs steps 1–6, not 2–6: step 1 cannot fire there in practice,
   and one function keeps the two passes identical.
3. The automatic update (step 5) also runs inside the prompt lock, so two tabs of the user never
   write the same change twice; a tab without the lock stops as the prompt path does.
4. `tm.l10n.zone-prompt`'s `auto` is the box's state at the answer, whatever the answer (Keep
   with the box ticked reports `auto: true` and never turns the option on).
5. A close without an answer that is not the user's (history navigation, `Dialog.closeAll`)
   records nothing and emits no `zone-prompt`, as "a tab closed before that" does, so the next
   check asks again. Escape and the close button are dismissals and record.
6. The backdrop does not dismiss the prompt (Escape and the close button do), so a stray click
   never answers it.
7. The offline retry happens once per change (per device zone), not once per check.
8. The display zone is also mapped through the aliases before comparing, so a preference saved
   under an old name (`Asia/Calcutta`) matches a device reporting the new one.
9. The zone document's writes are a third lazy chunk (`tm-zone-doc`), to keep the primary's
   raise small; `setAuto` therefore loads a chunk on its first call.
10. "Every tab re-renders" is verified in the e2e through the second tab's own localization, as
    its prompt names the display zone (the first tab's new zone), not through on-screen offset
    labels: those belong to spec 0030's grids, and the zone-labels e2e stays a fixme. The
    cross-tab adoption itself is spec 0025's, unit-tested there.
11. A tab that finds the prompt lock taken does not simply stop (step 7.1's "Without it, stop"):
    it waits for the lock once, in the background, and runs the steps again under it, so a
    holder that gives up without asking does not lose the prompt. Taking the lock with
    `ifAvailable` (new `TmLocks.tryRun`) is step 7.1 itself; spec 0025 §5.3's "never
    `ifAvailable`" is about the sync lock alone, so that is no deviation.

### Rulings taken (spec silent)

- The toast's Change navigates to `forTenant(tenant).page('me/region')`.
- A `Users.TimeZoneUnknown` answer to the prompt's Change records the zone (as the automatic
  update does) once the dialog is answered or dismissed, so it is not offered again until the
  device moves.
- Turning the option on after a ticked Change is best effort: a store refusal goes to telemetry,
  the change itself stands.

### Open risks

- The idle gate relies on `TmInputIdle`; a page that never sees input settle (a kiosk with a
  jittering pointer) never asks. That is the spec's intent, but there is no upper bound.
- Without Web Locks (plain HTTP from another machine) the prompt lock is per tab, so two such
  tabs can each ask once; each records, so the change is still handled once per tab at most.
- The e2e flows move the cast user's preferred time zone and clear it at the end (and at the
  start, after a killed run); while a flow runs, another spec of the same user in parallel would
  see the moved zone. No other spec reads either user's zone today.
- On a return to the tab, the idle clock has long run out, so the prompt opens at once
  (`whenIdle()` resolves at once while idle, spec 0028 §9.3); the example's "After 2 s without
  input" holds only while the user is using the tab. The orchestrator flags the spec-to-spec
  tension to Ahmad (D-286); no code change.

### What reviewers should examine hardest

- `TmZoneCheck.#locked`: the wait loop, the re-check after it, and the lock's release on every
  path (answer, dismissal, close by navigation, failure).
- The tenant-entry effect's keying and the serialization of checks (`#tail`), against a burst of
  triggers (tenant entry + visibility + start at once).
- `TmWebLocks.tryRun`'s fallback without Web Locks and `TmFakeLocks.tryRun`'s pending count.
- The offline retry's effect lifetime (`#retryOnline`) and that it fires at most once per change.

**R1-1 (major): no test covers the tenant-entry trigger**

- **Where:** `client/projects/core/tellma-core/src/l10n/tm-zone-check.ts:201-217`; there is no
  case in `tm-zone-check.spec.ts`.
- **The rule:** §7.8 says "`TmDeviceZone` checks after first render at idle, on each tenant entry
  and on `visibilitychange` to visible". The spec covers the visibility trigger (`:263`), and the
  startup's first check runs through the same effect's first run. Nothing enters a tenant a
  second time.
- **Failure scenario:** A refactor drops `this.#entered = null` on leaving a tenant, or keys the
  effect on the tenant id alone. Then leaving `/17` for the tenant picker and coming back, or a
  second user signing in on the tab, never checks until the tab is hidden and shown again. Every
  spec stays green. The implementer named this keying as a place to examine hardest, and it is
  the one trigger without a test.
- **Fix:** Add a case:
  1. Start in `/17` with `seen` equal to the device zone, so the startup's check stops.
  2. Set `deviceZone` to a new zone without dispatching `visibilitychange`.
  3. `tmNavigate` to a tenantless route and back to `/17`.
  4. Assert that the check ran: one write with `auto` on, or else a prompt.

  Add a burst case too: a tenant entry, a `visibilitychange` and a `check()` in one task give a
  single `zone-change` event.

**R1-2 (major): the e2e's "every tab follows" check reads the shared database, so it proves nothing about the second tab**

- **Where:** `distributions/acme/test/Tellma.Distro.Acme.E2E/specs/device-zone.spec.ts:160-169`
  and `:268`; deviation 10.
- **The rule:**
  - §7.8 says "The result is adopted (0025 §5.3), so every tab re-renders its times".
  - §13 says "every tab re-rendered".
  - Deviation 10 claims this is "verified in the e2e through the second tab's stored `me`
    document".
- **Failure scenario:** `displayZone(secondTab)` runs `indexedDB.open('tm-app')` in the second
  page. IndexedDB is per origin, so both tabs of the context share one database, and the poll

  re-rendered (its tab bus broken, or `store.changed` not reaching `TmLocalization`).

  Only the "no prompt in the second tab" check (`:269-273`) says anything about the second tab.
  It also passes when the second tab's in-memory device document caught up but its `me` did not.
- **Fix:** Drop the line-268 poll, or replace it with something per tab. No absolute time shows
  on screen before spec 0030's grids, so the honest fix is to reword deviation 10 and the README:
  - the second tab's re-render is not verified end to end;
  - the cross-tab adoption is 0025's, unit-tested there;
  - the on-screen check carries to the zone-labels flow.

  Keep `:269-273` as the evidence that the second tab saw the change handled.

**R1-3 (minor): a prompt can be lost when the lock holder turns hidden before it asks**

- **Where:** `tm-zone-check.ts:264` (`tryRun` returning false ends the check), `:268-293` and
  `:346-363`.
- **Failure scenario:**
  1. Tab A comes into view, takes `zone-prompt` and waits in `#quiet` for the idle moment.
  2. Within those 2 s the user switches to tab B. B's `visibilitychange` check finds the lock
     taken and stops ("another tab asks").
  3. A, now hidden, sees no input, so `whenIdle()` resolves. Its re-run returns `null` because
     the tab is not visible, and it releases the lock without asking.
  4. Nobody asks while the user stays in B; the next trigger is B hidden and shown again, or a
     tenant entry. The spec's premise for stopping, "another tab asks", does not hold.
- **Fix:** When `tryRun` returns `false`, queue a plain `TmLocks.run` on the same name, whose work
  only calls `check()` again once the lock is free. The check is idempotent: it stops at step 2 if
  the holder recorded an answer, and asks if the holder gave up. A second-best fix: `#quiet` also
  returns as soon as the tab turns hidden, which narrows the window but does not close it.

**R1-4 (minor, for Ahmad): on a return to the tab the idle gate is already open, so the prompt shows at once**

- **Where:** `tm-zone-check.ts:346-350`, over `attention/tm-input-idle.ts:72-79`.
- **The tension:**
  - Step 7.2 waits for `TmInputIdle.whenIdle()`, which per 0028 §9.3 "resolves at once while the
    tab is idle".
  - A tab the user comes back to has had no input in its window for well over 2 s, since they
    were elsewhere, so the dialog opens the instant the tab shows. That is the moment they are
    about to click or type, the moment the gate exists to avoid.
  - §7.8's example says the opposite: "After 2 s without input, the dialog asks".
  - The implementer's first e2e failure was exactly this (implementer notes, Tests). The flow now
    moves the mouse, which hides it.
