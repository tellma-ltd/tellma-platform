# PC-003: Queryex host-composition basics: rename, zones, restrictions, level, Prologue/Body, paging slots, versioned leaves, undeclared columns

## Implementer notes

### What was built, and where

All engine changes are in `src/core/Tellma.Core.Queryex` (no new project, no new package).

- **§F.18 rename (done first).** `LanguageVersion` → `QueryexVersion` on `ValidationOptions`,
  `QueryCompilationOptions`, `DiscoveryOptions`, `BindingContext`, `BindKey`, and every caller in
  the engine, the shared harness, both test projects and the inspection tool;
  `Versioning/LanguageVersionTests.cs` → `Versioning/QueryexVersionTests.cs`. XML docs say
  "Queryex version". While renaming, fixed a latent L2 bug: `BindKey.Equals` never compared the
  version (only the hash did), so two keys differing only in version that collided on hash would
  have been equal.
- **§F.22 zones.** `Time/CldrTimeZones.cs` is now two embedded tables: `ZoneData` (current ids →
  Windows name, 418 ids under 138 Windows names) and `AliasData` (the 19 aliases). Current =
  tzdb 2026b `zone.tab` locations plus `UTC`; every other id (renamed/deprecated spellings,
  `Etc/GMT±n`, `Etc/UTC`, `GB`, …) left the table. `TryResolve` resolves an alias through its
  current id. New public `QueryexTimeZones.Ids` (ordinal) and `.Aliases`. Checked-in id list:
  `test/core/Tellma.Core.Queryex.Tests/Time/zone-tab-ids.txt` (embedded resource), tests in
  `Time/TimeZoneTableTests.cs`.
- **§F.1 restrictions.** `KeySetRestriction(Path, TableSource)` (form checked in the record's
  init accessors and constructor, so `with` cannot bypass it); `QuerySpec.Restrictions`.
  `Pipeline/HostStructure.cs` resolves paths against the schema (caller errors naming
  `Restrictions[i]`); `QueryClauses.LowerRestrictions` walks the shared join trie under location
  `Restrictions[i]` (new `QueryexClause.Restrictions`, so QX5006 names the restriction);
  `PlanKeySetRestriction` emits `(<col> IN (SELECT [Id] FROM <source>))`; `QueryClauses.Conjoin`
  makes each one a top-level conjunct after the filter.
- **§F.2 `level`.** One registry entry (`FunctionLibrary.Hierarchy`), `TypeSpecs.Node`, template
  `{0}.GetLevel()` with store type `smallint`, `Propagate(0)`. Interpreter counts path segments.
- **§F.3 Prologue/Body.** `StatementEmitter.Write` returns the two parts; `QueryCompiler` builds
  `Sql = Prologue + Body + ";\n"` from them. `CompiledQuery.Prologue`/`Body` are `init` props.
- **§F.4 paging slots.** `Lowerer.PagingSlot(value, "skip"|"take")` makes fixed-name slots outside
  the shared slot table (never merged with an equal literal), appended last; still counted toward
  `MaxParameters`. `QueryKey` holds Skip/Take presence only; `QueryexEngine.Restamped` replaces
  the trailing slots' `Value` on a hit.
- **§F.6 versioned leaves.** `FilterTree.Leaf(text, queryexVersion)` (ArgumentOutOfRangeException
  unless supported), `LeafNode.QueryexVersion`; `FilterBinder` and `Discoverer` bind a stamped leaf
  under its stamp; `QueryKey` renders each leaf's stamp.
- **§F.16 undeclared columns.** `QuerySpec.UndeclaredColumns`; `HostStructure.RequireUndeclaredColumns`
  (form, duplicate ignoring case, Aggregate); `PlanUndeclaredColumn` on the root alias, appended
  to the select list after ordering/tiebreakers are settled, columns `(n, name, QxString,
  Nullable, null, false)`.
- **§F.0 cache keys.** L3 gains restrictions (ordered), undeclared columns (ordered), paging
  presence, leaf stamps. L2 already keyed on the (now per-leaf) version.
- **Harness/fixture.** `LedgerFixture.UndeclaredColumns` (Invoice: `ExtrasJson`, `AuditJson`,
  both `nvarchar(max)`), DDL and inserts include them, `LedgerRow.Undeclared`; `KeySet` (in-memory
  membership + `DECLARE … TABLE` script); `InterpreterContext.KeySets`; `QueryCase.KeySets`;
  `ReferenceQuery` applies restrictions by walking the path itself and appends undeclared values;
  `QueryexProbe.CurrentZones`/`ResolveZone`; `ProbeCacheKeys.ShareQueryEntry`.
- **Integration fixture** creates its database `COLLATE Latin1_General_100_CI_AS` (WATCHLIST lead;
  hard-coded string, not the `DatabaseCollations` constant 0010-a1 owns — see risks).
- **Inspection tool.** "restrictions" (`path @table = k1, k2; …`) and "undeclared columns" inputs;
  when run, each table is declared as `nvarchar(4000)` text keys. README updated. Smoke-tested
  by hand against the running tool.
- **READMEs.** Queryex README gains the public types and an "Amendments" table (with the tzdb
  release); test/harness/tool READMEs updated. ARCHITECTURE.md needed no change (it already
  describes the zone value set and Part F; nothing it says contradicts this).

### Deviations (also in the commit message)

1. `KeySetRestriction.TableSource` is also refused above 128 characters (the backend's variable
   name limit); the spec gives only the character form.
2. A filter that lowers to constant false keeps the WHERE as `(1 = 0)` and drops the restrictions
   (and pruning drops their joins); one that lowers to constant true is omitted beside them.
3. Antarctica/Troll (a zone.tab location) has no entry: the embedded CLDR table never mapped it
   and no Windows name was invented. Every other zone.tab location is current (418 ids).
4. `BindKey.Equals` now compares the version (latent bug fix, see above).
5. Paging slots stay counted toward `MaxParameters` (as before); the spec is silent.
6. A restriction's path form is checked when the record is built (and on `with`); its resolution
   against the schema at `CompileQuery`, on every call, a cache hit included.
7. QX5006 pushed over by a join that only a restriction needs carries location `Restrictions[i]`
   (new internal clause); a join shared with a user clause keeps that clause's location (since
   review 2). The spec names no location for restrictions.
8. The checked-in zone.tab ids pin tzdb 2026b (the spec names no release); the README records it.
9. The Queryex integration fixture's database collation was a literal, not 0010-a1's constant
   (resolved at integration: the merge takes `DatabaseCollations.Platform` and its collation pin).
10. The inspection tool declares restriction tables as `nvarchar(4000)` text keys when it runs.
11. `level` accepts any `HierarchyId`-typed operand, not only the node column (since review 2,
    recorded): `null`, `coalesce` and `if` produce one, and SQL Server accepts `GetLevel()` on
    each form, so the spec's premise that only a path supplies a position is wrong.

### Open risks / what to examine hardest

- **Restamp on hit** (`QueryexEngine.Restamped`): relies on the paging slots being the last one or
  two parameters, skip before take. Check no path can put another slot after them, and that a hit
  for `Skip`-only vs `Take`-only cannot collide (key holds both presence flags).
- **`PlanKeySetRestriction` is three-valued.** Sound only as a top-level WHERE conjunct; check that
  nothing (now or in PC-007 `Via`/`Exists`) can wrap it in `NOT`. It is built only in
  `QueryClauses.LowerRestrictions`.
- **String keys and collation.** `<varchar CI_AS_SC column> IN (SELECT [Id] FROM @tvp)` raises
  Msg 468 if the host's list type has a different collation. The engine cannot fix this; spec 0012
  hosts need collated list types (0010-G `UseCollation`). The differential tests use int keys only.
- **`level` over computed operands** emits `COALESCE(…).GetLevel()`; verified accepted by SQL
  Server 2022 (`fn-level-computed`), not by spec text.
- **DatabaseCollations constant**: the Queryex fixture hard-codes the collation string because
  0010-a1 (parallel) owns the constant; whichever integrates second may want to switch to it.
- Undeclared column names are not checked against the declared columns (a host could list a
  declared column again); the spec does not ask for it.

### Seams for PC-007 / PC-010 / PC-012

- `QueryexClause` and `DiagnosticLocation` take new clauses cheaply (`Restrictions` is the model).
- `QueryKey.Render` is the one place new `FilterTree` node types (`ViaNode`, `ExistsNode`) must
  be rendered; `FilterBinder.Bind`/`Discoverer.ReadFilter` are the two switches to extend.
- `HostStructure` is where further host-structure caller errors belong (Via/Exists navigation
  names, omitted-parameter names).
- Restrictions are root-only by construction (lowered once, against `Lowerer.Root`).

## Review 1

### Findings

Scope checked item by item against 0010 §F.0 (codes, cache-key rule, fixture growth for these
items), §F.1, §F.2, §F.3, §F.4, §F.6, §F.16, §F.18 and §F.22, and against the checkpoint's
deliverables and test list. Every requirement is met or covered by a listed deviation; the ten
deviations are justified and none changes results (the constant-false pruning returns the same
rows; the `TableSource` length cap and `BindKey.Equals` fix are strictly safer). Injection
boundary: `TableSource` and undeclared names are closed-form ASCII identifiers, the path never
reaches SQL as text, and undeclared names are bracket-quoted on top. Paging: the L3 key holds both
presence flags, the slots are always last (skip before take, outside the shared slot table), and
`Restamped` cannot index the wrong slot because presence is part of the key. Re-ran at bfc40a1:
`dotnet build` of both Queryex test projects (Build succeeded, 0 warnings), `Tellma.Core.Queryex.Tests`
(878 pass), `Tellma.Core.Queryex.IntegrationTests` with the PR-tier integration filter (183 pass).
Also confirmed on SQL Server 2022 that the computed-operand forms the emitter writes for `level`
(`COALESCE(...).GetLevel()` and `CASE ... END.GetLevel()`, the latter from
`level(if(IsPosted, Account.Node, AltNode))`) are accepted. Two minor findings; nothing blocking or
major.

**R1-1 (minor) — no test fails if a stamped leaf stops binding under its own stamp.**
`src/core/Tellma.Core.Queryex/Pipeline/FilterBinder.cs:147` (and `Pipeline/Discoverer.cs:227`)
implement §F.6's binding rule, but every test in `Versioning/QueryexVersionTests.cs` passes
unchanged if line 147 is replaced by `BindingContext leafContext = context;` (or the Discoverer
call drops `leaf.QueryexVersion`). `ATreeMixingBothForms_Compiles` compares SQL, which is identical
while one version exists. `TreesDifferingOnlyInALeafStamp_AreDifferentCacheEntries` probes only
the L3 key, and `Discovery_ReadsAStampedLeaf` only checks that discovery reads the leaf. The rule
therefore regresses silently until the first version bump, which is exactly when it starts to
matter. Suggested fix: add a probe in the `ProbeCacheKeys` style, which exists for differences
the public surface cannot yet produce. Build a leaf through the internal
`LeafNode(text, stamp)` constructor with a stamp different from the context's version and bind it
through `FilterBinder` (and through `Discoverer.ReadFilter`). Then assert that the bind key the
`ExpressionCompiler` cached for that text carries the stamp, not the context's version.

**R1-2 (minor) — the inspection tool drops the keys of a repeated table name.**
`eng/queryex-inspection/Tellma.Queryex.Inspection/Inspection.cs:421` declares each table once via
`DistinctBy(entry => entry.Table, …)`, keeping only the first entry's key list. Take an input that
restricts two paths to one table and lists the keys on the second entry:
`CustomerId @t; Id @t = 1, 2`. The tool declares `@t` empty and the run returns no rows, with no
message. Reversing the entries changes the answer, so a developer probing restriction semantics
gets a misleading result. Suggested fix: union the key lists of every entry naming the same table
(ignoring case, as the declaration does) before writing the `DECLARE`/`INSERT`. Alternatively,
throw the tool's caller-error `ArgumentException` when one table is given two different non-empty
key lists.

### Responses

R1-1: fixed in the "PC-003: review 1 fixes" commit. `ExpressionCompiler` gains an internal
`BindObserver` (null on every compiler the engine builds), told of each binding request with its
text and context before the cache is consulted. New probe `ProbeLeafBinding` builds leaves stamped
with an unsupported version (through the internal `LeafNode` constructor), binds them through
`FilterBinder` and through `Discoverer.DiscoverQuery` on an observing compiler, and reports the
version each leaf bound under. `QueryexVersionTests.ACompiledLeaf_BindsUnderItsOwnStamp` and
`ADiscoveredLeaf_BindsUnderItsOwnStamp` assert a stamped leaf binds under `Version + 1` and an
unstamped one under the named version. Mutation-checked: replacing the FilterBinder context with
`context` and dropping `leaf.QueryexVersion` from the Discoverer call each make the tests fail. An
observer was used rather than the bind cache, because discovery binds under inference and is never
cached.
R1-2: fixed in the same commit. `Inspection.Declarations` now groups the entries by table name,
ignoring case, and declares each table once with the union of every entry's keys, so the order of
the entries no longer changes the answer.

The new XML docs, messages and test names carry no spec, `§` or PC references.

Re-run at b780419: I rebuilt both Queryex test projects (Build succeeded, 0 warnings).
`Tellma.Core.Queryex.Tests` has 880 passing tests, and `Tellma.Core.Queryex.IntegrationTests`
with the PR-tier integration filter has 183. `dotnet format --verify-no-changes` is clean on both

I also probed the engine through its public API from a scratch console:

- **Paging re-stamp under contention.** I ran 20,000 parallel compilations over three filters and
  random pages on one engine. Every returned compilation carried its own skip and take, with no
  mismatch.
- **Restrictions in other positions.** A restriction with `Having` stays in `WHERE`. On `Bool`,
  `HierarchyId` and the bracket-named `not` column it emits correctly. A restriction through a
  deep self-navigation shares its joins.
- **Folded filters.** A constant-true filter (`And([])`) leaves the restriction alone. Both
  constant-false forms (`Or([])` and `Not(And([]))`) drop the restriction and its joins.
- **Undeclared columns** named like SQL keywords or like the engine's aliases (`select`, `c0`)
  are bracket-quoted.
- **`level` forms on SQL Server.** `GetLevel()` works as a grouping key, inside a paged derived
  table, and on `CAST(NULL AS hierarchyid)`, `CASE … END` and `COALESCE(…)` operands. I checked
  these on SQL Server 2019 LocalDB.
- **Arithmetic over `level`.** The `smallint` store type does not turn division into integer
  division, because literals bind as `decimal`.

I compared the zone table with the parent commit's table. No current id changed its Windows name.
Only `Antarctica/Troll` of the checked-in zone.tab ids is missing (deviation 3).

Injection review: `TableSource` is a closed ASCII identifier and is refused in `@qx` in any case.
The restriction path reaches SQL only as resolved descriptors. Undeclared names are a closed ASCII
form and bracket-quoted on top. I found no bypass of a restriction: restrictions are always
top-level conjuncts, and they are dropped only when the filter is already false. The cache stays
tenant-safe: the L3 key holds the schema by identity and every value-bearing input, and paging
values never reach the text.

Review 1 got no pushback; both of its fixes hold. I mutation-checked neither, and the
implementer's mutation note is plausible from the code. Two minor findings; nothing blocking or
major.

**R2-1 (minor): a join that the user's clause shares with a host restriction is blamed on the
restriction.**
`src/core/Tellma.Core.Queryex/Pipeline/QueryClauses.cs:142` lowers the restrictions before
`LowerSelect` (line 143), ordering and having. A join node keeps the origin of whichever clause
walked it first (`Lowering/RelationalPlan.cs:85`). QX5006 is scoped to that origin
(`Lowering/Lowerer.cs:329`).

The probe shows the failure. `Select = "Customer.Region.Name"` with `MaxJoins = 1` reports
`QX5006@Select[0]` over span (0, 20). Add the host's `Restrictions = [("Customer.Region.Id",
"@k")]` and the same user text reports `QX5006@Restrictions[0]` over span (0, 0). The user's own
select pushed the count over, but the diagnostic now points at host structure: an editor has
nothing to underline, and a host that maps locations to the clauses a user wrote (spec 0015) has
no field to show it on. Deviation 7 ("QX5006 pushed over by a restriction's joins") then
overstates what the location means.

Suggested fix: lower the restrictions after select, having and ordering, and conjoin them into
`where` afterwards. User clauses then claim shared joins first, and `Restrictions[i]` is named
only for joins that only a restriction needs. No golden's aliases change: in every new golden the
select already walks the shared navigations in the same order. Add a test with a shared join over
the ceiling that asserts the `Select[0]` location.

**R2-2 (minor): `level` accepts computed operands although §F.2 says anything but the node column
is QX3005, and neither the code nor the commit records the deviation.**
The `level` entry at `src/core/Tellma.Core.Queryex/Functions/FunctionLibrary.cs:682` admits any
`HierarchyId`-typed argument through `TypeSpecs.Node`. The XML doc of `TypeSpecs.Node`
(`Functions/TypeSpec.cs:77`) says "Only a path can supply one". In fact `null`, `coalesce` and `if`
all supply one:

- `level(coalesce(AltNode, Account.Node))` compiles to `COALESCE(…).GetLevel()`.
- `level(if(IsPosted, AltNode, null))` compiles to `CASE … END.GetLevel()`.
- `level(null)` compiles to `CAST(NULL AS hierarchyid).GetLevel()`.

All three run on the server. The behaviour is sound, and the spec's premise ("only a path can
supply a `HierarchyId`") is what is wrong. Still, the deliverable deviates from the letter of
"Anything else is QX3005", and PLAN §7.1 item 1 requires that under **Deviations**. It is only
under the implementer's "Open risks". The corpus pins the `COALESCE` form alone (`fn-level-computed`),
so nothing on the server covers the `CASE … END.GetLevel()` emission that Review 1 had to check by
hand.

Suggested fix: keep the behaviour and record it as a deviation in commit 3: the language's
`null`, `coalesce` and `if` produce `HierarchyId`, every such form is valid on the backend, and
the spec's premise is wrong. Correct the `TypeSpecs.Node` doc, and add an
`if(IsPosted, AltNode, Account.Node)` operand to the expression corpus so that the differential
runs the `CASE` form. Otherwise, refuse non-path operands as QX3005 to match the spec.

Seam note for spec 0012, which is not a finding against this checkpoint's code. Spec 0012 §5.4
compiles a keys-only twin and a display query for one statement, both under "batch ordinal `b`".
If both compile under the same `BatchOrdinal`, their prologues each declare `@qx{b}_v{n}` in one
batch (Msg 134) and their slots repeat the `@qx{b}_p{n}` names. The 0012 checkpoint must either
give the twin its own ordinal or de-duplicate. The engine's contract here (one ordinal, one
namespace) is clear and correct.
