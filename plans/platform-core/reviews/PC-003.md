# PC-003: Queryex host-composition basics: rename, zones, restrictions, level, Prologue/Body, paging slots, versioned leaves, undeclared columns

## Implementer notes

### What was built, and where

All engine changes are in `src/core/Tellma.Core.Queryex` (no new project, no new package).

- **§F.18 rename (done first).** `LanguageVersion` → `QueryexVersion` on `ValidationOptions`,
  `QueryCompilationOptions`, `DiscoveryOptions`, `BindingContext`, `BindKey`, and every caller in
  the engine, the shared harness, both test projects and the inspection tool;
  `Versioning/LanguageVersionTests.cs` → `Versioning/QueryexVersionTests.cs`. XML docs say
  "Queryex version". While renaming, fixed a latent L2 bug: `BindKey.Equals` never compared the
  version (only the hash did), so two keys differing only in version that collided on hash would
  have been equal.
- **§F.22 zones.** `Time/CldrTimeZones.cs` is now two embedded tables: `ZoneData` (current ids →
  Windows name, 418 ids under 138 Windows names) and `AliasData` (the 19 aliases). Current =
  tzdb 2026b `zone.tab` locations plus `UTC`; every other id (renamed/deprecated spellings,
  `Etc/GMT±n`, `Etc/UTC`, `GB`, …) left the table. `TryResolve` resolves an alias through its
  current id. New public `QueryexTimeZones.Ids` (ordinal) and `.Aliases`. Checked-in id list:
  `test/core/Tellma.Core.Queryex.Tests/Time/zone-tab-ids.txt` (embedded resource), tests in
  `Time/TimeZoneTableTests.cs`.
- **§F.1 restrictions.** `KeySetRestriction(Path, TableSource)` (form checked in the record's
  init accessors and constructor, so `with` cannot bypass it); `QuerySpec.Restrictions`.
  `Pipeline/HostStructure.cs` resolves paths against the schema (caller errors naming
  `Restrictions[i]`); `QueryClauses.LowerRestrictions` walks the shared join trie under location
  `Restrictions[i]` (new `QueryexClause.Restrictions`, so QX5006 names the restriction);
  `PlanKeySetRestriction` emits `(<col> IN (SELECT [Id] FROM <source>))`; `QueryClauses.Conjoin`
  makes each one a top-level conjunct after the filter.
- **§F.2 `level`.** One registry entry (`FunctionLibrary.Hierarchy`), `TypeSpecs.Node`, template
  `{0}.GetLevel()` with store type `smallint`, `Propagate(0)`. Interpreter counts path segments.
- **§F.3 Prologue/Body.** `StatementEmitter.Write` returns the two parts; `QueryCompiler` builds
  `Sql = Prologue + Body + ";\n"` from them. `CompiledQuery.Prologue`/`Body` are `init` props.
- **§F.4 paging slots.** `Lowerer.PagingSlot(value, "skip"|"take")` makes fixed-name slots outside
  the shared slot table (never merged with an equal literal), appended last; still counted toward
  `MaxParameters`. `QueryKey` holds Skip/Take presence only; `QueryexEngine.Restamped` replaces
  the trailing slots' `Value` on a hit.
- **§F.6 versioned leaves.** `FilterTree.Leaf(text, queryexVersion)` (ArgumentOutOfRangeException
  unless supported), `LeafNode.QueryexVersion`; `FilterBinder` and `Discoverer` bind a stamped leaf
  under its stamp; `QueryKey` renders each leaf's stamp.
- **§F.16 undeclared columns.** `QuerySpec.UndeclaredColumns`; `HostStructure.RequireUndeclaredColumns`
  (form, duplicate ignoring case, Aggregate); `PlanUndeclaredColumn` on the root alias, appended
  to the select list after ordering/tiebreakers are settled, columns `(n, name, QxString,
  Nullable, null, false)`.
- **§F.0 cache keys.** L3 gains restrictions (ordered), undeclared columns (ordered), paging
  presence, leaf stamps. L2 already keyed on the (now per-leaf) version.
- **Harness/fixture.** `LedgerFixture.UndeclaredColumns` (Invoice: `ExtrasJson`, `AuditJson`,
  both `nvarchar(max)`), DDL and inserts include them, `LedgerRow.Undeclared`; `KeySet` (in-memory
  membership + `DECLARE … TABLE` script); `InterpreterContext.KeySets`; `QueryCase.KeySets`;
  `ReferenceQuery` applies restrictions by walking the path itself and appends undeclared values;
  `QueryexProbe.CurrentZones`/`ResolveZone`; `ProbeCacheKeys.ShareQueryEntry`.
- **Integration fixture** creates its database `COLLATE Latin1_General_100_CI_AS` (WATCHLIST lead;
  hard-coded string, not the `DatabaseCollations` constant 0010-a1 owns — see risks).
- **Inspection tool.** "restrictions" (`path @table = k1, k2; …`) and "undeclared columns" inputs;
  when run, each table is declared as `nvarchar(4000)` text keys. README updated. Smoke-tested
  by hand against the running tool.
- **READMEs.** Queryex README gains the public types and an "Amendments" table (with the tzdb
  release); test/harness/tool READMEs updated. ARCHITECTURE.md needed no change (it already
  describes the zone value set and Part F; nothing it says contradicts this).

### Deviations (also in the commit message)

1. `KeySetRestriction.TableSource` is also refused above 128 characters (the backend's variable
   name limit); the spec gives only the character form.
2. A filter that lowers to constant false keeps the WHERE as `(1 = 0)` and drops the restrictions
   (and pruning drops their joins); one that lowers to constant true is omitted beside them.
3. Antarctica/Troll (a zone.tab location) has no entry: the embedded CLDR table never mapped it
   and no Windows name was invented. Every other zone.tab location is current (418 ids).
4. `BindKey.Equals` now compares the version (latent bug fix, see above).
5. Paging slots stay counted toward `MaxParameters` (as before); the spec is silent.
6. A restriction's path form is checked when the record is built (and on `with`); its resolution
   against the schema at `CompileQuery`, on every call, a cache hit included.
7. QX5006 pushed over by a restriction's joins carries location `Restrictions[i]` (new internal
   clause); the spec names no location for restrictions.
8. The checked-in zone.tab ids pin tzdb 2026b (the spec names no release); the README records it.
9. The Queryex integration fixture's database collation is a literal, not 0010-a1's constant.
10. The inspection tool declares restriction tables as `nvarchar(4000)` text keys when it runs.

### Open risks / what to examine hardest

- **Restamp on hit** (`QueryexEngine.Restamped`): relies on the paging slots being the last one or
  two parameters, skip before take. Check no path can put another slot after them, and that a hit
  for `Skip`-only vs `Take`-only cannot collide (key holds both presence flags).
- **`PlanKeySetRestriction` is three-valued.** Sound only as a top-level WHERE conjunct; check that
  nothing (now or in PC-007 `Via`/`Exists`) can wrap it in `NOT`. It is built only in
  `QueryClauses.LowerRestrictions`.
- **String keys and collation.** `<varchar CI_AS_SC column> IN (SELECT [Id] FROM @tvp)` raises
  Msg 468 if the host's list type has a different collation. The engine cannot fix this; spec 0012
  hosts need collated list types (0010-G `UseCollation`). The differential tests use int keys only.
- **`level` over computed operands** emits `COALESCE(…).GetLevel()`; verified accepted by SQL
  Server 2022 (`fn-level-computed`), not by spec text.
- **DatabaseCollations constant**: the Queryex fixture hard-codes the collation string because
  0010-a1 (parallel) owns the constant; whichever integrates second may want to switch to it.
- Undeclared column names are not checked against the declared columns (a host could list a
  declared column again); the spec does not ask for it.

### Seams for PC-007 / PC-010 / PC-012

- `QueryexClause` and `DiagnosticLocation` take new clauses cheaply (`Restrictions` is the model).
- `QueryKey.Render` is the one place new `FilterTree` node types (`ViaNode`, `ExistsNode`) must
  be rendered; `FilterBinder.Bind`/`Discoverer.ReadFilter` are the two switches to extend.
- `HostStructure` is where further host-structure caller errors belong (Via/Exists navigation
  names, omitted-parameter names).
- Restrictions are root-only by construction (lowered once, against `Lowerer.Root`).
