# PC-007: FilterTree.Via and FilterTree.Exists

## Implementer notes

### What was built, and where

All engine changes are in `src/core/Tellma.Core.Queryex` (no new project, no new package).

- **Public surface.** `FilterTree.Via(navigation, inner)` with `FilterTree.ViaNode` and
  `FilterTree.Exists(entity, navigation, inner)` with `FilterTree.ExistsNode` (`FilterTree.cs`).
  Construction refuses null arguments, an empty path or an empty/whitespace segment
  (`".A"`, `"A."`, `"A..B"`), empty names, and anything past `MaxDepth`; each node counts one level.
- **Caller errors** (`Pipeline/FilterStructure.cs`, called from `HostStructure.RequireFilters`):
  the whole tree is walked before the L3 lookup on every `CompileQuery` and `DiscoverQuery` call.
  It refuses a Via segment that is not a navigation of the current root, an unknown Exists
  entity, an Exists navigation that is missing or points at another entity than the current root
  (by descriptor identity), and either node anywhere in a `Having` tree (also without a schema in
  discovery). Messages name the node's location (`The Via at Filter.And[1] does not resolve: …`);
  `ParamName` is `spec`. Current root tracking: query root → Via target → Exists entity.
- **Binding** (`Pipeline/FilterBinder.cs`, rewritten as a small `TreeBinder` holding the shared
  state). Via binds `inner` with `context with { Root = target }`; Exists with
  `Root = entity`. New bound nodes `TypedVia` / `TypedExists` (`Binding/TypedFilterStructure.cs`,
  kinds added to `TypedExprKind`), NotNull in the nullity map, handled by `TypedEquivalence` and the
  nullity analyzer. Leaves inside bind/cache under the target root (the L2 key already holds the
  root), so a text is never served across roots.
- **Lowering** (`Lowering/Lowerer.Structure.cs`, plus `Lowerer.cs`/`Lowerer.Leaves.cs`).
  `_base` is the current root join node; `Walk` starts there, so a Via's criterion joins through
  the shared trie (one join with a select of the same path). `LowerVia` walks the path, lowers
  `inner` from the target, and when the target join is LEFT (absolute `JoinNode.IsInner`, as the
  spec words it) emits `(([Pn].[Key] IS NOT NULL) AND <inner>)`; inner `false` folds the node to
  false, inner `true` leaves the presence test alone (INNER path: the constant, and the join is
  pruned). `LowerExists` creates a `PlanSubquery` (own join trie rooted at the searched entity, own
  binding list, `_bindingsAllowed = true`), lowers `inner` into it, and emits `PlanExists` whose
  `Where` is `(([X].[FK] = <current root alias>.[Key]) AND <inner>)`, or the correlation alone for
  `And([])`; inner `false` folds to false and writes no subquery. Parameter slots and hoisted
  lookups stay the statement's.
- **Aliases and ceilings** (`Lowerer.Complete`). After the statement's own P-numbering, surviving
  subqueries (reached through `Reach`) are numbered `X1, X2, …` in creation order, which is the
  pre-order of the filter; each subquery's joins continue the P sequence and its live bindings
  continue the B sequence after the statement's. `MaxJoins` counts the statement's joins, then per
  subquery its source and its joins. `[C{n}]` calendar lookups do not exist yet (§F.11).
- **Emission** (`Emit/PlanEmitter.cs`, `StatementEmitter.cs`). Join and binding writing moved to
  `PlanEmitter.Join`/`Binding` (shared; the statement adds a line break after each). `PlanExists`
  writes `EXISTS (SELECT 1 FROM <Source> AS [X1] <joins> <bindings> WHERE <pred>)` on the WHERE
  line, joins and bindings space-separated.
- **Locations** (`Diagnostics/DiagnosticLocation.cs`).
  `Via(nav)` → `….Via[<nav as written>]`, `Exists(entity)` → `….Exists[<entity as written>]`.
  (After Review 1:) `FilterBinder` wraps every leaf occurrence in a per-compilation
  `TypedFilterLeaf` carrying its location, and `TypedVia`/`TypedExists` carry their criterion's
  location; `Lowerer.LowerPredicate` switches `_location` while lowering such a node, so
  QX5006/QX5007 raised at `Complete` name the leaf/Via/Exists occurrence. The Exists source's
  origin is the Exists criterion's location with an empty span. (Commit 1 used a node-identity side
  map, `FilterLocations`, removed by R1-1.)
- **L3 key** (`Caching/CacheKeys.cs`): `V<len:nav>(…)` and `E<len:entity><len:nav>(…)`.
- **Discovery** (`Pipeline/Discoverer.cs`): a `PathScope` (root, prefix, reports). Via resolves its
  target and prefixes reported `PathUse.Segments` with the navigation's segments as written;
  nested Vias concatenate. Exists binds its criterion (diagnostics, parameters, inference) but
  reports no `PathUse`, and nothing nested under it reports either. Without a schema, leaves inside
  are read syntactically as before.
- **Shared harness** (`test/shared/Tellma.Queryex.Testing`): the fixture's child table
  `InvoiceLine` (`[gl].[DocumentLines]`, key `LineId`, `Invoice` → Invoice NOT NULL, optional
  `Party` → Party, `Amount`, `Memo`, `CreatedById`) with seven rows (invoices 2 and 6 have none);
  the interpreter's `Rebased`/`Found` (`Semantics/Interpreter.Structure.cs`), written from the
  meaning (follow the navigations; scan the entity's rows); `ProbePlan` now reads children through
  the engine's `PlanWalk` and inspects subquery bindings; corpus `QueryCase.Sites` /
  `DiagnosticSite` pin code, location, span and arguments.
- **Inspection tool**: `via` (rebase the filter) and `exists` (`Entity Navigation: criterion; …`)
  inputs, README updated.

### Tests

- Unit (`Tellma.Core.Queryex.Tests`): 21 new goldens (`via-*`, `exists-*`), 7 new refusal corpus
  cases with pinned sites (`refuse-in-via`, `refuse-in-exists`, `refuse-joins-in-via`,
  `refuse-joins-in-exists`, `refuse-exists-source-over-ceiling`, `refuse-joins-in-composed-leaf`,
  `refuse-parameters-in-exists`); `Emit/FilterStructureTests` (construction refusals, depth, caller

  after folding, MaxJoins with nested sources, alias uniqueness and gap-free pre-order numbering over
  every compiled corpus statement, L3 key, cross-root cache isolation, names never reaching SQL);
  `Binding/DiscoveryTests` (Via prefixes incl. nested, Exists silence with parameters and
  diagnostics still reported); `Coverage/LocationCoverageTests` (every new location form pinned by a
  corpus case).
- Integration (`Tellma.Core.Queryex.IntegrationTests`): every new corpus case runs in the
  differential suite; `FilterStructureTests` asserts `Not(Via)` and `Not(Exists)` partition the
  invoices exactly (invoices with no customer / no lines in every negation) with hard-coded

- No existing golden changed (the update run rewrote every snapshot; `git status` showed only new
  files), which is the "tree without the new nodes compiles byte-identically" check.

### Deviations

1. **Lowering-time ceiling diagnostics inside a composed filter now name the leaf.** Before, a
   QX5006/QX5007 caused by a leaf at `Filter.And[1]` was reported at `Filter` with a span indexing
   that leaf's text (0008 §2.3 requires the tree location). Needed anyway so ceilings inside a Via
   or an Exists carry `…Via[…]`/`…Exists[…]`. Single-leaf filters are unchanged. Applies to
   `Having` leaves too.
2. **Structural parentheses** in the emitted guard and subquery predicate
   (`(([P1].[AgentId] IS NOT NULL) AND (…))`, `WHERE (([X1].[FK] = [T].[Key]) AND (…))`), per the
   emitter's existing convention; the spec's SQL blocks are shortened layout (§F.0).
3. **The fixture maps "lines with no center"** to invoices with no customer: in `LedgerFixture`
   the centre is mandatory and the customer optional, which is the LEFT case the test is about.

### Open risks / what to examine hardest

- `Lowerer.Complete` numbering: X in creation order = pre-order of the filter (subquery allocated
  before its criterion is lowered); P and B continue across subqueries. The corpus-wide alias test
  checks uniqueness and order; `exists-aliases` and `exists-nested` are the shapes to read.
- Soundness of reading the criterion's target-relative nullity behind the guard, especially nested
  Vias (the inner Via re-guards on its own LEFT target even when redundant) and a Via inside an
  Exists (IsInner is relative to the subquery root, which counts as inner).
- (Fixed by R1-1.) Locations are per occurrence, so one cached leaf tree under two rebases or two
  semi-joins is reported at the occurrence that created the offending join.
- Pre-validation runs before the cache on every call; `FilterBinder` re-resolves (it throws only
  for callers that skip validation, such as the reference interpreter's binding).
- Seam for §F.8 (PC-010): a `Via` or `Exists` node is one atom of the omitted-parameter folder;
  `FilterStructure` already walks the tree with the current root, and the folder sits before
  `FilterBinder`.
- Seam for §F.11 (`'uq'` month table): its `[C{n}]` lookups must be per subquery (in
  `PlanSubquery`), numbered after the statement's like P and B. Seam for §F.13/§F.21: discovery's
  `PathScope` already carries the Via prefix and the Exists silence those items need.
- Lead for the orchestrator: §F.21 says Via and Exists nodes "produce no conjunct; their paths
  still appear in `Paths`", while §F.12 says discovery reports no `PathUse` from inside an Exists.
  Built per §F.12; §F.21's implementer should read the sentence as applying to Via only.

**R1-1 (minor): the first-wins rule in `FilterLocations` names the wrong input when one leaf text
sits under two rebases or two semi-joins.**
`src/core/Tellma.Core.Queryex/Diagnostics/FilterLocations.cs:39` (`TryAdd`), read by
`src/core/Tellma.Core.Queryex/Lowering/Lowerer.cs:216-228` (`LowerPredicate`).
A leaf's bound tree is cached on its text and root, so the same `TypedExpr` instance appears at
every place the same text sits under the same current root. That is harmless at the query root,
where the second occurrence creates nothing new. Under two `Via`s that reach the same entity, or
two `Exists` over the same entity, the second occurrence lowers onto a *different* join tree and
creates its own joins, but it is still labelled with the first occurrence's location. The class
remark's premise does not hold across rebases or subqueries. It says the first location "is also
where every join and parameter it shares with a later occurrence was created".
Reproduced: Root `Invoice`, `MaxJoins = 3`,
`And([Via("Customer", Leaf("Region.Name = 'N'")), Via("Customer.Manager", Leaf("Region.Name = 'N'"))])`
reports `QX5006 @ Filter.And[0].Via[Customer]` (span 0,11). The fourth join, the manager's region,
was created by `And[1]`. With `'M'` in the second text the location is correctly
`Filter.And[1].Via[Customer.Manager]`. Likewise
`Or([Exists("InvoiceLine","Invoice",Leaf("Party.Name = 'a'")), Exists(…same…)])` with
`MaxJoins = 3` reports `Filter.Or[0].Exists[InvoiceLine]`, although the over-ceiling join belongs to
`Or[1]`'s subquery. Repeated texts under several semi-joins are the normal shape of host-composed
access criteria (e.g. `UserId = me()` under several `Exists`), so a host would point the user at
the wrong criterion. 0008 §2.3 requires the location to attribute the failure to the specific
criterion.
Fix: attribute locations by occurrence, not by node identity. For example, have `TreeBinder.BindLeaf`
wrap each leaf's root in a per-compilation marker node that carries its location, which lowering
unwraps (as `TypedVia`/`TypedExists` already are per compilation). Alternatively, have
`LowerVia`/`LowerExists`/`LowerLogical` pass the child's location down from a structure built in
pre-order alongside the bound tree. Add a refusal corpus case with a repeated text pinned at
`Filter.And[1].Via[…]` (and one for `Exists`).

**R1-2 (minor): the `[C{n}]` deliverable is left out without a Deviations line.**
The PC-007 entry in `plans/platform-core/CHECKPOINTS.md` lists "aliases
[X{n}]/[P{n}]/[B{n}]/[C{n}] continuing in pre-order" and a subquery with its own "lookups". Calendar
lookups do not exist before §F.11, so nothing can be numbered yet. The implementer notes say so, but
the commit message's Deviations does not, which PLAN.md §7.1 item 1 requires. The §F.11 checkpoint
(`0010-f5`) already carries "Exists subqueries carry their own lookups", so nothing is lost.
Fix: add a fourth Deviation at integration, naming the §F.11 checkpoint as the owner of `[C{n}]`
per subquery, numbered after the statement's, as the implementer notes describe.

**Rulings requested**

- *Deviations 1–3:* all three are justified. (1) brings composed-filter ceiling locations in line
  with 0008 §2.3, which the old `Filter`-plus-leaf-span pairing contradicted. No golden or corpus
  entry pinned the old form, and it is a precondition for `…Via[…]`/`…Exists[…]` ceiling locations.
  (2) is layout: §F.0 says the SQL blocks are shortened, and the structural parentheses are the
  emitter's existing convention. (3) is forced by the fixture, whose centre is mandatory. The
  customer is the optional navigation, which is the LEFT case the differential exists for.
- *§F.12 against §F.21:* Exists nodes' paths should **not** appear in `Paths`. §F.12's Discovery
  bullet, §F.13 ("inside `Exists` nothing is reported") and §F.7's contract that
  `PathUse.Segments` stay root-relative all agree. A path inside a semi-join resolves from the
  searched entity, and no prefix makes it root-relative. §F.21's "their paths still appear in
  `Paths`" is the outlier. Read it as "skipping them for conjuncts does not remove what discovery
  already reports": Via paths, prefixed, and nothing from inside Exists. The implementation is
  correct as built. The orchestrator should record this so the §F.21 checkpoint (`0010-f4`) does
  not add Exists paths.

**Checked and found sound (no finding)**

- Via join kind: `JoinNode.IsInner` is absolute (propagated from the scope root, and a subquery's
  root counts as INNER), so a Via inside a LEFT Via re-guards, and a Via inside an Exists is INNER
  only relative to rows that exist. The guard is a conjunct with the key test and never turns a
  LEFT join INNER. Folding: inner `false` gives false; inner `true` gives the key test (LEFT) or
  true with the join pruned (INNER). All of these are correct under 3VL, including under `not`.
  Probes: `Not(Via("Customer", Gender = 'F'))`, `Not(Via("Invoice.Customer", Exists(…)))` in an
  aggregate, and `Not(Via("Invoice", IsApproved))` (nullable bool, INNER path).
- Exists: the correlation `[X].[FK] = <current root alias>.[Key]` with an absent FK matches
  nothing, `NOT EXISTS` is two-valued, and the correlation keeps the outer LEFT join alive through
  `Reach`. Hoisted lookups stay in the statement prologue (probe: `descendantOf` inside an Exists).
  The restriction stays a top-level conjunct beside a subquery (probe), as §F.1 "Scope" requires.
- Aliases: X numbered in creation order (pre-order), then P and B continuing after the statement's.
  No collision across nested subqueries, restrictions or composed trees. The corpus-wide
  declaration-order test would catch a duplicate.
- L3 key: Via/Exists names are length-prefixed fields, inner parenthesized, all declarations in the
  key. Case-variant names only fragment the cache and never produce a false hit. Leaves under a
  rebase bind and cache under the target root (L2 key holds the root).
- Discovery: Via prefixes the as-written segments, Exists reports nothing, nested nodes inherit the
  silence, and parameters are still inferred inside Exists (probe: `@a` → `QxNumeric`).
- Security: host names resolve to descriptors and never reach SQL (test pins it). Restrictions are
  root-only by spec (§F.1, §F.12), and a semi-join only filters root rows and never projects
  subquery rows. User text cannot create either node, and tenant isolation is unchanged (schema
  identity in every key).
- AGENTS.md / PLAN.md §7.1: XML docs present, no spec/PC references in XML docs, messages or test
  names, READMEs updated, and the suites run are listed.
