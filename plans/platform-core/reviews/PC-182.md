# PC-182: Report stack and the generic sharing model

## Implementer notes

### What was built

- **The generic sharing model** (`src/core/Tellma.Core.Abstractions/Sharing`, `src/core/Tellma.Core/Sharing`).
  - Contracts: `IShareable` (owner and lineage), `IShareRow` (a grant to a user, a role or
    everyone), `ShareAccess`, the action arguments (`ShareArguments`, `PublishArguments`,
    `TransferArguments` with `UserGrant`/`RoleGrant`), the shares extra's records (`ShareList`,
    `ShareGrantView`), `SharingOptions`, `ShareableNames` and `SharingValidationCodes`.
  - `ShareableService<TEntity, TShare>` is the base service. A new row takes the caller as owner,
    or no one in a system scope. An update keeps the stored owner. A standard row (no owner) is
    read-only outside a system scope (`Sharing.StandardReadOnly`), except to share and publish,
    and `RefuseOnRecord` reports the same refusal per ability in the permissions extra. A
    lineage (`BasedOnId`) must be visible.
  - `ShareCommands<TEntity, TShare>` (`IShareCommands<TEntity>`) does share, publish and transfer:
    - It validates the grantees: active individuals, active roles, never the owner, and the
      200/50 caps.
    - It writes the grants beside the row with one DELETE and one UPDATE + INSERT…SELECT over the
      `ShareGrantList` table type, never stamping the row.
    - It raises the `Replace` notice per new user grantee (dedup key `<entity>:<id>`) and
      withdraws it with the grant.
    - Transfer assigns `OwnerId` through `ActionContext.Update` and drops the new owner's own grant.
  - The declaration `contribution.Shareable<TEntity, TShare>(notificationType)` is realised by
    `ShareableContributionRealizer`. It maps the share table through `ShareRowConfiguration`:
    unique user, role and Everyone indexes, the target and Everyone-is-View checks, and
    `ON DELETE CASCADE` to the row. It also registers the bespoke access criteria
    (`ShareableAccessCriteria`, reason `share`), the `shared-with-me` named filter and the
    `shares` extra (`SharesContributor`, through the new `DetailsPlan.AddComputedExtra`).
  - `core.shareables` (`ShareablesCheck`) refuses a shareable when:
    - its owner is not server-owned;
    - its share entity does not reference it exactly once;
    - its share entity is a stack or a child collection;
    - it has no stack, or its stack's service does not derive from `ShareableService`.
- **The reports' stack** (`src/core/Tellma.Core.Abstractions/Reports`, `src/core/Tellma.Core/Reports`).
  - The data model: `Report`, `ReportShare`, `ReportKind`, the strict `ReportDocument` records,
    `ReportSeed`, `IDashboardReadThrough` (null implementation by default), `ReportsOptions` and
    `ReportValidationCodes`.
  - `CoreFeature` contributes `Report` with `ReportService` as a shareable over `ReportShare`.
  - `ReportService` covers:
    - default titles per configured slot in each slot's tenant language, derived again under a
      changed root or kind while a slot still holds the old default;
    - strict binding of `DefinitionJson`, with every failure reported as `Report.UnknownMember`
      at an RFC 6901 pointer;
    - the `QueryexVersion` kept on update unless an expression changed;
    - feature-name code prefixes reserved outside a system scope (`Report.CodeReserved`);
    - deletes refused while dashboards show the report (`Report.InUse`).
  - Migrations regenerated: the Testing.Entities fixture, the core migrator test distribution
    and the Acme tenant migration.
- **Tests.**
  - Unit, `test/core/Tellma.Core.Tests`:
    - `Sharing/ShareableAccessCriteriaTests`: the criteria trees and the shared-with-me tree.
    - `Sharing/ShareableServiceTests`: owner stamping, standard-row refusals per hook and ability,
      lineage, delegation.
    - `Sharing/ShareablesCheckTests`: every check and realiser refusal.
    - `Reports/ReportServiceTests`: default-title vectors in English and Arabic, binding pointers,
      versions, reserved codes, in-use arguments.
  - Integration, `test/core/Tellma.Core.IntegrationTests/Sharing/ReportSharingTests` (16 cases after review 1,
    see its README row).
  - Web, `test/core/Tellma.Core.AspNetCore.IntegrationTests/Stacks/ReportOperationTests`:
    query, get, get-by-ids, save, share, publish, transfer, deactivate, activate and delete end
    to end on Acme's migrated tenant. The routes are pinned in `ProjectedRouteTests`, and
    `web.json`/`contracts.json` are regenerated.
  - Goldens and expectations that now include `core.Report`, `core.ReportShares` and
    `ShareGrantList` were updated:
    - the route and stack-descriptor goldens;
    - the client entity-model fixtures and `tellma-entities.d.ts.txt`, checked by
      `tools/tests/entity-model.spec.mts`;
    - the securables, model, leaf and notification-catalogue expectations.

### Deviations

1. **`OwnerId` is `[ServerOwned]`, not `[Derived]`.** Spec 0033 has it `[Derived]`, but spec
   0012 §9.1 lets a column update assign only editable or server-owned columns, so transfer's
   `ActionContext.Update` was refused at run time. Server ownership is also what §5.1 describes:
   an update keeps the stored owner, and the hook-set value is written on insert. The new
   `core.shareables` rule enforces it.
2. **Share rows are deleted by an `ON DELETE CASCADE` foreign key**, not a persist participant,
   because a participant runs after the row's delete.
3. **The share table has no stack**, so delete-by-query is not among the share operations (the
   registry refuses it alongside judged deletes).
4. **No `MERGE`.** The grant write is UPDATE + INSERT…SELECT `NEXT VALUE FOR`, then
   `IF EXISTS … THROW 50422` for the caps, because the `IDataBatch.Sql` analyzer refuses `MERGE`.
5. *(Retired in review 1: the shares extra reads its grants in one statement, the admission in
   its filter.)*
6. **New platform API: `DetailsPlan.AddComputedExtra<TRow, TValue>`.**
7. **`SharingOptions` uses get/set properties** (options binding), not init.
8. **The notification category `reports` is used for every shareable.**
9. **Every document binding failure is `Report.UnknownMember`.** `ChartTypeUnsupported` and
   `DisplayIncompatible` are left to the renderers' milestone, as is the 256 KB size rule.
10. **Duplicate grantees get `ValidationCodes.Unique`**, and `TooManyGrants` is reported at
    `Arguments.Set`.
11. **`Report.InUse` carries an extra `named` argument** (the ICU plural needs it).
12. **`Access_Reason_share` is added as a pending resource key.**
13. **Default titles with no tenant settings use the current culture and one slot.**
14. **The commands load only the name twins the tenant configures**, since the query schema does
    not declare an unconfigured twin.
15. **Under filtered decisions, the shares extra lists only the admitted rows that hold grants**
    (review 1). One statement filtered by the admission cannot tell an admitted row without grants
    from one the caller may not share, so neither gets an entry; under an unrestricted decision
    every visible row gets one. The share dialog reads a missing entry as no grants, and gates its
    abilities on the permissions extra (spec 0034 §10.4).
16. **A delete withdraws its rows' share notices with one set-based statement** (review 1), through
    the new internal `Notifier.WithdrawEach(batch, keyPrefix, ids)`. A delete's persist context
    carries no rows, only the batch table of deleted ids, and spec 0021's `WithdrawRequest` names
    one literal key, so a per-row request cannot be built. The statement spells each key from the
    prefix and an id, deletes in the delete's transaction, and announces the changed inboxes after
    commit like any withdrawal.
17. **Reports serve no `delete-by-query`.** Spec 0033 §2.1's `[Stack(Operations = …)]` omits it,
    while §2.2's route table and §5.6 list it; the code follows §2.1, and the spec should be made
    consistent (review 1, R1-6).

### Open risks

- Two concurrent grants of one user can each raise a notice. This is harmless under `Replace`.
- `NEXT VALUE FOR` inside INSERT…SELECT with NOT EXISTS is exercised only by the integration
  suite.

### What reviewers should examine hardest

- `ShareCommands` write text: the cap THROW, `NEXT VALUE FOR` per inserted row, and concurrency
  between two publishers of one Everyone grant (the unique index is the backstop).
- The OwnerId ownership switch, and that no save path can now set an owner.
- `ShareableAccessCriteria` against spec 0033 §5.2 (Edit saves, never deletes, activates or shares).

## Review 1

### Findings

Summary: 0 blocking, 3 major, 4 minor.

**Major**

- **R1-1 (major, defect, not a deviation). Deleting a shareable row leaves its share notices
  standing.** Spec 0033 §7 says "removing the grant withdraws it". Spec 0033 §5.6 says a delete
  "removes the report for everyone, shares included", and §5.6 puts that removal in a persist
  participant of `ShareableService`. Spec 0021 §2.3 makes the withdrawal trigger the raiser's job.
  A delete removes every grant, so it must withdraw every grant's notice. Code:
  `src/core/Tellma.Core.Abstractions/Sharing/ShareableService.cs:281-287` handles delete, but no
  `ContributeAsync` withdraws anything. The `ON DELETE CASCADE` in `ShareRowConfiguration.cs:47-50`
  removes the grants without telling the notifier.
  - Failure: the owner shares report 42 with Omar, then deletes it. Omar's inbox keeps "X shared
    Y with you", which opens `/{t}/reports/42` and gets a 404. The implementer lists this under
    "Open risks", but the spec requires the withdrawal, so it is a defect.
  - The cascade deviation (deviation 2) is fine for the rows. It does not excuse the notices: a
    withdrawal is keyed by `DedupKey`, not by the grant row, so it can be appended whatever order
    the cascade runs in.
  - Fix: override `ContributeAsync` in `ShareableService`. For a `DeletePersistContext`, append
    `context.Withdraw(new WithdrawRequest("<resource>:<id>"))` for each deleted row, with
    `RecipientIds` null so every recipient's notice goes. This covers `delete` and any later
    `delete-by-query`. One option is to expose the key or a `WithdrawAll(PersistContext)` through
    `IShareCommands`, so `ShareableShape.DedupKey` stays the only spelling. In
    `ReportSharingTests.A_share_never_stamps_its_row_a_transfer_does_and_a_delete_removes_the_rows_grants`
    (line 251), assert that the grantee's `core.report.shared` row is gone after the delete.

- **R1-2 (major, privacy). The `shares` extra leaks other grantees through `Related` for rows the
  caller may not share.** In `src/core/Tellma.Core/Sharing/SharesContributor.cs:98-109`, the
  grants read is limited only by `plan.IdsSource`, which holds every visible row. The admission
  filter is applied afterwards in C#, in `Lists` at lines 127-130. But
  `DetailsComposition.Related` (`src/core/Tellma.Core/Crud/Details/DetailsComposition.cs`, the new
  `_rowReads` loop) materialises the related columns of every row that read returns:
  `User.*`, `Role.*` and `SharedBy.*`.
  - Failure: Bea holds an `Edit` grant on report 42 but is not its owner. She calls
    `reports/get` with `include=shares`. `extras.shares` is `[]`, but `related` still carries
    the `core.User` row of the other grantee, Ada, and the `core.Role` row of the role grant.
    Neither is referenced by the report row itself. Spec 0033 §5.2 says readers of a report "never see who else holds it", and that other
    ids "get no entry". The test at `ReportSharingTests.cs:355-359` checks only the extra's length,
    so it misses this.
  - Fix: when no admitting decision is `Unrestricted`, put the admission into the grants read
    itself, with `Filter = Via(<row navigation>, Or(<Share filter>, <Publish filter>))` on the
    share-rooted query. Then drop the separate key read. That is one statement, as §5.2 says, and
    it retires deviation 5. Extend the Bea block to assert that `read.Related` holds no
    `core.Role` and no user other than those the report row itself references (owner, creator,
    modifier).

- **R1-3 (major, test adequacy). The grant caps and the duplicate-grantee rules have no test.**
  Spec 0033 §5.4 caps a row at 200 user grants and 50 role grants (`Sharing.TooManyGrants`). Three
  pieces of code enforce caps or duplicates, and no test would fail if any of them broke:
  - the C# cap checks, `ShareCommands.cs:146-155` and `215-224`;
  - the SQL backstop, `ShareCommands.cs:436-441` (`IF EXISTS … THROW 50422, N'Sharing.TooManyGrants'`);
  - `CheckGrantees` (`ShareCommands.cs:290-321`): `Required` for a hole, `Unique` for a grantee set
    twice or both set and removed.

  The implementer names the THROW and `NEXT VALUE FOR` per row as the hardest things to review.
  The only test of a multi-row insert is two user grants.
  - Fix: add integration cases to `ReportSharingTests`:
    - 201 user grants are refused at `Arguments.Set` with `TooManyGrants` (`kind = user`). Exactly
      200 succeed, with distinct ids from the sequence.
    - 51 role grants are refused (`kind = role`).
    - A grantee set twice, and a grantee both set and removed, are refused with `Unique` at the
      documented paths.
    - For the backstop, seed 200 user grants directly with SQL beside a report, then compose
      `Merge` through a test seam, or a second target, so the C# check passes and the batch
      throws. Assert that the 50422 surfaces as a 422 `ValidationException` and that nothing was
      written.

**Minor**

- **R1-4 (minor, test adequacy). The share notice's arguments, and the name-twin fix behind them,
  are never asserted.** Spec 0033 §7 requires `title = LocalizedText.Names(row, "Title")` and
  `actorName = LocalizedText.Names(sharer)`. `ShareCommands.cs:459-460` builds both, and
  `UsersOf` (lines 493-502) picks the name twins from the tenant's shape (deviation 14).
  `ReportSharingTests.A_new_user_grant_notifies…` (line 365) checks the recipient, actor, target and
  count, but never `ArgumentsJson`.
  - Failure: a regression could ship unnoticed. Examples: `Title` falls back to the id, because
    the action's target load lacked the title. Or `actorName` becomes the bare user id, because
    the sharer's row did not load.
  - Fix: assert `ArgumentsJson` = `{"title":["Sales",null,null],"actorName":["Owner eleven",null,null]}`
    on the ConnectDatabase tenant, which has one language. Assert the same on Acme in
    `ReportOperationTests` after its `reports/share` call, with the second slot filled if Acme is
    bilingual. Together these pin both branches of `UsersOf`.

- **R1-5 (minor, spec conformance). `core.ReportShare` is in the client metadata.** Spec 0033
  §2.1 says `ReportShare` "has no route, no child query surface and no client metadata". The
  regenerated server output includes it as a full entity:
  - `client/projects/core/tellma-core-testing/fixtures/entity-model/entities-chunk.json`, around
    line 569 of the added block;
  - `CoreReportShare` and its path shape in `client/tools/tests/fixtures/entity-model/tellma-entities.d.ts.txt`.

  This is not listed as a deviation.
  - Fix: leave a shareable's share entity out of the Entities chunk and the declarations. The
    realiser already knows the pair (`context.Record.Shareables`), so the chunk writer can skip
    those types. Alternatively, record a deviation and flag §2.1.

- **R1-6 (minor, spec misalignment not recorded). Reports serve no `delete-by-query`.** Spec 0033
  §2.2's route table lists `delete, delete-by-query`, and §5.6 says the shares go "for `delete`
  and `delete-by-query` alike". But §2.1's own `[Stack(Operations = …)]` omits `DeleteByQuery`.
  The code follows §2.1: `Report.cs:36`, with the remark at lines 27-29. The routes golden
  (`fixture-routes.txt:60-69`) has no `reports/delete-by-query`.
  - The choice is defensible, but the commit records it nowhere. Deviation 3 is about the share
    table, not the reports stack.
  - Fix: add a deviation line that names the §2.1 vs §2.2/§5.6 contradiction, so the spec can be
    corrected. If `DeleteByQuery` is added instead, `Sharing.StandardReadOnly`, `Report.InUse` and
    R1-1's withdrawal must also run on that path, with a test.

- **R1-7 (minor, judged as asked). The notification category is hard-coded to `reports` for every
  shareable.** See `ShareableContributionRealizer.cs:30-32,106`. For now this is acceptable:
  - Spec 0033 §5.1's signature, `Shareable<TEntity, TShare>(string notificationType)`, carries no
    category.
  - Both catalogued shareables, `core.report.shared` and `core.dashboard.shared` (spec 0021 §2.3),
    are in `reports`.

  But §1 and §5 present the model as open to "a pack's or a distribution's own entity". An Acme
  `acme.contract.shared` would then appear under "Reports" in My settings' Notifications section.
  - Fix: give `Shareable<,>()` an optional `category = "reports"` parameter, or an overload that
    takes a `NotificationTypeDescriptor`. Record the extension as a deviation and flag §5.1, so the
    category is set per declaration before a second module uses it.

**Judged and accepted (no finding)**

- **Deviation 1: `OwnerId` `[ServerOwned]` instead of `[Derived]`.** Server ownership is
  equivalent to what spec 0033 §5.1 asks for, and stricter.
  - Insert: `SaveRun.Normalize` resets server-owned members before the hook
    (`src/core/Tellma.Core/Crud/Save/SaveRun.cs:343-344`). `PreprocessAsync` then stamps the caller,
    or null in a system scope, and the insert writes that in-memory value.
  - Update: the column is never in a `SET` list, and the before image is restored after RT1
    (`SaveRun.Checks.cs:324-330`), so neither the payload nor a hook can change it.
  - `[Derived]` would have been weaker on update: every `SET` list writes it, so a hook that forgot
    to copy the before image would null the owner.
  - Transfer: spec 0012 §9.1 lets a column update assign `Editable` or `ServerOwned` columns only
    (around line 1669), so `[Derived]` was unworkable.
  - Enforcement: `ShareablesCheck` refuses a shareable whose `OwnerId` is not server-owned, and
    `ShareablesCheckTests.A_shareable_whose_owner_is_not_server_owned_is_refused` covers it.
  - The spec text (§2.1, §5.1) should be corrected. The implementer should report that
    misalignment.
- **Deviation 2 (cascade) and deviation 4 (no MERGE)** are justified. PC-F62's `ForeignKeyActions`
  declares the cascade's write. TELLMA0003 refuses `MERGE`.
- **Viewer scoping.** The criteria (`ShareableAccessCriteria.cs:40-54`) match the §5.3 trees
  exactly:
  - `Edit` grants `Save` only; `Delete`, `Activate` and `Share` are owner-only; no criterion
    exists for `Publish` or `Transfer`.
  - Grants touch only `core.Report` rows. No data securable is widened, and a run's data checks
    belong to a later checkpoint (§8.2).
  - The grantee and owner loads use the unfiltered keyed loader (`IContextLoader` remarks), so a
    sharer without `core.User × Read` still validates correctly.
- **The user-select fix (deviation 14).** It is correct for all three `MultilingualShape` values,
  and `LocalizedText.Names` reads the unloaded twins as null. The ConnectDatabase tenant (one
  language) runs it implicitly. R1-4 asks for an explicit assertion.
- **`ProjectedRouteTests`** now holds all ten `reports/*` routes. `ReportOperationTests` drives
  each of them on Acme.
- **Regenerated migrations.** Reviewer 1 ran `Tellma.Distro.Acme.Web.Tests` with the filter
  `TenantMigrationTests|CompositionTests`: 7/7 passed. The pc/PC-182 CI run (45052301149) was
  `skipped`, as expected for a non-integrate commit.
- **AGENTS.md / PLAN §7.1 item 5.** Added XML docs, error messages and test names cite no spec,
  `§`, `docs/` or PC id.

### Responses

- R1-1: fixed in the "PC-182: review 1 fixes" commit (child of 2bb25b2c). `ShareableService`
  overrides `ContributeAsync` and, on a `DeletePersistContext`, calls the new
  `IShareCommands.WithdrawAll`. The suggested per-row `WithdrawRequest` could not work:
  `DeletePersistContext.Entities` is empty for every delete (by ids, by query, with descendants),
  and the ids exist only as the batch's deleted-ids table. So `WithdrawAll` appends one statement
  through the new internal `Notifier.WithdrawEach(batch, "core.Report:", AffectedIds)`, which
  deletes every row whose key is the prefix plus a deleted id, in the delete's transaction, and
  announces the changed inboxes after commit (deviation 16). `ShareableShape.DedupKeyPrefix` keeps
  the one spelling. The delete test now asserts that the remaining grantee's notice is there before
  the delete and gone after it.
- R1-2: fixed in the same commit. When no admitting decision is unrestricted, `SharesContributor`
  filters the grants read itself by `Via(<row navigation>, <Share filter> or <Publish filter>)`,
  so the related users and roles come only from grants of rows the caller may share; the separate
  key read is gone and deviation 5 is retired. A consequence is recorded as deviation 15. The Bea
  block now asserts that `related` names neither Ada nor any role, and the owner's block that
  `related` holds Bea, Ada and the role.
- R1-3: fixed in the same commit. New integration cases: 201 user grants refused at
  `Arguments.Set` with `TooManyGrants` (`kind = user`, `max = 200`) and nothing written, exactly 200
  admitted, and one more on top of the stored 200 refused; 51 role grants refused (`kind = role`,
  `max = 50`) and 50 admitted. The backstop is exercised without a test seam: 199 grants are
  stored, two shares of two different new grantees (apart in the key order) are started while a
  side transaction holds the share table, so both pass the C# check, and on release exactly one
  commits while the other surfaces the 50422 as a `ValidationException` with `TooManyGrants`,
  leaving 200 grants. `CheckGrantees` is pinned for shares and publishes: a hole (`Set[i]`,
  `Required`), a grantee set twice (`Set[i].UserId`/`RoleId`, `Unique`), a grantee both set and
  removed and one removed twice (`Remove[i]`, `Unique`).
- R1-4: fixed in the same commit. The notice test on the one-language tenant asserts `title` =
  `["Sales",null,null]` and `actorName` = `["Owner eleven",null,null]`. A new case on the second
  tenant, made bilingual (Arabic second) on an instance that offers Arabic, saves a report titled
  in both languages and asserts `["Sales","مبيعات",null]` and the sharer's two names, which pins
  `UsersOf`'s two-language select. Acme's `ReportOperationTests` was not extended: the two tenants
  of the ConnectDatabase suite cover both branches.
- R1-5: fixed in the same commit. §2.1 gives `ReportShare` no client metadata and nothing on the
  client reads it (the dialog reads the `shares` extra), so `ClientEntityModel` leaves every
  shareable's share entity out (`ShareEntityTypes`, registered by the sharing composition). The
  Entities chunk, `core-entities.json` and `tellma-entities.d.ts.txt` were regenerated without
  `core.ReportShare`.
- R1-6: no code change, per D-227. The §2.1 vs §2.2/§5.6 contradiction on `delete-by-query` is
  recorded in the commit body and as deviation 17. `WithdrawAll` is set-based over the deleted
  ids, so it would also cover a later `delete-by-query`.
- R1-7: no code change, per D-227. The `reports` category stays (deviation 8).
