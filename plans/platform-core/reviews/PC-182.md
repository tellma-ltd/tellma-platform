# PC-182: Report stack and the generic sharing model

## Implementer notes

### What was built

- **The generic sharing model** (`src/core/Tellma.Core.Abstractions/Sharing`, `src/core/Tellma.Core/Sharing`).
  - Contracts: `IShareable` (owner and lineage), `IShareRow` (a grant to a user, a role or
    everyone), `ShareAccess`, the action arguments (`ShareArguments`, `PublishArguments`,
    `TransferArguments` with `UserGrant`/`RoleGrant`), the shares extra's records (`ShareList`,
    `ShareGrantView`), `SharingOptions`, `ShareableNames` and `SharingValidationCodes`.
  - `ShareableService<TEntity, TShare>` is the base service. A new row takes the caller as owner,
    or no one in a system scope. An update keeps the stored owner. A standard row (no owner) is
    read-only outside a system scope (`Sharing.StandardReadOnly`), except to share and publish,
    and `RefuseOnRecord` reports the same refusal per ability in the permissions extra. A
    lineage (`BasedOnId`) must be visible.
  - `ShareCommands<TEntity, TShare>` (`IShareCommands<TEntity>`) does share, publish and transfer:
    - It validates the grantees: active individuals, active roles, never the owner, and the
      200/50 caps.
    - It writes the grants beside the row with one DELETE and one UPDATE + INSERT…SELECT over the
      `ShareGrantList` table type, never stamping the row.
    - It raises the `Replace` notice per new user grantee (dedup key `<entity>:<id>`) and
      withdraws it with the grant.
    - Transfer assigns `OwnerId` through `ActionContext.Update` and drops the new owner's own grant.
  - The declaration `contribution.Shareable<TEntity, TShare>(notificationType)` is realised by
    `ShareableContributionRealizer`. It maps the share table through `ShareRowConfiguration`:
    unique user, role and Everyone indexes, the target and Everyone-is-View checks, and
    `ON DELETE CASCADE` to the row. It also registers the bespoke access criteria
    (`ShareableAccessCriteria`, reason `share`), the `shared-with-me` named filter and the
    `shares` extra (`SharesContributor`, through the new `DetailsPlan.AddComputedExtra`).
  - `core.shareables` (`ShareablesCheck`) refuses a shareable when:
    - its owner is not server-owned;
    - its share entity does not reference it exactly once;
    - its share entity is a stack or a child collection;
    - it has no stack, or its stack's service does not derive from `ShareableService`.
- **The reports' stack** (`src/core/Tellma.Core.Abstractions/Reports`, `src/core/Tellma.Core/Reports`).
  - The data model: `Report`, `ReportShare`, `ReportKind`, the strict `ReportDocument` records,
    `ReportSeed`, `IDashboardReadThrough` (null implementation by default), `ReportsOptions` and
    `ReportValidationCodes`.
  - `CoreFeature` contributes `Report` with `ReportService` as a shareable over `ReportShare`.
  - `ReportService` covers:
    - default titles per configured slot in each slot's tenant language, derived again under a
      changed root or kind while a slot still holds the old default;
    - strict binding of `DefinitionJson`, with every failure reported as `Report.UnknownMember`
      at an RFC 6901 pointer;
    - the `QueryexVersion` kept on update unless an expression changed;
    - feature-name code prefixes reserved outside a system scope (`Report.CodeReserved`);
    - deletes refused while dashboards show the report (`Report.InUse`).
  - Migrations regenerated: the Testing.Entities fixture, the core migrator test distribution
    and the Acme tenant migration.
- **Tests.**
  - Unit, `test/core/Tellma.Core.Tests`:
    - `Sharing/ShareableAccessCriteriaTests`: the criteria trees and the shared-with-me tree.
    - `Sharing/ShareableServiceTests`: owner stamping, standard-row refusals per hook and ability,
      lineage, delegation.
    - `Sharing/ShareablesCheckTests`: every check and realiser refusal.
    - `Reports/ReportServiceTests`: default-title vectors in English and Arabic, binding pointers,
      versions, reserved codes, in-use arguments.
  - Integration, `test/core/Tellma.Core.IntegrationTests/Sharing/ReportSharingTests` (12 cases,
    see its README row).
  - Web, `test/core/Tellma.Core.AspNetCore.IntegrationTests/Stacks/ReportOperationTests`:
    query, get, get-by-ids, save, share, publish, transfer, deactivate, activate and delete end
    to end on Acme's migrated tenant. The routes are pinned in `ProjectedRouteTests`, and
    `web.json`/`contracts.json` are regenerated.
  - Goldens and expectations that now include `core.Report`, `core.ReportShares` and
    `ShareGrantList` were updated:
    - the route and stack-descriptor goldens;
    - the client entity-model fixtures and `tellma-entities.d.ts.txt`, checked by
      `tools/tests/entity-model.spec.mts`;
    - the securables, model, leaf and notification-catalogue expectations.

### Deviations

1. **`OwnerId` is `[ServerOwned]`, not `[Derived]`.** Spec 0033 has it `[Derived]`, but spec
   0012 §9.1 lets a column update assign only editable or server-owned columns, so transfer's
   `ActionContext.Update` was refused at run time. Server ownership is also what §5.1 describes:
   an update keeps the stored owner, and the hook-set value is written on insert. The new
   `core.shareables` rule enforces it.
2. **Share rows are deleted by an `ON DELETE CASCADE` foreign key**, not a persist participant,
   because a participant runs after the row's delete.
3. **The share table has no stack**, so delete-by-query is not among the share operations (the
   registry refuses it alongside judged deletes).
4. **No `MERGE`.** The grant write is UPDATE + INSERT…SELECT `NEXT VALUE FOR`, then
   `IF EXISTS … THROW 50422` for the caps, because the `IDataBatch.Sql` analyzer refuses `MERGE`.
5. **The shares extra uses two statements** when both decisions are filtered.
6. **New platform API: `DetailsPlan.AddComputedExtra<TRow, TValue>`.**
7. **`SharingOptions` uses get/set properties** (options binding), not init.
8. **The notification category `reports` is used for every shareable.**
9. **Every document binding failure is `Report.UnknownMember`.** `ChartTypeUnsupported` and
   `DisplayIncompatible` are left to the renderers' milestone, as is the 256 KB size rule.
10. **Duplicate grantees get `ValidationCodes.Unique`**, and `TooManyGrants` is reported at
    `Arguments.Set`.
11. **`Report.InUse` carries an extra `named` argument** (the ICU plural needs it).
12. **`Access_Reason_share` is added as a pending resource key.**
13. **Default titles with no tenant settings use the current culture and one slot.**
14. **The commands load only the name twins the tenant configures**, since the query schema does
    not declare an unconfigured twin.

### Open risks

- Notifications are not withdrawn when a report is deleted; they point at a missing row.
- Two concurrent grants of one user can each raise a notice. This is harmless under `Replace`.
- `NEXT VALUE FOR` inside INSERT…SELECT with NOT EXISTS is exercised only by the integration
  suite.

### What reviewers should examine hardest

- `ShareCommands` write text: the cap THROW, `NEXT VALUE FOR` per inserted row, and concurrency
  between two publishers of one Everyone grant (the unique index is the backstop).
- The OwnerId ownership switch, and that no save path can now set an owner.
- `ShareableAccessCriteria` against spec 0033 §5.2 (Edit saves, never deletes, activates or shares).
