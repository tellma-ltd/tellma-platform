# PC-112: TmTelemetry pipeline, TmErrorHandler and redaction

## Implementer notes

### What was built, and where

All client-side; no C# changes. Paths are under `client/projects/core/` unless noted.

- **The front** (`tellma-core/src/observe/tm-telemetry.ts`, primary, eager). `TmTelemetry` stays
  the abstract API (spec 0026 §3) and its root default is now `TmTelemetryFront`, which replaces
  the old quiet default. The front stamps each call with `TM_NOW`, holds at most 1,000 calls (200 before fix 1) until
  the pipeline starts, logs every `error()` to `console.error`, and records the event the browser
  is dispatching at an `error()` call (`globalThis.event`) so the pipeline can tell `global` from
  `render`. `start(injector)` loads the pipeline chunk with `import()` and hands it the held calls.
  `TmTelemetryOptions` gains `traceId`.
- **The error handler** (`tellma-core/src/observe/tm-error-handler.ts`, primary, eager).
  `TmErrorHandler` (one call to `TmTelemetry.error`), `TmErrorSource`, `TmErrorRecord` (§4).
  `provideTellma` provides it as Angular's `ErrorHandler`; it is exported from `@tellma/core`.
- **The pipeline** (`tellma-core/src/observe/tm-telemetry-pipeline.ts`, lazy chunk
  `tm-telemetry-pipeline`, 4.42 KB against a 4.5 ceiling). `TmTelemetryPipeline` over a
  `TmTelemetryHost` (the app's services in an app, a fake in its spec):
  - the guard: name grammar and 64 characters, keys, values, 16 properties with the reserved ones,
    reserved keys, finite `ms`, trace ids; development throws `TmTelemetryError`, production
    drops the item (bad name) or the property (bad value) and counts it;
  - the envelope: `version`, `tabId`, `tenantId` per batch (one tenant per batch), `sentAt`, and
    per item `kind`, `name`, `at`, `traceId`, `properties` with `route`/`pageKind` from
    `TmPageContexts.current`, `ms` for timings, `sampleRate` for sampled items;
  - per-tab sampling (one `Math.random()` draw), sampled by default `tm.page.*`, `tm.vitals.*`,
    `tm.action.*` and non-`tm`, overridden by `options.sampled`;
  - the `recent` ring of 100, `console.debug('[tm]', name, props)` in development;
  - the queue: cap 200 (overflow drops the oldest non-error, else the oldest), flush at 50 items,
    30 s after the first item, 1 s after the latest error (debounced), `flush()`; batches of at
    most 100 items and 16,384 UTF-8 bytes measured on the JSON body, paced one a second, a regular
    flush joining one in progress; `tm.telemetry.dropped { count, reason }` leads the next batch;
  - holds: offline (`TmApi.online`), session not `active`, UI version unknown (read from
    `TmClientMetadataStore` until PC-113's `TmAppVersion`); disabled distributions queue nothing
    and clear what the cold defaults queued; cold launch uses enabled, rate 1;
  - `tmStartTelemetry` wires the app: an effect flushes on a tenant switch and when a hold lifts,
    `visibilitychange` to hidden flushes, `pagehide` flushes one batch, `DestroyRef` stops it; the
    held calls replay untracked, and a held call that throws in development is rethrown on its own
    microtask so the later calls still run.
- **Capture and redaction** (`tellma-core/src/observe/tm-error-capture.ts`, in the same chunk):
  `tmRedactMessage` (the five masks in order, then 200 characters), `tmReduceStack` (V8, Firefox
  and Safari frames; message lines dropped; URL to file name and position; non-ASCII masked; 30
  whole frames within 4,096 characters; top and first same-origin frame), `tmErrorClass`
  (`TmApiError`, `ChunkLoadError` by the three engines' wording, the name, the constructor),
  `TmErrorCapture` (global-only filters: cancelled/unauthenticated `TmApiError`, `ResizeObserver
  loop`, foreign top frame or a wrapped `ErrorEvent` naming a foreign file or `Script error.`;
  fingerprint `class@firstSameOriginFrame` limited to value characters and 64; the 50-record ring;
  10-minute per-fingerprint and 30-per-10-minutes throttles).
- **Call sites.** Every `telemetry.error(e, { source: 'tm-…' })` context became `{ where: … }`
  (the existing `tm-localization` convention), since `source` now names §4.1's source; the
  presenter's `{ source: 'api' }` stays. The contract-mismatch context's `route` became `api`,
  since `route` is reserved.
- **`TmFakeTelemetry`** (`tellma-core-testing/src/tm-fake-telemetry.ts`) keeps `options.traceId`.
- **`tm/telemetry-names`** (`tellma-core-tools/src/eslint/rules/telemetry-names.ts`): literal
  names of `event`/`timing` on a `TmTelemetry` (by type when the config is type-aware, a subclass
  included, else by the receiver's name), the `tm.` areas of Appendix A.2, conditional branches;
  literal action ids in `{ id, labelKey, invoke }` literals and `TmPageActions.invoke`. In the
  preset, and wired into the workspace's `tellma-core`/`core-testing` (type-aware) and
  `module` (by name) blocks. Fixture `src/eslint/fixtures/telemetry/`.
- **Budgets.** "." 49.89 → 50.09 (measured 49.88 → 50.083 linked gzip 6, cap 49.78 → 49.98 gzip
  9); the new chunk budget 4.5. Note in `budgetNotes["."]`.
- **Docs.** `tellma-core` README (new Telemetry and error logging section), `tellma-core-tools`
  README (rule row), ARCHITECTURE.md's `@tellma/core` row (the pipeline is a lazy chunk).

### Deviations

1. The pipeline, capture and redaction are a lazy chunk of the primary loaded at idle after the
   first render; spec 0026 §1 places them in the primary eagerly. The primary had 0.22 KB left
   under the 50 KB cap (D-247), and this kept 0.02. Errors and items before the load are held
   (at most 1,000 calls) and replayed with their original timestamps and with the tenant, page
   and recent requests each call saw (fix 1), so the queue's own overflow order and count apply
   at replay. What remains lost before the load (fix 1, R1-1):
   - `recent()` is empty until the chunk loads;
   - nothing is sent if the tab is hidden or closed before idle;
   - a chunk that fails to load drops the tab's calls, uncounted;
   - calls past the 1,000th are dropped uncounted.
2. In development, a malformed call made before the chunk loads throws asynchronously (its own
   microtask) at replay rather than synchronously at the call site. Calls after the load throw
   synchronously, as specified.
3. `TmTelemetryError` is a class of the chunk and is not exported from `@tellma/core`; code sees
   it only by its `name` (the abstract class's TSDoc says so). Exporting it would pull the class
   into the primary.
4. `TmTelemetryOptions.traceId` is added: §3.1's envelope names a per-item trace id, and the
   sketch's options had no way to pass one for events and timings.
5. A run of non-ASCII words with the spaces between them masks to one `…` (§4.3's example
   `القيمة غير صالحة` → `…` needs that); a single run elsewhere masks as specified.
6. `TmTelemetry.error`'s context uses `where` for the caller's location, and `source` only for
   §4.1's three values (anything else is a malformed property). Existing call sites were renamed.
7. Global versus render is read from the event being dispatched (`globalThis.event` is an
   `ErrorEvent` or a `PromiseRejectionEvent` while Angular's global listeners run), since
   Angular calls the same `ErrorHandler` for both.
8. The error records are reachable only through the pipeline (`TmTelemetryPipeline.errors`); the
   support dump (a later checkpoint) has no seam to read them yet.
9. The changed-user guard on a send is TmApi.send's own (spec 0024); the pipeline only reads the
   session's state for its hold.
10. A request error's fingerprint is `TmApiError@<kind>.<code>` (fix 1, R1-5), not §4.2's
    `errorClass@firstSameOriginFrame`: every request error is built at one site of the HTTP layer,
    so the frame cannot tell a 503 on one route from a 500 on another. Recorded for Ahmad.
11. `pagehide` and `visibilitychange` share one flush (fix 1, R1-4): every batch starts a
    one-second pace that any flush joins, so an unload sends one batch whatever the events'
    order, and a page that stays sends the rest a second later.

### Findings

**R1-1 (major): Calls held before the pipeline loads can be lost without a count, and the
overflow order is the reverse of the spec's.**

`client/projects/core/tellma-core/src/observe/tm-telemetry.ts:146` keeps the first 200 calls and
silently discards every later one, errors included. Spec 0026 §3.3 says overflow drops "the
oldest non-error item first", and the next batch carries
`tm.telemetry.dropped { reason: 'overflow' }`.

- **Scenario:** a boot that loops on an event or a render error before idle (`requestIdleCallback`
  has no `timeout`, so a busy first page delays it) fills the 200 slots. A distinct error raised
  after that is never recorded, sent or counted. The spec test pins this behaviour
  (`tm-telemetry.spec.ts:113-123`, which asserts that the newest calls are the ones lost).
- **The same lazy window has three other unstated losses:**
  - `recent()` stays empty until the chunk loads. §3.3 says every item enters the ring.
  - A tab hidden or closed before idle sends nothing. In the eager design, the
    `visibilitychange` and `pagehide` flushes would have sent the boot items.
  - A chunk that fails to load (`tm-telemetry.ts:177-182`) silently drops every call for the
    tab's life, with no retry and no count.
- **Fix, byte-neutral in the primary:**
  - Raise `HELD_CALLS` well past the queue cap (for example 1,000). The replay then runs every
    held call through `#enqueue`, so the pipeline applies the spec's overflow order and counts
    the overflow.
  - State the residual losses (past the held cap, pagehide before idle, a failed chunk, an empty
    `recent` before the load) under Deviations.
  - Add a spec in which an error held behind more than 200 events is sent after replay and the
    overflow is counted.

**R1-2 (major): Message redaction leaks single-quoted text that contains an apostrophe.**

At `client/projects/core/tellma-core/src/observe/tm-error-capture.ts:37`, `'([^'\n]*)'` ends the
quote at the first apostrophe. The first fragment is then often an identifier, which ships, and
the rest cannot re-open a quote, because it follows a letter.

- **Verified outputs:**
  - `Invalid value 'O'Brien Trading' at row 4` ships as `Invalid value 'O'Brien Trading' at row #`.
  - `Customer 'Farah's Bakery' not found` ships unchanged.
- **Why it matters:** §4.3 masks quoted text that is not an identifier, and the whole quoted value
  here is not one. Names with apostrophes are common (O'Brien, D'Souza, transliterated Arabic
  names), and the relay's backstop re-applies only the URL and e-mail masks (§6.2).
- **Fix:** let an apostrophe followed by a letter or digit continue the quote, and require the
  closing quote not to be followed by one:
  ```
  (?<![\p{L}\p{N}])'((?:[^'\n]|'(?=[\p{L}\p{N}]))*)'(?![\p{L}\p{N}])
  ```
  I checked it against both vectors and the existing ones: `Can't parse 'Farah Nasser'`,
  `(reading 'Name')`, `it's 'Mary Ann' who's here` and `'querySelector'` all come out as they do
  today. Add both new vectors to `tm-error-capture.spec.ts` beside the apostrophe test at
  lines 87-89.
- **Optional:** also treat `‘…’` as a quote pair. §4.3 does not list it, and today
  `Expected ‘Farah Nasser’` ships as `Expected …Farah Nasser…`.
- The fix lives in the chunk, which has 0.08 KB of headroom.

**R1-3 (minor): Held calls take their tenant, page and recent trace ids at replay, not at the call.**

The calls happen at `tm-telemetry-pipeline.ts:314`, `:338-339` and `:364`. Spec 0026 §3.1 records
`TmUrls.tenantId()` "when queued", together with the page's `route` and `pageKind`. §4 records the
last three trace ids at the error.

- **Scenario:** a cold launch at `/` records `tm.launch.cold` (tenantless) and a boot error.
  Idle comes after the launch redirect into tenant 17, so both items are batched as tenant 17,
  with the tenant page's `route` and `pageKind`. The error's `recentTraceIds` and record name
  requests made after it.
- **Fix:** capturing these in the front costs primary bytes the cap does not have, so record it as
  a deviation of the lazy placement. Alternatively, have the front stamp `TmUrls.tenantId()` only,
  if the budget allows.

**R1-4 (minor): Unload sends two batches back to back.**

The listeners are at `tm-telemetry-pipeline.ts:725-732`, and the flush logic at `:252-280`. On
unload, both `pagehide` and `visibilitychange` (hidden) fire, in either order depending on the
browser and the kind of unload.

- `flush('pagehide')` sets no pace timer, and a pagehide flush ignores one. So the pair always
  sends two batches, up to 32 KB of keepalive, in the same task burst.
- §3.3 allows one batch on `pagehide`, and outside it one batch a second.
- **Fix:** have the pagehide flush set the pace timer too, so that a regular flush right after it
  joins. Also skip the pagehide send when a pace started within the last second.
- Add a spec for each of the two event orders.

**R1-5 (minor, for Ahmad): Every request error shares one fingerprint, so the throttle reports
one per 10 minutes.**

At `tm-error-capture.ts:294`, the fingerprint follows §4.2 literally: `errorClass@firstSameOriginFrame`.

- Every `server`, `unavailable` and `partial-failure` `TmApiError` is built at the same site in
  `tm-http-api.ts`. So every `source: 'api'` item shares one fingerprint, and §4.2 admits only one
  of them per 10 minutes per tab.
- A 503 on one route then hides a 500 with another `code` on another route, and
  `tellma.client.errors` by `kind` undercounts.
- **Suggestion:** for a `TmApiError`, fingerprint `TmApiError@<kind>.<code>` (value characters
  only) and state it as a deviation. Or ask Ahmad whether §4.2 should say so.

**R1-6 (minor): Tests are missing for the lazy window's error path and for deviation 2.**

`tm-telemetry.spec.ts:99-123` covers only held events. Nothing pins three things:

- an uncaught error or rejection held before the chunk loads still ships as `source: 'global'`,
  with its message redacted after replay;
- a held global error from a foreign script is dropped as `foreign`;
- deviation 2: a malformed held call in development rethrows on its own microtask, and the calls
  after it still replay.

Each is a few lines in the existing "in an app" block, using `tmSettleUntil`.
