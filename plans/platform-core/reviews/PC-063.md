### Deviations

1. A feature that requires a stack's registrant may register the same stack again; its service and
   operations replace the registrant's, while the stack keeps the registrant's `Feature`.
2. "A class deriving from `EntityService<T>` registered by no stack" is judged over services
   registered in DI plus an assembly scan of feature assemblies restricted to entities whose stack
   runs the default service. A full scan would flag test or sample services that are never meant to
   run.
3. `StackDescriptor.Description` is `[ApiResource(Description)]` or null; runtime XML-doc reading is
   not attempted.
4. The `assignable` capability is not derived (its source spec has not landed); seam comment in the
   builder.
5. §2.6 property-annotation rules (`[Searchable]` non-string, `[Unique]`/`[NaturalKey]` without an
   index) stay with `core.entity-metadata`, which already names the entity; they are not re-reported
   under a stack check.
6. Companions' `[ApiAction]`s may take the Excel segments (`export`, `import`, …) a stack projects,
   so the Excel features can serve them; the service may not take any projected segment.
7. Stack services are registered through an `ActivatorUtilities` factory (so `ValidateOnBuild`
   sees their dependencies) until the pipeline checkpoint wires them.
8. Named filter contributors are created once from the root provider and never registered in DI.
9. A derived `DetailsExpand` includes children's references at every depth, as `Collection.Nav`.
10. `IStackRouteSource.Routes` holds stacks only; child surfaces and routed services are not routes
    the link builder targets.
11. A routed service's `[ApiRoute]` may hold `/`-joined segments; its first segment must be unique
    against stack and child-surface segments.
12. `core.entity-pipeline` treats an instance or factory registration as a substitute.
13. The unit suite now references `Tellma.Testing.Entities` (for the fixture golden), so
    `RequestContextHolderTests`' structural scan leaves out `Tellma.Testing.*` harness assemblies.
14. The §2.6 rules are split over eight named checks (spec names only `core.enlistments`).
15. *(Review 1)* An `[ApiAction]` method may take a trailing `CancellationToken` (D-079's async
    shape), beyond §2.3's "one body (or none)". The registry-owned `ActionMethod` records it
    (`TakesCancellationToken`), and the invoker binds the request's token to it, after the body.
16. *(Review 1)* `[ApiAction(Resource = …)]` on a stack's service or companion is refused: the
    stack's resource secures those actions, so a second resource would split their grants.
17. *(Review 1)* `[ApiAction]` with `MemberOnly` and a `Resource` or `Action` is refused, since a
    member-only action names no securable.
18. *(Review 1)* A method with both `[EntityAction]` and `[ApiAction]` is refused.
19. *(Review 1)* A component of any kind over an entity no stack owns is refused, not only a
    `ContributeAsync` participant, and so is a non-generic component whose entity only derived
    entities' stacks own: neither would ever run.

### Open risks

- Deviation 2's scan heuristics: a service class for a default-service entity in any feature
  assembly fails startup; test assemblies must keep such classes off default-service entities.
- `ActionMethods` reads only public instance methods of the service and companions, base first; an
  override of an action method keeps the base's attribute through `inherit: true`.
- Child-surface `Actions` are always empty, pending 0019; `StackSecurableContributor` registers only
  their `Read`.

### Examine hardest

- `StackDescriptorBuilder.Actions` and `StackRegistry.CheckSegments`: name grammar, projected-segment
  collisions, and ordering across service, companion and built-ins.
- `StackSecurableContributor.Securables`: filter roots (cacheable null, non-filter action null),
  dedupe by pair, and child owners/feature.
- `StackComposition`/`CrudComposition`: leaf closure of generic components and the substituted-leaf
  refusals; that `EntityService<TLeaf, TKey>` forwarding resolves the same scoped instance.
- `StackRegistry.DeclaredEnlistments` cycle detection and self-pair exclusion.
- `StackProjectionsCheck` FilterTree walk (`Via`/`Exists`).

**Major**

- **R1-1 — The touched integration suites were not all run or listed (PLAN.md §7.1 item 4).** The
  commit changes `src/core/Tellma.Core.Abstractions` (four new contribution items, `ComponentKind`,
  new `FeatureContribution` members), so every integration suite counts as touched. The commit
  message's `Tests:` line lists only `Tellma.Core.IntegrationTests`. Acme composes `CoreFeature` and
  therefore now runs all eight new stack checks at startup, so it was the suite most at risk. The
  reviewer ran the missing suites and all pass (see above), so no code is wrong.
  *Fix:* list the suites run, Acme, EF Core, Queryex and Identity included, in the commit message.

**Minor**

- **R1-2 — XML doc comments cite specs (AGENTS.md; PLAN.md §7.1 item 5).** They are at
  `src/core/Tellma.Core/Crud/StackDescriptorBuilder.cs:165` ("spec 0015 §2.4's table"), `:576`
  ("spec 0012 §2.5") and `src/core/Tellma.Core/Crud/StackSecurableContributor.cs:51` ("spec 0015
  §2.4"). *Fix:* remove the citations from the `<summary>`s. Move them into inline `//` comments if
  they are worth keeping.

- **R1-3 — The name grammars accept a trailing newline.**
  `src/core/Tellma.Core/Crud/StackNames.cs:102,107,112` anchor with `$`. Without `Multiline`, .NET's
  `$` also matches before a final `\n`. So `IsSegment("gadgets\n")`, `IsActionName("invite\n")`,
  `IsNamedFilterName("mine\n")` and `IsConfirmationKey("Gadget.Recost\n")` all return true.
  - *Failure:* `[ApiResource(Segment = "gadgets\n")]`, an `[ApiAction("x\n")]` or a named filter
    keyed `"mine\n"` passes every startup check. It then yields a route or a filter key nobody can
    address.
  - *Fix:* anchor with `\z` in all three patterns. Add one negative case per grammar.

- **R1-4 — A non-generic component on an entity no stack has as its leaf is silently dropped. This
  escapes the "ContributeAsync participant on an entity no stack owns" rule.**
  `src/core/Tellma.Core/Crud/StackComposition.cs:318-340` computes `applicable` (stacks whose leaf
  derives from the component's entity) before it skips non-generic components on stacks other than
  their own entity's.
  - *Failure:* `PersistEffect<Widget, WidgetEffect>()` with a non-generic `WidgetEffect`, where only
    a separately stacked `SpecialWidget : Widget` exists (or the entity is a base such as
    `TopLevelEntity`). `applicable.Count` is 1, so no problem is reported. The loop then `continue`s
    on every stack, so the effect never runs and startup passes. The same happens silently for a
    validator, a details contributor or a named filter contributor.
  - *Fix:* count the stacks the component was actually attached to. Report a `PersistEffect` attached
    to none, and preferably any kind of component, under `core.stack-components`. Add the failing
    fixture.

- **R1-5 — The securables audit is computed by the function it audits.**
  `src/core/Tellma.Core/Crud/Checks/StackSecurablesCheck.cs:75` takes the required pairs from
  `StackSecurableContributor.Securables(stack)`, which is the same mapping the contributor registers
  from.
  - *Failure:* a regression in that mapping, for example `Delete` dropped or `Import` no longer
    implying `Save`, removes the securable and its audit requirement together. The audit still
    passes, but §2.6 says it "verifies that every projected operation … is registered".
  - *Test gap:* no unit test pins the §2.7 rule that a `[Cacheable]` stack registers `Read` with
    `FilterRoot = null`. `fixture.Lookup` is in the golden, but the golden renders no securables.
  - *Fix:* derive the required standard-operation actions independently from the §2.4 table (for
    example from `ProjectedSegments` mapped to their actions). Add a test pinning the securables of
    a cacheable stack and of a `Read`-only stack.

- **R1-6 — Contract changes beyond the spec are missing from Deviations (PLAN.md §7.1 item 1).**
  - **Relaxation:** `src/core/Tellma.Core/Crud/ActionMethods.cs:188` lets an `[ApiAction]` method
    take a trailing `CancellationToken`. §2.3 says "taking one body (or none)", and §11.3's
    `IApiActionInvoker.InvokeAsync(action, body)` has no token to pass. Nothing records how PC-077
    is to bind it.
  - **New refusal:** `StackDescriptorBuilder.cs:293` and `:340` refuse `[ApiAction(Resource = …)]`
    on a stack's service or companion.
  - **New refusal:** `StackRegistry.cs:297` refuses `MemberOnly` together with `Action`.
  - **New refusal:** `StackDescriptorBuilder.cs:274` refuses `[EntityAction]` and `[ApiAction]` on
    one method.
  - *Fix:* list these under Deviations. For the token, either refuse it, or state the invoker
    contract and record on the descriptor that the method takes a token.

- **R1-7 — The remedy text misdirects for a missing routed-service securable.**
  `src/core/Tellma.Core/Crud/Checks/StackSecurablesCheck.cs:119` tells the author to "register a
  routed service's securable with contribution.Securables(...)". But `StackSecurableContributor`
  registers every routed action's securable itself (`StackSecurableContributor.cs:33-39`), and a
  second registration under another feature or filter root would conflict. *Fix:* name the real
  causes: the contributor is missing or replaced, or the action names a `Resource`/`Action` pair that
  another registration contradicts.

- **R1-8 — Some §2.6 sub-rules have no failing fixture (checkpoint test list: "each §2.6 check with
  a failing fixture").** `StackChecksTests` covers every check, but no fixture fails on:
  - a `[RelatedSelect]` text that does not validate. Only the default select, the default ordering,
    the details expansion and named filters are exercised.
  - a details contributor, as opposed to a service, declaring `permissions`. That branch is
    `StackDescriptorBuilder.cs:429-435`.
  - an arguments record the JSON contract refuses, the `GetTypeInfo` path of
    `ActionMethods.IsSerialisableRecord`. Only "not a concrete record" is pinned.

  *Fix:* add one fixture each to the existing tests.

**Scrutiny items the implementer flagged (judged, no finding beyond the above)**

- **`CoreFeature` no longer registers `core.User` × `Read`, and `NoStackRoutes` is gone:** accepted.
  Core always stacks `User`, so its `Read` (the `core.UserStamp` owner) is always contributed. A
  host's own route source is still honoured through `TryAddSingleton`. When the tenant model fails,
  the registry is empty and the securables check adds an owner problem beside the entity-metadata
  one, which is noise but no wrong verdict.
- **The unit suite references `Tellma.Testing.Entities`, and the writer scan excludes
  `Tellma.Testing.*`:** accepted. Those are harness assemblies, not platform code. The prefix also
  drops `Tellma.Testing.Support` from the scan, which is harmless for a scan of platform writers.
- **The unregistered-`EntityService` rule is scoped (deviation 2):** accepted as a deviation. It
  still catches the main authoring slip, `Entity<T>()` without naming the service written for `T`.
  The open risk is real and should go into `test/core/Tellma.Core.Tests/README.md`. Any feature
  assembly, the unit suite included since its `TestFeature`s live there, that defines a service
  class for `core.User`, `core.Role`, `core.Job` or `core.Schedule` (default-service stacks in every
  composition) fails startup for every composition built from that assembly.
