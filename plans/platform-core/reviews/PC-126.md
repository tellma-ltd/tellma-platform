# PC-126: Search host, grid view, read lifecycle, states, paging, Create and Refresh

## Implementer notes

### What was built, and where

All client paths are under `client/projects/core/`.

**`@tellma/core/search` (`tellma-core/search/`)**

- **`src/tm-search-host.ts` (+ `.css`).** `TmSearchHost` (`tm-search-host`), the routed page:
  - Resolves the setting from the routed entity's descriptor and declaration, reads the address
    into the canonical query (PC-124's model), writes the canonical address back with
    `replaceUrl` except for paging, which pushes (§5.4).
  - The grid view (§7.1–§7.3): `tmGridColumnFor` columns over the shown columns, `TmValue` cells,
    the first shown column of the display name as the details link; sort cycles asc/desc/none
    through the grid's header and writes `order`.
  - The read lifecycle (§5.2 minus the anchor): one request per canonical query, superseded reads
    aborted, the previous rows held under a busy line while the next page loads.
  - Every §5.3 state through `tm-search-state` (skeleton, empty, empty-with-filters, offline,
    forbidden, error), with the Columns slot reachable in every state.
  - The pager (§14), Create (§13.1; a link, or a disabled button with its reason) and Refresh
    (§13.4), the page context and the host's page actions (§19).
  - Row preloading: the highlighted row and the hovered row (by `aria-rowindex`) preload their
    details route; Create's target preloads once results show.
  - Re-plans the shown columns when a permissions move re-grants a column (the D-275 carry), and
    reads once per such move; a move that changes no request reads nothing.
- **`src/tm-search-read.ts`.** The read resource: the request PC-124 builds, the abort on
  supersede, the result with total and cap.
- **`src/tm-search-state.ts`.** The results-area states. The error state loads `@tellma/core/errors`
  by `import()` and renders `TmErrorState` (panel size) with Retry; if that chunk cannot load it
  falls back to its own line ("The results couldn't be loaded.") and a Retry button.
- **`src/tm-search-cell.ts`, `src/tm-search-context.ts`.** `TmSearchCell` and `injectTmSearch` /
  `TmSearchContext` for display hatches and page actions.
- **`src/tm-search-strings.ts`.** English strings; Arabic in
  `locale/tellma-locale-ar/queryex-strings/strings-queryex-ar.ts`.
- `tm-search-canonical.ts`, `tm-search-resolve.ts`, `tm-search-model.ts`: the canonical form
  compares `cols` with the default as this user can read it (`tmSearchShownDefaults`); the column
  resolution is exported as `tmSearchColumnsOf`; the setting carries tenant-bound URL builders.

**Primary (`tellma-core/src/`)**

- `routes/tm-route-hosts.ts`: the search route's loader; `routes/tm-route-host.ts`: the host fills

### Deviations

1. Types moved to the primary (`tm-search-types.ts`, `tm-select-plan-types.ts`) so the page
   action's `run` can be typed; zero bytes.
2. The error state loads `/errors` lazily and has its own fallback line, with a new
   `tm.search.failed` string, so a failed chunk still offers Retry.
3. The route host fills its block (`block-size: 100%`).
4. `cols` is canonical against the readable default, and the host re-plans columns on access
   moves; without it a re-granted column never came back.
5. `TmUrls.preload` ignores idle callbacks after destroy (NG0205 at teardown).
6. The host builds URLs with the routed tenant's builders (`TmSearchSetting.urls`): during a
   navigation away the ambient tenant is already gone, which produced `/null/...` addresses.
7. The host holds address writes while the app navigates away; a `replaceUrl` write would cancel
   that navigation.
8. The link text is the column's own text, not `tm-display-name`.
9. Page-state memory (§15.1) is not built here; the open passes `tmFrom` and `tmPage` in router
   state for it.
10. The Columns button is a placeholder that does nothing yet (the column editor is a later
    checkpoint); the Edit-filter actions are omitted; telemetry records the `grid` view only.
11. Arabic strings live in `./queryex-strings`, not `./platform-strings`.
12. Spec fallout: `tm-route-host.spec.ts`, `tm-urls.spec.ts` and `tm-error-state.spec.ts` now
    answer or wait for the search page that their navigations open.
13. `./search` measures 17.76 KB against spec 0030 §1's 16 KB for the route chunk (budget set to
    18, flagged below).

### Budgets

Package budgets (clean build after `rm -rf client/dist`, `npm run size:check` green):

- `.` 50.23 → 50.27: measured 51,468 B (50.26 KB); gzip 9 cap line 50.17 of 55. The bytes are
  the search route's loader in place of the placeholder, the route host's `block-size`, and the
  `TmUrls` destroy guard. `staticGraphExcludes` is unchanged and still checks `./search`.
- `./search` 0.5 → 18: measured 18,189 B (17.76 KB), rounded up to the next 0.5 KB. **This is
  over spec 0030 §1's 16 KB for the route chunk's own weight.** No savings were taken; the host
  is the bulk (27 KB raw before minification).
- locale-ar `./queryex-strings` 1 → 1.5: measured 1,244 B (1.21 KB), the part's first raise. The
  root and `./platform-strings` are unchanged.

**The build route budget fails, and this blocks the checkpoint.** `npx tellma-client build` for
Acme (and the fixture-build specs in `npm run lint:test`) fail with:

```
budget-exceeded budget:searchRoute acme - 192.26 KB gzip is over the budget's error level of 110 KB.
budget-exceeded budget:detailsRoute acme - 192.26 KB gzip is over the budget's error level of 80 KB.
```

- 192.26 is the tools' current measure, which counts every chunk holding an `/entity` module,
  including `/entity`'s on-use chunks. The correction to that measure is in held PC-127's fix1
  and is not on this branch. The search route's real static closure beyond the initial set,
  measured from Acme's `stats.json`, is **150.8 KB gzip in 5 files**:
  - 79 KB: the grid (grid-core, grid-view, grid-engine clipboard and history, keymap), the search
    host, and `/entity`'s view code (`TmValue`, `tmGridColumnFor`, `tmQx`, the filter);
  - 18 KB: `/entity`'s edit stack (`TmValueEditor`, the entity fields, `TmEntityPickers`,
    uploads, confirmations) with the checkbox and the select plan;
  - 46 KB: `@angular/forms` (signals), the entity picker, select, multi-select, date-picker,
    chip, number;
  - 6.5 KB: CDK dialog and the modal.
- The cause is esbuild's code splitting with the `/entity` barrel, reproduced outside Angular
  with plain esbuild over the sources (an entry importing only `TmFormats` from the barrel):
  once the barrel is in the graph, the lazy chunks `/entity` itself creates
  (`import('./tm-action-dialog')` in `tm-entity-actions.ts`, and the others) are entry points
  whether or not anything calls them, so the edit stack is live; and code splitting gives every
  live module the barrel re-exports to each entry that imports the barrel, so the search route's
  static chunks carry the edit stack although the search page uses only `TmFormats`, `TmValue`, `tmGridColumnFor`,
  the filter functions and `tmSelectPlan`. A packaged distribution (one FESM per entry point)
  has the same shape at file level.
- Experiment (reverted): with `/search` importing those symbols from `/entity`'s leaf modules,
  the route's real closure is **104.5 KB** (4 files: the 87 KB grid-and-host chunk, select 10 KB,
  modal 6.5 KB, findable 0.7 KB), inside 110, and the tools' measure 130.25. Cross-entry deep
  imports are not legitimate (the boundary lint, and ng-packagr would copy `/entity` code into
  `/search`'s FESM, duplicating injectables), so this only shows the bound a split would reach.
- Not verified because of this: the Acme build, so the PR-tier Acme e2e (`search-page.spec.ts`,
  `launch.spec.ts`) has not run against this branch, and `npm run lint:test` has 5 fixture-build
  failures, all these two budget lines.
- The ways out need a ruling: split `/entity`'s edit stack into an entry point of its own (D-285
  found the split not spec-backed), or raise the 110 KB route budget (spec 0024 §12) to the
  measured figure and flag it to Ahmad, as D-287 describes for the details route.
