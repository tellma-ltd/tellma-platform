## Implementer notes

### Deviations and additions

1. **`ServiceClientSecret` is not required in in-proc Development.** Spec §2.1 says "required".
   - In in-proc Development the web host generates the secret per boot (`IdentityClientSecrets`),
     and the migrator cannot know it.
   - The migrator's options therefore validate without a secret, and a call there fails with
     `InvalidOperationException` before anything is sent.
   - Everywhere else the secret is required, in-proc Production included.
2. **The service-secret check moved from `host.identity` to `core.options`.** It is validated once,
   in both hosts and both modes, instead of twice.
3. **In-proc mode derives `Authority` from `{Tellma:PublicOrigin}/id`** and ignores the configured
   value. This matches `IdentityHostOptions`, which ignores `Authority` in-proc.
4. **The client builds absolute URIs from the authority (with a trailing slash added) rather than
   setting `HttpClient.BaseAddress`.** The routes keep the authority's path (`/id`).
   - `Accept` and `User-Agent` are set per request.
   - The timeout is the transport's own, on the `TimeProvider`, with `HttpClient.Timeout` infinite.
     This is what lets the tests move the clock.
5. **The factory's request logging is removed for `Tellma.Identity` (`RemoveAllLoggers`).**
   - A test at Trace showed that `LoggingHttpMessageHandler`'s structured header state carries the
     raw `Authorization` value. `RedactLoggedHeaders` only redacts the formatted text, so a
     structured sink would record the bearer token.
   - `IdentityCall` replaces those logs.
6. **The outcome value `cancelled`** joins the spec's `ok | partial | unavailable | error` for a call
   the caller cancelled before any chunk completed. Counting it as `error` would report a
   caller's own cancellation as the identity server's failure.
7. **The `identity.delivery` activity** is the delivery-status counterpart of `identity.invite`, with
   the same tags.
8. **The `IdentityChunkFailed` log** (Warning, with the exception) records why a prefix was
   answered. `IdentityCall` carries no exception.
9. **Answer checks.**
   - Each result must echo its item's email (ordinal) or subject.
   - The count must match.
   - The status or state must be a known name.
   - A result must be either a status with a subject or an error alone.
   - Any violation raises `InvalidOperationException`. A misplaced result would otherwise record one
     user's subject on another user's row.
10. **The `UsersTelemetryNames` constants are partial.** It holds the identity names only;
   `Invites`, `TestNotifications` and `ChannelTag` belong to the user-service checkpoint that
   creates those instruments. The endpoint tag constant is spelt `EndpointTag`, as in the spec.

### Open risks

- **Chunks with duplicate addresses.** The server echoes `item.Email` verbatim, so the ordinal echo
  check holds today. If the server ever normalises case in its echo, every invite would fail loudly,
  which is the intended direction.
- **The token-endpoint error code.** It is quoted only when it matches the RFC 6749 §5.2 character
  set and is at most 64 characters. A free-text `error_description` is never read.
- **Web host and migrator hosts in Production standalone now need
  `Tellma:Identity:ServiceClientSecret`.** The secret was previously needed only in-proc. Deployment
  templates and onboarding must supply it; the startup gate will say so.

### What reviewers should examine hardest

- `IdentityTransport.SendAsync` and `GetTokenAsync`/`Discard`:
  - the single flight under cancellation of the waiting caller;
  - the compare-and-swap discard;
  - that a failed fetch never caches.
- `IdentityTransport.RunAsync`:
  - the caller's OCE versus the timeout versus `HttpRequestException`/`IOException`;
  - that the timeout timer is per exchange, not per call.
- `IdentityServerClient.RunChunkedAsync`:
  - a cancellation between chunks returns the prefix only when there is one;
  - `catch … when (results.Count > 0)` also turns a later chunk's `InvalidOperationException` into a
    prefix, as spec §2.3 says ("any failure").
- `IdentityComposition.Settle` and the validator in in-proc Development (deviation 1), and the web
  host's post-configure ordering relative to `Settle`.

### Findings

**R1-1 (major): a failed or cancelled token fetch is not shared, so during an outage concurrent callers fetch one after another with no time bound.**

- **Where:** `src/core/Tellma.Core/Identity/IdentityTransport.cs:174-199` (`GetTokenAsync`).
- **What happens:** the single flight is a `SemaphoreSlim` around `FetchTokenAsync`. Only a successful fetch is seen by the waiters, through `Fresh()`. When the fetch throws, each waiter in turn takes the gate and runs a fetch of its own. `_gate.WaitAsync` is bounded only by the caller's token.
- **Scenario 1, the token endpoint hangs:** the cache is empty or due for refresh and N invites arrive together. Caller 1 times out after 30 s and releases the gate. Caller 2 then waits another 30 s, so caller k fails after about k × 30 s.
- **Scenario 2, the server refuses fast:** with a fast 5xx or `invalid_client`, the server gets N token requests in a row instead of one.
- **Spec conflict:** §2.2 says "concurrent callers await one fetch" and sets a 30 s per-call timeout. Both fail on the failure path, which is exactly when an outage most needs a bound.
- **Fix:** share an in-flight `Task<CachedToken>`.
  - Create it under a small lock when absent, and clear it when it completes.
  - Each caller awaits it with `.WaitAsync(cancellationToken)`.
  - Run the fetch under its own exchange timeout rather than the token of the caller that started it. A starter's cancellation then neither cancels the others nor surfaces as their cancellation. The fetch stays bounded by the 30 s timeout.
  - A failure reaches every waiter of that flight, and the next call starts a fresh flight.
- **Tests to add:**
  - A held fetch that answers 503 to 8 waiting callers: one token request and 8 `DependencyUnavailableException`s.
  - A hung token endpoint with 3 callers: all three fail at 30 s, not at 30, 60 and 90 s.
  - The fetching caller cancels: the other callers still receive the token. Nothing tests the single flight under cancellation today.

**R1-2 (minor): an out-of-range `expires_in` escapes unclassified.**

- **Where:** `src/core/Tellma.Core/Identity/IdentityTransport.cs:266-268`.
- **What happens:** `requested + TimeSpan.FromSeconds(seconds) - RefreshMargin` throws `ArgumentOutOfRangeException` when `expires_in` is large. Two cases trigger it:
  - above about 9.2e11, where `TimeSpan.FromSeconds(long)` overflows;
  - above about 2.5e11, where the sum passes `DateTimeOffset.MaxValue`.
- **Why it matters:** `RunAsync` maps only OCE, `HttpRequestException`, `IOException` and `JsonException`. The exception therefore leaves as neither `DependencyUnavailableException` nor `InvalidOperationException`, which breaks the classification contract in §2.2. A buggy or hostile server can trigger it.
- **Fix:** clamp the lifetime to a sane ceiling before the arithmetic, for example one day, or refuse it with `InvalidOperationException`. Add a test case with `"expires_in": 99999999999999` to `A_token_answer_without_a_bearer_token_is_a_refusal`, or to a sibling test.

**R1-3 (minor): `Tellma.Identity.IntegrationTests` was neither run nor listed (PLAN §7.1 item 4).**

- **Why it is owed:** the commit changes `Tellma.Core.Abstractions`, so every integration suite counts as touched. `Tellma.Identity` also references `Tellma.Core.Abstractions` directly.
- **What the commit lists:** Core, Acme, Queryex and EFCore.

**R1-4 (minor): ARCHITECTURE.md now contradicts the code on who holds the service-client secret (PLAN §7.1 item 6).**

- **Where:** `ARCHITECTURE.md:691` says "the migrator, not the web app, holds the distribution's service-client credentials for the identity server".
- **What the commit does:** it makes every standalone web host, and in-proc Production, require `Tellma:Identity:ServiceClientSecret`. That is right for spec 0018, because `UserService`'s invite and issue-credentials actions run in the web host. The architecture text is stale.
- **A second stale text:** spec 0011 §5.7 says `host.identity` fails outside Development when the service secret is absent. That check is now owned by `core.options` (deviation 2).

### Responses

- R1-1: fixed in the "PC-055: review 1 fixes" commit (child of 9dce9595), per orchestrator ruling.
  - `IdentityTransport.GetTokenAsync` now keeps one in-flight `Task<CachedToken>`.
    - The flight is started under a `Lock` when absent and run outside it by `FlyAsync`.
    - It runs under its own 30 s exchange timeout and `CancellationToken.None`.
    - It caches the token and clears itself before it completes, so a failure reaches every
      waiter and the next call starts a fresh flight.
    - Each caller awaits it with `.WaitAsync(cancellationToken)`, so a caller's cancellation ends
      only that caller's wait.
  - The `SemaphoreSlim` is gone, so the transport and the client are no longer `IDisposable`.
  - New tests in `IdentityServerClientTokenTests`:
    - `A_failed_fetch_fails_every_caller_awaiting_it_with_one_request`: 8 callers, one 503, one
      token request, then a fresh flight.
    - `A_hung_token_endpoint_fails_every_caller_at_thirty_seconds`: 3 callers. None fails at
      30 s minus a tick, and all fail with a `TimeoutException` inner at 30 s.
    - `The_starting_caller_s_cancellation_ends_only_its_own_wait`.
  - Mutation-checked: with the previous transport dropped in, all three fail. The hung test fails
    on its 30 s guard.
