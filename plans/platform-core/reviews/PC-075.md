# PC-075: Client store and tab bus

## Implementer notes

### What was built, and where

All paths are under `client/projects/core/tellma-core/src/` unless noted.

- **`state/store/tm-client-store.ts`: `TmClientStore`** (spec 0025 §2).
  - **Mirror.** A map keyed `p\0n` of writable signals. `doc()` hands out a view that applies the
    §2.4 idle rule when it is read:
    - a tenant partition is absent unless its `sync.at` lies within the window;
    - `tenants` and `distribution` are absent once their `savedAt` is older than the window;
    - the window is the stored distribution's `session.idleDays`, else 7 days.
  - **`readAll`.** One readonly transaction with one `getAll` per partition range. It skips
    another build's stored names and empties mirrored entries the partition no longer holds.
  - **`put`.** Guard first, then the mirror (unless the mirror's copy is later). Then a readwrite
    transaction that compares the stored `savedAt`; a later stored copy wins in the mirror too.
  - **`patch`.** One readwrite transaction: get, update, then put or delete. The tag is kept and
    `savedAt` becomes `TM_NOW`. A throwing update or a clone error aborts the transaction.
  - **Commits.** Each commit posts `store.changed {partition: p, names: [n]}`. The first tenant
    write calls `host.persist()`, which skips Gecko.
  - **Sweeps.** Three rules:
    - `session-ended`: the `u:` range, plus the `tm-images-v1` cache in parallel;
    - `sessionOtherThan`: two ranges on either side of the kept session;
    - `tenant`: the exact partition bounds.

    Each sweep empties the mirror at once, posts `store.changed {partition: prefix, names: null}`
    and times `tm.store.sweep {rule}`.
  - **Receiving `store.changed`.** The store re-reads the mirrored entries that match, in one
    readonly transaction, and opens none when nothing matches. `pageshow` with `persisted`
    re-reads everything.
  - **Opening.** `#open` has a 3 s timeout. On failure it falls back to memory mode with
    `tm.store.unavailable {reason: missing|failed|version|timeout}`. `onupgradeneeded` recreates
    `docs`. `versionchange` closes the connection, which reopens on the next access. A transaction
    on a connection closed underneath gets one retry.
  - **Quota.** A `QuotaExceededError` emits `tm.store.quota {reason: put|patch}` and drops the
    write.
  - **Guard** (§2.5). Checks, in order: `other-user`, `cookie`, `session`. A refusal throws
    `TmStoreRefusedError` and emits `tm.store.refused`.
  - **Boot record.** `boot.read/patch/changes` work over `localStorage['tm.boot']`, reusing the boot
    script's parser and validating every patch. When local storage refuses, the record lives in
    memory and the store emits `tm.store.unavailable {reason: local-storage}` once. `changes` is
    the `storage` event, for key `tm.boot` or `null`.
  - **Boot step** `ɵstart(tenantId)` (§2.6):
    1. awaits the database and `TmTabBus.ɵopened`;
    2. runs the backstop `sweep('session-ended')` when the record's `sub` is null or another user;
    3. runs one `readAll(device, user, tenant?)`;
    4. writes `boot.patch({sub})`;
    5. at idle after the first render, sweeps `{sessionOtherThan: profile.sh}`.
  - **Teardown.** `DestroyRef` unsubscribes, removes listeners and closes the connection.
- **`state/store/tm-doc-formats.ts`.**
  - `TM_DOC_FORMATS` (frozen) and `tmDocFormat` (exact name first, then the `prefix:` entry).
  - Internal tokens `TM_STORE_FORMATS` (a test stands in another build) and
    `TM_STORE_EXTRA_FORMATS` (the seam for the leader documents' registrations).
- **`state/store/tm-store-host.ts`.** The internal `TM_STORE_HOST` seam. It covers IDB, local
  storage, caches, the event target, the document language and `persist`, each getter guarded. It
  is exported as `ɵTM_STORE_HOST` for core-testing only.
- **`state/store/tm-store-layout.ts` and the vectors.**
  - New helpers: `tmPrefixKeyBounds`, `tmPartitionKeyBounds`, `tmSessionsPrefix`, `tmStoredName`
    and `TM_USERS_PREFIX`.
  - `tm-store-layout-vectors.json` gains `storedNames`, `partitionReads` and `sweeps` (with their
    prefixes), plus documents that pin the edge cases:
    - a session handle that is a prefix of another (`sY4kQ1x-_` and `sY4kQ1x-_X`);
    - a tenant id that is a prefix of another (`t17` and `t170`);
    - another build's `settings@2`.
  - The same JSON drives the layout spec, the store spec and the boot script's expiry-delete
    spec, so the golden is shared with 0024's tmBoot.
- **`state/bus/tm-tab-bus.ts`: `TmTabBus`** (abstract, root factory) and `TmBroadcastTabBus`

  - **Channels.** The device channel `tm:<slug>` carries `session.*`; the user channel

### Deviations

1. **Receivers re-read rather than empty on a sweep's prefix.** §2.6 says every tab "empties those
   mirror entries". But a prefix can cover partitions the sweep kept:
   - `u:<sub>/s` covers the current session's partition;
   - `u:<sub>/t17` also prefixes `u:<sub>/t170`.

   Emptying would blank kept data, so receivers re-read the matching entries in one readonly
   transaction instead. Deleted ones come back absent. The sweeping tab itself empties exactly
   what its rule deleted.
2. **The open times out after 3 s and falls back to memory mode.** §2.7 covers only an `open` that
   fails. An open that never settles (a blocked upgrade, browser bugs) must not hold the app's
   start.
3. **The bus waits for the Core chunk, and the boot step waits for the bus.** The slug lives in the
   Core chunk, and spec 0024 §4.3 runs the initializers in parallel. So the bus opens on
   `TmClientMetadataStore.loaded` and queues earlier posts. `ɵstart` awaits `ɵopened` before its
   `readAll`, so no `store.changed` slips between the read and the subscription. The warm path
   keeps one transaction.
4. **The boot step writes `sub` itself** after its sweep and read. §2.6 and 0024 §8.1 assign the
   write to TmSession. Doing it here guarantees the ordering the PC-069 watch-list lead asks for,
   with no extra coordination.
5. **The interim expiry signs in instead of reloading.** This is the PC-069 → PC-075 dedupe: once
   `sub` is recorded, a reload reaches the boot script's 3c branch, which reports the expiry a
   second time. The new body follows §8.6's clean-up order where it can: sweep, cookie, then
   sign in. Its sign-in mark carries `expired: false`, so the expiry is reported exactly once.
   `TmClientCache.clearAll` (core-ui), the broadcast and the dialog remain PC-110's.
6. **The 20-user `zone` cap is not implemented here.** It belongs to TmDeviceZone's `patch` updater
   (spec 0024 §7.8, PC-152). The store tests pin that `zone` survives every sweep and the expiry
   delete, and that the boot step mirrors it.
7. **The boot step is not registered as an initializer.** `bootstrapTellma`/`provideTellma`
   initializers are PC-103's. `ɵstart` is exposed and noted in the WATCHLIST.
8. **Telemetry values were chosen where §15 leaves them open:**
   - `tm.store.unavailable.reason`: `missing|failed|version|timeout|local-storage`;
   - `tm.store.quota.reason`: `put|patch`;
   - `tm.store.sweep.rule`: `session-ended|session-other-than|tenant`.
9. **Testing additions beyond §1's list.**
   - `provideTellmaStateTesting` also provides `TmFakeSession`. Without it the in-memory store's
     guard refuses every write, since no profile cookie exists in a test.
   - Fake locks and `TmFakeHub` belong to the leader checkpoints.
   - Both providers report `tm.store.unavailable {reason: 'missing'}` once when the store first
     opens, as a browser without IndexedDB would. Session specs now filter to `tm.session.*`
     events.

### Budget

The `@tellma/core` primary was measured at 12.47 KB before and 16.56 KB after (+4.09 KB; rxjs is
external). That is within spec 0025's 9 KB share. The ceiling was raised from 12.5 to 16.75, with a
budgetNote. The boot bundle is unchanged: `tmUserKeyBounds` keeps its own body, because routing it
through `tmPrefixKeyBounds` cost 1 B over the 3,072 B cap.

### Open risks, and what reviewers should examine hardest

- **Store ↔ session cycle.** The cycle is broken only by lazy `Injector.get`, in the store, the bus
  and the session paths. A future eager `inject(TmSession)` in any of them reintroduces it.
- **The `put` mirror race.** The mirror is set before the transaction, and a concurrent
  `store.changed` re-read is suppressed for pending keys. Check the `#pending` counting under
  overlapping writes to the same key.
- **The `sessionOtherThan` two-range bounds** (`bound([prefix],[kept],false,true)` and
  `bound([kept,[]], upper, true)`), against the `sY4kQ1x-_`/`sY4kQ1x-_X` vectors.
- **The interim expiry signs in instead of reloading** (deviation 5). The boot page's sign-in
  loop guard still covers the "sign-in keeps failing" case, through the existing `showPage`
  branch.
- **`TmFakeSession` is provided as `TmSession` via `useExisting`** without subclassing (TmSession
  is concrete, with private fields). Every consumer only calls `profile`, `state`, `check` and
  `signIn`, but a new public member on TmSession must be mirrored in the fake.
- **Not done:**
  - the boot step's registration (PC-103);
  - sign-out's clean-up patch (PC-110);
  - the `zone` cap (PC-152);
  - the dump section `state` (spec 0026).

### Findings

**R1-1 (blocking): building the bus before the Core chunk loads breaks `TM_CLIENT_METADATA` for the
whole app.**

- **Where:** `client/projects/core/tellma-core/src/state/bus/tm-tab-bus.ts:152-158` (`#slugOf`),
  together with `src/metadata/tm-client-metadata.ts:173-180` and `:194-197`.
- **The failure:**
  - `#slugOf` calls `this.#injector.get(TM_CLIENT_METADATA)` and catches the "not loaded yet"
    error. The token's root factory is `inject(TmClientMetadataStore).get()`, which throws before
    `set()`.
  - Angular's `R3Injector.hydrate` (22.0.5, `_pending_tasks-chunk.mjs:1306-1330`) sets
    `record.value = CIRCULAR` before it runs the factory. It never resets the record when the
    factory throws.
  - So every later `inject(TM_CLIENT_METADATA)` in the root injector throws `NG0200: Circular
    dependency`, even after the Core chunk loads. This hits `TmHttpApi` and everything else that
    reads the metadata.
  - I reproduced it with Angular 22.0.5's own injector, using a throwaway Node script outside the
    repo: `Injector.create` with `ɵINJECTOR_SCOPE: 'root'` and a root-scoped token whose factory
    throws once. The first `get` throws "not loaded"; the second `get`, after loading, throws
    NG0200.
- **When it bites:** deviation 3 exists for exactly this case: the bus is built before the chunk
  loads. The WATCHLIST lead tells PC-103 to run `ɵstart` as an initializer beside the Core-chunk
  load. `ɵstart` injects the store, the store injects the bus, and the bus poisons the token, so
  every production boot would break.
  - It is latent today only because nothing registers `ɵstart`.
  - An expiry before the chunk loads would trigger it too: `#signInAgain` injects the store.
- **Why the tests pass:** `tm-tab-bus.spec.ts:130-141` ("holds the posts made before the Core
  chunk loads") never injects `TM_CLIENT_METADATA` after `set()`.
- **Fix:**
  - Never resolve the token before it can succeed. Read the slug from `TmClientMetadataStore`
    instead: an internal non-throwing `ɵpeek(): TmClientMetadata | null`, else `loaded`.
  - The specs that provide `TM_CLIENT_METADATA` by `useValue` would then need `set()` called, or
    `provideTellmaTesting` should call it, or `#slugOf` should check `TmClientMetadataStore`
    first and fall back to the token only once the store reports it loaded.
  - Add a regression test: build the bus before `set()`, call `set()`, then assert that
    `TestBed.inject(TM_CLIENT_METADATA)` returns the chunk and the bus opens.

**R1-2 (major): `ɵstart` passes any IndexedDB failure after the open up to its caller, so once it is
an app initializer a storage fault stops the app from starting.**

- **Where:** `client/projects/core/tellma-core/src/state/store/tm-client-store.ts:479-492`
  (the backstop `sweep` and the `readAll`), and `#transact` at `:714-724`.
- **The failure:**
  - `#open` falls back to memory on every open failure. But a transaction that aborts after a
    successful open makes `ɵstart` reject. Such a transaction ends with `UnknownError` on a
    corrupt Chromium backing store, or with WebKit's "Connection to Indexed Database server lost".
    A second `InvalidStateError` after the single retry does the same.
  - Registered as an app initializer (WATCHLIST, PC-103), that rejection fails
    `bootstrapApplication`.
  - Spec 0025 Decision 13 and §2.7 say no IndexedDB means memory mode and "nothing breaks". A
    cache must not stop the app.
- **Fix:** wrap the sweep and `readAll` in `ɵstart` in a try/catch:
  - report the error through `TmTelemetry.error`;
  - switch to memory mode, emitting `tm.store.unavailable { reason: 'failed' }`, or at least
    continue cold;
  - add a test with a transaction that aborts.

**R1-3 (minor): after the 3 s timeout, a sweep reports success but deletes nothing, and both
callers then treat the data as gone.**

- **Where:** `tm-client-store.ts:442-455` (the sweep resolves normally when `#transact` returns
  `null`) and `:499-501`; `src/session/tm-session-paths.ts:114-131`.
- **The failure:** in memory mode reached by `timeout`, IndexedDB exists and still holds data.
  - The boot step's backstop sweep is a no-op, yet it still writes `sub: P`. So the next launch
    (B = P) skips the backstop.
  - On the changed-user path, the boot script only resets the record, so the backstop is the only
    thing that deletes the previous user's partitions. Those partitions now stay on disk until P's
    next session ends.
  - Likewise, the interim expiry treats the no-op sweep as `swept` and keeps `sub`. The returning
    launch then skips the backstop, and P's pre-expiry documents can read warm whenever `sync.at`
    is recent, because syncs do not renew the session.
  - This works against the goal "a session that ends takes its stored data with it".
- **Fix:**
  - Have `sweep` tell its callers whether it deleted on disk, for example resolve `false` when
    nothing committed and IndexedDB exists.
  - Have `ɵstart` skip `boot.patch({ sub })` when a needed backstop did not commit.
  - Have `#signInAgain` treat a non-committed sweep like a cut-short one and patch `sub: null`.
  - With `missing`, nothing is on disk, so nulling `sub` there is harmless.

**R1-4 (minor): no test covers the user channel switching when the user changes.**

- **Where:** `tm-tab-bus.ts:178-185` (the effect) and `:208-215` (`#bindUser`).
- **The gap:** spec 0025 §6.1 says the user channel "is replaced when the user changes". This is
  what keeps a tab from hearing the previous user's `store.changed`, `prefs.changed` and
  `hub.event`. No bus spec changes the profile after open: `tm-tab-bus.spec.ts` covers no user,
  one user and bfcache only. A broken effect, such as a missed `untracked` or the wrong equality
  in `#bindUser`, would pass every test.
- **Fix:** add a spec that opens as Farah, switches the profile to another `sub` (cookie plus
  `check()`), flushes effects, and then asserts both directions:
  - a post on `tm:acme:<old>` is no longer received, while `tm:acme:<new>` delivers;
  - `bus.post` now goes to the new channel.

**R1-5 (minor): the quota test fakes a failure path no browser takes, and the real path is
untested.**

- **Where:** `tm-client-store.spec.ts:476-488`.
- **The gap:** the spec makes `IDBObjectStore.put` throw `QuotaExceededError` synchronously.
  IndexedDB never does that. A quota failure surfaces as the request's error and a transaction
  abort with `transaction.error` set, which goes through the `onabort` branch at `:722-723`.
  - The test therefore exercises the `try/catch` and `fail()` branch at `:330-336` and `:378-391`.
  - On that branch `patch` never sets the mirror (`:392` is skipped). Spec §2.7 says "the value
    stays in this tab's mirror", and the test does not assert the patch's mirror at all.
- **Fix:** simulate the abort instead, for example by making the transaction abort with a
  `QuotaExceededError` as its `error`. Then assert, for both `put` and `patch`, that the new value
  is in the mirror, that `tm.store.quota` is emitted, and that nothing is posted.

**R1-6 (minor): the fake session's public shape can drift from the real one without a compile
error.**

- **Where:** `client/projects/core/tellma-core-testing/src/tm-fake-session.ts:40`.
- **The failure:** `TmFakeSession implements Pick<TmSession, 'profile' | 'state' | 'check' |
  'signIn'>` and is provided as `TmSession` with `useExisting`. Spec 0024 §8.1 declares
  `signOut()`, which PC-110 adds. Once it exists, code under test that calls
  `session.signOut()` against `provideTellmaStateTesting()` fails at run time with
  `signOut is not a function`, and nothing fails at compile time.
- **Fix:** implement the whole public surface, for example
  `implements { [K in keyof TmSession]: TmSession[K] }`. Private `#` fields are not in `keyof`, so
  this compiles today and breaks the build when TmSession gains a member. Also mention it in the
  WATCHLIST lead for PC-110.

**R1-7 (minor): the testing providers add a production telemetry event to every consumer test.**

**R2-1 (major): after the open, a storage fault makes `put`, `patch` and `readAll` reject, and a

- **Where:** `client/projects/core/tellma-core/src/state/store/tm-client-store.ts`:

  - `#transact` at `:729-741`, the one retry;

  - `readAll` and `#reread` at `:271` and `:704`.
- **The failure:**

    backing store, WebKit's "Connection to Indexed Database server lost", and a second
    `InvalidStateError`. The fix catches them only in `ɵstart`. The same faults mid-session reject

**R2-2 (minor): a `patch` can land after a sweep that started after it, and a write in flight
refills the mirror a sweep has just emptied.**

- **Where:** `tm-client-store.ts`:
  - `:383`, the extra `await this.#database()` before `#write`;
  - `:723`, the second await, in `#transact`;
  - `:407` and `:342`, the mirror writes from inside the request;
  - `:455-468`, `sweep`.
- **The failure, part 1: the order.**
  - `put` and `sweep` each create their transaction one microtask after the call. `patch` takes
    two microtasks.
  - So the sweep's readwrite transaction is created first when the two start in the same turn. It
    is also created first when both wait on a database that is still opening, whatever the order
    of their tasks, because both resume in one microtask run.
  - The `patch` then reads nothing and writes `update(undefined)` into the swept partition. The
    value lands on disk after the delete, and in the mirror.
  - Two consequences:
    - with `{ tenant: t }`, which the presenter runs on `tenant-not-found`, a tenant document
      reappears;
    - an expiry sweep keeps `sub`, so it leaves behind a document that no backstop will take.
- **The failure, part 2: the mirror.** This part does not depend on the order.
  - Take a `patch`, or a `put` that meets a later stored copy, whose transaction comes before the
    sweep's. It still runs its `onsuccess` after `sweep()` emptied the mirror, and sets the entry
    again.
  - The sweep then deletes the record. The sweeping tab never hears its own `store.changed`, so its
    mirror keeps a document that is gone.
  - Spec 0024 §8.4 keeps writes allowed while sign-out waits, so a save's adoption can be in flight
    at the clean-up.
- **Fix:**
  - Create `patch`'s transaction through `#write` directly, and handle memory mode through the
    `null` result (R2-1).
  - In `sweep`, after the commit, empty the matching entries again, except those with a write
    started after the sweep. Alternatively, keep a sweep generation per entry and ignore an older
    write's `onsuccess`.
  - Test: start a `patch` on tenant 17, call `sweep({ tenant: 17 })` in the same turn, and assert
    that both the disk and the mirror are empty.
