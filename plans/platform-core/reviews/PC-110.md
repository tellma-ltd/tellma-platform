# PC-110: Service worker updates, error presentation and session paths

## Implementer notes

### What was built, and where

All client-side; no C# changes. Paths are under `client/projects/core/` unless noted.

### Deviations

1. **Placement.** TmUpdates, the worker registration and the Trusted Types policy live in the
   lazy `@tellma/core/updates`. TmErrorPresenter, `tm-error-state` and the step-up dialog live in
   the lazy `@tellma/core/errors`. The session flows live in a lazy chunk of the primary. Spec 0024
   §1 places all of them in the primary; they moved for the primary's 50 KB cap. Against §1's list
   of allowed dynamic-import sites, the primary gains three:
   - `TM_UPDATES_LOAD`, for the startup's `TmUpdates`, `TM_API_UPDATES`' first check and
     `./errors`' Reload;
   - `TM_ERRORS_LOAD`, for the cache refresher's `TM_SYNC_ERRORS` and the route view's
     `client-outdated` state;
   - the `./tm-session-flows` chunk, which `TmSessionPaths` loads and the startup preloads.

   Specs 0030 and 0031 cite `TmErrorPresenter` and `tm-error-state` from the primary; they import
   them from `@tellma/core/errors`.
2. **The update banner's source is in TmUpdates (`./updates`), not in `tmPlatformBanners()`.** Its
   `refresh-cw` icon registers there rather than in TM_PLATFORM_ICONS, and its message is
   `tm.updates.banner` rather than under `tm.attention.banners`. The banner still shows from the
   app's first settle, with the id `tm.update`, level 3, dismissible per version, and Reload
   running `reload()`.
3. **The error views' icons** (circle-alert, clock, lock, refresh-cw, search-x) register in
   `./errors` when no feature drew its own, not in TM_PLATFORM_ICONS.
4. **`SwUpdate` comes from `provideServiceWorker` in a child environment injector**, with Angular's
   registration disabled. `tmRegisterWorker` registers itself through a TrustedScriptURL, because
   Angular's registration passes a plain string, which the CSP's Trusted Types refuse.
5. **`NO_NEW_VERSION_DETECTED` naming a version other than the running one reads as `ready`.**
   The `VERSION_READY` that announced it may have reached the worker before this tab listened.
6. **TmUpdates runs one check once its worker is registered** (changed in review 1), beyond
   §5.5's rows. Without it, a `VERSION_READY` that the worker broadcast before `./updates` loaded
   is missed until the 6-hour check. The start check's "no new version" naming another version
   (deviation 5) recovers it, at one `ngsw.json` request per launch.
7. **`TmErrorView` gains `permission`**, the raw pair rendered in a left-to-right `bdi`, and
   **`TmErrorContext` gains `tenantId`**, so a background sync of a tenant other than the routed
   one is handled for its own tenant. **`TM_SYNC_ERRORS.present` takes that tenant id.**
8. **The error dialogs' support actions (Copy diagnostics) are not wired.** They wait for the
   support service of spec 0026.
9. **The tenant-state page is `tm-error-state` itself**, replaced into the shell's main area for
   `tenant-unavailable`.
10. **The `errors` strings scope merges into the existing `tm.errors`.** Reload's three strings
    moved into that scope in review 1, with the flow that shows them.
11. **Order of the expiry path.** The session turns `expired` before the clean-up runs, not after,
    so nothing renders the user's data while the flows chunk loads.
12. **The session-ended alertdialog ignores Escape and has no close button.** Only Sign in leaves
    it, because the session is gone. This departs from the Done-when's "Escape" for this one
    dialog.
13. **The 1 s sweep box also bounds sign-out's clean-up**, not only the expiry's. A sign-out
    clears the boot record's user and last tenant whether or not the sweep applied, so the next
    launch sweeps again when it did not.
14. **A tab that hears `session.signed-out` runs its own tab-local clean-up** before it shows
    the signed-out page: its session storage and the user's drafts. The signing-out tab already
    swept the shared stores.
15. **The changed-user path keeps its telemetry flush** before it leaves.
16. **`session.started` for the same user reloads only the tabs whose session is not active.**
17. **`pageshow` re-checks without looking at `persisted`.** After the chunk has loaded, any
    `pageshow` is a return from the back-forward cache.
18. **Tooling.** `scripts/bundle-size.mjs` starts its static-graph walk at the output built from
    the entry's FESM. It had picked an arbitrary output before, which reported a false
    "'.' reaches './leader'".

19. **`TmSession.signOut()` returns `Promise<void>`.** It never settles once the tab leaves, but it
    resolves when the user cancels the confirm and rejects, after the toast, when the sign-out
    fails. §8.1 declares `Promise<never>`, which cannot tell a caller that the tab stays.
20. **The sign-in-failed page on an in-app expiry.** An expiry within 60 s of the consumed
    sign-in mark's `at` shows `sign-in-failed` instead of the session-ended dialog, so a sign-in
    whose cookie is refused at once does not loop. §8.6 step 3 shows the dialog, and §4.2 3b's loop
    guard covers only a boot. The window runs from `at`, which is stamped when the sign-in starts.
    A sign-in longer than a minute (an email code, say) therefore never reaches this branch and
    shows the dialog, as §8.6 says.
21. **The client-outdated route view renders `tm-error-state`** once `./errors` loads: the
    presenter's 412 view, with its info tone, `refresh-cw` icon and Reload. Until then, or when
    `./errors` does not load, it shows a plain empty state whose Reload is a plain reload.
22. **`TM_API_UPDATES` is `check()` only.** §5.4 gives the primary seam `update()` and `reload()`
    too. Lazy callers reach `TmUpdates` through `TM_UPDATES_LOAD` (the internal `TmWorkerUpdates`
    shape), via `./errors`' `TmErrorUpdates`.
23. **`TmErrorUpdates` reloads at once when no service worker controls the page**, without
    loading `./updates`. That is §11 step 2's `disabled` outcome, decided before the import rather
    than by it. An app with no update service (a test app) reloads the same way.
24. **`TmModalConfig` gains `closeOnNavigation`** (default `true`). The session-ended dialog
    passes `false`, so history navigation does not close it; with deviation 12, only Sign in
    leaves it.

### Open risks

- The primary budget (see above): the reserved 1.8 KB no longer fits under 50 KB.
- `TmUpdates` against a real worker is covered only by the scripted `SwUpdate` fake here; the
  e2e updates flow (PC-114) is the first real-worker run. Angular's `NO_NEW_VERSION_DETECTED`
  carrying another version than the running one is read as ready, which relies on Angular's
  current event semantics.
- The flows chunk is preloaded after the first render; an expiry or a bus message before it
  loads waits on the import (the state turns `expired` first, so nothing renders stale data).
- `pageshow` re-checks without looking at `persisted`, so an ordinary load also re-checks once;
  this is cheap (one cookie read) but worth a glance.

### What reviewers should examine hardest

1. `tm-session-flows.ts` `#signOut` and `#wait`: the drafts loop, the 60 s cap, the confirm
   variants, and that a cancel or failure leaves every tab usable (the lift, the toast, the
   restored state).
2. `#cleanUp`: what is kept for expiry versus sign-out, and the `sub: null` rule when the sweep
   does not apply (the PC-075 carry).
3. `TmUpdates.check()`: the event-during-check detection, joining a running check, and the
   `NO_NEW_VERSION_DETECTED` tie with another version.
4. `TmErrorPresenter.present()` tenant-not-found and tenant-unavailable: the per-tenant guard,
   `replaceUrl` only when routed, and the sweep.
5. The lazy placements against spec 0024 §1's entry list, and whether any first-frame caller
   now waits on an import it should not.

### Findings

**R1-1 (major): `./errors` has no enforced ceiling, and the two new budget notes are in `budgetsInKb`, not `budgetNotes`.**
`client/projects/core/tellma-core/package.json:47-57`. `budgetsInKb` holds `"./errors": 6` and
then `"./errors": "Born at 5.52 KB …"`. It also holds `"./updates": "Born at 2.17 KB …"` and
then `"./updates": 2.5`. `JSON.parse` keeps the last value of a duplicate key:
- `budgetsInKb['./errors']` is the note string.
- `bundle-size.mjs:130` compares `gzipped > kb` against that string. The comparison is
  `NaN`-false, so `./errors` can grow without limit and the row still reads `ok`. The
  size:check table above shows the note text as the ceiling.
- `./updates` keeps 2.5 only because the numeric value happens to come last.
- `budgetNotes` has neither entry (`node -e` lists its keys). The rule "a raise with no note is a
  bug" therefore fails for both new entry points.
- esbuild reports both duplicates as warnings in the test build.
- Once PC-F76 merges, its `ceilingProblem` check (`budgetsInKb['./errors']` is not a positive
  number) turns this into a red size:check at integration.

*Fix:* keep `"./errors": 6` and `"./updates": 2.5` in `budgetsInKb`, and move the two
"Born at …" texts into `budgetNotes`.

**R1-2 (major): browser Back closes the session-ended dialog for good, which strands the tab.**
`tm-session-flows.ts:569-590`. `TmModal` opens through the CDK `Dialog`, which defaults to
`closeOnNavigation: true` (`@angular/cdk` `dialog.mjs:60`). The `OverlayRef` subscribes to
`Location` and disposes on popstate (`_overlay-module-chunk.mjs:777-778`). The detachment closes
the `DialogRef` (`dialog.mjs:374-376`), and `TmModalRef` reports that as an `'api'` close
(`tm-modal-ref.ts:165-170`). `escapeDismiss: false` and `backdropDismiss: false` do not cover
this path.

Scenario: the session expires, and the alertdialog shows. The user presses Back, Alt+Left or a
mouse back button.
1. The dialog closes.
2. `#ended` stays `true`, so `#showEnded` never opens it again.
3. The router's popstate navigation runs `tmSessionGuard`. `check()` returns `missing`.
   `paths.expired('cookie')` returns early, because the state is already `expired`, and the guard
   denies.
4. Every later in-app navigation is denied the same way.

The tab shows stale data, its reads are cancelled, and there is no Sign in anywhere until the user
thinks to reload. That breaks deviation 12's own premise that "only Sign in leaves it", and §8.6
step 3.

*Fix:* in `#showEnded`, subscribe to the ref's `closed`. While `this.#paths.state()` is still
`expired`, reset `#ended` and open the dialog again. The alternative is to add a
`closeOnNavigation` option to `TmModal`'s config and pass `false`.

*Test:* open the dialog, dispatch a `popstate` (or call `Location.back()` on a pushed state), and
expect the alertdialog to be present with focus on Sign in.

**R1-3 (major): the Done-when "Sign-out reaches every tab in a multi-instance unit harness" is not met.**
`tm-session-flows.spec.ts:39-64, 294-433`. Every sign-out test runs one `TmSessionFlows` against
`TmScriptedTabBus`:
- The "other tabs" are reply scripts that answer `drafts.query` with fixed `{ dirty, busy }`.
- The other side is played by hand with `rig.bus.receive({ type: 'session.signing-out' … })`.

No test has a second real `TmSessionFlows`, `TmSessionPaths` and `TmApi` hear the acting tab's
messages. So nothing proves the round trip:
- that a real tab's `#answer` (its `writesInFlight`, its drafts) reaches the acting tab's `#ask`
  within 300 ms;
- that its `session.signing-out` handler turns its state and aborts its reads;
- that `session.signed-out` takes every tab to `/signed-out`.

The checkpoint's Tests line asks for this too: "the sign-out state machine with fake bus and
drafts".

*Fix:* add a harness with two or three tab instances on one in-memory fabric. Each tab needs its
own environment injector (via `createEnvironmentInjector` over the test app's, or one per
`createApplication`), with its own `TmSessionPaths`, `TmSessionFlows`, `TmApi` fake,
`TM_DRAFTS_STORAGE` and session host. A fabric bus delivers each post to every other tab's
`messages`. Then assert three things across real instances:
- a busy tab holds the sign-out until its write settles;
- a dirty tab's count reaches the confirm;
- every tab ends at `/signed-out` with its session storage cleared.

**R1-4 (minor): Reload with no worker in the way still depends on loading `./updates`.**
`src/api/tm-api-seams.ts:105-119`. Spec 0024 §11 step 2 says Reload reloads at once on "`disabled`
with no worker in the way". The seam only learns `disabled` after
`import('@tellma/core/updates')` succeeds. A failed import answers `unreachable`. Then the route
error view (`tm-route-error.ts:143-149`), `tm-error-state` and the 5xx dialog all show "Couldn't
download the update", and they need a second failure before "Reload anyway" appears.

This happens in a tab whose post-first-render preload of `./updates` failed: browsers keep a
failed module fetch in the module map, so every later `import()` fails too. It also happens with
no controlling worker after a deployment has removed the old hashed chunk. The client-outdated
route view is the main Reload caller, and it appears exactly when chunk loads fail.

A related point: the seam's `update()` answers `disabled` without reloading when the loader yields
`null`, as `provideTellmaStateTesting` makes it do. That breaks the seam's own TSDoc ("reloads …
on `disabled`").

*Fix:* in the seam, read `navigator.serviceWorker?.controller` (through `DOCUMENT`). When it is
null, call `location.reload()` and answer `disabled` without importing anything. Do the same when
the import fails and there is no controller. This costs a few bytes and also keeps `update()`
true to its contract. It falls away if the budget move suggested below (C1) is taken.

**R1-5 (minor): a `VERSION_READY` that arrives before `./updates` loads is missed for up to 6 hours.**
`updates/src/tm-updates.ts:174-222`. `NgswCommChannel` adds its `message` listener when
`TM_UPDATES_HOST` builds `SwUpdate`. That happens after the first render, when the startup imports
`./updates`. A `VERSION_READY` broadcast before that is lost. Deviation 6 means nothing calls
`check()` at start, so deviation 5's "no new version naming another version" recovery never runs.
The banner then waits for one of three things: the 6-hour timer, a return after an hour hidden, or
a 412. Angular's worker checks about 5 s after a navigation, so this needs a slow start or a slow
