# PC-089: Blob web surface, Azure adapter and the Azure defaults

## Implementer notes

### What was built

- **Blob web surface (`src/core/Tellma.Core.AspNetCore/Blobs/`).**
  - `BlobEndpoints.MapTellmaBlobs(RouteGroupBuilder)`, called by `MapTellma` on the `Blobs` group right after the web API projection.
    - `POST /{tenantId}/blobs/{kind}?fileName=`: `AllowMember`, `WithMutation(true)`, `AcceptsBinary(BlobOptions.MaxUploadSize)`, `tellma-long` timeout. It hands the raw body, `Content-Length ?? -1`, `Content-Type` and `fileName` to `IBlobService.StageAsync`. It answers `201` with the `BlobDescriptor` and `Location: /{tenantId}/blobs/{staged.Kind}/{id}`. A `fileName` over 255 characters is `400 bad-request`. The service's refusals map through the existing `ProblemMapper` (`blob-rejected` 404/411/413/415/422, busy 503).
    - `GET /{tenantId}/blobs/{kind}/{id:int}?variant=&download=`: `AllowMember`, `WithMutation(false)`, `RequireRatePolicy(tellma-blobs)`. The order is: guards stamped in `OnStarting` (so a problem, a 304 and an exception-handler answer carry them too), `ResolveAsync` (the authorization, one round trip; null → `404 not-found`), ETag and `Cache-Control` from the row, `If-None-Match` → `304` without the store, `OpenReadAsync(RequireTenant().Id, StorageName)` (null → `404 not-found`), a primary-length integrity check (`content.Length != Size` → `BlobStoreException` → `500`), `Content-Disposition`, `DisableTimeout()`, then `Results.Stream(..., entityTag, enableRangeProcessing: true)` for 200/206/416/If-Range. An empty `variant` is the primary.
  - `BlobResponseHeaders`: the constants and pure functions (CSP `frame-ancestors 'self'`, `nosniff`, `Cache-Control` by state, inline set = the four image types + PDF + the three text types, RFC 8187 `filename*` encoding, the weak `If-None-Match` comparison with `*`).
  - `BlobDownloadMetrics`: `tellma.blobs.downloads{kind,outcome}` on the `Tellma.Core` meter. It is registered in `AddTellma` beside `ApiMetrics`. A kind no reference declares is never counted, as the upload does.
  - `AcceptsBinaryMetadata` now implements `IRequestSizeLimitMetadata`, so routing raises Kestrel's body limit to `MaxUploadSize` on the upload. The JSON ceiling already skipped binary endpoints.
  - `MapTellma`: the telemetry stage (`ApiTelemetryFilter.Wrap`) now wraps the `Blobs` group as well as `Web` (D-137), between the witness and the guard.
- **Azure adapter (`src/connector/azure-blobs/Tellma.Connector.AzureBlobs.Adapter/`, namespace `Tellma.Connector.AzureBlobs`).**
  - `AzureBlobStore` (internal, `IBlobStore`): one `BlobServiceClient` per process, container `{ContainerPrefix}t{tenantId}`.
    - Create-only uploads (`IfNoneMatch = ETag.All`; 409 `BlobAlreadyExists` or 412 → `BlobAlreadyExistsException`). Single put up to 256 MiB, otherwise 8 MiB blocks committed at once. A seekable content's length is checked up front. A content that cannot seek reads through `LengthGuardStream`, which fails an early end or an overrun with `InvalidDataException`, a type the SDK does not retry.
    - Lazy ensure (`CreateIfNotExists`, private) remembered per process. `ContainerNotFound` on a write forgets the container, logs `BlobTenantMissingOnWrite`, ensures it again and retries once (seekable content only).
    - Ranged `OpenRead` (`allowModifications: false`, `BufferSize = ReadBufferSize`): its open fetches properties, so a missing object is null at open and the length is known.
    - Bounded-parallel deletes (`MaxParallelism`, snapshots included, 404 = success). Listing by `prefix + "/"` skips names outside the grammar. The purge is a no-op. Every call is metered on the shared `Tellma.Blobs` instruments (`AzureBlobStoreMetrics`, the same names, units and descriptions as Core's `BlobStoreMetrics`).
  - `AzureBlobStoreOptions` (the spec's five members, `SectionName = "Tellma:Blobs:Azure"`), and `AzureBlobStoreOptionsValidator` (exactly one of `ServiceUri`/`ConnectionString`; absolute HTTPS endpoint; prefix + `t2147483647` a valid container name; positive limits).
  - `AzureBlobStoreCheck` (`blobs.azure`, needs infrastructure): validator failures, an unparsable connection string, an endpoint with no credential. It sends nothing to the account.
  - `AzureBlobsComposition.AddAzureBlobStore(services, configure, TokenCredential? credential)`: the spec's signature. The first call registers the store, the validator, the check and the metrics. Later calls add their settings action, and a credential when they pass one. A null credential resolves the host's registered `TokenCredential` when the store is built. The adapter never constructs one.
- **Azure defaults (`src/defaults/Tellma.Defaults.Azure`).** It references the adapter (Imaging was already referenced). `UseAzureDefaults()` registers `AddTellmaSkia()` plus exactly one store:
  - the Azure store when `Tellma:Blobs:Azure` exists, bound from it;
  - else the file-system store in Development;
  - else, outside Development, the Azure store with nothing bound, so `blobs.azure` fails startup.
  The credential is the host's `TokenCredential`, which `AddAcsEmail` already `TryAdd`s as `DefaultAzureCredential`. README and the csproj description are updated.

### Deviations

1. **The Azure option checks are a check of the adapter's own, `blobs.azure`, not part of `blobs`/`blobs.deployment`** (spec §9 lists them under the one `blobs` check, and the checkpoint's done-criterion says "the `blobs` check fails"). Core never references an adapter, so it cannot see `AzureBlobStoreOptions`. The adapter contributes an `IStartupCheck` that runs in the same realised gate with the same effect.
2. **A fifth test project, `Tellma.Connector.AzureBlobs.Adapter.Tests`** (spec §12 says four). The validator, the length guard and the composition need no emulator, so they run in the PR unit tier on every OS rather than only where Docker runs.
3. **`UseAzureDefaults` outside Development registers the Azure store even without its section** (spec §1.3 says the bundle "picks one"). Picking none would leave the generic "no store" problem; registering the Azure store makes the failure name the missing Azure settings. A configured section also wins in Development (Azurite).
4. **The upload takes `tellma-long`** (the spec gives no timeout). A 100 MiB body over a slow link outlasts the 30 s web timeout.
5. **The download lifts its request timeout once the object is open** (time-to-first-byte, D-145), via `IHttpRequestTimeoutFeature.DisableTimeout()`. `DisableRequestTimeout()` metadata would fail the endpoint audit. Streaming is then bounded by Kestrel's minimum data rate.
6. **A `fileName` over 255 characters is refused with `400 bad-request`** (the spec's request column states the limit; the sanitiser would otherwise shorten it silently).
7. **A stored primary whose length differs from its row's `Size` answers `500`** rather than serving. `Results.Stream` takes the length from the stream, and spec §5.3 wants `Content-Length` = the row's `Size`. A mismatch is corruption.
8. **The guards (CSP, nosniff) are stamped in `OnStarting`**, so they ride every download response, problems and exception-handler answers included, which `Response.Clear()` would otherwise strip.
9. **The `If-None-Match` comparison is the weak one RFC 9110 prescribes, and `*` matches.** Spec §5.3 says "match" without detail.
10. **The download counter skips undeclared kinds** (spec §10.1 says nothing). This follows the upload counter's rule, so a client cannot open the `kind` tag.

### Open risks

- **The `tellma-blobs` concurrency permit is held for the whole stream.** A tenant's 32 permits (queue 256) can be held by slow large downloads, and avatars then queue behind them. This is inherent to the spec's concurrency policy. A separate lane for large bodies would be a 0016 §8.2 change.
- **An SDK retry after a lost success answers 409 → `BlobAlreadyExistsException`.** This fails closed: the stager's write fails, and the staged row expires into the sweep. Upload blob names are random, so no real conflict is masked.
- **Real Azure differs from Azurite:**
  - `ContainerBeingDeleted` (409) can follow a container's removal; the write fails rather than retrying.
  - Storage Blob Data Contributor must cover `CreateIfNotExists`; spec §11 leaves that to the first deployment, with BlobContainerStep pre-creating as the fallback.
- **Above 256 MiB, or for a content that cannot seek, the SDK stages blocks.** Two writers racing to one name could both stage; only the commit is conditional, so the loser still fails, but it uploaded its blocks for nothing. Upload names are random 32-hex keys, so this is theoretical.
- **One 1 MiB buffer is rented per download stream** (`ReadBufferSize`), within the 32-per-tenant concurrency.
- **The telemetry stage stamps `Content-Language`, `Tellma-Calendar` and `Tellma-Version-Tags` on blob responses too.** This is harmless, but it is new on this surface.
- **Acme blob tests depend on Skia natives and real decoding on the CI runner** (Linux). The 1×1 PNG fixture is the smallest valid image.

### What reviewers should examine hardest

- **Tenant isolation.** The download opens `RequireTenant().Id`, never the route value. `StorageName` comes only from `ResolveAsync`'s row in the scope's tenant database. Azure container names derive from the tenant id and a validated prefix. Is there any path where a route-supplied tenant id or kind reaches a storage key? (Kind and variant reach `ResolveAsync`, which validates them, and the variant name grammar.)
- **Authorization on both endpoints.** Both are `AllowMember` (member witness). The upload's finer checks are the stager's (kind, quota, uploader). The download's are `ResolveAsync`'s (owner read, staged-to-uploader, step-up on sensitive owners). A 304 discloses only that the caller may read the blob, since it follows `ResolveAsync`.
- **The order of the timeout lift relative to the response start, and `TimeoutAbortMiddleware`** (which acts only when the timeout token fired).
- **`LengthGuardStream`'s seek and rewind semantics under SDK retries**, and the `ContainerNotFound` retry (a seekable content only).
- **`UseAzureDefaults` selection** (deviation 3), and the `blobs.azure` check name (deviation 1).
