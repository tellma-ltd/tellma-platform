### What was built

- **Blob web surface (`src/core/Tellma.Core.AspNetCore/Blobs/`).**
  - `BlobEndpoints.MapTellmaBlobs(RouteGroupBuilder)`, called by `MapTellma` on the `Blobs` group right after the web API projection.
    - `POST /{tenantId}/blobs/{kind}?fileName=`: `AllowMember`, `WithMutation(true)`, `AcceptsBinary(BlobOptions.MaxUploadSize)`, `tellma-long` timeout. ### Deviations

1. **The Azure option checks are a check of the adapter's own, `blobs.azure`, not part of `blobs`/`blobs.deployment`** (spec §9 lists them under the one `blobs` check, and the checkpoint's done-criterion says "the `blobs` check fails"). Core never references an adapter, so it cannot see `AzureBlobStoreOptions`. The adapter contributes an `IStartupCheck` that runs in the same realised gate with the same effect.
2. **A fifth test project, `Tellma.Connector.AzureBlobs.Adapter.Tests`** (spec §12 says four). The validator, the length guard and the composition need no emulator, so they run in the PR unit tier on every OS rather than only where Docker runs.
3. **Not a deviation (reclassified in Review 1: spec 0011 §1.3 registers the Azure store outside Development, so a missing section fails startup).** `UseAzureDefaults` outside Development registers the Azure store even without its section. Picking none would leave the generic "no store" problem; registering the Azure store makes the failure name the missing Azure settings. A configured section also wins in Development (Azurite).
4. **Not a deviation (reclassified in Review 1: spec 0016 §8.3 names `tellma-long` for the upload).** The upload takes `tellma-long`. A 100 MiB body over a slow link outlasts the 30 s web timeout.
5. **The download replaces its web timeout with a transfer deadline once the object is open** (time-to-first-byte, D-145), via `IHttpRequestTimeoutFeature.DisableTimeout()`. `DisableRequestTimeout()` metadata would fail the endpoint audit. Since review 1 (R1-1, D-169), the transfer then has its own deadline, past which the connection is aborted: since review 2 (R2-1, D-172) `RequestTimeout` plus the object's length at 32 KiB/s, at most a day.
6. **A `fileName` over 255 characters is refused with `400 bad-request`** (the spec's request column states the limit; the sanitiser would otherwise shorten it silently).
7. **A stored primary whose length differs from its row's `Size` answers `500`** rather than serving. `Results.Stream` takes the length from the stream, and spec §5.3 wants `Content-Length` = the row's `Size`. A mismatch is corruption.
8. **The guards (CSP, nosniff) are stamped in `OnStarting`**, so they ride every download response, problems and exception-handler answers included, which `Response.Clear()` would otherwise strip. Since review 2 (R2-5) they are the host's header stamp's, on every Blobs-surface response, the guard's, the limiter's and the binder's refusals included.
9. **The `If-None-Match` comparison is the weak one RFC 9110 prescribes, and `*` matches.** Spec §5.3 says "match" without detail.
10. **The download counter skips undeclared kinds** (spec §10.1 says nothing). This follows the upload counter's rule, so a client cannot open the `kind` tag.

### Open risks

- **The `tellma-blobs` concurrency permit is held for the whole stream.** A tenant's 32 permits (queue 256) can be held by slow large downloads, and avatars then queue behind them. Since review 1 each hold ends at the transfer deadline (since review 2, 30 seconds plus about 53 minutes for a 100 MiB object), but 32 slow downloads, legitimate or reopened on purpose, still fill the lane until then. Releasing the permit before the stream, or a per-user cap, would be a 0016 §8.2 change (D-169 flags both to Ahmad).
- **An SDK retry after a lost success answers 409 → `BlobAlreadyExistsException`.** This fails closed: the stager's write fails, and the staged row expires into the sweep. Upload blob names are random, so no real conflict is masked.
- **Real Azure differs from Azurite:**
  - `ContainerBeingDeleted` (409) can follow a container's removal; the write fails rather than retrying.
  - Storage Blob Data Contributor must cover `CreateIfNotExists`; spec §11 leaves that to the first deployment, with BlobContainerStep pre-creating as the fallback.
- **Above 256 MiB, or for a content that cannot seek, the SDK stages blocks.** Two writers racing to one name could both stage; only the commit is conditional, so the loser still fails, but it uploaded its blocks for nothing. Upload names are random 32-hex keys, so this is theoretical.
- **One 1 MiB buffer is rented per download stream** (`ReadBufferSize`), within the 32-per-tenant concurrency.
- **The telemetry stage stamps `Content-Language`, `Tellma-Calendar` and `Tellma-Version-Tags` on blob responses too.** This is harmless, but it is new on this surface.
- **Acme blob tests depend on Skia natives and real decoding on the CI runner** (Linux). The 1×1 PNG fixture is the smallest valid image.

### What reviewers should examine hardest

- **Tenant isolation.** The download opens `RequireTenant().Id`, never the route value. `StorageName` comes only from `ResolveAsync`'s row in the scope's tenant database. Azure container names derive from the tenant id and a validated prefix. Is there any path where a route-supplied tenant id or kind reaches a storage key? (Kind and variant reach `ResolveAsync`, which validates them, and the variant name grammar.)
- **Authorization on both endpoints.** Both are `AllowMember` (member witness). The upload's finer checks are the stager's (kind, quota, uploader). The download's are `ResolveAsync`'s (owner read, staged-to-uploader, step-up on sensitive owners). A 304 discloses only that the caller may read the blob, since it follows `ResolveAsync`.
- **The order of the timeout lift relative to the response start, and `TimeoutAbortMiddleware`** (which acts only when the timeout token fired).
- **`LengthGuardStream`'s seek and rewind semantics under SDK retries**, and the `ContainerNotFound` retry (a seekable content only).
- **`UseAzureDefaults` selection** (deviation 3), and the `blobs.azure` check name (deviation 1).

### Findings

**R1-1 (major): one member, or a handful of slow clients, can hold every `tellma-blobs` permit of
a tenant indefinitely.**
`src/core/Tellma.Core.AspNetCore/Blobs/BlobEndpoints.cs:66-69` and `:199`, with
`src/core/Tellma.Core.AspNetCore/Limits/RatePolicies.cs:84` and
`src/core/Tellma.Core.AspNetCore/Limits/LimitsComposition.cs:90-91`.
The download's only rate policy is a concurrency limiter partitioned by tenant alone (32 permits,
queue 256, replacing `tellma-user`). The rate-limiting middleware keeps the lease until the
endpoint returns, and that includes the whole `Results.Stream` copy. Before this change the 30 s
`tellma-web` timeout bounded how long a lease could be held. `DisableTimeout()` removes that bound,
so a lease is now held for as long as the client keeps reading. The only limit left is Kestrel's
`MinResponseDataRate` default (240 B/s after a 5 s grace), which the host does not configure.
Failure scenario: a member opens 32 downloads of any blob larger than the socket buffers (an
attachment kind up to `MaxUploadSize` = 100 MiB, or their own staged upload, which they may read)
and reads each at about 250 B/s. A 100 MiB blob then holds a permit for about five days and a
1 MiB one for over an hour, and the attacker re-opens each as it finishes. Every other member's
avatar, thumbnail and PDF request in that tenant waits in the queue. Because `UseRateLimiter` runs
before `UseRequestTimeouts`, a queued request waits with no deadline until its client gives up, and
past 256 waiters the rest get 429. The same happens without malice when 32 users on slow links
download large attachments at once. The implementer lists the held permit as an open risk, but the
unbounded hold is new in this commit.
Suggested fix: keep the spec's per-tenant concurrency for time-to-first-byte only, and bound what a
single caller can hold. Either (a) take the `tellma-blobs` lease inside the handler, around
`ResolveAsync` and `OpenReadAsync`, and release it before the stream starts (the router's limiter
can be acquired directly), or (b) add a per-user cap to the chain (a `TenantSubject` concurrency
partition, for example 8, so one account never holds the whole tenant lane). In either case, (c)
replace the open-ended lift with a deadline scaled to the size (for example the long timeout plus
the length divided by a floor rate), or raise `IHttpMinResponseDataRateFeature` for blob
responses. (a) and (b) change 0016 §8.2's chain and are for Ahmad. (c) alone is local and restores
a bound. Add a test that a stalled reader stops holding its permit within the bound chosen.

**R1-2 (major): a committed blob whose object is missing answers a 404 that the browser caches as
immutable for a year.**
`src/core/Tellma.Core.AspNetCore/Blobs/BlobEndpoints.cs:164` stamps `ETag` and
`Cache-Control: private, max-age=31536000, immutable` before the store is opened, and `:173-178`
then returns `NotFound()` on a null open. `ProblemWriter.WriteAsync` sets the status and the body
but clears no header, and the global stamp adds `no-store` only to Web, Api and Mcp JSON. So the
404 leaves with the year-long immutable caching and the strong tag. A 404 is cacheable by default
(RFC 9111). Any browser that requested the blob while its object was missing keeps the 404 for a
year without revalidating, even after an operator restores the object. The object can go missing
through a lost object, a tenant container recreated or restored, or the restore-recovery case §7.3
exists for. The server cannot undo the cached 404, and the URL never changes because the id does
not.
Suggested fix: stamp the caching headers only on the 304 path and after a successful open, or
remove `ETag` and `Cache-Control` before returning the not-found problem. Better, give every blob
problem `Cache-Control: no-store` (the global stamp could cover the Blobs surface whenever the
status is not 200, 206 or 304). Pin it with an endpoint test whose store returns null for a
resolved committed blob and asserts that the 404 carries neither `immutable` nor the tag.

**R1-3 (minor): the endpoint's own behaviours, the two carries included, are untested.**
The only endpoint-level suite is Acme's happy-path lifecycle. The Core.AspNetCore tests cover the
pure header functions and the metric class. Nothing fails if any of these is reverted:
(a) the time-to-first-byte lift (`BlobEndpoints.cs:199`, the D-145 carry): deleting the line passes
every suite, because no test streams past a lowered `RequestTimeout`; (b) the telemetry stage on
the Blobs group (`TellmaEndpointRouteBuilderExtensions.cs:204`, the D-137 carry): no test asserts
its headers or log scope on a blob response; (c) the 304 answered with storage untouched (§5.3),
the missing-object 404 counted as `not_found`, the length-mismatch 500, and the counter emitted per
outcome by the endpoint. §12 asks that each §10.1 instrument be asserted with its tag values, but
`BlobDownloadMetricsTests` calls the class directly.
Suggested fix: one Core.AspNetCore.Tests class that maps the real `MapTellmaBlobs` over a fake
`IBlobService` and a counting `IBlobStore`. It should cover a 304 with zero store calls, a null open
as a 404 with `not_found` counted (and R1-2's headers), a short stored object as a 500, a slow
stream that outlives a 1 s `RequestTimeout` and completes, and a blob response carrying
`Content-Language` from the telemetry stage.

**R1-4 (minor): `ServiceUri` accepts a query or a path, and its problem message echoes the whole
URI.**
`src/connector/azure-blobs/Tellma.Connector.AzureBlobs.Adapter/AzureBlobStoreOptionsValidator.cs:53-55`
checks only that the endpoint is absolute HTTPS. A URI pasted with a SAS query (`?sv=...&sig=...`)
or with a container path passes when it is HTTPS. With a path, every tenant's container becomes a
blob path under one container, and every write then fails at runtime rather than at startup. When
the URI is not HTTPS, the failure message prints all of it, signature included, into the startup
problem and its log.
Suggested fix: refuse a `ServiceUri` with a query, a fragment, user info, or a path other than `/`,
and print only its scheme and authority in every message. Add those cases to
`AzureBlobStoreOptionsValidatorTests`.

**R1-5 (minor): a range refusal or a failed precondition is counted as `served`.**
`src/core/Tellma.Core.AspNetCore/Blobs/BlobEndpoints.cs:195` counts `served` before
`Results.Stream` runs. The stream result may then answer 416 (an unsatisfiable range) or 412
(`If-Match`) without sending the object, so `tellma.blobs.downloads{outcome=served}` overstates
what was served.
Suggested fix: count from the response status as it starts (200 or 206 is `served`), or decide the
416 in the handler before counting. Spec 0017 §10.1 has no outcome for these, so the closed-set
answer is to leave them uncounted.

### Findings

**R2-1 (major, for Ahmad): the deadline ends a stalled download, but one member can still keep a
tenant's whole `tellma-blobs` lane full for as long as they like.**
`src/core/Tellma.Core.AspNetCore/Blobs/BlobEndpoints.cs:216` and `:234-238`.
The deadline is per request, and its floor is `LongRequestTimeout` (5 minutes) whatever the object's
size. A member opens 32 downloads of any object too large for the server's and the socket's send
buffers, reads each a little faster than Kestrel's 240 B/s minimum, and is cut off after 5 minutes
(about 58 minutes for a 100 MiB attachment, which may be the member's own staged upload). They then
reopen. 32 requests every 5 minutes hold all 32 permits permanently, the next 256 avatar and PDF
requests of the tenant queue with no deadline (the limiter runs before the timeouts), and the rest
answer 429. This is Review 1's scenario with one reconnect per deadline added, so R1-1's "one
member can hold every permit" is narrowed, not closed. D-169 describes the remaining exposure as
"32 legitimate slow downloads"; the deliberate case is the same size as before the fix.
Suggested fix: option (b) of D-169 (a per-caller cap inside the tenant lane) or option (a) (hold
the lease only around resolve and open) is what closes it, and both change 0016 §8.2, so this
needs Ahmad's ruling before the surface is exposed. Locally, without changing the chain, the
deadline's base could be `RequestTimeout` (the time-to-first-byte budget, 30 s) instead of
`LongRequestTimeout`. A small object's hold then drops tenfold, and a 100 MiB object still gets
its 53 minutes at the floor rate.

**R2-2 (minor): the deadline's test stalls the source, not the client, and two security-relevant
orders have no pin.**
`test/core/Tellma.Core.AspNetCore.Tests/Blobs/BlobEndpointTests.cs:163-186`.
(a) The test's comment says "a client that stops reading, or an object that stops arriving", but
only the second is exercised: `StallingStream` blocks the source read, on the in-memory test
server. The case R1-1 was about is a handler blocked in the body write under Kestrel's
backpressure. Reading the framework, `Abort()` does release that write, but no test would fail if
it did not.
(b) The test shows the object is let go. It does not show the permit is: nothing sets
`ConcurrentBlobReadsPerTenant` to 1 and checks that a second download is served after the deadline.
(c) Nothing pins authorization before the tag comparison. The scripted service always resolves.
The tag is `"{id}"` or `"{id}-{variant}"`, which a caller can derive from the address, and the
spec's wording ("the strong ETag is computed before any store call") invites computing it from the
route. A later change that answers 304 before `ResolveAsync` would be an oracle for any blob id
and would pass every suite.
Suggested fix: (a) and (b) in one test on a real Kestrel listener: a raw socket that reads the
headers and stops, one permit, the fake clock advanced past the deadline, then a second request
answered 200. (c) One case where the service resolves null and the request carries
`If-None-Match: "7"` and `*`: 404 `not-found`, zero opens, no tag.

**R2-3 (minor): a failure to get a token escapes the Azure store unwrapped and unmetered, and cuts
short the other operations of the call.**
`src/connector/azure-blobs/Tellma.Connector.AzureBlobs.Adapter/AzureBlobStore.cs:347-350`, used at
`:254`, `:301`, `:401`, `:465-470` and `:549`; and `:200`.
`IsStorageFailure` names three types: `RequestFailedException`, `AggregateException` and
`IOException`. When the host's `TokenCredential` cannot produce a token (the managed identity
endpoint unavailable or throttled, a credential misconfigured), the client's bearer policy throws
the credential's own exception, which is none of the three and is not retried. Failure scenario,
an identity outage with storage healthy:
- `OpenReadAsync`, `EnsureTenantAsync` and `ListAsync` throw that exception instead of the
  `BlobStoreException` the contract documents, and record no `failed` outcome, so
  `tellma.blobs.store.operations{outcome=failed}` and its alert stay flat through the outage;
- in `WriteAsync` and `DeleteAsync` the exception leaves the `Parallel.ForAsync` body, which
  cancels the loop. The sibling writes or deletes are cancelled rather than attempted (the
  contract says a failure leaves the others attempted), and the call's metric at `:219` or `:315`
  is skipped.

The file-system store maps its equivalent (`UnauthorizedAccessException`) to `BlobStoreException`.
Found by reading the catch filters; not reproduced.
Suggested fix: at every client call site treat any exception that is not a cancellation as the
storage's failure (`exception is not OperationCanceledException`), keeping the 404, conflict and
mismatch cases ahead of it. Pin it in the unit project, which needs no emulator: a store over an
HTTPS `ServiceUri` with a credential that throws fails before anything is sent. Assert
`BlobStoreException` and the `failed` measurement on a read, a write of two objects and a delete
of two names.

**R2-4 (minor): the prefix check passes a prefix under which the first tenants have no valid
container name.**
`src/connector/azure-blobs/Tellma.Connector.AzureBlobs.Adapter/AzureBlobStoreOptionsValidator.cs:74`,
and `test/connector/azure-blobs/Tellma.Connector.AzureBlobs.Adapter.Tests/AzureBlobStoreOptionsValidatorTests.cs:79`.
Only the longest name (`prefix + "t2147483647"`) is checked. A container name is 3 to 63
characters, so with `ContainerPrefix` set to the empty string the names `t1` to `t9` are invalid,
by the validator's own rule (`IsValidContainerName("ab")` is false). The unit test lists `""` among
the prefixes that are valid for every tenant id. Failure scenario: a deployment sets the prefix to
empty to get bare `t{id}` containers. The startup check passes, then every blob write and read of
tenants 1 to 9 (Acme's two seed tenants among them) fails at runtime with the service's
invalid-name refusal, while tenant 10 works.
Suggested fix: check the shortest name too (`prefix + "t1"`), and move `""` to the refused cases.
Spec 0017 §9 names only the longest suffix, so this is also a spec gap for Ahmad.

**R2-5 (minor): the framing and sniffing guards are missing from every blob answer the handler
does not reach.**
`src/core/Tellma.Core.AspNetCore/Blobs/BlobEndpoints.cs:160-166`.
Spec 0017 §5.3 puts `Content-Security-Policy: frame-ancestors 'self'` and `nosniff` "on every
response". The guards are registered inside the handler, so the tenant guard's 404 and 403, the
limiter's 429 and 503, a 401, and a 400 for an unbindable `download` leave without them.
Deviation 8 says they ride every download response. These bodies are problem JSON, so the exposure
is nil, but the rule as written is not met.
Suggested fix: stamp both in the `UseTellma` header stamp whenever the endpoint's surface is
`Blobs` (it already reads the surface for `IsRefusal`), and drop the handler's callback. Add the
two headers to an early-refusal assertion.

**R2-6 (minor): `LengthGuardStream` fails a zero-length read before the declared end as a short
content.**
`src/connector/azure-blobs/Tellma.Connector.AzureBlobs.Adapter/LengthGuardStream.cs:84-85`,
`:110-111` and `:166-173`.
With bytes still to come, a read into an empty buffer asks the content for zero bytes, gets zero,
and `Advance(0)` throws "ended after N of its declared M bytes" and records a mismatch. A
zero-length read is legal, and some transports issue one to wait for data. The current client does
not, so nothing fails today; if a later client version does, a whole content is refused as
corrupt.
Suggested fix: return 0 for an empty buffer before either branch, in both the synchronous and the
asynchronous read, and add the case to `LengthGuardStreamTests`.
