### Deviations

1. **Bracketed keywords.** §8.2's example `[Order]` is wrong for the engine. `Order` is not a
   Queryex keyword, so the engine, and therefore the client, prints it bare. The golden pins
   `Order = 1` and `[not].[in] = [desc]`.
2. **Description list style.** `in` descriptions use `Intl.ListFormat` with `unit` and **`short`**,
   not `narrow`. English's narrow unit list drops the commas ("Retail Wholesale"), which
   contradicts §13.2's own example "Type: Service, Sale".
3. **Insertion spacing.** `tmQxInsert` adds a space on both sides of the insertion. It adds one
   where the insertion's end would touch a word on its right, as well as where its start would
   touch a word on its left. It also treats `]` as a word end, and `[` and `@` as word starts, so a
   bracketed name or a parameter is never glued to its neighbour. §8.2 names only "an identifier,
   a digit or `)`" on the left.
4. **Builder edge cases** the spec leaves open:
   - `tmQx.in(x, [])` stands for `false`;
   - `tmQx.num` of a negative builds `negate(number)`, and `-0` builds `0`;
   - `tmQxPrint` of an `in` node with no items throws.
5. **Engine lexer.** `Lexer.TryTokenize` hands out the readable tokens around an unreadable run,
   and takes an optional collection of the unreadable spans, so the corpus can record what the
   client should show. No engine behaviour changes, because callers stop at `false` as before.
6. **Unnamed navigation values.** A navigation filter's description shows a row's id with no digit
   grouping ("1012") while the row is not yet named, then its display name. §13.2 says display
   names only.
7. **Unknown display zone.** An instant filter in a display zone the platform does not know reads
   that zone as UTC, as every other instant formatter does. It is not an invalid value.
8. **Wall-time helpers moved.** `tm-zone-wall-time.ts` moved from `@tellma/core-ui/date-time`'s
   internals to `@tellma/core-ui/l10n`, with `ɵ` exports, so that `/entity` does not import
   `date-time`'s components to compute a day start.

### Judgements on the deviations and the orchestrator's questions

- **Deviation 1 (`[Order]`): accepted.** The engine's keyword table
  (`src/core/Tellma.Core.Queryex/Lexing/Keywords.cs`) is the ten words of spec 0008 §4. Spec 0008
  uses `[Order]` as a bracket that escapes "any future keyword", not as a printer rule, and the
  golden pins the engine's bare `Order = 1`. For Ahmad: spec 0029 §8.2's example should read
  `[not]`.
- **Deviation 2 (`unit`/`short`): accepted.** In Node's ICU, English `unit`/`narrow` gives "A B C"
  and `short` gives "A, B, C", so `short` is what §13.2's own "Type: Service, Sale" needs. The
  conjunction problem of (b) is R1-3.
- **Deviations 3 and 4: accepted**, but the insertion rule is still incomplete; see R1-4.
- **Deviation 5 (`Lexer.TryTokenize`): accepted.** It changes no engine behaviour. The only
  production caller, `ExpressionCompiler.cs:91`, returns at `false` without reading `tokens`. The
  ceiling paths still leave `tokens` empty. The probes (`ProbeFolding`, `ProbeParameterBinding`,
  `QueryexProbe`) also stop at `false`. The only cost is one array allocation on a path that fails
  anyway.
- **Deviations 6 and 7: accepted.** An id stands in for a row until it is named, which is better
  than a blank. An unknown zone reads as UTC, as the formatters already do.
- **Deviation 8 (wall-time helpers in `/l10n`): accepted.** In an app build they tree-shake per
  statement, so they reach only the chunks that call them: the date-time fields and the instant
  filters. Moving them costs the eager bundle nothing, and the +0.40 on `./l10n` is an accounting
  move matched by `./date-time`'s −0.38. The raise is honest under D-031.
- **(d) The PC-117 R1-4 carry: done and tested.** An expression column is dropped as `unreachable`
  when a path it reads resolves, case-insensitively through `TmEntityModel.resolve`, and is not
  reachable. Function names, parameters and string contents are not taken for paths.
- **(e) The corpus generator and CI.** The generator is in `Tellma.slnx`, so CI builds it with
  warnings as errors on both OSes. The JSON's `regenerate` member and the README give the command.
  `TheLexerCorpus_IsCurrent` and `ThePrintGolden_IsCurrent` run in the PR tier on Linux and Windows
  and normalise line endings, so a stale file fails CI. The corpus's call flags and error tokens are
  derived from the engine's own token stream, which leaves unreadable runs out just as the client
  skips error tokens, so the two call rules agree by construction.

`client/projects/core/tellma-core/package.json:45` and `:61`.

**R1-2 (major): the number filter rounds decimals and longs to 15 significant digits, and so
silently changes the filter.**
`client/projects/core/tellma-core/entity/src/tm-column-filter.ts:149`, `:153`, `:157`
(`tmNumber`, which holds a `number`), `:280-286` and `:442-454`.

A starting value goes through `TmDecimals.toNumber` and back through `TmDecimals.fromNumber`,
which rounds to 15 significant digits. So a long column's `eq:1234567890123456` opens and
re-applies as `eq:1234567890123460`. A decimal's `ge:12345678901234567890.5`, the very value the
leaf test pins, becomes `ge:12345678901234600000`. A typed 16-digit value is rounded the same way.
In every case Apply is enabled and nothing tells the user. The value editor of this entry point
already avoids this: it gives decimals and longs its `'exact'` mode (`tm-value-editor.ts:410-412`,
with `ɵtmParseExact`), because `tmNumber` is exact only to 15 digits (the open risk PC-117
recorded).

Fix: give decimal columns and long-integer columns the exact text input with `ɵtmParseExact` in
the locale and at the column's scale, and keep the drafts as `TmDecimal` text. It still parses
Arabic-Indic digits and writes Latin ones. Keep `tmNumber` for ordinary integers only. State it as
a deviation from the table's `tmNumber`.

Tests:
- a long column started at `eq:9007199254740993` applies that same value;
- a typed 20-digit decimal round-trips.

**R1-3 (major): in Arabic and Amharic, an `in` chip reads as a conjunction.**
`client/projects/core/tellma-core/entity/src/tm-filter.ts:409`.

`Intl.ListFormat` `unit` lists join with "and" in both languages. Node's ICU gives `ar` "A وB" /
"A، وB، وC" and `am` "A እና B" / "A፣ B እና C", in every style. The chip then says the rows are of
both types, though the filter is any-of. Arabic is one of the platform's two UI languages, and the
chip is the filter's only visible statement. The message cannot fix this, because the joiner lives
inside `{values}`.

Fix (recommended): use `{ type: 'disjunction', style: 'short' }`. CLDR gives "Service or Sale" /
"A, B, or C", `ar` "A أو B أو C" and `am` "A ወይም B". That is the right meaning in every locale,
with no new strings and no added bytes. For Ahmad: §13.2's example becomes "Type: Service or Sale".

Alternative, if the comma-only English must stay: add a translatable `tm.filter.listSeparator`
(", ", "، ", "፣ ") and join the parts with it, each value still its own part.

Either way, add an Arabic `in` test that pins the joiner.

**R1-4 (minor): `tmQxInsert` can merge the insertion into the token beside it.**
`client/projects/core/tellma-core/entity/src/tm-qx.ts:639-652` and `:686-687`.

`endsWord` and `startsWord` test only names, digits, brackets and `@`, so two tokens that fuse
across the boundary are left touching. I ran these through the source with esbuild:
- `tmQxInsert("'a'", 3, "'b'")` gives `'a''b'`, which lexes as one string, `a'b`;
- `tmQxInsert('a <', 3, '= 1')` gives `a <= 1`, which changes the operator;
- `tmQxInsert('a.', 2, '5')` gives `a.5`, a malformed number.

PC-121's drag and drop of fields and values runs through this function.

Fix: also add the space when the boundary's two characters fuse. A cheap test is
`tmQxLex(left + right)` giving one token or an error, which covers `''`, the `<=`/`>=`/`!=`/`||`
pairs, and a point before a digit. Pin the three cases above.

**R1-5 (minor): `tmQx.num` builds numbers the engine refuses.**
`client/projects/core/tellma-core/entity/src/tm-qx.ts:255-271`.

The builder's TSDoc says a tree that prints is one the engine reads back. However:
- `tmQx.num(1e-40)` prints `0.0000000000000000000000000000000000000001`, whose 40 fraction digits
  exceed the 38-digit rule at `tm-qx-lex.ts:379-386`;
- `tmQx.num('123456789012345678901234567890123456789')` prints as given.

The engine (and `tmQxLex`) reads both as QX1004. `tmFilterLeaf` then returns a leaf the server
rejects, where §13.2 wants `null` for an invalid value.

Fix: in `num`, throw a `RangeError` when `max(integer digits without leading zeros + scale, 1) > 38`,
and test both cases.
