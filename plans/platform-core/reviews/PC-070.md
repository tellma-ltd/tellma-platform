## Implementer notes

### What was built

The details plan of spec 0015 §5.3 (`get`, `get_by_ids`) with the extras and the `permissions` extra, the rows of a tree by parent of §5.4 (`get_by_parent_ids`), and every row of a cacheable stack of §5.5 (`all`). Carries: the faulted `ActionContext.Persisted` is observed (PC-062), and `RequestContext.ApplyCultures` is re-applied after every runner call that the new steps make (PC-068).

- **Details plan** (`Tellma.Core/Crud/Details`):
  - `DetailsProjections` (singleton, cached per stack and schema instance) builds the root select, the child collections and the grouped target reads:
    - The root select is the schema's declared properties plus the related projection of each root-level navigation of `DetailsExpand`. Each navigation prefix selects its key and the related-select columns its schema entity declares, plus the next step's foreign key. Paths are cut at `MaxExpandDepth` navigations.
    - The children are every collection at any depth, dotted, parents first.
    - There is one `DetailsTargets` per collection level that a path's navigations start from. It is a grouped `Rows` rooted at the level's entity and restricted by the key path back to the root key (e.g. `WidgetPart.WidgetId`).
  - `DetailsPlanner` (scoped) composes the plan on a batch:
    - `Admit` runs before any round trip. More distinct names than `MaxExtras` is `LimitExceededException`. A name the stack does not serve is `BadRequestException` with argument `name`.
    - `Compose` decides `Read` from the connected user's set (a denial is `ForbiddenException`), then builds the composition.
    - The service runs `ContributeDetails` only when it declares a requested extra. Each `IDetailsContributor<T>` is given the requested names it declares.
    - Each producer gets a `DetailsPlan` with the shared `IdsSource` and a sink of its own.
    - A requested extra that no producer added is an `InvalidOperationException`.
    - The `permissions` abilities are taken from the stack. A denied ability is skipped, and a filter is passed only when the ability supports one.
    - `Compose(..., idsSource)` is the seam for the save's read-back (§6.9). With a table of saved ids, no main-ids statement is appended.
  - `DetailsComposition` makes one composition per batch, appending:
    1. the main ids (the key under the read filter, restricted on the ids TVP, `CaptureKeys`; with no ids, every row ordered by key);
    2. one `Query<TEntity>` (the projection's select, `AllProperties`, `Children`) restricted on the captured keys;
    3. the target reads;
    4. one keyed `Rows` per filtered ability, under the grant's filter over the captured keys.
    - Each producer's sink enforces the name rules: the name must be declared, requested and added once. Raw text may declare no writes, and a raw extra must declare at least one result set.
    - `Complete` returns:
      - the visible rows in request order (key order when every row is read);
      - the related entities, merged from the query's sets and the target reads through `RelatedCollector`, each entity once;
      - the extras in request order (a computed extra serialised under `TellmaJson.Options`, the `permissions` extra as `RecordPermissions<TKey>[]`);
      - `Extras` set to null when nothing was requested.
    - Permissions: a row that a filtered grant's read missed refuses that ability as `outside-filter`. Otherwise the service's `RefuseOnRecord` judges it after the batch.
  - `RecordAbilities`: `save` (Save operation), `delete` (Delete operation), `activate` (the built-in activation's securable), then `action:<name>` per declared entity action with its `SupportsFilter`.
  - `DetailsExtrasNames`: the `[DetailsExtras]` names of a class and its bases, cached.
  - `DetailsOperation` (scoped) runs inside the `CrudOperations` frame.
    - `get` runs in the small lane and throws `NotFoundException` with the invariant id when nothing is visible.
    - `get_by_ids` takes its lane from the count. Before any round trip it runs `RequireAsync(Read)`, the `MaxIds` check on the sent count, `Admit`, and the distinct ids. Then it makes one guarded round trip and calls `ApplyCultures`, then `Complete`.
    - `all` runs `RequireAsync(Read)` and `Admit`, then `ICacheableEntities.GetAsync`:
      - warm with no extras: the cached rows, with no round trip;
      - warm with extras: the plan over the cached ids;
      - oversized: one whole-table `Query<TEntity>` ordered by key, or the plan over every row when extras are requested.
    - `DataAccessRetryExhaustedException` becomes `DependencyUnavailableException("database", 1 s)`. An arithmetic failure passes through.
- **Rows by parent** (`QueryOperation.RunParentIdsAsync<TKey>`, operation `get_by_parent_ids`, lane by the parent count):
  - The order is: the tree metadata, `RequireAsync(Read)`, `MaxIds` on the sent count, the wire ids narrowed (`WireIds.ToKeys`) and made distinct, then `QueryShape.AdmitParentIds`, then the query's own read and recheck loop.
  - The shape is `Take = MaxTake + 1`, `Skip 0`, no count and no ancestors. Its ordering is the declared `DefaultOrderBy`, else `Id`.
  - With no parents, the roots are a `ParentId = null` platform conjunct (`QueryShape.PlatformFilters`, which the planner appends as `Platform` conjuncts).
  - With parents, the children are a `KeySetRestriction` on the parent key over the distinct parents' TVP. Spec 0016 §1.4 notes this applies the `IX_..._ParentId` index.
  - With `IncludeRoots`:
    - A batch-local key table of the key's width is declared, then filled by one `INSERT … SELECT … WHERE ParentId IS NULL UNION SELECT … WHERE ParentId IN (parents)`.
    - The read is restricted on that table, so the access filter and the active flag still apply to the read itself.
  - More than `MaxTake` rows is `LimitExceededException(MaxTake, MaxTake + 1, MaxTake)`.
  - The query's translations apply: an arithmetic failure becomes `ValidationException`, and exhausted retries become `DependencyUnavailableException`.
  - `QueryOperation` was restructured so that the query and the tree read share the guarded read, the recheck loop and the translation. `GuardedReadAsync` and `Compose` take an optional `narrow` that rewrites the planned spec before `batch.Rows`.
- **Data layer**: `IBatchKeyTables` (internal; D-062) is implemented by `DataBatch`.
  - `KeysOf(handle)` returns a captured key table.
  - `DeclareKeyTable(Type)` declares an `int` or `bigint` key table. `DeclareIdTable()` now delegates to it.
  - `KeyTables` (internal) binds a key list as `IdList`/`BigIdList` and casts a batch to its key tables.
- **Smaller changes**:
  - `CrudMetrics.Lane(count, threshold)`.
  - `QuerySurface.DeclaredOrderBy`.
  - `EntityPipeline` delegates `get`, `get_by_ids`, `all` and `get_by_parent_ids`. Its factory passes `DetailsOperation`.
  - `CrudComposition` registers `DetailsProjections`, `DetailsPlanner` and `DetailsOperation`.
- **The Persisted carry**: `ActionContext.PersistedSource` is private.
  - `CompletePersisted()` and `FaultPersisted(exception)` are internal. `FaultPersisted` observes the faulted task (`_ = Task.Exception`), so a failure that no action method awaited raises no `UnobservedTaskException`.
  - No production code completes it yet; the actions checkpoint will call these.
- **Tests**:
  - Unit tests in `test/core/Tellma.Core.Tests/Crud/Details/`: `DetailsModel` and `DetailsOperationTests`, 16 cases.
    - The setup:
      - The model is an order with lines pointing at customers. Its service declares a computed, a raw and a query extra, `RefuseOnRecord`, and two entity actions (one all-or-nothing). There is also a lineage contributor, a cacheable customer, and a tree with `MaxTake 5` and `MaxIds 3`.
      - It runs over `QueryRig`, which gained a `(compose, configure)` constructor, with a fake `ICacheableEntities`.
      - `ScriptedBatch` implements `IBatchKeyTables`, naming captured tables as the platform does.
    - What the cases pin:
      - one round trip with the main ids' shape, the query's restriction on the captured table, and the grouped target read with its key path;
      - request order with hidden ids left out, and related entities deduplicated;
      - NotFound;
      - Forbidden, `MaxIds`, `MaxExtras` and an unknown extra, each before any batch;
      - extras in request order, with the contributor given only its own names and the producers given the distinct ids;

      - permissions: one keyed read per filtered grant, outside-filter before the rule, and a denied ability not listed;
      - roots, children, and `IncludeRoots` (key table plus raw text plus restriction);
      - `MaxTake` and `MaxIds` on the tree;
      - the cached list: warm gives zero batches, extras give one batch over the cached ids, oversized gives a whole read each call.

  - Integration tests in `test/core/Tellma.Core.IntegrationTests/Crud/DetailsPipelineTests.cs`: 7 cases over `DetailsPipelineDatabase`.
    - The setup:
      - The database seeds widgets, parts, part notes, nodes and links, plus a crowded root with 10,001 children and two lookups.

    - The cases:

### Deviations (gap fills and obvious corrections)

1. **The lines' related entities come from grouped reads.** What a collection's rows point at is loaded by one grouped `Rows` per collection level, keyed back to the visible ids, and merged into `Related`. An entity query selects declared columns only below its root (spec 0012 §5.2), so the expansion cannot ride the query itself. This follows the provisional D-062 ruling.
2. **`IncludeRoots` needed a new internal key-table declaration.** It fills a batch-local key table through raw text. Because the public `DeclareIdTable` is int-only, `DeclareKeyTable(Type)` was added on the internal `IBatchKeyTables`; `KeysOf` is reached the same way (D-062).
3. **The spec's cacheable "Gadgets" are the fixture's `Lookup`.** The fixture has no gadget; `fixture.Lookup` is its cacheable entity (`MaxRows 50`).
4. **`all` with extras reads fresh rows.**
   - On a warm list it runs the details plan over the cached ids, so it returns fresh rows with related entities and extras rather than the cached instances. With no extras, `Related` is null.
   - When the list is oversized and extras are requested, the plan reads every row, with the main ids ordered by key.
5. **Duplicates are removed, but the ceilings count what was sent.** A repeated id is read and returned once, where it first appears, and a repeated extra name is likewise read once. `MaxIds` counts the sent ids, while `MaxExtras` counts the distinct names.
6. **Abilities the caller lacks are not listed.** A denied ability is absent from the `permissions` extra, because `RecordPermissions` carries only refusals and the client's own grant check shows what is not granted.
7. **A declared, requested extra that no producer added fails.** It is an `InvalidOperationException` naming the classes that declare it; the spec is silent.
8. **A raw extra must declare a result set.** It needs `SqlOptions.ResultSets ≥ 1`, because its first result set is the extra.
9. **`get`'s `NotFoundException` names the id in invariant form.**

### Open risks

- **Cached rows are shared.** A warm `all` with no extras returns the cache's own instances. A caller that mutates them corrupts the cached list for every scope of the tenant. The alternative is a copy per call, which costs memory.
- **Target reads group by their select.** A related-select column that cannot be grouped (a JSON or geography column) would fail the grouped target read. Related selects are scalars by convention, but nothing checks this.
- **Unbounded reads.**
  - Producers' `AddRead` and `AddExtra` specs are trusted: no access filter is added. That is the producer's responsibility, as the spec intends.
  - `all` with extras over an oversized table applies no `MaxIds` or row cap.
- **Integration fixture cost.** The 10,001-child seed adds a few seconds to the integration fixture's setup.

### Review hardest

- `DetailsComposition.Complete`: the order source (requested ids, else the main ids' key order), the merge of the query's related sets with the target reads, and the permissions logic.
- `DetailsProjections.Expand` and `KeyPath`: whether paths through nested collections pick the right level, root and key path, whether the next-step foreign key is added, and how the depth is cut.
- `QueryOperation.RootsAndChildren`: the raw text's identifiers, the key width, and how it interacts with the read filter, the active flag and `MaxTake + 1`.
- `DetailsOperation.AllAsync`: each branch, and the round-trip claims (zero round trips warm, one with extras).
- The culture re-application after each runner call, and the faulted-`Persisted` observation.

Checked and found sound (no finding):

- **Hidden equals missing.** The main ids carry the read decision's filter and are the only statement under it. The entity query, every collection, the root's related projection, each level's grouped target read and each permissions read restrict on the captured `@tb{n}_keys`, never on the requested-ids TVP (the unit test pins the captured name on the query and on the target read). `get` raises the same `NotFoundException` for hidden and missing ids, and `get_by_ids` drops hidden ids in request order. The integration test pins both.
- **Permissions.** One keyed `Rows` per filtered, granted ability, restricted on the captured keys. `SupportsFilter = false` drops the filter. Denied and unregistered abilities are skipped (deviation 6 reads the spec correctly: the extra answers only granted abilities). `outside-filter` wins over `RefuseOnRecord`, which runs after the batch, after `ApplyCultures`, over visible rows only. The unit test covers precedence with `P2`.
- **MaxTake + 1.** `Take = MaxTake + 1`, `Skip = 0`, no count and no ancestors. The refusal is `LimitExceededException(MaxTake, MaxTake + 1, MaxTake)`, the `int.MaxValue` ceiling does not overflow, and `MaxIds` is checked on the sent count before the read. With `IncludeRoots`, the raw fill reads unfiltered candidate ids, and the read itself still applies the access filter, the active flag and the bound. Identifiers are bracket-quoted by the batch.
- **Round trips.** Every details statement (main ids, query, level targets, extras, `AddRead`s, permission reads) is appended to the one composition inside one `runner.RunAsync`. So details, one or many, is 1, and get-by-parent-ids with `IncludeRoots` is 1. Both are pinned warm in integration. A warm `all` is 0.
- **Judgement 2: grouped `Rows` per collection level (D-062/D-109).** This stays within the §16.2 budget: each level adds one statement to the same batch, never a round trip. It is correct under access filters:
  - Each level's read is restricted by its key path (`OrderId`, or `WidgetPart.WidgetId` for a grandchild) to the captured visible ids, so lines of a hidden document contribute no targets.
  - The targets themselves carry no row filter, which is what §5.3 step 2 prescribes ("no row-level filter").
  - The default `DetailsExpand` (`StackDescriptorBuilder.DetailsExpand`) already emits `Collection.Navigation` paths, and the stacks check refuses a queryable child without its parent navigation, so the key path resolves for every reachable level.
  - The only caveat is cost inside the round trip (R1-3).
- **Cache refresh.** After a raw write and a tag move, the next scope's batch reads the snapshot and `all` reloads. This is the spec 0013 snapshot model, and the save that would bump the tag is not built yet.
- **Culture re-application.** `ApplyCultures` runs after each new runner call whose continuation runs culture-sensitive code: `RunPlanAsync`, before `Complete` (rules and computed extras), and `ReadWholeAsync`. The tree read does no culture-sensitive work after its runner call.
- **Faulted `Persisted`.** `FaultPersisted` observes the fault through `Task.Exception`, and `PersistedSource` is now private. The GC test filters on its own exception instance, so unrelated unobserved exceptions cannot fail it.
- **AGENTS.md and PLAN.md §7.1 item 5.** No spec, `docs/`, PC or decision ids appear in added XML docs, error messages or test names. Inline comments cite specs only. The READMEs are updated.

### Findings

**R1-1 (major): a warm `GetAllCachedAsync` hands every caller the cache's own mutable instances, and its own list.**

- **Where.** `src/core/Tellma.Core/Crud/Details/DetailsOperation.cs:213-219` returns `Entities = list.Items`, the `CachedEntitySet.Items` that spec 0013's store shares across every scope of the tenant. The behaviour is pinned by `test/core/Tellma.Core.Tests/Crud/Details/DetailsOperationTests.cs:301` (`Assert.Same(items, plain.Entities)`).
- **Why the entity types do not make this safe.**
  - Spec 0013 §3 says shared cached values are immutable records with read-only collections. That holds for `CachedEntitySet` itself, but not for its `TEntity` rows. These are ordinary entity classes with public setters (e.g. `Lookup.Code`, `Name`, `IsActive`).
  - Nothing on `EntityService.GetAllCachedAsync` or `EntitiesResult` warns a caller, and the sibling `GetByIdsAsync` on the same service returns fresh instances. So code that reads all rows, edits one, and saves it is the natural pattern.
- **Failure scenario.**
  - Spec 0015 §6.2/§6.3 have the save pipeline mutate its payload in place. It calls `EntityMetadata.ResetDerived` on every row (its XML doc: "The pipeline calls it on every row, new and existing"), trims strings, nulls empty strings, drops twins and rewrites ids.
  - An `[ApiAction]`, job or distribution service might call `GetAllCachedAsync`, change a row's `Name`, and pass the row to `SaveAsync`. That rewrites the cached instance itself.
  - If validation then fails, nothing commits and no tag bumps. Every reader of that tenant is served the altered row (edited name, reset derived values) until some unrelated write to the table bumps `entity:<Name>`. The same holds for any caller that sets a display-only field on the returned rows.
  - `list.Items` is the cache's own array or list, so a caller that casts it can also reorder or replace cached rows.
- **Fix: return per-call copies on the warm no-extras branch.**
  - Spec 0013 §4.2's startup check makes a cacheable entity top-level with no child collection. The probe (`CacheableEntityType.Query`) is an entity query of the row's own columns, so the cached rows carry no navigations. A shallow copy of each row is therefore an independent copy: `MemberwiseClone` through an internal hook on `Entity`, or a copier compiled once per type from `EntityMetadata`'s property getters and setters, as `EntityMaterializer` already compiles factories. The one exception is a `[JsonColumn]` property that holds a mutable object, which also needs copying.
  - Build a fresh `Entities` list around the copies.
  - Cost: at most `EntityMaxRowsCeiling` (10,000) small allocations per call, roughly a millisecond and about 1 MB transient at the ceiling, and no round trip. So the §16.2 row (all cached: 0) still holds. Freezing is not available for POCO entities.
  - A documented read-only contract alone is weaker, because the hazard comes from the platform's own save pipeline. If copies are rejected, the save pipeline (PC-072) must at least copy, or refuse, a payload row that is reference-equal to a `Peek` row.
- **Test changes.**
  - Replace the `Assert.Same` with an assertion that the rows are equal but not the same instances.
  - Add a case where mutating a returned row leaves the next warm call's row unchanged.

**R1-2 (minor): the oversized row of the §16.2 budget has no pin that measures it.**

- **Gap.** §16.2 and the checkpoint's done-when set "all cached on a table beyond `MaxRows`: the probe and the re-read, **2** on every call". The only oversized test, `DetailsOperationTests.cs:311-327`, runs over a fake `ICacheableEntities` whose probe costs nothing. It asserts 2 round trips for two calls, which is 1 per call. So it would pass if the probe were silently skipped or doubled.
- **Missing integration case.** None of the cases reaches `CacheOutcome.Oversized` or measures `all` with extras (1). §18.2's Budget pin asks for "every row".
- **Fix.** Add an integration case that measures 2 round trips per call (`MeasureAsync`) on a table beyond its `MaxRows`. For example, give a second cacheable fixture a small `MaxRows`, or seed `Lookup` beyond 50 rows in its own class fixture, so the warm test's two-row assertion is untouched. Measure `all` with `permissions` warm at 1 in the same case.

**R1-3 (minor): a collection level with several navigations groups by their combination, so the target read scales with the lines, not with the distinct targets.**

- **Where.** `src/core/Tellma.Core/Crud/Details/DetailsProjections.cs:145-169` puts every navigation of one level into one `SelectItems`. `DetailsComposition.cs:116-123` reads it as one `Aggregate = true` `Rows`, whose grouping keys are all of those columns together.
- **Failure scenario.**
  - Take a level whose rows point at both `Account` and `Center`, as the default expansion produces for every FK of a child. With 10,000 lines over 10,000 distinct accounts and one center, the read returns up to 10,000 rows.
  - Each of those rows repeats the center's projection. `RelatedCollector` deduplicates in memory, but SQL grouping, transfer and materialisation scale with the lines.
  - This works against §5.3's "ten thousand lines pointing at one center carry one center".
  - It is correct and within the round-trip budget.
- **Fix.** Group per (level, first navigation of the path): one grouped `Rows` per distinct leading navigation of a level, with its deeper steps kept in the same read. Each target is then read once per level. The statements still ride the same round trip. Update the unit test that expects a single aggregate statement.

**R1-4 (minor): no test catches an off-by-one in the tree-read bound.**

- **Where.** The refusal is `src/core/Tellma.Core/Crud/Query/QueryOperation.cs:190` (`RowCount > MaxTake`).
- **Gap.** Every existing case returns either well under `MaxTake` (2 rows against 5 in the unit roots case, 5 against 10,000 in the integration `IncludeRoots` case) or exactly `MaxTake + 1` (6 against 5, and 10,001 against 10,000). Changing `>` to `>=`, which wrongly refuses a level of exactly `MaxTake` rows, passes the whole suite.
- **Fix.** Add a unit case in `DetailsOperationTests` where the scripted read returns exactly `MaxTake` rows (`QueryRig.Page(1, 2, 3, 4, 5)` against the tree's `MaxTake = 5`) and assert that the five rows are returned.
