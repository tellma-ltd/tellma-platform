# PC-039: Securables registry, startup audit and securables metadata section

## Implementer notes

### What was built, and where

- **Contracts** (`src/core/Tellma.Core.Abstractions/Access/`): `SecurableRef`, `SecurableOwner`,
  `SecurableDescriptor` (`SupportsFilter` derived), `SecurableRegistryBuilder`,
  `ISecurableContributor` (`[CollectionService]`, D-016), `ISecurableRegistry`,
  `NoActivityStampMetadata` and `ClientSecurable`.
  - The builder records every call as made, with the feature of the running contributor
    (internal `SecurableDeclaration`, `SecurableAliasDeclaration`, `SecurableMarkDeclaration`).
  - It throws only on null arguments and once frozen. Grammar and conflicts are startup problems,
    so the gate reports them all at once.
  - `SecurableEndpointMetadata` and `MemberEndpointMetadata` were kept as PC-015 seeded them.
- **Contribution item**: `SecurablesContributionItem` and the sugar `FeatureContribution.Securables`.
  - `SecurablesContributionRealizer` registers each item as a singleton `ISecurableContributor`
    (`FeatureSecurableContributor`) on behalf of its feature.
  - A null configuration is a composition problem.
- **Registry** (`src/core/Tellma.Core/Access/SecurableRegistry.cs`, registered by `CoreFeature`):
  runs every contributor once, on first resolution, then freezes the builder. It:
  - merges by pair (ignoring case, the first spelling and feature win, sensitive if any
    registration says so);
  - composes the aliases (one step, to a registered resource);
  - applies Core's sensitive defaults and the marks;
  - sorts `All`, and computes the fingerprint.
  - Everything wrong is kept on `Problems`, which `core.securables` reports.
  - A throwing contributor fails resolution with an exception naming the contributor and its
    feature.
- **Check** `core.securables` (`Composition/Checks/SecurablesCheck.cs`, built-in, no
  infrastructure). It reports:
  - the registry's problems;
  - an unknown feature;
  - an owner that is not a registered resource, or one declared without a filter root;
  - owner-chain cycles, at pair level (each pair to the same action of its owner), once per
    cycle.
  - Against the model, when it builds:
    - a filter root that is not an entity of `GetSchema(MultilingualShape.All)`;
    - a child entity's securable without an owner;
    - an owner navigation that is not a path of navigations, or that ends elsewhere than the
      owner's filter root.
- **Endpoint audit** (`Tellma.Core.AspNetCore/Routing/TellmaEndpointAudit.cs`): an optional
  `ISecurableRegistry` parameter. Every `SecurableEndpointMetadata` on any endpoint must `Find` a
  pair registered under that resource. A pair reached only through an alias is refused.
  - The realised gate passes the registry. `MapTellma`'s early run passes none.
- **Client metadata**: `SecurablesClientAssetContributor` writes the Core chunk's `securables`
  section. Label keys follow spec 0032 §12.4's chains:
  - The keys come through a new internal seam, `INeutralStringKeys`: TryAdd-registered, reading
    every composed feature assembly's neutral `*.Resources.Strings.resources`.
  - Fallbacks come from a new internal `NameHumanizer` in `Tellma.Core.Localization`.
- **CoreFeature** registers:
  - the registry and the contributor;
  - `core.UserStamp` × `Read` (filter root `core.UserStamp`, owner `core.User` through `User`);
  - `core.User` × `Read` (filter root `core.User`). See the deviations.
- **`NotificationTypesCheck.CheckTargets`** (D-061) also accepts a registered securable
  resource, matched as spelled. The `int`/`long` key rule applies to stack resources only.

### Deviations

1. **The registry is composed and frozen on first resolution, not in `AddTellma`'s realise phase**
   (spec 0014 §1.2, §4.1 "frozen at realise").
   - Contributors are services that read other services: spec 0015's `StackSecurableContributor`
     reads `IStackRegistry`. None of them exists before the container is built.
   - The realised gate's `core.securables` resolves the registry at startup, so every §4.5
     finding still fails startup before traffic.
   - `ARCHITECTURE.md` does not say when it freezes, so it is unchanged.
2. **`CoreFeature` also registers `core.User` × `Read`.**
   - §4.5 requires every `Owner` to name a registered resource. Until PC-063's stack contributor
     lands, nothing registers `core.User`, so `core.UserStamp`'s owner would fail every host.
   - The stack contributor's identical registration will be idempotent. PC-063 may drop this
     line.
3. **The fingerprint also covers owners and aliases.**
   - Its lines are `Resource|Action|FilterRoot|IsSensitive|OwnerResource|OwnerNavigation` plus
     `alias|Old|New`, sorted ordinally.
   - Spec 0014 §4.1 lists only the first four fields. An owner and an alias change what a grant
     reaches as much as a filter root does.
4. **Rulings where the spec is silent** (WATCHLIST lead "MarkSensitive on an absent pair"):
   - A `MarkSensitive`/`MarkNotSensitive` of an unregistered pair is a problem.
   - A Core default whose pair nobody registers (`core.Schedule` until 0020) is ignored
     silently.
   - The same pair with another owner, or a resource or action spelled with another case, is a
     problem, like a different filter root. Any registration's `isSensitive: true` makes the pair
     sensitive.
   - A pair marked both ways is a problem and stays sensitive.
   - An explicit `feature` must name a composed feature.
   - A contributor registered by a factory or by the host, outside every feature, is attributed
     to `core`.
   - An alias is refused when it renames a resource to itself, names an old resource that is still
     registered, or a target that is not registered, or names a second target for the same old
     resource (which also rules out chains).
5. **Entity-resource label chain.** `<Schema>_<Entity>_Plural`, then `<Schema>_<Entity>` (spec 0013
   §7.6's plural → singular), then the humanized last segment of the entity name rather than of
   the leaf's class name, which a distribution's leaf renames.
   - The action prefix applies the entity-key rule (schema capitalized, dots → `_`) to every
     resource, including non-entity ones (`Core_Settings_General_Action_Save`).
6. **The child-entity test.** "Child entity" means an entity that some entity carries as a child
   collection (`EntityMetadata.Children`). `!IsTopLevel` would be wrong: system-written stacks
   derive from `Entity<int>`.

### Open risks

- **Missing label keys.** Core's `Strings.resx` has no `Action_Read`, `Action_Save`,
  `Action_Delete`, `Core_User_Plural` or `Core_Role_Plural`, so those labels emit humanized
  English fallbacks until the string work adds the keys.
- **`INeutralStringKeys`.** The default reads manifest resources ending in
  `.Resources.Strings.resources`. PC-046's string pack composer should replace it, or implement
  the seam, so the emit and the pack agree on which keys exist.
- **Sensitivity of a pair the stack contributor also registers.** PC-063's `StackSecurableContributor`
  will register `core.User` × `Read` with feature `core`, matching ours.
  - If it passes a different filter root or owner, the gate reports a conflict, which is the
    intended behaviour.
- **Settings securables.** `core.Settings.General` and the categories are not registered here; that
  is spec 0013 §5.5's checkpoint. The general category's `Save` default applies once it registers.

### What reviewers should examine hardest

- The merge and sensitivity rules in `SecurableRegistry`, especially the marked-both-ways
  outcome, the case-spelling problems, and the first-wins feature.
- The cycle detection's once-per-cycle reporting in `SecurablesCheck.CheckOwnerChains`, and the
  owner-navigation target rule: the owner pair's filter root, else the owner resource's first
  non-null one.
- The endpoint audit's alias refusal, and that `MapTellma`'s run stays registry-free.
- The label chains, especially settings categories and the entity detection by metadata name.

Deviation judgments:

- **Composed and frozen on first resolution.** Accepted. Contributors are services that read
  other services, so they cannot run before the container exists. The realised gate resolves the
  registry in `StartingAsync`, so every §4.5 finding still fails startup before traffic. Spec
  0014 §1.2's "frozen in the realise phase" should be amended to match.
- **`CoreFeature` registers `core.User` × `Read`.** Accepted as an interim. It is idempotent
  against 0015's stack contributor, which registers the same tuple (filter root `core.User`,
  feature `core`). Without it, §4.5's owner rule fails every host.
- **Fingerprint covers owners and aliases.** Accepted. No spec or component recomputes the
  fingerprint from §4.1's four fields; it is only compared with itself. An owner or alias change
  does change what a grant reaches. It is untested (R1-3).
- **Unregistered mark is a problem; a pair marked both ways stays sensitive.** Accepted. Both are
  fail-safe. A mistyped `MarkSensitive` would otherwise silently fail to protect a pair, and the
  both-ways pair fails startup anyway.
- **Internal `INeutralStringKeys` seam.** Accepted. It is internal and `TryAdd`-registered, so
  the string-pack checkpoint can replace it without breaking a contract.
- **Missing keys fall back to humanized labels.** Accepted: `ClientSecurable` declares nullable
  fallbacks for exactly this. The entity-resource fallback is singular next to a plural key
  (R1-5).

Implementer rulings not listed above, which I also checked:

- The child-entity test through `EntityMetadata.Children`: correct. Every Queryex navigation is
  many-to-one, so any resolved path is the to-one path §4.5 asks for.
- Pair-level cycle detection: consistent with §5.5, where the evaluator recurses on
  `(OwnerResource, A)`.
- Once-per-cycle reporting, lollipop chains and self-owners: traced by hand and pinned by
  `An_owner_cycle_is_refused_once_per_cycle`.
- The "marked both ways" message: always names the first marker, who necessarily marked the other
  way. Correct.

### Findings

**R1-1 (major): the registry orders a resource's actions alphabetically, against spec 0032 §5.2's
"registry order", and the conflict is not flagged.**

- Where: `src/core/Tellma.Core/Access/SecurableRegistry.cs:105-112` (the `ThenBy` over `Action`),
  and through it `ForResource` and the `securables` section that
  `SecurablesClientAssetContributor` writes in `All` order.
- What the specs say:
  - Spec 0014 §4.1 says `All` is "ordered by resource, then action".
  - Spec 0032 §5.2 (line 619) says the editor's actions "follow registry order ("Read", "Create and
    edit", "Activate and deactivate", "Invite")". That is Read, Save, Activate, Invite: the
    platform's operation order, not alphabetical.
- Failure: `core.User`'s actions reach the client as Activate, Credentials, Delete, Invite,
  Preferences, Read, Save. A role editor built to §5.2, which takes the metadata order as is,
  lists "Activate and deactivate" first and "Read" near the end. The two specs cannot both hold
  with ordinal sorting, and nothing records which one won. The order is a wire contract the client
  checkpoints will build on.
- Fix:
  - Within a resource, order actions by the platform order of `AccessActions` (Read, Save, Delete,
    Activate, Invite, Preferences, Credentials, Retry, Cancel, Resume, Share, Publish, Transfer).
    Put any other action after them, ordinal-ignore-case. This still reads as "by resource, then
    action", is independent of registration order, and gives §5.2's order.
  - Pin it in `All_is_ordered_by_resource_then_action_ignoring_case_and_lookups_ignore_case` and
    the golden. Alternatively keep ordinal sorting and report the conflict to the orchestrator for
    a ruling.

**R1-2 (minor): only part of Core's default sensitive set is pinned by a test.**

- Where: `SecurableRegistry.CoreSensitive`
  (`src/core/Tellma.Core/Access/SecurableRegistry.cs:42-57`), and
  `test/core/Tellma.Core.Tests/Access/SecurableRegistryTests.cs:194`.
- What is covered: `core.User` × `Save`/`Delete` (registry test), plus `core.Role` × `Activate`
  and `core.Settings.General` × `Save` (golden).
- Failure: delete any of these pairs from the set, or misspell them, and every test stays green.
  The user-administration step-up then silently stops applying.
  - `core.User` × `Activate`, `Invite`, `Credentials`
  - `core.Role` × `Save`, `Delete`
  - `core.Schedule` × `Save`, `Delete`, `Activate`
- Fix: one test asserting that `CoreSensitive` equals spec 0014 §4.3's twelve pairs exactly.
  Alternatively, register all twelve and assert `IsSensitive` on each, plus `false` on a
  neighbour such as `core.User` × `Read`.

**R1-3 (minor): the fingerprint's owner fields, an accepted deviation, are untested.**

- Where: `src/core/Tellma.Core/Access/SecurableRegistry.cs:431-432`, and
  `test/core/Tellma.Core.Tests/Access/SecurableRegistryTests.cs:270`.
- What is covered: the test moves the fingerprint with sensitivity, a filter root and an alias.
- Failure: drop `Owner.Resource` and `Owner.Navigation` from the line (or the alias lines' old
  name) and no test fails. Yet the commit lists owners and aliases as part of the fingerprint.
- Fix: add one `Assert.NotEqual` for the same securable with a different owner navigation.

**R1-4 (minor): a throwing contributor hides the endpoint audit's and the notification-types
check's other findings, and is reported three times.**

- Where:
  - `src/core/Tellma.Core.AspNetCore/Routing/TellmaEndpointAudit.cs:57`
  - `src/core/Tellma.Core/Composition/Checks/NotificationTypesCheck.cs:65`
  - `src/core/Tellma.Core/Access/SecurableRegistry.cs:88-94`
- Failure, step by step:
  1. A distribution's contributor throws, for example a `NullReferenceException`.
  2. DI does not cache a singleton whose constructor threw, so `core.securables`,
     `core.notification-types` and `host.endpoint-audit` each re-run every contributor. Each gets
     the same exception.
  3. The gate turns each into "The check failed with InvalidOperationException …".
  4. Every other finding of the endpoint audit (a tenant endpoint off the groups, a reserved
     route word) and of notification types (a Guid-keyed target) is lost in that run.
  5. The developer fixes the contributor and only then meets the rest. This defeats the gate's
     "every problem at once".
- Fix, either of:
  - Have those two consumers resolve the registry inside a try/catch and continue with `null`
    (`core.securables` already reports the failure).
  - Have the registry record a throwing contributor as a `Problem` and keep composing. That
    matches the class remark "Composition never throws over what the contributors registered",
    and the gate still fails startup.

**R1-5 (minor): an entity resource's fallback is singular while its key is the plural one.**

- Where: `src/core/Tellma.Core/Access/SecurablesClientAssetContributor.cs:110`. The golden pins
  it at `test/core/Tellma.Core.Tests/Access/SecurablesClientAssetContributorTests.cs:44`
  (`"resourceLabelKey":"Core_Role_Plural","resourceLabelFallback":"Role"`).
- Failure:
  - Spec 0032 §5.2 labels a resource in the plural ("Centers").
  - Core's `Strings.resx` declares neither `Core_User_Plural` nor `Core_Role_Plural`, as the
    implementer notes. So the deployed role editor's resource picker shows "User" and "Role"
    beside other features' plural labels.
  - A pack entity without strings shows "Center" for `gl.Center`.
- Fix, either of:
  - Add `Core_User_Plural` ("Users") and `Core_Role_Plural` ("Roles") to Core's `Strings.resx`,
    with the satellites if the satellite check requires them. The two entities this checkpoint
    exposes then resolve without a fallback.
  - Give the plural link a pluralized fallback.
  - Either way, record the gap in the ledger, so the string checkpoint does not miss it.

**R1-6 (minor): a second registration naming a different feature is dropped silently.**

- Where: `src/core/Tellma.Core/Access/SecurableRegistry.cs:252-253`.
- What the spec says: §2 defines the securable as the tuple
  `(Resource, Action, FilterRoot?, IsSensitive, Feature, Owner?)`. §4.1 makes only "the same
  tuple" idempotent. Merge reports a differing filter root, owner or spelling, but keeps the first
  registration's feature without a word.
- Failure:
  - `CoreFeature` registers `core.User` × `Read` (feature `core`).
  - A pack's stack contributor registers the same pair passing `feature: "acme"`, as 0015 §2.7
    does with each stack's `Feature`.
  - The permissions editor (0032 §5.2) groups the pair under whichever contributor realised
    first. Nothing tells the author their `feature` argument was ignored.
- Fix: compare the effective feature (`declaration.Feature ?? declaration.Contributor`) with the
  entry's. When they differ, report a problem as for the owner, or at least when the second
  registration named its feature explicitly.
