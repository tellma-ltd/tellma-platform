# PC-039: Securables registry, startup audit and securables metadata section

## Implementer notes

### What was built, and where

- **Contracts** (`src/core/Tellma.Core.Abstractions/Access/`): `SecurableRef`, `SecurableOwner`,
  `SecurableDescriptor` (`SupportsFilter` derived), `SecurableRegistryBuilder`,
  `ISecurableContributor` (`[CollectionService]`, D-016), `ISecurableRegistry`,
  `NoActivityStampMetadata` and `ClientSecurable`.
  - The builder records every call as made, with the feature of the running contributor
    (internal `SecurableDeclaration`, `SecurableAliasDeclaration`, `SecurableMarkDeclaration`).
  - It throws only on null arguments and once frozen. Grammar and conflicts are startup problems,
    so the gate reports them all at once.
  - `SecurableEndpointMetadata` and `MemberEndpointMetadata` were kept as PC-015 seeded them.
- **Contribution item**: `SecurablesContributionItem` and the sugar `FeatureContribution.Securables`.
  - `SecurablesContributionRealizer` registers each item as a singleton `ISecurableContributor`
    (`FeatureSecurableContributor`) on behalf of its feature.
  - A null configuration is a composition problem.
- **Registry** (`src/core/Tellma.Core/Access/SecurableRegistry.cs`, registered by `CoreFeature`):
  runs every contributor once, on first resolution, then freezes the builder. It:
  - merges by pair (ignoring case, the first spelling and feature win, sensitive if any
    registration says so);
  - composes the aliases (one step, to a registered resource);
  - applies Core's sensitive defaults and the marks;
  - sorts `All`, and computes the fingerprint.
  - Everything wrong is kept on `Problems`, which `core.securables` reports.
  - A throwing contributor fails resolution with an exception naming the contributor and its
    feature.
- **Check** `core.securables` (`Composition/Checks/SecurablesCheck.cs`, built-in, no
  infrastructure). It reports:
  - the registry's problems;
  - an unknown feature;
  - an owner that is not a registered resource, or one declared without a filter root;
  - owner-chain cycles, at pair level (each pair to the same action of its owner), once per
    cycle.
  - Against the model, when it builds:
    - a filter root that is not an entity of `GetSchema(MultilingualShape.All)`;
    - a child entity's securable without an owner;
    - an owner navigation that is not a path of navigations, or that ends elsewhere than the
      owner's filter root.
- **Endpoint audit** (`Tellma.Core.AspNetCore/Routing/TellmaEndpointAudit.cs`): an optional
  `ISecurableRegistry` parameter. Every `SecurableEndpointMetadata` on any endpoint must `Find` a
  pair registered under that resource. A pair reached only through an alias is refused.
  - The realised gate passes the registry. `MapTellma`'s early run passes none.
- **Client metadata**: `SecurablesClientAssetContributor` writes the Core chunk's `securables`
  section. Label keys follow spec 0032 §12.4's chains:
  - The keys come through a new internal seam, `INeutralStringKeys`: TryAdd-registered, reading
    every composed feature assembly's neutral `*.Resources.Strings.resources`.
  - Fallbacks come from a new internal `NameHumanizer` in `Tellma.Core.Localization`.
- **CoreFeature** registers:
  - the registry and the contributor;
  - `core.UserStamp` × `Read` (filter root `core.UserStamp`, owner `core.User` through `User`);
  - `core.User` × `Read` (filter root `core.User`). See the deviations.
- **`NotificationTypesCheck.CheckTargets`** (D-061) also accepts a registered securable
  resource, matched as spelled. The `int`/`long` key rule applies to stack resources only.

### Deviations

1. **The registry is composed and frozen on first resolution, not in `AddTellma`'s realise phase**
   (spec 0014 §1.2, §4.1 "frozen at realise").
   - Contributors are services that read other services: spec 0015's `StackSecurableContributor`
     reads `IStackRegistry`. None of them exists before the container is built.
   - The realised gate's `core.securables` resolves the registry at startup, so every §4.5
     finding still fails startup before traffic.
   - `ARCHITECTURE.md` does not say when it freezes, so it is unchanged.
2. **`CoreFeature` also registers `core.User` × `Read`.**
   - §4.5 requires every `Owner` to name a registered resource. Until PC-063's stack contributor
     lands, nothing registers `core.User`, so `core.UserStamp`'s owner would fail every host.
   - The stack contributor's identical registration will be idempotent. PC-063 may drop this
     line.
3. **The fingerprint also covers owners and aliases.**
   - Its lines are `Resource|Action|FilterRoot|IsSensitive|OwnerResource|OwnerNavigation` plus
     `alias|Old|New`, sorted ordinally.
   - Spec 0014 §4.1 lists only the first four fields. An owner and an alias change what a grant
     reaches as much as a filter root does.
4. **Rulings where the spec is silent** (WATCHLIST lead "MarkSensitive on an absent pair"):
   - A `MarkSensitive`/`MarkNotSensitive` of an unregistered pair is a problem.
   - A Core default whose pair nobody registers (`core.Schedule` until 0020) is ignored
     silently.
   - The same pair with another owner, or a resource or action spelled with another case, is a
     problem, like a different filter root. Any registration's `isSensitive: true` makes the pair
     sensitive.
   - A pair marked both ways is a problem and stays sensitive.
   - An explicit `feature` must name a composed feature.
   - A contributor registered by a factory or by the host, outside every feature, is attributed
     to `core`.
   - An alias is refused when it renames a resource to itself, names an old resource that is still
     registered, or a target that is not registered, or names a second target for the same old
     resource (which also rules out chains).
5. **Entity-resource label chain.** `<Schema>_<Entity>_Plural`, then `<Schema>_<Entity>` (spec 0013
   §7.6's plural → singular), then the humanized last segment of the entity name rather than of
   the leaf's class name, which a distribution's leaf renames.
   - The action prefix applies the entity-key rule (schema capitalized, dots → `_`) to every
     resource, including non-entity ones (`Core_Settings_General_Action_Save`).
6. **The child-entity test.** "Child entity" means an entity that some entity carries as a child
   collection (`EntityMetadata.Children`). `!IsTopLevel` would be wrong: system-written stacks
   derive from `Entity<int>`.

### Open risks

- **Missing label keys.** Core's `Strings.resx` has no `Action_Read`, `Action_Save`,
  `Action_Delete`, `Core_User_Plural` or `Core_Role_Plural`, so those labels emit humanized
  English fallbacks until the string work adds the keys.
- **`INeutralStringKeys`.** The default reads manifest resources ending in
  `.Resources.Strings.resources`. PC-046's string pack composer should replace it, or implement
  the seam, so the emit and the pack agree on which keys exist.
- **Sensitivity of a pair the stack contributor also registers.** PC-063's `StackSecurableContributor`
  will register `core.User` × `Read` with feature `core`, matching ours.
  - If it passes a different filter root or owner, the gate reports a conflict, which is the
    intended behaviour.
- **Settings securables.** `core.Settings.General` and the categories are not registered here; that
  is spec 0013 §5.5's checkpoint. The general category's `Save` default applies once it registers.

### What reviewers should examine hardest

- The merge and sensitivity rules in `SecurableRegistry`, especially the marked-both-ways
  outcome, the case-spelling problems, and the first-wins feature.
- The cycle detection's once-per-cycle reporting in `SecurablesCheck.CheckOwnerChains`, and the
  owner-navigation target rule: the owner pair's filter root, else the owner resource's first
  non-null one.
- The endpoint audit's alias refusal, and that `MapTellma`'s run stays registry-free.
- The label chains, especially settings categories and the entity detection by metadata name.
