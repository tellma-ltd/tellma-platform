### L0-B05-XC-2 (minor)
- Where: src/core/Tellma.Core/Notifications/Notifier.cs:393; src/core/Tellma.Core/Jobs/JobNotices.cs:99,133,141,185,194; src/core/Tellma.Core/Jobs/JobRunner.cs:579,592,820,845-849; src/core/Tellma.Core.Abstractions/Notifications/NotificationRequest.cs:41-44; docs/specs/0021-notifications-inbox-and-hub.md:230,474.
- Scenario: the job engine builds every worker notice with ActorUserId null, reading the request's XML doc ("null for the system"). The Notifier follows spec 0021 §3.1 instead and defaults a null actor to the scope's user unless the scope is the system's. A partition's completion notices are raised through the run-as user's scope, so a failed or confirmation-waiting job's notice names the run-as user as its actor (the user is shown as having caused their own failure; an administrator's notice for a user-owned schedule names its owner), while the same notices raised by a completion without a handler or by the poll store no actor.
- Fix: make "the system caused it" expressible and use it from the job engine (or raise the worker notices through a system-scoped notifier); correct the XML doc of ActorUserId; add an integration test that a failed run-as job's core.job.failed row has no actor on both the handler and the handler-less path.

### L2-PC-B05-FCS-1 (minor)
- Where: src/core/Tellma.Core/Jobs/JobRunner.cs:658-663 (same catch at :826-829); callbacks registered at JobRunner.cs:845-865, Notifier.cs:557 and :572-601, JobQueue.cs:152-167; skipped by DataExecutor.cs:247-249 when it throws at :486 / :641.
- Scenario: a completion batch whose commit the probe proves (the connection drops during COMMIT) ends in DataAccessAmbiguousException(Committed), and the executor never runs the batch's commit callbacks. JobRunner treats the completion as committed and runs only the write frame's post-commit phase, so inbox.changed is not published and the poller is not woken for the delivery jobs just inserted, job.changed does not reach the requester, and a job queued in the batch or a Retry-now outcome gets no wake. Nothing is lost, but follow-on jobs wait for the next poll and the requester's job row and inbox badge stay stale.
- Fix: on the proven-commit branches in JobRunner (SendAsync and CompleteAsync), wake the tenant's poller unconditionally and publish job.changed for each requester and inbox.changed for the notices' recipients; more generally, give DataBatch a way to run the committed callbacks for a commit the probe proved and call it from every Committed catch site. Add an integration test under fault injection asserting the wake and both events.

## Verdicts
- L0-B05-XC-1: fixed in a0800700: 'Jobs_OwnerUnavailable' has neutral and Arabic messages ("This item already has a job in progress. Wait for it to finish, then try again."). The inverse audit now also reflects JobEnqueueCodes, JobErrorCodes, JobValidationCodes, ScheduleValidationCodes and NotificationValidationCodes, with an allow-list of the three codes that never reach a user (Job.LeaseLost and Schedule.TickLeaseLost are caught by the worker and the scheduler; Jobs.EnqueueOutsideTransaction is a defect of the caller's batch). New integration test OutboxManagementTests.A_retry_is_refused_whole_when_another_retry_gave_the_email_a_live_job_since_its_validation drives the racing retry and asserts the root Jobs.OwnerUnavailable refusal and that nothing is written. Note on reachability: the retry's validation already refuses a row whose job is live, so only the race between the two rounds reaches the enqueue's refusal.
- L0-B05-XC-2: fixed in a0800700: the system user's id now means "the system caused it": the Notifier stores no actor for WellKnownIds.SystemUserId, whether named or defaulted from a system scope, and every job-engine notice (core.job.failed, core.job.pending-confirmation, core.job.held, core.scheduler.gap, core.schedule.paused) names it, so both completion paths and the poll agree. A handler's own success notices keep the default (the run-as user). NotificationRequest's ActorUserId doc now states the defaulting rule. Tests: NotifierTests (the system user stores none in a user and a system scope), JobCompletionRulesTests (the notices name the system), JobRunTests.Poll expectations, and NotificationJobsTests.A_failed_job_run_as_a_user_raises_its_notice_with_no_actor_whether_its_handler_or_the_system_completes_it (handler path in the run-as scope, and the handler-less path; the handler case fails against the old code). Deviation from spec 0021 §3.1's table: it says only "defaults to RequestContext.UserId; null in a System scope"; an explicit SystemUserId storing NULL is an extension that the spec should state.
- L1-B05-E2E-1: fixed in a0800700: both Acme READMEs give `provision --name "Acme 2" --category Live`; the distribution README also names `--category Sandbox --live-tenant <id>` and `provision --tenant <id>` to resume. The parser keeps refusing --name without --category, as spec 0011 states.
- L2-PC-B05-FCS-1: fixed in a0800700 for the job engine: on both proven-commit branches (the composed completion and the completion of the outcomes alone) JobRunner now wakes the tenant's poller unconditionally, publishes job.changed to each requester and inbox.changed to every recipient the completion's notices named (a superset of the changed inboxes, which costs a client a refetch at most), each sent at once rather than on the lost commit, and logs rather than throws a failure. The fixture audit gained a lost-response seam (the armed batch commits, then its caller hears only Committed, with no results completed and no callbacks run), and JobRunTests covers both branches (each fails against the old code). Pushed back on the general part (a DataBatch method replaying every committed callback from every Committed catch site): the other sites (save, delete, action, settings, schedule tick) each answer a proven commit their own way, and some callbacks read what the lost response carried (the version-tag bump announces from the outcome's snapshot), so replaying them is a data-layer contract change to spec 0012's ExecuteAsync rather than a batch fix. Left open for the orchestrator: a handler's enlisted writes on a proven completion still lose their own callbacks' events (their delivery jobs are covered by the unconditional wake), and ScheduleTick's proven-commit branch skips its wake.
