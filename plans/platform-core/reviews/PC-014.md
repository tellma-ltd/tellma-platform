# PC-014: Account entry URL and sign-in language

## Implementer notes

Spec 0010 Part A §A.9 and §A.10. Production code is under `src/apps/Tellma.Identity/`; nothing
under `client/` or in any other project changes.

### What was built, and where

**The account entry (§A.9)**

- `Controllers/AccountController.cs` (new): `GET account` (so `{issuer}/account`, `/id/account`
  in-proc through the existing route convention), `[Authorize]` on the identity cookie. It maps
  `section` through `Infrastructure/AccountSections.cs` (new; `profile` is the default and the
  answer to any unknown name), answers 302 with `Cache-Control: no-store`, and carries
  `client_id`, `return_url` and `ui_locales` to the page.
- `Hosting/IdentityConfigurator.cs`: the cookie's `OnRedirectToLogin` is wrapped. The challenge
  forwards the request's `ui_locales` as a top-level value of the sign-in URL and sets `no-store`,
  then calls the handler that was in place.
- `Infrastructure/ApplicationLinkResolver.cs`: `ResolveAsync(clientId, returnUrl, ct)`. A
  first-party client with a registered `Origin` gets the `return_url` when it is same-origin, else
  the origin's root; anything else gets `Ui:ApplicationUrl` or no link. The same-origin rule is
  `InvitationReturnUrlValidator.IsSameOrigin`'s, now exposed as `TryGetSameOriginUri` so the link is
  written from the parsed address.
- `Areas/Identity/Pages/Shared/_ManageLayout.cshtml`: reads the values through `CarriedQuery`,
  calls the new resolver, and no longer spells `asp-route-client_id` on each nav link (see below).

**The carried query (§A.9 "every Manage navigation link keeps the three values", §A.10 "links and
redirects between sign-in pages keep `ui_locales`")**

One mechanism instead of a route value repeated at about forty link and redirect sites:

- `Infrastructure/CarriedQuery.cs` (new): the one reader of the three values (single-valued,
  non-blank, length-capped; `ui_locales` reduced to well-formed tags), `AppendTo(url)` (adds only
  what the URL does not already name) and `WithUiLocales(url, culture)` (replaces an existing
  value, every other pair kept byte for byte).
- `Infrastructure/IdentityPageLinks.cs` (new): the rule. Only a local URL whose path, after the
  host's path base and the engine's, lies under `/Identity/Account` or `/Identity/Manage` receives
  the values. Protocol endpoints, `/identity/culture`, `/account`, absolute URLs and any path with
  a dot segment, an escape or a backslash do not.
- `Infrastructure/CarriedQueryTagHelper.cs` (new): applies the rule to `href`, `action` and
  `formaction` of every `a`, `form`, and `button`/`input` in an identity view. It runs after the
  framework's link and form helpers (default order 0 against their -1000).
- `Infrastructure/CarriedQueryRedirectFilter.cs` (new): applies it to `RedirectToPageResult`,
  `LocalRedirectResult` and `RedirectResult` of every page in the identity area, registered by an
  area-folder convention in `Hosting/TellmaIdentityServiceCollectionExtensions.cs`.
- `Areas/Identity/Pages/Account/ExternalLogin.cshtml.cs`: the callback address handed to the
  external provider goes through `IdentityPageLinks.Carry`, because it is neither a rendered link
  nor a redirect result.

**The sign-in language (§A.10)**

- `Controllers/AuthorizationController.cs`: `RedirectToLogin` adds the validated request's
  `ui_locales` (so a pushed request's value as readily as a query's). The controller carries
  `[RequestedLanguage]`.
- `Infrastructure/RequestedLanguageAttribute.cs` (new): a resource filter that renders the
  authorization endpoint's own pages (consent) in the request's language when only the default or
  `Accept-Language` decided the culture so far.
- `Infrastructure/LanguageCatalog.cs`: `Match(uiLocales)`, the same first-supported-tag rule with
  parent fallback that request localization applies to the query value.
- `Infrastructure/UiLocalesRequestCultureProvider.cs`: reads through `CarriedQuery`.
- `Controllers/CultureController.cs` and `Areas/Identity/Pages/Manage/Index.cshtml.cs`: a language
  the user picks replaces the `ui_locales` on the address they return to.

**Docs**: `src/apps/Tellma.Identity/README.md` (new section "The account entry and the requested
language"), `test/apps/Tellma.Identity.E2E/README.md`, and ARCHITECTURE.md's identity-amendments
sentence, which now names the entry URL, the same-origin rule and the pushed-request case.

**Tests**

- Unit (`test/apps/Tellma.Identity.Tests/Infrastructure/`, 180 cases): `AccountSectionsTests`,
  `ApplicationLinkResolverTests` (same origin, another port, userinfo, `javascript:`, `data:`,
  relative, protocol-relative, weaker scheme, look-alike host, backslash, unknown client,
  third-party client, origin-less client, configured fallback, canonical form),
  `CarriedQueryTests`, `IdentityPageLinksTests`, `CarriedQueryTagHelperTests`,
  `CarriedQueryRedirectFilterTests`, `RequestedLanguageTests`.
- Integration (`test/apps/Tellma.Identity.IntegrationTests/Flows/`): `AccountEntryTests` (9) and
  `SignInLanguageTests` (4), with `Infrastructure/HtmlPage.cs` to read pages as documents.
- E2E (`test/apps/Tellma.Identity.E2E/RequestedLanguageTests.cs`, 2): `ui_locales=ar` through a
  pushed request, signed in through the email code in Arabic to the client's callback; the account
  entry in Arabic and its back link followed to `return_url`. The fixture gains
  `CreatePushedRequestClientAsync`.

### Deviations from the spec

1. **The three values are kept on every link, form and redirect between all identity pages**, not
   only on the Manage navigation (all three) and between the sign-in pages (`ui_locales`). A
   sign-in page given a `client_id` keeps it; the signed-out page reached from an account page
   keeps all three. This is a superset of the spec, chosen so that a page added later cannot
   forget.
2. **`AccountController.Index` binds only `section`.** The other three values are read through
   `CarriedQuery`, so the entry passes on exactly what a page will accept: a value given twice,
   blank, or over its cap (`client_id` 100, `return_url` 2048, `ui_locales` 255) is dropped, and
   `ui_locales` is reduced to its well-formed tags. The spec lists four parameters and no limits.
3. **The back link is the parsed address** (`Uri.AbsoluteUri`), not the caller's text, so a browser
   cannot read it differently from the comparison that allowed it. For an ordinary URL the two are
   identical.
4. **Every cookie challenge** forwards `ui_locales` and sets `no-store`, not only the challenge of
   `/account`: an expired session on a Manage page behaves the same way.
5. **Consent under a pushed request follows the request's language** (`RequestedLanguageAttribute`).
   The spec's sentence "the return to the authorization endpoint re-applies it from the request" is
   satisfied by the redirect alone; without the filter an Arabic flow has an English consent page
   in the middle. It ranks below the language cookie on purpose (see "Examine hardest").
6. **The language switch and the profile's language field rewrite `ui_locales`** on the address
   they return to. The spec is silent; without it the query value, which outranks the cookie, would
   undo the user's own choice on every page that carries it.

### Open risks

- **Two pre-existing un-prefixed paths were left alone**: `EmailCode.cshtml.cs` falls back to the
  literal `/Identity/Account/Login`, and `EndSessionController` redirects to the literal
  `/Identity/Account/LoggedOut`. Both miss the in-proc path base. They are outside this
  checkpoint and unchanged by it.
- **In-proc coverage of the signed-in redirect is by unit test only.** The in-proc integration
  factory has no email capture, so the integration test covers the in-proc challenge, the Arabic
  sign-in page under `/id` and the page-recognition pin, not `/id/account` with a session.
- **A pathological `return_url`** (2048 characters, nearly all needing escaping) is escaped twice
  inside the challenge's return address and can exceed Kestrel's request-line limit. An ordinary
  URL of that length does not.
- **The `authenticator` section** opens `/Identity/Manage/EnableAuthenticator` as the spec says,
  a page the navigation deliberately omits.
- **E2E sign-in codes**: the standalone fixture now requests 8 of the 10 allowed per hour.
- **One existing E2E test failed once under load and was not retried into green.** In the full
  identity E2E run on Windows (38 passed, 1 failed, with other slots building on the same machine)
  `InProcPasskeyTests.Register_a_passkey_then_sign_in_with_it_under_the_path_base` timed out in
  `PasskeyCeremonies.RegisterThenSignInAsync`: the helper allows the conditional passkey ceremony
  5 seconds, then clicks "Sign in with a passkey" unconditionally. The ceremony finished just
  after the 5 seconds (the failure log shows the page already on `/id/Identity/Manage/Passkeys`),
  so the button was gone. Run alone, the test passed in 12 seconds. The helper and the passkey
  flow are untouched by this checkpoint, and the request carries none of the three values, so the
  tag helper and the redirect filter change nothing on that path. Reported to the orchestrator as
  a flaky-test item, not fixed here.

### What reviewers should examine hardest

1. **`IdentityPageLinks.IsIdentityPage`.** It decides where caller-written values are repeated. It
   must never say yes to `/connect/authorize` (a parameter added there changes the request) or to
   another origin. Look for a path form a browser resolves elsewhere that still passes.
2. **`CarriedQueryTagHelper.ReadAddress`** decodes an attribute the view wrote and re-encodes on
   write. Look for a double-encoding or an attribute break-out.
3. **`ApplicationLinkResolver`**: the only place `return_url` becomes something a user clicks.
4. **The convention's registration order.** `RazorPagesOptionsSetup` replaces the conventions
   collection, so the area-folder convention is registered after `AddRazorPages()`. Registered
   before it, the filter silently never ran; three integration tests caught that.
5. **`RequestedLanguageAttribute`'s precedence.** URL value, then cookie, then the pushed request,
   then `Accept-Language`. Ranking the pushed request above the cookie would be more uniform with
   the sign-in pages, but the language switch on a pushed request's consent page has no URL value
   to rewrite and would then do nothing.
6. **`CarriedQuery.WithUiLocales`** rebuilds a query by hand to keep every other pair's encoding;
   the consent test relies on the authorization URL surviving it unchanged.

## Review 1

### Findings

Paths are under `src/apps/Tellma.Identity/` unless they start with `test/`.

**R1-1 (major) — A language the user picks on the sign-in page is undone as soon as they sign in
to the account pages.**
`Controllers/CultureController.cs:73-76`, `Hosting/IdentityConfigurator.cs:150-160`,
`Controllers/AccountController.cs:44`.

- **What happens.** The cookie challenge puts `ui_locales` in two places on the sign-in URL: as a
  top-level value, and inside `ReturnUrl`, which is the challenged address
  (`/account?…&ui_locales=ar…`, or a Manage page's URL with its carried values). The language
  switch rewrites only the top-level value (`WithUiLocales` deliberately leaves a nested one
  alone; `test/apps/Tellma.Identity.Tests/Infrastructure/CarriedQueryTests.cs:185` pins that).
  After sign-in, Login and EmailCode `LocalRedirect` to `ReturnUrl`. `/account` is not an identity
  page, so the redirect filter leaves it as it is, and the URL already names `ui_locales` anyway,
  so `AppendTo` would keep it. The entry then forwards `ui_locales=ar` to the Manage page, where
  the URL value outranks the cookie that the switch just wrote.
- **Failure scenario.** A signed-out user prefers English. They open Account from an Arabic
  client (`/account?client_id=acme&ui_locales=ar&return_url=…`), land on the Arabic sign-in page,
  pick English and sign in. Every Manage page then renders in Arabic, because every link carries
  `ui_locales=ar`, until they pick English a second time. The same thing happens when a Manage
  page's session expires mid-visit. Deviation 6 exists to stop exactly this ("the carried value,
  which outranks the cookie, would undo the user's choice"), but it covers only the one hop the
  switch returns to. (A query-string authorization request behaves the same way at consent, but
  there the spec says the request's own value is re-applied, so that path is not part of this
  finding.)
- **Suggested fix.** Choose one:
  - In the challenge wrapper, remove `ui_locales` from the nested return address and keep only
    the top-level value. Then let `IdentityPageLinks` treat the account entry (`{PathBase}/account`)
    as a carry target, so the sign-in page's current value, switched or not, is what reaches the
    entry.
  - Or let `CultureController` also rewrite `ui_locales` inside a `returnUrl`/`ReturnUrl` value
    when that nested address is an identity page or the account entry, never a protocol endpoint.
- **Test.** An integration case: anonymous `/account?…&ui_locales=ar` → sign-in page → switch to
  `en` → sign in with the email code → follow the entry → the Manage page has `lang="en"`, and its
  links carry `ui_locales=en` (or no `ui_locales`).

**R1-2 (minor) — Nothing pins the redirect filter in the in-proc composition, the hosting shape
the implementer flagged for the convention-ordering trap.**
`Hosting/TellmaIdentityServiceCollectionExtensions.cs:225-234`;
`test/apps/Tellma.Identity.IntegrationTests/Flows/AccountEntryTests.cs:328-359`.

- **What happens.** The standalone integration tests catch a filter that never runs (the
  implementer says three did). The in-proc test covers only the challenge and the tag helper's
  links on the sign-in page. A distribution host composes the engine into its own service
  collection, and its own MVC and Razor Pages registrations may come before or after
  `AddTellmaIdentity`. If ordering ever discards the convention there, no test fails: page
  handler redirects silently drop `ui_locales`, `client_id` and `return_url` in-proc only, which
  is the production shape for every in-proc distribution.
- **Suggested fix.** Add an in-proc integration assertion that needs no email capture. For
  example, take the antiforgery token from `GET /id/Identity/Account/Login?ui_locales=ar`, then
  anonymously `POST /id/Identity/Account/Logout?ui_locales=ar&client_id=acme` (the page is
  `[AllowAnonymous]` and answers `RedirectToPage("LoggedOut")`). Assert
  `Location: /id/Identity/Account/LoggedOut?…ui_locales=ar…client_id=acme`.

**Checked, with no finding** (recorded for Review 2):

- **Back-link open redirect.** I traced `TryGetSameOriginUri` and the emitted `AbsoluteUri` for
  these inputs: userinfo (`acme@evil`, `user:pass@`), `%2F@` in the authority, a `#@` fragment
  trick, a backslash (`\@evil`), `https:` without slashes, protocol-relative, relative
  (`/x` parses as `file:///x` on Linux, then fails the scheme check), `javascript:`, `data:`,
  another port, a weaker scheme, a look-alike suffix host, a trailing-dot host and an IDN
  look-alike. Each one either keeps the registered host or falls back to the origin root. The
  response's `Referrer-Policy: strict-origin-when-cross-origin` keeps the carried values out of
  the client's Referer.
- **Carry rule.** `IsIdentityPage` refuses absolute, protocol-relative and `/\` forms, every
  `.`, `%`, `;` and `\` in the path, and every path outside the two folders after both path
  bases. The protocol endpoints, `/account` and `/identity/culture` never receive values. The
  tag helper decodes once and re-encodes on write, so there is no double encoding and no way out
  of the attribute.
- **The 2048-character `return_url` and Kestrel's 8 KB request line.** A client builds
  `return_url` from `location.href`, which is already ASCII and percent-escaped. Even if it were
  all `%XX` triplets, the challenge's doubly escaped sign-in URL would be about
  2048 × 7 / 3 ≈ 4.8 KB. Only raw non-ASCII text exceeds the limit, and only someone crafting
  the link would produce it. They harm only the person who follows their own link (414), which
  they could do with any long URL.
- **PAR consent precedence (URL > cookie > pushed > Accept-Language).** The code matches the
  intent, and the deviation is justified: a pushed request's switch has no URL value to rewrite.
- **Gates.** I rebuilt the unit and integration projects at 5d356b3 (0 warnings) and ran the
  `Tellma.Identity.Tests` unit filter (944 passed), plus `AccountEntryTests` and
  `SignInLanguageTests` (13 passed). I also ran `Tellma.Identity.E2E`'s `RequestedLanguageTests`
  on Windows (2 passed). The done-when's Linux E2E job still rests on CI.

### Responses

Both fixed in the commit "PC-014: review 1 fixes" (child of 5d356b3). Nothing pushed back.

- **R1-1: fixed**, by the reviewer's second option. The language switch now also replaces
  `ui_locales` inside the address a sign-in page returns to.
  - `IdentityPageLinks.WithLanguage` replaces the URL's own value as before
    (`CarriedQuery.WithUiLocales`). Then, when the URL is a sign-in or account page, it follows
    that page's `returnUrl` (matched without case, so the challenge's `ReturnUrl` too) and does
    the same there. It follows only an address that is itself an identity page or the account
    entry (`IsAccountEntry`, new, under both path bases). `CultureController` calls it in place
    of `WithUiLocales`.
  - Never a protocol endpoint, in either position. A nested `/connect/authorize` is left as
    written, and a `returnUrl` parameter on an authorization request is that request's own and
    is not looked into. A `returnUrl` given twice is not rewritten. The application's
    `return_url` is never looked into.
  - It follows up to three nested return addresses, not one. A page that holds a return address
    and is then challenged (the passkey prompt after sign-in, with an expired session) makes
    two.
  - I chose this over the first option (strip the nested value at the challenge and carry to the
    entry) because the nested value stays the single thing the final redirect reads. The first
    option depends on every way of finishing sign-in passing through the redirect filter.
  - `CarriedQuery.WithValue` is the new general piece: it rewrites the one value of a named pair
    and keeps every other pair as written.
  - Tests. Integration: `A_language_chosen_on_the_sign_in_page_holds_once_the_user_has_signed_in`
    runs the reviewer's scenario for the entry and for a Manage page whose session ran out:
    challenge, switch to English, sign in with the email code, and the account page has
    `lang="en"`, every internal address carries `ui_locales=en`, and the back link is intact.
    Unit: 10 new tests (46 cases) in `IdentityPageLinksTests` (the entry rule, the nested
    rewrite, each address it must not reach into, the depth bound, the in-proc mount) and 3
    (5 cases) in `CarriedQueryTests`.
  - Not changed, as the finding says: a query-string authorization request keeps its own
    `ui_locales` when the user switches on the sign-in page, so a consent page after it follows
    the request until the user switches there.
- **R1-2: fixed.** `Mounted_in_a_host_a_page_handlers_redirect_keeps_what_the_page_was_given`
  does what the reviewer suggested, against the in-proc host: an anonymous
  `POST /id/Identity/Account/Logout?ui_locales=ar&client_id=acme` answers
  `Location: /id/Identity/Account/LoggedOut` with exactly those two values, and that page
  renders in Arabic. A convention discarded in the in-proc composition now fails this test.
  The registration itself is unchanged: `AddTellmaIdentity` calls `AddRazorPages()` just before
  it adds the convention, so the convention is added after the options setup whichever side of
  `AddTellmaIdentity` a host makes its own MVC registrations.
- **Gates re-run**: `dotnet build Tellma.slnx` (0 warnings), `dotnet format --verify-no-changes`
  (clean), the unit filter across the solution (`Tellma.Identity.Tests` 995 passed),
  `Tellma.Identity.IntegrationTests` (193 passed), and `Tellma.Identity.E2E` on Windows
