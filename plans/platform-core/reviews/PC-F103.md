# PC-F103: core entity label strings

## Implementer notes

### The defect

Core's `Strings.resx` declared plurals and a few action labels for its entities, but not their
singular labels, members or enum values. The emit (spec 0029 §2.4) wrote a `labelFallback` for each
key a chain could not resolve, so the platform alone emitted 306 fallbacks and every
distribution's `tellma-client build` warned `label-missing` for keys it cannot own.

Measured before and after, with the same commands:

| Measure | Before | After |
|---|---|---|
| Platform alone: keys written with a fallback (`PlatformLabelsTests`, every client metadata section of `TestComposition.Compose(_ => { })`) | 306 | 0 |
| Acme: `label-missing` lines of `pnpm run build` in `Tellma.Distro.Acme.Client` | 323 | 0 |

Acme's 323 were core's 306, 12 of Acme's own (`Acme_*_Id`, `_CreatedById`, `_ModifiedById`) and 5 of
GL's (`Gl_Center_Id`, `_CreatedById`, `_ModifiedById`, `_SubtreeCount`, `_ActiveSubtreeCount`).
All 17 are columns the platform's conventions add, so they now resolve through Core's shared keys
(below) and Acme's own count falls to 0, not to 17.

### What was built

- **Core's labels, English and Arabic** (`src/core/Tellma.Core/Resources/Strings.resx`,
  `Strings.ar.resx`; 250 keys each). Every key is the first key of its spec 0013 §7.6 / spec 0029
  §2.4 chain; none is invented.
  - Each entity's singular label goes just before its existing `_Plural`; its members, its enums'
    values and its action fields follow it. New action and field keys sit after the existing
    `Core_User_Action_*` entries. Blob, Settings, SettingEntry and UserStamp had no block, so they get
    a new commented section before "Settings and access", with `Core_Blob_Plural` and
    `Core_SettingEntry_Plural`.
  - A foreign key carries the label (`Core_User_ImageId` = "Picture"), and its navigation resolves
    through the FK chain, as GL and Acme already do (`Gl_Center_ParentId`, `Acme_Customer_CurrencyId`).
    So no `Core_<Entity>_<Navigation>` key was needed.
  - Action fields that match an entity member resolve through `Core_User_<Field>`
    (`MeSave_ContactEmail` → `Core_User_ContactEmail`). Only fields with no member key got their own
    (`MeSave_Name2`, `MeSave_Name3`, `MeSave_Concurrency`, the report sharing fields, …).
  - Amharic carries only the CLDR region and calendar names and the boot strings, so no `am` labels
    were added. It falls back to English, as the brief allows.
- **Shared keys for the platform's own conventional columns.**
  - `Id`, `CreatedById`, `ModifiedById`, `SubtreeCount` and `ActiveSubtreeCount` are added to the
    shared labels block and to `StringKeyConventions.SharedMemberLabels`.
  - They are the key that `EntityBase`, the audit convention (`StackDescriptorBuilder.AuditColumns`)
    and `TreeEntity` give every entity. Their label is never entity-specific, and spec 0013 §7.6's
    `<Property>` step ("Core ships `Name`, `Code`, …") is the hook for this.
- **`ConventionalStringKeys` now derives the read-only roots' keys**
  (`src/core/Tellma.Core/Localization/ConventionalStringKeys.cs`).
  - The client metadata labels a read-only root (`core.UserStamp`) like an entity, but the key list
    only walked `IEntityMetadataProvider.All`, so the resource audit called the `Core_UserStamp_*`
    keys orphans.
  - It now also walks the All-shape query schema's roots that map no CLR type, with the same chains
    the emit uses. `ConventionalStringKeysTests` gains these cases.
- **`ReportKind_*` and `ShareAccess_*` renamed** to `Core_ReportKind_*` and `Core_ShareAccess_*`.
  The six keys were "pending" in `CoreResourceAuditTests`. The enums emit under the `<Schema>_<Enum>_<Value>`
  chain, so the bare keys were never looked up and the emit wrote fallbacks for the `Core_` ones.
  The pending entries are removed.
- **A guard: `test/core/Tellma.Core.Tests/Client/PlatformLabelsTests.cs`.** It runs every client
  asset contributor over the platform alone and fails, listing the keys, if any section carries a
  `*abelFallback` member (entities, members, actions, fields, enums, securables, job handlers). A new
  core entity, member, enum value or action without its strings now fails Core's unit suite.
- **Fixtures re-recorded** with the repo's command (`TELLMA_UPDATE_GOLDENS=1 dotnet test
  test/core/Tellma.Core.Tests --filter FullyQualifiedName~ClientEntityFixturesTests`, then a clean
  run). `core-entities.json` and `entities-chunk.json` lose every `core.*` fallback. The test model's
  own deliberate fallbacks (acme/gl stand-ins) remain. The two `.d.ts` fixtures are unchanged.
- **The client spec's fallback filter is removed**
  (`client/projects/core/tellma-core/config-check/src/tm-check-app-config.spec.ts`).
  - The `declared()`/`withoutRecordedFallbacks()` machinery that PC-F94 added dropped the recorded
    core fallbacks. The recording has none now, so it was dead code. `check()` takes
    `tmTestMetadata`/`tmTestEntitiesChunk` directly.
  - The test "warns label-missing for a platform label a spec patches in" keeps its assertions.
    Only its "drops only the recording's own" clause is gone from its name.
- Tests updated for the intended resolution change:
  - `ClientEntityModelTests` and `LabelProviderTests`: the `CreatedBy` navigation now resolves to
    the FK's shared `CreatedById`. A tree's `Parent` (`gl.Center` in the client model, `BlobFolder` in
    the fixture model) now covers the bare-navigation-key step.
  - `ExcelExportTests` (integration): the display export's `Id` header now reads "ID".
- READMEs: `src/core/Tellma.Core/README.md` (the resource families, the conventional columns, the
  read-only roots) and `test/core/Tellma.Core.Tests/README.md` (a `Client/` row, which was missing).

### Deviations

1. **Shared keys for the conventional columns** (`Id`, `CreatedById`, `ModifiedById`,
   `SubtreeCount`, `ActiveSubtreeCount`). Spec 0013 §7.6/§10.1 list `Name`, `Code`, `IsActive`,
   `Description`, `CreatedAt`, … and `Parent`, `CreatedBy` for navigations. These five extend that
   open list.
   - Consequence: a navigation's chain puts its FK's chain before the bare `<Navigation>`, so every
     `CreatedBy`/`ModifiedBy` navigation now resolves to `CreatedById`/`ModifiedById`, with the same
     text. The shared `CreatedBy`/`ModifiedBy` keys stay, because the spec names them and the audit
     derives them, but no conventional model reaches them any more.
2. **`ReportKind_*` and `ShareAccess_*` → `Core_ReportKind_*` and `Core_ShareAccess_*`.** Spec 0013
   §10.1's report list spells the bare keys. Its own enum rule (`<Schema>_<Enum>_<Value>`, §7.6)
   gives the `Core_` keys, which are the ones the emit and `ILabelProvider` look up.
3. **`ConventionalStringKeys` covers read-only roots.** Spec 0013 §7.6 does not say how the audit
   treats them. The emit labels them, so the audit must accept their keys.

### Open risks / what to examine hardest

- **The wording, especially the Arabic.** It follows the existing file's vocabulary: المعرّف,
  أنشأه/عدّله, المنشأة for tenant, بيئة الاختبار for sandbox, الأذونات/إذن for permission. A native
  reviewer should still read the 250 Arabic values.
- **`Id` reads "ID" in English.** Display exports and import header candidates show it. The
  for-import technical column is still the literal `Id` (`ExportPlanner.IdColumn`), and header
  matching ignores case, so the two never compete.
- **The `CreatedBy` key shift** (Deviation 1) changes the `labelKey` of every audit navigation in
  every distribution's metadata. Nothing on the client spells those keys (grep), and the label text
  is unchanged.
- **The `PlatformLabelsTests` walk is generic.** It treats any member ending in `abelFallback` as a
  fallback and pairs it with its `…LabelKey` sibling. A future section with a fallback under
  another name would escape it.
