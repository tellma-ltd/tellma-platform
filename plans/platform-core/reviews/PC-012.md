# PC-012: Calendars: the 'uq' month table, startOfQuarter, 'et'

## Implementer notes

### What was built, and where

- **Benchmark first** (`eng/queryex-uq-benchmark/`: `uq-join-shape.sql`, README with the recorded
  result). 10M lines over 1M headers, variable vs bound parameter vs in-place scalar vs
  `OPTION (RECOMPILE)`, covering and non-covering header date index, month and year selectivity,
  median of 7. Result: the hoisted variable is **18–26× a bound parameter at month selectivity**
  (0.34–0.40× at year selectivity). That is far past the 1.5× bar, so flag 4 is escalated (see
  decisions); the engine is built hoisted, as specified, pending the ruling.
- **Schema and binding** (§F.11): `QueryexSchemaBuilder.CalendarMap(calendar, source)` with
  `Build()` validation; `QueryexSchema.CalendarSource`; `CalendarCodes` (`gc`, `et`, `uq`; `uq` is
  tabular). The calendar-code constraint accepts `uq` only where the schema maps it (QX3101
  otherwise, `LedgerFixture.WithoutCalendarMaps` tests it). Nullity: every `uq` answer is Nullable,
  `et` and `gc` keep their operands' nullity.
- **Emission strategy**: `SelectedStrategy` is replaced by `CalendarStrategy` (per-calendar template
  plus a `CalendarOperation` saying what the call computes). `gc` and `et` lower through their
  templates; `uq` goes to `Lowering/Lowerer.Calendars.cs`, which picks the form:
  - **lateral** (operand reads a row, bindings allowed): `CalendarLookup` lateral sources, shared
    per scope list by (base, operand equivalence) for lookups by date and by (from, other, step,
    base, count) for lookups by month; named `[C{n}]` in creation order beside the `[B{n}]`
    bindings; an `Exists` subquery carries its own (`PlanSubquery.Laterals`).
  - **hoisted** (operand reads no row, a root exists): a `ComputedVariable`
    `DECLARE @qx{b}_v{n} <type> = (<scalar>);`, one per distinct call (`TypedEquivalence`); the
    calendar slot is allocated after the operand, so spec example 2's slot numbers hold.
  - **scalar** (operand aggregates, a row-grain operand where no binding may go, or a constant
    statement): `PlanScalarLookup`, nested levels `[M]`, `[M2]`, …, with values named inside it
    `[V1]`, `[V2]`, … (deepest level first, in text order).
  - Second lookups by (Calendar, Year, Month) for startOfYear, week, startOfQuarter, add and diff;
    arithmetic in `Functions/UmAlQuraArithmetic.cs`.
- **startOfQuarter** (§F.17) in all three calendars; gc is
  `DATEADD(QUARTER, DATEDIFF(QUARTER, epoch, d), epoch)`.
- **'et'** (§F.19) in `Functions/EthiopianArithmetic.cs`: day count from the Amete Mihret epoch
  (proleptic Gregorian 0008-08-27, offset 2922), inline year/day-of-year arithmetic and its
  inverse, Pagume in Q4, add with clamping, diff completed as gc's.
- **Emitter** (`Emit/PlanEmitter.cs`, `StatementEmitter.cs`): lateral lookups, scalar levels,
  computed-variable declarations. A lookup by date seeks the last month starting on or before the
  date and checks the end on the one row found (Deviation 1).
- **Test apparatus** (`test/shared/Tellma.Queryex.Testing`):
  - `CalendarMonths`: the fixture's month table, AH 1318–1500 from `UmAlQuraCalendar` (spec 0013
    §8.2's rule), DDL with PK (Calendar, Year, Month) and UNIQUE (Calendar, StartDate); seeded by
    `LedgerDdl`/`LedgerData`; mapped by `LedgerFixture.Schema`.
  - `CalendarReckoning` / public `ReferenceCalendars`: the interpreter's own Ethiopian (day
    arithmetic) and Umm al-Qura (runtime calendar) conversions; `Interpreter.Functions` implements
    every calendar function over them (`Reckoned`, `Moved`, `Completed`, …).
  - `EthiopicVectors.csv` (1,679 rows, embedded) from `eng/queryex-ethiopic-vectors/generate.mjs`
    (Node ICU, `ethiopic`); read by the constant corpus and by `ReferenceCalendarTests`.
  - `CalendarDays`: 1900-01-01..2100-12-31, generated set-based on the server and identically in
    memory; `ReferenceQuery.Run` gained an overload taking a schema and the root's rows.
- **Corpus**: `QueryCorpus.Calendars.cs` (17 query cases: et, startOfQuarter, uq lateral ×6,
  hoisted ×5, scalar ×2), constant cases `constant-calendar-quarters` / `-uq` / `-et` (two years of
  ICU vectors including a 6-day Pagume), expression rows for each calendar and startOfQuarter.
- **Tests**: binder (accepts every calendar; QX3101 without the map; computed calendars without
  it; nullity rows), registry (12 functions × 3 calendars, `CalendarStrategy`),
  `ReferenceCalendarTests` (every ICU vector both ways; every day 1900–2100 round-trips and
  follows its predecessor; every month-table day both ways; nothing outside the table; the table
  tiles), 20 new goldens. Integration: the differential, constant and expression suites now run
  the calendar cases on SQL Server (hoisted calls in WHERE, HAVING, a condition and a key
  executed), and `CalendarSweepTests` compares 14 functions × 3 calendars on all 73,414 days
  (beyond both ends of the month table for `uq`) — PR tier, ~20 s per calendar.

### Deviations

1. **Lookup by date checks the month's end outside the seek.** Spec examples 1 and 2 put
   `<d> < [M].[EndDate]` inside the `TOP (1) … ORDER BY StartDate DESC`. For a date past the
   table's last month that residual makes SQL Server read every month backward: measured 35 s for
   8,400 days after AH 1500 vs 139 ms with the end checked on the one row found, and equal in range
   (2,352 vs 2,359 ms, 5 × 64,834 lookups). A sentinel far-future date (a common ERP "open end")
   would cost a full table scan per row. Emitted as
   `(SELECT TOP (1) … WHERE Calendar AND StartDate <= d ORDER BY StartDate DESC) AS [M] WHERE d < [M].[EndDate]`;
   identical answers given non-overlapping months. Spec example 2's text therefore reads
   `DECLARE @qx0_v0 date = (SELECT [M].[StartDate] FROM (SELECT TOP (1) … ) AS [M] WHERE @qx0_p0 < [M].[EndDate]);`
   with the same slots.
2. **Scalar form names its non-atomic operands** (`(VALUES (MAX(…))) AS [V1] ([v])`, then
   `CROSS APPLY` ones) instead of repeating the operand; `[V{n}]` per scalar lookup, deepest level
   first, so the `[B{n}]` family of the statement stays declared in order.
3. A non-atomic DateTime `uq` operand is bound twice (the value, then `CAST(… AS date)`): sought by
   its date, moved with its time.
4. diffMonths' target is d2's own lookup; diffYears' is d1's month in d2's year; both corrected by
   the gc "completed" rule. The diff patterns are single templates repeating text over atomic
   operands.
5. The by-month lookup has no `TOP` (an equality on the key); lookups are written on one line.
6. Use counts are read from the chosen calendar's template (`SelectedStrategy` → `CalendarStrategy`).
7. Counts are truncated through `CAST(n AS int)`, as gc's `DATEADD` truncates.
8. The calendar code is bound as a varchar literal slot through `StoreTypes.Adopted` (the golden
   shows `QxVarChar(8000)`).
9. `et` templates: outer parentheses; `DATEDIFF` without a `CAST`; truncations in `D − K` form;
   quarter `LEAST(k / 90, 3) + 1`.
10. `TypedEquivalence` and the call's structural hash compare a selector argument by its resolved
    value, ignoring case, so `startOfYear(today(), 'UQ')` and `…'uq'` are one variable (and one
    grouping key) — a fix to the pre-existing comparison, which compared the literal as written.
11. `ConstantGoldenTests` now asserts that the statement has no clause of its own (`FROM`, `WHERE`,
    `APPLY` at line start) rather than that `FROM` appears nowhere: a `uq` scalar lookup has a source.
12. (Review 1, R1-2, ruled in D-050) **§F.3's invariant changes and `CompiledQuery` gains a public
    member.** `CompiledQuery.Recompile` (bool, init) is set when a surviving `ComputedVariable` is
    read from `WHERE` (semi-join predicates included) or `HAVING`; never for hierarchy
    `NodeLookupVariable`s, select/key/ordering/aggregation-condition reads, or constant statements.
    `Sql` is `Prologue + Body + (Recompile ? "OPTION (RECOMPILE)\n" : "") + ";\n"`; `Body` never
    carries the hint. Spec 0012's composers must merge `RECOMPILE` into their one `OPTION` clause
    (WATCHLIST, coordinator).
13. (Review 1, R1-1) **Single-emission form for multi-use template operands where no binding may
    go.** A value call whose pattern writes a non-atomic operand more than once, at group grain, in a
    constant statement or in a hoisted declaration, is emitted as
    `(SELECT <pattern over [N1].[v]…> FROM (VALUES (<operand>)) AS [N1] ([v]) CROSS APPLY (VALUES …) AS [N2] ([v]))`
    (`PlanNamedScalar`), names restarting per call in a family of their own (`N`), so nested calls
    grow linearly. Predicate-shaped templates write each operand once and are unchanged; the
    null-safe comparison forms (`Lowerer.Comparisons`) still repeat a non-atomic operand at group
    grain, a constant factor per comparison that was not in scope here.

### Open risks

- **Flag 4 is open**: the variable is 18–26× a parameter at month selectivity. Remedies measured:
  `OPTION (RECOMPILE)` (1.7–2.0×), or the host evaluating the call and binding a parameter.
  (Resolved in review 1 by deviation 12.)
- `et` truncations of dates in roughly the first eight months of AD 1 overflow `DATEADD` on the
  server (the epoch is 0008-08-27); a huge `n` overflows `CAST(n AS int)` (gc's `DATEADD` errors
  there too).
- The end-outside-the-seek form assumes months do not overlap (true of any well-formed table;
  `TheMonthTable_HasNoGapsOrOverlaps` checks the fixture's).
- `PlanEmitter.Value`'s `default:` branch silently writes nothing (pre-existing). A missing calendar
  slot slipped through it once during this work; `CalendarLookup`'s constructors now reject null.

### What reviewers should examine hardest

- `Lowering/Lowerer.Calendars.cs` `Compose`: every operation's lookups and operand order against
  `UmAlQuraArithmetic`'s templates — especially `Shift` (clamping into a shorter month) and the
  diff corrections; the sweep catches value errors but only for the 14 shapes it runs.
- Lookup sharing and scope: `_dateLookups` keyed by the scope list, `_base`, Exists subqueries,
  dead-lookup removal and alias numbering in `Lowerer.Complete`.
- The scalar form's validity on SQL Server: an outer aggregate inside `VALUES` in a nested
  subquery's `FROM` (runs in `calendar-uq-scalar-*` and `constant-calendar-uq`).
- `EthiopianArithmetic` against the interpreter's independent `EthiopianReckoning` (both are mine;
  ICU vectors anchor the conversions, the sweep the functions).

the benchmark ran first and is recorded; `CalendarMap` with source validation and both `Build()`

**R1-1 (blocking): `'et'` calls at group grain repeat their operand, so nested calls grow the SQL
exponentially.** `src/core/Tellma.Core.Queryex/Lowering/Lowerer.Calls.cs:283-290` (the
`TryShare` fallback) with the `'et'` patterns in
`src/core/Tellma.Core.Queryex/Functions/EthiopianArithmetic.cs:41-190`.
- **Cause.** Where no binding may be given, a multi-use operand is written once per use: in a
  constant statement, in `HAVING`, in a grouped non-key item, in `ORDER BY` of a grouped
  statement, and in a hoisted hierarchy key. The comment there says this is reachable only for
  an aggregation or a column-free value, "and costs nothing to repeat". The `'et'` patterns use
  the date operand roughly 4–40 times each. `addMonths`, `addYears` and the truncations return a
  date, so the calls nest, and the copies multiply about 25× per level.
- **Measured** through the public API:
  - `EvaluateConstant` of `addMonths(…addMonths(cast('2020-01-01','date'),1,'et')…,1,'et')`
    emits 2.7 KB at depth 1, 70 KB at depth 2, 1.76 MB at depth 3 and 43.9 MB at depth 4.
  - A `Having` of `addMonths(…max(PostingDate)…, 1, 'et') > today()` emits 2.8 KB, 68 KB and
    1.69 MB at depths 1–3.
  - Depth 5 would be about 1 GB. An 8 KB user-written report expression can therefore exhaust the
    host's memory at compile time, or send the server a batch it cannot parse.
- **Spec conflict.** §F.19 says a non-atomic date operand "enters once"; §F.9 says such an operand
  uses 0008 §12.3's single-emission form; and 0008 §12.3's rule "has no exceptions".
  `constant-calendar-et.sql` writes `CONVERT(date, @qx0_p0, 23)` 10 times in its first item.
- **Fix.** When the operand of a multi-use pattern is not atomic and no binding is allowed, write
  the pattern over a named value inside a scalar subquery:
  `(SELECT <pattern over [V1].[v]> FROM (VALUES (<operand>)) AS [V1] ([v]))`. This is the shape the
  `'uq'` scalar form already uses, and every position that denies bindings accepts a subquery: the
  constant select list, `HAVING`, grouped items, `ORDER BY` (checked on SQL Server 2022) and a
  `DECLARE` initializer. It also fixes gc's diff patterns in the same positions.
- **Tests.** Add goldens for `'et'` over an aggregate in `HAVING` and over a non-atomic operand in
  a constant statement. Add a property test that emitted length grows at most linearly with
  nesting depth for every calendar function.

**R1-2 (major): where `OPTION (RECOMPILE)` must go, and how it is scoped (the flag-4 ruling for
the fix round).** `src/core/Tellma.Core.Queryex/Emit/StatementEmitter.cs:40-66`,
`src/core/Tellma.Core.Queryex/CompiledQuery.cs:47-81`,
`src/core/Tellma.Core.Queryex/Pipeline/QueryCompiler.cs:61`.
- **Not in `Body`.** §F.3 makes `Body` embeddable, and spec 0012 embeds it in three ways:
  `Count` as `SELECT COUNT(*) FROM (<body>) AS q`, `Assert` as `IF (SELECT COUNT(*) FROM (<body>)
  AS q) <> …`, and key capture as `INSERT INTO @tb{b}_keys ([Id]) <body>`. `OPTION` inside a
  derived table is Msg 156 ("Incorrect syntax near the keyword 'OPTION'"), checked on SQL Server
  2022.
- **Not as text the host must splice either.** Spec 0012 appends its own `OPTION (RECOMPILE)`
  above 1,000 TVP rows and `OPTION (MAXRECURSION 32)` to tree statements. Two `OPTION` clauses on
  one statement are also Msg 156, while `OPTION (RECOMPILE, MAXRECURSION 32)` runs.
- **Suggested shape.** A structured member on `CompiledQuery`, for example `bool Recompile` or a
  list of statement hints, which the host merges into the one `OPTION` clause of its outermost
  statement:
  - after `AS q` for `Count`;
  - after the `INSERT … SELECT` for key capture;
  - for `Assert`, `SELECT @n = COUNT(*) FROM (<body>) AS q OPTION (RECOMPILE)` before the `IF`,
    since `IF` takes no `OPTION`.
- **`Sql`.** `Sql` should then end `… <body>OPTION (RECOMPILE)\n;\n`. That changes §F.3's
  invariant `Sql == Prologue + Body + ";\n"` and its property test, and it adds a public member
  beyond Part F's sketches. Both must be recorded as deviations. Spec 0012's composer needs a
  WATCHLIST note to merge the hint.
- **Scope.** Set the flag only when a `ComputedVariable` survives dead-variable removal
  (`Lowering/Lowerer.cs:419`, after the `RemoveAll`), not when one was created and folded away.
  Never set it for a statement whose only variables are hierarchy `NodeLookupVariable`s. Constant
  statements never hoist, so they never carry it, and a test should pin that. The `DECLARE`s need
  nothing: statement-level `RECOMPILE` sees the local variables' values (parameter-embedding
  optimisation), which is what the benchmark's `recompile` column measured.
- **Optional narrowing.** Consider setting it only when a surviving variable is read from a
  predicate: `WHERE`, `HAVING`, an aggregation's condition, a `CASE` condition in a key, or an
  `Exists` predicate. A variable read only in the select list gains no estimate. The README's own
  non-covering/year row shows recompile at 1,224 ms against the variable's 612 ms, so recompiling
  where no estimate benefits is not free.

**R1-3 (major): `CalendarMap`'s caller errors have no test.**
`src/core/Tellma.Core.Queryex/QueryexSchemaBuilder.cs:96-106` and `:152-172`. Part F Testing
requires "every new code and caller error", and §F.11 names two `Build()` errors. No test calls
any of these:
- `CalendarMap("gc", …)` or `CalendarMap("et", …)` then `Build()`
  (`InvalidOperationException`);
- a second map for `uq`, including the case variant `"UQ"` after `"uq"`, which the canonical-code
  dictionary is meant to catch;
- `CalendarMap` with a malformed or injected source (`ArgumentException`, as for `Entity`);
- `CalendarMap` after `Build()`.

Deleting either `throw` in `LinkCalendarMaps`, or the `ValidateSource` call, leaves the suite
green. Add a test per case.

**R1-4 (minor): `diffYears` answers the uncorrected crossing when the target month is missing,
where the interpreter answers absent.**
`src/core/Tellma.Core.Queryex/Functions/UmAlQuraArithmetic.cs:108-110` and `:138-142`.
- **Cause.** The target is d1's month in d2's year. If the table lacks that row, the moved date is
  NULL. Both `WHEN` arms are then unknown, the `CASE` gives `ELSE 0`, and the result is the raw
  `y2 − y1`. `Interpreter.Functions.cs` `Completed` returns absent there.
- **Reach.** §F.11 obliges a host table only to be contiguous, not to hold whole years. A table
  starting at month 6 of its first year, with d1 in month 3 of the next year and d2 in that first
  year, reproduces it. Spec 0013's full-year table and the fixture never do, which is why the sweep
  is green.
- **Fix.** Start the correction with `CASE WHEN <moved> IS NULL THEN NULL WHEN …`, so a missing
  target makes the sum absent, matching "a result beyond it is absent". Add a unit golden or a
  corpus row over a truncated month table.

**R1-5 (minor): an aggregated `'uq'` call in `ORDER BY` is never exercised.** §F.11 says the
aggregated form may sit in a grouped statement's `ORDER BY` and that no position refuses a
`'uq'` call. The corpus covers `SELECT` and `HAVING` only (`QueryCorpus.Calendars.cs:153-170`).
- **What I checked.** I compiled
  `Aggregate, Select = "Centre.Name, count()", OrderBy = "month(max(PostingDate), 'uq')"`. It
  emits `ORDER BY (SELECT [M].[Month] FROM (VALUES (MAX([T].[PostingDate]))) AS [V1] ([v]) CROSS
  APPLY (…) AS [M] WHERE …) ASC`. A hand-run copy executes on SQL Server 2022, so the shape is
  right, but nothing would catch a regression.
- **Fix.** Add that query to `QueryCorpus.Calendars.cs` so it gets a golden and runs in the
  differential.
