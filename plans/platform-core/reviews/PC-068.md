# PC-068: Pipeline skeleton and the query path (stacks and child surfaces)

## Implementer notes

### What was built

The pipeline skeleton of spec 0015 §3, the query operation of §5.2 with the search of §5.2.1, the arguments of §4.3, the arithmetic mapping of §14.2 and the §16.1 instruments it needs; the traversal rule of spec 0014 as `IQueryTraversalRule`; the child surfaces' `IChildQueryService.QueryAsync`.

- **Pipeline skeleton** (`Tellma.Core/Crud`):
  - `EntityPipelineFactory` (scoped `IEntityPipelineFactory`): `Create<TEntity, TKey>` finds the stack by its leaf (`StackRegistry.FindByLeaf`, a new `ByLeaf` index) and returns a sealed `EntityPipeline<TEntity, TKey>` over the descriptor and the service as its `IEntityBehavior`.
  - `EntityPipeline`: `QueryAsync` runs `QueryOperation` with the service's `SearchFilter`. Every other operation checks the stack serves it (operation flag, and `cacheable`/`tree` capability where §3 requires one) and throws `InvalidOperationException` when it does not, else `NotSupportedException` until its checkpoint builds it.
  - `CrudOperations` (scoped): the operation frame. Names `DataAccessScope.Operation` `<Resource>:<operation>` once per scope; counts `tellma.crud.operations` and times `tellma.crud.operation.duration` (with `crud.lane`) under `CrudOutcomes.Classify`, a token cancelled by the caller or the scope's data cancellation counting `cancelled`. `CrudMetrics` moved from `Crud/Validation` to `Crud` (three validation test files gained a using).
  - `CrudComposition` registers the factory, the frame, the surfaces, the discovery cache, the planner, the traversal rule (also as `IQueryTraversalRule`), the query operation and `IChildQueryService`; `core.entity-pipeline` accepts them (by type, from Tellma.Core).
- **Query path** (`Tellma.Core/Crud/Query`):
  - `QuerySurfaces` / `QuerySurface` (singleton, built once with no tenant scope): per stack and per child surface, the defaults, searchable columns, display name, capabilities, limits, plus the traversal facts (related select, owner navigation, grants by resource) of every entity a path can reach.
  - `QueryShape.Admit` (no I/O): `Take` 50 by default, `MaxTake`, the skip window (an overflowing window reported at `int.MaxValue`), the bidi strip (ZWJ/ZWNJ kept) then `MaxSearchLength`, blank clauses dropped with each filter keeping its request index, `Having` without `Aggregate` and case-colliding argument names as `BadRequestException`, named filters resolved in request order (every unknown name one `Query.UnknownNamedFilter` at `namedFilters[i]`, argument `name`), ancestors kept for a non-aggregate page of a tree only.
  - `QueryDiscoveries` (singleton): discovery of the caller's own clauses (filters, select, ordering, having), cached per schema instance and clause texts, timed by `tellma.crud.query.discover.duration` on a miss only; a discovery with problems is not cached.
  - `QueryArgumentValues`: JSON → declared type by the wire's exact grammars (bool literal; JSON string for text; number or invariant decimal string, no exponent in a string; ISO date / date-time / offset; `D`-format GUID; geography refused), explicit JSON null and a missing value bound to null, unmentioned values ignored, anything else `BadRequestException` naming the parameter.
  - `QuerySearch.Lower`: one `or(...)` over declared parameters (`search`, `searchId`, `left`, `right`): each searchable string column by its `SearchKind`, or the service's `SearchFilter` tree in their place; the id from an integer or `#integer` in Latin digits the key type can hold; the display name's source over every slot the tenant's shape admits (a string source by `contains`, an integer source by equality, Latin or Arabic-Indic digits); the prefix; the `prefix - source` split at the first separator when the prefix side parses. No applicable branch lowers to `false`.
  - `QueryPlanner` (singleton): `And(user leaves, named filter trees, IsActive = true, search, access filter)`, empty conjuncts dropped, no filter when none; default select (twins outside the tenant's shape dropped), `DefaultOrderBy` (stack attribute, else `Id desc`), an aggregate ordered by its select; compiled once under `QueryexProfiles.PipelineLimits` with the bound declarations, omitted parameters and `HasUser`; options `CountCap` (the surface's limit, when `IncludeCount`), `IncludeAncestors`/`CaptureKeys`, `AncestorsFilter` = access filter. `RequireSelectable` refuses geography select items.
  - `QueryDiagnostics.Locate`: maps `Filter.And[k]...` back to `filters[i]` / `namedFilters[i]` by the composition map; the engine's own `Select`/`OrderBy`/`Having` locations are kept; an ordering taken from an aggregate's sent select is relocated to `Select`; a QX5 ceiling in platform text is relocated at span (0,0), from a platform filter conjunct to the last `filters[i]`, else the last `namedFilters[i]`, else `Select`, and from a default select or ordering (an aggregate's default select standing in for its ordering included) to `Select`/`OrderBy`; any other diagnostic in platform text throws `InvalidOperationException` (a defect). Deduplicated by (code, location, span).
  - `QueryTraversalRule` (scoped, public as `IQueryTraversalRule`): walks each `PathUse` of the caller's discovery; an entity other than the root admits a segment only under an `Unrestricted` decision, else when the segment (or its navigation's foreign key) is in its related select. From a child root without a direct grant (its own resource or `*`), the owner reached through the owner navigation counts as root-like. One `TraversalRefusal` per refused path.
  - `QueryOperation` (scoped): `RequireAsync(Read)` → `QueryShape.Admit` → the service's search asked once → one guarded read (`BatchPurpose.Read`) whose compose sets `batch.Limits = PipelineLimits`, decides the root from the connected user's set (memoised per entity per composition), refuses a denied root, plans, applies the traversal rule (first refusal → `ForbiddenException(RestrictedPath, entity, Read, dotted path)`), asks `AssuranceCheck.Ensure` for each sensitive entity a path reads beyond its projection (as `RequireAsync` does for a direct read; not for system scopes), applies the select-type rule, then appends `batch.Rows`. A refusal caused by a `Denied` decision is re-checked once through `AccessEvaluator.EvaluateAsync` (one prologue-only round trip when the set is past `FastDenyWindow`, once per scope); an `Unrestricted` answer recomposes the read once under the refreshed set. `ArithmeticFailureException` → `ValidationException(Root, Query.ArithmeticFailed, reason)`; `DataAccessRetryExhaustedException` → `DependencyUnavailableException("database", RetryAfter 1 s)`, counted `unavailable`.
  - `ChildQueryService` (scoped): `QueryAsync` runs a child surface exactly as a stack (search null, no named filters); an unknown surface is `InvalidOperationException`. `ExcelRowSource` is `NotSupportedException` (export is a later checkpoint).
- **Tests**:
  - Unit, `test/core/Tellma.Core.Tests/Crud/Query/` (103 after review 1): `QueryModel` and `QueryRig` over the scripted batch; `QueryShapeTests`, `QuerySearchTests`, `QueryArgumentValuesTests`, `QueryDiagnosticsTests` (review 1), `QueryOperationTests` (composition order, empty conjuncts, named filters incl. unknown and trusted, default orderings and selects, an aggregate with no select, options, every ceiling, diagnostic locations and spans, a platform-text ceiling and a platform-text defect, argument errors, reserved search names, traversal theory over `core.User`/`*`/filtered grants, child owner path, the step-up of a sensitive path, the stale-denial re-check, root denied with no batch, geography, arithmetic, retries exhausted, telemetry and cancellation, discovery cached, child service, pipeline operations).
  - Integration, `test/core/Tellma.Core.IntegrationTests/Crud/QueryPipelineTests.cs` over a new `QueryPipelineDatabase` (wraps `ConnectDatabase`, seeds widgets, parts and nodes): count + ancestors in exactly 1 round trip warm (`DataAccessScope.RoundTrips`), ancestors under the access filter, `WidgetPart` child surface under a filtered `Widget` grant reading `Widget.Subject` in exactly 1 round trip warm, divide-by-zero → `Query.ArithmeticFailed`, `CreatedBy.Name` projected while `CreatedBy.Email` is refused with `RestrictedPath` / `core.User` / `CreatedBy.Email`; (review 1) on a one-tick `FastDenyWindow` instance, that path refused while the re-check finds nothing, then read after a save grants `core.User` Read. `DataQueryDatabase.Stamped` became internal for the seed.
  - READMEs: Tellma.Core (new "The entity pipeline and the query path" section, folder rows), both test READMEs.

### Deviations (gap fills and obvious corrections)

1. The default select drops multilingual twins the tenant's shape leaves out (the descriptor's default lists every twin; compiling an absent twin would fail).
2. `IncludeAncestors` is ignored on an aggregate page (no row ids to capture).
3. An aggregate without `OrderBy` orders by its select (`DefaultOrderBy`/`Id desc` cannot compile against a grouped select); a diagnostic in that ordering is reported at `Select`.
4. While a search applies, a caller's parameter named `search`, `searchId`, `left` or `right` is a `BadRequestException` (one name cannot carry two values), all four whatever the search text binds, so the outcome never turns on what the user typed.
5. Reads carry no `crud.source` tag (the tag describes a write's source).
6. A QX5 ceiling diagnostic in the platform's own text is relocated at span (0,0) to a clause spec 0016 §3.5's wire list holds: from the platform's filter conjuncts (active-only, search, access filter) to the last `filters[i]` the request sent, else the last `namedFilters[i]`, else `Select`; from a default select or ordering to `Select`/`OrderBy`. The caller's text may push the composed query past a ceiling, and those are the clauses it can shrink.
7. The engine reports select and ordering diagnostics at `Select` / `OrderBy` (no item index) with the item's span; those locations are kept rather than invented per item.
8. The select-type rule reports one diagnostic per geography item, argument `item`; a geography column in a default select is a defect (`InvalidOperationException`).
9. The discovery cache is keyed by the schema instance (one per fingerprint in the tenant database's lifetime) rather than the fingerprint string.
10. A parameter the discovery cannot type stays undeclared, so the compile reports QX3007 at its clause.
11. The query compiles twice: once in the planner (diagnostics before the round trip, columns for the select-type rule) and once in `batch.Rows` (its plan cache keeps the second cheap).
12. A search no branch can apply to (an integer-only display name and a text search, no searchable column) lowers to `false`.
13. Child `ExcelRowSource` and every pipeline operation but the query are `NotSupportedException` until their checkpoints; an operation the stack does not serve, or an unknown child surface, is `InvalidOperationException` as the contracts document.
14. (Review 1) A path that reads a sensitive entity beyond its related projection asks for the step-up a direct `Read` of that entity asks for (`StepUpRequiredException`, or `IndividualRequiredException` for a service account), after the traversal's refusals, as `RequireAsync` checks the denial before the assurance; the projection itself stays readable without it. The public `IQueryTraversalRule` still returns refusals only, so another consumer of it must ask for the step-up itself.
15. (Review 1) Only a refusal caused by a `Denied` decision is re-checked, since `Evaluate` re-checks only stale denials; a `Filtered` decision's refusal is not, as a direct read's filter is not either.

### Open risks

- The order is compile → traversal → select-type (spec 0015 §5.2 steps 3-4). Spec 0016 §5.6 describes the traversal before the compile; the outcomes differ only when a query is both invalid and restricted (the caller sees the diagnostics first). Raised to the orchestrator.
- Paths inside a semi-join (`exists`) are not in the discovery's paths (D-027), so the traversal rule does not see them; the semi-join reads another entity's rows under whatever rule governs it, which this checkpoint does not add.
- The runner's re-applied cultures do not reach the caller (an async callee cannot change its caller's `AsyncLocal` culture), so the edge and every other caller of the pipeline must re-apply `RequestContext.ApplyCultures()` after the call (carry recorded by the coordinator after review 1).
- No pipeline-level log events yet (only instruments).

### Review hardest

- `QueryDiagnostics.Locate` and its composition map: every way a diagnostic can land in platform text, and whether any caller-caused diagnostic can escape as `InvalidOperationException` (a 500).
- `QueryTraversalRule`'s root-like propagation from a child root, and the `Unrestricted`/related-select admission (foreign-key names, case-insensitivity, `*` grants).
- `QuerySearch`: the parameter shapes per root (plan-cache stability), `Fits` per key/prefix/source type, the Arabic-Indic normalisation, the split's prefix parse.
- `QueryArgumentValues` grammars against the wire's contracts (exact decimal, offset required, `D` GUIDs).
- The one-round-trip claim: the integration tests measure `DataAccessScope.RoundTrips` deltas on a second scope after a warm-up scope.

### Findings

**R1-1 (minor) — Whether a caller's `@left`/`@right`/`@searchId` collides depends on the search text.**
- **Where:** `src/core/Tellma.Core/Crud/Query/QueryPlanner.cs:187-202` (`Bind`).
- **Problem:** Only the parameters this particular lowering produced are checked. `searchId` exists only when the text parses as an integer, and `left`/`right` only when the text splits.
- **Scenario:** a client saves a filter `Code = @left` and pages with `search = "cash"`, which works. The same page with `search = "1101 - Cash"` or `search = "12"` returns 400 `bad-request`. The outcome flips on what the user types into the search box.
- **Fix:** while any search applies, refuse every name in `QuerySearch.Parameters` (all four), whatever the lowering produced. Add a case with `@left` and a plain-text search to `A_callers_parameter_named_as_the_searchs_is_refused_while_a_search_applies`.

**R1-2 (minor) — A platform-text ceiling is relocated to a location with no wire clause, and neither branch of `Trusted` is tested.**
- **Where:** `src/core/Tellma.Core/Crud/Query/QueryDiagnostics.cs:96-97, 124-129`.
- **Problem:** Deviation 6 reports a QX5 ceiling met inside the search, active or access-filter conjunct at `Location = "Filter"`, span (0,0). Spec 0016 §3.5's `QueryDiagnostic.Clause` is a closed list: `select | filters[i] | namedFilters[i] | orderBy | having | measures`. `Filter` maps to none of them, so the spec 0016 edge has no clause to emit for a 400 the caller did cause.
- **Scenario:** caller text with 62 joins plus an access filter with 3 gives QX5006 at the access conjunct (D-027 locates it at that leaf). The same happens with ≥1021 caller parameters plus the search's `search`/`searchId` (QX5007 at the search conjunct).
- **Missing tests:**
  - no test drives either case;
  - no test pins the other branch: a non-QX5 diagnostic in platform text is an `InvalidOperationException`.
- **Fix:** relocate a platform-filter ceiling to a clause the wire knows. The last caller conjunct's `filters[i]` is one choice; else `select` when the caller sent nothing, both at span (0,0). Alternatively, record an orchestrator decision amending spec 0016 §3.5's list. Then add the two unit tests: the MaxParameters case through a search, asserting location and span; and a trusted named-filter or default text that does not compile, asserting `InvalidOperationException`.

**R1-3 (minor) — An aggregate with no select treats the default select inconsistently, and that path is untested.**
- **Where:** `src/core/Tellma.Core/Crud/Query/QueryDiagnostics.cs:102-109`, with `QueryPlanner.cs` choosing `OrderingSource.Select` whenever `Aggregate` and no `OrderBy` are sent.
- **Problem:** with `Aggregate = true` and no `Select`, the select and the ordering are both the stack's default text.
  - A diagnostic at `Select` goes through `Trusted`: a defect (500), or a relocated ceiling.
  - The same item's diagnostic at `OrderBy` is relocated to `Select` and returned verbatim as the caller's 400, with a span into text the caller never sent. One faulty default can therefore yield a 500 or a 400, depending on which clause the engine reports first.
- **Not covered:** no test sends `Aggregate = true` without `Select`. Only `Select = "Code, count()"` is covered. So nothing pins that a stack's default select compiles as a grouped select and ordering. That path is caller-reachable and lands in the trusted-text handling.
- **Fix:** in the `OrderingSource.Select` arm, route to `Trusted(diagnostic, "Select", resource)` when `!map.SelectSent`. Add a unit test of `Aggregate = true` with no select on `Accounts` and on `Nodes`, asserting the spec's select and ordering and that it compiles.

**R1-4 (minor) — The `finally { accessor.Current.ApplyCultures(); }` in `QueryOperation` has no effect.**
- **Where:** `src/core/Tellma.Core/Crud/Query/QueryOperation.cs:98-102`.
- **Problem:** `QueryAsync` is an async method. A culture it sets (AsyncLocal-backed) is discarded when the method returns: `AsyncMethodBuilder` restores the caller's `ExecutionContext`. Nothing runs after the `finally` inside `QueryAsync`, so neither `CrudOperations.RunAsync` nor the service's caller sees it. The comment implies the opposite, which will mislead whoever builds the edge.
- **Scenario:** a stale-settings recompose refreshes the context to a new culture. The edge then renders the 403/400 problem in the old culture, with or without this block.
- **Fix:**
  - Remove the block, or reword its comment to say it only covers code later in this method (there is none).
  - Record the carry for the spec 0016 edge checkpoint and the other non-HTTP callers (MCP, job handlers): re-apply `RequestContext.ApplyCultures()` after every pipeline call. The WATCHLIST or a DECISIONS entry via the orchestrator are both fine.

**R1-5 (minor) — `DataAccessRetryExhaustedException` reaches the query's caller untranslated, and the carry is mis-attributed.** The ambiguous-commit row applies to updates only, so it does not concern a read.
- **Where:** `src/core/Tellma.Core/Crud/Query/QueryOperation.cs:87-97` (only `ArithmeticFailureException` is caught). Also Implementer notes, "Open risks", item 3.
- **Problem:** spec 0015 §14.2 says "the pipeline translates them for every stack operation". The retry-exhausted row is `DependencyUnavailableException("database", RetryAfter = 1 s)`. The CHECKPOINTS entry for PC-074 owns the "full §14.2 translation table"; the edge does not.
- **Scenario:** a query whose deadlock retries run out surfaces a raw data-layer exception. That is a 500 with no `Retry-After`, where the spec promises a 503. It is also counted as `crud.outcome = error` instead of `unavailable`.
- **Fix:** add the retry-exhausted mapping to `QueryOperation`'s catch now. It is one clause, and its outcome classification already exists. Otherwise, record the carry so PC-074 applies the table to the query path, not only to save and delete. In both cases, correct the open-risk note.

**R1-6 (minor) — Traversal decisions skip two checks that `RequireAsync`/`Evaluate` apply.**
- **Where:** `src/core/Tellma.Core/Crud/Query/QueryOperation.cs:126-137` (`Decide` via `DecideFrom`), consumed at `QueryTraversalRule.cs:112`.
- **Problem:** a non-root entity's `Read` decision is taken straight from the connected user's set.
  - **(a) Sensitive pairs.** If a distribution marks `(E, Read)` sensitive (spec 0014 §4.3 `MarkSensitive`), a caller below the step-up bar gets `StepUpRequired` on a direct query of `E`. A traversal from another root still reads every column of `E` under an `Unrestricted` decision. This breaks §5.2's "a traversal never reveals more than a direct query of `E` would". MCP, which refuses sensitive pairs, inherits the bypass.
  - **(b) Stale denials.** A `Denied` or `Filtered` decision on `E` from a set older than `FastDenyWindow` is never re-verified, unlike the root's (spec 0014 §5.1 `Evaluate`). `compose` throws before the batch executes, so the prologue never refreshes the set either. A user just granted `Read` on `E` keeps getting `RestrictedPath` until some other batch of theirs runs.

  Core ships no sensitive `Read` pair, so (a) is latent.
- **Fix:**
  - For (a): treat a sensitive pair whose assurance is below the bar as not `Unrestricted` in `Decide`, so only the projection is reachable. `AssuranceCheck` already holds the test. Or flag it to the orchestrator as a spec 0014/0015 gap.
  - For (b): either accept it and record it, or, when the traversal refuses under a set older than `FastDenyWindow`, let the run re-check once through the evaluator before throwing.

**R1-6: fixed in FIXSHA.** Both checks now apply to a traversal as they do to a direct read, with `RequireAsync`'s order: the denial first, then the assurance.
- **(a) Step-up.**
  - `QueryTraversalRule.Check` gained an internal overload. It also collects each entity a path reads beyond its related projection: those admitted by an `Unrestricted` decision, or as a child root's owner.
  - After the refusals, `QueryOperation` calls `AssuranceCheck.Ensure(context, StepUpBar.Requirement, now)` for each such entity whose `(entity, Read)` securable is sensitive, skipped for a system context exactly as `RequireAsync` skips it. A path to a sensitive entity therefore throws the same `StepUpRequiredException` (or `IndividualRequiredException` for a service account) a direct query of it throws.
  - The projection stays readable without a step-up. It is what any reader of the root may see, and a direct read is not what it reveals.
  - I chose this over downgrading the decision to projection-only. A downgrade would answer a weak sign-in with `RestrictedPath`, where a direct read answers `StepUpRequired`. The caller could not tell that a step-up would admit the read.
  - `QueryModel` marks `(qm.QmCounter, Read)` sensitive and gives tickets a `Counter` path.
  - `A_path_reading_a_sensitive_entity_beyond_its_projection_asks_for_the_step_up_a_direct_read_asks_for` covers it:
    - with no assurance, the direct counters query and `Counter.Label` from tickets both throw `StepUpRequiredException` with the default bar's acr;
    - the projected `Counter.Number` and `Counter.Id` pass;
    - with the default bar met, `Counter.Label` passes.
  - `A_path_into_a_sensitive_entity_under_a_filtered_grant_is_restricted_before_any_step_up` pins the order.
  - The public `IQueryTraversalRule` contract is unchanged: it still returns refusals only. A future consumer of it must ask for the step-up itself. This is noted as deviation 14.
- **(b) Stale denials.**
  - When a refusal's entity was `Denied` in the composition, `QueryOperation` re-checks it once through `AccessEvaluator.EvaluateAsync`. That runs the evaluator's own re-check: one prologue-only round trip, only past `FastDenyWindow`, and once per scope.
  - When the answer is `Unrestricted`, the read is recomposed once. The runner reads the refreshed connected user.
