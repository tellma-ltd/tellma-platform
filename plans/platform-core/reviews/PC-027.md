### Deviations (also in the commit message)

See the commit message. The non-obvious ones:

- `SET XACT_ABORT ON` opens every batch, right after `SET NOCOUNT ON`. Spec 0012 §5.5 step 3 places
  it inside the guard and only on a persist. Placing it in the frame keeps `TransactionMode.None`
  and `Explicit` batches, and a failed guard, from leaving an open transaction on a pooled
  connection. The prologue still autocommits because no transaction is open.
- The executor starts its own `Activity` on the `Tellma.Core` source, named
  `<operation> <purpose>`, with `tellma.db.role`, `tellma.data.purpose`, `.operation`, `.attempt`
  and `tellma.tenant.id`. It does not enrich SqlClient's span. The SqlClient span is a child when
  that instrumentation is on.
- The prologue stage runs lazily, at the first statement outside the prologue, or at execution.
  That lets the connect prologue's runner call `MarkConnectPrologue()` right after `CreateBatch`.
  The mark is refused once the stage has run and on a `Maintenance` batch.
- `BatchResult<T>` is a sealed class, not a record, because handles compare by reference (dedup
  returns the same handle).
- (Review 1) `nameof` holes. Spec 0012 §12.3 lists a `nameof` among the holes `TELLMA0003` admits,
  which reads as `nameof` naming a column. At run time a `nameof` is a plain string, which the batch
  cannot tell from a value, so it binds as a parameter (`WHERE {nameof(Widget.Code)} IS NOT NULL`
  is `WHERE @tb0_p0 IS NOT NULL`, always true). A column name is written
  `new SqlIdentifier(nameof(Widget.Code))`; a unit test pins both renderings. `TELLMA0003` is not in
  the tree, so the rule that it refuses a bare `nameof` hole goes to its owning checkpoint.
- (Review 2) The WATCHLIST c02 consolidation is done here, over four fixtures rather than three
  (Identity's is the fourth). Review 1's deferral wrongly said `Tellma.Testing.Support` did not
  exist; it did. The shared `SqlServerFixture` lives in `Tellma.Testing.Support/Sql`, so that project
  now references `Testcontainers.MsSql`, `Microsoft.Data.SqlClient`, `xunit.v3.extensibility.core`
  and the `SSH.NET` pin, and the unit suites that use its doubles carry them too. Queryex keeps its
  collection fixture (`LedgerDatabase`, renamed from its `SqlServerFixture`): it now seeds a uniquely
  named database on the shared fixture instead of reusing a fixed `TellmaQueryexTests`, so a stale
  database in another collation can no longer stop the suite, and the collation precondition is
  gone. Identity keeps a collection definition so that its protocol tests still run without Docker.
  `Tellma.Identity.E2E`'s `IdentityServerFixtureBase` starts its own container as part of a
  browser-driven host and is left alone.
- (Review 2) Statement deduplication is scoped to a write epoch. Spec 0012 §5.4 says `Sql`
  deduplicates "only when it declares no writes", which lets a read repeated after a write in the
  same batch share the pre-write handle. Appending a statement that declares a write clears the
  dedup cache (in `Append`, so internal-channel writes count). A statement that names a mutable batch
  table, meaning one `DeclareIdTable` or the batch declared (not a table-valued parameter), never
  collapses, because the statements that fill such a table cannot declare that write.
- (Review 2) `TransactionMode.Explicit` counts its begin and its commit as round trips, in
  `DataAccessScope.RoundTrips` and in `BatchOutcome.RoundTrips` (three per batch). The spec's
  "decision in C# before commit" has no hook in the contract; nothing is added here.
- (Review 1) A client-side failure after the send (a reader's defect, a result-set count
  mismatch, cancellation) now cancels the command before the reader is disposed, so a batch the
  server is still running rolls back under `XACT_ABORT`. The server holds output until a packet
  fills or the batch ends, so a small batch can already have committed when the client sees the
  failing set: such a failure stays ambiguous for a writing batch, and the next checkpoint's error
  taxonomy should classify it as ambiguous rather than as not committed.

### Open risks

- `ChangeTrackingAudit` is exact only while one batch at a time writes the database, because
  change-tracking versions are database-wide. It checks undeclared writes only, not
  declared-but-unwritten tables. It does not run on a failed batch.
- `FixtureTenant` creates and migrates a database per call. `DataBatchTests` now makes one call per
  class, but a suite that creates many still competes with its neighbours. The fixture raises its
  own command timeouts (5 minutes) and the batches' (`Tellma:Data:CommandTimeout` = 2 minutes).
- `DataExecutor.ExecuteAsync` reports `RoundTrips: 1`, and nothing retries yet.
- On LocalDB, `Tellma.Core.EntityFrameworkCore.IntegrationTests`' `MemoryOptimizedTests` fails
  (`AUTO_CLOSE` is not supported with `MEMORY_OPTIMIZED_DATA`) and
  `Tellma.Core.Queryex.IntegrationTests` stops at its collation precondition on the shared
  `TellmaQueryexTests` database. Both pass on Testcontainers, which the review 1 gate ran.
- The WATCHLIST item on `EvaluateFor`/`ForUser` is not addressed here, because nothing in this
  checkpoint compiles queries.

### What reviewers should examine hardest

1. **Transactions.** `BatchAssembly.Create` and `DataBatch.Assemble`: the in-text transaction
   applies only to `Auto` with a declared write. `DataExecutor.RoundTripAsync`: the
   `Explicit` path (begin, commit with `CancellationToken.None`, rollback when
   `transaction.Connection` is still set, rollback failure logged and swallowed). The guard
   wrapper's `BEGIN TRANSACTION` sits inside `IF @tm_Guard = 1 BEGIN … END;`.
2. **Concurrency.** `TenantDatabaseHandle`: the gate is held from `AcquireAsync` to
   `ReleaseAsync` across the whole round trip. `DisposeAsync` waits for a running round trip.
   A closed connection reopens under the gate. The scoped `TenantDatabase` opens a pooled
   connection per batch.
3. **Schema guard.** `BatchAssembly.SchemaGuardText` binds `@tm_schema` as `char(64)` from
   `IEntityMetadataProvider.StorageFingerprint`. Check the guard on every purpose, before any
   prologue, and on a guarded batch.
4. **Result-set accounting.** `ResultSetCursor` (the first position is checked with `FieldCount`)
   and `BatchAssembly.ReadAsync` (prologue sets read before the verdict, body skipped on a
   failed guard, `EndAsync` surfacing a trailing error). A server error between sets surfaces from
   `NextResultAsync` after the earlier readers ran.
5. **Hole rendering.** `DataBatch.RenderHole` / `RenderIdentifier`, `SqlTemplate`, `ScalarValues`:
   a `@` identifier must be declared in the batch or carry `@tm_`. Object names are
   bracket-quoted per part. Alignment and format specifiers are refused.
6. **Dedup.** `SqlStatementKey`: (format, values, options), with byte arrays by content. Writes
   collapse only when idempotent.
7. **Line map.** `BatchAssembly.TextWriter.Statement` and `StatementOrdinalAt`, against
   SqlClient's 1-based `LineNumber`. The integration test pins ordinals 3 and 4.

### Findings

**R1-1 (major) — A marked batch with no body emits `IF @tm_Guard = 1 BEGIN END;`, which does not
compile.** `src/core/Tellma.Core/Data/Batches/BatchAssembly.cs:154-177`. The wrapper is written
whenever `guarded` is true, even when no non-prologue statement carries text. T-SQL refuses an empty
`BEGIN … END` block (Msg 102, "Incorrect syntax near ';'", reproduced on LocalDB, also with a lone
`;` inside). Scenario: spec 0014's cold prologue-only round trip (§5.6 "one prologue-only round trip
per user per instance", §6.1 "the cold prologue-only round trip") is a marked batch carrying the
connect prologue and nothing else, so it fails to compile on every cold path; so does a marked batch
whose body holds only `Tvp` binding statements (their text is empty). Fix: emit the wrapper (and its
`END;`) only when at least one non-prologue statement carries text or the in-text transaction is
open; `ReadAsync` already asks for the verdict only at the first non-prologue statement. Add a unit
test (assembly text of a marked, body-less batch) and an integration test that executes one.

**R1-2 (major) — `nameof` holes, which spec 0012 §12.3 lets `TELLMA0003` accept as identifier-kind
holes, bind as string parameters, and this is not stated as a deviation.**
`src/core/Tellma.Core/Data/Batches/DataBatch.cs:621-630` (`RenderHole`) with
`ScalarValues.IsScalar` (`ScalarValues.cs:25-29`). §12.3 lists the admissible holes as "a
`SqlIdentifier`, a `nameof`, a `Tvp` result" or a value, which reads as `nameof` naming a column. At
run time a `nameof` is just a `string`, so `$"… WHERE {nameof(Widget.Code)} IS NOT NULL"` renders
`WHERE @tb0_p0 IS NOT NULL` (always true) and `$"SELECT {nameof(Widget.Code)} …"` selects the
constant `'Code'`: silently wrong results, and the future analyzer would bless the pattern. The
implementer flags it under open risks, but PLAN.md §7.1 item 5 requires a spec error to be stated
under Deviations. Fix: state it under Deviations (runtime cannot tell a `nameof` from a value; a
column name is written `new SqlIdentifier(nameof(Widget.Code))`), raise it as a spec misalignment for
the orchestrator (DECISIONS/WATCHLIST, routed to the `TELLMA0003` checkpoint so it refuses a bare
`nameof` hole), and add a unit test pinning that a string hole binds a parameter and a
`SqlIdentifier(nameof(...))` renders `[Code]`.

**R1-3 (major) — The §6.1 execution rules have no test that would fail if they broke.**
`src/core/Tellma.Core/Data/Batches/DataExecutor.cs:101-103` (cancellation), `:186-193` (span),
`:209` (timeout choice), `:249-264` (slow-round-trip log); `src/core/Tellma.Core/Data/DataOptions.cs:44-81`
(validation). Nothing exercises the scope token (`DataCancellation`) or the caller token: if
`afterSend` were the linked token for a `Persist`, a sent persist would be cancelled mid-flight and
every test would still pass; likewise a `Read` that ignores cancellation, a `Maintenance` batch
given the 30 s timeout, a span missing `tellma.data.operation`/`tellma.tenant.id` or named
otherwise than `<operation> <purpose>`, a slow-round-trip event missing its fields, and a
`DataOptions` with a zero timeout or negative `RetryAttempts` passing the gate. Fix: unit tests
through `BatchHarness` for the span (an `ActivityListener` on `Tellma.Core`: name, the five
attributes, no text attribute), the timeout per purpose (inspect the created command or the
assembly hand-off), the slow log (a fake `TimeProvider`) and `DataOptions` validation; one
integration test with `WAITFOR DELAY '00:00:02'` whose token is cancelled after send: a `Read`
surfaces cancellation, a `Persist` completes and its row exists.

**R1-4 (minor) — The `SET XACT_ABORT ON` deviation is not pinned by any test.**
`BatchAssembly.cs:36` and `test/core/Tellma.Core.IntegrationTests/Data/DataBatchTests.cs:161-180`.
The unit test compares against the `SessionSettings` constant, so dropping `SET XACT_ABORT ON` from
it changes nothing; the integration test reads the outcome over a fresh pooled connection, where
`sp_reset_connection` (or RCSI not seeing the uncommitted row) hides an open transaction left by
the `Auto` failure, so it also passes without `XACT_ABORT`. Fix: on a factory handle (one physical
connection), run a `Maintenance` batch that writes and then `THROW`s, then a second batch on the
same handle selecting `@@TRANCOUNT` and `@@OPTIONS & 16384`; assert 0 and 16384. Do the same for
`TransactionMode.None` and `Explicit`.

**R1-5 (minor) — The lazy prologue stage can make `Sql` throw after appending its statement.**
`src/core/Tellma.Core/Data/Batches/DataBatch.cs:269-277` and `:304-307`. `Sql` looks the dedup key
up before `Begin()` runs the prologue stage; a prologue contributor that appends the same text and
values through `Sql` (no writes) adds that key, and the caller's `_shared.Add(key, result)` then
throws `ArgumentException` (duplicate key) after the caller's statement was appended, so the batch
holds a statement whose handle nobody received and the caller sees a failure. Fix: call
`EnsurePrologue()` at the top of `Sql` (before `CheckAuthority` and the key lookup), or re-check
`_shared` after `Begin()` and use `TryAdd`.

**R1-6 (minor) — A contributor that throws leaves the batch re-executable, half composed.**
`DataBatch.cs:379-401` (and `EnsurePrologue`, `:586-600`). If a prologue contributor throws,
`_stage` stays `Prologue`; if an epilogue contributor throws, it stays `Epilogue`. A second
`ExecuteAsync` then skips the prologue stage (the batch runs without the rest of the prologues) or
re-runs every epilogue contributor (duplicating the epilogue statements already appended) and
executes, against §5.2's "A batch executes once; a second call throws". Fix: seal on failure (set
`_stage = Stage.Sealed` in a `catch` around the stage runs in `ExecuteAsync`, and make a failed
`EnsurePrologue` poison the batch), with a unit test using a throwing contributor.

**R1-7 (minor) — A statement whose text ends in a line comment ending in `;` stays unterminated.**
`BatchAssembly.cs:302-305`. `SELECT 1 AS a -- note;` passes the `EndsWith(";")` test, so no
terminator is written; when the next statement is a bare `THROW` (or `WITH`, `MERGE`), the batch
fails to parse (Msg 102 near 'THROW', reproduced). The implementer lists this as an open risk;
the fix is cheap: always write `\n;` after non-empty statement text (an extra empty statement is
legal T-SQL: `SELECT 1; ;; SELECT 3` runs), or skip the shortcut when the last line contains `--`.
Update the golden texts and add the comment case to the line-map test.

**R1-8 (minor) — A client-side failure after send reports failure for a batch that commits.**
`DataExecutor.cs:218-223`. When a statement reader throws mid-stream (an unsupported raw column
type such as `time` or `varbinary`, `RawResultReader.cs:87-97`; a result-set count mismatch; a
guarded batch whose prologue reported no verdict, `BatchAssembly.cs:253-257`), disposing the
`SqlDataReader` drains the rest of the stream, so the server runs the batch to `COMMIT`; the caller
gets `InvalidOperationException`, `OnCommitted` never fires and the snapshots are not replaced,
though the writes are durable. Fix: on a non-`SqlException` failure while reading, call
`command.Cancel()` before the reader is disposed (attention under `XACT_ABORT ON` rolls back a
transaction that has not committed), and have the next checkpoint's taxonomy treat a defect raised
after send as ambiguous for a writing batch. Pin it with a `Persist` that inserts and then returns a
`time` column.

**R1-9 (minor) — `SqlOptions.UserIds` accepts an object name.** `DataBatch.cs:262-265` validates
`UserIds` through `RenderIdentifier`, which bracket-quotes any non-`@` name, so
`new SqlOptions(writes, userIds: new SqlIdentifier("core.Users"))` is accepted and recorded as a
`UserIdSource` (`:299-302`). §5.2 says `UserIds` names a batch-local table or `IdList` TVP; the
epilogue would read every user of a permanent table. Fix: require `userIds.IsVariable` (declared,
or `@tm_callerIds`) and refuse otherwise with `ArgumentException`; unit-test both.

**R1-10 (minor) — WATCHLIST c02's test-helper item is neither done nor recorded.** WATCHLIST.md
cluster c02, "Test helpers": "Consolidate the three duplicate SqlServerFixture classes into
Tellma.Testing.Support when Tellma.Testing.Entities is created." This commit creates
`Tellma.Testing.Entities`; `test/core/Tellma.Core.IntegrationTests/Infrastructure/SqlServerFixture.cs`,
the Queryex suite's and the EF suite's fixtures remain separate, and the commit message does not
defer it. Fix: consolidate, or list it under Deviations with the checkpoint that will.

**R1-11 (minor) — A database per test makes the touched suite slow and its older tests flaky.**
`test/shared/Tellma.Testing.Entities/FixtureTenant.cs:63-107` with
`FixtureDatabase.cs:36-79`, used by every `DataBatchTests` test
(`test/core/Tellma.Core.IntegrationTests/Data/DataBatchTests.cs:307-310`). Each of the 11 tests
creates, alters (RCSI, change tracking), migrates and change-tracks a fresh database. On
Testcontainers the Catalog and Tenancy classes alone take 2 m 08 s (37/37); the full suite took
8 m 38 s on my first run with three pre-existing tests failing on `Execution Timeout Expired` at
their own 30 s default inside `SqlServerFixture.CreateEmptyCatalogAsync`'s `CREATE DATABASE` /
`ALTER DATABASE` (`MembershipDirectoryTests.Reconciling_a_tenant_with_no_users_clears_its_hints_alone`,
`CatalogMigrationTests.The_startup_check_reads_the_catalogs_migration_state`,
`TenantScopeTests.A_suspension_another_instance_wrote_refuses_the_next_scope_after_a_refresh`),
and 4 m 45 s, 48/48, on the second. The fixture raised only its own timeouts, so the tests it
competes with absorb the contention; CI's integration job has a 25-minute budget that more fixture
suites will share. Fix: create the fixture database once per test class (an `IClassFixture` /
collection fixture, as WATCHLIST 0012 suggests) and isolate tests by rows or by a reset statement,
keeping a fresh database only for the tests that need one (the schema-guard tests rewrite
`__TellmaSchema`).

### Responses

All fixes are in the "PC-027: review 1 fixes" commit (child of 7a4fc5e).

- R1-1: fixed in the "PC-027: review 1 fixes" commit (child of 7a4fc5e). `BatchAssembly.Create`
  writes `IF @tm_Guard = 1 BEGIN … END;` only when the batch opens its own transaction or a
  statement outside the prologue carries text. Unit test: a marked batch whose body is one TVP
  binding has no wrapper. Integration test: a marked batch that carries only its prologue, and one
  whose body is a TVP binding, both execute and report the guard.
- R1-2: fixed in the "PC-027: review 1 fixes" commit (child of 7a4fc5e). It is now a Deviation in
  the implementer notes and the commit message: a `nameof` hole binds as a value, and a column name
  is written `new SqlIdentifier(nameof(...))`. A unit test pins both renderings (`@tb0_p0` with
  the value `"Id"`, and `[Id]`). The `TELLMA0003` analyzer is not in the tree; no analyzer
  project exists and nothing in `src/` names `TELLMA0003`. So the refusal of a bare `nameof` hole
  goes to the orchestrator for its owning checkpoint.
- R1-3: fixed in the "PC-027: review 1 fixes" commit (child of 7a4fc5e). Each rule now has a test
  that fails if it breaks:
  - Timeouts. The choice moved into `DataExecutor.CommandTimeoutSeconds(purpose, options)`. A unit
    test checks that Maintenance gets the maintenance timeout, every other purpose the ordinary one,
    and that seconds round up.
  - `DataOptions`. `DataOptionsTests` checks that the defaults and zero retries are valid, that
    each non-positive duration or count and a negative retry count is refused by name, and that a
    zero timeout or a negative retry count bound from configuration fails `IOptions<DataOptions>`.
  - The span, the slow log and cancellation run against the database, because the executor
    acquires its connection before it starts the span. The no-database harness refuses at
    acquisition, so a unit test there could not observe either.
  - Span. An `ActivityListener` filtered by a unique `DataAccessScope.Operation` checks the name
    `<operation> read`, the `Client` kind, and exactly the five attributes, so no text attribute.
  - Slow log. The class host sets the threshold to one tick instead of using a fake `TimeProvider`.
    The test checks every structured field, checks that the text names the parameters, and checks
    that a bound value never appears.
  - Cancellation. A `WAITFOR` read is cancelled within seconds, once by the caller's token and once
    by `DataCancellation.Token`. A persist whose token is cancelled one second into a three-second
    `WAITFOR` completes, and its row exists.
- R1-4: fixed in the "PC-027: review 1 fixes" commit (child of 7a4fc5e), pushed back in part. On a
  factory handle, a Maintenance batch in each of `None`, `Auto` and `Explicit` writes and then
  `THROW`s. The next batch on the same connection reads `@@TRANCOUNT` = 0. I checked that the test
  bites: with `SET XACT_ABORT OFF` in the frame, it fails at `Auto`. The `@@OPTIONS & 16384` half
  is left out because it cannot fail. The probe batch's own frame sets `XACT_ABORT ON` before the
  `SELECT`, so it would read 16384 whatever the failed batch left behind.
- R1-5: fixed in the "PC-027: review 1 fixes" commit (child of 7a4fc5e). `Sql` runs
  `EnsurePrologue()` before the authority check and the key lookup. The cache uses `TryAdd`. Unit

### Findings

**R2-1 (major) — A read that repeats an earlier read after a write in the same batch gets the
earlier, pre-write handle.**
`src/core/Tellma.Core/Data/Batches/DataBatch.cs:278-284` and `:315-318`. The `_shared` cache
(`:55`) is never cleared, and its key (format, values, options) says nothing about position.

Scenario: a `Persist` batch receives `Sql(read)`, then `Sql(write, writes: {T})`, then the same
`Sql(read)` over `T`. The read is appended once, before the write. The third caller gets the first
handle and reads the pre-write state, with no error, inside the transaction that changed it. This
happens when two independent contributors or effects issue the same statement, one validating
before the write and one reporting after it. Collapsing such statements is exactly what dedup is
for.

The same happens around a statement that fills a batch table. That statement cannot declare its
write at all, because `SqlOptions.Writes` holds only permanent `TableName`s
(`DataBatch.cs:646-656`).

The code follows §5.4's wording ("`Sql` deduplicates on (text, parameter values) only when it
declares no writes"). So this is also a spec gap, and the structural key of `Query`/`Rows`/`Count`
will inherit it.

Fix:
- Scope the cache to a write epoch: clear `_shared` whenever a statement that declares writes is
  appended.
- Do the clearing in `Append`, so internal-channel writes count too.
- Clear before the writing statement adds its own key, so two adjacent identical idempotent writes
  still collapse. Read-only batches lose nothing.
- State it under Deviations.
- Raise §5.4's wording, and the batch-table case (which needs a way to declare a batch-table write),
  for the orchestrator.
- Unit test: read, write, same read gives two statements and two handles; read, read gives one.

**R2-2 (minor) — Dedup and the parameter merge treat values that bind differently as the same
value.**
`src/core/Tellma.Core/Data/Batches/ScalarValues.cs:80-85` (`AreEqual`, plain `Equals`) and
`:90-100` (`HashOf`). These are used by `SqlStatementKey.cs:85-104` and by
`ScalarParameter.BindsSame` (`BatchParameter.cs:70-76`).

`DateTimeOffset.Equals` compares instants and ignores the offset, and `decimal.Equals` ignores
scale. Both values bind with that information: `SqlDbType.DateTimeOffset` (`ScalarValues.cs:62`),
and `SqlDbType.Decimal` with precision and scale inferred from the value (`:55`).

Scenario: one contributor appends `Sql($"SELECT CAST({now} AS date) …")` with
`2026-11-11T01:30+03:00`. Another appends the same text with the same instant in UTC,
`2026-11-10T22:30Z`. The second collapses into the first and reads 2026-11-11 instead of 2026-11-10.

The same flaw hits a reserved `@tm_` parameter bound twice with one instant in two offsets: it
passes `BindsSame` in `BatchAssembly.cs:132`, and the second binding is silently dropped.

Fix:
- Compare `DateTimeOffset` with `EqualsExact`, and hash `UtcTicks` together with `Offset`.
- Compare decimals by `decimal.GetBits`, so scale counts.
- Unit tests for both, in the dedup path and in the parameter-merge path.

**R2-3 (minor) — The `OnCommitted` failure rule has no test.**
`src/core/Tellma.Core/Data/Batches/DataExecutor.cs:143-157`. §5.2 says a throwing callback is
logged as `DataBatch.OnCommittedFailed` (error level, with the operation name) and never thrown,
and that callbacks run in registration order. §14 asks for that event to be asserted by name.

The only tests register a callback that sets a flag (`DataBatchTests.cs:268` and `:385`). Remove the
`try`/`catch` and a throwing callback fails the caller's `ExecuteAsync` after the commit. The caller
then reports durable work as failed, and once PC-028 lands it may retry it. No test would fail.
Nothing pins that later callbacks still run, or the order either.

Fix: an integration test in `DataBatchTests` (the class host already has fake logging):
- Register three callbacks, the second of which throws.
- Assert that `ExecuteAsync` returns, and that the first and third callbacks run, in that order.
- Assert that the collector holds exactly one `DataBatch.OnCommittedFailed` at error level,
  carrying the operation and the tenant.

**R2-4 (minor) — `TransactionMode.Explicit` under-counts its round trips and offers no point
before commit.**
`src/core/Tellma.Core/Data/Batches/DataExecutor.cs:200-204`, `:216`, `:237-240` and `:141`.

- **Round-trip count.** The §5.2 table says `Explicit` costs two more round trips: begin and commit
  are each a round trip. Yet `batch.Access.RoundTrips` goes up by one, and `BatchOutcome.RoundTrips`
  is the constant 1. A scope that uses `Explicit` under-reports `DataAccessScope.RoundTrips`, which
  PC-028's `tellma.data.roundtrips` records, by two per batch.
- **No pre-commit point.** §5.2 justifies `Explicit` as "the escape hatch for a decision that must
  be taken in C# before commit". But `RoundTripAsync` commits straight after the last reader, and
  `IDataBatch` has no hook between reading and commit: `BatchResult<T>` has no continuation, and
  `OnCommitted` runs after the commit. No caller can take that decision, so `Explicit` behaves as
  `Auto` with two extra round trips and no retry.

Fix:
- Count begin and commit: three round trips for an `Explicit` batch, in the scope and in the
  outcome.
- Raise the contract gap for the orchestrator. Either add a before-commit hook (a callback over the
  read results that may veto the commit), or drop `Explicit` until a consumer needs it. The spec
  says the platform's own paths never use it.

**R2-5 (minor) — R1-10's deferral rests on a false premise, and no checkpoint owns it.**

- **The false premise.** Three places say `Tellma.Testing.Support` "does not exist yet" and that
  there are three `SqlServerFixture` classes: commit 3e11619's message, the implementer notes

  consolidation to the creation of `Tellma.Testing.Entities`, which is this checkpoint. The
  deferral names no checkpoint id ("the first checkpoint that puts a second suite on
  Tellma.Testing.Entities, or … a c02 test-helper checkpoint"), so nothing will pick it up.

The lifecycle differences may still justify deferring.

Fix:

  Identity fixture.

  LEDGER (or in DECISIONS).
