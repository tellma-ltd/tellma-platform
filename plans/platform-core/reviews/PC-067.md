# PC-067: Declaration API, metadata contract and the config check

## Implementer notes

### What was built, and where

All paths are under `client/projects/core/`.

- **Declaration API, primary entry point** (`tellma-core/src/`):
  - `declarations/`: `tmFeature` (copies and freezes the definition and every list), `tmOverride`,
    `tmPage`, `TmLazyComponent`, `TmSecurableRef` and `TmDeclarationKey`.
  - Interim declaration functions for the specs that own them: `tmEntity` (0029), `tmCodedReport`
    (0034) and `tmWidget` (0035), plus `TmNavSection`/`TmNavEntry`/`TmNavContext` and
    `TmShellSlot` (0027), `TmSettingsTabDeclaration` (0032) and `TmDistributionInfo`.
  - `tm-declaration-registry.ts`: a module-level WeakMap records which declaration function made
    each value. Declarations stay plain frozen objects of the spec's shape. The merge uses the
    registry to tell what an `overrides` entry is, and a spread copy of a declaration is reported
    as `dangling-override` (`reason: not-a-declaration`).
- **The merge rule:** `declarations/tm-merge.ts`, exported as `ɵtmMergeAppDeclarations`. It merges
  `core` first and then the features. Within a feature it applies `overrides`, then `hide`, then
  the feature's own declarations, so a feature never patches or hides its own keys. It never
  throws: each problem is recorded with structured facts, the declaration or patch at fault is
  skipped, and the merge goes on. It also returns provenance (`origin(key, member?)`), the declared
  sections (hidden ones included) and the patching features of each coded report, which the config
  check needs.
- **App wiring** (`app/`): `TmAppConfig` and its language, calendar and string-table types;
  `TM_APP_DECLARATIONS` and `TmAppDeclarations`; a minimal `provideTellma` that provides only
  `TM_APP_DECLARATIONS`, built on first injection from `TM_CLIENT_METADATA`; and `tmAppConfigOf`,
  which finds the config through a WeakMap keyed by the `EnvironmentProviders` object and searches
  nested provider arrays.
- **Metadata contract** (`metadata/`, `entity/`, `admin/`, `attention/`, `reports/`):
  - `TmClientMetadata`, `TmEntitiesChunk`, `TmContracts` and every section type, with full shapes
    for 0029 §2.2's entity metadata.
  - `tmMetadataLoaders`: lazy `fetch` plus `JSON.parse`, one shared promise per file, a retry after
    a failure, and the Core chunk refused when it is not format 1.
  - `TM_CLIENT_METADATA`: a root token that reads `TmClientMetadataStore`, which the boot sequence
    will fill. The store is not exported publicly.
- **`@tellma/core/config-check`**, a new lazy entry point: `tmCheckAppConfig`, `TmConfigProblem`
  and `TmConfigProblemCode`, with all 27 Appendix A config codes, problem messages built from the
  merge's facts, and an internal, interim entity-declaration check (`TmPathResolver`,
  `tmEntityFindings`). The entry point is registered in `core-entry-points.ts` and in
  ARCHITECTURE.md's entry-point list.
- **`@tellma/core-testing`**: `tmTestMetadata(patch?)` and `tmTestEntitiesChunk(patch?)` describe a
  small Acme distribution whose two chunks agree. `provideTellmaTesting()` now also provides
  `TM_CLIENT_METADATA`.
- **Build wiring:**
  - `@tellma/core` gains the peer `@tellma/core-ui` (type imports of `TmIconSource` and
    `TmCalendar`).
  - Its `tsconfig.lib.json` compiles against the built `dist/core-ui`, like core-testing and
    locale-ar do. A new `tsconfig.json` is the editor/lint/typecheck view; the typecheck script
    and the eslint project list use it, so core's specs are now typechecked as well.
  - core-testing's lib tsconfig maps `@tellma/core-ui` to dist too.
  - `provideTellma` is added to the reviewed unprefixed-export allowlist, because the prefix
    pattern requires a suffix after `provideTellma`.
  - The `tm/lazy-layouts` and `tm/literal-declaration-keys` rules are off for core and
    core-testing specs, which build declarations from stand-ins.

### Rulings worth a reviewer's eye

1. **Config check placement.** The spec puts `tmCheckAppConfig` in the primary. I put it in a lazy
   `./config-check` entry point, resolving WATCHLIST 0024's eager-checker concern. The merge itself
   stays in the primary, because `TM_APP_DECLARATIONS` needs it at runtime. The production
   startup emission (`tm.config.problem`) and `TmConfigError` belong to the boot checkpoint. That
   checkpoint must decide whether production loads the lazy check at all, given that it needs the
   Entities chunk.
2. **`TmAppDeclarations.hiddenEntries`**, a new member. The spec does not say how a hidden
   *derived* entry, or the entries of a hidden section, reach the navigation registry. Explicit
   entries that are hidden are also removed from `entries`.
3. **`tmCheckAppConfig(config, metadata, entities, strings?)`**: the fourth, optional argument
   carries the loaded string packs for `string-key-collision`. The check is synchronous and never
   calls a loader.
4. **Server-owned coded-report members.** The refused set is the full `TmCodedReportMetadata`
   minus `key`: `feature`, `route`, `securable`, `kind`, `titleKey`, `descriptionKey`, `export` and
   `parameters`. The appendix names only title, kind, securable, parameters and route. Each refused
   member is its own `coded-report-redeclared`, and the patch's other members still apply.
5. **Duplicate feature keys**, including an explicit `core`, are reported as `duplicate-key
   feature:<key>`, and the repeat is skipped whole.
6. **Derived entry ids** are taken up front from every coded report key, then from each known,
   routable entity (a segment and `query`) and each page without parameters. A collision is
   `duplicate-key entry:<id>` with `derivedFrom`/`takenBy` facts. A `tmOverride('entry:…')` of a
   derived entry is `dangling-override` (`reason: derived`), because the source is what gets
   patched.
7. **A hidden key stays taken.** Re-declaring it is `duplicate-key`, and overriding or re-hiding
   it is dangling (`reason: hidden`). A `tmOverride` that changes the key member (`id`, `path`,
   `category`) is refused as `dangling-override` (`reason: key-member`).
8. **`reserved-path` for pages**, stricter reading: a first segment that equals any metadata
   entity's segment is reserved unless the page's own feature declares that entity, even when no
   feature declares the entity (its routes exist anyway, §9.2). For patched coded-report keys I
   followed the appendix literally: reserved when *another* feature declares the entity.
9. **`unknown-entity`** comes from the merge, both for declarations and for overrides. An
   entity override of a name the metadata has, but that no earlier feature declared, is
   `dangling-override`.
10. **Problem attribution.**
    - Member-level problems name the feature that last set the member, using the merge's
      provenance.
    - Language, calendar and string problems name the distribution's slug.
    - `widget-missing` and `label-missing` name the namespace of the server key.
    - `label-missing` covers every `*LabelFallback` the emit writes (entities and their members,
      enum values, securables, job handlers), deduplicated by label key.
11. **`TM_CLIENT_METADATA` always throws when injected early**, in production too. Angular's
    R3Injector then leaves the record poisoned (later injects report a cycle). This is acceptable,
    because an early inject is a bug either way.
12. **Interim typings.**
    - `TmCodedReportRun`'s first parameter is `never` until `TmApi` lands.
    - `tmEntity` is non-generic, with an index signature.
    - The entity check reads members defensively (strings / `{path, select}` / `{expression}`
      columns, `orderBy` with `:desc`, tile corners unless `component`, `picker.description` and
      `picker.orderBy`). The 0029 checkpoint should replace it with the public
      `tmCheckEntityDeclaration` in the primary; the name is deliberately left free.
13. **Budgets (D-031).**
    - Primary: 1.26 → 4.26 KB, ceiling 1.5 → 4.5. Making the merge's state private saved
      0.11 KB.
    - `./config-check`: born at 4.20 KB, ceiling 4.5.

### Open risks

- `provideTellma` is minimal by design. PC-103-era checkpoints add the router, localization and
  boot pieces. The WeakMap registration that `tmAppConfigOf` relies on must survive that rewrite
  (keep returning one registered `EnvironmentProviders` object).
- The startup check needs the Entities chunk. When it runs is unresolved (see ruling 1).
- `TmRouteSkeleton` and `TmPageKind` are defined here because `tmPage` needs them. The route-data
  interface itself is left to §4.4's owner.

### What to examine hardest

- `tm-merge.ts`: the order inside a feature (overrides → hide → declarations), the derived-entry
  bookkeeping, and the end pass for hidden sections and the app bar.
- `tm-check-app-config.ts`: the path grammar (which failures are `invalid-path` and which are
  `reserved-path`) and the coded-report source rule.
- The lazy-members test in `config-check/src/tm-check-app-config.spec.ts`.

## Review 1

### Findings

Scope: commit 8a98924 only. Read 0024 §1, §2.1–§2.5, §3.1–§3.6, §9.1–§9.2 and Appendix A; 0027
§3.1–§3.2; 0029 §3; 0034 §2.2; PLAN.md §6–§7; WATCHLIST 0024; DECISIONS D-031/D-032. Gates
re-run on the worktree are listed under "Verification" at the end.

No blocking or major issue found. The merge (overrides → hide → declarations within a feature,
hidden keys staying taken, derived entry ids, member provenance, the end pass for hidden sections
and the app bar) holds against every scenario I traced. Neither the merge nor the check calls a
declaration member: they only read members, spread them and freeze copies.

**R1-1 (minor) — the `reserved-path` entity message is false under the strict reading the check
applies.** `config-check/src/tm-check-app-config.ts:221-224` reports a page whose first segment is
any entity's segment unless the page's own feature declares that entity (deviation 6), including
when *no* feature declares it. `config-check/src/tm-config-problem.ts:140-143` always words it as
"…the entity 'X', which another feature declares." Failure scenario: Acme declares
`tmPage('roles/matrix', …)` while no feature declares `core.Role` (the spec's own test case,
`tm-check-app-config.spec.ts:255`). The developer is told that another feature declares
`core.Role`, looks for it, and finds none. The test pins only `^reserved-path:` for this case, so
the wrong text passes. Fix: add a fact for the declaring feature (`declaredBy`, or empty) and word
the two cases apart, for example "…which feature 'gl' declares" or "…whose routes the platform
serves whether or not a feature declares it". Pin both messages.

**R1-2 (minor) — several rules have no test that would fail if the rule broke.**
- `coded-report-redeclared`: `SERVER_OWNED_REPORT_MEMBERS` (`src/declarations/tm-merge.ts:86-95`)
  has eight members, but the tests set only `titleKey`, `route` and `parameters`
  (`tm-check-app-config.spec.ts:308-317`) and `titleKey` and `kind` (`tm-merge.spec.ts:274-290`).
  If `securable`, which Appendix A names, or `feature`, `descriptionKey` or `export` were dropped
  from the set, every test would still pass, and a patch could re-gate a pack's report on the
  client. Fix: a table-driven test with one patch per server-owned member, asserting one
  `coded-report-redeclared` with that `member` fact and the merged entry unchanged.
- `label-missing`: deviation 10 says the check covers every fallback the emit writes, but the only
  test (`tm-check-app-config.spec.ts:436-453`) sets fallbacks on an entity summary and one
  property. The loops over navigations, children, actions, action fields, enum values, the three
  securable label keys and job handlers (`tm-check-app-config.ts:371-395`) could be deleted
  without a test failing; the fixture sets no fallback on any of them
  (`tellma-core-testing/src/tm-test-metadata.ts:167, 197, 272`). Fix: add one fallback of each
  source and assert one warning per key, with the feature attribution each loop computes.
- `dangling-hide` for an entry key that is *derived* and already hidden (`tm-merge.ts:574-577`) is
  untested. Only the declared-section path of "hidden already" is pinned
  (`tm-merge.spec.ts:341-359`).
- `tm-check-app-config.spec.ts:337` is named "…and never for core", but no `core` key reaches
  `checkServerFacts` in that test, and the fixture's `metadata.features` contains `core` anyway, so
  the exemption at `tm-check-app-config.ts:89` is never exercised. Either assert it, against
  metadata without `core`, or drop the claim from the test name.

**R1-3 (minor) — the lazy-members test leaves out the paths most likely to call a member.** The
"Done when" requires that lazy members are never invoked, and
`tm-check-app-config.spec.ts:108-144` is its only pin. Its config has no `overrides` (the list is
empty, `:134`), so the merge's patch path (`#apply`, `#overrideClient`, `#overrideEntity`,
`#patchReport` from `overrides`) never sees a spy. It has no `providers` (a `useFactory` must
never run in Node) and no `icons`. It sets no entity hatch members (`search`, `defaults`, `clone`,
`validate`, `beforeSave`, `rowLink`, `tile.component`, `columns[].display`, `actions[].dialog` and
`actions[].visible`), even though `tm-entity-checks.ts` walks `columns`, `tile`, `picker` and
`actions`. The first spy, `component` (`:110`), is destructured and asserted but never placed in
the config, so it proves nothing. Fix: route spies through `overrides`
(`tmEntity`/`tmPage`/`tmCodedReport`/`tmWidget` patches and `tmOverride` with a function member),
a `providers` entry with a `useFactory` spy, and the entity hatch members above, then assert that
none was called.

**R1-4 (minor) — the declaration registry depends on there being one module instance.**
`src/declarations/tm-declaration-registry.ts:17` keeps each value's kind in a module-local
`WeakMap`. The merge classifies every `overrides` entry through it (`tm-merge.ts:392`). If the
build's Node step (§3.6: `tsx` loading `src/app.config.ts`) evaluates `@tellma/core` twice, for
example once through a tsconfig `paths` mapping to sources and once from the built package that
`@tellma/core/config-check` imports, then every `tmEntity`, `tmPage`, `tmCodedReport`, `tmWidget`
and `tmOverride` value in `overrides` is reported as `dangling-override` (`not-a-declaration`),
and the build fails with an error that points nowhere useful. Angular's DI identity does not
protect this path, because no injector runs in the check. Fix (cheap): keep the registry on a
global keyed by `Symbol.for('tellma.core.declarationKinds')`, created on first use, so every
instance shares one map. If that is rejected, record the single-instance requirement in WATCHLIST
for the build checkpoint that wires the Node step.

### Judgement of the 11 deviations

1. **`./config-check` lazy entry point.** Accepted. It resolves WATCHLIST 0024's eager-checker
   concern. The built `dist/core/types/tellma-core-config-check.d.ts` imports `TmAppConfig` and
   the other types from `@tellma/core` rather than inlining them, so the branded `TmFeature` stays
   one type. The graph table and ARCHITECTURE.md are updated. The spec's §1 entry-point table
   needs the same row; that is for the orchestrator to note.
2. **`hiddenEntries`.** Accepted. 0027 §3.1 has the navigation read derived entries from
   `TM_APP_DECLARATIONS`, and without this member it could not tell that a derived or
   section-hidden entry is hidden.
3. **Optional `strings` argument.** Accepted. It keeps the check synchronous and loader-free. The
   build checkpoint must pass the packs, or `string-key-collision` silently never fires; that
   belongs in WATCHLIST.
4. **All server-owned report members.** Accepted (0034 §2.2: "a patch never sets … a server-owned
   member"). R1-2 asks for the pins.
5. **Repeated feature key → `duplicate-key feature:<key>`.** Accepted.
6. **Strict `reserved-path` for pages.** Accepted. §2.4 and §9.2 ("Any other page path starting
   with an entity segment is `reserved-path`") support it over the appendix's "another feature".
   The message is wrong for the case it adds (R1-1).
7. **`TM_CLIENT_METADATA` throws early in production too.** Accepted. Production has nothing else
   to return, and I confirmed in Angular 22.0.5's `R3Injector.hydrate` that the record stays
   `CIRCULAR` after a throw. That is a misleading follow-up error, but only after a bug that
   already threw.
8. **Minimal `provideTellma`.** Accepted. The rest of the provider list belongs to later
   checkpoints. The `tmAppConfigOf` WeakMap contract is recorded as an open risk.
9. **Interim `tmEntity`, `tmCodedReport`, `tmWidget` and the entity check.** Accepted. The name
   `tmCheckEntityDeclaration` is left free for 0029.
10. **`label-missing` over every fallback.** Accepted; R1-2 asks for the pins.
11. **Budgets.** Measurement confirmed (4.26 and 4.20 KB). The raise fits D-031's arithmetic: it
    adds 3.00 KB, and 4.26 rounds up to a 4.5 ceiling. The note names the feature, the bytes and
    the savings.
    - **Does the merge need to be in the primary?** Yes. `TM_APP_DECLARATIONS` is read before the
      first render on every route, so moving the merge to a lazy entry would put a dependent
      module fetch on the launch path.
    - **What the bytes are.** Measured with esbuild over the built FESM: the merge with
      `tmFeature` and the registry is about 2.3 KB gzip; everything else in the primary is
      2.17 KB.
    - **What else could move.** Only small pieces: `tmAppConfigOf` (build-only), and the merge's
      check-only bookkeeping (member provenance, problem facts, `reportPatchers`,
      `declaredSections`), which production never reads. Neither justifies a finding at this
      size. If the primary's ceiling tightens later, a merge with an optional recorder that only
      the check supplies would save a few hundred bytes.

Other wiring:
- **`@tellma/core` peer on `@tellma/core-ui`.** No cycle: core-ui has no workspace dependency on
  core. `scripts/build.mjs` derives the order from peerDependencies, and the clean build built
  core-ui before core. The built `tellma-core.mjs` has no runtime import of core-ui; only the
  `.d.ts` imports types from `@tellma/core-ui/l10n` and `/icon`, and core-testing's lib tsconfig
  maps those to `dist`.
- **`provideTellma` on the unprefixed allowlist.** Correct: the spec names it, and the pattern
  needs a suffix.
- **The two lint rules turned off for `*.spec.ts` in core and core-testing.** Acceptable. The
  scope is spec files only, and `tm-test-metadata.ts` and every other source stay covered.
- **Appendix A.** All 27 config codes are in `TmConfigProblemCode` and have at least one test that
  asserts the code, key and feature. The gaps are within rules, not missing codes (R1-2).
