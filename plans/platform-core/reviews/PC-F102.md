# PC-F102: Re-enable Angular's chunk optimizer within the hashed-name rule

## Implementer notes

PC-F102 has no CHECKPOINTS.md entry. It is a fix item, scoped by its LEDGER row, D-320 and the
brief. Spec 0024 §6 stays exactly as written: every hashed output carries a `-` and at least eight
`[A-Z0-9]` before its extension. Nothing under `docs/` changed, and the unhashed-asset pattern is
not widened.

### What was built, and where

All in `client/projects/core/tellma-core-tools`:

- `src/commands/build.ts`: `tellma-client build` now runs `ng build` with `TM_NG_BUILD_ENV`,
  which is `NG_BUILD_OPTIMIZE_CHUNKS=true` and `NG_BUILD_CHUNKS_ROLLDOWN=false`. Right after
  `ng build`, and before any later step reads the output (brand files, tm-boot.js, preloads,
  service-worker groups, source-map move, budgets), it calls `tmSettleChunks`. It logs
  `Named N chunks by their content`, plus `; deleted k that no import reaches (…)` when there are
  orphans.
- `src/output/chunk-names.ts` (new): `tmSettleChunks(browserDir, statsFile)`. It renames every
  chunk to a compliant content hash, rewrites every reference, deletes the orphans, and rewrites
  stats.json to match. Its header comment describes the scheme.
- `src/common/files.ts`: `tmContentHash` takes an optional length (12 by default, as before). A
  chunk's name uses 8.
- Tests: `src/output/chunk-names.spec.ts` (new, 9 tests), `build.spec.ts` (ng gets the two
  variables), `common.spec.ts` (the 8-character hash), and `build.fixture.spec.ts` (a new real-build
  test, described below).
- Docs: the tool README's step 1 and its corePrimaryFirstFrame paragraph, and the
  `@tellma/core-tools` row in ARCHITECTURE.md.

### Option 1 (a setting for the hash alphabet) does not exist

I checked this against `@angular/build` 22.0.5,
`src/builders/application/chunk-optimizer.js` lines 240-265. The optimizer calls Rollup's
`bundle.generate({ compact: true, sourcemap, chunkFileNames: … '-[hash].js' })`, and the Rolldown
path does the same. The generate options and the plugin list are literals. No option is read from
angular.json, and no environment variable reaches them (`environment-options.js` reads only
`NG_BUILD_OPTIMIZE_CHUNKS` and `NG_BUILD_CHUNKS_ROLLDOWN`). Rollup's default `hashCharacters` is
`base64`, so `[hash]` is eight characters of `[A-Za-z0-9_-]`. The lowercase letters, `_` and `-`
fail §6.

Patching @angular/build (a pnpm patch) or wrapping the builder would change what upstream runs,
and break with every Angular update. So option 2 it is: the tool renames after the build.

### D-065 reversed

D-065 turned the optimizer off for two reasons: the names fail §6, and stats.json fell out of step
with the output. Both now hold with the optimizer on:

- every chunk name is a compliant content hash;
- stats.json lists exactly the JS that the output holds.

`NG_BUILD_OPTIMIZE_CHUNKS=false` is gone. The orchestrator should record the reversal in
DECISIONS.md.

### The naming scheme, and its guarantee

- **Graph.** The chunks and their edges come from stats.json, walked from index.html's
  `<script src>` and `<link rel="modulepreload">`, through static and dynamic imports.
  - Each chunk's text is cut into literal pieces and quoted references: `"./name"`, `'./name'`,
    a backtick form, or a bare `"name"` in an attribute.
  - The references a chunk's text makes must equal its stats imports, as sets. Any difference
    fails the build, and nothing is written.
- **Cycles.** Rollup's lazy chunks import main, so the graph has cycles; in Acme it is one large
  SCC. The tool takes the SCCs (Tarjan) in reverse topological order.
  - A chunk outside any cycle is named `<stem>-<tmContentHash(final bytes, 8)>.js`, where the
    final bytes are its text with every reference already renamed.
  - A chunk in a cycle is named by the SHA-256 of a serialization of its SCC, walked breadth-first
    from that chunk:
    - one `F<stem>` line per member;
    - `T<sha256 of a literal piece>`;
    - `R<BFS index>` for a reference inside the SCC;
    - `N<final name>` for a reference outside it, which is already final.
  - Two members of one SCC therefore get different names, even when their own bytes match. This
    is the case of Rollup's facade chunks, which differ only in their targets.
- **Same length.** The new hash has the same length as Rollup's (8), so no byte moves:
  - the source maps stay exact; only each map's `file` field and file name change;
  - the byte counts in stats.json stay exact.
- **Guarantee.** A name is a function of the bytes of everything that chunk can reach, and of
  nothing else.
  - The same input gives the same names, on Windows and Linux: there is no path, time or order
    input, and the pieces are hashed as bytes.
  - A change renames the changed chunk and every chunk that reaches it, and nothing else.
  - The unit tests pin this: determinism, and a change that renames the chunk and its importers
    but not an unrelated leaf.
- **Safety checks before any write.**
  - Every new name is unique.
  - No new name equals an existing file in the output, so a rename never overwrites another
    chunk's old file.
  - After the rewrite, no old name is left anywhere in the output's non-map files. One left in a
    comment, a template or a computed string fails the build.

### Orphans: deleted, with the proof

The optimizer adds back esbuild's original outputs that Rollup did not use. Platform-core has none
(0 deleted in Acme and in the fixture). The PC-126 + PC-154 merge has 6, in Acme and in the fixture.

- An orphan is a JS output in stats.json that the walk from index.html does not reach.
- Before deleting an orphan, the tool scans every non-map file of the output, byte for byte as
  Latin-1, for its name. If any file names it, the build fails ("<file> names <orphan>, which no
  import in stats.json reaches from index.html; the stats are not the output's graph.").
- Otherwise it deletes the orphan, its `.map`, and both stats.json entries.

On the merge the log reads "Named 63 chunks by their content; deleted 6 that no import reaches
(chunk-56MQD6EQ.js, chunk-5HC6ANCT.js, chunk-E7GJKYV6.js, chunk-K2QMK76B.js, chunk-LPUKVYD5.js,
chunk-ORLPGH42.js)". So the scan found no reference to any of the six.

### stats.json is honest

The optimizer already rewrites stats.json for Rollup's chunks. Each input's `bytesInOutput` is
Rollup's proportional estimate: `Math.floor(renderedLength × proportion)`. It also leaves two
kinds of stale entry behind: the added-back orphans, and the `.map` entries of the esbuild chunks
Rollup merged away.

The tool rewrites stats.json:

- It renames the keys and the import paths.
- It drops the orphans and their maps.
- It drops every `.map` entry whose JS is no longer an output.
- It leaves the other outputs as they are. These are the component stylesheets that esbuild lists
  and Angular inlines; they were always listed and never written.

After the rewrite, the JS outputs in stats.json are exactly the JS chunks on disk, and each chunk's
imports are exactly the references in its text. The fixture spec checks both on a real build.

### How the figures are computed now

- **initialJs, initialCss, routes, workerShell, bootScript, codedReports.** Unchanged code. Each
  sums whole files of the static closure over the stats graph, which is now Rollup's chunks.
  There is no per-input share in any of them.
- **lazy:<input> lines.** Still the static closure of each dynamic-import target that the first
  frame does not already load. The label is the target's `entryPoint`. On both trees every label
  is a source path; no target without an `entryPoint` showed up, so no fallback label was needed.
- **corePrimaryFirstFrame.** Still cut through the source maps, which is how it was already
  computed. Rollup composes its maps with esbuild's, so the mapping back to `@tellma/core`'s
  primary-entry sources stays exact.
  - The stats' per-input bytes are now Rollup's proportional estimate, not exact counts.
  - The existing cross-check against the stats estimate (0.5% under, 1% over, plus 16 B) still
    passes on every build here.
  - The README now says that this one figure rests on the maps, and that the stats count beside
    it is an estimate held to that band.
- **lazyChunkBudgetsInKb and staticGraphExcludes.** Unchanged, and independent of this change.
  `scripts/bundle-size.mjs` bundles each entry point with its own esbuild run, never with
  `ng build`'s output. staticGraphExcludes' rationale holds with the optimizer on: Rollup treats
  each esbuild chunk as an indivisible module. It merges whole chunks but never splits one, so an
  input's chunk membership upstream is what size:check models.

### Deviations

1. **Web workers are not supported** under the renamer. A chunk that refers to another file through
   `new URL('./x.js', import.meta.url)` is a reference that stats.json does not list as an import,
   so the build fails loudly instead of shipping a stale name. Neither app has a worker today. When
   one comes, the scheme extends with the worker's edge.
2. **A cyclic SCC renames as a whole.** All of Rollup's lazy chunks import main, so in practice
   any change to the first frame renames every chunk in the SCC. Deploy-to-deploy cache reuse of
   unchanged lazy chunks is lost; with the optimizer off, esbuild kept an unchanged chunk's name.
   This is the price of a name that hashes everything the chunk reaches, which is what keeps a
   name from pointing at stale imports. Rollup's own `[hash]` has the same property.
3. **`NG_BUILD_CHUNKS_ROLLDOWN=false` is pinned**, so a future default flip to Rolldown cannot
   change the bundler underneath the renamer unseen. The renamer is bundler-agnostic, but its
   reference patterns were verified against Rollup's `compact: true` output.
4. **Main keeps its stem.** The optimizer changes main's bytes but keeps esbuild's main name. The
   tool renames it with the rest, so main's name now follows its final bytes too.

### What reviewers should examine hardest

- `referencePattern` and `split` in chunk-names.ts. Every form Rollup or Angular uses to name a
  chunk must be one of the quoted forms, or the edge check fails the build. The opposite risk is a
  quoted string that matches a chunk name but is not a reference; it would be renamed, which keeps
  the output consistent but changes the bytes of a string literal.
- The SCC serialization, as an injective encoding (the `F`/`T`/`R`/`N` line forms and their
  delimiters).
- The order of the checks and writes. Every check must run before the first write, so a failing
  build never leaves a half-renamed dist.
- The stats rewrite's three drop rules, against the budget code that reads stats.json.
