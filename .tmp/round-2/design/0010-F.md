# 0010-F — design note: spec 0010 Part F (amendments to Queryex, spec 0008)

Designer note for Part F of spec 0010 ("Amendments to Implemented Specs"). Every delta was checked
against the implemented engine under `src/core/Tellma.Core.Queryex/` (commit `19db172`) and its
test harness (`test/shared/Tellma.Queryex.Testing`, `test/core/Tellma.Core.Queryex.*Tests`). Where
the frozen text and the code differ, the code is the baseline.

Contract blocks are C# sketches: names and shapes are normative; `using` directives, XML docs,
bodies and cancellation tokens are omitted; each block shows only the members it adds. SQL blocks
show the emitted shape with the layout abbreviated (the emitter writes one clause per line, items
aliased `[c0]`…); the golden snapshots fix the exact bytes. Section numbers like "§10.4" are
0008's unless another spec is named. "A§n" is `00-architecture.md`; "N33 §n" is `design/0033.md`.

## 2. Decisions

Each: the decision — why — alternatives considered.

1. **0012 §11.2 moves here and becomes a pointer** (F.1–F.7) — one home for amendments to frozen
   specs. Alt: keep it in 0012 as a flagged exception.
2. **Every item is additive; `QueryexLanguage.Version` stays 1** (F.0.2) — no valid text changes
   meaning; new forms bind only under a host opt-in. Alt: version 2 with dual compilation.
3. **Host-built structure fails as caller errors, user text as diagnostics** (F.1, F.7, F.8, F.15)
   — `Via`/`Exists` names, restriction paths, key groups and option names are never user input
   (0008 §1.4). Alt: diagnostics, as 0012 §11.2 and N33 F8 wrote.
4. **Paging slots stay `Literal`, renamed and re-stamped per call** (F.4) — hosts already bind
   `Literal` from `Value`; a `Declared` name could collide with `@take`. Alt: `Declared` (0012).
5. **Context slots need no engine change** (F.5) — 0008 already emits them; binding is 0012 §5.1's.
6. **Tree rollups use level navigations** (F.9) — to-one joins keep every grouping set exact. Alt:
   A§6.4's closure join (double counts, challenge 1); a query per level; a measure per node.
7. **Level navigations are counted (`TreeLevels`), not listed in `Navigations`** (F.9) — no foreign
   key; `ForeignKey` stays non-null. Alt: list them with a nullable `ForeignKey`.
8. **Grouping sets over select ordinals with one `GROUPING_ID` indicator; `KeyGroups` optional**
   (F.8) — compact `int` indicator; text slots roll up together. Alt: `ROLLUP`/`CUBE`; a
   `GROUPING()` column per key.
9. **`Having` filters the finest set only** (F.8) — collapsed members never show holes (N33
   decision 9). Alt: SQL's semantics.
10. **Omitted parameters fold syntactically, by polarity; bare omitted list elements drop first**
    (F.10) — one routine for F.10 and F.13; `in (@A, @B)` keeps `@A`. Alt: fold the bound tree;
    whole-atom folding only (N33 F3).
11. **Parameter expressions are substituted at each occurrence** (F.11) — sniffable, one round
    trip. Alt: prologue variables; evaluate first, then run (two round trips).
12. **Constant statements are a second entry point emitting one `FROM`-less `SELECT`** (F.12) —
    complete, so not a fragment API. Alt: `CompileQuery` over a dummy root (one row per root row).
13. **`BindParameters` is syntax-only** (F.13) — only the engine has the lexer and printer. Alt:
    host string replacement (breaks on `@` inside strings).
14. **`'uq'` reads a host month table by grain: lateral seek, prologue variable, or QX3104**
    (F.14) — `GROUP BY` refuses subqueries (error 144). Alt: a per-day table; outer-aggregate
    subqueries.
15. **`Exists` is a host-built semi-join; no collection syntax** (F.15) — sharing needs "some child
    row" without fan-out. Alt: a host-filled key set (cannot sit under `Or`); per-user id lists.

## 3. Design — Part F's frame (future spec §F.0)

Part F opens with the rules every item shares, so each item states only its delta.

### F.0.1 Placement

- **Engine:** `src/core/Tellma.Core.Queryex` only; no new project, no new reference. Public
  additions are listed per item; the 0008 §20 rule "the public surface is exactly §1.4, §2, §3"
  extends to Part F's members.
- **Tests:** the existing three projects (§10); the inspection tool mirrors the new inputs (§9).

**Vocabulary**

- *Skeleton* — the nodes of a predicate reached from its root through `and`, `or` and `not` only,
  counting `FilterTree` connectives and parentheses; an *atom* is a skeleton node that is none of
  the three (a comparison, `in`, `is null`, a `Bool` call, a `Via` or `Exists` node).
- *Grain* — row grain (one row: `WHERE`, keys, aggregate arguments, ungrouped items) versus group
  grain (a grouped select item outside an aggregate, `HAVING`, grouped ordering).
- *Key group* — the grouping keys that roll up together; *grouping set* — the key groups one row
  level groups by; *level indicator* — the appended `GROUPING_ID` column.
- *Level navigation* — `Level{j}` on a tree entity: the row's ancestor at depth `j`.
- *Table calendar* — a calendar code whose arithmetic reads a host month map (`'uq'`).

### F.0.2 Compatibility rules

- **Additive.** With every new member at its default, the engine emits byte-identical SQL, slots
  and columns, except paging names (F.4). Every existing golden stays as is except those with
  paging, which are rewritten once with `TELLMA_UPDATE_GOLDENS=1` (0008 §18.2).
- **Version.** `QueryexLanguage.Version` and `Minimum` stay 1. A form that was a diagnostic and
  becomes valid only under a host opt-in (`level()` is a new function; `Level2` resolves only on a
  schema that declares levels; `'uq'` only under a month map) is additive under §17.
- **Positional records keep their constructors.** New members on `QueryexColumn`, `ParameterUse`,
  `CompiledQuery` are `init` properties, never new positional parameters.
- **New `FilterTree` node types** (`ViaNode`, `ExistsNode`) are sealed nested types like the
  existing four; a host that pattern-matches trees adds two cases.

## 4. Amendments I — moved from 0012 §11.2 (future spec §F.1–§F.7)

These seven were written into 0012 §11.2 and are **not implemented** (no `KeySetRestriction`,
`Prologue`, `Via` or `level` exists in the engine). Each is restated here as the amendment of
record; 0012 §11.2 becomes a pointer (§5, E2). Their consumers are 0012's batch, 0014's evaluator
and 0017's download resolution.

### F.1 Key-set restrictions (0008 §2.1, §13.4)

A host restricts a query to the rows whose key is in a set it supplies as a table, without putting
the values in the text.

```csharp
public sealed record KeySetRestriction(string Path, string TableSource); // a bare path; '@' + identifier with an [Id] column
public sealed record QuerySpec
{
    public IReadOnlyList<KeySetRestriction> Restrictions { get; init; } = []; // conjoined after Filter
}
```

- **Path** is a bare path from the root (`Id`, `ParentId`, `Invoice.Id`), resolved like a select
  path; joins ride the trie. It must end at an Equatable scalar.
- **TableSource** is `@` followed by `[A-Za-z_][A-Za-z0-9_]*`, not beginning with `@qx` (any
  case). The host binds a TVP of the key's list type (`IdList`, `BigIdList`, `GuidList`,
  `StringList`, `DateList`) or names a `@tb{b}_` table variable (0012 §4.4, §5.4). It is the third
  host text to reach SQL after `Source` and `Column` (0008 §3's injection boundary).
- **Emission:** each restriction is a further top-level conjunct of `WHERE`, after the filter:
  `<column> IN (SELECT [Id] FROM <TableSource>)`. With no filter the restrictions form the clause.
- **Nullity:** a top-level conjunct is never negated, so an absent key simply never matches.
- **Scope:** the root statement only; never inside `Exists` (F.15). Row level in an aggregate
  query. A restriction's joins count toward `MaxJoins`.
- **Caller errors:** an unresolvable or non-scalar path; a malformed or `@qx` table source.

**Example —** children of captured keys:

```sql
-- Filter = Leaf("IsActive"), Restrictions = [("ParentId", "@tb2_keys")]
WHERE [T].[IsActive] = 1 AND [T].[ParentId] IN (SELECT [Id] FROM @tb2_keys)
```

- **Tests:** goldens with zero, one and two restrictions, with and without a filter, in an
  aggregate query; caller-error vectors; differential (the interpreter filters by an in-memory set).
- **Code:** `QuerySpec`, the lowerer's `WHERE` assembly, `StatementEmitter.WriteWhere`, `QueryKey`.

### F.2 `level(node)` (0008 §10.10)

A registry entry: the depth of a hierarchy node.

```text
level(node: HierarchyId) -> Numeric        emitted {0}.GetLevel(); Propagate(0); store type smallint
```

- Only a path can supply `HierarchyId` (no literal or parameter form), so the argument is the tree
  node column (`level(Node)`, `level(Center.Node)`); anything else is QX3005.
- The engine reports `GetLevel()` as is. Under 0012 §10.1's id-path scheme a top-level row is depth
  1; the engine assumes no scheme.
- A property named `level` still resolves: function names are not reserved (Appendix C).

**Example —** `level(Node) <= 2` → `WHERE [T].[Node].GetLevel() <= @qx0_p0`.

- **Tests:** corpus (type, nullity, QX3005 on a non-node argument); differential (the interpreter
  counts the node's path segments). **Code:** `FunctionLibrary` entry and template only.

### F.3 Prologue and body (0008 §2.1 `CompiledQuery`, §13.4)

A host embeds a compiled statement in its own SQL (a capped count, key capture, delete-by-query),
so `CompiledQuery` exposes the two parts it already writes.

```csharp
public sealed record CompiledQuery
{
    public string Prologue { get; init; } = ""; // the hoisted DECLAREs, then one empty line; "" when none
    public string Body { get; init; } = "";     // SELECT … through the last clause and its line feed; no ';'
}                                               // Sql == Prologue + Body + ";\n", byte-identical to today
```

- **Embedding rule:** `Body` is a valid derived table or `INSERT … SELECT` source when it has no
  `ORDER BY`, or has paging (SQL Server refuses `ORDER BY` in a derived table without `TOP` or
  `OFFSET`). A host that needs a bare count compiles an unordered twin.
- **Prologue first:** the prologue's `@qx{b}_v{n}` variables precede the body in the same batch;
  a host composing several statements writes each prologue before its body.
- **Example (0012 §5.4 key capture):** `INSERT INTO @tb2_keys ([Id])` + `Body` of the keys-only
  twin, after its `Prologue`.
- **Tests:** for every golden, `Sql == Prologue + Body + ";\n"`; an integration test executes
  `SELECT COUNT(*) FROM (<Body>) AS q` for a paged and an unordered query.
- **Code:** `StatementEmitter.Write` returns the two parts; nothing else changes.

### F.4 Paging slots (0008 §13.1, §13.4, §16)

A page change must reuse the cached template and the server's plan, so `Skip` and `Take` stop being
part of the compilation's identity.

- **Names:** `@qx{b}_skip` and `@qx{b}_take`, listed last in `Parameters` (skip, then take); only
  the present ones exist. `Take` without `Skip` still writes `OFFSET 0 ROWS`.
- **Origin `Literal`, store type `int`, `Value` = the spec's value.** An L3 hit returns the cached
  query with those two slots' `Value` replaced, so every caller sees its own page.
- **L3 key:** whether `Skip` and `Take` are present, not their values (today the values are keyed,
  `QueryKey.Of`).
- **Why not `Declared` (0012 §11.2 item 4):** hosts bind `Literal` slots from `Value` unchanged
  (0012 §11.3), and a declared name could collide with a user parameter `@take`.

**Example —** `ORDER BY [c1] ASC, [c0] ASC OFFSET @qx0_skip ROWS FETCH NEXT @qx0_take ROWS ONLY`.

- **Tests:** pages 1 and 2 of one spec compile once (`ProbeCacheKeys` hit), with identical `Sql`
  and different `Value`s; goldens with paging rewritten. **Code:** `Lowerer.PagingSlot`,
  `Lowerer.Complete` naming, `QueryKey.Of`, `QueryexEngine.CompileQuery` (re-stamp on hit and miss).

### F.5 Context slots (0008 §10.6, §13.1) — no engine change

0008 already compiles `today()`, `now()`, `me()` and the implicit zone of `local()` to one slot per
statement with origins `Today`, `Now`, `UserId` and `TimeZone`. Binding `Today` to the date in the
tenant's zone and `TimeZone` to the tenant's zone is the platform host's rule, which stays in 0012
§5.1 and §11.3. Part F records it so the seven moved items are all accounted for; no code changes.

### F.6 Versioned leaves (0008 §2.3, §16, §17)

Stored criteria were validated under the language version stamped beside them, so each leaf of a
composed tree binds under its own version.

```csharp
public abstract class FilterTree
{
    public static FilterTree Leaf(string text, int languageVersion); // ArgumentOutOfRangeException unless QueryexLanguage.IsSupported
    public sealed class LeafNode : FilterTree { public int? LanguageVersion { get; } } // null: the one-argument form
}
```

- **Binding:** a leaf binds under `LanguageVersion ?? QueryCompilationOptions.LanguageVersion`
  (`?? DiscoveryOptions.LanguageVersion` in discovery).
- **Consumer:** 0014's evaluator, whose leaves carry each grant's `FilterLanguageVersion`.
- **Tests:** construction refuses 0 and `Version + 1`; a tree mixing both forms compiles; L3 keys
  differ when only a leaf's stamp differs. With one version the bound trees are identical, which is
  the point. **Code:** `FilterTree`, `FilterBinder.BindLeaf`, `QueryKey.Render`.

### F.7 `FilterTree.Via` (0008 §2.3)

A child entity's rows are filtered by a criterion written against its owner: the criterion is
rebased onto a to-one navigation, never rewritten as text.

```csharp
public abstract class FilterTree
{
    public static FilterTree Via(string navigation, FilterTree inner); // navigation: dotted to-one path, e.g. "Invoice", "Line.Invoice"
    public sealed class ViaNode : FilterTree { public string Navigation { get; } public FilterTree Inner { get; } }
}
```

- **Meaning:** true for a row whose navigation path reaches a row on which `inner` is true; false
  when the path reaches no row.
- **Binding:** each segment resolves to a navigation (a foreign-key one, or a level navigation,
  F.9) from the current root: the query root, an enclosing `Via` target, or an enclosing `Exists`
  entity (F.15). `inner` binds with the path's target as its root; its paths join through the
  navigation path in the shared trie, so `Via("Invoice", …)` and a select of `Invoice.PostingDate`
  use one join. Context functions and parameters bind as anywhere else.
- **Emission:** `inner`'s predicate. When the path's last join is `LEFT`, the engine prefixes a
  presence guard: `([Pn].[<Key>] IS NOT NULL AND (<inner>))`. Inside the guard `inner`'s own nullity
  (computed against the target) is sound, so the node stays two-valued under `not`.
- **Caller errors:** an empty path; a segment that is not a navigation; a `Via` in a `Having` tree.
- **Diagnostics** inside `inner` carry `…Via[<navigation>]` locations. The node counts one level
  toward `FilterTree.MaxDepth`; nesting is allowed.
- **Discovery:** `DiscoverQuery` binds `inner` against the target and reports its paths prefixed
  with the navigation's segments, so `PathUse.Segments` stay root-relative.

**Example —** from `acme.SalesInvoiceLine`, `Via("Center", Leaf("CenterType = 'Sale'"))`:

```sql
LEFT JOIN [gl].[Centers] AS [P1] ON [P1].[Id] = [T].[CenterId]
WHERE ([P1].[Id] IS NOT NULL AND [P1].[CenterType] = @qx0_p0)
```

- **Tests:** goldens through an `INNER` path (no guard) and a `LEFT` path (guard); `Not(Via(…))` is
  true exactly where the positive form is false, over rows without a center (differential); a
  shared join with a select path; nested `Via`; caller errors; discovery prefixes.
- **Code:** `FilterTree`, `FilterBinder` (a rebased context), the lowerer (paths start at the
  target's trie node; the guard), `QueryKey.Render` (`V(<navigation>,<inner>)`), `Discoverer`.

**Requests to round-2 notes** (this note's replacement of the brief's section 7):

- **0033:** adopt the deviations table of §2 (citations §F.8–§F.15, QX4009, optional `KeyGroups`,

- **0029:** `ComparedWith` is exactly N29 §6's shape (F.16); the client path model treats `Level{j}`

### F.8 Grouping sets and the level indicator (0008 §2.1, §8.3, §11.3, §13.4)

One aggregate statement returns every leaf cell, every subtotal and the grand totals a pivot
needs; an appended indicator tells a subtotal from a "(None)" member, since both carry null keys.

```csharp
public sealed record QuerySpec
{
    public IReadOnlyList<IReadOnlyList<int>>? KeyGroups { get; init; }    // partition of the grouping keys by select ordinal; null: one group per key
    public IReadOnlyList<IReadOnlyList<int>>? GroupingSets { get; init; } // each set lists KeyGroups indexes; [] is the grand total; null: plain GROUP BY
}
public sealed record QueryexColumn
{
    public bool IsGroupingLevel { get; init; } // true only on the appended indicator column
}
```

- **Caller errors:** `GroupingSets` without `Aggregate`; `KeyGroups` without `GroupingSets`;
  `KeyGroups` not a partition of exactly the derived keys' ordinals; an index out of range or
  repeated in one set; two equal sets (SQL Server does not merge duplicates); a group in no set
  (its key would be in no `GROUP BY`); more than 31 groups (the `int` indicator); more than 4,096
  sets (SQL Server); `Having` when no set holds every group.
- **QX5008** when the query derives more than 32 keys, each one `GROUP BY` expression (SQL Server's
  limit under `GROUPING SETS`); reported at the 33rd key's span, location `Select[i]`.
- **Emission:** `GROUP BY GROUPING SETS ((…), …, ())`, sets in caller order, each set's keys in
  select order, written exactly as in the select list (bindings included). The engine appends
  `GROUPING_ID(<first key of group 0>, …, <first key of group g−1>) AS [c{n}]` after the `n`
  select items; one key per group suffices because a group rolls up whole.
- **Indicator:** bit `g−1−i` is 1 when group `i` is rolled up in the row: 0 means every group is
  present; `2^g − 1` is the grand total. Its column: `Ordinal = n`, `Text = ""`, `Numeric`,
  `NotNull`, `Path = null`, `IsGroupingKey = false`, `IsGroupingLevel = true`.
- **Nullity:** a key whose group some set omits is `Nullable`. The query "has grouping keys" for
  §8.3 only when no set is empty, so `sum`, `avg`, `min`, `max` are `Nullable` once `()` is present
  (the grand total of an empty filter has no value; `count` stays `NotNull`).
- **`Having`** applies to the rows in which every group is present:
  `HAVING GROUPING_ID(…) <> 0 OR (<having>)`. Subtotals and totals include every row the `WHERE`
  admitted, so a visible subtotal can exceed the sum of its visible children (N33 §8.5).
- **Ordering and paging:** QX4005 and QX4006 are unchanged. Paging tiebreakers are the keys in
  select order, then the indicator, so the order is total across sets.

**Example —** `Select = "Center.Id, quarter(Invoice.PostingDate), sum(Amount)"`, `GroupingSets =
[[0, 1], [0], []]`, `OrderBy = "Center.Id"`, `Take = 1001`:

```sql
SELECT [P2].[Id] AS [c0], DATEPART(QUARTER, [P1].[PostingDate]) AS [c1], SUM([T].[Amount]) AS [c2],
       GROUPING_ID([P2].[Id], DATEPART(QUARTER, [P1].[PostingDate])) AS [c3]
FROM [acme].[SalesInvoiceLines] AS [T]
INNER JOIN [acme].[SalesInvoices] AS [P1] ON [P1].[Id] = [T].[SalesInvoiceId]
LEFT JOIN [gl].[Centers] AS [P2] ON [P2].[Id] = [T].[CenterId]
GROUP BY GROUPING SETS (([P2].[Id], DATEPART(QUARTER, [P1].[PostingDate])), ([P2].[Id]), ())
ORDER BY [c0] ASC, [c1] ASC, [c3] ASC OFFSET 0 ROWS FETCH NEXT @qx0_take ROWS ONLY;
```

`[c3]` is 0 on leaf cells, 1 on a center's subtotal and 3 on the grand total; a line with no center
reads `(NULL, 2, …, 0)`, never confused with a subtotal.

- **Tests:** goldens (one group, text-term group of two keys, `()` only with keys absent → caller
  error, `Having`); differential over `LedgerFixture` with null keys in data (the interpreter runs
  each set as its own `GROUP BY` and unions them with `GROUPING_ID`); nullity of `sum` in `()` over
  an empty filter; integration with 32 and 33 keys on SQL Server; every caller error.
- **Code:** `QuerySpec`, `QueryClauses` (the has-keys rule, groups, the indicator item,
  tiebreakers), `StatementEmitter.WriteGrouping`, `QueryexColumn`, `QueryKey`, the budget (QX5008).

### F.9 Tree level navigations — the tree-rollup key (0008 §3, §6.1, §10.10, §12.2)

A tree entity exposes its ancestor at each depth as a to-one navigation, so a tree dimension
groups by `Level1.Id`, `Level2.Id`, … and a grouping set over those levels yields every subtree
total exactly once. This is the "tree-rollup grouping key" of A§6.4, without the closure fan-out
(challenge 1).

```csharp
public sealed class QueryexSchemaBuilder
{
    public sealed class EntityBuilder { public EntityBuilder TreeLevels(int maxDepth); } // 1–32; needs TreeNode
}
public sealed class EntityDescriptor { public int TreeLevels { get; } }                  // 0: none declared
```

- **Meaning:** `Level{j}` of a row is the row's ancestor at depth `j`, where depth is the node's
  `GetLevel()`: the row itself at depth `j`, absent when the row is shallower. Under 0012 §10.1 a
  top-level row has depth 1, so `Level1` is the root of its tree.
- **Resolution:** a path segment resolves to a property, then a foreign-key navigation, then
  `Level{j}` for `1 ≤ j ≤ TreeLevels` (`Level` ignoring case, `j` decimal without leading zeros).
  The target is the entity itself. Level navigations are not listed in `Navigations` (they have no
  foreign key); `PathUse.Segments` and `QueryexColumn.Path` carry `Level2` like any segment.
- **Build rules (caller errors at `Build()`):** the `TreeNode` property is `IsUnique`; `maxDepth`
  within 1–32; no property or navigation of the entity is named `Level<n>` for `n ≤ maxDepth`.
- **Join:** always `LEFT`, `Nullable` always; the condition reads the parent join's node:
  `ON [Pn].[<node>] = CASE WHEN [Pp].[<node>].GetLevel() >= j THEN
  [Pp].[<node>].GetAncestor([Pp].[<node>].GetLevel() - j) END`. The `CASE` is required because
  `GetAncestor` raises on a negative argument; `j` comes from the descriptor, never from text.
  The join seeks the unique node index; nothing fans out.
- **Usable wherever a navigation is:** every clause, a `Via` path (F.7), the key path of
  `descendantOf` (`descendantOf(Center.Level1.Id, 10)`). Pruning and `MaxJoins` as any join.
- **Hosts:** an entity query cannot materialize a level path (no foreign key links the row to it);
  0012 §11.4 and 0015 §5.2 refuse it in `Select` (§5, E7, E12). Filters and ordering may use it.

**Example —** `Select = "Center.Level1.Id, Center.Level2.Id, sum(Amount)"`, `GroupingSets =
[[0, 1], [0], []]`:

```sql
SELECT [P2].[Id] AS [c0], [P3].[Id] AS [c1], SUM([T].[Amount]) AS [c2], GROUPING_ID([P2].[Id], [P3].[Id]) AS [c3]
FROM [acme].[SalesInvoiceLines] AS [T]
LEFT JOIN [gl].[Centers] AS [P1] ON [P1].[Id] = [T].[CenterId]
LEFT JOIN [gl].[Centers] AS [P2] ON [P2].[Node] = CASE WHEN [P1].[Node].GetLevel() >= 1
     THEN [P1].[Node].GetAncestor([P1].[Node].GetLevel() - 1) END
LEFT JOIN [gl].[Centers] AS [P3] ON [P3].[Node] = CASE WHEN [P1].[Node].GetLevel() >= 2
     THEN [P1].[Node].GetAncestor([P1].[Node].GetLevel() - 2) END
GROUP BY GROUPING SETS (([P2].[Id], [P3].[Id]), ([P2].[Id]), ());
```

Head office (10, depth 1) holds 2,000 of its own; Riyadh (11) and Jeddah (12) under it hold 30,000
and 20,000. Rows: `(10, NULL, 0)` 2,000 (the phantom child), `(10, 11, 0)` 30,000, `(10, 12, 0)`
20,000, `(10, NULL, 1)` 52,000, `(NULL, NULL, 3)` 52,000. Under a closure join the grand total would
read 102,000.

- **Tests:** goldens from a child root and from the tree entity as root; differential over a
  depth-4 fixture (every `Level{j}` of rows at every depth, including absent); the walk-through
  above as an integration test; `descendantOf` through a level path; build errors.
- **Code:** `QueryexSchemaBuilder`, `EntityDescriptor`, the binder's segment resolution, a
  computed-condition `JoinNode`, `StatementEmitter.WriteFrom`.

### F.10 Omitted parameters (0008 §6.3, §8.4, §9.2)

An optional report parameter left blank imposes no restriction. Without this, Queryex's
two-valued comparison makes `PostingDate >= @From` false for every row when `@From` is absent.

```csharp
public sealed record QueryCompilationOptions
{
    public IReadOnlyCollection<string> OmittedParameters { get; init; } = []; // declared names, matched ignoring case
}
```

- **Each name** is declared (caller error otherwise) and gets no slot; it counts as referenced
  (§6.3).
- **Folding** runs on the syntax tree before binding, in the skeleton of every `Filter` leaf, every
  `Having` leaf and the condition argument of every aggregation (the second argument of `count`,
  `sum`, `avg`, `min`, `max`), wherever the aggregation sits:
  1. In an `in` list and in the key list of `descendantOf`/`ancestorOf`, elements that are bare
     omitted parameters are dropped.
  2. An atom that still mentions an omitted parameter, or whose list is now empty, becomes `true`
     under an even number of negations on its skeleton path (`FilterTree.Not` nodes included) and
     `false` under an odd number. A `Via` or `Exists` node is one atom.
  3. Ordinary constant folding follows (§8.4).
- **Elsewhere** (select items, ordering, `if` conditions, other function arguments) an omitted
  parameter is the typed absent value, exactly as `cast(null, '<type>')` written in its place.
- A folded atom is not bound, so its diagnostics are not reported; save-time validation compiles
  with nothing omitted (N33 §3.4 rule 5).

| Clause (`@C`, `@B` omitted) | Becomes |
|---|---|
| `DueDate < @AsOf and CustomerId = @C` | `DueDate < @AsOf` |
| `not (CustomerId = @C)` | `true` |
| `Region = 'East' or CustomerId = @C` | `true` (an omitted parameter lifts the disjunction) |
| `CustomerId in (@A, @B)` | `CustomerId in (@A)` |
| `sum(Amount, CustomerId = @C)` | `sum(Amount, true)`, the same rows as `sum(Amount)` |
| select `if(Amount > @Limit, 'Big', 'Small')`, `@Limit` omitted | `'Small'` for every row |

**Example —** the first row, `@AsOf` declared `Date`, nullable:
`WHERE @qx0_p0 IS NOT NULL AND [T].[DueDate] < @qx0_p0`.

- **Tests:** a corpus entry per table row; polarity through `FilterTree.Not` and nested text
  `not`; list dropping in `in` and `descendantOf`; folding inside `Having` and inside a select
  measure's condition; caller errors; differential (the interpreter applies the rule from this
  text, its own implementation).
- **Code:** `QueryCompilationOptions`, one syntactic folder shared with F.13, `Symbols` (no slot),
  `BindKey` and `QueryKey`.

### F.11 Parameter expressions (0008 §6.3, §13.1)

A report parameter's default is an expression (`year(today())`). The query binds the parameter to
that expression, so a run with defaults stays one statement and one round trip.

```csharp
public sealed record QueryCompilationOptions
{

```

- **Each name** is declared and not omitted (caller errors otherwise); it gets no `Declared` slot.
- **Each expression** binds in `Value` mode under `QueryCompilationOptions.LanguageVersion`, sees

### F.13 Parameter binding — `BindParameters` (0008 §2.4, §4)

### F.14 `'uq'` through a host month map (0008 §3, §10.4)

The reserved Umm al-Qura code becomes implemented where the schema maps it to a host table, as
0008 §10.4 recorded ("a host-provided Hijri month-map table named through the schema contract").

```csharp
public sealed class QueryexSchemaBuilder
{
    public QueryexSchemaBuilder CalendarMap(string calendar, string source); // "uq", "[core].[CalendarMonths]"
}
```

- **The table** (`source` validated like an entity `Source`) has the columns `[Calendar]`
  (varchar), `[Year]`, `[Month]` (int), `[StartDate]`, `[EndDate]` (date, exclusive). Host
  obligations, like `IsUnique`: months are contiguous and never overlap per calendar; unique indexes
  on (`Calendar`, `StartDate`) and (`Calendar`, `Year`, `Month`). 0013 §8.2 (0033 E14) owns it.
- **Caller errors:** a calendar other than `'uq'` (`'gc'` and `'et'` are algorithmic); a duplicate
  map.
- **Binding:** `'uq'` joins the accepted `cal` values of the eleven calendar functions when the
  schema maps it; otherwise QX3101, as today.
- **Semantics** follow .NET `UmAlQuraCalendar`: `year`, `month`, `day` (of the month); `quarter` =
  `(month + 2) / 3`; `week` = `(dayOfYear − 1) / 7 + 1`; `startOfYear`, `startOfMonth` give the
  Gregorian date of the Hijri boundary; `addYears`, `addMonths` keep the time of day, clamp to the
  target month's last day and truncate `n` as `'gc'` does; `diffYears`, `diffMonths` count
  completed units by §10.4's rule. A date outside the map gives an absent result.
- **Nullity:** every `'uq'` result is `Nullable`: a registry rule "`Nullable` when the calendar
  argument selects a table calendar, else the signature's rule" (principle 6 holds).
- **Emission by the operand's grain:**
  1. **A path-reading operand at row grain** → one lateral lookup per distinct operand (structural
     equality) per statement, the operand atomic (a `Date` column, or a value binding of
     `CAST(d AS date)` for a `DateTime`, so the seek stays sargable); lateral sources emit in
     creation order, which respects their dependencies:
     `OUTER APPLY (SELECT TOP (1) [Year], [Month], [StartDate], [EndDate] FROM <source> WHERE
     [Calendar] = @slot AND [StartDate] <= d AND d < [EndDate] ORDER BY [StartDate] DESC) AS [Cn]`
     (a one-row backward seek). `startOfYear`, `diffYears`, `addYears` and `addMonths` add a second
     lookup by (`Calendar`, `Year`, `Month`) equality. Results read `[Cn].[Month]` and the like: a
     derived-table column, legal in `GROUP BY` and `GROUPING_ID` where a subquery is not.
  2. **A path-free operand** (`startOfMonth(today(), 'uq')`, F.11, F.12) → prologue variables:
     the operand, then each field it needs, as scalar subqueries of the same seek.
  3. **An operand containing an aggregation** (`month(max(PostingDate), 'uq')`) → QX3104. Rewrite
     `max(startOfMonth(PostingDate, 'uq'))`.
- `Exists` subqueries (F.15) carry their own lookups; the calendar code is a literal slot.

**Example —** `Select = "month(Invoice.PostingDate, 'uq'), sum(Amount)"`, aggregate:

```sql
SELECT [C1].[Month] AS [c0], SUM([T].[Amount]) AS [c1]
FROM [acme].[SalesInvoiceLines] AS [T]
INNER JOIN [acme].[SalesInvoices] AS [P1] ON [P1].[Id] = [T].[SalesInvoiceId]
OUTER APPLY (SELECT TOP (1) [M].[Year], [M].[Month], [M].[StartDate], [M].[EndDate] FROM [core].[CalendarMonths] AS [M]
             WHERE [M].[Calendar] = @qx0_p0 AND [M].[StartDate] <= [P1].[PostingDate] AND [P1].[PostingDate] < [M].[EndDate]
             ORDER BY [M].[StartDate] DESC) AS [C1]
GROUP BY [C1].[Month];
```

- **Tests:** differential for each function over every day from 1900-04-30 to 2077-11-16 and
  beyond both ends, against `UmAlQuraCalendar` in the interpreter; goldens for the three grains;
  QX3104; QX3101 on a schema without the map; a key and a `GROUPING_ID` over a `'uq'` key.
- **Code:** `QueryexSchemaBuilder`, `CalendarCodes` (accepted per schema), a registry nullity rule,
  lowering nodes for lookups (lateral and hoisted), `StatementEmitter.WriteFrom`.

### F.15 `FilterTree.Exists` (0008 §2.3)

A semi-join a host composes into a filter: "some row of a child entity points at this row and
satisfies `inner`". It serves 0033's sharing criterion; the language gains no collection syntax.

```csharp
public abstract class FilterTree
{
    public static FilterTree Exists(string entity, string navigation, FilterTree inner); // inner: And([]) for "any row"
    public sealed class ExistsNode : FilterTree { public string Entity { get; } public string Navigation { get; } public FilterTree Inner { get; } }
}
```

- **Binding:** `entity` names a schema entity; `navigation` is one of its foreign-key navigations
  whose target is the current root (the query root, a `Via` target or an enclosing `Exists`
  entity); `inner` binds with `entity` as its root. A level navigation cannot correlate.
- **Caller errors:** an unknown entity; a navigation that is missing, a level navigation, or
  targets another entity; an `Exists` in a `Having` tree.
- **Emission:** `EXISTS (SELECT 1 FROM <entity Source> AS [Xn] <joins> WHERE [Xn].[<FK column>] =
  <current alias>.[<Key>] AND (<inner>))`. Each subquery has its own join trie, bindings and
  calendar lookups; aliases `[X1]`, `[X2]`, … run in pre-order across the statement's subqueries;
  parameter and context slots and prologue variables are the statement's. Restrictions (F.1) never
  apply inside.
- **Nullity:** `NotNull`; `not` gives `NOT EXISTS`, two-valued. Nothing fans out, so aggregation
  stays sound. The subquery source and its joins count toward `MaxJoins`.
- **Nesting:** `Exists` and `Via` nest in either order. Diagnostics inside carry
  `…Exists[<entity>]`. `DiscoverQuery` binds `inner` for diagnostics and parameters but reports no
  `PathUse` from it (its paths are not root-relative).

**Example —** from `core.ReportDefinition`, `Exists("core.ReportDefinitionShare",
"ReportDefinition", Leaf("UserId = me()"))`:

```sql
WHERE EXISTS (SELECT 1 FROM [core].[ReportDefinitionShares] AS [X1]
              WHERE [X1].[ReportDefinitionId] = [T].[Id] AND ([X1].[UserId] = @qx0_p0))
```

N33 §5.3 shows the full criterion, with `Via` and a nested `Exists` inside.

- **Tests:** goldens (plain, nested, inside `Via`, `Via` inside, under `Or` and `Not`); differential
  over the fixture's child table; one plan for two users (identical SQL text); caller errors;
  `MaxJoins` counting.
- **Code:** `FilterTree`, `FilterBinder`, a nested plan in the lowerer, `PlanEmitter`,
  `QueryKey.Render` (`E(<entity>,<navigation>,<inner>)`).

## 11. Review flags

1. **`Literal` paging slots** (F.4). Alt: `Declared` (0012). Flips if a host must rebind pages
   without the engine re-stamping the query.
2. **Caller errors for host-built structure** (decision 3). Alt: diagnostics. Flips if a host
   builds `Via`, `Exists` or restrictions from user text.
3. **Folding before binding** (F.10): a drift error in a folded atom goes unreported at run time.
   Alt: bind, then fold. Flips if optional atoms break silently in stored definitions.
4. **Dropping bare omitted list elements** (F.10). Alt: N33's whole-atom fold. Flips on author
   confusion, or when list parameters ship.
5. **QX3104 for aggregated `'uq'` operands** (F.14). Alt: an outer-aggregate scalar subquery
   (select list and `HAVING` only; repeats the operand). Flips if users need `month(max(d), 'uq')`.
6. **Prologue variables for path-free `'uq'` operands** (F.14), opaque to estimation. Alt: inline
   subqueries (refused as keys). Flips on bad plans for `d >= startOfMonth(today(), 'uq')`.
7. **Per-occurrence parameter expressions** (F.11). Alt: one variable each. Flips if an expensive
   default appears.
8. **Counted level navigations** (F.9). Alt: list them with a nullable `ForeignKey`. Flips if hosts

11. **A month table with a (`Calendar`, `StartDate`) seek** (F.14). Alt: a per-day table with

## 12. Challenges to the architecture

1. **A§6.4's "tree-rollup grouping key over the dimension's node closure (`IsDescendantOf`), the
   only fan-out allowed" is unsound under grouping sets** (agreeing with N33 challenge 1). A closure
   join repeats each fact once per ancestor, so every set that omits the tree key (column
   subtotals, the grand total) counts a fact as many times as its depth, and two tree dimensions
   multiply. `GROUPING()` cannot correct it inside an aggregate. Evidence: F.9's walk-through reads
   102,000 instead of 52,000. Followed in name with level navigations (F.9), which also cover A§4.2's
   "tree rollups" row.
2. **A§6.4's Part F list omits three items 0033 needs:** parameter expressions (one-round-trip
   defaults), `BindParameters` (A§8's drill-through `?filter=` must be self-contained) and `Exists`
   (A§5's sharing criterion is not expressible with many-to-one navigations). Followed by adding
   F.11, F.13, F.15, each additive.
3. **A§6.4 counts "context slots" among seven engine amendments; it is a host binding rule.**
   0008 already emits the slots; 0012 §5.1 and §11.3 bind them. Followed as F.5 with no engine
   change.
4. **A§6.4 and A§10.1 name the constant entry point `EvaluateConstant`, but the engine never
   evaluates** (0008: "it compiles text; it never … executes SQL"). Proposed: `CompileConstants`.
   Followed: the name is kept (review flag 10).
