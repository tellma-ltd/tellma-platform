## 2. Decisions

1. **No browser telemetry SDK; one relay** (§6) — no connection string in the bundle, works
   on-prem, ~75 KB saved. Alt: Application Insights web SDK (session replay, RUM blades).
2. **Client items become OpenTelemetry log records** on the server: events and timings as
   Application Insights custom events (`microsoft.custom_event.name`), errors as Warning traces,
   plus a handful of closed-tag metrics (§6.4) — client strings never become metric tags. Alt:
   metrics per event name (unbounded tag values from a client).
3. **Request-linked items are logged under the request's trace id** (an unexported `Activity`
   parented to it), so a trace id from a dialog finds server and client records in one
   `operation_Id` search (§6.4). Alt: the trace id as a plain dimension.
4. **Request outcomes are aggregated per route per flush window**; only slow (≥ 3 s) or failed
   requests travel one by one (§5.3). Alt: one item per request (volume and cost).
5. **Sampling is per tab, configured on the server** (`Tellma:ClientTelemetry:SampleRate`, default
   1) and touches only page visits, vitals, action usage and distribution events (§3.5). Alt:
   per-item sampling (incoherent sessions).
6. **SPA page measurements are our own per-visit timings** (chrome, data, INP, layout shift) from
   `PerformanceObserver`; the hard load adds TTFB, FCP and LCP (§5.1). Alt: the `web-vitals`
   library (lifetime metrics misattribute in an SPA; Soft Navigations API not shipped).
7. **Every error goes through `TmErrorHandler`**, with Angular's
   `provideBrowserGlobalErrorListeners` feeding it; extension frames are dropped; repeats are
   counted, not resent (§4). Alt: a separate window listener.
8. **The request log records a request at send time**, not at its end, so a hanging request shows
   its trace id while it hangs (§8.1). Alt: one record after the response (N24 §10.3 step 5).
9. **"Copy diagnostics" is plain English text in the primary entry point**, bound to
   `Mod+Alt+Shift+D` by physical key, so it works offline and on Arabic layouts (§8.3). Alt: a
   console log (users can't reach it), a downloaded log file only.
10. **Page data is excluded from the dump unless the user ticks a box** (§10.2) — tenant admins and
    Tellma support read dumps of other users' screens. Alt: always include.
11. **Screenshots use `getDisplayMedia` with `preferCurrentTab`**, one frame to PNG, the support
    dialog hidden during capture; an "Attach image" fallback covers browsers without capture
    (§11). Alt: DOM rasterising (html2canvas) — inexact and a hack.
12. **Support files are child rows** (`core.SupportRequestFiles.FileId`, kind `support-bundle`),
    because 0017 allows one property per kind (§12.3, §12.4). Alt: two kinds, or one zip built in the
    browser.
13. **Support requests are readable by tenant administrators only** (no self-scope) and by Tellma
    support over the admin surface, every read logged (§12.6, §12.7). Alt: self-scoped read.
14. **Support requests expire after 30 days** through `core.file-retention` (§12.8).
15. **Actions dispatch through one path, `TmPageActions.invoke`**, which owns enabled, busy and
    destructive-confirmation checks for every origin (§9.5). Alt: each view confirms itself.
16. **`TmPageActions` resolves to the nearest page scope** (route host or overlay), else the
    current page (§9.4) — an action registered by a dialog belongs to that dialog's context.
17. **Page context reaches a future agent as AG-UI run input** (`context`, `tools`), not as
    `STATE_SNAPSHOT` (§9.7, challenge 1).
18. **UI version = the distribution's informational version** `X.Y.Z+<40-hex sha>`; the menu
    shows `X.Y.Z`, About shows and copies the full value (§7).

## 3. Design (the future spec's sections)

### §1 Placement

- **`@tellma/core` primary** (folders `observe/`, `requests/`, `context/`, `support/`):
  `TmTelemetry`, `TmErrorHandler`, `TmRequestLog`, `TmAppVersion`, `TmPageContexts`,
  `TmPageActions`, `provideTmPageScope`, `tmSerializePageContext`, `TmSupport` (facade),
  `TM_HELP_ARTICLES` (reserved). The vitals collector is a dynamic `import()` inside the primary,
  loaded at idle after first render. Budget: 0026's share of the primary ≤ 6 KB gzip (tests read
  the metafile).
- **`@tellma/core/support`** (lazy, on demand; A§2.2): `TmSupportDialog`, `TmScreenCapture`,
  `TM_DISPLAY_MEDIA`, `tmBuildSupportDump`, `TmDiagnosticsPanel` (`tm-diagnostics`),
  `TmSupportDumpSummary`, the `core.SupportRequest` details layout. Budget 25 KB gzip.
- **Server.** `Tellma.Core.Abstractions.Api`: `ClientTelemetryBatch`, `ClientTelemetryItem`,
  `ClientTelemetryNames`, `ClientTelemetryOptions`, `SupportOptions`.
  `Tellma.Core.AspNetCore`: the relay endpoint, the `tellma-telemetry` policy, the admin
  support routes. `Tellma.Core`: `SupportRequest`, `SupportRequestFile`, `SupportRequestService`
  (`submit`), the kind registration, Core resx keys (`Core_SupportRequest_*`,
  `SupportRequests.*`).
- **`@tellma/core-testing`**: `TmFakeTelemetry` (captures items), `tmFakeDisplayMedia()` (a canvas
  `captureStream`), `TmPageContextHarness` (reads `TmPageContexts`, invokes actions).

**Vocabulary**

- **Item** — one telemetry record: `event`, `timing` or `error`.
- **Batch** — the items one relay call carries.
- **Visit** — one routed page from its navigation start to the next navigation or page hide.
- **Request record** — one `TmRequestLog` entry.
- **Slow request** — a request whose duration reached 3 s, whatever its outcome.
- **Diagnostics text** — the plain-text block "Copy diagnostics" writes (§8.3).
- **Dump** — the `TmSupportDump` JSON file (§10).
- **Page data** — row values and form values a page displays (`visible`, `form` values, error
  messages).
- **Page scope** — the injector region of one page or overlay that owns a context (§9.4).
- **Origin** — who invoked an action: `user`, `shortcut`, `launcher`, `assistant`.

### §2 What a distribution writes

Nothing, for the common case: errors, launch and page timings, request outcomes, the request log,
version identity, the dump, the screenshot, support requests and the page contexts of every
framework page come from the platform. Three hatches:

```ts
// 1. An event of its own (A§3.6): scope = the feature key
inject(TmTelemetry).event('acme.aging.run', { kind: 'summary', rows: 120 });

// 2. A page action on a framework page or a tmPage (toolbar, Actions menu, shortcut, assistant)
inject(TmPageActions).register({
  id: 'acme.bank-reconciliation.auto-match', labelKey: 'Acme_BankRec_AutoMatch', icon: 'wand',
  group: 'primary', shortcut: 'Mod+M',
  invoke: async () => { await this.autoMatch(); return { outcome: 'done' }; },
});                                                   // destroyRef defaults to the caller's

// 3. A tmPage with richer context than the route host's default (title + empty state)
inject(TmPageContexts).register({
  kind: 'custom', routeTemplate: '/:t/bank-reconciliation', title: this.title, status: this.status,
  state: computed(() => ({ accountId: this.accountId(), unmatched: this.unmatched() })),
  errors: signal([]), actions: signal([]),
});                                                   // replaces the route host's default context
```

- **Escape hatches:** `TmPageContexts.register` on an overlay a distribution builds itself (with
  `overlay: true` and `provideTmPageScope()` in its providers); `TmTelemetry.error(err, ctx)` for
  a handled failure worth counting.
- **Lint** (`@tellma/core-tools/eslint`): `tm/telemetry-names` checks literal event names and
  action ids against the grammars of §3.2 and §9.3.

### §3 Telemetry API and pipeline

`TmTelemetry` takes items from any code, adds the envelope, samples, queues and sends them to the
relay in small batches. Nothing awaits it and it never throws.

```ts
type TmTelemetryValue = string | number | boolean;
type TmTelemetryProps = Readonly<Record<string, TmTelemetryValue>>;
declare class TmTelemetry {
  event(name: string, props?: TmTelemetryProps): void;
  timing(name: string, ms: number, props?: TmTelemetryProps): void;    // ms → property `ms`
  error(error: unknown, context?: Readonly<Record<string, string>>): void; // name 'tm.error.captured' (§4)
  flush(): void;                                                       // send now (sign-out, tests)
  readonly recent: Signal<readonly TmTelemetryItem[]>;                 // ring of 100, for the dump
}
interface TmTelemetryItem {
  readonly kind: 'event' | 'timing' | 'error'; readonly name: string; readonly at: number; // epoch ms
  readonly traceId?: string; readonly props: TmTelemetryProps;
}
```

#### §3.1 The envelope

| Member | Where | Source |
|---|---|---|
| `version` | batch | `TmAppVersion.ui` (§7) |
| `tabId` | batch | `TmTabBus.tabId` (0025) |
| `tenantId` | batch (one batch per tenant; a tenant switch flushes) | `TmUrls.tenantId()`; null on tenantless pages |
| `sentAt` | batch | client clock at send, for skew correction (§6.3) |
| `route` | every item (reserved prop) | the routed page's template (`/:t/centers/:id`), never a URL |
| `pageKind` | every item (reserved prop) | `TmRouteData.kind` (0024) |
| `traceId` | request-linked items | the request's trace id (§8) |
| `recentTraceIds` | error items | the last 3 request trace ids, comma-joined |

#### §3.2 Names and properties

- **Name grammar** `<scope>.<area>.<event>[.<more>]`:
  `^[a-z][a-z0-9]*(\.[a-z0-9][a-z0-9-]*){2,5}$`, ≤ 64 characters (A§11). Scope `tm` is the
  platform's; any other scope must be a composed feature key (`acme`, `gl`).
- **Prefix owners.** Each spec lists its own events; 0026 governs the names. The map of
  `tm.<area>` to owners is Appendix A.2; a new area is added there.
- **Properties:** ≤ 16 per item, the reserved ones included; keys `^[a-z][a-zA-Z0-9]{0,31}$`; values numbers, booleans, or
  strings ≤ 64 characters matching `^[A-Za-z0-9_.:/@+-]*$` (codes, kinds, route templates,
  entity names, versions). Error items alone carry `message`, `stack` and `recentTraceIds` (§4.3).
- **Guard.** A bad name or property throws `TmTelemetryError` in development; in production the
  item (bad name) or the property (bad value) is dropped and counted into the next
  `tm.telemetry.dropped`. The guard is a backstop for "no free text": a value with a space, a
  non-Latin letter or more than 64 characters never leaves the tab.
- **Never in telemetry:** URLs, query strings, filter or search text, field values, display
  names, e-mail addresses, problem `message`s, user ids (the server adds the session's `sub`).

#### §3.3 Queue and flush

1. `event`, `timing` and `error` stamp `at`, add the envelope props, push into the ring
   (`recent`, always) and, unless sampled out or disabled, into the send queue.
2. The queue flushes:
   - 30 s after the first queued item (at most two batches a minute per tab);
   - 1 s after an `error` item (debounced, so a burst is one batch);
   - when it holds 50 items;
   - on `visibilitychange: hidden` and `pagehide`;
   - on a tenant switch, and on `flush()`.
3. A flush serialises items into batches of at most 16 KB and 100 items and sends each with
   `TmApi.send('/api/client-telemetry', batch)` (`fetch` with `keepalive`, response unread) and
   `Tellma-Activity: background`, so telemetry from an idle tab never keeps a session alive. On
   `pagehide` it sends one batch at most and drops the rest: the 64 KiB keepalive budget is
   shared with the preference flush (A§5.7).
4. **Queue cap 200.** On overflow the oldest non-error item goes first; the drop count rides the
   next batch as `tm.telemetry.dropped { count, reason: 'overflow' }`.

#### §3.4 When nothing is sent

- **Offline** (`TmApi.online` false): the queue holds (cap 200) and flushes when it turns true.
- **No active session** (`TmSession.state` not `active`): the queue holds. `signing-out` flushes
  first: 0024's sign-out calls `flush()` before `/bff/logout`. The changed-user path drops the
  queue, because its items describe another user's session.
- **Disabled** (`DistributionInfo.telemetry.enabled` false): nothing is queued; the ring still
  fills for the dump.
- **Before `DistributionInfo` is known** (cold launch): items queue under the defaults (enabled,
  rate 1); warm launches read the cached `distribution` document (0025).
- **No retry.** `send` is unread, so a lost batch is lost. Relay calls never enter the request log
  or the request summaries.

#### §3.5 Sampling

- **Per tab, decided once:** `sampled = fnv1a32(tabId) / 2^32 < sampleRate`, where `sampleRate` is
  `DistributionInfo.telemetry.sampleRate` (0–1, default 1).
- **Sampled classes:** `tm.page.*`, `tm.vitals.*`, `tm.action.*` and every non-`tm` event. They
  carry `sampleRate` so queries can weight counts.
- **Always sent:** errors and every other `tm.*` event (launch, API summaries, slow requests,
  session, service worker, realtime, support), so error counts and launch timings stay exact.

#### §3.6 Development

- In development every item is also written to the console (`console.debug('[tm]', name, props)`).
- `TmFakeTelemetry` (`@tellma/core-testing`) records items for assertions and sends nothing.

### §4 Error logging

Every uncaught error, unhandled rejection and reported failure reaches `TmErrorHandler`, which
logs it to the console, records it for the dump and queues one `error` item named `tm.error.captured`.

```ts
declare class TmErrorHandler implements ErrorHandler { handleError(error: unknown): void } // provided by provideTellma
type TmErrorSource = 'angular' | 'window' | 'promise' | 'chunk' | 'api' | 'manual';
interface TmErrorRecord {                          // A§5.9, completed
  readonly source: TmErrorSource; readonly errorClass: string;   // 'TypeError', 'TmApiError'
  readonly kind?: TmApiErrorKind; readonly code?: string; readonly status?: number; readonly traceId?: string;
  readonly routeTemplate: string; readonly stack: string; readonly message?: string;
  readonly fingerprint: string; readonly repeats: number; readonly at: number;
  readonly recentTraceIds: readonly string[];
}
```

The primary keeps the last 50 records in memory for the dump (internal `TmErrors.recent`).

#### §4.1 Sources

| Source | How it arrives | Reported |
|---|---|---|
| `angular` | Angular's `ErrorHandler` (template, effect, lifecycle errors) | always |
| `window`, `promise` | `provideBrowserGlobalErrorListeners()` in `bootstrapTellma` (0024) forwards `error` and `unhandledrejection` | unless filtered below |
| `chunk` | a failed dynamic import (`Failed to fetch dynamically imported module`); 0024 also runs `TmUpdates.check()` | always |
| `api` | `TmErrorPresenter` calls `TmTelemetry.error` when it shows the 5xx dialog, and for a failed `background` read | kinds `server`, `unavailable`, `partial-failure`, `offline` with `outcome-unknown` |
| `manual` | `TmTelemetry.error(err, context)` from any code | always |

- **Filtered out:** a rejection whose reason is a `TmApiError` of kind `cancelled` or
  `unauthenticated` (normal outcomes of abort and expiry); an error whose top frame is not a
  same-origin script (`chrome-extension:`, `moz-extension:`, `safari-web-extension:`, another
  origin), counted as `tm.telemetry.dropped { reason: 'foreign' }`; `ResizeObserver loop`
  notices.
- **Other API errors are outcomes, not client errors:** validation, conflict, forbidden and
  not-found are logged by the server (0016 §10.1) and counted only in request summaries (§5.3).

#### §4.2 Deduplication

- `fingerprint` = the first 8 hex of SHA-1 over `errorClass`, the first same-origin frame
  (`chunk-K3J7Q2M9.js:1:2345`) and `routeTemplate`.
- Per tab, a fingerprint is sent at most 3 times per 10 minutes; later occurrences increment
  `repeats` on the next one sent. At most 30 error items per tab per 10 minutes in total.
- The console and the in-memory ring see every occurrence.

#### §4.3 Redaction of messages and stacks

- **`TmApiError`** never ships its `message` (A§5.9); `errorClass`, `kind`, `code`, `status` and
  `traceId` say everything.
- **Other messages**, in order: URLs → `<url>`; e-mail addresses → `<email>`; quoted text (`'…'`,
  `"…"`, `“…”`, `«…»`) that is not a plain identifier (`^[A-Za-z_$][A-Za-z0-9_$]{0,63}$`) →
  `"…"`; each run of digits → `#`; each run of non-ASCII characters → `…`; then cap at 200.

| Raw message | Shipped |
|---|---|
| `Cannot read properties of undefined (reading 'Name')` | unchanged (`'Name'` is an identifier) |
| `Invalid value "Farah Nasser" at row 42` | `Invalid value "…" at row #` |
| `Failed to load https://acme.app.tellma.com/17/centers?q=jed` | `Failed to load <url>` |

- **Stacks:** at most 30 frames and 4 KB; each frame's URL becomes its file name
  (`https://acme.app.tellma.com/chunk-K3J7Q2M9.js:1:2345` → `chunk-K3J7Q2M9.js:1:2345`).
- **Source maps** are hidden: the build writes them outside the deployable output and CI archives
  them with the build, keyed by UI version (request to 0024); support symbolicates a stack against
  that archive.

### §5 Platform measurements

0026 measures what every page shares: each visit's timings, the hard load's paint metrics, and
request outcomes. Page specs add only domain events. Appendix A.1 lists the items.

#### §5.1 Page visits (`tm.page.visit`, sampled)

A visit starts at the router's `NavigationStart` (for the first route: `performance.timeOrigin`)
and ends at the next `NavigationStart` or `pagehide`. One timing item per visit:

| Prop | Meaning |
|---|---|
| `ms` (= `dataMs`) | navigation start → the page's data on screen, or its error state |
| `chromeMs` | navigation start → the page context registered and painted |
| `inpMs` | the visit's INP: interaction durations (`event` entries grouped by `interactionId`) sorted descending, the entry at index `min(floor(n / 50), n − 1)` |
| `interactions` | `n` |
| `layoutShift` | sum of `layout-shift` values without recent input during the visit (Chromium only) |
| `visitS` | visit length in seconds |
| `entry` | `load` (first route of a document) or `navigation` |
| `outcome` | `ready`, `error`, or `left` (navigated away before data) |

- **"Painted"** = the `afterNextRender` after the event, then one `requestAnimationFrame`.
  `chromeMs` stamps the context's registration (§9.2); `dataMs` stamps the first `status` change
  away from `loading`.
- A metric the browser does not expose is omitted, never zero.

#### §5.2 The hard load (`tm.vitals.load`, sampled)

Once per document, when LCP finalises (first input or `visibilitychange: hidden`): `ttfbMs`
(Navigation Timing `responseStart`), `fcpMs` (`paint`), `lcpMs` (`largest-contentful-paint`),
`navigationType` (`navigate | reload | back_forward | prerender`), `controlled` (a service worker
served the page). Warm and cold launch timings stay 0024's (`tm.launch.warm|cold`). The collector
observes with `buffered: true`, so loading it at idle loses no entry.

#### §5.3 Request outcomes

- **`tm.api.requests`** (always sent): per flush window, one event per API route template
  (`centers/query`, `/bff/user`, `blobs/user-image/:id`), top 20 routes by count, with `api`,
  `count`, `ok`, `failed`, `cancelled`, `network`, `sumMs`, `maxMs`, `over1s`, `over3s`,
  `background` (count of background calls).
- **`tm.api.slow`** (always sent, at most 20 per tab per 10 minutes): one event per request whose
  duration reached 3 s, whatever its outcome, with `api`, `durationMs`, `outcome`, `status`,
  `code` and the item `traceId`. A slow request still pending at `pagehide` is reported with
  `outcome: 'pending'`; 0024's watchdog (60 s, 6 min for `long`) ends every other wait.
- **Blob GETs** (`TM_BLOB_FETCHER`) count in the summaries; they enter the request log only when
  slow or failed, so 50 avatars do not flush it.

#### §5.4 Usage

`tm.action.invoked { action, origin, outcome, ms }` (sampled) from the dispatcher (§9.5) is the
platform's usage signal; `tm.page.visit` gives page usage. Domain usage events are their specs'.

### §6 The relay: `POST /api/client-telemetry`

The relay accepts batches from signed-in browsers, validates every item, adds what only the
server knows, and writes each item into the host's OpenTelemetry pipeline, which exports to
Application Insights when it is configured and to Serilog's sinks always.

#### §6.1 Contract

```csharp
// Tellma.Core.Abstractions.Api — A§6.1's records, completed with SentAt
public sealed record ClientTelemetryBatch(string Version, string TabId, int? TenantId, DateTimeOffset SentAt,
    IReadOnlyList<ClientTelemetryItem> Items);
public sealed record ClientTelemetryItem(string Kind, string Name, DateTimeOffset At, string? TraceId,
    IReadOnlyDictionary<string, JsonElement>? Properties);   // Kind: event | timing | error

public sealed class ClientTelemetryOptions                    // Tellma:ClientTelemetry
{
    public bool Enabled { get; set; } = true;                 // false: 204 and discard; DistributionInfo tells the SPA
    [Range(0.0, 1.0)] public double SampleRate { get; set; } = 1.0; // published to the SPA (§3.5)
}

// Tellma.Core.AspNetCore — mapped by MapTellma
//   POST /api/client-telemetry
//   RequireAuthorization(TellmaPolicies.Web), AsTenantlessEndpoint("client-telemetry")
//   rate policy tellma-telemetry; request size limit 32 KB (413 limit-exceeded beyond)
//   excluded from ASP.NET Core request tracing (instrumentation filter)
//   never renews the session cookie (OnCheckSlidingExpiration: ShouldRenew = false), header or not
//   → 204 No Content when the batch parses, whatever was dropped; 400 bad-request otherwise
```

**Example —** a batch of two items, answered `204`:

```json
{ "version": "1.4.0+3f9c2ab1e5d4c0a7b6f8e9d2c1b0a9f8e7d6c5b4", "tabId": "k3J7q2M9xA", "tenantId": 17,
  "sentAt": "2026-10-20T11:03:12.512Z", "items": [
    { "kind": "timing", "name": "tm.page.visit", "at": "2026-10-20T11:02:41.020Z", "properties": {
        "route": "/:t/centers", "pageKind": "search", "ms": 412, "chromeMs": 38, "inpMs": 64, "outcome": "ready" } },
    { "kind": "event", "name": "tm.api.slow", "at": "2026-10-20T11:02:55.300Z", "traceId": "0af7651916cd43dd8448eb211c80319c",
      "properties": { "route": "/:t/centers", "pageKind": "search", "api": "centers/query", "durationMs": 4810, "outcome": "ok" } } ] }
```

#### §6.2 Validation and limits

| Check | Rule | On failure |
|---|---|---|
| CSRF | 0011 §5.4 applies: `Tellma-Client` with name `web`, JSON body, same origin | 403 / 415 |
| session | the `Tellma.Web` cookie policy | 401 `unauthenticated` |
| body | ≤ 32 KB | 413 `limit-exceeded` |
| batch | `Version` equals the `Tellma-Client` version part; `TabId` `^[A-Za-z0-9_-]{8,32}$`; `TenantId` null or ≥ 1; ≤ 100 items | 400 `bad-request` |
| `Kind` | `event`, `timing`, `error` | item dropped (`kind`) |
| `Name` | §3.2's grammar; `tm.error.captured` exactly for errors | item dropped (`name`) |
| `At` | within `SentAt − 24 h` … `SentAt + 1 min` | item dropped (`time`) |
| `TraceId` | 32 lowercase hex, not all zeros | member ignored |
| `Properties` | ≤ 16; keys §3.2; strings ≤ 128 (`stack` ≤ 4096, `message` ≤ 256), numbers, booleans; nothing nested | property dropped (`prop`) |

- **Backstop redaction:** the relay re-applies the e-mail and URL masks of §4.3 to `message` and
  `stack`.
- **Rate policy `tellma-telemetry`** (0016 §8.2 edit): partition `{sub}`, 60 batches per minute
  per user (`TelemetryBatchesPerMinutePerUser`), sliding window of 6 segments, queue 0; a
  separate bucket from `tellma-user`, so telemetry never starves user calls. Ten open tabs at two
  batches a minute use a third of it.

#### §6.3 What the server adds

Every record carries, besides the item's own name, time and properties:

| Dimension | Source |
|---|---|
| `Subject` | the session principal's `sub` (never e-mail) |
| `ClientVersion`, `ClientOutdated` | batch `Version`; true when it differs from `DistributionVersion` |
| `ClientTabId`, `ClientTenantId` | batch; the tenant id is the client's claim, used for filtering only |
| `ClientAt` | item `At` corrected by the batch's clock skew (`ReceivedAt − SentAt`) |

| `UserAgent` | the request's `User-Agent` |

| `PlatformVersion`, `DistributionVersion`, `service.version`, `tellma.deployment.id` | 0011 §9's enrichers and resource |

No tenant scope is opened and no database is touched; `ClientTenantId` is never used for
authorisation or as a metric tag.

#### §6.4 Emission

| Item | Record | Level | Application Insights |

### §8 Request log and trace ids

Every `TmApi` call has a client-generated trace id before it is sent (0024 §10.2), which the
server adopts (0011 §9 edit). The request log keeps the last 100 calls with their trace ids, so a
slow, failed or cancelled call can always be quoted.

#### §8.1 `TmRequestLog`

```ts
type TmRequestOutcome = 'pending' | 'ok' | 'cancelled' | 'error';
interface TmRequestRecord {                          // A§5.9, completed
  readonly traceId: string; readonly route: string;  // '4bf9…', 'centers/query' (TmApi's route; blobs: 'blobs/user-image/:id')
  readonly tenantId: number | null; readonly method: 'POST' | 'GET'; readonly background: boolean;
  readonly startedAt: number; readonly durationMs: number | null;   // null while pending
  readonly outcome: TmRequestOutcome; readonly status?: number; readonly code?: string; // TmApiError code
  readonly slow: boolean;                            // durationMs ≥ 3000, or pending for 3 s
}
declare class TmRequestLog {
  readonly recent: Signal<readonly TmRequestRecord[]>; // newest first, ring of 100
  diagnosticsText(count?: number): string;           // §8.3, default 10 requests; synchronous
  copy(): Promise<void>;                             // clipboard.writeText(diagnosticsText()) within the gesture
  begin(start: { traceId: string; route: string; tenantId: number | null; method: 'POST' | 'GET'; background: boolean }): TmRequestHandle; // TmApi only (internal)
}
interface TmRequestHandle { end(result: { outcome: Exclude<TmRequestOutcome, 'pending'>; status?: number; code?: string; serverBuild?: string }): void }
```

- **`TmApi` calls `begin` at send and `end` at settle** (request to 0024; it replaces N24 §10.3
  step 5's single record). A record is visible as `pending` from the first byte, so a hanging
  call's trace id can be copied while it hangs.
- **Not logged:** `send` calls (telemetry, pagehide flushes: no outcome); blob GETs unless slow or
  failed (§5.3).
- **`slow`** flips at 3 s even while pending (a timer per pending call, cleared at `end`); the
  record then feeds `tm.api.slow` at its end.
- **`end`** passes `Tellma-Build` to `TmAppVersion.server`.

#### §8.2 Slow requests (Supportability Q1)

- A slow request shows no UI (the brief): its loading state is the only feedback.
- Its trace id is reachable three ways: the Diagnostics panel (§8.4), "Copy diagnostics" (§8.3)
  and, for support without the user, `tm.api.slow` in Application Insights under the request's
  trace id, found by user (`Subject`) and time.
- Nothing is logged to the browser console in production: users do not open it.

#### §8.3 Copy diagnostics

`TmRequestLog.diagnosticsText()` builds a plain-text block for support. It is English with Latin

### §9 Page context and page actions — the assistant seam

Every page and every context-bearing dialog publishes one `TmPageContext`: what it is, what it
shows, what is wrong on it, and what can be done there. The page frameworks publish from state
they already hold; distribution layouts write nothing. The same registry feeds the toolbar, the
Actions menu, page shortcuts, the Shortcuts dialog, the support dump and the future assistant.

#### §9.1 Contracts

```ts
type TmPageKind = 'home' | 'search' | 'details' | 'report' | 'studio' | 'dashboard' | 'settings' | 'custom';
interface TmPageContext {                            // A§5.10, completed
  readonly kind: TmPageKind; readonly routeTemplate: string;   // '/:t/centers/:id'
  readonly overlay?: boolean;                        // true: an open dialog's context (default false)
  readonly entity?: string;                          // 'gl.Center'
  readonly title: Signal<string>;                    // localized, as displayed
  readonly helpKey?: string;                         // reserved (§9.8)
  readonly status: Signal<'loading' | 'ready' | 'error'>;      // added: the page's data state
  readonly state: Signal<TmJson>;                    // kind-specific (§9.3)
  readonly visible?: Signal<TmVisibleData | undefined>;        // what grids and lists display
  readonly form?: TmFormContext;                     // details and settings edit mode
  readonly errors: Signal<readonly TmContextError[]>;
  readonly actions: Signal<readonly TmPageAction[]>; // the publisher's own; the registry merges scoped ones (§9.4)
}
interface TmVisibleData {
  readonly columns: readonly { readonly path: string; readonly label: string }[]; // ≤ 50, as displayed
  readonly rows: readonly { readonly id: number | null; readonly cells: Readonly<Record<string, TmJson>> }[]; // ≤ 200
  readonly total: number | null;                     // the query's count when known
  readonly truncated: boolean;                       // more rows displayed than carried
}
interface TmContextError {
  readonly source: 'validation' | 'request' | 'render' | 'client';
  readonly code: string;                             // 'Required', 'query-invalid', 'server'
  readonly message: string;                          // localized, as displayed
  readonly path?: string;                            // 'Name', 'Lines[2].Quantity'
  readonly traceId?: string;
}
interface TmFormContext {
  readonly fields: Signal<readonly TmFormField[]>;
  readonly dirty: Signal<boolean>;
  readonly assisted: Signal<ReadonlySet<string>>;    // paths written by propose and not edited since
  propose(path: string, value: TmJson): boolean;     // writes the model through the field; false when unknown or not editable; never saves
}
interface TmFormField { readonly path: string; readonly labelKey: string; readonly label: string;
  readonly value: TmJson; readonly errors: readonly string[]; readonly editable: boolean }
```

- **`visible.cells`** hold what the cell shows, in lossless JSON: a navigation is its display name,
  with the id under `<path>.Id`; a date is ISO `yyyy-MM-dd`; an enum is its code.
- **`status`** (an addition to A§5.10) lets the dump, `tm.page.visit` and the assistant tell
  "still loading" from "empty".
- **`propose`** marks the path in `assisted`; 0031 renders the mark on the field until the user
  edits it. Nothing in v1 calls `propose` outside tests.

#### §9.2 The registry

```ts
declare class TmPageContexts {
  readonly current: Signal<TmPageContext | null>;          // the routed page, actions merged (§9.4)
  readonly overlays: Signal<readonly TmPageContext[]>;     // open context-bearing dialogs, bottom to top
  readonly top: Signal<TmPageContext | null>;              // the topmost overlay, else current
  register(context: TmPageContext, destroyRef?: DestroyRef): void; // destroyRef defaults to the injection context's
}
declare function provideTmPageScope(): Provider[];
declare function tmSerializePageContext(context: TmPageContext, options: { includeData: boolean }): TmPageContextSnapshot;
```

- **Who registers.** The route host (0024) registers a `custom` context for `tmPage` routes and
  provides a page scope for every page; the search, details, report, studio, dashboard, home and
  settings hosts register their kind's context (owners in §9.3); the 0024 error dialogs register
  an overlay context carrying their `TmContextError`. A layout never registers.
- **One routed context per page scope:** a second non-overlay `register` in the same scope
  replaces the first (the hatch of §2 example 3); overlay contexts never replace each other. `current` is the newest live non-overlay context. Overlays are
  ordered by registration; a destroyed scope removes its context at once.
- **Timing.** A host registers in its constructor; `chromeMs` stamps the registration's paint
  (§5.1). The context's signals are read lazily: registering costs no computation.

#### §9.3 What each page kind publishes

| Kind | `state` (minimum; the owner completes it) | `visible` | `form` | Owner |
|---|---|---|---|---|
| `home` | `{}` | assignment lists' rows | — | 0035 |
| `search` | `{ query: TmSearchQuery, view, selectedIds (≤ 200), selectedCount }` | grid or tile rows | — | 0030 |
| `details` | `{ id: number \| null, mode: 'view' \| 'edit' \| 'create', tab?: string }` | the open child grid's rows | edit and create modes | 0031 |
| `report` | `{ report: number \| string, parameters, reportKind }` | rendered rows (list, summary) | — | 0034 |
| `studio` | `{ report: number \| null, root: string, reportKind }` | preview rows | — | 0034 |
| `dashboard` | `{ dashboard: number, parameters, widgets: number }` | — | — | 0035 |
| `settings` | `{ category, mode }` | — | edit mode | 0032 |
| `custom` | the page's own; default `{}` | the page's own | the page's own | 0024 route host, or the page (§2) |

**Action ids** follow `^[a-z][a-z0-9]*(\.[a-z0-9][a-z0-9-]*){1,4}$`: framework actions
`search.*`, `details.*`, `report.*`, `studio.*`, `dashboard.*`, `settings.*`, `support.*`; entity
actions `<schema>.<entity-kebab>.<action>` (`gl.center.activate`); distribution actions
`<feature>.<area>.<verb>` (`acme.bank-reconciliation.auto-match`). Each page spec lists its ids.

#### §9.4 Page actions

```ts
interface TmPageAction {                             // A§5.10, completed
  readonly id: string; readonly labelKey: string; readonly descriptionKey?: string; // description: for the assistant
  readonly icon?: string; readonly group: 'primary' | 'menu' | 'hidden'; readonly order: number;
  readonly enabled: Signal<boolean>; readonly destructive: boolean;
  readonly confirm?: { readonly titleKey: string; readonly messageKey: string; readonly args?: Signal<TmJson> }; // required when destructive
  readonly shortcut?: TmKeys;                        // page scope; registered while its context is top
  readonly params?: TmJsonSchema;                    // object schema of arguments; absent = none
  invoke(args: TmJson, origin: TmActionOrigin): Promise<TmActionResult>;
}
type TmActionOrigin = 'user' | 'shortcut' | 'launcher' | 'assistant';
type TmJsonSchema = Readonly<TmJsonObject>;           // JSON Schema subset: type object, properties, required, enum, items, description
type TmActionResult =
  | { readonly outcome: 'done'; readonly data?: TmJson }
  | { readonly outcome: 'cancelled' }                // a confirmation or dialog declined
  | { readonly outcome: 'refused'; readonly reason: 'not-found' | 'disabled' | 'busy' }
  | { readonly outcome: 'failed'; readonly error: unknown };
type TmPageActionDefinition = Omit<TmPageAction, 'group' | 'order' | 'enabled' | 'destructive'> &
  Partial<Pick<TmPageAction, 'group' | 'order' | 'enabled' | 'destructive'>>; // defaults: 'menu', 100, true, false
declare class TmPageActions {
  register(action: TmPageActionDefinition, destroyRef?: DestroyRef): void;
  invoke(id: string, args: TmJson, origin: TmActionOrigin): Promise<TmActionResult>;  // §9.5
  readonly running: Signal<ReadonlySet<string>>;     // ids being invoked: views render busy
}
```

- **Scope.** `TmPageActions` injected inside a page scope (`provideTmPageScope()`, which the
  route host provides per page and an overlay provides for itself) adds to that scope's context,
  even before the context registers. Injected outside any scope (root), it adds to `current`, as
  A§5.10 states. Unregistering is automatic through `destroyRef`.
- **Merged views.** `current().actions()` and each overlay's `actions()` are the publisher's
  actions followed by the scope's, ordered by `group`, then `order`, then registration.
- **Views (owners render):** `group: 'primary'` → toolbar buttons (0030, 0031); `'menu'` → the
  Actions menu (0031) or overflow; `'hidden'` → only shortcuts, the launcher and the assistant.
  The Shortcuts dialog (0027) lists the top context's actions that have a `shortcut`.
- **Shortcuts.** The registry registers each `shortcut` with `TmShortcuts` (scope `page`) while
  its context is `top`; the run calls `invoke(id, {}, 'shortcut')`. An action whose `params`
  require members takes no shortcut (development error).

#### §9.5 The dispatcher (`TmPageActions.invoke`)

Every origin goes through it, so permission, double-submit and confirmation rules hold once:

1. Find `id` in `top`, then lower overlays, then `current`; absent → `refused: not-found`.
2. `enabled()` false → `refused: disabled` (permissions are already in `enabled`, from
   `TmPermissions`).
3. Already in `running` → `refused: busy` (no double submit).
4. `destructive` → the 0023 `confirm` with `confirm`'s keys (danger tone), for every origin;
   declined → `cancelled`. A destructive action without `confirm` throws in development.
5. Add to `running`, `await action.invoke(args, origin)`, remove; a throw → `failed` (the action
   still presents its own `TmApiError` through `TmErrorPresenter`).
6. Telemetry `tm.action.invoked { action, origin, outcome, ms }` (sampled).

- Views call `invoke(action.id, {}, 'user')`; they never call `action.invoke` directly, and they
  render `running` as the button's busy state in the click's frame (rule 2B).
- **Assistant safety:** `assistant` origin adds nothing to step 4 because every origin confirms; a
  form write is `propose`, which never saves; `params` validation of assistant arguments is the
  future adapter's (§9.7).

#### §9.6 Snapshots

`tmSerializePageContext(context, { includeData })` reads every signal once and returns plain
JSON, the one serialisation the dump and the future assistant share.

```ts
interface TmPageContextSnapshot {
  readonly kind: TmPageKind; readonly routeTemplate: string; readonly overlay: boolean;
  readonly entity?: string; readonly title: string; readonly helpKey?: string;
  readonly status: 'loading' | 'ready' | 'error'; readonly state: TmJson;
  readonly visible?: { readonly columns: readonly string[]; readonly rowCount: number; readonly total: number | null;
    readonly rows?: TmVisibleData['rows'] };       // rows only with includeData
  readonly form?: { readonly dirty: boolean; readonly fields: readonly { readonly path: string; readonly editable: boolean;
    readonly errorCount: number; readonly value?: TmJson }[] };   // value only with includeData
  readonly errors: readonly { readonly source: string; readonly code: string; readonly path?: string;
    readonly traceId?: string; readonly message?: string }[];     // message only with includeData
  readonly actions: readonly { readonly id: string; readonly enabled: boolean; readonly destructive: boolean;
    readonly group: string; readonly hasParams: boolean }[];
}
```

- **Without page data**, `state` is kept but its `query.q`, `query.filter` and
  `query.columnFilters` values become `"…"` (they are user text), and `title` is kept only for
  kinds whose title is not a record's display name (`details` titles become the entity label).

#### §9.7 AG-UI mapping (future; nothing ships now)

A future `@tellma/core/assistant` adapter maps the registry onto AG-UI's run input and tool
calls. AG-UI streams events from the agent to the client during a run; the client's facts reach
the agent in `RunAgentInput` when a run starts.

| Tellma | AG-UI |
|---|---|
| snapshots of `current` and `overlays`, plus a session block (tenant, language, calendar, UI version) | `RunAgentInput.context`: `{ description: 'tellma.page', value: JSON }`; also mirrored as `RunAgentInput.state.page` |
| enabled actions of `top` | `RunAgentInput.tools`: `{ name: id with '.' → '__', description: label + description, parameters: params ?? { type: 'object', properties: {} } }` |
| `TmFormContext.propose` | one tool `tellma__propose_values` `{ values: [{ path, value }] }`, offered while a form is in edit mode |
| `ToolCallStart`/`ToolCallArgs`/`ToolCallEnd` | adapter validates args against `params`, then `TmPageActions.invoke(id, args, 'assistant')` |
| `TmActionResult` | the tool message `{ role: 'tool', toolCallId, content: JSON, error? }` (`failed` and `refused` set `error`) |
| destructive confirmation | the platform's confirm dialog: human in the loop happens in the page, whatever the agent asks |
| agent `StateSnapshot` / `StateDelta` (RFC 6902) | the assistant panel's own state; never applied to a page, whose writes go only through `propose` |
| context changes during a run | carried by the next run's input (a run never receives client events mid-stream) |

#### §9.8 Help seams (reserved)

- **`helpKey`** on page contexts, on 0027's nav entries and on `tm-field` (0031): grammar
  `^[a-z][a-z0-9-]*(\.[a-z0-9][a-z0-9-]*)*$` (`gl.center`, `gl.center.fields.code`). Frameworks
  pass through a declaration's `helpKey` member when present (0029 reserves it on `tmEntity`);
  nothing derives one in v1.
- **`TM_HELP_ARTICLES`** (primary): `InjectionToken<(key: string, language: string) =>

### §10 The state dump

```json
  "includesPageData": false, "truncated": [], "versions": { "ui": "1.4.0+3f9c2ab…", "server": "1.4.0+3f9c2ab…" },

```

- **Never in a dump:** cookies, the profile cookie's name and e-mail, storage contents, launch
  document bodies (only their names, tags and ages), drafts, request or response bodies.

#### §10.2 Page data

`includesPageData` false (the default): `tmSerializePageContext(…, { includeData: false })`,
so no row values, form values, error messages or user text of the query. True only when the user
ticks "Include the data shown on the page" in the support dialog (§12.2). A downloaded dump uses
the same tick; "Download diagnostic file" outside the dialog never includes page data.

#### §10.3 Size cap

- **2 MiB** UTF-8 (`TM_SUPPORT_DUMP_MAX_BYTES`). Over it, the builder drops in this order until
  the dump fits, naming each step in `truncated`: `telemetry` to 50, `contexts.*.visible.rows` to
  50, `form` values, `requests` to 50, `errors` to 20, `telemetry` to none.
- A typical dump without page data is 30–80 KB; with 200 rows of 20 columns about 300 KB.

#### §10.4 Building and downloading

1. `TmSupport` (primary) snapshots the contexts synchronously when the user asks (the dialog
   opening is not yet in them), then imports `/support`, whose `tmBuildSupportDump(snapshot)`
   adds the rest (`navigator.storage.estimate()` is the only await, time-boxed to 200 ms).
2. Download: a `Blob` (`application/json`), `URL.createObjectURL`, a temporary `<a download>`
   clicked, the URL revoked after a tick. File name `<slug>-diagnostics-<yyyyMMdd-HHmmss>.json`
   (local time, Latin digits): `acme-diagnostics-20261020-140312.json`.
3. Telemetry `tm.support.dump-downloaded { pageData }`.

### §11 The screenshot (Supportability Q2)

The screenshot is one frame of a screen-capture stream, taken only after the browser's own
consent prompt. Where capture does not exist, the user attaches an image they took themselves.

```ts
interface TmScreenshot { readonly blob: Blob; readonly width: number; readonly height: number;
  readonly surface: 'browser' | 'window' | 'monitor' | 'file'; }
declare class TmScreenCapture {                    // @tellma/core/support
  readonly supported: boolean;                     // isSecureContext && navigator.mediaDevices?.getDisplayMedia
  capture(): Promise<TmScreenshot | null>;         // call inside a click handler; null = the user declined
  fromFile(file: File): Promise<TmScreenshot>;     // the attach fallback (png, jpeg, webp)
}
declare const TM_DISPLAY_MEDIA: InjectionToken<(options: DisplayMediaStreamOptions) => Promise<MediaStream>>; // test seam
```

#### §11.1 Capture

1. The user presses "Take screenshot" in the support dialog. In that click handler, before any
   `await`, the dialog sets `capturing` (its panel and backdrop get `visibility: hidden`, so no
   layout moves) and calls `getDisplayMedia` (transient activation is required):
   `{ video: { displaySurface: 'browser' }, audio: false, preferCurrentTab: true,
   selfBrowserSurface: 'include', surfaceSwitching: 'exclude', monitorTypeSurfaces: 'exclude' }`,
   each hint only when the browser recognises it.
2. The browser prompts. Chromium (`preferCurrentTab`) asks to share this tab in one click; Firefox
   and Safari show their window and screen picker.
3. Granted: a muted, off-screen `<video>` plays the stream; after two video frames
   (`requestVideoFrameCallback`, else two `requestAnimationFrame`s after `loadeddata`), the frame
   is drawn to a canvas of `videoWidth × videoHeight`; every track stops at once; `toBlob('image/png')`.
4. The dialog leaves `capturing` and shows the preview. Declined (`NotAllowedError`) → back to the
   dialog, nothing shown. No frame within 3 s, or any other error → "Couldn't take a screenshot.
   You can attach one instead.".

- **Size:** a PNG over 8 MiB is redrawn at half size (`surface` unchanged); the kind allows 16 MiB.
- **The browser's sharing indicator** is browser chrome, outside the tab's pixels; the capture
  lasts well under a second.
- **Not used:** DOM rasterising (html2canvas and alikes: approximate rendering, a hack the brief
  rules out); Element and Region Capture (Chromium-only; hiding the dialog is enough).
- **Policy:** `Permissions-Policy: display-capture=(self)` on `index.html` (A§6.6); the CSP needs
  nothing new (`img-src blob:` covers the preview).

#### §11.2 Support matrix and the fallback

| Browser | Capture | What the user sees |
|---|---|---|
| Chrome, Edge (desktop) | tab, preselected | "Allow this site to see this tab?" |
| Firefox, Safari (desktop) | window or screen | the browser's picker |
| Safari iOS 27+ | screen | the system prompt |
| Chrome Android, Firefox Android, Samsung Internet, older iOS | none | "Take screenshot" hidden; "Attach image" only |

- **"Attach image"** (always offered) opens a file input (`accept="image/png,image/jpeg,image/webp"`)
  so a device screenshot can be sent; a hint below it says "Use your device's screenshot keys to
  capture the whole screen."
- **Download:** the preview offers "Download" (`<slug>-screenshot-<yyyyMMdd-HHmmss>.png`).
- Telemetry `tm.support.screenshot { outcome: 'taken' | 'declined' | 'failed' | 'attached', surface }`.

### §12 Support requests (Supportability Q3)

The dump and screenshot are always downloadable. When the distribution opts in, the user can
send them to support from Tellma: the files are staged as tenant blobs and one `submit` call
writes a `core.SupportRequests` row. Tenant administrators see the row on a stock page; Tellma
support reads it over the admin surface. No outbound channel to a control plane is needed.

#### §12.1 Opt-in and `TmSupport`

- **`Tellma:Support:Enabled`** (default false) is published as
  `DistributionInfo.support { enabled, providerAccess }` (0011 §5.9 edit); `providerAccess` is
  true when the admin surface is mapped, and chooses the warning's wording.

```ts
declare class TmSupport {                          // primary facade
  readonly canSend: Signal<boolean>;               // support.enabled, a tenant route, a member, online, tenant not read-only
  open(options?: { error?: TmApiError }): void;    // the support dialog (§12.2); never throws
  copyDiagnostics(): void;                         // = TmRequestLog.copy(), inside the gesture
  downloadDump(): void;                            // §10.4 without page data
}
```

- **Entry points:** the session menu row "Report a problem" (icon `life-buoy`, 0027); the
  Diagnostics panel's button; the 5xx dialog's "Report this problem" (0024), which passes its
  error: the dump records it as `reported` and its trace id heads `traceIds`. The 5xx dialog stays
  open beneath, so its overlay context is in the snapshot and in the screenshot.
- **`open` meets rule 2B:** it opens the `TmModal` in the click's frame with a final-geometry
  placeholder body, snapshots the contexts, then imports `/support` (a cache read once fetched;
  on demand the first time).

#### §12.2 The support dialog

**Compose state** (`canSend` true), top to bottom: title "Report a problem"; the message field
"What happened?" with the placeholder "Describe what you were doing and what went wrong."; the
list "What's included": "Diagnostic information" (always; View, Download), "Screenshot" (Take
screenshot, Attach image, or the preview), the checkbox "Include the data shown on the page"; the
warning; the buttons "Download instead" (link style), Cancel, Send (primary).

- **Message:** optional, ≤ 2,000 characters, `dir="auto"`, counter from 1,800.
- **Warning** (0023 inline banner, tone warning, `role="note"`): with `providerAccess` "Your
  administrators and the {displayName} support team will see what you send, including any
  screenshot."; without "Your administrators will see what you send, including any screenshot.";
  both continue "Don't send it if the page shows information you're not allowed to share."
- **View** opens the dump as formatted JSON in a read-only, LTR, monospace panel inside the
  dialog (no network).
- **Screenshot slot:** the preview thumbnail (fixed 16:9 box, so nothing shifts) with Remove,
  Retake and Download.
- **Download-only state** (`canSend` false): no message field or Send; the text "Download the
  diagnostic file and screenshot, then send them to your support contact." and the reason when
  one applies ("You're offline.", "This tenant is read-only.").
- **Keyboard and ARIA:** `role="dialog"` labelled by the title; focus starts in the message;
  Escape and Cancel close it, aborting uploads in flight (staged blobs expire); once `submit` is
  sent the dialog waits for its answer; capture state announced politely ("Taking a screenshot",
  "Screenshot added"); Send is the default button with Ctrl+Enter.
- **Responsive and RTL:** full screen below `sm` (0010 Part D), buttons stacked; the layout
  mirrors; JSON and trace ids stay LTR-isolated.

**Send flow:**

1. Send → `sending`: the fields lock; the button shows busy; "Sending 2 files…".
2. The dump (`support-diagnostics.json`, `application/json`) and the screenshot (`screenshot.png`)
   upload in parallel through `TmApi.upload('support-bundle', blob, { fileName })` (request to
   0024), each returning a staged `BlobDescriptor` (0017).
3. `TmApi.write('support-requests/submit', submission)`.
4. **Sent:** "Sent to support" / "Your request number is 1042. Quote it when you talk to support."
   with a `tm-reference` (label "Request", value "1042") whose copy text is "Acme support request
   1042, tenant 17"; Close. Telemetry `tm.support.sent { screenshot, pageData }`.
5. **Failed** (any step): an inline error with the problem's text, the trace id chip, Try again
   (re-sends only what failed; staged blobs live 24 h) and Download instead. Telemetry
   `tm.support.send-failed { stage: 'upload' | 'submit', kind }`.

**Example —** the submission:

```json
{ "message": "Saving a center hangs for a minute, then fails.", "uiVersion": "1.4.0+3f9c2ab1e5d4…",
  "routeTemplate": "/:t/centers/:id", "pageUrl": "https://acme.app.tellma.com/17/centers/5",
  "traceIds": ["4bf92f3577b34da6a3ce929d0e0e4736", "0af7651916cd43dd8448eb211c80319c"],
  "includesPageData": false,
  "files": [{ "role": "dump", "fileId": 9001 }, { "role": "screenshot", "fileId": 9002 }] }
→ 200 { "id": 1042 }
```

`traceIds`: the trace ids of the dump's errors and slow requests first, then the newest requests,
at most 20.

#### §12.3 Server contract

```csharp

}

public sealed record SupportRequestSubmission(string? Message, string UiVersion, string? RouteTemplate,
    string? PageUrl, IReadOnlyList<string> TraceIds, bool IncludesPageData,
    IReadOnlyList<SupportRequestFileSubmission> Files);
public sealed record SupportRequestFileSubmission(string Role, int FileId);
public sealed record SupportRequestReceipt(int Id);

public sealed class SupportRequestService                     // the entity service
{
    // MemberOnly; Mutation = true, Idempotent = false; enlisted insert (0019 §12.2 pattern)

public sealed class SupportOptions                             // Tellma:Support

```

- **`submit`** builds one row (server values: `ServerVersion`, `UserAgent`, `ExpiresAt`), enlists
  its insert with the `IOpenWriteHost` of the action's frame and awaits `PersistAsync` (spec 0015
  §13.3), so 0017's attach rule confirms the staged blobs in the same transaction: kind
  `support-bundle`, staged by the caller, unexpired, used once.
- **Validation codes** (`SupportRequests.*`, Core resx, at the stated path):

| Code | Path | Rule |
|---|---|---|
| `SupportRequests.Disabled` | root | `Tellma:Support:Enabled` is false |
| `SupportRequests.DumpRequired` | `files` | exactly one `dump` file |
| `SupportRequests.TooManyFiles` | `files` | at most one `screenshot`; no other role |
| `SupportRequests.FileType` | `files[i]` | `dump` is `application/json`; `screenshot` is `image/png`, `image/jpeg` or `image/webp` |
| `SupportRequests.DailyLimit` | root | more than `MaxRequestsPerUserPerDay` rows by the caller since tenant midnight (one count read in the validation round) |
| `SupportRequests.TraceId` | `traceIds[i]` | 32 lowercase hex; at most 20 |
| 0017's `Blob.NotAttachable`, `Blob.DuplicateReference` | `files[i].fileId` | per 0017 §4 |

- **Tenant states:** a `ReadOnly` tenant refuses `submit` (403 `tenant-read-only`), which is why
  `canSend` is false there.
- **Round trips:** 2 (a validation round with 0017's blob checks and the daily count; the persist).
- **MCP:** not exposed (dumps hold page data of other users).

#### §12.4 Blob kind `support-bundle` (0017 §1.3 edit)

| Owner column | Preset | Overrides | Read access |
|---|---|---|---|
| `SupportRequestFile.FileId` | `Attachment` | `MaxSize` 16 MiB; types `application/json`, `image/png`, `image/jpeg`, `image/webp`; thumbnail 256 px WebP for images | `OwnerRead` through `core.SupportRequest` |

## 4. Open questions owned

- **Observability Q1 — what to collect, and the principles.** Principles: (1) no tenant content
  or free text leaves the tab (§3.2's guard, §4.3); (2) closed, low-cardinality names, with
  client strings never becoming metric tags (§6.4); (3) bounded volume: aggregate the frequent,
  send the rare one by one, sample only the optional (§3.5, §5.3); (4) every item joins its
  context (version, route template, tenant, tab, trace ids) so one query reconstructs a session
  (§3.1); (5) best effort: telemetry never blocks, retries or throws. Collected: errors,
  launch timing (0024), per-visit chrome/data/INP/layout shift, the load's TTFB/FCP/LCP, request
  outcomes per route with slow requests by trace id, service-worker, session and hub lifecycle
  (0024, 0025), action usage. Alternatives: full RUM with session replay (privacy, weight);
  errors only (no way to see "slow").
- **Observability Q2 — transport and UI error logging.** Batches over `POST
  /api/client-telemetry` with `fetch` `keepalive` (§3.3); the relay writes OpenTelemetry log
  records (custom events, Warning traces) and closed-tag metrics that the host's Azure Monitor
  exporter sends to Application Insights (§6.4); errors through `TmErrorHandler` (§4).
  Alternatives: the Application Insights web SDK (~75 KB, a connection string in the bundle, no
  on-prem story); `sendBeacon` (cannot carry `Tellma-Client`, fails CSRF); OTLP from the browser
  to a collector (another public endpoint to run).
- **Supportability Q1 — slow-request trace ids.** Client-generated trace ids known before the
  response; a 100-entry request log in About › Diagnostics; "Copy diagnostics" on
  `Mod+Alt+Shift+D` copying version, page and the last 10 requests; slow requests also reach
  Application Insights under their own trace id (§8). This follows desktop practice (Teams'
  `Ctrl+Alt+Shift+1` collects diagnostic logs). Alternatives: console logging (users never open
  it); a toast per slow call (noise; the brief wants no UI).
- **Supportability Q2 — a page screenshot.** Yes, through the Screen Capture API:
  `getDisplayMedia({ preferCurrentTab })` gives a one-click "share this tab" on Chromium, a window
  picker on Firefox and Safari desktop, and nothing on Android; one frame becomes a PNG, the
  dialog hidden meanwhile; an attached device screenshot covers the rest (§11). Alternatives: DOM
  rasterising (html2canvas: approximate, a hack); Element Capture (Chromium only).
- **Supportability Q3 — where dump and screenshot go.** Always downloadable. With
  `Tellma:Support:Enabled`, staged as tenant blobs (`support-bundle`) and recorded as a
  `core.SupportRequests` row; tenant admins read it on a stock page and Tellma support over the
  admin surface (§12). Alternatives: the distribution's blob storage alone (only devops can reach
  it); a control-plane upload (an outbound client and credentials in every distribution, and no
  tenant-admin view).
- **Supportability Q4 — the UI version.** The distribution's informational version
  `X.Y.Z+<commit sha>`, the same value as the server's `Tellma-Build` (§7). Alternatives: a
  separate SPA build id (two numbers for one build); the bare commit hash (unreadable in a menu).

## 11. Review flags

1. **Relay, no Application Insights SDK** (decision 1; A§12 #15). Alternative: the web SDK.
   Flips if session replay or browser-side dependency tracking is needed.
2. **Page data off by default in dumps** (§10.2). Alternative: on by default. Flips if support
   finds most dumps useless without rows.
3. **Client request outcomes aggregated per window** (decision 4). Alternative: one item per
   request. Flips if per-request latency analysis is needed and the volume is affordable.
4. **Client errors as Warning traces, not the `exceptions` table** (§6.4). Alternative: a
   synthetic exception type so errors appear in the Failures blade. Flips if the team lives in
   that blade.
5. **Support requests visible to administrators only** (§12.6). Alternative: self-scoped read.
   Flips if users ask to see what they sent.
6. **Per-tenant admin listing, no cross-tenant index** (§12.7). Alternative: a catalog index row
   per request. Flips if support must triage requests nobody quoted.
7. **30-day retention** (§12.8). Alternative: 90 days. Flips on a support or privacy policy.
8. **Distribution-level opt-in only** (§12.1). Alternative: a tenant setting that can switch
   support off. Flips if a customer forbids sending screens to the provider.
9. **`Mod+Alt+Shift+D` for Copy diagnostics** (§8.3). Alternative: Teams' `Mod+Alt+Shift+1`
   habit, or no shortcut. Flips on a conflict found in a target market's layouts.
10. **Tab-level sampling, default 1** (decision 5). Flips if ingestion cost grows.
11. **Trace-parented client records** (decision 3). Alternative: trace id as a dimension only.
    Flips if parenting confuses the transaction view.
12. **No user opt-out of telemetry** (§3). Pseudonymous operational data only. Flips on a legal
    review in a target market.
13. **Own per-visit measurements instead of `web-vitals`** (decision 6). Flips when the Soft
    Navigations API ships everywhere.

## 12. Challenges to the architecture

1. **AG-UI direction (A§5.10).** The skeleton maps the page context to `STATE_SNAPSHOT` with
   `STATE_DELTA` changes. Those are events the agent streams to the client; the client's facts
   reach the agent in `RunAgentInput` (`context`, `state`, `tools`) when a run starts. Followed
   where it binds (nothing ships now; the snapshot is the one serialisation); §9.7 records the
   correct directions for the future adapter and keeps agent state deltas off the page.
   Evidence: AG-UI events and `RunAgentInput` types (section 13).
2. **`/support` in the on-demand worker group (A§6.6).** Its features matter most when things
   fail, including offline or right after a broken deploy, and it weighs ~25 KB against a 1.5 MB
   shell group. Alternative: prefetch it. Followed: on demand, with Copy diagnostics in the
   primary and an offline notice in the panel (§8.4).
3. **The request log needs a begin hook (A§5.9, N24 §10.3 step 5).** One record after the
   response cannot show a hanging call, which is the slow case the brief cares about. Changed:
   `begin`/`end` and a `pending` outcome (§8.1); request 1 to 0024.
4. **0017 allows one blob property per kind (A§6.2 "dump and screenshot blob refs").** Followed
   the single kind `support-bundle` by adding the child table `core.SupportRequestFiles` (§12.3).
5. **`TmApi` has no upload (A§5.3).** Support, and every details page with an image or
   attachment, needs one; request 2 to 0024.
6. **"Adds to the current context" (A§5.10 `TmPageActions`).** An action registered from a dialog
   would land on the page beneath. Changed: the nearest page scope wins, root falls back to
   `current` (§9.4).
7. **Interface completions others consume (A§5.9, §5.10, §6.1):** `TmPageContext.status` and
   `overlay`; `TmPageAction.group`, `order`, `confirm`, `descriptionKey`; `TmFormContext.dirty`,
   `assisted` and a boolean `propose`; `TmErrorRecord.source`, `fingerprint`, `repeats`;
   `ClientTelemetryBatch.SentAt`; new primary services `TmAppVersion` and `TmSupport`. 0030,
   0031, 0034 and 0035 must build against these.
8. **"Every item carries … the last trace ids" (A§10.1 Observability Q1).** Only error items carry
   the last three; request-linked items carry their own; the rest none (volume).
