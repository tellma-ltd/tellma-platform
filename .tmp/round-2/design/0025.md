## 2. Decisions

1. **One database `tm-app`, one object store, compound key `[p, n]`, user partitions prefixed
   `u:<sub>/`** (§2.2): any user, tenant, session or "every other user" is one key-range delete in
   an open connection. Alt: a database per user (`deleteDatabase` blocks on open tabs); a store
   per partition (a schema upgrade per tenant).
2. **Documents are whole JSON values with a client format version and `savedAt`** (§2.3). Alt:
   normalized rows (nothing queries them).
3. **The store holds server truth only;** unconfirmed preference values live in memory overlays
   (§9.3). Alt: store the bag overlaid with unflushed keys (a crash leaves unsent values shared).
4. **Held tags are keyed by tag name, not document** (§4.2). Alt: by document (`me` has two tags).
5. **`client/sync` is one `Read` batch: the connect prologue plus one bag select** (§5.1). Alt:
   `users/me` + `settings/client` + `settings/entity-tags` (three round trips, no tenant facts).
6. **The refresher queues on the sync lock and re-checks inside it** (§5.3). Alt: `ifAvailable`
   and wait for `store.changed` (lost wake-ups).
7. **A 100 ms settle window and a superseded-tag set** keep own writes and late responses from
   syncing (§5.3). Alt: call sites flag their own writes.
8. **User-addressed `cache.changed` events carry their value** (§4.4). Alt: name-only (a wasted
   sync per preference flush per browser).
9. **Every write of `settings`, `me`, `tenant` or `sync` runs under the sync lock** (§5.3). Alt:
   unordered writes (tag regressions, each repaired by one more sync).
10. **`prefs.changed` carries values** (§6.2). Alt: keys plus a shared pending document.
11. **`hub.status` carries the leader's visibility; disconnected leaders are stolen from only when
    hidden** (§7.3). Alt: the skeleton's rule (leadership ping-pongs between visible windows).
12. **A shared per-tenant `visible` lock gates degraded polling** (§7.4). Alt: bus heartbeats.
13. **`TmHub` runs its own reconnect loop** (§8.3), so waits can be cut short and failed starts
    share the schedule. Alt: `withAutomaticReconnect` (neither is possible).
14. **Hub traffic is background:** it never stamps activity or renews the session (E13, E16).
    Alt: as today (a forgotten tab keeps its session alive forever).
15. **Refused negotiates and `session.ended` go through a foreground `client/sync`** (§8.5), so
    `TmApi` stays the one HTTP classifier. Alt: synthetic `TmApiError`s built by the hub.
16. **Leader documents are a registry, `TM_LEADER_DOCUMENTS`, filled by 0028** (§8.6). Alt:
    0025 hard-codes 0021's and 0028's routes.
17. **The tenant shell supplies the `/realtime` loader (`TM_REALTIME`)** (§8.1), honouring A§2.2's
    import rule. Alt: a dynamic import from the primary (an entry-point cycle).
18. **Write-behind values carry an envelope `{ at, v }`** (§9.2), enabling eviction at the server's
    key cap. Alt: no eviction (columns stop persisting for heavy users).
19. **Page state is keyed by canonical path; a tenant's entries drop when its `permissions` or
    `settings` tag moves; hosts mark entries stale after writes** (§10). Alt: key by full URL.
20. **Recents hold pages, not records, keyed by tenant-relative path** (§13). Alt: by route
    template (stored reports collapse); include details pages (records flood ten slots).
21. **SignalR Q1: yes**, through the same refresher (note section 4).
22. **`settings/entity-tags` stays for API callers; the SPA no longer calls it** (review flag 9).
23. **No IndexedDB means memory-only mode**: every launch is cold, nothing breaks (§2.7).

## 3. Design (the future spec's sections)

### §1 Placement and vocabulary

- **Primary entry point `@tellma/core`** (eager): `TmClientStore`, `TmLaunchCache`,
  `TmCacheRefresher`, `TmTabBus`, `TmLeader`, `TmPreferences`, `tmPreferenceKey`, `TmPageState`,
  `TmDrafts`, `TmTreeExpansion`, `TmRecents`, the tokens `TM_REALTIME` and `TM_LEADER_DOCUMENTS`.
  Folder `client/projects/core/tellma-core/src/state/` (`store/`, `launch/`, `sync/`, `bus/`,
  `leader/`, `prefs/`, `memory/`). Budget share: ≤ 9 KB gzip of the primary's 30 KB.
- **`@tellma/core/realtime`** (lazy, leader tab only): `TmHub`, `TmHubHttpClient`. The only importer
  of `@microsoft/signalr` (pinned to the server's ASP.NET Core major). Budget 18 KB gzip with the
  library.
- **Server:** `ClientSyncService` in `Tellma.Core` (namespace `Tellma.Core.Client`, registered by
  `CoreFeature` through `contribution.ApiService<ClientSyncService>()`); its records in
  `Tellma.Core.Abstractions.Api`.
- **Testing:** `@tellma/core-testing` gains `provideTellmaStateTesting()` (in-memory store, fake bus,
  fake locks, `TmFakeHub`), and its `/e2e` helpers gain `hubEvents(page)`, `freezeTab(page)`,
  `countRequests(route)`.
- **Vocabulary**
  - *Partition* — one user's, tenant's or session's slice of the store (§2.2).
  - *Document* — one named value in a partition (`settings`, `me`, `entity:gl.Center`).
  - *Launch documents* — the tenant-partition documents the chrome renders from (§3.1).
  - *Held tag* — the wire tag a tab's stored document was fetched under (§4.2).
  - *Sync* — one `client/sync` call and the store writes it causes.
  - *Leader* — the tab holding a tenant's hub lock; every other tab of that tenant is a *follower*.
  - *Leader document* — a document only the leader refreshes (`inbox`, `assignments`).
  - *Degraded mode* — realtime disabled, or the hub not connected for over 60 s: the leader polls.
  - *Curated* / *write-behind* — the two preference kinds of 0014 §3.4.
  - *Overlay* — preference values a tab shows before the server confirms them (§9.3).

### §2 The client store

The store is the only owner of IndexedDB and the boot record. It decides where every cached value
lives, when a stored value counts as absent, and who may write it.

#### §2.1 Contract

```ts
type TmPartition =                                            // A§5.5
  | { kind: 'device' }
  | { kind: 'user'; sub: string }
  | { kind: 'tenant'; sub: string; tenantId: number }
  | { kind: 'session'; sub: string; sessionHandle: string };
interface TmStoredDoc<T> { readonly tag: string | null; readonly savedAt: number; readonly formatVersion: number; readonly data: T }
type TmSweepRule =
  | 'session-ended'                                           // every user partition, plus CacheStorage tm-images-v1
  | 'other-users'                                             // every user partition but the profile's sub
  | { sessionOtherThan: string }                              // the profile user's other sessions
  | { tenant: number };                                       // one tenant partition of the profile user (tenant-not-found)
declare class TmClientStore {
  readAll(partition: TmPartition): Promise<ReadonlyMap<string, TmStoredDoc<unknown>>>; // one readonly transaction; fills the mirror
  doc<T>(partition: TmPartition, name: string): Signal<TmStoredDoc<T> | undefined>;   // the mirror; live across tabs
  put<T>(partition: TmPartition, name: string, doc: TmStoredDoc<T>): Promise<void>;    // guarded (§2.5); posts store.changed
  patch<T>(partition: TmPartition, name: string, update: (current: T | undefined) => T | undefined): Promise<void>; // read-modify-write in one transaction
  sweep(rule: TmSweepRule): Promise<void>;
  readonly mode: 'indexeddb' | 'memory';
  readonly boot: {
    read(): TmBootRecord;                                     // synchronous; defaults when absent or invalid
    patch(delta: Partial<Omit<TmBootRecord, 'v'>>): void;     // the app's only writer of tm.boot
    readonly changes: Observable<TmBootRecord>;               // another tab's write (the storage event)
  };
}
interface TmBootRecord {                                      // A§5.5, localStorage 'tm.boot'
  v: 1; theme: 'system' | 'light' | 'dark'; lang: string; dir: 'ltr' | 'rtl';
  sub: string | null; lastTenantId: number | null;
}
```

- **`patch`** exists for adoption writes (§9.5) and the refresher's merges: the update runs inside
  one `readwrite` transaction, so no other tab's write lands between the read and the write.
  Returning `undefined` deletes the document.
- **`doc()` mirror.** `readAll`, `put` and another tab's `store.changed` (one readonly re-read)
  fill an in-memory mirror whose signals `doc()` returns. A `put` updates the mirror synchronously,
  before its transaction commits (the settle check of §5.3 relies on it).
- **Boot-record writers** are A§5.5's list. `tm-boot.js` (0024 §4.2) is the only other reader and
  writer. `changes` lets 0024's theme glue follow a theme changed in another tab.

#### §2.2 Layout (frozen: `tm-boot.js` deletes by it)

| Item | Value |
|---|---|
| Database | `tm-app`, schema version `1` |
| Object store | `docs`, key path `['p', 'n']`, no indexes |
| Record | `{ p, n, tag, savedAt, formatVersion, data }` |
| Device partition key `p` | `device` |
| User partition | `u:<sub>/` |
| Tenant partition | `u:<sub>/t<tenantId>` (`u:0b4…/t17`) |
| Session partition | `u:<sub>/s<sessionHandle>` (`u:0b4…/sY4kQ1x…`) |

- **Key ranges.** One partition: `bound([p], [p, []])` (an array key sorts after every string).
  One user: `bound(['u:<sub>/'], ['u:<sub>/\uffff'])`. Every user: `bound(['u:'], ['u:\uffff'])`.
  "Every other user" is every user minus one user (two ranges). The `/` terminator keeps one
  `sub` from matching another that begins with it.
- **Opening.** `onupgradeneeded` creates `docs` when absent. A future schema version deletes and
  recreates it: the store is a cache. Every connection closes itself on `versionchange` and reopens
  on its next access, so 0010 Part D's `clearAll` (`deleteDatabase`) is never blocked for long.
- **`tm-boot.js`'s delete** opens `tm-app` without a version; when `onupgradeneeded` fires with
  `oldVersion = 0` (no database) it aborts the transaction, so the boot script never creates an
  empty database the app would then open without its store. It deletes the expired user's range
  and `tm-images-v1`, time-boxed to 1 s (0024 §4.2).
- **Writes** use `durability: 'relaxed'` (the default since Chrome 121, explicit for the others).

#### §2.3 Documents

| Document | Partition | `tag` | Written by | Refreshed |
|---|---|---|---|---|
| `tenants` | user | null | `TmLaunchCache` from `GET /bff/user` | stale-while-revalidate: on a tenantless route, at the launch redirect (0024 §9.3), once per launch at idle |
| `distribution` | user | null | `TmLaunchCache` from `GET /api/distribution-info` | stale-while-revalidate, once per launch at idle |
| `settings` | tenant | `settings` wire tag | the refresher | §5 |
| `me` | tenant | null (the held tags are `PreferencesTag` and `Access.Tag` inside, §4.2) | the refresher; preference and locale adoptions | §5, §9.5 |
| `tenant` | tenant | null | the refresher (every sync) | every sync |
| `sync` | tenant | null | the refresher | every sync |
| `inbox`, `assignments` | tenant | null | the leader | leader-document events (§8.6) |
| `entity:<Name>` | tenant | `entity:<Name>` wire tag | `TmLaunchCache` from `{segment}/all` | lazily when stale (§3.3) |
| `tree:<path>` | session | null | `TmTreeExpansion` | §12 |

```ts
interface TmSyncDoc {                                         // internal; the refresher's bookkeeping
  readonly at: number;                                        // last successful sync (ms)
  readonly entities: string;                                  // the held `entities` composite
  readonly entityTags: Readonly<Record<string, string>>;      // entity name → current wire tag, from the last sync that sent them
}
```

- **The device partition is empty in this release.** It is reserved for documents that carry no
  user data and survive sign-out.
- **Page data is never written to disk** (A§5.5); the only rows on disk are cacheable lists.

#### §2.4 When a stored document counts as absent

- **Format.** Every document name has a client format constant (`TM_DOC_FORMATS`, all `1`), bumped
  whenever the shape the client stores changes, including a server `FormatVersion` bump the code
  adopts. A document with another `formatVersion` is absent; a new bundle ignores old formats
  (A§7.5).
- **Idle window.** A document whose `savedAt` is more than 7 days old is absent. `savedAt` means
  "last written or last confirmed current": a sync that confirms a document unchanged re-puts it
  with a new `savedAt` when the stored one is over 24 hours old (one write per document per day).
- **Housekeeping** at idle after first render deletes absent documents of the profile user and
  tenant partitions untouched for 30 days.

#### §2.5 The write guard

- **`put` and `patch` refuse** (reject with `TmStoreRefusedError`, no write, telemetry
  `tm.store.refused`) when any of these holds:
  - the partition is not the device partition and its `sub` is not `TmSession.profile().sub`;
  - `TmSession.check()` is not `same` (the cookie changed or vanished under the tab);
  - `TmSession.state()` is not `active` (signing out or expired).
- **Why:** a response checked by `TmApi` (0024 §10.3) can still be applied after the cookie
  changed; the guard is the last line that keeps one user's data out of another's partition.

#### §2.6 Sweeps

| Rule | Deletes | Run by |
|---|---|---|
| `session-ended` | every user partition; CacheStorage `tm-images-v1` | 0024 §8.4 step 6, §8.5, §8.6 step 2 |
| `other-users` | every user partition except the profile user's | the store's boot step 2 below |
| `{ sessionOtherThan: sh }` | the profile user's session partitions except `s<sh>` | at idle after first render |
| `{ tenant: t }` | `u:<sub>/t<t>` | 0024's `tenant-not-found` presentation (0024 request 4) |

**The store's boot step** (0024 §4.3 initializer):

1. Open `tm-app`. Read `boot.sub` (B) and the profile's `sub` (P).
2. `B === null` → sweep every user partition (the backstop for `tm-boot.js`'s time-boxed delete,
   0024 request 3). `tm-boot.js` already resets a record whose `sub` differs to `sub: null`
   (0024 §4.2), so `B !== P` → `other-users` is a second backstop. Either sweep is a `readwrite`
   transaction before the read below; both happen only on cold launches.
3. On a tenant path, `readAll(tenant P, t)`: one `readonly` transaction (the warm path's only
   store access).
4. `TmSession` then writes `boot.patch({ sub: P })` (0024 §8.1).

Sweeps never touch `sessionStorage`: drafts survive the expiry path (A§5.5). `tm.boot`'s user
fields are cleared by their callers (0024 §8.4 step 6).

#### §2.7 Persistence, quota and fallback

- **`navigator.storage.persist()`** is requested once, after the first successful tenant-partition
  write, only on Chromium and WebKit, where it never prompts; never on Gecko, which prompts.
- **Quota.** A `QuotaExceededError` deletes the profile user's `entity:*` lists of other tenants,
  oldest `savedAt` first, and retries once; a second failure keeps the value in the mirror only
  (telemetry `tm.store.quota`).
- **Memory mode.** When `indexedDB.open` fails (blocked storage, a private mode without
  IndexedDB), `mode` is `memory`: the mirror works for this tab, nothing persists, every launch is
  cold, and `store.changed` still syncs the mirrors of the tab's peers. When `localStorage`
  throws, the boot record lives in memory.

### §3 Launch documents and `TmLaunchCache`

The launch documents are what the chrome renders from on a warm launch. `TmLaunchCache` exposes
them for the tenant the routed page shows and decides whether a launch is warm.

#### §3.1 Contract

```ts
interface TmLaunchDocs {                                      // A§5.7
  settings: TenantSettingsForClient;                          // 0013 §5.6
  me: MeResult;                                               // 0016 §3.4; Access.Tag = the composite permissions tag
  tenant: TmTenantFacts;
  inbox?: InboxSummary;                                       // leader document (0021 §5.2, registered by 0028)
  assignments?: AssignmentsSummary;                           // leader document (0028)
}
interface TmTenantFacts {                                     // ClientSyncResult.Tenant + Realtime
  readonly id: number; readonly category: 'Live' | 'Sandbox'; readonly state: 'Active' | 'ReadOnly';
  readonly liveTenantId?: number; readonly realtime: boolean;
}
interface TmCachedEntitySet<T = TmJson> { readonly items: readonly T[]; readonly byId: ReadonlyMap<number, T>; readonly stale: boolean }
declare class TmLaunchCache {
  readonly docs: { readonly [K in keyof TmLaunchDocs]-?: Signal<TmLaunchDocs[K] | undefined> }; // current tenant
  readonly warm: Signal<boolean>;                             // settings, me and tenant present (§2.4)
  entitySet<T = TmJson>(entity: string): Signal<TmCachedEntitySet<T> | undefined>; // starts a lazy load when absent or stale
  readonly tenants: Signal<readonly TmMembership[] | undefined>;  // user partition, /bff/user (0011 §5.5 shape)
  readonly distribution: Signal<TmDistributionInfo | undefined>;  // user partition, /api/distribution-info (0011 §5.9 shape)
  revalidateUser(): Promise<void>;                            // refetch tenants and distribution
}
```

- **`state` is `Active` or `ReadOnly` only.** A `Suspended` tenant answers `403 tenant-suspended`
  and a `Provisioning` or `Retired` one `404 tenant-not-found` (0011 §3.3), so the sync never
  stores them.
- **Tenant switch inside the app** (`/17/…` → `/22/…`) is not a launch: `TmLaunchCache` runs
  `readAll` for tenant 22 and, when not warm, a cold sync (§3.2).

#### §3.2 Cold and warm entry

| Entering tenant `t` | What happens |
|---|---|
| warm | the chrome renders from the documents; no sync is awaited; the leader's sync on election (§7.2) and the page data's header (§4.3) revalidate |
| cold (any of the three absent) | `refresh(t, ['settings', 'me', 'tenant'])` in the foreground (§5.3) starts with the page data request (A§7.1 step 5); the shell shows final-geometry skeletons until it writes the documents |
| cold, the sync fails `offline` or `unavailable` | the tenant shell shows its error state with Retry (0027); a retry reruns the sync |
| cold, the sync fails `tenant-not-found` / `tenant-unavailable` | 0024's presentation (picker with notice / tenant-state page) |

**Example —** Farah opens `/17/centers` on Monday after using tenant 17 on Friday:

1. `tm-boot.js` sees her cookie and `tm.boot.sub`; the worker serves every chunk.
2. The store's boot step reads tenant 17's partition in one transaction: `settings`, `me`,
   `tenant`, `inbox`, `assignments`, two cacheable lists.
3. The shell renders the app bar, badges and pinned bar; the search host renders title, toolbar
   and columns from the `search.gl.Center.columns` preference; rows show their loading state.
4. `centers/query` starts. Its response header carries tags equal to the held ones: no sync.
5. Tab elected leader (no other tab is open): `client/sync` confirms the documents, the hub
   connects, `inbox/summary` and `assignments/summary` refresh the badges.

#### §3.3 Cacheable entity lists

- **`entitySet(name)`** returns the list's signal and, when the document is absent or stale, starts
  one load (single flight per name per tab):
  1. Read `sync.entityTags[name]`; when missing, run a sync first (it sends every tag, §5.1).
  2. `TmApi.read('{segment}/all', {}, { signal, background: true })` (0016 §2.3; the server returns
     every scalar of the cached probe, 0013 §4.4).
  3. `put` `entity:<name>` with the tag from step 1. A list that changed between steps 1 and 2 is
     stored under an older tag than its rows; the next sync reports it stale again (convergent, the
     rule of 0013 §2.5).
- **Stale lists keep serving** (`stale: true`) until the reload lands: reference data on screen
  never blanks. A `403` stores nothing and the signal stays `undefined`.
- **Staleness arrives two ways:** a sync's `StaleEntities`, or a valued `cache.changed
  { tag: 'entity:<Name>', value }` (§4.4), which updates `sync.entityTags` and marks the list stale
  with no sync at all.

### §4 Version tags on the client

The client holds a wire tag for each cached document and compares it with every tag the server
reports, from response headers and hub events. A mismatch is the only trigger of a refresh.

#### §4.1 The tags

| Tag | Wire form | Covers |
|---|---|---|
| `settings` | `{TenantSettingsForClient.FormatVersion}.{settings:N}` | `settings` |
| `preferences` | the user's `PreferencesTag` wire (0013 §2.7) | `me`'s profile and bag |
| `permissions` | **composite:** `{UserAccess.FormatVersion}.{tenantPermissions:N}{userPermissions:N}` | `me.Access` |
| `entities` | `{CachedEntitySet.FormatVersion}.{entities:N}` | "some cacheable list changed" |
| `entity:<Name>` | `{CachedEntitySet.FormatVersion}.{entity:<Name>:N}` | one cacheable list |

**Example —** `permissions=1.3f2a9c1d0e7b4a5f8c6d2e1f0a9b8c7dd41e7a0b3c9f4e2d8a6b5c1f0e3d7a92` is
the tenant tag `3f2a…8c7d` followed by Farah's user tag `d41e…7a92`. A role edit changes the first
half for everyone; a change to Farah's memberships changes the second half for Farah only (0013
§2.1's two levels). The composite reaches the header, `MeResult.Tags` and `AccessSummary.Tag`
(edits E3, E8, E10).

#### §4.2 What a tab holds

| Held tag | Read from |
|---|---|
| `settings` | the `settings` document's `tag` |
| `preferences` | `me.data.PreferencesTag` |
| `permissions` | `me.data.Access.Tag` |
| `entities` | `sync.entities` |
| `entity:<Name>` | the `entity:<Name>` document's `tag`, only for lists held |

`me.data.Tags` is never a source: its `settings` and `entities` members may be newer than the
documents this tab holds.

#### §4.3 Response headers

- `TmApi` calls `TmCacheRefresher.observe(t, tags)` with `Tellma-Version-Tags` of every checked
  tenant response (0024 §10.3 step 5).
- **An absent member is no information.** The header omits `preferences` and `permissions` on a
  response whose last batch carried no connect prologue (edit E10).
- **No jitter** applies: only the tab that made the request sees the header.

#### §4.4 `cache.changed` over the hub

The leader handles the event; followers never fetch on it (SignalR Q1). Payload `{ tag, value? }`
(edit E14).

| Event | Recipients | Leader action |
|---|---|---|
| `{ tag: 'settings', value }` | tenant group | after 0–3 s jitter, `observe(t, { settings: value })` |
| `{ tag: 'entity:<Name>', value }` | tenant group | `sync.entityTags[Name] = value`; the held list (if any) is marked stale; no sync |
| `{ tag: 'permissions' }` (role or permission edit, language change) | tenant group | after 0–10 s jitter, `refresh(t, ['me'])` |
| `{ tag: 'preferences' }` (`settings/refresh-caches`) | tenant group | after 0–10 s jitter, `refresh(t, ['me'])` |
| `{ tag: 'permissions', value }` (this user's memberships) | that user | `observe(t, { permissions: value })` |
| `{ tag: 'preferences', value }` (this user's profile, bag, notification preferences) | that user | `observe(t, { preferences: value })` |

- **Valued events refresh only on a mismatch,** so the tab that wrote a preference (and adopted the
  result, §9.5) and a tab that already synced from a header both do nothing.
- **Jitter only for tenant-group events,** which reach every browser of the tenant at once.
- **Unknown tags are ignored** (forward compatibility with packs' tag names).

### §5 `client/sync` and `TmCacheRefresher`

`client/sync` revalidates every launch document of one tenant in one round trip, answering only
what changed. `TmCacheRefresher` is the one client path that calls it: headers, events, cold
entry and the leader all go through it, and one browser runs at most one sync per tenant at a time.

#### §5.1 Server contract

```csharp
// Tellma.Core.Client (runtime); [ApiRoute("client")], registered by CoreFeature
public sealed class ClientSyncService
{
    // MemberOnly, Idempotent, Mutation = false; NoActivityStampMetadata (0016 §4.3); a retried read (0016 §2.2)
    [ApiAction("sync", MemberOnly = true, Idempotent = true, Mutation = false)]
    public Task<ClientSyncResult> SyncAsync(ClientSyncRequest request);
}

// Tellma.Core.Abstractions.Api
public sealed record ClientSyncRequest(IReadOnlyDictionary<string, string> Held); // tag name → wire tag held; empty = cold; ≤ 1 + 4 + cacheable entities entries
public sealed record ClientSyncResult(
    TenantFacts Tenant,                            // always
    bool Realtime,                                 // TellmaRealtimeOptions.Enabled: the hub is mapped
    IReadOnlyDictionary<string, string> Tags,      // always the four; entity:<Name> for every cacheable entity when Held["entities"] differs or is absent
    TenantSettingsForClient? Settings,             // only when Held["settings"] differs; written from the cache's pre-serialized bytes
    MeResult? Me,                                  // only when Held["preferences"] or Held["permissions"] differs
    IReadOnlyList<string> StaleEntities);          // held entity:<Name> tags that differ (names, without the prefix)
public sealed record TenantFacts(int Id, TenantCategory Category, TenantState State, int? LiveTenantId); // A§6.1
```

- **The batch.** One `IGuardedBatchRunner.RunAsync(BatchPurpose.Read, …)`:
  - the connect prologue (0014 §7.3): tenant tags, the caller's two user tags, permission rows
    and profile only when stale, settings only when stale or cold (0013 §5.7);
  - one statement: `SELECT [Key], [Value] FROM [core].[UserPreferences] WHERE [UserId] =
    @tm_UserId;` — a primary-key range of at most `MaxPreferenceKeys` rows, read unconditionally
    because the need for `Me` is known only after the prologue.
- **In memory after the round trip:** `TenantSettingsForClient` bytes from
  `ITenantSettingsCache.GetForClientAsync()`; entity tags from
  `ICacheableEntities.GetWireTagsAsync()` (the snapshot the prelude just refreshed);
  `AccessSummary` from `IAccessEvaluator.EvaluateAllAsync()`; `TenantFacts` from
  `RequestContext.Tenant`. `MeResult` is composed exactly as 0018 §3.5's `Me` composes it.
- **Round trips:** 1 on a warm instance; +1 cold, per 0013 §2.10 and 0014 §7.5.
- **Comparison** is ordinal equality of wire strings; an unknown `Held` name is ignored.
- **0016 §3.10 fingerprints** cover the route like any projected endpoint.

#### §5.3 `TmCacheRefresher`

```ts
declare class TmCacheRefresher {                              // A§5.7
  observe(tenantId: number, tags: Readonly<Record<string, string>>): void; // headers and valued events
  refresh(tenantId: number, docs: readonly string[]): Promise<void>;       // forced: cold entry, name-only events, the leader
  readonly lastSyncAt: Signal<number | null>;                 // current tenant; the bell's "last refreshed" and the dump
}
```

**`observe(t, tags)`**

1. For each of `settings`, `preferences`, `permissions`, `entities` in `tags`: skip when equal to
   the held tag, or when the value is in the tag's *superseded set* (values this browser replaced
   in the last 60 s, so a response that left the server before the last sync never triggers
   another). Otherwise record it as *wanted*.
2. An `entity:<Name>` member (events only) updates `sync.entityTags` and marks the list stale
   (§3.3).
3. When anything is wanted, wait the **settle window** (100 ms), then re-compare against the mirror.
   A tab's own write adopts its result within that window (§9.5), so its own header never syncs.
4. Still wanted → `refresh(t, docs)`.

**`refresh(t, docs)`**

1. **Coalesce in the tab:** a pending refresh of `t` absorbs this one (one promise).
2. **Queue on the lock** `tm:<slug>:<sub>:<t>:sync` (exclusive, queued; never `ifAvailable`).
3. **Inside the lock, re-check** against a fresh read of `settings`, `me` and `sync`: an observed
   trigger whose wanted tags are now all held, or a forced trigger older than `sync.at`, ends here
   (another tab synced meanwhile).
4. **Throttle:** when `now − sync.at < 2 s`, wait the remainder, still inside the lock. Triggers
   arriving meanwhile join this run.
5. **Call** `TmApi.read('client/sync', { held }, { signal, background })` with every held tag.
   `background` is false only for cold entry (§3.2). The signal aborts when the tab leaves the
   tenant or is hidden for good (`pagehide`).
6. **Apply** in one `readwrite` transaction: `settings`, `me`, `tenant` (with `realtime`), `sync`
   (`at`, `entities`, `entityTags`), stale flags on held lists, the daily `savedAt` confirmations
   (§2.4). Record replaced tags in the superseded sets. Post one `store.changed`.
7. **Errors.** `tenant-not-found` and `tenant-unavailable` are presented through `TmErrorPresenter`
   even when background: the refresher is the tenant's authority. `unauthenticated` and
   `client-outdated` are `TmApi`'s (0024 §10). Anything else is telemetry only; the next trigger
   retries.

- **Every write of `settings`, `me`, `tenant` or `sync` runs under this lock**, including §9.5's
  adoptions, so no write interleaves with a sync (decision 9).
- **Cost bound:** at most one sync per tenant per browser per 2 s; one follow-up queues while one
  runs.

**Example —** three tabs on tenant 17; an admin changes Farah's pins (A§7.3):

1. The leader receives `cache.changed { tag: 'preferences', value: '1.c9d0…' }` and calls
   `observe(17, { preferences: '1.c9d0…' })`; tab B's `centers/query` header carries the same
   value 400 ms later.
2. The leader takes the lock and syncs; the result carries only `Me`; the store writes `me`.
3. Tab B's refresh queued behind the lock, re-checks inside it, finds `1.c9d0…` held, and returns.
4. All three pinned bars re-render from the `store.changed`. Total: one `client/sync`.

### §6 The tab bus

The tab bus carries every cross-tab message of the app over two `BroadcastChannel`s. It knows
nothing of what the messages mean; their owners (this spec, 0024) do.

#### §6.1 Contract and channels

```ts
declare class TmTabBus {                                      // A§5.6
  readonly tabId: string;                                     // crypto.randomUUID() per document load; never persisted
  post(message: TmBusMessage): void;                          // to every other tab; never echoed to this tab
  readonly messages: Observable<TmBusMessage>;                // from other tabs only
}
interface TmBusEnvelope { readonly v: 1; readonly from: string; readonly message: TmBusMessage } // the posted value
```

| Channel | Name | Carries |
|---|---|---|
| device | `tm:<slug>` | `session.*` (every user of the browser hears a sign-in or sign-out) |
| user | `tm:<slug>:<sub>` | everything else |

- **The bus picks the channel by message type.** The user channel opens when the profile is known
  and is replaced on a changed user.
- **Versioning.** A tab ignores an envelope whose `v` it does not know and a `type` it does not
  know, so an old tab and a new tab coexist after a deployment. A breaking change bumps `v` and
  suffixes channel and lock names with `.v<n>`; tabs of two versions then elect two leaders until
  the old ones reload (A§7.5's banner).
- **bfcache.** A page in the back-forward cache that receives a channel message is evicted, so the
  bus closes both channels on `pagehide` with `persisted` and reopens them on `pageshow`; the
  store then re-reads every mirrored document (it may have missed `store.changed`).
- **Frozen pages** (Page Lifecycle `freeze`) keep their channels; their handlers run on `resume`.

#### §6.2 Message catalogue

| Message | Channel | Posted by | Handled by |
|---|---|---|---|
| `store.changed { partition, names }` | user | `TmClientStore` after every committed `put`, `patch` or partition sweep | every tab's store: re-read the names into the mirror |
| `hub.event { tenantId, event }` | user | the leader, for every hub event (§8.4) | `TmLeader.events()` in every tab of that tenant |
| `hub.status { tenantId, status, since, leaderVisible }` | user | the leader, on change, on its own visibility change, and answering a probe | `TmLeader.hubStatus` in followers; the steal rules (§7.3) |
| `leader.probe { tenantId }` | user | a follower at start and whenever it becomes visible | the leader: answer with `hub.status`; in degraded mode, poll when the last poll is over 60 s old |
| `prefs.changed { tenantId, values, at }` | user | `TmPreferences.set` (§9.3) | `TmPreferences`: foreign overlay |
| `drafts.query { replyTo }` / `drafts.reply { replyTo, dirty }` | user | 0024 §8.4 step 2 / every tab | sign-out confirmation |
| `session.signing-out \| signed-out \| expired \| started \| changed { sub }` | device | 0024 §8 | 0024 §8 |

```ts
type TmBusMessage =                                           // A§5.6, completed (challenges 2 and 3)
  | { type: 'store.changed'; partition: string; names: readonly string[] }
  | { type: 'hub.event'; tenantId: number; event: TmClientEvent }
  | { type: 'hub.status'; tenantId: number; status: TmHubState; since: number; leaderVisible: boolean }
  | { type: 'leader.probe'; tenantId: number }
  | { type: 'prefs.changed'; tenantId: number; values: Readonly<Record<string, string | null>>; at: number } // raw stored value; null = deleted
  | { type: 'drafts.query'; replyTo: string } | { type: 'drafts.reply'; replyTo: string; dirty: number }
  | { type: 'session.signing-out' | 'session.signed-out' | 'session.expired' | 'session.started' | 'session.changed'; sub: string };
```

- `prefs.changed`'s `values` replace A§5.6's `keys`; `hub.event` stays ≤ 4 KB (0021's cap).

### §7 Leader election

One tab per browser per tenant holds the hub lock and so the realtime connection. The election
needs no timers in the healthy case: Web Locks hand the lock to the next tab when the leader goes
away, and followers check on the leader only when they start or become visible.

#### §7.1 Contract

```ts
type TmHubState = 'connecting' | 'connected' | 'reconnecting' | 'offline' | 'disabled'; // disabled: realtime off on this deployment
interface TmHubStatus { readonly state: TmHubState; readonly since: number; readonly leaderVisible: boolean }
interface TmClientEvent { readonly name: string; readonly tenantId: number; readonly payload: TmJson | null } // 0021's ClientEventEnvelope
declare class TmLeader {                                      // A§5.6
  readonly isLeader: Signal<boolean>;                         // for the tenant this tab shows
  readonly hubStatus: Signal<TmHubStatus>;                    // the leader's, mirrored; { connecting, now, true } until the first status
  events(name: string): Observable<TmClientEvent>;            // hub events of this tab's tenant, in every tab
}
```

| Lock | Mode | Held by |
|---|---|---|
| `tm:<slug>:<sub>:<t>:hub` | exclusive | the leader of tenant `t`; followers queue on it |
| `tm:<slug>:<sub>:<t>:sync` | exclusive | the tab running a sync or an adoption write (§5.3) |
| `tm:<slug>:<sub>:<t>:visible` | shared | every tab of tenant `t` while `document.visibilityState === 'visible'` |

#### §7.2 Lifecycle in one tab

1. **Enter.** When the tenant shell is active for `t` and `TmSession.state()` is `active`, the tab
   requests the hub lock with an `AbortSignal` and holds it until released; it posts
   `leader.probe` and waits for `hub.status`.
2. **Granted.** `isLeader` turns true; the leader posts `hub.status { connecting }`, calls
   `refresh(t, ['tenant'])` (the warm launch's revalidation), refreshes the leader documents
   (§8.6), then, unless `tenant.realtime` is false (state `disabled`, polling, §8.7), loads
   `/realtime` through `TM_REALTIME` and connects.
3. **Release** on: leaving the tenant (switch or tenantless route), `pagehide`, `freeze`, a session
   state other than `active`, or being stolen. Stolen means the lock's promise rejects with
   `AbortError`; the old leader then stops its connection at once (it can no longer assume it is
   the only one). On release the tab stops its hub (`await connection.stop()`), then re-queues as
   a follower unless it is leaving the tenant.
4. **Return.** `pageshow` with `persisted` and `resume` re-run step 1.
5. **Queued requests** are aborted on `pagehide` too, so a pending lock request never holds a page
   out of the back-forward cache.

- **Failover is free:** a closed, crashed or discarded leader's lock is released by the browser and
  the next queued tab is granted it (A§7.8).
- **Nothing moves on tab switches:** a healthy hidden leader keeps the connection (A§7.8, with
  0021's 150 s client timeout, edit E15).

#### §7.3 Probing and stealing

A follower never times the leader in the background. It checks at two moments only: when it
starts and whenever it becomes visible.

1. Post `leader.probe { t }`; note the hub lock's holder `clientId` from `navigator.locks.query()`.
2. **Hung leader.** No `hub.status` within 5 s, the lock still held → candidate.
3. **Disconnected hidden leader.** The last `hub.status` has `state` `connecting`, `reconnecting`
   or `offline`, `since` over 30 s ago, and `leaderVisible: false` → candidate. A visible leader
   is never stolen from for being disconnected (its backoff already runs unthrottled), and a
   `disabled` leader never (there is nothing to connect).
4. **Steal** only while visible: wait a 0–2 s jitter, re-query the locks; when the holder's
   `clientId` is unchanged and the condition still holds, request with `{ steal: true }`. A changed
   holder means another follower stole first: re-probe instead.
5. Hidden followers never steal.

#### §7.4 The visibility lock

- Every tab of tenant `t` holds `…:<t>:visible` in `shared` mode while visible and releases it when
  hidden, on `pagehide` and on `freeze`.
- The leader reads `navigator.locks.query()` before each degraded poll (§8.7): any held `visible`
  lock of `t`, or its own visibility, means a user is looking, so it polls. With every tab hidden it
  skips the poll; the next `leader.probe` (a tab becoming visible) triggers one.

### §8 `TmHub` and the realtime connection

`TmHub` is the leader's SignalR connection to `/{t}/hub`. It checks the session before every
negotiate, retries forever on transient failures, relays every event to all tabs, and turns the
hub's terminal signals into 0024's standard paths.

#### §8.1 Loading

```ts
// @tellma/core (primary)
interface TmHubFactory { create(tenantId: number, sink: TmHubSink, injector: Injector): TmHubConnection } // injector: TmSession, TmApi
interface TmHubSink {
  event(event: TmClientEvent): void;                          // every received event
  state(state: TmHubState): void;
  connected(): void;                                          // after every successful (re)connect
  refused(status: 401 | 403 | 404): void;                     // a terminal negotiate verdict
  ended(reason: 'session-terminated' | 'access-revoked' | 'tenant-unavailable'): void;
}
interface TmHubConnection { start(): void; stop(): Promise<void>; nudge(): void } // nudge: cut the current wait short
declare const TM_REALTIME: InjectionToken<() => Promise<TmHubFactory>>;

// @tellma/core/realtime
declare class TmHub implements TmHubConnection { constructor(tenantId: number, sink: TmHubSink, injector: Injector) }
declare const tmHubFactory: TmHubFactory;
```

- **The tenant shell provides `TM_REALTIME`** in its route providers:
  `() => import('@tellma/core/realtime').then(m => m.tmHubFactory)` (request to 0027). The primary
  never imports `/realtime` (A§2.2), and `/realtime` imports only the primary.
- **`@microsoft/signalr` loads only in the leader tab, after first render** (A§2.2).
- `/realtime` is not for application code (its API golden marks it platform-internal).

#### §8.2 The connection

```ts
const connection = new HubConnectionBuilder()
  .withUrl(`/${tenantId}/hub`, { httpClient: new TmHubHttpClient(session), withCredentials: true })
  .configureLogging(tmHubLogger)                             // warnings and errors to TmTelemetry, no message content
  .build();                                                  // JSON protocol; no withAutomaticReconnect (§8.3)
connection.serverTimeoutInMilliseconds = 30_000;             // a hidden page still receives the 15 s pings
connection.keepAliveIntervalInMilliseconds = 15_000;         // throttled to ~1/min when hidden: covered by 150 s (E15)
connection.on('event', (e: { name: string; tenantId: number; payload: unknown }) => /* §8.4 */);
connection.onclose(error => /* §8.3 */);
```

- **`TmHubHttpClient`** extends the library's `DefaultHttpClient`; its `send` first runs
  `TmSession.check()` (A§5.3's "`TmHub` runs the same check before every negotiate"). `missing` or
  `changed` throws without sending and stops the loop; the leader then runs a foreground
  `client/sync`, whose own user check (0024 §10.3 step 1) runs 0024's expiry or changed-user
  path. Every reconnect negotiates, so the check runs before every connect.
- **Transports:** the library's default order (WebSockets, then Server-Sent Events, then long
  polling); Azure SignalR's negotiate redirect is followed. CSP `connect-src` already lists the
  Azure origins (0024 §6).
- **No custom headers** reach the WebSocket handshake, so the server treats every Hub-group request
  as background (edits E13, E16) instead of the client sending `Tellma-Activity`.
- **No stateful reconnect:** events are thin, and every reconnect syncs (§8.4), so nothing missed
  matters.

#### §8.3 Reconnect policy

| Attempt after a drop or a failed start | Delay |
|---|---|
| 1 | 0 s |
| 2, 3, 4 | 2 s, 10 s, 30 s |
| 5 onward | the previous delay doubled, capped at 5 min |

- **Jitter** ±20 % on every delay but the first. **Never gives up** on transient failures (network,
  `429`, `5xx`). The attempt counter resets after a connection that lasted 60 s.
- **A wait is cut short** (`nudge`) when `TmApi.online` turns true, when any tab of `t` becomes
  visible (a `leader.probe` arrives) and when this tab has just been elected.
- **While `TmApi.online` is false** the loop waits without attempting; `hub.status` is `offline`.
- **Terminal verdicts** stop the loop: a negotiate answering `401`, `403` or `404` (the
  `HttpError.statusCode`) calls `refused`, and a `session.ended` event calls `ended` (§8.5).
- **Hub loss is not connectivity loss:** no banner, only 0028's "Live updates paused" line while
  `state` is not `connected` (A§7.8).

#### §8.4 Event relay

For every `event` the leader receives:

1. Drop it when `tenantId` is not `t` (defensive) or `name` is not a registered client event
   (the metadata's `clientEvents`, 0024 §3.1).
2. Deliver it to this tab's `TmLeader.events()` subscribers and post `hub.event` (followers
   deliver it to theirs).
3. Act on it:

| Event | Leader action |
|---|---|
| `cache.changed` | §4.4 |
| an event a leader document lists (`inbox.changed`, `job.changed`, `assignments.changed`) | refresh that document (§8.6) |
| `session.ended` | §8.5 |
| any other | none (pages may react through `events()` in their own tab) |

On every successful (re)connect (`connected`): `refresh(t, ['tenant'])` and every leader document,
which catches up on whatever the gap missed (A§7.8).

- **Duplicates are harmless:** during a steal two leaders can relay one event twice; every
  consumer is idempotent (a refresh trigger), and 0028 decides toasts from document contents, not
  from events.

#### §8.5 Terminal signals

| Signal | Leader action | Result in every tab |
|---|---|---|
| `session.ended { session-terminated }` | post `session.signed-out { sub }` and run 0024 §8.5 locally | 0024 §8.5: sweep, delete the stale cookie, `/signed-out` |
| `session.ended { access-revoked }` or `{ tenant-unavailable }` | stop the hub; run a foreground `client/sync` | each tab of `t` that receives the relayed event also runs one (the one exception to "followers never fetch on hub events"; the event is rare); its `404 tenant-not-found` or `403 tenant-suspended` takes 0024's path (picker with notice; tenant-state page) |
| negotiate `401` | a foreground `client/sync` | `401 unauthenticated` → 0024 §8.6 |
| negotiate `403` / `404` | a foreground `client/sync` | as `access-revoked` above |

- **One classifier.** The hub never interprets HTTP outcomes beyond "terminal or not": `TmApi`'s
  verdict on the sync decides, so the presentation is exactly a page call's (decision 15). A sync
  that succeeds (a refusal that has since cleared) restarts the loop.

#### §8.6 Leader documents

```ts
interface TmLeaderDocument {
  readonly name: string;                                      // tenant-partition document name: 'inbox', 'assignments'
  readonly route: string;                                     // 'inbox/summary' (0021 §5.2), 'assignments/summary' (0028)
  readonly events: readonly string[];                         // ['inbox.changed', 'job.changed'], ['assignments.changed']
  readonly formatVersion: number;
}
declare const TM_LEADER_DOCUMENTS: InjectionToken<readonly TmLeaderDocument[]>; // multi; 0028 provides both
```

- **Refreshed by the leader only:** on election, on every (re)connect, on each listed event
  (coalesced over 250 ms; one in flight per document, one follow-up queued), and on every degraded
  poll. Through `TmApi.read(route, {}, { signal, background: true })` (the routes carry
  `NoActivityStampMetadata`), then `put`; every tab renders the badge from the store.
- **On a warm launch** the badges render from the stored documents before any call (A§7.2).
- **Followers never call these routes** on hub events (SignalR Q1). A page that opens a panel may
  read fresher data itself (0028's choice).

#### §8.7 Degraded mode: polling

- **Enters** when `tenant.realtime` is false (state `disabled`), or the hub has not been
  `connected` for 60 s.
- **Every 60 s** the leader polls, when §7.4 says a tab is visible: `refresh(t, ['tenant'])` and
  every leader document, all `background`.
- **Leaves** on `connected`. A `disabled` leader re-reads `tenant.realtime` after each sync; a
  deployment that turns realtime on is picked up within one poll.
- **Cost bound:** one sync and one call per leader document per minute per browser per tenant
  while someone looks; nothing while every tab is hidden.

### §9 Preferences

`TmPreferences` gives every page typed, per-tenant user preferences that apply at once, reach the
user's other tabs at once, and reach the server per the key's kind. The server bag (0014 §3.4)
stays an opaque string map; the client owns encoding, kinds and the flush policy.

#### §9.1 Contract

```ts
type TmPreferenceKind = 'curated' | 'write-behind';
interface TmPreferenceKey<T> {                               // A§5.7
  readonly key: string; readonly kind: TmPreferenceKind; readonly fallback: T;
  readonly validate?: (value: unknown) => value is T;        // a stored value failing it reads as the fallback
}
declare function tmPreferenceKey<T>(key: string, kind: TmPreferenceKind, fallback: T,
  validate?: (value: unknown) => value is T): TmPreferenceKey<T>;
declare class TmPreferences {                                 // the current tenant; tenantless pages have none
  get<T>(key: TmPreferenceKey<T>): Signal<T>;
  set<T>(key: TmPreferenceKey<T>, value: T): void;            // applied and broadcast at once; flushed per kind
  reset(key: TmPreferenceKey<unknown>): void;                 // deletes the key: get() returns the fallback
}
```

**Example —** a distribution's page remembers the bank account it last reconciled (three lines):

```ts
const lastAccount = tmPreferenceKey<number | null>('acme.bankReconciliation.account', 'write-behind', null);
// inside the page component
private readonly prefs = inject(TmPreferences);
readonly account = this.prefs.get(lastAccount);              // Signal<number | null>
pick(id: number) { this.prefs.set(lastAccount, id); }
```

- **Key grammar** is 0018 §3.5's, widened (edit E11). `tmPreferenceKey` checks it in development,
  and checks that the first segment is a platform segment (Appendix A) or a composed feature key
  (`acme`), so a distribution's keys never collide with the platform's.
- **`set` of a value deep-equal to the fallback deletes the key**, which keeps the bag small and
  lets a fallback that changes (a new column default) reach users who never customized.
- **Size.** A value whose stored form exceeds 32 KB (0014's `MaxPreferenceValueBytes`) is refused:
  development throws, production drops it with `tm.prefs.dropped { reason: 'too-large' }`.

#### §9.2 Encoding

| Kind | Stored string | Example |
|---|---|---|
| curated | `JSON.stringify(value)` | `nav.pinnedBarVisible` → `false` |
| write-behind | `JSON.stringify({ at, v: value })`, `at` in epoch seconds | `search.gl.Center.view` → `{"at":1792400000,"v":"tree"}` |

- **Why the envelope:** `at` lets the client evict the oldest write-behind keys when the server's
  key cap is reached (§9.5). Curated values stay plain JSON, so an administrator's tool writing
  `nav.pinned` through `users/preferences/set` (0018) needs no client convention.
- **Decoding** parses once per distinct stored string (memoized); invalid JSON, a missing
  envelope on a write-behind key, or a failed `validate` reads as the fallback and emits
  `tm.prefs.invalid { key family }`.

#### §9.3 Applying and broadcasting

What `get` returns, highest first:

1. **This tab's dirty value** for the key (set here, not yet confirmed by a flush result).
2. **The foreign overlay:** a value another tab set, received in `prefs.changed`.
3. **The stored bag:** `me.data.Preferences[key]` (server truth, §2.3).
4. **The fallback.**

- **`set`** updates the dirty map synchronously (the signal changes in the same frame: rule 2B),
  posts `prefs.changed { tenantId, values: { [key]: stored string | null }, at: Date.now() }`, and
  schedules the flush (§9.4).
- **Receiving `prefs.changed`:** each value enters the foreign overlay with its `at`. When this tab
  has a dirty value for the same key with an older `at`, the dirty value is dropped: the later
  intent wins and only its tab flushes it.
- **A foreign overlay entry ends** when the stored bag holds the same string (its writer flushed)
  or 60 s after its `at` (its writer died unflushed: fall back to server truth).
- Nothing is written to the store by `set`: the store holds server truth only (decision 3).

#### §9.4 Flush policy

| | Curated | Write-behind |
|---|---|---|
| When | at once (sets within one task coalesce) | 2 s after the key's last change, at most once per 10 s per tab; at once on `visibilitychange: hidden`; at once when the value's stored form exceeds 8 KB |
| Through | `TmApi.write('users/me/preferences/set', { items })`; resets through `users/me/preferences/delete` with `{ keys }` (0018 §3.5) | same |
| What | this tab's dirty keys only; tabs never coordinate (the server sets keys one by one, last writer wins) | same |
| On `pagehide` | every dirty and in-flight key through `TmApi.send('users/me/preferences/set', …)`, unread, newest first up to 16 KB; the rest dropped with `tm.prefs.dropped { reason: 'pagehide-cap' }` | same |

- **In-flight keys go into the `pagehide` send too:** a write started on `hidden` is aborted by the
  unload; resending an identical value is harmless.
- **Failures.** `offline`, `unavailable`, `server`: the keys stay dirty and retry on the next
  schedule and when `TmApi.online` turns true. `validation` with `Users.TooManyPreferenceKeys`:
  §9.5's eviction, then one retry. Any other `validation` code: the key is dropped (development
  code never sends one: `tmPreferenceKey` checks first). `unauthenticated`, `step-up` and
  `client-outdated`: 0024's paths; unflushed keys are lost when the expiry path reloads the tab.
- **Writes are never cancelled** (A§7.9) and never block navigation.

#### §9.5 Adopting the result, and eviction

1. The flush result is `PreferencesResult(Preferences, PreferencesTag)` (0018 §3.5): the full bag
   after this write.
2. Under the tenant's sync lock (§5.3), `patch` the stored `me`: `Preferences` = the returned bag,
   `PreferencesTag` and `Tags.preferences` = the returned tag. Nothing else in `me` changes.
3. Each sent key whose dirty value is still the one sent leaves the dirty map; a key set again
   meanwhile stays dirty.
4. The response header's new `preferences` tag now equals the held one within the settle window,
   and the user's valued `cache.changed { preferences }` event matches too: no sync anywhere
   (A§7.3 "own writes need no sync").

- **0014 §3.4's warm-writer rule** ("adopt the returned bag, overlay unflushed keys") holds: the
  overlay is §9.3's read order rather than a stored merge (challenge 6).
- **Out-of-order adoptions** across tabs can store an older bag; the next header carries a newer
  `preferences` tag and one sync repairs it (convergent).
- **Eviction.** On `Users.TooManyPreferenceKeys` the tab deletes the 64 write-behind keys with the
  oldest envelope `at` in the stored bag (one `delete` call), then retries its flush once;
  telemetry `tm.prefs.evicted { count }`.
- **Locale is not a preference here:** `PreferredLanguage` and `PreferredCalendar` go through
  `users/me/locale` (0024 §7.2). Its result's tag is adopted the same way, patching
  `me.User.PreferredLanguage` or `PreferredCalendar` (request to 0027).

### §10 Page state

`TmPageState` keeps, per tab and in memory only, what a page needs to look exactly as it did when
the user returns within the SPA: query, data, scroll, selection, active tab. It is a bounded
container; each host decides what to remember.

```ts
type TmPageStateKey = string & { readonly __tmPageStateKey: true };
declare function tmPageStateKey(path: string): TmPageStateKey;        // canonical path, no query or fragment: '/17/centers'
declare class TmPageState {                                   // A§5.8
  remember<T>(key: TmPageStateKey, state: T): void;           // replaces; marks the entry most recently used
  recall<T>(key: TmPageStateKey): T | undefined;
  isStale(key: TmPageStateKey): boolean;                      // the data part must be refetched; the rest restores
  markStale(scope: { tenantId: number; entity?: string }): void; // after a save, delete, import or action on that entity
  forget(key: TmPageStateKey): void;
}
```

- **Key.** The canonical path (0024 §9.1) of the page: `/17/centers`, `/17/centers/5`,
  `/17/reports/acme-aging`. The query is state, not identity: returning to `/17/centers` from the
  launcher (no query) finds the remembered query, and 0030's precedence (URL, then page state)
  decides what applies.
- **Bound.** 20 entries, least recently used evicted. Values are held by reference and must be
  immutable; a host remembers at most its rendered window (0029's `maxTake`), never a whole
  table.
- **Invalidation.**
  - **Permissions or settings moved:** when the held `permissions` or `settings` tag of tenant `t`
    changes (any source), every entry of `t` is forgotten: remembered rows may hold data the user
    can no longer see, or a shape the tenant's languages no longer admit.
  - **Writes:** a host that saves, deletes, imports or runs an action calls `markStale` with the
    entity (0030, 0031); entries for that entity's pages restore query, scroll and selection and
    refetch rows.
  - **Language switch:** nothing; display names re-render from the remembered rows.
- **Consumers:**

| Host | Remembers (owner decides) |
|---|---|
| search (0030) | query, row window, total, scroll, selection, active row, expanded ids |
| details (0031) | the entity and related, extras, selected tab, scroll of the page and every panel |
| report (0034), dashboard (0035) | parameters, results, scroll |

### §11 Drafts

`TmDrafts` keeps a tab's unsaved form copies in `sessionStorage`, so a reload, a step-up or a
re-authentication returns the user to edit mode with nothing lost, while a new tab starts clean.

```ts
declare class TmDrafts {                                      // A§5.8
  key(tenantId: number, entity: string, id: number | 'new'): string; // 'tm.draft:<sub>:17:gl.Center:5'
  save(key: string, value: TmJson): void;                     // debounced 300 ms; flushed on pagehide
  load(key: string): TmJson | undefined;
  clear(key: string): void;
  clearAll(sub: string): void;                                // 0024 §8.4, §8.5, §8.7
  readonly dirtyCount: Signal<number>;                        // this tab's drafts of the profile user
}
```

- **Stored value** `{ v: 1, at, data }` as JSON under the key. The key embeds `sub`, so another
  user signing in within the same tab session never sees it; `load` refuses a key whose `sub` is not
  the profile's.
- **Written continuously:** 0031 calls `save` on every model change; the write is debounced 300 ms
  and flushed synchronously on `pagehide` and `visibilitychange: hidden`, so a reload loses
  nothing.
- **Lifetime.** Until `clear` (save, cancel, discard), `clearAll` (sign-out, changed user), or the
  end of the tab's session storage. Drafts survive the expiry path (A§5.5) and every store sweep.
  No age limit: a draft restored after a long absence meets 0031's concurrency check on save.
- **Survives** reload, Back from another site and "reopen closed tab"; **not** a new tab with the
  same URL. "Duplicate tab" copies session storage by design; 0031's concurrency check covers two
  saves.
- **Quota.** A `QuotaExceededError` (about 5 MB per tab) deletes this tab's oldest other drafts and
  retries once; then the draft lives in memory only (lost on reload) and `tm.drafts.quota-exceeded`
  is emitted. 0031 shows nothing extra: the in-app leave guard still protects the edit.
- **`sessionStorage` holds only drafts and `tm.login`** (`tm-boot.js`'s sign-in loop guard,
  0024 request 2).

### §12 Tree expansion memory

`TmTreeExpansion` remembers which nodes of a tree search page the user expanded, for the rest of
the sign-in session, in every tab, so the next visit fetches the same nodes expanded in one call
(0030 with 0015 §5.4's `IncludeRoots`).

```ts
declare class TmTreeExpansion {                               // A§5.8, completed (challenge 12)
  expanded(page: string): Signal<ReadonlySet<number>>;        // page = the search page's canonical path '/17/centers'
  toggle(page: string, id: number, open: boolean): void;
  replace(page: string, ids: Iterable<number>): void;         // a collapse that drops descendants; pruning unknown ids
}
```

- **Storage.** Session partition (`u:<sub>/s<sh>`), document `tree:<page>`, value
  `{ ids: number[] }` in expansion order, oldest first. Writes debounce 250 ms. The partition dies
  with the session (sweeps, §2.6), so a new sign-in starts collapsed (the brief's "same session").
- **Bound.** 500 ids per page: expanding a 501st drops the oldest. 0030 sends at most the
  entity's `limits.maxIds` of the newest ids.
- **Across tabs:** the signal follows `store.changed`, but 0030 reads it once when the page loads;
  an open tree never re-expands under the user.

### §13 Recently visited pages

`TmRecents` lists the last ten pages the user visited in this tenant, for the launcher (0027) and
the home page (0035), from the write-behind key `nav.recent`.

```ts
interface TmRecentPage {
  readonly url: string;                                       // '/17/centers' — no query: the page restores its own state
  readonly kind: TmPageKind;                                  // 'search' | 'report' | 'dashboard' | 'settings' | 'custom'
  readonly title: Signal<string>;                             // the launcher entry's label, else the title shown at the visit
  readonly icon: string | null;                               // the launcher entry's icon, else null (the consumer's kind icon)
  readonly visitedAt: number;
}
declare class TmRecents { readonly pages: Signal<readonly TmRecentPage[]> } // current tenant, newest first, ≤ 10
```

- **What counts.** The routed page's context (0026 `TmPageContexts.current`) has kind `search`,
  `report`, `dashboard`, `settings` or `custom`, its route is not the drill-through list
  (`/:t/list/:segment`), and it stays current for 2 s while the document is visible (a background
  tab's dwell starts when it becomes visible). Home, details and studio pages never count: records
  are not pages.
- **De-duplication** by the tenant-relative path (`centers`, `reports/42`): a revisit moves the
  entry to the front. Cap 10; the oldest falls off.
- **Stored value** (`nav.recent`, write-behind envelope):
  `[{ "p": "reports/42", "t": 1792400000, "n": "Monthly sales by region" }, { "p": "centers", "t": 1792399000 }]`.
  `n` is stored only when no launcher entry matches the path (a stored report, a dashboard): it is
  the title as displayed, in the language of that visit.
- **Title and icon** come from the `TmNavigation` entry whose `url(t)` equals the URL, so they
  follow the active language; an entry hidden by permissions hides the recent too.
- **Across tabs:** a visit's `set` reaches every tab through `prefs.changed`; the next visit in any
  tab builds on the merged list.

## 4. Open questions owned

**SignalR Q1 — should the owner tab also refresh settings, permissions and entities on
`cache.changed`?** Yes, with no machinery of its own. The leader passes the event to the same
`TmCacheRefresher` every tab uses for header-detected staleness (§4.4, §5.3); the sync writes the
shared store, and followers re-render from `store.changed`, which they already handle for syncs
another tab ran. Followers never fetch on hub events. The new cost is two rules: jitter on
tenant-wide events, and values on events so that tabs already current do nothing.
Alternatives: every tab refreshes on the relayed event (N calls per browser instead of one, the
very cost the leader exists to avoid); events carry the changed content (tenant content on the
hub, breaking 0021's thin-event rule and its 4 KB cap); only headers refresh (an idle tab's menus
and permissions stay stale until the user clicks, f03 G18).

## 11. Review flags

1. **`client/sync` as one composite endpoint** (A§12 #3; §5). Alternative: fix `settings/client`,
   `entity-tags` and `users/me` and call three. Flips on a preference for no composite routes.
2. **Composite `permissions` tag and wider `cache.changed`, with values on user events** (A§12 #4;
   E1, E3). Alternative: a separate `userPermissions` tag; no push for permissions. Flips if hub
   fan-out on large tenants proves costly (a role edit sends one tenant-group event; a bulk
   membership import sends one event per affected user).
3. **No heartbeats; steals only from a hung or a hidden disconnected leader** (A§12 #5; §7.3).
   Alternative: timer heartbeats. Flips if a browser throttles BroadcastChannel or WebSocket
   handlers in hidden tabs.
4. **The store holds server truth; unflushed preferences live in memory** (decision 3). A crashed
   tab loses up to 10 s of write-behind changes. Alternative: a persisted pending overlay. Flips if
   users report lost column choices.
5. **Hub traffic never keeps a session alive** (E13, E16). A user who only watches an open tab for
   seven days is signed out. Alternative: hub reconnects renew. Flips if wall-display use cases
   (dashboards left open) matter.
6. **Page state drops a tenant's entries when its permissions or settings tag moves** (§10).
   Alternative: keep them and let the next refetch correct. Flips if the drops feel like lost
   scroll positions after routine role edits.
7. **Recents hold pages, not records; ten per tenant** (§13). Alternative: include details pages.
   Flips if users ask for "recent records" before global search's records bucket exists.
8. **Tree expansion is per sign-in session, 500 ids per page** (§12). Alternative: per user across
   sessions (tenant partition). Flips if users expect trees to stay open after signing in again.
9. **`settings/entity-tags` stays, unused by the SPA** (E5). Alternative: remove it (five edit
   sites in 0013 and 0016). Flips if no API caller needs it.
10. **Write-behind envelope `{ at, v }` and eviction of the oldest 64 keys at the cap** (§9.2,
    §9.5). Alternative: no envelope, no eviction. Flips if 1,024 keys per user proves ample.
11. **Degraded polling every 60 s while a tab is visible** (§8.7). Alternative: 30 s, or poll
    hidden too. Flips on the server cost of polling fleets with realtime disabled.
12. **Sync throttle 2 s, settle window 100 ms, jitter 0–3 s valued and 0–10 s name-only** (§5.3,
    §4.4). Flips on measured burst load after tenant-wide changes.
13. **Theme is device-level** (A§12 #13); **session expiry deletes stored data** (A§12 #26, shared
    with 0024).

## 12. Challenges to the architecture

1. **User-addressed `cache.changed` events should carry values** (A§7.4, A§6.3 row "0013 §2.3,
   §2.4, 0021 §6.3"). Name-only `preferences` events make every write-behind flush (as often as
   every 10 s while a user works) cost one wasted `client/sync` in each of that user's browsers,
   since the leader cannot tell its own tab's write from another device's. A user-addressed event
   can carry the user's own wire tag, the composite included. Followed: the skeleton's names and
   recipients, with values on user events (E1).
2. **`prefs.changed` must carry the values** (A§5.6, §5.7 "other tabs apply at once"). With keys
   only, a receiving tab has nothing to apply: the store holds the server's bag, not the
   unflushed value. Followed: `values` and `at` replace `keys` (§6.2).
3. **The steal rule ping-pongs between two visible windows** (A§7.8 "or leader not connected for
   30 s"). With the hub down, a visible follower steals, then the old leader, now a visible
   follower, steals back 30 s later, each move a reconnect and a sync. A visible leader's backoff is
   unthrottled, so stealing from it gains nothing. Followed with `leaderVisible` on `hub.status`
   and a `disabled` state (§7.3).
4. **`ifAvailable` plus "wait for its `store.changed`" loses wake-ups** (A§7.3 step 2). When the
   holder's sync was sent before the change tab B observed, its result does not contain it, and B
   never syncs. Followed with a queued lock and a re-check inside it (§5.3).
5. **`ClientSyncRequest.Held` is keyed by tag name**, not "document" (A§6.1 comment): `me` depends
   on two tags. The C# shape is unchanged.
6. **The tab should not store a bag "overlaid with keys still unflushed"** (A§5.7). A crash would
   leave values in the shared store that the server never received, shown by every tab until the
   next `me` refetch. Followed in effect: the overlay is applied when reading (§9.3).
7. **Recents "by route template"** (A§5.8) would collapse every stored report (`/:t/reports/:id`)
   into one entry. Followed with the tenant-relative path as the key, among page kinds (§13).
8. **The primary cannot load `/realtime`** under A§2.2's import rule. Followed with `TM_REALTIME`
   supplied by the tenant shell (§8.1). 0024 meets the same question for the shells themselves;
   one answer (tokens filled by `/shell`, or an exception for dynamic imports from the primary)
   should serve both.
9. **Realtime-disabled deployments need a runtime signal** (A§7.8 "Realtime disabled"): the
   skeleton names the mode but no way for the client to learn it; a negotiate against an unmapped
   hub answers `404 route-not-found`, which `TmApi` reads as an outdated client. Added
   `ClientSyncResult.Realtime`.
10. **Hub traffic is missing from the background rule** (A§6.3 rows "0011 §5.5 profile cookie" and
    "0014 §7, 0016 §4.3, §6.1"). Without E13 and E16 a hidden leader's reconnects renew the
    session cookie and stamp activity, so a forgotten tab keeps a session alive indefinitely,
    against the 7-day idle design.
11. **`TmLaunchDocs`' `entity:*` index member** (A§5.7) cannot start a lazy load from a signal read.
    Followed with `TmLaunchCache.entitySet()` (§3.3).
12. **`TmTreeExpansion` needs `replace`, `TmPageState` needs `markStale`** (A§5.8): a collapse must
    drop descendants in one write, and a save must stale the search page it came from.
