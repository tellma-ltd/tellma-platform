## 2. Decisions

1. **One grid engine for dashboards and home** (§8, §15). Home renders a code-defined widget list
   through the same grid; no stored home row in v1. Alt: a seeded shared dashboard as home
   (research Q6: a network read before the home renders); the launcher's browse content (shell D11).
2. **Columns for layout and references; JSON for type settings and dashboard parameters** (§3).
   Alt: a `DashboardParameters` table (a list always read whole); a layout blob (no FK).
3. **12 columns of 30 px rows, fixed tile heights, two layouts** (§8): wide (≥ `md`) keeps stored
   positions with compaction; narrow is one column. Alt: a medium band (research Q2); natural
   heights (a growing list pushes the tiles below it, against rule 2D).
4. **Reading order is derived, never stored** (§8.2). Alt: a stored `Ordinal` (a second truth).
5. **Widget types are registered on the server and declared on the client, checked at build**
   (§4). Alt: client-only keys (the server could not refuse an API or MCP typo).
6. **Report widgets are 0034's host in `widget` mode; the tile is 0035's** (§9.1). Alt: a second
   report pipeline.
7. **Dashboards Q1: same-key binding by default; a widget may bind to another dashboard parameter
   or a fixed value; dashboard parameters have no default** (§10). Alt: section 4.
8. **A required report parameter with no default must be bound to a fixed value or a required
   dashboard parameter** (§5.3): the brief's rule, widened to dashboard parameters.
9. **One scheduler per grid: completion-based, only while visible, online, near the viewport and
   not editing; six runs in flight; scheduled runs are background requests** (§11). Alt: fixed
   intervals (overlaps); a leader-tab scheduler; an inactivity pause (wall displays would freeze).
10. **A user's refresh always clears and shows the spinner** (§11.3), forced or per tile. Alt: a
    silent tile refresh (no feedback on the click).
11. **"Updated 10:42" is absolute** (§8.5). Alt: relative time (changes every minute).
12. **Tiles whose data the viewer cannot read are hidden before the first render; editors see a
    placeholder** (§6.2; sharing research D8). Alt: a placeholder for everyone.
13. **The dashboard page is 0031's `page` hatch; edit mode edits the details form** (§12, §13).
    Alt: an own lifecycle like 0034's studio (whose document is one JSON string).
14. **Moves and resizes by pointer, keyboard and menu; collisions push down, then the grid
    compacts** (§13.3). Alt: free placement with gaps.
15. **Coded reports may be widgets** (§3.1), their bindings checked by the editor only. Alt:
    stored definitions only (Acme's aging report could not sit on a dashboard).
16. **Seeded dashboards mirror seeded reports** (§7.3). Alt: none in v1.
17. **Greeting by time band in the display zone and by first name through a first-token rule**
    (§15.2). Alt: a `User.ShortName` group (0014, 0018 edits for one sentence); the full name.
18. **The date line is today in the user's calendar and display zone** (§15.2). Alt: the
    browser's zone (disagrees with the rest of the app, A§12 #12).
19. **Home lists: up to 10 rows in fixed tiles with "View all"** (A§10.2). Alt: the design's 5 + 2.
20. **The home seam is the widget model** (§15.6). Alt: a server call per home render (research
    D15; a network wait before home).
21. **The `home` hatch gets building blocks** (§2.3). Alt: the hatch alone.
22. **The dashboards page is the plain search page** (§14). Alt: 0034's tabs (a generic `browse`).
23. **At most 24 widgets** (§3.1): one dashboard fits 0033's per-user `tellma-reports` budget (8
    running, 16 queued). Alt: 40 (research D4).
24. **The home route reaches `/reports` only through `import()`** (§1.1). Alt: a `/home` entry
    point (dynamic imports chunk the same).

#### §1.2 Vocabulary

- *Widget* — one `core.DashboardWidgets` row, or one code-defined `TmDashboardWidgetModel`;
  *widget type* — its registered key (`core.report`, `acme.cash-position`); *report widget* — type
  `core.report`; *built-in widget* — the other Core types (§9.2).
- *Tile* — a widget's rendered frame: header, "Updated" line, menu, body. *Cell* — one column by
  one row of the grid.
- *Wide* and *narrow layout* (§8.2); *reading order* — the derived tile order (§8.2).
- *Dashboard parameter* (§10.1); *binding* — how a report parameter gets its value (§10.2).
- *Silent run* — a refresh that swaps data in place; *clearing run* — one that clears first (§11).
- *Home model* — the widget list the home page renders (§15).

### §2 What a distribution writes

Stored dashboards need no code. A new widget type is one declaration on each side; a different
home page is one hatch.

#### §2.1 The common case: nothing

- The core feature declares `core.Dashboard` (search page, details hatch, launcher entry under
  `analysis`) and the four Core widget types. Users build dashboards in the app.
- A pack ships standard dashboards as seeds (§7.3), next to its report seeds.

#### §2.2 A widget type of its own

```csharp
// Acme composition (server): the key, and the settings type the server validates
contribution.WidgetType<CashPositionSettings>("acme.cash-position");
public sealed record CashPositionSettings(int AccountId, bool ShowTrend);
```

```ts
// app/widgets/cash-position.widget.ts (client) — listed in acmeFeature.widgets
export const cashPosition = tmWidget('acme.cash-position', {
  labelKey: 'Acme_Widget_CashPosition', icon: 'wallet', status: true,
  component: () => import('./cash-position'),                 // reads injectTmWidget()
  settingsEditor: () => import('./cash-position-settings'),   // edit mode only
  defaultSize: { w: 4, h: 4 }, minSize: { w: 3, h: 3 },
  requires: ['acme.CashPosition', 'Read'],
});
```

- **Drift rule.** `tellma-client build` fails with `widget-missing` when the emitted metadata lists
  a server key no client declaration has, and with `widget-not-registered` for the reverse
  (request R5(c)). The server refuses an unregistered key at save (§5.2).
- **Data:** the body fetches through `inject(TmApi)` with the context's signal and reports its
  status (§9.3). This is a hatch; a report definition covers most needs with no code.

#### §2.3 A different home page

```ts
// acme.feature.ts
export const acmeFeature = tmFeature({ key: 'acme', home: () => import('./home/acme-home') /* , … */ });

// home/acme-home.ts — the greeting, the default widgets, one report below them
@Component({
  selector: 'acme-home',
  imports: [TmHomeGreeting, TmDashboardGrid],
  template: `<tm-home-greeting /><tm-dashboard-grid [widgets]="widgets" />`,
})
export default class AcmeHome {
  protected readonly widgets: readonly TmDashboardWidgetModel[] = [...TM_HOME_WIDGETS,
    { key: 'sales', type: 'core.report', report: { code: 'acme.monthly-sales' }, x: 0, y: 18, w: 12, h: 9 }];
}
```

- The hatch replaces the page body; the route, skeleton, page context and telemetry stay
  `TmHomeHost`'s (§15.1). A code-defined report widget runs under the viewer's own access to that
  definition (no read-through without a stored dashboard). The reference distribution keeps the
  default home; the harness covers the hatch.

### §3 The dashboard tables

`core.Dashboards` holds one row per dashboard, `core.DashboardWidgets` its tiles,
`core.DashboardShares` its user and role grants. The stack's segment is `dashboards`, its resource
`core.Dashboard`.

- **Every widget's data comes from `reports/run`** with `DashboardId` (0033 §8.2) or a coded

#### §3.3 Limits

- **`DashboardOptions`** (`Tellma:Dashboards`, validated at startup) has one member,
  `MinRefreshMinutes` (default 1, range 1–60), the floor checked on save.
- **Constants:** 24 widgets (`MaxChildren`), 20 dashboard parameters, `SettingsJson` 8 KB,
  `ParametersJson` 32 KB, `RefreshMinutes` ≤ 1440.

### §4 Widget types

A widget type is a key registered on the server and declared on the client. The server validates
the key and the settings; the client renders the body.

#### §4.1 Server registry

```csharp
// FeatureContribution extensions (0011 edit E2)
public static FeatureContribution WidgetType(this FeatureContribution contribution, string key);            // no settings
public static FeatureContribution WidgetType<TSettings>(this FeatureContribution contribution, string key) where TSettings : class;

public interface IWidgetTypeRegistry                          // Tellma.Core.Abstractions.Dashboards
{
    IReadOnlyList<WidgetTypeDescriptor> Types { get; }
    WidgetTypeDescriptor? Find(string key);
}
public sealed record WidgetTypeDescriptor(string Key, string Feature, Type? SettingsType, WidgetSubject Subject);
public enum WidgetSubject { None, Report }                    // Report: exactly one of ReportDefinitionId, ReportKey
```

- **Key grammar** `^[a-z][a-z0-9]*\.[a-z][a-z0-9]*(-[a-z0-9]+)*$`; the first segment is the
  contributing feature's key (`core` is the platform's). Startup refuses a duplicate key or a
  foreign prefix.
- **Settings** deserialize strictly with System.Text.Json (unmapped members refused) into
  `TSettings`, whose data annotations are validated. Only `core.report` has `Subject = Report`.
- **The emit** writes the keys into the core metadata chunk as `widgetTypes: string[]` (request
  R5(c)), so the build checks drift (§2.2).

### §5 Validation (save)

`DashboardValidator` runs in the save's first round trip and maps every failure to a field path,
so 0031's inline summary shows it next to the right control. Codes are Appendix A's.

#### §5.1 The dashboard

1. `Title` required; `RefreshMinutes` null or between `MinRefreshMinutes` and 1440
   (`Dashboard.RefreshOutOfRange`, argument `min`).
2. `ParametersJson` parses as `DashboardParameter[]` (`Dashboard.ParametersInvalid`); at most 20
   (`Dashboard.TooManyParameters`); keys follow 0033 §4.1's grammar, unique ignoring case
   (`Dashboard.ParameterKeyInvalid`, `Dashboard.ParameterKeyDuplicate`); `Type` is in 0033
   §4.1's vocabulary; `Entity` only on `Numeric`, naming a queryable entity
   (`Dashboard.ParameterEntityInvalid`). Paths point into the list: `ParametersJson/2/key`.

#### §5.2 Each widget

1. `Type` is registered (`Dashboard.WidgetTypeUnknown`); the subject matches it
   (`Dashboard.WidgetSubjectInvalid`): `core.report` holds exactly one of `ReportDefinitionId`
   and `ReportKey`; other types hold neither.
2. `ReportKey` follows 0034's coded-key grammar (kebab-case with a hyphen); whether the key exists
   is the client's check (decision 15).
3. A `ReportDefinitionId` added or changed by this save names a definition the saver reads
   directly (`Dashboard.ReportInvisible`). One kept from the before image stays, even when the
   saver reads it only through this dashboard.
4. **Grid:** `X + W ≤ 12`, `W` 1–12, `H` 1–24, `Y` 0–1000 (`Dashboard.WidgetOutOfGrid`); no two
   widgets overlap (`Dashboard.WidgetsOverlap`, argument `other` = the other row's index; an
   O(n²) check over at most 24 rows).
5. `RefreshMinutes` as §5.1 rule 1; `SettingsJson` deserializes into the type's settings within
   8 KB (`Dashboard.SettingsInvalid`).

#### §5.3 Report widget bindings

For a stored definition, against its document's parameters (0033 §4.1):

1. Every binding key names a report parameter, and every `parameter` binding names a dashboard
   parameter (`Dashboard.BindingUnknown`, argument `key` or `parameter`).
2. The dashboard parameter feeding a report parameter (explicitly or by same key, §10.2) has the
   same `Type` and, for entities, the same `Entity` (`Dashboard.BindingTypeMismatch`). A fixed
   value converts to the report parameter's type (`Dashboard.BindingValueInvalid`).
3. **A required report parameter with no default** is bound to a non-null fixed value or fed by a
   **required** dashboard parameter; otherwise `Dashboard.WidgetParameterRequired` (arguments
   `key`, `label`) at `Widgets[i].SettingsJson`.

**Example —** the Overdue invoices definition requires `AsOf` with no default:

| Dashboard parameters | Widget bindings | Result |
|---|---|---|
| none | none | `Dashboard.WidgetParameterRequired` (`AsOf`) |
| `AsOf` (Date, optional) | none (same key) | `Dashboard.WidgetParameterRequired`: an unset optional parameter sends nothing |
| `AsOf` (Date, required) | none (same key) | valid: the bound tile waits for a value (§10.3) |
| none | `"AsOf": { "value": "2026-12-31" }` | valid |
| `Period` (Date, required) | `"AsOf": { "parameter": "Period" }` | valid |

- **Coded-report widgets** get the same checks in the editor against the declaration, as
  warnings: `required` there only marks the bar, and the C# may default it ("As of may need a
  value. Bind it to be sure.").
- **A definition edited later** can break a saved dashboard; the tile then shows "This widget needs
  a value for {label}" from the run's `422 Report.ArgumentRequired` (§8.6).

### §8 The grid

`tm-dashboard-grid` lays widgets on a 12-column grid of fixed 30 px rows. Above `md` it uses the
stored positions; below `md` it stacks tiles in one column. Tile heights never depend on data.

#### §8.1 Model and geometry

```ts
// @tellma/core (primary): one widget shape, stored or code-defined

interface TmDashboardWidgetModel {

  readonly type: string;                          // a widget type key
  readonly report?: TmReportRef;                  // core.report: { id } | { code } | { key } (0034 §3.1)
  readonly title?: TmTextSlots; readonly titleKey?: string;            // stored slots, or a string key in code
  readonly description?: TmTextSlots; readonly descriptionKey?: string;
  readonly x: number; readonly y: number; readonly w: number; readonly h: number;
  readonly refreshMinutes?: number | null;        // absent or null: the dashboard's
  readonly settings?: TmJson;                     // the parsed SettingsJson
}

// @tellma/core/dashboards
@Component({ selector: 'tm-dashboard-grid' })

  readonly widgets: InputSignal<readonly TmDashboardWidgetModel[]>;
  readonly parameters: InputSignal<TmDashboardArgs>;          // §10.3; default {}
  readonly dashboardParameters: InputSignal<readonly TmDashboardParameter[]>; // default []
  readonly dashboardId: InputSignal<number | undefined>;      // read-through (0033 §8.2); absent for code-defined grids
  readonly refreshMinutes: InputSignal<number | null>;        // the dashboard default; default null
  readonly view: InputSignal<TmDashboardView | undefined>;    // the `view` extra (§6.1); absent: every tile visible
  readonly label: InputSignal<string>;                        // the region's accessible name
  readonly tiles: Signal<readonly TmTileState[]>;             // reading order; for the page context

}
interface TmTileState { readonly key: string; readonly title: string; readonly status: 'idle' | 'loading' | 'ready' | 'waiting' | 'error'; readonly executedAt: string | null }
```

- **Geometry.** CSS grid, `grid-template-columns: repeat(12, minmax(0, 1fr))`,
  `grid-auto-rows: var(--tm-dashboard-row)` (30 px), `gap: var(--tm-dashboard-gap)` (10 px). A
  tile `h` rows tall is `30h + 10(h − 1)` px: 9 rows = 350 px, close to 0034's 360 px card. The
  band sits on `--surface-subtle` with a `--border-subtle` top rule and 14×16 px
  padding (11×10 below `sm`), as the design's home body.
- **Stored dashboards** map to the model with `tmDashboardModel(entity)`: key `w{Id}`, `title`
  from `Title…Title3`, `report` from `ReportDefinitionId` or `ReportKey`, `settings` parsed.

#### §8.2 Two layouts

- **Wide** (the grid's container ≥ 768 px, `md`): every visible tile keeps its stored `x` and
  `w`; rows compact upward (rule 1 below), so a hidden tile leaves no hole.
- **Narrow** (< 768 px): one column; tiles stack in reading order (rule 2) at their stored `h`.
- **Mechanics.** The host declares `container-type: inline-size; container-name: tm-dashboard`
  (A§9: components use container queries with the closed values). `tmPackDashboard` computes both
  arrangements once per widget set; each tile carries `--tm-col`, `--tm-span`, `--tm-row`,
  `--tm-rows`, `--tm-row-narrow` as 1-based integers, and two `@container` rules apply one
  arrangement or the other. A resize across 768 px swaps layouts in CSS with no script.
  `@media print` uses the narrow arrangement.

```ts
interface TmPlacement { readonly key: string; readonly col: number; readonly span: number; readonly row: number; readonly rows: number; readonly rowNarrow: number }
declare function tmPackDashboard(widgets: readonly TmDashboardWidgetModel[]): readonly TmPlacement[]; // visible widgets in; reading order out
```

1. **Compaction (wide).** Widgets sorted by `(y, x)`; each takes the lowest row `r ≤ y` whose cells
   `[x, x + w) × [r, r + h)` are free of the widgets already placed.
2. **Reading order.** Over the compacted positions, a band starts at the topmost unread tile and
   grows while another tile starts above the band's bottom edge; within a band, tiles read by `x`,
   then `y`; bands read top to bottom.
3. **Narrow rows.** Tile *i* starts at row 1 + the sum of the earlier tiles' `h`; the grid gap
   separates them.

**Example —** the home default (§15.3) and a dashboard where Omar cannot see widget B:

| Grid | Stored `(x, y, w, h)` | Wide `col/span · row/rows` | Reading order | Narrow row |
|---|---|---|---|---|
| home | to-me `(0,0,7,9)`, recents `(7,0,5,9)`, by-me `(0,9,7,9)` | 1/7·1/9, 8/5·1/9, 1/7·10/9 | to-me, recents, by-me | 1, 10, 19 |
| Omar's | A `(0,0,6,9)`, B `(6,0,6,9)` hidden, C `(6,9,6,9)` | A 1/6·1/9, C 7/6·1/9 | A, C | 1, 10 |

#### §8.3 Reading order is the DOM order

- Tiles render in reading order, so Tab, screen readers, the narrow layout and the run queue
  (§11.1) share one sequence (WCAG 1.3.2, 2.4.3). CSS placement never reorders focus.
- **RTL.** `x` is logical: column 1 is the inline-start edge, so the wide layout mirrors with no
  arithmetic and the stored layout is direction-neutral.

#### §8.4 The tile

```text

│ Quarterly sales, functional currency               Updated 10:42 (!)  │  12 px secondary: description · Updated · stale mark
```

- **Title**, first that exists: the widget's title (active content slot, else slot 1), `titleKey`,

- **Description** ellipsizes on the status line; the full text is the region's description and the

- **Menu** (`tm-menu`, "Widget options for {title}"). View mode: Refresh; Open report (report

#### §8.5 The "Updated" line

- Shown for report widgets and for types declaring `status: true`.
- **Text** "Updated {time}": `TmL10n.formatTime(executedAt)` when `executedAt` falls on today in

  `<time datetime>` element; its tooltip has the seconds. `executedAt` is the run's
  `ReportResult.ExecutedAt` (0033 §9.1), so it says when the server computed the numbers.
- **Before the first result** a skeleton bar of the text's final width holds the place.
- **Stale.** When a silent run fails and the tile keeps its data, a 16 px `circle-alert` in the
  warning tone follows the time; its name and tooltip read "Couldn't refresh. Showing data from
  10:42." with the reference chip (0034 §3.4). The next successful run removes it.

### §10 Dashboard parameters (Dashboards Q1)

A dashboard may declare parameters; its bar shows them above the grid. Each report widget's
parameters bind to them by key unless the widget binds them otherwise.

#### §10.1 Declaration

```csharp
public sealed record DashboardParameter(            // one item of ParametersJson
    string Key,                                     // 0033 §4.1's grammar; unique ignoring case
    string? Label, string? Label2, string? Label3, string? LabelKey,   // default label: the key
    bool Required,                                  // bound tiles wait until it has a value
    string Type,                                    // 0033 §4.1's vocabulary: Numeric, String, Bool, Date, DateTime, DateTimeOffset, Guid
    string? Entity);                                // a picker; Numeric only
```

```ts
// TmDashboardParameter mirrors the record member for member (camelCase)
type TmDashboardArgs = Readonly<Record<string, TmJson>>;   // supplied values by key; null = cleared (omitted); absent = unset
```

- **No default expression.** An unset parameter sends nothing, so each bound report applies its
  own default (decision 7). The editor prefills `Type` and `Entity` from the first report
  parameter bound to it.

#### §10.2 Binding

`tmBindWidgetArguments` resolves, for one report widget, each parameter the report declares (the
`view` summary's `Parameters`, or the coded declaration's), in order:

1. **Explicit binding** (`settings.bindings[key]`, keys matched ignoring case):
   `{ "value": v }` sends `v` (`null` sends `null`: omitted); `{ "parameter": "d" }` takes
   dashboard parameter `d`.
2. **Same key**: a dashboard parameter whose key equals the report parameter's, ignoring case.
3. **Unbound**: nothing is sent; the report applies its default or no restriction.

A dashboard parameter `d` gives its supplied value, `null` when cleared, nothing when unset. When
`d` is required and unset or cleared, the tile waits (§8.6) and does not run. Only the report's
own keys are sent (A§10.1).

```ts
declare function tmBindWidgetArguments(
  reportParameters: readonly { key: string; required: boolean }[], settings: TmJson | null,
  declared: readonly TmDashboardParameter[], args: TmDashboardArgs,
): { readonly args: TmReportArgs; readonly waitingFor: string | null };   // waitingFor: the dashboard parameter key
```

**Example —** Acme's Sales overview declares `Customer` (Numeric, `acme.Customer`, optional) and
`Year` (Numeric, required); the URL is `/17/dashboards/3?p.Year=2026`:

| Widget | Report parameters | Bindings | Sent |
|---|---|---|---|
| Aging (coded `acme-aging`) | `AsOf` (required, C# default), `Customer` | none | `{}`: `Customer` unset, `AsOf` defaults in C# |
| Sales by center | `Year` | none (same key) | `{ "Year": 2026 }` |
| Last year by center | `Year` | `"Year": { "value": 2025 }` | `{ "Year": 2025 }` |
| Monthly sales | none | — | `{}` |

With `?p.Year=2026&p.Customer=1012` Aging gets `{ "Customer": 1012 }`; with `?p.Customer=` it gets
`{ "Customer": null }` (no restriction); with no `p.Year` the two center tiles wait.

#### §10.3 The bar, the URL and remembered values

- **The bar** is 0034's parameter bar (request R4(d)) over the dashboard's declarations, rendered
  above the grid only when the dashboard declares parameters. It commits on pick, Enter or blur,
  never per keystroke; below `sm` it collapses to "Parameters" with a one-line summary (0034 §4.2).
- **Unset display.** An unset parameter shows its effective value greyed with the hint "Default"
  when every bound tile's last result echoes the same `Default` value for it (0033 §9.1's
  `Arguments`); otherwise the placeholder "Report default".
- **A commit** re-runs every tile bound to the changed key, presented as `spinner` (held output
  dimmed, request R4(b)), and resets their due times (§11.1).
- **URL** `?p.{Key}=` through 0034's codec with the dashboard's declarations: a supplied value is
  written, `p.Key=` means cleared, an unset parameter is absent; changes `replaceUrl`.
- **Precedence:** the URL (any `p.*` defines every parameter), then page state, then
  `dashboard.<id>.params` (write-behind `{ v: 1, args }` of supplied non-null values; request
  R2(a)), then unset. Code-defined grids (the home) have no parameters.

### §11 Refresh

One scheduler per grid refreshes each tile on its interval, silently, only while someone can see
it. A forced refresh clears every tile and shows its spinner.

#### §11.1 The scheduler

- **Interval** of a tile: `refreshMinutes ?? the dashboard's RefreshMinutes`; none means no
  automatic refresh. Built-in list types are never ticked (§9.2).
- **Due** = the end of the tile's last run (success or failure) + interval × (1 + u), u uniform in
  [0, 0.1), the jitter capped at 30 s. Runs never overlap; viewers who opened together drift apart.
- **A due tile runs** when all hold: `document.visibilityState` is `visible`; `TmApi.online()`;
  the grid is not in edit mode; the tile is within 480 px of the viewport (one
  `IntersectionObserver` per grid, `rootMargin: '480px 0px'`); fewer than 6 widget runs are in
  flight on the page. Otherwise it waits, in reading order, and runs as soon as they hold:
  becoming visible, coming back online or scrolling into range runs every overdue tile at once,
  six at a time.
- **First runs** on open follow the same gate and cap, in reading order: the top of the dashboard
  loads first and a long phone column loads as it scrolls.
- **One timer.** The scheduler keeps a single `setTimeout` to the earliest due time and re-arms it
  after every run and every gate change; `TM_NOW` drives it in tests.

**Example —** a dashboard with `RefreshMinutes = 5` and one tile overridden to 1 minute: the 1-minute
tile refreshes about every 60–66 s, the others every 5–5.5 min, silently. Farah switches tabs at
10:00 and returns at 10:20: nothing ran meanwhile; on return every visible tile runs once, six at
a time, and the "Updated" lines move to 10:20.

#### §11.2 Silent runs and the session

- **Background.** A scheduled run is `host.run()` in silent mode, which sends `Tellma-Activity:
  background` (0034 §3.4, 0024 §10.2): it stamps no activity and renews neither the session cookie
  nor the profile cookie, so a dashboard left open never keeps a session alive. Opening, a
  parameter commit, a forced refresh and a tile's Refresh are foreground (request R4(c)).
- **Errors** of a background run are never presented as dialogs (0024 §10). A tile with data
  keeps it and shows the stale mark (§8.5); without data it shows its failure state. `401` follows
  0024's expiry path for the whole tab. `403` and `404` clear the held data and show the state, so
  revoked data never lingers (request R4(c)).
- **Wall displays.** No inactivity pause: a visible dashboard refreshes until its session expires,
  then shows 0024's "Your session ended" dialog.

#### §11.3 Forced refresh and a tile's Refresh

- **Refresh** (toolbar, action `dashboard.refresh`): every report tile in range runs
  `run({ clear: true })`, cleared to its skeleton at once; tiles out of range drop their data and
  run when they come into range; types that report status get `tick({ clear: true })`; the
  assignment lists clear to skeleton rows and re-read `assignments/summary` (request R6(a)). A
  polite status announces "Refreshing the dashboard", then "Dashboard updated" when the tiles in
  range settle.
- **A tile's Refresh** clears and re-runs that tile only. Both reset the due times from the end of
  the new runs.
- **A run in flight** when Refresh is pressed is aborted and restarted (0034's `resource()` key).

#### §11.4 Returning to a dashboard

- On destroy the page remembers `{ args, held: { key → { result, executedAt, endedAt } }, scroll }`
  under `/{t}/dashboards/{id}` (`TmPageState`, 0025 §10; memory only).
- A return within the SPA renders each held result at once through the host's `held` input
  (request R4(b)), restores the scroll, and runs silently every tile whose due time has passed, or,
  for tiles without an interval, whose result is older than 5 minutes.

### §13 Edit mode

Edit mode rearranges, resizes, adds, configures and removes widgets in place, on the details
host's working copy. Save writes the dashboard and its widgets in one `dashboards/save`.

#### §13.1 Entering and leaving

- **Edit** is 0031's `edit()`; the hatch swaps the grid for `TmDashboardEditor` (deferred chunk,
  prefetched on hover or focus of Edit). Drafts, leave guard and concurrency dialog are 0031's; a
  reload restores edit mode from the draft.
- **While editing** tiles stay live (a move or resize re-runs nothing; a new or reconfigured
  report widget runs once), auto refresh pauses, and bodies are `inert`.
- **Identity.** Tiles track by `w{Id}`; a row without an id gets `n{k}` when it enters the editor,
  kept in a key list parallel to `form.Widgets`.

#### §13.2 The canvas

- A toolbar row ("Add widget", "Dashboard settings") over the canvas, which always shows the wide
  layout: at the grid's width from `md` up, at a fixed 768 px in a horizontally scrolling region
  below. While dragging, twelve dashed column guides and a drop placeholder show; nothing animates.
- Each tile gains a header grip (a `button` "Move or resize {title}") and a pointer-only resize
  handle at its block-end, inline-end corner.

#### §13.3 Moving and resizing

```ts
declare function tmMoveWidget(widgets: readonly TmDashboardWidgetModel[], key: string, x: number, y: number): readonly TmDashboardWidgetModel[];
declare function tmResizeWidget(widgets: readonly TmDashboardWidgetModel[], key: string, w: number, h: number): readonly TmDashboardWidgetModel[];
```

1. **Clamp** the target into the grid and to the type's `minSize` (and `h` ≤ 24).
2. **Push.** Every tile the target overlaps moves down to just below it, and so on for the tiles
   those overlap (a cascade in `(y, x)` order).
3. **Compact** every tile, the moved one included (§8.2 rule 1). The result is what Save sends.

| Input | Move | Resize |
|---|---|---|
| pointer | drag the grip (pointer capture; snaps to cells; Escape cancels) | drag the corner handle |
| keyboard, focus on the grip | Up, Down; Left and Right map to the visual direction (in RTL Left is inline-end) | Shift + arrows: Up and Down change `h`; the visual arrows grow or shrink `w` |
| single click (WCAG 2.5.7) | tile menu Move ▸ Up, Down, To start, To end | tile menu Size ▸ Quarter (3), Third (4), Half (6), Two thirds (8), Full width (12), Taller (+3), Shorter (−3) |

- Each change announces politely: "Sales by center: row 3, column 7, 6 columns by 9 rows." A key
  that cannot move the tile announces "Can't move further."
- Every operation writes the working copy through `injectTmDetails().update(…)`, so drafts follow.

#### §13.4 Adding, configuring, removing

- **Add widget** opens the gallery (`TmModal` `md`, full screen below `sm`) with a
  `tm-segmented`: **Reports** (a search over `reports/browse { scope: All }`, coded reports the user
  may run first, 0034 §11's rows) and **Other** (registered types the user may add: `requires`
  passes). Choosing one appends it at `x = 0` below the lowest tile, at its `defaultSize`, compacts,
  focuses its grip and announces "Added Monthly sales." For a report with a required parameter
  that same-key binding leaves unbound, the widget dialog opens at once.
- **Edit widget…** (`TmModal` `md`): Title and Description in each tenant language (one field per
  content slot); "Refresh" (`tm-segmented`: "Dashboard default ({n} min)" / "Every … minutes",
  min `MinRefreshMinutes` is checked by the server); for report widgets a **Parameters** table, one
  row per report parameter: label, then a `tm-select` "Same as dashboard parameter {X}" (shown when
  a same-key parameter exists) / "Dashboard parameter…" / "Fixed value" / "Report default"; a fixed
  value uses 0034's typed field (request R4(d)); "Report default" is refused for a required
  parameter without a default (§5.3 rule 3, shown inline). Other types render their
  `settingsEditor`, which writes `settings`.
- **Remove** (tile menu, or Delete on the grip) removes the tile at once with no confirmation
  (Cancel restores everything) and moves focus to the next tile's grip, else the previous, else
  Add widget.

#### §13.5 Dashboard settings

- `TmModal` `md`: Title in each content slot, Code, "Refresh every … minutes" (empty = never), and
  the parameter list (`tm-reorder-list`, 0023): each item Key, Label per slot, Type, Entity (an
  entity picker over queryable entities, `Numeric` only), Required. Removing a parameter that
  widgets bind shows the affected tiles' names before it applies.

#### §13.6 Save, errors, create, Save as

- **Save** is 0031's `save()`: `dashboards/save` with `Widgets` synchronized (new rows have no id,
  removed rows are absent) and `Shares: null` (untouched).
- **Errors** map by path: `Widgets[i].*` errors mark tile *i* with an error outline and icon; the
  inline summary item focuses its grip or opens its dialog; `ParametersJson/*` errors open the
  settings dialog at the field.
- **Create** (`/{t}/dashboards/new`, "New dashboard" on the search page) opens the same page in
  create mode: the editor with an empty canvas and the empty state "Add your first widget"; Title
  defaults to "Untitled dashboard" (`tm.dashboard.untitled`).
- **Save as** is 0031's clone (`?clone={id}`) with the declaration's `clone` member (§12.1):

## 4. Open questions owned

**Dashboards Q1 — how do dashboard-level parameters reach the reports?** Same-key binding by
default: a report parameter takes the dashboard parameter with its key, ignoring case, with zero
configuration. A widget may bind a report parameter explicitly to another dashboard parameter or to
a fixed value, which overrides the key match. Dashboard parameters carry no default: an unset one
sends nothing, so each report applies its own default; a required one makes its tiles wait for a
value. The host sends each report only the parameters it declares. *Alternatives:* (a) one shared
key only (A§10.1's minimum: the same report could not show 2025 and 2026 side by side, and keys
must be agreed across authors); (b) a mandatory mapping per widget (configuration for the 90 % case
that the key already answers); (c) dashboard default expressions evaluated by `dashboards/get`
(stale after midnight on a wall display unless re-read); (d) the server binding widgets inside
`reports/run` from `WidgetId` (couples 0033's run to 0035's tables, and coded reports would still
bind on the client). *Why:* zero configuration in the common case, one client rule for stored and
coded reports, and no evaluator anywhere new (§10).

**Home research, Part 4, settled here:** Q1 — 12 columns of 30 px rows (§8.1); Q2 — no
per-breakpoint layouts, two arrangements (§8.2); Q6 — the platform default is code
(`TM_HOME_WIDGETS`), not a seeded row (§15.3); Q7 — no parameters on home in v1; Q8 — private
dashboards surface on the dashboards page only (§14). Q3–Q5 and Q9 wait with per-user homes.

**Deviations from the home research** (A§10.2 settles the sharing one):

| Research | This design | Why |
|---|---|---|
| D1 home is a resolved, stored dashboard | home renders through the same grid from a code model; no stored home row | swapping is deferred (A§1); warm launch (§15.6) |
| D2 widget, parameter and role child tables | three tables; parameters in `ParametersJson`; visibility through `DashboardShares` | one list always read whole; 0033's share model (A§10.2) |
| D3 sizes and securables in the server registry | the server registers key and settings; sizes and `requires` are client declarations | sizes are presentation; the client gates by `TmPermissions` |
| D4 stored `Ordinal`, compaction on save | no `Ordinal`; reading order derived; compaction at render and in the editor | one truth (decision 4) |
| D5–D8 pointer, rules, forks, locks, reset | deferred; seam §15.6 | A§1, A§12 #25 |
| D9, D10 catalogue with Menu, Inbox, Text, Links, Image | report, two assignment lists, recents | the brief's default; the registry admits more |
| D11 Customize mode with undo | edit mode on 0031's host; Cancel, no undo | one lifecycle |
| D12 inactivity pause | none | wall displays |
| D14 `OwnerId` cleared on publish; role visibility rows | 0033's owner, user and role shares at View or Edit | A§10.2 |

## 11. Review flags

1. **Dashboard parameters have no default expression** (decision 7). Alt: defaults evaluated by
   `dashboards/get`. Flips if authors need a dashboard-wide default that differs from their
   reports' own.
2. **Widgets hidden from viewers who cannot read their data** (decision 12). Alt: a placeholder for
   everyone. Flips if users report "missing" widgets they expected to see.
3. **Two layouts, no medium band** (decision 3). Alt: halve widths at `md`. Flips if tablet
   telemetry shows cramped tiles at 768–991 px.
4. **Fixed tile heights, home lists included** (decision 3). Alt: content heights. Flips if a
   sparse home (two assignments in a 350 px tile) reads as broken.
5. **First name by a first-token rule** (decision 17). Alt: a `User.ShortName` group (0014, 0018
   edits). Flips on wrong-name reports from real tenants.
6. **Refresh floor 1 minute; no inactivity pause** (§11). Alt: a 5-minute floor; pause after 30
   minutes idle. Flips on server load from wall displays.
7. **Runs gated to 480 px around the viewport, six in flight** (§11.1). Alt: run every tile at
   once. Flips if users print or export long dashboards and find unloaded tiles.
8. **At most 24 widgets** (decision 23). Alt: 40. Flips if real dashboards hit the cap.
9. **Coded reports as widgets, checked only by the editor** (decision 15). Alt: stored
   definitions only.
10. **A tile's own Refresh clears it** (decision 10). Alt: silent. Flips if users find the flash
    jarring.
11. **"Updated 10:42", not "2 min ago"** (decision 11). Alt: relative time.
12. **Widget types registered on both sides** (decision 5). Alt: client-only keys with opaque
    settings. Flips if distributions find the second line a burden.
13. **Narrow home order: My assignments, Recently visited, Assigned by me** (§15.3). Alt: a stored
    order. Flips if phone users want both assignment lists first.
14. **No Mine / Shared tabs on the dashboards page** (decision 22). Alt: 0034's tabs through a
    generic `browse`. Flips past ~20 dashboards per tenant.
15. **Edit mode at every width, a 768 px canvas below `md`** (§13.2). Alt: Edit only from `md`.
16. **No undo in edit mode** (D11 deviation). Alt: a session command stack. Flips on lost-work
    reports from Cancel.
17. **Home swapping deferred** (A§12 #25). Alt: ship D5 now. Flips on a customer need this round.

## 12. Challenges to the architecture

1. **A§1's 0035 row lists no dependencies and A§6.3 has no 0035 rows** beyond 0014 §2's resource,
   yet dashboards need edits to 0011 (contribution items, provisioning order), 0013 (keys), 0016
   (routes, policy), 0021 (a notification type) and 0018 (Acme's seed). Followed with section 5.
2. **0031 §3.7 says the `page` hatch's page context stays the host's**, while A§5.10 and 0026 §9.3
   give dashboards their own `dashboard` kind (recents count it, 0025 §13; `details` never counts).
   Followed A§5.10: the hatch registers `dashboard`, replacing the host's context; request R8(a)
   keeps the host's actions.
3. **A§2.2's flowchart draws `/dashboards` from `/reports` only.** `/dashboards` also imports
   `/details` and `/attention`, and reaches `/reports` through `import()` alone, so the home route
   stays small (decision 24). Additive edges.
4. **A§10.1's Dashboards Q1 answer** is followed and refined: fixed-value bindings, and no
   dashboard defaults (section 4).
5. **A§8's "edit mode edits the layout"** understates it: edit mode also edits widget settings and
   the dashboard's settings and parameters (§13). Wording only.
6. **A§9 places component reflow on container queries**; the grid follows it, so a grid inside a
   narrower hatch region goes narrow on its own width, not the viewport's. Followed; noted because
   the home and dashboard pages otherwise read like page layout.
