## 2. Decisions

1. **A hand-off log: one row per hand-off, at most one `Open` row per target** (filtered unique
   index, §2.1). Why: "by me" and "returned to me" need the replaced hand-off. Alt: a mutable row
   per target with temporal history (Queryex cannot read `FOR SYSTEM_TIME`); a second history table.
2. **`IAssignments` is a platform composer on 0012's internal channel, like `INotifier`** (§3.1):
   fixed text on the caller's batch, no extra round trip. Alt: an `Enlist` stack written through
   `IEnlists<Assignment>` by every document service (validators and a marker per writer for a
   derived row).
3. **`[Assignable]` is a stack capability whose delete effect withdraws open rows** (§3.4). Why:
   rule 1, no module forgets the cleanup. Alt: each module withdraws on delete by hand.
4. **States `Open`, `Handed`, `Completed`, `Withdrawn`** (§2.3). Alt: a bool plus a reason column.
5. **"Returned" is derived at insert** (`IsReturn`, §3.2). Alt: a request flag every module computes.
6. **Captions are language-neutral data rendered at read time** (§11.3), as notifications are.
   Alt: a stored rendered title (one language).
7. **The summary carries both home lists and the actors** (§4.3), so tray and home render warm.
   Alt: two `assignments/query` calls on home (network before the lists).
8. **`assignments.changed` reaches every party** (assignees and assigners, §4.5). Alt: assignees
   only (challenge 1).
9. **Closed rows live 180 days** (§4.7). Alt: forever (the document keeps its own history).
10. **Badges render from stored leader documents; opening a panel hides or neutralizes the badge
    in the frame, calls `seen`, then refreshes the document itself** (§5.3). Alt: wait for the
    leader's refresh (the badge lingers a round trip).
11. **Arrival toasts are decided per tab from document diffs, shown only by the visible, focused
    tab, armed after its first fresh copy** (§8.2). Alt: the leader decides (a hidden leader cannot
    know where the user looks). Feedback toasts stay the acting feature's `TmToasts.show` call.
12. **`TmBanners` gates only height changes, announces at queue time, and applies at once on a
    hidden page or the user's own dismiss** (§9.3, §9.4). Alt: gate swaps too; announce on entry
    (a typing keyboard user would wait indefinitely).
13. **The job ring shows for `Pending` and `Running`, not `Held`** (§6.2): a held job waits on an
    administrator. Alt: all three.
14. **Attention verbs are hidden on a read-only tenant** (§5.4; 0011 refuses mutations). Alt:
    reclassify them as non-mutations.
15. **Read on visit over the stored `Latest`** (§6.5). Alt: read only on a click in the bell.
16. **Notification settings save automatically** (§10.3). Alt: an explicit Save button.
17. **Job labels at enqueue (`LabelKey` + arguments) with a handler fallback; an `entity` argument
    renders as the plural label** (§11.2). Alt: a label stored in the requester's language.
18. **Live progress through an early renewal at ≥ 5 points (≥ 5 s apart) and through `Append`**
    (E8). Alt: shorter leases (more renewals for every job).
19. **The four pages are CRUD-framework declarations; the missing host members are general
    requests to 0030** (§10). Alt: four `search`-hatch bodies. **No push reloads a page** (rule
    2D): events refresh named rows in place, otherwise a Refresh dot.
20. **The update banner reads "A new version is available."** (§9.5). Alt: A§7.5's text
    (challenge 5).
21. **No platform assignment email** (§3.6): a module raises its own channel-only type. Alt: a
    platform type (needs a caption nested inside ICU text, which 0013's renderer cannot do).

**Vocabulary**

- *Input-idle gate* — the 2 s without key, pointer or wheel input that a banner's entry or exit

### §2 `core.Assignments` and the `Assignment` entity

The table is a hand-off log. Each `Assign` closes the target's open row and inserts a new one, so
"assigned by me", "returned to me" and the target's trail are plain reads.

#### §2.1 The table

Non-temporal; `[TableType]` (fixture tier only); sequence `core.sq_Assignments START WITH 1000`;
written only by the statements of §3 and the retention deletes of §4.7; carries no version tag.

| Column | Type | Null | Constraints | Notes |
|---|---|---|---|---|
| `Id` | `int` | no | PK clustered; `CK_Assignments_Id CHECK ([Id] > 0)` | reserved inside the assign statement |
| `Resource` | `varchar(128)` | no | | the target's entity name, an `[Assignable]` stack resource |
| `TargetId` | `bigint` | no | | the target row's id |
| `State` | `varchar(9)` | no | | `AssignmentState` as text |
| `AssigneeId` | `int` | no | `FK_Assignments_AssigneeId → core.Users(Id)` | an active individual at assign time |
| `AssignedById` | `int` | yes | `FK_Assignments_AssignedById → core.Users(Id)` | null: the system |
| `AssignedAt` | `datetimeoffset(3)` | no | | the hand-off time |
| `IsReturn` | `bit` | no | `DF_Assignments_IsReturn 0` | §3.2 |
| `Comment` | `nvarchar(1024)` | yes | | the assigner's note |
| `CaptionJson` | `nvarchar(4000)` | yes | | §11.3 |
| `ClosedAt` | `datetimeoffset(3)` | yes | `CK_Assignments_Closed ((State = 'Open' AND ClosedAt IS NULL) OR (State <> 'Open' AND ClosedAt IS NOT NULL))` | |

| Index | Key | Include | Filter | Serves |
|---|---|---|---|---|

| `IX_Assignments_Assigner` | `(AssignedById, AssignedAt DESC, Id DESC)` | `(State, AssigneeId)` | `AssignedById IS NOT NULL` | `OpenByMe`, `LatestByMe`; the "by me" page |

- The plan test of note section 10 pins every summary seek. No `ON DELETE CASCADE` (a user is
  never deleted after `New`).
- No foreign key reaches the target: the target lives in any stack's table. The delete effect of
  §3.4 keeps the two consistent.

#### §2.2 The entity and its stack

```csharp
// Tellma.Core.Abstractions.Assignments
public enum AssignmentState { Open, Handed, Completed, Withdrawn }

public sealed class Assignment : Entity<int>   // [Table("Assignments", Schema = "core")], [TableType], [Stack(Operations = Query | Details)]
{
    public string Resource { get; set; }            // every member server-owned; never written through Save
    public long TargetId { get; set; }
    public AssignmentState State { get; set; }
    public int AssigneeId { get; set; }             // navigation Assignee
    public int? AssignedById { get; set; }          // navigation AssignedBy
    public DateTimeOffset AssignedAt { get; set; }  // datetimeoffset(3)
    public bool IsReturn { get; set; }
    public string? Comment { get; set; }
    public string? CaptionJson { get; set; }        // not [JsonColumn] (nvarchar(4000)); the client parses it
    public DateTimeOffset? ClosedAt { get; set; }   // datetimeoffset(3)
    public int? ClosedById { get; set; }            // navigation ClosedBy
}
```

- **A system-written entity** (spec 0012): `Entity<int>`, no audit set, no concurrency token. The
  stack is `Query | Details`: `query`, `get`, `get-by-ids`; no save, delete, actions or Excel, so
  MCP sees it read-only. Segment `assignments`; entity name and securable resource
  `core.Assignment` (`CoreResources.Assignment`, 0014 edit). `[DefaultSelect]` is every column.
- **Default order** `AssignedAt desc, Id desc` (`StackDescriptor.DefaultOrderBy`, A§6.3 row 0015
  §1.2). Navigations `Assignee`, `AssignedBy`, `ClosedBy` project spec 0012's default related
  projection (`Id`, the `Name` group, `ImageId`).
- **Self-scope.** `AssignmentAccessCriteria : IAccessCriteriaProvider` (`Resource =
  "core.Assignment"`) returns `AccessCriterion("Read", FilterTree.Leaf("AssigneeId = me() or
  AssignedById = me()"), "self")` for every user: each member reads the rows assigned to them and
  by them, with no role. A stored grant on `core.Assignment × Read` widens it (a supervisor seeing
  who is sitting on what); none is seeded.

#### §2.3 States and transitions

| From | To | By |
|---|---|---|
| (none) | `Open` | `Assign` |
| `Open` | `Handed` | the next `Assign` of the same target (`ClosedById` = the new row's assigner) |
| `Open` | `Completed` | `Complete` (the work is done: posted, approved, closed) |
| `Open` | `Withdrawn` | `Withdraw` (recalled, cancelled), and the delete effect (§3.4) |

- Closed states are terminal; nothing reopens a row. Assigning a target whose assignment completed
  starts a new `Open` row; `IsReturn` looks only at an `Open` row being replaced (§3.2).
- **Deactivating a user** changes nothing: their open rows stay so the work is not lost, and the
  module reassigns. The Assignments page's `all` tab with an `Assignee.IsActive` filter finds them
  (§10.4).

### §3 Writing assignments

The module that owns a target writes its assignments in the same batch as the change that causes
them, through `IAssignments` or one line of context sugar. The platform composes fixed-text
statements on the internal channel, as it does for notifications.

#### §3.1 Contracts

```csharp
// Tellma.Core.Abstractions.Assignments
[AttributeUsage(AttributeTargets.Class)]
public sealed class AssignableAttribute : Attribute;          // on the entity: capability "assignable" (§3.4)

public sealed record AssignmentCaption(
    string? Code = null,                                      // the target's short reference "INV-0023"; null: the id
    decimal? Amount = null, string? Currency = null,          // rendered "SAR 12,400.00"; Currency an ISO 4217 code
    object? Detail = null);                                   // ICU arguments of Assignment_<Resource>_Detail (§11.3)

public sealed record AssignmentRequest(
    string Resource, long TargetId, int AssigneeId, string? Comment = null, AssignmentCaption? Caption = null,
    int? AssignedById = null);                                // null: RequestContext.UserId in a user scope, the system in a system scope

public interface IAssignments                                 // scoped
{
    void Assign(IDataBatch batch, IReadOnlyList<AssignmentRequest> requests);
    void Complete(IDataBatch batch, string resource, IReadOnlyList<long> targetIds);
    void Withdraw(IDataBatch batch, string resource, IReadOnlyList<long> targetIds);
    Task AssignAsync(IReadOnlyList<AssignmentRequest> requests);              // own Persist batch, current scope
    Task CompleteAsync(string resource, IReadOnlyList<long> targetIds);
    Task WithdrawAsync(string resource, IReadOnlyList<long> targetIds);
}

// Tellma.Core.Abstractions.Crud (0015 edit): on PersistContext<TEntity> and ActionContext<TEntity, TKey>
public BatchAssignments Assignments { get; }                   // bound to the context's Batch and its stack's Resource

public sealed class BatchAssignments
{
    public void Assign(long targetId, int assigneeId, string? comment = null, AssignmentCaption? caption = null);
    public void Complete(IReadOnlyList<long> targetIds);
    public void Withdraw(IReadOnlyList<long> targetIds);
}

public sealed class AssignmentsOptions                         // Tellma:Assignments; validated at startup
{
    public int MaxRequestsPerCall { get; set; } = 10000;
    public int MaxCommentChars { get; set; } = 1024;          // ≤ 1024 (the column)
    public int MaxCaptionChars { get; set; } = 4000;          // ≤ 4000 (the column)
    public int SummaryCountCap { get; set; } = 100;           // ≤ 1000
    public int SummaryLatestCount { get; set; } = 10;         // ≤ 50
    public TimeSpan ClosedRetention { get; set; } = TimeSpan.FromDays(180);
    public int RetentionPageSize { get; set; } = 1000;        // ≤ 10000
}
```

- **Synchronous and append-only.** Each call appends one statement (§3.2, §3.3) to `batch`,
  registers the batch's one post-commit callback (§4.5) and returns. No id comes from the
  allocator's buffer; nothing awaits.
- **Programmer errors** (`InvalidOperationException`, a 500 with a trace id), checked in C# before
  anything is appended: `Resource` is not an `[Assignable]` stack resource; `TargetId` or
  `AssigneeId` not positive; a target twice in one call; `Comment` over `MaxCommentChars`; the
  serialized caption over `MaxCaptionChars`; more than `MaxRequestsPerCall` requests or ids. An
  empty list appends nothing.
- **Parameters:** one TVP for `Assign`; one TVP and three scalars for a close.
- **Where it runs.** `ContributeAsync` and every `[EntityAction]` method (through the context's
  `Assignments`); a job handler on `JobBatch.Batch`; an `[ApiAction]` on its open frame's batch;
  the `*Async` forms from code holding no batch. The internal channel is not subject to
  `CallerAuthority` (0012 §5.2 edit), so a job may write assignments of any assignable stack.

**Example —** Acme's sales invoice, the whole module side (the entity carries `[Assignable]`):

```csharp
[EntityAction("assign")]                                          // POST …/sales-invoices/assign { ids, arguments }
public Task AssignAsync(ActionContext<SalesInvoice, int> context, AssignInvoiceArguments args)
{
    foreach (var invoice in context.Entities)
        context.Assignments.Assign(invoice.Id, args.AssigneeId, args.Comment,
            new AssignmentCaption(invoice.SerialNumber, invoice.Total, invoice.CurrencyId));
    return Task.CompletedTask;
}

// in the post action, after its own statements:
context.Assignments.Complete(context.Entities.Select(i => (long)i.Id).ToList());
```

#### §3.2 The assign statement

`@tb{b}_t0 : AssignmentRequestList` (`Ordinal int PK`, `Resource varchar(128)`, `TargetId bigint`,
`AssigneeId int`, `AssignedById int NULL`, `Comment nvarchar(1024) NULL`, `CaptionJson
nvarchar(4000) NULL`), one row per request, `Ordinal` from 0. `SqlOptions(Writes =
[core.Assignments], ResultSets = 1)`.

```sql
-- ASSIGN (IAssignments.Assign; ids reserved here, never from the allocator's buffer)
DECLARE @tb{b}_now datetimeoffset(3) = SYSUTCDATETIME();
IF EXISTS (SELECT 1 FROM @tb{b}_t0 AS [r] LEFT JOIN [core].[Users] AS [u] ON [u].[Id] = [r].[AssigneeId]
           WHERE [u].[Id] IS NULL OR [u].[IsActive] = 0 OR [u].[Kind] <> 'Individual')
    THROW 50422, N'Assignments.AssigneeInvalid', 1;
DECLARE @tb{b}_closed TABLE ([Resource] varchar(128) NOT NULL, [TargetId] bigint NOT NULL, [AssigneeId] int NOT NULL,
                             [AssignedById] int NULL, PRIMARY KEY ([Resource], [TargetId]));
UPDATE [a] SET [State] = 'Handed', [ClosedAt] = @tb{b}_now, [ClosedById] = [r].[AssignedById]
OUTPUT [deleted].[Resource], [deleted].[TargetId], [deleted].[AssigneeId], [deleted].[AssignedById] INTO @tb{b}_closed
FROM [core].[Assignments] AS [a]
INNER JOIN @tb{b}_t0 AS [r] ON [r].[Resource] = [a].[Resource] AND [r].[TargetId] = [a].[TargetId]
WHERE [a].[State] = 'Open';
DECLARE @tb{b}_first sql_variant, @tb{b}_n int = (SELECT COUNT(*) FROM @tb{b}_t0);
EXEC sys.sp_sequence_get_range @sequence_name = N'core.sq_Assignments', @range_size = @tb{b}_n, @range_first_value = @tb{b}_first OUTPUT;
INSERT INTO [core].[Assignments] ([Id], [Resource], [TargetId], [State], [AssigneeId], [AssignedById], [AssignedAt], [IsReturn], [Comment], [CaptionJson])
SELECT CAST(@tb{b}_first AS int) + [r].[Ordinal], [r].[Resource], [r].[TargetId], 'Open', [r].[AssigneeId], [r].[AssignedById], @tb{b}_now,
       CASE WHEN [c].[AssignedById] = [r].[AssigneeId] THEN 1 ELSE 0 END, [r].[Comment], [r].[CaptionJson]
FROM @tb{b}_t0 AS [r]
LEFT JOIN @tb{b}_closed AS [c] ON [c].[Resource] = [r].[Resource] AND [c].[TargetId] = [r].[TargetId];
SELECT [AssigneeId] AS [UserId] FROM @tb{b}_t0
UNION SELECT [AssignedById] FROM @tb{b}_t0 WHERE [AssignedById] IS NOT NULL
UNION SELECT [AssigneeId] FROM @tb{b}_closed
UNION SELECT [AssignedById] FROM @tb{b}_closed WHERE [AssignedById] IS NOT NULL;   -- the event's recipients (§4.5)
```

- **The assignee check** runs first: a missing, inactive or non-individual assignee aborts the
  batch with `50422`, which spec 0015 §14.2 reports as the validation error
  `Assignments.AssigneeInvalid` at the root (0012 §6.3 edit lists the code). A module validates its
  assignee field earlier for a field-level message; the check is the fence.
- **A hand-off to the same assignee** is still a hand-off: a new `Open` row with a fresh
  `AssignedAt` and the new comment, so it is new again in the assignee's tray.
- **`IsReturn`** is 1 when the new assignee assigned the row being replaced: Farah assigned to
  Omar; Omar assigns back to Farah; Farah's row reads "Returned by Omar Haddad".
- **Races.** The `UPDATE` locks the open row, so two hand-offs of one target serialize. Two
  batches that both found no open row both insert; the second raises 2601 on
  `UX_Assignments_OpenTarget`, which spec 0015 §14.2 maps to `Unique` at the root, and the user
  retries.

#### §3.3 The close statement (complete, withdraw)

`@tb{b}_t0 : BigIdList` (the target ids), `@tb{b}_p0 varchar(128)` the resource, `@tb{b}_p1
varchar(9)` `Completed` or `Withdrawn`, `@tb{b}_p2 int` the actor (`RequestContext.UserId`, null in
a system scope). `SqlOptions(Writes = [core.Assignments], ResultSets = 1)`; idempotent.

```sql
-- CLOSE (IAssignments.Complete / Withdraw; the delete effect binds the deleted-key table instead of @tb{b}_t0)
DECLARE @tb{b}_users TABLE ([AssigneeId] int NOT NULL, [AssignedById] int NULL);
UPDATE [a] SET [State] = @tb{b}_p1, [ClosedAt] = SYSUTCDATETIME(), [ClosedById] = @tb{b}_p2
OUTPUT [deleted].[AssigneeId], [deleted].[AssignedById] INTO @tb{b}_users
FROM [core].[Assignments] AS [a] INNER JOIN @tb{b}_t0 AS [t] ON [t].[Id] = [a].[TargetId]
WHERE [a].[Resource] = @tb{b}_p0 AND [a].[State] = 'Open';
SELECT [AssigneeId] AS [UserId] FROM @tb{b}_users UNION SELECT [AssignedById] FROM @tb{b}_users WHERE [AssignedById] IS NOT NULL;
```

- A target with no open row changes nothing; repeating a close is harmless.

#### §3.4 `[Assignable]`: the capability, the delete effect, the trail extra

- **Capability.** `[Assignable]` on an entity adds `assignable` to the stack's
  `StackDescriptor.Capabilities` (0015 edit) and so to the client metadata's entity section (0029):
  the client knows which entities can be assigned.
- **The delete effect.** The realizer registers `AssignableDeleteEffect<T> : IPersistEffect<T>` for
  each assignable stack. On a `DeletePersistContext<T>` (delete by ids, by query, with
  descendants, and an enlisted delete) it appends §3.3's statement with `Withdrawn`, binding
  `context.AffectedIds` as the target list. The tray never shows a row whose target is gone.
- **The trail extra.** The realizer also registers `AssignmentTrailContributor<T> :
  IDetailsContributor<T>` with the extra name `assignments` (§4.4), so a details page can show
  "With Omar Haddad since 2 h" and the hand-off history with no module code.
- **Startup check `assignments`:** every `[Assignable]` entity has a stack with `Query` and
  `Details` (a target the tray can open through `TmUrls.target`); the options are within bounds.
- **Ordering.** Statements run where they are appended: a module that saves and assigns in one
  action appends the assign after its own write; two `Assign` calls for one target in one batch
  are two hand-offs.

#### §3.5 What a distribution writes

| Need | Lines |
|---|---|
| Make an entity assignable | `[Assignable]` on the class (1) |
| Assign, return, reassign | one `context.Assignments.Assign(...)` in the action that hands the document on (1–3) |
| Close on posting or approval | one `context.Assignments.Complete(ids)` (1) |
| A detail line under the title | one resx key per language, `Assignment_<Resource>_Detail` (§11.3) |
| Delete cleanup, tray, badges, toasts, home lists, pages, events | nothing |
| Email on assignment (uncommon) | its own channel-only notification type (§3.6) |

#### §3.6 Assignment email (the hatch)

The platform raises no notification for an assignment. A module that wants email or push
registers a channel-only type (`Inbox = false`, spec 0021 §2.3) and raises it in the same batch:

#### §4.3 The summary

```csharp
// Tellma.Core.Abstractions.Assignments
public sealed record AssignmentsSummary(
    int Open, int New, int OpenByMe,                 // capped at SummaryCountCap (99+ in the UI)
    DateTimeOffset? SeenAt,                          // the caller's AssignmentsSeenAt: rows after it carry "New"
    IReadOnlyList<Assignment> Latest,                // ≤ SummaryLatestCount open rows assigned to the caller, newest first
    IReadOnlyList<Assignment> LatestByMe,            // ≤ SummaryLatestCount open rows the caller assigned to others, newest first
    RelatedEntities Related);                        // core.User: assigners of Latest, assignees of LatestByMe (0012 related projection)
```

One `Read` batch through `IGuardedBatchRunner.Run(Read, …)`, `ResultSets = 4`, `@tb{b}_p0 =
SummaryCountCap`, `@tb{b}_p1 = SummaryLatestCount`:

```sql
DECLARE @tb{b}_seenAt datetimeoffset(3) = (SELECT [AssignmentsSeenAt] FROM [core].[UserStamps] WHERE [UserId] = @tm_UserId);
SELECT
  (SELECT COUNT(*) FROM (SELECT TOP (@tb{b}_p0) 1 AS [x] FROM [core].[Assignments]
     WHERE [AssigneeId] = @tm_UserId AND [State] = 'Open') AS [o]) AS [Open],
  (SELECT COUNT(*) FROM (SELECT TOP (@tb{b}_p0) 1 AS [x] FROM [core].[Assignments]
     WHERE [AssigneeId] = @tm_UserId AND [State] = 'Open' AND [AssignedAt] > COALESCE(@tb{b}_seenAt, '0001-01-01')
       AND ([AssignedById] IS NULL OR [AssignedById] <> @tm_UserId)) AS [n]) AS [New],
  (SELECT COUNT(*) FROM (SELECT TOP (@tb{b}_p0) 1 AS [x] FROM [core].[Assignments]
     WHERE [AssignedById] = @tm_UserId AND [State] = 'Open' AND [AssigneeId] <> @tm_UserId) AS [b]) AS [OpenByMe],
  @tb{b}_seenAt AS [SeenAt];
DECLARE @tb{b}_rows TABLE ([List] tinyint NOT NULL, [Id] int NOT NULL PRIMARY KEY, [UserId] int NULL);
INSERT INTO @tb{b}_rows SELECT TOP (@tb{b}_p1) 0, [Id], [AssignedById] FROM [core].[Assignments]
  WHERE [AssigneeId] = @tm_UserId AND [State] = 'Open' ORDER BY [AssignedAt] DESC, [Id] DESC;
INSERT INTO @tb{b}_rows SELECT TOP (@tb{b}_p1) 1, [Id], [AssigneeId] FROM [core].[Assignments]
  WHERE [AssignedById] = @tm_UserId AND [State] = 'Open' AND [AssigneeId] <> @tm_UserId ORDER BY [AssignedAt] DESC, [Id] DESC;
SELECT [r].[List], [a].* FROM @tb{b}_rows AS [r] INNER JOIN [core].[Assignments] AS [a] ON [a].[Id] = [r].[Id]
ORDER BY [r].[List], [a].[AssignedAt] DESC, [a].[Id] DESC;
DECLARE @tb{b}_users TABLE ([Id] int NOT NULL PRIMARY KEY);
INSERT INTO @tb{b}_users SELECT DISTINCT [UserId] FROM @tb{b}_rows WHERE [UserId] IS NOT NULL;
-- then Query<User> with the related projection and KeySetRestriction("Id", "@tb{b}_users") (spec 0012 §5.2)
```

- **Cost:** capped seeks on `IX_Assignments_Assignee` and `IX_Assignments_Assigner`; one round
  trip warm. `NoActivityStampMetadata` (applied by 0024's E18): polling never keeps a session alive.
- **Self-assigned rows** count in `Open` and `Latest`, never in `New`, `OpenByMe` or `LatestByMe`.

#### §4.5 The `assignments.changed` event

- **Registered** by `CoreFeature` through `FeatureContribution.ClientEvent("assignments.changed")`;
  payload none (0021 §6.3 catalogue row, edit).
- **Published once per batch:** the first assign or close on a batch registers one `OnCommitted`
  callback that unions the user ids every statement returned (new and old assignees, assigners of
  new and closed rows) and calls `IClientEventPublisher.PublishAsync(new ClientEvent(
  "assignments.changed", userIds, null))`. `seen` publishes to the caller on its own batch.
  Failures are logged (`AssignmentsEventFailed`), never thrown.
- **Recipients' leaders** refresh the `assignments` document (§5.1); nothing else listens.

#### §4.6 Securables and MCP

- `core.Assignment × Read` only, registered by the stack, held by every member through the
  self-scope (§2.2). No sensitive pair. `summary` and `seen` are member-only.
- MCP: `tellma_query` and `tellma_get` over `core.Assignment` answer under the self-scope.

#### §4.7 Retention

- `[JobHandler("core.assignment-retention", LeaseSeconds = 600)]`, a `Maintenance` batch per page:
  `DELETE TOP (@tb{b}_p0) FROM [core].[Assignments] WHERE [State] <> 'Open' AND [ClosedAt] <
  DATEADD(second, -@tb{b}_p1, SYSUTCDATETIME());` until a page deletes fewer than
  `RetentionPageSize` rows. Open rows are never deleted.
- Built-in schedule `BuiltInSchedule(8, "core.assignment-retention", "15 4 * * *")` (0020 §7.9
  table edit; id 7 is 0022's).

#### §4.8 Composition, telemetry, logs

  `Scoped<IAssignments, AssignmentsWriter>()`, `Singleton<IAccessCriteriaProvider,
  AssignmentAccessCriteria>()`, the `[Assignable]` realizer, `ClientEvent("assignments.changed")`,
  `JobHandler<AssignmentRetentionHandler>()`, the built-in schedule, `Options<AssignmentsOptions>`,
  the `AssignmentRequestList` table type and the startup check `assignments`.
- **Meter `Tellma.Core`:** `tellma.assignments.written` (counter, `{assignment}`, tags `op ∈ assign

### §5 The client attention model

Every tab renders the bell, the tray and the home lists from the two stored attention documents.
Only the leader refreshes them on events; a tab that opens a panel refreshes them once itself.

#### §5.1 Leader documents

`provideTellma` adds 0028's two `TM_LEADER_DOCUMENTS` entries (N25 §8.6), primary entry point:

```ts

  { name: 'inbox', route: 'inbox/summary', events: ['inbox.changed', 'job.changed'], formatVersion: 1 },
  { name: 'assignments', route: 'assignments/summary', events: ['assignments.changed'], formatVersion: 1 },
];
```

- They load on election, on every (re)connect, on each listed event (coalesced over 250 ms), and on
  each degraded poll (N25 §8.6, §8.7). A warm launch renders badges from them before any call
  (A§7.2). `formatVersion` bumps when the stored shape changes (N25 §2.4).

#### §5.2 `TmAttention`

```ts
// @tellma/core/attention
type TmPanel = 'bell' | 'tray';
interface TmBellBadge { readonly count: number | null; readonly tone: 'accent' | 'attention'; readonly jobsRunning: number; readonly label: string }
interface TmTrayBadge { readonly count: number | null; readonly tone: 'accent' | 'neutral'; readonly label: string }
declare class TmAttention {                                // root in the tenant shell's injector
  readonly inbox: Signal<InboxSummary | undefined>;        // TmLaunchCache.docs.inbox, with local overlays applied
  readonly assignments: Signal<AssignmentsSummary | undefined>;
  readonly bell: Signal<TmBellBadge>; readonly tray: Signal<TmTrayBadge>;
  readonly open: Signal<TmPanel | null>;
  readonly live: Signal<'live' | 'paused' | 'polling'>;    // from TmLeader.hubStatus (§6.2)
  readonly writable: Signal<boolean>;                      // tenant Active and TmApi.online (§5.4)
  toggle(panel: TmPanel, via: 'click' | 'shortcut' | 'toast'): void;
  read(ids: readonly number[]): Promise<void>; readAll(): Promise<void>;
  clear(ids: readonly number[]): Promise<void>; clearRead(): Promise<void>;
  cancelJob(id: number): Promise<void>;
}
```

- **Overlays, not store writes.** `read`, `readAll`, `clear` and `clearRead` change `inbox` in the
  same frame through a per-tab overlay (rows marked read, rows removed), then call the verb; the
  overlay drops when a stored document saved after the verb's response arrives (0021 publishes
  `inbox.changed` to the caller, so the leader refreshes). A failed verb drops its overlay at once
  and shows an error toast "Couldn't update your notifications. Try again." (sticky, Try again).
- **Badge rules:**

| Badge | Count shown | Tone | Extra |
|---|---|---|---|
| Bell | `Unseen` when > 0, `99+` past the cap; hidden while the bell's seen overlay holds | `attention` while `MaxUnseenSeverity` is `Warning` or `Error`, else `accent` | the job ring while `Running` has a `Pending` or `Running` row |
| Tray | `Open` when > 0, `99+` past the cap; never hidden by opening | `accent` while `New` > 0 and the tray's seen overlay does not hold, else `neutral` | — |

- **Accessible names** (the counter is `aria-hidden`, N23 §3.4), built from parts joined by the
  list separator of the active language: "Notifications", "{n} new", "needs attention", "{n} job
  running" / "{n} jobs running"; "My assignments", "{n} open", "{n} new". **Example —**
  "Notifications, 3 new, needs attention, 1 job running".
- `count` 0 and `null` render nothing; the counter's fixed box means 9 → 10 moves nothing (A§9).

#### §5.3 Opening a panel

1. **Same frame:** the panel renders from the stored document (warm, no network); the bell's seen
   overlay hides its count, or the tray's turns its tone neutral; `open` changes.
2. **When the document says there is something new** (`Unseen` > 0 or `New` > 0) and the tenant is
   writable: `TmApi.write('inbox/seen' | 'assignments/seen')`.
3. **Then** `TmApi.read('inbox/summary' | 'assignments/summary', {}, { signal: panelLifetime })` and
   `TmClientStore.put` of the result: every tab re-renders from it (N25 §8.6: a tab that opens a
   panel may read fresher data). The overlay lifts when a stored copy's `savedAt` is later than
   the `seen` response (or than the open, when no `seen` was sent), so an older refresh never
   brings the count back.
4. **Rows inside an open panel** update in place, keyed by id. New rows insert at the top; the
   list uses CSS scroll anchoring (`overflow-anchor`, Baseline 2026) so the row under the pointer
   stays put, and a polite announcement says "{n} new notifications".

- The tray's "New" marks use the `SeenAt` of the document the panel opened with, so they stay
  visible for this opening even though step 2 moved the stamp.
- **Closing** aborts step 3 if pending (rule 2C). Escape, an outside click, choosing a row and the
  button again close it; focus returns to the button (N27 §7.2).

#### §5.4 States that limit the verbs

| State | Bell and tray |
|---|---|
| Tenant `ReadOnly` (`TmLaunchCache.docs.tenant`) | panels open; no `seen`, `read` or `clear` (0011 refuses mutations); "Mark all as read", Clear and job Cancel are absent; the count stays |
| `TmApi.online` false | panels open from the store; verbs disabled with the tooltip "You're offline"; no refresh is attempted |
| No document yet (cold, sync pending) | buttons render with no count; the panel shows three skeleton rows with final geometry |
| `TmLeader.hubStatus` not `connected` or `disabled` for 5 s | the bell panel's status line (§6.2) |

### §8 The toast policy

A toast interrupts, so it is reserved for arrivals that deserve it and for feedback on the user's
own action. Everything else waits in a badge, a panel or an inline state. 0023's `TmToasts` is the
mechanism; this section is the policy every spec follows.

#### §8.1 What toasts

| Trigger | Toast | Shown by | Tone | Duration | Action |
|---|---|---|---|---|---|
| A notification arrives whose type has `Toast = true` | title + detail of the row | the visible, focused tab | by severity: `Success` success, `Warning` warning, `Error` error, `Info` neutral | 6 s; `Error` sticky | "Download" (`core.export.ready`), else "View" when it has a target |
| A notification of a type with `Toast = false` (approvals, shares, "added to tenant", every activity type) | **never** | — | — | — | — |
| One assignment arrives, not self-assigned | "{code} assigned to you" (or "{code} returned to you"), detail "{assigner}: {comment}" | the visible, focused tab | accent, icon `inbox` | 6 s | "Open" |
| Several assignments arrive in one document change | "{n} documents assigned to you" | same | accent | 6 s | "View" (opens the tray) |
| The tenant turns `ReadOnly` mid-session (`tenant` document) | "{tenant} is now read-only. You can view data but not change it." | same | warning | 6 s | — |
| Feedback on the user's own action that has no inline home | the outcome, e.g. "Export started" / "We'll let you know when it's ready" | the acting tab | neutral or success | 4 s | optional, e.g. "Track" (opens the bell) |
| The user's own action failed and has no inline home | e.g. "Couldn't sign out. Check your connection and try again." | the acting tab | error | sticky | "Try again" |
| Saves, deletes, activations, validation and request errors on a page | **never** (the page's inline states, 0030, 0031) | — | — | — | — |
| Connection lost, update available | **never** (banners, §9) | — | — | — | — |

- **Admitted feedback toasts** (the full list; a spec adds one by an edit here): export and import
  started (0030; "Track" opens the bell), "Diagnostics copied" and "Couldn't copy" (0026), "Pinned
  {label}" below `md` (0027), "Couldn't sign out…" (0027), "Couldn't update your notifications"
  (§5.2), "Test message sent" (§10.3).
- **Feedback toasts are the acting feature's call:** `inject(TmToasts).show({ tone, title,
  detail?, action?, duration: TM_TOAST_FEEDBACK_MS })`, with the constants `TM_TOAST_FEEDBACK_MS =
  4000` and `TM_TOAST_ARRIVAL_MS = 6000` exported from the primary entry point.
- **The overflow pill** (0023's `provideTellmaToasts`, called by 0024 with this action) reads "{n}
  more · Open notifications" and navigates to `/{t}/notifications` (the primary cannot open the
  bell, which lives in `/attention`; challenge 8).
- **A per-user switch** (`notifications.toasts`, curated, fallback `true`; N25 Appendix A row,
  request) turns arrival toasts off; feedback and errors still show.

#### §8.2 The arrival engine (`TmArrivals`)

1. **Which tab.** Every tab observes the stored `inbox`, `assignments` and `tenant` documents (the
   store mirror, N25 §2.1). Only a tab with `document.visibilityState === 'visible'` and
   `document.hasFocus()` at the moment a document changes shows toasts (A§7.8); the others update
   their badges only. Toasts are never decided from relayed hub events (N25 request 4).
2. **Arming.** A tab is *armed* for a document once it has seen one copy of it written after the
   tab started (`savedAt ≥ tabStartedAt`). Copies stored before (a warm launch) and the first fresh
   copy are the baseline: what arrived while the app was closed never pops (0021 §5.4's "first
   summary after load pops none").
3. **Diff, notifications.** An arrival is a `Latest` row whose type has `Toast = true`, that is
   unread, and whose `CreatedAt` is later than the newest `CreatedAt` of the previous copy's
   `Latest` (every such row when that list was empty). A replaced row (fresh `CreatedAt`, same id)
   is an arrival again (0021 §5.4).
4. **Diff, assignments.** An arrival is a `Latest` row with `AssignedAt` later than the previous
   copy's newest and `AssignedById` other than the user.
5. **Baselines move on every copy**, armed or not, focused or not, so a tab that gains focus later
   never replays what another tab showed.

#### §8.3 Keys, withdrawals and limits

- **Keys.** A notification toast uses `key: 'n:<id>'`, an assignment toast `'a:<id>'`, the grouped
  one `'a:many'`, so a replaced row updates its open toast in place (0023 `key`).
- **Withdrawn or read.** When a row disappears from `Latest` (withdrawn, cleared) or becomes read
  elsewhere, `TmArrivals` closes its open toast (`TmToastRef.close()`); a closed assignment
  (completed, handed on) closes its `a:<id>` toast.
- **"View", "Open", "Download"** run the same activation as the panel row (§6.2), then the toast
  closes.
- **At most three** visible (0023); a burst of more than three notification arrivals in one change
  shows the newest three and counts the rest in the pill.

### §9 Banners: `TmBanners`

The banner row shows one passing condition at a time, chosen by a fixed precedence, with a pager
for the rest. `TmBanners` lives in the primary entry point because the primary's own code (the
offline and update sources) shows banners (A§2.2).

#### §9.1 Contract

```ts
// @tellma/core (primary)
type TmBannerLevel = 1 | 2 | 3 | 4 | 5;   // 1 connection lost; 2 critical announcement (reserved); 3 update; 4 warning; 5 info
interface TmBannerOptions {               // A§5.14's TmBanner, renamed (challenge 2)
  readonly id: string;                    // 'tm.offline', 'tm.update', 'acme.period-closing'; show() with a live id updates it
  readonly level: TmBannerLevel;          // 1–3 are the platform's (a distribution id there throws in development)
  readonly tone: 'info' | 'warning' | 'error';
  readonly message: Signal<string>;       // localized; ≤ 45 characters so one 32 px line fits 390 px
  readonly icon?: string;
  readonly action?: { readonly label: Signal<string>; readonly run: () => void }; // "Reload", "Learn more"
  readonly dismissible: boolean;          // never for levels 1 and 2
}
interface TmBannerRef { update(patch: Partial<Omit<TmBannerOptions, 'id' | 'level'>>): void; close(): void }
declare class TmBanners {
  show(options: TmBannerOptions): TmBannerRef;
  readonly current: Signal<TmBannerView | null>;  // what the row renders now (after the gate)
  readonly visible: Signal<boolean>;              // the row is open: 0027 sets --tm-banner-height from it
}
interface TmBannerView { readonly options: TmBannerOptions; readonly index: number; readonly count: number }
```

#### §9.2 Precedence and the pager

- **Order:** level ascending, then the time `show` first ran, earliest first. The *head* is the
  first entry that is neither dismissed nor closed.
- **One at a time.** The row shows the head, or the entry the user paged to. A higher-level banner
  that arrives takes the row (a swap, §9.3); a lower or equal one only raises the pager's count.
- **Pager.** With two or more entries, `tm-banner-bar`'s position shows "1 of 3" with previous and
  next buttons; paging is the user's own and sticks until that entry closes or is dismissed.
- **Dismiss** hides the entry for this tab's life (the update banner: for that version, 0024
  §5.5) and shows the next; a dismissed entry leaves the pager's count.
- **`update` of a live id** changes its message or action in place; `close()` removes it.

#### §9.3 The input-idle gate

- **What waits.** Only changes of the row's height: the row opening (0 → 32 px) and closing.
  Swapping the message inside an open row is immediate (nothing moves).
- **The gate** opens after 2 s without `keydown`, `pointerdown`, `pointermove`, `wheel` or
  `touchstart` on the window (passive capture listeners); the pending change applies then.
- **Exceptions:** the user's own dismiss closes at once (they caused it); a hidden page
  (`visibilityState = 'hidden'`) applies at once, so the user returns to a settled layout.
- **The closing message.** When level 1 closes while the row waits for the gate, the bar reads
  "Connection restored." (info) until the row closes; a banner that closed is never shown stale.

#### §9.4 `tm-banner-host`

- Placed by 0027 in both shells between the app bar and the pinned bar (N27 §5.2); renders
  `tm-banner-bar` (0023) from `TmBanners.current`, with `position`, `action`, `dismiss`,
  `previous`, `next` wired back.
- **Announcement at queue time:** the host owns one visually hidden live region (`assertive` for
  level 1, `polite` otherwise) and writes the message when an entry becomes the head, before the
  gate opens, so keyboard and screen-reader users are told at once; the bar's own region is
  silenced (`announce = false`, request to 0023).
- **Focus** never moves to a banner (N27 §5.3). The bar's buttons are in the header's tab order
  after the app bar.

#### §9.5 The platform's banners

| Id | Level | Tone, icon | Message | Action | Dismissible | Shows while |
|---|---|---|---|---|---|---|
| `tm.offline` | 1 | error, `wifi-off` | "Connection lost. Reconnecting…" | — | no | `TmApi.online()` has been false for 5 s (0024 §10.5); closes when it turns true |
| `tm.update` | 3 | info, `refresh-cw` | "A new version is available." | "Reload" → `TmUpdates.reload()` | yes, for that version | `TmUpdates.available()` is not null (0024 §5.5) |

- Both sources are started by `provideTellma` (an environment initializer in the primary) and run
  in every shell, the tenantless one included. Hub loss shows no banner (A§7.8).
- **Reserved:** level 2 for critical announcements and `announcements.dismissed` (N25 Appendix
  A). Levels 4 and 5 serve distribution banners now (§9.6) and warning and info announcements
  later (A§1).

#### §9.6 A distribution's banner (the hatch)

```ts
// acme: a condition the distribution watches itself; levels 4 and 5 only
const ref = inject(TmBanners).show({ id: 'acme.period-closing', level: 4, tone: 'warning', dismissible: true,
  message: computed(() => t('Acme_Banner_PeriodClosing')) });   // later: ref.close()
```

### §10 The four pages

The pages are the core feature's declarations on the CRUD framework (0030 search, 0031 details);
their only custom code is cells, the settings page and the Jobs alerts.

#### §10.1 Shared rules

- **No push reloads a page (rule 2D).** An event that names visible rows refreshes those rows in
  place (`refreshRows(ids)`, request to 0030); anything else lights a dot on the page's Refresh
  action ("New items. Refresh to see them."). Own verbs refresh their rows right after the
  response.
- **Row activation goes to the target**, not to a details page, through the declaration's
  `rowLink` (request to 0030): a real `<a href>` (new tab, copy link) and Enter on the row.
- **Routes** (A§8): `/{t}/notifications`, `/{t}/me/notifications`, `/{t}/assignments?tab=`,
  `/{t}/jobs` and `/{t}/jobs/{id}`. Launcher entries per N27 §3.2: Notifications and Assignments
  search-only, Notification settings `core.me.notifications`, Jobs under Administration.

**Example —** the Notifications declaration (the shape a distribution would write; members other
than `columns` are the 0030 requests of note section 7):

```ts
export const tmNotifications = tmEntity<CoreNotification>('core.Notification', {

  onActivate: (rows, { injector }) => injector.get(TmAttention).read(rows.filter(r => !r.ReadAt).map(r => r.Id)),
```

#### §10.2 Notifications (`/{t}/notifications`)

- **Columns:** the notification (severity icon, title, detail; client-rendered, not sortable or
  filterable, 0021 review flag 1), Actor, Created (relative, absolute on hover), Read. Order
  `CreatedAt desc`. Unread rows bold.
- **Filters:** tabs All / Unread; column filters on Type (an `in:` list of the metadata's types
  labelled `NotificationType_<Key>`), Category, Severity and Created.
- **Actions:** page actions "Mark all as read" (`inbox/read-all`) and "Clear read notifications"
  (`inbox/clear-read`, confirmed); bulk actions on the selection "Mark as read" (`inbox/read`) and
  "Clear" (`inbox/clear`, confirmed). No create, export or import (0021 review flag 12).
- **Live:** `inbox.changed` in this tab lights the Refresh dot; own verbs refresh their rows.
- Empty: "No notifications" / under Unread "You're all caught up".

#### §10.3 Notification settings (`/{t}/me/notifications`)

A core-feature page (0024 §9.2), page context kind `settings`. It reads
`notification-preferences/get` and the metadata's `notificationTypes` and `notificationChannels`.

```text

┌ Pop-up messages ───────────────────────────────────────────────────────────────┐
│ Show a pop-up when a notification or an assignment arrives               [on]   │
```

- **Grid:** one card per category (`NotificationCategory_<Category>`, 0021 edit), in the
  metadata's category order; rows are types (`NotificationType_<Key>`), columns are channels in
  registration order (`NotificationChannel_<Key>`; `inbox` reads "In the app").
- **Cells:** `tm-switch`, value = the stored deviation, else the channel's `DefaultEnabled`. The
  `inbox` switch of a non-mutable type is checked and disabled, described "Always on". A
  channel-only type (`Inbox = false`) has no `inbox` cell ("—"). Each switch's accessible name is
  "{type}, {channel}".
- **Pop-up messages:** `tm-switch` bound to `notifications.toasts` through `TmPreferences` (applies

- **Auto-save.** A change applies in the frame; 600 ms after the last change the page sends the

  `NotConfigured` → inline "Email isn't set up for this server". Errors through
  `TmErrorPresenter`.
- **Layout:** below `md` the channel columns stack under each type (label above its switches).
- **Page actions:** `notifications.settings.set` (params `{ type, channel, enabled }`, the
  assistant's way to change a switch; it saves like a click) and `notifications.settings.test`.

#### §10.4 Assignments (`/{t}/assignments?tab=to-me|by-me|all`)

- **Tabs** (`tab`, default `to-me`): Assigned to me (`AssigneeId = me()`), Assigned by me
  (`AssignedById = me() and AssigneeId <> me()`), All (no extra filter: everything the user may
  read — for a member the union of the two, for a supervisor with a grant the whole team). Each tab
  starts with the column filter `f.State=in:Open`, which the user may clear to see history.
- **Columns:** the target (`TmAssignmentTargetCell`: icon, "{entity} {code}", detail), the comment,
  Assignee, Assigned by, Assigned (relative), State (badge), Closed. Order `AssignedAt desc`.
- **Row link:** `TmUrls.target(Resource, TargetId)`. No create, edit, actions or export: writes
  belong to the module's document (§3).
- **Live:** `assignments.changed` lights the Refresh dot.

#### §10.5 Jobs (`/{t}/jobs`, `?mine=1`) and the job details page (`/{t}/jobs/{id}`)

- **Rows.** Members see their own jobs (0020 §11.2's self-scope); a user with an unrestricted
  `core.Job × Read` sees all, and the tab group `mine` (param `mine`, values `1` "My jobs" and
  absent "All jobs") appears only for them (`TmPermissions.filtered('core.Job', 'Read')` false).
- **Columns:** job (`TmJobLabelCell`, §11.2), Status (badge: Waiting neutral, Running accent,
  Succeeded success, Failed error, Cancelled neutral, Held warning), Progress
  (`TmJobProgressCell`: bar and percent while running), Requested by (admins), Created, Completed,
  Error (the `ErrorCode` message). Order `CreatedAt desc`.
- **Actions** come from the stack's entity actions (Cancel, Retry, Resume) with their securables
  (0030, 0031 derive them); Cancel is enabled for `Pending`, `Held` and `Running` without
  `CancelRequestedAt`.
- **Live (own jobs):** `job.changed { jobId }` in this tab refreshes that row in place when visible,
  else lights the Refresh dot. Other users' jobs never push (A§10.2): Refresh only.
- **Alerts** (`TmJobsAlerts`, above the grid, from `jobs/status`, 0020 edit): "{n} jobs are on
  hold after a service interruption." with "Show held jobs" (sets `f.Status=in:Held`); for a user
  with unrestricted Read, "Background processing stopped. Last activity {relative}." when
  `LastTickAt` is older than 10 minutes. Members see only their own held count.
- **Details** (`TmJobDetails`, view mode only; no `save` operation): label, status, progress and
  message, handler key, attempts, created, started, completed, requested by, run as, schedule
  (link), the error message with its trace id in `tm-reference` (copy), arguments (JSON,
  collapsed). The Actions menu offers Cancel, Retry and Resume. `job.changed` for this id calls
  `injectTmDetails().refresh()` while visible. `core.job.failed` notifications land here.

### §11 Rendering server text on the client

#### §11.1 `TmAttentionText`

- Captions are written in the assigner's moment: a counterparty name in `detail` is the text the
  module passed (one language; review flag 9).

## 11. Review flags

1. **A hand-off log, not a mutable row per target** (decision 1). Alt: one row per target with
   temporal history. Flips if the closed rows' volume proves heavy before retention.
2. **`IAssignments` on the internal channel, not enlistment** (decision 2). Alt: an `Enlist` stack.
   Flips if modules need validators on assignment rows.
3. **Closed rows kept 180 days** (§4.7). Alt: 90 or 365. Flips on users asking for older "by me"
   history.
4. **A deactivated assignee keeps their open rows** (§2.3). Alt: withdraw them on deactivation.
   Flips if orphaned work goes unnoticed.
5. **Attention verbs hidden on a read-only tenant** (decision 14). Alt: classify seen/read/clear as
   non-mutations. Flips if read-only tenants are common and users mind stale badges.
6. **No confirmation on Cancel job** (§6.2), although a cancelled non-atomic import keeps its
   committed chunks. Alt: confirm for imports. Flips on a support case about partial imports.
7. **Toasts only in the visible, focused tab** (A§7.8). A user watching Tellma on a second monitor
   while typing elsewhere gets none. Alt: the most recently focused visible tab. Flips on feedback.
8. **The idle gate has no maximum hold** (A§12 #27, §9.3); screen readers hear the banner at
   once. Alt: a 10 s cap. Flips if sighted users miss "Connection lost" during long typing.
9. **Caption details are one language** (§11.3). Alt: entity references resolved by
   `TmDisplayNames`. Flips if bilingual tenants complain.
10. **Read on visit over the ten stored rows** (decision 15). Alt: none, or server-side. Flips if
    users expect a notification to stay unread after visiting.
11. **Notification settings save automatically** (decision 16). Alt: an explicit Save. Flips on a
    preference for one confirmation.
12. **No open-assignment count in the browser tab title.** Alt: "(3) Sales invoices". Flips if
    users keep Tellma in a background tab and miss work.
13. **Jobs sits under Administration for every member** (N27 §3.2). Alt: search-only or a personal
    section. Flips if members cannot find their jobs beyond the bell's link.
14. **The trail extra shows comments to whoever reads the document** (§4.4). Alt: only to the
    parties. Flips on a privacy concern about hand-off notes.
15. **No platform assignment email** (decision 21). Alt: a platform type with a flat text. Flips if
    most distributions need email on assignment.
16. **The `entity` argument convention for job labels** (§11.2). Alt: labels stored rendered. Flips
    if more argument kinds need localization.

## 12. Challenges to the architecture

1. **A§6.2 "publishes `assignments.changed` to the old and new assignee"** misses the assigners:
   when Omar hands on or completes a row Farah assigned, Farah's "Assigned by me" changes. Followed
   with recipients = old and new assignees plus the assigners of the closed and new rows (§4.5).
2. **A§5.14 `show(banner: TmBanner)`:** rename the data type `TmBannerOptions`, as N23 C3 asks, so
   `@tellma/core` and `@tellma/core-ui` do not export two `TmBanner` meanings. Followed renamed.
3. **A§8 spells one concept twice:** `?mine=1` for Jobs and `?tab=to-me|by-me` for Assignments.
   Proposed: `?tab=mine|all` for Jobs. Followed the skeleton through a `param` on 0030's `tabs`.
4. **A§8's Assignments grammar gains `all`** (`?tab=to-me|by-me|all`): a member's union and a
   supervisor's team view need it. Additive.
5. **A§7.5's banner text "A new version of Tellma is available"** names the platform inside a
   branded distribution and is long at 390 px. Followed as "A new version is available."
6. **A§9's gate** says nothing of hidden pages or of announcements: a hidden page applies at once
   and the host announces at queue time (§9.3, §9.4), else keyboard users wait indefinitely.
7. **N27 request 1 asks `tm-banner-host` to expose `visible`;** the primary's `TmBanners.visible`
   serves the shell without reaching into a component instance. Followed with the service signal.
8. **The toast overflow action cannot open the bell from the primary** (A§2.2's import rule:
   `provideTellma` cannot reference `/attention`). Followed: the pill navigates to the
   Notifications page. Alternative: a primary "open panel" request signal `/attention` listens to.
9. **A§1 places "the Jobs page" with 0028 and N27 §3.2 lists Jobs under Administration**, which
   every member sees because the self-scope grants `Read`. Raised as review flag 13.
