# 0032 — Stock Pages: design note

Spec file: `docs/specs/0032-stock-pages.md`. Contract blocks are TypeScript and C# sketches: names
and shapes are normative; imports, documentation comments, bodies and cancellation tokens are
omitted. Skeleton references are "A§n" (00-architecture.md); other notes' future-spec sections are
"0029 §n", "0030 §n", "0031 §n", "BE C.n" (0010-BE.md). This note's future-spec sections are "§n".

## 1. Scope

  `core.Role`, `core.Schedule`, `core.OutgoingEmail`, `core.Export`, `core.Import`; the core pages

- **The `settingsTabs` declaration** (A§3.6): `TmSettingsTabDeclaration`, `injectTmSettings()`.
- **The settings half of 0013's edits** (A§6.3 rows 0013 §5.3/§10.1 and §6.3): the `settingKeys`
  and `settingCategories` sections, entry stamps, the save result.
- **The securables section's shape** (A§6.3 row 0014 §10; 0029 leaves it "applied with 0032").

## 2. Decisions

1. **Every stock page is a declaration on 0030 and 0031** (§3): six entity declarations as data in
   the primary, layouts in `/admin`; a distribution writes nothing. Alt: a component per page.
2. **`@tellma/module-gl` has two entry points** (§6): the eager primary (`tmGlFeature()`, the
   declaration) and `/centers` (layout, `TmGlCenterFields`), because eager code may not import
   `/details` (A§2.2). Alt: one entry point (pulls `/details` into the initial bundle).
3. **Settings and My profile run on 0031's host through a `TmDetailsSource`** (§12, R1): edit
   mode, save, drafts, the leave guard, conflicts and the error summary for free. Alt: two
   bespoke pages re-implementing the lifecycle.
4. **One Settings page, one edit mode, one tab per readable category** (§7.1); `{category}` selects
   the tab; Save sends every dirty field. Alt: edit and save per tab.
5. **Setting-key descriptors ship in the client metadata** (§7.3); `settings/details` drops
   `Keys`. Tabs, labels and controls render on a warm launch with no request. Alt: keep them in
   `details` (a second copy of build facts).
6. **Category order and in-tab groups are derived** (§7.3): General first, then registry order; a
   key's middle name segments are its group. Alt: explicit declarations.
7. **Per-entry expected stamps; the typed row's stamp only when a typed member is listed** (§7.6,
   E3). Different keys never conflict; entries-only saves need no `General`. Alt: per-category
   stamps (challenge 1).
8. **A value equal to its default is saved as a reset** (§7.6), so later default changes reach the
   tenant; a nullable key must default to `null` (E1). Alt: store explicit defaults.
9. **Secrets are write-only on the page** (§7.4): "Set" / "Not set", Replace, Clear.
10. **Setting fields reuse 0029's typed controls through a value descriptor** (§7.4, R10). Alt: a
    settings-only control set.
11. **Language, calendar and time-zone fields are platform components** (§4.2), not a metadata
    `format`. Alt: `TmPropertyMetadata.format` (review flag 7).
12. **Time zones come from `Intl.supportedValuesOf('timeZone')`** (§4.2); the server stays the
    authority. Alt: an emitted list (the build machine's ICU may differ from the host's).
13. **The permissions editor is a grid plus one filter panel for the active row** (§5.3): securables
    from the metadata, the filter in 0029's editor checked live by `queryex/discover`
    (`permission` profile), drift from `roles/problems`. Alt: filters in grid cells.
14. **Role members are the `members` extra: deferred, read-only, row-filtered, capped at 500**
    (§5.4, E11). Alt: 0033's child-query route (challenge 2).
15. **Invite and Issue credentials are entity actions with declared dialogs** (§4.3, §4.4) that
    confirm, run and show per-row results or the one-time secret; a `visible` predicate (R4) hides
    them per record. Alt: hand-written toolbar buttons.
16. **Invitation delivery is a live drill-down** (§4.5), read when the Sign-in aside renders, only
    for `State = Invited` (0018 decision 4). Alt: a grid column (identity calls per page).
17. **The Access tab shows effective access for every securable** (§4.6) through `access/check` in
    chunks of 200. Alt: the design's one-securable check.
18. **Signatures are drawn or uploaded and render on a light "paper" box** (§4.7), so transparent
    ink shows in the dark theme. Alt: upload only.
19. **My profile renders from the stored `me` with no request** (§8; E15) and saves through
    `me/save`, adopting the result. Alt: `users/get` of the own row on every visit.
20. **Email HTML renders in a sandboxed iframe from a `blob:` URL with its own CSP `meta`**
    (§10.2): no scripts, no remote loads, `cid:` images as `data:` URLs. Alt: `srcdoc` (a Trusted
    Types sink under A§6.6's CSP).
21. **Admin pages get no push** (A§10.2), except an Import's details page, which refreshes on its own
    job's `job.changed`. Alt: polling.
22. **`Job`'s related projection carries status and label** (E18), so job-linked rows show state to
    any reader.
23. **Last active and schedule state are eager extras** (`activity`, `state`; A§6.3). Alt:
    `[Sibling]` navigations (challenge 3).
24. **Built-in schedules lock fields and hide actions from `Id ≤ 999`** (§9), 0020 §7.1's rule; the
    server still refuses.
25. **A language change asks for confirmation before saving** (§7.6): names keep their slot, and a
    removed language's names are erased from a record on its next save (0015 preprocessing).

## 3. Design (the future spec's sections)

### §1 Placement and vocabulary

| Part | Entry point | Folder | Loaded |
|---|---|---|---|
| the six declarations, `TmSettingsTabDeclaration` and the `injectTmSettings` types | `@tellma/core` | `core/tellma-core/src/admin/` | eager, ≤ 2 KB gzip |
| layouts, pages, sources, dialogs, editors, cells, field groups | `@tellma/core/admin` | `core/tellma-core/admin/` | lazy, one chunk, 28 KB self-weight |
| `tmGlFeature()`, `tmGlCenters` | `@tellma/module-gl` | `module/tellma-module-gl/src/` | eager, < 1 KB |
| `TmGlCenterDetails`, `TmGlCenterFields` | `@tellma/module-gl/centers` | `module/tellma-module-gl/centers/` | lazy |

- **Imports.** `/admin` imports the primary, `/entity`, `/search` (the import result view),
  `/details` and `/attention` (job labels). Declarations `import()` `/admin` (challenge 5).
- **Dialogs** (invite, credentials, signature) are `import()`ed on use (≤ 4 KB each). Every chunk
  sits in the worker's `shell` group (A§6.6).
- **Testing exports:** `TmSettingsPageHarness`, `TmPermissionsEditorHarness`,
  `TmUserAccessHarness`, `tmFakeSettingsDetails()`. **Strings:** client scope `tm.admin`.

**Vocabulary**

- *Source page* — a details page on 0031's host fed by a `TmDetailsSource` (Settings, My profile).
- *Category* — a settings tab: `general` (the typed row plus `general` keys) or a key category.
- *Group* — a titled card inside a category, from a key's middle name segments.
- *Entry stamp* — a `core.SettingEntries` row's `ModifiedAt`, or `null` when no row exists.
- *Drift* — a stored permission that grants nothing (0014 §9).

### §2 What a distribution writes

For the stock pages, nothing.

| Need | What the distribution writes | Lines |
|---|---|---|
| Centers with an extra field (A§3.4) | an override + a layout reusing `TmGlCenterFields` | 4 + 6 |
| Users with extra columns (`MyUser : User`) | an override + a layout reusing `TmUserFields`, `TmUserTabs`, `TmUserSignIn` | 4 + 7 |
| Its own settings | `SettingKey<T>` fields in a C# holder (0013 §5.3) + resx labels | 0 client |
| A settings tab with its own editor | `settingsTabs: [{ category, component }]` + a component | 1 + ~14 |
| Hide a stock entry or tab | `hide: ['entry:core.Schedule']`, `hide: ['settingsTab:gl']` (0024 §2.3) | 1 |

**Example — Acme's user layout over `MyUser`** (the override replaces `columns` and `details`):

  template: `<tm-details-card><tm-user-fields /><tm-field path="EmployeeNumber" /></tm-details-card>
             <tm-user-tabs /><tm-user-sign-in /><tm-details-audit />` })

The core feature (A§5.1) declares the stock entities: launcher place (0027 §3.2), search defaults

- **`visible`** (R4 to 0031): `(entity, { userId }) => boolean` over the wire object; hides a
  promoted button or menu item for this record, built-in actions included; never replaces the
  server's check. Search-page bulk actions ignore it (the server refuses per row, 0030 §12.3).
- **Launcher order** under `administration`: Users 10, Roles 20, Centers 30, Settings 40 (0027's
  `core.settings`), Schedules 50, Jobs 60 (0028), Exports 70, Imports 80, Outgoing emails 90,
  Support requests 100 (0026). Member names per 0029 §3 (challenge 7).
- **Derived** (0030, 0031): routes `/{t}/{segment}` and `/{t}/{segment}/{id}`, `/new` where the stack
  saves (Users, Roles, Schedules); the stacks without `save` open view mode with no Edit or New;
  Export and Import menus where the operations exist; Activate, Deactivate, Delete and entity
  actions from metadata; pickers for `core.User`, `core.Role`, `core.Schedule` (0029 §14).
- **Notification targets** (0028's request) land here through `TmUrls.target` (R2). Members see
  their own Exports and Imports (0019 §12.1's self-scope), so the launcher shows them both.

### §4 Users

The details page shows the user's fields, role memberships and effective access, with a Sign-in
aside for invitation or credential state.

#### §4.1 The layout and field groups

```ts
// @tellma/core/admin — users/ (8 + 15 + 13 = 36 lines)
@Component({ selector: 'tm-user-details', imports: [TmDetailsKit, TmUserFields, TmUserTabs, TmUserSignIn], template: `
  <tm-details-card><tm-user-fields /></tm-details-card> <tm-user-tabs /> <tm-user-sign-in /> <tm-details-audit />` })
export class TmUserDetails {}

@Component({ selector: 'tm-user-tabs', imports: [TmDetailsKit, TmUserAccess], template: `
  <tm-details-card flush><tm-details-tabs>
    <tm-details-tab id="roles" collection="RoleMemberships"><ng-template tmDetailsTabContent>
      <tm-child-grid collection="RoleMemberships" [columns]="[{ path: 'Role', filter: 'IsPublic = false' }, 'Notes']" />
    </ng-template></tm-details-tab>
    @if (canSeeAccess()) {
      <tm-details-tab id="access" labelKey="tm.admin.users.access">
        <ng-template tmDetailsTabContent><tm-user-access /></ng-template></tm-details-tab> }
  </tm-details-tabs></tm-details-card>` })
export class TmUserTabs { protected readonly canSeeAccess = inject(TmPermissions).can('core.Role', 'Read'); }

@Component({ selector: 'tm-user-fields', hostDirectives: [TmFieldGroup], imports: [TmDetailsKit, TmUserLocaleFields, TmSignatureField],
  template: `
    <tm-field path="Image" /> <tm-field path="Name" /> <tm-field path="Kind" />
    @if (d.model()?.kind !== 'Service') {
      <tm-field path="Email" [readonly]="d.mode() !== 'create' && d.entity()?.state !== 'New'" hintKey="tm.admin.users.emailHint" />
      <tm-field path="ContactEmail" /> <tm-field path="ContactMobile" /> <tm-field path="Gender" />
      <tm-user-locale-fields /> <tm-signature-field path="Signature" />
    }` })
export class TmUserFields { protected readonly d = injectTmDetails<TmCoreUser>(); }
```

- **Kind** is write-once (0014 §3.1); a Service account shows Image, Name, Kind only
  (`Users.EmailNotAllowed`). **Email** locks once the user leaves `New`
  (`Users.EmailLockedAfterInvite`): "Sign-in email. It can't change after the invitation is sent."
- **Memberships.** The Role picker excludes public roles (column `filter`, R11 to 0029; public roles
  take no members, 0014 §3.5) and, by the activatable conjunct, inactive roles. A hint under the
  grid: "Public roles apply to everyone and don't need members." Lockout and escalation codes
  land on the row (0031 §8.5).
- **`TmUserLocaleFields`** (also My profile): `tm-language-field`, `tm-calendar-field`,
  `tm-time-zone-field` for the three `Preferred*` columns, each nullable ("Tenant default").
- **`TmUserSignIn`** sits in `tm-details-aside` (0031 §6.7). **Step-up:** `core.User × Save` is
  sensitive (0014 §4.3); 0031's host warns and keeps the draft across the redirect.

#### §4.2 Language, calendar and time-zone fields

```ts
@Component({ selector: 'tm-language-field', hostDirectives: [TmFieldGroup] })
declare class TmLanguageField { readonly path: InputSignal<string>; readonly scope: InputSignal<'tenant' | 'offered'> }
@Component({ selector: 'tm-calendar-field', hostDirectives: [TmFieldGroup] })
declare class TmCalendarField { readonly path: InputSignal<string>; readonly scope: InputSignal<'tenant' | 'registered'> }
@Component({ selector: 'tm-time-zone-field', hostDirectives: [TmFieldGroup] })
declare class TmTimeZoneField { readonly path: InputSignal<string> }
```

Each wraps `tm-field` with a view and an edit template:

| Field | View | Edit options (`tm-select`) |
|---|---|---|
| language | "العربية (ar)" | `tenant`: the tenant's content languages (as the session menu, A§12 #11); `offered`: the metadata's languages |
| calendar | "Umm al-Qura" (`tm.calendar.<code>`, 0027) | `tenant`: the tenant's pair; `registered`: the metadata's calendars |
| time zone | "Asia/Riyadh (GMT+03:00)" | searchable, `Intl.supportedValuesOf('timeZone')` grouped by region, each with its `longOffset` |

- **Nullable** fields add "Tenant default ({effective value})" first; a stored value outside the
  option set stays as an option so it is never lost.
- **Codes and zone ids** render in LTR isolates. **The server validates** (`Users.LanguageNotOffered`,
  `Users.CalendarUnknown`, `Users.TimeZoneUnknown`, `Settings.*`), so an unmappable zone returns
  as a field error.

#### §4.3 Inviting users

`users/invite` (`IdsRequest` → `list<InviteResult>`, 0018 §3.3) opens its declared dialog from the
promoted button (one user) or the search page's bulk menu (a selection, 0031 R21).

1. **Confirm.** "Invite {name}?" / "Invite {n} users?" — "Each person gets an email from the
   identity server to set up their sign-in, and a welcome email with a link to {tenant}." On a
   sandbox tenant (`docs.tenant().category`): "This is a sandbox. Only people who already have an
   account are added, and no one gets an invitation email." When sensitive: "You'll be asked to
   confirm it's you."
2. **Run** `run({}, { keepOpen: true })` (R5) under the busy overlay.
3. **Outcome:**

| Response | Dialog |
|---|---|
| 200, all rows have `Status` | one user: closes with a toast "Invitation sent to {name}." or "{name} already had an account and was added."; several: a results list |
| 200, some rows have `Error` | results list: Name and "Invitation sent", "Invitation sent again", "Added: already had an account", or the error (`TmServerText` for `Users.*`, the identity server's text otherwise) |
| 422 (one invalid row fails all) | the dialog's error area, a line per row (`Users.NotIndividual`, `Users.Inactive`, `Users.AlreadyJoined`) |
| 502 `partial-failure` | `errorDetails.results`, then "{n} weren't attempted because the identity server stopped responding." with "Try again for these" → `run({}, { keepOpen: true, ids: errorDetails.failed })` |
| other | `TmErrorPresenter` (0024); the dialog stays |

- After close the host re-reads the record and marks the list stale (0031 §10.4). A step-up
  redirect returns to the page; the user presses Invite again.

#### §4.4 Service accounts and credentials

`issue-credentials` (`IdRequest` → `CredentialsResult`, 0018 §3.8) returns the secret once.

1. **Confirm.** "Issue credentials for {name}?"; with an existing subject: "The current secret stops
   working at once. Update every system that uses it."
2. **Run** with `keepOpen`; the dialog becomes "Credentials for {name}": Client id and Client secret
   as read-only mono LTR fields with Copy each and "Copy both" (`navigator.clipboard.writeText` in
   the click's activation), a warning "This secret is shown only once. Copy it now and store it
   somewhere safe.", and Done. Closing before any copy asks "Close without copying the secret?".
3. **Never kept:** the secret lives in the dialog only — not in a page context, draft, page state,
   telemetry, the state dump or the record; an `assistant` origin never receives it.

- The aside warns: "Deactivating this account deletes its credentials. Issue new ones after
  activating it." (0018 §3.6).

#### §4.5 The Sign-in aside (`TmUserSignIn`)

| User | Shows |
|---|---|
| Individual `New` | "Not invited yet." |
| Individual `Invited` | "Invited {relative}", the invite status, `LastInviteError` (`TmServerText`), the delivery line |
| Individual `Joined` | "Joined {relative}" |
| Service | Client id (`Subject`, mono, Copy) or "No credentials yet." |
| everyone | "Last active {relative}" / "Never" from the `activity` extra (E12) |

- **Delivery** (`Invited`, `InviteStatus ≠ Active`): `users/invitation-status { ids: [id] }` when the
  aside renders, aborted on leave, with Refresh. States: Pending "Waiting to send"; Sent "Sent"
  (+ "Delivery isn't tracked" when `ExpectsDeliveryEvents` is false); Delivered "Delivered
  {relative}"; Bounced, Rejected, Complained, Abandoned "{state}: {reason}"; NotFound "Sent by
  another application". A failure shows "Couldn't check delivery" with Retry; loading keeps the
  line's final height.

#### §4.6 The Access tab (`TmUserAccess`)

"What can this user do, and why", through `access/check` for another user (0018 §3.7: needs
`core.Role × Read`; the tab is absent without it).

- **Request:** every non-wildcard metadata securable (§13.4) in registry order, chunks of 200 (the
  endpoint's cap), two in flight, the host's signal. About 150 securables: one call.
- **Rows** grouped by resource label, one per action, with "Allowed" (`Unrestricted`), "Allowed for
  some records" (`Filtered`) or "Not allowed" (`Denied`), icon plus text. Enter expands the
  reasons: role grants (role link, filter in mono LTR), bespoke criteria (`Access_Reason_<reason>`:
  "Their own records" for `self`), "System user", drifted permissions ("Not in effect", §5.5).
- **Tools:** search over labels; `tm-segmented` All / Allowed / Not allowed; Refresh. A language
  switch re-renders with no request.
- **Page action** `admin.user.check-access` (hidden, `{ resource, action }`) returns one decision:
  the assistant's answer to "why can't Farah see invoices".

#### §4.7 Image, signature, activation

- **Image:** `tm-field path="Image"`, 0031 §6.3's `tm-image` with the `user-image` avatar policy.
- **Signature** (`tm-signature-field`, `user-signature`, PNG ≤ 1 MiB, 0014 §3.1). View: the image on
  a fixed light paper box (`--tm-paper`, both themes, 240 × 80, 1 px border); "—" when empty. Edit:

#### §7.6 Saving

The source turns the change into one patch of what the user changed, each entry with its own
expected stamp, and runs 0031's save flow.

1. **Diff.** Changed typed members → `fields` (`name2`, `primaryLanguage`). Entries whose canonical
   JSON changed → `entries.<key>` with the value, or `null` when it equals the default (decision
   8). A secret is listed only when replaced or cleared.
2. **Stamps.** `expectedModifiedAt` = the base row's raw stamp, only with a typed member;
   `expectedEntryStamps[key]` = the entry's stamp, or `null` when no row existed.
3. **Language confirmation** (decision 25): a language position that changes — "Change the second
   language from Arabic to French?" / "Names already entered in the second language stay as they
   are and will be shown as French." — or a removed secondary or tertiary language — "Remove
   Arabic?" / "Names in Arabic are hidden, and erased from a record the next time it's saved." —
   with [Cancel] and [Change languages] (danger for removal). Cancel keeps edit mode.
4. **Write** `settings/save` under 0031's overlay; **success** takes `details` as the new server copy
   (view mode, new stamps) and adopts `client` (§7.7).
5. **Errors:** 422 by `errorSegments`; 409 opens 0031's conflict dialog, whose Overwrite resends with
   `concurrency: 'Override'`; the rest per 0031 §8.6.

#### §7.7 Effects on the warm cache and other tabs

1. **This tab** adopts `client` and the response's `settings` tag into the stored document under
   the sync lock (R9), recording the old tag as superseded, so the header never syncs. The app

2. **Other tabs** of this browser re-render from `store.changed`; **other browsers** follow
   `cache.changed { settings, value }` (A§7.4).
3. **A language change** also bumps `permissions` (0013 §6.3): one `client/sync` for the new `me`;
   descriptors rebuild for the new shape (0029 §4.1); 0025 forgets the tenant's page state.
4. **A Settings page in view mode** in any tab re-reads `details` when the stored `settings` tag
   moves (`changes`); in edit mode it does not, and its save meets the stamps.
5. **The tenant picker** may show the old name until the catalog mirror runs (0013 §6.3 step 6).
6. **Refresh caches** (Actions menu, `settings.refresh-caches`, with `can('core.Settings.General',
   'Save')`): "Refresh caches?" / "Every user's next request reloads settings, permissions and
   lists. Use this after changing data outside Tellma." → `settings/refresh-caches` (sensitive);

## 11. Review flags

1. **Per-entry stamps instead of per-category** (decision 7). Flips if a category's keys must save
   as one consistent set.
2. **One edit mode for the whole Settings page** (decision 4). Alternative: per tab. Flips if admins
   want separate saves per category.
3. **`details` drops `Keys`** (decision 5). Flips on a non-SPA settings editor.
4. **Groups derived from key names** (decision 6). Alternative: `group:` on `SettingKey`. Flips when
   a pack's naming cannot express its grouping.
5. **A value equal to its default resets** (decision 8). Flips if tenants must pin today's default.
6. **JSON keys edit as raw text** without a `settingsTabs` component (§7.4). Alternative: hide them.
   Flips on misuse.
7. **Field components, not a metadata `format`** (decision 11). Flips when distributions add many
   language, calendar or zone properties.
8. **Role members read-only and capped at 500** (decision 14). Alternatives: add and remove from the
   role, or the paged child-query route (challenge 2). Flips if admins reject editing from users.
9. **The Access tab checks every securable** (decision 17). Alternative: one check. Flips on
   measured slowness (`tm.admin.users.access`).
10. **Delivery loads on render for `Invited` users** (decision 16). Alternative: a "Check delivery"
    button. Flips on identity-server load.
11. **No admin Notifications tab on the user page**, which the design draws (0028 keeps them
    self-service). Flips if admins must change others' notification settings.
12. **Drawn signatures through a 0023 pad** (decision 18). Alternative: upload only. Flips if
    unused.
13. **My profile meets the conflict dialog after a same-tab locale switch while editing** (§8).
    Alternative: rebase when only locale fields moved. Flips on user reports.
14. **Remote email images always blocked** (§10.2). Alternative: a "Show remote images" switch.
    Flips if admins must see emails exactly as sent.
15. **Built-in schedule names stay technical until renamed** (§9; 0020 §7.9). Alternative: seeded
    localized names. Flips on admin confusion.
16. **No cron preview, no "Schedule this export"** (§9). Flips when more handlers are schedulable.
17. **Deactivating a service account needs no confirmation** (0031's rule); the aside warns.
    Flips on accidental credential loss.
18. **The system user shows in the Users list** (§4.7). Alternative: a default filter hiding it.
    Flips on admin confusion.
19. **Exports and Imports under Administration for every member** (§3). Alternative: "My exports"
    entries for members; follows 0028 review flag 13.

## 12. Challenges to the architecture

1. **A§6.3 row 0013 §6.3: "entries carry per-category expected stamps".** A category has no stamp:
   rows' `ModifiedAt` miss deletions (a reset deletes the row), so a category stamp needs a new
   table or a digest. Per-entry stamps use existing rows, conflict only on keys both saves touch,
   and keep the row's goals. Followed with per-entry stamps; a category digest would be one rule
   in step 3.
2. **A§6.3 row 0018 §4: the `members` extra gains columns.** The extra is unpaged and, as written,
   ignores a filtered `core.User × Read`. 0033 §10's child-query route (`role-memberships/query`)
   pages, searches and respects row security with no new server code, and 0034's drill-through
   list could host it. Followed with the extra plus a row filter and a cap (E11).
3. **A§6.3 row 0020 §7.2: `ScheduleStates` as a details extra.** 0012's `[Sibling]` navigation would
   make `State.NextDueAt` (and `core.UserStamp.LastActiveAt`) sortable, filterable search columns,
   given a traversal rule that checks a sibling as its owner. Followed with the `state` and
   `activity` extras.
4. **A§2.1: `@tellma/module-gl` as one entry point.** Its layout imports `/details`, which the eager
   primary may not (A§2.2). Followed with `@tellma/module-gl/centers`; every pack with layouts
   needs the same split, which A§2 should state.
5. **A§2.2: `/admin` named by eager declarations.** The primary's declarations `import()`
   `@tellma/core/admin`; 0029 challenge 5 and 0025 challenge 8 raise the same exception. One
   ruling should cover all.
6. **A§1, A§3.6: Settings and My profile have no framework.** They are single records with no
   entity route. Followed by requesting the source seam (R1); the skeleton should list it under
   0031.
7. **A§5.2 lists `settingKeys` alone; launcher member names differ.** Tabs also need categories
   (labels, order, groups): `settingCategories` is added (R3). And 0027's note names the
   `tmEntity` navigation members `section`, `navOrder`, `icon`, `synonymsKey`, while 0029 §3 (the
   shape's owner) has `launcher: { order, icon, synonymsKey, labelKey }`; this note uses 0029's.
