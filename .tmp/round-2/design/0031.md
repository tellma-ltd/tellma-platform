## 2. Decisions

1. **Details Q1: the host owns the lifecycle; a layout is markup** (§3, §4). The route host loads
   `TmDetailsHost`, which loads, holds the form, switches modes, saves, maps errors, keeps drafts,
   guards leaving, pages, runs actions and publishes the page context. The layout composes
   `TmDetailsKit` and reads `injectTmDetails()` only for custom logic. Alt: a base class layouts
   extend (inheritance couples every layout to the host's internals); a generated form per entity
   (the brief rejects auto-generated layouts).
2. **One form per record, over the working copy, alive in every mode** (§4.2). View mode renders
   values, edit mode renders controls, from the same `FieldTree`. Signal Forms writes copy only the
   objects along the written path, so entering edit mode copies nothing and `dirty` is one
   reference comparison. Alt: build the form on Edit (a visible delay on large documents; two
   code paths for view and edit).
3. **One host instance per record** (§3.1). Changing `:id` (paging) or `new` ↔ id recreates the
   per-record state (form, extras, registrations) while the header stays mounted. Alt: reset one
   form in place (stale touched flags and server errors leak across records).
4. **The layout renders in the loading state** (§3.3). Fields show labels and value skeletons,
   grids show headers, so nothing moves when the record lands. Alt: a generic skeleton until data
   (a layout shift on every load).
5. **Save blocks; reads never do** (§8). The save runs under 0023's busy overlay, the router guard
   refuses navigation, and `beforeunload` is armed only while the write is in flight. Alt: an
   optimistic save (A§6.5 drops optimistic UI for mutations).
6. **422 shows an inline error summary plus field errors, not a modal** (§8.4; A§10.2). The same
   summary serves client validation failures. Its items never disappear while the user types
   (fixed items turn into "Fixed"), so the form never shifts under a keystroke. Alt: the brief's
   modal (review flag 1).
7. **Server errors live in the host and reach fields through one tree validator** (§8.5). The
   host splits each `errors[].path` into segments, walks the `FieldTree`, and reports the error on
   that node while its value is still the one sent; the next Save clears them all. Child-row
   errors land on grid cells. Alt: Signal Forms submission errors (they reset only when a field's
   value changes and have no public clear, so an error the server no longer reports would block
   the next Save; verified fact 3).
8. **A conflict offers Reload theirs or Overwrite; a deletion offers Save as new** (§9). Overwrite
   resends with `Override` (0015 §8). Alt: a merge view (deferred).
9. **Drafts are continuous and the only way edit mode survives a page load** (§11; A§10.1 Q3).
   Edit mode is never in the URL; create mode is (`/new`). Alt: a `beforeunload` prompt while dirty
   (fires on reload, which the brief wants silent).
10. **The leave guard asks only for in-app navigation** (§11.3), with `canceledNavigationResolution:
    'computed'` so a refused Back keeps history intact. Alt: no guard on Back (silent data loss).
11. **Paging replaces the history entry and crosses page boundaries by reading the next page with
    the search page's own request** (§12). The details host writes the new page into the search
    snapshot with `supersedes`, so Back shows the new page. Alt: push per record (Back would walk
    records, not return to the list).
12. **Returning restores the remembered record with no request** (§13), unless a write marked it
    stale. Alt: always revalidate (a request on every Back, against the brief).
13. **Non-aggregate Q1: opt-in by convention** (§14). `?child=Lines:42` opens the
    `tm-details-tab collection="Lines"` (tab content is lazy, so the tab names its collection),
    then the grid binding `Lines` scrolls to and flashes the row. Alt: a per-entity drill callback
    (code in every distribution); parent only (loses the brief's flash).
14. **Extras are eager by default; an extra the server declares deferred loads when its panel
    renders**, through a new `{segment}/extras` read (§6.8). Alt: always eager (an edit history
    read on every view); re-calling `get` with one include (re-reads the whole document).
15. **Clone strips by ownership, keys and blob references, then runs the declaration's `clone`**
    (§3.6). Unique values such as `Code` stay and the server flags them. Alt: also clear `unique`
    properties (review flag 3).
16. **Actions are page actions** (§10; A§10.2): Edit and New are buttons; Clone, Activate or
    Deactivate, Delete and custom actions sit in the Actions menu; `button: true` promotes a custom
    action. Zero-argument actions need no code; an action with arguments needs its declared dialog.
17. **The action runner and the dialog contract live in `@tellma/core/entity`** (§10.4), shared by
    the search page's bulk actions and the details page.
18. **No toast on save; the record flips to view mode and the status region says "Saved"** (§8.3;
    0028 policy). Delete leaves the page, so it is the one write that toasts (request to 0028).
19. **Child grids defer the grid chunk** (§6.4): `@defer (on viewport; prefetch on idle)` with a
    placeholder of final geometry, which keeps the editable grid out of the details route's
    budgeted closure (challenge 6).
20. **Child grids keep one height per mode** (§6.4): rows + 1, between 4 and 12, fixed at load and
    at each mode change, so adding a row in edit mode never pushes content down (rule 2D).

## 3. Design (the future spec's sections)

### §1 Placement and vocabulary

`@tellma/core/details` holds the details page. It imports `@tellma/core` and `@tellma/core/entity`
only (A§2.2).

| Part | Exports | Loaded |
|---|---|---|
| host | `TmDetailsHost` (`tm-details-host`, internal selector), `injectTmDetails`, `TmDetailsContext`, `TmDetailsExtraState`, `TmRelated` | with the route |
| kit | `TmDetailsKit` = `TmDetailsCard`, `TmField`, `TmFieldView`, `TmFieldEdit`, `TmFieldGroup`, `TmChildGrid`, `TmChildFiles`, `TmDetailsTabs`, `TmDetailsTab`, `TmDetailsTabContent`, `TmDetailsAside`, `TmDetailsExtra`, `TmDetailsAudit`, `TmDetailsTitleExtra` | with the route |
| picker page | `TmDetailsPickerPage` (provided as `TM_ENTITY_PAGES.details`, 0029 §14.4) | with the modal |
| dialogs | internal concurrency, deletion and action-dialog shells | `@defer` / `import()` on use |
| in `@tellma/core/entity` | `TmEntityActions`, `injectTmActionDialog`, `TmActionDialogContext` (§10.4) | shared lazy |
| types in the primary | `TmDetailsSnapshot`, `TmDetailsDraft` (types only) | eager, zero bytes |

- **Folder** `client/projects/core/tellma-core/details/`. **Budget** 22 KB gzip self-weight for
  the route chunk; each dialog ≤ 4 KB, deferred. The editable grid stays outside the route
  closure (`@defer` in `tm-child-grid`, §6.4), so the details route fits 0024's 80 KB.
- **Every deferred chunk sits in the worker's `shell` group** (A§6.6): "on use" is a cache read on
  a warm launch.
- **Testing exports** (`@tellma/core-testing`): `TmDetailsPageHarness`, `TmFieldHarness`,
  `TmChildGridHarness`, `tmFakeDetails()` (a `TmDetailsContext` for layout unit tests).

**Vocabulary**

- *Record* — the entity the page shows, identified by entity and id; `new` in create mode.
- *Server copy* — the record as the last `get`, `save` or action returned it (`entity()`).
- *Working copy* — the value the form edits (`model()`); the server copy itself in view mode.
- *Base* — the server copy at the moment edit or create began; its `modifiedAt` is the stamp the
  save sends.
- *Dirty* — the working copy is not the base (one reference comparison, decision 2).
- *Layout* — the distribution's markup component (`details: () => import(…)`).
- *Eager extra* / *deferred extra* — an extra included in every `get` / loaded when its panel
  renders (§6.8).
- *Search snapshot* — 0030's `TmSearchSnapshot`, found through `history.state.tmFrom`.
- *Child target* — the `?child=Collection:id` row to reveal (§14).

### §2 What a distribution writes

The common case is A§3.3: one declaration member (`details: () => import(…)`) and a markup-only
layout. Everything else in this section is optional.

### §3 The host and its lifecycle

`TmDetailsHost` renders the header (§5) and the body of one entity route, owns the record's state
and moves between three modes. This section decides how it starts, loads and changes mode.

#### §3.1 Routes and instances

| URL (A§8) | Mode on entry | Request |
|---|---|---|
| `/{t}/{segment}/{id}` | view; edit when this tab holds an edit draft of the record (§11.2) | `get`, unless the page state holds it (§13) |
| `/{t}/{segment}/{id}?child=Lines:42` | view, then the child target (§14) | `get` |
| `/{t}/{segment}/new` | create (defaults, or the tab's create draft) | none |
| `/{t}/{segment}/new?clone=5` | create from a clone of record 5 (§3.6) | `get` of 5, unless held |

- **Route host.** 0024's `TmRouteHost` awaits `TmEntities.load()` and the page chunk, then creates
  `TmDetailsHost`, which loads the declaration's layout or `page` hatch. The descriptor is
  therefore synchronous inside the host.
- **One instance per record** (decision 3). The host keys its body on `entity + (id | 'new')`; a
  key change (paging, a create's first save, clone) destroys the old body view and creates a new
  one. The header sits outside the keyed block, so the title row and pager never blink.
- **Operations gate the toolbar, not the route:** a stack without `save` opens view mode with no
  Edit, New or Clone (0028's request); a user without `Read` gets the inline forbidden state.

#### §3.2 States

Transitions: loading → view (200) or error; view → edit (Edit) or create (New, Clone push
`/new`); edit → view (Save 200, Cancel); create → view (Save 200 replaces the URL with `/id`); a
failed Save stays in its mode; error → loading (Try again, Refresh).

| `status` | `mode` | Header | Body |
|---|---|---|---|
| `loading` | view | crumb; title from the display-name cache, else a fixed-width skeleton bar; toolbar at final geometry with Edit and Actions disabled; pager | the layout with value skeletons (§3.3) |
| `ready` | view | title = display name; badges; full toolbar | the layout with values |
| `ready` | edit, create | "Unsaved changes" badge when dirty; Save, Cancel; pager arrows disabled | the layout with controls |
| `error` | view | crumb; title from the cache, else the entity label; New and the pager stay | `tm-error-state` (§3.5) |

#### §3.3 Loading

1. The host starts the read in its constructor through one `resource()` keyed by the record and a
   refresh generation: `TmApi.read('{segment}/get', { id, include: eagerExtras }, { signal })`.
   `eagerExtras` are the descriptor's extras not marked `deferred` (§6.8). No `select` is sent: the
   SPA does not use the row echo, because writes mark the search page stale (§8.3).
2. Meanwhile the layout already renders: `tm-field` shows its label and a value skeleton at value
   geometry, `tm-child-grid` its placeholder, `*tmDetailsExtra` a skeleton.
3. The title renders at once when `TmDisplayNames.label(entity, id)` knows the record (the search
   page remembers every row it showed, 0030 §5.2).
4. On success: `entity` and `model` take `entities[0]`; `TmDisplayNames.rememberRelated(related)`
   and `remember(entity, [record])`; `extras` set; `status` becomes `ready`.
5. Leaving the page aborts the read (the `resource()` signal, rule 2C); a refresh supersedes it.

- **Only step 1 waits on the network.** Labels, descriptors, permissions and the layout chunk come
  from caches (A§7.2).

#### §3.4 View → edit, instantly

- **Edit** (`details.edit`): `base` = `entity()`; `mode` = `edit`; no copy and no request
  (decision 2). Focus moves to the first editable control (`focusBoundControl()` on the first
  registered field in document order); the status region says "Editing {name}".
- **Cancel** (`details.cancel`): when dirty, `TmConfirm.ask` "Discard changes?" / "Your changes to
  this record will be lost." with [Discard changes] (ghost) and [Keep editing] (primary). Then the
  server errors are cleared (§8.5), `tree().reset(base)`, `mode` = `view`, the draft is cleared, and
  focus returns to Edit, which sits in Save's slot. In create mode Cancel leaves the page: Back
  when the previous entry is in-app, else the search page (§11.3).
- **Read-only in edit mode** follows ownership (0029 §12.2): `server-owned`, `derived` and
  `database-owned` render as values with a lock glyph; `write-once` is editable in create mode
  only.

#### §3.5 Read failures

| Kind (0024 §10.6) | Body | Actions |
|---|---|---|
| `not-found` | 0024 `describe`: "This {entity} doesn't exist or you can't see it" | primary "{Plural}" (the search page); the pager stays live |
| `forbidden` | 0024's forbidden view | the same link |
| `offline`, `unavailable`, `server` | 0024's view with the "Reference …" chip | Try again |
| `client-outdated` | 0024 §5.6's inline view | Reload |
| `tenant-not-found`, `tenant-unavailable` | `TmErrorPresenter.present` (cross-cutting) | — |

#### §3.6 Create and clone

- **New** (`details.create`) is a link button to `TmUrls.create(entity)` (Mod+click opens a tab).
  The model starts as: every child collection `[]`, every non-nullable `bool` `false`, then
  `declaration.defaults?.()` merged over it. The title is `<Schema>_<Entity>_New` ("New
  customer"; 0030 R20's chain).
- **Clone** (`details.clone`) pushes `TmUrls.create(entity, { clone: id })`. The new instance takes
  the source from the previous record's snapshot (§13), else reads it with `get`. The strip, in
  order:
  1. a structured copy (`TmDecimal` values kept as they are);
  2. remove the key and every `server-owned`, `database-owned` and `derived` property, by
     descriptor (this drops `modifiedAt`, the audit columns and `IsActive`);
  3. set every blob reference to `null` (0017's attach rule: one owner per blob, staged by the
     saver);
  4. in every child collection, recursively by the child's descriptor: the same, plus the parent
     key; each child row gets a fresh negative id (§6.4);
  5. `declaration.clone?.(copy)`.
- `write-once` and `unique` values are kept; a duplicate `Code` comes back as `Unique` on its field
  (review flag 3). The draft records `clonedFrom` (§11.2).

#### §3.7 The `page` hatch

- `details: { page: () => import(…) }` renders the component as the whole body region
  (`block-size: 100%`, its own scroll). The header, toolbar, pager, page actions, drafts, leave
  guard and page context stay the host's. The component reads `injectTmDetails()` and adds toolbar
  buttons as page actions with `group: 'primary'` (0026 §9.4).
- Users: 0035's dashboard view (edit mode edits the layout) and 0034's stored report view.

### §4 `TmDetailsContext`

The one contract a layout, a hatch page, an extra panel or a layout test sees. It completes
A§5.13.

#### §4.1 Contract

```ts
declare function injectTmDetails<T = TmJsonObject>(): TmDetailsContext<T>;   // inside the host's injector

interface TmDetailsContext<T> {
  readonly descriptor: TmEntityDescriptor;
  readonly id: Signal<number | null>;                          // null in create mode
  readonly mode: Signal<'view' | 'edit' | 'create'>;
  readonly status: Signal<'loading' | 'ready' | 'error'>;
  readonly error: Signal<TmApiError | null>;                   // the read's failure
  readonly entity: Signal<T | undefined>;                      // the server copy
  readonly model: Signal<T>;                                   // the working copy; entity() itself in view mode
  readonly form: FieldTree<T>;                                 // Signal Forms over model (§4.2)
  readonly dirty: Signal<boolean>;
  readonly busy: Signal<boolean>;                              // a write in flight
  readonly related: TmRelated;
  readonly extras: Signal<Readonly<Record<string, unknown>>>;  // eager extras of the last read or save
  extra<E = unknown>(name: string): Signal<TmDetailsExtraState<E>>; // a deferred extra loads on first call
  readonly can: { readonly edit: Signal<boolean>; readonly create: Signal<boolean>;
                  readonly delete: Signal<boolean>; readonly activate: Signal<boolean> };
  readonly childTarget: Signal<{ readonly collection: string; readonly id: number } | null>; // §14
  edit(): void;
  cancel(): Promise<boolean>;                                  // false: the user kept editing
  save(): Promise<boolean>;                                    // true: saved, back in view mode
  refresh(): void;                                             // view: re-read; edit: related and extras only
  update(recipe: (model: T) => T): void;                       // a programmatic write; edit and create only
}
interface TmRelated { get(entity: string, id: number | null | undefined): TmJsonObject | undefined } // related projections by id
interface TmDetailsExtraState<E> {
  readonly status: 'loading' | 'ready' | 'error'; readonly value: E | undefined;
  readonly rows: readonly TmJsonObject[] | undefined;          // a QueryRowSet extra as objects keyed by column name
  readonly error: TmApiError | null;
  reload(): void;
}
```

- **Typing.** `T` comes from the generated `TmEntityTypes` (0029 §15):
  `injectTmDetails<AcmeSalesInvoice>()`; members are the wire's camelCase.
- **`update`** writes through `model` and is a development error in view mode; it is how a layout
  computes a value live (`lineTotal = quantity × unitPrice`), and it marks the record dirty.
- **`refresh` in edit mode** never replaces the working copy or the base stamp, so a concurrent
  change still surfaces as a conflict on save (§9).
- **`can`** = the operation exists ∧ `TmPermissions.allows` (0029 §7) ∧ the mode admits it
  (view, `ready`).

#### §4.2 The form

```ts
// inside the host, once per record (decision 3)
const model = signal<T>(initial);
const tree = form(model, (p) => {
  tmDetailsPlatformSchema(p, descriptor);   // §7.1
  declaration.validate?.(p);                // §7.2
});
```

- **One form, three modes.** View mode renders `tm-value` from the field values and binds no
  control; edit and create mode bind controls to the same nodes.
- **Writes are immutable.** A field write replaces only the objects along its path (Signal Forms'
  `deepSignal`, verified fact 2), so `base` and `entity()` keep their references and
  `dirty = model() !== base` costs nothing per keystroke. Typing a value back to its original
  still counts as dirty.
- **Child collections are arrays in the model;** `tm-child-grid` binds `form.lines` with 0004's
  editable binding.
- **`initial`** before the read lands is the create model (§3.6) or `{}`; the layout shows
  skeletons until `status` is `ready`.

|---|---|---|

| `text` (a group anchor, `Name`) | one cell per admitted slot, labels with the slot suffix ("Name (E)", "Name (ع)"), each value in its content direction | one control per slot, each `dir` = the slot's content direction |

  renders nothing (A§3.3).
- **Equal geometry in both modes.** A view-mode value box has the control height (30 px, 44 px

- **Semantics.** View mode: each cell is a `div` with a `dt`-styled label and `dd` value inside the

- **Registration.** Each field registers its resolved paths with the host while rendered, so the
  error summary can focus it, the page context can list it, and errors map to it (§8.5).
- **`TmFieldGroup`** (a host directive setting `display: contents` and forwarding registration)
  lets a component of fields (a pack's `tm-gl-center-fields`) join the card's grid.

#### §6.3 Images and files (0017 staging)

1. **Pick.** `tm-image` or `tmFilePicker` takes `accept` and the size cap from the property's blob
   policy (0029 §16); `tmCheckBlobFile` refuses a wrong type or size at once with a field error
   ("This file is too large. The limit is {max}."). `cover-square` images are cropped before upload.
2. **Upload** at once: `TmApi.upload(kind, file, { fileName, signal, onProgress })` (0024, requested
   by 0026); the field shows a progress ring and its node is `pending` (request R18 to 0029), so Save
   waits for it (§8.1). Replacing or removing the file before it lands aborts the upload.
3. **Staged.** The descriptor's id becomes the field value (`imageId`); the staged blob previews
   through `TmUrls.blob(kind, id)` (0017 §5.1 serves it to its uploader). The descriptor is kept in
   the draft, so a reload still previews it.
4. **Save** attaches it (0017 §4). `Blob.NotAttachable` (`expired`, `uploader`, …) returns as a
   field error: "This file expired. Choose it again." Removing a value sends `null`, which releases
   the old blob.
5. **Upload errors** (`blob-rejected`: too large, unsupported type, image rejected, quota) render
   through `TmServerText` on the field; a 5xx shows "Upload failed" with a retry button in the
   field.

- **Concurrency.** At most three uploads run at once per page; more queue.
- **Downloads** in view mode use `TmUrls.blob(kind, id, { download: true })`; images and PDFs open
  in 0005's `TmFilePreview` on click.

#### §6.4 Child grids: `tm-child-grid`


- **Binding.** One `tm-grid` instance in every mode, bound to `form.<collection>` (0004 editable

- **New rows** come from the grid's placeholder row through `newRow` = `{ id: −n, ...defaults() }`
  with `n` a per-page counter, so every row has a stable `rowId` and the server inserts rows with

- **Height** (decision 20) = `min(max(rows + 1, 4), maxRows)` rows plus the header, fixed when the

- **Totals** sum exactly: values are scaled to the column's scale as `BigInt` (`TmDecimal` text
  included), summed, and formatted by `TmFormats`; the footer row aligns with its columns and is

- **Loading.** The grid renders inside `@defer (on viewport; prefetch on idle)` with a placeholder
  of identical geometry (header row and skeleton rows), so the editable grid chunk stays out of the
  route closure (decision 19). In the loading state the same placeholder shows.
- **Links.** In view mode navigation cells are links (0029 §12.2); Enter on a link cell follows it
  (0004's readonly Enter rule).
- **Registration.** The grid registers its collection with the host (errors, deep link, page
  context `visible`).

#### §6.8 Extras and their data loading

An extra is a per-entity result set the server's details plan adds (0015 §5.3). The layout shows
one with `*tmDetailsExtra`; the host decides when it loads.

```ts
@Directive({ selector: '[tmDetailsExtra]' })     // structural
declare class TmDetailsExtra<E> {
  readonly tmDetailsExtra: InputSignal<string>;  // the extra's name
}
// template context: { $implicit: rows (QueryRowSet extras) or value, value, reload }
```

| Kind (metadata, request R14 to 0029) | Loaded | Request |
|---|---|---|
| eager (the default) | with every `get` and every save read-back | `include: [every eager name]` (≤ `MaxExtras`, 16) |
| deferred (declared by the server) | when its directive first renders for this record version | `POST {segment}/extras { id, include: [name] }` (note §5 E1–E3) |

- **States.** Loading: a skeleton of three text lines at the panel's geometry; error:
  `tm-error-state` (compact) with Try again; empty: the panel's own content decides.
- **Deferred loads** are reads with the host's signal (aborted on leave), one request per name,
  coalesced per animation frame (two deferred panels visible at once share one request).
- **Refresh.** A save or action changes `modifiedAt`; deferred extras that are rendered reload then
  (their key includes the stamp); eager ones arrive with the read-back.
- **Reports in a card** need no extra: a card hosts 0034's `TmReportHost` with the record's id as a
  parameter.

### §7 Validation

The client checks only what the metadata knows, plus the distribution's schema; the server stays
the authority for everything else (uniqueness, references, business rules).

#### §7.1 The platform schema

`tmDetailsPlatformSchema(p, descriptor)` applies, per editable property (and per child entity
through `applyEach`):

| Rule | When | Signal Forms |
|---|---|---|
| required | not nullable, not `bool` (a `false` counts as empty), not a twin | `required(p.x)` |
| maximum length | `maxLength` set | `maxLength(p.x, n)` |
| digits | `precision` set: at most `precision − scale` integer digits; `tmNumber` already caps decimals at `scale` | `validate(p.x, …)` kind `precision` |
| read-only | `server-owned`, `derived`, `database-owned`; `write-once` outside create mode | `readonly(p.x, { when })` |
| server errors | §8.5 | one `validateTree(p, …)` |

- **Messages** come from 0002's `tmResolveFieldErrors` (`tmUi.errors.<kind>`), shown in the
  focus-only error popover with the invalid border (0002 §5 as shipped).
- **Display.** Errors show once a field is touched or dirty; Save marks every interactive field
  touched (`submit`).

#### §7.2 The distribution's schema

```ts
type TmEntityType<N extends string> = N extends keyof TmEntityTypes ? TmEntityTypes[N] : TmJsonObject;
// the tmEntity member (shape in 0029 §3; typed here)
validate?: (path: SchemaPathTree<TmEntityType<N>>) => void;   // a Signal Forms schema function
```

**Example —** a corporate customer needs a credit limit:

```ts
export const customers = tmEntity('acme.Customer', {
  details: () => import('./customer-details'),
  validate: (p) => {
    required(p.creditLimit, { when: ({ valueOf }) => valueOf(p.customerType) === 'Corporate' });
  },
});
```

- The schema runs after the platform schema, so it can add rules but never weaken a server rule.

### §8 The save flow

Save validates on the client, then runs one blocking write and maps every outcome. This section
decides the steps, the body, and what each response does.

#### §8.1 Steps

```mermaid
sequenceDiagram
  participant U as User
  participant H as Details host
  participant O as Busy overlay
  participant API as TmApi
  U->>H: Save (button, Mod+S, details.save)
  H->>H: wait for uploads; clear server errors; submit(tree)
  alt client errors
    H-->>U: error summary, focus it
  else valid
    H->>H: beforeSave, mark the draft savingAt
    H->>O: run(write save) — page inert, guard on, beforeunload armed
    O->>API: POST {segment}/save
    API-->>H: 200 or problem
    H-->>U: view mode / summary + field errors / dialog
  end
```

1. **Trigger.** The Save button, `Mod+S` or `details.save` from any origin; the dispatcher refuses
   a second invoke while one runs (0026 §9.5).
2. **Uploads.** If any field is `pending` (an upload), the overlay shows "Finishing uploads…" until
   they settle; a failed upload leaves its field invalid.
3. **Client validation.** The host clears its server errors (§8.5), then calls Signal Forms'
   `submit(tree, { action, onInvalid })`: interactive fields become touched; when the form is
   invalid, `onInvalid` shows the error summary (§8.4) and no request is sent.
4. **Payload.** `action` takes `model()`, applies `declaration.beforeSave?.(model, { mode })`, and
   builds the body (§8.2). The draft is marked `savingAt` and flushed (§11.2).
5. **Write.** `TmBusyOverlay.run(TmApi.write('{segment}/save', body), { label: 'Saving…' })` (0023):
   the page is inert, `busy` is true, the leave guard refuses navigation, `beforeunload` is armed
   (§8.7). A write is never aborted (A§7.9).
6. **Outcome** per §8.3–§8.6. The `action` itself always resolves with no Signal Forms errors: a
   422 goes to the host's server-error store (§8.5), every other outcome to its handler.

#### §8.2 The body

```json
POST /17/api/web/sales-invoices/save
{ "entities": [ { "id": 1284, "serialNumber": 1284, "invoiceDate": "2026-10-20", "customerId": 77,
                  "centerId": 12, "memo": "Quarterly supply", "modifiedAt": "2026-10-19T08:14:02.1234567+00:00",
                  "lines": [ { "id": 5501, "itemId": 9, "quantity": 48, "unitPrice": 21.5 },
                             { "id": -1, "itemId": 12, "quantity": 2, "unitPrice": 400 } ],
                  "attachments": [ { "id": 801, "fileId": 9921 }, { "id": -2, "fileId": 10433 } ] } ],
  "returnEntities": true, "include": ["related-documents"], "concurrency": "Check" }
```

- **The working copy as is.** Server-owned members travel back and are ignored (0016 §3.1's
  round-trip rule); `modifiedAt` is the base's raw string, never parsed (0015 §8); `TmDecimal`
  values write their exact text (0024 §10.4); create mode sends no `id` and no `modifiedAt`.
- **Children** are always the full arrays the `get` returned, edited; new rows carry negative ids,
  deleted rows are absent (0015 §6.5). `null` is never sent for a collection the page loaded.
- **`include`** = the eager extras, so the read-back refreshes them. No `select` (§3.3).
- **`concurrency`** is `Check`; `Override` only after the user chose Overwrite (§9.1).

#### §8.3 Success (200)

1. `entity` = `entities[0]`, the committed read-back (trimmed strings, derived values, final child
   ids); `extras` = the eager extras; `rememberRelated` and `remember` feed `TmDisplayNames`.
2. `tree().reset(entity)`: touched and dirty cleared; `model` = `entity`; `mode` = `view`;
   `base` = null; the draft cleared.
3. Create mode: `router.navigate(TmUrls.details(entity, id), { replaceUrl: true })`, so Back does
   not return to `/new`; the body re-keys on the new id with the saved copy (no request).
4. `TmPageState.markStale({ tenantId, entity })` (0025 §10): the search page and other remembered
   details of this entity refetch on return.
5. The polite status region says "Saved" (`tm.details.saved`); focus goes to Edit, in Save's slot.
   No toast (0028 policy).

#### §8.4 The error summary (422 and client errors)

- **Where.** Top of the main column, above the first card, scrolled into view; focused
  (`tabindex="-1"`), labelled by its heading. It is a 0005 `tm-alert` (`kind="error"`).
- **Heading** "Fix {count, plural, one {# problem} other {# problems}} to save" (`tm.details.fix`).
- **Items**, at most 10, then "and {n} more":

| Error | Item | Activating it |
|---|---|---|
| a field the layout renders | button "{label}: {message}" | opens its tab, expands its card, `focusBoundControl()` |
| a child-row cell | button "{collection} · row {n} · {column}: {message}" | opens the tab, `scrollToRow(rowId, { column, focus: true })` (0010 Part C request) |
| a field the layout does not render, or `ValidationPath.Root` | plain text "{label}: {message}" / "{message}" | — |

- **Stable while typing.** Items never leave while the user edits: an item whose error cleared
  shows a check and "Fixed" in the same box (decision 6). The summary is replaced on the next Save
  and removed on success or Cancel.
- **Tabs and cards** holding errors show the error dot (§6.6); collapsed cards with errors expand.
- **The page context** lists every item as a `TmContextError` (`source: 'validation'`, §16).

#### §8.5 Mapping server errors to fields

```ts
// internal: one entry per errors[] item of a 422
interface TmServerFieldError { readonly segments: readonly (string | number)[]; readonly sent: unknown;
  readonly item: TmProblemError; readonly entity: string }   // entity: the path's own entity, for labels
```

1. **Split** `errors[].path` by the 0016 §7.3 grammar: `name` segments and `[digits]` segments
   (`entities[0].lines[1].quantity` → `entities`, 0, `lines`, 1, `quantity`). The leading
   `entities[0]` is the record; anything else at the root (`body`) is a root error.
2. **Walk** the `FieldTree` by the json names (0029 decision 4): a property segment names a member,
   an index segment an array element. The child collection's descriptor gives each step's entity.
   A segment that does not resolve stops the walk: the error attaches to the deepest node reached
   and is listed as not rendered.
3. **Record** the node's value as sent; the tree validator reports the error on that node while
   its value is the one sent, so editing the field clears it and undoing brings it back.
4. **Message** = `TmServerText.error(item, entity)` (0024 §7.5): the code and arguments through
   the string pack, `arguments.property` labelled for the path's entity; a language switch
   re-renders it.
5. **Clear** all on the next Save, on Cancel, and on success.

- **Index safety.** Indices point into the payload sent; the overlay blocks edits during the
  write, so the working copy's arrays still match when the 422 arrives.

**Example —** `{ "path": "entities[0].lines[1].quantity", "code": "Range", "arguments": { "property":
"Quantity", "min": 1 } }` lands on row 2's Quantity cell and lists "Lines · row 2 · Quantity: Must
be at least 1."

#### §8.6 Other outcomes

| Response (`kind`) | Handling | Mode after |
|---|---|---|
| 409 `conflict` (`concurrency-conflict`) | the concurrency dialog (§9.1) | edit, unless the user reloads |
| 404 `not-found` on an update | the deletion dialog (§9.2) | edit |
| 400 `bad-request`, 413 `limit`, 403 `forbidden`, 403 `read-only` | `TmErrorPresenter.present(e, { kind: 'save', entity })`: 0024's 400 dialog | edit |
| 401 `step-up` | 0024's step-up dialog; the draft is already written; back on the page the draft restores edit mode (§11.2) and the user presses Save again | edit |
| 412 / route-not-found (`client-outdated`) | 0024 §5.6's write dialog "Tellma was updated. Reload to continue. Your changes are kept." | edit |
| `offline` (`not-sent`) | 0024's dialog; nothing was sent | edit |
| `offline` (`outcome-unknown`), 5xx, `unavailable` | 0024's 5xx dialog with the reference and Try again (re-runs `save()`); a save that did commit then meets its own stamp (§9.1's self case) | edit |
| 422 `validation` with `blob-rejected` items | field errors on the blob field (§6.3) | edit |
| `cancelled` | cannot happen (writes carry no signal) | — |

#### §8.7 The navigation lock

- **Overlay.** `TmBusyOverlay` makes the app `inert` (no clicks, no focus, no shortcuts) and
  shows "Saving…" after 200 ms (0023 §3.5).
- **Router.** The details route's `canDeactivate` returns false while `busy`; with
  `canceledNavigationResolution: 'computed'` (0024 router option, request) a refused Back or
  Forward returns to the same history index instead of rewriting the entry.
- **Browser.** A `beforeunload` listener is added for the duration of the write only; the browser
  shows its fixed prompt on reload or close (the Save click gave sticky activation). This is the
  brief's "navigation is prevented until the server answers", not a dirty-form prompt (§11.4).

### §9 Concurrency and deletion dialogs

A save that meets a newer stamp, or a record that is gone, asks the user what to do. Both dialogs
are 0023 `TmConfirm.ask` dialogs (`alertdialog`, focus on the primary choice) rendered by the host.

#### §9.1 The concurrency dialog (409 `concurrency-conflict`)

| Part | Another user saved | This user saved elsewhere (`modifiedById` = me) |
|---|---|---|
| title | "This record changed while you were editing" | the same |
| message | "{name} saved a newer version {relative time}. Reload to take theirs, or overwrite with yours." | "You saved this record in another tab or window {relative time}. Reload that version, or overwrite it with this one." |
| choices | ghost "Overwrite", primary "Reload theirs" | ghost "Overwrite", primary "Reload saved version" |

- **Data.** `errorDetails.conflicts[0]`: `modifiedByName` (already in the request language),
  `modifiedById`, `modifiedAt` (a parsed copy for `tm-relative-time`; the raw string is never
  reused as a stamp).
- **Reload theirs** reads the record (`get`, under the overlay labelled "Loading…"), adopts it as
  the server copy, `tree().reset(entity)`, view mode, and clears the draft. The user's edits are
  discarded; the choice's label says so.
- **Overwrite** resends the same body with `"concurrency": "Override"` under the overlay; every
  outcome is handled as in §8; a 404 opens §9.2.
- **Dismiss** (Escape, close) keeps edit mode and the working copy; nothing is sent. The next Save
  sends `Check` again.
- **Origins.** An assistant-invoked save shows the same dialog: the human decides (0026 §9.5).
- Telemetry `tm.details.conflict { choice: reload | overwrite | dismiss, self: bool }`.

#### §9.2 The deletion dialog (404 on save, or every conflict `isMissing`)

- "This record was deleted" / "Someone deleted it while you were editing, so your changes can't be
  saved." Choices: secondary "Save as new", ghost "Discard changes"; Escape keeps editing.
- **Save as new** applies the clone strip (§3.6) to the working copy, re-keys the draft to `new`,
  and replaces the URL with `TmUrls.create(entity)` in create mode; the user reviews and saves.
- **Discard changes** clears the draft and goes to the search page.

#### §10.2 Delete

1. `details.delete` confirms (0026's dispatcher, `confirm` keys): "Delete this {entity}?" /

   with children: "Delete {display name} and everything under it?" for the second action.
2. `TmApi.write('{segment}/delete', { ids: [id] })` (or `delete-with-descendants`) under the overlay
   "Deleting…".
3. **Success:** `markStale`; the draft (none in view mode) and the record's snapshot are forgotten;
   `router.navigate` to the crumb's target with `replaceUrl` (the record no longer exists); the
   search page refetches; 0028's toast "{Entity} deleted." (request: the one write toast, because
   the page is left).
4. **Failure:** 422 `Fk.InUse` → 0024's 400 dialog with `TmServerText` ("It is used by {entity}");

#### §10.3 Activate and deactivate

- `TmApi.write('{segment}/activate' | 'deactivate', { ids: [id], returnEntities: true, include:
  eagerExtras })` under the overlay; the result replaces the server copy (new `isActive`, new
  stamp); the badge flips; `markStale`. No confirmation (not destructive).

#### §10.4 Custom entity actions and their dialogs

`TmEntityActions` builds an action's request from its metadata, so the search page's bulk actions
and the details page run actions the same way; an action with arguments opens its declared dialog.

```ts
// @tellma/core/entity (designed here; consumed by /details and /search)
declare class TmEntityActions {
  run(entity: string, action: string, ids: readonly number[],
      options?: { arguments?: TmJson; include?: readonly string[] }): Promise<TmEntityActionOutcome>; // a write
  dialog(entity: string, action: string, ids: readonly number[]): Promise<TmEntityActionOutcome | null>; // null: dismissed
}
type TmEntityActionOutcome =
  | { readonly kind: 'entities'; readonly result: TmEntitiesResult }   // result: 'entities' actions
  | { readonly kind: 'own'; readonly result: TmJson }                  // the method's own result
  | { readonly kind: 'none' };
interface TmActionDialogContext<A> {
  readonly entity: string; readonly action: TmEntityActionDescriptor; readonly ids: readonly number[];
  run(args: A, form?: FieldTree<A>): Promise<boolean>;  // true: done, the dialog closes; false: errors are shown
  cancel(): void;
}
declare function injectTmActionDialog<A = TmJsonObject>(): TmActionDialogContext<A>;
```

- **The body** follows 0016 §2.3's selection: `result: 'entities'` → `EntityActionRequest`
  `{ ids, returnEntities: true, include, arguments? }`; otherwise `singleTarget` → `IdRequest`
  `{ id, arguments? }`, else `IdsRequest` `{ ids, arguments? }`. Route `{segment}/{name}`.
- **Which actions appear** on the details page: every non-built-in `entity` action the user
  `allows`, with no arguments, or with arguments and a declared `dialog`. `api` actions and actions
  with arguments but no dialog never appear (a development warning names them).
- **After success** (details): an `entities` result replaces the server copy; another kind re-reads
  the record (the action may have stamped it); `markStale`. Destructive actions confirm first
  through the dispatcher: "{action label}: {display name}?" / "This cannot be undone."
- **The dialog** is a `TmModal` (`md`, full screen below `sm`) loading the declared component.
  `run` executes the action under the busy overlay; a 422 whose paths start with `arguments` maps
  onto the dialog's `form` (§8.5's walk, rooted at `arguments`), other errors list in the dialog's
  error area; dismissing is `null`. The dialog registers an overlay page context (0026 §9.2).

**Example — Acme's "Set credit limit" dialog (16 lines):**

```ts
@Component({
  selector: 'acme-set-credit-limit',
  imports: [TmFormField, TmNumber, FormField, TmButton],
  template: `
    <tm-form-field [label]="t('Acme_Customer_CreditLimit')">
      <input tmNumber [maxDecimals]="2" [formField]="f.creditLimit" />
    </tm-form-field>
    <div tmModalFooter>
      <button tmButton variant="secondary" (click)="d.cancel()">{{ t('Cancel') }}</button>
      <button tmButton variant="primary" (click)="d.run(args(), f)">{{ t('Acme_Customer_Action_SetCreditLimit') }}</button>
    </div>`,
})
export default class SetCreditLimitDialog {
  protected readonly d = injectTmActionDialog<{ creditLimit: number | null }>();
  protected readonly args = signal({ creditLimit: null as number | null });
  protected readonly f = form(this.args, (p) => required(p.creditLimit));
}
```

### §11 Drafts, the leave guard, and refresh versus leaving

Edit mode survives a reload through a session-storage draft; leaving inside the app asks first.
This section decides what a draft holds, when it restores, and when the guard asks (Details Q3).

#### §11.1 What a draft holds

```ts
// @tellma/core (types only); stored by TmDrafts under TmDrafts.key(t, entity, id | 'new')
interface TmDetailsDraft {
  readonly v: 1;
  readonly mode: 'edit' | 'create';
  readonly model: TmJson;                               // the working copy, lossless (TmDecimal text kept)
  readonly baseModifiedAt: string | null;               // the stamp the save will send; null in create mode
  readonly clonedFrom?: number;                         // create from ?clone=
  readonly savingAt?: number;                           // set just before a write; cleared on any answer
  readonly uploads?: readonly TmBlobDescriptor[];       // staged blobs the model references (previews)
  readonly tab?: Readonly<Record<string, string>>;      // selected tab per tabs id
}
```

- **Written** through `TmDrafts.save` on every change of `model` while dirty (debounced 300 ms,
  flushed on `pagehide`, 0025 §11); never while clean.
- **Cleared** on save success, Cancel, Discard in the leave guard, Reload theirs, delete, and
  sign-out (0025).
- **Modal pages** (§15) keep no draft.

#### §11.2 When edit mode returns

| On opening | Draft in this tab | Result |
|---|---|---|
| `/{segment}/5` | `mode: 'edit'` | read the record (related, extras), then edit mode with the draft's model and `baseModifiedAt`; the notice below |
| `/{segment}/new` | `mode: 'create'`, no `clonedFrom` | create mode with the draft |
| `/{segment}/new?clone=5` | `clonedFrom: 5` | create mode with the draft (the source is not read) |
| `/{segment}/new?clone=5` | another or no `clonedFrom` | the draft is discarded; a fresh clone |
| any | none | view or create mode as §3.1 |

- **The notice** (an info `tm-alert` at the top of the main column, dismissible, rendered before
  the user interacts): "Your unsaved changes were restored." When the server's `modifiedAt`
  differs from `baseModifiedAt`: "This record changed since you started editing. Saving will ask
  how to resolve it." (the stamp is kept, so Save meets §9.1).
- **`savingAt` set** on restore (the tab reloaded or closed during a write): the notice reads "Your
  last save may have finished. Check the record before saving again."; a save of an already
  committed write meets its own stamp, and §9.1's self case explains it.
- **Covered paths:** browser reload, step-up and expiry sign-in (same-tab redirects, A§7.7), the
  412 reload, Back from another site, "reopen closed tab" (session storage survives it, A§13).
  **Not covered:** a new tab with the same URL (0025: drafts are per tab).

#### §11.3 The leave guard (in-app)

- **When.** The details route's `canDeactivate` runs on every router navigation away from a dirty
  record (links, the launcher, pins, Back and Forward). Clean
  edit mode leaves silently. During a write it refuses (§8.7).
- **The dialog** (0023's example): "Leave without saving?" / "This record has unsaved changes. They
  are lost if you leave now." [Discard changes] (ghost) [Stay] (primary, focused).
  - Discard → clear the draft, allow; the record's snapshot keeps the server copy.
  - Stay or Escape → refuse; history stays put (`canceledNavigationResolution: 'computed'`).
- **Exempt navigations:** the host's own (create → `/id` after save, clone, Save as new), and
  full-page navigations it does not see (step-up, sign-in), which the draft covers.
- **Sign-out** asks through 0024 §8.4 with `TmDrafts.dirtyCount` across tabs.
- **Picker modals** (§15) ask through `TmModal.canDismiss` with the same dialog.

#### §11.4 Refresh versus leaving (Details Q3)

- **The browser cannot tell them apart:** `beforeunload` fires the same way for reload, close and
  navigation to another site, shows only a browser-fixed text, and needs sticky activation (A§13).
- **So there is no prompt while dirty.** The draft is written continuously, so a reload, a Back
  from another site and a reopened tab all return to edit mode with nothing lost; closing the tab
  is the one loss, and the in-app guard covers every in-app path.
- **One exception:** `beforeunload` is armed while a write is in flight (§8.7).

### §12 Paging through search results

A record opened from the search page can step to its neighbours in the search page's order, across
page boundaries, and returning to the list shows the page the user ended on.

#### §12.1 The source

1. The search page opens a row with router `state: { tmFrom: <page-state key> }` (0030 §4.4),
   persisted in `history.state` (survives a reload, not a new tab).
2. The host recalls `TmPageState.recall<TmSearchSnapshot>(tmFrom)`. No snapshot, another entity,
   or an id not in `snapshot.ids` → no pager (the slot keeps its width, empty).
3. **Position** = `(page − 1) × size + index + 1`; **total** = `result.total` ("10,000+" when
   capped). A browse-tree snapshot (unpaged, 0030 §16.2) counts its shown rows in display order.

The pager is 0023's `tm-pager mode="item"`: "52 / 293" (isolated LTR, `ar-SA` digits), previous and
next.

#### §12.2 Stepping

- **Within the page:** `router.navigate(TmUrls.details(entity, neighbour), { replaceUrl: true,
  state: { tmFrom } })`; the body re-keys and reads the neighbour; the header stays. The snapshot's
  `highlight` becomes the neighbour (a new snapshot object), so the list highlights it on return.
- **At an edge** (next from the page's last row, previous from its first), when a neighbour page
  exists (`page × size < total`, or a capped total and a full page):
  1. the next button shows its busy state; the current record stays on screen;
  2. the host reads `snapshot.request.route` with `{ ...request.body, skip, take: size,
     includeCount: true }` (the search page's own select, filters and order; `TmApi.read` with the
     host's signal; a second click while it runs is ignored);
  3. an empty answer disables the arrow and stops; otherwise the host remembers a new snapshot
     under the same key: `query.page ± 1`, `canonical` and `result` for the new page, `ids`,
     `highlight` = the target, and `supersedes` = the old `canonical` (request to 0030);
  4. it navigates to the new page's first (next) or last (previous) id as above.
- **Back to the list.** The crumb links to the new canonical URL. Browser Back lands on the
  history entry of the old page (`?page=2`); 0030 adopts the snapshot whose `supersedes` equals
  that URL's canonical query and replaces the URL, so the list shows the new page with no request.
- **Gaps.** A neighbour deleted or hidden since the search shows the not-found state with the
  pager still live, so the user steps past it.
- **Modes.** Paging needs view mode; the arrows are disabled while editing (the design) and the
  shortcuts refused.

**Example —** Farah opens customer 52 of 293 from page 2 (size 50) and presses next until row 50
of the page: the 51st press reads `skip: 100, take: 50`, writes page 3 into the snapshot, opens
customer 101. Back shows the list on page 3, row 101 highlighted.

### §13 State restoration

Returning to a record within the SPA shows it exactly as the user left it: data, selected tabs,
scroll of the page, of the aside and of every scrollable panel, collapsed cards.

```ts
// @tellma/core (types only); TmPageState value under tmPageStateKey('/17/sales-invoices/1284')
interface TmDetailsSnapshot {
  readonly v: 1;
  readonly entity: TmJsonObject; readonly related: Readonly<Record<string, readonly TmJsonObject[]>>;
  readonly extras: Readonly<Record<string, unknown>>;        // eager and loaded deferred extras
  readonly tabs: Readonly<Record<string, string>>;           // tabs id → selected tab id
  readonly cards: Readonly<Record<string, boolean>>;         // collapsible card id → expanded
  readonly scroll: { readonly body: number; readonly aside: number; readonly panels: Readonly<Record<string, number>> };
}
```

- **Remembered** when the host is destroyed or re-keyed with `status` `ready` (view mode, or the
  server copy when leaving edit mode through Discard), and before a clone navigation.
- **Restored** when the route opens and `recall(key)` holds a snapshot: the record renders at once
  with no request (decision 12); tabs and cards apply before first render; scroll positions apply
  after it (`afterNextRender`). Child grids restore their own scroll from 0004's state store
  (`gridId` + `contentKey`).
- **Stale** (`isStale(key)` after a write on this entity anywhere in the tab, 0025 §10): the held
  record renders at once, and a read refreshes it in the background; scroll and tabs stay.
- **A draft wins** over the snapshot for the working copy (§11.2); the snapshot still supplies
  related and extras when fresh, and the read still runs (for the stamp check).
- **Invalidated** with every entry of the tenant when its `permissions` or `settings` tag moves
  (0025 §10). Memory only, LRU of 20 (0025).

### §14 The child-row deep link (Non-aggregate Q1)

`/{t}/{segment}/{id}?child={Collection}:{childId}` opens the record, the tab that shows the
collection, scrolls to the child row and flashes it once. It needs no code beyond naming the
tab's collection.

#### §14.1 Flow

1. The host parses `child` (`Lines:42`; a malformed value is ignored) into `childTarget`.
2. After the record loads, it looks for, in order: a `tm-details-tab` with `collection="Lines"`
   (it selects it), else a rendered `tm-child-grid collection="Lines"` outside tabs.
3. The grid registers once its rows render; the host calls
   `grid.scrollToRow(42, { flash: true })` (0010 Part C, BE C.8) and announces "Showing line 42"
   politely (the label is the child's display name when it has one). Focus stays on the page title
   (0024 §4.4).
4. The host removes `child` from the URL (`replaceUrl`), so a reload, a pin or a recent does not
   flash again, and sets `childTarget` to null.

| Case | Result |
|---|---|
| no tab or grid for the collection | the parent opens; info notice "This page doesn't show {collection label}." |
| the row is not in the collection (deleted) | the tab opens; notice "That line no longer exists." |
| the record is not found | the not-found state (§3.5) |

#### §14.2 Who builds the link

- `TmUrls.details(owner, ownerId, { collection, id })` (0024 §9.4). A drill-through from a report
  rooted at a child entity (0034) selects the child's `parentKey` (0029's `owner` metadata) so it
  knows `ownerId`.

#### §14.3 Hatch pages

- A `details.page` hatch reads `childTarget()` and reveals the row itself; when it is done it calls
  nothing: the host clears the parameter after the first render that read the signal.

### §16 Page context, the form context and page actions (the assistant seam)

The host publishes the `details` context from state it already holds (0026 §9.3); a layout
writes nothing.

| Member | Value |
|---|---|
| `kind`, `routeTemplate`, `entity` | `'details'`, `'/:t/sales-invoices/:id'` (or `…/new`), `'acme.SalesInvoice'` |
| `title` | the display name; create: "New sales invoice" |
| `status` | the host's `status` |
| `state` | `{ id, mode, dirty, tab?: { [tabsId]: tabId }, child?: 'Lines:42' }` |
| `visible` | the active tab's child grid (else the first rendered one): its columns (path, slash label) and ≤ 200 rows as displayed |
| `form` | edit and create modes only (below) |
| `errors` | the error summary's items (`source: 'validation'`, `path` in PascalCase: `Lines[1].Quantity`), the read failure or the last write failure (`source: 'request'`, with `traceId`) |
| `actions` | §10.1's actions |

- **`TmFormContext.fields`** lists every registered field (§6.2) and every child-grid column cell
  as `{ path, labelKey, label, value, errors, editable }`; paths are PascalCase with indexes
  (`Lines[1].Quantity`), mapped to the json `FieldTree` through descriptors.
- **`propose(path, value)`** writes through the node (edit and create only; `false` otherwise or
  for a read-only node), marks the path in `assisted` until the user edits that field, and never
  saves. The field shows the assisted mark (§6.2).
- **Dialogs** (concurrency, deletion, action dialogs, the picker modal) register overlay contexts.

### §17 Accessibility, RTL and responsive summary

- **Landmarks.** The title is the `h1`; the band is a `region` labelled by it; the aside a
  `complementary` region; titled cards are `section`s with an `h2`.
- **Keyboard.** Tab order: crumb, toolbar (leading, then trailing), notice or summary, cards in
  document order, the aside. Shortcuts per §10.1; grids per 0004; tabs per 0005.
- **Focus moves:** Edit → the first editable control; Save success and Cancel → Edit; a failed Save
  → the summary; a dialog → its primary choice, then back to the invoker.
- **Announcements** (one polite region): "Editing {name}", "Saved", "Showing line {n}", the
  record's display name after a paging step.
- **Non-colour cues:** icon + text badges, error dots + ", has errors", lock + "Read only", "Fixed".
- **Targets** 24 × 24 minimum; 44 px controls below `sm` (A§9).
- **RTL.** Logical properties; chevrons and pager arrows mirror; "52 / 293" and references stay
  isolated LTR; numbers keep physical right alignment (0004); slot fields take their content
  direction. **Responsive:** §5.2 and §5.3; every e2e at 390, 768, 992, 1440, LTR and RTL.

## 4. Open questions owned

- **Details Q1 — the lifecycle without boilerplate.** `TmDetailsHost` owns load, modes, the form,
  save and every outcome, drafts, the leave guard, paging, restoration, actions and the page
  context (§3–§16). A distribution writes one declaration member and a markup-only layout from
  `TmDetailsKit` (17 lines, §2); `injectTmDetails()`, `defaults`, `clone`, `validate`,
  `beforeSave`, `actions` and the `page` hatch cover the rest. *Alternatives:* a base class layouts
  extend (they inherit internals and break on host changes); a service each layout wires by hand
  (the boilerplate the question wants gone); an auto-generated form (rejected by the brief).
- **Details Q3 — refresh versus leaving.** The SPA cannot tell them apart (one `beforeunload` for
  reload, close and cross-site navigation, fixed text, sticky activation). Compromise: drafts go to
  session storage continuously, so reload, Back from another site and a reopened tab silently
  return to edit mode; the in-app guard asks "Leave without saving?"; no prompt while merely dirty;
  `beforeunload` only while a save is in flight (§11). *Alternatives:* a prompt whenever dirty (it
  fires on reload too, which must stay silent); `localStorage` drafts (they leak into new tabs).
- **Non-aggregate Q1 — drill to a child row.** Opt-in by convention: `?child=Lines:42` selects the
  `tm-details-tab collection="Lines"` (or finds a `tm-child-grid` bound to `Lines` outside tabs),
  and the grid scrolls to and flashes the row; a layout without either opens the parent with a
  notice; a `page` hatch reads `childTarget()` (§14). The tab names its collection because its
  content is lazy, which also buys its count and error dot. *Alternatives:* a per-entity drill
  callback (code in every distribution); the parent only (loses the flash); rendering every tab to
  search it (slow and visible).

## 11. Review flags

1. **Inline error summary instead of the brief's 422 modal** (decision 6; A§12 #9). Alternative:
   the modal. Flips on a preference for a blocking acknowledgement.
2. **No `beforeunload` prompt while dirty; armed only during a write** (§11.4; A§12 #10).
   Alternative: prompt whenever dirty. Flips on data-loss reports from closed tabs.
3. **Clone keeps `unique` values** (§3.6). Alternative: clear `unique` properties (the user retypes
   `Code`). Flips if users find the uniqueness error annoying.
4. **Paging replaces the history entry** (decision 11). Alternative: push per record. Flips if users
   expect Back to return to the previous record.
5. **Delete returns to the list**, not to the next record (§10.2). Alternative: step to the neighbour
   when paging is available. Flips if users delete in series.
6. **Returning shows the remembered record with no request** (decision 12). Alternative: always
   revalidate in the background. Flips if stale details after Back cause mistakes.
7. **The aside sits beside the form from `lg`, not from 768** (§5.3), so cards keep two field
   columns at `md` (A§9). Alternative: the design's 768. Flips with a design review.
8. **Reload theirs discards my edits; no merge** (§9.1). Alternative: a field-level merge view.
   Flips on conflict frequency in real use.
9. **Deferred extras need a new standard operation** (E1–E3). Alternative: every extra eager.
   Flips if no extra is heavy enough to matter.
10. **Child grids keep one height per mode** (decision 20). Alternative: grow with rows. Flips if
    users dislike inner scrolling on long documents.
11. **Promoted actions render as secondary buttons**; the design's workflow primary ("Close
    document" filled) is not offered. Alternative: a `variant: 'primary'` on `actions`. Flips on
    the first workflow entity.
12. **Actions with arguments need a hand-written dialog** (§10.4; A§3.6). Alternative: a generated
    dialog from the action's argument schema. Flips when distributions write many trivial dialogs.
13. **Shortcuts `F2`, `Mod+S`, `Alt+PageUp/PageDown`** (§10.1). Alternative: none, or Gmail-style
    letters. Flips with 0027's reserved-key review.
14. **Edit mode renders inactive tabs at idle** (§6.6) so every error can be reached. Alternative:
    render on visit only (errors in unvisited tabs list as plain text). Flips if pre-rendering
    heavy tabs costs noticeable time.
15. **View-mode values take the control height** (§6.2), against the design's 26 px, so the mode
    flip moves nothing. Flips with a design review.
16. **"Save as new" after a deletion** (§9.2). Alternative: only Discard. Flips if it confuses users.
17. **One create draft per entity per tab** (`new` key, §11.1). Alternative: a draft per creation.
    Flips if users run two creations of one entity in one tab (impossible in-app today).
18. **No toast on save** (decision 18). Alternative: a "Saved" toast. Flips if users miss the flip
    to view mode.

## 12. Challenges to the architecture

1. **A§10.1 Non-aggregate Q1: "opens the tab whose `tm-child-grid` binds `Lines`".** Tab content is
   a lazy `ng-template` (0005), so no grid exists in an unopened tab. Followed with
   `tm-details-tab collection="Lines"` naming the collection; a grid outside tabs is still found.
2. **A§5.13 `TmDetailsContext`.** `cancel(): void` cannot confirm when dirty; it returns
   `Promise<boolean>`. Added `id`, `status`, `error`, `model`, `dirty`, `extra(name)`, `can`,
   `childTarget`, `update`; `extras` stays the eager ones.
3. **Extras loading is not in the skeleton.** 0015 offers no extras-only read (f02 gap 14); a lazy
   panel would re-read the document. Followed with E1–E3 (`extras`, declared deferred names).
4. **A§3.6 "an entity action with arguments: `dialog`" (0031) vs A§2.2's import rule.** The search
   page's bulk actions open the same dialogs and `/search` cannot import `/details`; the runner and
   the dialog contract go to `@tellma/core/entity` (R16).
5. **A§10.1 Details Q3: "no `beforeunload` prompt".** Followed for dirty forms; the listener is armed
   only while a save is in flight, which is the brief's "navigation is prevented until the server
   completes the call". A refinement, not a reversal.
6. **A§11 budget: details route 80 KB** against an editable grid (~57 KB with its engine, 0030's
   figure) plus `/entity` (28 KB). Followed by deferring the grid inside `tm-child-grid`
   (decision 19); the route closure then holds the host, kit and `/entity`. If 0024 counts deferred
   chunks in the route budget, the budget must rise.
7. **A§8 history.** Query-only paging through `replaceUrl` keeps Back pointing at the list, but the
   list's history entry still names the old page; 0030 must adopt the details page's snapshot
   (`supersedes`, R19), which A§8's precedence ("URL, then page state") does not foresee.
8. **A§5.8 `TmDrafts` key `<id|new>`.** A clone shares `new` with a plain create; the draft's
   `clonedFrom` disambiguates (§11.2). No change needed, noted for 0025.
