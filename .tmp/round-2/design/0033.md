## 2. Decisions

1. **"Coded report" vs "report definition"** (§1). Alternatives in section 4.
2. **Coded reports have no rows** (§11). Alternatives in section 4.
3. **Kinds `List`, `Summary`, `Pivot`, `Chart`** (§3; Visibility Q1, section 4).
4. **One JSON document, versioned, with exactly one kind block** (§3.1). `Root` and `Kind` are
   columns (filterable, listable); everything else is `DefinitionJson`. Alt: child tables for terms
   and parameters (dozens of columns for a document that is always read whole).
5. **Terms are column keys or expressions** (§3.2). `{ "path": "Center" }` uses 0029's column-key
   kinds, so navigations and multilingual groups expand exactly as on the search page; `{ "expr" }`
   is any Queryex value expression. Alt: expressions only, with lexical bare-path detection
   (ambiguous intent; one form normalizes to the other at save instead).
6. **Every aggregate kind groups a navigation by its key alone and reads its display columns as
   `max(...)`** (§8.4). The `GROUP BY` stays one expression per level, which keeps pivots under SQL
   Server's 32-expression limit for grouping sets. Alt: group by `Id` plus every display column
   (0029's aggregate preview; four expressions per level).
7. **Pivot subtotals and totals come from one statement with `GROUPING SETS`** (§8.5). Alt: one
   query per level pair in one round trip (A§12 #20; re-scans the facts per level).
8. **Tree dimensions use level navigations, not a closure fan-out** (§8.6). `Center.Level2.Id` is a
   to-one join on `Node.GetAncestor(…)`; a `ROLLUP` over levels yields every subtotal and the
   phantom child (a level that is null while its parent is not). Alt: the closure join of A§6.4,
   which multiplies every fact row in the grouping sets that omit the tree key (challenge 1).
9. **`Having` filters the finest grouping set only** (§8.5). Subtotals and totals always include
   every filtered row, so collapsed parents never show holes. Alt: SQL's own semantics (subtotal
   rows vanish when they fail the predicate).
10. **An omitted optional parameter imposes no restriction** (§4.4). Every atom in a clause's Boolean
    skeleton that mentions it folds to the value that removes it (true, or false under `not`);
    elsewhere it binds as absent. Alt: bind null (Queryex's two-valued comparison then returns no
    rows); authors writing `(@p is null or …)` by hand.
11. **Defaults are evaluated inside the run's single round trip** (§4.3). The report query binds
    defaulted parameters to their expressions, and one constant statement echoes the values. Alt:
    evaluate first, then run (two round trips on every dashboard refresh).
12. **Sharing is a bespoke access criterion with a semi-join** (§5.3). One constant criterion
    (`FilterTree.Exists` over the share rows) gives everyone their own, shared and public
    definitions, compiles to one plan for every user and needs no per-user list. Alt: `Id in (…)`
    computed per user (unbounded, 128-item cap); a materialized audience table (stale on every
    membership change).
13. **Authoring, sharing with users and publishing to roles are separate securables** (§5.2).
    Every member authors and shares their own (bespoke criteria); `Publish` and `Transfer` are role
    grants. Alt: authoring only through a role grant (research D4 leaning; the brief says every
    user can author).
14. **Shares change only through actions** (§5.4). `share` (users) and `publish` (roles, everyone)
    are bulk set/remove commands; a save never writes shares. Alt: shares as an editable child
    collection inside save (an Edit grantee could re-share).
15. **Dashboards reuse the sharing model whole** (§5.7). `IShareable`, the share row, the criteria,
    the commands and the resolver are generic; 0035 declares its entity and four one-line actions.
16. **"Who can see this, and why" is one resolver over grants** (§6): owner, user shares, role
    shares, everyone, permission grants (filtered ones evaluated against the row) and dashboards,
    each member with the reasons and whether they can read the root entity. Alt: list only the
    denied grantees (research D5; does not answer the admin's question).
17. **Delete removes a definition for everyone; a dashboard reference blocks it** (§5.6;
    Visibility Q6, section 4).
18. **Drill-through uses server-bound filter text** (§9.4). Each aggregate result carries the
    definition filter (and expression terms) with arguments bound as literals and omitted atoms
    folded, so the drill-through list is a plain `query` with a self-contained filter. Alt:
    arguments and an omitted list in the drill URL (new `query` semantics, URL churn).
19. **`drillColumns` per definition, defaulting to the root's column default** (§3.3; Visibility
    Q3, section 4).
20. **Running totals wait** (§3.1; Visibility Q5, section 4).
21. **Child entities get read-only `query` routes under their owner's `Read`** (§10). Every child of
    a stack with `Query` is a query surface by default; traversal through the owner navigation is
    checked as from the owner. Alt: opt-in per child (reports on invoice lines would need a
    declaration in every pack).
22. **Results are self-describing** (§9). Every `ReportResult` carries its column labels, display
    types and formats, so coded reports render and export with no client code. Alt: the client
    reads labels from the definition (coded reports would need a second path).
23. **Excel export renders the result server side for every kind** (§12): list and summary flat,
    pivot fully expanded in compact form with styled subtotals, chart as its flat data. Alt:
    client-side workbook generation (bundle weight, no background path).
24. **`Title` is required** (§2.1). Pins, recents, notifications and sheet names need it; the
    studio pre-fills "Untitled report". Alt: optional, as the brief says (review flag 1).

## 3. Design (the future spec's sections)

### §1 Placement and vocabulary

- **Contracts** in `Tellma.Core.Abstractions`, namespace `Tellma.Core.Abstractions.Reports`:
  entities, the document records, `IShareable`, `IShareRow`, request and result records,
  `IReportEngine`, `IAudienceResolver`, `IShareCommands`, `ReportOptions`, `ReportErrorCodes`.
- **Runtime** in `Tellma.Core`, folder `Reports/`: `ReportDefinitionService`,
  `ReportDefinitionValidator`, `ReportCompiler`, `CubeBuilder`, `ReportExcelWriter`,
  `ShareableAccessCriteria<TEntity, TShare>`, `ShareCommands`, `AudienceResolver`,
  `ReportSeedProvisioningStep`. Child query surfaces in `Crud/ChildQueries/` (0015 edit).
- **Composition**: `CoreFeature` registers the stack (`contribution.Entity<ReportDefinition,
  ReportDefinitionService>()`), `contribution.Shareable<ReportDefinition, ReportDefinitionShare>()`
  (§5.7), the notification type (§7), the provisioning step (§13), `ReportOptions` from
  `Tellma:Reports`.
- **Tests**: `test/core/Tellma.Core.Tests/Reports/` (unit), `test/core/Tellma.Core.IntegrationTests/
  Reports/` (real SQL).
- **Vocabulary**
  - *Report definition* — a stored `core.ReportDefinitions` row; *definition document* — its JSON.
  - *Coded report* — a C# `[ApiAction]` returning `ReportResult` (§11).
  - *Kind* — `List`, `Summary`, `Pivot`, `Chart`.
  - *Term* — one column, dimension, measure or attribute of a document (§3.2).
  - *Dimension* — a grouping term of a pivot or chart; *measure* — an aggregate term.
  - *Level* — one grouping position: a flat dimension has one; a tree dimension one per tree level.
  - *Phantom child* — the row of a tree member that holds the member's own facts, distinct from its
    children's (§8.6).
  - *Owner* — the user a definition belongs to; *grantee* — a user or role a share names.
  - *Standard definition* — a seeded definition with no owner (§13).
  - *Audience* — the users who can see a definition, with reasons (§6).
  - *Run* — one execution of a definition, draft or coded report.

### §2 The report definition entity

`core.ReportDefinitions` holds one row per definition; `core.ReportDefinitionShares` its user and
role grants. The stack's segment is `reports`; its resource `core.ReportDefinition`.

- **No version tag.** The client caches no definitions (A§5.7); a save bumps nothing.
- **No `Export`/`Import` operations**, so the Excel companion does not attach and the names
  `export` and `export/start` belong to the report service (0015 edit E5).
- **Ownership rules** (the service's hooks):
  - `OwnerId` is `[Derived]`: a new row takes the caller's user id, or null when the caller is the
    system user (seeding, §13); an existing row keeps its before image's value (set in the
    validator's continuation after RT1, as 0014 §3.7 sets `FilterLanguageVersion`). `transfer` is
    the only writer of a new owner.
  - `LanguageVersion` is `[Derived]`: `QueryexLanguage.Version` when any expression changed, else
    the stored stamp; the validator mints it.
  - `Shares` is set to `null` in `PreprocessAsync` on every saved row, so a round-tripped details
    payload saves and the shares stay as they are.
  - A standard definition (`OwnerId` null) refuses save, delete, activate and share outside a
    system scope: `ReportDefinition.StandardReadOnly` (copy it to change it).
  - `BasedOnId` must name a definition the caller can read (`ReportDefinition.BasedOnInvisible`).

### §3 The definition document

The document is camelCase JSON with a format version, the parameters, the row filter, exactly one
kind block matching the `Kind` column, and the drill-through columns. C# records in
`Tellma.Core.Abstractions.Reports` mirror it member for member and are its only reader and writer.

#### §3.1 Shape

```ts
interface ReportDocument {
  formatVersion: 1;
  parameters?: ReportParameter[];            // §4
  filter?: string;                           // Queryex predicate over Root, row level
  list?: ReportList; summary?: ReportSummary; pivot?: ReportPivot; chart?: ReportChart; // exactly one, = Kind
  drillColumns?: string[];                   // column keys (N29 §6.1); summary, pivot, chart only
}
interface ReportTerm {                       // one column, dimension, measure or attribute
  path?: string;                             // a column key: scalar, group anchor, navigation, image, file
  expr?: string;                             // a Queryex value expression; exactly one of path, expr
  label?: string; label2?: string; label3?: string; // content slots 1–3, ≤ 255 each
  labelKey?: string;                         // a string-pack key instead (seeds, coded reports)
  display?: ReportDisplay; enum?: string;    // display override (§3.2); enum: an enum name for display 'enum'
  format?: { decimals?: number; grouping?: boolean; dateStyle?: 'short' | 'medium' | 'long' };
  running?: never;                           // reserved for running totals (Visibility Q5)
}
type ReportDisplay = 'number' | 'integer' | 'percent' | 'text' | 'enum' | 'date' | 'month' | 'quarter'
  | 'year' | 'datetime' | 'instant' | 'bool';
type ReportOrder = { term: number; desc?: boolean } | { expr: string; desc?: boolean };
interface ReportList { columns: ReportTerm[]; orderBy?: ReportOrder[]; top?: number }
interface ReportSummary { columns: ReportTerm[]; orderBy?: ReportOrder[]; having?: string; top?: number; totals?: boolean }
interface ReportDimension extends ReportTerm {
  order?: 'asc' | 'desc';                    // member order; default asc
  expand?: boolean;                          // pivot: expanded on open; default true
  tree?: boolean;                            // a navigation to a tree entity; default true for one
  levels?: number;                           // tree levels shown, 1–10; default min(MaxDepth, 6)
  attributes?: ReportTerm[];                 // pivot, the only row dimension: columns before the measures
}
interface ReportPivot {
  rows: ReportDimension[]; columns: ReportDimension[]; measures: ReportTerm[];
  having?: string; rowTotals?: boolean; columnTotals?: boolean; // the grand total row; the grand total column
}
interface ReportChart {
  type: 'column' | 'bar' | 'line' | 'area' | 'pie' | 'doughnut' | 'heatmap' | 'treemap' | 'gauge' | 'card';
  dimensions: ReportDimension[];             // 0–2 per type (§3.4 rule 10)
  measure: ReportTerm;                       // exactly one; Numeric
  having?: string; top?: number; orderBy?: 'dimension' | 'measure'; order?: 'asc' | 'desc';
  options?: {
    stack?: 'none' | 'stacked' | 'normalized'; legend?: 'auto' | 'none' | 'top' | 'bottom' | 'start' | 'end';
    markers?: boolean; labels?: boolean; palette?: 'categorical' | 'sequential' | 'diverging';
    min?: number; max?: number; thresholds?: { value: number; tone: 'positive' | 'warning' | 'negative' }[];
  };
}
```

- **Unknown members are refused**, not ignored: a typo must never silently drop a filter.
- **Format version.** A reader refuses a higher version (`ReportDefinition.FormatUnsupported`); a
  later version upgrades older documents in the migrator, never at read time.
- **A `path` is a column key** with 0029's kinds (N29 §6.1): `value` (scalar or twin), `text` (group
  anchor), `navigation`, `image`, `file`. An `expr` that is lexically a bare path (identifier
  segments joined by dots, 0008 §4.2) is normalized to `path` at save.
- **Labels.** `label`, `label2`, `label3` follow the content slots with fallback to slot 1. When all
  are absent the label derives from the path (the slash label, N29 §11.4) or the expression text.
  `labelKey` excludes the three slots.
- **Chart semantics** (palette tokens, axis rules, what `normalized` draws) are 0034's; this
  section fixes only the stored vocabulary.

#### §3.2 Display overrides

An override changes how a value renders, never the query. It must suit the term's Queryex type.

| Queryex type | Allowed `display` (default first) | `format` members |
|---|---|---|
| `Numeric` | `number`, `integer`, `percent` (value × 100 with `%`) | `decimals` 0–6, `grouping` |
| `String` | `text`, `enum` (values render as the labels of the enum named by `enum`) | — |
| `Date` | `date`, `month`, `quarter`, `year` (rendered in the viewer's calendar) | `dateStyle` |
| `DateTime` | `datetime`, `date` | `dateStyle` |
| `DateTimeOffset` | `instant`, `date` | `dateStyle` |
| `Bool` | `bool` | — |
| `Guid` | `text` | — |

A navigation or text term takes no override. A mismatch is `ReportDefinition.DisplayIncompatible`.

#### §3.3 Drill-through columns

- `drillColumns` lists column keys of `Root` for the drill-through list (A§8 `cols`). Absent, the
  list uses the root's column default (A§3.3). Visibility Q3.
- The list kind has none: its rows open their own record (§9.2).

#### §3.4 Validation

The save validator checks the whole document against the tenant's current schema. A failure is a
`ValidationException` (0015 §7.3) at path `[i].DefinitionJson` with argument `pointer` (an RFC 6901
pointer into the document) plus the rule's own. Expression diagnostics are
`ReportDefinition.InvalidExpression` with `code`, `start`, `length` and the engine's arguments.

1. `Root` names a queryable entity: a stack with `Query` or a child query surface (§10)
   (`ReportDefinition.UnknownRoot`).
2. The kind block present is exactly the one `Kind` names (`ReportDefinition.KindMismatch`).
3. Counts: list 1–100 columns; summary 1–50 terms with at least one measure; pivot 0–5 rows, 0–3
   columns, 1–20 measures, not both axes empty; chart per rule 10.
4. Every term is exactly one of `path` and `expr`; a `path` resolves (`ReportDefinition.UnknownPath`);
   `image` and `file` keys appear only in a list.
5. **The compile check.** The validator compiles the document exactly as a run would (§8), with
   every parameter declared and none omitted, under `ReportLimits`, and discards the SQL. Every
   diagnostic is reported; spans index the expression text at `pointer`.
6. Roles: list terms are row-level (QX4002 otherwise); summary terms are keys or measures (QX4007
   otherwise) with at least one measure; pivot and chart dimensions are keys, measures contain an
   aggregation, attributes are keys whose paths begin with their dimension's path
   (`ReportDefinition.AttributeNotOfDimension`).
7. `attributes` only when the pivot has exactly one row dimension (`ReportDefinition.AttributesNeedOneRow`).
8. `tree: true` only on a navigation whose target is a tree entity (`ReportDefinition.NotATree`).
9. `having` only on summary, pivot and chart; `top` 1–10,000 (list), 1–1,000 (summary, chart).
10. Chart dimensions: `pie` and `doughnut` exactly 1; `heatmap` exactly 2; `column`, `bar`, `line`,
    `area` and `treemap` 1 or 2; `gauge` and `card` none. The measure is `Numeric`
    (`ReportDefinition.ChartMeasureNotNumeric`). Tree dimensions are flat in charts.
11. `orderBy`: a term index into `columns`, or an expression; in a summary a key or a measure
    (0008 QX4005).
12. Display overrides per §3.2; `enum` names an enum of the composition.
13. `drillColumns` resolve on `Root`; at most 50.
14. Parameters per §4.5.
15. Grouping limits per §8.8 (`ReportDefinition.TooManyLevels`).

The validator costs no round trip: the schema and metadata are in memory, and the engine compiles
without the database.

### §4 Parameters

A parameter is a named input the document's expressions reference as `@Key`. The document declares
each one with its labels, requirement, type and an optional default expression. A run's arguments
supply values, and an omitted optional parameter imposes no restriction.

#### §4.1 Shape

```ts
interface ReportParameter {
  key: string;                               // ^[A-Za-z][A-Za-z0-9_]{0,63}$; matched ignoring case, as Queryex does
  label?: string; label2?: string; label3?: string; labelKey?: string; // default label: the key
  required?: boolean;                        // default false
  default?: string;                          // a path-free, parameter-free Queryex value expression
  type?: 'Numeric' | 'String' | 'Bool' | 'Date' | 'DateTime' | 'DateTimeOffset' | 'Guid'; // always stored (§4.2)
  entity?: string;                           // set by the server: the entity a key or FK comparison names
}
```

#### §4.2 Inference and types

- **Discovery.** The studio's `queryex/discover` (N29 §9) proposes each parameter with its type and
  `ComparedWith`. The save validator runs the same `DiscoverQuery` over every clause of the compiled
  query and normalizes the document:
  1. a referenced parameter missing from the list is added (optional, label = key);
  2. a listed parameter no expression references is removed (0008 §6.3 forbids declaring it);
  3. an absent `type` takes the inferred type; an unconstrained parameter without a `type` is
     `ReportDefinition.ParameterTypeRequired`; a conflict (QX3400) is an error;
  4. a stated `type` must equal the inferred one, or may be any type when inference is
     unconstrained (`ReportDefinition.ParameterTypeIncompatible`): Queryex has no coercion between
     parameter types (0008 §7.3), so "compatible" means equal;
  5. `entity` is set from `ComparedWith` when the compared path ends at a key or a foreign key
     (`CustomerId = @Customer` → `acme.Customer`), else removed.
- **Declared at run.** A run declares every referenced parameter with its stored `type` and
  `IsNotNull = false`, so the compiled query never depends on inference. 0015 §4.3's inference path
  is not used for reports.

#### §4.3 Defaults

- **Grammar.** `default` is a Queryex value expression with no path and no parameter (`today()`,
  `startOfMonth(today(), 'uq')`, `addMonths(today(), -1)`, `me()`, `'East'`, `5`). It must check
  against the parameter's type; a string literal coerces to a date type (0008 §7.3).
- **When it applies.** An argument absent from the request takes the default; an explicit `null`
  never does (§4.4).
- **Evaluation** happens inside the run's batch, with no extra round trip:
  1. the report query binds each defaulted parameter to its default expression
     (`ParameterExpressions`, Part F item F4), so `today()` and `me()` bind to the request's context
     slots;
  2. one constant statement (`EvaluateConstant`, F5) computes the same expressions under the same
     slots, and the run echoes the values as `Default` arguments (§9.1).
- **Dashboards** hide parameters; a required parameter without a default there is 0035's
  validation error.

#### §4.4 Arguments and omission

`ReportRunRequest.Arguments` is a JSON object keyed by parameter key, matched ignoring case.

| The request carries | Optional parameter | Required parameter |
|---|---|---|
| a value | that value | that value |
| `null` | omitted | `422 Report.ArgumentRequired` at `arguments.<Key>` |
| nothing, a default exists | the default | the default |
| nothing, no default | omitted | `422 Report.ArgumentRequired` |

- **Values** use the platform scalar encoding (0016 §3.2) of the declared type: `Date`
  `"2026-10-01"`, `Numeric` a JSON number, `Bool`, `String`, `DateTime`, `DateTimeOffset`, `Guid`. A
  value that does not convert is `422 Report.ArgumentInvalid` (arguments `key`, `type`). A key no
  parameter declares is ignored.
- **Omitted means no restriction.** The run compiles with `OmittedParameters` (F3). Every atom in a
  clause's Boolean skeleton that mentions the parameter folds to the value that removes it; in value
  positions the parameter is absent (null).

| Clause | `@Customer` omitted | Effective |
|---|---|---|
| filter `DueDate < @AsOf and CustomerId = @Customer` | the atom → true | `DueDate < @AsOf` |
| filter `not (CustomerId = @Customer)` | the atom → false (under `not`) | true |
| filter `Region = 'East' or CustomerId = @Customer` | the atom → true | true: an omitted parameter in a disjunction lifts it |
| filter `coalesce(@Customer, 0) = CustomerId` | the atom → true | true: write a `default` instead of `coalesce` |
| measure `sum(Amount, CustomerId = @Customer)` | the condition's atom → true | `sum(Amount)` |
| select `if(Amount > @Limit, 'Big', 'Small')` | value position: absent | `Amount > null` is false → `'Small'` |

- **URL form** (0024's codec carries it; 0034 owns the page): `?p.{Key}=<value>`, the value as
  culture-free text of the type (`p.AsOf=2026-10-01`, `p.Customer=1012`, `p.Posted=true`). An empty
  value is `null` (omitted); an absent key takes the default.

#### §4.5 Parameter validation (save)

1. Keys match the grammar and are unique ignoring case (`ReportDefinition.ParameterKeyInvalid`,
   `ReportDefinition.ParameterKeyDuplicate`); at most 20 parameters.
2. Types per §4.2; `default` compiles with `EvaluateConstant` against the type (diagnostics at
   `/parameters/<i>/default`).
3. `entity` only on a `Numeric` parameter.

### §5 Sharing and visibility

Sharing shares the definition, never the data: every run is the viewer's query under the viewer's
`Read` on the root (research D1). A definition is visible to its owner, to the users and roles it is
shared with, to everyone when public, and to holders of a role grant on `core.ReportDefinition`.

#### §5.1 The shareable contract (reused by 0035)

```csharp
// Tellma.Core.Abstractions.Reports
public interface IShareable                                 // on a TopLevelEntity with a [NotMapped] share collection
{
    int? OwnerId { get; set; }                              // [Derived]; null = standard
    bool IsPublic { get; set; }                             // [ServerOwned]
}
public interface IShareRow                                  // on its ChildEntity
{
    int? UserId { get; set; }
    int? RoleId { get; set; }
    ShareAccess Access { get; set; }
    int SharedById { get; set; }
    DateTimeOffset SharedAt { get; set; }
}
// FeatureContribution extension (Tellma.Core): registers the criteria provider, IShareCommands for the pair,
// the audience resolver's source and the startup check (one share collection implementing IShareRow).
public static FeatureContribution Shareable<TEntity, TShare>(this FeatureContribution contribution)
    where TEntity : TopLevelEntity, IShareable where TShare : ChildEntity, IShareRow;
```

#### §5.2 Who may do what

| Ability | Securable | Granted to every member by the bespoke criterion | Role grants |
|---|---|---|---|
| See and run | `Read` | owner, any share, public | admins: unfiltered `Read` sees every definition (A `*/*` included) |
| Edit, "Save as" | `Save` | owner; `Edit` shares | report managers |
| Create | `Save` | every member (a new row's owner is the caller) | — |
| Delete, deactivate | `Delete`, `Activate` | owner | admins |
| Share with users; see the audience | `Share` | owner | admins (share anyone's) |
| Share with roles; make public | `Publish` | — | admins, module leads |
| Change the owner | `Transfer` | — | admins |

- **`Edit` does not confer re-sharing** (research D3): `Share` is the owner's alone.
- **A filtered `Publish`** (for example `OwnerId = me()`) lets a role publish its own definitions;
  "only roles I belong to" is not expressible and is not offered (research Part 4 Q3).

#### §5.3 The access criteria

`ShareableAccessCriteria<TEntity, TShare>` is the `IAccessCriteriaProvider` (0014 §5.1) for the
entity's resource. It returns constant trees: no per-user list, no database read, byte-identical
SQL for every user. `me()` binds per request.

```text
Read  : Or( Leaf("OwnerId = me()"), Leaf("IsPublic = true"), Exists(Share, "ReportDefinition", Grantee) )
Save  : Or( Leaf("OwnerId = me()"), Exists(Share, "ReportDefinition", And(Leaf("Access = 'Edit'"), Grantee)) )
Delete, Activate, Share : Leaf("OwnerId = me()")
Grantee = Or( Leaf("UserId = me()"),
              Via("Role", And( Leaf("IsActive = true"),
                               Or( Leaf("IsPublic = true"),
                                   Exists("core.RoleMembership", "Role", Leaf("UserId = me()")) ))) )
```

- `Exists(entity, navigation, inner)` is Part F item F8: "some row of `entity` whose to-one
  `navigation` targets the current row satisfies `inner`", emitted as `EXISTS (SELECT 1 …)`. It is
  a semi-join, so the no-fan-out invariant holds. `Share` stands for the share entity
  (`core.ReportDefinitionShare`) and `ReportDefinition` for its `[ParentKey]` navigation; 0035's
  pair substitutes its own names.
- **Reasons**: every criterion carries reason `share` (0014 `BespokeAccessGrant.Reason`), so
  `access/check` explains "via sharing".
- **Effect on the client.** Every member's `Read` and `Save` on `core.ReportDefinition` are
  `Filtered` in `me.access`, so the launcher's Reports entry (0027) and the studio's New button show
  for everyone.

**Example —** the `Read` decision of a member with no role grant, compiled into `reports/query`:

```sql
WHERE ( [T].[OwnerId] = @qx0_p0 OR [T].[IsPublic] = 1
     OR EXISTS (SELECT 1 FROM [core].[ReportDefinitionShares] AS [X1]
                LEFT JOIN [core].[Roles] AS [X2] ON [X2].[Id] = [X1].[RoleId]
                WHERE [X1].[ReportDefinitionId] = [T].[Id]
                  AND ( [X1].[UserId] = @qx0_p0
                     OR ( [X2].[IsActive] = 1 AND ( [X2].[IsPublic] = 1
                          OR EXISTS (SELECT 1 FROM [core].[RoleMemberships] AS [X3]
                                     WHERE [X3].[RoleId] = [X2].[Id] AND [X3].[UserId] = @qx0_p0) ) ) ) ) )
```

(Illustrative; the exact text is the engine's. `@qx0_p0` is the `me()` slot.)

#### §5.4 The sharing actions

```csharp
// ReportDefinitionService (each delegates to IShareCommands, which 0035's DashboardService also uses)
[EntityAction("share", Action = "Share", LoadChildren = true, Description = "Shares definitions with users.")]
public Task ShareAsync(ActionContext<ReportDefinition, int> context, ShareArguments arguments);
[EntityAction("publish", Action = "Publish", LoadChildren = true, Description = "Shares definitions with roles or everyone.")]
public Task PublishAsync(ActionContext<ReportDefinition, int> context, PublishArguments arguments);
[EntityAction("transfer", Action = "Transfer", Description = "Changes the owner of definitions.")]
public Task TransferAsync(ActionContext<ReportDefinition, int> context, TransferArguments arguments);

public sealed record ShareArguments(IReadOnlyList<UserGrant>? Set, IReadOnlyList<int>? Remove);   // user ids
public sealed record PublishArguments(IReadOnlyList<RoleGrant>? Set, IReadOnlyList<int>? Remove, bool? IsPublic);
public sealed record UserGrant(int UserId, ShareAccess Access);
public sealed record RoleGrant(int RoleId, ShareAccess Access);
public sealed record TransferArguments(int OwnerId);
```

- **Semantics.** `Set` adds a grant or changes its access; `Remove` deletes a grant; anything else
  is untouched, so two people sharing at once never clobber each other. Every target row (bulk
  over `ids`) gets the same change.
- **Writes** (0015 §11.2): `share` and `publish` mark the rows with their updated `Shares` through
  `ActionContext.Save`, and the emitter synchronizes the collection; `publish` sets `IsPublic`
  through `ActionContext.Update` (a server-owned column); `transfer` marks the rows with the new
  `OwnerId` through `ActionContext.Save` (a derived column, written as the method set it). Each
  stamps the parent like any user-visible change.
- **New rows** take `SharedById` = caller and `SharedAt` = the request's `Now`; a changed access
  keeps `SharedAt`.
- **Validation** (RT1): a user grantee is an active `Individual` member (`Sharing.UserInvalid`); a
  role is active (`Sharing.RoleInvalid`); not the owner (`Sharing.OwnerIsImplicit`); `IsPublic`
  grants View only; at most 200 user and 50 role grants per row (`Sharing.TooManyGrants`); a
  standard definition accepts `publish` but not `share` (it has no owner to share for it).
- **Notification.** Newly added user grants raise `core.report.shared` (§7); role grants, access
  changes and `IsPublic` raise nothing (research D7).
- **`transfer`**: the new owner is an active `Individual` member (`Sharing.OwnerInvalid`); an
  existing user grant of the new owner is removed; the old owner keeps nothing; a standard
  definition cannot be transferred.
- **Grantees who cannot read the root** are allowed (warn, don't block, research D5): the share
  dialog shows them from the audience's `RootRead` (§6).

#### §5.5 Browsing: Mine, Shared with me, All

`reports/browse` answers the reports page's tabs (A§8 `?tab=mine|shared|all`). The tabs depend on
share rows the client cannot express in Queryex, so the server composes them.


| Scope | Filter conjoined with the query's own and the access filter |
|---|---|
| `Mine` | `OwnerId = me()` |
| `Shared` | `OwnerId != me()` and (`IsPublic` or `Exists(Share, …, Grantee)`): shared with me, my roles or everyone, standard definitions included |
| `All` | none: everything I can read (admins: every definition) |

- `Query` is the stack's `QueryRequest` (select, filter, search, order, paging, count), run as
  `query` would run it (0015 §5.2) plus the scope leaf; the activatable conjunct hides inactive
  definitions unless `IncludeInactive`.
- Coded reports are not rows; 0034 heads the list with the client registry (A§8).

#### §5.6 Lifecycle and delete (Visibility Q6)

- **Delete removes the definition for everyone** with its shares (a child collection). The client
  first reads `audience` counts and warns "Shared with 3 users and 2 roles" (0034).
- **A dashboard widget blocks the delete.** `FK_DashboardWidgets_ReportDefinitionId` (0035) is NO
  ACTION; before the persist, the service counts referencing widgets through 0035's
  `IDashboardReadThrough.DashboardsUsing(ids)` and fails `ReportDefinition.InUse` naming up to five
  dashboard titles. Deactivation is the soft alternative.
- **Deactivating the author changes nothing**: there is no running user (D1). Admins find orphaned
  definitions by filtering `OwnerId` on inactive users and `transfer` them.
- **"Save as"** is a client create with `BasedOnId` and the copied document; no shares are copied.

### §6 The audience resolver

`audience` answers "which users can see this definition, and why": every member with each reason,
the access it gives, and whether they can read the definition's root entity.

#### §6.1 Contract

```csharp
[ApiAction("audience", Action = "Share", Mutation = false, Idempotent = true)]
public Task<ShareAudience> AudienceAsync(IdRequest request);

public interface IAudienceResolver { Task<ShareAudience> ResolveAsync(string resource, int id, string? root); } // root null: RootRead not computed (a dashboard)

public sealed record ShareAudience(
    int Total, bool Capped,                                  // distinct users; Members capped at MaxAudienceMembers
    IReadOnlyList<AudienceMember> Members,                   // ordered by display name in the request's content slot
    IReadOnlyList<AudienceGrant> Grants,                     // one row per grant, with counts, for the share dialog
    RelatedEntities Related);                                // core.User, core.Role, core.Dashboard display projections
public sealed record AudienceMember(int UserId, AudienceAccess Access, AccessOutcome? RootRead, IReadOnlyList<AudienceReason> Reasons);
public sealed record AudienceReason(AudienceReasonKind Kind, AudienceAccess Access, int? RoleId, int? SharedById,
    DateTimeOffset? SharedAt, int? PermissionId, bool Filtered, long? DashboardId);
public sealed record AudienceGrant(AudienceReasonKind Kind, int? UserId, int? RoleId, long? DashboardId, int? PermissionId,
    AudienceAccess Access, int Members, int CannotReadRoot);
public enum AudienceReasonKind { Owner, UserShare, RoleShare, Everyone, Permission, Dashboard }
public enum AudienceAccess { View, Edit, Owner }
```

#### §6.2 Resolution

1. **Authorize.** `audience` requires `Share` on the row: the row loads under the caller's `Share`
   filter (404 when invisible).
2. **One Read round trip** loads: the row's owner, its shares with `SharedById`; the active
   `Individual` members of each shared active role (a public role: every active member); every
   active member when `IsPublic`; every stored permission of an active role (public included) whose
   resource is `core.ReportDefinition` or `*` and whose action is `*`, `Read` or any other (any
   action implies `Read`, 0014 §5.2), with its role's members; and, per distinct filter text among
   them, one count of `Id = @id and (<filter>)` compiled under the filter's own language version.
3. **Dashboards.** `IDashboardReadThrough.DashboardsUsing([id])` lists up to 20 dashboards; each
   one's audience (the same resolver, one level deep) adds reasons of kind `Dashboard`.
4. **Root access.** `IAccessEvaluator.EvaluateOutcomesAsync(userIds, root, "Read")` (0014 edit E2)
   gives each member's `RootRead` in one more round trip.
5. **Merge.** One `AudienceMember` per user with every reason; `Access` is the highest: `Owner` >
   `Edit` (an `Edit` share, or a permission implying `Save`) > `View`. The system user never
   appears. Members beyond `MaxAudienceMembers` (2,000) are cut, and `Total` stays exact.

- **Cost:** two round trips plus one per dashboard batch; the route is a dialog's, not a page's.
- **Visibility of memberships.** The audience lists role members to whoever holds `Share`
  (review flag 9).

### §7 The `core.report.shared` notification

| Key | Category | `Mutable` | `Severity` | `Toast` | Target | Raised by | Arguments |
|---|---|---|---|---|---|---|---|
| `core.report.shared` | `reports` | true | `Info` | true | `core.ReportDefinition` | `share` (§5.4) | `{ title, actorName }` |

- **One request per content slot.** The action groups new grantees by the content slot of their
  preferred language and raises one `NotificationRequest` per group; `title` and `actorName` are the
  definition's title and the sharer's name in that slot, falling back to slot 1. `ActorUserId` is
  the sharer, so the bell shows the actor's avatar (0021 §5.3 edit, 0028).
- **Dedup.** `DedupKey = 'core.ReportDefinition:<id>'`, `OnDuplicate = Replace`: a second share
  of the same definition before the first was read replaces it, unread, on top.
- **Text** (Core `Strings.resx`): `Notification_core_report_shared` = "{actorName} shared {title}
  with you"; Arabic "شارك {actorName} معك {title}". The target opens `/{t}/reports/{id}` through
  `TmUrls.target` (0024).
- **Withdrawal.** Removing a grant withdraws the row for that user
  (`WithdrawRequest('core.ReportDefinition:<id>', [userId])`).

| `Id` + `DashboardId` | as above; when invisible, `IDashboardReadThrough.AllowsAsync(dashboardId, id)` (0035) loads it without its own filter (research D8) | 404 |
| `Draft` | member only (the invoker's type-level `Read` passes for every member, §5.3) | — |
| every source | `RequireAsync(Root, "Read")` on the root (a child root's decision composes its owner's, 0014 §5.5); the traversal rule over every path of every clause (0015 §5.2 step 4, as refined for child roots by edit E7) | 403 `forbidden` naming the entity |

- **The definition never widens access.** The root decision's filter is conjoined into the row
  filter of every statement, so every list row, group, subtotal and chart point counts only rows
  the viewer may read. The integration suite pins it: a summary's grand total equals the sum of the
  list rows the same viewer sees (research D1).
- **`me()` means the viewer**, so "my open invoices" shows each viewer their own.

#### §8.3 The run, step by step

1. **Load.** Read the row (or take the draft); parse the document; refuse an unsupported format
   version. A draft is validated in full (§3.4); a stored document is validated only by compiling.
2. **Arguments.** Apply §4.4: the supplied values, the defaulted set, the omitted set; 422 on a
   missing required or an unconvertible value.
3. **Access.** The root decision and its filter (§8.2).
4. **Plan.** Build the `QuerySpec` per kind (§8.4–§8.6) with
   `Filter = And(Leaf(document.filter, LanguageVersion)?, decision.Filter?)`. No activatable
   conjunct: a report filters `IsActive` explicitly when it means to.
5. **Check.** `DiscoverQuery` over the clauses gives the paths; the traversal rule refuses a path
   the viewer may not touch.
6. **Compile** under `ReportLimits` with every referenced parameter declared, `OmittedParameters`,
   `ParameterExpressions` for the defaulted ones, and `BatchOrdinal`. A stored definition that no
   longer compiles (a property was removed) answers `400 query-invalid` with each diagnostic's
   `clause` set to its document pointer (`/pivot/rows/0`).
7. **Execute** one Read batch through `IGuardedBatchRunner`: the constant statement (when any
   parameter is defaulted), the main statement (`CountCap` when `IncludeCount`), and a summary's
   totals statement.
8. **Shape** the result (§9): columns from the terms, the table or the cube, the bound drill text.

#### §8.4 Terms to select items

Each term expands by its kind (N29 §6.1). Navigations use 0012's `IDisplayNames.Columns(entity,
shape, navigationPath)` (0029 E3), so the expansion is the search page's and follows the tenant's
shape (twins it does not admit never appear).

| Term | List: select items | Aggregate kinds: key | Aggregate kinds: label items |
|---|---|---|---|
| value path `Amount`, `Invoice.PostingDate` | the path | the path | — |
| text path `Name` (group anchor) | `Name`, `Name2` (admitted slots) | every admitted slot, one key group | — |
| navigation `Customer` | `Customer.Id` + display-name columns | `Customer.Id` | `max(Customer.Name)`, `max(Customer.Name2)`, `max(Customer.Code)` |
| image `Image`, file `File` | `ImageId`, `Image.Variants`; `FileId`, `File.FileName` | refused (§3.4 rule 4) | — |
| `expr` | the expression | the expression (a key) or a measure, as written | — |

- **Why `max(...)` labels.** A navigation's display columns depend on its key, so a group has one
  value of each; reading them as measures keeps the `GROUP BY` at one expression per level, inside
  SQL Server's limit of 32 grouping expressions under `GROUPING SETS` (§13 verified facts).
- **Identity columns (list).** The root `Id` comes first. A child root adds its owner's key through
  the owner navigation (`Invoice.Id`), and a grandchild its top-level owner's too
  (`Line.Invoice.Id`), so a row opens `/{t}/{ownerSegment}/{ownerId}?child={Collection}:{id}` (0031).
- **Ordering.** `{ term: i }` orders by the term: a value by the path; a text term by its active
  content slot (`coalesce(Name2, Name)` at slot 2, N29 §6.1); a navigation by its prefix then name
  in the active slot, written over the label measures in aggregate kinds
  (`max(coalesce(Customer.Name2, Customer.Name))`). The slot is the request language's (0013 §9.2).
  A list without `orderBy` orders by the root's `DefaultOrderBy`; a summary by its first key.
- **Top and paging.** A list or summary page is `Skip`/`Take` within `top`: the effective take is
  `min(Take, top − Skip)`, and `count` is capped at `top`.
- **Summary totals.** `totals: true` adds a second statement: the measures alone, `Aggregate`, no
  keys, the same filter, no `Having`, no `top`. The total therefore covers every filtered row.
- **Chart.** One aggregate statement: dimension keys, label items, the measure. `orderBy:
  'measure'` orders by the measure, else by the first dimension; `top` takes that many; without
  `top` the statement takes `MaxChartPoints + 1` and a larger result is `413 Report.TooManyPoints`.

#### §8.5 Pivot: levels, grouping sets, having

A pivot is one aggregate statement with `GROUPING SETS` (Part F item F1) that returns every leaf
cell, every subtotal at every level of both axes, and the grand totals the definition asks for.

1. **Levels.** Each row dimension contributes one level (flat) or `levels` levels (tree, §8.6), in
   definition order: R1 … Rp. Column dimensions likewise: C1 … Cq.
2. **Key groups.** One group per level: a flat navigation `[Center.Id]`; a value or expression
   `[quarter(Invoice.PostingDate)]`; a text term `[Name, Name2]`; tree level j
   `[Center.Level{j}.Id]`.
3. **Other items.** The label items of §8.4 per level (tree level j reads
   `max(Center.Level{j}.Name)` …), the attributes as `max(...)` per level, the measures, and one
   truncation probe per tree dimension (§8.6).
4. **Grouping sets.** Every pair of prefixes: for i from (rowTotals ? 0 : 1) to p and j from
   (columnTotals ? 0 : 1) to q, the set `R1…Ri ∪ C1…Cj` (an axis with no dimensions contributes only
   i = 0 or j = 0). The finest set (`i = p`, `j = q`) is first. At most (p + 1)(q + 1) sets.
5. **Level indicator.** The engine appends `GROUPING_ID` over the first expression of every group,
   in group order: bit g (counting from the most significant) is set when group g is rolled up in
   that row.
6. **Having** filters the rows of the finest set only (F1): subtotals and totals include every row
   the filter admitted, so a collapsed member never shows an empty total. A visible subtotal can
   therefore exceed the sum of its visible children (documented; review flag 4).
7. **Cap.** The statement takes `MaxPivotRows + 1` rows ordered by the first key; more is
   `413 Report.TooManyRows`. The cube builder (§9.3) enforces the member and cell caps.

**Example —** the pivot of §3.5 with `levels: 2` (to keep it short), as the engine would emit it
(illustrative; the exact text is the engine's):

```sql
SELECT [P3].[Id] AS [c0], [P4].[Id] AS [c1], DATEPART(QUARTER, [P1].[PostingDate]) AS [c2],
       SUM([T].[Amount]) AS [c3], COUNT_BIG(*) AS [c4],
       MAX([P3].[Name]) AS [c5], MAX([P3].[Name2]) AS [c6], MAX([P3].[Code]) AS [c7],
       MAX([P4].[Name]) AS [c8], MAX([P4].[Name2]) AS [c9], MAX([P4].[Code]) AS [c10],
       MAX([P2].[Node].GetLevel()) AS [c11],
       GROUPING_ID([P3].[Id], [P4].[Id], DATEPART(QUARTER, [P1].[PostingDate])) AS [c12]
FROM [acme].[SalesInvoiceLines] AS [T]
INNER JOIN [acme].[SalesInvoices] AS [P1] ON [P1].[Id] = [T].[SalesInvoiceId]
LEFT JOIN [gl].[Centers] AS [P2] ON [P2].[Id] = [T].[CenterId]
LEFT JOIN [gl].[Centers] AS [P3] ON [P3].[Node] = CASE WHEN [P2].[Node].GetLevel() >= 1
     THEN [P2].[Node].GetAncestor([P2].[Node].GetLevel() - 1) END
LEFT JOIN [gl].[Centers] AS [P4] ON [P4].[Node] = CASE WHEN [P2].[Node].GetLevel() >= 2
     THEN [P2].[Node].GetAncestor([P2].[Node].GetLevel() - 2) END
WHERE YEAR([P1].[PostingDate]) = @qx0_p0 AND (<access filter>)
GROUP BY GROUPING SETS (([P3].[Id], [P4].[Id], DATEPART(QUARTER, [P1].[PostingDate])),
                        ([P3].[Id], [P4].[Id]), ([P3].[Id], DATEPART(QUARTER, [P1].[PostingDate])), ([P3].[Id]),
                        (DATEPART(QUARTER, [P1].[PostingDate])), ())
ORDER BY [c0] OFFSET 0 ROWS FETCH NEXT @qx0_take ROWS ONLY;
```

`@qx0_p0` is bound to `year(today())` through `ParameterExpressions` when `Year` is defaulted.

#### §8.6 Tree dimensions

A navigation to a tree entity with `tree: true` renders as the tree of the members that have facts,
each parent aggregating its subtree, with a phantom child holding the parent's own facts.

- **Level navigations** (Part F item F2). Every tree entity exposes `Level1` … `Level{MaxDepth}`:
  to-one, nullable navigations to the entity itself. `LevelJ` of a row is its ancestor at depth J
  (a root has depth 1): the row itself at depth J, null when the row is shallower. They are joins
  on the unique `Node` index, so nothing fans out and every grouping set stays exact.
- **Decoding** a tree dimension in a set that includes its levels L1 … Lj, where the row's levels
  are non-null up to m:

| m | Meaning |
|---|---|
| j | the member at level j (its subtree's aggregate) |
| j − 1 ≥ 1 | the phantom child of the level-m member: the facts on that member itself |
| j − 1 = 0 | the "(None)" member: facts with no value |
| < j − 1 | redundant (the same facts, one set up); dropped |

- **Leaves.** A member whose only child is its phantom is a leaf; the phantom is dropped.
- **Ancestors come free.** Level navigations reach every ancestor of every fact's node, so no
  ancestor query exists (f08 gap 22).
- **Truncation.** When `levels` is below the entity's `MaxDepth` the statement adds
  `max(level(Center.Node))`. A value above `levels` means facts deeper than the last level were
  counted in their level-`levels` ancestor's phantom; the result reports it in `truncated` (§9.3).
- **Flat.** `tree: false` groups by the navigation itself (`Center.Id`), one level.

**Example —** Head office (10) has its own facts of 2,000 and two children, Riyadh (11) 30,000 and
Jeddah (12) 20,000; one quarter column, totals on:

| Set | Row (L1, L2) | m, j | Becomes |
|---|---|---|---|
| (L1, L2) | (10, null) | 1, 2 | Head office (own) 2,000 — phantom |
| (L1, L2) | (10, 11), (10, 12) | 2, 2 | Riyadh 30,000; Jeddah 20,000 |
| (L1) | (10) | 1, 1 | Head office 52,000 |
| () | () | — | Total 52,000 |

#### §8.9 Cancellation and background refresh

- `run` is a retried, cancellable read (A§6.3). The client aborts on a parameter change, on

#### §8.10 Caching

- The compiler caches the plan (terms, expansions, specs) per (definition id, `ModifiedAt`, shape,

  `OmittedParameters` are part of the L3 key (F3, F4), so each combination compiles once.

#### §9.3 The cube (pivot)

The cube builder decodes the grouping-set rows in C# into members and sparse cells, so the client

#### §9.4 Drill-through

A click on a summary row, a pivot cell or a chart point opens the drill-through list
`/{t}/list/{segment}?filter=…&cols=…&from={id}` (A§8, 0034). The list is a plain `query` over the
root, so its filter must be self-contained Queryex: no parameter, no omitted atom.

```csharp
public sealed record ReportDrill(
    string Segment,                                      // the root's query segment (a child segment included)
    string? Filter,                                      // the document filter, arguments bound, omitted atoms folded (F6)
    IReadOnlyList<string?> Terms,                        // parallel to Columns: an expression dimension's bound text; null for paths
    IReadOnlyList<string> Columns);                      // drillColumns, else the root's column default (A§3.3)
```

The client conjoins `(Filter)` with one condition per clicked coordinate, built with 0029's `tmQx`
builder (a `raw` node for a bound expression term, request R1 to 0029):

| Coordinate | Condition |
|---|---|
| navigation member, flat | `Customer.Id = 1012`, written on the FK path: `CustomerId = 1012` |
| tree member at level j | `descendantOf(Center.Id, 11)` (reflexive: the member and its subtree) |
| phantom of a tree member | `CenterId = 10` |
| (None) | `CenterId = null` |
| value member | `Region = 'East'`; a date `Invoice.PostingDate = cast('2026-03-01', 'date')` |
| text member | every slot it grouped by: `Name = 'Jeddah' and Name2 = 'جدة'` (`= null` for an empty slot) |
| expression member | `(<Terms[i]>) = <literal>`, e.g. `(quarter(Invoice.PostingDate)) = 3` |
| `Total` | no condition |

- **Measure conditions are not applied**: a cell of `sum(Amount, IsPosted = true)` drills to every
  row of its coordinates (review flag 7).
- **The `Having` clause is not applied** to drilled rows (it filters groups, not rows).

**Example —** the sales-by-customer summary of §3.5, `@From` defaulted and `@To` omitted, binds to
`Filter = "Invoice.PostingDate >= cast('2026-01-01', 'date') and true"`; a click on Olive Inc.
(1012) opens `/17/list/sales-invoice-lines?filter=(Invoice.PostingDate >= cast('2026-01-01',
'date') and true) and Invoice.CustomerId = 1012&cols=Invoice.SerialNumber,…&from=42` (URL-encoded).

### §10 Child-entity query routes

Every child collection of a stack with `Query` is a read-only query surface: one
`POST /{t}/api/web/{child-segment}/query` route over the child entity, under the owner's `Read`
rebased through `FilterTree.Via` (0014 §5.5). Reports and drill-through lists over invoice lines
use it; nothing is declared.

```csharp

    string ResourceSegment,                             // 'sales-invoice-lines': the kebab plural of the table; [ApiResource(Segment)] overrides
    Type EntityType,
    string OwnerResource, string OwnerNavigation,       // 'acme.SalesInvoice', 'Invoice' (the [ParentKey] navigation)

    string DefaultOrderBy, StackLimits Limits, McpExposure Mcp);
// IStackRegistry gains: IReadOnlyList<ChildQueryDescriptor> ChildQueries { get; } and ChildQueryDescriptor? FindChildQuery(string resource);
```

- **Which children.** Every `[NotMapped]` child collection, at any depth, of a stack whose
  `Operations` include `Query`. A child type opts out with `[ApiResource(Queryable = false)]`.
  A grandchild's owner is the child query surface above it, so the owner chain composes (0014 §5.5).
- **Securable.** `(Child, Read, FilterRoot = Child, Owner = (OwnerResource, OwnerNavigation))`
  registered by the stack contributor (0015 §2.7 edit); no other action.
- **Operation.** `query` only: `QueryRequest` → `RowPage`, as 0015 §5.2 for a stack, with `Root =`
  the child, `Select ?? DefaultSelect`, the search disjunction over the child's searchable
  properties (convention `Name`, `Code` when present), no activatable conjunct unless the child is
  activatable, no ancestors. `DefaultSelect` is `Id`, the parent key, the natural keys, the `Name`
  group and `Code`; `DefaultOrderBy` is `Id desc`.
- **Traversal through the owner** (0015 §5.2 step 4, edit E7). When every grant of the child's
  decision comes from the owner (no direct child grant), a path through `OwnerNavigation` is
  checked as if the owner were the root: the rows are already the owner rows the viewer may read,
  so `Invoice.PostingDate` passes under a filtered `Read` on invoices. Otherwise the ordinary rule
  applies.
- **Projection.** 0016 §2.1 adds the route; the startup audit refuses a child segment colliding
  with a stack segment or a reserved word; the contract fingerprint covers it; MCP's `tellma_query`
  accepts the child's entity name.
- **Client metadata.** The child's summary carries its `segment` and `operations: ['query']`
  (N29 §2.2 already reserves it); the drill-through list (0034) is the only SPA page over it.
- **No export** of a child list in v1; the report's own export covers the common need (review
  flag 10).

- A summary with totals ends with a bold total row ("Total"). A chart exports dimension columns then
  the measure column; the chart image is not exported.

#### §12.3 The pivot layout ("compact form", fully expanded)

1. **Header rows:** one per column level, plus one for measure names when there are two or more
   measures. A column member's label sits in the first cell of its span (no merged cells, so the
   sheet sorts and filters). The column total appears at the end as "Total".
2. **Row headers:** one column holding every row member's label indented by `Depth − 1`
   (`alignment indent`); attribute columns follow it; then one data column per (column member,
   measure).
3. **Row order:** each member is followed by its children; a parent's row carries its subtotals;
   the phantom child sits first among its siblings in italics; the grand total row ends the sheet.
4. **Styles** (four, plus the phantom): grand total bold with a double top border; depth-1
   subtotals bold on the lightest fill; depth-2 subtotals bold; deeper members regular. The same
   ladder applies to column totals.
5. **Freeze panes** below the header rows and after the row-header and attribute columns; a
   right-to-left sheet view when the request culture is right-to-left (0019 §3.3).
6. **Limits:** Excel's 16,384 columns and 1,048,576 rows; a wider pivot is `413
   Report.ExportTooWide`.

## 4. Open questions owned

- **Reports: is "hardcoded" the best term?** No: **coded report** (in code) versus **report
  definition** (stored); "ad-hoc" stays an informal synonym for the latter. *Alternatives:*
  "hardcoded" (reads as a defect to customers), "tier-2" (an internal tier number), "built-in"
  (seeded definitions are built in too). (§1, Decision 1.)
- **Reports: rows for coded reports?** No rows. A coded report is one `[ApiAction]` returning
  `ReportResult` with its own securable; the reports page merges the client registry with stored
  definitions, filtered by `TmPermissions`. *Alternatives:* read-only rows to unify access control
  (they would duplicate the registry, drift from code on every deploy, and sharing them could
  grant nothing beyond the securable). (§11, Decision 2.)
- **Visibility Q1: names of the four kinds.** `List`, `Summary`, `Pivot`, `Chart` (wire and storage
  values; UI List, Summary, Pivot, Chart). *Alternatives:* "non-aggregate, aggregate flat,
  aggregate pivot" (precise, long); "tabular, grouped, crosstab" (less familiar to the users the
  design draws). (§3, Decision 3.)
- **Visibility Q3: choose the drilled-through columns?** Yes: optional `drillColumns`, defaulting to
  the root's column default. *Alternatives:* always the column default (users ask for the measure's
  source column); the definition's own terms (aggregate terms are not row columns). (§3.3.)
- **Visibility Q4: Queryex changes for pivots.** Eight additive Part F items: grouping sets with a
  level indicator and finest-set `Having` (F1), tree level navigations (F2), omitted-parameter
  folding (F3), parameter expressions (F4), constant evaluation (F5), parameter binding for drill
  text (F6), the `'uq'` month map (F7), and the `Exists` semi-join for sharing (F8). `ComparedWith`
  is 0029's. Navigation expansion and labels stay in the host. *Alternatives:* one query per level
  pair (re-scans facts); a closure fan-out for trees (wrong under grouping sets, challenge 1);
  client aggregation (forbidden by the brief). (Section 6.)
- **Visibility Q5: running totals.** Not in v1. The term reserves `running`; a later window-function
  amendment (`SUM(x) OVER (ORDER BY …)`, and `SUM(SUM(x)) OVER` for summaries, which Queryex's
  no-nesting rule forbids today) is additive and needs no document change. *Alternatives:* client
  accumulation (client aggregation, and wrong across pages); an opening-balance measure (covers
  ledgers only). (§3.1, Decision 20.)
- **Visibility Q6: a published report whose author deletes it.** Delete removes it for everyone
  after a warning that names its reach; a dashboard that uses it blocks the delete; deactivation is
  the soft path; admins `transfer` ownership instead; deactivating the author changes nothing.
  *Alternatives:* ownership moves to the system on delete (content nobody answers for); soft delete
  (a third state beside active and inactive). (§5.6, Decision 17.)

### F1 Grouping sets with a level indicator

```csharp
public sealed record QuerySpec
{
    public IReadOnlyList<IReadOnlyList<int>>? KeyGroups { get; init; }    // a partition of the grouping keys, by select-item ordinal
    public IReadOnlyList<IReadOnlyList<int>>? GroupingSets { get; init; } // each set: indexes into KeyGroups; [] = the grand total
}
public sealed record QueryexColumn { public bool IsGroupingLevel { get; init; } }   // the appended indicator column
```

- **Caller errors:** `GroupingSets` without `Aggregate` or without `KeyGroups`; `KeyGroups` not a
  partition of exactly the derived grouping keys; an index out of range; a duplicate set; more than
  31 groups; more than 256 sets; `Having` when set 0 is not the set of every group.
- **Diagnostic:** more than 32 grouping expressions across the sets' union → `QX5008` (SQL Server's
  limit for `GROUPING SETS`).
- **Emission:** `GROUP BY GROUPING SETS ((<keys of set 0>), …, ())`, keys written exactly as in the
  select list; an appended result column `GROUPING_ID(<first key of group 0>, <first key of group
  1>, …)`, reported last in `Columns` with `IsGroupingLevel = true`, type `Numeric`, `NotNull`. Bit
  g from the most significant is 1 when group g is rolled up in the row.
- **Having** emits as `HAVING GROUPING_ID(…) <> 0 OR (<having>)`: it filters set 0's rows only.
- **Nullity:** every key `Nullable`; `sum`, `avg`, `min`, `max` `Nullable` when any set is `[]`.
- **Ordering and paging:** unchanged rules (QX4005, QX4006); the paging tiebreakers append the
  indicator column after the keys, so the order is total across sets.
- **Example:** `KeyGroups = [[0], [1]]`, `GroupingSets = [[0, 1], [0], []]` over
  `Select = "Center.Id, quarter(PostingDate), sum(Amount)"` emits
  `GROUP BY GROUPING SETS (([P1].[Id], DATEPART(QUARTER, [T].[PostingDate])), ([P1].[Id]), ())` and
  `GROUPING_ID([P1].[Id], DATEPART(QUARTER, [T].[PostingDate])) AS [c3]` (values 0, 1, 3).

### F2 Tree level navigations

```csharp
public sealed class EntityBuilder { public EntityBuilder TreeLevels(int maxDepth); }   // 1–32; requires TreeNode
```

- **Declares** `Level1` … `Level{maxDepth}` on the entity: to-one navigations to the entity itself.
  `LevelJ` of a row is its ancestor at depth J (root depth 1): itself at depth J, absent when the row
  is shallower.
- **Build rules:** the `TreeNode` property is `IsUnique`; no other member of the entity is named
  `Level<n>` for n in range.
- **Emission:** `LEFT JOIN <Source> AS [Pn] ON [Pn].[<Node>] = CASE WHEN [Pp].[<Node>].GetLevel() >= J
  THEN [Pp].[<Node>].GetAncestor([Pp].[<Node>].GetLevel() - J) END`. The `CASE` is required:
  `GetAncestor` raises on a negative argument.
- **Nullity:** always `Nullable`. Usable wherever a navigation is: paths in every clause and the
  key path of `descendantOf`.
- **Example:** `Center.Level2.Name` from `acme.SalesInvoiceLine` joins `[gl].[Centers]` twice (the
  center, then its depth-2 ancestor) and reads the ancestor's `Name`.

### F3 Omitted parameters

```csharp
public sealed record QueryCompilationOptions { public IReadOnlySet<string> OmittedParameters { get; init; } = []; } // ignore case
```

- **Each name** must be declared (caller error otherwise) and gets no slot.
- **Boolean skeleton:** in a `Filter` leaf, a `Having` leaf, and the condition argument of an
  aggregation, the nodes reached from the root through `and`, `or` and `not` only. An **atom** is a
  skeleton node that is none of the three.
- **Folding:** an atom whose subtree mentions an omitted parameter becomes `true` under an even
  number of `not`s on its skeleton path and `false` under an odd number; the ordinary constant
  folding (0008 §8.4) follows.
- **Elsewhere** (select items, ordering, `if` conditions, function arguments other than an
  aggregation's condition) an omitted parameter is a typed absent value.
- **Example:** `DueDate < @AsOf and CustomerId = @Customer`, `Customer` omitted →
  `WHERE [T].[DueDate] < @qx0_p0`; `not (CustomerId = @Customer)` → `WHERE 1 = 1`.

### F4 Parameter expressions

```csharp
public sealed record QueryCompilationOptions { public IReadOnlyDictionary<string, string> ParameterExpressions { get; init; } } // name → text
```

- **Each name** is declared and not omitted; its expression compiles in `Value` mode at the current
  language version, path-free (`QX3304`), aggregation-free (`QX4002`), parameter-free (`QX3007`), and
  checks against the declared type (string literals coerce as usual).
- **Emission:** every occurrence of the parameter emits the expression's lowered form (its literals
  and context functions become slots as usual); the parameter itself gets no slot. Diagnostics
  locate `Parameter[<name>]`.
- **Example:** `year(Invoice.PostingDate) = @Year` with `Year → "year(today())"` emits
  `WHERE YEAR([P1].[PostingDate]) = YEAR(@qx0_p0)`, `@qx0_p0` the `Today` slot.

### F7 `'uq'` through a host month map

```csharp
public sealed class QueryexSchemaBuilder { public QueryexSchemaBuilder CalendarMap(string calendar, string source); }
// source: a bracket-quoted table with Calendar varchar(2), Year int, Month int, StartDate date, EndDate date (exclusive)
```

- **`'uq'`** becomes an implemented `cal` code when the schema maps it; unmapped, QX3101 as today.
- **Semantics** follow .NET's `UmAlQuraCalendar`: `year`, `month`, `day`; `quarter = (month + 2) / 3`;
  `week` counts 7-day weeks from the first day of the Hijri year; `startOfYear` and `startOfMonth`
  return the Gregorian date of that Hijri boundary; `addYears` and `addMonths` clamp to the target
  month's last day; `diffYears` and `diffMonths` count completed units.
- **Nullity:** every `'uq'` result is `Nullable` (dates outside AH 1318–1500 have no answer).
- **Emission constraint:** the lookup is join-shaped (`OUTER APPLY (SELECT … FROM <source> WHERE
  [Calendar] = 'uq' AND [StartDate] <= d AND d < [EndDate]) AS [Cn]`), one per distinct date operand,
  never a scalar subquery: these functions are grouping keys, and SQL Server refuses a subquery in
  `GROUP BY` (error 144).
- **Example:** `month(PostingDate, 'uq')` as a key emits `[C1].[Month]` in the select list and the
  `GROUP BY`, with the `OUTER APPLY` above over `[T].[PostingDate]`.

```csharp
}
```

- **Meaning:** true for the current row when some row of `entity` whose to-one `navigation`
  targets the current row satisfies `inner`. `inner` binds with `entity` as its root.
- **Binding:** `navigation` is one to-one navigation of `entity` whose target is the current root
  (the query root, a `Via` target or an enclosing `Exists` entity); anything else is a diagnostic at
  `Filter.Exists[<entity>]`. Allowed in `Filter` trees only (a `Having` tree is a caller error);
  nesting and `Via` inside are allowed; `FilterTree.MaxDepth` counts it.
- **Emission:** `EXISTS (SELECT 1 FROM <entity Source> AS [Xn] <inner joins> WHERE [Xn].[<FK>] =
  <current alias>.[<Key>] AND (<inner>))`. Inner joins live in the subquery's own join trie; context
  slots are shared. A semi-join: nothing fans out, so aggregation stays sound.
- **Hosts construct it; the language does not change** (no collection syntax).
- **Example:** §5.3's `Read` criterion and its SQL.

## 11. Review flags

1. **`Title` required** (§2.1). Alternative: optional, as the brief says, with "#id" displays.
   Flips if users want throwaway untitled reports more than readable pins and notifications.
2. **Level navigations instead of a closure fan-out** (§8.6, F2). Alternative: the closure join of
   A§6.4. Flips only if a correct closure emission under grouping sets is shown; the evidence
   against it is in challenge 1.
3. **Default tree depth 6, at most 10 levels** (§3.1). Alternative: always the entity's `MaxDepth`.
   Flips if real charts of accounts run deeper and the truncation notice appears often.
4. **`Having` filters the finest set only** (F1). Alternative: SQL's semantics, hiding subtotal
   rows. Flips if users expect totals to drop with filtered leaves.
5. **Omitted parameters fold by polarity; inside `or` they lift the disjunction** (§4.4, F3).
   Alternative: drop the atom from its parent connective (then `a or b = @p` → `a`). Flips on
   author confusion in practice.
6. **Parameter expressions and constant evaluation for one-round-trip defaults** (F4, F5).
   Alternative: evaluate first, then run (two round trips, one fewer engine option). Flips if the
   Part F reviewer prefers fewer options over dashboard round trips.
7. **Drill ignores measure conditions and `Having`** (§9.4). Alternative: carry a measure's
   condition into the drill filter for that column. Flips on user reports that drilled rows
   disagree with conditional measures.
8. **Shares stamp the definition's `ModifiedAt`** (§5.4). Alternative: raw share writes that leave
   the parent unstamped (a studio editor would not get a 409 after a share). Flips if conflicts after
   sharing show up.
9. **`audience` lists role members to anyone holding `Share`** (§6.2). Alternative: show role
   grants as counts unless the caller holds `core.Role` × `Read`. Flips if role membership is
   treated as confidential.
10. **No Excel export from a child drill-through list** (§10). Alternative: an `export` on child
    query surfaces. Flips when users ask to export drilled invoice lines.
11. **Admins' "All" tab shows everyone's private definitions** (§5.5). Alternative: research D6's
    "Include others' private" toggle. Flips if admin lists get cluttered.
12. **A definition's grouping never follows the viewer's calendar** (§8.7). Alternative: an ambient
    calendar for an omitted `cal` argument (a filter `month(d) = 3` would change meaning per
    viewer). Flips if Hijri users need one definition that groups in their calendar.
13. **Every member authors and shares their own definitions** (§5.2). Alternative: authoring
    through a role grant (research D4). Flips if tenants want to restrict authoring.
14. **Owners cannot transfer their own definitions; `Transfer` is an admin grant** (§5.4).
    Alternative: an owner may hand over to a colleague. Flips on off-boarding friction.
15. **Pivot caps: 250,000 statement rows, 20,000 row members, 2,000 column members** (§8.8).
    Flips on measured payload and render times.
16. **Reports apply no activatable conjunct** (§8.3). Alternative: hide inactive master rows by
    default, as the search page does. Flips if master-data reports surprise users.

## 12. Challenges to the architecture

1. **A§6.4's tree rollup "over the dimension's node closure (`IsDescendantOf`), the only fan-out
   allowed" is wrong under grouping sets.** With the closure join, each fact row appears once per
   ancestor; every grouping set that omits the tree key (the column subtotals, the grand total)
   then counts a row as many times as its depth, and `GROUPING()` cannot be used inside an
   aggregate to correct it. Followed in name ("a tree-rollup grouping key", 0010 Part F) with a
   sound mechanism: level navigations (F2), to-one joins on `Node.GetAncestor`, under which a
   `ROLLUP` over the levels gives every subtotal and the phantom child exactly. Evidence: §8.6's
   walk-through: under the closure, Riyadh's and Jeddah's facts pair with both themselves and Head
   office, so the grand total reads 102,000 (2,000 + 2 × 30,000 + 2 × 20,000) instead of 52,000.
2. **A§6.4's Part F list is incomplete for the binding routes and model.** Sharing needs a
   semi-join the language lacks (F8: "shared with me or my roles" is not expressible with
   many-to-one navigations); one-round-trip defaults need F4 beside `EvaluateConstant`; the
   drill-through list's `?filter=` (A§8) needs server-bound text (F6). And `'uq'` must emit
   join-shaped, since grouping keys cannot contain subqueries. Followed by adding them, each
   additive.
3. **`reports/export` and `reports/export/start` (A§6.1) collide with 0015's reserved standard
   segments.** Followed: the stack omits `Export` and `Import`, and 0015's reserved-name rule
   narrows to the segments a stack projects (E5).
4. **The reports page's tabs (A§8 `?tab=mine|shared|all`) cannot be expressed in client Queryex**
   (share rows are a child table). Followed by adding `reports/browse` beside A§6.1's list.
5. **A§3.4's `tmCodedReport` `run` function hides the coded report's route**, so the platform
   cannot export a coded report server side, which A§3.4 promises ("the platform renders
   parameters, table, export"). Proposed: the data-only form declares `route` (R3). Likewise
   `default: 'today()'` there cannot be evaluated on the client (no client evaluator, N29 decision
   8); the coded report's method applies it and echoes it.
6. **A§6.3's 0015/0016 rows cover the child-entity route but not its traversal consequence**: under
   a filtered owner grant, 0015 §5.2's rule confines `Invoice.PostingDate` to the invoice's
   `RelatedSelect` and the report 403s. Followed with the owner-path refinement (E7(b)) and the
   matching client rule (R1).
7. **Research D5's narrow share-target check is not enough for the brief's "which users can see it,
   and why"**, and 0014's `access/check` is one user at a time. Followed with the audience
   resolver and a bulk outcome evaluation in 0014 (E2).
