## 2. Decisions

1. **One host component renders every entity's search page from its descriptor** (§1). The route host
   (0024 §4.4) loads `TmSearchHost`; a distribution writes a declaration, never a page. Alt: a
   generated component per entity (code a distribution would carry).
2. **Search Q1: click anywhere on a row opens it, except the checkbox cell; Enter opens the
   highlighted row; the display-name cell and every navigation cell are real `<a href>` links**
   (§7.2, note §4). Alt: link-only (precision clicks for the common case); row-only (no native
   new-tab, no links to other entities).
3. **The highlight is the grid's active row, driven from the search field** through BE C.2's
   `TmGridDriver` and a host-owned target proxy (§6.3). Focus never leaves the field while arrows move
   the highlight. Alt: move focus into the grid (loses the typed text's caret and the IME context).
4. **Type-to-search intercepts one printable key, focuses the field and inserts the key with
   `execCommand('insertText')`** (§6.2). Deterministic in every engine and one undo step. Alt: move
   focus in `keydown` and let the browser deliver the character (old, unspecified behaviour).
5. **Enter before the results reflect the typed text opens the first result when it lands** (§6.3).
   A fast "type, Enter" never opens a stale row. Alt: open whatever is highlighted (a race).
6. **The URL query is all-or-nothing against page state** (§4.2). A URL with any query parameter
   defines the whole query; without one, the remembered query applies. Alt: per-field merge (a pin
   with one filter would inherit an unrelated remembered search).
7. **The address bar is canonical**: after resolution the host replaces the URL with the canonical
   form (§4.3), so copying it always reproduces the page. Alt: write only on user changes (a page
   opened from preferences would share a URL that shows something else).
8. **Query changes replace the history entry; page changes push** (A§8; §4.4).
9. **`view` and `list` are two axes** (`view=grid|tiles`, `list=1` for a tree entity shown flat), so a
   tree of tiles and a flat tiles list are both addressable (§4.1). Challenge 1 to A§8's single
   four-valued `view`.
10. **The view preference is kept per breakpoint class** (`narrow` below `md`, `wide` from `md`), so a
    phone's tiles never become the desktop's view (§3.4). Alt: one sticky value (the design's note).
11. **The select is the union of the column plan and the tile plan**, so switching grid ↔ tiles never
    re-queries (§5.1). Alt: per-view selects (a request per toggle).
12. **Column filters, custom filters and the advanced filter travel as separate `Filters` leaves**
    (§5.1, note §5 E1). Diagnostics then point at the leaf the user wrote. Alt: one `and`-joined
    `Filter` (spans shift; one bad leaf hides which control is wrong).
13. **Ordering is by one column; the default order shows no indicator** (§7.3). A tie-break `Id` is
    appended so paging is stable. Alt: show the default order's arrow (a third click then does
    nothing visible).
14. **In tree view an order sorts siblings; it never drops the tree to a list** (§16.5). The
    get-by-parent-ids `OrderBy` makes it cheap. Alt: the design's "any order-by shows a list" (a hidden
    mode switch).
15. **The browse tree is unpaged: roots plus remembered expansions in one `get-by-parent-ids` call
    with `IncludeRoots`; a tree beyond `MaxTake` rows falls back to the list for that visit** (§16.2).
    Alt: page the roots (a second request on every restore; pages of a tree read badly).
16. **A search or filter on a tree shows matches inside their ancestors, statically expanded, the
    ancestors muted and labelled** (§16.4). Lazy expansion is off in that mode, and it never writes the
    expansion memory. Alt: lazy children under matches (mixes filtered and unfiltered rows).
17. **Trees Q1: export sends the displayed column model (`ExportColumn[]`), never the grid's
    select** (§13.2, note §4). A navigation exports one display-name column in the request language.
18. **Export by query runs synchronously when the grid's count is exact, else in the background;
    by selection always synchronously** (§13.2). The count cap (10,000) sits below the synchronous
    export cap (100,000), so the client needs no extra limit. Alt: always try synchronously and fall
    back on `413` (wastes a round trip on large sets; the `413` path is kept as a fallback).
19. **The column editor applies live; Done only closes** (§11.2). Additions re-query; removals and
    moves re-render only. Alt: a draft applied on Done (an accidental outside click loses the work).
20. **User expression columns live in the preference only, never in URLs** (§11.3, 0029 §6.1).
    A URL's `cols` that equals the preference's path keys adopts the preference, expressions
    included. Alt: expressions in URLs (a crafted link could render arbitrary constant text in every
    cell).
21. **Filter popups apply on Apply** (column filter, advanced filter); the Active-only switch and custom
    filters sit in the advanced popup and apply with it (§10). One rule for every filter. Alt: instant
    toggles (two behaviours inside one popup).
22. **Selection survives query and page changes, is capped at `limits.maxIds`, and clears after a
    successful write action** (§12). Alt: keep it after writes (rows that vanished from an active-only
    list stay selected invisibly).
23. **Tree deletes offer two actions: Delete and Delete with descendants** (§12.2). Alt: one Delete
    that cascades (the design's copy; destructive by surprise).
24. **The selection bar replaces only the leading toolbar group; the trailing group never moves**
    (§3.2). The view toggle stays visible in selection mode (the design hides it). Rule 2D.
25. **Page size options 20, 50, 100, 200; default 50** (§14). Alt: the design's 20 (half a desktop
    screen empty).
26. **The search hatch replaces the results region only** (§2.5); rows 1–2, URL, state and actions stay
    the platform's. Alt: replace the whole page (every hatch re-implements the toolbar).

## 3. Design (the future spec's sections)

### §1 Placement and vocabulary

`@tellma/core/search` holds the search page; it imports `@tellma/core` and `@tellma/core/entity`
and nothing else of `@tellma/core` (A§2.2).

| Part | Exports | Loaded |
|---|---|---|
| host | `TmSearchHost` (`tm-search-host`), `injectTmSearch`, `TmSearchContext`, `TmSearchCell` (the `display` hatch's inputs), `injectTmCustomFilter` | with the route |
| picker page | `TmSearchPickerPage` (provided as `TM_ENTITY_PAGES.search`, 0029 §14.4) | with the modal |
| column editor | internal `tm-search-column-editor` | `@defer (on interaction)` from the Columns button |
| advanced filter | internal `tm-search-filters` | `@defer (on interaction)` |
| import dialog | internal `TmImportDialog` | `import()` on the Import action |
| types in the primary entry point | `TmTileDeclaration`, `TmCustomFilterDeclaration`, `TmSearchSnapshot` (types only, zero bytes) | eager |

- **Folder** `client/projects/core/tellma-core/search/`. **Budget** 16 KB gzip self-weight for the
  route chunk (host, grid and tiles glue, field, pager, filters glue); the editor, the filter popup
  and the import dialog are separate deferred chunks (≤ 6 KB each). The search route as a whole
  stays inside 0024's 110 KB (A§11: grid + engine ≈ 57 KB, `/entity` 28 KB).
- **Every deferred chunk is in the worker's `shell` group** (A§6.6), so "on interaction" is a cache
  read on a warm launch.
- **Testing exports** (`@tellma/core-testing`): `TmSearchPageHarness`, `TmColumnEditorHarness`,
  `TmImportDialogHarness`.

**Vocabulary**

- *Query state* — every `TmSearchQuery` field the page shows: text, filters, order, columns, page,
  size, view, list.
- *Canonical query* — the codec's canonical URL query string of the resolved state with defaults
  omitted (0024 §9.5); the identity of a result.
- *Result* — one page of rows (and ancestors in tree search) for one canonical query.
- *Highlight* — the grid's active row (`activeRowId`) or the tiles' active tile (`activeId`).
- *Leaf* — one `Filters` entry of a request: the advanced filter, a custom filter, a column filter.
- *Browse tree* — a tree entity in tree view with no text and no filter; *search tree* — the same
  with text or a filter.
- *Context row* — an ancestor shown only because a descendant matched.
- *Breakpoint class* — `narrow` (below `md`, 768 px) or `wide` (from `md`).

### §2 What a distribution writes

The common case is the declaration of A§3.3 and nothing else. This section gives the meaning of the
five search members and their hatches.

```ts
// customers/customers.entity.ts — the whole search page
export const customers = tmEntity('acme.Customer', {
  section: 'sales',
  columns: ['Code', 'Name', 'CustomerType', 'Currency', 'CreditLimit', 'IsActive'],
  orderBy: 'Code',
  tile: { image: 'Image', title: 'Name', subtitle: 'Code', badge: 'IsActive' },
  filters: [{ key: 'mine', labelKey: 'Acme_Customer_CreatedByMe', queryex: 'CreatedById = me()' }],
  details: () => import('./customer-details'),
});
```

#### §2.1 `columns` and `orderBy`

- **`columns`** is the default column set of the grid, the picker's advanced search, the export and
  0034's drill-through (A§3.3). Each entry is a column key (0029 §6.1): a path, a group anchor, a
  navigation (its display name), or a declared expression `{ expression, labelKey, type? }`.
- **Absent:** the display-name columns (0029 §5.1), the other natural keys, then `IsActive` when
  activatable.
- **`{ path, width }`** fixes a width in px; otherwise `tmGridColumnFor` (0029 §12.1) chooses by type.
- **`orderBy`** (`'Code'`, `'Name:desc'`) is the order when the user has chosen none; absent →
  the metadata's `defaultOrderBy`. It is never shown as a header indicator (decision 13).

#### §2.2 The cell hatch: `{ path, display }`

A column whose cell needs a custom rendering names a lazy component; the host loads every `display`
component of the shown columns in parallel with the data (both from the worker cache when warm) and
renders it in the grid's `*tmGridDisplay`.

```ts
// @tellma/core/search
@Directive()
declare abstract class TmSearchCell<V = TmCellValue> {
  readonly value: InputSignal<V>;            // 0029's TmColumnPlan.value(row)
  readonly row: InputSignal<TmPlanRow>;
  readonly column: InputSignal<TmColumnPlan>;
}
```

**Example —** a credit-utilization bar beside the limit (5 lines in Acme):

```ts
columns: ['Code', 'Name', { path: 'CreditLimit', display: () => import('./credit-cell') }],
// credit-cell.ts
@Component({ selector: 'acme-credit-cell', template: `<tm-progress-bar [value]="pct()" [label]="text()" />` })
export default class CreditCell extends TmSearchCell<number> { /* pct, text computed from value() and row() */ }
```

- **Rules.** The cell is static (no focusable content except a link), fixed row height, single line;
  it must not fetch. Tiles never use `display`.

#### §2.3 `tile`

```ts
// @tellma/core (types only)
type TmTileDeclaration<N extends string> =
  | { readonly image?: TmPath<N>; readonly title?: TmPath<N>; readonly subtitle?: TmPath<N>;
      readonly topEnd?: TmPath<N>; readonly badge?: TmPath<N> }      // the four corners and the image
  | { readonly component: TmLazyComponent };                         // hatch: a TmSearchCell-like tile body
```

| Member | Corner (0023 §3.8) | Default when `tile` is absent | Rendering |
|---|---|---|---|
| `image` | image column | the first property with an `Avatar` or `Photo` blob policy, else none | thumbnail through `TmUrls.blob` (0029 §16); a navigation or its FK scalar both resolve |
| `title` | top-start, a link | the display name | display name for a navigation or group; `TmFormats.text` otherwise |
| `subtitle` | bottom-start | the first natural key the display name does not show (`Code`) | `TmFormats.text` |
| `topEnd` | top-end, tabular when numeric | none | `TmFormats.text` |
| `badge` | bottom-end badge | `IsActive` when activatable | `IsActive`: "Active" (success) / "Inactive" (neutral); another bool: its label when true, nothing when false; an enum: the value's label (neutral) |

- **`{ component }`** replaces the tile body inside the fixed 60 px tile (0023 `tmTileContent`); the
  component extends `TmSearchCell` with `column` unset and `value` = the row id.
- Tile keys join the select (decision 11); `tmCheckEntityDeclaration` (0029 §3) reports
  `unknown-path` for a bad tile path.

#### §2.4 `filters`: custom filters (URL `x.{key}`)

```ts
// @tellma/core (types only)
type TmCustomFilterDeclaration =
  | { readonly key: string; readonly labelKey: string; readonly queryex: string }        // a switch: on → x.key=1
  | { readonly key: string; readonly labelKey: string;
      readonly options: readonly { readonly value: string; readonly labelKey: string; readonly queryex: string }[] } // a radio group: x.key=<value>
  | { readonly key: string; readonly labelKey: string; readonly component: TmLazyComponent;
      readonly toQueryex: (value: string) => string | null };                              // hatch: its own control
```

- **`key`** matches `^[a-z][a-z0-9-]*$`; the URL carries `x.{key}={value}`.
- **Switch** (common): value `1` applies `queryex`. **Options**: the value names an option; an
  unknown value is dropped. **Hatch**: the component edits a value string and `toQueryex` builds the
  leaf with 0029's `tmQx` builder (never string concatenation); `null` means "no filter".
- **Hatch contract.** The component injects `injectTmCustomFilter()`:
  `{ value: WritableSignal<string | null>, descriptor }`; the popup's Apply reads `value`.
- **Leaves come from code**, so the server reports a bad one as a development error (a `query-invalid`
  on a custom leaf logs `tm.search.custom-filter-invalid` and shows the generic invalid state).

**Example —** the options form:

```ts
filters: [{ key: 'credit', labelKey: 'Acme_Customer_Credit', options: [
  { value: 'none', labelKey: 'Acme_Customer_Credit_None', queryex: 'CreditLimit = 0' },
  { value: 'high', labelKey: 'Acme_Customer_Credit_High', queryex: 'CreditLimit >= 500000' } ] }],
// URL: /17/customers?x.credit=high
```

#### §2.5 The `search` hatch: a results region that is not a list

`search: () => import('./customers-board')` replaces row 3 (§3) with the component. Rows 1–2, the URL,
page state, preferences, page context and actions stay the host's; the view toggle and the Columns
button are hidden (they configure the platform's views).

```ts
// @tellma/core/search
declare function injectTmSearch<T = TmJson>(): TmSearchContext<T>;
interface TmSearchContext<T = TmJson> {
  readonly descriptor: TmEntityDescriptor;
  readonly query: Signal<TmSearchQuery>;                 // resolved state (§4), canonical
  readonly plan: Signal<TmSelectPlan>;                   // 0029 §6.2, columns ∪ tile keys
  readonly rows: Signal<readonly TmPlanRow[]>;           // the result's page rows
  readonly ancestors: Signal<readonly TmPlanRow[]>;      // search tree context rows; [] otherwise
  readonly total: Signal<number | null>; readonly totalIsLowerBound: Signal<boolean>;
  readonly status: Signal<'loading' | 'ready' | 'error'>; readonly error: Signal<TmApiError | null>;
  readonly selection: Signal<ReadonlySet<number>>;
  select(ids: Iterable<number>, mode: 'add' | 'remove' | 'replace'): void;
  readonly activeId: WritableSignal<number | null>;      // the highlight
  update(patch: Partial<TmSearchQuery>): void;           // §4.4's history rules apply
  refresh(): void;
  open(id: number, options?: { newTab?: boolean }): void;
  url(id: number): string;                               // the details URL
  readonly mode: 'page' | 'picker';
}
```

- **Who uses it.** The `search` hatch, the `display` and tile hatches (read-only use), and the platform
  pages that set the hatch (0034's reports page, 0028's pages when they need a custom body).
- **Example —** the reports page (0034) renders coded reports first, then `ctx.rows()`, and opens a
  definition with `ctx.open(id)`.

### §3 Page anatomy and layout

The page is 0023's `tm-page-header` (rows 1–2) over a results region (row 3) that fills the rest of
`main` (A§9: `block-size: 100%`; pages never compute chrome heights). 0024's route skeleton `search`
draws the same geometry, so the chrome replaces it with zero layout shift.

#### §3.1 Rows 1 and 2

| Slot | Content (in DOM and visual order) |
|---|---|
| row 1 `[tmPageTitle]` | `h1`: the entity's plural label (`TmEntities.label(name, true)`), ellipsis |
| row 1 `[tmPageHeaderEnd]` | search field (§6), Filters button (§10) |
| row 2 `[tmPageToolbar]` (leading group) | Create (§13.1), Export menu (§13.2), Import (§13.3), the distribution's `group: 'primary'` page actions; or, while rows are selected, the selection bar (§12.1) |
| row 2 `[tmPageToolbarEnd]` (trailing group) | Columns (§11), Refresh (§13.4), pager and page size (§14), separator, view toggle (§3.4), Tree/List toggle (tree entities, §16.1) |

#### §3.2 Responsive behaviour (A§9 thresholds)

| Element | `xs` < 576 | `sm` | `md` | `lg` | `xl`, `xxl` |
|---|---|---|---|---|---|
| search field | fills row 1 after the title (min 160) | 240 px | 240 px | 240 px | 240 px; `xxl` 320 px |
| Filters | icon + chevron | icon + chevron | label | label | label |
| Create | `+` icon button | "New customer" | label | label | label |
| Export, Import | one `…` overflow menu | buttons with labels | labels | labels | labels |
| Columns | icon | icon | icon | label | label |
| pager | status + arrows | same | same | same | same |
| page size | hidden | hidden | "50" | "50" | "50 per page" |
| view toggle | icons | icons | icons | icons | icons + labels (`labels="xl"`) |
| default view | tiles | tiles | grid | grid | grid |
| popups (column filter, advanced filter, column editor) | `TmModal` `placement: 'end'`, full width | popovers | popovers | popovers | popovers |
| control height | 44 px (touch) | 30 px | 30 | 30 | 30 |

- **Fixed geometry.** Each row has a fixed block size (the field height, 44 below `sm`); row 2 is
  `nowrap`. Every button's label visibility is decided by container width only (0023 `segmented`
  `labels`, container queries per BE B.1), never by content, so a selection, a filter or a loading
  state never changes a width.
- **The selection bar** swaps the leading group's content in place. The trailing group is anchored at
  the inline end and keeps every control (decision 24). Below `sm` the Columns button hides while rows
  are selected; it is the trailing group's first item, so nothing to its end moves.
- **Filters button** reserves a two-digit `tm-counter` slot (empty when no filter is active), so
  applying the first filter does not move the search field.

#### §3.3 Row 3: the results region

- **Grid** (`tm-grid`, or `tm-tree-grid` in tree view): full bleed, frozen header, zebra rows, dense
  (`size: 'sm'`, 28 px rows), the checkbox column first, `rowHeaders: false`, stable column widths
  (never data-dependent, 0004 §7), `scrollbar-gutter: stable` (BE C.7). Its scroller is the only
  scrollbar; it never spans rows 1–2.
- **Tiles** (`tm-tiles`): fills the region and scrolls inside (0023 §3.8).
- **States** (§5.3) replace the rows inside the region; rows 1–2 never move.
- **Loading indicator**: a 2 px indeterminate `tm-progress-bar` absolutely positioned on the region's
  top edge, shown 150 ms after a request starts (no flash for fast answers); `aria-busy` is set at once.

#### §3.4 Grid or tiles

- **Default** by breakpoint class: tiles when `narrow`, grid when `wide` (A§9 `md` row).
- **Toggle** `tm-segmented` (Grid `table-2`, Tiles `layout-grid`, 0023 §3.6 example). A change writes
  the preference for the current breakpoint class and the URL (§4.4).
- **Preference** `search.<entity>.view` = `{ narrow?: 'grid' | 'tiles'; wide?: 'grid' | 'tiles';
  list?: boolean }` (decision 10; challenge 2). Crossing `md` on resize applies the other class's
  choice (a resize, never a click, so rule 2D holds).
- **No re-query** on a toggle (decision 11); the highlight, selection and page carry over.

### §4 Query state: meaning, precedence, URL, history

The page's state is one `TmSearchQuery` (0024 §9.5 parses and prints it). This section says what
each field means, which source wins when the page opens, and how changes reach the URL and history.

#### §4.1 Fields

| Field (URL) | Meaning | Default (omitted from the URL) | Request (§5.1) |
|---|---|---|---|
| `q` | search text, trimmed, at most `limits.maxSearchLength` | empty | `Search` |
| `columnFilters` (`f.{key}`) | one filter per column key, 0029 §13.2 operators | none | one leaf each |
| `filter` (`filter`) | advanced Queryex predicate | none | one leaf |
| `inactive` (`inactive=1`) | include inactive rows; activatable entities only, dropped otherwise | false | `IncludeInactive` |
| `custom` (`x.{key}`) | declared custom filters (§2.4) | none | one leaf each |
| `order` (`order=Name:desc`) | one column key and direction | the declaration's `orderBy`, else `defaultOrderBy` | `OrderBy` + `, Id` |
| `cols` (`cols=Code,Name,Parent`) | column keys, written only when they differ from the code default | the code default (§2.1) | the select (§5.1) |
| `page`, `size` | 1-based page; page size | `1`; the preference, else 50 | `Skip`, `Take` |
| `view` (`view=tiles`) | `grid` or `tiles`, written only when it differs from the breakpoint class's default | the preference, else the class default | — |
| `list` (`list=1`) | a tree entity shown flat; dropped on other entities | false (the tree) | — (decides the call, §16) |

- **Challenge 1.** A§8's `view: 'grid' | 'tiles' | 'tree' | 'list'` cannot say "tree of tiles" or
  "tiles list of a tree entity"; this note needs 0024 to split it into `view` and `list` (note §7).
- **A key that does not resolve or is unreachable** (0029 §6.4) is dropped from `cols`, `order` and
  `f.`; an `f.` value invalid for its kind (`tmFilterLeaf` → null) is dropped. Each drop emits 0029's
  `tm.entity.column-dropped { source: 'url' }` and rewrites the canonical URL.
- **Expression columns never appear in `cols`** (decision 20; §11.3).

#### §4.2 Precedence when the page opens

1. **URL.** When the URL carries any query-state parameter (`q`, `f.*`, `filter`, `inactive`, `x.*`,
   `order`, `cols`, `page`, `size`, `view`, `list`), the URL defines the whole query; absent fields
   take steps 3–4 (decision 6).
2. **Page state.** Otherwise, when `TmPageState.recall(key)` holds a `TmSearchSnapshot` for this page
   (§15), its query applies whole.
3. **Preferences** for `cols`, `size`, `view` and `list` (§11.4, §14, §3.4).
4. **Code defaults** (§2.1, §4.1).

- **Selection and expansion** restore from page state whenever an entry exists for this page,
  whatever the query source (selection survives queries, §12.1).
- **Rows** restore from page state only when the entry's canonical query equals the resolved one
  (§15.2).

**Example —** three ways to open Centers:

| Opened from | URL | Applies |
|---|---|---|
| pinned bar, no query, after searching "jed" earlier in this tab | `/17/centers` | page state: `q=jed`, rows, scroll; no request |
| a pin `/17/centers?f.CenterType=in:Service` | that URL | URL: the filter; `q` empty; columns from the preference; selection from page state |
| a colleague's link `/17/centers?q=jed&cols=Code,Name,Parent&page=2` | that URL | exactly that, whatever the reader's preference |

#### §4.3 The canonical URL

- After resolving, the host compares `TmUrls.search(entity, state)` with the address bar and, when
  they differ, writes the canonical form with `replaceUrl: true` (decision 7). The address bar then
  always reproduces the page, and pins and recents (0027, 0025) store canonical strings.
- **`cols` reconciliation.** When the URL's `cols` equals the path keys of the user's
  `search.<entity>.columns` preference, the preference's column list applies (with its expression
  columns, in its order). Otherwise the URL's keys apply.
- **Picker mode** never touches the URL (§17).

#### §4.4 Changes and history

| Change | URL write | History | Page | Preference |
|---|---|---|---|---|
| text (each settled `search` emission, §6.1) | yes | replace | → 1 | — |
| column filter, advanced filter, Active only, custom filter, Clear filters | yes | replace | → 1 | — |
| order | yes | replace | → 1 | — |
| columns (§11) | yes | replace | kept | `columns` |
| page | yes | **push** | — | — |
| page size | yes | replace | the page holding the first visible row | `pageSize` |
| view, list | yes | replace | kept (list ↔ tree: → 1) | `view` |
| selection, highlight, expansion, scroll | no | — | — | — (page state; expansion: `TmTreeExpansion`) |

- **Writes go through the router** (`router.navigate([], { queryParams, replaceUrl })`) so the
  router's state stays true; a query-only navigation reuses the host component and never moves focus
  (0024 §4.4's title rule fires on path changes only).
- **Back and Forward.** The host subscribes to the route's query parameters. A change it did not
  write itself (its last written canonical string differs) re-resolves the state from the URL alone
  (§4.2 step 1) and loads; Back therefore steps through pages, not keystrokes. The installed app's
  buttons read the Navigation API (A§8, 0027).
- **Opening a row** pushes the details URL with router `state: { tmFrom: <page-state key> }`, which
  the router persists in `history.state` (survives reload; §13 verified facts), for 0031's paging.

### §5 Loading results

One read per resolved query, cancelled the moment it is superseded or the page is left; the previous
rows stay on screen until the new ones land.

#### §5.1 The request

- **Route.** `{segment}/query` with `TmApi.read(route, body, { signal })`; tree browse uses
  `get-by-parent-ids` (§16.2).
- **Select** = `tmSelectPlan(descriptor, columns ∪ tile keys ∪ tree keys)` (0029 §6.2), `Id` first,
  `dropped` keys never sent. Tree keys are `ParentId` and `SubtreeCount` (`ActiveSubtreeCount` while
  inactive rows are excluded on an activatable tree).
- **Filters** (decision 12), in this order, each built by its owner's function:

| Leaf | Built by | Present when |
|---|---|---|
| advanced filter text, verbatim | the user | `filter` non-empty |
| custom filters, declaration order | §2.4 | `x.{key}` set and resolving |
| column filters, key order | `tmFilterLeaf` (0029 §13.1) | `f.{key}` valid |
| picker filters | `picker.filter`, the field's `filter` (0029 §14.2) | picker mode |

- **Order** = the order column's `TmColumnPlan.orderBy(dir)` (reads the active slot), else the default
  order, then `, Id` unless it already ends with `Id` (decision 13).
- **Paging** `skip = (page − 1) × size`, `take = size`, `includeCount: true`.
- **`includeAncestors: true`** in a search tree (§16.4); **`includeInactive`** from `inactive`.

**Example —** Customers, `en` + `ar` tenant, `?q=al&filter=CreditLimit%20%3E%20100000&x.mine=1&f.CustomerType=in:Corporate&order=Name`:

```json
{ "select": "Id,Code,Name,Name2,CustomerType,Currency.Id,Currency.Name,Currency.Name2,CreditLimit,IsActive,ImageId,Image.Variants",
  "search": "al",
  "filters": ["CreditLimit > 100000", "CreatedById = me()", "CustomerType in ('Corporate')"],
  "orderBy": "coalesce(Name2, Name), Id", "skip": 0, "take": 50, "includeCount": true }
```

The `orderBy` reads slot 2 because the user's UI language is Arabic (0029 §6.1).

#### §5.2 Lifecycle

- **One `resource()`** keyed by the canonical query and a refresh generation; its `abortSignal` is the
  read's signal. A new key aborts the read in flight (rule 2C); leaving the page aborts it through
  the host's `DestroyRef`; the server sees `RequestAborted` (A§7.9).
- **Never blocked.** Typing, filtering, sorting, paging, toggling and navigating stay available while
  a read runs; nothing is disabled by loading.
- **On success** the host builds `TmPlanRow`s (0029 `rows(set)`), feeds the display-name cache
  (`TmDisplayNames.rememberRows`, request to 0029) so the details title renders at once, seeds the
  highlight (§6.3) and announces the count (§18).
- **Retries** are `TmApi`'s (0024 §10.5); the page stays in its loading state meanwhile.

#### §5.3 States of the results region

| State | When | Shows (copy) | Actions |
|---|---|---|---|
| first load | no rows held yet | skeleton rows at row geometry (12 grid rows; 0023 skeleton tiles); headers, checkbox column and filter buttons already drawn | — |
| reloading | rows held, a read runs | the held rows + the 150 ms progress bar | everything stays live |
| no data | 0 rows, no text, no filter, default Active only | `inbox`, "Nothing here yet", "Add one to get started." | New (when allowed) |
| no matches | 0 rows otherwise | `search-x`, "No matches", "Clear the filters or widen the search." | Clear filters (any filter active), else Clear search |
| invalid filter | `400 query-invalid` | `circle-alert`, "This filter expression is not valid", the first diagnostic's message (0029 §9 messages) with its token as a mono chip | Edit filter (opens §10 at the span) |
| forbidden | `forbidden` on the read | `lock`, "You don't have access to these records" | — |
| offline | `offline`, no rows held | `wifi-off`, "You're offline", "The results will load when you're back online." | Try again |
| failed | `server`, `unavailable`, others | `circle-x`, "The server could not complete this search", "Try again. If it keeps failing, send this reference to support." + `tm-reference` (trace id) | Try again |
| outdated | `client-outdated` | 0024 §5.6's inline "Tellma was updated" state | Reload |

- **Offline with rows held** keeps them; 0028's "Connection lost" banner says why nothing updates.
- **Diagnostics map to their leaf** through the request's leaf order (§5.1): a diagnostic on the
  advanced filter shows its message and "Edit filter"; one on a custom leaf shows the generic message
  and logs `tm.search.custom-filter-invalid` (a distribution bug).
- **`limit` (413)** on paging beyond `maxSkipWindow` cannot happen (§14 disables Next); on a bad URL
  it drops `page` and reloads page 1.
- Every state is a `tm-empty-state` (0023 §3.5) with `live="polite"`; copy is entity-neutral so no
  label is lower-cased mid-sentence (review flag 15).

#### §5.4 Language and permission changes

- **Language switch.** Labels, display names, enum labels and formats re-render from the held rows
  with no request (0029 §4.2, §5.3). When the order column is of kind `text` or `navigation`, its
  order terms change with the slot, so the host re-queries (0029 §6.2 asked).
- **Permissions tag moved.** The plan re-resolves (`TmPermissions.reachable`), newly unreachable
  columns drop (`source: 'preference'` or `'url'`), toolbar gates re-render, and the host re-queries.
  0025 already forgets this tenant's page-state entries.
- **Settings tag moved** (a language added): descriptors rebuild (0029 §4.1), the plan follows, and
  the host re-queries.

### §6 The search field and the keyboard model

The search field filters as the user types, steers the highlight with the arrow keys, and opens the
highlighted row on Enter, all while focus stays in the field. Any printable key typed elsewhere on
the page lands in the field.

#### §6.1 The field

- **Component:** 0023's `tm-search-field` with `[(value)]` (every keystroke) and `(search)` (the
  query). Its timing is the brief's: 50 ms sliding debounce; while `KeyboardEvent.repeat` is true it
  waits for that key's `keyup`; Enter and the clear button emit at once; IME composition waits for
  `compositionend`; equal values never re-emit (0023 §3.6, A§7.9).
- **Attributes:** `aria-label` "Search" (`tm.search.field`), `aria-describedby` the page title and a
  hidden hint "Arrow keys move through the results. Enter opens one." (`tm.search.fieldHint`),
  `maxlength` = `limits.maxSearchLength`, placeholder "Search".
- **Clear** (the reserved slot, 0023): clears, emits, keeps focus. **Escape** clears when the field
  has text; otherwise it propagates.
- **Instant feedback.** The characters show in the keystroke's frame (native input); the request
  starts within 50 ms of the last key; the progress bar appears only after 150 ms; rows swap in place.

#### §6.2 Type-to-search

A page-scoped `keydown` listener on `document`, in the bubble phase (so focused components and
0027's `TmShortcuts` see the key first), captures a key when all hold:

1. **Untouched:** not `defaultPrevented`, not `isComposing`, `key` not `'Process'`, not `repeat`.
2. **One printable character:** `key` is a single grapheme, not a control character, and not a space
   (Space activates buttons and toggles checkboxes; a search never starts with one).
3. **No command modifier:** no Ctrl, Meta or Alt; Shift is allowed; AltGr
   (`getModifierState('AltGraph')`) counts as typing.
4. **Not in an editable control:** the target is not an `input`, `textarea`, `select` or
   `[contenteditable]`, and no grid editor is open. A focused readonly grid, tile, button or the page
   body qualifies.
5. **The page is on top:** no modal, popover, menu or launcher is open
   (`TmPageContexts.overlays()` is empty and no CDK overlay pane is attached).

Then, in the same task (decision 4):

1. `preventDefault()`;
2. focus the field with the caret at the end (`TmSearchField.focus()`);
3. `document.execCommand('insertText', false, key)`, which fires `input`, so the search runs as if typed
   and Ctrl+Z undoes it; when the command reports failure, `setRangeText` at the end plus a
   synthetic `input` event.

- **Dead keys** (`key === 'Dead'`) only focus the field (no `preventDefault`); the accent of that one
  keystroke is lost.
- **Telemetry** `tm.search.type-to-search` (sampled).

#### §6.3 Highlight and Enter

- **The driver.** The field carries `[tmGridDriver]="target"` (BE C.2). `target` is the host's own
  `TmGridDriverTarget`: it forwards `moveActiveRow` and `activeRowId` to the grid or, in tiles view, to
  `tm-tiles` (request to 0023), and wraps `activateRow` with the staleness rule below.
- **Seeding** (BE R-4). When a result lands and focus is in the field, the highlight moves to the first
  row; in a search tree, to the first match in visible order. Otherwise the grid keeps its active row
  when that row is still present.
- **Stale results.** Results are stale while a read runs or while the field's trimmed text differs
  from the text of the shown result.
- **Enter on fresh results** opens the highlighted row (`Mod+Enter`: a new tab).
- **Enter on stale results** flushes the search and arms a pending open: when the result for the
  current text lands, its first row opens. Any other key in the field, a pointer press, focus leaving
  the field, or a navigation disarms it; an empty result disarms it and announces "No matches"
  (decision 5).

#### §6.4 The keyboard model

| Focus | Key | Effect |
|---|---|---|
| page, not in an editable control | printable character | §6.2: focus the field and type it |
| search field | ArrowDown / ArrowUp | move the highlight one row (tiles: one lattice row); with none, ArrowDown → first row |
| search field | PageDown / PageUp | move by the visible row count |
| search field | Enter / Mod+Enter | open the highlighted row / in a new tab (§6.3) |
| search field | Escape | clear the text |
| search field | Left, Right, Home, End, Backspace | the input's own |
| grid | arrows, Home/End, PageUp/Down | move the active cell (0004 §8.2) |
| grid | Enter / Mod+Enter | open the active row / in a new tab (BE C.1) |
| grid | F2 | follow the active cell's link (BE C.1) |
| grid | Space; Shift+click; Ctrl+Shift+Space | toggle the row's checkbox; range-check; toggle the page's checkboxes (BE C.5) |
| grid | ArrowUp on the first row | into the header row; there Enter sorts, Alt+ArrowDown opens the column filter (BE C.4) |
| grid, tree | Alt+ArrowRight / Alt+ArrowLeft | expand / collapse (0004 §13.3) |
| tiles | arrows (2D), Enter, Space, Ctrl+Shift+Space | 0023 §3.8; tree of tiles: Right / Left expand and collapse |
| popups | Escape | close, focus returns to the trigger (the shared Escape stack) |

- **Tab order** follows the visual order: field, Filters, leading group, trailing group, results (one
  stop; header cells reachable by ArrowUp).
- **Context menu** on a grid row adds "Open in new tab" and "Copy link" (`extraMenuItems`) to 0004's
  Copy items.

### §7 Grid view: rows, links, ordering

The grid is the amended 0004 grid in readonly, row-activation mode, with one column per column plan.

#### §7.1 The binding

```html
<!-- inside TmSearchHost; distributions never write this -->
<tm-grid [gridId]="'search.' + entity" [contentKey]="canonical()" [data]="rows()" [rowId]="byId"
         selectable [(selectedIds)]="selection" rowActivation="row" (rowActivate)="open($event)"
         [rowHeaders]="false" [(activeRowId)]="highlight" [(orderBy)]="sort" [extraMenuItems]="rowMenu()">
  @for (col of plan().columns; track col.key) {
    <tm-grid-column [key]="col.key" [header]="col.label()" [sortable]="col.orderBy('asc') !== null"
                    … the other inputs from tmGridColumnFor(col) … >
      <ng-template tmGridHeaderEnd> … filter button, §9.1 … </ng-template>
      <ng-template tmGridDisplay let-row="row"> … link, display hatch, or nothing … </ng-template>
    </tm-grid-column>
  }
  <ng-template tmGridLoading> … skeleton rows … </ng-template>
  <ng-template tmGridEmpty> … §5.3 state … </ng-template>
</tm-grid>
```

- **Identity.** `gridId` = `search.<entity>` (widths survive navigation, 0004 §12); `contentKey` = the
  canonical query, so returning to the same result restores scroll and the active cell from the
  grid's state store, and a new query starts at the top.
- **Columns** come from `tmGridColumnFor(column)` (0029 §12.1): type, alignment (numbers and dates
  physically right in both directions), width or flex, format. A declaration `width` wins.
- **Static cells** everywhere except the columns that need a template: the link columns (§7.2) and
  `display` hatches (§2.2). Templates are the costlier path (0004 §7), so a plain column never uses one.

#### §7.2 Opening rows and links (Search Q1)

- **Row activation** (`rowActivation: 'row'`, BE C.1): a click anywhere but the checkbox cell, a tap,
  or Enter opens the row's details; Mod+click, middle click and Mod+Enter open it in a new tab
  (`window.open(url, '_blank', 'noopener')`). A drag still selects a range for copying.
- **The display-name cell is a link:** the first shown column whose key is the display-name source
  or its prefix (0029 §5.1) renders `<a [routerLink]>` to the row's details. Its native affordances
  (open in new tab, copy link address, status-bar URL) work; a plain click follows the link, which is
  the same destination as row activation.
- **Navigation cells are links** to the target's details when `TmPermissions.allows(target,
  'details')` (0029 §12.2): the Accounts grid's Center cell opens the center.
- **Links are `tabindex="-1"`** (the grid's single tab stop, 0004); F2 follows the active cell's link.
- **Preloading.** Hovering or focusing a row (or a link) calls `TmUrls.preload` for the details route
  once per page, so the details chrome renders in the click's frame (rule 2B).
- **Opening** remembers the page state (§15.1), then navigates with `state: { tmFrom }` (§4.4).
  On return the highlight is the opened row, so BE C.1's active-row tint and accent bar are the
  design's "Came back from this record" marker, with no extra class.
- **Picker mode** renders no links and activation picks the row (§17).

#### §7.3 Ordering

- **One column** (BE C.3): a click on a sortable header cycles ascending → descending → none; another
  header replaces the order. The URL's `order` and the grid's `orderBy` model are one value.
- **Sortable** = the plan says the key is orderable (`orderBy(dir) !== null`: not `image`, not
  JSON-typed expressions).
- **None** means the default order (§2.1), with no indicator (decision 13).
- **A column not shown may order the rows** when the URL says so (`order=CreatedAt:desc`); no header
  shows it, and the advanced filter popup lists it as a removable "Ordered by Created at, descending"
  chip (§10.1).
- **Tree view** sorts siblings (§16.5).

### §8 Tiles view

Tiles are 0023's `tm-tiles`, fed the same rows, selection and highlight as the grid, with a layout
mapped from the declaration's `tile` member.

- **Layout mapping** follows §2.3's table; 0023 §3.8's example is the Customers mapping verbatim
  (title = display name with `href` to details, `bottomStart` = Code, `bottomEnd` = the Active
  badge, `image` = the avatar through `TmUrls.blob`).
- **Geometry** is 0023's: 220 px minimum tile inline size, 10 px gaps, a divided one-column list
  below `sm` (`search-page-tiles-narrow.png`); column count changes only on resize.
- **Activation** (`activate`): a click or tap anywhere on a tile but its checkbox opens the row; the
  title is a real link (new tab, copy link); Mod+click and middle click open a new tab.
- **Selection.** `selectable`; the checkbox slot is reserved at inline start; `selectedIds` is the
  page's one selection (§12).
- **Highlight.** `[(activeId)]` is the page's highlight; the field's driver moves it (§6.3).
- **States** (§5.3) render through `[tmTilesEmpty]` and `[tmTilesLoading]`.
- **Scroll on return** restores the remembered offset (request to 0023: `scrollOffset()` and
  `scrollTo(offset)` on `tm-tiles`), else `scrollToItem(highlight)`.
- **Tree of tiles** (tree entities in tiles view): `parentId`, `hasChildren`, `expandedIds` and the
  batched `loadChildren` exactly as the tree grid (§16); context rows take
  `tm-tiles__item--context`.
- **Ordering and column filters** have no headers in tiles view; both are reachable from the Filters
  popup (§10.1), so the narrow default view loses no capability.

### §9 Column filters

Every filterable column header carries a filter button that opens 0029's `tm-column-filter` for that
column; an applied filter is one `f.{key}` URL entry and one leaf.

#### §9.1 The header affordance

```html
<ng-template tmGridHeaderEnd>
  <button tmGridHeaderAction [active]="filtered(col.key)" [tmPopoverTriggerFor]="filterPanel"
          [attr.aria-label]="filterLabel(col)"><tm-icon name="funnel" /></button>
</ng-template>
<!-- filterPanel: tm-popover size="sm" holding
     <tm-column-filter [column]="col" [value]="value(col.key)" (applied)="apply(col.key, $event)" /> -->
```

- **Which columns.** Those whose plan has a filter kind (`TmColumnPlan.filter !== null`: text,
  number, date, instant, enum, bool, navigation; 0029 §13.2). Every such column reserves the action
  slot (BE C.4), so applying a filter moves nothing.
- **Active state.** `active` gives the accent glyph and a hidden "Active" description; the accessible
  name is "Filter Name" or "Filter Name, active" (`tm.search.filterColumn`, `…Active`).
- **Keyboard.** Alt+ArrowDown on the header cell opens it (BE C.4); focus starts in the operator
  select; Escape closes and returns to the button.
- **Below `sm`** the same content opens in a `TmModal` `placement: 'end'` drawer, controls at 44 px
  (0029 §13.3).

#### §9.2 Values

- **Apply** sets `f.{key}` to the control's value; **Clear** removes it (0029 §13.1 `applied`). Either
  replaces the URL, resets to page 1 and reloads (§4.4).
- **Operators and leaves** are 0029 §13.2's: text `contains` (default), `starts-with`, `ends-with`,
  `eq`, `ne`; numbers `between`, `lt`, `le`, `eq`, `ge`, `gt`; dates and instants `between`, `before`,
  `after`; enums `in` (a checkbox list, a multi-select beyond 8 values); bools `is`; navigations `in`
  (the entity multi-picker, at most 50).
- **A filter on a column that is not shown** (from a link, or after its column was removed) stays
  applied. It is listed, removable and editable in the Filters popup (§10.1).

### §10 The advanced filter popup

The Filters button opens one popup holding the Queryex filter, the Active-only switch, the
distribution's custom filters, and the list of every applied column filter. Its changes are staged
and apply together on Apply (decision 21).

#### §10.1 Layout

- **Surface.** `tm-popover` `size: 'md'` (440 px, BE D.3) anchored to the Filters button,
  end-aligned; below `sm` an end drawer. Heading "Filters"; the button's `aria-expanded` follows it.
- **Sections, in order:**
  1. **Filter expression** — `tm-expression-editor clause="filter" [root]="entity" [rows]="3"`
     (0029 §10), label "Filter expression", placeholder "CreditLimit > 100000". Highlighting at
     every key; server diagnostics (`queryex/discover`, 250 ms) underlined; F8 walks them;
     Ctrl/Cmd+Enter applies.
  2. **Active only** — `tm-switch`, on by default, activatable entities only; off = `inactive=1`.
  3. **Custom filters** — one control per declaration (§2.4): a switch, a radio group, or the hatch's
     component, in declaration order, labelled by their `labelKey`s.
  4. **Applied** — one removable `tm-chip` per column filter ("Name contains jed", "Type: Service,
     Sale", from `tmDescribeFilter`, request to 0029), plus a chip for an order on a hidden column
     (§7.3). Activating a chip's label opens that column's `tm-column-filter` in place, with a Back
     button. "Add column filter" (a `tm-menu` of the filterable shown columns) does the same for a new
     one; this is how tiles view filters by column.
- **Footer.** "Clear all" (ghost: stages empty text, no column or custom filters, Active only on) and
  "Apply" (primary).

#### §10.2 Behaviour

- **Apply** turns the staged state into one query change (one URL write, one request, page 1),
  closes the popup and returns focus to the Filters button in the click's frame.
- **Dismiss** (Escape, outside click, the drawer's close button) discards staged edits.
- **Apply is disabled** only while the expression's last completed check, for its current text,
  reported problems; while checking, offline or after a failed check it stays enabled (the server is
  the authority).
- **The invalid-filter state** (§5.3) offers "Edit filter", which opens the popup with the editor
  focused and the diagnostic's span selected (request to 0029: `TmExpressionEditor.select(start,
  length)`).
- **The Filters button** shows the active count in its reserved `tm-counter` slot: one for the
  expression, one per column filter, one per custom filter, one when inactive rows are included. Its
  name is "Filters" or "Filters, 3 active". While the advanced filter is invalid the button takes the
  error tone and its name adds ", the filter expression is not valid".

### §11 The column editor

The Columns button opens a two-pane editor: the path tree of the root entity on one side, the ordered
shown columns on the other. Changes apply at once and become the user's preference.

#### §11.1 Layout (`choose-columns.png`)

- **Surface.** `tm-popover` `size: 'lg'` (640 px) anchored to the Columns button; below `sm` a
  full-width end drawer with the two panes as tabs (`tm-segmented` "Available" / "Shown").
- **Header** "Choose columns" and "{n} shown". **Footer** "Reset to default" (link button) and Done
  (primary).
- **Available** — `tm-path-picker mode="columns" selection="multiple" [(selected)]` over the root
  (0029 §11): its built-in "Search columns" field, type pills on navigations ("Parent center ·
  Center"), slash labels, unreachable paths absent, expanded from local descriptors with no request.
  Below it, "Add expression" (§11.3).
- **Shown** — `tm-reorder-list [(items)]` (0023 §3.8): grip handle, a checked checkbox (unchecking
  removes), the slash label. It accepts `tm.path` drops from the tree (`accepts: ['tm.path']`,
  inserting at the drop index); keyboard reorder through the handle (grab, move, drop).

#### §11.2 Semantics

- **Checking** a node adds its key at the end of Shown: a scalar or group anchor adds that path; a
  navigation adds its display-name column (`Parent`); a nested field adds the dotted path
  (`Parent.Code`, labelled "Parent center / Code").
- **Activation** (Enter, double-click) on a node toggles it: the non-drag path (WCAG 2.5.7).
- **Limits.** At least one column (the last checkbox is disabled); at most 50 ("You can show up to 50
  columns", announced politely).
- **Live apply** (decision 19). Each change updates `cols`, replaces the URL and writes the
  preference (write-behind, 0025 §9). An addition re-plans and re-queries (the select grows); a
  removal or a move re-renders from the held rows with no request. Done, Escape and an outside click
  only close.

#### §11.3 Expression columns

- **"Add expression"** opens an inline form: `tm-expression-editor clause="select" [root]` (two
  rows, checked by discover), a required "Column label" input (at most 60 characters), and Add.
- **Stored** as `{ expression, label }` in the preference; shown with an `ƒ` glyph and an edit
  button; ordered and removed like any column.
- **Never in URLs** (decision 20). With an expression column present, `cols` carries the path keys;
  §4.3's reconciliation restores the full list for the user, and a colleague's link shows the path
  columns only.

#### §11.4 Defaults and the preference

- **`search.<entity>.columns`** = `TmColumnPreference[]`, where `type TmColumnPreference = string |
  { readonly expression: string; readonly label: string }` (request to 0025: the registry row's value
  type).
- **Written** when the shown list differs from the code default; **reset** (`TmPreferences.reset`,
  0025 §9) when it equals it, so later code-default changes reach the user.
- **"Reset to default"** applies the code default, resets the preference and removes `cols` from the
  URL.
- **Stale keys** in a preference (an entity changed shape, a permission was revoked) are dropped by
  the plan (0029 §6.4, `source: 'preference'`); the preference is rewritten on the next change only.

### §12 Selection and bulk actions

Checked rows form one selection that survives searching and paging; the selection bar acts on it.

#### §12.1 Selection

- **One `Set<number>`** shared by grid, tiles and tree (`selectedIds` models); select-all toggles the
  current rows and keeps the others (BE C.5). Search, filters, order, page and view changes never
  clear it (the brief).
- **Cap** `limits.maxIds` (10,000): actions disable beyond it with "Select at most 10,000 items".
- **Cleared** by the bar's X, after a successful write action (decision 22), and when the tenant
  changes. Remembered in page state (§15).

#### §12.2 The selection bar

- **Replaces the leading group** while the selection is non-empty (`search-page-typed.png`):
  "{n} items selected" (`tm.search.selected`, ICU plural; below `sm` "{n} selected"), the Actions menu
  button, and an X button ("Clear selection").
- **Actions menu** (`button[tmMenuTriggerFor]`, BE C.10), groups in this order, each item present when
  the operation exists and `TmPermissions.allows` grants it (0029 §7):

| Group | Items | Request |
|---|---|---|
| export | Export (`export`), Export for import (`import`) | by ids (§13.2) |
| state | Activate, Deactivate (activatable) | `activate` / `deactivate` `{ ids, returnEntities: false }` |
| entity actions | each zero-argument, non-`singleTarget` entity action (`TmEntityActionDescriptor`); one with arguments opens its declared `dialog` (0031's hatch) | `{segment}/{name}` `{ ids, arguments? }` |
| delete | Delete; on tree entities also Delete with descendants | `delete` / `delete-with-descendants` `{ ids }` |

#### §12.3 Running an action

1. The item invokes its page action (`TmPageActions.invoke`, 0026 §9.5): destructive ones confirm
   first ("Delete 3 items? This cannot be undone.", danger; "Delete 3 items and everything under
   them?" for descendants).
2. The menu item shows `running` busy at once; the page stays usable; a second invoke is refused
   (`busy`).
3. **Success:** toast "{n} items deactivated." (0028 policy), clear the selection,
   `TmPageState.markStale({ tenantId, entity })` (0025 §10), re-query the current page.
4. **Failure:** 404 (some ids gone or hidden) and 422 (`Fk.InUse` at `ids[i]`) are all-or-nothing on
   the server (0015 §10.1); the host shows `TmErrorDialog` with the affected rows' display names
   (`TmDisplayNames.label`) as details; other kinds go to `TmErrorPresenter` (`kind: 'action'`). The
   selection stays.

### §13 Create, export, import, refresh

#### §13.1 Create

- **"New customer"** (primary; `<Schema>_<Entity>_New`, fallback "New"; request to 0029) is a link
  button to `TmUrls.create(entity)` (Mod+click: new tab), shown when the entity has `save` and
  `details` and `allows(entity, 'save')`.

#### §13.2 Export (Trees Q1)

- **The Export menu** (row 2): "Export grid" (`export`), "Export for import" (`export-for-import`),
  "Import template" (`export-for-import` with `ids: []`, 0019 §2.1); each item exists with its
  operation. The Actions menu's two export items use the selection.
- **The display request** carries the shown columns as `ExportColumn`s (note §5 E5): each column key
  (0029 §6.1) as `expression` and its slash label (as displayed, in the UI language) as `header`; an
  expression column its text and label; `image` columns are left out; a `file` column sends
  `File.FileName`. The source is the grid's query: the same `filters`, `search`, `orderBy` and
  `includeInactive`, no paging; or `ids` for the selection.

```json
POST /17/api/web/centers/export
{ "columns": [ { "expression": "Code", "header": "الرمز" }, { "expression": "Name", "header": "الاسم" },
               { "expression": "Parent", "header": "المركز الأب" }, { "expression": "Parent.Code", "header": "المركز الأب / الرمز" } ],
  "filters": ["CenterType in ('Service', 'Sale')"], "search": "jed", "orderBy": "Code, Id", "includeInactive": false }
```

The server exports four columns: `Name` in the request language's slot (falling back to slot 1),
`Parent` as the parent's display name, no `Id` (Trees Q1).

- **Synchronous or background** (decision 18):

| Source | Path |
|---|---|
| selection (≤ `maxIds`) | synchronous `export` |
| query, count exact (not capped) | synchronous `export` |
| query, count capped (`10,000+`) | background `export/start` |
| a synchronous answer `413 Excel.Export.RowLimitExceeded` | retried once as `export/start` |

- **Synchronous** runs through `TmApi.download(route, body, { signal, long: true, onProgress })` and
  saves through an object URL and `<a download>` with the server's file name. A sticky toast
  "Exporting…" with Cancel (aborts the signal) and a progress line shows meanwhile (0028 policy);
  leaving the page cancels it (0024 §10.5).
- **Background** answers `JobAccepted`; the toast "Export started. You'll get a notification when it's
  ready." with "Track" (the Jobs page, 0028); the file arrives with `core.export.ready` (0019 §12).
- **Export for import** uses `ExportForImportRequest` with the same source (by query: `filters`,
  `search`, `orderBy`, `includeInactive`), every editable column, every child collection; the
  template sends `ids: []` and runs synchronously always.

#### §13.3 Import

`TmImportDialog` (a `TmModal` `size: 'lg'`, full screen below `sm`) walks four steps; the dialog is the
only import surface (A§8).

1. **File.** `tm-dropzone` (0005 §8.1) accepting `.xlsx`, `accept` and `maxFileSize` from the
   `import-file` blob policy on `core.Import.FileId` (0029 §16), with a "Download the template" link
   (the template export). The pick uploads at once through `TmApi.upload('import-file', file,
   { signal, onProgress })` with a `tm-progress-bar`; Cancel aborts.
2. **Check.** `inspect-import { fileId }` → `ImportPlan`. The dialog shows the sheets with their row
   counts and status, the mapped columns, and each unmapped column with a `tm-select` of its
   suggestions plus "Ignore"; "Ignore every unmapped column" sets `ignoreUnmappedColumns`. Mode
   (`tm-radio-group`: Add new rows, Update existing rows, Add and update) and, for update modes, the row
   key (`RowKeyCandidates`, default `DefaultRowKey`). Warnings list below. A changed mapping re-runs
   `inspect-import` (the plan is not stored, 0019).
3. **Import.** When `RequiresBackground` is false, "Import" calls `import` (a write: never aborted;
   the dialog cannot be dismissed while it runs and shows an indeterminate bar). Otherwise the dialog
   says "This file is large, so it imports in the background." and offers "All or nothing"
   (`atomic`) when `AtomicAllowed`; "Import" calls `import/start`.
4. **Result.**
   - Synchronous success: "{inserted} added, {updated} updated" plus child counts and warnings; the
     page marks its state stale and re-queries; Close.
   - `422 ImportException`: a table of the errors (Sheet, Row, Column, Message; first 100, "and N
     more"), "Copy errors" (tab-separated, for Excel), "Back" to step 2, "Choose another file".
   - Background: the dialog closes; toast "Import started" with "Track" (the import's details page,
     `/{t}/imports/{importId}`, 0032); completion arrives as `core.import.completed` or `.failed`.

- **Step-up.** When `TmPermissions.sensitive(entity, 'Save')`, step 1 notes "You'll be asked to
  confirm it's you." (the file stays staged; a step-up redirect returns to the page, not the dialog).

#### §13.4 Refresh

- The icon button re-runs the current query with a new refresh generation: page, selection, scroll and
  highlight are kept; the progress bar shows after 150 ms.

### §14 Paging

- **Control.** 0023's `tm-pager` `mode="range"`: status "1–50 / 55" (`ar-SA` digits, isolated LTR),
  previous and next, page sizes 20, 50, 100, 200 (filtered to `≤ limits.maxTake`), default 50
  (decision 25).
- **Count.** Every query asks `includeCount`; a capped count shows "1–50 / 10,000+"
  (`totalIsLowerBound`); Next stays enabled until a short page or `page × size ≥ maxSkipWindow`.
- **Paging is a push** (§4.4); a click while the previous page loads re-writes `page` and the
  `resource()` supersedes the read.
- **Size change** keeps the first visible row: `page = floor((page − 1) × old / new) + 1`.
- **Preference** `search.<entity>.pageSize` (write-behind).
- **Browse tree** is unpaged (§16.2): the pager shows "1–N / N" with its arrows and size select
  disabled (request to 0023: `tm-pager` `disabled`), so its geometry never changes.

### §15 Page state and return

#### §15.1 What the host remembers

`TmPageState.remember(tmPageStateKey('/17/customers'), snapshot)` runs when the host is destroyed
and before it opens a row.

```ts
// @tellma/core (types only; written by 0030, read by 0031's paging)
interface TmSearchSnapshot {
  readonly v: 1;
  readonly entity: string;
  readonly query: TmSearchQuery;                      // resolved (§4)
  readonly canonical: string;                         // the result's identity
  readonly request: { readonly route: string; readonly body: TmJsonObject }; // the last read, paging fields removed
  readonly result: { readonly set: TmQueryRowSet; readonly ancestors?: TmQueryRowSet;
                     readonly total: number | null; readonly capped: boolean } | null;
  readonly ids: readonly number[];                    // the shown rows in display order
  readonly selection: readonly number[];
  readonly highlight: number | null;                  // the row last opened, else the active row
  readonly expanded?: readonly number[];              // the tree view's expanded ids
  readonly scroll?: number;                           // tiles only; the grid's store keeps its own (§7.1)
}
```

#### §15.2 Returning

1. §4.2 resolves the query. When the snapshot's `canonical` equals it, its rows render at once with no
   request (the brief: "returning should not refresh the data"); the grid restores scroll and the
   active cell from its store (same `contentKey`); tiles scroll to `scroll`.
2. When `TmPageState.isStale(key)` (a save, delete, import or action on the entity, 0025 §10), the held
   rows render at once and a read refreshes them; scroll and highlight keep their rows.
3. When the canonical query differs, only the selection and expansion restore; the result loads.
4. An evicted entry (LRU of 20) is a normal first load.

#### §15.3 What 0031 reads

- The details page reads `history.state.tmFrom`, recalls the snapshot and pages through `ids`; past
  either end it reads `request.route` with `request.body` plus `select: 'Id'`, `skip` and `take`
  (0031 owns that flow). A details page opened without `tmFrom` has no paging.

### §16 Trees

A tree entity (`descriptor.tree` set, `get-by-parent-ids` present) shows a tree by default: roots
first, children loaded lazily, expansion remembered for the session; a search shows matches inside
their ancestors.

#### §16.1 Tree or list

- **Toggle** `tm-segmented` Tree (`list-tree`) / List (`list`) in the trailing group, tree entities
  only; List writes `list=1` and the preference's `list` (§3.4).
- **List** is the flat page of §5–§14 over the same entity (paged `query`).
- **Grid or tiles** is independent: tree grid (`tm-tree-grid`) or tree of tiles (`tm-tiles` tree
  mode, the default below `md`, as the brief asks).

#### §16.2 Browse tree: roots first, one call

- **The call** (no text, no filter; `inactive` allowed):

```json
POST /17/api/web/centers/get-by-parent-ids
{ "parentIds": [12, 40, 41], "includeRoots": true, "select": "Id,Code,Name,Name2,ParentId,SubtreeCount,ActiveSubtreeCount,IsActive",
  "orderBy": "Code, Id", "includeInactive": false }
```

- **`parentIds`** = the remembered expansion (`TmTreeExpansion.expanded('/17/centers')()`, read once
  at load, 0025 §12), newest `limits.maxIds` ids; empty → roots only.
- **Pruning.** The answer holds the roots and the children of every listed parent. The host keeps a
  row only when it is a root or its parent is kept (orphans of a collapsed ancestor are dropped), so
  the grid never sees a parentless child.
- **`hasChildren`** = `SubtreeCount > 1` (`ActiveSubtreeCount > 1` while inactive rows are excluded;
  0015 §12.1: a leaf has count 1). A node whose children came back empty is marked loaded-empty.
- **Unpaged** (decision 15). The pager shows the loaded row count (§14). An answer of `413
  limit-exceeded` (more than `MaxTake` rows, note §5 E3) switches this visit to List with the inline
  note "This tree is too large to show at once, so it's shown as a list." (no preference write;
  `tm.search.tree-fallback`).

#### §16.3 Expanding, collapsing, remembering

- **Expand.** The grid (or tiles) calls the batched `loadChildren(rows)` (BE C.9): one
  `get-by-parent-ids { parentIds: those ids, includeRoots: false, … }`; the host appends the rows and
  calls `TmTreeExpansion.toggle(page, id, true)` per id. A failure collapses and announces (BE C.9).
- **Collapse** removes the node and every loaded descendant from the expansion:
  `TmTreeExpansion.replace(page, remaining)` (0025 §12), so memory never holds orphans.
- **Binding.** `[expandedIds]` = the host's set, seeded from memory at load; `(expandedIdsChange)`
  writes memory. An open tree never re-expands when another tab changes the memory (0025 §12).
- **Another tab, same session:** the next visit sends the remembered ids and renders the same tree in
  one call (the brief).

#### §16.4 Search tree: matches inside their ancestors

- **The call** is §5.1's `query` with `includeAncestors: true`; matches are paged as in a list;
  ancestors of the page's matches ride the same answer (0015 §5.2 step 5).
- **Rendering.** Rows = matches ∪ ancestors, every present parent expanded (`expandedIds` = all
  of them), no lazy loading (`hasChildren` = has present children), and the expansion memory is not
  written (decision 16). Clearing the text and filters returns to the browse tree with its memory.
- **Distinct context rows** (the brief, `ERP 3d`): `rowClass` → `tm-grid-row--muted` (BE C.6;
  tiles: `tm-tiles__item--context`); the display-name cell adds a visually hidden "(ancestor of a
  match)" (`tm.search.tree.context`), so the difference is not colour alone (WCAG 1.4.1); a one-line
  legend under the region reads "Grey rows are ancestors of matches." (`tm.search.tree.legend`).
- **Highlight** seeds on the first match (§6.3). **Selection** may include context rows (they are
  real rows).
- A match that is also an ancestor of another match on the same page renders as a match.

#### §16.5 Ordering a tree

- An order sorts siblings: the browse call sends `orderBy`, the search call orders matches, and the
  tree grid keeps data order among siblings (request to BE: state it). The view never switches to a
  list because of an order (decision 14).

## 4. Open questions owned

- **Search Q1 — row click or a link column.** Both, without the machinery cost: a click anywhere on a
  row except the checkbox cell opens it, Enter opens the highlighted row, and the display-name cell
  and every navigation cell render real `<a href>` links (§7.2), all on BE C.1's opt-in row
  activation. The common case (open the row) needs no precision; links keep native new-tab and copy
  behaviour and reach other entities; leaving the checkbox cell out prevents accidental opens.
  *Alternatives:* (A) row click only (no native link affordances, no route to the row's center);
  (B) a link column only (a small target for the most common action, the brief's objection).
- **Trees Q1 — the Excel `select`.** Yes, a different request: the page sends the displayed column
  model (`ExportColumn[]`: the column key as `expression`, the label as `header`), not the grid's
  select (§13.2, edits E5–E7). The server expands each navigation and multilingual group itself and
  writes one display-name or one active-slot column in the request language; `Id` appears only when
  shown. *Alternatives:* the grid's select verbatim (Id plus `Center.Id`, `Center.Name`,
  `Center.Name2` as four columns); a client-built select of chosen terms with headers (a navigation
  still needs several terms, and the server could not render the display name); server-side columns
  from the declaration (the server does not know the user's columns).

## 11. Review flags

1. **The browse tree is unpaged, capped at `MaxTake` with a fall-back to the list** (§16.2).
   Alternative: page the roots. Flips if a real tree has thousands of roots or children per node.
2. **An order sorts tree siblings and never switches to a list** (decision 14). Alternative: the
   design's "any order shows a list". Flips if users expect a sorted flat view when they sort.
3. **The view preference is per breakpoint class** (decision 10). Alternative: one sticky value
   across devices (the design note). Flips if users want one choice everywhere.
4. **Page size default 50; options 20, 50, 100, 200** (decision 25). Alternative: the design's 20.
   Flips on measured response times or user feedback.
5. **The column editor applies live** (decision 19). Alternative: a draft applied on Done. Flips if
   live re-queries prove distracting.
6. **Export path chosen by the capped count** (decision 18): 10,000+ rows always go to the
   background even when under 100,000. Alternative: a client-visible synchronous cap in the metadata.
   Flips if users find background exports of mid-size sets slow.
7. **Expression columns never travel in URLs** (decision 20); a shared link drops them. Alternative:
   encode them with a safety rule. Flips if users share expression-column views often.
8. **The URL query is all-or-nothing against page state** (decision 6). Alternative: per-field
   merge. Flips if pins with a filter should keep the user's last text.
9. **Selection clears after a successful write** (decision 22). Alternative: keep it. Flips if users
   chain actions on one selection.
10. **Tree delete is two actions** (decision 23). Alternative: one cascading Delete (the design's
    copy). Flips if users always mean the subtree.
11. **The search tree is static** (decision 16). Alternative: lazy children under matches. Flips if
    users drill from matches.
12. **Pending Enter opens the first result on arrival** (decision 5). Alternative: ignore Enter until
    results settle. Flips on reports of unexpected opens.
13. **The view toggle stays in selection mode** (decision 24), against the design. Flips with a design
    review that accepts the shift.
14. **Space never starts type-to-search; dead keys lose their accent** (§6.2). Flips if users of
    accented layouts report it.
15. **Entity-neutral state copy** ("No matches", "Nothing here yet") instead of the design's "No
    customers match this search" (§5.3): the plural label cannot be lower-cased safely. Alternative:
    per-entity keys (`<Schema>_<Entity>_NoMatches`). Flips if Ahmad prefers the named copy.
16. **The invalid filter shows on the Filters button and in the region, not echoed into the search
    field** (§5.3, §10.2), against the design. Flips with a design review.
17. **Column widths are not persisted across sessions** (§1 deferred). Alternative: a write-behind
    `search.<entity>.widths` key over 0004's `serializeWidths`. Flips on user demand.

## 12. Challenges to the architecture

1. **A§8 and A§5.13: `view` has four values on one axis** (`grid | tiles | tree | list`). A tree
   entity has two independent choices (grid or tiles; tree or list), and the brief asks for a tree of
   tiles on narrow screens. Followed as: `view=grid|tiles` plus `list=1` (R4), §4.1.
2. **A§5.7 / 0025 Appendix A: `search.<entity>.view` is `'grid' | 'tiles' | 'tree' | 'list'`** and
   **`search.<entity>.columns` is `string[]`.** The first cannot hold both axes or the per-class
   choice; the second cannot hold the user's expression columns. Followed as: R11's shapes.
3. **A§6.3's 0015 §5.4 row (`IncludeRoots` + `OrderBy`)** omits that `get-by-parent-ids` is unbounded
   and still takes one `Filter`. Followed as: E3 adds `Filters` and a `MaxTake` cap.
4. **A§8 route table: `/{t}/jobs?mine=1`** is outside the query grammar; a custom filter is
   `x.mine=1` (§2.4). Followed by requesting 0028 to use `x.mine` (R15).
5. **A§10.1 Trees Q1 and A§6.3's 0019 row** name `ExportRequest.Columns` but not the source's
   `Filter`, which must become `Filters` for an export to run the grid's query (E4).
6. **A§3.6: "`search: () => import(…)` replaces the body".** "Body" is defined here as the results
   region (row 3); rows 1–2 stay the platform's (decision 26), and the route host loads the host,
   not the hatch (R6).
7. **A§3.3's tile example uses `image: 'ImageId'`** (the FK scalar), while 0029's column keys name the
   navigation (`Image`). Followed as: both resolve for `image` (§2.3); the note's examples use `Image`.
8. **A§8 precedence "URL, then page state, then preferences"** is read as the URL query as a whole,
   not field by field (decision 6, §4.2).
9. **A§2.2 import rule vs 0031's paging.** `/details` cannot import `/search`, so the page-state
   entry's type lives in the primary as a type-only export (R10).
