## Item 6 — §9.3: can the BFF skip the tenantless skeleton for a single-tenant user?

**Current design**

- §9.3: at `/`, a matching `boot.lastTenantId` replaces to `/{lastTenantId}`. Otherwise the SPA
  reads `/bff/user` "under the tenantless shell's skeleton list". Exactly one membership that is
  `Live`, `Active` and `isActive` → replace to `/{id}`.
- §4.2 step 3c: on an expired session `tm-boot.js` deletes the user's data, then "nulls the
  record's `sub` and `lastTenantId`". Step 3d goes to `/bff/login?returnUrl=/`.
- 0011 §5.5: "After the callback the BFF redirects to `returnUrl ?? "/"`, and the SPA's launch
  redirect decides where `/` lands". 0011 Decision 29: "The BFF never picks a tenant".
- 0024 Review flag 7(b) names "the skip in the BFF" as the alternative.

**Your scenario, traced**

1. The installed app opens `start_url` `/` (§5.1). The session cookie is gone.
2. Step 3c wipes the data and `lastTenantId`; 3d sends the browser to sign-in with `returnUrl=/`.
3. After sign-in the BFF redirects to `/`. The boot is cold, with no `lastTenantId`.
4. Angular paints the tenantless shell's skeleton and waits for `/bff/user`.
5. One membership → replace to `/17`. The tenant shell replaces the tenantless one, and the cold
   tenant entry (§4.4) waits again.

So you are right: two shells, two waits and one visible swap. A first sign-in on any device takes
the same path.

**Why the rule moved to the SPA** (design note 0024 §4 "Tenant picker Q1"; edit X-0011-10)

- The reason given was one owner of the landing decision. The alternative it rejected was the
  picker at `/` with a `?pick=1` bypass, which gave "two meanings for one URL; the BFF and the SPA
  would both own the landing decision".
- Decision 13 then put the picker at `/tenants`, which never redirects. So the URL problem is
  gone. What remains is only "one owner".

**Analysis — you are right**

- The BFF already has the data. `/bff/user` answers from the membership directory in one catalog
  query (0011 §3.8). The callback already writes the session row to the catalog, so one more
  indexed read on sign-in is cheap.
- It is a small hook. The handler's `OnTicketReceived` event can set
  `TicketReceivedContext.ReturnUri`, "the URL to redirect to after signin"
  ([Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/microsoft.aspnetcore.authentication.ticketreceivedcontext.returnuri)).
  The principal's `sub` is available there.
- Gains: no tenantless skeleton, no shell swap (rule 2D), one round trip less on the cold path,
  and the tenant shell is the first thing painted.
- The SPA rule must stay. Angular still reaches `/` with a live session and no `lastTenantId`:
  the changed-user path (§8.7 calls `location.replace('/')`), an in-app link to `/`, or a sign-in
  finished in another tab. So one rule runs in two places. One shared vector file, read by the C#
  and the TS tests (like 0010's format golden), keeps them from drifting.
- Same staleness risk as today: the SPA reads the same hint (0011 §3.8), and a stale hit ends at
  the picker with a notice (§11).
- Apply it only when the target is exactly `/`. Deep links, `/tenants` and step-up returns are
  untouched, so "the picker never redirects" still holds.

**Recommendation — agree.** After sign-in, when the target is `/`, the BFF applies the
single-membership rule and redirects straight to `/{id}`. The SPA keeps the same rule for an
in-app `/`, and both test against one shared vector file.

**Edit plan**

- 0011 §5.5 `/bff/login`: a target of `/` with exactly one `Live`, `Active`, `isActive`
  membership (sandboxes never count) redirects to `/{id}`, set through `ReturnUri` in
  `OnTicketReceived`; otherwise `returnUrl ?? "/"`.
- 0011 §3.8 Readers: add "the post-sign-in redirect (§5.5)".
- 0011 §3.2 last paragraph: name both readers of the membership list.
- 0011 Decision 29: "The BFF picks a tenant only for a sign-in that returns to `/`, by the SPA's
  rule (spec 0024 §9.3)".
- 0011 §10 Sessions tests: one live membership, two, sandbox-only, and a `/tenants` target.
- 0024 §9.3: one sentence: after sign-in the BFF applies the same rule (spec 0011 §5.5).
- 0024 §4.3 "At most two waits when cold": a sign-in at `/` has one.
- 0024 Review flag 7(b): delete; add a Decisions row.
- 0024 §13 e2e: "expired session at `/`, one live tenant → sign-in → `/1`; the tenantless skeleton
  never renders".

**Question back**

- Multi-tenant users still land on the picker after an expiry, because 3c erases
  `lastTenantId`. Should `tm-boot.js` at `/` send `returnUrl=/{lastTenantId}` before erasing it?
  Upside: everyone returns to their last tenant. Downside: on a shared device, a different user
  lands on a "tenant not found" notice about someone else's tenant. My lean: not now.

## Item 7 — §9.4: why do only `home()` and `page()` take a tenant?

**Current design**

- §9.4: `home(tenantId?)` and `page(path, tenantId?)` take an optional tenant. `search`,
  `details`, `create`, `target` and `blob` always use `tenantId()`, "the tenant the routed page
  shows".
- `tenantId()` is null on tenantless pages (0026 §3.1), but no rule says what a tenant builder
  returns then. The nearest rule: "An unknown entity throws in development and yields the tenant
  home in production."
- §10.1 has the same gap: `TmReadOptions.tenantId` defaults to `TmUrls.tenantId()`, with no rule
  for null.

**Analysis — the asymmetry has no recorded reason**

- No design note explains it. No spec passes a tenant to `home` or `page`. The cross-tenant links
  that exist are hand-built strings: the picker's Connect is `href="/{id}"` (0027 §6.2), and the
  sandbox marker's "Open {live name}" goes to `/{liveTenantId}` (0027 §7.4).
- Nothing technical stops the other builders from taking a tenant. Segments come from the Core
  chunk, and "every section is tenant-independent" (§3.1).
- Cross-tenant links will grow: sandbox ↔ live ("open this record in live"), and rule 3's
  assistant giving a link into another tenant.
- Outside a tenant, today's behaviour is undefined. `search('core.Notification')` on `/tenants`
  could build `/null/notifications`.
- A trailing `tenantId?` on every method is a poor fix. `details` and `create` already end in
  option objects, so the tenant would sit in a different place in each signature. Coding agents
  (rule 1) do better with one shape.

**Recommendation — agree with a change.** Every tenant builder resolves the tenant the same way,
and one scoped builder covers other tenants: `urls.forTenant(17).details('gl.Center', 5)`. Outside
a tenant, the plain builders throw in development and return `/tenants` in production with
telemetry, the same pattern as the unknown-entity rule.

```ts
interface TmTenantUrls {   // home(), page(path), search, details, create, target, blob: today's signatures, minus tenantId
  home(): string; page(path: string): string; /* … */
}
declare class TmUrls implements TmTenantUrls {             // bound to tenantId()
  readonly tenantId: Signal<number | null>;
  forTenant(tenantId: number): TmTenantUrls;               // links into any tenant
  // unchanged: parseSearch, picker, signedOut, describe, preload
}
```

**Edit plan**

- 0024 §9.4: the sketch above; drop `tenantId?` from `home` and `page`; add an "Outside a
  tenant" bullet (throws in development; `/tenants` and `tm.urls.no-tenant` in production).
- 0024 §10.1: a tenant route with no `tenantId` and no routed tenant is a programming error: it
  throws in development and rejects without sending in production.
- 0027 §6.2 Connect and §7.4 "Open {live name}": build with `TmUrls.forTenant(id).home()`.
- 0024 §13: unit vectors for `forTenant`, the routed default and the no-tenant rule.

## Item 8 — §10.1: decimals as strings instead of a lossless parser?

**Current design**

- 0016 §3.2: `decimal` is a JSON number at full scale; `long` "beyond 2^53 is still written
  exactly". "Lossless numbers are a client obligation."
- 0024 §10.4: a regex fast path; a `context.source` reviver where `JSON.rawJSON` exists; and for
  older Safari "a linear pre-pass that tracks string literals", a `\u0000tm:` marker and a
  post-pass on `JSON.stringify`'s output.
- 0024 §10.1: the `TmDecimal` class. 0029 §15: "`decimal` is `number | TmDecimal`".
- 0016 Review flag 2 already names "decimals as JSON strings" as the alternative.

**How each consumer is affected**

| Consumer | Today (numbers) | With strings |
|---|---|---|
| SPA parse | two shapes per value; parser, pre-pass, post-pass | one shape; plain `JSON.parse` |
| Display | `TmDecimal` formats from its text (0029 §12) | `Intl.NumberFormat.format("…")` formats a string exactly ([MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/NumberFormat/format)); Chrome 106, Firefox 116, Safari 15.4 ([caniuse](https://caniuse.com/mdn-javascript_builtins_intl_numberformat_format_number_parameter-string_decimal)) |
| Editing | `tmNumber` holds a `number` within 15 digits (0005 §5, frozen) | same, converting at the binding |
| Totals | 0031 §6.4: "decimal arithmetic on the values' text" | already text |
| Cache, drafts, cross-tab | `TmDecimal` needs lossless JSON in IndexedDB (0025 §11) and a special copy (0031 §3.6), because structured clone does not keep prototypes ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Structured_clone_algorithm)) | strings survive `structuredClone`, `postMessage` and IndexedDB |
| MCP | "never re-parses numbers; it forwards the serialized text" (0016 §3.2) | unchanged; the model sees `"1234.5000"` |
| Public API, agents' scripts | a JS or Python client reads a double: silently wrong past 15 digits | exact text; .NET's web defaults already read numbers from strings ([Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/configure-options)) |
| Excel / Power Query on the API | Number columns | Text columns; the user sets the type. Excel keeps 15 digits either way |
| Excel codec (0019) | server-side C# | unchanged |

**Downsides of strings**

1. Generic tools see text (Power Query, jq, BI tools). OpenAPI can say `type: string,
   format: decimal`, but the registry warns that format "is not interoperable"
   ([OpenAPI registry](https://spec.openapis.org/registry/format/decimal.html)).
2. A JavaScript trap: `amount + 1` on a string concatenates, and `<` compares as text ("9" >
   "10"). TypeScript allows `string + number`. Mitigate with a branded type and typescript-eslint's
   `restrict-plus-operands`. Note the flip side: today's `number | TmDecimal` union only takes the
   `TmDecimal` path past 15 digits, so its bugs hide until a hyperinflation tenant appears.
   Strings send every value down the same path every day.
3. Mixed encoding: `int` is a number, `decimal` a string. A generic client already knows the type:
   every row set carries `type` and `scale` (0016 §3.5).
4. Two quote bytes per value; negligible after compression (0016 §8.4).
5. It reverses 0016 Decision 5 and touches six specs (edit plan below).

**Upsides of strings**

1. It deletes the hardest code in §10.4: regex, reviver, string-tracking pre-pass, marker and
   post-pass. Rule 1.
2. Speed: native `JSON.parse` on every body. Today a 16-digit run anywhere sends the whole body to
   the reviver, and IBANs or long reference numbers inside strings trip the regex. ERP payloads
   carry those often. Rule 2B.
3. The standard says so. RFC 7493 (I-JSON): such numbers "SHOULD NOT" be JSON numbers, and "it is
   RECOMMENDED to encode them in JSON string values" ([RFC 7493 §2.2](https://www.rfc-editor.org/rfc/rfc7493#section-2.2)).
   OData's `IEEE754Compatible=true` sends `Edm.Int64` and `Edm.Decimal` as strings for the same
   reason ([OASIS CSDL JSON 4.02](https://docs.oasis-open.org/odata/odata-csdl-json/v4.02/odata-csdl-json-v4.02.html)).
4. No browser floor question: `JSON.rawJSON` needs Chrome 114, Firefox 135, Safari 18.4
   ([caniuse](https://caniuse.com/mdn-javascript_builtins_json_rawjson)). Strings need nothing.
5. Exact for every consumer, not only the SPA (rule 3: agents with code tools).

**`long` too.** Otherwise a `long` above 2^53 still needs the parser. `int` keys stay numbers;
the row-set converter already switches per buffer type, so `long[]` cells become strings too.

**Server cost.** Two small converters that write the string and read a string or a number.
`JsonNumberHandling.WriteAsString` would quote every number, `int` included
([Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/system.text.json.serialization.jsonnumberhandling)).

**Recommendation — agree.** Send `decimal` and `long` as JSON strings (full scale, no exponent),
accept both forms inbound, and delete the lossless parser. The client type becomes a branded
decimal string; display formats the text through `Intl.NumberFormat`, and editors keep 0005's
15-digit envelope. This serves rule 1 (less code, one shape), rule 2B (native parse) and rule 3
(exact values for agents).

**Edit plan**

- 0016 §3.2: `decimal` and `long` rows → string; inbound takes string or number; the "Lossless
  numbers are a client obligation" block → the string rule.
- 0016 §3.5: `long` and `decimal` cells write as strings; fix the example.
- 0016 Decision 5 → "Decimals and longs as JSON strings (RFC 7493)"; delete Review flag 2; reword
  the §13.3 round-trip test.
- 0024 §10.1: `TmDecimal` becomes a branded string with helpers (`format`, `add`, `toNumber`);
  `TmJson` drops the object member.
- 0024 §10.4: delete; "bodies parse with `JSON.parse`". Update Decision 6, Review flag 2 and the
  §13 vectors.
- 0024 §12 gates: enable `restrict-plus-operands` for client code.
- 0029 §15 types and §12.2 display row: format from text; §8.2 `tmQx.num(number | string)`.
- 0025 §11 drafts: plain storage; drop the `TmDecimal` round-trip test row.
- 0026 §9.1 state dump: "in lossless JSON" → plain JSON.
- 0031 §3.6 clone copy and §8.2 save body: drop the `TmDecimal` special cases.

**Question back**

- Move `long` with `decimal`? I recommend yes, so the parser goes entirely.

## Item 9 — §10.2: show the zone when the device zone differs?

**Current design**

- §7.1: in a tenant, `timeZone` is "`me.PreferredTimeZone`, else the settings' `TimeZone`";
  tenantless, the browser's zone.
- §10.2: "No `Tellma-Time-Zone`"; the client formats in the server's zone.
- 0010 §D.4: `formatDateTime` gives "20/10/2026, 10:42", no zone name.
- 0029 §12.2: instants show "date-time in the display zone". 0023 §4.5: `tm-relative-time` has a
  tooltip with the absolute date-time.
- Review flag 8(d) names "travelling users" as what would flip the zone choice.

**Analysis — you are right that a silent mismatch misleads**

- Farah's zone is Asia/Riyadh. In London she sees "10:42" for an event at 07:42 London time.
- It matters for absolute date-times: audit stamps, job times, details fields, tooltips. Relative
  times ("3 hr ago") and plain dates have no zone.
- Use the offset form, `timeZoneName: 'shortOffset'` ("GMT+3"). MDN: `short` gives "PST" or
  "GMT-8" depending on locale data, while `shortOffset` always gives the GMT form
  ([MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/DateTimeFormat/DateTimeFormat)).
  Abbreviations are ambiguous ("IST", "CST"); offsets are not, and they localize. Supported since
  Chrome 95, Firefox 91, Safari 15.4 ([caniuse](https://caniuse.com/mdn-javascript_builtins_intl_datetimeformat_datetimeformat_options_parameter_options_timezonename_parameter_extended_values)),
  inside the current gate.
- Compare offsets at the instant shown, not zone ids: Asia/Kuwait and Asia/Riyadh are both +3.
- Keep rule 2D. In a grid, put the label once in the column header ("Created at (GMT+3)"), not in
  every cell. Details fields and tooltips append it. Relative times stay bare.
- The device zone can change while the app is open (after a flight). No browser event exists for
  it; a WICG proposal says code must poll ([WICG](https://discourse.wicg.io/t/add-event-for-changing-current-timezone/2081)).
  Re-read it on `visibilitychange`, as §8.8 does for the cookie.
- Prior art: Google Calendar keeps the chosen zone and offers "Ask to update my primary time zone
  to current location" ([U-M KB](https://teamdynamix.umich.edu/TDClient/30/Portal/KB/Article/12013/Preventing-Google-Calendar-Time-Zone-Event-Shifts)).
  Tellma's zone is already a preference (0032 My profile), so a hint linking there fits.
- Rule 3: the page context (0026) should carry the display zone. (Server text and Excel stay
  unlabelled; out of scope.)

**Recommendation — agree with a change.** Label absolute date-times with the GMT offset
("GMT+3") only when the display zone's offset differs from the device's. In grids, label the
column header once, and never use zone abbreviations.

**Edit plan**

- 0010 §D.4: format options gain `zoneLabel?: boolean` (appends `shortOffset`); `TmL10n` sets it
  when the offsets differ at the instant; a `TM_DEVICE_TIME_ZONE` token (default: the browser
  zone) pins tests; `TmL10n.zoneMismatch: Signal<boolean>`; golden rows with labels.
- 0024 §7.1: `TmLocalization.deviceTimeZone`, re-read on `visibilitychange`; the label rule.
- 0029 §12.2 `instant` row and 0030's column header: the header suffix for `instant` columns.
- 0023 §4.5: the tooltip uses the labelled form.
- 0026 page context: add the display zone.
- 0024 Review flag 8(d): name the label as the mitigation for travelling users.

**Question back**

- Labels only, or also a one-time hint ("Times show in GMT+3. Change") linking to the time-zone
  preference? My lean: labels now, the hint later.

## Item 10 — §10.5: can the server say which routes are long?

**Current design**

- §3.4: "The map carries no retry class: the call site picks `read` or `write`, and `long`."
- §10.1: `long?: boolean` "a tellma-long operation: the watchdog allows 6 min"; §10.3: watchdog
  60 s, or 6 min with `long`.
- 0016 §8.3: `tellma-long` (5 min) on `export`, `export-for-import`, `import`, `inspect-import`,
  `reports/run`, `reports/export`, `reports/audience`, `dashboards/audience` and the upload. 0016
  §4.3 stamps it during projection, by a fixed list.
- Call sites passing `long: true`: 0030 §13.2, 0034 §3.1 and §9 (projected); 0034 §2.2 coded
  routes and 0024 §14's `acme-reports/aging` (hand-mapped).

**Analysis — you are right**

- The server already decides which routes are long. The client repeats that fact at each call
  site: two sources of truth.
- A miss fails late and badly. Forget `long` on `reports/run`: the server allows 5 min, the
  watchdog kills the call at 60 s, and the user sees `offline` / `outcome-unknown` (§10.6). It
  surfaces only with a slow report in production. Rule 1 puts this plumbing in the platform.
- The emit can know it. The Contracts chunk is written from the realised composition (0016
  §3.10's contributor). Make "long" data: a `Long` flag on `[EntityAction]` and `[ApiAction]`
  (0015 §2.3), plus the four Excel operations. The projector reads it to attach `tellma-long`; the
  emit reads it to list the routes. Bonus: a distribution's slow custom action can be long; today
  only a hand-mapped route can.
- The emit sees only projected routes. Hand-mapped routes carry no `ContractMetadata` (0016
  §3.10), and the Migrator composes without ASP.NET. So `long` stays as a hatch for routes outside
  the map: effective long = the map says so, or the caller does.
- Emit a class, not seconds: `LongRequestTimeout` is runtime configuration (0016 §1.3). The
  chunk grows by a few dozen strings and is already awaited before the first call (§3.3).
- Same idea for the retry class. Calling a non-idempotent route through `read` would retry it
  (§10.5), which can repeat a mutation. With `Idempotent` in the chunk, that throws in
  development and never retries in production. Decision 8 stays: the method still forces a signal
  at compile time.

**Recommendation — agree.** The Contracts chunk lists the routes that carry `tellma-long`, and
`TmApi` applies the 6-minute watchdog to them on its own. `long` stays only as a hatch for
hand-mapped routes, and one attribute flag drives both the server policy and the emit.

**Edit plan**

- 0024 §3.1: the `contracts` loader returns `{ fingerprints: Record<string, string>; long:
  readonly string[] }`.
- 0024 §3.4: replace the "no retry class" bullet: the chunk lists long routes for `TmApi`.
- 0024 §10.1 `long?` comment and §10.3 step 3: "only for a route outside the map".
- 0016 §3.10: the contributor also writes the long list; `contracts.json` includes it; a test
  matches it against the endpoints carrying `tellma-long`.
- 0016 §4.3 and §8.3: the long set = the four Excel operations plus every action with `Long`.
- 0015 §2.3: `[EntityAction]` and `[ApiAction]` gain `bool Long = false`; `ActionDescriptor.Long`.
- 0033 §8.1 `run`, the `export` and `audience` actions, and 0035 §3.2 `audience`: `Long = true`.
- 0030 §13.2, 0034 §3.1 and §9: drop `long: true`. 0034 §2.2 and 0024 §14 keep it (hand-mapped).
- 0024 §13: unit test: a long route gets 6 min without the option.

**Question back**

- Add the retry class (`Idempotent`) to the chunk too, so `read` on a non-idempotent route is
  caught? My lean: yes; it is one more list in the same chunk.
