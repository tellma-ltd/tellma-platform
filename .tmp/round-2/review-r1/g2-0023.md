## Item 1: existing components draw glyphs through `tm-icon`

**Current design**

- 0023 §3.1: `tm-icon` draws Lucide data. Its `svg` input takes "direct data, bypassing the
  registry (the library's own glyphs)". The library registers no names. Non-goals: changes to
  existing entry points belong in 0010 Parts B–E.
- Spec 0002 §3.5 (frozen): built-in glyphs are static inline SVGs, and "the built-in glyphs can
  migrate to it then without any public-API change".
- The design pass decided against migrating. `.tmp/round-2/design/0023.md` §6 says: "the built-in
  inline glyphs of existing components stay as they are". 0010 §C.10 moves only the menu's
  consumer icons to registry names, and §D.10 lets `tmButton` size `tm-icon` children.

**Inventory**: inline glyphs in `client/projects/core/tellma-core-ui/`: 17 files, about 40
glyphs in total, about 25 of them distinct.

| 0010 Part (spec) | Entry point: glyphs |
|---|---|
| B (0002) | `checkbox`: check, minus · `select`: chevron-down caret, option check · `form-field`: circle-alert |
| C (0004) | `grid`: 7 menu glyphs in `internal/icons.ts` (scissors, copy, copy-plus, clipboard-paste, plus, corner-down-right, trash-2); find bar: chevron-up, chevron-down, x; status bar: chevron-left, circle-alert, chevron-right; tree expander chevron (one per visible tree row); check and minus as CSS `mask` data URIs in `grid-view.css` (one per checkbox cell) |
| D (0005) | `alert`: info, circle-check, triangle-alert, circle-x · `date-picker`: circle-alert, calendar, popup chevron-left/right · `file-preview`: circle-x, file-text · `files`: upload · `image`: image-off, image, camera, crop, trash-2, plus the edit pane's check · `modal`: x · `private` (error popover): circle-alert · docs examples in `button` and `input` |
| E (0006) | `entity-picker`: circle-alert, search, option check |
| keep as is | `spinner`: a two-part animated arc, not a Lucide icon |

**Analysis**

- **Ahmad is right.** The same glyph is copied by hand in several places: circle-alert 5 times,
  check 4 times plus the CSS mask, chevrons 8 times. Each copy has its own size token, its own
  stroke, and its own RTL rule.
- **RTL is handled three different ways today.** The date popup flips with
  `transform: scaleX(-1)`. The grid expander rotates under `:host-context([dir='rtl'])`, which reads
  the attribute, not the live computed direction. The status-bar chevrons do not mirror at all.
  `tm-icon`'s `mirrorInRtl` replaces all three with one rule (0023 §3.1).
- **Budgets: about neutral.** The path data moves from the template into a data array. The
  repeated `viewBox`, `fill`, `stroke` and cap attributes disappear. `size:check` measures
  self-weight, with other `@tellma` entry points left external
  (`client/scripts/bundle-size.mjs`), so the `icon` import costs nothing per entry point. A
  measurement of the last local build (`dist` from 26 Aug, so approximate) shows the tight ones:
  `alert` 1.98 of 2 KB, `form-field` 4.68 of 5, `image` 9.66 of 10, and `grid` 38.00 of 38
  (§C.11 raises it to 42). Re-measure; any raise gets a `budgetNotes` entry.
- **Eager bundle: no change.** `icon` is already eager (0023 §11). **Goldens: small churn.** No
  public API changes, except the internal `ɵTmGridIconTemplates` and the menu's icon type (which
  §C.10 changes anyway). No harness queries SVG markup. Two unit specs and one e2e spec mention
  `svg`.
- **Risk: stroke weight.** Every shipped glyph uses `stroke-width="1.75"`, but 0023 does not give
  `--icon-stroke-width` a value. Pin it at 1.75, or every glyph changes weight. The checkbox
  check and the grid's mask must also stay identical (the comment in `grid-view.css` says so).
- **Risk: first frame.** `tm-icon` builds its SVG with `createElementNS`. If it draws after the
  change-detection pass that creates it, every control loses its glyph for one frame. §3.1 must
  say it draws in that pass.
- **Risk: per-row cost.** The tree expander and the option check become one component per visible
  row. Likely fine, but measure it against the grid's scroll probe ("no long task over 50 ms").
  The per-cell check and dash stay CSS masks: a grid paints thousands.
- **The menu type.** The library registers no names, so the grid's context menu passes icon data.
  §C.10's `TemplateRef<void> | string` needs `| TmIconSource`.

**Recommendation.** Agree. Every library glyph draws through `<tm-icon [svg]>` with data imported
from `lucide`, and directional glyphs set `mirrorInRtl`. There are two exceptions: `tm-spinner`,
and the grid's per-cell check and dash masks.

**Edit plan**

- 0023 §3.1: library glyphs use `[svg]` with `lucide` data, and `tm-icon` draws in the pass that
  creates it. §9: `icon.strokeWidth` is 1.75. Decisions record: one new entry.
- 0010 "Parts B–E: rules shared": add a rule that built-in glyphs draw through `tm-icon`, with the
  two exceptions. Order: 0023 §3.1 lands before Parts B, D and E, not only before Part C.
- 0010 Part B, new §B.7: `checkbox`, `select` and `form-field` glyphs.
- 0010 Part C, new §C.13: grid glyphs, the expander reading the live direction, and the masks
  kept. §C.10: `TmMenuIcon` gains `TmIconSource`.
- 0010 Part D, new §D.11: `alert`, `date-picker` (with `mirrorInRtl`, its CSS flip dropped),
  `file-preview`, `files`, `image`, `modal`, `private`, and the `button` and `input` docs examples.
- 0010 Part E, new §E.5: `entity-picker` glyphs.
- Each new section states its budget re-measure and a geometry e2e: same box and same stroke,
  in LTR and RTL.

## Item 2: existing components match keys through `kbd`

**Current design**

- 0023 §3.2: `kbd` owns the grammar (`TmKeys`), matching (`tmKeysMatch`, with the `event.code`
  fallback for letters and digits) and rendering. The design trail (rulings.md, 0023 additions)
  added the fallback because `event.key` fails on Arabic layouts.
- 0010 §C.10: menu hints become `TmKeys` rendered with `tmFormatKeys`, and the grid's context
  menu passes `Mod+X`-style keys.
- 0010 §C.12: `TM_GRID_KEYS` lists the grid's keys as `TmKeys`, but "TmKeys imported as a type".
  The grid publishes `TmKeys` and still matches keys with its own code.

**Inventory**: where layout or platform matters today.

- `grid/internal/grid-keymap.ts`: `Mod+A/Z/Y/D/F` match by `event.key.toLowerCase()`. On an
  Arabic layout, Ctrl+Z sends an Arabic letter, so undo, redo, fill down, select all and find do
  nothing.
- `grid/internal/grid-core.ts` and `find-bar.ts`: two private `IS_MAC` copies (a regex on
  `navigator.platform`), a second `Mod+F` check, and `GRID_MENU_SHORTCUTS`, a set of
  pre-formatted strings (`'⌘⌥+'`, `'Ctrl+Alt++'`). These strings feed the `grid.menu.pasteHint`
  string, "Press {shortcut} to paste".
- `menu`: `shortcut?: string`, pre-formatted (§C.10 already fixes this).
- No change needed: the other components match named keys (Alt+ArrowDown, typeahead, arrows,
  Escape), which are the same on every layout. Ctrl+C, X and V are left to the browser's native
  clipboard events.

**Analysis**

- **Ahmad is right, and this is a real Arabic bug, not only tidiness.** The grid's main editing
  shortcuts fail on the Arabic layout today. Matching on `event.code` when `event.key` is not
  Latin is the common fix (W3C bug 18341; the PeerTube and Faiwer write-ups).
- **`kbd` has two gaps of its own:**
  - *Punctuation.* The fallback covers letters and digits only. On Arabic 101 the `/` key types an
    Arabic character, and Shift+/ types "؟". So 0027 Appendix A's `Mod+/` (Shortcuts dialog)
    fails on an Arabic layout. Extend the fallback to the US punctuation keys (`Slash`, `Period`,
    `Comma`, `Semicolon`, `Quote`, `BracketLeft`, `BracketRight`, `Backslash`, `Backquote`,
    `Minus`, `Equal`).
  - *AltGr.* On Windows, AltGr reports as Ctrl+Alt (MDN, `getModifierState`). On a Polish or
    Hungarian layout, AltGr+letter types a non-Latin character. With the `event.code` fallback,
    that would match `Mod+Alt+<letter>` and swallow the character. Rule: never use the fallback
    while `getModifierState('AltGraph')` is true. 0030 §6.2 already treats AltGr as typing.
- **Implied Shift needs one more sentence.** The grid accepts `Mod+Alt+Plus` with or without Shift
  (`+` on the numpad, `=` on the main keys). §3.2 says a symbol "implies Shift". It should also say
  that Shift is not compared for symbols.
- **Hint text.** `tmFormatKeys` returns one string per key, for `<kbd>` caps. Sentences need one
  joined string: 0023's `copy.manual` "Press {keys} to copy", and the grid's paste hint. Add
  `tmKeysText(keys)`, which gives "Ctrl+V" or "⌘V".
- **Cost is low.** The grid gains a runtime import of `kbd`. That is 1 KB, already eager, and
  outside the grid's self-weight. §C.12 already asks for a binding table, so the matcher simply
  reads it. Cache parsed `TmKeys`, so a keydown costs microseconds.
- **Don't over-migrate.** Moving the named-key handlers to `TmKeys` gains users nothing and churns
  tested code. To keep the problem from coming back, an ESLint rule in the `lint:test` vectors can
  refuse `navigator.platform` and `userAgentData` outside `kbd`.

**Recommendation.** Agree. The grid's keymap, its find bar and its pointer modifiers use
`tmKeysMatch` and `tmIsApplePlatform`. Its hints and paste text use `tmFormatKeys` and
`tmKeysText`. Named-key handlers stay as they are. Fix `kbd` itself first (punctuation, AltGr,
implied Shift), or the migration copies its gaps.

**Edit plan**

- 0023 §3.2: extend the fallback to US punctuation, add the AltGraph guard, say Shift is not
  compared for symbols, and add `tmKeysText`. §1 table: `kbd` exports gain `tmKeysText`.
- 0023 §12 unit row: add vectors for Arabic `Mod+/`, Polish AltGr+A not matching, and numpad
  `Mod+Alt+Plus`.
- 0010 §C.12: `TmKeys` and `tmKeysMatch` are imported at runtime. The keymap matches through its
  binding table. `TM_GRID_KEYS` and the matcher are one table.
- 0010 §C.10: the grid's paste hint uses `tmKeysText('Mod+V')`.
- 0010 Part C, Testing: the grid's `Mod+Z`, `Mod+D`, `Mod+A` and `Mod+F` on an Arabic layout, in
  Playwright with a synthetic `key`/`code` pair.
- 0010 "Parts B–E: rules shared": add a lint rule refusing platform sniffing outside `kbd`.
- 0027 §4.2: no edit; it already matches through `tmKeysMatch` and gains `Mod+/` on Arabic.

## Item 3: avatar colour from a hash

**Current design**

- 0023 §4.2: "One tone in both themes: `--avatar-bg`, the accent teal, with ink initials at 6.1:1
  contrast." §9: "No new semantic tokens."
- 0023 Review flag 10 names this exact alternative: "a deterministic colour per name. Flip: users
  needing to tell people apart at a glance". Ahmad is flipping it.

**Analysis**

- **Ahmad is right.** Colour helps most where initials don't: two "AA"s in a members list.
  Fluent UI does the same: `color="colorful"` "picks a color from a set of pre-defined colors,
  based on a hash of the name (or idForColor if provided)", from a set of 30.
- **What to hash.** Neither email nor `sub` is available where most avatars are drawn:

| Input | Stable | Private | Available on screen |
|---|---|---|---|
| email | no: OIDC Core §5.7 says email "MUST NOT be used as unique identifiers" | no: personal data | no: 0016 §3.6, "`CreatedBy.Email`, `CreatedBy.Subject` … never travel" |
| `sub` | yes: "never reassigned" (OIDC Core §2) | weak: the same `sub` in every tenant links one person across tenants | no (0016 §3.6); and customers with avatars (0018) have no `sub` |
| display name | no: changes with the language (Name, Name2) | yes | yes, but Arabic and English would give two colours |
| **record key** `core.User:17` | yes: ids are never reused (sequence) | yes: nothing new travels | **yes: every avatar column comes with its row id** |

- **The one cost of the record key.** The same person can get a different colour in a different
  tenant, because the user id is per tenant. Inside a tenant, every page and both languages agree.
- **Palette: tints, not solid colours.** On 0034 §7.7's eight series colours, white initials score
  3.07–4.42 and fail AA, except violet (5.77) and green (4.95). A pale tint with dark same-hue
  initials passes in both schemes (WCAG formula; it reproduces the spec's 6.12:1 for today's teal).

| Tone | Light bg / fg | Ratio | Dark bg / fg | Ratio |
|---|---|---|---|---|
| teal | `#D3E9EE` / `#084B5D` | 7.7 | `#144554` / `#AED6DF` | 6.7 |
| blue | `#D8E6F7` / `#134373` | 8.0 | `#1C4063` / `#B6D1EE` | 6.8 |
| violet | `#E2DFF7` / `#2C3173` | 9.0 | `#2E3363` / `#C7C5EE` | 7.2 |
| magenta | `#F7DFE8` / `#60314D` | 8.2 | `#533348` / `#E9C5D4` | 6.9 |
| red | `#F9DDDD` / `#662E33` | 8.2 | `#583136` / `#EDC3C3` | 6.9 |
| orange | `#FBE3DA` / `#6A3B2A` | 7.5 | `#5A3A2F` / `#F0CCBD` | 6.8 |
| amber | `#F4E8D0` / `#5A4813` | 7.3 | `#4F441F` / `#E6D5AE` | 6.7 |
| green | `#D0E8D0` / `#004813` | 8.3 | `#0F431F` / `#A9D4AE` | 6.9 |

  (Light: 18 % hue over `#FEFEFE`, initials 45 % hue over ink `#001722`. Dark: 32 % hue over the
  card `#16252D`, initials 30 % hue over `#F2F7F8`.) Every pair clears 4.5:1, which the 9–11 px
  initials of the small sizes need.
- **Tokens: the contract can't hold this yet.** Component tokens are emitted once; only
  `TmSchemeColors` switches under `[data-theme=dark]` (`emit/emit-css.ts`). Tones that differ by
  scheme need a new semantic group, a change to spec 0002 §4 (an amendment in 0010 Part B).
- **0034 §7.7 has the same gap**: its `chart` component group lists light and dark values the
  emitter can't express. One semantic `categorical` group (`mark`, `tint`, `onTint` per tone)
  serves both: charts use `mark`, avatars use `tint` and `onTint`.
- **Forced colours.** The tint disappears. Add a 1 px transparent border so the circle still
  shows, and the initials take the system text colour.
- **Rule 1.** Most avatars go through 0029 §12.2's `tm-value` binding, so one platform line passes
  the key. Distribution code writes nothing.

**Recommendation.** Agree with a change. `tm-avatar` takes an opaque `colorKey`, hashes it with a
pinned hash, and picks one of eight tinted tones. Without a key it shows today's accent tone. The
platform passes the record key (`{entity}:{id}`), never email or `sub`.

**Edit plan**

- 0023 §4.2: add the `colorKey` input; add `tmAvatarTone(key)`, which is 32-bit FNV-1a over the
  key's UTF-16 units, mod 8, pinned by fixed test vectors; tinted tones; no key keeps the accent
  tone; the forced-colours border.
- 0023 §1 table: `avatar` exports gain `tmAvatarTone`. 0023 §9: one exception to "no new semantic
  tokens", the `categorical` group. Close Review flag 10 and add a Decisions entry.
- 0010 Part B, new §B.8: `TmSchemeColors.categorical` (8 × `{ mark, tint, onTint }`) in the
  contract, the preset, `tokens:check`, and a contrast unit test for `tint`/`onTint` ≥ 4.5:1.
- 0034 §7.7: series 1–8 read `categorical.N.mark`, and the chart group stops holding
  per-scheme literals.
- 0029 §12.2 (`tm-value`): an avatar column passes `colorKey` `{entity}:{id}`. 0031 §6.2 then
  follows through it.
- 0027 §7.4: the session button passes `core.User:{me.user.id}`. 0027 §6.1 (tenantless) passes no
  key.
- Direct users pass the key too: 0032 §5.4 members, 0034 sharing and owner lists, 0035 owner, and
  0021/0028 actors.

**Question back.** Is it acceptable that one person can have a different colour in each tenant?
If not, the only clean fix is a 3-bit tone that the server computes from `Subject`, added to
0012's default related projection. That costs a column in 0012, 0014 and 0016, for a small gain.

## Item 4: busy-overlay delay to zero

**Current design**

- 0023 §5.4: step 1, "at once, in the same task", makes the page `inert` behind a transparent
  blocker. Step 2, "after `--busy-overlay-delay` (200 ms)", shows the scrim, the spinner and the
  label.
- 0023 Decision 9: "no flash on fast saves". Review flag 3 names Ahmad's alternative: "scrim and
  spinner at once". The brief: "When clicking save, a full page spinner appears".
- **Already instant:** 0031 §5.2 and 0026 §9.5 show the clicked page action's `running` state "in
  the click's frame". `tmButton`'s `pending` (spec 0005 §3) hides the label, keeps the box and
  shows a spinner at once.

**Who uses the delay.** 0031 §8.1 Save: the button spins at 0 ms, `Mod+S` included. 0031 §10.4
and 0032 §4.3 action dialogs: the spec gives the action button no busy state. 0024 §8.4 sign-out: the
confirm closes, other tabs have no trigger, and sign-out is never fast. (0027 §4.2 reads only
`active()`.)

**Analysis**

- **For Save, the 200 ms is not the click's feedback.** The button spins in the click's frame. But
  0023 §5.4 never says so, so it reads as 200 ms of nothing. Two callers really do have nothing
  for 200 ms: sign-out, and the action dialogs.
- **A dark scrim at 0 ms blinks the whole page on every fast save.** The scrim is
  `rgba(4, 18, 24, 0.32)` (design note, token table). A save that ends in 80 ms gives a full-page
  dim-and-back. That reads as flicker: the "heavy" feel Ahmad wants to avoid. Nielsen: under
  0.1 s, the result itself is the feedback.
- **A delay alone only moves the blink** to saves that end just after it. Angular's `@defer` adds
  `minimum` for this (`@loading (after 100ms; minimum 1s)`). But on the overlay a minimum keeps
  the page inert after the save ends (against rules 2B and 2C), so the overlay gets none.
- **The button is the right instant signal.** Its spinner leads straight into the next state
  (Save becomes Edit), so nothing appears and then vanishes.
- **Options:**
  - A, Ahmad's literal change: scrim, spinner and label at 0 ms. Simplest, but fast saves blink.
  - B, recommended: at 0 ms, the trigger's busy state (required of every caller) and
    `cursor: progress` on the blocker. Callers with no visible trigger (sign-out, action dialogs
    that close) pass `immediate: true`, which shows everything at 0 ms. Otherwise the scrim
    follows at 200 ms.
  - C, a middle way: a faint veil (about 8 %) plus the spinner and label at 0 ms, and the full
    scrim at 200 ms. Fast saves give a barely visible blink. It adds one CSS state.

**Recommendation.** Agree that feedback must start at 0 ms. Disagree with the dark scrim at 0 ms,
because it trades a delay for a flicker. Choose B: instant through the trigger and the cursor,
`immediate` for callers with no trigger, and the scrim kept for long writes.

**Edit plan (for B)**

- 0023 §5.4: step 1 adds `cursor: progress`, and the caller must show its trigger busy in the same
  frame. `run(work, { label, immediate? })`: `immediate` shows the scrim, spinner and label at
  once.
- 0023 Decision 9 and Review flag 3: restate them. §12: the Playwright overlay spec checks the
  trigger busy and the cursor in the click's frame, and `immediate` at 0 ms. §13 "Instant
  feedback": the same pin.
- 0024 §8.4: the sign-out overlay passes `immediate: true`, in every tab.
- 0031 §10.4: the dialog's action button shows `pending` in the click's frame. 0032 §4.3 follows
  through it.
- 0031 §8.1 step 5: cite the Save button's `running` state as the instant feedback.
- For A instead: 0023 §5.4 step 2 becomes "at once". Drop the `--busy-overlay-delay` token (§9).
  Decision 9 and flag 3 flip. 0031 is unchanged.

**Question back.** A, B or C? The real choice is whether a dimmed page at 0 ms is worth a blink on
every fast save.

## Item 5: search feedback begins at 50 ms

**Current design**

- 0023 §6.2 and 0030 §6.1: `value` (the echo) updates in the keystroke's frame; `search` emits
  after a sliding 50 ms debounce; "the request and its cancellation are the consumer's".
- 0030 §3.3: the progress bar shows "150 ms after a read starts". So the first sign of loading
  comes about 200 ms after the last key: Ahmad's 200. 0034 §3.3 "reloading" uses the same 150 ms.
- 0024 §10.5: a keystroke read is cancelled by the next keystroke.
- 0006 §4.2 (the shipped picker): "the spinner shows at once and holds until a fresh,
  uninterrupted result set returns", with a leading-and-trailing 50 ms debounce.

**Analysis**

- **Ahmad is right.** The brief says keypress feedback "should be instant". The shipped picker
  already shows its spinner at once, so the search page is the odd one out.
- **Trap: don't tie the bar to "a read is running".** Each keystroke cancels the read (0024
  §10.5). The next read starts 50 ms later. A bar that follows the read would blink off and on at
  every key while the user types.
- **Tie the bar to 0030 §6.3's "stale" rule instead.** The bar turns on when `search` emits
  (50 ms) and stays on until the result for the current text paints. It stays on through
  continuous typing.
- **Fast answers.** A cached or very fast read (under about 50 ms) would flash the 4 px bar. A
  bar blocks nothing, so it can safely stay on screen for a minimum time (about 250 ms) while the
  rows render the moment they arrive. This is the `@defer` `minimum` idea, applied where it costs
  no waiting. `aria-busy` follows the truth, not the minimum.
- **Optional: the first key at 0 ms.** A leading-edge debounce, as in 0006, makes the first key
  after a pause search, and show the bar, at once. That costs one extra cancelled read per burst.

**Recommendation.** Agree. Loading feedback starts when the search emits, never later, and holds
while results are stale, with a short minimum on screen so fast answers don't flicker. Apply the
same rule to 0034's reloading bar for consistency.

**Edit plan**

- 0023 §4.4: `tm-progress-bar` gains `active` (default true). Once shown, it stays at least
  `--progress-min-visible` (250 ms). It never reserves space, and it never delays content.
- 0023 §6.2: add a consumer rule: loading feedback starts when `search` emits and holds while the
  result is stale. If leading edge is adopted: `debounce` becomes leading and trailing, as in 0006
  §4.2, and the §12 timing unit tests change with it.
- 0030 §3.3: "150 ms after a read starts" becomes "when `search` emits, held while the result is
  stale (§6.3)". Update the 0030 §5.3 "reloading" row and the 0030 §18 timing test to match.
- 0034 §3.3 "reloading": the bar shows at once, with the same `active` hold.

**Question back.** Should the search page take the picker's leading-edge debounce, so the first
key after a pause searches at 0 ms, not 50 ms?
