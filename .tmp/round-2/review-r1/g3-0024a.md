## Item 1 — §2.6: why `init`? Can `dotnet new` scaffold everything?

**Current design**

- §2.1: "`tellma-client init <slug>` writes the boilerplate. A platform test asserts that
  `init acme` reproduces Acme's files byte for byte, apart from `src/app/**`."
- §2.6 table: `init <slug>` "Writes §2.1's boilerplate with Tellma's default icons and brand
  files." §5.1: "`init` scaffolds `public/manifest.webmanifest`." §13 and §14 test and require
  the `init acme` reproduction.
- Spec 0011 §1.2 (Client project): "`tellma-client init` scaffolds it."
- ARCHITECTURE.md plans a `dotnet new tellma-distribution` template in `templates/tellma-distribution/`
  (repo layout and "Tenant & Distribution Onboarding"). It also says the Client esproj is
  "scaffolded by `tellma-client init`". So it plans two scaffolders.
- The repo's `templates/` folder holds only `.gitkeep`. **No spec owns the `dotnet new` template.**

**Analysis — you are right**

- One distribution, two scaffolders, is one too many. A new distribution would run
  `dotnet new` for the server and then `tellma-client init` for the client.
- The client files point at server files. One template keeps them in step:
  - `package.json` has `"tellma": { "migrator": "../Tellma.Distro.Acme.Migrator" }`;
  - the esproj has a `ProjectReference` to the Migrator;
  - `serve` reads `<SLUG>_CLIENT` and `<SLUG>_WEB` from `.dev-ports.local`.
  With two tools, both must agree on the slug and the paths. With one, they cannot disagree.
- `dotnet new` can write everything `init` writes:
  - any file, including the PNG icons (`copyOnly`);
  - the name in file names and contents. By default `-n Acme` replaces `Acme` and the lowercase
    `acme` ([naming and value forms](https://github.com/dotnet/templating/wiki/Naming-and-default-value-forms)).
    The uppercase `ACME_` port names need one extra symbol using the `casing` generator
    ([template.json reference](https://github.com/dotnet/templating/wiki/Reference-for-template.json));
  - it runs on Windows and Linux, and ships as a NuGet template package versioned with the platform.
- What `init` gave that the template must copy: the client scaffold always matched the installed
  `@tellma/core-tools`. The template gets the same by stamping the platform version into the
  scaffolded `package.json` when it is packed.
- After scaffolding, `pnpm install` is a printed next step (the "Display manual instructions" post
  action), safer than a script post action. The first `dotnet build` already restores the
  `dotnet tellma` tool (ARCHITECTURE.md, `Tellma.Core.targets`).
- One detail affects either tool. In-repo Acme uses workspace references (`workspace:*`, project
  references), while a real distribution uses versions. So the byte-for-byte test needs an
  "in platform repo" template switch, or it must skip those lines.
- Rule 1 fit: one command creates a whole working distribution. That is simpler for coding agents.
  It also lines up with ARCHITECTURE.md's rule "configuration is scaffolded once and owned by the
  distribution".

**Recommendation — agree.** Drop `init`. `dotnet new tellma-distribution -n Acme` scaffolds the
whole distribution, client included. The parity test becomes "the template, instantiated as Acme,
reproduces Acme's scaffold-owned files".

**Edit plan**

- 0024 §2.1: "`tellma-client init <slug>` writes…" → "the `dotnet new tellma-distribution`
  template writes these files"; the parity test instantiates the template as Acme.
- 0024 §2.6: delete the `init` row; "Five Node commands" → four (three if item 2 is approved too).
- 0024 §5.1: "`init` scaffolds" → "the template scaffolds".
- 0024 §13 row "`init` reproduction" and §14 "Acme" bullet: name the template test instead.
- 0011 §1.2, Client project bullet: "`tellma-client init` scaffolds it" → "the distribution
  template scaffolds it", citing the template's owner (see the question).
- The template's owner (0011 §1.2, or a new spec): template package name, the list of files it
  owns, the `-n` name forms, the in-repo switch, the parity test on Ubuntu and Windows.
- ARCHITECTURE.md (repo layout, Client row): "scaffolded by `tellma-client init`" → "scaffolded by
  the `dotnet new tellma-distribution` template".
- Log the 0011 change in `.tmp/round-2-spec-changes.md`.

**Question back**

- Which spec owns the template? Option A: a short "The distribution template" part in 0011 §1.2
  (it already owns Acme's shape). Option B: a later spec for distribution tooling (template,
  Bicep, CI), with 0024 and 0011 listing only the files they need. I lean to A, kept small.

## Item 2 — §2.6: why is `check` its own command?

**Current design**

- §2.6 table: `check` runs "Budgets (§12), the manifest lint (§5.1), hashed names (§6), the
  `index.html` rules (§4.1), brand files (§7.6)."
- `build` already runs it as its last step ("6. runs `check`"). §4.1, §5.1, §6, §7.6 and §12 name
  the command.
- §3.6's "config check" (`tmCheckAppConfig`) is a different thing, run in `build` step 1. Two
  things share the word "check".

**Analysis — you are right**

- Nothing runs `check` alone. §12's PR gate runs `tellma-client build` on Acme. The esproj runs
  `pnpm run build`. `serve` never checks.
- `check` cannot do much without a build. Budgets and hashed names need the build output and
  `stats.json`. A manifest or `index.html` change needs a rebuild anyway, because the output
  carries those files.
- Folding it in lets the build fail sooner. Some checks read only source files: the `index.html`
  rules, the manifest members and icon sizes, the brand SVGs. They can run in step 1, beside the
  config check, before the slow `ng build`. Only budgets and hashed names must wait for the output.
- Small gap found: §2.6 says every problem prints as `code key feature`, but the `check` problems
  have no codes (Appendix A lists only config codes). Folding is a good moment to name them.
- Rule 1 fit: fewer commands, and the one word "check" then means one thing.

**Recommendation — agree.** Remove the `check` command. `build` runs the source checks in step 1
and the output checks in its last step, all failing with exit 3 and a code per problem.

**Edit plan**

- 0024 §2.6: delete the `check` row; step 1 adds "the source checks (§4.1, §5.1, §7.6)"; step 6
  becomes "the output checks: budgets (§12) and hashed names (§6)".
- 0024 §4.1, §5.1, §6, §7.6, §12: "`tellma-client check` fails/requires/measures…" →
  "`build` fails/requires/measures…".
- 0024 Appendix A: add the output and source check codes (for example `budget-exceeded`,
  `unhashed-asset`, `manifest-invalid`, `index-html-invalid`, `brand-file-invalid`) and widen the
  title from "Configuration problem codes" to "Build problem codes".
- 0024 §13 and §14: no change beyond the wording.

**Question back:** none.

## Item 3 — §2.3: why hide an entity on the client only (`entity:`)?

**Current design**

- §2.2: `TmDeclarationKey` kinds include `entity`.
- §2.3: "`entity:` drops the entity's routes, launcher entry and picker." `entry:` drops only the
  launcher entry, so the pages stay reachable.
- The decision trail shows `entity:` came in with the kind-qualified key list (register C-0024-4,
  rulings §0 and §2.3). No use case was argued for it. No other spec uses `hide: ['entity:…']`.

**Analysis — you are right**

- Client-only hiding is not access control. The web API, the MCP tools and the server metadata all
  still expose the entity. Only the UI forgets it.
- It breaks rule 3 (AI-native). The future assistant sees the UI context and acts through MCP. It
  could offer or open things the UI says do not exist.
- It half-breaks the UI too. Other entities' fields still point at a hidden entity, but "drops the
  picker" removes the way to fill them.
- The client already follows the server elsewhere. §9.2 matches `:segment` routes through
  `TmEntities.bySegment` against the emitted metadata, and the launcher shows an entity only when
  `TmPermissions.allows(name, 'query')` (0029 §3).
- The server today has no "this distribution does not use pack entity X" switch:
  - ARCHITECTURE.md's composition has a closed set: reuse, extend or fork a pack entity. There is
    no "drop".
  - The nearest server switch is per stack, `[ApiResource(Mcp = McpExposure.Hidden)]` (0016
    §4.1), which gates MCP tools only and still projects the web endpoints.
- What a distribution can do today without `entity:`:
  - grant no role the entity's permissions (spec 0014): the launcher, routes, API and MCP all
    refuse, consistently, for those users;
  - `hide: ['entry:…']` to drop the launcher entry but keep deep links.
- A real server switch, if wanted, is bigger than it looks. Removing a stack's endpoints means
  every navigation to it needs a rule (no picker, display name only). The config check must also
  stop calling a pack's declaration of a removed entity `unknown-entity`.
- The same question applies to two other kinds that have a server half:
  - `widget:`: the server still registers the type, so a hidden client declaration would trip
    `widget-missing` (0035 §2.2) if the check runs after `hide`;
  - `report:`: a coded report with a server `run`.
  The other kinds (`page:`, `section:`, `entry:`, `settingsTab:`, `appBar:`) are pure client.

**Recommendation — agree.** Remove `entity:` from client `hide`. Whether an entity exists is a
server fact, and the client follows the metadata. Until a distribution needs more, permissions plus
`entry:` cover the common case.

**Edit plan**

- 0024 §2.2: remove `'entity'` from `TmDeclarationKey` (and `'widget'`, `'report'` if you agree
  below).
- 0024 §2.3, Hide bullet: delete the `entity:` sentence. Add one line: "Which entities exist is
  the server's: the client follows the metadata (§9.2)."
- 0024 §13, the `tmCheckAppConfig` row: "each `hide` kind" stays; drop the `entity:` case.
- No cascade into 0027, 0029 or 0032: none of them uses `entity:` hiding.
- If you want the server switch now: one attribute or composition call in 0015/0016, its effect on
  0029 §2.2 (metadata) and 0024 Appendix A (`unknown-entity` for packs), plus a review flag.

**Question back**

1. Server switch now, or later? Now: a server call that removes a pack stack's web endpoints, MCP
   tools and metadata, with rules for navigations to it. Later: permissions plus `entry:` until a
   distribution needs it. I lean to later.
2. Should `widget:` and `report:` lose client `hide` for the same reason?

## Item 4 — §5.3: the Angular service worker is in maintenance mode

**Current design**

- §5: "Angular's service worker caches the whole app except three on-demand sets."
- §5.3: `tellma-client build` writes `ngsw-config.json` and runs `ngsw-config`. Settings:
  `appData` versions, `navigationRequestStrategy: performance`, no data groups, a `shell`
  prefetch group, an `on-demand` lazy group.
- §5.4: our own registration through a `TrustedScriptURL`; §5.5: `TmUpdates` over `SwUpdate`
  (`VERSION_READY`, `unrecoverable`, `VERSION_INSTALLATION_FAILED`); §6 serves `ngsw.json`,
  `ngsw-worker.js`, `safety-worker.js`.
- The rule we rely on (§5.5): "running tabs keep their version, and a reload or a new tab gets the
  new one."

**Is the claim true? Yes.**

- The README says: "We will not be accepting any new features or bug fixes other than security
  fixes." It suggests "native browser APIs directly" for advanced needs, and does not mention
  Workbox ([README](https://github.com/angular/angular/blob/main/packages/service-worker/README.md)).
- History: "no new features" was added in August 2025 (angular/angular PR #63364). In September
  2026 it was widened to bug fixes, because bug-fix PRs were already being closed (commit
  `dec9755646`).
- So "maintenance mode" here means frozen, but not deprecated or removed. It still ships with
  every Angular release. Bug reports are now closed as "not planned" (for example #61567, about
  outdated versions served, closed June 2026).
- Open bugs that matter to us:
  - #45377: going offline during the first prefetch leaves the cache invalid, with no retry on
    refresh. Our `shell` group is large (1.5 MB warn), so a flaky first visit could miss warm
    launch until the next version.
  - #55975 and #44402: `checkForUpdate` can do nothing on a first load or after a hard reload.
    §5.5's `disabled` verdict already covers an uncontrolled page.

**What this design needs, compared**

| Need | Angular SW (NGSW) | Workbox | Hand-rolled |
|---|---|---|---|
| Prefetch `shell` group, lazy `on-demand` | yes, asset groups | yes, precache manifest | write it |
| Hash-checked versions | yes: hashes in `ngsw.json`; a bad hash re-fetches, then the whole version is refused ([devops guide](https://angular.dev/ecosystem/service-workers/devops)) | revisions; optional SRI `integrity` per entry | write it |
| Old tabs keep their version; reload or new tab gets the new one | yes: versions are data inside one long-lived worker, and each tab is tied to its version | **no**: one precache per worker. A new worker waits until no tab uses the old one, and "refreshing the page isn't enough" ([web.dev](https://web.dev/articles/service-worker-lifecycle)). `skipWaiting` plus outdated-cache cleanup breaks old tabs' lazy chunks | write NGSW's version model |
| Update detection | `SwUpdate`: `VERSION_READY`, `checkForUpdate`, `unrecoverable` | `workbox-window` events, per worker, not per app version | write the protocol |
| Safe mode, kill switch | yes: degraded states, `safety-worker.js`, self-destruct on an `ngsw.json` 404 | none built in | write it |
| Trusted Types registration | our own `register()` (Angular passes a plain string, checked in `provider.ts`; `register()` is a `TrustedScriptURL` sink in the [SW spec](https://w3c.github.io/ServiceWorker/)) | same | same |
| Future Web Push | shows a notification when the payload has `notification.title`; `SwPush` subscribes; custom code goes in a wrapper script that `importScripts('./ngsw-worker.js')` ([docs](https://angular.dev/ecosystem/service-workers/custom-service-worker-scripts)) | no push module; write handlers | write handlers (small) |
| Notification clicks | declarative: `openWindow`, `focusLastFocusedOrOpen`, `navigateLastFocusedOrOpen`, `sendRequest` (GET only) ([docs](https://angular.dev/ecosystem/service-workers/push-notifications)). Opening the target works; "mark read" needs a POST, so it needs the wrapper | write it | write it |
| Upkeep | security fixes only | v7.4.1 (May 2026), about one release a year, mostly dependency bumps | ours |
| Code we own | none | a few hundred lines, plus the version-model gap | about 2,000–3,000 lines (estimate) |

- NGSW's worker is about 4,000 lines of TypeScript (`driver.ts` alone is 1,395). Without data
  groups, which we do not use, it is about 3,300. That is the bar a hand-rolled worker must meet.
  The hard part is not caching. It is tying each tab to its version and recovering from a broken
  cache safely.
- A broken worker can strand users on a bad version. That makes a new worker a high-risk component
  that must be tested across Chromium, Firefox and WebKit.
- Workbox does not help with the hard part: its lifecycle conflicts with §5.5. It is also only
  lightly maintained.
- The frozen state is less risky than it sounds. We use only "basic caching", which the README
  says it covers. The code is MIT licensed, so if Angular refuses a fix we need, or drops the
  package, we fork the worker into our build tooling; frozen code is cheap to fork. And only
  `TmUpdates` and `tellma-client build` touch it, so a swap changes no distribution code (rule 1).
- Web Push later: the push spec can switch registration to a Tellma wrapper (`tm-worker.js`) that
  imports NGSW and adds `push` and `notificationclick` handlers. Registering a new script at the
  same scope updates the registration (SW spec, `register()`: "creates or updates a service worker
  registration for the given scope"). It also widens the `tellma` policy from `/ngsw-worker.js`.
- If we ever hand-roll, one cascade to know: 0010 §D.5 `clearAll` deletes every `tm-*` cache and
  says NGSW's `ngsw:` caches "never match". A Tellma worker's caches must not use `tm-`, or a
  sign-out would wipe the app cache.

**Recommendation — disagree with hand-rolling now; stay on NGSW, on the record.** It covers this
design's needs today, including the per-tab version model that is hardest to rebuild. Write down
the maintenance status, the fork fallback and the push wrapper path, so the switch is planned, not
a surprise.

**Edit plan**

- 0024 Decisions record, new row: "**Angular's service worker, though it takes security fixes
  only**: it covers prefetch groups, hash-checked per-tab versions and safe mode; a hand-rolled or
  Workbox worker must rebuild the per-tab version model (§5.5)", §5.
- 0024 Review flags row 6: add (c) "NGSW in maintenance; alternative: fork its MIT worker into
  `@tellma/core-tools`, or hand-roll; flips if Angular refuses a fix we need, deprecates the
  package, or Web Push needs code a wrapper script cannot hold."
- 0024 §5.4, one line: "A later push spec may register a wrapper script that imports
  `ngsw-worker.js`; the `tellma` policy then admits that script instead."
- 0021 Review flag 3 (no push channel yet): add one clause that the push spec owns the worker
  wrapper (0024 §5.4).
- No change to 0010, 0025 or 0026.

**Question back:** none, unless you want the wrapper (`tm-worker.js`) registered from day one as a
hedge. That costs one generated file and one hosting row now, and saves nothing that cannot be done
later.

## Item 5 — §8.4: don't ask while another tab is saving; wait, then check again

**Current design**

- §8.4 sequence: `drafts.query` → `drafts.reply {dirty, busy}`: "confirm if any, wait while any is
  busy".
- The confirm: with dirty drafts, "Sign out and discard unsaved changes?" / "You have unsaved
  changes in {count} tabs." With a busy tab, the message adds "A save is still running. Sign-out
  waits for it to finish." Buttons: Sign out, Cancel.
- Waiting: "After Sign out, the tab re-asks every second until no tab is busy, for at most the 60 s
  write watchdog."
- Then `session.signing-out`, and every tab shows the "Signing out…" overlay (0023 `busy-overlay`).

**Analysis — you are right, and it fixes a false alarm**

- A saving tab still holds its draft. A draft is cleared only on save success (0025 §11, 0031 §11),
  and the reply's `dirty` is `TmDrafts.dirtyCount()`. So today every running save also counts as
  dirty. The user is asked "discard unsaved changes?" about a save that will most likely succeed a
  second later.
- After the wait the first answer may be wrong both ways. The save succeeded, so nothing was at
  risk. Or it failed, and the user agreed to discard before seeing the failure.
- Today's spec also does not say what the acting tab shows during the wait. Your overlay fills
  that gap.
- Proposed flow:
  1. Sign out → the acting tab's overlay starts at once ("Signing out…"). It sends `drafts.query`.
  2. Any tab busy → the label becomes "Waiting for a save to finish…". Re-ask every second, for at
     most 60 s.
  3. Decide on the fresh answers:
     - nothing dirty → sign out, with no question;
     - dirty (a failed save shows up here) → close the overlay, show the confirm;
     - still busy after 60 s → the confirm, with the busy sentence.
  4. After the confirm → "Signing out…" and today's steps (`session.signing-out`, telemetry flush,
     `/bff/logout`).
- Edge cases:
  - **A save starts while the confirm is open.** After Sign out, re-ask; if busy, wait again, but
    don't ask about dirty again. The user already agreed.
  - **Background writes** (preferences, the locale write) count as busy. They are short, and the
    scrim shows only after 200 ms (0023 §5.4), so usually nobody sees them.
  - **The saving tab is not blocked.** `session.signing-out` goes out only after the wait, so that
    tab finishes its save and shows the outcome.
  - **No way out of the wait.** The busy overlay has no Cancel, and Escape does nothing (0023 §5.4).
    The worst case is 60 s in the acting tab. That is bounded, and the user asked for it, so I
    would accept it (see the question).
- Rule fit: 2B, the overlay blocks input in the same task; 2C, only the acting tab waits, for the
  user's own request, up to the cap; 2D, overlays and dialogs float; 2F, the label is a polite
  status and focus returns.
- No message change: `drafts.reply { dirty, busy }` (0025 §6.2) already carries both facts.

**Recommendation — agree.** Wait first, under the overlay, then ask only if a draft is still dirty
or a save still runs after 60 s. One question, asked once, with true facts.

**Edit plan**

- 0024 §8.4 sequence diagram: the overlay at the click; a wait loop on `busy` before the confirm;
  a re-ask; then the confirm only when needed.
- 0024 §8.4 "The confirm" bullet: dirty is judged after the wait; the busy sentence only on the
  60 s timeout. Suggested copy: "A save is still running in another tab. If you sign out now, you
  won't see whether it finished."
- 0024 §8.4 "Waiting" bullet: rewrite as steps 1–3 above, with the label "Waiting for a save to
  finish…" and the rule "a confirmed sign-out never asks again".
- 0024 §8.4 "Signing out" bullet: the acting tab's overlay is the same run, with its label
  switching to "Signing out…".
- 0024 §13 Playwright "sign-out across three tabs with a dirty draft and a running save": split
  into (a) a save that succeeds signs out with no question; (b) a save that fails shows the confirm;
  (c) a dirty idle tab shows the confirm at once.
- 0027 §10.3: "confirmation, broadcast, overlay, failure toast, redirect" → "overlay, wait for
  saves, confirmation when needed, broadcast, failure toast, redirect".
- No change to 0023 (unless you want Cancel), 0025 or 0031.

**Question back**

- Should the wait offer Cancel? No (my lean): 60 s at most, and 0023 stays as is. Yes: a Cancel
  button on the wait, which needs a 0023 `busy-overlay` option (for example `cancel` in `run`
  options); 0023 is a round-2 spec, so it changes in place.
