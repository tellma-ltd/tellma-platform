## Item 11 — §11: show the exact missing securable on `forbidden`

**Current design**

- 0024 §11: `forbidden` → "You don't have access to {entityPlural}" / "Ask your administrator for
  access." No securable shown. A read shows it inline, a write in the 400 dialog (§10.6).
- The server already sends the pair: 0016 §7.1 maps `ForbiddenException(Code, Resource, Action)`
  to 403 `forbidden` with `arguments.resource` and `arguments.action`. The client ignores them.
- The client already has a label for every pair: the Core chunk's `securables` section (0014 §10,
  label chains in 0032 §12.4). No client helper turns a pair into a label yet.
- One code covers three causes (0015):
  - **no grant** on the pair (§9.1);
  - **outside the filter**: the grant exists, but not for this record (§6.6, §9.2, §9.3);
  - **restricted path**: a query reads a related entity `E`'s column beyond its `[RelatedSelect]`
    projection (§5.2 step 4, 0014 §5.3, 0033 §8.2). The pair is then `(E, Read)`.

**Analysis — you are right, and it also fixes wrong copy today**

- Support: the user says "I need Sales invoices: Save"; the admin opens that user's Access tab
  (0032 §4.6), which uses the same labels, and finds the row at once.
- Today's copy is wrong in two of three causes. Restricted path: on a Sales invoices page the 403
  names `acme.Customer`, but the copy says "no access to Sales invoices". Outside the filter: the
  user *has* access to Sales invoices, just not to this record.
- So the client also needs the cause. Guessing it from the cached `me.access` is unsafe (it may be
  stale, and "filtered Read" fits two causes). The raise sites know the cause exactly.
- **Security — nothing new leaks:**
  - only connected members get a 403; others get 404 `tenant-not-found` (0016 §5.4);
  - the pair is already in the body, and every signed-in user already holds the full securable
    list in the Core chunk (0014 §10, 0024 §6);
  - "outside the filter" reveals nothing: a hidden record answers 404 first (0015 §9.2), so a 403
    only hits a record the user can already read, or just wrote (post-check);
  - keep out: which roles grant it, the filter text, other users. That stays behind
    `access/check` (0014 §10).
- Rule 3 bonus: MCP gets the same `arguments` (0016 §11.7), and the error dialog's page context
  carries them (0024 §11), so an agent can tell the user what to ask for.

**Recommendation — agree, with one addition.** Show the missing permission by its labels, and add
a `reason` argument (`no-grant`, `outside-filter`, `restricted-path` with its `path`) so the
message is true. Keep roles, filters and other users out of the error.

| Reason | Title | Message |
|---|---|---|
| `no-grant` | "You don't have permission for this" | "It needs “{resource}: {action}”. Ask your administrator to grant it." |
| `outside-filter` | "Your access doesn't cover this record" | "Your “{resource}: {action}” permission covers only some records. Ask your administrator if you need this one." |
| `restricted-path` | "You can't see {field} here" | "It needs full “{resource}: Read” access. Ask your administrator to grant it." |

The dialog details and the inline reference line also show the raw pair in mono, LTR isolated
(`acme.SalesInvoice · Save`), for support.

**Edit plan**

- 0015 §14.1: `ForbiddenException` gains `ForbiddenReason Reason` and `string? Path`.
- 0015 §5.2 step 4, §6.6, §9.1, §9.2, §9.3, §14.2: each raise site passes its reason.
- 0014 §5.3: name the three reasons where the 403s are described.
- 0016 §7.1 row: `arguments.reason`, plus `arguments.path` for `restricted-path`; §13.3: one
  assertion per reason.
- 0013 §10.1: `Problem_forbidden_Detail` uses the labels and the reason (MCP, scripts).
- 0029 §7: `TmPermissions.label(resource, action): Signal<string>` over 0032 §12.4's chains.
- 0024 §11: three `forbidden` rows replace one; the raw pair joins the details.
- 0024 §2.4: the `tmPage` gate renders the `no-grant` view from its declared pair.
- 0024 §13: `TmErrorPresenter` cases per reason.

## Item 12 — §5.6: the update download fails; decide from `Tellma-Build` at once

**Current design**

- 0024 §5.6: on 412 `client-outdated` or 404 `route-not-found`, `TmApi` awaits
  `TmUpdates.check()`: `ready` → `client-outdated`; `none` → `server-outdated`; `disabled` (no
  worker) → `client-outdated` when `Tellma-Build` *differs* from the UI version.
- 0024 §5.5: `check()` returns only `ready | none | disabled`.
- 0016 §3.10 already says the SPA compares `Tellma-Build` "to tell a newer server from an older
  one". 0024 §5.6 only tests equality. The two specs disagree.

**What happens today when the download fails (verified in Angular's source)**

1. `check()` calls Angular's `checkForUpdate()`, which waits for the *whole* new version.
2. On a failed download Angular emits `VERSION_INSTALLATION_FAILED`, switches the worker to
   `EXISTING_CLIENTS_ONLY` and resolves `false` (it never rejects). An unreachable `ngsw.json`
   also resolves `false`, with no event.
3. `false` maps to `none`, so the verdict is `server-outdated`: "Tellma is being updated. Try
   again in a minute." The 30 s retry gets the same 412 and the same wrong message. The server is
   fine; the client is old. A manual reload would actually work (in that mode new loads go to the
   network), but the copy says "wait".

Even when the download works, nothing shows until the whole new version (the `shell` group, up to
1.5 MB per §12) has arrived. A Save click can spin for seconds (rule 2B).

**Analysis — you are right; the header decides most cases at once**

- `Tellma-Build` is `X.Y.Z[-pre]+<sha>` (0026 §7) and is on every response, the 412 included
  (0016 §6.2). Compare by SemVer precedence; SemVer ignores the `+sha` build metadata.
  - **server newer** → `client-outdated` at once (an old tab after a deploy: the common case);
  - **server older** → `server-outdated` at once (a new tab hit an old instance mid swap);
  - **same `X.Y.Z[-pre]`, other sha** (no version bump) → unordered: ask the worker, as today;
  - **same build** → a contract mismatch is impossible; a bug: kind `server`, code
    `contract-mismatch`, to telemetry.
- Trap: a **rollback** leaves the server older for good, so "try again in a minute" would loop.
  The worker treats *any* different manifest as an update, so keep it as the tie-breaker: when the
  30 s retry meets the same older build, ask the worker; `ready` turns it into `client-outdated`.
- `check()` needs two more results so a failure is not read as "no update": `failed`
  (`VERSION_INSTALLATION_FAILED` during the check) and `unreachable` (`false` with no event).
  `none` only when the stable `NO_NEW_VERSION_DETECTED` event arrived.

**Recommendation — agree.** Decide from `Tellma-Build` and show the message at once; ask the worker
only for unordered versions or to catch a rollback. Make Reload download first, show progress, and
offer a plain reload after a repeated failure.

The `client-outdated` flow: "Tellma was updated" with Reload shows at once, and a background check
starts. Reload runs `TmUpdates.update()`: ready → reload now; otherwise the button shows busy
("Getting the update…", fixed width) until the check ends. `failed` or `unreachable` → "Couldn't
download the update. Check your connection and try again." After a second failure, add "Reload
anyway" (a plain reload, which the degraded worker sends to the network). Drafts survive (0025 §11).

**Edit plan**

- 0024 §5.5: `check()` returns `ready | none | failed | unreachable | disabled`, with how each is
  detected; add `update()` and a `checking` signal.
- 0024 §5.6: the precedence table, the rollback tie-break, and the unordered fallback (worker
  check capped at 3 s; past that, or on `failed`/`unreachable`, `client-outdated`, the likelier
  cause). The `disabled` row uses precedence, not inequality.
- 0024 §11: Reload runs `update()`; add the "Couldn't download" state and "Reload anyway".
- 0024 §4.4 "Failure" (a chunk that fails to load): the same `failed` handling.
- 0024 §13: vectors per result and precedence case, rollback included; Playwright: a 412 with the
  update download blocked.
- 0026 §7: `TmAppVersion.compare(other): -1 | 0 | 1 | null` (null = unordered).
- 0027 §11.1 item 4: the "server differs" alert shows only when the server is newer.
- 0016 §3.10 `Tellma-Build` bullet: state the precedence rule and the unordered case.
- ARCHITECTURE.md: the fast path needs a higher `X.Y.Z[-pre]` per deployment; without a bump the
  worker fallback still answers correctly.

## Item 13 — §14: replace `bank-reconciliation` and `aging` as Acme's examples

**Current design and the problem**

- Acme's custom page is `tmPage('bank-reconciliation')` under GL's `financials` section; its coded
  report is `acme-aging` (`acme-reports/aging`, securable `acme.AgingReport`).
- Both will belong to the GL module. A coding agent may learn "distributions build core accounting
  features", which is wrong.
- What the replacements must keep exercising:
  - page: a section *another feature* declares, a path parameter (§2.4), a write-behind preference
    (0025 §9.1), a page action with a shortcut and its own page context (0026 §2), a `page`-scope
    shortcut (0027 §4.1);
  - report: `AsOf` (required, defaulted in C#), a `Customer` parameter, kind `Summary`, a `long`
    read, a details card (0034 §2.1), a home widget (0035), a pin URL (0027 §8.2), a telemetry
    event, a stream endpoint (0016 §4.5), an MCP tool class (0016 §11.9).

**Proposal — a "credit control" pair built on Acme's own model.** The test for
"distribution-specific": it reads or writes Acme's *own* entities, so no pack could own it. Acme
owns `Customer.CreditLimit`, `CustomerType` and the `set-credit-limit` action (0018 §1.4).

- **Page `credit-review`:** a work queue of customers near or over their limit. The reviewer sets a
  new limit (`set-credit-limit`) and moves on. It stays under `financials` (credit control is a
  finance task), so the cross-feature section test survives.
- **Report `acme-credit-exposure`:** per customer, the limit, open invoices posted on or before
  `AsOf`, the headroom and an over-limit flag, sorted by headroom. Same parameters as aging, so
  the 0034/0035 binding examples keep their shape.
- Caveat: a future sales pack might have credit limits, but these sit on Acme's own entity.
- Alternatives: an "invoice dispatch board" page; a "sales commission statement" report (Acme's
  tiered rules need code by nature, but it loses the Customer details card).

## Item 14 — Review flag 8: per-user formats (ar-SA vs ar-AE)

**Current design — every Arabic user of a distribution gets the same formats**

- 0024 §7.1: `locale` is "the definition's `locale`" (`tmArabic({ locale: 'ar-SA' })`): one value
  per language, for every tenant. Review flag 8(b): "`ar-SA` digits everywhere".
- 0024 §10.2 sends that locale as `Accept-Language`, which 0013 §9.2 puts *above* the stored
  preference, so the server formats the same way.
- 0013 §9.2 says a user "stores a regioned `PreferredLanguage` (`ar-SA`)" to get a region's
  digits. That path is broken: 0018 §3.2 validates with `ILanguageCatalog.IsOffered`, an exact code
  match (0013 §7.2), so `ar-AE` is refused; 0024 §7.1 uses the preference only "if offered" (same
  match); and the header overrides it anyway. Fix this whatever you decide.
- So, to your question: today all users see the same numerals and formats, per distribution.

**What the locales actually do** (Node 24.18, ICU 78.3, CLDR 48; the data current browsers ship)

| Locale | Digits | 1234567.89 | Date (medium) | Week starts | Weekend |
|---|---|---|---|---|---|
| `ar` | Latin | 1,234,567.89 | 19/06/2026 | Saturday | Fri–Sat |
| `ar-SA` | Arabic-Indic | ١٬٢٣٤٬٥٦٧٫٨٩ | ١٩/٠٦/٢٠٢٦ | Sunday | Fri–Sat |
| `ar-AE` | Latin | 1,234,567.89 | 19/06/2026 | Monday | Sat–Sun |
| `ar-EG` | Arabic-Indic | ١٬٢٣٤٬٥٦٧٫٨٩ | ١٩/٠٦/٢٠٢٦ | Saturday | Fri–Sat |
| `ar-MA` | Latin | 1.234.567,89 | 19/06/2026, 24-hour time | Monday | Sat–Sun |
| `ar-SA-u-nu-latn` | Latin | 1,234,567.89 | 19/06/2026 | Sunday | Fri–Sat |

- Real differences, including the date picker's first weekday (`tmFirstDayOfWeek`, 0005 §2.2,
  reads the locale). A UAE user forced to `ar-SA` gets Arabic-Indic digits and Sunday weeks.
- Trap: `en-SA` is not in the browser's data and falls back to `en` (US dates, "Jun 19, 2026"),
  while week data still follows SA. Offer only pairs that resolve exactly.
- Server: .NET formats with Latin digits only. On .NET 10, `ar-SA` prints `1٬234٬567٫89`, so an
  `ar-SA` user sees ١٬٢٣٤ in the app and 1٬234 in server text. `ar-AE` matches on both ends.
- Precedent: Dynamics 365 Business Central has separate per-user **Language** and **Region**
  settings; Region drives dates, numbers and currency. Windows and macOS do the same.

**Analysis — you are right.** Language and formats are separate axes, as the spec already holds
for UI language versus content language (0024 decision 12). A tenant default matters too: one
distribution can host a KSA tenant and a UAE tenant, and with a tenant region most users never
touch the setting. Rule 2 holds: `me` and `settings` are warm launch documents, so the locale is
known before first render; a region switch re-renders in place like a language switch;
`TM_ACTIVE_LOCALE` is already a signal (0010 §D.4).

**Recommendation — agree.** Add a per-user **Region** (formats) preference, separate from
language, plus a tenant default region. The locale is `<active language>-<region>` when that pair
is in the shared list, else the language definition's `locale`. Region: user → tenant → none.

**Edit plan**

- 0014 §3.1: `core.Users.PreferredRegion varchar(2) NULL` (ISO 3166-1 alpha-2); add it to
  `UserProfileView` and the §7.3 prologue `SELECT`.
- 0013 §5.2: `core.Settings.Region varchar(2) NULL`; §5.6 resolved view; §6.5
  `Settings.RegionUnknown`.
- 0013 §9.2: culture = language × region (header region, then `PreferredRegion`, then tenant
  `Region`); drop the "regioned `PreferredLanguage`" sentence; `NegotiationInput` gains
  `PreferredRegion`; update decision 7.
- 0013 §1.2 / 0024 §3.1: `languages[]` gains `regions` (the pairs .NET resolves exactly), so both
  ends offer one list; the client drops a pair the browser resolves differently.
- 0018 §3.2: `Users.RegionUnknown`; §3.5: `MeSaveRequest`, `MeLocaleRequest`, `MeLocaleResult`
  gain `Region`. 0025 §9.5: adoption covers `region`.
- 0024 §7.1: `region` signal and `setRegion`; the `locale` row follows the rule above; §7.2: a
  region switch follows the language-switch steps; review flag 8(b) rewritten.
- 0032 §4.1, §4.2: `tm-region-field` in `tm-user-locale-fields` (names from `Intl.DisplayNames`,
  a live sample "١٬٢٣٤٫٥ · 19/06/2026"); Region on the tenant's General settings tab.
- 0027 §10.1: optional "Format" item beside language and calendar in the session menu.

**Questions back**

1. Digits: many Saudi business users want Latin digits with Saudi weeks (`ar-SA-u-nu-latn`). Add
   a "Digits: native / Latin" choice, or is Region enough?
2. Tenant default region: include it (recommended), or per-user only?

## Item 15 — Review flag 9: `displayName` and `copyright` are not localized

**Current design**

- 0024 §3.1: one `displayName` and one `copyright`, from `Tellma:DisplayName` and
  `Tellma:Copyright` (0011 §8), emitted into the Core chunk.
- Users see them in: `document.title` "<page> · <displayName>" (0024 §4.4); "Tenants · {display
  name}" (0027 §6.2); the signed-out page, which reads `index.html`'s `<title>` (0027 §6.3); the
  wordmark link (0027 §7.1); the About dialog (0027 §11.1); the support dialog (0026 §12.2). The PWA
  `name`/`short_name` are hand-written in the manifest (0024 §5.1).
- Emails are unaffected: they name the tenant (0022 §4, 0018 §3.3), and the sender name is
  transport config (0007).
- The seam exists: the About text is the localizable server key `Distribution_About` (0027 §11.1).

**Analysis — a small but real gap**

- Latin brand names in an Arabic UI are common and fine. But a distribution with an Arabic brand,
  or a registered Arabic legal name (common in KSA and UAE), cannot show it.
- String packs fix it cheaply: they sit in the `shell` group and load before first render (0024
  §3.3), so warm launch stays offline (rule 2A) and decision 15's "titles need the name offline"
  still holds.
- The signed-out and boot pages load no string pack (0024 §6), but `TM_BOOT.strings` already
  carries per-language boot strings (§4.2), so the name can ride there and set `document.title`
  before first paint.
- Manifest: Chrome and Edge 148 (April 2026) support `name_localized` and `short_name_localized`
  (also description and icons), keyed by BCP 47 tags; the browser picks by its own language
  preferences, else `name`. The announcement names no other browser.
- `DistributionInfo.DisplayName` (0011 §5.9) stays one value: an anonymous document, no language.

**Recommendation — agree, light touch.** Optional resx keys `Distribution_DisplayName`,
`Distribution_ShortName` and `Distribution_Copyright` in the distribution's `Strings`, falling back
to the config values. The client reads them through `TmServerText`, like `Distribution_About`;
`build` copies them into `TM_BOOT` and the manifest.

**Edit plan**

- 0024 §3.1: the config values become fallbacks; name the three keys and the order.
- 0024 §4.2: `build` copies `Distribution_DisplayName` into `TM_BOOT.strings`; `tm-boot.js` sets
  `document.title` in the boot language.
- 0024 §5.1: `build` writes `name_localized` and `short_name_localized`; `check` applies the
  12-character rule to each localized short name.
- 0024 §4.4, 0027 §6.2, §6.3 (boot string, not `<title>`), §7.1, §11.1, 0026 §12.2: "the
  localized display name".
- 0011 §8 config table: `DisplayName` and `Copyright` are the keys' fallbacks.
- 0024 review flag 9: rewrite (localized via string packs; a rename still needs a rebuild).

**Question back:** 0024's copy hard-codes "Tellma": "Tellma couldn't start" (§4.2) and, in §11,
"Tellma is busy", "Tellma was updated", "Tellma is being updated", "Tellma couldn't finish this",
"before Tellma answered". Acme's users see "Tellma", yet the About dialog says "{display name} is
built on Tellma" (0027 §11.1), so distributions have their own brand. Should these say
`{displayName}`?
