## 1. Consolidated critique of the brain dump

**The general design is right.** One bulk-shaped service per top-level entity; a save pipeline of preprocess → validate → persist → effects; row-level security composed as a `FilterTree`; validators loading context in one batch; app-assigned ids; version-tag caches; per-row leasing for background work; staged blobs; an intent-oriented MCP surface; three API surfaces with different compatibility promises. All of it stands. What follows is what had to change.

**Things that cannot work as written**
1. "Upsert" reads as `MERGE`; two live engine defects and the temporal tables make it unusable. The emitter writes separate `INSERT`/`UPDATE`/`DELETE` with two TVPs per table (new rows, existing rows), so a row deleted under you is a conflict, never a resurrection.
2. "Start the transaction … validate … save … commit" holds a transaction across round trips and C# code. Under RCSI it protects nothing; on-prem it holds locks across client I/O. The transaction is the persist round trip's text, and every write-time invariant is a SQL statement inside it.
3. `MayRetry` conflates reported failures (rolled back under `XACT_ABORT`; always safe to re-run) with ambiguous ones (connection dropped; safe only when every statement is idempotent). The flag is `Idempotent` and retry is the executor's job — SqlClient's own retry is inert inside a transaction.
4. `Node` in the UDTT row image is impossible: `hierarchyid` cannot ride a TVP without `SqlHierarchyId`. Node is a platform-owned shadow column computed in SQL.
5. "Read the versions before executing any API call" and a separate `OnConnect` call double the read path. Connect, tag reads, activity stamp and the permission guard ride the first business round trip as a fixed prologue.
6. Per-entity lease columns collide with business statuses, churn temporal history every renewal, contaminate the concurrency stamp, and cannot be pruned. One `core.Jobs` table per tenant with a `JobId` FK from business rows replaces them.
7. The tree re-path "from saved rows whose parent is not in the batch" double-paths a row whose parent is a descendant of another saved row; the affected set must be computed first. `MAXRECURSION` does not detect cycles.
8. Healing a desynchronised sequence with `ALTER SEQUENCE … RESTART` needs `ALTER`; the web identity must not hold it. The allocator heals by consuming the gap through `sp_sequence_get_range`.
9. "Pre-commit non-transactional side effects (creating blobs)" and "post-commit deletion" both orphan objects with nothing to retry from. Staged uploads plus a blob table make blob creation precede the request and deletion a state flip inside the transaction.
10. `X-Today` lets a client move a security predicate (`ValidUntil >= today()`); spec 0008 already binds `today()` to the tenant's zone. The user's zone formats; it never binds.
11. "Values are exported raw" is unachievable for `long`, `decimal(19,4)`, `Guid`, dates and Ethiopian calendars; encoding is by property type with text fallbacks, and import never reads a cell format.

**Detailed choices corrected**
12. Two audit vocabularies (`SavedAt/SavedById` + period on temporal entities; four columns elsewhere). One vocabulary: `CreatedAt/CreatedById/ModifiedAt/ModifiedById` on every top-level entity; system-versioning is additive; `ModifiedAt` is the concurrency token; children carry no audit columns; `SavedById` on weak entities goes.
13. `Center.IsLeaf` is `SubtreeCount = 1`; `Level` is `level(Node)`; both go. `SubtreeCount`/`ActiveSubtreeCount` stay (expanders per rendered row). `CenterType`'s three values drop the two grouping types the parent rule needs; five values are restored.
14. Tags on temporal rows (`SettingsVersion`, `UserSettingsVersion`, `PermissionsVersion`, `LastActive`, inbox tracking) write a history row per bump. Tags live in `core.VersionTags` (tenant) and `core.UserStamps` (user); "version tag" is the word; "metaversion" is a per-shape `FormatVersion` constant on the wire, never stored.
15. `core.User` (singular) contradicts ARCHITECTURE.md (`gl.Invoices`) and spec 0001; tables are plural, classes and Queryex names singular.
16. `Subject` has no type (it is a ≤ 255-char case-sensitive ASCII string; the authority is swappable); `Resource = "all"` can collide with a real name (`*`); a filter on a wildcard resource is unbindable; `RoleMembership` lacks `(UserId, RoleId)` uniqueness; `Filter`/`FilterLanguageVersion` lack their CHECK; anyone with `Save` on roles or users could make themselves an administrator (escalation rules bound delegation).
17. The user state list mixes tenant facts, identity-server facts and email-provider facts, misses the `Active` invite outcome (no email is sent), refusal, and prefix results. The tenant stores `New | Invited | Active` plus the last invite's outcome and error; delivery is a live drill-down.
18. `UserSettings` collides with tenant `Settings` and needs no surrogate id; it is `core.UserPreferences (UserId, Key, Value)`, opaque to the server, written only by self-service. `PushSettings` conflates preferences with device credentials; `ImageFitJson` is a presentation choice applied before storage.
19. `TenantRegistry.ResolveConnectionString` returns a secret on the hottest path and `RegisterConnectionString` stores one; two topologies are two code paths. No tenant database has a password (managed identity / integrated security); the catalog stores a location; one catalog database per distribution always.
20. "Which tenants am I a member of" by fan-out is an N+1 that turns a listing into an authorization result. A catalog hint table, reconciled by the migrator, is navigation only.
21. `IBlobService { Write(tenantId, pathBlobPairs) … }` invites client-derived paths; `ImageId` has no type or FK; no limits, processing or authorization are stated. Names are server-generated, `ImageId` is `int?` FK to `core.Blobs`, and image bytes are re-encoded.
22. The natural-key inference chain ends in non-unique columns; it stops at unique-index-backed candidates and falls back visibly to the surrogate id. Tree import "using the surrogate key for parents" cannot reference a parent new in the same sheet; parents are references resolved in-sheet first. "Merge" collides with SQL `MERGE`; it is `Upsert`.
23. "Save admits a single entity" contradicts the guiding principle; save takes an array and the UI sends one. "If you can read an entity you can read all related entities" leaks every referenced user's email and subject through `CreatedBy`; related entities are a declared display projection.
24. "Pre-commit side effects", "cron strings stored anywhere", "toggle_activate" as an action name, `Task` as a type family, `InboxItem`, "etag"/"fingerprint" for cache versions, `TenantConfigurationKV`, `CenterType` vs `Type`, layer folders named after layers — all renamed or dropped below.

**Gaps the design fills**
25. No session model (BFF store, refresh, back-channel logout, staleness bound) and no CSRF posture. No request context as an explicit value reaching services and job scopes. No tenant state model (`Provisioning | Active | ReadOnly | Suspended | Retired`).
26. No enforcement point for the lockout invariants (two administrators removing each other both pass an `EXISTS` under RCSI); no system principal for seeds and schedules; no drift policy stated as a mechanism; no securables-registration mechanism that is hard to forget.
27. No statement of what the distribution author writes. Under this design: one entity class, one line of composition, zero web, zero MCP, zero permission code; a service class only when there is logic.
28. No wire precision rule for `decimal(19,4)` through `JSON.parse`; no concurrency rule when the client sends no stamp (it is a 422 under `Check`); no rate-limit mechanism separation; no drain contract on deploy.
29. No overlap policy, cancellation, checkpoints, retention, poison threshold, clock rule, handler idempotency contract, or restore safeguard for *queued* rows in the background design; no per-type notification registry, dedup, target link or retention in the inbox design.
30. No manifest in the Excel file, no blank-cell or child-sheet semantics, no synchronous/background boundary, no error coordinates, no intake path, no zip-bomb limits.
31. No `Blob` table (orphans and reconciliation are unanswerable without it), no staging TTL unit (hours, not days), no server-generated blob path (exports).
32. Two axes conflated in localization: content languages (tenant, ≤ 3) versus the request culture (any language the distribution ships); two fallback chains, not one; no calendar header and a `-u-ca-` trap; no settings key discipline (`SettingKey<T>`).
33. Feature composition (ARCHITECTURE.md's answer to boilerplate) is absent; it is built at minimal fidelity: BCL-only feature contract, `Requires` edges, data-only contribution items, two aggregated gates.

### 2.1 Table names — plural; classes and Queryex names singular
**Decision.** Every table is plural (`core.Users`, `gl.Centers`, `core.Jobs`, `core.Blobs`, `core.VersionTags`); single-row state tables keep a singular state noun (`catalog.CatalogState`, `core.JobWorkerState`); `core.Settings` is already plural. Sequences `sq_<Table>` in the table's schema (`core.sq_Users`, `gl.sq_Centers`, `core.sq_Jobs`, `core.sq_Blobs`). History tables `<Table>History` in the same schema (`core.UsersHistory`). Index and constraint names: `PK_<Table>`, `FK_<Table>_<Column>`, `UX_<Table>_<Cols>` (unique), `IX_<Table>_<Cols>`, `CK_<Table>_<Name>`, `DF_<Table>_<Column>`.
**Why.** ARCHITECTURE.md (`gl.Invoices`), spec 0001 (`InvoicesList`), and eight of ten themes; T7 and T10 wrote singular conditionally.
**Corrected.** T7: `core.Blob` → `core.Blobs`, `sq_Blob` → `sq_Blobs`, every `core.Blob` reference. T10: `core.Job/Schedule/ScheduleState/Notification/NotificationPreference/Export/Import` → `core.Jobs/Schedules/ScheduleStates/Notifications/NotificationPreferences/Exports/Imports`; `sq_Job/Schedule/Notification` → plural. T8: `<Table>_History` → `<Table>History`; `FK_<Table>__<Column>` → single underscore. T2: unique indexes `IX_<Table>_Node` → `UX_<Table>_Node`.

### 2.3 Entity base shapes and capability declarations
**Decision.** In `Tellma.Core.Abstractions.Entities`:
- `Entity<TKey>` (`Id: TKey`, `TKey` ∈ `int | long`) — the keyed base; also the base of **system-written entities** (`Job`, `Notification`, `Blob`, `Schedule` is not one) that carry `CreatedAt` explicitly and are never written through `Save` [synthesizer].
- `TopLevelEntity<TKey> : Entity<TKey>` — adds the four audit columns; `TopLevelEntity = TopLevelEntity<int>`.
- `ChildEntity<TKey> : Entity<TKey>` — saved only with its owner; no audit columns; owning FK marked `[ParentKey]`.
- `TreeEntity<TKey> : TopLevelEntity<TKey>` — `ParentId: TKey?`, `SubtreeCount: int`; `TreeEntity = TreeEntity<int>`; `ActivatableTreeEntity<TKey> : TreeEntity<TKey>, IActivatable` adds `IsActive` (write-once, §2.5), `ActiveSubtreeCount`; `ActivatableTreeEntity = ActivatableTreeEntity<int>`. Neither declares a CLR `Parent` property: the tree convention configures the self-referencing FK without a navigation, and the Queryex navigation `Parent` is derived from the FK column name (`ParentId` → `Parent`) exactly as every other navigation-less FK is, so `Parent.Name`, `descendantOf`, `ancestorOf` and `level(Node)` work unchanged; the in-memory graph a details read returns carries the parent row in `Related` (the `Parent` navigation is in the default `[RelatedSelect]` projection), so the UI needs no CLR navigation, and EF LINQ users of the `Linq<T>()` escape hatch join on `ParentId` explicitly. Node is a shadow column. `Center : ActivatableTreeEntity` is a single non-abstract, unsealed class in `Tellma.Module.Gl.Abstractions` (no `Center<TCenter>` generic base); a distribution extends it by plain inheritance (`MyCenter : Center`) like `User` and `Role` and registers the leaf with `tellma.UseEntity<Center, MyCenter>()`, where `TLeaf : TDefault` is the one constraint for every entity kind. ARCHITECTURE.md's generic-base fork pattern remains available for pack entities whose navigations point at *other* entities; self-referencing trees do not use it (S38).
- Capability interfaces: `IActivatable { IsActive }`, `IJobEntity { JobId: int? }` (replaces `ILeasable`). No `IAudited`, no `IMultilingual`, no `ISystemVersioned`, no `ITreeEntity<TKey>`: audit is on the base, temporal is `[Temporal]`, multilingual is `[Multilingual]`, tree is the base.
- Annotations: `[Temporal(enabled)]`, `[Tree(MaxDepth)]`, `[ParentKey]`, `[Children(parentKey)]` (only to disambiguate a `[NotMapped]` list when the child has two FKs to the parent type), `[ServerOwned]`, `[WriteOnce]`, `[SelfEditable]` (column-set marker read by self-service saves), `[NaturalKey(Order?)]`, `[Unique]`, `[Searchable(Kind)]`, `[PreserveWhitespace]`, `[JsonColumn]`, `[Multilingual]` (on the primary of a `P/P2/P3` group), `[Cacheable(MaxRows)]`, `[BumpsVersionTag(name)]`, `[BumpsUserVersionTag(column, userIdProperty)]`, `[BlobReference(kind, preset, …)]`, `[ExcludeFromExcel]`, `[Stack(…)]`, `[ApiResource(…)]`, `[DefaultSelect]`, `[RelatedSelect]`, `[DetailsExpand]`. A child collection is any `[NotMapped]` `list<TChild>` property whose `TChild : ChildEntity`.
**Why.** Base classes for shapes that add columns, one-property interfaces for gates, attributes for declarations — T2's contract, with T3's `[Multilingual]` (a pure naming convention mistakes `Address2` for a twin), T5's `[Unique]`/`[Searchable]`/`[PreserveWhitespace]`, T8's `[SelfEditable]`, T10's `IJobEntity`.
**Corrected.** T2 D7 (convention only → `[Multilingual]` anchors the group; twins by name), D22/§3.1/§4.1 (`ILeasable` and the leasable column set removed; `IsLeasable` → `IsJobEntity`; fixture `fixture.Jobs` gets `JobId` instead of lease columns). T5 §3.2 (`IEntity<TKey>`/`IAudited`/`ITreeEntity<TKey>`/`IMultilingual`/`IHasImage` → the bases above; `[GatedBy]` dropped, see 2.5). T8 §3 (`IAudited`, `ISystemVersioned`, `IMultilingual`, `[Child]`, `TreeEntity<TSelf, TKey>` → `[Temporal]`, `[Multilingual]`, plain `[NotMapped]`, `TreeEntity<TKey>` without a CLR `Parent`). T4 §4 headers (`AuditedEntity`, `ActivatableEntity`, `MultilingualName` → `TopLevelEntity`, `IActivatable`, `[Multilingual]`). T10 §3.1 (`Schedule` "carries AuditedEntity, ActivatableEntity, MultilingualEntity" → `TopLevelEntity`, `IActivatable`, `[Multilingual]`).

### 2.4 Audit columns, timestamps, and the concurrency token
**Decision.** Every top-level entity: `CreatedAt datetime2(7)`, `CreatedById int FK core.Users`, `ModifiedAt datetime2(7)`, `ModifiedById int FK core.Users`, all server-owned, stamped server-side once per batch from `SYSUTCDATETIME()`. `ModifiedAt` is the concurrency token; no `rowversion` anywhere. User-visible mutations (save, actions, invite) stamp it; bookkeeping never touches the entity row (tags, `LastActiveAt`, `InboxSeenAt` live on `core.UserStamps`; lease columns on `core.Jobs`); the one documented exception is the prologue's `Invited → Active` flip. Children carry no audit columns; any child change stamps the parent. Every other timestamp column is `datetime2(3)` UTC. The persist batch's ambiguous-failure probe checks inserted ids only; an update-only batch that loses its connection during `COMMIT` surfaces `DependencyUnavailableException` with a reload instruction [synthesizer].
**Why.** T2/T4/T5/T8 agree on the vocabulary; server stamping (T2, T4, T8) beats T5's C#-computed stamp because instances skew and the database clock is one source per tenant; the C#-stamp's only advantage — the update probe — is traded for honesty on a rare path.
**Corrected.** T5 D13/D14 (`@tm_stamp` computed in C#, `max + 1 tick`, the update-side commit probe → server stamp; probe inserts only). T4 §4 (`InvitedAt`, `ActivatedAt` `datetime2(7)` → `datetime2(3)`; `LastActiveAt datetime2(0)` → `datetime2(3)`). T1 catalog stays `datetime2(3)` (not entity audit).

### 2.5 `IsActive` is write-once; write-once is validated and excluded
**Decision.** `IsActive` carries `[WriteOnce]` (`PropertyOwnership.WriteOnce`): a client may set it when **creating** a row — a save with `id = 0`, an import in `Insert` mode, and the insert half of `Upsert` — so imported reference data can arrive inactive; the emitter's `INSERT` takes it from the payload (default `true`) and never puts it in an `UPDATE` set list. After creation it changes **only** through the `activate`/`deactivate` actions (`IDataBatch.Update` under the `Activate` securable); a changed value on an update is the `WriteOnce` validation error at the path, exactly like any other `[WriteOnce]` column. The editable Excel shape **includes** `IsActive` (settable on insert); on `Update` and on the update half of `Upsert` a changed value is the `WriteOnce` error reported with the sheet coordinates; the display export includes it as before. The `IncludeInactive` default filter and the `Activate` securable are unchanged. `[WriteOnce]` columns are excluded from every `UPDATE` by the emitter **and** a changed value on update is the validation error `WriteOnce` at the path. `[ServerOwned]` values are overwritten from the before image (update) or the fresh-instance default (insert), silently. `[GatedBy(action)]` is not built (deferred): with `IsActive` write-once its only user is gone.
**Why.** One path after creation, one securable, no save-bypasses-activate hole (T5 §1.2) and no silent import deactivation, while imports and seeds can create rows inactive; T5's diff gate becomes unnecessary; T2, T4, T9's server-owned reading (always created active) is replaced because it makes inactive reference data unimportable.
**Corrected.** T5 D11/D19 (`[GatedBy("activate")]` on `IsActive` → `[WriteOnce]`; `[GatedBy]` removed from §3.2). T8 D5 (`IsActive` "client-settable through the admin save" → settable on create only; afterwards through the actions only). T2 D4/T4/T9 (`IsActive` server-owned → write-once). T6 D7 (`[ServerOwned(AfterCreate = true)]` → `[WriteOnce]`).

### 2.7 The batch abstraction: `IDataBatch`

### 2.8 Id allocation
**Decision.** `IIdAllocator` (T2's design) with a small warm buffer: `Reserve(batch, entityType, rows)` computes the exact deficit, takes what the buffer holds, and appends one `sp_sequence_get_range` statement per short sequence to the batch it is given (the pipeline's RT1); `TakeAsync(entityType, count)` answers from the buffer or pays one dedicated round trip (rare, metered `tellma.data.ids.refills`) for callers with no batch in flight (job enqueue inside `ContributeAsync`). Every batch the executor runs may carry a refill to a low-water mark (default 64 per sequence) so the common create is one round trip. Ids are assigned after RT1 (or immediately when the buffer covered the deficit), **before validators run**; temporary negative ids (`Id < 0`, unique within the payload) are rewritten in every self-typed FK. A validation failure returns unused ids to the buffer (nothing external saw them); a persist attempt never does. Healing by consuming the gap (T2 D10), triggered only by a 2627 on the table's primary key — a duplicate on any other unique index is a validation error, never a heal. System-written rows inserted by fixed-text statements (`core.Jobs`, `core.Notifications`) take their ids inside the statement (`sp_sequence_get_range` in-batch, `Id = first + ordinal`), so `INotifier.Notify` and `IJobQueue.Enqueue` are synchronous and never depend on the buffer; `TakeAsync` serves only callers with no batch in flight [synthesizer]. [synthesizer merge of T2 D10 and T5 D9]
**Corrected.** T2 D10 (`Assign` "after validation passed" → after RT1, before validation; buffer gains a bounded refill). T5 D9 ("never un-consumed", "background prefetch", `AppendRefill` → as above; `IIdAllocator.TakeAsync` kept). T10 §3.3 (`ReserveIds<T>(count)` sync → `IIdAllocator.TakeAsync` or `Reserve` on the batch).

### 2.9 Background work: `core.Jobs`, `IJobEntity`, Guid lease token
**Decision.** No lease columns on business entities; one `core.Jobs` table per tenant (T10 D1) with `LeaseToken uniqueidentifier`, `LeaseExpiresAt datetime2(3)`, `LeaseOwner nvarchar(128)`, `Attempts int`; business rows reference it through `IJobEntity.JobId` (FK `ON DELETE SET NULL`, unique filtered). The job statements (claim, renew, append, complete, gap-hold, tick, enqueue) are fixed-text statements owned by 0019 and executed through `IDataBatch.Sql` with declared writes; every write that follows a lease is fenced by the lease token and a row-count check (`THROW 50422 Job.LeaseLost` / `Schedule.TickLeaseLost`), and the completion `UPDATE` is the first statement of its transaction so nothing a handler wrote survives a lost lease; the claim never selects a row whose `Attempts` reached the handler's `MaxAttempts` (exhausted rows are failed set-based); the entity join load is `Query<TEntity>` restricted by `KeySetRestriction("JobId", "@tb{b}_claimed")`. Jobs and schedules are tenant-scoped only: nothing deployable rides `core.Jobs`, and the catalog session sweep is a hosted timer in `Tellma.Core.AspNetCore`, not a job [synthesizer].
**Why.** T10 owns the semantics; T2's `ILeasable` was written before T10's design and its four reasons (status collision, temporal churn, prunability, one code path) win.

### 2.10 Tree node scheme

**Decision.** Every batch executed on a caller's behalf — `Read`, `Validate`, and `Persist` — begins with 0013's fixed-text prologue (`@tm_` names): resolve the subject, refuse unknown/deactivated, throttled activity stamp (60 s; skipped under `NoActivityStampMetadata`), the one-time `Invited → Active` flip, read all tenant tags and the caller's two user tags, return permission rows and profile only when stale, compute `@tm_Guard` from `UserId`, the tenant `permissions` tag and the user's `PermissionsTag`; the body is wrapped in `IF @tm_Guard = 1 BEGIN … END`. For `Persist` batches, the in-transaction re-check is the first statement after `BEGIN TRAN` and closes the window rather than narrowing it: it reads the tenant `permissions` row (and every declared dependency) **and** the caller's `UserStamps.PermissionsTag` `WITH (REPEATABLEREAD, ROWLOCK)`, so the shared locks are held to `COMMIT` and a concurrent role or membership save — whose bump is its last statement — waits for this persist instead of committing under it; the cost is a wait bounded by one round trip, paid only by permission writers, never by other saves. No `UPDLOCK` on stamp rows. `IGuardedBatchRunner.Run` recomposes once, then `StaleContextException`. On a `ReadOnly` tenant the premises carry `StampActivity = false` and `AllowStateFlip = false`, so the prologue writes nothing and reads succeed against a read-only database. `ConnectAsSystem` throws unless `RequestContext.Kind = System`. Cold path: one prologue-only round trip per user per instance. Failure modes as T4 D19 with the status changes of 2.20.
**Why.** T4 owns seam 16; the `IF` wrapper never runs a body under stale premises; T3's per-kind mismatch policy is the C#-side contract; T5's stamp-row lock would either serialize every save of the tenant or require the fan-out T4 rejected.
**Corrected.** T2 D12/§5/§6.16 ("the connect prologue never rides a Persist batch" → it does; the transaction opens inside the guarded block). T3 D4 (reads "optimistic, compared after" → guarded before; policies unchanged; `permissions` and `PermissionsTag` dependencies are the guard's inputs). T4 D18 (`@tm_Guard` includes `@tm_SettingsTag = @tm_ExpectedSettingsTag` → excluded; settings mismatch reported in the connect row as `SettingsStale`). ### 2.31 Schema evolution — the N−1 rule
