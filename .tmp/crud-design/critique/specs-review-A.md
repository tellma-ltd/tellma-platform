# Cross-spec review A — specs 0010–0014

Reviewed 2026-09-04 against `ledger.md`, `seams.md`, `spec-style.md`, `notation.md`, `docs/AGENTS.md` and `crud-stack-specs.md`, with greps across all eleven specs. Severity: blocking / major / minor. Each finding: location, problem, evidence, fix. Checks run on every spec: header and date (all five match the verbatim shape), mandatory sections (Context, Goals / Non-goals, Testing, Definition of done, Decisions record, Review flags — all present in all five), sibling-spec section references (none found), narration and process words (none found), XML doc comments (none), C# fences (0010: 3 labelled ≤ 5 lines; 0011: 1; 0012: 1; 0013: 0; 0014: 3 — one over length, see 0014-5), "Owns:" completeness of the breakdown (complete in all five), and every ledger §5 review flag for the spec (all present in all five; 0010 carries 15 + 4 cross-cutting, 0011 13 + 11, 0012 14 + 7, 0013 26 + 7, 0014 18 + 7).

## Spec 0010

1. **blocking** — `docs/specs/0010-distribution-host-and-multitenancy.md` §4.4 and §6.2. Provisioning steps must run "inside a tenant scope with `Kind = System` (through `ITenantScopeFactory`; the tenant is `Provisioning` at that moment, which the migrator's caller is permitted)", but §4.4 states `CreateScopeAsync` "throws `TenantUnavailableException` for every state but `Active`" and §3.3's verdict table says `Provisioning` → "throws". The contract (`CreateScopeAsync(snapshot)`) has no member, option or documented exemption through which the migrator obtains a scope for a `Provisioning` tenant; "which the migrator's caller is permitted" names no mechanism. Evidence: seams §9 ("background scopes exist only for `Active`") and seams §18 ("runs in a System tenant scope") carry the same tension; 0012 §5.7 and 0013 §11 both rely on a `System` scope during `provision`. Fix: add an explicit mechanism to §4.4 and the contract — e.g. `CreateScopeAsync(snapshot, allowProvisioning: bool = false)` usable only from `Tellma.Core.Migrator`, or a migrator-internal `IProvisioningScopeFactory` — and make the `Provisioning` row of §3.3's last column read "throws, except for the migrator's provisioning run (§6.2)".

2. **minor** — §7.3 `catalog.TenantMemberships.Subject nvarchar(36)`, §7.4 `catalog.Sessions.Subject nvarchar(36)`, §3.8 `TenantMembershipRecord.Subject: nvarchar(36)`. The ledger fixes `Subject` as "a ≤ 255-char case-sensitive ASCII string; the authority is swappable" (ledger §1.16, §2.29) and 0013 §3.1 stores it as `varchar(255)` binary-collated; a subject longer than 36 characters (any non-GUID authority) cannot be recorded in the hint or the session table, and `nvarchar` is case-insensitive under the default collation while 0013 compares subjects case-sensitively. seams §9 restates `nvarchar(36)`, so this is reported as a doubt rather than a departure. Fix: align the three catalog columns and the TVP to `varchar(255) COLLATE Latin1_General_100_BIN2`, or state in §7.3/§7.4 why the catalog assumes GUID subjects.

3. **minor** — §6.1 command table. `provision --name … --category … [--id <n>] …` where seams §18 lists `provision --tenant <id> [--admin-email | --admin-subject]` (also `migrate [--tenant <id> | --all-tenants]`, which 0010 extends with `--catalog-only` and `--parallelism`). The spec is the owner and its form is richer, but the flag naming drifts (`--id` vs `--tenant`), and §6.3 uses `provision --id <tenantId>`. Fix: either adopt `--tenant <id>` for resuming an existing row (matching `set-state --tenant`) or correct seams §18; one spelling.

4. **minor** — §1.2, `taxonomy.json` bullet: "`reservedSlugs` (the architecture document's list plus `acme`…)". `spec-style.md` allows naming the architecture document in passing only in Context. Fix: "the reserved-slug list of the platform plus `acme`" (the DoD's Docs bullet already names the reserved-slug list concretely).

5. **minor** — §5.2 says `AllowAnonymous` is permitted on "the BFF login, logout and back-channel receiver", while §5.5 defines `POST /bff/logout` under the cookie scheme (it signs the current session out and needs its ticket for `id_token_hint`). Fix: drop "logout" from the anonymous list (or state that logout is cookie-authenticated but tolerates an absent session).

6. **minor** — Review flag 19 (§1.2): "`reference`, which must then **leave** the reserved list" where ledger S39 reads "which must then be **added** to the reserved list". Either reading can be argued (`reference` may or may not already be reserved); a doubt only. Fix: state which it is by checking `taxonomy.json`'s reserved list as created by this spec.

7. **minor** — §3.7 `RenameAsync` row: "spec 0012's `SettingsService.Save` calls it post-commit, best effort" — 0012 §6.3 never calls it (see 0012-2). No change needed here if 0012 adds the call; otherwise the row is a dangling cross-reference.

## Spec 0011

1. **major** — `docs/specs/0011-data-access-layer.md` §1.3. `UseTellmaSqlServer` sets "an explicit `Application Name` (`<slug>-web`, `<slug>-migrator`, `<slug>-worker`) on the connection string so EF's injected name and the executor's raw connections share one pool key", while 0010 §3.5 (the owner of connection composition, seam 9) composes the tenant string with `Application Name` = `DeploymentIdentity.DeploymentId`. Two different values defeat the stated purpose (one pool key) and split each tenant's pool in two. Fix: restate 0010's rule verbatim — `Application Name` is `DeploymentIdentity.DeploymentId` for every connection of a host — and delete the `<slug>-web|migrator|worker` list; if per-process discrimination is wanted, propose it to 0010 as the owner.

2. **minor** — §5.2 (`Update` row) and §9.1. The `Update` contract says assigned properties are "editable or server-owned, never write-once (a compose-time `ArgumentException`)" and in the same sentence that `IsActive` — a write-once column — "is the documented case where a server-side action writes a write-once column, and it does so only here". As written the compose-time check rejects the activate action. Fix: state the carve-out in the rule ("never write-once, except `IsActive` on an `IActivatable` when assigned by the platform's activate/deactivate recipe") or expose it as an `UpdateSpec` flag the recipe sets.

3. **minor** — §5.2 (`Purpose` row): "`Maintenance` batches … carry no connect prologue" versus §5.3: "`Maintenance` batches and batches in a `System` scope carry the `System` prologue variant (tags only; `@tm_Guard = 1`)". Fix: one statement — `Maintenance` carries the `System` variant (the tag read must still head the batch for the epilogue's snapshot).

4. **minor** — §7.3. "`TakeAsync` serves callers that hold no batch (spec 0019's enqueue inside `ContributeAsync` when the buffer is empty)" is contradicted two sentences later ("`core.Jobs`, `core.Notifications` take their ids inside the statement … so `INotifier.Notify` and `IJobQueue.Enqueue` are synchronous") and by ledger S27. seams §23 lists `IIdAllocator.TakeAsync` as consumed by 0020, not 0019. Fix: name a real consumer (or "callers outside any batch, e.g. a job handler creating rows outside the pipeline") and drop the enqueue example.

5. **minor** — §13.2 fixture table `fixture.Tasks`. Ledger §2.3/§8 (0011 #17) names the job-entity fixture `fixture.Jobs`, and ledger §1.24 retires `Task` as a type family. Fix: rename to `fixture.Jobs`-style naming that does not collide with the `core.Jobs` stand-in (e.g. `fixture.Widgets` already carries `IJobEntity`, or `fixture.Batches`); avoid `Task`.

6. **minor** — §4.1: "no `ON DELETE CASCADE` except the user-sibling tables spec 0013 names (`core.UserStamps`, `core.UserPreferences`)". 0013 §3.9 and 0020 §… (`FK_NotificationPreferences_UserId → core.Users(Id) ON DELETE CASCADE`) make `core.NotificationPreferences` a third cascading sibling. Fix: list all three (or say "the user-sibling tables of specs 0013 and 0020").

7. **minor** — §5.1 `ITenantDatabase.Linq<TEntity>()` is not in seams §1's `ITenantDatabase` (`Schema`, `Context`, `CreateBatch`); the ledger (§2.3) mentions the `Linq<T>()` escape hatch, and review flag 24 covers it. Owner addition; no consumer restates it. Fix: none in the spec; add the member to seams §1 so the contract files agree.

8. **minor** — §13.2 fixture list omits `fixture.Lookups`, which 0012 §12 says the fixture database "gains" as a `[Cacheable(MaxRows = 50)]` entity for its suite; 0014 §18.2 describes yet another fixture set (see 0014-2). Fix: 0011 owns the fixture schema (seams §23): list `fixture.Lookups` here, or state that sibling specs extend the fixture model and where.

## Spec 0012

1. **major** — `docs/specs/0012-settings-localization-and-cache.md` §5.7 (also §1.1, §1.2, flag 20). A platform provisioning step `core.settings` (`Order = 15`, `Version = 1`) completes a `HasData` placeholder row (`TenantId = 0`, `Name = N''`). seams §18 and 0010 §6.2 list the platform steps as `10 core.bootstrap-administrator` and `20 core.blob-container` only, and seams §18 describes the `core.Settings` `HasData` row as carrying `Name` = tenant name and `PrimaryLanguage` = the distribution default (no placeholder, no step). 0017 §6.3 has already followed 0012 and lists `core.settings` among the steps it runs, so the drift now spans three specs against the owner. Fix: keep the step (a migration cannot know the tenant's name, so the seams' `HasData` shape is unrealisable), but add `15 core.settings` to 0010 §6.2's platform step list and to seams §18, and state the placeholder shape once (here) with 0010 pointing at it.

2. **minor** — §6.3 step 5 ("Warm the writer"). 0010 §3.7 states that `SettingsService.Save` calls `ITenantCatalog.RenameAsync(tenantId, name)` post-commit, best effort, to mirror the display name into `catalog.Tenants.Name`; this spec never mentions the call. Fix: add to step 5 (or a post-commit step 6): "when `Name` changed, call spec 0010's `ITenantCatalog.RenameAsync` after commit; a failure is logged, never surfaced".

3. **minor** — §2.7: "spec 0013's `UserProfileView.FormatVersion` and `AccessSummary.FormatVersion`". Both records are 0015's (seams §13.1, `Tellma.Core.Abstractions.Api`); `AccessSummary` carries `FormatVersion`, `UserProfileView` does not (0013 §2 places the constant on `UserAccess.FormatVersion`). Fix: "spec 0015's `AccessSummary.FormatVersion` and spec 0013's `UserAccess.FormatVersion`", and drop `UserProfileView` unless 0015 adds the member.

4. **minor** — §2.9: `StaleContextException` "members this spec relies on are `Code = "stale-context"` and `Arguments` carrying the dependency names". seams §10 defines `StaleContextException(Dependencies: list<VersionTagDependency>)`. Fix: name `Dependencies` as the member carrying the mismatched names.

5. **minor** — §5.2 `core.Settings`: "no sequence; the row is a `HasData` placeholder". 0011 §1.3 `SequenceConvention` emits `<schema>.sq_<Table>` for "every keyed table" with no opt-out named. Fix: state the opt-out (`Settings` is `Id`-fixed; the convention skips a `CK (Id = 1)` table, or an `[NoSequence]`-style declaration 0011 must then define) so the two specs agree on what the migration contains.

6. **minor** — §5.3 illustration (`public static class GlSettings { … }`). `notation.md` allows a C# illustration only for a distribution author's call site, "never to define a type"; this block defines a class. Five lines, so within the length limit. Fix: show the two `SettingKey<T>` field declarations without the enclosing class, or accept as the declaration site (doubt).

7. **minor** — §3.2 table gives the `permissions` kind the size limit `PermissionsEntries` and no `MaxAge`; 0013 §6.2 sizes the same cache by `AccessOptions.MaxCachedUsers` with a sliding expiration (reported under 0013-2). No change here unless 0013's reading wins, in which case this row must say so.

## Spec 0013

1. **blocking** — `docs/specs/0013-users-roles-and-permissions.md` §8.3. `IAccessGuards.Contribute(batch)` is one `sync` call that must emit "the lock before the writes; L1–L3 after them", yet `IDataBatch` is append-only and the guards are appended around statements another component owns. seams §1.6 confirms two positions — step (6) the applock before the emitter's statements and step (10) L1–L3 after `ContributeAsync` — which one call cannot produce. The three specs also disagree on the caller: this spec says "called by the pipeline (spec 0014)", 0014 §6.7 step 4 says "the executor calls it for every `Persist` batch; the pipeline adds nothing", and 0011 §5.5 step 6 lists "the access guards' application lock" inside "spec 0014's persist assembly". Fix: split the contract into two members (`ContributeLock(batch)` / `ContributeInvariants(batch)`, or `Contribute(batch, stage: AccessGuardStage = Lock | Invariants)`), state that the pipeline calls the first before `Save`/`Update`/`Delete` and the second after the effects and before the post-check, and have 0014 §6.7 and 0011 §5.5 restate that placement.

2. **major** — §6.2 "Store". The `permissions` kind is sized by `AccessOptions.MaxCachedUsers` (10,000) with "sliding expiration `CacheSlidingExpiration`", while 0012 §3.2 (owner of seam 5) sizes it by `TellmaCacheOptions.PermissionsEntries` (50,000) with no `MaxAge`, and seam 5's `VersionedCache` constructor takes `(kind, sizeLimit, maxAge, meters)` — no sliding expiration exists on the base. Review flag 33 acknowledges the split but leaves two specs stating different limits for one cache. Fix: pick one options surface: drop `MaxCachedUsers` and `CacheSlidingExpiration` from `AccessOptions` and read `TellmaCacheOptions.PermissionsEntries` (the seam), or have 0012 §3.2 point the `permissions` row at `AccessOptions` and add a sliding-expiration parameter to `VersionedCache`.

3. **minor** — §7.4 and Appendix A: `THROW 50401, N'Access.CallerInvalid'`. seams §1.6 step (5) and 0011 §5.5/§6.3 (owner of `TellmaSqlErrors` messages) use `N'CallerInvalid'`. The executor maps by number, so the drift is cosmetic, but the message is the code a log carries. Fix: `CallerInvalid`, matching 0011.

4. **minor** — §5.3 and Appendix A: the post-check is "appended through `IDataBatch.Assert(countSpec, arguments, expected = |saved|, 50403, "Access.RowSecurity")`". seams §1.6 step (11) and 0014 §9.3 emit a raw `DECLARE @tm_visible … THROW 50403, N'RowSecurity'` statement; 0011 §6.3's message for 50403 is `RowSecurity`. Fix: use 0011's message `RowSecurity` and either name the mechanism as 0014 does or leave the mechanism to 0014 ("appended by spec 0014 as a `50403` count assertion over `@tb{b}_saved`").

5. **minor** — §9 `IPermissionDriftScanner`: "Spec 0010's migrator invokes `IPermissionDriftScanner.ScanAsync` per tenant database after `migrate`". Neither 0010 §6.1's `migrate` row nor seams §18 lists the scan, and the contract is absent from seams. Fix: add the invocation to 0010 §6.1 (`migrate` … "membership reconciliation, the permission drift report of spec 0013") and the contract to seams §11; otherwise state that the scan is run by `status`, which this spec controls less.

6. **minor** — §3.3: the `UserStamps` row is "re-created by the cold connect path when absent". The prologue of §7.3 inner-joins `UserStamps`, so an absent row resolves `@tm_UserId = NULL` and the caller is refused as an unknown subject; no statement re-creates it. Fix: either delete the sentence (the companion insert of §8.2 and `HasData` are the only writers) or add the re-create statement to the prologue and its failure mode to §7.6.

7. **minor** — §1.2: `CoreFeature` contributes `contribution.Entity<User, UserService<User>>()` and `Entity<Role, RoleService<Role>>()` "(the services are spec 0017's)". If 0017's `CoreFeature` content also registers the same stacks, the composition sees two `StackContributionItem`s for one entity (a §2.6 startup failure in 0014). Fix: state that this spec's contribution lines *are* the registration 0017 relies on, and that 0017 registers nothing for `User`/`Role` (cross-check with 0017 §1).

## Spec 0014

1. **major** — `docs/specs/0014-crud-service-pipeline.md` §3.1, §3.2, §5.3. `DetailsPlan<TEntity, TKey>` (and its `TKey`-erased `DetailsPlan<TEntity>`) is named in `ContributeDetails`, `IDetailsContributor.Contribute`, and §5.3 ("`DetailsPlan.AddExtra`", "the plan's `IdsSource`") but is never defined. seams §3.3 defines it (`Ids`, `Request`, `Context`, `IdsSource: SqlIdentifier`, two `AddExtra` overloads) and seams §23 lists it among 0014's owned `.Crud` types. Fix: add the contract block from seams §3.3 to §7.1 or §13.1 (beside `PersistContext`) with a Members row for `IdsSource` (`@tb{b}_keys` per §5.3 — seams says `@tb{b}_main`; pick one and correct the other).

2. **major** — §1.1 and §18.2: fixture entities `Widget` (with `[WriteOnce] Serial`), `WidgetLine`, `Bucket`, `Gadget` and a `WidgetService` live in `test/shared/Tellma.Testing.Entities`, "shared with spec 0011". 0011 §13.2 (the owner of the fixture schema, seams §23) defines `TellmaFixtureDbContext` inside `test/core/Tellma.Core.IntegrationTests/Data/` with `fixture.Widgets` (`[WriteOnce] [Unique] Subject`), `WidgetParts`, `WidgetPartNotes`, `Nodes`, `Links`, `Tasks`, `Blobs`; no `Bucket`, `Gadget`, `WidgetLine` or shared project exists there, and 0012 §12 adds `fixture.Lookups` to 0011's set. Fix: restate 0011's fixture set and location verbatim and add only what this spec needs (`[Stack(Operations = Read)]` on one existing table, a `WidgetService`), or move the fixture model to `test/shared/Tellma.Testing.Entities` in 0011 §13.2 so the three specs share one schema.

3. **minor** — §6.7 step 4: "`IAccessGuards.Contribute(batch)` … the executor calls it for every `Persist` batch; the pipeline adds nothing". 0013 §8.3 says the pipeline calls it and 0011 §5.5 places it in the pipeline's persist assembly; seams §1.6 needs it at two positions (see 0013-1). Fix: after 0013 splits the contract, state here that the pipeline calls the lock member before step 1 and the invariants member between steps 3 and 5.

4. **minor** — §11.1 fast path declares `@tb{b}_vis` and its own `THROW 50404` pre-check, then calls `IDataBatch.Update`, whose statement (0011 §9.1) already captures `@tb{b}_keys` under the filter and documents the all-or-nothing form "asserts `COUNT(@tb5_keys) = COUNT(@tb5_t0)` with `THROW 50404` before the `UPDATE`". The keys are captured twice per action, and `@tb{b}_vis` is absent from 0011 §1.4's reserved-name list (which is what `TELLMA0003` enforces). Fix: drop the `@tb{b}_vis` block and request the all-or-nothing assertion through `UpdateSpec` (an `AllOrNothing: bool` 0011 must then add, with the missing-ids result set), or ask 0011 to list `@tb{b}_vis`.

5. **minor** — §7.2 illustration (`protected override async ValueTask ValidateAsync(SaveContext<Center, int> c) { … }`): eight lines and a method body, where `spec-style.md`/`notation.md` allow one to five lines of a call site. Fix: cut to the two loader lines (`var parents = await c.Loader.ByIds<Center, int>(…)` and one `c.Errors.Add(i, x => x.ParentId, …)`), or move the rule to prose.

6. **minor** — §8 and §14.2: `ConcurrencyException("Concurrency.Stamp", conflicts)`. `TellmaException.Code` is "the kebab-case problem code" (§14.1, seams §10: `409 concurrency-conflict`), and the same spec passes `"forbidden"` to `ForbiddenException`. `Concurrency.Stamp` is also not among the validation codes of §7.3. Fix: `ConcurrencyException("concurrency-conflict", conflicts)`; if a dotted sub-code is wanted, carry it in `Arguments`.

7. **minor** — §12.1 and §14.2: error 530 → `ValidationException(Tree.TooDeep)`. This agrees with 0011 §6.4 and seams §1.4, but ledger §8 (0014 #10) says "530 → `ConcurrencyException(Tree.TooDeep)` only" and ledger §2.10 says `ConcurrencyException(Tree.Cycle)`. The specs are consistent with each other; the ledger is not. Fix: none in the spec; correct the ledger's two entries to `ValidationException(Tree.TooDeep)`.

8. **minor** — §16.1: `tellma.crud.stale_context.reruns` tag `crud.tag ∈ permissions | settings`. 0012 §2.6 and 0013 §7.3 give `settings` the `Refresh` policy ("never fails the guard"), so a `settings` rerun cannot occur; the value comes from ledger seam 5 and is reported as a doubt. Fix: drop `settings` from the closed set, or document the case that produces it.
