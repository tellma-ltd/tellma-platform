## 1. ASP.NET Core 10 minimal APIs

### 1.1 Platform versions

- **Verified.** `Microsoft.AspNetCore.OpenApi` latest stable is **10.0.11**, published 2026-08-11
  (10.0.10 on 2026-07-14, 10.0.9 on 2026-06-09). `Microsoft.Extensions.Validation` latest stable is
  **10.0.11**, published 2026-08-11, targets net10.0.
  Sources: https://www.nuget.org/packages/Microsoft.AspNetCore.OpenApi ,
  https://www.nuget.org/packages/Microsoft.Extensions.Validation
- **Implication.** The repo's 10.0.9 pin is two patches behind; the OpenAPI and Validation packages
  must be pinned to the same 10.0.x patch line as the framework when spec 0015 adds them.

### 1.2 Route groups (`MapGroup`)

- **Verified.** `MapGroup` returns a `RouteGroupBuilder`; conventions applied to a group
  (`RequireAuthorization`, `WithTags`, `WithMetadata`, `AddEndpointFilter`,
  `AddEndpointFilterFactory`, `CacheOutput`, `RequireRateLimiting`) apply to every endpoint in it.
  Groups nest, and prefixes may carry route parameters and constraints that inner handlers capture
  (`var org = all.MapGroup("{org}"); var user = org.MapGroup("{user}"); user.MapGet("", (string org,
  string user) => ...)`). A group prefix may be empty (used only to attach metadata/filters).
  Filters on an outer group run before filters on an inner group regardless of registration order;
  order matters only among filters on the same group or endpoint. Endpoint names (`WithName`) are
  case-sensitive, globally unique, and become the OpenAPI `operationId`.
  Source: https://learn.microsoft.com/en-us/aspnet/core/fundamentals/minimal-apis/route-handlers?view=aspnetcore-10.0
  (doc dated 2026-04-28).
- **Implication.** A `{tenantId}` prefix group with tenant-resolution, authentication and rate-limit
  conventions attached once, and per-entity sub-groups generated by the platform, is directly
  supported; the distribution adds custom endpoints by mapping onto the same group.

### 1.3 Endpoint filters

- **Verified.** `IEndpointFilter.InvokeAsync(EndpointFilterInvocationContext, EndpointFilterDelegate)`;
  the context exposes `HttpContext` and the positional `Arguments` list (`GetArgument<T>(index)`).
  Multiple filters: code before `next` runs FIFO, code after `next` runs FILO. A filter may
  short-circuit by returning a result (e.g. `Results.Problem(...)`). `AddEndpointFilterFactory`
  receives `EndpointFilterFactoryContext` with the handler's `MethodInfo`, so a factory can inspect
  parameter types and register a pass-through when the signature does not match. Filters "can
  resolve dependencies from DI" but "filters themselves can't be resolved from DI" (they are
  constructed by the framework; constructor parameters are resolved). `AddEndpointFilter` also works
  on `MapControllers()` builders.
  Source: https://learn.microsoft.com/en-us/aspnet/core/fundamentals/minimal-apis/min-api-filters?view=aspnetcore-10.0
  (doc dated 2026-04-28).
- **Implication.** The platform's "connect + permission check + culture/calendar/today negotiation"
  can be endpoint filters attached at the group level; filter factories can inspect handler
  signatures to attach only where a request-body type is present.

### 1.4 `TypedResults` and `Results<T1..T6>`

- **Verified.** `TypedResults` helpers return concrete `IResult` implementations
  (`Microsoft.AspNetCore.Http.HttpResults`) that "automatically provide the metadata for the
  endpoint" (no `.Produces(...)` needed). A handler returning several result types must declare
  `Results<T1, ..., TN>` (up to six) so OpenAPI metadata is retained; the union implements implicit
  conversions and the compiler rejects an undeclared result type. `TypedResults.Problem` and
  `TypedResults.ValidationProblem` produce `ProblemDetails` / `HttpValidationProblemDetails`.
  `TypedResults.ServerSentEvents(IAsyncEnumerable<SseItem<T>>)` is new in .NET 10. File results:
  `TypedResults.File(byte[]|Stream, contentType, fileDownloadName)`, `TypedResults.Bytes`,
  `TypedResults.PhysicalFile`.
  Source: https://learn.microsoft.com/en-us/aspnet/core/fundamentals/minimal-apis/responses?view=aspnetcore-10.0
  (doc dated 2026-06-16); https://learn.microsoft.com/en-us/aspnet/core/release-notes/aspnetcore-10.0
- **Implication.** Platform-generated endpoints should return `Results<Ok<T>, ProblemHttpResult,
  ValidationProblem, NotFound>`-style unions so the OpenAPI document for the public surface is
  correct without hand-written `Produces` metadata; Excel exports return `FileStreamHttpResult`.

### 1.5 Built-in OpenAPI document generation

- **Verified.** Package `Microsoft.AspNetCore.OpenApi`; `builder.Services.AddOpenApi()` /
  `app.MapOpenApi()`. In .NET 10 the default document version is **OpenAPI 3.1** (3.2 becomes the
  default in .NET 11); override with `options.OpenApiVersion = OpenApiSpecVersion.OpenApi3_0`. YAML is
  served by mapping the endpoint with a `.yaml`/`.yml` suffix
  (`app.MapOpenApi("/openapi/{documentName}.yaml")`); build-time YAML is not supported. Multiple
  named documents: `AddOpenApi("v1"); AddOpenApi("v2")`. Document, operation and schema
  transformers exist; the transformer context now exposes `GetOrCreateSchemaAsync` to generate a
  schema for a C# type with the same logic as the generator. XML doc comments (`<summary>`,
  parameter docs) flow into the document when `<GenerateDocumentationFile>true</GenerateDocumentationFile>`
  is set, including XML comments on `[AsParameters]` property types. Nullable complex types and
  collections are emitted with `oneOf` instead of `nullable`; relative `$ref`s are resolved;
  descriptions may sit beside `$ref` (3.1); numbers/dates are formatted with the invariant culture;
  `[ProducesResponseType]` accepts a `Description`. Build-time generation via
  `Microsoft.Extensions.ApiDescription.Server` (runs a `GetDocument` step during `dotnet build`).
  `IOpenApiDocumentProvider` is injectable. The document is regenerated on every request to the
  OpenAPI endpoint ("can be cached to avoid executing the document generation pipeline on each HTTP
  request"). The generator is trimming/Native-AOT compatible.
  Sources: https://learn.microsoft.com/en-us/aspnet/core/fundamentals/openapi/aspnetcore-openapi?view=aspnetcore-10.0
  (doc dated 2026-08-19); https://learn.microsoft.com/en-us/aspnet/core/release-notes/aspnetcore-10.0
- **Not verified.** Whether schema generation honours a source-generated `JsonSerializerContext`
  registered through `ConfigureHttpJsonOptions` for polymorphic `[JsonDerivedType]` hierarchies was
  not confirmed from the docs (the generator uses `JsonSerializerOptions` contract metadata; the
  page does not list polymorphism among limitations, but it does not promise it either).
- **Implication.** The `/api/v1` public surface can publish an OpenAPI 3.1 document from the same
  minimal-API endpoints with no third-party generator; the private `/api/web` surface can be excluded
  by document name or tag. Because the document is rebuilt per request, expose it only behind
  output caching or in non-production environments.

### 1.6 `[AsParameters]` and parameter binding

- **Verified.** `[AsParameters]` "enables simple parameter binding to types and not complex or
  recursive model binding": the properties/constructor parameters of a class, struct or record are
  bound from route/query/header/body/services exactly as if they were handler parameters; a
  `struct` "can be more performant than using a `record` type". `[FromForm]` properties may be used
  on `[AsParameters]` types. Custom binding: static `TryParse(string, IFormatProvider, out T)` for
  route/query/header sources; static `BindAsync(HttpContext[, ParameterInfo])` /
  `IBindableFromHttpContext<TSelf>` for whole-request binding. `[FromHeader(Name = "X-...")]` binds
  headers, including arrays. Binding failures: `TryParse` false → 400; `BindAsync` null → 400;
  `BindAsync` throws → 500.
  Source: https://learn.microsoft.com/en-us/aspnet/core/fundamentals/minimal-apis/parameter-binding?view=aspnetcore-10.0
  (doc dated 2026-07-16).
- **Implication.** A `RequestContext`-style `[AsParameters]` struct (tenant route value +
  `Accept-Language` + calendar/time-zone/today headers + services) can be bound once and passed to
  every generated handler; a `BindAsync` type is the cleanest home for header-negotiation logic.

### 1.7 JSON options for minimal APIs and source generation

- **Verified.** "The body binding source uses System.Text.Json for deserialization. It is not
  possible to change this default", but options are configurable globally with
  `builder.Services.ConfigureHttpJsonOptions(options => options.SerializerOptions...)` and per call
  with `ReadFromJsonAsync(JsonSerializerOptions | JsonTypeInfo<T>)`. Defaults are
  `JsonSerializerDefaults.Web` (camelCase, case-insensitive property matching). Source-generated
  contexts are attached by `options.SerializerOptions.TypeInfoResolverChain.Add(MyContext.Default)`
  (the chain is queried in order; the first non-null contract wins; `TypeInfoResolver` and
  `TypeInfoResolverChain` mirror each other). In .NET 10 "MVC, Minimal APIs, and
  `HttpRequestJsonExtensions.ReadFromJsonAsync` ... use the new Json+PipeReader support without
  requiring any code changes".
  Sources: parameter-binding doc above;
  https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/source-generation
  (doc dated 2025-11-13); https://learn.microsoft.com/en-us/aspnet/core/release-notes/aspnetcore-10.0
- **Implication.** One platform `JsonSerializerContext` (wire envelopes, `FilterTree`, problem
  details) plus one per distribution (its entity wire types) chained through
  `TypeInfoResolverChain` is the supported composition; see §2 for coverage limits.

### 1.8 Built-in validation (new in .NET 10)

- **Verified.** `builder.Services.AddValidation()` enables DataAnnotations validation of minimal-API
  parameters (body, query, header, `[AsParameters]`), for classes and records, "AoT-compatible and
  extensible". It is implemented by a Roslyn source generator in `Microsoft.Extensions.Validation`
  that "only discovers validatable types in the assembly where `AddValidation` is called"; when
  endpoints or their types live in another assembly, that assembly must expose its own extension
  method that calls `AddValidation()` and the host must call it, otherwise "invalid requests are
  processed and return a 200". An endpoint filter is added per endpoint; `DisableValidation()`
  opts an endpoint out. Pipeline: parameter attributes → type properties → type-level attributes →
  `IValidatableObject`. `[ValidatableType]` forces generation for types not reachable from
  handler signatures; `[SkipValidation]` skips a member. Both attributes are **experimental in .NET
  10** (analyzer `ASP0029` in plain `Microsoft.NET.Sdk` class libraries; the docs give suppression
  and an "embedded attribute" workaround; not experimental from .NET 11). Known limitation:
  nullable value-type parameters are not validated in .NET 10 (dotnet/aspnetcore #67033). Errors
  are returned as 400 `HttpValidationProblemDetails` whose `errors` dictionary is keyed by the
  validation path (documented example `Customer.Address.Street`; collection items use index
  notation such as `Items[0].Name` per the `ValidateContext.CurrentValidationPath` source comments).
  The response can be customized through `IProblemDetailsService`
  (`AddProblemDetails(o => o.CustomizeProblemDetails = ...)`). Asynchronous validation
  (`IAsyncValidatableObject`) is .NET 11 only.
  Sources: https://learn.microsoft.com/en-us/aspnet/core/fundamentals/validation?view=aspnetcore-10.0
  (doc dated 2026-08-14); https://learn.microsoft.com/en-us/aspnet/core/release-notes/aspnetcore-10.0 ;
  https://github.com/dotnet/aspnetcore/blob/main/src/Validation/src/ValidateContext.cs
- **Not verified.** Whether error keys use JSON property names (camelCase) or CLR names.
- **Implication.** The built-in validator is a fit for *shape* validation of wire payloads only
  (required, length, range); it runs before the handler, has no DB access, is synchronous in .NET
  10, and cannot express the platform's batched, context-loading validators, which must stay inside
  the service pipeline (spec 0014). Its 400 `errors` dictionary (path → messages) is a natural
  format to reuse for the pipeline's own 422 output so the SPA parses one shape.

### 1.9 Problem details (`IProblemDetailsService`) and RFC 9457

- **Verified.** `AddProblemDetails()` registers the default `IProblemDetailsService`; with it,
  `ExceptionHandlerMiddleware`, `StatusCodePagesMiddleware` and the developer exception page emit
  problem-details responses (unless the `Accept` header excludes them). `IExceptionHandler`
  implementations (`AddExceptionHandler<T>()`, singletons, called in order until one returns true)
  map exceptions to responses; `ExceptionHandlerOptions.StatusCodeSelector` maps exception types to
  status codes; `CustomizeProblemDetails` adds extensions (e.g. `traceId`, `nodeId`). New in .NET
  10: the middleware "no longer writes exception diagnostics for exceptions handled by
  `IExceptionHandler`" (`SuppressDiagnosticsCallback` restores the old behaviour). Default `type`
  URIs point at RFC 9110 sections (e.g. `https://tools.ietf.org/html/rfc9110#section-15.5.1` for
  400). The ASP.NET docs still cite RFC 7807; **RFC 9457 obsoletes RFC 7807**, keeps the
  `application/problem+json` media type and the five members (`type`, `status`, `title`, `detail`,
  `instance`), and says "Clients consuming problem details MUST ignore any such extensions that they
  don't recognize"; it "encourages" resolvable `type` URIs.
  Sources: https://learn.microsoft.com/en-us/aspnet/core/fundamentals/error-handling?view=aspnetcore-10.0 ;
  https://www.rfc-editor.org/rfc/rfc9457.html
- **Implication.** ASP.NET's output is RFC 9457 output. A closed set of platform exception types
  mapped by one `IExceptionHandler` (or a `StatusCodeSelector`) to problem details with a
  Tellma-owned `type` URI per error code is fully supported; the localized message goes in `detail`
  and the machine code in `type`/an extension member, which answers the brain dump's "messages vs
  codes" question with "both".

### 1.10 Rate limiting (`AddRateLimiter`)

- **Verified.** `Microsoft.AspNetCore.RateLimiting` middleware: `AddRateLimiter` + `UseRateLimiter`
  (after `UseRouting` when endpoint-specific policies are used). Four built-in limiters: fixed window
  (`AddFixedWindowLimiter`: `PermitLimit`, `Window`, `QueueLimit`, `QueueProcessingOrder`,
  `AutoReplenishment`), sliding window (`AddSlidingWindowLimiter`, plus `SegmentsPerWindow`), token
  bucket (`AddTokenBucketLimiter`: `TokenLimit`, `TokensPerPeriod`, `ReplenishmentPeriod`),
  concurrency (`AddConcurrencyLimiter`). Partitioned limiters:
  `PartitionedRateLimiter.Create<HttpContext, string>(ctx => RateLimitPartition.GetFixedWindowLimiter(partitionKey, factory))`
  keyed by user, IP, API key or path; `PartitionedRateLimiter.CreateChained(...)` runs several in
  sequence; `options.GlobalLimiter` applies to all endpoints; named policies attach with
  `RequireRateLimiting("name")` on endpoints or groups, `[EnableRateLimiting]`,
  `[DisableRateLimiting]`; `IRateLimiterPolicy<TPartitionKey>` for DI-built policies. Rejection:
  `RejectionStatusCode` (503 unless set; docs set 429) or `OnRejected` writing `Retry-After` from
  `lease.TryGetMetadata(MetadataName.RetryAfter, ...)`. Built-in metrics under
  `Microsoft.AspNetCore.RateLimiting`. The docs warn that partitioning on client-supplied input
  (including IP) is a DoS vector. The page (updated 2026-08-31) lists no .NET 10 additions.
  Source: https://learn.microsoft.com/en-us/aspnet/core/performance/rate-limit?view=aspnetcore-10.0
- **Inferred.** The limiters are `System.Threading.RateLimiting` in-process objects; no distributed
  store is offered or documented, which matches the brain dump's "in-memory, per instance"
  requirement exactly.
- **Implication.** Per-tenant-per-user sliding-window partitions (key = `{tenantId}:{sub}`) with a
  chained per-IP limiter for the unauthenticated MCP discovery endpoints, a 429 with `Retry-After`,
  and a separate concurrency limiter for expensive endpoints (export/import) are all one
  configuration block; payload-size limits are a separate mechanism (§1.11).

### 1.11 Request body size limits

- **Verified.** `KestrelServerLimits.MaxRequestBodySize` "Defaults to 30,000,000 bytes, which is
  approximately 28.6MB"; `null` = unlimited; it "can be overridden per-request via
  `IHttpMaxRequestBodySizeFeature`" but only before the body is read (`IsReadOnly`), otherwise an
  exception is thrown; IIS out-of-process disables Kestrel's limit. `IRequestSizeLimitMetadata`
  (`Microsoft.AspNetCore.Http.Metadata`, in `Microsoft.AspNetCore.Http.Abstractions.dll`) exposes
  `MaxRequestBodySize` and is implemented by `[RequestSizeLimit]` and `[DisableRequestSizeLimit]`
  (both in the `Microsoft.AspNetCore.Mvc` namespace but usable as endpoint metadata).
  Sources: https://learn.microsoft.com/en-us/dotnet/api/microsoft.aspnetcore.server.kestrel.core.kestrelserverlimits.maxrequestbodysize?view=aspnetcore-10.0 ;
  https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/kestrel/options?view=aspnetcore-10.0 ;
  https://learn.microsoft.com/en-us/dotnet/api/microsoft.aspnetcore.http.metadata.irequestsizelimitmetadata?view=aspnetcore-10.0
- **Implication.** Per-surface body limits (small for `/api/web` JSON, larger for import uploads
  and blob staging) are endpoint metadata (`WithMetadata(new RequestSizeLimitAttribute(bytes))`)
  applied per group; entity-count and string-length limits are not a framework feature and belong
  to the wire-shape validation.

### 1.12 Request timeouts

- **Verified.** `AddRequestTimeouts()` / `UseRequestTimeouts()` (after `UseRouting`). Per endpoint
  `WithRequestTimeout(TimeSpan)` / `WithRequestTimeout("policy")` / `[RequestTimeout]`; named
  policies via `options.AddPolicy`; `DefaultPolicy` for endpoints without one. A
  `RequestTimeoutPolicy` has `Timeout`, `TimeoutStatusCode` and `WriteTimeoutResponse`. On timeout
  `HttpContext.RequestAborted` is cancelled; `Abort()` is not called; if the app does not produce a
  response the default status is **504**. `DisableRequestTimeout()` / `[DisableRequestTimeout]`;
  `IHttpRequestTimeoutFeature.DisableTimeout()` cancels a started timeout. "When an app is running
  in debug mode, the timeout middleware doesn't trigger."
  Source: https://learn.microsoft.com/en-us/aspnet/core/performance/timeouts?view=aspnetcore-10.0
- **Implication.** A default policy for the web surface plus a longer one for exports/imports is
  cheap; because the timeout only cancels `RequestAborted`, the batch executor must honour that
  token on the SQL command so a timed-out request does not keep a DB connection busy.

### 1.13 Output caching

- **Verified.** `AddOutputCache()` / `UseOutputCache()` (after `UseCors`, `UseAuthentication`,
  `UseAuthorization`); `CacheOutput()` / `[OutputCache]` on endpoints or groups; policies via
  `AddBasePolicy` / `AddPolicy`. Default policy: "Only HTTP 200 responses are cached. Only HTTP GET
  or HEAD requests are cached. Responses that set cookies aren't cached. Responses to authenticated
  requests aren't cached." (requests carrying an `Authorization` header or an authenticated user are
  skipped). A custom `IOutputCachePolicy` can allow POST. Keys vary by the full URL by default;
  `SetVaryByQuery`, `SetVaryByHeader`, `VaryByValue`; `Tag(...)` plus
  `IOutputCacheStore.EvictByTagAsync`; resource locking (stampede protection) is on by default;
  ETag / `If-None-Match` and `If-Modified-Since` revalidation is automatic. Limits: `SizeLimit` 100
  MB, `MaximumBodySize` 64 MB, `DefaultExpirationTimeSpan` 60 s. The default store is in-process
  memory ("each server has a separate cache"); Redis via
  `Microsoft.AspNetCore.OutputCaching.StackExchangeRedis`.
  Source: https://learn.microsoft.com/en-us/aspnet/core/performance/caching/output?view=aspnetcore-10.0
  (doc dated 2026-06-09).
- **Implication.** Output caching is unusable for the cookie-authenticated, all-POST web surface
  without a custom policy that deliberately caches authenticated POST responses, which would be a
  cross-user data-leak hazard; the only safe consumers are anonymous, tenant-independent GETs
  (`/api/distribution-info`, the OpenAPI document, the MCP protected-resource-metadata document).
  Entity-level caching stays in the version-tag cache designed by spec 0012.

### 1.14 Response compression

- **Verified.** `AddResponseCompression()` / `UseResponseCompression()` ("must be called before any
  middleware that compresses responses"). Default providers in .NET 10 are Brotli and Gzip (Zstandard
  is added in .NET 11), both defaulting to `CompressionLevel.Fastest`; configure with
  `BrotliCompressionProviderOptions` / `GzipCompressionProviderOptions`. `EnableForHttps` "is
  disabled by default because of the security risk" (CRIME/BREACH); the docs say antiforgery tokens
  mitigate BREACH. Default MIME list includes `application/json`; wildcard MIME types are not
  supported. Compression removes `Content-Length`, adds `Vary: Accept-Encoding`; "Don't compress
  files smaller than about 150-1,000 bytes". Kestrel and HTTP.sys have no built-in compression;
  IIS/Azure App Service may compress at the server regardless.
  Source: https://learn.microsoft.com/en-us/aspnet/core/performance/response-compression?view=aspnetcore-10.0
  (doc dated 2026-07-02).
- **Inferred.** BREACH requires attacker-controlled input reflected next to a secret in the same
  compressed response; query results and details payloads contain no session secret, so compressing
  authenticated JSON over HTTPS is the common practice, but it is an explicit `EnableForHttps = true`
  decision that spec 0015 must record with its reasoning (no CSRF token or session identifier may
  ever be reflected in a compressed body).
- **Implication.** Enable Brotli/Gzip for the JSON surfaces (large query results and details
  payloads compress 5–10x); never reflect the antiforgery token into a compressed body.

### 1.15 Antiforgery for minimal APIs; cookie authentication on APIs

- **Verified.** `AddAntiforgery()` / `UseAntiforgery()`; the middleware "does not short-circuit
  the request pipeline", records the verdict in `IAntiforgeryValidationFeature`, and validates only
  POST/PUT/PATCH; automatic enforcement (400) happens only for endpoints that bind forms
  (`IFormCollection`, `[FromForm]`): "JSON API endpoints and handlers that don't consume form data
  are not automatically rejected". `DisableAntiforgery()` opts a form endpoint out; header-based
  validation for SPAs uses `options.HeaderName = "X-XSRF-TOKEN"`, `IAntiforgery.GetAndStoreTokens`
  (request token in a non-HttpOnly cookie) and explicit `IAntiforgery.ValidateRequestAsync(context)`;
  when both header and form carry a token only the header is validated. New in .NET 10: requests to
  "known API endpoints" (marked by `IApiEndpointMetadata`) protected by cookie authentication get
  401/403 instead of login redirects; authentication/authorization metrics were added.
  Sources: https://learn.microsoft.com/en-us/aspnet/core/security/anti-request-forgery?view=aspnetcore-10.0 ;
  https://learn.microsoft.com/en-us/aspnet/core/release-notes/aspnetcore-10.0
- **Implication.** For the cookie-authenticated `/api/web` surface, CSRF protection must be an
  explicit endpoint filter (validate `X-XSRF-TOKEN` via `IAntiforgery.ValidateRequestAsync`, or
  require a custom header plus `SameSite=Lax/Strict` on the session cookie); the framework does not
  protect JSON POSTs by itself. Bearer-authenticated surfaces (`/api/v1`, `/mcp`) need none.

## 2. System.Text.Json in .NET 10

- **Verified — .NET 10 additions.** (a) `[JsonSourceGenerationOptions(ReferenceHandler =
  JsonKnownReferenceHandler.Preserve)]` — source-generated contexts no longer throw on cycles when
  a reference handler is declared; (b) `JsonSerializerOptions.AllowDuplicateProperties = false`
  (also `JsonDocumentOptions`) rejects duplicate JSON properties; (c) `JsonSerializerOptions.Strict`
  preset = `JsonUnmappedMemberHandling.Disallow` + no duplicate properties + case-sensitive property
  names + `RespectNullableAnnotations` + `RespectRequiredConstructorParameters`, read-compatible with
  `Default`; (d) `JsonSerializer.Deserialize(PipeReader, ...)` overloads.
  Source: https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-10/libraries
- **Verified — source-generation coverage.** Since .NET 8 "full support for `required` and
  `init` members has been added" to the source generator (records with `init`/`required` members
  serialize and deserialize); `JsonSourceGenerationOptions` accepts most `JsonSerializerOptions`
  settings at compile time (`PropertyNamingPolicy`, `DefaultIgnoreCondition`,
  `UseStringEnumConverter`, `GenerationMode`, ...); `JsonStringEnumConverter<TEnum>` is the
  AOT-safe enum-as-string converter (the non-generic one "is not supported by the Native AOT
  runtime"); `TypeInfoResolverChain` composes contexts; `JsonSerializerIsReflectionEnabledByDefault=false`
  turns any reflection fallback into an `InvalidOperationException` (and it is off automatically
  under `PublishTrimmed`).
  Known limits: "Source-generation mode supports only `public` or `internal` members and `public` or
  `internal` accessors of `public` properties. If you set `[JsonInclude]` on `private` members or
  accessors and choose source-generation mode, a `NotSupportedException` will be thrown at runtime";
  members declared as `object` need their runtime types listed with `[JsonSerializable]`;
  polymorphism (`[JsonDerivedType]`, `[JsonPolymorphic]`) "is supported in metadata-based source
  generation, but not fast-path source generation"; the `$type` discriminator must be the first
  property unless `AllowOutOfOrderMetadataProperties = true` (which may over-buffer); derived types
  must be declared on the base (`UnknownDerivedTypeHandling` otherwise throws); polymorphic
  configuration on derived types is not inherited.
  Sources: https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/source-generation ;
  https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/source-generation-modes ;
  https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/polymorphism ;
  https://devblogs.microsoft.com/dotnet/system-text-json-in-dotnet-8/
- **Verified — performance vs reflection.** Docs: metadata-mode source generation "eliminates
  runtime metadata collection"; measured "up to 40% or more startup time reduction, private memory
  reduction, throughput speed increase (in serialization optimization mode), and app size
  reduction". The fast path (serialization-optimization mode) "doesn't support asynchronous
  serialization or any mode of deserialization"; streaming (async) serialization "falls back to
  fast-path if the payloads are known to be small enough to fit in the predetermined buffer size";
  the fast path is bypassed (falls back to metadata mode) when unsupported options or attributes are
  present: `Converters`, `DictionaryKeyPolicy`, `Encoder`, `NumberHandling`, `ReferenceHandler`,
  `[JsonConstructor]`, `[JsonConverter]`, `[JsonExtensionData]`, `[JsonNumberHandling]`.
  Sources: source-generation-modes page above; source-generation page above.
- **Implication for the design.** Wire types must be public/internal classes or records with
  public setters or `init`/`required` members (no private setters relying on `[JsonInclude]`);
  the wire `FilterTree` (a discriminated union) should use `[JsonPolymorphic]`/`[JsonDerivedType]`
  with the discriminator first, not a custom converter, so it stays on the source-generated path;
  query results as arrays of arrays of `object` require every scalar runtime type (string, int,
  long, decimal, bool, DateTime/DateOnly, byte[], Guid ...) to be declared `[JsonSerializable]`, or
  better a hand-written `Utf8JsonWriter` emitter for the row grid (custom converters are legitimate
  there, they only forfeit the fast path for that one type). ASP.NET's response writing is async, so
  the metadata-mode benefit (no reflection, AOT-safe) is the realistic gain, not the fast path.

## 3. The Model Context Protocol as of 2026-09

### 3.1 Revisions

- **Verified.** Current protocol revision: **2026-07-28** (released July 28, 2026). Prior revisions:
  2025-11-25, 2025-06-18, 2025-03-26, 2024-11-05. Version strings are `YYYY-MM-DD` of the last
  backwards-incompatible change. Features are Active → Deprecated (minimum twelve-month window, or
  ninety days under the expedited exception) → Removed. All Tier-1 SDKs (TypeScript, Python, Go, C#)
  shipped 2026-07-28 support on release day.
  Sources: https://modelcontextprotocol.io/specification/versioning ;
  https://blog.modelcontextprotocol.io/posts/2026-07-28/ ;
  https://modelcontextprotocol.io/specification/2026-07-28/changelog

### 3.2 Headline changes in 2026-07-28 (vs 2025-11-25)

- **Verified** (all from the changelog and the transport/versioning pages):
  1. **Stateless core.** The `initialize`/`notifications/initialized` handshake and the
     `Mcp-Session-Id` header are removed. Every request carries `_meta` with
     `io.modelcontextprotocol/protocolVersion`, `io.modelcontextprotocol/clientCapabilities`, and
     SHOULD carry `io.modelcontextprotocol/clientInfo`; results SHOULD carry
     `io.modelcontextprotocol/serverInfo`. `server/discover` is a mandatory RPC returning
     `supportedVersions`, `capabilities`, `instructions`, server identity, `ttlMs`/`cacheScope`.
     Servers reject unknown versions with `UnsupportedProtocolVersionError` (-32022) listing
     `supported` versions.
  2. **Header routing.** Every POST MUST carry `MCP-Protocol-Version`, `Mcp-Method` (all requests)
     and `Mcp-Name` (`tools/call`, `resources/read`, `prompts/get`); servers MUST reject mismatches
     with HTTP 400 and JSON-RPC `HeaderMismatch` (-32020). Tool parameters may be mirrored into
     `Mcp-Param-{name}` headers via an `x-mcp-header` schema extension (primitive, statically
     reachable properties only; never sensitive values); clients MUST support it.
  3. **Multi Round-Trip Requests (MRTR)** replace server-initiated requests: a server returns
     `resultType: "input_required"` with `inputRequests` (elicitation/sampling/roots) and an opaque
     `requestState`; the client retries the original request (new id) with `inputResponses` and the
     echoed `requestState`. Servers MUST integrity-protect `requestState` when it influences
     authorization or logic (HMAC/AEAD), SHOULD bind it to the principal, a TTL and the originating
     request, and MUST NOT send input requests the client did not declare capability for. Every
     result carries a required `resultType` (`"complete"` | `"input_required"`).
  4. **Streams.** The GET SSE endpoint, `resources/subscribe`/`unsubscribe`, SSE resumability
     (`Last-Event-ID`) and `ping`/`logging/setLevel`/`notifications/roots/list_changed` are removed;
     a `subscriptions/listen` POST opens one long-lived stream for opted-in change notifications;
     request-scoped notifications (`notifications/progress`, `notifications/message`) flow only on
     that request's response stream; closing the stream is the cancellation signal.
  5. **Cacheable lists.** `tools/list`, `prompts/list`, `resources/list`, `resources/read`,
     `resources/templates/list` MUST return `ttlMs` and `cacheScope` (`public`|`private`); tools
     SHOULD be returned in deterministic order.
  6. **Schemas.** `inputSchema`/`outputSchema` accept any JSON Schema 2020-12 keywords (with
     `$ref` resolution and composition bounds); `structuredContent` may be any JSON value.
  7. **Tasks** moved out of core into the `io.modelcontextprotocol/tasks` extension
     (`tasks/get` polling, `tasks/update`, `tasks/cancel`; `resultType: "task"`); a formal
     `extensions` field appears in both capability objects; OpenTelemetry `traceparent`/`tracestate`/
     `baggage` `_meta` keys are documented.
  8. **Deprecated:** Roots, Sampling, Logging features; HTTP+SSE transport; DCR as a registration
     mechanism (in favour of CIMD). Error-code allocation policy: -32020..-32099 reserved for the
     spec.
  9. **Authorization hardening:** RFC 9207 `iss` (AS SHOULD emit, clients MUST validate when
     present or advertised), `application_type` required in DCR, client credentials keyed by
     issuer.
  Sources: https://modelcontextprotocol.io/specification/2026-07-28/changelog ;
  https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http ;
  https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning ;
  https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr ;
  https://modelcontextprotocol.io/specification/2026-07-28/server/discover
- **Implication.** A Tellma MCP endpoint can be fully stateless per request — the same shape as the
  web API (tenant from the route, user from the bearer token, no server-side session), and
  `Mcp-Method`/`Mcp-Name`/`Mcp-Param-*` headers let rate limiting and telemetry key on tool names
  without parsing bodies. Confirmations for destructive tools use MRTR elicitation (with a signed
  `requestState` bound to `sub`), not sessions.

### 3.3 Changes introduced by 2025-11-25 (still relevant)

- **Verified.** OIDC Discovery 1.0 accepted for AS metadata; CIMD added as the recommended
  registration mechanism (SEP-991); incremental scope consent through `WWW-Authenticate`
  (SEP-835); tool-name guidance (SEP-986); URL-mode elicitation (SEP-1036); `ElicitResult`/enum
  schema updates; icons on tools/resources/prompts; JSON Schema 2020-12 as the default dialect;

  `Origin`; experimental tasks (SEP-1686).
  Source: https://modelcontextprotocol.io/specification/2025-11-25/changelog

### 3.4 Authorization (2026-07-28 text)

- **Verified — roles and MUSTs.** "A protected MCP server acts as an OAuth 2.1 resource server."
  Authorization servers MUST implement OAuth 2.1. MCP servers MUST implement RFC 9728 Protected
  Resource Metadata whose document MUST include `authorization_servers`; discovery is either the
  `WWW-Authenticate: Bearer resource_metadata="..."` parameter on a 401 or the well-known URI, tried
  first at the path of the MCP endpoint (`https://example.com/.well-known/oauth-protected-resource/public/mcp`
  for `https://example.com/public/mcp`) then at the root; clients MUST support both. AS metadata
  discovery: RFC 8414 (`/.well-known/oauth-authorization-server`) or OIDC discovery; for issuers
  with a path clients MUST try, in order, `/.well-known/oauth-authorization-server/{path}`,
  `/.well-known/openid-configuration/{path}`, `/{path}/.well-known/openid-configuration`; the
  document's `issuer` MUST equal the issuer used to build the URL. RFC 9728 §3 itself: "any
  terminating slash following the host component MUST be removed before inserting `/.well-known/`
  and the well-known URI path suffix between the host component and the path", and the returned
  `resource` MUST be identical to the resource identifier.
- **Verified — client registration.** Clients MUST obtain a client id by one of three mechanisms and
  SHOULD prefer, in order: pre-registered credentials → CIMD (when the AS metadata has
  `client_id_metadata_document_supported: true`) → DCR (when `registration_endpoint` exists) →
  prompt the user. AS and clients SHOULD support CIMD; MAY support DCR ("deprecated ... retained
  for backwards compatibility"). CIMD: `client_id` is an HTTPS URL with a path whose document
  contains at least `client_id`, `client_name`, `redirect_uris`; the AS SHOULD fetch it on seeing a
  URL-formatted `client_id`, MUST check the document's `client_id` equals the URL, MUST validate
  redirect URIs exactly against the document, SHOULD cache per HTTP headers, MUST guard against
  SSRF, MUST show the `client_id` hostname / redirect hostname on the consent screen and SHOULD warn
  for localhost-only redirect URIs; the IETF draft (draft-ietf-oauth-client-id-metadata-document-00,
  2025-10-08) forbids client secrets in CIMD (auth method `none` or `private_key_jwt` with
  `jwks_uri`), recommends a 5 KB size cap and domain trust policies.
- **Verified — tokens.** Clients MUST send RFC 8707 `resource` = the canonical MCP server URI
  (`https://mcp.example.com/mcp`, or a path form "when path component is necessary to identify
  individual MCP server"; no trailing slash, no fragment) in both authorization and token requests,
  "regardless of whether authorization servers support it"; servers MUST validate the token was
  issued for them (audience) and MUST reject others; tokens travel only in `Authorization: Bearer`;
  token passthrough is forbidden; invalid/expired tokens → 401; insufficient scope → 403 with
  `WWW-Authenticate: Bearer error="insufficient_scope", scope="...", resource_metadata="..."`, and
  servers SHOULD list all scopes needed for the operation in one challenge; 401 challenges SHOULD
  include `scope`; PRM `scopes_supported` is the minimal set; `offline_access` must not be in either.
  PKCE: clients MUST use S256 and MUST refuse to proceed when `code_challenge_methods_supported` is
  absent from AS metadata (OIDC providers MUST therefore include it). Refresh tokens MUST be rotated
  for public clients; access tokens SHOULD be short-lived; redirect URIs MUST be `localhost` or
  HTTPS and exactly registered.
- **Verified — machine clients.** The core spec acknowledges "Clients acting on their own behalf
  (`client_credentials` clients)" in the step-up flow. The `modelcontextprotocol/ext-auth`
  repository publishes two extensions: **Enterprise-Managed Authorization** (stable; identity
  assertion JWT authorization grant, "ID-JAG") and **Client Credentials** (draft; OAuth
  `client_credentials` grant signalled through PRM/AS metadata).
  Sources: https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization ;
  https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery ;
  https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration ;
  https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations ;
  https://www.rfc-editor.org/rfc/rfc9728.html ;
  https://datatracker.ietf.org/doc/html/draft-ietf-oauth-client-id-metadata-document-00 ;
  https://github.com/modelcontextprotocol/ext-auth
- **Implication.** With one MCP endpoint per tenant at `/{tenantId}/mcp`, the RFC 8707 resource
  identifier is `https://<slug>.app.tellma.com/{tenantId}/mcp` and the PRM document lives at
  `https://<slug>.app.tellma.com/.well-known/oauth-protected-resource/{tenantId}/mcp` (path
  insertion) — one registered resource per tenant, so a token for tenant A cannot be replayed at
  tenant B. The identity server must accept and echo `resource` into `aud`, advertise
  `code_challenge_methods_supported: ["S256"]`, and rotate refresh tokens for public clients.
  Autonomous agents should be a separate confidential client per service account using
  `client_credentials` (draft extension or plain bearer via a headers helper), not a user flow.

### 3.5 Transport details that constrain hosting

- **Verified.** One POST endpoint; clients send `Accept: application/json, text/event-stream`;
  the server answers each request with either a JSON object or a request-scoped SSE stream and
  SHOULD send `X-Accel-Buffering: no` on SSE; notifications get `202 Accepted`. Servers MUST
  validate `Origin` (403 on invalid). A 2026-07-28-only server SHOULD answer GET/DELETE with 405 and
  ignore `Mcp-Session-Id`/`Last-Event-ID`. A server MAY be "dual-era": requests carrying modern
  `_meta` are served statelessly, an `initialize` request selects legacy semantics scoped to a
  session, and both may be served concurrently on one endpoint; a server that supports pre-2025-06-18
  clients MAY treat a missing `MCP-Protocol-Version` as `2025-03-26`.
  Sources: streamable-http and versioning pages above.
- **Implication.** Serving legacy (session-based) clients on Azure requires session affinity or a
  session-migration store; serving only 2026-07-28 clients needs neither. Which clients still speak
  legacy is a client-by-client question (§5.4).

### 3.6 Tools

- **Verified.** Tool fields: `name`, `title`, `description`, `icons`, `inputSchema` (MUST be a
  valid JSON Schema object; for no parameters use `{ "type": "object", "additionalProperties":
  false }`), `outputSchema`, `annotations`, `_meta`. Names SHOULD be 1–128 chars from
  `A-Z a-z 0-9 _ - .`, case-sensitive, unique within a server; aggregating clients may prefix with
  a server identifier. Annotations `readOnlyHint`, `destructiveHint`, `idempotentHint`,
  `openWorldHint` are hints that clients "MUST consider ... untrusted unless they come from trusted
  servers". If `outputSchema` is declared, `structuredContent` MUST conform and the server SHOULD
  also return the serialized JSON as a text block. Input validation and business errors are tool
  execution errors (`isError: true`) so the model can self-correct; unknown tool / malformed request
  are JSON-RPC protocol errors. The tool set "MUST NOT vary per-connection", "MAY vary by the
  authorization presented on the request — for example, returning only the tools the caller's
  granted scopes permit", and SHOULD be in deterministic order. Stateful tools use explicit
  server-minted handles passed as ordinary arguments; "for authenticated servers, a handle is a
  name, not a capability" — authorization must be re-checked per call. Servers MUST validate inputs,
  implement access controls, rate-limit tool invocations, sanitize outputs. Pagination is opaque
  cursor based; page size is server-determined; invalid cursors → -32602.
  Sources: https://modelcontextprotocol.io/specification/2026-07-28/server/tools ;
  https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/pagination
- **Implication.** Per-permission tool lists are spec-legal (the tool set may depend on the
  bearer's authorization) but per-session lists are not — so hide tools by evaluating the user's
  permissions on each `tools/list`, deterministically ordered, and keep `ttlMs` short. Every tool
  must carry the four annotations; queries are `readOnlyHint: true`, saves `destructiveHint: false`
  + `idempotentHint: false`, deletes `destructiveHint: true`.

### 3.7 Elicitation (form and URL modes) under MRTR

- **Verified.** Form mode collects a flat object of primitives (string with `format`
  email/uri/date/date-time, number/integer, boolean, single/multi-select enums, defaults); nested
  objects are intentionally unsupported; servers MUST NOT request secrets through form mode. URL
  mode sends the user to a URL out of band (payments, third-party OAuth, sensitive input); the client
  MUST show the full URL and obtain consent; the server MUST verify that the user opening the URL is
  the same `sub` that triggered the elicitation (anti-phishing), and URL mode "is not for authorizing
  the MCP client's access to the MCP server". Client capability
  `elicitation: { form: {}, url: {} }` is declared per request in `_meta`; servers MUST NOT send
  modes the client did not declare. Results are `accept` (with `content` in form mode) / `decline` /
  `cancel`.
  Source: https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation
- **Implication.** "Are you sure? This will delete 1,204 records" is a form-mode elicitation with
  a boolean; step-up authentication for sensitive operations (spec 0003's `insufficient_user_authentication`)
  can be surfaced to agents as URL-mode elicitation pointing at the identity server, correlated by
  `requestState`.

### 3.8 Tasks (extension)

- **Verified.** `io.modelcontextprotocol/tasks` lets a `tools/call` return `resultType: "task"`
  with a durable task id; clients poll `tasks/get`, feed input through `tasks/update`, cancel with
  `tasks/cancel`; the C# SDK ships it as `ModelContextProtocol.Extensions.Tasks` and notes the
  extension "is not wire-compatible between v1 and v2".
  Sources: https://modelcontextprotocol.io/specification/2026-07-28/changelog ;
  https://github.com/modelcontextprotocol/ext-tasks ;
  https://devblogs.microsoft.com/dotnet/announcing-v20-of-the-official-mcp-csharp-sdk/
- **Implication.** Long imports/exports (spec 0019 background tasks) map naturally onto the tasks
  extension: the tool returns a task handle backed by the platform's task row; polling reads the
  same row. Adopt only after the extension stabilises; a plain "start job" + "get job status" tool
  pair is the fallback.

### 5.3 What the platform identity server must do (derived)

1. **Verified-by-API.** Register one resource per tenant MCP endpoint (`RegisterResources(new
   Uri("https://<slug>.app.tellma.com/{tenantId}/mcp"))`, or, once 8.0 ships, dynamic resources)
   and grant each MCP client the `rsrc:` permission for it; in the authorization endpoint copy the
   requested `resource` values into `SetResources` so `aud` equals the MCP server URI the SDK's
   `AddJwtBearer(ValidAudience = ...)` validates. Because `RegisterResources` is static
   configuration in 7.x, per-tenant resources for a multi-live distribution either use a
   distribution-wide resource (`https://<slug>.app.tellma.com/mcp`, tenant enforced from the token's
   membership) or wait for 8.0's `IOpenIddictResourceManager` — **a design decision for T1/T6**.
2. **Verified-by-API.** Serve nothing for PRM on the identity server; the distribution serves it
   through `AddMcp(ResourceMetadata)` (§4). The identity server only needs discovery (already
   emitted) and PKCE S256 (already advertised).
3. **Inferred.** With neither DCR nor CIMD in OpenIddict 7.6, every MCP client must be
   **pre-registered** on the identity server (public native or web applications with exact redirect
   URIs from §5.4), and the users must supply that client id on their side. Implementing CIMD is a
   bounded custom extension (an application-store decorator that materialises URL client ids by
   fetching, validating and caching the document; plus emitting `client_id_metadata_document_supported`)
   and is the standards-track direction; implementing DCR is larger (registration endpoint, secrets,
   management API) and is deprecated by MCP, so if only one is built it should be CIMD. OpenIddict
   8.0 (milestone `8.0.0-preview.4`) is the first place DCR may land natively.
4. **Verified.** Loopback clients (Claude Code, Codex, Cursor desktop) must be registered as
   `ApplicationTypes.Native` with the port-less loopback redirect URIs so OpenIddict's relaxed match
   accepts the ephemeral port.

## 6. MCP tool-set design for large applications

- **Verified — vendor guidance (Anthropic).** "More tools don't always lead to better outcomes";
  build "intent-based tools consolidating multiple operations" rather than 1:1 API wrappers
  (`schedule_event` instead of `list_users` + `list_events` + `create_event`;
  `get_customer_context` instead of three getters); namespace by service and resource
  (`asana_projects_search`); return semantic identifiers instead of UUIDs; add a
  `response_format` enum (`concise` | `detailed`; measured ~65% token reduction); implement
  pagination, range selection, filtering and truncation with defaults; description quality "can
  yield dramatic improvements"; evaluate with realistic multi-step tasks. Claude Code caps a tool
  result at **25,000 tokens** by default (`MAX_MCP_OUTPUT_TOKENS`; warning at 10,000; a tool may
  declare `anthropic/maxResultSizeChars` up to 500,000 chars). The "code execution with MCP"
  article measures 150,000 → 2,000 tokens (98.7%) by loading tool definitions on demand and
  recommends progressive disclosure / `search_tools` with a detail-level parameter.
  Sources: https://www.anthropic.com/engineering/writing-tools-for-agents ;
  https://www.anthropic.com/engineering/code-execution-with-mcp ; https://code.claude.com/docs/en/mcp
- **Verified — numbers from Anthropic platform docs.** "Claude's ability to pick the right tool
  degrades once you exceed 30–50 available tools"; a typical five-server setup costs ~55k tokens of
  definitions; tool search reduces that by >85% by loading the 3–5 tools needed; use tool search
  when there are 10+ tools or >10k tokens of definitions; keep the 3–5 most used tools non-deferred;
  "Use consistent namespacing in tool names: prefix by service or resource ... so one search matches
  the whole group"; up to 10,000 deferred tools per request. Claude Code / Agent SDK: tool search is
  on by default; `ENABLE_TOOL_SEARCH=auto` activates it when deferrable definitions reach **10%** of
  the model's context window (`auto:N` customises), "50 tools can use 10-20K tokens", five tools per
  search, MCP tools may be exempted with `alwaysLoad`.
  Sources: https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool ;
  https://code.claude.com/docs/en/agent-sdk/tool-search
- **Verified — spec-level affordances.** Tool names ≤128 chars with `.` allowed (dotted
  namespaces like `admin.tools.list` are the spec's own example); `tools/list` may vary by the
  caller's authorization; deterministic ordering and `ttlMs` enable client-side caching; input
  validation errors go back as `isError` text so the model can retry (§3.6).
- **Community-reported, not primary-verified.** Cursor's ~40 active-tool ceiling (forum threads
  2025–2026); "quality degrades around 40–50 always-loaded tools" measurements in third-party posts.
- **Implication.** A per-tenant Tellma server should expose on the order of ten to twenty
  intent-oriented tools (e.g. `tellma.schema.describe`, `tellma.entities.query`,
  `tellma.entities.get`, `tellma.entities.save`, `tellma.entities.delete`, `tellma.actions.run`,
  `tellma.import`, `tellma.export`, `tellma.me`), with entity discovery inside `describe` rather
  than one tool per entity, `readOnlyHint` set correctly so hosts can auto-approve reads, a
  `format: concise|detailed` argument and hard result caps well under 25k tokens, and names prefixed
  `tellma.` so hosts that aggregate many servers still group them; per-permission filtering keeps
  the list short and honest.

## 7. Public REST API versioning (the seam only)

- **Verified.** `Asp.Versioning.Http` latest stable **10.2.3**, published 2026-08-22 (10.2.2 on
  08-12, 10.2.1/10.2.0 on 08-06, 10.0.1 on 07-30, 10.0.0 on 2026-04-21); targets net10.0; depends on
  `Asp.Versioning.Abstractions ≥ 10.2.1`. `Asp.Versioning.OpenApi` **10.2.3** stable (2026-08-22)
  integrates with the built-in `Microsoft.AspNetCore.OpenApi` (≥ 10.0.10): `app.MapOpenApi().WithDocumentPerVersion()`
  emits `/openapi/v1.json`, `/openapi/v2.json`; `AddApiExplorer` is required and the
  `Asp.Versioning` namespace's `AddOpenApi()` must be called after versioning. Minimal-API usage:
  `app.NewVersionedApi()` / `NewApiVersionSet()`, `MapGroup("api/v1/users").HasApiVersion(1.0)`,
  `UrlSegmentApiVersionReader` with `{version:apiVersion}` route tokens. 10.x breaking changes from
  8.x: analyzers on by default (AV0012/AV0018/AV0019 are errors), several extension methods became
  properties, `AddApiVersioning()` registers `IHttpContextAccessor`; 10.2.0 adds versioned-model
  member filtering and gRPC preview.
  Sources: https://www.nuget.org/packages/Asp.Versioning.Http ; https://www.nuget.org/packages/Asp.Versioning.OpenApi ;
  https://github.com/dotnet/aspnet-api-versioning/releases ;
  https://devblogs.microsoft.com/dotnet/api-versioning-in-dotnet-10-applications/ (2026-04-28)
- **Implication.** The `/api/v1` seam is a URL-segment version set on a route group; the private
  `/api/web` surface is unversioned and excluded from the versioned API explorer. Nothing in the
  web-surface design needs to change for versioning to be added later, provided endpoint projection
  emits onto a caller-supplied `RouteGroupBuilder`.

## 8. Findings most likely to change a design decision

1. MCP 2026-07-28 is stateless (no sessions), so a per-tenant `/{tenantId}/mcp` endpoint is one
   ordinary authenticated POST route; per-request tool filtering by permission is spec-legal,
   per-session variation is not.
2. The C# SDK 2.2.0 serves PRM and the 401 challenge itself (`AddMcp`), with `MapMcp(pattern)`
   accepting route parameters, request filters exposing `HttpContext`/`User`, and hybrid session
   mode for legacy clients.
3. OpenIddict 7.6.1 has RFC 8707 resources and PKCE/`iss` metadata but **no PRM, no DCR
   (8.0-preview.4 milestone), no CIMD**; every MCP client must be pre-registered unless Tellma adds
   CIMD; loopback clients must be `Native` applications. RFC 8707 resources are static
   (`RegisterResources`) in 7.x — per-tenant audiences need 8.0 dynamic resources or a
   distribution-wide resource.
4. Client asymmetry: Claude Code/hosted Claude/ChatGPT/Codex prefer CIMD (hosted Claude and Codex
   require `token_endpoint_auth_methods_supported` to include `none`); Cursor is DCR-or-static only;
   hosted Claude cannot do machine-to-machine.
5. ASP.NET's built-in minimal-API validation is shape-only, source-generated per assembly, and
   returns a path-keyed 400 `errors` dictionary — reuse the shape, not the mechanism, for 422s.
6. Output caching cannot serve authenticated POST responses safely; response compression over HTTPS
   is opt-in and must be justified; antiforgery does not cover JSON POSTs automatically.
7. `System.Text.Json` source generation excludes private members and custom converters from the
   fast path and requires runtime types of `object` members to be declared — the array-of-arrays
   grid needs a hand-written writer or an explicit scalar type list.
