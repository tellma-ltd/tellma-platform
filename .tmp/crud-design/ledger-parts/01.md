## 1. Consolidated critique of the brain dump

### 1.1 The general design

The brain dump's direction survives intact: plumbing in the platform, every API bulk-shaped, one save emitter and one multi-statement executor, app-assigned ids, Queryex as the one expression language, staged caching by version tags, a tenant MCP server designed from day one, and three separate API surfaces with different compatibility promises. Ten themes examined it from three lenses and none proposed replacing any of these. What changed is the machinery underneath, in five places where the draft as written would not have worked on SQL Server or would have been unsafe.

1. **The transaction boundary.** "Start the transaction … validate … save … commit" holds a transaction across two round trips and across C# code. Under read-committed snapshot (the Azure SQL default, and now a tenant-database invariant the migrator sets) that protects nothing against write skew; on-prem it holds locks while C# runs. The transaction now lives entirely inside the text of the persist round trip (`SET XACT_ABORT ON; BEGIN TRAN … COMMIT`), and every decision that needs in-transaction semantics — connect guards, the concurrency check, the row-security post-check, tree integrity, the lockout invariant — is a T-SQL assertion that aborts the batch.

2. **"Upsert" and MERGE.** Two MERGE defects survive on SQL Server 2022 (temporal targets with an indexed history table; DELETE actions under indexed views) and the security tables are exactly temporal. The emitter writes separate `UPDATE`/`INSERT`/`DELETE` statements against two TVPs per table (new rows, existing rows); app-assigned ids remove the upsert race, and "update a row somebody deleted" is a conflict, not a silent resurrection.

3. **The connect call.** DB call #1 before every request doubles the cost of every read. The connect step now rides the first business round trip as SQL guards (user active, permissions tag, settings tag) that `THROW` before any business statement runs, so a deactivated user or a stale permission set never sees a row and never commits a write; the cold path is one dedicated round trip per user per instance. The optimistic run-then-discard variant the orchestrator hinted at was rejected because a read would execute under stale permissions and a write could commit under them.

4. **Blobs.** Option 1 (staged upload, token on the record, sweep) wins, and it removes the brain dump's pipeline steps 10 and 12 entirely: blob bytes are written before any transaction exists; deletion is a state flip inside the transaction plus a background sweep. The pipeline has no pre-commit non-transactional step and no post-commit blob deletion.

5. **Background work.** The draft had no attempt counter, no poison state, no retry backoff, no cancellation, no checkpoint, no overlap policy, and sized leases from duration estimates. The machinery now uses a sliding lease renewed at one fifth of its length, a fencing token on every write, at-least-once delivery with idempotent or checkpointed handlers, dead-lettering after five attempts, and per-schedule misfire and overlap policies with a global gap safeguard.

### 1.2 The detailed choices

- **Two audit vocabularies** (`SavedAt/SavedById` + period on temporal rows, four columns elsewhere) become one: `CreatedAt`, `CreatedById`, `ModifiedAt`, `ModifiedById` on every top-level entity, system-versioning as an additive `[Temporal]` capability. `ModifiedAt` is not redundant with `ValidFrom`: it is the concurrency token, it is an app-visible column that rides the UDTT (period columns are EF 10 shadow properties and cannot), and it never moves on bookkeeping. Child entities carry no audit columns and no `SavedById`: a child change stamps its root.
- **Singular table names** (`core.User`) contradict ARCHITECTURE.md's `gl.Invoices` and spec 0001's `InvoicesList`; tables are plural, CLR classes and Queryex entity names singular. `TenantConfigurationKV` becomes `core.SettingEntries`; `UserSettings` becomes `core.UserPreferences` (settings belong to the tenant, preferences to the person); `CenterType` keeps its name (`Type` collides with `System.Type` and reads badly in Queryex); "version tag" replaces version/etag/fingerprint and "format version" replaces "metaversion"; "securable" is the term for `(resource, action)`; the inbox row is a `Notification`.
- **`core.User` mixes three kinds of state.** Editable profile columns, invitation bookkeeping the tenant learns from the identity server, and churn (activity, tags, inbox tracking). The churn moves to the non-temporal sibling `core.UserStamps`; the invitation columns become server-owned columns on the temporal row (`State`, `InvitedAt`, `InvitationOutcome`, `InvitationError`, `ActivatedAt`); the six-state invitation model collapses to the three states the tenant can own (`New`, `Invited`, `Active`), everything finer being a live drill-down of the identity server's delivery-status API and never stored.
- **`ImageFitJson`** is dropped: the client crops before upload, the server produces fixed variants, blobs are immutable by id. `ImageId` becomes a `uniqueidentifier` foreign key to `core.Blobs`.
- **`Center.IsLeaf` and `Level`** are derivable (`SubtreeCount = 1`, `level(Node)`) and are dropped; `SubtreeCount`/`ActiveSubtreeCount` stay because the tree view needs expanders for every rendered row. `Service | Operation | Sale` misses the two grouping types the legacy schema relied on; the enum is `Abstract, BusinessUnit, Service, Operation, Sale` with the rule that only the first two may have children.
- **`hierarchyid` cannot ride a TVP** without `Microsoft.SqlServer.Types`; `Node` is a shadow column excluded from the UDTT, computed in SQL as the path of ids, in the same transaction.
- **"Reserve ids every time … large ranges cause gaps"** dissolves once reservation is exact (the save's deficit), rides a round trip the save already makes, and leftovers stay in a bounded in-process buffer.
- **`RowVersion`** is rejected as the concurrency token for the reason the draft gives (it moves on bookkeeping); `ModifiedAt`, server-stamped and strictly increasing per row, is the token, and the guard travels in the existing-rows TVP's own `ModifiedAt` column — no second `(Id, ExpectedStamp)` TVP.
- **Two UDTTs for write-once columns** is the rejected `ForSave` pattern; one row image, `[WriteOnce]`/`[ServerOwned]` ownership markers the emitter honours, and a validation error when a client changes a write-once value.
- **`X-Today`** is the wrong primitive: a client clock is a second source of truth. `today()` is the tenant's business date; the request's time zone (`Tellma-Time-Zone`) formats instants only.
- **"Permissions read before executing any API call"** becomes tags read inside the first batch and asserted in the persist batch; **"the cache versions of the user stuff live in the User table"** becomes `core.UserStamps`; tenant tags live in `core.VersionTags`, non-temporal, app-generated GUIDs.
- **Public permissions**: `IsPublic` on `Role` (memberships refused) reuses the whole role editor and validator; a `Public` role is seeded as a convenience, never referenced by id in code.
- **"TenantRegistry" storing connection strings** is split into the `catalog` schema (locations and state, never secrets), a credential-profile template in configuration, and `ITenantRegistry` reads; no database ever holds a password.
- **"MERGE", "SqlBatch", "TransactionScope"** all lose to concatenated text on one `SqlCommand` walked with `NextResult()`, which is what spec 0008's `BatchOrdinal` was designed for.
- **Save takes one entity** contradicts the guiding principle; save takes an array everywhere and the UI sends an array of one.
- **All-POST web surface** is adopted and made the CSRF story (`Tellma-Client` header + origin check); REST verbs are reserved for the public `v1` surface. ARCHITECTURE.md changes accordingly.
